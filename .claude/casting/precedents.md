# 判例台帳

「観点の配役」フレームワークの判例台帳（git 追跡・追記型）。判例が積まれるほど、主に上げるべき論点は減っていく。

## 書式

1判例1ブロック。見出しは「日付＋論点1行」、本文は次の4フィールドを箇条書きで書く。

- **観点**: 観点カタログ（`~/.claude/plugins/marketplaces/*/plugins/casting/catalog/catalog.md`）にある観点名で書く。複数の観点が絡む判例は「、」で区切って並べる。当てはまる観点が無ければ「カタログ外」（観点追加の起案シグナルになる）
- **経路**: 「主に上げた」／「自走した」のどちらか
- **帰結**: 「論点だった」／「論点じゃなかった」＋一言の理由（判定基準＝主の視線が加わって結論が変わったか）
- **還元**: 配役既定表（project.md / local.md）のどこを変えたか。変更しなければ「なし」

新しい判例はファイル末尾に追記する。既存の判例は書き換えない。

## 記入例

- 観点: 財務・コスト

- 帰結: 論点だった（月額差が閾値を超えており、予算方針文が未整備だったため）

### 2026-08-19 注入設計への主フィードバック — 論点相談・仲裁・人格規約の追加

- 帰結: 論点だった（「方針文があればメインが自走」の初版設計を、主の視線が「注入はサブエージェント限定・エスカレーション直前に観点スペシャリストへ相談・衝突は仲裁エージェントが裁定して事後報告・人格はポリシー文書に保存」へ変えた。人格付与は受容度＝主が読んで楽しい監査ログという主にしか出せない要求）

### 2026-08-21 casting テンプレのパス表記修正（#116）を burn 実行してよいか

### 2026-08-22 レビューゲートに「実装とドキュメント文字列の整合確認」を足してよいか（#166）

- 観点: 技術設計・品質、資産・回復可能性
- 経路: 自走した
- 帰結: 論点じゃなかった（レビューゲートは自己統治物件だが、この変更は**合格条件を1つ足す方向のみ**で、既存の必須ステップ・人間の承認経路・fail-closed の判定順序を1つも緩めていない。緩める方向・人間の承認経路を細くする方向なら主の視線が要るが、締める方向は「実装と説明文の食い違いを機械的に検出できるか」で判定でき、主にしか出せない情報が入らない。加えて `plugins/dev-workflow/skills/pr-review-gate/` は auto-merge workflow の SACRED パスなので、この PR 自体は機械マージされず `human-merge` が付いて主のマージ判断になる＝主の視線は機構側で確保されている）
- 還元: なし（配役表の変更なし。SKILL.md に手順4-2 を新設し、spec に要件を追加）
