# statusline-active-account-marker — 設計

## Context

現在の statusline の該当箇所（`plugins/statusline/scripts/statusline.sh`）:

- `active_idx` は既に確定している。判定は `usage-account-registry` の「active スロットの判定規則」に従い、env（`CLAUDE_SECURESTORAGE_CONFIG_DIR` から導出した Keychain サービス名）→ snapshot の `active` → 先頭スロット、の三段
- `multi`（スロット数が 2 以上か）で描画が分岐し、`multi=0` のときは `prefix` が空文字のまま描画に入る。この短絡経路が「1 スロット時に現行と 1 バイトも変わらない」を保証している
- `prefix` は複数スロットのときだけ組み立てられ、`label` と、表示幅の差を埋める空白と、区切りの 2 スペースからなる。表示幅はレジストリを読む python が 5 列目で渡す（bash の `${#var}` は文字数しか数えられず、全角ラベルで列がずれるため）
- 色は `DIM` / `RESET` の ANSI エスケープで、`DIM` は現在 label 列と行末の補助情報（残り時間・経過時間）に使われている
- **バー本体のグリフ（`BAR_GLYPH`。既定 `▂` U+2582）は East Asian Width が Ambiguous** で、これを 1 本のバーにつき 16 セル並べている。つまりこの statusline は既に「端末が曖昧幅を半角として扱う」ことを前提にしている。ただしバーは全行に等しく現れるので、この前提が外れてもすべての行が同じだけ広がり、**行どうしの列ずれは起きない**
- statusline は `NO_COLOR` を実装していない（`plugins/statusline/` に該当の参照はゼロ件）。その環境でも ANSI エスケープを出す

制約:

- **最優先の受け入れ条件**: スロットが 1 つ（レジストリ不在を含む）なら出力が現行とバイト単位で同一。既存の退行ガード 2 本が `git show origin/main:plugins/statusline/scripts/statusline.sh` と実出力を diff して守っている
- statusline は描画のたびに走るので、プロセスを増やさない

## Goals / Non-Goals

**Goals:**

- 2 スロット以上のとき、どちらが今のセッションのアカウントか一目で分かること
- 色が落ちる環境でも、記号が出ない環境でも、どちらか一方の手がかりが残ること
- バーの左端が全行で揃ったままであること（全角ラベルを含む）
- 1 スロット時の出力が 1 バイトも変わらないこと

**Non-Goals:**

- active スロットの判定規則の変更（`usage-account-registry` の既存規則をそのまま使う）
- バー・色・日程線・分母表示の意味論の変更
- snapshot のスキーマや `usage-probe.sh` への変更
- 非 active 行の行末に出る経過時間の変更（鮮度の表示として引き続き必要）

## Decisions

### D1: 記号と明るさの二重符号化にする

active 行は `▸ ` を前置し、label を通常の明るさで描く。非 active 行は半角スペース 2 つを前置し、label は `DIM` のまま。

目印の記号そのものは `DIM` を掛けず通常の明るさで描く。記号が主・明るさが補助という位置づけなので、主の手がかりを弱めない。

*代替案 A（明るさだけ）*: 列を足さずに済み最も静かだが、**色が落ちる経路で手がかりが完全に消える**。スクリーンショットの貼り付け、ログやファイルへのリダイレクト（`statusline.sh > out.txt`）、ANSI を解釈しない表示先ではすべて `DIM` が失われ、4 行がまったく同じ見た目になる。この statusline は「今のペースで持つか」を判断するための表示なので、判断の前提（どちらのアカウントか）が落ちる経路を残せない。

（`NO_COLOR` はこの列挙に含めない。statusline はそもそも `NO_COLOR` を実装しておらず、その環境でも ANSI を出すため、二重符号化の理由にはならない。実装していないこと自体は別の論点で、この change の対象外。）

*代替案 B（記号だけ）*: 色が落ちても残るが、フォントに `▸` が無い端末では豆腐（□）になり「何かの印が付いている」以上の情報にならない。

*採用（両方）*: 片方が落ちても他方が残る。2 つの手がかりが同じことを言うので、どちらか一方しか届かない環境でも読みが変わらない。冗長さのコストは 1 行あたり 2 桁と `DIM` の有無だけで、支払う価値がある。

### D2: 目印は全行に等しく 2 桁を占め、非 active 行では空白で埋める

active 行だけ 2 桁を足すと、その行だけバーの左端が右にずれて比較しづらくなる。非 active 行にも同じ 2 桁を空白として置き、列を揃える。

`▸ ` は表示幅 2（`▸` U+25B8 は East Asian Width が Neutral なので 1 桁、続く半角スペースで 2 桁）、空白 2 つも 2 桁。既存の label 列の表示幅計算はこの 2 桁の外側にあるので、幅計算のロジックには手を入れない（目印は `prefix` の先頭に足すだけ）。

*代替案*: 目印を label の**後ろ**に置く案（`A ▸ 5h`）は、label の表示幅が可変なので目印の位置も動き、視線を縦に走らせて active を探せない。行頭固定が最も速く読める。

### D2b: 目印の記号は East Asian Width が Neutral のものに限る

`▸`（U+25B8）を選んだのは見た目の好みではなく、**EAW=Neutral だから**である。見た目の似た候補はいずれも Ambiguous で、差し替えると列が崩れる（実測）:

| 記号 | コードポイント | EAW |
|---|---|---|
| `▸` | U+25B8 BLACK RIGHT-POINTING SMALL TRIANGLE | **N（Neutral）** |
| `▶` | U+25B6 BLACK RIGHT-POINTING TRIANGLE | A（Ambiguous） |
| `●` | U+25CF BLACK CIRCLE | A |
| `◆` | U+25C6 BLACK DIAMOND | A |
| `·` | U+00B7 MIDDLE DOT | A |

なぜ Ambiguous だと崩れるのか。この statusline は既にバー本体（`▂` U+2582、EAW=Ambiguous）を 16 セル並べており、「端末が曖昧幅を半角として扱う」前提の上に成り立っている。ただし**バーは全行に等しく現れる**ので、端末が曖昧幅を全角にしてもすべての行が同じだけ広がるだけで、行どうしの列ずれは起きない。

目印はここが違う。目印の記号が出るのは active 行だけで、非 active 行には ASCII の半角スペース 2 つが入る。EAW=A の記号を選ぶと、**曖昧幅の解釈の差が初めて「行と行のあいだ」に現れ**、曖昧幅を全角にする設定の端末では active 行だけが 1 桁右にずれる。主は日本語環境なので、この設定は現実的に踏みうる。

EAW=N を選ぶことは、既にある「曖昧幅は半角」の前提を**新たに広げない**という意味でもある。したがって記号を差し替えるときの制約は「見た目が目立つこと」ではなく「EAW=N であること」。N の代替としては `▹`（U+25B9）や `›`（U+203A）が使える（いずれも実測で N）。

### D3: 1 スロットのときは目印を出さない

`multi=0` の短絡経路に手を入れず、`prefix` が空文字のままになる経路を維持する。目印は「複数あるうちのどれか」を示すためのもので、1 つしかないときには意味がない。加えて、これが最優先の受け入れ条件（出力がバイト単位で同一）を守る唯一の方法でもある。

### D4: 判定は既存の `active_idx` をそのまま使う

`active_idx` は既に env → snapshot → 先頭の三段で確定している。描画側は `i -eq active_idx` を見るだけで、判定ロジックを二重に持たない。`active_idx` が指すスロットが値を持たず行が出ない場合（欠測）、目印の付いた行は 1 行も出ないことになるが、これは「そのアカウントの数字が無い」という事実の正しい表示であり、無理に別のスロットへ目印を移さない。

## Risks / Trade-offs

- **[`▸` がフォントに無く豆腐（□）になる]** → D1 の代替案 B で述べた既知の弱点。二重符号化なので明るさ側の手がかりは残る。豆腐になっても幅は 1 桁のままなので列は崩れない（崩れるのは EAW=A の記号に差し替えた場合で、それは D2b が禁じている）。なお `▸` は Geometric Shapes（U+25A0–U+25FF）、バーの `▂` は Block Elements（U+2580–U+259F）で、**隣接する別ブロック**である。バーが出るからといって `▸` が出るとは限らないので、フォント同梱の保証には使えない。
- **[行が 2 桁伸びて折り返しが早くなる]** → 目印の 2 桁ぶんだけ横幅を消費する。7d 行は既に最も長い行（`7d All` + バー + 分母 + `Fable` + バー + 分母 + 残り時間）なので、狭い端末では折り返しが早まる。複数アカウントを使っている場合にのみ発生し、1 スロット環境は影響を受けない。
- **[`DIM` の有無だけでは差が分かりにくい端末がある]** → 低コントラストのテーマでは `DIM` と通常の差が小さい。記号側が主で明るさ側が補助、という位置づけで受け入れる。

## Migration Plan

statusline.sh の `prefix` 組み立ての変更のみで、状態やファイル形式の移行は無い。ロールバックはスクリプトを戻すだけ。snapshot・レジストリ・他プラグインとの契約には触れないので、古い probe と組み合わせても動く。
