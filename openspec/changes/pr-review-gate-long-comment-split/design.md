# Design

## Context

動機は proposal.md の Why のとおり。

いまの実物は次のとおり。`レビュー三表:` のコメントは、照合と振り分けの G が補足の `needs-reviewer` を返す前に投稿し、補足結果を受け取る次の G が読む。補足済み回数の唯一の置き場所なので、投稿が途中で切れると回数が 0 に戻る。順 3 の一覧は W が push の前に投稿し、G が表をファイルにして `review-hit-set.py` に渡す。

`review-hit-set.py` は、1 つの表ファイルを読む。`修正前 SHA:` と `検索コマンド:` の行がちょうど 1 回ずつ、表の見出しが 1 つで、見出しのあとの行が `|` で始まらなくなると表が終わる（表の途中の空行で以後の行を読まなくなる）。

開いた PR が triage.md と gate-runner.md を広く触る（#1436 は全面、#1410 は順 3 の節、#1455 は gate-runner.md の要約受領の段落）。

## Goals / Non-Goals

**Goals**

- 三表と順 3 の一覧の、上限を超えるときの置き方と読み方を、同じ 1 つの規則で決める
- 新しいスクリプトを作らず、`review-hit-set.py` も変えない
- 上限に収まる PR の動きを変えない

**Non-Goals**

- レビュアーの return がコンテキスト上限で 2 回に分かれた件（#1243 の背景に書かれた別の問題で、受け入れ条件に無い）
- 順 3 の一覧に全ヒット要約を当てること（順 3 は行ごとの扱いが要るので全行のまま）
- 1 行だけで上限を超える行を分けて載せること（下の Risks のとおり止める）
- 親のコメントの偽造への対策（これまでの `レビュー三表:` と一覧のコメントも投稿者を確かめていない）

## Decisions

### 本文を行の境界で切り、連結で元に戻す

部分のコメントには、元の本文を行の境界で切ったものをそのまま置く。読む側は k の順に連結するだけで元の本文に戻り、表の形式を知らなくてよい。

- 別案: 表ごとにコメントを分け、部分ごとに表の見出しを繰り返す（#1243 の G の形）。1 つの表が上限を超えると分けられない。順 3 の一覧はまさに 1 つの表が大きいので使えない。部分ごとに `review-hit-set.py` へ渡せば、部分の外のヒットが `missing:` になるので、スクリプトの変更も要る
- 採った形の短所: 2 番目以降の部分は表の見出しが無く、GitHub の画面で表に見えない。読むのは G とスクリプトなので受け入れる

### 親は見出しの行と部分の URL だけを持つ

親のコメントの 1 行目は今と同じ `レビュー三表:` / `## 一覧（順 3）` にする。本文は親に置かず、すべて部分に置く。

- 別案: 変更点の一覧とハンク被覆を親に残し、照合表だけを部分に置く（#1243 の G の形）。三表と順 3 で規則が変わり、どこまで親に残すかの判断が要る
- 部分の 1 行目は `レビュー三表の部分 k/n` / `一覧（順 3）の部分 k/n` にする。`レビュー三表:` / `## 一覧（順 3）` で始まらないので、最新の親を探す読み手が部分を親と取り違えない

### 親を最後に投稿する

部分を先に投稿して URL を受け取り、親を最後に投稿する。親が 1 件の投稿で全部分を指すので、途中で失敗しても親が無い部分は読まれず、読み手は不完全な組を見ない。URL は `gh pr comment --body-file` の標準出力から取る。

- 別案: 親を先に投稿して、あとから編集で URL を書き足す。途中で切れると、不完全な親が最新として読まれる

### 長さはバイトで測る

分けるかどうかと部分の大きさは、`wc -c` のバイト数で 65,536 以下かを見る。GitHub が 65,536 を文字で数えるかバイトで数えるかは、#1243 の実物では決まらなかった（部分 1 は 30,079 字・54,255 バイトで、どちらの数え方でも通る）。バイト数は字数より小さくならないので、どちらで数えられていても上限を超えない。ロケールによらず同じ値になる。

- 別案: `wc -m` の字数で測る。GitHub がバイトで数えていると投稿に失敗する。ロケールで値が変わる
- 短所: 日本語の本文は、要らない場面で分かれることがある。部分が増えるだけで照合の結果は変わらない

### 整合の確認は親子の対応だけにし、中身は既存の照合に任せる

読み手は、部分が親と同じ PR のコメントであること、1 行目の k/n が親の行と一致すること、2 行目の SHA が親と一致することを確かめる。行の欠落は、既存の照合（ヒット集合・ハンク被覆・受け入れ条件の被覆）が差分として拾うので、ハッシュは持たない。

- 別案: 親に本文全体のハッシュを書く。GitHub が末尾の改行を保つかに結果が左右され、誤った不一致を生みうるうえ、既存の照合で拾える欠落しか拾わない

### 読めなかったときは既存の止まり方に乗せる

新しい Status を足さない。三表の部分が読めないのは「元の三表の欠落」なので、残差として `review-incomplete` で止める（補足済み回数が 1 のときの既存の止まり方）。順 3 の部分が読めないのは「W に表の出し直しを求める」場合に当たり、差し戻し 1 回に数える。

### 既存の要件は書き換えず、例外の要件を足す

既存の要件「一覧の一致で閉じる（順 3）」の「1 つの PR コメントに投稿」は MODIFIED にせず、ADDED の要件で上限を超えるときの例外を書く。この要件は #1410 が MODIFIED にしていて、全文の置き換えが衝突するため。triage.md の順 3 の節も、文は変えず箇条を 1 つ足すだけにする。規則の本体は `## 出口` の前の新しい節に置き、どの開いた PR の差分とも重ならない位置にする。

## Risks / Trade-offs

- [1 行だけで上限を超える行（ミニファイされたファイルのヒットなど）は部分に収まらない] → 投稿せずに止める。W は投稿も push もせず return で本体へ報告する。G は補足の `needs-reviewer` を返さず `review-incomplete` で止める。このリポジトリには当たらず、止まれば気づける
- [#1436 が triage.md を複数のファイルに分けると、新しい節の置き場所が変わる] → 節を独立させてあるので、後からマージする側がそのまま移せる
- [部分が多いと G が読み込む量が増える] → 読み手は部分をファイルに書き出して連結し、スクリプトに渡す。本文を会話に出さない
- [部分のコメントが PR に増えて読みにくい] → 上限を超えた PR だけに起きる。受け入れる

## Migration Plan

上限に収まるコメントは今までどおりなので移行は要らない。読み手は親に `部分 k/n:` の行があるときだけ新しい読み方をする。規則の前に #1243 の形で投稿された PR は既にマージ済みで、読み直されない。
