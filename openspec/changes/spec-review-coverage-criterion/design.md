# Design — spec-review-coverage-criterion

## Context

R1（仕様レビュアー）は `references/roles/spec-reviewer.md` の 5 観点で change の artifact を読み、BLOCKER が 0 件なら APPROVE、1 件以上なら REQUEST_CHANGES を返す。pr-review-gate は 2 周目以降の指摘を「受け入れ条件または仕様の守備範囲のどの文に違反するか」で仕分けるが、仕様に守備範囲の文が無いと引用できず、指摘を範囲外として落とせない。

## Goals / Non-Goals

- Goals: 入力を検査・判定する要件を新たに書く／改定するとき、実装前に守備範囲の段落が揃う
- Non-Goals: 既存 `openspec/specs/` の検査系要件に守備範囲を後から書き足すこと。pr-review-gate 側の仕分け手順の変更（#281 の PR-A の範囲）

## Decisions

### 1. 対象は「入力を検査・判定する要件」に限る

入力（ファイル・コマンド引数・PR 本文・コメント・環境変数など）を受け取って、通す／落とす／分類する振る舞いを定める要件だけを対象にする。例は検査・lint・ゲート・パーサ・バリデータ。文書の書き方や手順だけを定める要件には要求しない。

- 採用理由: 守備範囲が要るのは「この入力も通る」という指摘が際限なく出うる要件で、手順の要件にまで求めると R1 の差し戻しが増えるだけになる
- 退けた案: 全要件に守備範囲を必須にする。レビューの手間に見合う効果が無い

### 2. 守備範囲の段落に必ず含めるもの

「何から守るか」（想定する入力の出どころと、拾いたい誤り）と「何は守らないか」（想定外として通ることを許す入力）の両方。片方だけなら欠落とみなす。書き方の手本は `openspec/specs/injection-budget-gate/spec.md` の「この書式検査の守備範囲は…」の段落（守らない入力の具体例を挙げ、塞ぎ切ることを完了条件にしないと書いている）。

- 採用理由: pr-review-gate の仕分けで範囲外と判定する根拠になるのは「守らない」側の文である。「守る」側だけでは指摘を落とせない

### 3. 欠落は BLOCKER とする

R1 の判定基準は「BLOCKER 0 件なら APPROVE」なので、差し戻すには BLOCKER に分類する必要がある。SHOULD_FIX にすると実装に進めてしまい、PR レビューの周回で同じ問題が再発する。

### 4. 遡及しない範囲の切り方

R1 が検査するのは、レビュー対象の change の delta spec が ADDED / MODIFIED する要件だけ。change が触れない既存 spec の検査系要件に守備範囲が無くても指摘しない。MODIFIED で既存要件を改定した場合は、その要件が対象なら守備範囲を求める（改定は「新規・改定時に適用」の改定に当たる）。

## Risks / Trade-offs

- 「入力を検査・判定する要件」かどうかの判断が R1 ごとにぶれうる → 例（検査・lint・ゲート・パーサ・バリデータ）と定義（通す／落とす／分類する）を spec-reviewer.md に併記して抑える
- 守備範囲を書いても、その文の範囲内の指摘は引き続き出る。この変更は範囲外の指摘を落とす根拠を用意するだけで、周回そのものの上限は pr-review-gate の収束ルールが受け持つ
