## Context

動機は proposal.md の Why。前提になる今の状態は次のとおり。

- 見張りの待ち `ci-watch.sh wait` は状態ファイルを読み書きせず、`next` だけが状態ファイル（`pr-state.sh decide` の状態）を書き換える。待ちが切れても状態ファイルは最後の `next` の時点のまま残る
- `decide` は、観測が `wait` なら `none`（待ちに戻る）、`ready` なら常に `ready`、前回と同じ状態・同じ HEAD の決着なら `none`（見張りを終える）を返す。`rerun` の判定では次の状態を `wait` に置くので、やり直しの結果は次の `next` で通常どおり判定される
- 見張り中かどうかは PR のコメント（1 行目が `CI 見張り開始:` / `CI 見張り終了:`）で判定する。今の 2 は「前のセッションが閉じて終了のコメントが残らなかった」再開にオーナーの指示を求めている
- flatmate#1312 の起動し直し（2026-10-18 10:08:04）では、起動直後に `<task-notification>` の `<status>stopped</status>`（summary: Background shell command didn't finish before the previous session ended）が会話に入った。#1240 の調査ログに残る範囲では、そのあと親の返事（10:10:42）まで本体の発言が 1 行も無い。通知がターンを起こしていれば、手順が無くても何か出力されるはずなので、この唯一の観測は「起動し直しのときの通知はターンを起こさない」側を示している。通知がターンを起こすかは Claude Code の版にも依存しうる
- エピックの親の `epic-dispatch.sh wait --watch-stopped` は、子の記録の `stop` が `stopped` の子だけを返す。会話ログの止まった時間で子を返す経路は無い（#1084 は OPEN）

## Goals / Non-Goals

**Goals:**
- 起動し直したセッションが、見張りの待ちが切れたという通知を受けたら、決着していない見張りを主の入力なしに `next` から再開する
- 決着済み（終了のコメントがある・PR が merged / closed）の見張りは再開しない

**Non-Goals:**
- 起動し直らないまま落ちたセッションを拾うこと（子の側の手順では救えない。#1084 の親の検知が受け持つ）
- 通知を受けていない新しいセッション（たとえば親の `reply --relaunch` で作り直されたセッションや、#1323 の `/clear` してから `/develop #<N>` で起こすセッション）が、前のセッションの見張りを自動で引き継ぐこと。そのセッションは見張りが自分のものか分からないので、今の 2 の規則（オーナーの指示で再開）のまま
- `ci-watch.sh` / `pr-state.sh` の振る舞いの変更、hooks の追加・変更、`epic-dispatch.sh` と `reply-after-idle.md` の変更

## Decisions

### 再開の発火点は背景タスクの通知にし、手順は reference に置く（SessionStart hook は足さない）

- 採る案: 起動し直したセッションが、自分の会話で起動した `ci-watch.sh wait` について `stopped` / `killed` の通知を受けたあとの最初のターンで、`references/ci-watch.md` の新しい節（9 として足す）の手順で再開する。ターンを起こすのが通知そのものでも、親の返事や主の入力でも同じ手順で再開するので、通知がターンを起こさなくても、次のターンが来れば親の `reply` の文面に頼らずに再開できる
- 退けた案 A（SessionStart hook で起動時に未決着の見張りを探して文脈に足す）: hook は文脈を足すだけで、入力の無いセッションにターンを起こせない。通知が会話に入る点は採る案と同じで、ターンを起こせない点も変わらない（どちらもターンが来たときに何をするかを渡すだけ）。さらに hooks は聖域（変更に人の判断が要る）で、起動のたびに `gh` を呼ぶ費用と遅れがかかる。どの PR を見張っていたかも hook からは会話を読まないと分からない
- 退けた案 B（両方置く）: 案 A を足しても入力なしのターンは起きず、聖域の変更と起動ごとの費用だけが増える
- 入力なしにターンが起きるかは、flatmate#1312 の観測では起きない側に見える。tasks 1.1 で実機で確かめ、起きないと分かれば下の「1.1 で通知がターンを起こさなかったとき」に進む

### 1.1 で通知がターンを起こさなかったとき（本体が主に聞く内容）

tasks 1.1 で、起動し直したセッションの通知が入力なしにターンを起こさないと分かったら、W は実装に進まず本体に返し、本体は主に次の 1 問を聞く。flatmate#1312 の観測からは、こちらになる見込みが高い。

- 質問: 受け入れ条件の 1 つ目「主の入力なしに `next` を実行する」を、「通知が会話にある状態で次のターンが来たら（親の返事・主の入力のどちらでも）、再開してよいかを聞かずに `next` を実行する」に縮めて、この change の手順だけで進めてよいか。それとも、入力なしの再開は親の検知（#1084 の経路で止まった子を見つけ、親が `reply` で起こす）に寄せ、この change はその経路ができてから進めるか
- 推奨は前者。理由: 親や主が起こした最初のターンで自動的に `next` まで進むので、flatmate#1312 で要った「`next` で一手を決めよ」という親の具体的な指示が要らなくなり、親の検知は #1084 で別に入る
- このとき、1.1 で残した記録（セッション ID・Claude Code の版・通知の行・続かなかったこと）を質問に添える

### 対象の見張りは通知の背景タスクから特定する

通知の task id / tool-use id から、会話の中でその背景タスクを起動したコマンドを確かめ、`<owner/repo>` と PR 番号を取る。起動し直したセッションは前のセッションの会話を持っている（`stopped` の通知はその会話の背景タスクについて届く）ので、状態ファイルを走査して PR を当てる必要は無い。状態ファイルの一覧は複数の PR を含みうるので、手がかりに使わない。

### 決着済みかは PR の状態とコメントで判定する

- PR が open で、最新の `CI 見張り開始:` のあとに `CI 見張り終了:` が無い → 再開する
- `CI 見張り終了:` がある → 何もしない（ほかの手順が見張りを閉じている）
- PR が merged / closed → 再開しない。開始のコメントだけが残っているので、`CI 見張り終了:` を投稿して記録を閉じる（閉じないと、あとで見張りを始めるセッションが見張り中と読んで止まる）。merged ならマージを報告する
- 状態ファイルの `raised` は判定に使わない。上げ済みの見張りは終了のコメントを投稿して終えているので、コメントの判定で拾える
- コメントは `gh api --paginate` で全ページ読む。1 ページ（30 件）で切ると、コメントの多い PR で最新の開始・終了を見落とす
- 守備範囲は spec の要件「決着済みの見張りは起動し直しても再開しない」に書く（入力は通知・PR の状態・開始と終了のコメントの 3 つ。拾いたい誤りは二重の再開と放置。別のセッションの再開との重なり・人によるコメントの削除や書き換え・通知が届かない起動のしかたは通ることを許す）。落ちる時点は `wait` の実行中に限られ（`wait` が終わったあとに落ちた場合は通知が `completed` で、この手順の対象外）、`wait` の前の一手は済んでいるので、2 の「中断した一手」の確認は要らない

### 再開の一手は `next`（`--unrelated` なし）

`next` は PR を取り直して一手を決めるので、待ちが切れていた間に起きたこと（CI の決着・push）を 1 回で拾える。観測が `wait` なら `none` で待ちに戻り、`rerun` のあとの結果も通常どおり判定される。`--until-merged` の待ちが切れた場合も `next` から入る（`ready` なら「`ready` を受けたあと」に戻り、ラベルを見てから `--until-merged` で待ち直す）。

最初の `next` に `--unrelated` を渡さないのは、5 の判断が `wait` の観測（`obs.checks` の `cause`）を入力にしていて、再開の時点ではその観測が手元に無いため。関係ない失敗は `fix` に回り、7 の②で実装者が関係ないと判断して返せば `next --unrelated --after-fix` に進む。

### 同じ見張りの続きとして扱い、2 と書き分ける

通知は自分の会話で起動した待ちについて届くので、見張りの持ち主はこのセッション自身と分かる。2 の開始の判定をすると、自分が投稿した `CI 見張り開始:` を「ほかのセッションが見張り中」と読んで自分で止まる（`fix` のあとに `wait` から始め直すときと同じ理由）。2 のオーナーの指示を求める再開の規則は、通知を受けていない別のセッションが始める場合に限ると書き分ける。

### エピックの親の検知はこの change に入れない

子のセッションが起動し直れば、この手順で子が自分で再開する。起動し直らない子（落ちたまま）は子の側で救えないので、親の `wait` が拾う必要がある。今の `wait --watch-stopped` は記録の `stop` しか見ず、#1084 が提案する「会話ログが一定時間更新されていない子を返す」経路がまだ無い。その経路ができれば、CI の見張りが決着していない子も止まった時間だけで拾えるので、CI の見張り専用の条件を足す必要は無い。ただし #1084 の案のうち Stop フックの案（ターンの終わりを見る）だけでは、落ちてターンが終わらない子は拾えないので、「CI の見張り中に落ちて起動し直らない子（flatmate#1312 の 09:00〜10:08）」を拾う対象として #1084 にコメントで送った（https://github.com/oratta/claude-harness/issues/1084#issuecomment-6409774131 ）。経路を足すのは `epic-dispatch.sh` の `wait` の変更で、同じ `wait` を #1324（親の短い待ち直し）が、同じ会話ログの事実（`decide_relaunch`）を #1323 が触っている。親エピック #1325 の注意書きどおり、この change では触らない。

## Risks / Trade-offs

- [起動し直したセッションで、`stopped` / `killed` の通知が入力なしにターンを起こさない。flatmate#1312 の観測はこちらを示していて、見込みは高い] → この場合は手順を足しても受け入れ条件の「主の入力なしに」を満たせない。tasks 1.1 で `kill -9` による再現で確かめ、起こさないと分かったら実装に進まず本体に返す（主に聞く内容は上の「1.1 で通知がターンを起こさなかったとき」）
- [通知を受けても本体が reference の節を読まない（コンパクトで reference の中身が会話から落ちている）] → develop の `SKILL.md` の CI の見張りの行から節を指す。コンパクト後は既存の `develop-compact-reread.sh` が SKILL.md を読み直させる
- [関係ない失敗でも最初の `next` が `fix` を返し、修正回数を 1 つ使う] → 損失は実装者の判断 1 回と修正回数 1 つ。3 回目で `escalate` になる上限に 1 つ近づくが、オーナーに上がって止まるだけで誤ったマージにはならない
- [起動し直したセッションと、主の指示で見張りを再開した別のセッションが重なる] → 別のセッションは 2 の判定で開始のコメントの有無を見る。起動し直したセッションは開始のコメントを投稿し直さないので、どちらも同じ開始のコメントを見て、別のセッションは始めない
