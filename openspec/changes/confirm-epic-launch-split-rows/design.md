## Context

#1128 の仕分けの表は、エピック実行の Orca 経路にかかわる 5 行を「保留（#1123 の後）」にし、#1129 の担い手が #1123 の結果を見て確定すると決めた（`docs/public-private-split.md`「保留の行の確定」）。#1123 は閉じ、結果は次のとおり。

- `epic-dispatch.sh` は起動部品を別のプロセスとして呼ぶ形になった。部品は `epic-launch-orca.sh`（Orca）と `epic-launch-tmux.sh`（tmux。orca を呼ばない）の 2 本で、`EPIC_DISPATCH_LAUNCHER` か、今いる場所（Orca 管理のワークツリーか tmux の中か）で選ぶ（`plugins/dev-workflow/scripts/epic-dispatch.sh` の `launcher_run`・`pick_launcher`）
- 経路の判定は、Orca 管理下なら orca、tmux の中なら tmux、それ以外はサブエージェント方式（同 390 行目付近）
- develop の SKILL.md「エピックの扱い」は、別セッション方式（起動部品は Orca か tmux）として書き直された

#1129 は 2 つの change に割った（記録先: https://github.com/oratta/claude-harness/issues/1129#issuecomment-6332494744 ）。この change は前半で、部品を移さずに表を確定する。後半の `move-private-parts-to-private-repo` は、この change の表を入力にして個人版のリポジトリへ部品を移す。

## Goals / Non-Goals

**Goals:**

- 保留の 5 行を公開版か個人版に確定し、理由を表に残す
- 確定に合わせて、文書の分類の値・載せない行の基準・検査を矛盾の無い形にする
- 公開版に確定した部品の中で、Orca だけを前提にした書き出しを直す

**Non-Goals:**

- 個人版の部品を移すこと・個人版のリポジトリを作ること（後半の change）
- 固有名の混入検査を新しく作ること（#1207）
- `epic-dispatch.sh` の振る舞いを変えること

## Decisions

### 1. 保留の 5 行はすべて公開版にする

| 部品 | 決め方（表の理由の欄に書いてあった条件） | #1123 の結果 | 確定 |
|---|---|---|---|
| `epic-dispatch.sh` | Orca が無い環境でもエピックを回せるなら公開版 | tmux の部品とサブエージェント方式で回せる | 公開版 |
| `epic-launch-orca.sh` | 差し替えの部品の 1 つとして残るなら公開版 | `epic-launch-<名前>.sh` の 1 本として残った | 公開版 |
| `stop-judge.sh` | `epic-dispatch.sh` と同じ側 | — | 公開版 |
| `parent-pass-criteria.md` | `stop-judge.sh` と同じ側 | — | 公開版 |
| `parent-merge-criteria.md` | サブエージェント方式からも使われるなら公開版、Orca 経路だけなら `epic-dispatch.sh` と同じ側 | 別セッション方式（Orca・tmux）の親が使う | 公開版 |

`epic-launch-orca.sh` を個人版にする案は取らない。Orca はオーナーの持ち物ではなく誰でも入れられる製品で（文書の基準「一般の製品を例の 1 つとして並べる行」でも Orca を一般の製品として扱っている）、判断の基準の「個人版: オーナーに固有の業務・アカウント・資格情報の置き場・固有名に依存するもの」に当たらない。また `epic-dispatch.sh` は部品が見つからないときの既定を orca にしているので、Orca の部品だけを個人版へ移すと公開版の既定の経路が壊れる。

`epic-launch-orca.sh` が公開版なので、#1177 で外した「起動部品の 1 つとして一覧から外した行」は一覧に戻さない（戻す条件は個人版に決まったときだけ）。節は場所の記録として残し、前提が満たされたことを書く。

### 2. 分類の値「保留（#1123 の後）」は消す

使う行が 0 行になるので、文書の「分類の値」と検査の `ALLOWED` から外し、値を 3 つ（公開版・個人版・分割）にする。

- 残す案は取らない。値が許されたままだと、新しい部品の行を決める人も時期も書かずに保留へ置けてしまう。消しておけば、保留の値の行は「決めた値以外の分類」として検査で落ちる
- 「保留の行の確定」の節は消さず、確定した結果（どの行をどちらに、何を見て）の短い記録に書き換える。経緯を読む人が #1128 の文書と #1129 の PR を突き合わせなくて済むようにするため
- 「載せない行の基準」の「個人版や保留の部品の中の行」は「個人版の部品の中の行」にする

### 3. Orca の起動部品の中の行は、載せない行の基準を 1 項目足して外す

5 本を公開版にすると、候補語 `Orca` に `epic-dispatch.sh` の約 25 行と `epic-launch-orca.sh` の約 10 行が当たる（どちらも主にコメント）。一覧に載せる案と比べて、基準を足す案を取る。

- 一覧に載せる案は取らない。一覧の行には担い手が要り、「担い手なし」は残せない（要件「固有記述の一覧に担い手なしの行を残さない」）。ところがこの行は Orca の部品そのもの（`epic-launch-orca.sh`）と、その部品を選んだときの振る舞い（orca のコマンドの呼び出し順・Orca の画面の印・Orca 管理のワークツリーの判定）の説明で、「Orca を使う場合」の書き方に直す余地が無い。直す issue を立てても直す中身が無い
- 足す基準: **Orca の起動部品の中の行と、起動部品を呼ぶ側で Orca の部品を選んだときの振る舞いを書いた行**。`epic-launch-orca.sh` の全行と、`epic-dispatch.sh` の中で Orca の部品を選んだときの動き（orca のコマンド・Orca の画面の印・Orca 管理のワークツリーの判定・Orca に登録されたリポジトリ）を書いた行が当たる。Orca を入れていない環境では Orca の部品は選ばれず（経路の判定が tmux かサブエージェント方式になる）、読み手の環境に Orca が無くても誤った指示にならない
- 当たらない行: develop の SKILL.md など、起動部品の外で Orca だけを前提にした手順を書く行（「Orca 経路の子は…」）。これは従来どおり「Orca を使う場合」の書き方に直すか一覧に載せる。この change で直す `parent-pass-criteria.md:3`・`parent-merge-criteria.md:3` はこちらに当たる
- `epic-dispatch.sh` の冒頭のコメントで dev-workflow-develop spec の要件名「Orca 経路の親は、止まった印のまま completed で閉じた子に完了を促す返事を送る」を引く行は、既存の基準「出典や経緯としてだけ名前を挙げる行」に当たる（正本の要件の名前を引いているだけで、指示ではない）
- この基準は機械の検査に足さない。候補語による取りこぼしの確認は、既存の要件「表と一覧の検査の守備範囲」のとおり人のレビューが見る

### 4. Orca だけを前提にした書き出しを直す

`parent-pass-criteria.md:3` の「Orca 経路のエピックで」「develop の SKILL.md の Orca 経路の手順 8」と、`parent-merge-criteria.md:3` の「Orca 経路のエピックで」を、「別セッション方式（起動部品は Orca か tmux）のエピックで」「別セッション方式の手順 8」に直す。#1177 で `reply-after-idle.md` などを直したときと同じ言い方にそろえる。`stop-judge.sh` には候補語の当たりが無い。

### 5. 検査

`tests/public-private-split.bats` を次のとおり直す。

- `ALLOWED` から「保留（#1123 の後）」を外す
- 確定した 5 行のパスを検査の中に固定の文字列で持ち、5 行とも表にあって分類が「公開版」であることを確かめる。1 行でも公開版以外になれば、その部品のパスを挙げて落ちる。分類の判断の正しさは検査しないという既存の守備範囲の例外ではなく、この PR で確定した値が後の編集で黙って変わることを止めるための固定である（確定を覆すときは、この検査も一緒に直す）。守備範囲は要件「各行は決めた分類と理由を持つ」の段落に書く
- 「`epic-launch-orca.sh` is a pending part」の検査を 2 つに置き換える: (a) 一覧に `epic-launch-orca.sh` を指す行を足しても「公開版に決まる部品に属さない」で落ちない（確定後は公開版の部品なので）。(b) 表のある行の分類を「保留（#1123 の後）」に書き換えると、決めた値以外の分類として落ちる
- dev-workflow の `moko` などの検索の対象（`devwf_public_files`）は、もともと保留のファイルを除いていないので変えない。要件の文の「保留の行のファイルは対象に含めない」だけを消して実装にそろえる

## Risks / Trade-offs

- [基準を足すことで、Orca の部品の外に Orca だけを前提にした行が紛れても見逃す] → 基準の当たる範囲を「起動部品の中」と「起動部品を呼ぶ側で Orca の部品を選んだときの振る舞い」に限り、当たらない例（SKILL.md の手順）を文書に書く。紛れ込みは人のレビューと次の候補語の再検索が見る。起きる頻度は、`epic-dispatch.sh` の Orca の分岐に手を入れる PR が出るときだけ
