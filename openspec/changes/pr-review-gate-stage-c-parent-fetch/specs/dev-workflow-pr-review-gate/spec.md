## MODIFIED Requirements

### Requirement: 候補探しのスクリプトは 1 回だけ走らせ、失敗を候補なしと読まない

G は、段 B を通った指摘（範囲で成り立つ・後で成り立つ）が 1 件以上あるとき、`plugins/dev-workflow/scripts/review-issue-candidates.sh` を、その周の振り分けにつき 1 回だけ走らせなければならない（MUST）。引数は次のとおりとする（MUST）:

- `--repo <owner>/<name>`
- `--exclude <PR 番号>` と、記録先が issue なら `--exclude <記録先 issue の番号>`
- エピックに属する PR で、親が `<owner>/<name>` にあるときは `--epic <エピック番号>`。親のリポジトリが `<owner>/<name>` と違うとき・親の取得が失敗し続けたときは `--epic` を付けない（親の取得は段 C の要件のとおり、この走らせる前に済ませる）。`--children-only` は付けない（1 回の実行で、候補がエピックの子か外かを各行の 3 列目 `child` / `other` で見分けるため）
- 段 B を通った指摘の場所のパス。指摘の場所が `ファイル:行番号` や `ファイル:行範囲` の形なら、`:` 以降を落としてファイルのパスだけを渡す（そのまま渡すと検索語が `"triage.md:53"` になり、ほぼ 0 件になるため）

出力は、`== <パス>` の見出し行ごとに、候補の行 `<番号><TAB><題名>[<TAB>child|other]`、`(該当なし)`、`(15 件で打ち切り。ほかにも一致あり)` として読む（MUST）。候補が「同じ場所を直す」かは題名で判断し、issue の本文を読むのは段 C で外の issue の受け入れ条件を確かめるときだけとする（MUST）。

終了コードが 0 でないとき（1 は検索の失敗、2 は引数の不備）、G は標準出力が空であることを「候補なし」と読んではならない（MUST NOT）。引数を直して 1 回だけ走らせ直し、それでも 0 にならなければ、仕分けの PR コメントに「候補探しに失敗した」と終了コードを書いたうえで、既存 issue への相乗り（段 C の上 3 行と段 D）をせずに段 C の「当たる issue が無い」と段 E へ進む（MUST）。

#### Scenario: 行番号を落として渡す

- **WHEN** 段 B を通った指摘の場所が `plugins/dev-workflow/skills/pr-review-gate/stages/triage.md:53-57` である
- **THEN** G がスクリプトに渡すパスは `plugins/dev-workflow/skills/pr-review-gate/stages/triage.md` である

#### Scenario: エピックに属する PR

- **WHEN** 記録先 issue #985 の親エピックが #973 で、PR が PR #N（番号 N）で、段 B を通った指摘が 2 つのファイルを指す
- **THEN** G は `review-issue-candidates.sh --repo <owner>/<name> --exclude <N> --exclude 985 --epic 973 <パス 1> <パス 2>` を 1 回だけ走らせ、`--children-only` を付けない

#### Scenario: 検索が失敗した

- **WHEN** スクリプトが 2 回とも終了コード 1 で終わる
- **THEN** G は仕分けの PR コメントに候補探しの失敗と終了コードを書き、既存 issue へのコメントも受け入れ条件への追記もせず、指摘を段 C の「当たる issue が無い」または段 E に当てる

### Requirement: エピックの完了条件に効く指摘は既存 issue との関係で分ける（段 C）

エピックに属する PR で、段 B の「いまの範囲で成り立つ」に当たった指摘について、G はその指摘がエピックの完了条件に効くか（出荷物を使う人の体験が変わるか）を、エピックの本文の完了条件を根拠に決めなければならない（MUST）。効く指摘は、候補探しの結果で次の表のとおりに分ける（MUST）。効かない指摘は段 D へ進める（MUST）。

| 候補探しの結果 | 扱い |
|---|---|
| 同じエピックの子 issue（`child`）に、同じ場所を直すものがある | その子 issue の受け入れ条件に足す |
| エピックの外の issue（`other`）に当たり、その issue の受け入れ条件が、この指摘を直せば全部満たされる | その issue をエピックの子に足す。新しい子は作らない。足した理由をその issue にコメントする |
| エピックの外の issue に当たるが、満たされない項目が 1 つでも残る。または受け入れ条件が書かれていない | この指摘だけの新しい子 issue を作る。外の issue には「この部分は子 issue で直す」と番号を書き、エピックには足さない |
| 当たる issue が無い | 新しい子 issue を作る |

外の issue に open の PR が付いているときは、新しい子 issue に「外の PR のマージ後に着手」と書く（MUST）。エピックの中と外に同じファイルを直す issue が並ぶときは互いの番号を書く（MUST。重なりそのものは防がない）。

エピックに属するかは、記録先 issue の親を `gh api repos/<owner>/<name>/issues/<記録先>/parent --jq '{number,repository_url}'` で番号とリポジトリ（`repository_url`）の両方を取って決める（MUST）。この取得は候補探しの前に済ませる（MUST。候補探しの `--epic` が親で決まるため）。判定は終了コードでなく出力で行い（404 も 5xx も終了コードは 1 のため）、出力に `HTTP 404` を含むときだけエピックに属さない PR として段 C を飛ばす（MUST）。それ以外の失敗（レート制限・5xx・通信断など）は 1 回だけやり直し（MUST）、それでも取れなければ、仕分けの PR コメントに親の取得の失敗を書き（MUST）、エピックに属さない PR とは読まない（MUST NOT）。このときは、段 C を飛ばし、候補探しは `--epic` を付けずに走らせ、段 B の範囲は記録先の issue で読み、「範囲で成り立つ」に当たった指摘は段 D の参考コメントで済ませず、段 E の判定もせず、エピックの外の新しい issue にする（MUST）。親のリポジトリ（`repository_url` の末尾の `<owner>/<name>`）が、小文字にそろえて `<owner>/<name>` と違うときは、エピックの本文と `## 条件の答え` を親のリポジトリで読み書きし、候補探しは `--epic` を付けずに走らせて全候補を `other` として読む（MUST）。表の「エピックの子に足す」操作は、既存の issue も新しい子 issue も `repos/<親のリポジトリ>/issues/<親の番号>/sub_issues` に対して行い、新しい issue そのものは `<owner>/<name>` に作る（MUST）。親のリポジトリの本文を読めない・書けないときは、親の取得の失敗と同じに扱う（MUST）。全候補を `other` と読むので、すでに親の子である `<owner>/<name>` の issue も「外の issue」に当たりうる。その確かめはしない（子に足す操作が拒否されたら、仕分けの PR コメントに書く）。

守備範囲: 入力は、親の取得の応答（HTTP の状態・`number`・`repository_url`）、エピックの本文の完了条件、候補探しのスクリプトが返した番号・題名・3 列目、投稿者を確かめた外の issue の本文に限る。拾いたい誤りは、エピックの完了条件に効く指摘がエピックの外の issue になって配布の前に直されないこと、同じ場所を直す子 issue があるのに新しい子 issue を作ること、別リポジトリの親の番号を `<owner>/<name>` の番号と読むこと、一時的な失敗を親が無いと読むこと。次は誤ったまま通ることを許す: 受け入れ条件があいまいな外の issue を G が「全部満たされる」と読み違えてエピックの子に足すこと（足した理由をその issue にコメントするので、あとから外せる）／完了条件に効かない指摘を G が効くと読んで子 issue が 1 件増えること／題名だけでは同じ場所を直すと分からない子 issue を見落とすこと／記録先 issue 自体が見えない 404 を「親が無い」と読むこと（`No parent issue found` かの区別はしない）／リポジトリ名の変更で `repository_url` が `<owner>/<name>` と違って見え、`--epic` なしで走ること／別リポジトリの親で、すでに親の子である issue を子に足そうとして拒否されること。これらを塞ぎ切ることは完了条件にしない。

#### Scenario: 同じ場所を直す子 issue がある

- **WHEN** エピックの完了条件に効く指摘の場所のパスについて、スクリプトが 3 列目 `child` の候補を返し、その題名が同じ場所を直すものである
- **THEN** G はその子 issue の受け入れ条件に指摘を足し、新しい issue を作らない

#### Scenario: 外の issue の受け入れ条件が全部満たされる

- **WHEN** `other` の候補の投稿者が `OWNER` で、その issue の受け入れ条件が、この指摘を直せば全部満たされる
- **THEN** G はその issue をエピックの子に足し、足した理由をその issue にコメントし、新しい子 issue を作らない

#### Scenario: 外の issue に満たされない項目が残る

- **WHEN** `other` の候補の受け入れ条件のうち 1 項目が、この指摘を直しても満たされない
- **THEN** G はこの指摘だけの新しい子 issue を作り、外の issue に子 issue の番号を書き、外の issue をエピックの子に足さない

#### Scenario: 親が別リポジトリにある

- **WHEN** 記録先 issue の親の取得が `{"number":896,"repository_url":"https://api.github.com/repos/genetta-inc/flatmate"}` を返し、`<owner>/<name>` が `oratta/claude-harness` で、候補が当たらない指摘がエピックの完了条件に効く
- **THEN** G はエピックの本文を `genetta-inc/flatmate#896` で読み、`## 条件の答え` もそのリポジトリの本文に書き、候補探しを `--epic` なしで走らせて全候補を `other` として読み、新しい issue を `oratta/claude-harness` に作って `repos/genetta-inc/flatmate/issues/896/sub_issues` に足す。`oratta/claude-harness#896` をエピックとして扱わない

#### Scenario: 親が無い

- **WHEN** 親の取得の出力が `HTTP 404`（`No parent issue found`）を含む
- **THEN** G はエピックに属さない PR として段 C を飛ばす

#### Scenario: 親の取得が 404 以外で失敗し続ける

- **WHEN** 親の取得がレート制限・5xx・通信断のいずれかで失敗し、1 回やり直しても取れず、段 B で「範囲で成り立つ」に当たった指摘の場所に、同じ場所を直す open の issue の候補がある
- **THEN** G はエピックに属さない PR と読まず、仕分けの PR コメントに親の取得の失敗を書き、段 C を飛ばし、候補探しを `--epic` なしで走らせ、その指摘を段 D の参考コメントで済ませず段 E の判定もせずに、エピックの外の新しい issue にする

#### Scenario: 親のリポジトリの本文を読めない

- **WHEN** 親が別リポジトリにあり、そのリポジトリのエピックの本文をトークンの権限で読めない
- **THEN** G は親の取得の失敗と同じに扱い、エピックに属さない PR とは読まない

### Requirement: 相乗りの参考コメント（段 D）と費用対効果（段 E）

段 D で、G は同じ場所を直す open の issue の候補があれば、その issue に「参考。この issue の受け入れ条件には足さない」で始まるコメントで指摘の中身と元の PR の URL を入れなければならない（MUST）。候補が複数あるときは、最も近い 1 件にだけ入れる（MUST）。G は、その issue をエピックの子にも配布の前提にも足してはならない（MUST NOT）。ただし、親の取得が失敗し続けたときの「範囲で成り立つ」に当たった指摘は、段 D を通さない（MUST。段 C の要件）。

段 E で、G は起きる見込みと起きたときの影響を、issue 1 件を通す手間（仕様・レビュー・ゲートを 1 回通す分）と比べ、見合えばエピックの外の新しい issue を作り、見合わなければ捨てて PR コメントに理由を 1 行残さなければならない（MUST）。ただし、親の取得が失敗し続けたときの「範囲で成り立つ」に当たった指摘は、この判定をせずエピックの外の新しい issue にする（MUST。段 C の要件）。費用対効果を比べるのは段 E だけとする（MUST。段 B で捨てる指摘は効果そのものが無く、段 D は相乗りで手間がほぼかからないため）。

#### Scenario: 同じ場所の issue に参考として入れる

- **WHEN** エピックの完了条件に効かない止めない指摘の場所のパスについて、スクリプトが同じ場所を直す候補 #886 を返す
- **THEN** G は #886 に「参考。この issue の受け入れ条件には足さない」で始まるコメントを入れ、コメントの URL を PR コメントに記録し、新しい issue を作らない

#### Scenario: 手間に見合わない

- **WHEN** 候補が `(該当なし)` で、指摘が起きても影響がテストの見出しの読みやすさにとどまる
- **THEN** G は issue を作らず、PR コメントに理由を 1 行残す
