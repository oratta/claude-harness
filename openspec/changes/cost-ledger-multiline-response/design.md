## Context

`facts_from_lines`（`plugins/cost-ledger/scripts/cost_ledger.py`）は、行ごとに JSON を読み、`requestId`（無ければ `uuid`）が `seen` にあれば捨て、無ければ `build_fact` で 1 つの事実にして `seen` に足す。1 回の API 応答が複数行に分かれると、先頭の行（考えた内容・本文のことが多い）だけが事実になり、後続のツール呼び出しの行にある `gh issue ...` と投稿の印は `scan_tool_calls` に渡る前に捨てられる。

台帳（`COST_LEDGER_PATH`）は append-only の JSONL で、1 行は事実 1 つ。控え（`<台帳>.state.sqlite`）が書いた `requestId` の索引と、会話ログごとの読み終え位置を持つ。区間分割 `split_intervals` は事実の列だけを入力とし、`sessionId` ごとに `(timestamp, request_id)` 順に並べ、`post_marker` を持つ事実で区間を閉じ、区間内で最後に触れた issue へ寄せる。

主の環境の台帳は 159,483 行・約 68 MB で、既に動いている（2026-10-07 時点。行数だけ確認し、中身は見ていない）。

## Goals / Non-Goals

**Goals:**
- 同じ `requestId` の 2 行目以降の issue 番号と投稿の印を事実に反映する。トークンと金額は 1 回分のまま
- 台帳の append-only を保つ。既存の行を書き換えない
- 既に台帳へ書いた行の取りこぼしを、会話ログが残る範囲で補う
- LLM のトークンも `gh` の呼び出しも増やさず、hook を遅くしない

**Non-Goals:**
- 2 行目以降のトークンを数え直す（1 回分だけ数える今の扱いを保つ）
- 会話ログが既に消えた期間の補完（元データが無い）
- `/cost` の出力の書式や合計の定義を変える（#689 の範囲）

## Decisions

### 1. 補足の事実を足す（既存の事実に足し込まない）

後続行ごとに、その行が触った issue 番号か投稿の印を持つときだけ、補足の事実を 1 つ作る。

```
{"request_id": "<元の requestId>#<その行の uuid>", ..., 全トークン 0,
 "issues": [...], "post_marker": ..., "continuation": true}
```

`timestamp`・`session_id`・`is_sidechain`・`repo_id`・`branch`・`model` はその行の値（`build_fact` をそのまま使い、トークン 5 種だけ 0 に置き換える）。`request_id` は先頭の鍵のままなので、台帳の索引（`LEDGER_ID_PREFIX`）はそのまま使える。

**理由**: 補足の事実は事実の列の中の 1 要素にすぎないので、台帳・`split_intervals`・各集計の読み方を 1 つも変えずに使える。トークンが 0 なので金額は増えない。後続行の `timestamp` は先頭行より後ろなので、投稿の印の行で区間が切れる位置は、元の応答が持っていたはずの位置と同じになる。

**却下した案**:
- 先頭の事実に後続行の `issues`・`post_marker` を足し込む。ストリームを読む途中で後続行の到着を待つ必要があり、台帳の既存の行は書き換えられないので、同期の境目を跨いで後続行が来た応答と既存の行を直せない
- 後続行の台帳の行を別の種類（`kind: supplement`）にして読む側で先頭の事実に合流させる。全読み出しの経路（台帳は約 16 万行）に合流の処理が入り、`seen` による重複排除と衝突する

### 2. 補足の事実の鍵は `<requestId>#<その行の uuid>`

同じ会話ログを再読み込みしたとき（控えの消失・`--rescan`）に同じ鍵になり、台帳の索引で重複が排除される。resume で複製された会話ログの後続行も、複製が元の `uuid` を保てば同じ鍵になる。`uuid` が無い行は `timestamp` を使う。どちらも無い行は足さない。

**確認が要る前提**: 複製された履歴の後続行が元と同じ `uuid` を持つこと。実装の最初に実ログで確かめ（件数だけを記録する）、違うなら鍵を `timestamp` に変える（tasks 1.1）。

### 3. 補足の事実はメッセージ数に数えない

`continuation: true` の事実は、`summarise` の `messages`・`per_model[...]["messages"]`・`price_intervals` の `messages`・`cmd_report` のリポジトリ別件数・`cmd_intervals` の件数に数えない。トークンも金額も 0 なので他の値は変わらない。区間の `request_ids` には残す（区間が何でできているかは事実の列のまま）。

### 4. 既存の台帳の行: 書き直さず、補足の行を追記する

主の環境の台帳には、取りこぼした行が既にある。選択肢は 2 つで、台帳は append-only が仕様なので、書き直しではなく追記を採る。

| 案 | 内容 | 判断 |
|---|---|---|
| 書き直す | 台帳を作り直して既存の行に issue・印を足す | **採らない**。append-only（`cost-ledger-persistence`）の変更になり、約 68 MB の台帳を 1 つずつの行の書き換えで壊す事故のリスクを負う。台帳が消えれば取り戻せない |
| 新しい行だけ直す | 今後の同期だけが補足の事実を足す。過去の取りこぼしは放置 | 会話ログがまだ残っている期間の取りこぼしを直せるのに、直さない理由が無い |
| **補足を追記する（採用）** | 新しい行は常に直す。過去分は `ledger-sync --rescan` で会話ログを先頭から読み直し、索引に無い補足の事実だけを追記する | 既存の行は 1 バイトも変わらない。やり直しても索引で重複しない |

`--rescan` は、控えの読み終え位置を使わずに、今読む置き場所の会話ログを全部先頭から読む。台帳の索引は使うので、既存の応答の先頭行は読み飛ばされ、足りない補足の事実だけが追記される。会話ログの保持期間（既定 30 日、#688 で 365 日にする）より古い期間は元データが無く直せない。

**hook では自動で回さない**。全履歴の読み直しは 1 パスで数十秒かかり、Stop hook の `timeout` は 120 秒、実行中に切られると控えが更新されず次の hook がまた同じ読み直しを始める。1 秒以上セッションを止める処理は裏で走らせる、というエピックの制約にも合わない。`--rescan` は人が 1 回だけ明示的に流す。

**戻し方**: `--rescan` の前に台帳の控えを取る（`cp` で別の場所へ）。追記された行は台帳の末尾にまとまっていて、各行に `continuation: true` が付くので、戻すときは控えを元に戻すか、追記前のバイト数で切り詰める。

### 5. 全履歴の取り込みは増えた分だけで、通常の動きは変えない

`facts_from_lines` の `seen` 判定は、既出の `requestId` の行でも `scan_tool_calls` を 1 回呼ぶ形になる。1 行ずつの JSON パースは今も済んでいるので、増えるのは `Bash` の `tool_use` 走査だけ。生の文字列に `"Bash"` が無い行は走査しない（パースの前の文字列の絞り込みと同じ考え方）。所要時間は変更の前後で実測して PR に書く。

## Risks / Trade-offs

- 後続行を数行持つ応答の途中を別セッションの hook が読むことがある（書きかけ）。その後続行は次の同期で補足の事実として追記されるので、取りこぼさない（補足の事実の鍵が行ごとに決まるため）。新しい穴は無い
- 複製された会話ログの後続行の `uuid` が元と違う場合は、補足の事実が重複して区間が 1 つ余分に切れる可能性がある。決定 2 の確認で `uuid` が違うと分かった場合は鍵を `timestamp` にして塞ぐ。確認の結果は PR に書く
- 台帳の行が 1 割弱増える（最大でも `gh issue` を実行した行数 7,623 件／30 日ぶん）。区間の数は増えない（印の行で区間が切れる位置は同じ）
