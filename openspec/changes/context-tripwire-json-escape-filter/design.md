# design — context-tripwire-json-escape-filter

## Context

`plugins/dev-workflow/scripts/context-tripwire.sh` は 2 層でできている。上層は bash で、payload を読んで「サブエージェント発火でなければ python3 を起動せずに exit 0」する早期 exit。下層は python3 で、payload をパースして対象トランスクリプトを導出し、コンテキスト量を測って通知・拒否を出す。

早期 exit があるのは、この hook が install 先の全ユーザーの全ツール呼び出し（PostToolUse は matcher 無し = 全ツール）で走るためで、その大多数はメインスレッド（`agent_id` が payload に無い）である。ここに python3 の起動コスト（数十 ms）を課さないことが早期 exit の唯一の目的で、この目的は spec の Requirement「起動の途中でコンテキストを測る hook」に MUST として書かれている。

現在の判定は生文字列 `"agent_id"` の有無だけを `case` で見る。JSON のキーは同じ文字列を Unicode エスケープでも書けるため（`"\u0061gent_id"` は `json.loads` すると `agent_id`）、この判定は JSON 意味論と一致していない（issue #278）。

## Goals / Non-Goals

**Goals:**

- JSON 意味論的に `agent_id` を持つ payload が、python3 に届かないまま無音で exit 0 することを無くす
- 早期 exit の目的（メインスレッドの通常の payload に python3 起動コストを課さない）を保つ
- 判定の根拠を「必要条件」として説明できる形にする（見つかった 1 表記だけを塞ぐ弥縫策にしない）

**Non-Goals:**

- bash 側で JSON をパースすること（起動コストを課さない目的と両立しない）
- エスケープの並びを含むメインスレッド payload で python3 を起動しないこと（起動してよい。パース後に `agent_id` が無いと判定されて fail-open するだけ）
- 通知・拒否のメッセージ、計測の式、閾値、hooks.json の登録の変更（この change の範囲外）

## Decisions

### Decision 1: issue の 2 択のうち「フィルタを強化する」を採る

issue #278 は「フィルタを強化する」か「この経路は原理的に到達不能だとコメント・設計文書で明示する」の 2 択を挙げている。前者を採る。

到達不能を保証しているのは Claude Code のハーネス側の JSON シリアライズ実装（非 ASCII をエスケープしない出力）であって、このリポジトリで固定できる契約ではない。ハーネスが `ensure_ascii` 相当の出力に変わるだけで穴が開き、そのときコメントは嘘になって、しかも無音で fail-open するので誰も気づかない。強化のコストが `case` の 1 arm とテスト数件で済む以上、契約を他所に預ける理由がない。

### Decision 2: 早期 exit の条件に「`\u00` を含まない」を足す（必要条件で切る）

判定を次の 3 分岐にする（bash の `case`。python3 の起動は依然としてこの後）:

- payload が生文字列 `"agent_id"` を含む → python3 に渡す（従来どおり）
- payload が 4 文字の並び `\u00` を含む → python3 に渡す（今回追加）
- どちらでもない → exit 0（従来どおり）

**なぜエスケープの前置が必要条件になるか**: JSON のキーは文字列リテラルなので、`agent_id` という 8 文字を生の文字以外で書く手段は文字列エスケープしかない。JSON が定める文字列エスケープは `\"` `\\` `\/` `\b` `\f` `\n` `\r` `\t` `\uXXXX` の 9 種で、`\uXXXX` 以外の 8 種が生む文字は `"` `\` `/` とバックスペース・改頁・改行・復帰・タブであり、`agent_id` を構成する英小文字とアンダースコアはどれも作れない。つまり `agent_id` を生表記以外で書いた payload は必ず `\uXXXX` を含む。

**なぜ 2 文字 `\u` ではなく 4 文字 `\u00` で切るか**: `agent_id` の 8 文字は `_`（U+005F）から `t`（U+0074）までの範囲に収まるので、それを綴る `\uXXXX` は上位 2 桁が必ず `00` になる。16 進の大文字小文字の揺れは下位 2 桁にしか現れないため、前置を 4 文字に伸ばしても必要条件としての健全性は変わらず、サロゲートペアや非 Latin-1 のエスケープを除外できる。これは Decision 1 が想定した「ハーネスが `ensure_ascii` 相当の出力に変わる」世界で効く: そこでは日本語を含む payload がすべて非 Latin-1 のエスケープ（`\u3042` 等）を含むため、2 文字条件だと日本語プロジェクトのメインスレッド呼び出しの大半で python3 が起動し、早期 exit の目的が実質失われる。

**なぜこれで目的が壊れないか**: 新たに python3 を起動するのは「`agent_id` を生表記で持たず、かつ生文字列 `\u00` を含む payload」だけである（JSON エンコード由来の `\"` や `\\` では発火しない）。python3 が起動しても `agent_id` フィールドが無いと判定されて何も出力せず exit 0 する。これは現在のコメントが「無害」と書いている既存の誤検知（コマンド文字列に `agent_id` と書いた場合）と同じ向きの外し方である。

**代替案**: (a) bash 側で JSON をパースする → 起動コストを課さない目的と両立しない。(b) `\u0061gent_id` など既知のエスケープ表記を列挙して `case` の arm にする → `agent_id` の 8 文字それぞれに `\uXXXX` 表記があり、複数文字の同時エスケープまで含めると 2^8 − 1 通りで、しかも 16 進の大文字小文字で表記が割れる（列挙は必ず漏れる）。(c) 何もせず到達不能と書く → Decision 1 で退けた。

**大文字 `\u` の扱い**: `\U0061...` のように大文字で書かれた表記は JSON として不正である（`json.loads` が `Invalid \escape` で失敗する。Python 3.14 で実測）。`case` は大文字小文字を区別するので、この payload は python3 に渡らず早期 exit で無音に終わる（JSON として不正なので python3 に渡しても結果は同じ無音 exit 0 であり、扱いを分ける必要はない）。

### Decision 3: 判定は payload 全体に対して行い、キーの周辺だけを見ない

`"agent_id"` の直前直後（`{` や `,`、コロン）を見て精度を上げることはしない。早期 exit は「安く必要条件で切る」ためのもので、精度を上げるほど bash 側に JSON 文法の知識が入り込み、下層のパース結果とずれる余地が増える（#269 で Bash の許可リストが「検査側と実行側のトークン化のずれ」で 2 周連続で破られたのと同じ構図）。判定の正しさは下層の `json.loads` に一元化し、上層は必要条件だけを見る。

## Risks / Trade-offs

- **`\u00` を含むメインスレッド payload で python3 が余分に起動する** → 起動しても無音で exit 0 する（fail-open 経路は既存）。起動の頻度は「低い」とは言えず、**payload の内容に依存する**。PostToolUse の payload には `tool_response` が入るため、Read で読んだファイル内容・Bash の出力・Grep の結果にこの並びがあれば発火する（JavaScript / Python / Java / JSON ソースの Unicode エスケープ表記、正規表現、この change 自身の spec と bats も該当する）。加えて JSON シリアライザは `\b \f \n \r \t` 以外の制御文字を 4 桁 16 進で綴るため、ANSI エスケープを含む出力でも発火する。方向は安全側（余計に起動して無音で終わる）なので設計は変えない。コスト上限は hook 1 回 100ms 未満の既存要件の中に収まる。退行テストで「その並びを含まないメインスレッド payload では python3 が起動しない」ことを固定し、目的が壊れていないことを機械で見る
- **早期 exit の条件が spec の MUST に書かれている** → spec の当該 Requirement を MODIFIED で書き換え、Scenario も条件を明確にした形に更新する。実装だけ直して spec を古いまま残すと、次に読んだ人が「生文字列 `"agent_id"` だけ見ればよい」と戻してしまう
- **エスケープ表記の payload を実際に生成するハーネスは未確認** → issue が非 blocking と明記しているとおり、これは攻撃経路が確認された脆弱性の修正ではなく、外部実装に預けていた前提を自分側の判定に引き取る変更である。この change で挙動が変わるのは「今まで無音だった表記で hook が動く」方向だけで、既存の通知・拒否・fail-open の振る舞いは変えない
- **テスト側の payload 生成が実機とずれている** → 既存の bats ヘルパは `json.dumps` の既定（`ensure_ascii=True`）で非 ASCII をエスケープに潰すため、`mktemp -d` のパスに非 ASCII があると `transcript_path` がエスケープの並びを含み、「早期 exit で python3 を起動しない」テストが環境依存で落ちる。ハーネス（Node の `JSON.stringify`）は非 ASCII をエスケープしないので、ヘルパを `ensure_ascii=False` にして実機に寄せる
