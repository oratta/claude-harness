## Context

条件表の「実機操作でない」は「MFA・OAuth・ログイン・ダッシュボードの操作など、主の手が要る操作を含まない」。通る例の CI の再実行は原因の切り分けを通す条件にしない。節「CI の見張りのやり直しの上限で止まった子」（#1268）は、上限で止まった子に限って、確認が先の推奨と `job-timeout` の `escalate` を主に上げると書く。節の外の読み方と、節と通る例の優先順位が空いている。

## Goals / Non-Goals

- Goals: ランナーの状態の確認を含む推奨を通すか主に上げるかと、節と通る例の優先順位が、基準を読んで一通りに決まる。
- Non-Goals: 見張りの上限自体の変更、条件表への条件追加、`ci-watch.md` の変更、`stop-judge.sh` の変更。

## Decisions

1. **確認の種類で「実機操作」を分ける**: `gh api` や `gh run view` など、親や子が API で読むだけで済む確認（ランナーの登録状態・オンライン・ジョブの待ち時間）は主の手が要らないので「実機操作でない」に当たる。ランナーの機械に入る操作（ログイン、再起動、プロセスやディスクの確認と操作、設定変更）が要る確認は、主の手が要る操作として当たる。種類が判断できなければ当たる側に倒す（「迷ったとき」と同じ向き）。
2. **確認を含む推奨から再実行だけを切り出せる条件**: 再実行の可否が確認の結果に依らず、再実行だけで推奨が完結するときは切り出して通す（再実行は戻せるに含まれ、原因の切り分けを通す条件にしない決まりと同じ）。返事は再実行だけを送り、機械での確認は求めない。推奨が「確認して結果に応じて再実行」「直してから再実行」のように再実行が確認や操作の結果に依るとき、または切り出しても失敗の原因が分からないまま同じ失敗を重ねるだけのときは切り出さず、機械での確認が要るものは主に上げる。却下案: 確認を含む推奨は常に主に上げる（通る例の趣旨と食い違い、主の手間だけが増える）、常に再実行へ書き換えて通す（推奨と違う返事を親が作ることになる。切り出しは推奨の中に独立した再実行が書かれているときに限る）。
3. **優先順位**: 子の記録の `止まった理由:` が見張りのやり直しの上限を挙げている止まり（`job-timeout` の `escalate` と手順 7 の 2 経路に限らず、節の対象全体）は、節が通る例の「CI の再実行」より先に効く。通る例の「原因の切り分けを通す条件にしない」は、節の対象の止まりには当てない。理由は、上限で止まった子の再実行は、見張りが既に 1 回やり直した後の 2 回目で、因果の説明（失敗が差分と因果を持たない）が追加のやり直しを許す根拠になっているから。子の記録が「原因は断定できない」と書いて再実行だけを勧めた場合も節の対象で、節の「通す場合」の因果の説明が子の記録にないので通さず主に上げる。
4. 条件表は増やさず、追加は文章の段落と節への一段落に限る。`epic-dispatch.bats` が表の行数（見出し＋9 行）を数えるため。
5. 公開版の部品なので、他リポジトリの org 名や issue 番号を例に書かない。

## Risks / Trade-offs

- 節の対象で原因が断定できない再実行を主に上げるので、主の手間が増える。ただし 1 回目のやり直しが既に済んでいるので、同じ失敗を重ねる前に主が見る価値がある。
