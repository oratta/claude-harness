## Context

`worker/implement.md` の「全経路共通の大原則」は、対象リポジトリの `.github/workflows/*.yml` / `*.yaml` のうち PR・push で起動するジョブの `run:` から検査コマンドを拾い、すべて手元で実行するよう求めている（PR #489 で CI の shellcheck を作業者が取りこぼしたのがきっかけ）。claude-harness の CI は lint（`scripts/lint.sh` と `scripts/test-auto-merge-workflow.sh`）と、bats の全体を `TEST_SHARD=k/4` で 4 つのジョブに分けた `scripts/test.sh` を回す。手元でこれを全部回すと `scripts/test.sh` が直列で約 40 分かかる。

レビュアーへの指示（`stages/reviewer-brief.md` 2-1）は「テスト・lint は報告を信用せず自分で再実行する」と書き、範囲を決めていない。ゲートの担当の動作確認（`stages/pass.md` 手順 4）は受け入れ条件ごとに自力で検証させるので、受け入れ条件に「`bash scripts/test.sh` が通る」があると全体を回すことになる。#1208 ではこの 3 者と本体がそれぞれ全体を回した。

ゲートの合格後は、本体が `references/ci-watch.md` の手順で CI を見張り、PR に関わる失敗なら作業者に直させ、ゲートを取り直す。auto-merge を配備したリポジトリでは必須チェックが緑になるまでマージされない。

develop は claude-harness 以外のリポジトリでも使われ、CI の構成（テストランナー、Draft で CI を走らせるか、そもそも CI があるか）はリポジトリごとに違う。

## Goals / Non-Goals

**Goals:**

- 作業者・レビュアー・ゲートの担当のどれも、手元で全体のテストを回さないようにする
- 作業者が CI の検査を取りこぼさない仕組み（CI の定義から拾う）と、lint の取りこぼし（PR #489）を防ぐ効き目を残す
- 規則を develop を使うどのリポジトリでも通じる形で書く（コマンド名をリポジトリ固有の値に固定しない）

**Non-Goals:**

- `scripts/test.sh` の並列化（D5）
- 関係するテストを機械で選ぶスクリプトを作ること。選び方は手順として書き、作業者が grep で選ぶ
- CI の見張り（`references/ci-watch.md`）の手順を変えること

## Decisions

### D1: 手元で回すものと CI に任せるものの線をどこに引くか

CI の定義から拾った検査を 3 つに分ける。

| 種類 | 手元での扱い |
|---|---|
| テストの全体実行（テストランナーをファイルで絞らずに起動するもの。claude-harness では `scripts/test.sh`） | 回さない。関係するテスト（D2）に置き換え、全体は CI に任せる |
| lint・型検査などの静的検査 | 回す。ツールがファイルを引数に取れるなら変えたファイルに当て、取れないなら CI と同じ形で回す |
| ビルド | 回さない。CI に任せる |

加えて、仕様化した change では `openspec validate <change> --strict` を回す（今までどおり）。

選んだ理由: 時間の大半は全体のテストで、lint は数分で終わり、PR #489 で取りこぼしたのは lint だった。lint を残せば元の事故は防げる。ビルドは主の指示と issue の概要が手元で回すものに挙げておらず、リポジトリによっては長いので CI に任せる。

退けた案: (a) 所要時間の目安（例: 5 分以内なら手元で回す）で線を引く。リポジトリや機械の混み具合で同じ検査が線の両側に動き、作業者の判断が揺れる。(b) CI の検査を全部 CI に任せる。lint の取りこぼしで、ゲート合格後に CI が落ちて W・レビュー・G をもう 1 周回す事故（PR #489）が戻る。

フォールバック: 対象リポジトリに、PR・push で起動してテストの全体実行をするジョブが無いとき（workflow が無い、テストのジョブが無い、検査コマンドを判別できない）は、全体のテストを CI に任せられないので、今までどおり手元で全体を回す（`scripts/test.sh` 等の慣例コマンドへのフォールバックも今までどおり許す）。Draft では CI を走らせないリポジトリは、Ready にした時点で CI が走るので「CI に任せられる」側に数える。

### D2: 関係するテストの選び方

作業者は次の和集合を関係するテストとし、テストランナーにファイルを渡して回す（claude-harness なら `bats <file>`）。

1. この変更で足した・変えたテストのファイル
2. テストのファイルのうち、変えたファイルのパスかファイル名を含むもの（`git grep -l` で探す。探したコマンドを return に書く）
3. テストランナーが変えたファイルから関係するテストを選ぶ機能を持つなら、その結果（例: `jest --findRelatedTests`）

選んだ理由: claude-harness の bats はテスト対象のファイルをパスで読むものが大半で、パスかファイル名の grep で拾える。他のリポジトリでも、テストが対象を名前で参照する慣習は広い。機械で選ぶスクリプトを作らないのは、リポジトリごとにテストの置き場と書き方が違い、汎用にすると作るものが大きくなるため（Non-Goals）。

退けた案: テストのディレクトリ単位（例: `plugins/dev-workflow/tests` 全体）で回す。claude-harness の dev-workflow のテストは数十ファイルあり、絞り込みの効果が薄い。

### D3: レビュアーの再実行の範囲

「報告を信用せず自分で再実行する」は残し、再実行するのは関係するテスト（D2 の選び方）と lint に限る。全体のテストは回さず、全体の結果は作業者の return か CI の結果を見る。区画に分けたレビューで再実行するのが区画 1 だけという既存の規則はそのまま。

選んだ理由: レビュアーが自分で回す目的は作業者の報告の裏取りで、作業者が回したものと同じ範囲を回せば足りる。全体は CI が別に回す。

### D4: ゲートの担当の動作確認で全体のテストをどう扱うか

ゲートの担当は手順 4 で全体のテストを手元で回さない。受け入れ条件が全体のテストの合格を求めるとき（例: 「`bash scripts/test.sh` が通る」）は、対象 HEAD に付いた CI の結果（`gh pr checks` と run の URL）を証拠にする。

- 対象 HEAD の CI が成功していれば、run の URL を結果の欄に書く
- CI の結論がまだ無い（実行中、または Draft のため未実行）ときは、その状態と、合格後の CI の見張り（`references/ci-watch.md`）で結論を確かめることを結果の欄に書いて進める
- 対象 HEAD の CI が既に失敗していれば、結果の欄を成功の印にせず、失敗した run の URL と、合格後の CI の見張りで直しに回すことを書く。結論の無い CI や失敗した CI を成功として書かない

関係するテストと lint の結果は、作業者の return（PR に載った証拠）を使ってよい。

選んだ理由: ゲートの合格後に CI を見張って落ちたら直す仕組みと、auto-merge の必須チェックが既にあるので、ゲートが CI の結論を待つ必要は無い。待たせると、Draft では CI を走らせないリポジトリで手順 4 が進めなくなる。CI が既に落ちている場合も合格処理を止めないのは、合格後の見張りが、PR に関わる失敗なら passed を外して作業者に直させてゲートを取り直し、関わらない失敗（たまに落ちるテスト）ならやり直す判定を既に持っているからで、ゲートで止めても直したあとのゲートの取り直しは同じ 1 周になる。止める側にすると、合格処理の段から作業者へ戻す新しい返り方（今の合格処理の段が返すのは passed と保留だけ）と、たまに落ちるテストの判定をゲートの側にも作ることになる。

退けた案: (a) ゲートの担当が CI の結論が出るまで前景で待つ。claude-harness なら 5 分ほどで済むが、Draft で CI を走らせないリポジトリでは結論が出ない。(b) 対象 HEAD の CI が落ちていれば合格処理を止めて作業者に返す。上の理由で、得るものが無く返り方を増やす。

この選び方で確定すること: auto-merge を配備していないリポジトリでは、CI が落ちたまま passed が付いている時間がある。その間に人がマージしうるのは、合格後の見張りが passed を外すまでのあいだで、GitHub の PR の画面には CI の失敗が出ている。

### D5: `scripts/test.sh` の並列化は範囲に入れない

この変更で作業者・レビュアー・ゲートの担当のいずれも手元で全体のテストを回さなくなり、並列化で縮む待ちが残らない。手元で全体を回したい人は、今の `scripts/test.sh` でも `TEST_SHARD=k/N` を別々の端末で起動すれば同じことができる。

## Risks / Trade-offs

- [関係するテストの選び方（D2）が、変えたファイルを間接的に読むテスト（別のスクリプトを経由して読むもの）を拾えず、CI で初めて落ちる] → ゲート合格後の CI の見張りが直しに回す（`references/ci-watch.md` の `fix`）。1 回起きると CI の 1 周（claude-harness で約 5 分）と直しの 1 周が増える。頻度は分からない。調べ方は、この変更のあとの PR で CI の見張りが `fix` を返した回数と、そのうち手元で回さなかったテストが落ちた回数を数える
- [CI を持つが lint をファイルで絞れないリポジトリでは、lint が全体を回す] → lint は数分で終わる想定で、全体のテストの待ちより短い。今と比べて遅くはならない
