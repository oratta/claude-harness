## Context

`git-destructive-guard.sh` の決定部（`plugins/dev-workflow/scripts/git-destructive-guard.sh` 730-776 行）は次の順で `permissionDecision` を決めている。

1. payload の `agent_id` が空でない文字列（子の呼び出し）なら `deny`
2. そうでなければ `DEV_WORKFLOW_GIT_GUARD_FORCE` が `ask` / `deny` ならその値
3. そうでなければ `permission_mode` が `default` / `acceptEdits` / `plan` / `bypassPermissions` なら `ask`、それ以外は `deny`

flatmate の住人は `boot.sh` が組み立てた `--dangerously-skip-permissions --remote-control <agent> ...` で対話 TUI として起動し、tmux に常駐する。payload の `permission_mode` は `bypassPermissions` になり、3 で `ask` が返る。オーナーは Discord だけを見ているので、確認画面は誰にも押されない。オーナーの対話セッション（Orca や端末で直接開いたもの）も `bypassPermissions` になりうるので、payload の値だけでは両者を見分けられない。

`boot.sh` は claude を起動する前に `AGENT_NAME`・`FLATMATE_DIR`・`TASK_STORE_MODE` などを `export` しており、起動する側が claude の環境に値を入れる経路は既にある。hook のプロセスは claude の環境を引き継ぐので、hook から環境変数として読める（`DEV_WORKFLOW_GIT_GUARD` / `DEV_WORKFLOW_GIT_GUARD_FORCE` と同じ経路）。

rules/destructive-git-guard.md の「hook との分担」節は「サブエージェントから呼ばれたときは確認画面を出さずに拒否されるので、子は打ち直さず作業を止めて親に返る」と書いており、#1108 で入った実装（1 の分岐）と一致している。この変更でこの文は変えない。

## Goals / Non-Goals

**Goals:**

- 画面を見ている人のいないセッションを、起動する側が付ける印で見分ける方法を spec に定める
- 印のあるセッションでは、対象の 9 種が確認画面を出さずに `deny` になり、拒否理由がチャンネルでオーナーに承認を求めるよう案内する
- 印の無いオーナーの対話セッションでは今までどおり `ask` を返す
- flatmate の住人の起動で印が付くよう、flatmate 側の作業を起票する

**Non-Goals:**

- flatmate の `boot.sh` を直すこと（別リポジトリ。起票までがこの change の範囲）
- 住人が tmux などで起動する別のセッション（エピックの子など）に印を引き継ぐこと。起動部品の差し替えは #1123、住人が develop を使うときの決まりは #1126 で扱う（下の「Risks」）
- 承認されたあと住人がそのコマンドを実行できるようにする経路。ルールどおり、承認されてもオーナーが自分で実行する
- 印を develop のモード判定など git ガード以外で読むこと（#1126 で同じ印を使ってよいように、名前を git ガード専用にしないだけにとどめる）

## Decisions

### 無人の見分け方は、起動する側が付ける環境変数 `DEV_WORKFLOW_UNATTENDED`

- 採る: 環境変数。住人を起動する `boot.sh` が `export DEV_WORKFLOW_UNATTENDED=1` してから claude を起動する。hook はこの値を読む
- 採らない: `permission_mode` が `bypassPermissions` なら一律 `deny`。オーナーの対話セッションでも確認画面から承認できなくなり、受け入れ条件「オーナーの対話セッションでは今までどおり ask」に反する
- 採らない: payload のほかの値（チャンネル経由の発言に付く値など）や、親プロセスが tmux かどうかで推し量る。payload にはセッションに画面を見ている人がいるかを表す値が無く、オーナーも tmux の中で claude を開くことがあるので、推し量りは両方向に外れる。誰が見ているかを知っているのは起動する側だけである
- 採らない: 既存の `DEV_WORKFLOW_GIT_GUARD_FORCE=deny` を住人に恒久設定する。FORCE は実機確認と bats のための上書きで恒久設定にしない約束になっており、理由文も「入力欄で `!` を付けて打つ」と、画面の前に人がいる前提の案内になる

名前は `DEV_WORKFLOW_GIT_GUARD_*` にせず `DEV_WORKFLOW_UNATTENDED` にする。印の意味は「このセッションの画面を見ている人がいない」というセッションの性質で、git ガードの設定ではないため（#1126 の住人向けの決まりが同じ印を読む余地を残す）。

### 値の読み方: 未設定・空・`0` は印なし、それ以外は印あり

印を付ける側が `1` 以外の値（`true`・`yes` など）を書いた場合に、印なしとして扱うと確認画面で止まる元の事故に戻る。印ありとして扱えば、誤って付いたときに起きるのは「確認画面の代わりに拒否される」で、止めすぎる向きにしか外れない。`0` だけを打ち消しとして認めるのは、起動する側が一時的に印を外したいとき（`DEV_WORKFLOW_UNATTENDED=0`）の書き方を 1 つ用意するため。値の前後の空白は除いてから比べる（`DEV_WORKFLOW_GIT_GUARD_FORCE` の読み方と同じ）。

### 判定の順: 子 → 印 → FORCE → permission_mode

- 子の呼び出しは今までどおり最初に決める。印のあるセッションで起きた子も子の理由文（親に返る）を受け取り、拒否の回数も数える。子は親に返し、主に上げるのは親の役目という分担を変えないため
- 印は FORCE より先に見る。FORCE=ask が残った住人のセッションで確認画面を出して止まらないため（子を FORCE より先に見る理由と同じ）
- 印の無いセッションは FORCE と `permission_mode` の規則のまま変えない

### 印のあるセッションへの理由文

主の呼び出しの `deny` の文面は「入力欄で `!` を付けて打つか、自分の端末で」と画面の前に主がいる前提で書かれている。印のあるセッションでは、住人がオーナーに届く経路はチャンネルだけなので、次を書く: このコマンドは実行していない／何を・なぜ・いつ実行するかをチャンネル（Discord など）でオーナーに伝えて承認を求める／承認されたらオーナーが自分で実行する（住人自身は実行しない）／言い換えたコマンドで再実行しない。確認画面を出している旨は書かない（出していないので、住人が画面の操作を待って止まる余地を残さない）。当たった操作の種類・規範の正本・判定しきれなかった入れ子の文面（`head`）は、印の無い主の呼び出しと共通にする。

## Risks / Trade-offs

- [起動する側が印を付け忘れると、住人は今までどおり確認画面で止まる] → flatmate の起票で、`boot.sh` の起動経路すべて（再起動ループ・既定の引数列への退避の経路を含む）で claude の環境に印が入ることをテストで確かめることを受け入れ条件に入れる
- [住人が tmux で別に起動したセッション（エピックの子など）は、tmux のサーバーの環境を引き継ぐので住人の `export` が届かず、印が付かない] → この change では塞がない。#1123（起動部品の差し替え）と #1126（住人が develop を使うときの決まり）で、起動部品が子のセッションに印を渡すことを扱うよう、#1124 の完了報告とエピック #1122 にこの穴を書き残す
- [オーナーが住人の画面を Remote Control や tmux attach で見ていても、印のあるセッションでは確認画面が出ず、承認しても住人は実行できない] → 許す。オーナーは自分で実行する（ルールどおり）。印が付くのは起動する側が「人が見ていない」と決めたセッションだけである
- [rules の文が増えて常時注入の量が増える] → 1 文の追加で、現在の合計 38,920 バイトに対し予算 40,260 バイトの範囲に収まる見込み。超えたら予算ファイルを動かさず文を縮める
