## Context

`epic-dispatch.sh launch <epic> <child>...` は、渡された子のうちワークツリーがまだ無い子をすべて起動する。親（`/develop <エピック>` の本体）は依存の解けた開いた子を毎回すべて `launch` に渡し、起動済みの子は `skipped` で見分ける。`launch` 自身は状態を持たず、`orca worktree list --json` を読んで判断している。子の状態はワークツリーに付く印で分かる: 完了の印は `workspaceStatus` が `completed`（`mark done`）、主の返事待ちで止まった印は `comment` が `epic-stopped`（子が付ける）か `epic-stopped-seen`（親の `wait` が受けた）、止まりから戻ると `epic-resumed`。親の `launch` が作った子は `parentWorktreeId` が親のワークツリーの id になる（`reap` がこれで親の子かを確かめている）。

サブエージェント方式（Orca が無い・Orca 管理外）では、本体が子ごとに 1 ループを並列に起こす。ここにも上限が無い。

### 実測（2026-10-20、オーナーの Mac）

| 項目 | 値 |
|---|---|
| 物理メモリ | 32 GiB（`sysctl -n hw.memsize` = 34359738368）、CPU 10 コア |
| 同時に動いていた Claude Code のプロセス | 36 個、RSS の合計 8,547 MB |
| 1 セッションの RSS（本体のプロセスのみ） | 146〜404 MB、中央値およそ 215 MB |
| 1 セッションの RSS（子プロセスを含む） | 最大 564 MB（子プロセス 17 個） |
| サブエージェントを 1 体動かしている最中のセッション（この仕様を書いた作業のセッション） | 400〜430 MB |
| セッションが起こす子プロセス 1 個 | 多くは 20〜40 MB、最大は codex の 101 MB |
| そのときの空きメモリ | `memory_pressure` の free 45% |

測り方: `ps -axo pid,ppid,rss,comm` の `comm` が `claude` のプロセスごとに、自身の RSS と、親をたどってそのプロセスに行き着く子孫の RSS の合計を出した。

測れていないもの: 子のセッションが動かすテストやビルドの山（Next.js のビルドや Playwright など、flatmate 側の重い処理）。この Mac では同時に走っていなかった。

## Goals / Non-Goals

**Goals:**

- 着手できる子が上限より多いとき、上限まで起動して残りを後回しにし、どの子を後回しにしたかを出力する
- 枠が空いたら（子が閉じた・完了の印が付いた・主の返事待ちで止まった）、親が後回しの子を起動する
- 設定が無くても、PC のメモリ量に合った既定値で動く
- サブエージェント方式でも同じ上限を使う

**Non-Goals:**

- 客の Mac で値を設定する置き場（住人の `.env` など）の配線（flatmate 側の子 issue）
- 動いている子の実際のメモリ使用量を見て止める仕組み（上限は件数で抑える）
- 主の返事待ちから戻った子を、枠が空くまで止めておくこと（後述のトレードオフ）
- 1 つの子の中で change ごとに W を並列に起こす場合の数の制御（エピックの子をまたいだ数だけを抑える）

## Decisions

### 1. 環境変数の名前は `EPIC_DISPATCH_MAX_PARALLEL`

`epic-dispatch.sh` の設定はすべて `EPIC_DISPATCH_` で始まる（`EPIC_DISPATCH_MODEL`・`EPIC_DISPATCH_BASE` など）ので揃える。値は 1 以上の整数。0・負数・数字以外・空文字は使い方を出して exit 1（`EPIC_DISPATCH_IDLE_COMPACT_MIN_TOKENS` と同じ扱い。上限は設けない）。「上限なし」を表す特別な値は作らない（大きな数を書けば同じになる）。

### 2. 既定値は物理メモリから決める: `floor(物理メモリの GiB / 4)`、最小 1。読めなければ 2

案は 2 つあった。

- 固定値（例: 3）: 実装は簡単。ただし 32 GiB の Mac では遅すぎ、8 GiB の Mac では 3 でも多すぎるおそれがあり、どの値でもどちらかの環境で外れる
- メモリ量から決める: 環境ごとに合う。読み方（macOS は `sysctl -n hw.memsize`、Linux は `/proc/meminfo` の `MemTotal`）の分岐が要る

メモリ量から決める案を採る。客の Mac はメモリ量がまちまちで、設定なしで安全側になることが目的だから。

式の根拠: 子 1 件に 2 GiB を見込み、物理メモリの半分を子に充てる（残りの半分は OS・ブラウザ・Orca・親のセッション用）。2 GiB の内訳は、実測した 1 セッションの子プロセス込みの最大 564 MB を切り上げた 0.5 GiB と、測れていないテスト・ビルドの山の見込み 1.5 GiB。結果として 8 GiB → 2、16 GiB → 4、32 GiB → 8、64 GiB → 16 になる。

メモリ量を読めないとき（`sysctl` も `/proc/meminfo` も無い・数字でない）は 2 にする（8 GiB の Mac の値と同じで、最小の構成に合わせる）。stderr に読めなかったことを出す。

オーナーは 2026-10-19 に 32 GiB で 15 件を同時に動かして落ちていないので、既定の 8 は控えめな側にある。それより多く動かしたいときは `EPIC_DISPATCH_MAX_PARALLEL` で上げる。

### 3. 上限の値を出すサブコマンド `max-parallel` を足す

サブエージェント方式では本体（LLM）が自分で数を抑えるので、既定値の計算を手順書に書き写すと二重管理になる。`epic-dispatch.sh max-parallel` が実際の値（環境変数か既定値）を stdout に 1 行で出し、本体はそれを使う。`launch` も同じ関数で値を決める。`max-parallel` は orca も gh も呼ばない。

### 4. 「枠を使っている子」は orca の一覧から毎回数える

案は 2 つあった。

- 親が動いている子の番号を `launch` に渡す（例: `--running 11 12`）: `launch` は数えなくてよい。ただし親が起動し直したときや、親の覚えている集合とずれたとき（`failed` で残ったワークツリーなど）に数が狂う
- `launch` が `orca worktree list --json` から数える: 親の記憶に頼らず、起動し直した親でも同じ数になる

一覧から数える案を採る。`launch` は今も状態を持たずに一覧で `skipped` を決めているので、同じ作りに揃う。

数える対象は、一覧のワークツリーのうち、同じ `repoId`・`parentWorktreeId` が今のワークツリーの id（`orca worktree current --json` の `.result.worktree.id`）・`isArchived` が true でない・`linkedIssue` があるもの。そのうち次をすべて満たすものを「枠を使っている子」とする。

| 子の状態 | 数えるか | 理由 |
|---|---|---|
| 完了の印（`workspaceStatus` が `completed`） | 数えない | 子のループは終わっていて、親の `reap` がすぐ端末を閉じる。サブエージェントもテストも動かない |
| issue が閉じている（`gh api repos/{owner}/{repo}/issues/<N> --jq .state` が `closed`） | 数えない | 子の仕事は終わっている。完了の印より先に閉じることがあり、数えると受け入れ条件「1 件閉じると 1 件起動される」を満たせない。閉じたのに印を付けずに子のセッションが落ちた場合に枠を永久に塞がないためでもある |
| 主の返事待ちで止まった印（`comment` が `epic-stopped` / `epic-stopped-seen`） | 数えない | 止まった子のセッションは入力待ちで、サブエージェントもテストも動かない（実測ではアイドルのセッションは 146〜404 MB）。数えると、主の返事が遅れるあいだ枠が塞がり、他の子が進まなくなる |
| それ以外（動いている子。`epic-resumed` の印の子を含む） | 数える | |
| issue の state を読めない（gh が失敗・出力が `open` / `closed` 以外） | 数える | メモリを守る側に倒す。stderr に読めなかった子を出す |

今のワークツリーの id が取れないときは、数える対象が 0 件になる（stderr にその旨を出す。実機の orca は id を返すことを `reap` が前提にしている）。

### 5. 後回しの子は `deferred <N>` の 1 行で出す

`launch` の stdout は子ごとに `launched` / `skipped` / `failed` の 1 行という形を保ち、4 つめの語 `deferred <N>` を足す。親は今の手順と同じく 1 行ずつ読んで分ければよい。後回しは失敗ではないので exit code に影響しない（`failed` が無ければ exit 0）。

あわせて stderr に 1 行で、上限・その出どころ・数えた子を出す（例: `max parallel 2 (EPIC_DISPATCH_MAX_PARALLEL); in use 1: #11`）。全部が後回しになったのに親が動いている子を知らないとき、何が枠を塞いでいるかを主に示すため。

枠の割り当ては引数の順で行う。重複した番号と既存のワークツリーがある子は今までどおり `skipped`（枠を新たに使わない。既存のワークツリーが動いていれば、すでに数に入っている）。それ以外の子は、空き枠が残っていれば `orca worktree create` 以降に進み、結果（`launched` か `failed`）にかかわらず空き枠を 1 つ減らす（`failed` でもワークツリーが残り、次の数え直しでは数に入りうるため）。空き枠が無ければ create を呼ばずに `deferred <N>`。

### 6. 親の手順: 起こされて枠が変わる処理をしたら、後回しの子を `launch` に渡し直す

枠が空くのは、`wait` が `done`（手順 3）・`closed`（手順 4）・`stopped`（手順 8）を返したとき。手順 4 はもともと依存グラフを読み直して解けた子を `launch` するので、後回しの子もそこに含まれる。手順 3 と手順 8 の処理のあと、2 に戻る前に、後回しの子が残っていれば、依存の解けた開いた子を `launch` に渡し直す（起動済みは `skipped`、まだ枠が無ければまた `deferred`）。後回しの子は `wait` の位置引数（動いている子）にも `--watch-done`（片付け待ち）にも入れない。

`launch` のあと動いている子も片付け待ちの子も 0 件なのに後回しの子が残るときは（親が知らないワークツリーが枠を塞いでいる）、待たずに主に報告する。報告には `launch` の stderr の数えた子を添える。

起動し直した親（手順 7）は、今までどおり依存の解けた開いた子を `launch` に渡すので、後回しの子はその出力で分かる。後回しの子の一覧はどこにも保存しない。

### 7. サブエージェント方式: 本体が `max-parallel` の値で、同時に 1 ループを回す子の数を抑える

サブエージェント方式の開始時に `epic-dispatch.sh max-parallel` を 1 回呼び、その値を上限にする。子の 1 ループは、最初の W を起こしてから、子の PR がマージされる・子 issue が閉じる・子が主の返事待ちで保留に入る、のどれかまで枠を使う。枠が空いたら、依存の解けた次の子の 1 ループを起こす。1 つの子のループで同時に動く W は 1 人なので、同時に動く W の数は上限を超えない。

主の返事を受けて保留から戻る子は、枠の空きを待たずに再開する（Orca 経路で止まった印から戻った子と同じ扱い）。

## Risks / Trade-offs

- [止まった子が戻ると上限を超える] 主の返事待ちで止まった子を数えないので、戻った子の分だけ一時的に上限を超えうる（超える数は、止まっていた子の数まで）→ 止まった子はアイドルで、戻るのは主が返事をしたときだけ。数えると返事が遅れるあいだ全体が止まるので、こちらを飲む
- [テスト・ビルドの山を測れていない] 2 GiB の見込みのうち 1.5 GiB は実測ではない → 既定値の式と見込みを文書に書き、足りなければ `EPIC_DISPATCH_MAX_PARALLEL` で下げられるようにする。重いビルドを子ごとに同時に走らせるリポジトリでは客側で下げる
- [`launch` の gh の呼び出しが増える] 親の子のワークツリー 1 件ごとに `gh api` を 1 回呼ぶ → 件数は上限と片付け待ちの数ほどで、数件〜十数件。失敗しても数える側に倒すだけで、`launch` は止まらない
- [ワークツリーの id を読めない orca] 数える対象が 0 件になり、上限が新しく起動する数にだけ効く → stderr に出す。`reap` も同じ id を前提にしているので、壊れていれば片付けも止まって気づける
