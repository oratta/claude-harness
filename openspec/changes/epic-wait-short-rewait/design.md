## Context

動機は proposal.md の Why。ここでは今の作りと制約だけを書く。

- `epic-dispatch.sh wait`（`cmd_wait`）は、上限を `--timeout` → `EPIC_DISPATCH_TIMEOUT` → 既定 21600 の順で決め、`SECONDS`（bash の経過秒。壁時計で進むので PC が寝ていた時間も数える）で上限を判定する。ポーリングの間隔の既定は 300 秒で、「経過 + 間隔 > 上限」なら眠らずに `timeout` で終わる
- 親は手順 2 で `wait` を `run_in_background: true` で起動してターンを終え、`wait` が終わると起こされる。今の手順 5 は、`timeout` で起こされたら子 issue の `needs-approval` と止まっている旨のコメントを見て、あれば主に報告してから掛け直す。子エピックの行（`後で別に起動するエピック: #N`）で子を外す確認も `timeout` と `closed` の両方で行う
- 子が主の返事を待って止まったことは、子の印（`mark stopped`）を `wait --watch-stopped` が拾い、`--resolve` が判断を呼び、通せなければ `stopped` で親を起こす（要件「epic-dispatch.sh は子が止まった印を付け、wait が止まった子を返す」）。`needs-approval` の確認は、子が印を付けずに止まったときの予備の手がかりで、待ちをやめる直前の確認にも入っている
- Claude Code のトランスクリプトの assistant の行は `message.usage.cache_creation` に `ephemeral_5m_input_tokens` と `ephemeral_1h_input_tokens` を持つ（2026-10-26 にこの worktree のトランスクリプトで確認。キャッシュを書かなかった行は両方 0）。サブエージェントのトランスクリプトは `<置き場>/<セッション>/subagents/*.jsonl` に分かれる
- 子のワークツリーのトランスクリプトの置き場は `transcript_dir`（`CLAUDE_PROJECTS_DIR` か `CLAUDE_CONFIG_DIR/projects` の下、パスの英数字以外を `-` にした名前）で求めていて、親のワークツリーにも同じ求め方が使える。判断のモデル呼び出し（`stop-judge.sh`）は `--no-session-persistence` なので、親のワークツリーにトランスクリプトを残さない

## Goals / Non-Goals

**Goals:**

- 子に動きの無い間、親が 1 時間より短い間隔で起き、1 回の Bash の呼び出しで `wait` を掛け直すだけでターンを終える
- 親のキャッシュの有効期限が 5 分のとき（使用量の超過中・5 分に固定した人）は、今の 6 時間の上限に戻す
- キャッシュの有効期限を読む関数を、順番 2 の change が子のワークツリーにそのまま使える契約にする

**Non-Goals:**

- 子への声かけ（順番 2 の change `epic-child-cache-keepalive`）
- #1323 の範囲（子のアイドル時のコンパクトを切ること、60 分以上止まった子を起動し直すこと）。`reply-after-idle.md` の閾値の表と、そのまま送るか起動し直すかの表は触らない
- `wait` の出力の 1 行（`closed`・`done`・`stopped`・`unrecorded`・`timeout`・`error`）と exit code の契約は変えない
- 効果の測定（#1324 のやること 13）は実装後のエピック 1 本分で行い、この change の作業には入れない

## Decisions

### D1. 短い上限は `wait` の既定で持ち、親は `--timeout` を付けない

上限の既定を、`wait` が起動の時点で親のキャッシュの有効期限から決める。`--timeout` か `EPIC_DISPATCH_TIMEOUT`（空でない値）があれば、今までどおりその値を使い、有効期限は読まない。

- 退けた案: `references/epic.md` の手順 2 で親が `--timeout 2700` を付ける。使用量の超過中かどうかを親（LLM）が毎回トランスクリプトから判断することになり、判断の費用と読み違えが出る。`wait` が LLM なしで読めば、掛け直しのたびに判定し直せる
- 退けた案: `EPIC_DISPATCH_TIMEOUT` の既定を 2700 に変えるだけにする。超過中に 45 分ごとに起きて、そのたびに会話全体を書き直すことになる

### D2. 短い上限は 2700 秒、長い上限は 21600 秒

- キャッシュの有効期限は最後のリクエストから 1 時間。`wait` は背景で起動された直後から数え、上限の手前のポーリング（間隔 300 秒）と gh の呼び出しの時間が少し足される。親が起動コマンド（`cld`）で入れるアイドル時のコンパクトは最後のリクエストから約 54 分で走る（`reply-after-idle.md`）。2700 秒なら、起きるのは最後のリクエストから約 45〜46 分で、コンパクトの前に 8 分ほどの余裕が残る
- 退けた案: 3000 秒（issue の「50 分前後」）。コンパクトまでの余裕が 4 分ほどで、`--resolve` の判断の呼び出しや gh の遅れで超えうる。コンパクトが走ると親の判断の流れが要約に置き換わる
- 長い上限は今の既定の 21600 秒のまま。超過中は起きる回数を減らすほど安い（起きるたびに書き直す）ので、今より長くしてもよいが、子が印を付けずに止まったときの手がかり（手順 5 で外す `needs-approval` の確認）がもう無いので、これ以上長くはしない

### D3. 有効期限は、親のトランスクリプトで最後にキャッシュを書いた行から読む

`cache_ttl_of <ワークツリーのパス>`（下の契約）が `5m` を返したら長い上限、`1h` を返したか判定できなかったら短い上限にする。

- 最新の行ではなく「最後にキャッシュを書いた行」を見る理由: 書き込みの無い行（`ephemeral_5m_input_tokens` と `ephemeral_1h_input_tokens` がどちらも 0）からは有効期限が分からない
- 両方が正の行は `1h` とする。これは確かめた事実ではなく、この判定の限りとして置く。Claude Code の文書は超過中に「main conversation を 5 分に落とす」と書いており、超過中でも system prompt 側の書き込みだけが 1 時間のまま残るなら、両方が正の行が出る。そのとき `1h` と読んで短い上限で起き、1 回分の書き直し（損の側）を払う。ただし次に起きたターンでは会話が 5 分で書き直され（system prompt 側は 1 時間のキャッシュの読み出しになり書き込みが出ない見込み）、その行は `5m` と読めるので、次の掛け直しから長い上限に戻る。外れても 1 回で戻る
- 判定できないとき（トランスクリプトが無い・書き込みの行が無い・python3 が無い・読めない）は短い上限にする。外れたときの損は、超過中に 45 分ごとに起きて書き直す費用で、6 時間に 8 回ほど。逆に倒すと、超過していないのに 6 時間眠ってキャッシュを切らす（この change で減らしたい費用そのもの）。#1324 が狙うのは後者なので、判定できないときは短いほうに倒す
- この判定は「使用量の超過中か」ではなく「親の会話のキャッシュの有効期限が今 5 分か」を見ている。結果として次のとおりに振る舞い、どれも上限の選び方として正しい側になる
  - 超過中で、有効期限を固定していない: Claude Code が 5 分に縮める → `5m` → 長い上限
  - `CLAUDE_CODE_PROMPT_CACHE_TTL=1h` か設定 `promptCacheTtl` で 1 時間に固定している: 超過中でも 1 時間で書かれる（ドキュメントの記述どおりなら） → `1h` → 短い上限。キャッシュは 1 時間残るので、45 分ごとの読み出しで延ばせる（読み出しはクレジットで払う）
  - 5 分に固定している、または API キーの利用で 5 分になっている: 常に `5m` → 長い上限。短く起きてもキャッシュは残らない
  - 超過が明けた: 次のリクエストから 1 時間で書かれるので、次の掛け直しで短い上限に戻る
- 判定は `wait` の起動の時点で 1 回だけ行う。待っている間に親はリクエストを出さないので、有効期限は変わらない
- 退けた案: ステータスラインの入力の `prompt_cache.ttl`（v2.1.251 以降）を読む。ステータスラインは主の画面の部品で、`wait` からは読めず、値を書き出す仕組みを足す必要がある。トランスクリプトなら今ある置き場の求め方がそのまま使える
- 退けた案: 環境変数 `CLAUDE_CODE_PROMPT_CACHE_TTL` を見る。固定していない人の超過中を見分けられない

### D4. 既定で上限を決めたときは、stderr に 1 行出す

`--timeout` も `EPIC_DISPATCH_TIMEOUT` も無いときだけ、ポーリングの前に stderr へ `wait limit <秒> (parent cache <5m|1h|unknown>)` を 1 行出す。

- 理由: 6 時間眠った理由を、起こされた親と後から調べる人が見分けられる。bats は `sleep` をスタブにするので経過時間で上限を確かめられず、この行が上限を確かめる唯一の手がかりになる
- stdout の 1 行の契約は変えない。待ちをやめる直前の確認（`--interval 0 --timeout 0`）は上限を明示するので、この行は出ず、「stderr が空」の条件は今までどおり使える

### D5. `timeout` で起こされた親は、同じ引数の `wait` を 1 回掛け直すだけにする

`references/epic.md` の手順 5 を次の中身にする。

- `timeout <N>...`（位置引数の子があるとき）で起こされたら、子 issue もエピックも読まず、主への報告も書かず、直前と同じ引数の `wait` を `run_in_background: true` で 1 回起動してターンを終える。主への発言は書かない（書くなら `主がすること: なし` の 1 行だけ）。`--timeout` は足さない（足すと掛け直しのたびの有効期限の判定が効かなくなる）
- 手順 4 の片付け待ちの子だけを待つ `wait`（位置引数の子なし）の `timeout` は手順 5 に当たらず、今までどおり待ちをやめる直前の確認を通してやめる
- 子が記録（`子の停止: 主の返事待ち`）と印を残さずに自分のタブで質問して止まると、手順 5 では検知できない。今までは手順 5 の報告のたびに「子のタブも見て」と主に伝えていたが、手順 5 は主に何も書かなくなる。そこで、検知できない旨は手順 5 に注記として残し（`記録`・`子のタブ`・`検知できない` の語を含む）、主へは手順 1 の `launch` のあと最初に手順 2 で待ちに入る通知で一度だけ「記録を残さずに子のタブで質問して止まった子には気づけないので、子のタブも見てほしい」と伝える。掛け直しのたびには伝えない（毎回伝えると、短い上限で起きるたびに主への発言が出て、この change で消したい発言が残る）。手順 5 の掛け直しの文は「同じ引数の `wait` を再び背景で起動する」と書き、既存のテスト（`timeout` の行に `再び`）をそのまま通す
- 外す確認と、その確認が残る場所:
  - `needs-approval` と止まっている旨のコメントの確認: 子が印を付けて止まれば `wait --watch-stopped` が `stopped` で親を起こすので、この確認は印を付けずに止まった子の予備だった。待ちをやめる直前の確認（`needs-approval` の有無を見る）と、親を起動し直したときの手順 7（`pending-owner`）に残る
  - 子エピックの行で子を外す確認: 子エピックは手順 2 の前（**エピックである子を外す**）で `launch` に渡す前に外すので、ここは念のための確認だった。`closed` で起こされたときに残す
- 「待ちをやめてよい条件」は変えない。`timeout` が何度続いても、動いている子が残るあいだはやめない
- 退けた案: 掛け直しの何回かに 1 回だけ（6 時間分たったら）今までの確認をする。親が回数を数え続ける必要があり、#1324 の完了条件「上限で起きたターンで、親が子の調べ直しや主への報告をしない」にも合わない
- 退けた案: `needs-approval` の確認を `wait` に移す（ポーリングの gh でラベルも読み、付いた子を新しい行で返す）。出力の行と親の手順が増え、この change の範囲を超える。印を付けずに止まる子が実際に問題になったら別の issue で扱う

### D6. 片付け待ちの子だけを待つ `wait` には `--timeout 21600` を付ける

この待ち（手順 4）は `timeout` で終わったら待ちをやめる。既定の短い上限にすると、主にマージを頼んで見張りを終えた子のマージを 45 分しか待たずにやめてしまう。明示すれば、有効期限の判定もせず今の振る舞いのまま残る。この待ちだけは、今までどおり親が最長 6 時間眠ってキャッシュを切らす（起きたときの 1 回の書き直しを払う）。待ちをやめる前の 1 回だけなので、短い上限で掛け直す手間は掛けない。

### D7. 規則のファイルには、親の待ちの費用を別の節として書く

`references/reply-after-idle.md` に節「親の待ちの費用（#1324）」を足し、D2・D3・D5 の要点と、PC が寝ていたときは効かないこと（`SECONDS` は寝ていた時間も数えるので、起きた直後に `timeout` で親が起き、キャッシュは切れている。この 1 回は書き直しになる）を書く。#1323 が触る「閾値」と「そのまま送るか、起動し直すか」の表、「親への適用」の節の文は変えない（短い上限で起きる親は最後のリクエストから 60 分未満なので、「親への適用」の表ではそのまま続ける行に当たる。これは書き足さなくても表のとおりに決まる）。

## 順番 2 の change が使う関数の契約

関数 `cache_ttl_of`（`epic-dispatch.sh` の中のシェル関数。サブコマンドにはしない）。

| 項目 | 中身 |
|---|---|
| 入力 | 引数 1 つ: ワークツリーの絶対パス。置き場は `transcript_dir <パス>` で求める。引数が空なら置き場を求めずに exit 1（判定できない）。`toplevel` は失敗すると空を返し、空のまま `transcript_dir ""` を呼ぶと置き場の親（projects の直下）を指して、どのワークツリーのものでもない jsonl を読むため |
| 読む行 | 置き場の直下の `*.jsonl`（サブエージェントの `<セッション>/subagents/*.jsonl` は読まない）の、`type` が `assistant`・`isSidechain` が true でない・`timestamp` が文字列・`message.usage.cache_creation` がオブジェクトで、`ephemeral_5m_input_tokens` と `ephemeral_1h_input_tokens` の和が正の行（数でない値は 0 とみなす）。そのうち `timestamp` が最も新しい 1 行を使う |
| 出力（判定できた） | stdout に `<ttl> <epoch 秒>` の 1 行で exit 0。`<ttl>` はその行の `ephemeral_1h_input_tokens` が正なら `1h`、0 なら `5m`。`<epoch 秒>` はその行の `timestamp` を整数の秒にしたもの。これは「最後にキャッシュを書いた行の時刻」で、「最後のリクエストの時刻」ではない（キャッシュを読み出しただけの行は書き込みが 0 なので飛ばされ、その後のリクエストがあってもこの時刻は進まない）。キャッシュがまだ生きているかを見積もる用途でこの時刻を使うと早めに切れたと見積もるので、最後のリクエストの時刻が要るときは `decide_relaunch`／`last_activity` 側の値を使う |
| 出力（判定できない） | stdout に何も出さず exit 1。引数が空・置き場に `*.jsonl` が無い・python3 が無い・該当する行が無いとき |
| 副作用 | 無い。gh も LLM も呼ばず、stderr にも何も出さない |

`wait` は `cache_ttl_of "$(toplevel)"` を呼び、`5m` なら長い上限、それ以外は短い上限にする。順番 2 は子のワークツリーのパスで呼び、`5m` の子には声かけをしない（声かけでキャッシュが残らないため）ことに使う見込み。判定できないときの扱いは順番 2 の design で決める。

## Risks / Trade-offs

- [子が印を付けずに `needs-approval` だけで止まると、ほかの子が動くまで親が気づかない（今までは 6 時間ごとに気づけた）] → 子の手順（`epic-child-stop.md`）は `needs-approval` の保留でも記録と印を残すと決めている。待ちをやめる直前の確認と、起動し直した親の `pending-owner` には残る
- [親の会話が掛け直しのたびに少しずつ伸びる（1 回あたり Bash の呼び出し 1 回とその結果）] → 24 時間で約 32 回。伸びが自動コンパクトの閾値に届けば Claude Code のコンパクトが走る。会話全体の書き直しより安い
- [PC が寝ている間は効かない] → 規則のファイルに書く（D7）。起きた直後の 1 回は書き直しになり、そのあとは短い間隔に戻る
- [有効期限の判定が外れる（トランスクリプトの形が変わる・別のセッションが同じワークツリーで動いている）] → 判定できないときは短い上限で、損は D3 のとおり小さい。同じワークツリーの別セッションの行が最新なら、その行の有効期限で決まる（同じアカウントなら超過の状態も同じ）
- [ドキュメントの「超過中は 5 分に縮める」が変わる] → 判定は実際に書かれた有効期限を見ているので、仕組みが変わっても上限の選び方は正しい側に残る

## Migration Plan

- 版は上げない。プラグインの更新後に起動した `wait` から新しい既定が効く。更新前に起動していた背景の `wait` は 6 時間の上限のまま終わり、そのあとの掛け直しから短くなる
- 戻すときは、親の環境で `EPIC_DISPATCH_TIMEOUT=21600` を付ければ上限は今までどおりになる（手順 5 の掛け直しの扱いはそのまま）
