## Context

`route` は今、`EPIC_DISPATCH_PARENT_EPIC` か親ワークツリーの `linkedIssue` で `nested` を先に判定し、子でなければ「子が 2 件以上 かつ `orca worktree current --json` が exit 0」のとき `orca`、それ以外は `subagent` を返す（`plugins/dev-workflow/scripts/epic-dispatch.sh` の `cmd_route`）。件数の条件は `[ "$#" -ge 2 ]` の 1 か所で、SKILL.md・2 つの README・spec・bats に同じ条件が書き写されている。

エピック #811 の別の子 #827 が、同じ SKILL.md の Orca 経路の手順 2〜4（片付け待ちの子の集合）とそれに対応する spec を同時に直している。この変更は #827 の範囲に入らない。

## Decisions

### 1. 件数の条件は「2 件以上」を「1 件以上」にするだけにする

`[ "$#" -ge 2 ]` を `[ "$#" -ge 1 ]` にする。子 0 件は `subagent` のまま（issue の受け入れ条件「子 0 件の出力は今と変わらない」）。0 件のとき `orca` を返すと、起動する子が無いのに Orca 経路で待つ手順に入ってしまう。`orca` の有無・Orca 管理外・`nested` の判定順・`orca worktree current` を 1 回だけ呼ぶことは変えない。

### 2. 途中切り替えの規則は作らない

結論は「作らない」。「経路は最初の開始時に 1 回だけ決めて途中で変えない」と「再開時は `回し方:` の最新のコメントから経路を引き継ぎ、`route` をやり直さない」は今のまま残す。理由:

- 経路を変えるには、動いているサブエージェント方式の子（親のセッションの中で動く W / R1 / G）と、Orca の子ワークツリーの別セッションが同時に存在する状態を扱う規則が要る。同じ子を二重に起動しない仕組み（`launch` の `skipped`）は Orca 経路の子にしか効かず、サブエージェント方式で途中まで進んだ子を Orca の子ワークツリーに引き継ぐ手段が無い
- その規則を書く場所は「経路の決め方」の段落と Orca 経路の手順（片付け待ちの子の集合を含む）の両方にまたがる。Orca 経路の手順 2〜4 は #827 が同時に直しているので、この変更の範囲（「経路の決め方」の段落だけ）に収まらない
- 影響を受けるのは、この変更より前に `回し方: サブエージェント` と記録した、いま進行中のエピックだけである。この変更のあとに始めるエピックは、着手できる子が 1 件でも `route` が `orca` を返すので、途中で切り替える必要が起きない。#811 はオーナーの指示で手で切り替えた実績がある。進行中のエピックを切り替えたいときは、オーナーが `回し方:` のコメントを手で書き直し、サブエージェント方式の子が全部終わってから再開する（規則にはしない）

受け入れるリスク: すでに `回し方: サブエージェント` と記録した進行中のエピックは、エピックが終わるまでサブエージェント方式のままになる。起こる根拠は、この変更のマージ時点で進行中のエピックが #811 など少数あること。発生頻度はその数に限られ、新しいエピックでは起きない。

### 3. spec は件数に関わる行だけを直し、新しい要件を ADDED で足す

`openspec/specs/dev-workflow-develop/spec.md` で件数の条件を持つ行は次の 5 か所に限られる（`git grep -n "2 件以上"` と「1 件ならサブエージェント方式」で確かめた）。それぞれの該当の文言だけを置き換える。要件ごと MODIFIED で全文を書き写すと、#827 が同じファイルの別の文を直しているときに巨大な差分が衝突するので使わない。

- 要件「エピックの条件・作り方・回し方・完了条件を規定する」の「回し方（経路の決め方）」の段落の `blocked されていない子が 2 件以上あり、` の句と、Scenario「回し方に 2 経路の振り分け条件が書かれている」の同じ句
- 要件「epic-dispatch.sh はエピックの子の経路判定…」の `route` の文の `引数の子が 2 件以上あり、` の句、Scenario「並列にできる子が 1 件ならサブエージェント方式になる」（`orca` を返す Scenario に変える）、Scenario「並列にできる子が 2 件以上で Orca 管理下なら Orca 経路になる」の題
- 要件「エピックの子への注意書きと…引き継ぐ」の `route` の段落の `子が 2 件以上で` の句と、Scenario「親も環境変数も無ければ今までどおりで一覧を読まない」の `route 11` の期待値

直さない行（片付け待ちの子の集合・`reap`・`wait`、Orca 経路の段落の「解けた子を件数にかかわらず `launch` する」）は #827 の範囲なので触らず、重なる記述が見つかったら return で報告する。

## Risks / Trade-offs

- 子ごとに `/develop` を丸ごと回すセッション（既定で opus）が、着手できる子が 1 件のときも 1 本増える。状況の見やすさと引き換えにすることは、オーナーが 2026-10-08 に指示した
- 実機の確認はこの change のテストでは尽くせない（`orca` をスタブにしているため）。受け入れ条件の実機確認は tasks 4.2 に書く
