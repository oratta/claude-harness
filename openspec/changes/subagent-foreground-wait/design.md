## Context

dev-workflow の 1 ループは本体（オーケストレータ）が W / R1 / G を名前付きサブエージェントとして spawn し、SendMessage で再開する形で回る。サブエージェントは idle になると、自分が起動した背景タスクの完了では再起動されない（完了通知は `queued_command` として積まれるだけ）。再開できるのは親からの SendMessage だけで、実測では送れば 3〜16 秒で復帰した。

一方で手順書は逆のことを指示していた。`roles/gate-runner.md` は Codex レビューを `run_in_background` で起動して出力ファイルを読めと書いており、10 分より長く待つ方法は書かれていない。`pr-review-gate/SKILL.md` は companion の `status <job-id> --wait --timeout-ms 900000` を指示しているが、Claude Code の Bash 前景呼び出しの上限は 600 秒なので 1 回では完走しない。結果として G は「完了通知を待つ」と書いてターンを終え、親が気づくまで止まった（2026-09-08 に 5 件、合計約 4 時間）。

同種の事故は 2026-08-07 にも起きており、flatmate 側の `docs/agent-loop-steps.md` には正しい規則（完了待ちでターンを終えない・同一ターン内でポーリングする）が既にある。しかし G はそのファイルを読まないため、dev-workflow プラグイン側に正本が要る。

制約として、この harness の Bash ツールは前景 1 回あたり最大 600000 ms、行頭の裸の長時間 `sleep` は拒否される。ループ内の `sleep` は許可されることを本 change の作業中に実測で確認した（`until [ ... ]; do sleep 1; done` が前景で完走）。

## Goals / Non-Goals

**Goals:**

- サブエージェントが長時間処理（Codex レビュー・フルテスト）の完了を、ターンを終えずに待てる手順を dev-workflow の手順書に持たせる
- W / R1 / G のどの役割の指示書からも同じ規約に到達できるようにする
- `--timeout-ms` のような「前景上限を超える待ち値」を機械検出できるようにして、同じ退行が黙って戻らないようにする

**Non-Goals:**

- 親側の保険（親が idle のサブエージェントを検知して起こす仕組み）は扱わない。issue #255 が担当し、この change が効かなかったときだけ着手する
- flatmate や codex プラグインなど dev-workflow 以外のリポ・プラグインへの規約の波及は扱わない
- Codex レビューそのものの所要時間短縮（`model_reasoning_effort` の調整）は既存の規約のままとし、この change では変えない

## Decisions

### 1. 正本は `plugins/dev-workflow/references/subagent-waiting.md` に 1 本置き、各手順書からは 1 行で参照する

読み手は W / R1 / G の 3 つの指示書と pr-review-gate/SKILL.md の計 4 か所ある。同じ十数行を 4 か所に複製すると、片方だけ直って食い違う（`--timeout-ms 900000` が gate-runner.md と SKILL.md の両方にあり、片方だけ古い書き方で残っていたのが今回の事故の遠因でもある）。dev-workflow には「共有契約はプラグイン直下 `references/` に置く」という既存の規約（capability `dev-workflow-shared-references`）があり、`model-tiers.md` / `pr-body-format.md` / `self-verification.md` / `workflow-execution.md` が同じ形で置かれている。待ち方の契約もこれに並べる。

- 却下案 A: 4 か所にそのまま書く。file を開く回数は減るが、次に待ち方が変わったとき 4 か所を直す必要があり、今回と同じ食い違いが再発する
- 却下案 B: `templates/escalation-tripwires.md` に相乗りする。あれは「手を止めて本体に return する条件」の正本で、主題が違う
- 受け入れるコスト: サブエージェントが開くファイルが 1 つ増える。緩和として、各指示書に置く 1 行は参照だけでなく**禁止そのものを書き切る**（「完了通知を待つためにターンを終えない」）。詳しい待ち方が要るときだけ正本を開けばよい形にする

### 2. 禁止するのは「待つためにターンを終えること」であって、`run_in_background` での起動そのものではない

Codex レビューは 10 分を超えることがあり、前景 1 回では起動から完了まで到達できない。したがって起動は background のままにし、**完了の確認だけを同一ターン内の前景ポーリングで行う**。禁止語を「`run_in_background` を使うな」にすると Codex 経路が成立しなくなる。

- サブエージェントが禁止されるのは、Monitor や `run_in_background` の「完了したら続きが動く」に頼ること（起きないため）
- メインセッションは背景タスクの完了で再起動されるので、この禁止はサブエージェントに限定する。`pr-review-gate/SKILL.md` は本体とサブエージェント G の両方が読むため、この条件分岐を本文に書く

### 3. 待ち方は前景 Bash の有限 `until` ループを、必要な回数だけ呼び直す

```bash
# timeout を明示した 1 回の前景呼び出し（最大 9 分）
until [ -f "$out" ] && grep -q 'DONE' "$out"; do sleep 10; done
```

1 回で終わらなければ同じ呼び出しをもう一度発行する。1 回の Bash 呼び出し = 1 ターンではないので、ターンは続いたまま何度でも回せる。ループ内の `sleep` は許可対象で、拒否されるのは行頭の裸の長時間 `sleep` だけ。

- 却下案: Monitor ツールの until 条件を使う。ハーネスの一般的な案内では正しいが、サブエージェントでは完了で起こされないため今回の事故と同じ形になる

### 4. 前景の待ち値は 540000 ms（9 分）に統一する

Bash 前景の上限は 600000 ms なので、上限ちょうどを指定するとループの後処理ごと切られる。9 分に揃えて 1 分の余裕を残す。`status --wait --timeout-ms` と Bash 側 `timeout` の両方に同じ値を使い、タイムアウトしたら同じ呼び出しを繰り返す。

- 受け入れるコスト: 30 分かかる Codex レビューでは前景呼び出しが 4 回に分かれる。ターンは継続しているので停止にはならない

### 5. 退行ガードは bats のテキスト検査で置く

この change の成果物は手順書の文言なので、退行検出も文言に対して行う。`tests/*.bats` を `scripts/test.sh` が `git ls-files '*.bats'` で自動発見する既存の仕組みにそのまま乗る。検査するのは 3 点 — 待ちを伴う `run_in_background` / Monitor の指示が dev-workflow の手順書に残っていないこと、`--timeout-ms` の指定値がすべて 600000 未満であること、`references/roles/` 配下の各指示書に禁止行があること。

- 受け入れるコスト: grep ベースなので、規約を守った書き換えでも語を含めば落ちる。テスト側に理由コメントと hint を書いて、落ちたときに何を直すかが分かるようにする

## Risks / Trade-offs

- **前景ポーリングはサブエージェントを 9 分間ブロックする** → その間に親が SendMessage を送っても処理されない。ただし従来は無期限に止まっていたので悪化はしない。長い待ちの前に「これから最大 9 分待つ」と出力してから入る
- **ハーネス側の `sleep` 制限が将来変わるとループが拒否されうる** → 正本にループ内 `sleep` が許可対象である根拠を明記し、拒否されたときの代替（ポーリング間隔を `date` 比較のビジーウェイトにせず、呼び出しを短く刻んで回数を増やす）を 1 行添える
- **grep ベースのガードの偽陽性** → 正本ファイル自身は「使わない」文脈で禁止語を含むため、ガードの対象パスから正本と本テスト自身を除外する。除外の理由をテスト内にコメントで残す
- **受け入れ条件の 4 番目（develop 実行 1 回で G の idle 通知に「完了を待つ」文言が出ない）はテストで検証できない** → 実装後の動作確認として親のトランスクリプトで確認し、pr-review-gate の動作確認の証拠として PR に添える
