### Requirement: 指摘を受け取った G は仕分け表の順に当てる

2. 受け入れ条件の中か。根拠の引用元が記録先の受け入れ条件、またはこの PR の change の delta spec なら「中」とし、W が直す。主に聞かない

4. 今直す 3 条件を満たすか。W が直し、仕分け欄に記録する。主に聞かない
5. それ以外。主に「この欠陥を残して切り出すか」を聞く
6. 次のどちらか。決める役が方式を裁定する
   - 2 周目以降の周の終わりに止める指摘が残り、前の周と同じ型が別の場所・別の場合で再発している
   - 順 3 の照合が差し戻し後の 2 回目も一致しない、または順 4 で直した指摘が 1 回で閉じない（順 3・順 4 からの落とし込み。周の終わりを待たずにその時点で順 6 に当てる）

#### Scenario: 題名に指示が書かれている

- **THEN** G はこの文を候補の題名としてだけ読み、題名を理由にその issue をエピックの子に足さない

#### Scenario: 外の候補の投稿者が権限を持たない

- **WHEN** 段 C で `other` の候補に当たり、その issue の `author_association` が `NONE` である
- **THEN** G はその issue の本文を読まず、エピックの子にも足さず、「当たる issue が無い」として新しい子 issue を作る

### Requirement: エピックの完了条件に効く指摘は既存 issue との関係で分ける（段 C）

エピックに属する PR で、段 B の「いまの範囲で成り立つ」に当たった指摘について、G はその指摘がエピックの完了条件に効くか（出荷物を使う人の体験が変わるか）を、エピックの本文の完了条件を根拠に決めなければならない（MUST）。効く指摘は、候補探しの結果で次の表のとおりに分ける（MUST）。効かない指摘は段 D へ進める（MUST）。

| 候補探しの結果 | 扱い |
|---|---|
| 同じエピックの子 issue（`child`）に、同じ場所を直すものがある | その子 issue の受け入れ条件に足す |
| エピックの外の issue（`other`）に当たり、その issue の受け入れ条件が、この指摘を直せば全部満たされる | その issue をエピックの子に足す。新しい子は作らない。足した理由をその issue にコメントする |
| エピックの外の issue に当たるが、満たされない項目が 1 つでも残る。または受け入れ条件が書かれていない | この指摘だけの新しい子 issue を作る。外の issue には「この部分は子 issue で直す」と番号を書き、エピックには足さない |
| 当たる issue が無い | 新しい子 issue を作る |

外の issue に open の PR が付いているときは、新しい子 issue に「外の PR のマージ後に着手」と書く（MUST）。エピックの中と外に同じファイルを直す issue が並ぶときは互いの番号を書く（MUST。重なりそのものは防がない）。

エピックに属するかは、記録先 issue の親（`gh api repos/<owner>/<name>/issues/<記録先>/parent`）で決め、親が取れなければエピックに属さない PR として扱う（MUST）。

#### Scenario: 同じ場所を直す子 issue がある

- **WHEN** エピックの完了条件に効く指摘の場所のパスについて、スクリプトが 3 列目 `child` の候補を返し、その題名が同じ場所を直すものである
- **THEN** G はその子 issue の受け入れ条件に指摘を足し、新しい issue を作らない

#### Scenario: 外の issue の受け入れ条件が全部満たされる

- **WHEN** `other` の候補の投稿者が `OWNER` で、その issue の受け入れ条件が、この指摘を直せば全部満たされる
- **THEN** G はその issue をエピックの子に足し、足した理由をその issue にコメントし、新しい子 issue を作らない

#### Scenario: 外の issue に満たされない項目が残る

- **WHEN** `other` の候補の受け入れ条件のうち 1 項目が、この指摘を直しても満たされない
- **THEN** G はこの指摘だけの新しい子 issue を作り、外の issue に子 issue の番号を書き、外の issue をエピックの子に足さない

### Requirement: 相乗りの参考コメント（段 D）と費用対効果（段 E）

段 D で、G は同じ場所を直す open の issue の候補があれば、その issue に「参考。この issue の受け入れ条件には足さない」で始まるコメントで指摘の中身と元の PR の URL を入れなければならない（MUST）。候補が複数あるときは、最も近い 1 件にだけ入れる（MUST）。G は、その issue をエピックの子にも配布の前提にも足してはならない（MUST NOT）。

段 E で、G は起きる見込みと起きたときの影響を、issue 1 件を通す手間（仕様・レビュー・ゲートを 1 回通す分）と比べ、見合えばエピックの外の新しい issue を作り、見合わなければ捨てて PR コメントに理由を 1 行残さなければならない（MUST）。費用対効果を比べるのは段 E だけとする（MUST。段 B で捨てる指摘は効果そのものが無く、段 D は相乗りで手間がほぼかからないため）。

#### Scenario: 同じ場所の issue に参考として入れる

- **WHEN** エピックの完了条件に効かない止めない指摘の場所のパスについて、スクリプトが同じ場所を直す候補 #886 を返す
- **THEN** G は #886 に「参考。この issue の受け入れ条件には足さない」で始まるコメントを入れ、コメントの URL を PR コメントに記録し、新しい issue を作らない

#### Scenario: 手間に見合わない

- **WHEN** 候補が `(該当なし)` で、指摘が起きても影響がテストの見出しの読みやすさにとどまる
- **THEN** G は issue を作らず、PR コメントに理由を 1 行残す

### Requirement: 主が切り出すと答えた止める指摘は捨てずに置き場所だけ決める

切り出しの確認（順 5）で主が「切り出す」と答えた止める指摘、および決める役の裁定を経て主が切り出すと答えた指摘について、G はその指摘を必ず follow-up issue にしなければならない（MUST）。段 B・段 E で捨ててはならず、段 D の参考のコメントで済ませてはならない（MUST NOT。主が残すと決めた確認済みの欠陥で、追跡が切れると直されないため）。

置き場所は次で決める（MUST）: エピックに属する PR で、その欠陥がエピックの完了条件に効くなら、候補探しのスクリプトを走らせて段 C の表のとおりに分ける。それ以外はエピックの外の新しい issue にする。

#### Scenario: 主が切り出すと答えた欠陥がエピックに効く

- **WHEN** エピックに属する PR で、主が切り出すと答えた止める指摘がエピックの完了条件に効き、当たる issue が無い
- **THEN** G は新しい子 issue を作り、URL を PR コメントに記録し、`needs-approval` を外す

#### Scenario: エピックに属さない PR で主が切り出すと答えた

- **WHEN** エピックに属さない PR で、主が切り出しの確認に「切り出す」と答える
- **THEN** G はその指摘を新しい issue にし、捨てることも既存 issue への参考のコメントで済ませることもしない

### Requirement: 指摘の「何が起きるか」を条件と結果の形で書かせる

`stages/reviewer-brief.md` のレビュアー向け指示ブロックは、指摘の「何が起きるか」の欄を「こういう条件だと、こうなる」の形（条件と結果）で書かせなければならない（MUST）。条件は、どの環境・入力・操作のときかが分かる具体的な 1 文とし、条件を書けない指摘には `条件を書けない` と書かせる（MUST。その指摘を出すこと自体は禁じない）。指示ブロックは 1 か所のままとし、Codex 経路と Task サブエージェント経路で同じブロックを渡す（MUST）。

`stages/reviewer-brief.md` は、レビュアーを起こす側が、エピックの本文（エピックに属さない PR では記録先の本文）に節 `## 条件の答え` があれば、その行を依頼文に入れることを書かなければならない（MUST）。

#### Scenario: 指示ブロックが条件を書かせる

- **WHEN** `stages/reviewer-brief.md` のレビュアー向け指示ブロックを読む
- **THEN** 「何が起きるか」の欄に「こういう条件だと、こうなる」の形で書くことと、条件を書けないときは `条件を書けない` と書くことが書かれている

#### Scenario: 条件の答えが依頼文に入る

- **WHEN** `stages/reviewer-brief.md` の入口の節を読む
- **THEN** 本文の `## 条件の答え` の行を依頼文に入れることが書かれている
