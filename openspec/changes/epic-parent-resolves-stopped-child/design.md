## Goals / Non-Goals

**Goals:**

- 止まった子のうち親が進めてよいと決められるものは、親のセッションを起こさず、主も触らずに、子が続きから進む
- 親が通した判断が、エピックに 1 行ずつ残る（主が事後に見て、違えば止められる。親を起動し直しても復元できる）
- 親が決められないものは、親が窓口になり、エピックの目的と他の子との関係を含めて主に分かる形で上げる。主の答えは親が子に届ける
- 親が通してよい範囲の基準の案を、主が PR で読める 1 ファイルに書く

**Non-Goals:**

- 子の記録の 2 行目以降の形（#1036）。判断は 4 つの情報（理由・推奨と根拠・リスク・途中経過）が読めればよい
- 子の PR のマージの可否（#1030）。マージを求める止まりはこの基準では通さず、#1030 の手順に任せる
- 主の判断が要るもののうち gene に任せるもの（issue #1034「決まっていないこと」。この子が動いてから考える）
- 記録を残さずに止まった子を見つけること（#1033 の範囲。入力待ちからの推定は入れない）
- Orca 経路でない（サブエージェント方式の）エピックの子。止まった印が無いので対象にしない

## Decisions

### 1. 判断は `wait` の中から直接呼び、通すときは親を起こさない

`wait --watch-stopped` に `--resolve <epic>` を足す。止まった子を見つけたら、`wait` がその子ごとに `scripts/stop-judge.sh <epic> <child>` を呼び、結果が「通す」で返事が届いたら、その子を出力せずに待ちを続ける。「主に上げる」・判断の失敗・送信の失敗のときだけ `stopped <N>` を出して終わり、親を起こす。

比べた案:

| 案 | 通すときの親のターン | 欠点 |
|---|---|---|
| A. `wait` から直接判断を呼ぶ（採用） | 0 | `wait` がモデルを呼ぶ。判断の失敗は親を起こす側に倒す必要がある |
| B. 親が `stopped` で起き、決める役のサブエージェントを起こす | 1 件ごとに 1 ターン以上（起動と結果の読み込み） | 親が長く待ったあとはキャッシュが切れていて、1 件ごとに親の文脈全体を読み直す |
| C. 親が `stopped` で起き、自分で判断する | 1 件ごとに 1 ターン | B の欠点に加え、判断に親の大きな文脈が混ざる |

エピック #1038 は「親を起こさずに `wait` から直接呼べるなら、そうする」としている。通す件は 2 週間で 35 件の規模なので、A なら親の 35 ターン分（長く待ったあとは文脈全体の読み直し）が要らなくなる。判断を呼ぶのはシェルなので、見張りを LLM にさせない方針（#811）とも矛盾しない。

`--resolve` は `--watch-stopped` と一緒のときだけ意味を持つ。`--resolve` が無い `wait` は今までどおり `stopped <N>` を返す（#1033 の振る舞いを変えない）。

### 2. 判断は `stop-judge.sh` に分け、ツールなしの小さなモデルで 1 回だけ呼ぶ

`scripts/stop-judge.sh <epic> <child>` が入力を集め、モデルを 1 回呼び、決まった形の 4 行を stdout に出す。`orca` の語を含まないので、`orca` を呼ぶスクリプトが 1 本という既存要件のままにできる。`epic-dispatch.sh` は `EPIC_DISPATCH_JUDGE`（既定は同じディレクトリの `stop-judge.sh`）で判断のコマンドを呼ぶので、テストではスタブに差し替えられる。

- **入力**（`gh` で集める）: エピックの本文、子 issue の本文、子 issue の `親エピックからの注意書き:` のコメント（投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` のものだけ。既存の規則と同じ）、子 issue の 1 行目が `子の停止: 主の返事待ち` の最新のコメントとその URL、エピックのコメントのうち `親の判断: 子 #<child> ` で始まる行、`references/parent-pass-criteria.md` の本文、リポジトリに `.claude/casting/project.md`・`.claude/casting/local.md` があればその本文。親の会話・子の会話・他の子の記録は渡さない
- **呼び方**: 既定は `claude -p --model <EPIC_DISPATCH_JUDGE_MODEL、既定 sonnet> --tools "" --no-session-persistence`（`EPIC_DISPATCH_JUDGE_CMD` で丸ごと変えられる）。ツールを渡さないので、判断は渡した文面だけで行われ、何も書き換えない
- **出力**: 1 行目 `判断: 通す` か `判断: 主に上げる`、2 行目 `理由: <1 行>`、3 行目 `返事: <1 行>`（通すときに子へ送る文。主に上げるときは空でよい）までがモデルの出力で、4 行目 `記録: <停止の記録の URL>` は `stop-judge.sh` が付ける（エピックの 1 行に使う）。モデルの出力がこの形で読めなければ `stop-judge.sh` は exit 1 で終わり、`wait` は親を起こす側に倒す
- **モデルを `sonnet` にする理由**: 判断は基準の表に照らして通すか上げるかを決めるだけで、数ターンで終わる。`dev-workflow:decider`（決める役の種別、`fable`）は修正方針・マージ可否のような判断が一点に集中する仕事に使うもので、1 件ごとに呼ぶこの判断に最上位の枠を使わない。通すと決めた件は主が事後にエピックで見られるので、誤って通したときに戻せる範囲に基準を絞ることで、小さいモデルの誤りを受け止める

`casting:casting`（観点の配役。主に上げる前の確認手順）は、セッションの中で手順を踏むスキルで、ツールなしの 1 回の呼び出しからは呼べない。代わりに、その手順のうち「聖域なら無条件で主に上げる」と「担い手が主の観点があれば主に上げる」を基準の表に入れ、配役表があれば判断の入力に入れる。

### 3. 返事の送り方は `epic-dispatch.sh reply` に置く

`epic-dispatch.sh reply [--relaunch] --as <parent|owner> <epic> <child> <text>` を足す。子のワークツリー（同じ repoId・linkedIssue が `<child>`・archive されていない、ちょうど 1 件）を一覧から探し、そのワークツリーの端末を数える。

| 状態 | 動き | stdout |
|---|---|---|
| 端末が 1 つで `--relaunch` なし | その端末に返事を打ち込む（`launch` と同じ送り方。ターンの開始まで確かめる） | `sent <child>` |
| 端末が無い、または `--relaunch` | （`--relaunch` なら端末を閉じてから）`launch` と同じ起動コマンドで端末を作り、`/develop #<child>` の起動の指示のうしろに返事を付けて送る | `relaunched <child>` |
| 端末が 2 つ以上 | 送らない（どれが子のセッションか分からない） | `failed <child> ambiguous-terminal` |
| ワークツリーが 0 件か 2 件以上・送れない | 送らない。送り直しのコマンドを stderr に出す | `failed <child> <理由>` |

返事の文の頭には、送り手を必ず付ける: `--as parent` は `親エピック #<epic> の判断（主の承認ではない）: `、`--as owner` は `主の返事（親エピック #<epic> 経由）: `。子は端末への入力を主の入力として受け取るので、親の判断を主の承認と取り違えないようにするためである。親が通す範囲を、主の承認が要らないものに絞る（決定 4）のも同じ理由による。

`wait --resolve` の「通す」は `reply --as parent` と同じ処理を中で呼ぶ。止まった直後の子は最後のリクエストから 60 分未満なので、`reply-after-idle.md` の表では常に「そのまま送る」に当たり、時刻の判定は要らない（端末が無いときだけ起動し直す）。主の答えを届けるときは止まってから時間がたっていることがあるので、親が `reply-after-idle.md` の表で決め、起動し直す行に当たれば `--relaunch` を付ける。

案として、`wait` が返事を送らずに子 issue へ親の判断をコメントし、子にそれを読ませる形も考えた。止まった子は次の入力が来るまでターンを始めないので、コメントだけでは子が進まない。端末への入力は必要である。

### 4. 親が通してよい範囲の基準（案）

`references/parent-pass-criteria.md` に置く。次をすべて満たすときだけ「通す」。1 つでも満たさないか、満たすか判断できなければ「主に上げる」。

| 条件 | 中身 |
|---|---|
| 推奨がある | 子の記録に推奨とその根拠がある（推奨の無い止まりは、主の好みや事業判断を聞いている） |
| 範囲の内側 | 推奨が、エピックの目的と子 issue の受け入れ条件の範囲を広げず、逆向きにもしない |
| 聖域でない | 自己統治物件（`CLAUDE.md`・hooks・権限設定・`rules/`・常時注入の予算ファイル）、破壊的な git 操作（`rules/destructive-git-guard.md` の一覧）、秘密情報の値、外部への公開・送信・課金、PR のマージ（#1030 の手順に任せる）に触れない |
| 戻せる | 推奨どおり進めて誤りだったとき、そのブランチの中の commit の取り消しや設定の戻しで戻せる。戻すのにかかる手間が判断できなければ戻せない側に倒す |
| 主の側の情報が要らない | 好み・事業判断・主しか知らない事実・リスクの許容が要らない。記録の「受け入れるリスク」は、エピックや子 issue に既に許容と書かれているか、その子のブランチの中に閉じるものに限る |
| 実機操作でない | MFA・OAuth・ログイン・ダッシュボードの操作など、主の手が要る操作を含まない |
| 配役表で主の観点が無い | 配役表が渡されたとき、その止まりに要る観点の担い手が主でない |
| 繰り返していない | このエピックで同じ子の同じ件を既に一度通していて、子がまた同じ件で止まっていない |

2026-10-01〜10-14 の 35 件から、通る例として、仕様レビューの周の上限を超えた続行、PR のトークン上限の引き上げ（その PR の中に閉じるもの）、hook が止めたファイルの読み取り（リポジトリの中のソースで、ファイル名が止められた理由のもの）、手順外の判断を推奨どおり受け入れること、自分の実行の配下で暴走したプロセスの停止（他のプロジェクトのプロセスは含まない）を書く。通らない例として、マージの承認、聖域のファイルの変更、実機操作、主しか知らない設計意図を書く。

この案は #1030 の「合理性があり危険が低い」と揃える前提で書く（#1030 はこのファイルを参照すればよい）。基準の中身の最終決定は主が PR で行う。

### 5. 記録の形

- **エピックへの 1 行**（通して返事が届いたとき、`wait` が投稿）: `親の判断: 子 #<child> 通した — <理由> <停止の記録の URL>`
- **子 issue への判断の結果**（主に上げる・失敗のとき、`wait` が投稿）: 1 行目 `親の判断: 主に上げる`（判断や送信に失敗したときは `親の判断: 判断できなかった`）、2 行目以降に理由と、送れなかったときは送るはずだった返事
- 親は `stopped <N>` で起きたら、子 issue の最新の `子の停止:` と `親の判断:` を読む。`親の判断: 判断できなかった` で、判断が「通す」だったのに送れなかった件は、主に上げずに `reply --as parent` で送り直してよい（送れたらエピックに同じ 1 行を残す）
- 親を起動し直したら、`親の判断: 子 #N` の行から通した判断を復元できる（`reply-after-idle.md` の復元の表に足す）

### 6. 主に上げる説明

親は、子の記録と判断の結果をもとに、`output-styles/readable.md` の「判断を求めるときは、背景から書いて推奨まで出す」の順（目的 → いま取り組んでいる場所 → 起きた事実 → 決めてほしいこと 1 つ → 推奨と受け入れるリスク）で書き、エピックの目的と他の子との関係を含める。子の停止の記録の URL を添える。実機操作は、どの子の・どの画面で・何をするかを書く。この説明は親の文脈（エピック全体と他の子）が要るので、親のターンで書く（主に上がるのは 2 週間で 12 件ほどの見込み）。

### 7. 子の側で足す 1 項目

子が止まるときの節（#1033）に、端末に `親エピック #<E> の判断（主の承認ではない）:` か `主の返事（親エピック #<E> 経由）:` で始まる入力が届いたら、止まった件への返事として受け取り、`mark resumed` を呼んで続きから進む、と 1 項目足す。親の判断で進めた件は完了報告に書く。主の承認が要る操作（聖域・破壊的操作）は、親の判断では進めない（親の基準がそれらを通さないので、届くのは主の返事だけのはず）。記録の形と完了報告の書式は #1036 の範囲なので、この 1 項目の外は触らない。

## Risks / Trade-offs

- [判断のモデルが、通してはいけない件を通す] → 基準を戻せる件に絞り、通した件はエピックに 1 行残して主が事後に止められるようにする。返事の頭に「主の承認ではない」を付け、子が聖域や破壊的操作を親の判断で進めないようにする
- [子が親の返事を受けたあと、同じ件でまた止まり、判断が通し続ける] → 判断の入力に同じ子への過去の `親の判断:` を入れ、「繰り返していない」を基準に入れる
- [判断のコマンドが無い・落ちる・形が崩れる] → 主に上げる側に倒し、`stopped <N>` で親を起こす。`wait` の待ちは止めない（他の子の監視は親が `wait` を呼び直して続ける）
- [端末への入力が子に届かない（入力欄に打ち込まれただけでターンが始まらない）] → `launch` と同じくターンの開始まで確かめ、確かめられなければ `failed` として親を起こし、送り直しのコマンドを stderr に出す
- [親が主の答えを書き換えて届ける] → `reply --as owner` には主の答えをそのまま渡すと手順に書く。完全には防げないが、主の答えは親のタブに残るので照合できる
- [起動し直した子が、返事の前提を失う] → 起動の指示のうしろに返事を付け、子は記録先の引き継ぎと停止の記録から再開する（#1033 の記録は引き継ぎの URL を持つ）
- [止まった件ごとに判断の費用が増える] → エピック #1038 が見込んだ増加（停止 1 件ごとに小さなモデル 1 回）の範囲。件数と金額は合否に使わず、エピックの再集計で記録する

## Migration Plan

- `--resolve` を付けない `wait` は今までどおり動くので、この変更より前に始めたエピックの親は、`wait` を呼び直すときに SKILL.md の新しい手順で `--resolve` が付く
- 戻すときは SKILL.md の手順 2 から `--resolve` を外せば、#1033 の報告だけの振る舞いに戻る
