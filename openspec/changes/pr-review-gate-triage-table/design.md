## Context

#349（PR #353）で、指摘の固定書式と「マージを止めるかの判定（全周共通）」が SKILL.md 手順 2-1 に入った。止めるかどうかは全周で同じになったが、止める指摘が残ったときの動き方は周で分かれたままで、1 周目は一律 failed、2 周目の終わりは `needs-approval` で主に「続けるか、範囲外として閉じるか」を聞く。後者の質問には判断材料（欠陥が何を起こすか・直す見積もり・推奨）が付かないので、主は答えられないか、常に「続ける」と答えて 3 周目以降に入る。

issue #354 は、指摘が届くたびに G が当てる仕分け表（順 1〜6）を定め、主への質問を「この欠陥を残して切り出すか」に絞り、推奨と見積もりを必須にする。設計の経緯と過去 8 本への当てはめは issue 本文の備考にあるリンク先。

## Goals / Non-Goals

**Goals:**

- 指摘を受け取った G の動き方を、周回によらない 1 つの表（順 1〜6）で決める
- 「同じ文が別の場所に残る」型を、G がレビューせず検索結果の集合一致で閉じられるようにする
- 主への質問を、推奨と見積もり付きの「切り出すか」1 つにする
- 同じ型の再発（#253・#268 型）に、決める役が方式を裁定して周回を打ち切る経路を作る
- 差分限定の周でも例外 3 種の新規指摘を出せることを明記する（#241 型）

**Non-Goals:**

- 1 周目の網羅を上げること（#355）。指摘の書式に「前周と同型か」の欄を足すことも #355 で扱う
- 止めるかどうかの判定そのもの（手順 2-1「マージを止めるかの判定（全周共通）」）の変更
- 手順 2-2 の原因分類とモデル昇格、`agents/decider.md` の出力契約の変更（順 6 の依頼は既存の「可否と根拠」の形に載せる。決定「順 6 の決める役は本体が起こす」を参照）

## Decisions

**仕分け表は判定の直後に 1 か所だけ置く。** 手順 2-1「マージを止めるかの判定（全周共通）」の直後に表を置き、収束ルール節・手順 6・gate-runner.md・worker.md は表の順番号と見出しで参照する。表の中身を他の面で言い換えない（#349 で判定の文を 1 か所にしたのと同じ理由）。

**順 2「受け入れ条件の中」は、根拠の引用元で決める。** 引用元が記録先の受け入れ条件、またはこの PR の change の delta spec なら「中」（直さないと PR の目的が達成されない）。引用元がこの PR の触れる既存の spec だけのもの、例外 3 種に当たるものは「中」に数えず、順 3 以降に進む。G の照合結果（どこから引用したか）がそのまま使えるので、新しい判断を足さずに済む。

**2 周目の終わり（と、それ以降の周の終わり）では順 2〜4 を使わない。** 止める指摘が残っていれば、前の周と同じ型が別の場所・別の場合で出ているものは順 6、それ以外は順 5 で主に聞く。順 2〜4 は「聞かずに W が直す」経路なので、2 周目の終わりに使うと主の回答なしに 3 周目が開き、#351 のキャップが外れる。

**3 周目以降が開くのは 2 通りだけにする。** 主が順 5 で「この PR で直す」と答えたとき（従来の「主の続行指示」と同じ扱い）と、決める役が順 6 で「全部列挙してから直す」と裁定したとき。後者は PR ごとに 1 回までとし、2 回目の順 6 は「切り出す」側に倒して順 5 の経路で主に聞く。回数は G のコンテキストでは数えない。G は再 spawn されると前の周の記憶を持たないので、裁定を受け取るたびに 1 行目 `決める役の裁定: (全部列挙してから直す|切り出す)` の PR コメントを残し、再開時にその件数を PR コメントから数える。issue は「切り出すなら 5 と同じ経路で主に聞く」とだけ書いていて列挙側の上限を定めていないので、ここで上限を足す。上限が無いと、列挙のたびに新しい型が出る PR で、主が知らないまま周回が続く。

**順 6 の発火は 2 通りにする。** 1 つは 2 周目以降の周の終わりに前の周と同じ型が再発したとき、もう 1 つは順 3・順 4 からの落とし込み（順 3 の照合が差し戻し後も一致しない、順 4 の「今直す」が 1 回で閉じない（#177 型））。順 3 の照合は周に数えないので、落とし込みは周の終わりを待たずにその時点で起きる。

**順 3 の照合はレビューの周に数えない。** G はレビューをせず、W の表と同じ検索コマンドの結果を突き合わせるだけなので、周回キャップとは別に「差し戻し 1 回まで」で止める。W に戻すときのラベルは順 2・4 と同じ `agent-review:failed` にし、新しいラベルを足さない。戻した指摘が順 3 だけなら、集合一致で閉じたあとに差分限定の再レビューをせず、周を消費しない。順 2・4 の指摘が同じ failed に入っていれば、それらの差分限定の再レビューで周を 1 つ消費する（順 3 の照合の分は数えない）。

**同じ周に順 5 と順 2〜4 が混ざったら、保留を先にする。** G は順 2〜4 の指摘も含めて仕分けを PR コメントに記録し、Status を保留にして return する。主の回答が来たら、切り出す指摘は follow-up issue にし、残りを 1 回の failed でまとめて W に戻す。`needs-approval` と `agent-review:failed` を同時に付けず、ラベルの状態を 1 つに保つため。主の回答が来るまで、W は順 2〜4 の指摘の修正にも着手しない（切り出す指摘に触れる修正を先に進めると、主が「この PR で直す」と答えたときに同じ箇所を 2 回直すことになるため）。

**順 6 の決める役は本体が起こす。** G は孫を持てないので、needs-reviewer と同じ形で Status `needs-decider` を return し、本体が `dev-workflow:decider` を起こして裁定を受け取り、裁定を渡して G を再開する。本体の動きは develop の SKILL.md (4) に `needs-decider` の行として足す（(4) の return 一覧に無いと、本体は `needs-decider` を受け取っても何をするかを読めない）。決める役への依頼は `agents/decider.md` の既存の出力契約のうち「可否と根拠」の形で出し、問いを「この PR の中で、同じ型を全部列挙してから直すべきか（可）、切り出すべきか（否）」の 1 つにする。本体が可否を方式に読み替えて G に渡す。decider.md に「方式」の出力を足す案もあるが、decider.md は全経路の決める役が読む層間契約で、1 つの用途のために出力の型を増やすと他の呼び出し側への影響を確かめる範囲が広がる。2 値の問いなら既存の形に載るので、decider.md は範囲外のままにする。入力は、G の return に載った同じ型の指摘と前の周の指摘の原文（PR コメントの本文を貼る）、対象ファイルのパス、G の仕分け欄とする（decider の入力契約「記録先の本文とコメント」「失敗の出力」「対象ファイルのパス」に当たる）。決める役のモデルは既存の残量モードの規定に従う。決める役が裁定するのは方式（全部列挙してから直す／切り出す）だけで、止めるかどうかの判定は G のまま。これに合わせて「決める役はキャップの判定に関与しない」の要件を外し、関与する範囲を順 6 に限る要件に置き換える。

**主の回答は「切り出す」と「この PR で直す」にする。** 手順 6 の保留の種類「2周目キャップ」は「切り出しの確認」に改め、1 周目から出うることを表す。手順 5 の合格条件の除外も「主が切り出すと答えて follow-up issue に切ったもの」に揃える。

**差分限定の周の新規指摘は、例外 3 種だけ出してよい。** レビュアー向け指示ブロックの「新規の指摘を出さない」に但し書きを足す。出てきた新規の指摘は仕分け表の順 1 から通す。

## Risks / Trade-offs

- 主への質問が「その周で」届くので、2 周目の終わりに 1 回まとめて聞くより回数は増えることがある → 1 件ごとに推奨と見積もりが付くので、1 回あたりの判断の負担は減る想定（issue 本文で主が受け入れを明記）
- 決める役の「全部列挙してから直す」裁定は主の回答なしで 3 周目を開く → PR ごとに 1 回までに限り、2 回目は主に聞く
- 順 3 では、G は W の表の「該当しない理由」が正しいかを見ない（集合の一致だけを見る）→ W が本当は直すべきヒットに誤った「該当しない理由」を付けても閉じてしまう。G がレビューをしないことで周回を増やさないための代償として受け入れる。誤りが残れば、マージ後に follow-up issue で直せる範囲のものになる想定
- 順 3 の集合一致は、W が書いた検索コマンドの範囲が狭すぎると漏れを検出できない → G は検索コマンドが指摘の型（語・軸の全域）を覆っているかを確かめ、書けないなら順 3 に当てない（issue の「検索コマンドや軸の全域を W が書けないなら順 3 には当たらない」）
