# Design

## Context

動機と分割は proposal.md を参照する。既存 3 スクリプトは各自に定数を持ち、`--cap > 明示 env > 定数` の順に扱う。context-tripwire.sh は不正値で fail-open する。この既存契約を保ったまま後続が使える部品を先に追加する。

#1799 の結論（2026-11-24）は `opus-5-5` の作業者の費用、`sonnet-5-5` の手渡し損益分岐、およびモデル混在の累計を測った。調査役が sonnet だったことを、値を決めたモデルの根拠にはしない。品質の最適値は測れていない。

## Goals / Non-Goals

**Goals:** 固定 ID と実測の根拠を伴う表を 1 つ持ち、後続の呼出元が解決値と警告を同時に受け取れるようにする。再検証手順を 1 か所に集める。

**Non-Goals:** モデルを選ぶ処理、使用中モデルをログや環境から推定する処理、既存 hook の出力・拒否・fail-open の変更、エピックの権限付与の自動化、#1802 の計算スクリプト、今回の再測定。

## Decisions

### 共通契約: 根拠付きの JSON 表を Python の解決処理から読み、値と注意をまとめて返す

JSON の表 `references/token-thresholds.json` と Python 標準ライブラリの `scripts/token_thresholds.py` を使う。表を文書から解析する案は形式に依存し、各スクリプトにモデル表を置く案は更新漏れを生むため採らない。Markdown 手順には値を複製せず、JSON の位置・読み方と出典を案内する。

表の schema は `schema_version: 1`、`models`（固定 ID → 4 指標のレコード）、`fallback`（4 指標のレコード）を持つ。指標名は `context_cap` / `context_hard_cap` / `pr_token_cap` / `epic_child_token_cap`。レコードは `value` と、その横の `decided_models`（固定 ID の配列）・`decided_at`（判断日）・`evidence`（実測の説明）・`source`（結論コメント URL）を必須とする。モデルと fallback の初期値はすべて同じ組とする。

初期キーは `claude-opus-5-5` と `claude-sonnet-5-5`。結論中の測定対象ラベル `opus-5-5` / `sonnet-5-5` にプロバイダ接頭辞を付けた対応であり、日付付き ID を推測して作らない。各レコードの `decided_models` はこの 2 ID、`decided_at` は `2026-11-24`、`source` は #1799 の結論とする。`evidence` で次の適用限界を各値に添える。

| 指標 | 値 | 各値に添える実測の要点 |
|---|---:|---|
| context_cap | 150000 | 1410 体の分布と W の手渡し 17 組。Opus 5.5 / Sonnet 5.5 の費用比較では引き上げる根拠がなく、品質の最適値は未測定 |
| context_hard_cap | 220000 | 1410 体のうち到達 0 体。強制停止が有効な線か、品質が保てる線かは未検証 |
| pr_token_cap | 30000000 | 38 件の Claude サブエージェント＋Codex の混合集計。測れた停止 10 件は超過、非停止 27 件の最大 28.1M。単一モデルの品質評価ではない |
| epic_child_token_cap | 60000000 | 同じ 38 件で超過 6 件、p90 78.6M。エピックの子について親が使える権限の現行値を維持。単一モデルの評価ではない |

累計の根拠には Codex の消費も含むが、結論には固定 Codex ID の内訳がない。Codex のモデルを「測定済み」として登録しない。`decided_models` は判断の根拠で扱った Claude モデルの集合であって、4 指標すべてをモデル別に単独検証したという意味ではない。未知モデルの安全側とは「既存値を維持し、窓の大きさなどから値を引き上げない」意味であり、未知モデルの窓に必ず収まる保証ではない。

共通の import 用 API は `resolve_thresholds(model_id, environ=None)`。`None` の environ は現在の環境、渡した mapping はそれだけを使う。モデルは呼出元が計測対象の実効固定 ID を明示する。モデルを省いたら不明として扱い、親のモデル・`AGENT_MODEL`・別名から推定しない。表のパスはモジュールの位置から解決し、cwd に依存しない。

返り値は `requested_model`、`matched_model`（未知時 null）、`fallback_used`、`revalidation_required`、`thresholds`、`diagnostics` を持つ JSON 化可能なオブジェクトとする。各 `thresholds` 項目は `value`・`source_kind`（`model` / `fallback` / `environment`）・表からの根拠レコードを含む。環境上書き時にも表の根拠は `baseline` として残し、上書き値を測定済みとは書かない。

モデルは固定 ID の完全一致だけで引く。未知・空文字・None・`opus` / `sonnet` などの可変別名は fallback。`fallback_used=true` と `unknown_model` 診断を返す。使用モデルが選択した値の `decided_models` に無い（不明を含む）場合は `revalidation_required=true` と `revalidation_required` 診断を返す。既知行でも根拠モデル集合に入っていない ID なら同じ通知を出す。診断には使用モデル（不明なら不明）、根拠モデル、対象指標、手順への repo 相対パスを載せる。状態ファイルや通知の抑制は作らず、該当する呼出しごとに返す。

CLI は `python3 .../token_thresholds.py [--model <固定ID>]`。成功時は同じ結果を stdout に 1 行 JSON、診断の人向け文を stderr に出し、exit 0。未知モデル・再検証通知だけでは失敗にしない。import API は出力せず結果を返すので、後続の hook が自分の契約どおりに通知を載せられる。この change では CLI の stderr と JSON が通知先で、GitHub 投稿や既存 hook への配線はしない。

明示の `DEV_WORKFLOW_CONTEXT_CAP` / `DEV_WORKFLOW_CONTEXT_HARD_CAP` / `DEV_WORKFLOW_PR_TOKEN_CAP` は対応する 3 指標だけを上書きし、モデル既定値より優先する（flatmate #2334 の契約）。空文字・空白だけは未設定扱い。前後の空白を除いた ASCII 非負整数を受け付ける。0 は現在の CLI の数値契約に合わせて通すが、hook に接続するときの正数チェックは change 2 の責務。負数・小数・非数値は名前と理由を持つ `invalid_override` エラーとし、API は ValueError、CLI は stdout に `error` の JSON、stderr に理由、exit 1（利用できる thresholds は返さない）。不正値を黙って既定値に置き換えない。`epic_child_token_cap` の env は新設しない。権限 60M は候補値を返すだけで、`pr_token_cap` を自動で 60M にしない。呼出元の `--cap` はこの部品の外で引き続き最優先になる。環境上書きでもモデルに関する診断を消さない。

同梱表の欠損・不正 JSON・schema 不一致・必須指標や根拠の欠落は設定不良（API は ValueError、CLI は `invalid_table` の error JSON と stderr、exit 1）。表が使えないときに第二の隠れた定数表を持たない。追加フィールドは無視する。ここでの失敗を既存 hook の拒否と結び付ける配線はしない。

### 再検証手順の構成

`skills/develop/references/token-thresholds.md` にだけ再実行の手順を書く。#1799 の一時スクリプトを repo に足さず、取得・材料の準備・順番・出力・比較・結果記録を次の形にする。

1. 対象期間、固定 ID、採用単価と適用日、対象 PR / issue の集合、調査時 HEAD を記録する。基準標本は #1799 結論の子 38 本・エピック 5 本の一覧で指定し、新しい期間の標本は別に分ける。ログの開始日 2026-10-25、欠損する古い子、#1238 の除外理由も記録する。
2. ログの所有者から #1799 の一時スクリプト一式と実行引数・依存バージョン・設定を取得し、hash と起動コマンドを記録する。原スクリプトは repo に無い。取得できなければその点で再現未完とし、同じ集計を再実行したとは扱わない。品質の最適値を測定済みとも扱わない。
3. 作業ディレクトリを `$TMPDIR` / `mktemp -d` の repo 外に作る。会話ログは所有者が示した場所から読み、対象の親セッションとサブエージェントを対応付ける。保存する会話ログの派生物・引き継ぐ集計一式は `LLM_LOG_DIR` で解決し、未設定なら保存先を所有者に確認する。個人のパスや生ログを git に入れない。
4. `gh` で記録先コメント全ページ（停止印・再開判断・スレッド別 Codex 消費）と各 PR の差分・変更後ファイル情報を集め、`cap_comments.json` / `codex.json` / `prfiles.json` を作る。Codex は thread ID ごとの最大値で重複排除、ログ欠損は 0 消費としない。
5. 原スクリプトの実行引数を確認して `collect.py` → `calib.py` → `analyze.py` → `analyze2.py` → `analyze3.py` → `handover.py` → `ctxcap.py` → `analyze4.py` → `analyze5.py` の順に実行する。`units.jsonl` / `children.json` と各集計結果を保存し、基準標本の再現と新モデル標本の比較を分ける。取得前に架空のコマンド引数は書かない。
6. 本体＋Claude サブエージェントの総消費と、上限計測対象の Claude サブエージェント＋Codex を別に集計する。usage の入力・キャッシュ作成・キャッシュ読み・出力を重複排除し、応答別単価でドルに換算する。固定分（起動文脈×ターン数、共通手順書 5 本の保持、回帰切片）、消費見積もり（Read/Bash 換算、逐次ファイル量、1 件ずつ除いた補正と誤差）、手渡し（立ち上がり費用、旧文脈の継続費用差からの損益分岐ターン）を出す。係数 0.77 / 0.65、補正 1.37 は基準標本の値としてだけ扱い、新モデルでは再校正する。
7. 文脈 150k / 220k の到達分布・モデル別ターン単価と、累計 30M / 60M の超過・非超過・停止後の判断を出す。#1684 の停止時合計 69,491,619 と PR #1689 の変更ファイル数などを原記録と検算する。標本数・欠測・p10〜p90・回帰の区間・品質未測定を残し、値を動かす根拠の有無を判断する。
8. 値を変えるごとに、同じ手順の結果を判断用 issue または PR のコメントへ残す（対象モデル・日付・材料と再実行コマンド/hash・集計表・旧新値・採否理由・限界）。表の各値の出典をその結果へ更新する。環境上書きは検証済み既定値を追加したことにはしない。

decision-criteria.md の文脈上限の節に、表とこの手順へのリンク、現時点では共通部品が既存計測経路へ未配線である旨を追記する。「数値と環境変数名はこの節にだけ置く」は、同節の表が未配線期間に実際に動く既存経路の既定値・環境変数・停止動作を説明し、JSON 表が後続の配線で利用するモデル別既定値と根拠を持つことを区別する文に置き換える。共通処理と利用手順には入力として扱う環境変数名を置けるが、手順に数値の表は複製しない。`dev-workflow-develop` の配置要件も同じ契約に改定する。既存の定数値・停止動作・fail-open の意味・手渡し権限、および return-declaration.md と他の面への再掲禁止は変更しない。

## Risks / Trade-offs

- 混在標本をモデル別の品質保証と誤読する → 各値の evidence と手順に混在・品質未測定の限界を明記する。
- 別名で呼ぶと同じ数値でも警告が出る → 固定 ID の明示を促し、推測による測定済み扱いを避ける。
- 元の一時スクリプトが手元に無い → 取得を再現の前提とし、未取得なら未完と記録する。代替集計を黙って同等としない。
- change 1 だけでは既存処理に警告が出ない → 文書で未配線を明示し、change 2 / 3 に API と診断を渡す。

## Migration Plan

この change は部品と文書だけを追加する。unittest と文書のリンク・範囲確認後にマージし、後続 change から利用する。切り戻し時も既存 3 スクリプトは単独で動く。PR 作成・レビュー・archive は本体が指定する後工程で行う。
