# Design

## Context

背景は proposal.md の Why のとおり。周の終わりの扱いは `triage.md` の仕分け表の直後の段落と、手順 2-1 の手順 3 の 2 か所にある。順 6 の裁定は PR ごとに 1 回で、裁定を使い切ると順 6 の指摘は順 5 に入り、同じ周の全件が主への確認に回る。合格処理の前提（`stages/pass.md` の手順 5）は「最後のレビュー結果に止まる指摘が、除外するもの以外 0 件」なので、閉じた指摘を除外に足さないと合格処理に進めない。

下の Decisions は記録先に無い決定で、develop の本体が確認したもの。R1 のレビュー対象とする。

## Goals / Non-Goals

**Goals**

- 2 周目以降の周の終わりに、条件が成り立つ予定の無い止める指摘が、順 6・直し方の判定・順 5 に進まず、理由を残して閉じる
- G が決められないときも、今の動きより悪くならず、オーナーへの確認が増えない

**Non-Goals**

- マージを止めるかの判定（全周共通）の変更
- 1 周目への適用。1 周目は順 2〜5 の扱いのままで、W に戻す費用が小さく、この issue の問題（周の終わりの周回とオーナーへの確認）が起きない
- 順 3・順 4 からの落とし込みで順 6 に当てる指摘への適用。周の終わりの指摘ではなく、W が今の周で閉じられなかった指摘である
- 主が順 5 に条件で答えたときの `hold.md` の扱い
- 段 C・候補探し・順 5 の切り出しの置き場所の変更
- 新しいスクリプト、機械照合する新しいコメント書式

## Decisions

### D1: 条件を判定するのは G で、本体の手順は PR 側に作らない

- 案: `fix-check.md` の節「残った指摘の条件を確かめる」を PR レビューにも広げる（issue の候補）。その節は R1 の当て直しの手順で、G にはレビュー中に条件を判定する立場がある。本体は `needs-fix-check` を受けた時点で判定せず、捨てても照合と振り分けの G に届かない
- 採用: G が `triage.md` の中で判定する。本体は判定しない。R1 の当て直しに当たる手順を PR 側に作らない。#1121 の D1 の「本体は判定しない」と同じ

### D2: 順 6・直し方の判定・順 5 の振り分けより先に当てる

順 6 の裁定は PR ごとに 1 回なので、起きない指摘に使うと、後で本当に要るときに残らない。直し方の判定も決める役を起こす費用が掛かる。止める判定のあとで振り分けの前に当てれば、止める判定そのものは変えずに済む。

### D3: 閉じるのは段 B の「成り立つ予定が無い」の行だけにする

段 B の表の行をそのまま使うと、「条件を書けない」も閉じることになる。段 B で捨ててよいのは止めない指摘だからで、止める指摘は判定を通っているので、条件を書けないことは閉じる理由にならない。「範囲で成り立つ」「後で成り立つ」も止める指摘としては残るので閉じず、既存の経路に進める。

### D4: 閉じない歯止めを 3 つ置く

止める指摘は条件の読み違いの費用が大きいので、次の歯止めを置く。

- 受け入れ条件や delta spec の文がその場面の振る舞いを求めている指摘は閉じない。文がその場面を求めているなら、その場面は仕様の中で成り立つ
- 主が順 5 で「この PR で直す」と答えた指摘は閉じない。主の判断を G が覆さない
- 根拠は段 B と同じに限り、change の artifact の想定は根拠にしない。根拠から言い切れなければ「決められない」に倒す。#1121 の R1 の根拠の規則と同じで、artifact は実装者が書いた想定であって主の答えではない

### D5: G が決められないときは閉じずに既存の仕分けへ進める

- 案: 段 B と同じく `条件の確認待ち` のコメントで聞く。段 B の経路はマージを止めないので、止める指摘には使えない
- 案: `needs-approval` で条件を主に聞く。issue の目的はオーナーへの確認を減らすことで、新しい質問はこれに反する
- 採用: 閉じずに既存の仕分けへ進め、新しい質問も保留も足さない。今の動きより悪くならない。その指摘が順 5 に進んで主が条件を答え、`## 条件の答え` に行が足されれば、後の周で G はそれを根拠に閉じられる

### D6: 記録と合格処理の前提

閉じた指摘は、仕分けの PR コメントに条件と理由を 1 行残し、return の仕分け欄にも書く。全件を閉じたら「止める指摘が残らなかったとき」と同じ扱いにする。

`pass.md` の前提の除外に「G が周の終わりの止める指摘の条件で閉じたもの」を足す。閉じた指摘は最後のレビュー結果に `blocking` のまま残るので、足さないと 0 件にならない。閉じた PR コメントの URL を仕分け欄に残す点は順 3 の除外と同じにする。

### D7: spec の書き方

pr-review-gate は ADDED で新しい Requirement を足し、既存の Requirement「周の終わりに残った指摘を直し方の判定に回す」の「残った止める指摘」は、この段を通したあとの指摘を指すと ADDED の Requirement で定義する。Requirement は検証の長さの上限に合わせ、順序・閉じる範囲・決められないとき・記録・守備範囲に分ける。既存の Requirement は長く、全文の MODIFIED は差分が読めず、#1436 との衝突も増えるので書き換えない。合格条件の Requirement は文が変わるので MODIFIED にする。その際、本文の「SKILL.md 手順 5」は今の置き場の `stages/pass.md` に直す。

develop の Requirement「条件の確かめは PR のレビューに当てない」は MODIFIED で「本体の手順は当てない。G が `triage.md` で確かめる」に直す。要件名は変えない。

## Risks / Trade-offs

- G が根拠を読み違えて、成り立つ指摘を閉じる。歯止め（D4）で減らし、閉じた理由を PR コメントに残して後から見えるようにする。人が見るのは合格後のリスク宣言と PR コメントなので、誤りが 1 件も無いことは完了条件にしない
- 決められない指摘は今までどおり主に上がる。減らせる確認は根拠から言い切れるものだけになる
