## Context

pr-review-gate の手順 1 は、取り直しのたびに `origin/main` をブランチへマージしてから対象 HEAD を固定する。手順 3 の宣言と手順 4 の証拠は `対象 HEAD: <40 桁>` で HEAD に結び付き、手順 5 は現在の HEAD の宣言の実在を実測してから合格処理する。主の許容は、手順 6 で宣言コメントに `主の回答: 許容 — <回答リンク>（<日時>）` と `真正性確認: 済 — 確認者 … / 日時` を追記して記録する。

この仕組みには「前の HEAD で得た許容を新しい HEAD に持ち越してよいか」の規定が無い。main の取り込みで HEAD が動くと、中身が同じでも新しい HEAD の宣言は「主のリスク許容が必要」のまま回答リンクを持たず、ゲートは手順 6 で主に聞き直す。PR #428 ではこれが 2 回起きた（2 回目の回答は「前回の許容のままでよい」）。

制約:

- `対象 HEAD:` 規約（宣言 1 行目 `## リスク宣言`・2 行目 `対象 HEAD: <40 桁>`・行頭 `主のリスク許容が必要。`）は auto-merge workflow の合格条件なので変えない
- G（ゲート担当）の既定モデルは sonnet で、仕事は照合作業。git の履歴グラフの読み取りを文章の指示だけで任せると読み違いが起きやすい
- pr-review-gate は全リポに配られる。版番号や CHANGELOG の置き方はリポごとに違う（このリポは #447 で `version` を撤去し `CHANGELOG.md` を凍結したが、他のリポには残っている）
- 投稿者名は独立した承認の証拠にならない（エージェントが主のアカウントで代理投稿できる。PR #428 の回答コメントも代理投稿）

## Goals / Non-Goals

**Goals:**

- main の取り込みだけで HEAD が動いたとき、主に聞き直さずに前の許容を新しい HEAD の宣言に引き継げる
- 引き継げる条件を満たさないときは、今までどおり主に聞く（fail-closed）
- 引き継ぎで主の許容を捏造できない

**Non-Goals:**

- auto-merge workflow と `対象 HEAD:` 規約の変更
- 許容リンクの真正性確認そのもの（手順 5 の author 実測）のやり方の変更
- レビュー・動作確認証拠・仕様宣言の取り直しの省略。引き継ぎで省けるのは主への質問だけ
- main 以外の変更（W の修正 commit など）が積まれた場合の許容の持ち越し

## Decisions

### 判定の分担: git から決まる条件はスクリプト、許容の真正性とリスクの中身はゲート担当

issue は「機械で判定するか、ゲート担当の確認に任せるか」を仕様化に委ねている。条件を 2 種類に分けて担い手を決める。

| 条件 | 担い手 | 理由 |
|---|---|---|
| 差分が main の取り込みとその衝突解消だけ | スクリプト | git の履歴だけで決まる。merge commit の親の判定や衝突解消の抽出は手で追うと読み違える |
| 衝突解消の中身が版番号と CHANGELOG の並べ直しだけ | スクリプト | 同上 |
| 根拠ファイルが前後の HEAD で同一 | スクリプト | `git diff` が空かどうかで決まる |
| 元の回答が主の直接の許容で、真正性確認済み | G | GitHub のコメントを開いて読む必要があり、「許容の意思が読み取れるか」は読んで判断する |
| 新しい HEAD のリスクの中身が、許容されたものと同じ | G | 手順 2 のレビュー結果から手順 3 の宣言を書くのは G で、その比較も G がする |

代替案「すべてゲート担当の確認に任せる（文書だけ）」は採らない。受け入れ条件の bats が SKILL.md の記述検査に留まり、条件を満たす例・満たさない例の実際の判定を確かめられない。また、この判定はマージ権限（ゲートの通過条件）そのもので、読み違いがそのまま無審査マージにつながる。

代替案「すべてスクリプト（GitHub API で回答コメントも読む）」は採らない。許容の意思の読み取りは機械にできず、author の実測だけでは代理投稿を見分けられない。

### スクリプトの入出力

`plugins/dev-workflow/scripts/risk-carryover-check.sh [--base <ref>] <前 HEAD> <新 HEAD> <根拠ファイル>...`

- ローカルの git リポジトリだけを読む（gh を呼ばない）。G は手順 1 で `git fetch origin` と main の取り込みを済ませているので、両 HEAD と base は手元にある
- `--base` の既定は `origin/main`
- 出力: `CARRYOVER=yes|no`、`MAIN_MERGES=<件数>`、`RESOLVED_FILES=<衝突解消したファイル。空なら none>`、不可の理由ごとに `NG: <理由>` の行
- 終了コード: 0 = 引き継げる / 1 = 引き継げない / 2 = 引数不足・SHA が解決できない・git が古い（`git merge-tree --write-tree` は git 2.38 以上）。2 も引き継げない側に倒す
- 根拠ファイルが 1 つも渡されなければ 2

### 「差分が main の取り込みだけ」の定義

`git rev-list <新> ^<前> ^<base>`（新しい HEAD にあって、前の HEAD にも base にも無い commit）の全件が、次を満たすこと。

1. 前の HEAD が新しい HEAD の祖先である（`git merge-base --is-ancestor`）
2. 各 commit が merge commit で、第 1 親以外の親がすべて base の祖先である
3. 各 commit の第 1 親は、前の HEAD か、この集合の別の commit である（main 以外の commit を merge commit の第 1 親の側に紛れ込ませない）

1 件でも外れたら `NG: non-main commit <sha>` 等で不可にする。前と新が同じ SHA なら件数 0 で引き継げる。

代替案「PR 全体の差分（base との差分）の patch-id を前後で比べる」は採らない。main 側が PR の触ったファイルの別の箇所を変えただけで patch-id が変わって引き継げなくなる一方、どのファイルが動いたのかを理由として出せない。

### 「衝突解消の中身」の定義と許すファイル

各 merge commit について、`git merge-tree --write-tree <第1親> <第2親>` が作る自動マージの tree と、実際の merge commit の tree を比べ、差のあるファイルを「衝突解消したファイル」とする（衝突した箇所の解消と、衝突していない箇所への手入れの両方を拾う。自動でマージできた箇所は拾わない）。3 親以上の merge commit は定義できないので不可にする。

衝突解消したファイルは、次の許可リストに入り、かつ中身の条件を満たすときだけ許す。

| ファイル | 中身の条件 |
|---|---|
| `.claude-plugin/marketplace.json`、`plugins/*/.claude-plugin/plugin.json`（ほかの JSON は含めない） | `"version"` を含む行を除いた本文が、第 1 親か第 2 親のどちらかの同じファイル（同じく `"version"` 行を除く）と一致する |
| `CHANGELOG.md`（リポ直下とサブディレクトリの両方） | merge commit の版のすべての行が、第 1 親か第 2 親の版のどちらかに存在する（並べ直しと取捨だけで、新しい文を足していない） |

issue の「版番号（plugin.json・marketplace.json）と CHANGELOG」をこの 2 行に落とした。許可リストは固定で、リポごとの拡張オプションは設けない。版番号の置き方が違うリポでは引き継げず主に聞く側に倒れるだけで、安全側の失敗になる。このリポでは #447 以降この 2 種類の衝突は起きないので、実際に引き継げるのは衝突なしの取り込みになる。

### 根拠ファイルの出どころ

issue の条件は「許容したリスクの根拠として宣言に挙げたファイル」だが、今の雛形にはファイルを挙げる行が無い。雛形に `- 根拠ファイル: <パス>, <パス>` を足し、G がリスク宣言を書くときにリスクの発生源になっているファイルを列挙する。この行の無い宣言（この変更より前の宣言を含む）からは引き継げない。

代替案「行が無ければ PR の変更ファイル全部を根拠ファイルとみなす」は採らない。宣言が根拠を示していないのに機械が補うと、何を許容したのかが後から読み取れない。

### 捏造を防ぐ条件

引き継ぎの元（元の回答）は、次をすべて満たすときだけ使える。G が確かめ、満たさなければ主に聞く。

1. 前の HEAD の宣言に `主の回答: 許容 — <回答リンク>` か `主の回答: 許容（引き継ぎ） — <回答リンク>` があり、`真正性確認: 済` の行がある
2. 引き継ぎの記録に書く回答リンクは、元の直接の回答（主が許容を述べたコメント・メッセージ）を指す。引き継ぎの記録そのもの（エージェントが書いた宣言コメント）を回答リンクにしない。引き継ぎが 2 回以上続いても、回答リンクは最初の直接の回答のまま
3. 引き継ぐたびに、手順 5 の真正性確認（リンク先を開き、主の発言で許容の意思が読み取れることを確かめ、GitHub コメントなら author を実測する）を元の回答リンクに対してやり直し、新しい宣言に `真正性確認: 済` を追記する
4. 新しい HEAD のリスク宣言の中身（リスク内容・該当する観点・発生条件・影響範囲と戻し方・根拠ファイル）が、元の回答が許容した宣言と同じである。レビューで新しいリスクが見つかった・観点が増えた・根拠ファイルが増えたときは引き継げない

投稿者名だけで主の許容とみなさない点は既存の手順 5 と同じで、ここでは変えない（代理投稿の見分けは本件の範囲外）。

### 宣言の書式

新しい HEAD の宣言は、前の宣言と同じ本文（行頭 `主のリスク許容が必要。` を含む）で出し直し、末尾に次を追記する。宣言本文は書き換えない規則（手順 5）はそのまま適用する。

```
主の回答: 許容（引き継ぎ） — <元の直接の回答リンク>（<元の回答の日時>）
引き継ぎ元: <前の HEAD の 40 桁フル SHA> の宣言 <前の宣言コメントのリンク>
引き継ぎの根拠: risk-carryover-check.sh 終了コード 0 — main の取り込み <件数> 件、衝突解消 <none またはファイル>、根拠ファイルの diff は空
真正性確認: 済 — 確認者 <エージェント名> / <日時>（元の回答を再確認）
```

1 行目は issue の案 `主の回答: 許容（引き継ぎ） — <前の回答リンク>` を採り、リンク先を「元の直接の回答」に定めた。手順 5 の合格条件の表には「引き継ぎで許容済み」の行を足し、この 4 行が揃っていれば合格処理に進めるとする。

### 手順上の位置

手順 3 で「主のリスク許容が必要」と判定したとき、手順 6 に行く前に引き継げるかを確かめる小節（3-c）を置く。引き継げれば `needs-approval` を付けずに手順 4・5 へ進み、引き継げなければ手順 6 で主に聞く（主への質問文に、引き継げなかった理由のスクリプト出力 `NG:` 行を添える）。手順 6 の復帰の表と gate-runner.md の取り直しの節からはこの小節を参照するだけにし、条件を再掲しない。

## Risks / Trade-offs

- [根拠ファイルの列挙漏れ] G がリスクの発生源を根拠ファイルに挙げ損ねると、そのファイルが main 側で変わっても引き継げてしまう → 条件 4 で新しい HEAD のリスクの中身を G が比べ直す。レビューは新しい HEAD で取り直すので、main 側の変更でリスクが変われば宣言の中身が変わって引き継げなくなる
- [許可リストの JSON で版以外の行が変わる] → 中身の条件で `"version"` 行以外が親のどちらかと一致することを求める
- [他リポで版番号の衝突が起きたとき許可リスト外で引き継げない] → 主に聞く側に倒れるだけで、今と同じ動き
- [git 2.38 未満の環境] → 終了コード 2 で引き継げない側に倒れる
- [編集ファイル数] スクリプト・bats・SKILL.md・gate-runner.md・変更記録の 5 つに既存 bats の追記が加わり、実装で規模超過のトリップワイヤー（5 個超）に当たりうる。分けると SKILL.md の手順とスクリプトの入出力が別 PR に割れて片方だけでは動かないので、1 change のまま進める
