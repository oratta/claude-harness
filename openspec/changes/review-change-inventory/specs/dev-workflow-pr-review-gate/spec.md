## ADDED Requirements

### Requirement: 順 3 と一周目照合は共通の全ヒット一覧契約を使う

SKILL.md は、仕分け表の順 3 の第 1 段と一周目レビューの `照合表` が共有する全ヒット一覧契約を 1 か所に定めなければならない（MUST）。共通部分は、`修正前 SHA: <40 桁>`、`検索コマンド: git grep -n <語の指定> <rev> -- .`、および `| ファイル | 行（修正前 SHA） | ヒットした行の本文 | 扱い |` の列とする（MUST）。一周目レビューでは固定した対象 HEAD を `修正前 SHA` とし、順 3 では W が修正に着手する直前の HEAD を使う（MUST）。

検索起点はリポジトリルートで、固定 revision の追跡対象パスをすべて含めなければならない（MUST）。サブディレクトリだけへの限定や追跡対象パスの除外をしてはならない（MUST NOT）。`.git` のメタデータと固定 revision に含まれない untracked / ignored の生成物は対象外とするが、追加の追跡対象除外は設けない（MUST）。

共通照合スクリプトは、SHA・検索コマンド・表の共通列を受け取り、第 4 列の値を集合の同一性に使わず、固定 SHA での全ヒット集合と表の全行を比較しなければならない（MUST）。一周目レビューの `扱い` は `一致` / `食い違い: <finding ID>`、順 3 の `扱い` は `直した` / `該当しない: <理由>` とする（MUST）。順 3 の修正後 HEAD に対する本文・件数・削除行の照合は順 3 固有の第 2 段として維持し、一周目の同一 SHA 照合には適用してはならない（MUST NOT）。

#### Scenario: 両経路が同じ共通入力を受理する

- **WHEN** 同じ修正前 SHA・repository-wide な検索コマンド・同じ 3 列のヒット集合を持ち、第 4 列だけが一周目用と順 3 用で異なる 2 表を照合する
- **THEN** 共通照合スクリプトは両方を同じヒット集合として受理し exit 0 を返す

#### Scenario: 別ディレクトリの未変更ファイルも対象にする

- **WHEN** 検索語が変更ファイルのほか別ディレクトリの未変更ファイルにも存在し、表が変更ファイルのヒットだけを載せている
- **THEN** 共通照合スクリプトは未変更ファイルのヒットを missing として出力し exit 1 を返す

#### Scenario: 検索範囲の限定を拒否する

- **WHEN** 検索コマンドが `-- .` ではなく変更ディレクトリだけを起点にするか追跡対象パスを除外する
- **THEN** 共通照合スクリプトは共通一覧契約違反として exit 1 を返す

### Requirement: G は一周目の三表を機械照合してから指摘を受理する

G は一周目のレビュー結果について、指摘の内容を読む前に次を機械照合しなければならない（MUST）: 記録先の各受け入れ条件が `変更点の一覧` の 1 項目以上に対応していること、各 `照合表` の全ヒット集合が表に記載された再実行可能な検索コマンドを対象 HEAD で実行した集合と一致すること、固定した PR diff の全ハンクが `ハンク被覆` に 1 回以上現れること。G はこの照合で変更点の意味や `一致` / `食い違い` の正しさを再レビューしてはならない（MUST NOT）。

dev-workflow プラグインは、共通一覧契約の表から得たヒット集合と G が検索コマンドを固定 SHA で再実行して得たヒット集合の差分を比較するスクリプトを含まなければならない（MUST）。集合が一致するときは exit 0、表に無いヒットまたは検索結果に無い表の行があるときは exit 1 と差分の `file:line` を出力する（MUST）。このスクリプトは一周目照合と順 3 の第 1 段で共用しなければならない（MUST）。

照合に差分または欠落した表があり `補足済み回数: 0` のとき、G はレビュー全体をやり直させず、固定 HEAD・元の三表・残差・補足済み回数を含む Status `needs-reviewer` で、不足した項目だけの補足を求めなければならない（MUST）。本体が fresh reviewer を起動する経路でも、その reviewer は同じレビューの不足分だけを補い、元の三表を置き換えたりレビューを最初から行ったりしてはならない（MUST NOT）。

補足結果は `補足済み回数: 1` とともに G へ渡し、G または reviewer が fresh thread に交代しても回数をリセットしてはならない（MUST NOT）。補足後も差分または欠落が残る場合、G は残差を記録して terminal Status `review-incomplete` で return し、合格処理へ進んではならない（MUST NOT）。develop 本体は `review-incomplete` を受けたら新しい reviewer を起動せず、`agent-review:pending` のまま残差を報告して工程を止めなければならない（MUST）。

#### Scenario: 照合表に無いヒットを検出する

- **WHEN** レビュアーの照合表に無い `file:line` を 1 件含む検索結果を照合スクリプトへ渡す
- **THEN** スクリプトは exit 1 で終了し、その `file:line` を差分として出力する

#### Scenario: ヒット集合が一致する

- **WHEN** レビュアーの照合表と検索結果が同じヒット集合を持つ入力を照合スクリプトへ渡す
- **THEN** スクリプトは exit 0 で終了する

#### Scenario: 受け入れ条件とハンクを照合する

- **WHEN** 一周目のレビュー結果を G が受け取る
- **THEN** G は各受け入れ条件が変更点に対応し、固定した diff の各ハンクがハンク被覆に現れることを機械照合してから指摘の仕分けへ進む

#### Scenario: 補足後にも差分が残る

- **WHEN** G が不足項目だけを 1 回追加依頼した後も照合差分が残る
- **THEN** G は残った差分と `補足済み回数: 1` を記録して `review-incomplete` で return し、本体は reviewer を再起動せず、合格処理へ進まない

#### Scenario: fresh reviewer でも補足回数を増やさない

- **WHEN** Codex 経路で本体が補足用の fresh reviewer を起動し、その結果を fresh G に渡した後にも差分が残る
- **THEN** payload の固定 HEAD・元の三表・残差・`補足済み回数: 1` が引き継がれ、fresh G は `review-incomplete` で終了し、2 回目の `needs-reviewer` を返さない

### Requirement: 三表を含む指示を codex exec で実測する

この change の実装は、手順 2-1 のレビュアー向け指示ブロックを渡した `codex exec` の実測を 1 回行い、`変更点の一覧`・`照合表`・`ハンク被覆` が出力されたかを PR コメントに記録しなければならない（MUST）。三表の一部または全部が出なかった場合も、実際に出た形と欠けた表を同じコメントに記録する（MUST）。Codex が既存の不可条件（バイナリ無し・認証切れ・待ち方の正本の総待ち上限）で使えない場合は、実測した不可条件を記録する（MUST）。

#### Scenario: 三表が出力される

- **WHEN** レビュアー向け指示ブロックを渡した `codex exec` が完了し、三表を出力する
- **THEN** PR コメントに実行した対象と、三表が出たことが記録されている

#### Scenario: 表が欠ける

- **WHEN** 実測した Codex 出力に三表の一部または全部が無い
- **THEN** PR コメントに実際の出力形と欠けた表が記録されている

### Requirement: 二周目以降の指摘を四分類で記録する

`skills/develop/references/roles/gate-runner.md` の Gate Result は、二周目以降に新しく出た、または未解決で残った各指摘について、`同じ文が複数か所`・`場合分けの漏れ`・`直したつもりで直っていない`・`直しで新しく入った` のいずれか 1 つを記録する欄を持たなければならない（MUST）。この分類は効果測定用であり、マージを止めるかの判定や仕分け表の順を変更してはならない（MUST NOT）。

#### Scenario: 二周目の指摘を分類する

- **WHEN** 二周目以降のレビュー結果に新規または未解決の指摘がある
- **THEN** G の PR コメントと return は指摘ごとに四分類のいずれか 1 つを記録する

#### Scenario: 分類だけで blocking にしない

- **WHEN** 指摘が四分類のいずれかに当たるが全周共通の停止判定を満たさない
- **THEN** G は分類を理由にマージを止めず、既存の判定と仕分けに従う

## MODIFIED Requirements

### Requirement: レビュアーの指摘に固定書式を課す

SKILL.md 手順 2-1 は、レビュアー（Codex CLI・Task サブエージェント）が書く指摘 1 件ごとの固定書式を規定しなければならない（MUST）。各指摘は次のフィールドを持つ（MUST）: 見出し（命令形 1 行・80 字以内）、深刻度（`blocking` / `should` / `nit`）、検証（`confirmed`＝実行・テストで裏取り済み / `plausible`＝推測・未検証）、根拠（深刻度が `blocking` のとき必須。記録先の受け入れ条件または PR が触れる openspec spec の原文の引用、または例外 3 種＝安全機構の穴・データ破壊・無言の機能不全のどれに当たるか）、場所（`file:line-range`、diff と重なる範囲で 10 行以内）、何が起きるか（入力・状態と誤動作、発生条件）、直し方（行レベルの置換コードか 3 行以内の手順で、そのとおりに直せば指摘が閉じるもの）。ただし `照合表` で見つけた食い違いの指摘は、変更した記述と diff 外の既存記述を結ぶ 2 つの場所を書いてよく、少なくとも一方が diff と重なればよい（MUST）。再レビューでは各指摘に状態（`fixed` / `unresolved` / `wontfix`）を足す（MUST）。

SKILL.md は深刻度 3 値の定義表を持たなければならない（MUST）: `blocking` は受け入れ条件または仕様の文に違反しマージすると壊れるもの、`should` は直すべきだがマージ後に issue で直せるもの、`nit` は好み・スタイル。

書式と深刻度の定義表は SKILL.md 手順 2-1 に 1 か所だけ置き（MUST）、レビュアーへの指示文に貼り付けられるブロックの形にする（MUST）。他のファイルは書式を再掲せず、このブロックを参照する（MUST NOT 再掲）。Codex が優先度付きの形で返したときの読み替え表は、三表が無い出力を完全なレビュー結果へ読み替えず、不足したレビュアー出力として扱うことを明記しなければならない（MUST）。

#### Scenario: 書式の見出し語と深刻度 3 値がある

- **WHEN** SKILL.md 手順 2-1 を読む
- **THEN** 深刻度・検証・根拠・場所・何が起きるか・直し方の各欄と、`blocking` / `should` / `nit` の定義表がある

#### Scenario: 再レビューの状態欄がある

- **WHEN** SKILL.md の固定書式を読む
- **THEN** 再レビュー時に各指摘へ `fixed` / `unresolved` / `wontfix` の状態を足すことが書かれている

#### Scenario: 食い違いは diff 外を含む二か所を示せる

- **WHEN** 変更したルールと diff 外に残る既存ルールの食い違いを指摘する
- **THEN** 指摘の場所欄は diff と重なる場所と diff 外の場所の 2 か所を記録できる

#### Scenario: 優先度付き出力に三表が無い

- **WHEN** Codex が優先度付きの指摘を返したが `変更点の一覧`・`照合表`・`ハンク被覆` のいずれかが無い
- **THEN** 読み替え表は欠けた表を不足したレビュアー出力として扱い、G は一周目の照合を完了扱いにしない

### Requirement: レビュアーへの指示に全件列挙と再レビューの制限を含める

SKILL.md 手順 2-1 のレビュアー向け指示ブロックは、一周目に指摘を書く前に、次の三表を順に出すことを要求しなければならない（MUST）。

1. `変更点の一覧`: この PR が新しく決めたルール・判定・用語を ID 付きで列挙し、各項目に対応する受け入れ条件と検索語を書く。各受け入れ条件は 1 項目以上に対応させる
2. `照合表`: 変更点 ID ごとに、共通一覧契約の `修正前 SHA`（固定した対象 HEAD）、repository-wide な `git grep -n ... <rev> -- .`、diff 外を含む全ヒットのファイル・修正前 SHA での行・本文・`扱い`（`一致` または `食い違い: <finding ID>`）を書く。順 3 との差は第 4 列の値と、修正後 HEAD を検査する第 2 段が無いことだけとする
3. `ハンク被覆`: 固定した PR diff の各ハンクについて、ファイル・ハンクヘッダーと指摘 ID または `問題なし` を書く

レビュアーは `変更点の一覧 → 照合表 → ハンク被覆 → 三表の自己点検 → 指摘` の順で進め、三表を指摘より前に出さなければならない（MUST）。保証範囲は変更点の一覧に載った項目についてリポジトリ内の出現箇所をすべて照合したことまでとし、一覧自体に載らなかった暗黙の変更を発見したことを完了条件にしてはならない（MUST NOT）。

同じ指示ブロックは、1 周目は対象範囲に該当する指摘を全部列挙するまで止まらないこと、差分限定の再レビューは前回指摘の閉鎖確認（状態欄の付与）に限り新規の指摘を出さないことを含まなければならない（MUST）。ただし例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる新規の指摘は、差分限定の周でも出してよい。方式の書き換え後の全体レビューでも新規に出してよい深刻度は `blocking` だけとし、前回の「直し方」どおりに直した箇所を再指摘してはならない（MUST NOT）。直し方自体が誤っていた場合はレビュアー側の誤りとして `wontfix` 相当の記録にする。差分限定の周に出た例外 3 種の新規指摘は、仕分け表の順 1 から通す（MUST）。

#### Scenario: 三表が指摘より前にある

- **WHEN** 一周目のレビュアー向け指示ブロックに従ってレビュー結果を作る
- **THEN** `変更点の一覧`・`照合表`・`ハンク被覆` がこの順で指摘より前に出力される

#### Scenario: 受け入れ条件と変更点を対応づける

- **WHEN** `変更点の一覧` を作る
- **THEN** 記録先の各受け入れ条件が 1 つ以上の変更点 ID に対応し、各変更点に検索語がある

#### Scenario: 照合表は diff 外を含む

- **WHEN** 変更点の検索語が diff 外のファイルにも現れる
- **THEN** `照合表` は再実行可能な検索コマンドと diff 外を含む全ヒット、その判定を記録する

#### Scenario: 全件列挙の一文がある

- **WHEN** SKILL.md のレビュアー向け指示ブロックを読む
- **THEN** 「該当する指摘を全部列挙するまで止まらない」旨の 1 文がある

#### Scenario: 再レビューで新規 nit を出さない

- **WHEN** SKILL.md のレビュアー向け指示ブロックを読む
- **THEN** 再レビューでは新規の `nit` を出さず、全体レビューに戻っても新規に出してよいのは `blocking` だけと書かれている

#### Scenario: 差分限定の周でも例外 3 種は出せる

- **WHEN** SKILL.md のレビュアー向け指示ブロックの、新規の指摘を出さない文を読む
- **THEN** 例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる新規の指摘は出してよいという但し書きがある
