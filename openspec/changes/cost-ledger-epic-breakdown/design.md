## Context

`/cost <番号>` は `cost_ledger.py cost <番号>` を呼ぶ。`resolve_number()` が `gh` で PR か issue かを判別し（PR の問い合わせ 1 回、PR でなければ issue の問い合わせ 1 回）、issue なら `cmd_issue` に渡して「その issue の番号を触った区間」の合計を出す。

#689（PR #738）で、issue の合計を「その issue を閉じた PR のヘッドブランチの行すべて + その issue に帰属した区間の行のうち、それらのブランチ上に無い行」と定めた（spec `cost-ledger-attribution` の「issue の合計は、閉じた PR の分と、PR のブランチ上に無い区間の分の和である」）。この合計は `cost_ledger.py issue <N> --closing-pr <番号>:<ヘッドブランチ>` と、`gh issue close` の hook が積む合計の行で出る。`/cost <issue番号>` は今も区間だけの合計を出す。

#689 からの申し送り: 1 本の PR が複数の issue を閉じると、その PR の分は閉じた各 issue の合計に全額入る。エピックで子 issue の合計を足すと、その分が issue の数だけ重なる。足し方は #690 で決める。

仕様づくりの時点（HEAD 6fa8dbb4）で確かめた事実:

- REST の `repos/oratta/claude-harness/issues/272` の応答に `sub_issues_summary.total`（20）がある
- GraphQL 1 回で、#272 の子 20 件と、子ごとの閉じた PR が取れた（0.66 秒）。owner と name は `-F owner={owner} -F name={repo}` で渡せる
- 番号の判別の REST は 1 回 0.52 秒。#272 の `gh` は合わせて 3 回、約 1.7 秒
- 実データに、1 本の PR が 2 件の子を閉じている例がある（PR #719、ヘッドブランチ `oratta/issue-699` が #699 と #702 を閉じている）
- 今の #272 に、孫を持つ子は 0 件
- 実環境の台帳は約 68 MB・159,711 行で、読み通し 1 回が約 0.7 秒（`plugins/cost-ledger/changes/701.md` の実測）

エピック #272 の「全体の制約」: LLM のトークンを使わない（集計はスクリプトだけ）。待ち時間と `gh` の呼び出し回数を実測して PR に書く。

## Goals / Non-Goals

**Goals:**

- 子 issue を持つ issue に `/cost` を実行すると、子 issue ごとの額と合計が出て、内訳の和が合計と一致する
- 同じ PR を複数の子が参照していても、その PR の分を 1 回しか数えない
- `gh` は子を持つ issue ごとに 1 回で、子を持たない子 issue の数と PR の数では増えない。台帳の読み取りは issue の数にも PR の数にも比例しない
- 子を持たない issue と PR の `/cost` は、出力も `gh` の回数も変えない
- 一部の子しか読めていない額を、エピックの合計として見せない

**Non-Goals:**

- `/cost <子 issue の番号>` に閉じた PR の分を足す
- エピックのコメントに hook が積む行に子 issue の分を入れる（`timeline`・`gate_report.py` は変えない）
- GitHub の子 issue として登録されていない issue（本文の表に書いてあるだけの issue）を数える
- 別のリポジトリの子 issue を数える
- #691・#695・#726 の範囲

## Decisions

### 1. エピックかどうかの判定: 番号の判別で既に呼んでいる issue の問い合わせの応答を使う

`resolve_number()` が呼ぶ REST の `repos/{owner}/{repo}/issues/<番号>` の応答の `sub_issues_summary.total` が 1 以上なら、子 issue を持つ issue として扱う。今は `--jq .number` で番号だけを取り出しているので、同じ呼び出しの jq に子の数を足す。`gh` の呼び出しは増えない。

値が応答に無いか整数として読めないときは、子を持たない issue として扱う。既存のテストの偽 `gh`（番号だけを返す）はこの扱いでそのまま通り、応答にこの値が無い環境でも今までどおり区間の合計が出る。

退けた案:

- **`--epic` のような引数で利用者に指定させる。** `/cost 272` と打つだけでは今までどおりほぼ 0 が出るので、issue の「やらないとどうなるか」が解決しない
- **判定のために `sub_issues` を別に呼ぶ。** 子を持たない issue の `/cost` でも `gh` が 1 回増える

### 2. 辿り方: GraphQL を、子を持つ issue 1 件につき 1 回

`gh api graphql` 1 回で、ある issue の `subIssues(first: 100)` と、子 1 件ごとの番号・題名・状態・リポジトリ・子の数（`subIssuesSummary.total`）・閉じた PR（`closedByPullRequestsReferences(first: 100)`）を取る。エピック自身への問い合わせでは、エピック自身を閉じた PR と、作業ディレクトリのリポジトリの `nameWithOwner` も同じ 1 回で取る。子の数が 1 以上の子には同じ問い合わせをもう 1 回行い、0 の子には問い合わせない。

`gh` の回数は「番号の判別の 2 回 + 子を持つ対象の issue の数（エピック自身を含む）」になる。#272 は 3 回。子を持たない子 issue が何件あっても増えないが、子が 1 件ずつ入れ子になった鎖では、子を持つ issue が段の数だけあるので、その数だけ呼ぶ（最大で 2 + 8 回。決定 6）。

issue #690 の本文は REST の `repos/<owner>/<repo>/issues/<N>/sub_issues` を挙げ、備考で「子の数だけ `gh api` を呼ぶ」と見込んでいる。REST では子の一覧に閉じた PR が入らないので、子ごとに閉じた PR の問い合わせが要り、#272 で 22 回以上（1 回 0.5 秒として 11 秒以上）になる。エピック #272 の「全体の制約」（待ち時間を抑える）に合わせて GraphQL にした。本文の REST の記述は手段の例として読み、求めている結果（子を辿って内訳を出す）は変えていない。

問い合わせの文字列は固定で、owner・name・番号は `-F` の変数で渡す（文字列に埋め込まない）。数える PR の絞り方（ベースのリポジトリが一致し、`isCrossRepository` が偽）と応答の形の検査は、`gate_report.py` の `closing_prs()` と同じにする。`gate_report.py` を import はしない（hook 側のスクリプトと集計側のスクリプトを互いに依存させない。#689 の決定「`gh` を呼ぶのは `gate_report.py`、計算するのは `cost_ledger.py`」は `timeline` についての決まりで、`cost` サブコマンドは元から `gh` を呼んでいる）。

### 3. エピックの合計: 行の和集合

エピックの合計は、エピック自身と子孫の issue が数える行を、行ごとに 1 回だけ足した額にする。issue が数える行は #689 の定義のまま（その issue を閉じた PR のヘッドブランチの行と、その issue に帰属した区間の行）。

重なりは 2 種類ある。

- 1 本の PR（または同じヘッドブランチ）が複数の issue を閉じる
- ある issue に帰属した区間の行が、別の issue を閉じた PR のヘッドブランチ上にある

退けた案:

- **PR を単位に重複を除く**（申し送りが例に挙げた形）。1 つ目の重なりは消えるが、2 つ目が残る。子 A の区間の行が子 B の PR のブランチ上にあると、A の「PR の外の区間の分」と B の「PR の分」の両方に入る。行を単位にすれば両方が消え、定義も 1 文で済む
- **子ごとの単独の合計をそのまま足す。** 重なった分だけ総額が大きくなる。受け入れ条件「その PR の分を 1 回しか数えない」を満たさない

### 4. 重なった行の割り当て: PR のブランチの行は番号がいちばん小さい issue へ

行を次の順で 1 つの issue に割り当てる。

1. 行のブランチ名が、対象の issue を閉じた PR のどれかのヘッドブランチと一致する行は、そのヘッドブランチの PR が閉じた対象の issue のうち、番号がいちばん小さい issue へ
2. それ以外の行で、対象の issue に帰属した区間の行は、その issue へ

#689 が同じ場面で選んだ向きに合わせた（区間と PR が重なったら PR の側に数える。同じヘッドブランチの PR が複数あれば番号がいちばん小さいものだけ数える）。規則が入力だけで決まるので、GitHub が子を返す順が変わっても結果が変わらない。

複数の issue を閉じた PR の分は、番号がいちばん小さい issue に全額が入り、ほかの issue の割り当てた額には入らない。行からは、実際にどの issue の作業だったかは分からない。これは起きるかどうか分からないことではなく、この規則の性質なので、表示で単独の合計との差として見せる（決定 5）。

退けた案:

- **均等割り。** 行の実体と対応しない額になり、行を 1 つの issue に割り当てられないので、JSON で「どの行をどこに数えたか」を説明できない
- **PR を先に閉じた issue へ。** 閉じた時刻の問い合わせが増え、同時に閉じた場合の決め方がもう 1 つ要る

### 5. 子ごとの額の見せ方: 割り当てた額を並べ、単独の合計と違うときだけ添える

内訳の額は「割り当てた額」にする。対象の issue すべての割り当てた額の和が、合計と一致する。割り当てた額が単独の合計（#689 の定義でその issue だけを見た額）と違う issue の行には、末尾に `（単独 $3.00、PR #300 は #11 に計上）` を添える。違いの原因が「別の issue の PR のブランチ上にある区間の行」だけのとき（その issue を閉じた PR はどれも自分に割り当てられている）は、`（単独 $3.00）` だけになる。

JSON は issue ごとに `usd`（その issue と下の issue すべての和）・`own_usd`（割り当てた額）・`standalone_usd`（単独の合計）・`closing_prs[].counted_in`（その PR の行を割り当てた issue の番号）を持つ。`own_usd` の和が `total_usd` と一致する。

これで受け入れ条件の「合計が子の額の和と一致する」と「同じ PR を 1 回しか数えない」を同時に満たし、「この子に結局いくらかかったか」（単独の合計）も失わない。

退けた案:

- **単独の合計を並べて、最後に「重複 −$X」の行を足す。** 子の額の和が合計と合わない
- **共有された PR を、どの子にも属さない別の行に出す。** 子の額の和が合計にならず、PR の行が子の行と同じ並びに混ざる

### 6. 孫・循環・深さ・状態・別のリポジトリ

- **孫も辿る**（issue の本文の指定）
- **一度出てきた番号は、2 回目以降は数えず辿らない。** 循環で止まらなくなることと、同じ issue を 2 回数えることを防ぐ
- **深さはエピックから 8 段下まで。** GitHub が許す入れ子の上限と同じにした。8 段下の issue がさらに子を持つと分かったら、その時点で終了コード 2 を返す（決定 7）。問い合わせるのは深さ 0〜7 の issue なので、1 件ずつの鎖なら GraphQL は 8 回で止まる
- **open の子も closed の子も数える。** エピックは進行中に見るものなので、closed だけにすると作業中の子が抜ける。open の子では、結び付いている open の PR のブランチも数える（作業の途中の額になる）
- **別のリポジトリの子は、数えず、辿らず、別立ての 1 行に出す。** issue に帰属する行は、実行した作業ディレクトリのリポジトリの行に限る決まりがあり、別のリポジトリの区間は手元の番号と突き合わせられない。黙って落とすと「全部数えた」と読めるので、行に出す

### 7. 読み切れないときは合計を出さない

次のときは、標準出力を空にし、標準エラーにどの issue で何が読めなかったかを書いて、終了コード 2 を返す。

- GraphQL の呼び出しが失敗した
- 応答が JSON でない、または 1 件でも形が崩れている（番号が整数でない、ヘッドブランチが空など）
- `subIssues` か `closedByPullRequestsReferences` の `hasNextPage` が真（100 件を超える）
- エピックから 8 段下の issue がさらに子を持つ

#689 の「一部しか読めていない結果を合計にしない」と同じ考え方。#689 の hook は合計の行を積まずに済ませたが、こちらは利用者が打ったコマンドなので、黙って区間だけの額に戻すと「エピックの額はこれだけ」と読めてしまう。失敗として返す。

ページ送りは実装しない。子が 100 件を超えるエピックと、1 件の issue を閉じた PR が 100 件を超える場合は、今のデータに無い（#272 で子 20 件）。必要になったら足す。

### 8. 表示: 1 行目は `headline()`、内訳は入れ子の字下げ

1 行目は既存の `headline()` で作る（`コスト: $7.00 / ¥1,050 @150 — issue #10 (acme/ra) 帰属: 子 issue 込み`）。帰属の種別を新しくしたのは、同じ issue 番号でも `区間`（`cost_ledger.py issue` と hook の行）と額が違うことを 1 行目だけで見分けられるようにするため。

内訳の行は `#<番号> <状態> <額>` に、子を持つ issue では `（自身 <割り当てた額>）` を続け、` — <題名>` を書く。額は、その issue と下の issue すべての和。エピックから 1 段下がるごとに空白を 2 つ足す。題名が 40 文字を超えるときは先頭 39 文字と `…` にする（行が端末の幅で折り返すのを抑える。全文は JSON の `title` にある）。

子の区間ごとの内訳は出さない（子が 20 件あると数百行になる）。`/cost <その issue の番号>` で見られることを 1 行で伝える。

### 9. 変えないもの

- 子を持たない issue と PR の `/cost`（出力と `gh` の回数）
- `cost_ledger.py issue`（子を調べない。エピックの番号を渡しても、今までどおり区間の合計と `--closing-pr` の合計）
- `cost_ledger.py timeline` と `gate_report.py`（hook がエピックのコメントに積む行は、エピックの番号を触った区間だけの累計のまま）

`/cost <エピックの番号>` の 1 行目が変わると、既存の spec の 3 つの記述と食い違う（`/cost <issue番号>` は区間の合計を返す・帰属の種別は 2 種類・`timeline` の累計は `cost <issue番号>` と一致する）。食い違いを残さないため、3 本の要件を MODIFIED にした。`timeline` の振る舞いは変えず、子 issue を持つ issue では一致の相手が `cost_ledger.py issue <番号>` になる、と言い直している。

### 10. 読み取りは子の数に比例させない

- 台帳への差分の追記は、1 回の呼び出しで 1 回
- 区間の行は、対象の issue すべての分をまとめて読む（`iter_ledger_issue_facts` を番号の集合で受けられるようにする。番号 1 件での呼び出しの結果は変えない）
- PR の分は、全ヘッドブランチの分を `load_branches_facts()` でまとめて読む（#689 で足した関数をそのまま使う）

台帳を読み通す回数は、子が何件でも同じになる。回数の値は tasks の実測で確かめて PR に書く。

### 11. 単価表のずれの突き合わせ

合計に数えた行のセッションを対象に、`price_drift()` を `facts` を渡さずに呼ぶ（既定の 1 秒の上限で打ち切られる。`cmd_branch` と同じ呼び方）。`--no-drift-check` を渡したときは行わない。エピックは対象のセッションが多いので、上限なしで読み直すと待ち時間が延びる。

### 12. 子 issue の合計とエピック自身の額を別の行に出す

issue #690 の受け入れ条件は「合計が子の額の和と一致する」。一方で、エピック自身の番号を触った区間の額（計画やレビューの作業）は実際にかかった額で、合計から落とすと 1 行目が実額より小さくなる。両方を満たすために、次のようにする。

- 内訳の前に `  子 issue の合計: <額>` と `  issue #<番号> 自身: <額>` を 1 行ずつ出す。JSON は `children_usd` と `self_usd` を持つ
- 「子 issue の合計」は、エピックの直下の子の行の額の和と一致する（受け入れ条件を、エピック自身の区間があってもなくても、この行で文字どおり確かめられる）
- 1 行目の合計は「子 issue の合計 + エピック自身の額」。エピック自身の区間が無ければ、1 行目の合計は子の額の和と同じになる

Scenario「合計が子の額の和と一致する」は、エピック自身の区間が無いデータで 1 行目の合計と子の額の和の一致を確かめる。エピック自身の区間があるデータは別の Scenario にして、子 issue の合計の行と、1 行目がその和に自身の額を足した値であることを確かめる。

退けた案:

- **エピック自身の区間の額を合計に入れない。** 合計が実際にかかった額より小さくなる
- **エピック自身の額を足した値だけを出す**（R1 の 1 周目までの形）。受け入れ条件の「子の額の和と一致」を、エピック自身の区間があるデータで確かめられない

## Risks / Trade-offs

確定している性質（起きるかどうかではなく、この設計がそうなっているもの）:

- 複数の issue を閉じた PR の分は、番号がいちばん小さい issue に全額が入る → 行の末尾の `（単独 …、PR #N は #M に計上）` と JSON の `counted_in` で見える
- `/cost <子の番号>`（区間だけ）と、エピックの内訳のその子の額（閉じた PR 込み）は一致しない → 内訳の下の 1 行と README に書く。揃えるのは別の子 issue の候補
- エピックのコメントに hook が積む累計は、`/cost <エピックの番号>` の 1 行目と一致しなくなる → 帰属の種別（`区間` と `子 issue 込み`）で見分けられる。README に書く
- GitHub の子 issue として登録されていない issue は数えない。#272 では #273・#274・#276 が本文の表にだけあり、`/cost 272` の内訳に出ない
- エピックの `/cost` は、子を持つ issue の数だけ `gh` が増える（#272 で 2 回から 3 回。鎖状の入れ子では段の数だけ増え、最大で 10 回）

起きるかもしれないこと:

- **同じ名前のブランチを別の作業で使い回していると、その行も PR の分に入る。** `/cost <PR番号>` と #689 の合計にも同じ性質がある。エピックは対象のブランチが子 issue の数だけ増えるので、当たる機会は増える。手元のブランチ名は issue 番号入り（`oratta/issue-690` など）で、使い回しは今のところ見ていない
- **GitHub が `subIssues` の応答の形を変えると、エピックの `/cost` が終了コード 2 になる。** 子を持たない issue と PR の `/cost` には影響しない。標準エラーに読めなかった箇所が出る
- **実機の所要時間が見積もりを超える。** 見積もりは `gh` 約 1.7 秒に、台帳の読み通し数回（1 回約 0.7 秒）を足した数秒。tasks の実測で確かめ、PR に書く
- **#695 が同じ spec ファイル（`cost-ledger-attribution`）の別の要件を変える。** 要件は重ならないが、archive で本体の spec に取り込むときに、先にマージされた側の変更を取り込み直す必要が出ることがある

## Migration Plan

移行は要らない。台帳の形式・`hooks.json`・既に積まれたコメントは変えない。反映に `/reload-plugins` は要らない。

戻し方: この change の PR を revert する。`/cost <エピックの番号>` は区間だけの額に戻る。台帳には何も残らない。
