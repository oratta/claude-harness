## MODIFIED Requirements

### Requirement: 2 つの鍵は独立である
第 1 の鍵（ブランチ）と第 2 の鍵（リポジトリ識別子と issue 番号の組）は独立で、同じ行が両方に帰属すること SHALL がある。feature ブランチ上で `gh issue view 273` を実行した行は、そのブランチにも issue 273 にも帰属する。したがって `/cost <PR番号>` と `/cost <issue番号>` の値は重なることがあり、足し合わせて総額としてはなら MUST NOT ない。2 つの鍵の値を合わせた額を出してよいのは、「issue の合計は、閉じた PR の分と、PR のブランチ上に無い区間の分の和である」が定める issue の合計と、「エピックの合計は、エピック自身と子孫の issue が数える行を 1 回ずつ足した額である」が定めるエピックの合計だけと MUST する（どちらも、重なる行を 1 回だけ数える）。

#### Scenario: feature ブランチ上で issue を触る
- **WHEN** feature ブランチ上のセッションで `gh issue view 273` が実行されている
- **THEN** その行のコストはブランチの合計にも issue 273 の合計にも含まれる

#### Scenario: 単純な和は issue の合計と一致しない
- **WHEN** issue #12 に帰属する区間の行が 3 行（各 $1.00）あり、そのうち 1 行がブランチ `feat/a` の行で、ブランチ `feat/a` の行が全部で 3 行（各 $1.00）ある会話ログで、`cost_ledger.py issue 12 --closing-pr 300:feat/a --json` を実行する
- **THEN** `combined_total_usd` は 5.0 で、`total_usd`（3.0）と PR の分（3.0）の和 6.0 より、重なった 1 行の $1.00 だけ小さい

## ADDED Requirements

### Requirement: エピックの合計は、エピック自身と子孫の issue が数える行を 1 回ずつ足した額である
システムは、子 issue を持つ issue（以下「エピック」）の合計を、次のように SHALL 定める。

- **対象の issue**: エピック自身と、数える子孫の issue（どの子孫を数えるかは spec `cost-ledger-cost-command` の「子 issue を持つ issue では、子 issue ごとの内訳と合計を返す」が定める）
- **issue が数える行**: 「issue の合計は、閉じた PR の分と、PR のブランチ上に無い区間の分の和である」がその issue について数える行。つまり、その issue を閉じた PR のヘッドブランチの行と、その issue に帰属した区間の行
- **エピックの合計**: 対象の issue のどれかが数える行を、行ごとに 1 回だけ足した額

1 つの行を複数の対象の issue が数えるのは、1 本の PR（または同じヘッドブランチ）が複数の issue を閉じたときと、ある issue に帰属した区間の行が、別の issue を閉じた PR のヘッドブランチ上にあるときの 2 つで MUST ある（区間の行は 1 つの issue にしか帰属しないので、区間どうしは重ならない）。システムはこのとき、行を次の順で 1 つの issue に割り当て SHALL る。

1. 行のブランチ名が、対象の issue を閉じた PR のどれかのヘッドブランチと一致する行は、そのヘッドブランチの PR が閉じた対象の issue のうち、番号がいちばん小さい issue に割り当てる
2. それ以外の行で、対象の issue に帰属した区間の行は、その issue に割り当てる

issue ごとの「割り当てた額」は、その issue に割り当てた行の合計と SHALL する。割り当てた額を対象の issue すべてについて足した値は、エピックの合計と一致 MUST する。issue ごとの「単独の合計」は、その issue だけを見たときの issue の合計（他の issue との重なりを除く前の値）と SHALL し、割り当てた額は単独の合計を超えてはなら MUST NOT ない。同じヘッドブランチを持つ PR が 1 つの issue に複数あるときは、「issue の合計」と同じく番号のいちばん小さい PR だけを数え MUST る。

守備範囲: この計算が受け取る入力は、台帳または会話ログの行と、GitHub の応答から組み立てた「対象の issue と、それぞれを閉じた PR のヘッドブランチ」の一覧に限る。拾いたい誤りは、1 本の PR が複数の子 issue を閉じたときにその PR の分を issue の数だけ足すこと・ある issue の区間の行を、別の issue の PR の分としてもう一度足すこと・割り当てた額の和がエピックの合計と合わないことの 3 つ。次のことは誤ったまま通ることを許す: 複数の issue を閉じた PR の分は、番号がいちばん小さい issue に全額が割り当てられ、ほかの issue の割り当てた額には入らない（実際にどの issue の作業だったかは行からは分からない。単独の合計との差として表示する）／同じ名前のブランチを別の作業や別のリポジトリで使い回しているときは、その行も PR の分に入る（`/cost <PR番号>` と同じ）／手元の台帳に無い作業は数えられない／`Closes` で結び付いていない PR は数えない。これらの穴を塞ぎ切ることはこの要件の完了条件にしない。

以下の Scenario の共通のデータ: リポジトリ acme/ra の会話ログで、どの行も $1.00。行 r1・r2 はブランチ `main` で issue #11 に帰属する区間の行、r3 は `main` で issue #12 の区間の行、r4 は `main` で issue #10 の区間の行、r5・r6 はブランチ `feat/a` でどの issue の区間にも無い行、r7 はブランチ `feat/b` でどの issue の区間にも無い行。`gh` は、#10 の子 issue が #11 と #12 の 2 件だと答える。

#### Scenario: 子が別々の PR で閉じられている
- **WHEN** 共通のデータで、#11 を閉じた PR が #300（ヘッドブランチ `feat/a`）、#12 を閉じた PR が #301（`feat/b`）のとき、`cost_ledger.py cost 10 --json` を実行する
- **THEN** 割り当てた額は #10 が 1.0、#11 が 4.0、#12 が 2.0 で、`total_usd` は 7.0（3 つの和）であり、どの issue も割り当てた額と単独の合計が同じ

#### Scenario: 1 本の PR が 2 件の子を閉じている
- **WHEN** 共通のデータで、#11 と #12 のどちらも PR #300（`feat/a`）が閉じたとき、`cost_ledger.py cost 10 --json` を実行する
- **THEN** `total_usd` は 6.0（`feat/a` の 2 行を 2 回足した 8.0 ではない）で、割り当てた額は #10 が 1.0、#11 が 4.0、#12 が 1.0、単独の合計は #11 が 4.0、#12 が 3.0

#### Scenario: ある子の区間の行が、別の子の PR のブランチ上にある
- **WHEN** 「子が別々の PR で閉じられている」の状態に、ブランチ `feat/a` で issue #12 の区間に帰属する行 r8（$1.00）を足して、`cost_ledger.py cost 10 --json` を実行する
- **THEN** `total_usd` は 8.0（行は 8 行）で、割り当てた額は #11 が 5.0、#12 が 2.0、#12 の単独の合計は 3.0

#### Scenario: 同じヘッドブランチの PR が 2 件の子に 1 件ずつある
- **WHEN** 共通のデータで、#11 を閉じた PR が #305（`feat/a`）、#12 を閉じた PR が #300（`feat/a`）のとき、`cost_ledger.py cost 10 --json` を実行する
- **THEN** `feat/a` の 2 行は #11（issue の番号が小さい方）に割り当てられ、`total_usd` は 6.0

#### Scenario: 台帳から読んでも同じ値
- **WHEN** 「1 本の PR が 2 件の子を閉じている」の会話ログを `COST_LEDGER_PATH` の台帳へ取り込んでから `cost_ledger.py cost 10 --json` を実行する
- **THEN** `total_usd` と issue ごとの割り当てた額・単独の合計は、`COST_LEDGER_PATH` を未設定にして実行した場合と同じ
