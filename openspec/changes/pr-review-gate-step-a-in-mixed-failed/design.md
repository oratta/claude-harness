# Design

## Context

段 A の扱いは要件「段 A の直しは周の歯止めの内側だけで戻す」に既にある。1 周目は止める指摘の有無によらず failed で W に戻し、順 5・順 6 との混在では順 2〜4 と同じに扱う。この change は、その決定と食い違って読める 2 か所を揃える（proposal.md の Why）。

## Goals / Non-Goals

**Goals:** 段 A の指摘が、切り出しのあとも順 3 との混在でも W に戻り、差分限定の再レビューを通ること。

**Non-Goals:** 段 A の定義の変更。2 周目以降の扱いの変更。順 6 の処理順の変更。

## Decisions

**段 A の条件は「1 周目」に限る。** 2 周目以降の周の終わりの段 A は、既存の要件どおり段 B から当てるので、切り出しのあとも W に戻さない。「1 周目」を外すと、周の歯止めをこの経路だけ抜けることになる。

**確認の順番は、未処理の順 6 → 止める指摘と 1 周目の段 A → 手順 3 以降、とする。** 順 6 が残っていれば failed を付けない規則を先に保つ。裁定のあとにまとめて 1 回の failed で戻す既存の処理順と同じになる。

**1 周目か、段 A が残っているかは PR コメントと Gate Result から読む。** 保留の解除の G は前の段の会話を持たない。周は前の段の Gate Result の `周回:` で、段 A は仕分けの PR コメントの「段 A・この PR で直す」の印で読み、印が無ければ段 A の指摘は無いものとして扱う（判定をやり直さない）。印を読むので、保留で return する G が同じ印を仕分けの PR コメントに残すと hold.md の保留の return に書く（これまで印の義務は failed の PR コメントだけに書かれていた）。

**段 A が残って failed で返すときの欄は `stages/triage.md` の「failed のとき」を使う。** 残りが段 A だけなら原因分類は「段 A だけ（昇格なし）」、順 2〜4 も残っていれば手順 2-2 の表どおりとする。

**受け入れ条件が名指しした文の隣も、同じ分岐を持つなら揃える。** hold.md の「保留の解除」は切り出しの確認の行の return 側なので、「切り出して残りが無いとき」の「残り」を具体的に書き、段 A が残るときの failed を足す。triage.md の failed の `次の段:` の箇条の第 2 文（順 3 の一覧をどの G が照合するか）にも段 A を足す。足さないと、順 3 と段 A の混在で順 3 の照合の担い手が書かれていない状態になる。

**gate-runner.md と develop の SKILL.md は変えない。** どちらも「順 3 だけなら `照合と振り分け`、それ以外は `前提確認と重さ判定`」の形で、段 A が混ざれば「それ以外」に入る。dev-workflow-develop spec 837 行目も変えない。「残り」を段 A を含む語として残し、hold.md:160 ではその中身を書き下す。
