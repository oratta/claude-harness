## Context

develop の (4) では、本体が G を名前付きで 1 体 spawn し、レビュー担当の要約・決める役の裁定・主の回答・W の修正のたびに SendMessage で同じ G を再開している。再開のたびに全履歴を読み直すので、G のコンテキストは段を重ねるごとに積み上がり、上限 150K による手渡しが起きる。#553 で pr-review-gate の手順を段のファイル（`stages/prepare.md`・`review-run.md`・`reviewer-brief.md`・`triage.md`・`pass.md`・`hold.md`）と `declarations.md` に分け、`gate-runner.md` に「時点ごとに読むファイル」の表を置いた。G の起動 1 回あたりの固定分（約 45〜60K）は変わらないが、1 体が 1 段だけを担当すれば、固定分に 1 段分の作業が乗るだけで上限に届かない。

## Goals / Non-Goals

**Goals:**

- G を段ごとに新しく起こし、SendMessage で再開しない。
- 段と段の間で何を渡すかを、G が前の段の会話を持たない前提で定める。
- 次にどの段の G を起こすかを本体が機械的に決められるようにする。

**Non-Goals:**

- 段のファイルの中身（規則・閾値・雛形・コマンド）を変えること。
- レビュー担当（R）や W の起こし方を変えること。
- #514（検査担当とレビュー担当の仕事の大きさ）の範囲を決めること。

## Decisions

### 段は 4 つにする

| 段 | 起こす時点 | 読むファイル（`skills/pr-review-gate/` から） | 返しうる Status |
|---|---|---|---|
| 前提確認と重さ判定 | ゲートの開始、W の修正後の再レビュー、保留の解除が `次の段: 前提確認と重さ判定` を返したとき、CI の見張りで `ready` になったあとの取り直し | `stages/prepare.md`（W の修正後の再レビューのときは加えて `stages/triage.md` の収束ルールの節と「W の修正後の再レビュー」の入力） | `needs-reviewer` / 保留 |
| 照合と振り分け | レビュー要約・補足レビューの結果・決める役の裁定を受け取ったとき、戻した指摘が順 3 だけの修正のあと | `stages/triage.md` | `次の段へ` / failed / 保留 / `needs-reviewer`（補足） / `needs-decider` / `review-incomplete` |
| 合格処理 | 照合と振り分けが止める指摘なしで終わったとき、保留の解除が `次の段: 合格処理` を返したとき | `declarations.md` と `stages/pass.md`（前の HEAD の許容があるとき・保留を返すときは加えて `stages/hold.md`） | passed / 保留 |
| 保留の解除 | 主の回答が届いたとき | `stages/hold.md` | `次の段へ`（合格処理か前提確認と重さ判定） / failed / needs-decider / 保留 |

従来経路（develop の本体以外から G を起こし、G がレビューを自分で起こす経路）は、#553 の表どおり前提確認と重さ判定の G が `stages/review-run.md` と `stages/reviewer-brief.md` も読んでレビューを起こし、照合と振り分けまで同じ G で続けてよい。従来経路の G はレビューを自分の起動の中で起こして待つので、レビュー要約を受け取るための再開が無い。そこで従来経路の G は、今の gate-runner.md どおり手順 1〜5 と保留までを 1 体で続けてよいとし、Gate Result は `段: 一括（従来経路）`、`次の段: なし` と書く。develop の本体以外の呼び出し元は段のしくみを知らないので、段を分けると合格処理を起こす担い手がいなくなるためである。この変更が段を分けるのは、develop の本体がレビュアーを起こす adapter 経路である。

W の修正後の再レビューで起こす前提確認と重さ判定の G は、前の周の会話を持たない。差分限定か全体レビューか・2 周で打ち切るかの規則は `stages/triage.md` の収束ルールにあるので、この G はその節と「W の修正後の再レビュー」の入力も読み、前の周の指摘を仕分けコメントから取り、全体レビューの判定と行数の記録を自分で行う。規則を `stages/prepare.md` へ写さないのは、同じ規則を 2 か所に書かない #553 の要件に合わせるためである。

保留の解除のあとで起こす合格処理の G は、前の Gate Result の `段: 保留の解除` でこの場合だと見分け、同じ HEAD で宣言を出し直さず手順 5 の真正性確認から入る。許容済みの PR で HEAD が動いていたときの許容の引き継ぎ（手順 3-c）は、宣言を書く合格処理の G が宣言の前に `stages/hold.md` を読んで試す。

保留の解除の G は、復帰手順の表が別の段の作業（再レビュー・合格処理）に進めと示したら、その段の作業を自分でせず、Status `次の段へ` と `次の段:` で返す。1 体 1 段を崩さないためである。

却下した案: 段を 3 つ（保留を合格処理か振り分けに含める）にする案。保留の解除は主の回答からいつ来るか分からず、どの段の後にも起きうるので、独立した段にしないと「どの段の G を起こすか」を本体が主の回答の中身で判断することになる。

### Gate Result に `段:` と `次の段:` を足す

共通欄に `段: <前提確認と重さ判定|照合と振り分け|合格処理|保留の解除|一括（従来経路）>` と `次の段: <段の名前|なし>` を足し、Status に `次の段へ` を足す。本体は Status と `次の段:` だけを見て次に起こす G を決め、段についての判断（止める指摘が残っているか、戻した指摘の仕分け、復帰手順がどこに進むか）は G 側に置く。`次の段:` の値は Status ごとに G が決める。

| Status | `次の段:` |
|---|---|
| `次の段へ` | 照合と振り分けの G は `合格処理`。保留の解除の G は `合格処理` か `前提確認と重さ判定` |
| failed | 戻した指摘が順 3 だけなら `照合と振り分け`、それ以外は `前提確認と重さ判定` |
| needs-reviewer / needs-decider | `照合と振り分け` |
| 保留 | `保留の解除` |
| passed / review-incomplete | `なし` |

failed の行き先は戻した指摘の仕分けの中身で決まるので、G が書き、本体は W の修正のあとその値どおりに起こす。

却下した案: 本体が Status から次の段を推論する案。`次の段へ` のように Status だけでは行き先が決まらない返り方があり、推論を本体に置くと SKILL.md (4) の分岐表が段のファイルの内容と二重になる。

### 段と段の間の受け渡しは PR コメントを正とする

| 渡すもの | 置き場所 | 書く担い手 |
|---|---|---|
| 固定した HEAD | `レビュー重量:` コメントに足す `固定 HEAD: <SHA>` の行（周ごとに増えるので最新の 1 件を正とする） | 前提確認と重さ判定の G |
| 重さ判定 | 既存の `レビュー重量:` コメント | 前提確認と重さ判定の G |
| レビューの三表（変更点の一覧・照合表・ハンク被覆）と補足済み回数 | 1 行目 `レビュー三表:` のコメント（`補足済み回数:` の行を持つ。補足の `needs-reviewer` を返す前に投稿する） | 照合と振り分けの G |
| 振り分けの結果 | 既存の仕分けコメント | 照合と振り分けの G |
| 決める役の裁定 | 既存の `決める役の裁定:` コメント | 照合と振り分けの G |

止める指摘が無い周で止めない指摘を follow-up issue に切るのは、照合と振り分けの G が `次の段へ` を返す前に行う。

本体は次の G の起動指示に、前の段の `## Gate Result` ブロックを要約し直さずそのまま貼り、段に固有の入力（レビュー要約・補足レビューの結果・裁定・主の回答・W の修正の要約）を足す。起動指示と PR コメントが食い違ったら PR コメントを正とする。本体の要約を正にすると、要約で落ちた情報を G が確かめる手段が無くなるためである。

固定した HEAD を `対象 HEAD:` の行にしないのは、auto-merge workflow がこの文字列を宣言の照合に使っているためである。

### 周回は前の段から引き継ぐ

`周回:` は前の段の Gate Result の値を引き継ぐ。W の修正後の再レビューで起こした前提確認と重さ判定の G が 1 増やす。戻した指摘が順 3 だけの修正のあとは周を消費しない（`stages/triage.md` の既存規則どおり）。

### SendMessage は G への停止の指示だけに残す

G への SendMessage は、`decision-criteria.md`「コンテキスト上限（サブエージェントの手渡し）」の、前任が動作中に交代させるときの停止の指示だけに残す。この規則は decision-criteria.md 側にあるので、`gate-runner.md` と SKILL.md の (4) からは `SendMessage` の語と `G を再開` の文字列を無くし、bats でこの 2 つの文字列を否定する。G を起こす前の `subagent-context.sh` による計測は、再開が無くなるので W だけに残す（PR トークン上限の計測は spawn の前にも行うので変わらない）。

### G が `工程中断:` で返したら同じ段の新しい G を起こす

起こしてよい条件は decision-criteria.md の「手渡しの許可」を参照するだけにし、書き写さない。新しい G には前任の return 全文と、前任の起動指示に書いた入力を渡す。

### G の名前と description

名前は `G-<PR>-<prepare|triage|pass|hold>-<n>`（`n` はその PR・その段で起こした回数）、description は `G: <段> for PR #N (#issue)` にする。先頭の `G:` を残すのは、`subagent-context-audit.sh --by-role` がこの接頭辞で G と判定するためである。

### 「レビュー実行者:」コメントの段落を `stages/triage.md` へ移す

このコメントはレビュー要約を受け取った G が投稿する。段を分けるとそれは照合と振り分けの G になるので、段落を `stages/prepare.md` の「G として動くとき（develop）」節から `stages/triage.md` の同じ節へ移す。

### adapter 経路の保持規則を消す

`gate-runner.md`・SKILL.md・`references/codex-develop.md` にある「`レビュー経路: adapter` で起動済みの同一 G は、行の無い再開でも adapter 経路を保持する」規則は、再開が無くなると使われない。すべての G の起動指示に `レビュー経路: adapter` の行を常に書く既存規則は残るので、行の無い指示を受けた G は既存どおり新しい G として扱えば足りる。

### 既存要件は書き換えず、読み替えの要件を足す

#553 と同じく、既存要件の本文は丸写しで書き換えず、読み替えの要件を足す。読み替えの対象は specs の読み替え要件に列挙する。

### 規模

実装で編集するファイルは約 14 個で、W の規模超過トリップワイヤーの閾値 5 個を超える。どれも「G を SendMessage で再開する」同じ記述の直しで、分けると文書どうしが食い違ったままの期間ができるので、本体の判断で単一 change のまま進める。

## Risks / Trade-offs

- G の起動が段の数だけ増え、起動 1 回ごとの固定分（約 45〜60K）を段ごとに払う → #553 で段ごとに読むファイルを小さくしたこと、上限による手渡し（固定分の払い直しに加えて前任の途中成果の読み直し）が無くなることで相殺する見込み。受け入れ条件 2 と 3 で測る。
- 前の段の会話を持たないので、前の段で見たことを G が知らない → 受け渡すものを PR コメントに置き、本体が前の段の Gate Result をそのまま渡す。PR コメントに無い情報に頼る段の規則が見つかったら、その段のファイルに「何をどのコメントから読むか」を足す。
- 受け入れ条件 2（どの G も 150K を超えない）は、実行時に読まれるプラグインのキャッシュが変更前の版なので、この PR 自身のゲートを本体が worktree 側の新しい SKILL.md と gate-runner.md に従って回して測る。マージ前の版で測った値になることを PR 本文に明記する。

## Migration Plan

マージ後、次に develop を回す PR から段ごとの G になる。途中の PR で古い版の G が名前付きで動いている場合、本体はその G を再開せず、次の段の G を新しく起こす（前の段の Gate Result を渡す）。
