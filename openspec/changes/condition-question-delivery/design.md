# Design

## 決定

- **担い手は「G を起こした側」。** develop の G はサブエージェントで主と話せない。G を起こした側は、develop では本体である。自分でゲートを回すセッションは G を起こした側を兼ねる。無人運用（loop-dev-agent）は G を起こさない（SKILL.md の実行モード）ので、そこでの記録先へのコメントは、ゲートを回すセッションが行う。既存の「答えを受け取ったセッション（develop では本体）」と同じ言い方に揃える。
- **届ける中身は質問文と `条件の確認待ち` の PR コメントの URL。** 質問文は return の仕分け欄に既にある。URL を添えるのは、主が答えを返信する先を開けるようにするため。
- **届け先は、主と話せるときは主への次の報告、無人運用では記録先のコメント。** 無人運用（loop-dev-agent）では主への報告の場が無く、記録先が主の見る場所になる。
- **本体が必ず読む SKILL.md には参照だけを足す。** 本体が必ず読むのは SKILL.md で、gate-runner.md は G の指示書。SKILL.md (4) の `次の段へ` の行に短い 1 文（gate-runner.md への参照）を足す。起動時予算の残りが少ないため全文は写さない。
- **文は 1 つにして 3 か所に同じ文で書く。** 本体が読む `gate-runner.md`、G が読む `stages/triage.md`、規定の正本の spec の 3 か所で食い違うと、片方だけ従う事故になる。issue の受け入れ条件 1。
- **マージは止めない。** G は `条件の確認待ち` で `needs-approval` を付けず、保留で return しない現行の規定のまま。届ける義務は、G の Status や合格処理の流れを変えない。

## 採らなかった案

- G の Status に待ちの値を足して合格処理を止める案: 受け入れ条件 2（マージは止めない）に反する。
- 質問文を PR 本文に写す案: 質問は指摘ごとに増え、本文が長くなる。PR コメントの URL を添えれば足りる。

## 同じ文

照合と振り分けの G の return の仕分け欄に `条件の確認待ち` の質問文があれば、G を起こした側（develop では本体）は、その質問文と `条件の確認待ち` の PR コメントの URL を主への次の報告にそのまま載せる（無人運用（loop-dev-agent）では記録先にコメントする）。
