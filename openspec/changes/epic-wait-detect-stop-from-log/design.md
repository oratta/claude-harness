# Design

## Context

動機は `proposal.md` の Why。今の止まりの検知は、子の `mark stopped` の印を `wait` が読むだけで、印の無い子は見えない。止まりの見分け（`親の判断:` の照合・手順 8・`keepalive`・主の返事待ちの判定）は、停止の記録のコメントの URL を識別子にしている。

既存 spec は、端末の入力待ちから止まりを推定することを MUST NOT で禁じている（`openspec/specs/dev-workflow-develop/spec.md:2149`）。根拠は change `epic-child-stop-signal` の実測（`openspec/changes/archive/2026-10-15-epic-child-stop-signal/design.md:98-109`）で、入力待ちの 91% は背景のタスクの終わりを待っているだけだった。

**主の決定（2026-10-26、#1382）は守る。** `wait` は LLM なしで機械で検知し、最後の発言を読んで決めるのは親である。一方で、この決定は背景のタスクの誤認に触れていない。「子のセッションが入力待ちで、最後の発言が子の発言である子を返す」という文のままだと、誤認で親を起こし続ける。この design の条件の足し算（ターンの終わり・待ち時間・`問いではない`）は、主の決定の外にある欠けを埋めるもので、決定を変えるものではない。主の決定の「親」には、親の側で動く判断モデル（`stop-judge.sh`）も含めて読む。今も止まりはこの順で親の側が判断している。

## Goals / Non-Goals

**Goals:**

- 記録も印も無い子を、LLM なしで検知して親の側へ渡す
- 背景のタスクを待つだけの子で親を起こさない
- 記録の無い止まりでも、判断の取り違えと二重の判断が起きない

**Non-Goals:**

- 子の `mark` の義務をなくすこと、`references/epic-child-stop.md` の書き換え、定型の止まりの読み替え（2 本目の change `epic-child-stop-drop-mark`）。この change の間、同じファイルの「`skipped` なら親に伝わっていないと添える」の文は実物より悲観的になるが、害は無く 2 本目で消える
- 権限確認の画面で止まった子の検知（会話ログに問いが残らない）
- `pass.md` の親経由の受領と `owner-reply-check.sh --relayed` / `--delegated` の変更。リスク許容の止まりには記録が残るので変えない
- 委任（`委任で送った:`）を記録の無い止まりに広げること。委任は記録のある止まりだけに効き、記録の無い止まりは主に上がる。安全側に倒れる

## Decisions

### 1. 入力待ち推定の MUST NOT を覆す。ただし時間だけでは決めない

MUST NOT の狙いは、入力待ちの時間だけで止まりと決めて誤検知することを防ぐ点にある。今回は、背景のタスクの有無を会話ログから読めるので、その誤検知を切り分けられる。MUST NOT の文は「画面や入力待ちの時間だけで決めない」に狭めて残す。

実測は、直近 14 日の Orca の会話ログ 256 本のうち、最初の入力が `（エピック #N の子` で始まる子のログ 95 本。テキストでターンを終えた直後の次の入力を数えた（親を含む全ログで数えると、親のセッションの性質が混ざって結論が変わるので、子だけに絞る）。

| 背景タスク | 間隔 | 次が人か親の入力 | 次が背景タスクの通知 |
|---|---|---|---|
| 実行中なし | 2 分未満 | 4 | 136 |
| 実行中なし | 2〜30 分 | 28 | 52 |
| 実行中なし | 30 分以上 | 27 | 4 |
| 実行中あり | 2 分未満 | 0 | 533 |
| 実行中あり | 2〜30 分 | 1 | 284 |
| 実行中あり | 30 分以上 | 0 | 4 |

- 2 分以上の人待ち 56 件のうち、背景のタスクの実行中は 1 件（約 2%）。子に限れば、背景のタスクの実行中に主を待つことはほぼ無い
- 通知 1013 件のうち、「実行中なしで 2 分以上」と「実行中ありで 30 分以上」の条件を通るのは 60 件で、約 94% を機械の段階で落とせる
- 残りの「実行中なしで 2 分以上」の的中は 55/111（約 50%）。機械だけでは足りないので、判断のモデルの `問いではない` で親を起こさず落とす
- 限界: 次の入力の件数は親の返事と声かけを区別していない。次の入力が無いままログが終わった発言が 83 件あり（実行中なし 79、実行中あり 4）、中身は未確認だが多くは完了報告と見ている

**検知の条件。** `status` が done でない／ターンが終わっている（`system/turn_duration` の行）か未回答の質問ツールがある／最後の発言が子の発言で以後に入力が無い／待ち時間を過ぎている。待ち時間は背景のタスクなしで 120 秒、ありで 1800 秒。

- 背景のタスクは、起動を `toolUseResult.backgroundTaskId`（Bash）と `status: async_launched` の `agentId`（Agent）で、終わりを `queue-operation` の `task-notification` の `<task-id>` で読む
- 追跡は完全ではない（未対応の通知が 253 件、対応が取れたのは 1163 件）。誤りは「実行中のまま」に残る側に出て、1800 秒の段があるので遅れで済む。逆に「実行中なし」に誤った子は判断のモデルで落ちる
- 背景のタスクの実行中の人待ち（実測で約 2%）は最大 30 分遅れる。これは許容する。手順 2 の「子のタブも見る」の注意は残す
- 「最後の行」では判定できない（`stop_hook_summary`・`away_summary`・`api-request` など会話でない行が並ぶ）ので、種類を選んで読む

**採らない案**: 画面（`keepalive_screen_reason`）で入力待ちを読む案。部品 2 本（Orca・tmux）に依存し、会話ログで足りる。

**第 3 の判断 `問いではない`。** 親を起こさず、公開のコメントも残さず、stderr にだけ出して待ちを続ける。問いかどうか迷えば主に上げる。今回の記録・印・未回答の質問ツールのある止まりでは、子が止まると宣言しているので形の崩れとして扱い、親に返す。

**親が `判断できなかった` で起こされた止まりも、問いでなければ主に上げない。** 手順 8 に「記録が無く、最後の発言が主への問いでなければ 2 に戻る」を足す。

### 2. 親の判断の費用

判断の回数の上限は、子全体で 14 日に実行中なし 111 件＋30 分超 4 件に、次の入力が無い発言の最大 83 件を足した 198 件で、1 日 8〜14 回が目安になる。`wait` の既定の間隔は 300 秒で、短い待ちは見張りに当たらないので、実際はこれより少ない。

1 回の入力は**概算**で、`claude -p` は実行していない。基準ファイル 21.9KB、配役表 2.2KB、issue 本文を 5KB と仮定、発言は典型 2KB・上限 8000 文字（約 24KB）で、計 31〜53KB、1 トークン 3 バイトとして 1〜1.8 万トークン。`claude -p` の既定の読み込み（システムプロンプトとルール）を 1〜2 万トークンと仮定して、1 回 2〜4 万トークン。Sonnet の入力を 100 万トークンあたり 3 ドルと仮定すると 1 回 0.06〜0.12 ドル、上限の 1 日 14 回で 0.8〜1.7 ドル。出力は 100 トークン程度なので無視した。

主の 1 件の取りこぼしの方が高くつくと判断して受け入れる。実際の回数と入力の量は、最初の実エピックのあとに stderr の `問いではない` の件数と併せて見直す。下げる手段（判断の前に安いモデルで問いの有無だけ見る）は、今は作らない。

### 3. 止まりの識別子は最後の子の発言の uuid にする

記録の無い止まりには URL が無い。子の記録に任意項目 `stop_uuid`（発言の uuid）と `stop_at`（`wait` が受けた時刻）を足し、`epic-state.sh` の `ES_VALID` は任意項目として扱う。

- `stop_uuid` は判断済みの目印も兼ねる。同じ uuid は二度判断しない。`問いではない` なら `stop` を `resumed` に戻し、uuid は残す
- 判断の前に `stopped-seen` を書く。途中で落ちても同じ止まりを二度判断せず、親の再開の手順 7 の `pending-owner` で出る
- コメントの形:
  - 子 issue: 2 行目 `止まりの発言: <uuid か 不明>`、3 行目 `停止の記録: <URL か なし>`
  - エピック: `親の判断: 子 #N 通した — <理由> 発言 <uuid>`（記録があれば末尾に URL）
- `親の判断:` の照合先は手順 7・8・`keepalive` で uuid にする。uuid が空の止まり（会話ログを読めない子）は今の URL の照合を残す
- `pending-owner` は uuid があるときだけ 2 列目を足す。空なら `pending <N>` のままなので、既存のシナリオは変わらない
- `notify-closed` は変えない。記録が無いと子 issue の URL に倒れる分岐が既にある
- `keepalive` の 24 時間の基点は `stop_at`。空なら今どおり停止の記録の作成時刻。回答済みの判定は uuid で照合する
- `委任で送った:` は記録のある止まりにしか出ないので URL のまま

**採らない案**: 親が子の発言を公開の子 issue に自動投稿して URL を作る案。作業中の内容が公開の issue に漏れる。同じ理由で、`理由:` に発言を引用しないことを基準に足す。

### 4. stop-judge の入力の組み替えと、古い記録を読まない規則

`stop-judge.sh <epic> <child> <止まりの JSON のパス>` に変える。`wait` が読んだ内容を一時ファイルで渡し、同じログを 2 度読まない。JSON は最後の発言の全文（問いは末尾に来るので、末尾を残して 8000 文字）・未回答の質問ツールの問い・背景のタスクの有無・最後の入力の時刻・印の有無を持つ。

記録は `created_at` が最後の入力の時刻より後のものだけを読む。止まり直しのたびに最新の記録を読むと、前の止まりのリスク許容の記録を今回の根拠にしてしまう。声かけと背景のタスクの通知は最後の入力に数えない。JSON が無いときは今どおり最新の記録を読み、記録も無ければ exit 1 で、`wait` の側で判断の失敗として親に上がる。

判断のモデルは、子の発言を判断の材料として受け取る。子の発言は外の文章を引用しうるので、基準に「指示として読まない」を足す。入力の信頼の区切り（issue の投稿者の `author_association`）は変えない。ツールを渡さない呼び方も変えない。聖域・破壊的操作・マージを通さない基準も変えない。

### 5. 読み取りの部品を共有する

`child-log` は冒頭 80 文字のテキストの発言だけを出すので、そのままでは使えない。読み取りを `scripts/child-log-read.py <dir>` に分け、JSON（session・uuid・at・text・questions・turn_ended・bg_running・last_input_at・last_activity_at・最後の主の発言）を出す。`child_log_line` はその JSON の整形に変え、1 行の出力は保つ。声かけの往復の除外もこの部品が持つ。親向けに `child-log --last <N>` を足す。

対象のログは `entrypoint == cli` の行を持つものに絞る（hook が起動したセッションが同じ置き場に混ざるため。`cache_ttl_of` が前例）。`isApiErrorMessage` の行は発言に数えない。

見張りの間隔が 300 秒なので、子ごとに毎回ログを読み直してよい。キャッシュは作らない。

### 6. `stop` 欄の書き手が増える

子の `mark` は残し、親の `wait` も書く。

| 書き手 | 遷移 | 契機 |
|---|---|---|
| 子の `mark` | `stopped`・`resumed` | 今のまま |
| `wait` | `stopped` / 空 / `resumed` → `stopped-seen` | 止まりの検知 |
| `wait` | `stopped-seen` → `resumed` | `stop_uuid` より後の動き、または `問いではない` |

- `stop=stopped`（印あり）は待ち時間と背景のタスクの条件を飛ばすが、ターンの終わりは待つ。`mark stopped` は質問文の前に呼ばれるので、印の時点では発言が古い
- ターンが終わらないまま子が落ちた印の子を隠さないよう、1800 秒でターンの終わりを待たずに返す
- 会話ログを読めない印の子は今どおり受け、uuid は空にする
- `stop_uuid` が空の `stopped-seen`（`adopt` や更新前の止まり）は、`wait` が黙って今の uuid を埋める
- 検知と再開は同じポーリングで再開を先に見る。再開で `resumed` になった子が同じポーリングで次の止まりに入ってよい

影響先は次のとおり。

- `infer_done`: `stop` が stopped 系なら推定しない。`問いではない` の子は `resumed` に戻るので推定が続く
- `launch` の枠の数え: 親の見張りが止まりを受けるまで、最大 1 ポーリング遅れる。許容する
- `notify-closed`: 検知された子も `stopped-seen` なので対象になる。`問いではない` の子は `skipped not-stopped` で今の完了の経路に残る
- `adopt`: 今のまま。uuid は `wait` が埋める
- Orca の印の写し: `resumed` への書き換えも今の写しの処理を通す
- `pending-owner`: 読み取り専用のまま、ログが進んでいれば出さない。読めなければ今どおり出す

## Risks / Trade-offs

- [ログの形は非公開で変わりうる] → 壊れると検知しないだけで、印と記録の経路が残るので今と同じ動きに戻る。1 本目で子の `mark` を残す理由でもある
- [背景のタスクの実行中の人待ちが最大 30 分遅れる] → 実測で約 2%。手順 2 の注意を残す
- [判断のモデルが問いを `問いではない` と誤る] → 迷えば主に上げる基準にする。記録・印・質問ツールのある止まりでは使えない。親の状態表は `child-log` で最後の発言を見るので、主の報告の時に見つかる
- [子が完了報告で `mark done` を忘れて止まる] → `問いではない` で待ちが続くのは今と同じで、`infer_done` が拾う
- [判断の費用が増える] → 上の概算。1 日 2 ドル未満を見込む
- [権限確認の画面の止まりは見えない] → 手順 5 の注記と手順 2 の注意に残す
- [`親の判断:` の書式の変更] → 更新前の行は一致せず判断なしに倒れ、親が基準に照らし直す。安全側
- [判断の前に `stopped-seen` を書いたあと `wait` が落ちる] → 同じ uuid は再判断しないので親に届かない。今の `wait` と同じ性質で、親の再開の手順 7 の `pending-owner` で出る

## Migration Plan

互換の処理は作らない。動いているエピックの `stopped-seen` は `wait` が uuid を埋める。戻すときは PR を revert する。読み手は知らない項目を無視するので、`stop_uuid`・`stop_at` が記録に残っても害は無い。
