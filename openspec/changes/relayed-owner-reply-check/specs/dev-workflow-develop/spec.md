### Requirement: Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる

- 動いている子を待つ `wait` には、`--watch-stopped` に加えて `--resolve <エピック番号>` を付ける（MUST）。通すと判断された止まりは `wait` の中で返事が送られ、親は起こされない
- `wait` の出力が `closed`・`done`・`stopped`・`unrecorded` の 1〜4 行であることを書く（MUST）。この 1〜4 行は `--resolve` を付けたときだけで、要件「エピックの子は止まる前に記録と印を残し、親は stopped を受けて報告する」の `closed`・`done`・`stopped` の 1〜3 行とする規定に優先する。`--resolve` を付けない `wait` の出力は従来どおり 1〜3 行であることも書く（MUST）
- `unrecorded <N>...` で起こされたら、子には返事が届いているので主に上げず、`wait` が stderr に出した投稿し直しのコマンドでエピックに `親の判断: 子 #N 通した` の 1 行を残す（MUST）。stderr を読めなければ、`親の判断: 子 #N 通した — 理由は記録できなかった <最新の子の停止の記録の URL>` を投稿する（MUST）

  - それ以外は主に上げる（MUST）。主に上げる説明は本文で書き、質問ツールで聞かない（MUST。子の `--relayed` は親の発言の本文に停止の記録の URL があることで結び付けを見る）。説明は `output-styles/readable.md` の「判断を求めるときは、背景から書いて推奨まで出す」の順（目的 → いま取り組んでいる場所 → 起きた事実 → 決めてほしいこと 1 つ → 推奨と受け入れるリスク）で書き、エピックの目的と他の子との関係を含め、子の停止の記録の URL を添える。実機操作は、どの子の・どの画面で・何をするかを書く
- 主の答えを受けたら、`references/reply-after-idle.md` の表でそのまま送るか起動し直すかを決め、`epic-dispatch.sh reply --as owner`（起動し直すなら `--relaunch` も）に主の答えを書き換えずに渡して子に届ける（MUST）。主の答えの末尾には、要件「親は主の答えに発言の場所を添えて送り、子は親の会話ログで確かめてからリスク許容として受け取る」の発言の場所の添え書き（` [主の発言: セッション <親のセッション ID> / uuid <uuid>]`）を付けて渡す（MUST。主の答えそのものは書き換えず、末尾に足すだけ。場所を引けないときの扱いも同じ要件に従う）。`reply` の出力が `failed` なら主に報告する（MUST）
- 止まった子を動いている子から外さず、2 に戻る（MUST。既存の規定のまま）
- 親が通してよい範囲の基準は `references/parent-pass-criteria.md` を指す（MUST）

develop の手順書（`skills/develop` 配下）に `orca` のサブコマンドを書いてはならない（MUST NOT）。

この要件の守備範囲で入力として扱うのは、`wait` の出力と、子 issue の `子の停止:` と `親の判断:` のコメント、主の答え（親のセッションの会話）、`reply` の出力である。拾いたい誤りは、通せなかった止まりを主に上げずに待ち続けること、主に上げる説明が子の会話を前提にして主が読めないこと、主の答えを子に届けないこと、時間がたった子に表を見ずに送ることの 4 つである。次は通ってよく、この要件では止めない: 説明の文の良し悪し（順序と含めるものが書かれていればよい）／主が子のタブで先に答えていて、親の届けた答えが 2 度目になること（子は受け取って続ける）。説明が主に読めない書き方を見つけるたびに手順を足して塞ぎ切ることは、この要件の完了条件としない。

**Orca 経路の手順 8（親の送り方）**: 親は主の答えを `scripts/epic-dispatch.sh reply --as owner` で送る前に、`owner-reply-check.sh --locate "$CLAUDE_CODE_SESSION_ID" <主の答え>` を回し、`MATCH:` のうち全文が主の答えと同じで timestamp がいちばん新しい行の uuid を取り、主の答えの末尾に ` [主の発言: セッション <親のセッション ID> / uuid <uuid>]` を添えて渡さなければならない（MUST）。主の答えそのものは書き換えてはならない（MUST NOT。添え書きは末尾に足すだけ）。`--relayed` の結び付けは親の発言の本文に停止の記録の URL があることで見るので、親は止まった子の報告を本文で書き（質問ツールで聞かない）、その本文に停止の記録の URL を書かなければならない（MUST）。終了コードが 0 でない、または該当する行が無いときは添え書きを付けずに送り、主に「子のゲートは親経由の許容を確かめられないので、リスク許容なら子のタブで打ってほしい」と伝えなければならない（MUST）。

**「エピックの子が主の返事を待って止まるとき」の「親から届いた返事」（子の受け取り方）**: 子は、`主の返事（親エピック #<E> 経由）:` で始まる入力（起動し直されたセッションの最初の指示 `/develop #<N> （エピック #<E> の子。返事を受けて起動し直し） 主の返事（親エピック #<E> 経由）: …` の、括弧のうしろに付いて届いたものを含む）が止まった件のリスク許容への返事で、末尾に `[主の発言: セッション <ID> / uuid <uuid>]` があるとき、記録先の最新の `子の停止: 主の返事待ち` のコメント（投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のもの）の作成日時と URL で `owner-reply-check.sh --relayed <ID> <uuid> <作成日時> <URL>` を回さなければならない（MUST）。exit 0 で、`MATCH:` の全文から許容の意思が読め、全文がこの子・この PR への許容と読め、別の子・別の PR・別のリスクだけを名指しした答えでないときだけ、保留の解除の G に、親のセッション ID・uuid・`MATCH:` の timestamp・停止の記録の URL・`MATCH:` の全文を渡さなければならない（MUST。記録の書式と真正性確認は pr-review-gate 手順 5 の「親経由で受領」が正本で、SKILL.md に書式を再掲しない）。添え書きが無い・`--relayed` が exit 0 でない・全文から許容と読めないときは、主本人の返事として扱ってはならず（MUST NOT）、G を起こさずに、主に子のタブで直接返事を打ってもらうよう頼み（止まる前の記録と印は同じ節の手順どおり）、頼む文に確かめられなかった理由（`REASON=` の値か「添え書きが無い」）を添えなければならない（MUST）。起動し直されたセッションでは、この受け取り方を「新しいセッションでの再開」の手順 2（`/develop` の引数の残りを自分のセッションの会話で受けた回答として扱う）より先に当て、引数の残りのうち `主の返事（親エピック #<E> 経由）:` で始まる部分を自分のセッション ID で `owner-reply-check.sh` に掛けてはならない（MUST NOT。子の会話ログのその行は⑨で主の発言として数えないので、掛けると主に受け直しを頼むことに落ちる）。この順序は「親から届いた返事」の箇条に書き、再開手順の本文は変えない（MUST）。リスク許容以外の返事（動作確認の結果・切り出しの確認への回答など）の受け取り方は変えない。

**保留の行の「リスク許容を会話で受けたら」の文**: エピックの子が親経由で許容を受けたときは、自分のセッション ID ではなく、上の「親から届いた返事」の手順で確かめてから G に渡すことを、参照で書かなければならない（MUST）。

この要件の守備範囲で入力として扱うのは、親の会話の主の答え、子に届いた入力の頭と末尾の添え書き、子の記録先の停止の記録のコメント、同じ PC の親の会話ログである。拾いたい誤りは、親の打ち込みや確かめられない親経由の返事を主のリスク許容として G に渡すこと、別の止まり・別の子への主の答えを流用すること、親が場所を添えずに送ったときに主に子のタブでの返事を頼まないこと、の 3 つである。次は通ってよく、この要件では止めない: 親が報告した 2 件の止まりにまとめて答えた名指しの無い「許容」と、両方の子を名指しした「1034 も 1030 も許容」（どちらも両方の子で受け取る）、親の報告と主の答えのあいだに親の会話の圧縮が挟まったもの。会話ログの改変と、頭の無い自由な文での親の打ち込みを見破ること、偽造の経路を見つけるたびに塞ぎ切ることは、この要件の完了条件としない。
