# Design

## Context

動機と対象は proposal.md を参照。dispatch HEAD `b9cd7a0568d5e9329d3ff6738603bad1deb914c9` では、decision-criteria.md:60 が通常判断の投稿を「実装前」とだけ定め、worker/spec.md:33-61 の一般手順は先に判断記録を要求する。一方 ci-watch.md:104 はログ確認後に無修正で返すことを許す。したがって「通常判断の投稿 → ログ確認 → 無関係なので return」という順序が手順の文面上で成立する。実 CI の障害再現ではなく、この順序が許されることを確認した。

最新 1 件の仕様化判断を正とする既存契約があるため、後で判断を戻す方式では、不要な記録や一時的な通常化が発生する。共有手順には無関係と判断する基準と `next --unrelated <チェック名> --after-fix` が既にある。

## Goals / Non-Goals

**Goals:**

- CI fix から新しく起きた spec 段 W に、通常判断の投稿前に済ませる関係確認と、そこで終了する条件を定める。
- 一般の spec 段手順を読む W も同じ順序に到達できるようにする。
- 無関係時の返却と、関係あり／判断不能時の通常復帰を既存のコマンドとレビュー契約へ接続する。

**Non-Goals:**

- CI 失敗の因果関係を機械で保証することや、既存の `--unrelated` の基準を広げること。
- 通常経路の既存 W の再開段、競合の復帰方法、R1・ゲートの合否条件、状態ファイルや回数上限を変えること。
- #1583・#1590・#1597 の作業、文書の重複整理、起動時予算対象ファイルの編集。

## Decisions

### 判断再投稿の前に共有手順の関係確認を行う

軽い通し方の `ci-fail` による fix から起きた新しい W は、仕様化判断の手順に入る前に ci-watch.md「7. 直し方」手順 2 のログ確認を行う。ログと PR 差分の関係は同文書「5. `--unrelated` を渡す基準」で判定する。既存の観測・失敗ログ・変更ファイルを使い、新しい判定基準や完全な原因究明の義務は足さない。

無関係と判断できたら、仕様化判断を投稿し直さず、artifact 作成・修正・push に入らずに、チェック名と無関係と判断した根拠を本体へ返す。本体は既存の `next --unrelated <チェック名> --after-fix` を 1 回だけ実行し、その一手に従う。同じ PR・同じ状態ファイル・同じ HEAD を使い、最新の軽い判断はそのまま残る。手順 3 以降の passed 解除・Draft 化・pending 付与にも進まない。

関係がある、または既存基準で無関係と判断できない場合は、確認のあとに `通し方:` の行の無い通常判断を投稿する。「する／しない」は W が決め、する場合は artifact 一式と R1 の APPROVE、どちらでもテストを経て修正する。競合は無関係な CI 失敗の返却対象ではなく、従来の通常復帰に進む。通常経路の既存 W の implement 再開や、通常復帰後の再 fix は変えない。

比較した案:

- 判断を先に通常化してから無関係なら軽い判断を再投稿する: 最新判断が一度不要に変わり、同じ記録先に軽い判断を投稿し直さない既存契約にも反する。
- 本体だけで事前確認し、W は必ず通常化する: 見張りで判断できなくても W のログ確認で無関係と分かる既存の返却経路を扱えない。
- 採用案は共有手順の確認を W の判断再投稿より前に置く。新しい分類を増やさず、変更する順序を 1 か所の復帰契約で定義できる。

### 正本と一般の spec 段を接続する

develop 固有の順序は decision-criteria.md「CI 見張りの fix からの戻し方」に置く。起動指示で関係確認を判断投稿より先に行うことも渡す。worker/spec.md の仕様化判断節の前には、この起動理由の場合に正本の先行確認を行い、無関係なら判断記録の手順へ入らず返す入口を置く。

共有 ci-watch.md 手順 2 は、develop の軽い通し方から来た W では判断再投稿前の確認になることを正本への参照で接続する。無関係時の返却・`next --unrelated ... --after-fix` の既存手順を使い、非 develop の実装者や通常経路の既存 W の手順は維持する。

変更する仕様は `dev-workflow-develop` の「G が passed を返したら本体が CI を見張る」だけでよい。`dev-workflow-ci-watch` は既にログ確認後の無修正返却と after-fix の意味を規定しており、今回の判断投稿の順序を担う capability ではない。過去の archive 済み artifact は変更しない。

## Risks / Trade-offs

- [一般の spec 段指示に従い先に判断を投稿する] → worker/spec.md に先行確認への入口を置き、起動指示・正本・共有手順の接続を Bats で確認する。
- [無関係と確定できない失敗で通常復帰が止まる] → 共有の 2 条件を満たした場合だけ返す。判断不能時は従来どおり通常経路に進むことを明記する。
- [文書の語句だけのテストでは実際の順序を保証できない] → 関係確認が判断投稿より先である契約と、無関係時に投稿しない契約の両方を検査する。既存の after-fix 実行テストで、同じ HEAD の rerun と fixes 保持を確認する。エージェントの因果判断の誤りを塞ぎ切ることは完了条件にしない。
- [起動時予算が増える] → 予定する編集対象は予算対象 3 ファイルを含まない。追加が必要になって超過した場合は、近くの文を圧縮せず、OWNER の指示どおり該当予算を追記分まで増やす。finish の PR 本文に理由と https://github.com/oratta/claude-harness/issues/1586 を書く。

## Migration Plan

今工程は artifact 作成・検証・commit・push まで。R1 の APPROVE が記録先にあることを確認した後の実装工程で、関係テストの red → green と手順の更新を行う。verify 後の finish 工程で delta を archive して主仕様へ反映する。状態ファイルの移行は不要で、ロールバックは今回の手順変更を戻すだけでよい。
