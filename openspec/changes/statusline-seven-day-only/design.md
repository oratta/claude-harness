# Design

## Context

`plugins/statusline/scripts/statusline.sh` は stdin の `rate_limits` から 5 時間枠と週次の値を取り出し、次の 5 か所で「5 時間の値がある」を条件にしている: snapshot の書き込み、記録のハッシュ計算と書き込み、`.headroom.json` の値を使う判定（`hr_use`）、`render_slot` の打ち切り、複数アカウント時の `取得待ち`。条件の周辺にも、空の値でそのまま失敗する箇所が 2 か所ある。`--argjson five_pct "$five_h_pct"` は空だと jq が失敗して本文が空になり snapshot が書かれない。記録の printf は空だと壊れた JSON を書く。

読み手を読んだ結果（未実行）は次のとおりで、リポジトリ内はすべて null に耐える。

| 読み手 | null の扱い |
|---|---|
| `usage_view.py` の `_source` | その情報源の窓は無い扱い。0 にしない |
| `headroom.py` の `_row`・`_best` | 5 時間が null でも候補に残す |
| `select-account.sh` | null 判定済み |
| `usage-probe.sh` の `window()` | `five_hour: null` でも落ちず、7d があれば成功 |
| `session-tripwires.sh`・`agent-model-guard.sh` | 週次のみを読む |
| `codex-develop.py` | headroom の行の margin のみを読む |
| statusline の非 active 用の値の選択 | 空文字と null を無い扱い |

リポジトリの外の連携先の読み手も落ちないことを読んで確かめた（Risks に、落ちないが誤解を招く点を書く）。

## Goals / Non-Goals

**Goals:**

- 週次だけの入力で、Claude の `7d All` の行が出て、snapshot と記録が更新される
- 5 時間枠と週次の両方があるときの出力と書き出す内容は、変更前と同じ
- 5 時間の値がまた返るようになれば、何もしなくても元の表示に戻る

**Non-Goals:**

- 読み手のコードの変更
- 連携先の読み手の修正
- Claude Code が渡す stdin の中身の調査（マージ後の確認で済ませる）
- 5 時間枠が恒久に無くなる前提での整理（`5h` の行のコードや `five_hour_*` のキーの削除）

## Decisions

### D1. 書く条件は「5 時間か週次の使用率のどちらかがある」にする

snapshot・記録・ハッシュ計算の 3 か所とも同じ条件にする。無い枠は `null` で書き、キーは省かず、0 は作らない。

- 週次を必須にする案は採らない。7d が無く 5h だけの入力は今も書いており、両方があるときと同じく動きを変えない
- キーを省く案は採らない。読み手は「キーがあって null」と「キーが無い」のどちらも欠測として読めるが、書き手の形を入力によらず一定に保つほうが読み手の前提が増えない

### D2. 署名は 5 時間が無いと `null|...` にする

`obs_sig` と `_rec_sig` の先頭の値を `${five_h_pct:-null}` にする。既に他の項目が使っている書き方に揃える。両方の値があるときの署名は今と同じ文字列なので、更新の直後に同じ観測の `observed_at` が進むことはない。5 時間が戻れば署名が変わるので、新しい観測として書かれる。

### D3. 読み手のコードは変えず、移行時の古い値も特別に扱わない

新しい記録の 5 時間が null でも、もう一方の情報源に古い値があれば、既存の「古い値を下限として使う」規則のとおりそれを採る。古い値を消す処理を足す案は採らない。5 時間枠が戻る可能性があるなか、「null を見たら他の情報源の 5 時間も捨てる」規則は、片方の情報源だけが欠けた通常の状態でも値を失う。影響は Risks に書く。

### D4. 連携先の修正はこの change に含めない

連携先の読み手は null で落ちないことを確かめた。そこで見つかった点（Risks）は連携先のリポジトリの問題なので、ここでは直さない。

### 描画の組み立て

`render_slot` の打ち切りは「5 時間も週次も無い」ときだけにする。`5h` の行の組み立てを 5 時間の値があるときに限り、以降の 7d の組み立ては既存のまま通す。経過時間とリセット権の区画は「そのスロットの最後の行」に付く既存の規則のままで、週次だけなら `7d All` の行に付く。`hr_use` は週次の値だけで判定する。`.headroom.json` の条件 4 が見るのは週次のリセット時刻で、5 時間の値を見るのは仕様に無い実装の都合だった。

## Risks / Trade-offs

- **stdin の中身は未確認**: Claude Code が status line に渡す生の stdin は取得していない。`rate_limits.seven_day.used_percentage` が来る前提が外れると、この修正では直らない。確かめ方は、マージ後に `.rate-limit-snapshot` の更新が再開するかを見ること
- **連携先の読み手の stale からの自己回復（未解決）**: 連携先の読み手の自己回復は「いずれかの枠がリセット済み」が入口で、5 時間枠が恒久に無くなると入口は週次のリセットだけになる。回復までの時間が延びうる。連携先の別 issue の候補
- **連携先の読み手の通常の判定**: `.rate-limit-snapshot` が止まったため、連携先の読み手が通常の判定を stale で飛ばしている可能性がある。この修正で解消するはずで、上の stdin の確認と同時に確かめられる
- **連携先の読み手の 5 時間の表示**: 連携先の判定は null を使用率 0.0 として扱う。5 時間では止めないだけで 7d の判定は効くが、判定ログの 5 時間の使用率は 0.0 と出る。利用者向けの一覧は null を `?` と表示する。どちらも落ちない
- **非 active の行に古い `5h` の行が残る**: 記録か snapshot の片方に古い 5 時間の値が残ると、非 active のスロットに `5h` の行が出続ける。新しい記録が null で snapshot が古い場合は、usage-probe の次回の取得で null に変わる。snapshot が null で記録が古い場合は、そのアカウントのセッションが次に記録を書くまで残る。既存の動きで、影響は表示とリセット後の読み替えによる 0% だけで、自動選択の候補から一時的に外れる側にしか倒れない
- **`7d` だけの行の見え方**: 1 スロットでは Claude の行が 1 行に減る。Codex の行とのバーの開始位置は既存の規則で揃う
