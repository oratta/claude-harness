## Context

issue #973 の 2026-10-12 のコメント「止めない指摘の振り分けの流れ」の「候補探しのスクリプト」の節が、このスクリプトの入出力の正本である。

- 入力: 指摘が指すファイルのパスの一覧、いまの PR と記録先 issue の番号（候補から外す）、エピックの子だけに絞る指定
- 中身: パスごとに `gh issue list --state open --search '"<ファイル名>" in:title,body'` を 1 回引き、番号と題名を最大 15 件返す。本文は返さない
- 既存 issue へのコメントは `gh issue comment` の定型文で、スクリプトにしない

同じコメントの振り分けの表は、このスクリプトを 1 回走らせた結果を 2 つの段で使う。エピックの完了条件に効く指摘を分ける段は「同じエピックの子 issue に当たるか、エピックの外の issue に当たるか」を見る。既存 issue に相乗りする段は「同じ場所を直す open の issue があるか」を見る。

本体の決定（issue #973 の 2026-10-12 の分割のコメント）で、bats の置き場は `plugins/dev-workflow/tests/`（既存のスクリプトのテストと同じ場所）と決まっている。

## Goals / Non-Goals

**Goals:**

- ゲート役が、指摘 1 件が指すファイルについて「同じ場所を直す open の issue の候補」を 1 回の実行で得られる
- 候補がエピックの子かどうかを、同じ 1 回の実行で見分けられる
- 検索に失敗したとき、「候補が無い」と読み違えない

**Non-Goals:**

- 候補が指摘と同じ箇所を本当に直すかの判定（題名を読んでゲート役が決める。必要なら本文をゲート役が読む）
- 既存 issue へのコメント、受け入れ条件への追記、子 issue への追加、新しい issue の起票（どれも `gh` の定型のコマンドで行い、スクリプトにしない）
- 振り分けの手順書（`stages/triage.md` など）からの呼び出し（次の change `gate-nonblocking-finding-triage`）
- 本文にファイルのパスを書いていない issue を見つけること（2026-10-12 時点で open の 239 件のうち 57 件。issue #973 で受け入れ済み）

## Decisions

### 1. 検索語はパスの最後の要素（ファイル名）にする

パス全体ではなくファイル名で引く。issue #973 の決定がファイル名と書いていることに加え、実測で `triage.md` は 10 件、パス全体では 5 件と、パス全体にすると半分を取りこぼす。issue の本文は `stages/triage.md` や `triage.md` のように短く書かれることが多い。

捨てた案: パス全体で引く（取りこぼしが多い）。ファイル名で 15 件を超えたら親ディレクトリ名を足して引き直す（パスごとに検索が 2 回になり、決定の「パスごとに 1 回」から外れる）。

受け入れること: `SKILL.md`（52 件）や `spec.md`（59 件）のようにどこにでもあるファイル名は 15 件で打ち切られ、目当ての issue が入らないことがある。打ち切ったことは出力に書く（決定 4）。

### 2. エピックの指定は「子かどうかを行に添える」と「子だけに絞る」の 2 段にする

`--epic <番号>` を渡すと、各候補の行に、そのエピックの子なら `child`、そうでなければ `other` を添える。さらに `--children-only` を渡すと、子だけを返す。

issue #973 の決定は入力を「エピックの子だけに絞る指定」と書いている。一方、同じコメントの振り分けの表は、スクリプトを 1 回走らせた結果で「同じエピックの子に当たるか」と「エピックの外の issue に当たるか」の両方を見る。絞る指定だけでは、1 回の実行でこの両方を答えられない（絞ると外の issue が消え、絞らないと子かどうかが分からない）。そこで、決定に書かれた「絞る指定」をそのまま持ったうえで、絞らないときに子かどうかを添える列を足した。これは記録先に書かれていない決定で、W が埋めた。

子かどうかの取り方は 2 つを使い分ける。

| 場面 | 取り方 | 理由 |
|---|---|---|
| `--epic` だけ（添える） | 実行の最初に `gh api repos/<repo>/issues/<番号>/sub_issues`（`--paginate`）を 1 回呼び、子の番号の集合を作って各行と突き合わせる | 検索はパスごとに 1 回のまま。追加の呼び出しは実行全体で 1 回 |
| `--epic` と `--children-only`（絞る） | 検索語に `parent-issue:<repo>#<番号>` を足す | 検索の側で絞るので、子が一致度の順で 15 件より後ろにいても落ちない。手元で絞ると、先に 15 件で切った結果から子を拾うことになり取りこぼす |

捨てた案: 候補ごとに `gh api repos/<repo>/issues/<番号>/parent` を呼ぶ（候補 1 件につき 1 回の呼び出しになる）。絞る指定だけを持ち、ゲート役に絞った実行と絞らない実行の 2 回を走らせる（パスごとの検索が 2 回になる）。

### 3. `--repo <owner>/<name>` は必須にする

`gh` は作業ディレクトリからリポジトリを推測できるが、`parent-issue:` の検索語と `sub_issues` の API には `<owner>/<name>` が要る。推測に任せる経路と明示の経路を両方持つと、片方だけ動く状態を作れてしまうので、常に受け取る。pr-review-gate の手順書は他のコマンドでも `--repo` を渡している。

### 4. 出力はパスごとの見出し行と、タブ区切りの候補の行にする

```
== plugins/dev-workflow/skills/pr-review-gate/stages/triage.md
886	stages/triage.md:53 の --repo <repo> がリポジトリルートのパスだと明記する	other
578	Fable フォールバックの bats を triage.md に向ける	child
== plugins/dev-workflow/scripts/no-such.sh
(該当なし)
```

- パスごとに `== <渡されたパス>` の見出し行を出し、その下に候補を 1 行 1 件で `番号<TAB>題名` と出す。`--epic` があるときは 3 列目に `child` か `other` を足す
- 候補が 0 件のパスは、見出し行の下に `(該当なし)` と出す。見出し行ごと省くと、検索しなかったのか 0 件だったのかが出力から分からない
- 外す番号を除いたあとに 15 件を超えるときは、先頭 15 件を出し、最後に `(15 件で打ち切り。ほかにも一致あり)` と出す。超えたかを知るため、`gh issue list --limit` には「15 ＋ 外す番号の個数 ＋ 1」を渡す
- 題名のタブは空白 1 個に置き換える（列がずれないようにする）
- 並び順は `gh` の既定（検索の一致度の順）のままにする。ファイル名が題名にある issue が先に来るので、打ち切られるときも関係の近いものが残りやすい

捨てた案: JSON で出す（読むのはゲート役で、題名を読むだけなので行のほうがトークンが少ない）。

### 5. 失敗したら何も出さずに終了コード 1 で終わる

`gh` の呼び出しが 1 つでも失敗したら、標準出力には何も出さず、標準エラーに失敗したコマンドの要約を書いて終了コード 1 で終わる。途中まで出すと、失敗したパスより前の結果だけを見て「残りは該当なし」と読み違える。出力は全部の検索が済んでからまとめて出す。

| 終了コード | 意味 |
|---|---|
| 0 | 全パスの検索が済んだ（候補が 0 件でも 0） |
| 1 | `gh` の呼び出しが失敗した。標準出力は空。呼び出し側は「候補が無い」と扱わない |
| 2 | 引数の不備（パスが 1 つも無い、`--repo` が無い、番号が数字でない、`--children-only` に `--epic` が無い、知らないオプション、ファイル名を取り出せないパス、ファイル名に `"` を含むパス）、または `gh`・`jq` が無い |

既存の `owner-reply-check.sh` と同じく、2 は「確かめられない」を表す。

### 6. 同じパスが 2 回渡されたら 1 回だけ検索する

指摘が複数あると同じファイルが重なって渡される。同じ文字列のパスは最初の 1 つだけを検索し、見出し行も 1 つにする。ファイル名が同じで別のパス（`a/SKILL.md` と `b/SKILL.md`）は別のパスとして扱い、それぞれ検索する（結果は同じになるが、見出し行と渡されたパスが 1 対 1 に対応するほうが読み違えない）。

### 7. 言語は bash、テストは `gh` を偽物に差し替えた bats

`plugins/dev-workflow/scripts/pr-state.sh` と `plugins/dev-workflow/tests/pr-state.bats` と同じ形にする。テストは一時ディレクトリに偽物の `gh` を置いて `PATH` の先頭に足し、呼び出しの引数をログに残して、検索語・`--limit` の値・呼び出しの回数を確かめる。実物の GitHub は呼ばない。

## Risks / Trade-offs

- どこにでもあるファイル名（`SKILL.md`・`spec.md`・`README.md`）では 15 件で打ち切られ、目当ての issue が候補に入らないことがある。実測で `SKILL.md` は 52 件。入らなかったときは今と同じく新しい issue が作られる（重なりは防がない。issue #973 で受け入れ済み）→ 打ち切ったことを出力に書き、ゲート役が「候補が無い」と読み違えないようにする
- GitHub の検索は、作られた直後の issue を数秒〜数十秒返さないことがある。同じ周で切ったばかりの issue が候補に出ず、同じ場所の issue を 2 本作ることがある → 手当てしない。起きるのは同じファイルへの指摘を同じ周に別々に振り分けたときで、どの指摘をどの issue にしたかはゲート役がその周の中で分かっている
- `parent-issue:` の検索語と `sub_issues` の API は GitHub の sub-issue の機能に依存する。エピックの子を sub-issue ではなく本文のチェックリストだけで持つリポジトリでは、子が 1 件も `child` にならない → 手当てしない。develop スキルのエピックは sub-issue で子を持つ（`skills/develop/SKILL.md` が `sub_issues_summary.total` で判定している）
- このスクリプトを呼ぶ箇所は次の change まで無い。マージしてから次の change までの間は使われないコードが置かれる
