## Context

develop の本体は、記録先のコメントとラベル、各役割の return の要約だけで次を決める設計になっているので、会話の履歴が無くても続けられるはずである。足りないのは、名前付きで起こした W の名前、実行先（profile・account・executor）の選択、周回の数、PR トークン上限の最新値のように、本体の会話の中にしか無い情報である。これを保留で止まる時点で記録先に書き出せば、新しいセッションの本体は履歴なしで再開できる。

## Goals / Non-Goals

**Goals:**

- 保留の全場面で、引き継ぎを同じ書式・同じ場所（記録先のコメント）に 1 種類だけ残す。
- 新しいセッションの本体が、そのコメントとラベルだけで続けられるようにする。
- 主に、返事の渡し方（新しいセッションで `/develop <記録先>` と一緒に）を毎回案内する。

**Non-Goals:**

- 保留の判定条件や、主に聞いてよい 4 分類を変えること。
- 同じセッションで続ける経路をやめること（1 時間以内に返事ができるなら続けてよい）。
- 本体のコンテキスト上限（`DEV_WORKFLOW_CONTEXT_CAP`）の規則を変えること。

## Decisions

### 引き継ぎは記録先のコメント 1 種類で、場面ごとに書式を作らない

1 行目は `引き継ぎ: 主の返事待ち`（正規表現 `^引き継ぎ: 主の返事待ち$` に完全一致。`仕様化判断:` と同型）。2 行目以降は次の項目を `項目名: 値` で 1 行ずつ書く。

| 項目 | 中身 |
|---|---|
| 待ち理由 | `リスク許容` / `動作確認` / `切り出しの確認` / `PR トークン上限` / `2 周キャップ超え` のどれか |
| 主への依頼 | 主に依頼したコメントの URL（同じ内容を新しいセッションで主に見せ直せるように） |
| 対象 | PR 番号・HEAD の 40 桁 SHA・ブランチ・worktree のパス |
| 実行モード | interactive / unmanned |
| 実行先 | `--profile` などの実行先オプションと account-home の対応（あれば。無ければ `なし`）。新しいセッションでは再推測せず、これを使う |
| 次に起こす役割 | 返事のあとに最初に起こす役割（例: `G 保留の解除`・`W 修正`・`W (3b)`）と、渡す入力の在り処（コメント URL） |
| 周回 | 仕様レビューと G の周回の数、W の修正の周回の数 |
| 前任 W | 直近の W の return の 1 行目（`工程完了: …` か `工程中断: …`）と、return の要約またはそのコメント URL。W を起こしていなければ `なし` |
| PR トークン上限 | 最新の `PR トークン上限:` の値（無ければ既定値）と、止まった時点の合計 |
| 回し方 | エピックの子のとき、エピックの最新の `回し方:` の値。エピックの子でなければ `なし` |

理由: 本体が止まる場面は 3 つあるが、再開に要る情報は場面によらず同じで、違うのは待ち理由と次に起こす役割だけである。場面ごとに書式を作ると、新しいセッションの本体が書式を見分ける分岐を持つことになり、直すときに片方が漏れる。最新の 1 件を正とし（`仕様化判断:` と同じ）、再び止まるときは新しいコメントを書く。

W の名前は項目に入れない。新しいセッションでは前のセッションで起こした W に SendMessage できず、名前を書いても使えない。G は段ごとに新しく起こすので名前を持ち越さない。

### 引き継ぎを書く条件は「W の状態が記録先から分かること」

W が `工程中断:` で返っていても止まる場面はありうる（PR トークン上限の exit 2 では W を起こせない）。そのため、引き継ぎを書く条件を「前任の W が `工程完了:` であること」に絞らず、前任 W の項目に実際の 1 行目を書く。新しいセッションの本体は、`工程完了:` なら手渡しの条件①を満たすものとして新しい W を起こし、`工程中断:` なら既存の規則どおり、未コミット差分を先に確認してから手渡す。本体が止まる時点で未コミット差分が残っていれば、本体がその場で commit する（強制停止のときと同じ）。

### 新しいセッションの再開手順

`/develop <記録先>` で起動した本体は、次の順で状態を組み立てる。

1. 記録先の最新の `引き継ぎ:` コメントを読む。無ければ通常の入口 0 に進む。
2. 引き継ぎのコメントより後の主の回答（記録先のコメント、または `/develop` の引数の残り）を探す。あればそれを回答として使う。無ければ、引き継ぎの「主への依頼」を主に見せ直して返事を聞く（返事が来るまで役割を起こさない）。
3. `needs-approval` がまだ付いていること、PR の HEAD が引き継ぎの HEAD と同じことを確かめる。HEAD が動いていれば、引き継ぎの HEAD からの差分を主に報告して続けるかを聞く。
4. W を再開するときは SendMessage を使わず、手渡し（前任の return と記録先を渡して新しい W を起こす）にする。G は今までどおり段ごとに新しく起こす。
5. 計測の `--cap` には記録先の最新の `PR トークン上限:` の値を使う。待ち理由が `PR トークン上限` で主が「続ける」と答えたときは、今の手順どおり新上限のコメントを投稿する。

### 主への案内

本体は、待ち理由によらず主への依頼に「返事は新しいセッションで `/develop <記録先>` と一緒に渡す。1 時間以内に返事ができるなら、このセッションで続けてもよい」と書く。本体は返事がいつ来るかを知らないので、引き継ぎは必ず残し、どちらにするかは主に任せる。

### 受け入れ条件 2〜4 の扱い

条件 2（保留で止めた PR を新しいセッションで再開して合格まで進める）と条件 3（`--cap` を小さくした記録先で引き継ぎのコメントを残す）は、実装後に本体が実機で行い、PR 本文に記録する。条件 4（マージ後の 5 PR で 1 時間以上あいたあとの書き直し代が 1 PR あたり 0.5 ドル以下）はマージ後でないと測れないので、PR のマージ条件にせず、マージ後にエピック #511 へコメントして満たす。

## Risks / Trade-offs

- 引き継ぎの項目が足りず、新しいセッションの本体が会話の外にある事情を再現できない → 実機の再開（条件 2）で足りない項目が見つかれば、項目を足して同じ書式のまま直す。
- 引き継ぎが古いまま残り、別の状態のときに読まれる → 最新の 1 件を正とし、HEAD と `needs-approval` の現状と突き合わせる（手順 3）。
