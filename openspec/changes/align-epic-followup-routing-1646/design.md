# Design

## Context

動機と受け入れ条件は proposal.md と issue #1646 を参照。段 C は `stages/triage-epic.md`、段 D・段 E は `stages/triage-nonblocking.md` に分かれている。既存の段 C・段 E は正しいが、develop の共通規則・注意書き・参照案内と develop spec に矛盾する文がある。

## Goals / Non-Goals

**Goals:** 問題の発見元によらず、エピックに入れる境界を段 C にそろえる。完了条件の根拠を子の起動前に本文へ残し、修正対象外のレビュー指摘が W の依頼に混ざる入口を閉じる。

**Non-Goals:** #1647 の途中追加された子の起動前確認・主の承認範囲・状態表は扱わない。判定の自動化、新しいスクリプト、ラベル、件数の上限は作らない。並行 PR の対象段落は変更しない。

## Decisions

### 完了条件への効果を、注意書きより先に当てる

issue が指定する段 C・段 E の境界を採る。レビュー由来は G の振り分けをそのまま保ち、実装中の範囲外の問題は本体が既存の段 B〜段 E の問いを借りる。効かない問題は段 D の参考コメント、または段 E の外の issue／捨てるに進める。親の「新しい問題は子にする」の注意書きでも、この境界を変えない。

段 C で効くとした問題については、新しい子を指定した注意書きを既存の子への受け入れ条件の追加より優先する現行動作を保つ。注意書きの置き場所指定を全面的に廃止する案は、今回必要な変更を超えるため採らない。

既存要件「エピックの子への注意書きと子であることを、起動し直したセッションにも引き継ぐ」も MODIFIED に含め、「すべて従う」に置き場所の例外を入れる。`OWNER`・`MEMBER`・`COLLABORATOR` の投稿者検査、対象外・取得不能の扱い、W・R1・G へのコメントの引継ぎは維持する。置き場所の指定に従えない場合もコメント自体は渡し、起動し直したセッションでも同じ境界を適用する。同期後に無条件で従う規定だけが残らないよう、タスクでこの既存要件との照合を行う。

`epic.md` の共通規則、SKILL.md の「エピックの注意書き」と「エピックの扱い」の参照案内を同時に直す。G の段 C・段 E 本文に新しい判定表は複製しない。

### 完了条件の欠落は、両方式に共通する親の開始時に補う

`epic.md` の「読むもの」の表が親の開始を案内する `epic-loop.md` の冒頭で、経路ごとの子の起動より先に本文を確認する。節が無いときは本文の依頼から完了条件を記し、本文だけで決まらないときだけ主に聞く。既存の完了条件や依頼の目的は広げない。

G がレビューのたびに補う案は、子の実装中の振り分けにも要る根拠が後回しになるので採らない。開始時に全件を主へ確認する案も、issue が「本文から決められないときだけ」と指定しているため採らない。

### failed の修正対象一覧と G の振り分けの記録を区別する

`triage.md` の 1 周目の failed の説明と仕分け表の順 1 を直す。W に戻す一覧は止める指摘と段 A の指摘に限る。段 A に当たらない止めない指摘を、任意・ついで・序での修正候補としても渡さない。

対象外の指摘は G の振り分けの記録に残し、段 B 以降を当てる時点は既存どおり G が手順 3 へ進むときとする。全指摘を failed の修正候補として残す案は、issue に記録された範囲外修正を再発させるため採らない。マージを止める判定・周回数は変えない。

### 判定要件ごとに守備範囲を残す

delta の「完了条件の節が無いエピックは子の起動前に本文に記す」「マージを止めるかの判定は全周共通にする」「相乗りの参考コメント（段 D）と費用対効果（段 E）」に、それぞれ入力元・拾う誤り・通ることを許す具体例・穴を塞ぎ切ることを完了条件にしない旨を置く。既存の段 A の守備範囲も維持する。

開始時の手順は本文の節の欠落を拾い、既存の曖昧な完了条件の全面改訂までは求めない。全周共通の判定は引用・検証の印と原文の照合、W に戻す一覧の境界を守り、再現証拠の全件再検証までは保証しない。段 D・段 E は行き先と受け入れ条件の境界を守り、候補の近さや費用対効果の見積もりの完全な正確さまでは保証しない。これらを完全に検査する新しい仕組みを足す案は採らない。

## Risks / Trade-offs

- [本文の完了条件への効果の読み違い] → 判定は本文を根拠にし、既存の振り分け記録で後から追えるようにする。意味判断の誤りを機械で全件検出することは求めない。
- [手順書の別の案内に無条件の子追加が残る] → epic.md と SKILL.md の共通規則・参照案内を対象に否定の検査を置き、段 C「効かない」・段 E「見合う」と親の注意書きを組み合わせた spec シナリオを固定する。
- [並行 PR との spec の衝突] → 起点は main `700c4941`。#1768 は epic-loop.md の待機案内、#1768・#1769 は develop spec、#1410 等は gate spec/tests に差分がある。今回の要件の変更箇所だけを残し、取り込み時は他の要件・シナリオを保存する。
- [ファイル数] → 仕様成果物は proposal/design/tasks と delta spec 2 本（CLI の .openspec.yaml は別）。後続は手順書 4 本、bats 2 本、main spec 2 本と変更記録に及ぶ見込みなので、規模超過の判断は本体へ返す。仕様工程で実装や archive は行わない。

## Migration Plan

仕様レビューの承認後、手順書と bats を同じ変更でそろえる。既存 issue をエピックから自動で外す処理や、過去の仕分けの変更はしない。archive 時に既存 spec の該当要件を更新する。戻す場合は、この変更で追加・変更した文とテストを差分単位で戻す。
