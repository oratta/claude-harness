## Context

Orca 経路のエピックでは、親セッション（エピックの解決セッション）が `epic-dispatch.sh launch` で子ごとに Orca の子ワークツリーと Claude Code セッションを作り、`epic-dispatch.sh wait` を背景で走らせて待つ。`wait` は子 issue の state（`closed`）と、`--watch-done` の子のボードの列（`workspaceStatus` が `completed`）を見て親を起こす。子セッションは interactive の `/develop` なので、主に質問すると自分のタブで止まるだけで、親には何も伝わらない。

使える材料（`orca worktree set --help` と実機で確かめた）:

- ボードの列 `--workspace-status <id>` の既定は `todo` / `in-progress` / `in-review` / `completed`。独自の列は Orca 側で設定しないと使えない。`mark done` が `completed`、`mark waiting`（マージ後のオーナー確認待ち）が `in-review` を使っている
- コメント欄 `--comment <text>`。`orca worktree list --json` の各ワークツリーの `comment` に出る。`--comment ""` は「指定なし」として無視され、空に戻せない（実機で確認。空白 1 文字なら書ける）
- `--worktree path:<path>` でほかのワークツリーのメタデータも書ける（親から子を書ける）

## Goals / Non-Goals

**Goals:**

- エピックの子が主の返事を待って止まるとき、子 issue に止まった理由と推奨が残り、親の `wait` が LLM のポーリングなしに `stopped <N>` で起きる
- 親が一度受けた止まりで、次の `wait` がすぐ同じ子で起き続けない
- 子が返事を受けて再開し、また止まったときは、親がもう一度起きる

**Non-Goals:**

- 親が止まった子をどう解決するか（決める役・子への返事の送り方）。#1034 の範囲
- 記録の書式の細部と、主への完了報告。#1036 の範囲
- 記録を残さずに止まった子を拾うこと（下の「記録を残さずに止まった子は拾わない」）

## Decisions

### 1. 止まった印はボードの列ではなくコメント欄に置く

印の置き場の候補は 3 つあった。

| 案 | 判断 |
|---|---|
| ボードの列 `in-review` を流用する | 採らない。`mark waiting` と同じ値になり、親の `--watch-done` や `reap` の判断と取り違える |
| Orca に独自の列（例 `stopped`）を足す | 採らない。主の Orca の設定に依存し、設定の無い PC では `orca worktree set` が失敗する |
| コメント欄に決まった値を書く | 採る。既定の Orca で使え、ボードの列（完了の印）と独立している |

コメント欄の値は 3 つに固定し、完全一致で見る。

| 値 | 書く者 | 意味 |
|---|---|---|
| `epic-stopped` | 子の `mark stopped` | 止まった。親はまだ受けていない |
| `epic-stopped-seen` | 親の `wait --watch-stopped` | 止まった。親は `stopped` で一度受けた |
| `epic-resumed` | 子の `mark resumed` | 返事を受けて動いている |

`wait` が `stopped` を返すのは `epic-stopped` だけで、ほかの値（主が書いたメモを含む）は無視する。値は英字にして、Orca のサイドバーに出ても主が意味を読める語にした。コメント欄を空に戻せないので、「動いている」も `epic-resumed` という値で表す。

`mark stopped` は主がコメント欄に書いたメモを上書きする。エピックの子のワークツリーは `launch` が作るもので、主がそこにメモを書く使い方は今のところ無いので受け入れる。`mark resumed` は今の値が `epic-stopped` か `epic-stopped-seen` のときだけ書き換え、ほかの値は触らない。

### 2. 印を「受けた」に変えるのは wait、外すのは子

親が `stopped <N>` を受けてユーザーに報告し、もう一度 `wait` を呼んだとき、子がまだ主の返事を待っていれば印は残っている。印を外すのが子だけだと、親の次の `wait` は最初のポーリングで同じ子の `stopped` を返し続ける。

候補:

- **親が受けた子を覚えて `wait` に渡す**（`--seen-stopped <N>`）: 親の LLM が集合を持ち回る必要がある。子が返事を受けて再開し、1 回のポーリング間隔（既定 300 秒）のうちにまた止まると、印は消えずに続いているように見え、2 回目の止まりを取りこぼす
- **印に時刻などの通し番号を入れ、`wait` の出力にも載せる**: 取りこぼしは無くなるが、`stopped <N>` の行の形が変わり、親が番号を持ち回る
- **`wait` が受けた印を `epic-stopped-seen` に書き換える**（採る）: 親は何も覚えなくてよく、出力は `stopped <N>` のまま。子が再び止まると `mark stopped` が `epic-stopped` を書き直すので、再開の印を付け忘れても 2 回目の止まりで親は起きる

`wait` は印を書き換えられたときだけその子を `stopped` に数える。書き換えが失敗した子は報告せず、そのポーリングを「失敗したポーリング」に数える（一覧を読めないときと同じ扱い）。報告したのに書き換えられていない状態を作らないためで、失敗が 3 回続けば今までどおり `error workspaces` で終わる。

子の `mark resumed` は、主の返事を受けた直後のツール呼び出しで呼ぶ（待ち方ごとの順序は 4.）。正しさはこれに依存しない（付け忘れても `epic-stopped-seen` は `wait` に無視され、次の止まりで上書きされる）。役目は、親がまだ受けていない `epic-stopped` を、主が子のタブで先に答えた場合に取り消すことと、サイドバーの表示を戻すことである。

一覧を読んでから書き換えるまでの間に子が `mark resumed` を呼ぶと、`wait` が `epic-resumed` を `epic-stopped-seen` で上書きし、親は再開した子の `stopped` を受ける。間はミリ秒単位で、受けた親は記録を読んで報告するだけ（解決は #1034）なので、ロックは入れない。

### 3. wait は --watch-stopped を付けたときだけ止まった印を見る

止まった印の検知は `--watch-stopped`（値なし）を付けたときだけ行い、位置引数の子（動いている子）を対象にする。付けないときは今までどおり `--watch-done` が無ければ `orca` を呼ばない。`--watch-done` と一緒なら一覧はポーリングごとに 1 回だけ取り、両方に使う。同じポーリングで閉じていた子は `closed` だけに数え、`stopped` には数えない。出力は `closed` → `done` → `stopped` の順に、該当するものを 1 行ずつ出して exit 0 で終わる。

既定で常に見る案は採らない。既存の `wait` の呼び出しとテスト（`orca` を呼ばない前提）を壊し、Orca 経路以外の利用者に Orca への依存を足すため。

### 4. 子が止まるときの記録は、引き継ぎとは別の 1 行目にする

既存の「保留で止まるときの引き継ぎ」（1 行目 `引き継ぎ: 主の返事待ち`）は、新しいセッションの本体が同じ記録先を再開するためのもので、読み手は子自身の次のセッションである。項目も HEAD の SHA や PR トークン上限など再開の材料で、親が判断に使う「推奨と、それを選ぶと受け入れるリスク」を持たない。場面も 3 つの保留に限られ、本文での質問（止まりのほとんど）を含まない。

そこで親向けの記録は別の 1 行目にする。#1033 で決めるのは、識別用の 1 行目 `子の停止: 主の返事待ち`（`^…$` に完全一致。親が機械的に最新の 1 件を探せるように）と、2 行目以降に issue 本文の 4 つの情報（止まった理由・推奨とその根拠・推奨を選ぶと受け入れるリスク・再開に要る途中経過）を含めることまでとする。2 行目以降の項目名・並び・改行の形は決めず、文言のテストでも固定しない。書式の細部は #1036 で決める。たとえば次の形で書けるが、これは例であって規定ではない。

```
子の停止: 主の返事待ち
止まった理由: <何を決められずに止まったか>
推奨: <子が選ぶ案>（根拠: <その案を推す理由>）
受け入れるリスク: <その案を選ぶと受け入れること>
途中経過: <再開に要る状態。PR・HEAD・終わった工程。引き継ぎを書いたならその URL>
```

3 つの保留の場面では、今までどおり引き継ぎを書き、そのあとに親向けの記録を書いて、再開に要る途中経過として引き継ぎの URL を入れる。2 つの記録を 1 つにまとめないのは、読み手と項目が違い、引き継ぎの書式の照合（新しいセッションの再開手順）を変えずに済むため。

記録と印を付けるのは、エピックの子のセッションだけにする。判定は `epic-dispatch.sh route`（子の番号なし）が `nested` を返すかで行う（子のセッションの環境変数と、ワークツリーの親子関係のどちらでも判定され、起動し直したセッションにも効く）。エピックの子でない `/develop` には親がいないので、記録は読む者のいないコメントになるため付けない。`mark` 自身の linkedIssue の一致の確認は今までどおり効く。

順序はどの待ち方でも「記録 → `mark stopped`」とする。印を先に付けると、親がポーリングで印を見た時点で記録がまだ無いことがあるため。そのうえで、待ち方で 2 つに分ける。

| 待ち方 | 順序 | 再開の印 |
|---|---|---|
| 本文で質問してターンを終える（質問ツールを使わない保留を含む） | 記録 → `mark stopped`（そのターンの最後のツール呼び出し） → ターンを終える | 返事が届いた次のターンの最初のツール呼び出しで `mark resumed` |
| 質問ツール（AskUserQuestion）の中で待つ | 記録 → `mark stopped` → 質問ツール | 回答を受けた直後のツール呼び出しで `mark resumed` |

質問ツールは回答が来るまで同じターンの中で待つので、`mark stopped` を最後のツール呼び出しにはできない。どちらの待ち方でも、印が付いている間は子が主の返事を待っていて、外れるのは返事を受けた直後になる。止まりのほとんどは本文での質問で、質問ツールは 88 件中 0 件だった（issue 本文）が、develop の手順には AskUserQuestion で主に聞く場面があるので両方を書く。

### 5. 記録を残さずに止まった子は拾わない

issue は「端末が入力待ちのまま一定時間たった子を `stopped` として返す」案を、誤検知が多いなら入れないとしていた。子セッションのログで確かめた。

`~/.claude/projects/` のうち Orca のワークスペースのディレクトリ（`-Users-oratta-orca-workspaces-*`。サブエージェントの worktree を除く）にある直近 14 日の会話ログ 1,289 件で、アシスタントがターンを終えた（`stop_reason: end_turn`。端末は入力待ちになる）あとの次の入力を数えた。

| 次の入力 | 件数 | 30 分以上空いた件数 |
|---|---|---|
| 背景のタスクの終了通知（`<task-notification>`） | 3,582 | 440 |
| 人の入力 | 351 | 108 |

入力待ちの 91% は人を待っておらず、背景のタスク（サブエージェント・CI の見張り・`wait` 自身）の終わりを待っている。30 分の閾値で区切っても、拾った止まりの 8 割（440 / 548）は人を待っていない。親のエピックのセッションのログも含むので子だけの割合とは少しずれるが、develop の子は CI の見張りやレビューの背景タスクを同じように使うので、傾向は変わらない。誤検知が多いので入れない。記録を残さずに止まった子は、今までどおり `timeout` の確認と、ユーザーに子のタブを見てもらうことで拾う。

## Risks / Trade-offs

- [子が記録と印を付け忘れる] → 印は SKILL.md の手順に頼る。付け忘れた子は今までどおり検知できず、`timeout` の確認とユーザーが子のタブを見ることに頼る。手順は SKILL.md に置き、`launch --note` に頼らない（起動し直したセッションにも効かせるため）
- [主のコメント欄のメモが消える] → `mark stopped` が上書きする。エピックの子のワークツリーでメモを使う運用は今のところ無い
- [Orca がコメント欄の値を自分で書き換える] → 書き換えた場合は印が消えたように見え、親は止まりを受けない（今までと同じ状態に戻るだけで、誤って起きることは無い）

## 実機での確かめ方

本体（Orca 上の子ワークスペースで動くセッション）が、マージ前にこのブランチのスクリプトで確かめる。`<wt>` はこの worktree（`/Users/oratta/orca/workspaces/claude-harness/issue-1033`）、`<epic>` は親のエピックのワークツリー。

1. スクリプトの往復（子のワークスペースで打つ）
   - `<wt>/plugins/dev-workflow/scripts/epic-dispatch.sh route` → stdout `nested`、stderr に `parent epic: #1038`
   - `<wt>/plugins/dev-workflow/scripts/epic-dispatch.sh mark stopped 1033` → `marked 1033 stopped`。`orca worktree list --json | jq '.result.worktrees[] | select(.linkedIssue==1033) | .comment'` が `"epic-stopped"`、`workspaceStatus` は `in-progress` のまま
2. 親の検知（`<epic>` で打つ。位置引数に 1033 だけを渡す）
   - `cd <epic> && <wt>/plugins/dev-workflow/scripts/epic-dispatch.sh wait --interval 5 --timeout 60 --watch-stopped 1033` → stdout `stopped 1033`、exit 0。直後の一覧で 1033 の `comment` が `"epic-stopped-seen"`
   - 同じコマンドをもう一度 `--timeout 10` で打つ → stdout `timeout 1033`、exit 2（受けた印で起き続けない）
3. 再開と 2 回目の止まり（子のワークスペースで打つ）
   - `mark resumed 1033` → `marked 1033 resumed`、`comment` が `"epic-resumed"`
   - `mark stopped 1033` のあと、2 の 1 つ目のコマンドがまた `stopped 1033` を返す
4. 通しの確認（受け入れ条件そのもの）: 試しの子 issue を 1 件作って親のエピックで `launch` するとき、子のセッションがこのブランチの SKILL.md を読むように `EPIC_DISPATCH_CLAUDE_CMD='cld --plugin-dir <wt>/plugins/dev-workflow'` を付ける。子に主への質問が要る指示（例: 「着手前に、A と B のどちらで作るかを主に聞いて止まる」）を `--note` で渡す。親が `wait --watch-stopped` を背景で走らせ、子が質問して止まったら、子 issue に 1 行目 `子の停止: 主の返事待ち` のコメントが付き、親の `wait` が `stopped <N>` で終わることを確かめる。子が主の返事を受けたら、最初のツール呼び出しで `mark resumed` を呼び、コメント欄が `epic-resumed` になることも見る
5. 質問ツールで待つ場合の確認: 4 と同じ起動で、子への指示を「着手前に、A と B のどちらで作るかを AskUserQuestion で主に聞く」にする。質問ツールの画面が出た時点で子 issue に記録が付き、コメント欄が `epic-stopped` で、親の `wait` が `stopped <N>` で終わることを確かめる。画面で答えたあと、子が次のツール呼び出しで `mark resumed` を呼び、コメント欄が `epic-resumed` になることを確かめる
6. 後片付け: 子のワークスペースのコメント欄を `mark resumed 1033` で `epic-resumed` に戻す（空には戻せない）。試しの子 issue は閉じ、ワークツリーは親の `reap` か主の判断で片付ける
