## Context

bats はテスト本文の最後の文の終了コードだけを合否判定に使う。本文途中の `[[ ... ]]` は組み込みキーワードで、偽でも `set -e` の対象外になり（bats はテスト本体を関数として実行するため `[[ ]]` の非ゼロ終了はそこで握りつぶされる）、テストを落とさずに素通りする。通常の外部コマンド（`grep -q` 等）はこの穴に当たらない。cost-ledger は #273 で `|| return 1` を全アサーションに付けて対処済み。本 change はそれ以外の 24 ファイルに同じ対処を広げる。

## Goals / Non-Goals

**Goals:**
- 対象 24 ファイルの `[[ ... ]]` アサーションすべてに、偽なら即座にテストを失敗させるガードを付ける。
- ガードが効いていることを固定する見張りテストを追加し、同じ穴の再発を検知できるようにする。

**Non-Goals:**
- 本文途中の `! cmd`（否定検査）の扱いは対象外（issue #283 が別途 `run` + status 比較で対処する）。
- ガードを付けた結果として露呈した実装側の不具合の修正（別途 issue を切る）。
- bats 以外のテストランナー・テスト規約の変更。

## Decisions

**採用: 各アサーションに `|| return 1` を付ける（bats-assert は導入しない）**

検討した案:
1. **`|| return 1` を付ける**（採用） — cost-ledger が #273 で既に採った形。追加の依存が要らず、対象行の直後にトークンを足すだけの機械的な差分になる。24 ファイル・約380箇所という規模でも、既存の書き方から逸脱しないため diff が読みやすく、レビューコストが低い。
2. **`bats-assert`（`bats-support` 込み）を導入し `assert_equal` 等に置き換える** — 見た目は読みやすくなるが、(a) 新しい git submodule / vendoring の追加が要り CI・`scripts/test.sh` 側の導入手順も増える、(b) 対象箇所を `[[ ]]` から `assert_*` の呼び出し形式に書き換える必要があり機械的な置換で済まない、(c) 同じエピック（#402）の子である issue #283 は `! cmd` を `run` + status 比較に直す方針で、これも新しい依存を持ち込まない。片方だけ bats-assert に寄せると、同じテストスイート内でアサーションの書き方が二重に混在する。

規模（24 ファイル、`[[ ` で始まる行が約380、うち途中アサーションはその一部）に対して、実績のある機械的な変換を選ぶほうが失敗コストが低いと判断し、案 1 を採用する。

**見張りテストの置き場所**

新規ファイル `tests/bats-assertion-guard.bats` を追加し、その中に「偽の `[[ ]]` を途中に置いたテストが実際に落ちること」を確認する fixture テストを書く（bats を子プロセスとして起動し、TAP 出力で `not ok` になることを見る形。`tests/test-sh-residual-guard.bats` が同様に bats を子プロセスとして起動する前例がある）。

## Risks / Trade-offs

- [Risk] ガードを付けた結果、これまで見逃されていた本物のバグに当たり、対象テストが赤くなる可能性がある → Mitigation: 受け入れ条件で明記済み（実装の欠陥として別 issue を切る。本 change の受け入れ条件は変えない）。
- [Risk] 24 ファイルにまたがる機械的編集は、対象行の見落とし（ガード追加漏れ）や誤って最終文にまでガードを付けて可読性を下げる可能性がある → Mitigation: 受け入れ条件 (2) で「ガード無しの途中 `[[ ]]` アサーションが0件」を grep で機械照合する。
