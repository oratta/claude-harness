# Design

## Context

動機は proposal.md の Why。今の主の委任は次の形で動いている。

- 親: 定型の記録（`主の委任: リスク許容` は 1〜4 行目、`主の委任: 論点なしの止まり` は 1〜5 行目が固定）を投稿 → 本文で問う → 問いのあとの、任せる意思が読める最初の主の発言を確認にし、`--locate` で uuid を引いて `委任の確認の場所:` を残す（`epic-stop.md`）
- 子と G: `owner-reply-check.sh --delegated <ID> <uuid> <記録の作成日時> <記録の URL> <停止の記録の作成日時>` で、確認が主の発言・記録より後（`not-after`）・記録の URL を書いた親の発言の後（`not-asked`）・停止の記録より前（`not-before`）であることを確かめ、`epic-delegation.md` の「委任が有効か」6 条件と「委任が効く止まり」を確かめる
- 記録にはもう `きっかけ:` の行（主が任せる旨を述べた発言の全文。無ければ `なし`）があるが、照合には使っていない

主の決定（issue #1609 のコメント 7212285228）: きっかけの発言を確認にするのは `主の委任: リスク許容` だけ。確認より前に止まった子にも、リスク許容の止まりなら当てる。

## Goals / Non-Goals

**Goals:**

- 主が会話で 1 回任せる旨を述べれば、問いに答え直さなくても、以後と、その時点で返事待ちのリスク許容の止まりを親が通せる
- 親が主の古い雑談や別の話を委任として拾う誤りを、照合スクリプトで機械的に落とす

**Non-Goals:**

- `主の委任: 論点なしの止まり` をきっかけの形で受けること（聖域の変更・破壊的な git 操作が会話の一言で通るのを避ける）
- 聖域の変更・破壊的な git 操作・マージ待ちの止まりの、委任の確認との前後の条件を緩めること
- 委任の範囲・取り消し・失効の条件、宣言コメントに追記する `主の回答:` の行の形、`--relayed` の変更
- 会話ログの改変の検知

## Decisions

### D1: きっかけの形は記録の 4 行目で見分ける

`主の委任: リスク許容` の 1〜3 行目はそのままにし、4 行目の `期間:` を次の定型にした記録をきっかけの形とする。5 行目は `きっかけ: ` に続けて主の発言の全文を書き、本文の終わりまでをその値とする（あとに行を足さない。`なし` は書かない）。

```
期間: きっかけの発言から、このエピックに `主の委任:` で始まる次のコメントが付くか、エピックが閉じるまで
```

- 案 B（1 行目を `主の委任: リスク許容（きっかけ）` のような別の種類にする）は捨てた。範囲は同じなのに、「委任が効く止まり」の種類の分岐（`リスク許容` でも `論点なしの止まり` でも効く、など）と、1 行目を見ているすべての所に 3 つ目の種類が増えるため
- 期間の始まりは確認の発言の時刻で、きっかけの形ではきっかけの発言の時刻になる。4 行目の文がそれをそのまま書くので、文と意味がずれない
- 値を本文の終わりまでにしたのは、主の発言が複数行のこともあるため。照合は空白（改行を含む）をまとめて比べるので、GitHub が改行を `\r\n` にしても揃う

### D2: 照合は別名の `--delegated-trigger` にする

`owner-reply-check.sh --delegated-trigger <セッション ID> <uuid> <委任の記録の作成日時> <きっかけの全文>` を足す。確かめる順と理由は `not-found` → `not-owner`（既存と同じ）→ `not-before-record`（行の timestamp が記録の作成日時より前でない）→ `not-same`（空白をまとめた行の全文が、空白をまとめたきっかけの全文と同じでない）→ `not-adjacent`（その行の後、記録の作成日時より前に、主の発言の 9 条件を満たす別の行がある）。通れば `--delegated` と同じ `MATCH:` / `MATCHES=1` を出す。きっかけの全文が空白をまとめると空なら exit 2。

- 案 B（`--delegated` に引数を足して形を切り替える）は捨てた。確かめることが違い（問いの有無・前後の向き・全文の一致）、REASON の集合も違うのに、1 つの名前で引数の数が変わると、呼び出し側の写し間違い（形と引数の取り違え）が exit 2 で落ちずに別の照合として通りうるため。別名なら引数の数が固定で、使い方の文も短い
- 全文の一致にしたのは、部分一致だと主の長い発言の一部（別の件の話）をきっかけに切り出せるため。記録に全文を書く決まりは今もある
- `not-adjacent` は、親がきっかけを受けたターンのうちに記録を出すことを機械で確かめる代わり。主が次に何か打つ前に記録が出ていれば、主はその記録を報告で見てから次の発言ができる。間に合わなかったときは問いの形に戻す
- 停止の記録との前後は確かめない（D3。きっかけの形はリスク許容の止まりにしか効かない）。そのため停止の記録の引数を持たない
- 委任の意思を全文から読むこと・記録の書式・投稿者・最新か・編集の有無は、今の `--delegated` と同じく呼び出し側が確かめる（GitHub は読まない）

### D3: リスク許容の止まりでは委任の確認との前後を見ない

「委任が効く止まり」のリスク許容の③を「停止の記録の作成日時が、②のコメントの作成日時より後」にする（委任の確認の timestamp との比較を外す）。委任の種類によらない。聖域の変更・破壊的な git 操作の止まりと、マージ待ちの「委任の確認の timestamp より後」は残す。

`--delegated` の 5 番目の引数（停止の記録の作成日時）に `-` を渡したときは `not-before` を確かめない。子と G はリスク許容の止まりでは `-` を渡し、聖域の変更・破壊的な git 操作の止まりでは作成日時を渡す。

- 案 B（`--delegated` から `not-before` を外す）は捨てた。聖域の変更・破壊的な git 操作の止まりは今どおり確認より後の止まりに限るため
- 案 C（別のフラグ `--any-stop`）は捨てた。引数の数を変えずに済み、どの値を渡したかが呼び出しの文に残る `-` で足りるため
- issue の「確認の直後なら」は機械では確かめられないので条件にしない。代わりに、親が委任の確認の場所を残した直後に、いま返事待ちのリスク許容の止まりの子を見て、委任が効けば送る手順を足す（`wait` は同じ止まりを二度は返さないので、すでに報告した止まりは親が自分から拾う必要がある）。送れる止まりは最新の停止の記録・今の HEAD の宣言・`主の回答:` が無いものに限られるので、古い HEAD の止まりや答え済みの止まりには効かない

### D4: ゲートの記録行は変えず、真正性確認の行に照合の名前を書く

宣言コメントに追記する `主の回答: 許容 — 親経由で受領（委任）（親セッション … / 委任の確認 <uuid> / <日時>）…` は変えない（`委任の確認` の uuid がきっかけの発言の uuid になるだけ）。pass.md の合格条件の表と carryover.md の見分け方（`親経由で受領（委任）（親セッション ` で始まる行）もそのまま使える。真正性確認の行は `（owner-reply-check.sh --delegated 終了コード 0）` か `（owner-reply-check.sh --delegated-trigger 終了コード 0）` にする。引き継ぎ（carryover.md）で確かめ直すときは、委任の記録の 4 行目で形を見分けて同じ照合を回す。

## Risks / Trade-offs

- [主の会話の一言で、以後のリスク許容が親経由で通る。主が軽い気持ちで言った言葉を親が委任と読む] → 範囲はリスク許容の推奨が許容・論点なしのものに限ったまま。記録を出したら主に範囲・期間・取り消し方を報告し、主は `主の委任: 取り消し` で止められる。G は `MATCH:` の全文から任せる意思を読む
- [すでに止まっていた子に、主が見て保留にしていた止まりがあっても通る] → 主が委任を述べた時点で返事待ちの、推奨が許容・論点なしの止まりに限る。主が特定の子を除きたいときは、委任の発言で除くか（範囲が変わるので問いの形に戻る）、取り消す
- [主の発言が長く、`きっかけ:` に写し間違えると `not-same` で通らない] → 通らなければ親は問いの形に戻す（落ちる向きの失敗）
- [親が主の次の発言より前に記録を出せない] → `not-adjacent` で落ち、問いの形に戻す（落ちる向きの失敗）

## Migration Plan

記録の形と照合の名前を足すだけで、投稿済みの問いの形の記録はそのまま効く。戻すときはこの PR の差分を戻し、投稿済みのきっかけの形の記録は `主の委任: 取り消し` を投稿すれば効かなくなる。
