## MODIFIED Requirements

### Requirement: 親は主の委任を、定型の委任の記録への主の直接の確認で受ける

`references/epic-stop.md` は、別セッション方式の親が、主が親のタブで子の止まりを任せる旨を述べたとき、その発言だけを委任として扱わず（MUST NOT）、エピックの issue に定型の委任の記録を投稿することを書かなければならない（MUST）。記録の種類は `主の委任: リスク許容` と `主の委任: 論点なしの止まり` の 2 つで、主が任せた範囲がどちらか読めないときは狭い側の `主の委任: リスク許容` を投稿する（MUST）。

`主の委任: リスク許容` は、次の条件をすべて満たす発言だけをきっかけの形で受ける（MUST）。①発言の全文だけから、子の止まり（リスク許容）を親に任せる旨が読める（対象を書かない「任せる」だけの短い発言は当たらない） ②任せる対象が、親が報告した 1 件の止まりや親の問いの件に限られない（「この件は任せる」「それでいい」のように、直前の親の発言を読まないと対象が決まらない発言は当たらない。親が 1 件の止まりを報告した直後の発言でも、全文だけから①が読めれば当たる） ③任せる範囲から子・止まりを除いたり、期限や条件を付けたりしていない。どれかを満たさない発言には、きっかけの形を使わない（MUST）。そのうち全文が子の止まり全般を任せる旨とも読める発言だけを下の問いの形で受け、ほかは元の問い・報告への答えとして扱う（MUST）。親は主のその発言を受けたターンのうちに（主の次の発言より前に）、4 行目をきっかけの形の `期間:` にし、5 行目の `きっかけ:` にその発言の全文を書いた記録を投稿し、問いを出さない（MUST NOT）。きっかけの発言そのものを委任の確認とする（MUST）。投稿したら本文で、記録の URL と記録の `範囲:` と `期間:` の文と、取り消すときは取り消す旨を述べればよいことと、要件「親は有効な委任が効く止まりにだけ、委任で許容を送る」で同じターンに委任を当てて送った子（子の番号と停止の記録の URL。無ければ無い旨）を、主に事後の報告として書く（MUST。主がすることは無い報告の型で書く）。主の次の発言より前に記録を投稿できなかったとき、または要件「親は委任の確認の場所をエピックに残す」の照合が通らなかったときは、きっかけの形を使わず、下の問いの形で受け直す（MUST）。

`主の委任: 論点なしの止まり` と、きっかけの形で受けられなかった `主の委任: リスク許容` は、問いの形で受ける（MUST）。親は記録を投稿し、本文に記録の URL と範囲・期間の文を書いて主に問う（MUST）。問いの答え方の行には、親のタブで `任せる` と打つことを書く（MUST）。問いのあとの主の発言のうち、全文から任せる意思が読める最初の発言を委任の確認とする（MUST）。問いと確認のあいだに主の別の発言が挟まっただけでは問い直さない（MUST NOT）。挟まった発言が委任を取り消すか範囲を変える内容なら、委任を使わずに問いを本文で出し直す（MUST）。

委任の定型と有効性・種類別の適用条件の正本は `references/epic-delegation.md` とし、この親の操作手順から適用前に読む（MUST）。

### Requirement: 親は委任の確認の場所をエピックに残す

`references/epic-stop.md` は、親が委任の確認を受けたら（きっかけの形では記録を投稿したら）、`owner-reply-check.sh --locate "$CLAUDE_CODE_SESSION_ID" <確認の全文>` で確認の uuid を引き、エピックに `委任の確認の場所: セッション <親のセッション ID> / uuid <uuid> / 記録 <委任の記録の URL>` の 1 行を投稿することを書かなければならない（MUST）。きっかけの形では、確認の全文はきっかけの発言の全文で、投稿の前に `owner-reply-check.sh --delegated-trigger "$CLAUDE_CODE_SESSION_ID" <uuid> <委任の記録の作成日時> <きっかけ: の値>`（4 番目の引数は、投稿した記録を読み直した `きっかけ:` の値）が exit 0 になることを確かめる（MUST）。通らなければその記録を使わず、問いの形で受け直す（MUST）。親は起動し直したあとも、最新の `主の委任:` で始まるコメントの URL を `記録` に持つ最新のこの行から値を取る（MUST）。引けないときは委任を使わない（MUST）。

委任の定型と有効性・種類別の適用条件の正本は `references/epic-delegation.md` とし、この親の操作手順から適用前に読む（MUST）。

### Requirement: 委任が有効かを決まった条件で確かめる

委任が有効かの手順書の正本は `references/epic-delegation.md` とし、親と子はその正本を読んで次の条件を確かめなければならない（MUST）。G（pr-review-gate の stages/pass.md）も判定前にこの正本を読み、同じ条件で確かめる（MUST）。G が扱うのはリスク許容の止まりだけで、今確かめている委任の形の記録の行だけは除く。確かめる条件: 委任の記録が、①エピック #<E> の issue のコメントで、1 行目が `主の委任: リスク許容` なら 1〜4 行目が問いの形かきっかけの形のどちらかの定型の文ちょうど（きっかけの形なら 5 行目が `きっかけ: ` で始まり、そのあとの値が空白をまとめて空でなく `なし` でない）、`主の委任: 論点なしの止まり` なら 1〜5 行目が定型の文ちょうど、2 行目の番号が <E> ②投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` のどれか ③エピックの、投稿者が同じ 3 種の `主の委任:` で始まるコメントのうち最新 ④`lastEditedAt` が null ⑤エピックが開いている ⑥子 issue がエピックの子（sub-issue か本文の子の表にある）。<E> は子では返事の頭 `主の返事（親エピック #<E> 経由）` の番号で、記録の URL の issue 番号と同じでなければならない（MUST）。記録の形（問いの形かきっかけの形か）は 4 行目の `期間:` の文で見分ける（MUST）。

- **THEN** 委任は有効でないとして扱う

- **THEN** 1〜5 行目が定型の文ちょうどでないので、委任は有効でないとして扱う

### Requirement: 委任が効く止まりを決まった条件で確かめる

止まりに委任が効くかの手順書の正本は `references/epic-delegation.md` とし、親と子はその正本を読んで止まりの種類ごとに次の条件を確かめなければならない（MUST）。G（pr-review-gate の stages/pass.md）も判定前にこの正本を読み、同じ条件で確かめる（MUST）。G が扱うのはリスク許容の止まりだけで、今確かめている委任の形の記録の行だけは除く。

- **リスク許容の止まり**（委任の種類が `リスク許容` でも `論点なしの止まり` でも、記録が問いの形でもきっかけの形でも効く）: ①子 issue の番号を、本文で最初に現れる `Closes #N`・`Fixes #N`・`Refs #N` の `N` に持つ開いた PR に `needs-approval` が付いている ②その PR の、投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` で `## リスク宣言` で始まる最新のコメントが `主のリスク許容が必要。` の行を持ち、`対象 HEAD:` が PR の今の HEAD と同じで、`主の回答:` で始まる行をまだ持たない（G では、今確かめている委任の形の記録の行だけは除く） ③停止の記録の作成日時が、そのコメントの作成日時より後（委任の確認の timestamp との前後は見ない。委任の確認より前に止まった子にも効く） ④停止の記録の `推奨:` の値（先頭の空白を除く）が `許容する` で始まる ⑤②の宣言が `論点なし — ` の行を持ち、停止の記録の `主に聞く理由:` が論点なしと書く
- **聖域の変更・破壊的な git 操作の止まり**（委任の種類が `論点なしの止まり` のときだけ効く）: 停止の記録の `止まった理由:` が `聖域の変更の承認: ` か `破壊的な git 操作の承認: ` で始まり、`推奨:` の値（先頭の空白を除く）が `進める` で始まり、`主に聞く理由:` が論点なしと書き、停止の記録の作成日時が委任の確認の timestamp より後
- **マージ待ち**（委任の種類が `論点なしの止まり` のときだけ効く）: 停止の記録は残らないので、子の最後の発言とその時刻を入力にする。委任が有効で、子の最後の発言の時刻が委任の確認の timestamp より後で、今の HEAD の宣言が `論点なし — ` の行を持ち同じ HEAD の `論点なしの確認: 通す` の記録があり、要件「親がマージに回してよい子の PR の基準を 1 つのファイルに置く」の可の条件を満たす。送り方は要件「親は論点なしの止まりの委任で、マージ待ちの子の PR に判断の印を付ける」
- **実機操作の止まり**: どの種類の委任も効かない

#### Scenario: 推奨が許容しないの止まりには効かない

- **WHEN** 停止の記録の `推奨:` の値が `許容しない。代替案で`
- **THEN** 委任は効かず、親は今どおり主に上げ、子は委任の返事を受け取らない

#### Scenario: リスク許容待ちでない止まりには効かない

- **WHEN** リスク許容の止まりとして確かめるが、PR に `needs-approval` が無いか、最新の `## リスク宣言` のコメントに `主のリスク許容が必要。` の行が無い
- **THEN** リスク許容の止まりとしては、どちらの種類の委任も効かない。マージ待ちはこの条件ではなく、上のマージ待ちの条件と要件「親は論点なしの止まりの委任で、マージ待ちの子の PR に判断の印を付ける」で判断する

#### Scenario: リスク許容の委任は聖域の変更とマージに効かない

- **WHEN** 委任の記録の 1 行目が `主の委任: リスク許容` で、止まった理由が聖域の変更の承認・破壊的な git 操作の承認・マージ待ち・実機操作・方針の選び直しのどれか
- **THEN** 委任は効かない

#### Scenario: 論点なしの止まりの委任でも実機操作には効かない

- **WHEN** 委任の記録の 1 行目が `主の委任: 論点なしの止まり` で、止まった理由が実機操作
- **THEN** 委任は効かない

#### Scenario: 論点なしの確認の無いマージ待ちには効かない

- **WHEN** `主の委任: 論点なしの止まり` の有効な記録があり、子がマージ待ちで止まっているが、今の HEAD の `論点なしの確認: 通す` の記録が無い
