## MODIFIED Requirements

### Requirement: 合格条件は主の委任で親経由に受けた許容を、委任の確認と記録で確かめて受け付ける

`skills/pr-review-gate/stages/pass.md` の手順 5 は、主の委任で親経由に受けた回答の形を持ち、宣言コメントに `主の回答: 許容 — 親経由で受領（委任）（親セッション <ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <確認の発言の全文>` を追記しなければならない（MUST。`<日時>` と `<原文>` は照合の `MATCH:` 行のもの）。行頭は既存の要件「合格条件はエピックの親経由で受けた許容を、親の会話ログで確かめて受け付ける」と同じく `主の回答: 許容` のまま保つ（MUST）。委任の記録がきっかけの形（develop の要件「親は主の委任を、定型の委任の記録への主の直接の確認で受ける」）のときも同じ行を追記し、`委任の確認` の uuid はきっかけの発言の uuid、`原文` はきっかけの発言の全文になる。合格条件の表は、Scenario の真正性確認を通したときだけこの形を許容済みとして扱う（MUST）。

G は委任の記録の 4 行目の `期間:` の文で形を見分け、問いの形なら `owner-reply-check.sh --delegated <ID> <uuid> <委任の記録の作成日時> <委任の記録の URL> -`（リスク許容の止まりなので停止の記録の引数は `-`）を、きっかけの形なら `owner-reply-check.sh --delegated-trigger <ID> <uuid> <委任の記録の作成日時> <記録の きっかけ: の値>` を回さなければならない（MUST）。`--relayed` では確かめない（MUST NOT）。手順 3-c の引き継ぎで元の記録を確かめ直すときも、元の委任の記録の形で同じ照合を選ぶ（MUST）。

#### Scenario: 委任の形の真正性確認

- **WHEN** G が `親経由で受領（委任）` の記録を確かめる
- **THEN** G は、停止の記録が記録先の最新の `子の停止: 主の返事待ち`（投稿者が `OWNER`・`MEMBER`・`COLLABORATOR`）であること、develop の要件「委任が有効かを決まった条件で確かめる」と「委任が効く止まりを決まった条件で確かめる」を同じ文で満たすこと（後者の ② のコメントは記録を追記する宣言コメント）、記録の形に合った照合が exit 0 で `MATCH:` の timestamp が記録の日時と同じで全文から任せる意思が読めること、をすべて確かめ、`真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh --delegated 終了コード 0）` か `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh --delegated-trigger 終了コード 0）` を、使った照合に合わせて追記する

#### Scenario: きっかけの形の委任で、確認より前に止まった子を通す

- **WHEN** 委任の記録がきっかけの形で、停止の記録がきっかけの発言より前に作られ、②の宣言より後で、`--delegated-trigger` が exit 0 で、委任が有効で止まりに委任が効く
- **THEN** G は停止との前後では落とさずに合格の記録を追記する

#### Scenario: どれかを満たさなければ合格させない

- **WHEN** `--delegated` が exit 1（`not-found`・`not-owner`・`not-after`・`not-asked`）、`--delegated-trigger` が exit 1（`not-found`・`not-owner`・`not-before-record`・`not-same`・`not-adjacent`）、どちらかが exit 2 を返す、または委任が有効でない（取り消し済み・新しい記録がある・記録の編集・エピックが閉じている・別のエピック・きっかけの形で `きっかけ:` が なし）か、止まりに委任が効かない（`推奨:` の値が `許容する` で始まらない・リスク許容待ちでない・宣言が今の HEAD でない・宣言が `論点なし — ` の行を持たない）
- **THEN** G は合格処理をせず、手順 6 に戻して主に子のタブで直接返事を打ってもらうよう頼む

#### Scenario: 委任の確認の前の名指しの許容は委任の形で通らない

- **WHEN** 問いの形の記録で、記録の uuid が委任の記録より前の主の発言（例 別の子だけを名指しした `1034は許容`）を指す
- **THEN** `--delegated` が `REASON=not-after` で落ち、G は合格させない

#### Scenario: きっかけの形でも、きっかけと違う発言は通らない

- **WHEN** きっかけの形の記録で、記録の uuid が委任の記録より前の、きっかけと全文の違う主の発言（例 別の子だけを名指しした `1034は許容`）を指す
- **THEN** `--delegated-trigger` が `REASON=not-same`（その発言のあと記録までに主の発言があれば `not-adjacent`）で落ち、G は合格させない

#### Scenario: 手順 6 の復帰手順が委任の形を扱う

- **WHEN** `stages/hold.md` の手順 6 の復帰手順の表のリスク許容待ちの行を読む
- **THEN** 主の委任で親経由に受けた回答のときに `親経由で受領（委任）` の記録を追記してから手順 5 の真正性確認に進むことが書かれている

### Requirement: 委任の形の合格条件の守備範囲

委任の形の合格条件は、次の守備範囲で読まなければならない（MUST）。①入力の出どころは、develop の本体が渡す値（親の添え書きを写したもの）、エピック・子 issue・PR のコメントとラベル（`gh api` で読む）、ゲートが動く PC の親の会話ログ。本体と G は協力的だが、写し間違い・別の記録との取り違え・確かめの省略をする前提で扱う ②拾いたい誤りは、確認でない発言（きっかけの形では、記録に写した全文と違う発言・記録より後の発言・記録の前に主が次の発言をしていたきっかけ）・別のエピックの記録・取り消し済みや編集済みの記録・範囲外の止まりを根拠に合格させること ③委任の確認のあとに親が起動し直したもの、主が会話で任せる旨を述べたきっかけの発言そのものを確認にしたもの、委任の確認より前に止まったリスク許容の止まりは通してよい ④会話ログの改変の検知と、穴を塞ぎ切ることは完了条件にしない（MUST NOT）。

#### Scenario: 範囲外の止まりでは合格させない

- **WHEN** 委任は有効だが、停止の記録の `推奨:` の値が `許容しない` で始まる
- **THEN** G は合格させず、手順 6 で主に聞く
