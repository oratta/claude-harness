## MODIFIED Requirements

### Requirement: レビュアーへの指示に全件列挙と再レビューの制限を含める

SKILL.md 手順 2-1 のレビュアー向け指示ブロックは、一周目に指摘を書く前に、次の三表を順に出すことを要求しなければならない（MUST）。

1. `変更点の一覧`: この PR が新しく決めたルール・判定・用語を ID 付きで列挙し、各項目に対応する受け入れ条件と検索語を書く。各受け入れ条件は 1 項目以上に対応させる
2. `照合表`: 変更点 ID ごとに、共通一覧契約の `修正前 SHA`（固定した対象 HEAD）、repository-wide な `git grep -n ... <rev> -- .`、diff 外を含む全ヒットのファイル・修正前 SHA での行・本文・`扱い`（`一致` または `食い違い: <finding ID>`）を書く。順 3 の grep の語の経路との差は第 4 列の値と、修正後 HEAD を検査する第 2 段が無いこと（全ヒット要約で返す語の形を除く）だけとする。順 3 の場合分けの軸の経路にはこの共通一覧契約を適用しない。全ヒットが 10 行を超える語は、全行の代わりに要件「件数の多い語の一周目の照合表は全ヒット要約で返す」の形で書く
3. `ハンク被覆`: 固定した PR diff の各ハンクについて、ファイル・ハンクヘッダーと指摘 ID または `問題なし` を書く

レビュアーは `変更点の一覧 → 照合表 → ハンク被覆 → 三表の自己点検 → 指摘` の順で進め、三表を指摘より前に出さなければならない（MUST）。保証範囲は変更点の一覧に載った項目についてリポジトリ内の出現箇所をすべて照合したことまでとし、一覧自体に載らなかった暗黙の変更を発見したことを完了条件にしてはならない（MUST NOT）。全ヒット要約で返した語の保証範囲は、検索範囲と全ヒット集合の一致までとし、すべてのヒットの本文を読んだことを保証に含めてはならない（MUST NOT）。

レビュアー向け指示ブロックは、最終の照合表を投稿前に語ごとに共通照合スクリプトへ渡し、exit 0 を確認する自己検査を要求しなければならない（MUST）。抜粋の本文・列名の変更・ヒットなしのプレースホルダ行・パス列のバッククォートを自己検査で検出し、既存の共通一覧契約に従って直して再実行する（MUST）。検査用と投稿用は同じ表とし、検査できなかった場合は理由を報告して検査済みと扱ってはならない（MUST NOT）。結果の要約には検査した語数・コマンド・終了コードを残す（MUST）。

同じ指示ブロックは、1 周目は対象範囲に該当する指摘を全部列挙するまで止まらないこと、差分限定の再レビューは前回指摘の閉鎖確認（状態欄の付与）に限り新規の指摘を出さないことを含まなければならない（MUST）。ただし例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる新規の指摘は、差分限定の周でも出してよい。方式の書き換え後の全体レビューでも新規に出してよい深刻度は `blocking` だけとし、前回の「直し方」どおりに直した箇所を再指摘してはならない（MUST NOT）。直し方自体が誤っていた場合はレビュアー側の誤りとして `wontfix` 相当の記録にする。差分限定の周に出た例外 3 種の新規指摘は、仕分け表の順 1 から通す（MUST）。

#### Scenario: 三表が指摘より前にある

- **WHEN** 一周目のレビュアー向け指示ブロックに従ってレビュー結果を作る
- **THEN** `変更点の一覧`・`照合表`・`ハンク被覆` がこの順で指摘より前に出力される

#### Scenario: 受け入れ条件と変更点を対応づける

- **WHEN** `変更点の一覧` を作る
- **THEN** 記録先の各受け入れ条件が 1 つ以上の変更点 ID に対応し、各変更点に検索語がある

#### Scenario: 照合表は diff 外を含む

- **WHEN** 変更点の検索語が diff 外のファイルにも現れる
- **THEN** `照合表` は再実行可能な検索コマンドと diff 外を含む全ヒット、その判定を記録する

#### Scenario: 全件列挙の一文がある

- **WHEN** SKILL.md のレビュアー向け指示ブロックを読む
- **THEN** 「該当する指摘を全部列挙するまで止まらない」旨の 1 文がある

#### Scenario: 再レビューで新規 nit を出さない

- **WHEN** SKILL.md のレビュアー向け指示ブロックを読む
- **THEN** 再レビューでは新規の `nit` を出さず、全体レビューに戻っても新規に出してよいのは `blocking` だけと書かれている

#### Scenario: 差分限定の周でも例外 3 種は出せる

- **WHEN** SKILL.md のレビュアー向け指示ブロックの、新規の指摘を出さない文を読む
- **THEN** 例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる新規の指摘は出してよいという但し書きがある

#### Scenario: 投稿前に四種の不正形を検出する

- **WHEN** 最終の照合表に、抜粋の本文・変更された列名・ヒットなしのプレースホルダ行・バッククォートで囲まれたパスのいずれかがある
- **THEN** レビュアーは投稿前の語ごとの共通照合スクリプトで非 0 の終了を検出し、固定 SHA・検索語・判定を維持して正確な列名と本文全体・空表・装飾のないパスへ直し、exit 0 を確認してからその表を投稿する

#### Scenario: 零件と全ヒット要約も自己検査する

- **WHEN** 検索結果が 0 行の語、または全ヒット要約を使う語の最終の照合表を作った
- **THEN** 0 行の語は正しいヘッダーと区切りだけの空表を、要約の語は既存契約に従った要約と必要な食い違い行だけを同じ共通照合スクリプトへ渡し、結果の要約に語数・コマンド・終了コードを残す

#### Scenario: 自己検査を実行できない

- **WHEN** レビュアーが投稿前の共通照合スクリプトを実行できない
- **THEN** 実行できない理由を報告し、自己検査が成功したとは記録しない。G の既存の照合・補足・review-incomplete の規則は免除しない

### Requirement: G は一周目の三表を機械照合してから指摘を受理する

G は一周目のレビュー結果について、指摘の内容を読む前に次を機械照合しなければならない（MUST）: 記録先の各受け入れ条件が `変更点の一覧` の 1 項目以上に対応していること、各 `照合表` の全ヒット集合が表に記載された再実行可能な検索コマンドを対象 HEAD で実行した集合と一致すること（`全ヒット要約:` の行を持つ表では行数とハッシュの一致をもって満たす）、固定した PR diff の全ハンクが `ハンク被覆` に 1 回以上現れること。G はこの照合で変更点の意味や `一致` / `食い違い` の正しさを再レビューしてはならない（MUST NOT）。

dev-workflow プラグインは、共通一覧契約の表から得たヒット集合と G が検索コマンドを固定 SHA で再実行して得たヒット集合の差分を比較するスクリプトを含まなければならない（MUST）。集合が一致するときは exit 0、表に無いヒットまたは検索結果に無い表の行があるときは exit 1 と差分の `file:line` を出力する（MUST）。`全ヒット要約:` の行を持つ表については、要件「共通照合スクリプトは全ヒット要約を再実行して照合する」の `summary:` / `extra:` の出力をもってこの差分の出力とする。このスクリプトは一周目照合と順 3 の grep の語の経路の第 1 段で共用しなければならない（MUST）。場合分けの軸の経路をこのスクリプトの grep コマンド・4 列検証へ通してはならない（MUST NOT）。

全ハンクの比較には新規ファイルの `@@ -0,0 +1,N @@` も含め、固定 PR diff のファイルと正確なハンクヘッダーをキーにしなければならない（MUST）。区画がある場合は全区画の実際の被覆行の和集合を使い、「他区画で被覆済み」という文章だけやヘッダーを省いた「新規」の行を被覆に数えてはならない（MUST NOT）。G は補足を依頼する前に、未被覆の全ハンクをファイルと正確なヘッダーの一覧で示し、既存の補足先の規則に従って要求に含めなければならない（MUST）。

照合に差分または欠落した表があり `補足済み回数: 0` のとき、G はレビュー全体をやり直させず、固定 HEAD・元の三表・残差・補足済み回数を含む Status `needs-reviewer` で、不足した項目だけの補足を求めなければならない（MUST）。本体が fresh reviewer を起動する経路でも、その reviewer は同じレビューの不足分だけを補い、元の三表を置き換えたりレビューを最初から行ったりしてはならない（MUST NOT）。

補足結果は `補足済み回数: 1` とともに G へ渡し、G または reviewer が fresh thread に交代しても回数をリセットしてはならない（MUST NOT）。補足後も差分または欠落が残る場合、G は残差を記録して terminal Status `review-incomplete` で return し、合格処理へ進んではならない（MUST NOT）。develop 本体は `review-incomplete` を受けたら新しい reviewer を起動せず、`agent-review:pending` のまま残差を報告して工程を止めなければならない（MUST）。

#### Scenario: 照合表に無いヒットを検出する

- **WHEN** レビュアーの照合表に無い `file:line` を 1 件含む検索結果を照合スクリプトへ渡す
- **THEN** スクリプトは exit 1 で終了し、その `file:line` を差分として出力する

#### Scenario: ヒット集合が一致する

- **WHEN** レビュアーの照合表と検索結果が同じヒット集合を持つ入力を照合スクリプトへ渡す
- **THEN** スクリプトは exit 0 で終了する

#### Scenario: 受け入れ条件とハンクを照合する

- **WHEN** 一周目のレビュー結果を G が受け取る
- **THEN** G は各受け入れ条件が変更点に対応し、固定した diff の各ハンクがハンク被覆に現れることを機械照合してから指摘の仕分けへ進む

#### Scenario: 補足後にも差分が残る

- **WHEN** G が不足項目だけを 1 回追加依頼した後も照合差分が残る
- **THEN** G は残った差分と `補足済み回数: 1` を記録して `review-incomplete` で return し、本体は reviewer を再起動せず、合格処理へ進まない

#### Scenario: fresh reviewer でも補足回数を増やさない

- **WHEN** Codex 経路で本体が補足用の fresh reviewer を起動し、その結果を fresh G に渡した後にも差分が残る
- **THEN** payload の固定 HEAD・元の三表・残差・`補足済み回数: 1` が引き継がれ、fresh G は `review-incomplete` で終了し、2 回目の `needs-reviewer` を返さない

#### Scenario: 新規ファイルのハンクがどの区画にも無い

- **WHEN** 固定 PR diff に新規ファイルのハンクがあり、どの区画の被覆行にも対応するファイルと正確なハンクヘッダーが無い
- **THEN** G は補足を頼む前にそのファイルとヘッダーを未被覆一覧に載せ、既存の補足先へ回し、被覆が揃うまで指摘仕分けへ進まない

#### Scenario: 他区画への参照だけでは被覆されない

- **WHEN** ある区画が「他区画で被覆済み」と書いたがその区画の表にも被覆行が無い、または行のヘッダーが「新規」とだけ書かれている
- **THEN** G は固定 PR diff にある実際のファイルとハンクヘッダーを未被覆一覧に残す

#### Scenario: 補足後にも新規ファイルが未被覆である

- **WHEN** 補足済み回数が 1 で再照合しても未被覆の新規ファイルのハンクが残る
- **THEN** G は残ったファイルと正確なヘッダーを記録し、既存規則どおり review-incomplete で return して合格処理へ進まない
