## Context

issue #689（エピック #272 の子）。節目ごとに 1 行積む仕組み（#303、PR #704、archive 済みの change `cost-ledger-timeline`）の上に、「issue を閉じたときの合計」を足す。

いまの形（HEAD f26fbecf）:

- `gh issue close` を実行すると、hook `gate-report.sh` が裏のプロセス `gate_report.py` を起こし、その issue の 1 本のコメントに `issue クローズ` の行を 1 行積む。累計は `/cost <issue番号>` と同じ値（その issue に帰属した区間の合計）
- `gate_report.py` が呼ぶ `gh` は対象 1 件あたり 3 回（対象の確認・既存コメントの取得・書き込み）。数字と書式は `cost_ledger.py timeline` が作り、`timeline` は `gh` を呼ばない
- 行の書式は `cost_ledger.py` の `timeline_row()` だけが持つ。#303 の design は、この関数を #689 と #691 が同じ書式に乗る入口にすること、合計の定義の変更は #689 が行うことを書いている
- spec `cost-ledger-attribution` の「2 つの鍵は独立である」は、`/cost <PR番号>` と `/cost <issue番号>` を足して総額とすることを禁じている

仕様づくりの時点で実測した事実:

- GraphQL の `closedByPullRequestsReferences(first:100)` は 1 回の呼び出しで、PR の番号・`headRefName`・`baseRepository.nameWithOwner`・`isCrossRepository`・`pageInfo.hasNextPage` を返す。issue #303 では PR #704（`MERGED`、ヘッドブランチ `oratta/issue-303`）が 1 件返った
- 閉じた PR が無い issue（#689）では 0 件で返る
- PR の番号を issue として問い合わせると失敗する（#704 で終了コード 1）

エピック #272 の「全体の制約」: LLM のトークンを使わない。hook は出力を出さない。セッションを 1 秒以上止める処理は裏で走らせる。積む 1 行は短く保つ。hook 1 回の所要時間と `gh` の呼び出し回数を変更の前後で実測して PR に書く。積む行には金額・入出力トークン・キャッシュトークンの 3 項目を「累計（増分）」で載せる。

## Goals / Non-Goals

**Goals:**

- issue の合計を、同じ行を二重に数えない形で定義する
- `gh issue close` を実行したときに、合計とその内訳（PR ごとの額と、PR の外の区間の額）を、既存の 1 本のコメントに 1 行で載せる
- 閉じた PR が 0 件の issue では、合計が今の `/cost <issue番号>` と同じ値になる
- `gh` の呼び出しを 1 回だけ増やし、PR の数に比例させない

**Non-Goals:**

- auto-merge のマージや `Closes` による自動クローズのときの行（#691）
- エピックの子 issue ごとの内訳（#690）
- `/cost <issue番号>` の出力と `gh` の呼び出しを変えること（新しい子 issue の候補として return に書く）
- 既に積まれた行をさかのぼって直すこと

## Decisions

### 1. 合計の定義: PR のヘッドブランチの行と、そのブランチ上に無い区間の行を足す

issue の合計は次の 2 つの和とする。

- **PR の分**: 数える PR 1 件ごとに、ヘッドブランチの行の合計。`/cost <PR番号>` と同じ引き方（行のブランチ名がヘッドブランチと一致する行。リポジトリでは絞らない）
- **PR の外の分**: その issue に帰属した区間の行（`/cost <issue番号>` が数える行）のうち、行のブランチ名が、数える PR のどのヘッドブランチとも一致しない行の合計

どちらも `--at` の時刻以前の行だけを数える。1 つの行はブランチ名を 1 つしか持たないので、ブランチの違う PR どうしは重ならず、PR の外の分はどの PR の分とも重ならない。したがって二重に数える行は無い。

同じヘッドブランチを持つ PR が複数あるときは、番号のいちばん小さい PR だけを数え、残りは数えない（内訳にも出さない）。同じブランチの行を 2 回足さないため。

**理由**: issue の本文の定義「（その issue を閉じた PR の分）+（issue の番号を触った区間のうち、それらの PR のブランチ上に無い分）」をそのまま行の単位に落とした形で、判定に使うのは各行が既に持っているブランチ名だけで済む。

**選ばなかった案**:

- 2 つの行の集合を `request_id`（行の識別子）で突き合わせて重複を除く案。結果は同じになる（PR の分は「ブランチ名が一致する行すべて」なので、区間の行がその集合に入るかどうかはブランチ名だけで決まる）。突き合わせのために PR の分の行を全部メモリに持つ必要があり、定義を読む人にも「何が重なりか」が伝わりにくいので採らない
- PR の分を区間の境界で切る案（issue を触ったあとの PR の行だけ数える）。PR のブランチ上の作業は issue の番号に触れずに進むのが普通で、切る位置に根拠が無い

**この定義が持つ性質**（確定していることなので、リスクではなくここに書く）:

- PR の分は `/cost <PR番号>` と同じく、ブランチ名だけで引く。同じ名前のブランチを別のリポジトリでも使っていれば、その行も入る。`/cost <PR番号>` が既に持っている性質で、この change では変えない
- 1 本の PR が複数の issue を閉じるとき、その PR の分は各 issue の合計に全額入る。issue の合計どうしを足すと重なる（エピックでの足し方は #690 が決める）
- 手元の台帳（会話ログ）に無い作業は数えられない。別の PC や別の人が進めた PR の分は $0.00 になる

### 2. 数える PR: `closedByPullRequestsReferences` の結果のうち、同じリポジトリの中の PR

GraphQL の `closedByPullRequestsReferences(first: 100)` を既定の引数で呼ぶ（クローズ済みで未マージの PR は含まれない）。返った PR のうち、次の両方を満たすものだけを数える。

- `baseRepository.nameWithOwner` が対象の issue のリポジトリと一致する（大文字と小文字は区別しない）
- `isCrossRepository` が偽（ヘッドブランチが同じリポジトリにある）

`pageInfo.hasNextPage` が真（100 件を超える）なら、問い合わせの失敗と同じに扱い、合計の行を積まない。

**理由**: PR の分はブランチ名で引くので、ヘッドブランチが別のリポジトリ（fork）にある PR を数えると、fork の側の `main` のようなありふれた名前が手元の同じ名前のブランチの行を全部引き込む。別のリポジトリの PR も同じ理由で外す。100 件を超える issue は、一部だけ足した数字を合計と呼ばないために積まない。

**選ばなかった案**: `includeClosedPrs: true` でクローズ済み・未マージの PR も数える案。その PR で使った額も issue にかかった額ではあるが、issue の本文は「その issue を閉じた PR」と書いており、GitHub の既定の結果がその意味に合う。

### 3. `gh` を呼ぶのは `gate_report.py`、計算するのは `cost_ledger.py`

`gate_report.py` の `stack()` が、対象が PR でない issue で、きっかけに `issue クローズ` を含むときだけ、`gh api graphql` を 1 回呼ぶ（既存の `gh_api()` を通すので、ホストは github.com に固定される）。結果から決定 2 の条件で PR を選び、`cost_ledger.py timeline --issue <N>` に `--closing-pr <番号>:<ヘッドブランチ>` を PR の数だけ付けて渡す。`cost_ledger.py` は今までどおり `gh` を呼ばない。

問い合わせは対象ごとのロックを取ったあと、既存コメントの取得と同じ場所で行う。失敗したら `--closing-pr` を付けずに `timeline` を呼ぶ（`issue クローズ` の行は積む）。

`gh` の回数は、`issue クローズ` を含むきっかけで PR でない issue に積むときだけ 4 回（対象の確認・閉じた PR の問い合わせ・既存コメントの取得・書き込み）。それ以外は 3 回のまま。

**理由**: 数字と書式を `cost_ledger.py` の 1 か所に集め、ネットワークは `gate_report.py` に集める、という #303 の分け方を保つ。`timeline` のテストが `gh` の stub 無しで書ける。

**選ばなかった案**: `cost_ledger.py timeline` が自分で `gh` を呼ぶ案。spec の「`timeline` は `gh` を呼ばない」を崩し、`timeline` のテスト全部に stub が要るようになる。

### 4. 合計の行: `issue クローズ` の行の直後に 1 行足す

`timeline --issue <N>` に `--closing-pr` が 1 つ以上渡されたとき、1 回の呼び出しで 2 行足す。

1. 今までどおりの行（きっかけは `--trigger` の値。累計は区間だけの合計）
2. 合計の行。時刻は同じ。きっかけの欄は `合計（PR #704 $39.62 + PR 外 $2.00）` の形。金額・入出力・キャッシュの累計は決定 1 の合計

きっかけの欄の内訳は、PR を番号の昇順に ` + ` でつなぎ、最後に `PR 外 $<額>` を置く。額は `$` と小数 2 桁、3 桁区切り。手元に行が無い PR も `PR #710 $0.00` と書く（問い合わせで見つかったことが分かるようにする）。

合計の行の並びの鍵は他の行と同じ（時刻、きっかけの欄の文字列の UTF-8 のバイト順、累計）。`合` の先頭バイトは `issue ...` で始まるどのきっかけよりも大きいので、同じ時刻の `issue クローズ` の行のあとに来る。合計の行かどうかは、きっかけの欄が `合計（` で始まるかで見分ける（隠し行の記録の形は変えない。版は `v1` のまま）。

**合計の行の増分**は、同じ呼び出しで作った「今までどおりの行」の累計との差にする。意味は「区間だけの累計に、閉じた PR の分を合わせて増えた分」で、表の上では直前の行との差になる。この値は同じ呼び出しの中で計算できるので、既存のコメントが読めなかったときも `(?)` にならず、あとから別の行が挿し込まれても書き直さない。

読む人が誤読しうる点と対処: 合計の行の増分は「前の節目からこの節目までに使った額」ではない。README の「3 項目の読み方」に、合計の行の増分は区間だけの累計との差であることを書く。行そのものには説明を足さない（行を短く保つ制約）。

**理由**: issue の本文が「issue のクローズ時の最後の行として載せる」と書いている。区間だけの累計の行を残すので、再オープンして閉じ直したときも、区間の増え方は今までどおり追える。

**選ばなかった案**:

- `issue クローズ` の行そのものの累計を合計に置き換える案。行は 1 行で済むが、区間だけの累計の列の途中に別の定義の値が混ざり、前後の行の増分が意味を持たなくなる
- 合計を 1 行目にだけ出す案。1 行目は次の節目で差し替わるので、合計が残らない
- 合計の行の増分を `(—)` のように空にする案。エピックの要件「3 項目を累計（増分）で載せる」と `timeline_row()` の書式から外れる
- 合計の行の増分を、1 つ前の合計の行との差にする案。再オープンしない限り合計の行は 1 行しか無く、ほとんどの場合に累計と同じ値が並ぶだけになる

### 5. 増分の基準: 合計でない、1 つ前の行

合計の行でない行の増分は、並びの上でその行より前にある行のうち、合計の行でない、いちばん近い行の累計との差にする。順序が前後して挿し込まれたときに書き直すのも、新しい行より後ろにある行のうち、合計の行でない最初の 1 行だけにする。合計の行は書き直さない（決定 4）。

**理由**: 合計は区間だけの累計より大きい。再オープン後の `issue コメント` の行が合計の行を基準にすると、何も使っていなくても増分が負になる。合計の行を飛ばせば、合計の行があっても無くても、ほかの行の増分は同じ値になる。

合計の行が 1 行も無いコメントでは、今までの規則（1 つ前の行との差、直後の 1 行を書き直す）と結果が同じになる。

### 6. 1 行目: 最後の行が合計の行のときだけ合計を出す

本文の 1 行目は今までどおり、いちばん最後の行の累計から `headline()` で作る。最後の行が合計の行のときは、金額が合計になるので、帰属の種別を `区間+閉じた PR` と書く（例: `コスト: $41.62 / ¥6,243 @150 — issue #12 (acme/repo) 帰属: 区間+閉じた PR`）。それ以外のときは今までどおり `/cost <番号>` の 1 行目と同じ行。

再オープンして次の行が積まれると、1 行目は区間だけの累計に戻る。合計は表の行として残る。

**理由**: 1 行目だけを取って使う読み手が、`/cost <issue番号>` と違う金額を同じ種別の名前で受け取らないようにする。

### 7. 合計の行を積まない場合

| 場合 | 動き |
|---|---|
| 数える PR が 0 件（問い合わせの結果が 0 件、または決定 2 の条件で全部外れた） | `--closing-pr` を付けない。`issue クローズ` の行だけ積む。その行の累計がそのまま合計 |
| 問い合わせが失敗した・応答が読めない・100 件を超える | 同じく `issue クローズ` の行だけ積む |
| きっかけに `issue クローズ` を含まない、または対象が PR | 問い合わせない |
| 緊急停止 `COST_LEDGER_GATE_REPORT=off` | 今までどおり全部止まる |

0 件の場合と失敗した場合は、コメントの上では見分けが付かない。見分ける印を足すと行が長くなるか行が増えるので、この change では足さない（新しい子 issue の候補として return に書く）。

区間の累計が 0 でコメントも無い issue でも、合計が 0 でなければ 2 行とも積む（`issue クローズ` の行は `$0.00 (+0.00)`）。区間の累計も合計もすべて 0 でコメントも無いときは、今までどおり何も積まない。

### 8. きっかけの欄の長さ: PR は 3 件まで個別に書く

数える PR が 3 件以下なら PR ごとに書き、4 件以上なら `合計（PR 4 件 $50.00 + PR 外 $2.00）` と、件数と PR の分の和にまとめる。

issue の受け入れ条件「合計とその内訳（PR ごとの額と、PR の外の区間の額）が出る」との関係: PR が 3 件以下のときはコメントの行で満たす。4 件以上のときは、コメントの行には PR の分の和と PR の外の額しか出ず、PR ごとの額は `cost_ledger.py issue <N> --closing-pr ...` の出力（決定 9）でしか見られない。つまり 4 件以上では、コメントの上ではこの受け入れ条件を満たさない。エピックの制約「積む 1 行は短く保つ」を優先した結果で、実機確認（PR が 1 件）と bats は 3 件以下の形で受け入れ条件を確かめる。

**選ばなかった案**: 何件でも個別に書く案。1 件あたり 17 文字前後増え、行を読むエージェントのトークンが PR の数に比例して増える。上限を置かないと 100 件まで伸びる。

### 9. 手で引く入口: `cost_ledger.py issue <N> --closing-pr ...`

`issue` サブコマンドに `--closing-pr <番号>:<ヘッドブランチ>`（繰り返し可）を足す。

- JSON に `closing_prs`（`{"number", "branch", "usd"}` の配列。番号の昇順）・`outside_pr_usd`・`combined_total_usd` を足す。既存の鍵（`total_usd` など）は変えない
- `--closing-pr` を渡さないとき、`closing_prs` は空の配列、`outside_pr_usd` と `combined_total_usd` は `total_usd` と同じ値
- 表示では、`--closing-pr` を渡したときだけ、1 行目の下に `  合計（閉じた PR 込み）: $41.62 — PR #704 $39.62 + PR 外 $2.00` の行を足す。ここでは PR が何件でも個別に書く。1 行目は変えない

`timeline` と `issue` は同じ関数で合計を計算する。受け入れ条件「閉じた PR が 0 件の issue では、合計が今の `/cost <issue番号>` と同じ値になる」は、`--closing-pr` 無しの `combined_total_usd` が `cost <issue番号>` の金額と一致することで確かめる。

`--closing-pr` の値は最初の `:` で 2 つに分け、前が 1 以上の整数、後ろが空でない文字列のときだけ受ける。それ以外は標準エラーに理由を書いて終了コード 2。`timeline` で `--pr` と一緒に渡されたときも終了コード 2。

### 10. 台帳への差分追記は 1 回の呼び出しで 1 回

`load_facts()` は呼ぶたびに会話ログの差分を台帳へ追記する。合計の計算では区間の行と PR のブランチの行を読むので、そのまま呼ぶと PR の数 + 1 回の追記が走る。合計の計算では、追記を最初の 1 回だけにし、PR のブランチの行は台帳を 1 回走査して全部のヘッドブランチの分をまとめて読む。

**理由**: 所要時間を PR の数に比例させない。途中で会話ログが増えても、区間の行と PR の行が同じ時点の台帳を読むようになる。

## Risks / Trade-offs

- [閉じた PR の問い合わせで、裏の処理が `gh` 1 回分遅くなる] → hook の同期部分は変わらないので、セッションは止まらない。裏の処理全体の所要時間は変更の前後で実測して PR に書く（tasks 5.1）
- [同じ名前のブランチを別の作業で使い回していると、PR の分にその行が入り、合計が大きく出る。ブランチ名を使い回す運用のときにだけ起こり、`/cost <PR番号>` でも同じ額が出る] → 内訳に PR ごとの額を書くので、`/cost <PR番号>` と見比べて気付ける。README に書く
- [`gh issue close` を実行した PC に PR の作業の記録が無いと、PR の分が $0.00 になり、合計が小さく出る。別の PC で作業した issue を閉じるたびに起こる] → 内訳に `PR #710 $0.00` と出るので、数えられていないことが行から分かる
- [合計の行の増分を「この節目までに使った額」と読み違える] → README に読み方を書く（決定 4）
- [問い合わせの失敗と 0 件が見分けられない] → 決定 7。新しい子 issue の候補

## Migration Plan

`hooks.json` を変えないので、マージ後は marketplace の自動更新だけで反映される。既に積まれたコメントは読み方が変わらない（合計の行が無いコメントでは、増分の規則の結果が今までと同じ）。戻すときは PR を revert する。合計の行が付いたコメントは、revert 後の `timeline` でもふつうの行として読める（ただし、そのあとに積まれる行の増分は合計の行を基準にする）。
