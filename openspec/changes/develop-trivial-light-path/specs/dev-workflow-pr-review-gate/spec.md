## ADDED Requirements

### Requirement: 前提確認と重さ判定の段で軽い通し方の条件を確かめる
pr-review-gate の `stages/prepare.md` の手順 1（前提を揃える）は、対象 HEAD を固定した直後（手順 1 の 5 のあと、手順 2-0 の前）に、記録先の最新の仕様化判断のコメント（1 行目が `^仕様化判断: (する|しない)$` に完全一致するコメントのうち最後の 1 件）に `^通し方: 軽い$` に完全一致する行があるときだけ、軽い通し方の条件を確かめる手順を持たなければならない（MUST）。記録先は手順 1 の 3 で解決したもの（issue 参照が無い PR では PR 自身）を使う（SHALL）。その行が無い PR では、この手順を行ってはならず（MUST NOT）、確認のコメントも投稿してはならない（MUST NOT）。確認はレビュアーを起こす前に終えなければならない（MUST）。

#### Scenario: 行の無い PR では確かめない
- **WHEN** 記録先の最新の仕様化判断のコメントに `通し方: 軽い` の行が無い
- **THEN** G は軽い通し方の確認をせず、確認のコメントも投稿せずに手順 2-0 へ進む

### Requirement: 軽い通し方の条件のうち機械で測る点
前提確認と重さ判定の段の軽い通し方の確認で、G は次の 4 点を機械で測り、1 つでも外れたら条件外としなければならない（MUST）: 仕様化判断の 1 行目が `仕様化判断: しない` ちょうどであること、`種類:` の行の値が 6 種類（`typo` / `lint` / `コメント` / `フォーマット` / `ワンライナー fix` / `設定値`）のどれか 1 つちょうどであること、`^確かめ方: .` に当たる行が 1 行以上あること、PR の変更ファイルに `openspec/` の下のファイルが 1 つも無いこと。測るコマンドは `stages/prepare.md` に書き（MUST）、`scripts/` にスクリプトを足してはならない（MUST NOT）。grep の 0 件は終了コードではなく出力の値で判定する（SHALL）。

#### Scenario: openspec の下に差分がある
- **WHEN** 仕様化判断のコメントが `通し方: 軽い` を持ち、PR の変更ファイルに `openspec/` の下のファイルがある
- **THEN** 機械で測る点が外れ、条件外になる

#### Scenario: 確かめ方の行が無い
- **WHEN** 仕様化判断のコメントが `通し方: 軽い` を持つが、`確かめ方:` の行を持たない
- **THEN** 機械で測る点が外れ、条件外になる

### Requirement: ワンライナー fix だけは変更の大きさを機械で測る
`種類:` が `ワンライナー fix` のとき、G は、変更の記録のファイル（パスが `changes/<数字>.md` で終わるもの）を除く変更ファイルが 1 つで、その追加が 1 行以下かつ削除が 1 行以下であることを機械で測り、外れたら条件外としなければならない（MUST）。変更の記録のファイルは、どの種類でも機械で測る点の対象に数えてはならない（MUST NOT）。ワンライナー fix 以外の種類に、変更ファイル数や行数の上限を置いてはならない（MUST NOT）。

#### Scenario: ワンライナー fix と書いて 2 ファイルを変えた
- **WHEN** 仕様化判断のコメントが `通し方: 軽い` と `種類: ワンライナー fix` を持ち、PR が変更の記録のほかに 2 つのファイルを変えている
- **THEN** 機械で測る点が外れ、条件外になる

#### Scenario: 変更の記録のファイルは数えない
- **WHEN** 仕様化判断のコメントが `通し方: 軽い` と `種類: ワンライナー fix` を持ち、PR が 1 ファイルの 1 行と `plugins/<name>/changes/<番号>.md` を変えている
- **THEN** 変更の記録のファイルは数えず、機械で測る点はすべて満たされる

### Requirement: G は差分を読んで変更が宣言した種類の条件に収まるかを判断する
機械で測る点をすべて満たしたとき、G は PR の差分（`gh pr diff`）を読み、変更の記録のファイルを除くすべての変更が `種類:` の行の種類に収まるかを判断しなければならない（MUST）。種類が typo・lint・コメント・フォーマット・設定値なら、プログラムの挙動を変えないか（設定値なら、値を変えても挙動が変わらないか）を判断する（MUST）。種類がワンライナー fix なら、明白なバグを直す 1 行で、直し方に選択肢がないかを判断し、挙動が変わることを条件外の理由にしてはならない（MUST NOT）。判断がつかないときは条件外とする（MUST）。

#### Scenario: typo と書いて関数の中身を変えた
- **WHEN** 仕様化判断のコメントが `種類: typo` を持ち、差分が関数の条件分岐を変えている
- **THEN** G は条件外と判断する

#### Scenario: 既存のチェックで確かめられる明白な 1 行のバグ修正は条件内
- **WHEN** 仕様化判断のコメントが `種類: ワンライナー fix` と `確かめ方:` の行を持ち、差分が明白なバグ（例: 比較の向きの取り違え）を 1 ファイルの 1 行で直していて、直し方がほかに無い
- **THEN** 挙動は変わるが、G は条件内と判断する

#### Scenario: 直し方に選択肢がある 1 行修正は条件外
- **WHEN** 仕様化判断のコメントが `種類: ワンライナー fix` を持ち、差分の 1 行が既定値を選び直すなど、直し方が複数考えられる修正である
- **THEN** G は条件外と判断する

### Requirement: 軽い通し方の確認の守備範囲
前提確認と重さ判定の段の軽い通し方の確認（機械で測る点・ワンライナー fix の大きさ・G の判断）の守備範囲を、次のとおりとする（MUST）。入力は記録先の最新の仕様化判断のコメント（本体が書く）と PR の差分・変更ファイル一覧である。拾う誤りは、行の書式の誤り・6 種類以外の種類・`openspec/` の差分・宣言した種類に収まらない変更・ワンライナー fix の大きさ超えを、レビュアーを起こす前に止めること。変更の記録のファイル（`changes/<数字>.md`）は機械の点と G の判断の両方から外すので、その中身は通ることを許す（レビュアーが差分全体と一緒に見る）。`確かめ方:` のコマンドの妥当性も見ない。穴を塞ぎ切ることは完了条件にしない。

#### Scenario: 変更の記録のファイルの中身は確認で止めない
- **WHEN** 軽い通し方の PR の `plugins/<name>/changes/<番号>.md` に、変更の記録以外の内容が書かれている
- **THEN** 軽い通し方の確認はこれを止めず、レビュアーが差分全体と一緒に見る

### Requirement: 軽い通し方の確認の結果を PR コメントに残し、条件外なら failed にする
G は軽い通し方の確認の結果を PR コメントに残さなければならない（MUST）。1 行目は正規表現 `^軽い通し方の確認: (条件内|条件外)$` に完全一致させ（MUST）、2 行目は `対象 HEAD: <40 桁フル SHA>` にし（MUST）、そのあとに確かめた点ごとの結果（条件外なら外れた点）を書く（SHALL）。条件内なら手順 2-0 へ進む（SHALL）。条件外なら `agent-review:pending` を外して `agent-review:failed` を付けなければならず（MUST）、レビュアーを起こしてはならない（MUST NOT）。develop の G は Status failed・`次の段: 前提確認と重さ判定`・`原因: 軽い通し方の条件外` で return しなければならない（MUST）。develop 以外の呼び出し元は、PR コメントの結果を見て通常の通し方に戻す（SHALL）。

#### Scenario: 条件外の return
- **WHEN** develop の前提確認と重さ判定の G が、軽い通し方の条件外と判定する
- **THEN** G は 1 行目が `軽い通し方の確認: 条件外` の PR コメントを投稿し、`agent-review:failed` を付け、レビュアーを起こさずに Status failed・`次の段: 前提確認と重さ判定`・`原因: 軽い通し方の条件外` で return する

#### Scenario: 条件内なら重さ判定へ進む
- **WHEN** 機械で測る点と G の判断の点がすべて満たされる
- **THEN** G は 1 行目が `軽い通し方の確認: 条件内` の PR コメントを投稿して手順 2-0 へ進み、レビュー重量の判定・レビュー・宣言・合格処理はこれまでどおり行う

### Requirement: 軽い通し方の PR の動作確認では確かめ方のコマンドを G が走らせる
`stages/pass.md` の手順 4（動作確認）は、記録先の最新の仕様化判断のコメントに `通し方: 軽い` の行がある PR では、`確かめ方:` の行のコマンドを G が PR の HEAD の作業ツリーで走らせ、動作確認の表の 1 行（手順＝そのコマンド、結果＝終了コードと出力の要点）にすることを書かなければならない（MUST）。そのコマンドがテストランナーを絞らずに全体のテストを起動するものなら、既存の規則どおり CI の結果で扱う（SHALL）。

#### Scenario: 動作確認の表に確かめ方の行がある
- **WHEN** 軽い通し方の PR の合格処理で、G が動作確認の表を作る
- **THEN** 表に `確かめ方:` のコマンドを走らせた行があり、終了コードと出力の要点が書かれている
