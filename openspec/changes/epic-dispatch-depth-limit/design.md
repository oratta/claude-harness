## Context

`epic-dispatch.sh launch <E> <C>...` は子ごとに `orca worktree create --parent-worktree path:<親>` で子ワークツリーを作り、`orca terminal create --command "<cmd> --model '<model>'"` で子セッションを起こして `/develop #C （エピック #E の子。…）` を送る。子に渡るのはこの指示の文言だけで、SKILL.md はこの文言を参照しない。子の issue がエピックなら、子のセッションは「エピックの扱い」をそのまま実行する。子ワークツリーは Orca 管理なので `route` は孫が 2 件以上なら `orca` を返し、孫のワークツリーが作られる。孫が 1 件ならサブエージェント方式で子のセッションの中で回る。どちらも深さの制限が無い。親の `wait` は子の `state` が closed になるまで待つだけで、エピックである子は孫が全部終わるまで閉じない。

`orca terminal create --command` の文字列は Orca が起動するログインシェル（zsh）に打ち込まれる（`epic-dispatch-child-model` の design.md で確かめた事実）。`cld` はシェル関数で、zsh と bash のどちらでも `VAR=x 関数` の形の代入は関数の中から起動した子プロセスに渡り、関数を抜けると消える（2026-09-25 に確認）。

同じ `epic-dispatch.sh` と SKILL.md を、並行する子 #429 #431〜#434 が触る。#431 は `wait` を触る。

## Goals / Non-Goals

**Goals:**

- 並列起動された子のセッションでは `epic-dispatch.sh` が子ワークツリーを作らない（スクリプトで止め、テストで確かめる）
- 子がエピックだったとき、親の完了報告に「後で別に起動するエピック」として番号が載る
- 子エピックは後で `/develop <子エピック>` を人が別に起動して回す

**Non-Goals:**

- 深さ 2 段以上を許す設定（段数を数える仕組み）。必要になってから足す
- `wait` の出力や終了条件の変更（#431 と衝突するため）
- サブエージェント方式の中で子がエピックだったときの機械的な停止。親の事前確認（下の「親が launch の前にエピックの子を外す」）で扱い、スクリプトでは止めない

## Decisions

### 子であることは環境変数 `EPIC_DISPATCH_PARENT_EPIC` で伝える

`launch` は端末のコマンドを `EPIC_DISPATCH_PARENT_EPIC=<E> <cmd> --model '<model>'` にする。値はエピック番号（数字だけなのでクォート不要）。子セッションの Claude Code のプロセスが環境に持ち、その Bash ツールとサブエージェントの Bash に引き継がれるので、子のセッションの中で呼ばれた `epic-dispatch.sh` が機械的に見分けられる。端末作り直しのコマンド（stderr に出す `orca terminal create --command ...`）にも同じ前置きを入れる（`agent_cmd` を 1 か所で組み立てているので自然にそうなる）。

採らなかった案:

- **起動の指示の文言だけで伝える**（今の `（エピック #E の子。…）` を SKILL.md が読む）: 読むのは LLM だけで、スクリプトは見分けられない。受け入れ条件「`epic-dispatch.sh` が子ワークツリーを作らない（テストで確認）」を満たせない
- **`epic-dispatch.sh` に `--nested` のような引数を足す**: 子のセッションの LLM が付け忘れれば効かない。止めたいのはまさに LLM が手順どおり展開してしまう場面なので、LLM に頼る口では足りない
- **`orca worktree current --json` で親ワークツリーの有無を見る**: 親の有無を示すフィールドの形を実機で確かめていない。人が手で `--parent-worktree` を付けて作ったワークツリーで `/develop <エピック>` を起動した場合も止まってしまう
- **`ANTHROPIC_*` のような Claude Code の既存の変数に載せる**: 意味が違う。`EPIC_DISPATCH_` の接頭辞でこのスクリプトの変数だと分かるようにする

### `route` は `nested` を返し、`launch` は拒否する

`EPIC_DISPATCH_PARENT_EPIC` が空でないとき:

- `route` は子の番号の検査のあと、件数・`orca` の有無・`orca worktree current` の結果によらず `nested` の 1 行を出して exit 0 で終わる。SKILL.md の手順ではエピックを解決するセッションは子を起動する前に必ず `route` を呼ぶ（unmanned と `回し方:` からの再開を除く）ので、ここで展開しない経路に入れる。`subagent` を返すとサブエージェント方式で孫が回ってしまうので、第 3 の値にする
- `launch` は引数の検査のあと、`orca` / `git` を 1 つも呼ばずに stderr に理由（親エピックの番号と「展開しない」旨）を出して exit 1 で終わる。`route` を飛ばした場合（`回し方:` のコメントから経路を引き継いだ場合）の止め具。stdout には何も出さない（既存の「子を 1 件も作らずに exit 1」と同じ扱い）

`launch` の拒否を引数の検査のあとに置くのは、引数の誤りの扱い（使い方を出して exit 1）を変えないため。

### 親が `launch` の前にエピックの子を外す

親は依存グラフから求めた blocked されていない子のうち、`gh api repos/{owner}/{repo}/issues/<N> --jq .sub_issues_summary.total` が 1 以上の子（sub-issue を持つ子）をエピックとして外し、`route` / `launch` / サブエージェント方式のどれにも渡さない。`route` が `nested` 以外を返したあとで、外した子ごとにエピックへ `後で別に起動するエピック: #N` とコメントする（`nested` のセッションが孫について書かないよう、コメントは `route` のあとにする）。これで通常の場合は子エピックのセッションがそもそも起動されず、親はその子を待たない。外した結果、渡す子が 0 件になったときも `route` は呼ぶ（引数 0 件の `route` は `subagent`、`EPIC_DISPATCH_PARENT_EPIC` があれば `nested` を返す）。再開時に `回し方:` から経路を引き継ぐ場合も、`launch` に渡す前に同じ確認で外す。

sub-issue を持たないが本文で子を列挙しているエピックは、この確認をすり抜けて起動されうる。そのときは子のセッションで `route` が `nested` を返し、次の手順で止まる。

### `nested` を受けた子のセッションは止まって親に知らせる

子のセッションは `route` が `nested` を返したら、エピックの回し方を進めず（Orca 経路もサブエージェント方式も使わない）、親エピック（`EPIC_DISPATCH_PARENT_EPIC` の番号。起動の指示の文言にも載っている）と自分の issue に `後で別に起動するエピック: #C` とコメントし、ユーザーに「このエピックは後で `/develop #C` を別に起動して回す」と伝えて止まる。自分の issue は閉じない。

親の `wait` は子の state しか見ないので、この子を待ち続ける。`wait` を変えずに扱うため、親は `timeout` で起こされたときの確認（今は `needs-approval` などを見ている）で、エピックに `後で別に起動するエピック: #N` の行がある子を動いている子から外す。ほかの子が閉じれば `closed` で起こされるので、遅れるのは子エピックが最後の 1 件になった場合だけ（最長で `wait` の上限 6 時間）。

### 親の完了報告に載せる

動いている子が無くなったとき（完了条件の確認に入る前）の親の報告（エピックへのコメントとユーザーへの報告）に、`後で別に起動するエピック: #N...` を載せる。エピックの完了条件（全子 PR がマージ）は子エピックが閉じるまで満たされないので、親エピックは開いたまま残る。

## Risks / Trade-offs

- [子エピックが事前確認をすり抜けて最後の 1 件になると、親が最長 6 時間待つ] → `wait` を変えない代わりに受け入れる。sub-issue で子を張る運用なら事前確認で外れる
- [`EPIC_DISPATCH_PARENT_EPIC` は子のセッションの中で起動されたものすべてに引き継がれる] → 子のセッションは 1 つの子 issue 専用なので、その中でエピックを展開しないことは意図どおり。端末のシェル自体には残らない（前置きの代入はそのコマンドの間だけ）
- [`EPIC_DISPATCH_CLAUDE_CMD` がシェルの関数や別名でなく、前置きの代入を受け付けない形（例えば `exec` で始まる文字列）だと値が渡らない] → 既定の `cld` と `cld-account b` のような引数付きの関数・コマンドでは渡る。実機確認で `cld` の子セッションの Bash から値が見えることを確かめる
- [`回し方:` のコメントから経路を引き継いだ子エピックのセッションがサブエージェント方式だと、スクリプトでは止まらない] → 並列起動された子の issue に `回し方:` が付いているのは、以前に人が根として回した場合だけ。起きたらそのセッションは人が見ている

## Migration Plan

スクリプトと SKILL.md の変更だけで、移行手順は無い。既に動いている子セッションには環境変数が無いので、この変更の前に起動された子は今までどおり（展開しうる）。
