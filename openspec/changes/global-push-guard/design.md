## Context

#60 のガードは `loops-dev-agent-install` Step 6 が設置する `.githooks/pre-push` に実装されており、`core.hooksPath` をリポジトリローカルに設定する。したがって自律ループを導入した repo にしか存在しない。

一方、事故の実発生源は対話セッション（人間が手で push する / Claude が Bash で push する）であり、これはリポジトリを選ばない。git フックはコマンドの出所を問わないため、グローバル `core.hooksPath` に置けば両方を 1 枚で覆える。Claude 専用の PreToolUse deny では人間の手打ちが漏れる。

実測（このマシン、2026-07-30）:

| 項目 | 実測 |
|---|---|
| `gh pr list` 1 回 | 約 0.5 秒（プロセス起動 0.06 秒 + ネットワーク往復） |
| 現行実装（2 回呼び） | +約 1.0 秒/push |
| 素の小さい push | 約 0.8 秒 |
| `timeout` / `gtimeout` | **どちらも未インストール** |

## Goals / Non-Goals

**Goals:**

- 人間の手打ち push と Claude の push を、リポジトリを問わず同じ層で止める
- オフライン・不安定回線でフックが体感で固まらない（数秒で諦めて通す）
- push あたりのオーバーヘッドを半減させる
- 既存のリポジトリローカル層（厳しい方）を壊さない

**Non-Goals:**

- 既に `core.hooksPath` を独自運用しているリポジトリへの介入（ローカル設定が優先されるので手を出さない）
- `.git/hooks/` に直置きされたフックの移行（無効化される旨の警告と回避方法の提示に留める）
- closed PR のブランチ、GitHub 以外のホスティング（#60 の Non-Goals を引き継ぐ）
- 複数マシンへの自動配布（導入スキルを実行すれば再現できる、で十分とする）

## Decisions

### D1: 層を 2 枚に分け、グローバル層にはマージ済みチェックだけを置く

| 層 | 置き場所 | 内容 | 対象 |
|---|---|---|---|
| グローバル | `~/.githooks/pre-push` | マージ済み PR チェックのみ | 全リポジトリ |
| ローカル | `<repo>/.githooks/pre-push` | main/master 直 push 拒否 + マージ済み PR チェック | 自律ループ導入 repo |

- main/master 直 push 拒否をグローバルに広げる案 → 却下。`~/.claude/rules/git-commit-policy.md` の「ローカル main 運用」リポジトリでは、承認後の `git push origin main` が正常系であり、これを全リポジトリで拒否すると正当な操作を壊す
- git の設定優先順位（ローカル > グローバル）により、ローカル層を持つ repo は自動的に厳しい方が使われる。片方を無効化する仕組みは不要

### D2: `gh` は `--state all` で 1 回だけ呼ぶ

`gh pr list --head <branch> --state all --json state` を 1 回呼び、jq で `MERGED` と `OPEN` の件数を同時に数える。実測で 2 回呼び 1.0 秒 → 1 回 0.5 秒。判定ロジック（merged > 0 ∧ open == 0）は #60 のまま変えない。

### D3: 自前タイムアウトで fail-open を「速く諦める」に格上げする

fail-open は「最終的には通す」ことしか保証していない。回線が死んでいると `gh` の接続タイムアウトまでフックが固まり、全 push に効かせた瞬間に体感が壊れる。

実装は 2 段構え:

1. `timeout` または `gtimeout` が PATH にあればそれを使う（`timeout 3 gh pr list ...`）
2. 無ければバックグラウンド実行 + 0.1 秒刻みのポーリング + `kill` にフォールバックする

このマシンには `timeout` も `gtimeout` も無いため、**フォールバック経路が主経路**になる。したがってフォールバック側もテストで固定する。

- 代案「`gh` の設定でタイムアウトを指定」→ 却下。`gh` に接続タイムアウトのオプションは無い
- 代案「タイムアウトを付けない」→ 却下。ローカル層のみなら許容できたが、全 push に効かせるなら許容できない
- タイムアウト値は 3 秒。実測 0.5 秒の 6 倍で、正常系を誤って切らない余裕がある

### D4: 導入スキルは `dev-workflow` プラグインに置く

グローバル層は自律ループとは無関係（人間の手打ちが主対象）なので `loops` には置かない。`dev-workflow` は「人間依頼と loop-dev-agent 無人サイクルの両対応」を掲げており、両者に共通するガードの置き場所として整合する。

### D5: 導入は冪等にし、既存の `core.hooksPath` を無断で上書きしない

- `~/.githooks/pre-push` は毎回上書きしてよい（生成物であり、内容はスキルが唯一の出所）
- `git config --global core.hooksPath` に既に別の値が入っている場合は、上書き前に確認する。他のツール（自作の hooks 集など）を無言で殺さないため
- 2 回実行しても壊れないこと（同じ内容を書き、同じ設定を再設定するだけ）

### D6: フックの本体は 2 箇所に重複させる

グローバル層とローカル層はどちらも自己完結した 1 ファイルである必要がある（ローカル層は対象リポジトリに配布され、このプラグインを参照できない）。共通スクリプトを参照させる案は、参照先が無い環境でフックが壊れるため却下。約 20 行の重複を許容し、両方をテストで固定することで乖離を検出する。

## Risks / Trade-offs

- **グローバル `core.hooksPath` が `.git/hooks/` 直置きフックを無効化する** → 導入スキルで警告し、回避方法（当該 repo で `git config core.hooksPath .git/hooks`）を提示する。husky 等は自前で hooksPath を設定するため影響を受けない
- **フォールバックのポーリングが `sleep 0.1` に依存する** → POSIX の `sleep` は整数秒しか要求されないが、macOS / GNU coreutils はどちらも小数を受け付ける。受け付けない環境では 1 秒刻みに落ちるだけで、機能は壊れない
- **タイムアウト 3 秒でも遅い回線では誤って fail-open する** → 見逃しは第 2 層（GitHub の head branch 自動削除）・第 3 層（`/wt-clean`）で回収する。ガードを外されるより遥かに軽い
- **重複した 2 つのフック本体が乖離する** → 両方に同等のテストを置き、拒否条件・タイムアウト・1 回呼び出しを別々に検証する
- **グローバル設定は `~/.gitconfig` に入るため、この repo の再 clone では失われない**が、新しいマシンでは再実行が必要 → 導入スキルの実行が再現手順そのものになる
