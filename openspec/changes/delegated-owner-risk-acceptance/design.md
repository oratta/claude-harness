## Context

親経由のリスク許容は今、`owner-reply-check.sh --relayed` だけで確かめている（archive の `2026-10-16-relayed-owner-reply-check`）。`--relayed` が見るのは、親の会話ログの 1 行が主の入力であること（9 条件）、その行が停止の記録より後であること、そのあいだに親が停止の記録の URL を本文に書いたこと、URL を書いた最後の親の発言とその行のあいだに別の主の発言が無いこと、の 4 つである。後ろの 3 つが「主がこの止まりへの報告を見て答えた」ことの機械的な裏付けで、許容の意思と名指しの範囲は呼び出し側（子の本体と G）が `MATCH:` の全文で読む。

包括的な委任はこの裏付けを構造的に持てない。委任は止まる前に述べられ、特定の停止の記録を見て答えたものではない。この変更は、同じ強さの機械的な裏付けを「委任」に対して作る。

前提と制約:

- 主の会話ログの行（`origin.kind` が human など 9 条件）は、エージェントが作れない主の入力の証拠として使える。GitHub のコメントの投稿者（`author_association: OWNER`）は、エージェントも主のアカウントで投稿するので、主本人の証拠にならない
- 主は自由な文で任せる。実例の発言（エピック #1038 の 11:03）には決まった語が無く、別の issue 番号（1238）も含む
- `parent-pass-criteria.md` は兄弟の子が同時に触っているので、この変更では触らない
- 公開版のリポジトリなので、オーナーの固有名・PC の絶対パスを書かない

## Goals / Non-Goals

**Goals:**

- 主が一度確認した委任で、その後に止まった同じエピックの子の PR のリスク許容を、主が子のタブを開かずに通せる
- 委任が主本人の発言であること、効く範囲・期間・取り消しを、エージェントの判断ではなく会話ログと GitHub の記録で確かめる
- 委任より前に述べた、別の子・別の PR だけを名指しした許容は、どちらの経路でも今どおり落とす

**Non-Goals:**

- 委任より前に止まっていた子への適用（その止まりは主が委任の確認の時点で見えているので、今どおり報告して直接答えてもらう）
- 主の自由な文から委任の意思や範囲を機械的に読み取ること
- 聖域の変更・破壊的な操作・マージの承認・不許容の委任（どれも今どおり主本人が答える）
- 会話ログの改変の検知（既存の `--relayed` と同じ守備範囲）

## Decisions

### D1. 委任は「定型の委任の記録」への主の直接の確認で成立させる

主が任せる旨を述べたら、親はエピックの issue に定型の委任の記録を投稿し、その URL を本文に書いて「この範囲で任せてよいか」を主に問い、主がその直後に別の発言を挟まずに答えた発言を委任の確認とする。`--delegated` はこの確認の行を、`--relayed` と同じ「URL を書いた親の発言への直接の答え」の作りで確かめる（確かめる URL が停止の記録ではなく委任の記録になる）。

採らなかった案:

- **主の自由な発言そのものを委任とみなす（親が uuid を添えるだけ）**: どの発言を委任と読むかが親の判断だけになり、`1034は許容` のような名指しの許容を親が委任として送ったときに、機械的に落とせない。受け入れ条件の「別の子・別の PR だけを名指しした許容は落ちる」をテストで固定できない
- **主の発言に決まった語（例 `全部任せる`）を求める**: 主は自由な文で話す。実例の発言も決まった語を持たない
- **主の GitHub コメントで委任する**: エージェントも主のアカウントで投稿するので、投稿者で主本人を確かめられない
- **委任の範囲を主の文から読む**: 実例の文は別の issue 番号を含み、番号の有無で範囲を決められない。範囲は定型の記録の文で決め、主はそれに同意するだけにする

主の手間は委任 1 回につき確認の 1 回が増えるが、子が止まるたびに子のタブを開く今の手間よりずっと少ない。

### D2. 範囲と期間は定型の文で固定し、記録の読み手が文字列で照合する

委任の記録の書式（1 行目と 2〜4 行目は spec に書いた文字列ちょうど）:

```
主の委任: リスク許容
エピック: #<E>
範囲: このエピックの子が pr-review-gate で求めるリスク許容のうち、子の停止の記録の推奨が「許容する」のもの。聖域の変更・破壊的な操作・マージの承認・不許容は含まない
期間: この記録への主の確認の発言から、このエピックに `主の委任:` で始まる次のコメントが付くか、エピックが閉じるまで
きっかけ: <主が任せる旨を述べた発言の全文。無ければ なし>
```

- **誰の発言か**: 主の会話ログの確認の行（9 条件）で確かめる。記録のコメントの投稿者は `OWNER`・`MEMBER`・`COLLABORATOR` を求めるが、主本人の証拠には使わない（取り違えの防止）
- **どの子か**: そのエピックの子だけ（エピックの sub-issue か本文の子の表に記録先の番号がある）。別のエピックの子には効かない
- **どの止まりか**: 委任の確認より後に作られた停止の記録で、記録先の PR が pr-review-gate の `主のリスク許容が必要` で止まり、停止の記録の `推奨:` が `許容` で始まるもの
- **期間**: 確認の発言から、エピックに `主の委任:` で始まる次のコメント（取り消し `主の委任: 取り消し` か、新しい委任の記録）が付くか、エピックが閉じるまで。固定の時間の上限は置かない（エピックの長さはまちまちで、上限で切れると止まるたびに打ち直す今の状態に戻る。代わりに取り消しをいつでも効くようにする）
- **取り消し**: 主が親のタブで取り消しを述べたら、親はエピックに 1 行目 `主の委任: 取り消し` のコメントを投稿する。主が GitHub で直接投稿してもよい。取り消しは範囲を狭める向きにしか働かないので、投稿者がエージェントでもよい（主本人の確認を求めない）
- **記録の改ざん**: 委任の記録が確認のあとに編集されていたら（GraphQL の `lastEditedAt` が null でない）使わない。範囲を変えたいときは新しい記録を出して確認を取り直す

### D3. `owner-reply-check.sh` はローカルの会話ログだけを見る

`--delegated` は会話ログの確認だけを持ち、GitHub は読まない（既存の 3 つの使い方と同じく、オフラインで決定的にテストできる形を保つ）。記録の書式・投稿者・最新か・編集の有無・エピックが開いているか・子の所属・停止の記録の推奨は、子の本体と G が `gh api` で確かめる。

確かめる順と理由（すべて `--relayed` の同名の理由と同じ意味に揃える）:

| 順 | 確かめること | 落ちたとき |
|---|---|---|
| 1 | 引数がちょうど 5 個、ID と uuid が UUID の形、2 つの作成日時が読める、URL が `https://` で始まる | exit 2 |
| 2 | uuid の行がある | `not-found` |
| 3 | その行が主の発言の 9 条件を満たす | `not-owner` |
| 4 | その行が委任の記録の作成日時より後 | `not-after` |
| 5 | 委任の記録の作成日時より後でその行より前の親の発言に、委任の記録の URL がある（URL の境界の判定は `--relayed` と同じ） | `not-asked` |
| 6 | URL を書いた最後の親の発言とその行のあいだに別の主の発言が無い | `not-direct` |
| 7 | その行が停止の記録の作成日時より前 | `not-before` |

受け入れ条件の 2 つ目（委任より前に別の子だけを名指しした許容）は、4 の `not-after`（委任の記録より前の発言）で落ちる。`--relayed` に同じ uuid を渡しても、今どおり `not-after`（停止の記録より前）で落ちる。

### D4. 親の返事は既存の `reply --as owner` に新しい添え書きを付けて送る

送る文は `許容する（主の委任による。停止の記録: <停止の記録の URL>） [主の委任: セッション <親のセッション ID> / uuid <確認の uuid> / 記録 <委任の記録の URL>]`。`reply --as owner` が頭 `主の返事（親エピック #<E> 経由）: ` を付けるので、子の会話ログのこの行は既存の 9 つ目の条件で主の発言として数えない。`epic-dispatch.sh` は変えない。子は末尾の添え書きが `[主の発言: …]` か `[主の委任: …]` かで経路を分ける。

採らなかった案: 新しい頭（例 `主の委任（親エピック #`）を足す。9 つ目の条件と `epic-dispatch.sh` の両方を直すことになり、得るものが無い。

親は委任で送ったら、エピックに `主の委任で送った: 子 #<N> <停止の記録の URL>` の 1 行を残す（`親の判断:` で始めない。`stop-judge.sh` と手順 8 の `親の判断:` の照合に混ざらないため）。

### D5. ゲートの記録は `主の回答: 許容` の頭を保ち、委任の形を足す

```
主の回答: 許容 — 親経由で受領（委任）（親セッション <ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <確認の発言の全文>
```

行頭を `主の回答: 許容` のまま保ち、手順 3-c の「前の宣言の選び方」が拾えるようにする。`--relayed` の形の確認 4（主の発言が宣言コメントより後）は委任では成り立たないので、代わりに「停止の記録が宣言コメントより後」を確かめる（子がこの宣言で止まったことの裏付け）。引き継ぎ（3-c）では、`--delegated` を元の値で回し直し、委任がまだ有効か（最新の `主の委任:` が同じ記録・エピックが開いている・記録が未編集）を確かめ直す。取り消し後の引き継ぎは通さない。

## Risks / Trade-offs

- [親が委任の記録を出して確認を求めるとき、主が中身を読まずに「はい」と答える] → 記録の範囲は定型で狭く（子の推奨が許容のリスク許容だけ）、主の確認の問いにも範囲の文を本文で書かせる
- [委任中に、子の推奨が「許容」に偏る（子が自分の推奨で自分を通す）] → 推奨は停止の記録にあり主は後から読める。親はエピックに送った件を 1 行ずつ残し、主はいつでも `主の委任: 取り消し` で止められる。子の推奨を検証する仕組みはこの変更では足さない
- [期間に時間の上限が無い] → 取り消しと、エピックが閉じたら切れることで代える。長く開いたエピックでは主が取り消しを忘れうる
- [GitHub の確認を子と G が手で行う（スクリプトにしない）] → 手順の文と bats の文面検査で固定する。誤っても通さない側に倒れる項目（最新か・未編集か・開いているか）だけで構成する
- [実装の編集対象が 5 ファイルを超える（スクリプト・参照 4 つ・bats 3 つ・変更の記録）] → 1 つの設計判断に従う一連の文の追加で、分けると半端な状態（スクリプトだけあって誰も呼ばない）が main に入る。1 change・1 PR で通す
