# Design

## Context

動機は proposal.md の Why を参照。

レビュー後の指摘は 2 つの表を通る。全周共通の判定で止める指摘は「止める指摘の仕分け表」（順 1〜6）、それ以外は「止めない指摘の振り分け表」（段 A〜E）。この変更が動かすのは順 4 と段 A の 2 か所で、どちらも `stages/triage.md` にある。

止める判定の根拠は 3 つある: 記録先の受け入れ条件、PR が触れる openspec spec、例外 3 種。順 2 は受け入れ条件と delta spec の引用を受け取るので、順 4 に届く止める指摘は「例外 3 種」か「PR が触れる spec のうち delta spec でないものの引用」のどちらかになる。

「順 4」「今直す 3 条件」の語は spec・bats・`worker/implement.md`・`gate-runner.md` の複数の場所から参照されている。

## Goals / Non-Goals

**Goals:**

- 範囲外の直しを今の PR に入れる入口を、例外 3 種だけに絞る
- 順番号と段の呼び方、`needs-fix-check` などの周の扱いを変えない

**Non-Goals:**

- レビュアーが見る範囲を狭めること（#1389 の「やらないこと」）
- 作業の途中で受け入れ条件が足される経路への対処（#1390）
- 順 3（一覧の一致で閉じる）の条件の変更。順 3 はこの PR の変更の取りこぼしを閉じる型で、issue の触る範囲に入っていない
- PR #1002 の振り分け表の穴（#1011〜#1016）、段 A だけの原因分類の列挙（#1014）、段 A と順 3 の混在の読み方（#1015）
- `agents/reviewer.md`・`agents/gate-runner.md`・`roles/gate-runner.md` の変更。どれも `stages/` の手順を指すだけで、語を再掲していないので直す文が無い

## Decisions

### 順 4 は消さず、根拠が例外 3 種の指摘に限る

順 4 の行を残し、条件に「根拠が例外 3 種」を足す。「今直す 3 条件」の語はそのまま使う。

- 消す案は採らない。消すと、例外 3 種の小さな直しまで毎回順 5 で主に聞くことになる。順番号の振り直しも hold.md・pass.md・spec・bats に波及する
- 順 4 から外れるのは「PR が触れる spec を引用した、受け入れ条件でも delta spec でもない止める指摘」で、これは順 5 に行く。止める判定を変えて止めない指摘に落とす案は、全周共通の判定を動かすので採らない。主に聞く回数は増えるが、当たるのは delta spec の外の spec に PR が触れたときだけに限られる

### 段 A は記録先の受け入れ条件だけを見る

順 2 は delta spec の引用も「受け入れ条件の中」に数えるが、段 A の問いは issue の受け入れ条件の文どおり記録先の受け入れ条件に限る。delta spec の文に確かに反する指摘は `blocking` かつ `confirmed` になって順 2 で止まるので、段 A に残るのは裏取りのない指摘だけで、段 B 以降で追跡できる。

### 段 A の例外 3 種には行数の上限を付けない

止める指摘の順 4 には 30 行の上限があり、超えると主に聞く。段 A にはこの上限を足さない。

- 振り分け表の要件は「件数や行数の上限は置かない」と定めている
- 段 A で W に戻せるのは 1 周目だけで、直した差分はレビューの周を通る
- 上限を足す案（今直す 3 条件を段 A にも当てる）は、段 A の直しも累計に数える記録が `worker/implement.md` まで広がるので採らない

### 新しい部品・機能の提案は「受け入れ条件が求めていないもの」に限る

issue の文は「新しい部品や機能を足す提案は、行数によらず範囲外」。受け入れ条件そのものが求める部品は提案ではないので、「受け入れ条件が求めていない」を明記する。例外 3 種に当たれば、部品を足す直しも段 A・順 4 の条件で直せる。

### 印は参考にとどめ、機械照合しない

`受け入れ条件の要否` は深刻度と同じ扱いにし、判定は G が受け入れ条件の文と照らして行う。レビュアーは PR を落とす側なので印が甘くも辛くも振れる。印が無いことを補足の理由にしないのは、補足が 1 回分のレビューの費用を使い、この変更の目的に反するため。欄の名前に `受け入れ条件の要否` を選んだのは、`根拠` の欄の引用（止める判定の材料）と役割を分けるため。

## Risks / Trade-offs

- [レビュアーが要らない指摘を省いて、範囲外の安全の穴を見落とす] → 指示ブロックに「`要らない` の指摘も省かない」と書き、例外 3 種の指摘は根拠の欄に書かせる
- [`要らない` にした指摘が段 B・段 E で捨てられ、直されないまま残る] → 段 B〜E は今のまま理由か URL を PR コメントに残す。捨てる判断の基準は変えない
- [段 A の例外 3 種の指摘が裏取りのないまま大きな直しになる] → 1 周目だけに限られ、差分はレビューされる。実例が出たら条件の追加を別 issue で検討する
- [#1436 の分割と衝突する] → どちらが先に入っても、あとから入る側が移動先のファイルへ同じ文を移す

## Migration Plan

手順書の文の変更だけで、データの移行は無い。マージ後に開くレビューから効く。戻すときは PR を revert する。
