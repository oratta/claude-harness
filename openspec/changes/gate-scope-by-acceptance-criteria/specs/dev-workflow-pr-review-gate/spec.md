## ADDED Requirements

### Requirement: レビュアーに受け入れ条件を渡し、指摘ごとに要否の印を付けさせる

`stages/reviewer-brief.md` は、レビュアーを起こす側が記録先の受け入れ条件の全文を依頼文に入れることを、区画の有無によらず書かなければならない（MUST）。レビュアー向け指示ブロックは、指摘 1 件ごとに `受け入れ条件の要否` の欄を書かせなければならない（MUST）。値は `要る: <受け入れ条件 ID>`（直さないとその受け入れ条件を満たせない）か `要らない`（直さなくても受け入れ条件をすべて満たせる）のどちらかとする（MUST）。受け入れ条件が求めていない新しい部品・機能を足す提案は、行数によらず `要らない` とする（MUST）。

印はレビュアーが見る範囲を狭めてはならない（MUST NOT）。レビュアーは `要らない` の指摘も省かず、1 周目は該当する指摘を全部列挙する（MUST）。例外 3 種に当たる指摘も、受け入れ条件に要らなければ `要らない` と書き、例外 3 種に当たることは根拠の欄に書く（MUST）。

#### Scenario: 依頼文に受け入れ条件の全文が入る

- **WHEN** レビュアーを起こす側が、区画の無い PR のレビューの指示を `stages/reviewer-brief.md` に沿って組み立てる
- **THEN** 依頼文には記録先の受け入れ条件の全文が入っている

#### Scenario: 要らない指摘も列挙される

- **WHEN** 1 周目のレビュアーが、受け入れ条件には要らないが直す価値のある `should` を見つける
- **THEN** レビュアーはその指摘を省かず、`受け入れ条件の要否: 要らない` を付けて返す

### Requirement: 受け入れ条件の要否の印は参考にとどめ、判定は G が照合する

印は深刻度ラベルと同じく参考にとどめ、判定の根拠は G の照合とする（MUST）。G は `要る` の指摘でも、受け入れ条件の文と照合して要ると読めなければ要らないものとして扱い、`要らない` の指摘でも、文から要ると読めれば要るものとして扱う（MUST）。印が無い指摘は G が受け入れ条件の全文と照らして決め、印の欠落を理由に補足を頼んではならず、一周目の三表の機械照合の対象にも足してはならない（MUST NOT）。印はマージを止めるかの判定（全周共通）を変えてはならない（MUST NOT）。

Codex が優先度付きの形で返したときの読み替え表は、`受け入れ条件の要否` に対応する欄が Codex の出力に無いこと、書式ブロックを貼った指示文で書かせること、欠けていれば G が決めることを書かなければならない（MUST）。

#### Scenario: 印と受け入れ条件の文が食い違う

- **WHEN** レビュアーが `要る: AC2` と付けた止めない指摘について、G が AC2 の文を読むと、直さなくても AC2 を満たせる
- **THEN** G はその指摘を受け入れ条件に要らないものとして扱い、段 A の例外 3 種に当たらなければ段 B から当てる

#### Scenario: 印が無い指摘

- **WHEN** Codex の出力の指摘に `受け入れ条件の要否` の欄が無く、三表は揃っている
- **THEN** G は補足を頼まず、受け入れ条件の全文と照らして要否を決めて仕分けを進める

`skills/pr-review-gate/stages/triage.md` は、2 周目以降の周の終わりに止める指摘が残ったとき、G が直し方の判定に回す条件と手順を書かなければならない（MUST）。判定役・「直し方が決まっている」の定義・判定の記録と事後報告の書式は `dev-workflow-develop` の「レビューの 2 周目以降の周の終わりは直し方の判定を通して続ける」Requirement の正本（`skills/develop/references/fix-check.md` の節「レビューの周を主に聞かずに続ける（直し方の判定）」）を指し、再掲してはならない（MUST NOT）。

**直し方の判定は順 6 の回数に数えない**: 判定の記録（1 行目 `直し方の判定:`）は順 6 の裁定の回数を数える正規表現に一致せず、順 6 の回数に数えてはならない（MUST NOT）。G は直し方の判定を受け取っても `決める役の裁定:` の PR コメントを残してはならない（MUST NOT）。直し方の判定で開いた周があっても、順 6 の「PR ごとに 1 回まで」は使われていないものとして扱う（MUST）。

**回し方**: G は判定に回す指摘ごとに「仮の順」（1 周目なら当たる順 2〜4 のどれか）と根拠を仕分けの PR コメントに記録し、Status `needs-fix-check`・`次の段: 照合と振り分け` で return する（MUST）。G は決める役を起こせず、判定の記録も投稿しない（MUST NOT。本体が起こし、本体が記録先に投稿する）。

**判定を受け取った G**: 本体から判定と判定の記録の URL を渡されて起こされた照合と振り分けの G は、URL を仕分け欄に書く（MUST）。判定が「決まっている」なら、仮の順どおりに順 2〜4 の扱いで指摘を W に戻し（`agent-review:failed`。順 3 なら一覧、順 4 なら今直す記録）、次の周に入る（MUST。`needs-approval` を付けない）。判定が「選び直しが要る」なら、それらの指摘を順 5 に当てて主に聞く（MUST）。

**順 6 と混ざったとき**: 同じ周に判定に回す指摘と、この PR でまだ裁定を受けていない（上の数え方で 0 件）順 6 の指摘があれば、直し方の判定を先にする（MUST）。G は全件の仕分けを PR コメントに記録し、順 6 の指摘を仕分け欄に「順 6・未裁定」として載せて `needs-fix-check` で return する。判定が「決まっている」なら、照合と振り分けの G は `agent-review:failed` を付けずに Status `needs-decider` で return し、順 6 の裁定が済んでから、判定に回した指摘と順 6 の指摘をまとめて 1 回の `agent-review:failed` で W に戻す（MUST。裁定が「切り出す」なら、順 6 の指摘について順 5 と同じ経路で主に聞き、その回答まで W はどの指摘の修正にも着手しない）。判定が「選び直しが要る」なら、判定に回した指摘は順 5 になり、「順 5 と順 6 が同じ周に混ざったときの処理順」Requirement に従う（MUST）。直し方の判定と順 6 の裁定を 1 回の決める役への依頼にまとめてはならない（MUST NOT。順 6 の依頼と数え方を変えないため）。

決める役（`dev-workflow:decider`）が PR のレビューで裁定するのは、順 6 の方式と、この直し方の判定の 2 つだけとする（MUST）。止めるかどうかは全周共通の判定で G が決める（MUST）。

この判定の守備範囲は、周の終わりに残った止める指摘のうち、1 周目なら G が主に聞かずに W に戻していた種類（順 2〜4）を、周の数だけを理由に主へ上げないようにすることである。拾いたいのは、直し方が 1 つに決まらない指摘・記録先の範囲を変える指摘・前の周で決まっているとした直し方で閉じなかった指摘で、これらは主に上げる。1 周目でも主に聞く指摘（順 5）と同じ型の再発（順 6）は判定の対象外で、従来の経路を通る。判定が「決まっている」とした直し方が外れることは防がない（次の周の終わりの判定と順 6 で拾う）ので、判定の誤りが 1 件も無いことをこの手順の完了条件にしない。

#### Scenario: 順 2〜4 に当たる指摘だけが残る
- **WHEN** 2 周目の終わりに、受け入れ条件を引用した止める指摘と、一覧の一致で閉じられる型の止める指摘が 1 件ずつ残り、どちらも前の周と同じ型ではない
- **THEN** G は仮の順 2 と仮の順 3 を仕分けの PR コメントに記録し、`needs-fix-check` で return する

#### Scenario: 判定が決まっているなら仮の順で W に戻す
- **WHEN** 照合と振り分けの G が、直し方の判定「決まっている」と判定の記録の URL を受け取る
- **THEN** G は URL を仕分け欄に書き、仮の順 3 の指摘には一覧を作らせる形で、1 回の `agent-review:failed` で W に戻す

#### Scenario: 順 6 と混ざる
- **WHEN** この PR でまだ順 6 の裁定を受けておらず（`決める役の裁定:` の PR コメントが 0 件）、2 周目の終わりに、前の周と同じ型の再発の指摘 1 件と、仮の順 2 に当たる指摘 1 件が残る
- **THEN** G は再発を「順 6・未裁定」として載せて `needs-fix-check` で return し、判定が「決まっている」なら次の G が `needs-decider` で return し、裁定のあと 1 回の `agent-review:failed` で両方を W に戻す

#### Scenario: 順 6 の裁定を使い切った PR で混ざる
- **WHEN** 1 行目が `決める役の裁定: 全部列挙してから直す` の PR コメントが 1 件ある PR で、周の終わりに、前の周と同じ型の再発の指摘 1 件と、受け入れ条件を引用した止める指摘 1 件が残る
- **THEN** G は直し方の判定に回さず（`needs-fix-check` も `needs-decider` も返さない）、再発の指摘を「切り出す」として、受け入れ条件を引用した指摘とあわせて順 5 に当て、`needs-approval` を付けて 1 回の保留で主に聞く

#### Scenario: 直し方の判定は順 6 の回数に数えない
- **WHEN** 1 行目が `直し方の判定: 決まっている` の記録先コメントが 1 件あり、`決める役の裁定:` の PR コメントが 0 件の PR で、周の終わりに同じ型の再発の指摘が残る
- **THEN** G は裁定の回数を 0 件と数え、その指摘を順 6 に当てて決める役の裁定を求める（「切り出す」として扱わない）

#### Scenario: triage.md が書式を再掲しない
- **WHEN** `skills/pr-review-gate/stages/triage.md` を読む
- **THEN** 直し方の判定に回す条件と `needs-fix-check` の return が書かれ、判定の記録と事後報告の書式は `skills/develop/references/fix-check.md` の節を指していて、`^直し方の判定:` と `^主に聞かずに回した周:` の書式の定義は無い

### Requirement: 止めない指摘は振り分け表に上から当てる

`stages/triage.md` は、手順 2-1 に「止めない指摘の振り分け表」を 1 か所だけ置かなければならない（MUST）。対象は、全周共通の判定でマージを止めない指摘とする（MUST）。段 A は G が指摘を受け取った時点で当て、段 B 以降は W がその周で直さなかったものに、G が手順 3 へ進む時点で当てる（MUST）。表は次の 5 つの段をこの順番で持ち、G は上から当てる（MUST）:

| 段 | 問い | 当たったときの行き先 |
|---|---|---|
| A | 直さないと受け入れ条件を満たせないか、または例外 3 種に当たるか。当たる | この PR で直す |
| B | 「こういう条件だと、こうなる」の条件を書けるか、その条件がいつ成り立つか | 「段 B は条件がいつ成り立つかで分ける」Requirement の表 |
| C | エピックの完了条件に効くか。効く | 「エピックの完了条件に効く指摘は既存 issue との関係で分ける（段 C）」Requirement の表 |
| D | 同じ場所を直す open の issue があるか。ある | その issue に、受け入れ条件に足さない参考としてコメントで入れる |
| E | 起きる見込みと起きたときの影響が、issue 1 件を通す手間に見合うか | 見合えばエピックの外の新しい issue、見合わなければ捨てる |

段の呼び方は「段 A」〜「段 E」とし、止める指摘の仕分け表の「順 1」〜「順 6」と同じ数字の呼び方を使ってはならない（MUST NOT。hold.md・pass.md・gate-runner.md・仕様・bats が「順 5」「順 6」で止める指摘の仕分け表を指しているため）。止める指摘の仕分け表の順 1 の行き先は、この振り分け表とする（MUST）。

G は、どの段でも指摘の扱い（直すか・issue にするか・捨てるか）を主に聞いてはならない（MUST NOT）。主に聞いてよいのは、段 B で G が決められない条件だけとする（MUST）。エピックに属さない PR では段 C を飛ばす（MUST）。段 B と段 C の間で候補探しのスクリプトを走らせ、結果を段 C と段 D の両方で使う（MUST）。

指摘を捨てるとき（段 B・段 E）は、PR コメントに指摘ごとに理由を 1 行残さなければならない（MUST）。issue にする・コメントで入れると決めたときは、その issue またはコメントの URL を残す（MUST）。G は指摘ごとに当てた段と行き先を仕分けの PR コメントに記録し、return の仕分け欄にも書く（MUST）。段 A に当てた指摘には、要る受け入れ条件の ID か、当たる例外 3 種のどれかもあわせて書く（MUST）。

`stages/` の各ファイルは、止めない指摘を振り分け表に通さずに follow-up issue にすると読める文を持ってはならない（MUST NOT）。「follow-up issue」の語は、振り分け表で issue にすると決まった指摘と、主が切り出すと答えた止める指摘の issue を指すときだけ使う（MUST）。

件数や行数の上限は置かない。issue になった件数とならなかった件数は記録するだけで、合否に使ってはならない（MUST NOT）。派生が続くときに止まる別の仕組みは持たず、PR ごとの歯止め（レビューの既定 2 周・PR トークン上限）をそのまま使う（MUST）。

- **THEN** 「止めない指摘の振り分け表」が 1 つだけあり、段 A〜段 E がこの順に並び、段 B と段 C の間に候補探しのスクリプトを走らせる行がある

- **THEN** 出たどの行も、振り分け表で issue にすると決まった指摘か、主が切り出すと答えた止める指摘についての文で、止めない指摘を振り分け表に通さずに issue にすると読める行は無い

- **THEN** G は段 C を飛ばし、候補探しのスクリプトを `--epic` なしで走らせて段 D・段 E に進む

### Requirement: 段 A の直しは周の歯止めの内側だけで戻す

段 A に当たるのは、止めない指摘のうち、直さないと記録先の受け入れ条件を満たせない指摘と、例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる指摘だけとする（MUST）。どちらでもない指摘は、直す場所がこの PR の diff が触れたファイルの中でも、直し方の行数が小さくても、今の PR で直さず段 B から当てる（MUST）。受け入れ条件が求めていない新しい部品・機能を足す提案は、行数によらず範囲外とする（MUST）。範囲外の提案を今の PR で直せるのは、例外 3 種に当たるときだけとする（MUST）。

G は 1 周目に段 A に当たる指摘を受け取ったら、止める指摘の有無によらず `agent-review:failed` で W に戻し、failed の PR コメントの一覧でその指摘に「段 A・この PR で直す」と印を付けなければならない（MUST）。止める指摘（順 2〜4）と同じ周なら 1 回の `agent-review:failed` にまとめ、順 5・順 6 との混在では順 2〜4 の指摘と同じに扱う（MUST）。段 A だけで戻した failed では手順 2-2 のモデル昇格を当てず、W のモデルを据え置く（MUST。戻す中身が止めない指摘で、モデルを上げても収束の見込みは変わらないため）。failed の return の原因分類には「段 A だけ（昇格なし）」と書く（MUST）。

2 周目以降の周の終わりには、段 A に当たる指摘が残っていても、それを理由に次の周を開けてはならない（MUST NOT）。その指摘は段 A に当たらないものとして段 B から当てる（MUST）。段 B 以降は、G が手順 3 へ進む時点で、未解決の止めない指摘に当てる（MUST）。

#### Scenario: 1 周目に段 A の指摘だけが届く

- **THEN** G は `agent-review:failed` で W に戻し、failed の PR コメントにその指摘を「段 A・この PR で直す」として載せて AC1 を添え、issue は作らない

- **THEN** G は `agent-review:failed` にせず、その指摘を段 B から当てて手順 3 以降へ進む

- **WHEN** 1 周目のレビューが、受け入れ条件が求めていない補助スクリプトを 10 行で足す `should` を返し、例外 3 種に当たらない
