## Context

pr-review-gate 手順 3-c は、main の取り込みだけで HEAD が動いたときに、前の HEAD で主が許容したリスクを新しい HEAD に引き継ぐ（#441、archive `2026-09-24-pr-gate-risk-carryover`）。git から決まる条件は `risk-carryover-check.sh` が、許容の真正性とリスクの中身の同一性は G が確かめる分担になっている。

スクリプトの条件 3 は、merge commit の衝突解消したファイル（`git merge-tree --write-tree <第1親> <第2親>` の tree と実 tree で差のあるファイル）がすべて許可リスト（`.claude-plugin/marketplace.json`・`plugins/*/.claude-plugin/plugin.json` の版の行、`CHANGELOG.md` の並べ直し）に入ることを求める。#441 の design はこの許可リストを「衝突解消で誰にも見られていない変更が入るのを防ぐ」ために置いた。

ところが合格処理の G が 3-c を試す時点では、新しい HEAD で手順 1 から取り直し、手順 2 のレビューも新しい HEAD で行っている。そのレビューが PR 全体を見ていれば、衝突解消の結果（PR の base との差分に現れる）はそこで見られており、許可リストによる制限は二重になる。flatmate PR #1388 では衝突解消が `openspec/specs/client-package/spec.md` に及んだだけで exit 1 になり、宣言の本文は同一・根拠ファイル 3 件の diff は空だったのに、主は 3 回目の許容を求められた。

制約:

- 手順 2 のレビューには周の種類がある。ゲートの開始と CI の見張りのあとの取り直しは PR 全体を見る。W の修正後の再レビューは差分限定で「前回の指摘が閉じたか」だけを見て新規探索をしない（`stages/triage.md` 収束ルール）。戻した指摘が順 3 だけの周はレビューをせずに閉じ、`レビュー重量:` コメントだけを新しい `固定 HEAD:` で出し直す。つまり「固定 HEAD が新しい HEAD」だけでは、衝突解消の中身が見られた証拠にならない
- 兄弟 #721（会話での許容の返事を正式回答にする）が `stages/hold.md` を並行して触る。この change は hold.md の 3-c だけを変える
- 引き継ぎの 4 行を機械で読むワークフローは無い（auto-merge は `対象 HEAD:` と `主のリスク許容が必要。` だけを見る）。`pr-review-gate-skill.bats` が 3-c の追記行の書式を文字列で検査している

## Goals / Non-Goals

**Goals:**

- 衝突解消が許可リストの外に及んでも、新しい HEAD の取り直しのレビューが PR 全体を見ていて、根拠ファイルの diff が空で、宣言の本文が同一なら、主に聞き直さずに引き継げる
- 根拠ファイルの diff・main 以外の commit・履歴の書き換えは、今までどおり引き継げない（終了コード 1）
- 引き継ぎの根拠行から、どの取り直しのレビューに頼って引き継いだかを後から辿れる
- #478（根拠ファイルが両 HEAD に無いと無言で通る）と #480（衝突解消ファイルの列挙が rename 検出で元ファイルを落とす）を同じスクリプトの同じ箇所で直す

**Non-Goals:**

- 差分限定の再レビューの周で、レビュアーに衝突解消したファイルを追加で見させること（`reviewer-brief.md` や `triage.md` の変更）。その周に main を取り込んだ場合は今までどおり主に聞く
- 許可リストそのものの拡張や、リポごとの設定
- 3-c の条件 2〜4（根拠ファイル行の有無・真正性・本文の同一性）と前の宣言の選び方の変更
- hold.md の 3-c 以外の節（手順 6 の保留処理・復帰の表）の変更

## Decisions

### 終了コードを 0 / 3 / 1 / 2 に分ける

| 終了コード | `CARRYOVER=` | 意味 |
|---|---|---|
| 0 | `yes` | 衝突解消がすべて許可リストの条件を満たす（または衝突解消なし）。今までと同じ |
| 3 | `if-rereviewed` | `NG:` は無いが、許可リストの条件を満たさない衝突解消がある。取り直しのレビューが PR 全体を見ていれば引き継げる |
| 1 | `no` | `NG:` が 1 行以上ある（前の HEAD が祖先でない・main 以外の commit・3 親以上の merge・base の外の merge・第 1 親が PR の履歴の外・根拠ファイルの diff）。許可リストの条件を満たさない衝突解消が同時にあっても 1 |
| 2 | （出さない） | 引数不足・SHA が解決できない・根拠ファイルが無い・根拠ファイルが前後どちらの HEAD にも無い・git が古い |

`NG:` を優先するのは、根拠ファイルの diff や main 以外の commit はレビューの有無で補えない誤りだから。

代替案「許可リスト外の衝突解消は 0 にして、取り直しレビューの確認を 3-c の文面だけに任せる」は採らない。スクリプトの出力だけを見た G が「0 なら無条件で可」と読む今の手順と区別が付かず、取り直しのレビューの確認を飛ばしても気付けない。終了コードで分ければ、3-c の条件 1 が「3 なら追加の確認が要る」と機械的に分岐でき、bats でも区別を検査できる。

代替案「新しいフラグ（例 `--rereviewed`）を渡すと許可リスト外を 0 にする」は採らない。取り直しのレビューが全体を見たかはスクリプトに分からず、G が自己申告でフラグを付けるだけになる。判定の材料は G 側にあるので、スクリプトは事実を出し、G が 3-c で確かめる分担を保つ。

### 「許可リストの条件を満たさない」は名前の外と中身の違反をまとめる

`RESOLVED_OUTSIDE_ALLOWLIST=<ファイル>` に出すのは、今のスクリプトで `allowed` が偽になる衝突解消すべて、すなわち (a) 許可リストに無いファイル、(b) 許可リストの JSON で `"version"` 行以外を変えたもの、(c) CHANGELOG に第 1 親・第 2 親のどちらにも無い行を足したもの、(d) 衝突していないファイルへの手入れ、とする。

(b)〜(d) だけを 1 のまま残すと、「任意のファイルの任意の解消」は 3 で通るのに「版の行以外の 1 行の変更」は 1 で止まる、という逆転が起きる。どれも merge commit の中身が自動マージと違うという同じ性質で、PR の base との差分に現れて全体レビューで見られる点も同じなので、同じ扱いにする。出力の名前は issue の例をそのまま使い、意味（ファイル名と中身の両方の条件）を spec とスクリプトの冒頭コメントに書く。

出力はファイルごとに 1 行（`RESOLVED_OUTSIDE_ALLOWLIST=<ファイル>`、重複は除く）。`RESOLVED_FILES=` は今までどおり全件をカンマ区切りで出す。

### 3-c で G が確かめる「取り直しのレビューが PR 全体を見た」

終了コード 3 のときは、3-c の条件 1 を次で満たす:

1. 最新の `レビュー重量:` コメントの `固定 HEAD:` が新しい HEAD の 40 桁 SHA と一致する
2. その周が PR 全体を見たレビューである。PR 全体を見た周は、ゲートの開始（一周目）・CI の見張りのあとの取り直し・方式の書き換え後の全体レビューの 3 つ。W の修正後の差分限定の再レビューと、戻した指摘が順 3 だけでレビューをせずに閉じた周は当たらない
3. G が 2 を確かめられないとき（周の種類が前の段の Gate Result と PR の仕分けコメントから読めないとき）は、引き継げない側に倒して手順 6 で主に聞く

1 だけにしない理由は Context の制約のとおり。順 3 だけの周も差分限定の周も `固定 HEAD:` は新しい HEAD になるが、衝突解消の中身は見ていない。

代替案「レビュアーのハンク被覆に `RESOLVED_OUTSIDE_ALLOWLIST` のファイルが入っているかを確かめる」は採らない。合格処理の G はレビューの三表を持たず（`レビュー三表:` コメントは補足を頼んだときにしか投稿されない）、確かめる材料が PR に残らない。周の種類なら前の段の Gate Result と仕分けコメントから読める。

### 引き継ぎの根拠行の書式

追記 4 行の 3 行目を次に直す（4 行のままにする）:

```
引き継ぎの根拠: risk-carryover-check.sh 終了コード <0 または 3> — main の取り込み <件数> 件、衝突解消 <none またはファイル>、許可リスト外 <none またはファイル>、根拠ファイルの diff は空、取り直しのレビュー <終了コード 3 のとき: 固定 HEAD <新しい HEAD の 40 桁フル SHA>（<周の種類>） <その `レビュー重量:` コメントのリンク>。終了コード 0 のとき: 不要>
```

終了コード 3 のときに、頼ったレビューの固定 HEAD・周の種類・コメントのリンクを残し、後から「どのレビューが衝突解消を見たことにして引き継いだか」を辿れるようにする。行頭 `引き継ぎの根拠: risk-carryover-check.sh 終了コード ` は保ち、pass.md の合格条件の表（4 行が揃っているかを見る）は変えない。

### #478 と #480 を同じ change で直す

- #478: 根拠ファイルごとに `git cat-file -e <前>:<f>` か `git cat-file -e <新>:<f>` のどちらかが通ることを確かめ、どちらにも無ければ stderr に理由を出して終了コード 2。SHA の解決の前に `cd "$(git rev-parse --show-toplevel)"` して pathspec をルート相対に固定する（`git diff -- <pathspec>` は cwd 相対、`git show <rev>:<path>` はルート相対で扱いが違うため）
- #480: 衝突解消ファイルの列挙を `git diff --no-renames --name-only` にする。#480 の受け入れ条件 2 は「削除が列挙される（NG になる）」だったが、この change のあとは許可リスト外の衝突解消は NG ではなく `RESOLVED_OUTSIDE_ALLOWLIST=` に出るので、bats は「削除したファイルが `RESOLVED_OUTSIDE_ALLOWLIST=` に出て終了コード 3」で確かめる

同じ Requirement（スクリプトの判定）を 2 つの change が並行して MODIFIED にすると archive で衝突するので、1 つの change にまとめる。どちらも triage 済みの受け入れ条件がある機械的な追加で、新しい設計判断を持ち込まない。

## Risks / Trade-offs

- [全体レビューが衝突解消の中身を見落とす] → 取り直しの全体レビューは base との差分を全ハンク被覆で読むので、衝突解消の結果はハンクとして必ず読まれる。見落としはレビュー一般の見落としと同じで、許可リストで塞いでいた範囲がレビューの精度に移る。根拠ファイルの diff と宣言本文の同一性は今までどおり機械と文の一致で確かめる
- [差分限定の周で main を取り込むと、今までどおり主に聞く] → この change の Non-Goal。flatmate #1388 のような「合格処理の取り直しで main を取り込む」経路は全体レビューの周なので救える。差分限定の周で頻発するなら、レビュアーに衝突解消ファイルを渡す follow-up を切る
- [G が周の種類を読み違えて 3 を引き継ぐ] → 根拠行に周の種類とコメントのリンクを書かせ、読み違いを後から検査できるようにする。読めないときは引き継がない側に倒す（fail-closed）
- [兄弟 #721 との hold.md の衝突] → 3-c の条件 1・スクリプトの出力の説明・根拠行の書式の 3 か所だけを変え、手順 6 と復帰の表に触れない
- [出力名 `RESOLVED_OUTSIDE_ALLOWLIST` が中身の違反（許可リスト内のファイル）も含む] → spec とスクリプト冒頭のコメントで「許可リストの条件（ファイル名と中身）を満たさない」と定義する。名前を変えるより、issue の例と揃えて辿りやすさを取る

## Open Questions

- 周の種類を G が読む場所: 前の段の Gate Result の `段:` と、PR の仕分けコメント・`レビュー重量:` コメント（方式の書き換え後の全体レビューは 2 つの行数のコメントが残る）で足りると見ているが、取り直し（CI の見張りのあと）の周がそれと分かる記録が PR に残るかを実装時に `stages/prepare.md` と `stages/pass.md` で確かめる。残らない場合は 3-c の確認 3（読めなければ引き継がない）に倒れるだけで安全側だが、救えるケースが減る。その場合は R1 に報告して扱いを決める
