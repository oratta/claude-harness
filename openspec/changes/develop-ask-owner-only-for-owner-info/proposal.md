## Why

2026-10-01〜10-14 の子セッションの停止 88 件のうち 13 件は、子が自分で決められることを主に聞いて止まっていた（issue #1035）。10/8 以降も残っているのは 4 つの型で、どれも主の側にしか無い情報は要らなかった。

| 型 | 例 | 聞くことを選ばせた規則 |
|---|---|---|
| 自分（ゲート担当を含む）の誤りの後始末を聞く | claude-harness #977：ゲート担当が実ホームの `~/.claude/accounts.json` に誤って書き足した `z` の 1 件を消してよいか、いつ実行するかを聞いた | `rules/perspective-casting.md` 手順 1 の「破壊的操作は無条件で人間承認」「回復コストが判定できない操作は回復不能側に倒す」に、自分側の誤りを戻す操作の扱いが無い。develop の SKILL.md にも後始末の規則が無い。聞き方は `destructive-git-guard.md` の「いつ・どうやって」まで確かめる形を git 以外に持ち込んでいた |
| 範囲外の問題を issue にするかを聞く | claude-harness #709（10/9）。#985（10/13 マージ）のあとも flatmate #1104 の本体（10/14）が「起票するかはオーナーが決める」「それでよければ起票します」と聞いた | `skills/pr-review-gate/stages/triage.md` の振り分け（段 A〜E）は G がレビュー指摘に当てるときだけ効く。本体が作業中に見つけた問題や、仕分けの結果を本体がまとめ直すときの規則が develop に無い |
| 頻度・影響がほぼゼロの実装の選択を聞く | flatmate #1564（10/14）：仕様レビューの BLOCKER を閉じるテストの方式 A/B | SKILL.md「レビューの周を主に聞かずに続ける（直し方の判定）」の定義①「直し方が 1 つに決まる（設計の選択肢から選ぶ必要が無い）」が、どれを選んでも受け入れ条件も利用者に見える振る舞いも変わらない選択肢まで「選び直しが要る」＝主に聞く側に入れる |
| 受け入れ条件を満たしたのに閉じる操作を主に渡す | claude-harness #693（10/7）：調査だけの issue で「推奨どおりでよければ `gh issue close` で閉じてください」 | SKILL.md「ループの終わり」が PR のマージで閉じる記録先しか想定しておらず、PR を伴わない記録先を誰が閉じるかが書かれていない |

## What Changes

- develop の SKILL.md に節「主に聞かずに決めること」を足す。主に聞くのは主の側にしか無い情報（好み・事業判断・許容度・主の手でしかできない操作・規則が承認を求める操作）が要るときだけとし、4 つの型それぞれの決め方を書く
  - 自分側の誤りの後始末: 戻し先が差分から一意に決まるなら、戻す前の状態の控えを取って戻し、記録先に事後報告する。git の破壊的操作（`destructive-git-guard.md` の一覧）は対象外で、事前承認のまま
  - 範囲外の問題の起票: 本体も `triage.md` の振り分け表（段 B〜E）を当てて自分で決め、起票したら事後報告する。可否を主に聞かない
  - 小さな実装の選択: どれを選んでも受け入れ条件と利用者に見える振る舞いが変わらない選択肢は、担い手が選んで理由を記録先に残す
  - 閉じる操作: 節「ループの終わり」に従う
- SKILL.md「レビューの周を主に聞かずに続ける（直し方の判定）」の定義①を、「直し方が 1 つに決まる、または選択肢の違いが受け入れ条件と利用者に見える振る舞いを変えず決める役が 1 つを選べる」に広げ、守備範囲の段落の「拾いたい指摘」を主の側の情報が要る選択に絞る
- SKILL.md「ループの終わり」に、PR を伴わない記録先 issue（調査だけの issue など）で受け入れ条件を満たしたら本体が閉じることと、閉じたあとにワークスペースの印を付けることを足す
- `rules/perspective-casting.md` 手順 1 と、その正本の `plugins/casting/skills/casting/SKILL.md` 手順 1 に、自分側が入れた誤りで戻し先が一意に決まるものを戻す操作は回復可能な操作として扱う（git の破壊的操作は除く）一文を足す
- `rules/destructive-git-guard.md` は変えない
