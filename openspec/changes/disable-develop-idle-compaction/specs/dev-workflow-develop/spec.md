# Spec Delta

## ADDED Requirements

### Requirement: develop の開始はセッションの役割によらず idle compaction を切る
Claude Code で develop を開始する本体は、役割別工程や返事待ちより前に、現在の worktree の `.claude/settings.local.json` の idleCompaction を boolean false にしなければならない（MUST）。親・子・単発、interactive・unmanned によってこの方針を分岐しない。ホームの settings.json・共有設定・通常の自動 compact を止める設定は変えてはならない（MUST NOT）。子の既存の起動オプションは維持する。委譲先 Codex worker に Claude の実設定を変更させない。

#### Scenario: 親と子と単発で同じ入口を使う
- **WHEN** 親エピック、別セッションの子、単発 interactive のそれぞれで develop を開始する
- **THEN** SKILL.md の同じ入口で local 設定を確認・適用し、親か子かの判定で適用を省略しない
- **AND** 新セッションでの引き継ぎや compact 後の再読でも同じ確認を行い、既に false なら何も書かない

#### Scenario: 通常の自動 compact の指定を維持する
- **WHEN** 開始時の設定・子の起動コマンドの差分を調べる
- **THEN** DISABLE_AUTO_COMPACT など通常の自動 compact を止める指定を追加せず、既存の compact 後の手順書再読み込み hook を残す

### Requirement: idle compaction の設定操作は既存設定と承認規則を保つ
設定部品は check と apply を分け、idleCompaction 以外の値を保持し、false 済みは無変更としなければならない（MUST）。PR 本文とリスク宣言に継続適用の範囲を明記し、主のマージ承認（リスク宣言の許容）をその範囲への一度の承認として記録する（MUST）。承認後の develop 開始では worktree ごとに操作承認を確認・質問してはならない（MUST NOT）。承認前の実設定変更や権限・hooks による迂回はせず、他キー・別ファイル・symlink 先は従来の聖域承認を要する（MUST）。他セッションへの持続・自動復元しないこと・戻し方も案内する。

#### Scenario: 他キーを保持し false 済みを変更しない
- **WHEN** permissions、hooks、任意の未知キーを持つ正常な設定に apply する
- **THEN** idleCompaction だけが false となり、他キーの値が保存される
- **AND** 再適用では内容と mtime が変わらず、ホームや共有設定に書き込みが無い

#### Scenario: 一度承認した仕組みを新しい worktree でも質問せず適用する
- **WHEN** 主が上記の継続適用の範囲を記した PR のマージを承認し、リスク宣言を許容した仕組みで、新しい worktree の develop を開始する
- **THEN** check が exit 2 なら本体は当該キーだけの apply を行い、対象 worktree ごとの承認確認や追加質問を行わない
- **AND** PR 本文とリスク宣言の両方に「develop 開始時、現在の worktree の `.claude/settings.local.json` の idleCompaction だけを false にする。他の設定値は保持し、ホーム・共有設定には書かない」と記し、新しい worktree・新セッション・interactive / unmanned にも継続適用する範囲を含める
- **AND** R1 の APPROVE やエージェントの投稿だけを主の承認と読み替えない

#### Scenario: 新規ファイルも一度の承認の範囲で作る
- **WHEN** 継続適用を承認された仕組みで develop を開始し、local 設定が無い
- **THEN** apply は idleCompaction false だけの JSON object を作り、共有設定やユーザー設定を複製しない

#### Scenario: 継続適用の範囲外には従来の承認を残す
- **WHEN** 他キー・別ファイル・symlink 先への書き込みが必要になる
- **THEN** この PR の承認を流用せず従来の聖域承認を求め、専用部品は symlink を追って書かない

#### Scenario: 仕組み自体の承認前は実設定を変えない
- **WHEN** PR は仕様・レビュー中で、主のマージ承認とリスク宣言の許容がまだ無い
- **THEN** 実 worktree の設定へ apply せず、仕様の作成や隔離した fixture の検証を承認済みと取り違えない

### Requirement: idle compaction の設定を確かめられなければ成功にしない
設定部品は、読めない・壊れた・object でない・重複キーのある JSON、不正な worktree、対象への symlink を検出したら書かず exit 1 にしなければならない（MUST）。check は disk 上で false なら exit 0、false への変更が必要なら exit 2 とする（MUST）。本体は disk 上の成功だけで live 反映を断定せず、反映しなければ記録から新セッションで再確認し、それでも off でなければ開始を止める（MUST）。

#### Scenario: 不正な入力を上書きしない
- **WHEN** 壊れた JSON、配列、重複キー、読めないファイル、worktree でないパス、.claude または settings.local.json の symlink を渡す
- **THEN** exit 1 で対象パスと原因を出し、設定全体を出さず、ファイルとリンク先を変更しない

#### Scenario: ファイルが false でも反映していない
- **WHEN** disk 上は false だが、実機の /config では Idle compaction が on のままである
- **THEN** live 反映済みとは報告せず、issue の記録から同じ worktree の新セッションで再確認する。再起動でも off を確認できなければ開始を止めて報告する

この検査の入力元は利用者の worktree の通常の設定ファイルとパスである。拾う誤りは設定破損・他キー消失・別パスへの書き込み・未反映を成功と呼ぶこと。未知の正常な設定キーや同じ worktree の別セッションへの設定の持続は通してよい。同時書き換えの完全な排他、悪意あるファイル差し替え、将来の Claude 設定形式のすべてを防ぐ検査ではない。穴を塞ぎ切ることを完了条件にしない。

### Requirement: idle compaction 無効化の実機結果はマージ後に記録する
実装担当は #1385 に実機チェックリストを残し、主はマージ・plugin 更新後の最初の親・子で設定が off になる手順と結果を記録しなければならない（MUST）。idle の対象となる会話量、スリープなし、リクエストなしで 60 分以上の待機区間を親・子それぞれ観測し、新しい compact_boundary が無いことを記録する（MUST）。通常の上限近くでの自動 compact の発生は別区間で確認する。完了前は未検証とし、Bats の合格を代用にしない。

#### Scenario: 有効な待機観測を記録する
- **WHEN** 主が更新済み plugin の親・子を各 60 分以上待機させる
- **THEN** 版、commit、off の確認方法・結果、会話量と適用中の idle 閾値、最後のリクエスト時刻、観測開始位置、経過秒、スリープ・追加リクエスト無し、新規 compact_boundary が 0 件である結果を #1385 にコメントする
- **AND** 単発の設定確認結果、親の live 反映または再起動の要否も記録する

#### Scenario: 観測条件不足は未検証とする
- **WHEN** 待機中に PC が寝た、会話量が idle の対象に達していない、API リクエストや別種の compact が発生した、または off を確かめていない
- **THEN** 印が無くても合格にせず未検証としてやり直す。ログの文章中に含む compact_boundary という単語をイベントとして数えない

#### Scenario: 通常の自動 compact を別に確認する
- **WHEN** 主が別区間で会話の上限近くに達した通常利用を観測する
- **THEN** 自動 compact が発生し、既存 hook が develop の手順書再読み込みを案内する結果を記録する

#### Scenario: 規則のファイルに子の切り方と分ける条件と根拠が書かれている
- **WHEN** `plugins/dev-workflow/skills/develop/references/reply-after-idle.md` を読む

### Requirement: 親が長く待ったあとは親の表で続けるか起動し直すかを決める
`plugins/dev-workflow/skills/develop/references/reply-after-idle.md` は、親も子・単発と同じくアイドル時のコンパクトを切ること、親が最後のリクエストから 60 分以上待ったら compact の有無や会話量によらずエピックの記録から起動し直すこと、60 分未満なら続けることを規定しなければならない（MUST）。親だけの 120,000 の設定・compact 後なら続ける分岐・監視が続くから残す説明は現行の規則に残さない（MUST NOT）。

時間分類は timeout・子の通知・主の返事を処理する前に適用する（MUST）。最後のリクエストは起床の API リクエストを除いた待機前のものを使い、キャッシュを書いた行の時刻と混同しない。60 分以上なら旧親は未処理イベントをエピックに記録し、同じ worktree の新セッションで `/develop <エピック番号>` から手順書と記録を読み直して再開するよう主に案内して終える（MUST）。再開手順は要件「親は wait の上限で起きたら子を調べ直さずに同じ wait を掛け直す」に定め、親の表と epic.md の手順 5 のどちらから読んでも時間分類が優先すると分かるようにする（MUST）。

#### Scenario: 規則のファイルに親の値と表と復元元が書かれている
- **WHEN** 規則のファイルを読む
- **THEN** 親にも idleCompaction false を適用し、60 分未満は続け、60 分以上は起動し直すと分かり、compact や N による継続の例外・親だけの閾値が無い
- **AND** 回し方、終わった子、外した子エピック、残した worktree、親が通した判断、主の返事待ち、残りの子の復元元が記録されている

親の状態はエピックと子 issue のコメント・依存グラフ・子の状態記録から復元できると書く（SHALL）。`回し方:`、`子 #N マージ → 残り k 件` / `子 #N 見送り`、`後で別に起動するエピック:`、`子 #N のワークツリーを残した`、`親の判断: 子 #N 通した` と停止記録 URL の対応、`pending-owner` の確認を残す。比較する相手は手順書と引き継ぎを読む新セッションであり、要約と手順書再読み込みを二重に払う親の方針を #1385 で覆したと書く（SHALL）。監視停止が compact のせいだったとは断定しない。古い集計のリンクは履歴として残せるが、親の idle 閾値の再集計を現行の宿題にしない。

この規則の入力は、親のトランスクリプトの最後のリクエスト時刻と、エピックの復元記録である。拾う誤りは、compact 済み・会話量が小さいことを理由に 60 分以上止まった親を続けること。境界の時刻が曖昧で 60 分前後の扱いが揺れる場合は続けてよく、時刻不明から長時間経過を捏造しない。復元元の記録自体の誤りや欠落はこの時間分類だけでは防がない。穴の追加封鎖を完了条件にしない。

#### Scenario: 親が compact 済みでも長く待ったら起動し直す
- **WHEN** 親の最後のリクエストから 60 分以上たち、compact_boundary がある場合と無い場合を比較する
- **THEN** どちらも会話量によらず起動し直し、エピックのコメントから親が通した判断を含め復元する

#### Scenario: 短時間の親は続ける
- **WHEN** 親の最後のリクエストから 60 分未満である
- **THEN** 親はそのまま続け、この規則を理由に短い wait のやり直しを止めない

### Requirement: epic.md の回し方は子の起動コマンドの指定と返事の規則のファイルを指す
`references/epic.md` の回し方は、すべての develop セッションが開始時に worktree-local の idleCompaction を false にすること、子は既存の起動オプションでも切ること、時間がたった子・親は `references/reply-after-idle.md` に従うことを書かなければならない（MUST）。親だけの閾値の付け方を案内してはならない（MUST NOT）。子の起動コマンドの `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` や `EPIC_DISPATCH_IDLE_COMPACT_MIN_TOKENS` も案内しない。対応する Bats はこの記述を確かめる（MUST）。

#### Scenario: epic.md の回し方が起動コマンドの指定と規則のファイルを指す
- **WHEN** references/epic.md の回し方を読む
- **THEN** 親・子を分けない開始時の設定と、子の --settings '{"idleCompaction":false}'、長時間待機後の共通方針が分かり、親だけの閾値の付け方を参照していない

この要件は、要件「エピックの条件・作り方・回し方・完了条件を規定する」の回し方の段落のうち、epic-dispatch.sh が足すのは --model だけとする部分に優先する（足すのは --settings '{"idleCompaction":false}' と --model）。既存の子の起動・返事の動作は変えない。

### Requirement: 親は wait の上限で起きたら子を調べ直さずに同じ wait を掛け直す

develop の `references/epic.md` の別セッション方式は、手順 3〜8 の起床後の処理や主の返事の処理より前に、要件「親が長く待ったあとは親の表で続けるか起動し直すかを決める」の時間分類を適用しなければならない（MUST）。timeout・通知（closed / done / stopped / unrecorded 等）・主の返事が重なっても、60 分以上と確認できたときの起動し直しを最優先とする。起床の API リクエストによる時刻更新を使って短時間と判定してはならない（MUST NOT）。

手順 5（位置引数の子がある wait の `timeout <N>...`）は、60 分未満か、時刻不明で 60 分以上と確認できず、他の通知や主の返事も無いときに限り、親が子 issue もエピックも読まず、主に報告もせず、直前と同じ引数の `wait` を `run_in_background: true` で再び 1 回起動してターンを終えることと、`--timeout` を足さないことを書かなければならない（MUST）。主への発言は書かないか、書くなら書き分けに従う `主がすること: なし` の 1 行だけとする（SHALL）。主への問いが未回答のあいだはその 1 行も書かず、問いを繰り返さない（SHALL）。60 分未満の通知や主の返事は既存の対応手順で処理し、timeout の掛け直しで捨てない（MUST）。親がターンを終えるときの発言の一覧は、短時間の純粋な timeout の報告を除外し、長時間後の再開案内は除外しない（MUST）。

60 分以上の場合、旧親は子を調べ直したり返事を送ったり wait を掛け直したりせず、既に持つ回し方・worktree・直前の wait の引数・起床理由・未処理の出力行と stderr / exit code・未処理の主の返事と元セッション ID / 発言 uuid / 時刻・次の再開手順をエピックに追記する（MUST）。同じ worktree の新セッションで `/develop <エピック番号>` として再開するよう主に案内して旧セッションを終える（MUST）。追記に失敗したら再開可能とは報告せず、エラーと未保存内容を主に示して止める（MUST）。

新親は develop の入口と手順書を読み、エピックと子の状態から手順 7 の adopt・reap・pending-owner と停止記録 URL の照合で復元する（MUST）。未処理の主の返事は元発言の真正性と対象を既存手順で確かめて先に扱い、次に未処理通知を現在の状態と照合して既存手順へ渡し、最後に純粋な timeout の待ちを現在の対象で組み直す（MUST）。引き継ぎコメントの写しだけを主の許容と認定してはならない（MUST NOT）。`stopped-seen` の停止を pending-owner で拾い、同じ停止記録 URL の送信済み判断や記録済みの完了を二重処理しない（MUST）。起動し直しだけを理由に動いている子の監視を終えてはならない（MUST NOT）。片付け待ちだけの wait（位置引数の子なし）の `timeout` は短い掛け直しの対象にせず、長時間なら先に起動し直しても **待ちをやめてよい条件 (d)** と既存の終了直前の確認を保持し、復元だけで新たな 6 時間待ちへ入り直さない（MUST）。

守備範囲: 子が印を付けずに `needs-approval` だけで止まったとき、ほかの子が動くか待ちをやめる直前まで親が気づかないことは通してよい。時間分類の入力と時刻が読めない場合の限りは親の表の要件と同じである。

#### Scenario: 手順 5 は同じ wait を掛け直すだけにする
- **WHEN** 位置引数の子がある wait が、待機前の最後のリクエストから 60 分未満で timeout になり、他の通知や主の返事が無い
- **THEN** 子 issue もエピックも読まず主に報告もせず、同じ引数の wait を背景に 1 回だけ掛け直してターンを終え、`--timeout` を足さない
- **AND** 手順 5 は **待ちをやめてよい条件** を指し、`needs-approval` の確認を追加しない。未回答の問いを繰り返さない

#### Scenario: 5 分キャッシュの長い timeout は起動し直しを優先する
- **WHEN** 5m の既定上限 21600 秒で待ち、最後のリクエストから 60 分以上経過して位置引数の子がある wait の timeout を受ける
- **THEN** 旧親は wait を掛け直さず、未処理の timeout と引数をエピックへ残して新セッションへ渡す
- **AND** 新親が手順 7 で状態を復元して待ちを組み直し、監視を終了しない

#### Scenario: スリープを挟んだ timeout も起動し直しを優先する
- **WHEN** 1h の上限 3000 秒で待った親が PC のスリープ後に timeout で起き、待機前の最後のリクエストから 60 分以上経過している
- **THEN** 今回の起床リクエストを最後の時刻と読まず、旧親で短い wait を掛け直さず新セッションへ引き継ぐ

#### Scenario: 長時間後の停止通知は受けた印を失わずに復元する
- **WHEN** 60 分以上経過した親へ stopped の通知が届き、wait が停止の印を stopped-seen にしている
- **THEN** 旧親は子へ返事を送らず通知を記録して起動し直し、新親は pending-owner と最新の停止記録 URL を照合して対応する
- **AND** 同じ停止記録へ既に送信済みの判断は再送しない。closed / done / unrecorded の通知も復元後に現在の状態と照合して対応する

#### Scenario: 長時間後の主の返事は新親で元発言を確かめる
- **WHEN** 60 分以上経過した親に主の返事と timeout または通知が同時に届く
- **THEN** 時間分類を先に適用して全てを記録し、新親が元発言の真正性と対象を確かめて返事を先に扱い、次に通知、最後に純粋な timeout の待ちを処理する
- **AND** 引き継ぎコメントだけを主の許容と認めず、旧親へ返事を打ち直してもらうことを再開の条件にしない

#### Scenario: 短時間の通知や返事を timeout 扱いで捨てない
- **WHEN** 最後のリクエストから 60 分未満で通知または主の返事があり、timeout の通知も届いている
- **THEN** 既存の対応手順で通知・返事を処理し、同じ wait の掛け直しだけで終わらせない

#### Scenario: 片付け待ちだけの timeout は復元後も終了条件を保持する
- **WHEN** 位置引数の子が無く、片付け待ちだけの --timeout 21600 が timeout で終わり、親の最後のリクエストから 60 分以上たっている
- **THEN** 旧親は起動し直しを先に行い、新親は元の timeout が条件 (d) に当たることを保持して既存の終了直前の確認を行い、終了可否を決める
- **AND** 手順 5 の短い掛け直しにも新たな 6 時間待ちにも無条件には入らない

### Requirement: 規則のファイルに親の待ちの費用と使用量の超過中の扱いを書く

`references/reply-after-idle.md` は、時間分類の表とは別の節に、wait が TTL によって 1h / unknown は上限 3000 秒、5m は 21600 秒を選ぶことと費用の理由を書かなければならない（MUST）。3000 秒は通常のポーリング間隔で約 45 分に起き、1 時間のキャッシュが切れる前に短く掛け直して読み出しで延ばすためと説明する。全 develop で idle compaction を無効にするため、約 54 分の idle compact 回避を現行の理由としてはならない（MUST NOT）。5m では短く起きてもキャッシュが残らず、起床回数を減らすため 21600 秒にする説明を残す（MUST）。

短い timeout の掛け直しは 60 分未満に限り、5m の長い timeout やスリープで 60 分以上たった場合は時間分類が優先し、記録から新セッションで再開すると書く（MUST）。使用量の超過中は有効期限が 5 分に縮むので 21600 秒に戻すこと（根拠 https://code.claude.com/docs/en/prompt-caching を添える）、`CLAUDE_CODE_PROMPT_CACHE_TTL` / `promptCacheTtl` で固定した人の扱い、PC が寝ている間はキャッシュを延ばせないこと、片付け待ちだけの明示上限も残す（MUST）。従来の「節を足すだけで表と文を変えない」という制約は、この change の共通 idle 無効化と親の表の改定には適用しない。

守備範囲: 入力は親の会話の TTL と最後のリクエストからの経過時間である。拾う誤りは、idle compact 回避を無効化後も費用の根拠にすることと、TTL による上限選択を捨てること。TTL の判定方法・値・wait の stdout / exit code は変更しない。

#### Scenario: 規則のファイルに親の待ちの費用と超過中の扱いがある
- **WHEN** 規則のファイルの親の待ちの費用の節を読む
- **THEN** 3000 / 21600 秒の TTL 選択、1 時間のキャッシュ維持と 5 分の起床回数削減、使用量超過時の 5 分への短縮と根拠 URL、TTL 固定、スリープの限りが分かる
- **AND** 約 54 分の idle compact の前に起きることを現行の理由にせず、共通 idle 無効化と親の 60 分の表に整合する

#### Scenario: 待ちの費用の節も長時間後の再開を優先する
- **WHEN** 5m の 21600 秒の timeout またはスリープ後の 60 分以上の経過を、費用の節からたどる
- **THEN** 旧親で無条件に掛け直す案内は無く、時間分類を先に適用して記録から起動し直すと分かる
