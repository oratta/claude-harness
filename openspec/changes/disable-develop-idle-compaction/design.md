# Design

## Context

動機は proposal.md「Why」を参照。R1 修正時は dispatch HEAD `28b16803` に origin/main `1b203ef5`（#1379）を merge した。既存の `epic-dispatch.sh` は子の起動に `--settings '{"idleCompaction":false}'` を足すが、主が起動する親・単発には付けられない。`reply-after-idle.md:50-109` と既存 spec は親だけ閾値 120,000 を残す。#1379 の timeout 後の無条件の掛け直しと、約 54 分の idle compact を避ける説明も変更対象である。

`cld` の実行ファイルは repo に無く、`plugins/dev-workflow/README.md:46-78` に、利用者がシェルへ置く `cld` / `cld-account` の関数例がある。既存の関数を plugin 更新で置換する仕組みではない。`commands/develop.md:16-35` は SKILL.md を Read して本体として実行し、同 SKILL.md から直接始める経路もある。

## Goals / Non-Goals

**Goals:** develop を始めた時点から、親・子・単発を調べずに idle compaction を切る。通常の自動 compact と compact 後の手順書再読み込みは維持する。長く止まった親も issue の記録から起動し直す。

**Non-Goals:** 通常の自動 compact の閾値変更、Claude Code 自体の改変、外部のシェル定義の変更、全プロジェクトへの設定配布、子の既存の会話量による再起動の変更、親の監視ループの再設計。Codex の compact 設定も変更しない（この設定の実行主体は Claude の本体であり、委譲された Codex W ではない）。

## Decisions

### 適用点は develop の入口、保存先は worktree-local

`skills/develop/SKILL.md` の役割別作業や返事待ちより前に、現在の worktree を明示して専用部品を呼ぶ指示を一か所置く。新しい develop 開始と、同じ worktree で新セッションとして引き継ぐ開始の両方に適用し、親か子か・interactive かどうかによる分岐を足さない。通常の compact 後に同 SKILL.md を読む場合も冪等な確認となる。コマンドの別名・自然文から SKILL を読む経路も同じ入口を使う。SessionStart hook を新設しない。

採用するのは、その worktree の `.claude/settings.local.json` の最上位 `idleCompaction` を false にする方法。ユーザー設定・共有設定には書かない。同じ worktree 内の develop 以外のセッションにも残るが、issue の候補が許容する worktree 単位の範囲であり、全プロジェクトへ波及しない。終了時に元へ戻すと、まだ待つ別セッションを再有効化しうるため、自動復元しない。

比較した案:

- `cld` の `--settings`: プロセスだけに効く利点があるが、repo の関数例を変えても手元の既存定義は変わらず、直接 `claude` で起動して develop を呼ぶ経路を覆えない。既存の子の指定は防御として残す。
- `/config` の手動変更だけを入口にする: 人の手が全開始で必要になる。主の操作は反映確認に使い、自動設定の主経路にはしない。
- ホームの settings・全 SessionStart で無条件に設定: develop 外や別プロジェクトにも効き、主の指示と範囲が合わない。

### 設定部品は単一キーに限定し、検査と書き込みを分ける

新規 `scripts/develop-idle-compaction.py` を `python3 <script> --check <worktree>` / `--apply <worktree>` で呼ぶ。対象は git の worktree root であることを確かめる。check は一切書かず、JSON object の `idleCompaction` が boolean false なら exit 0、キー無し・true などなら exit 2、構文エラー・非 object・読めない・worktree 不正なら exit 1。apply は同じ検査後、そのキーだけ false にして exit 0。既に false ならバイトも mtime も変えない。正常な値のある他キーを保持し、変更した場合は同じディレクトリの一時ファイルから置換する。無いファイル・ディレクトリは承認済み apply で作れる。

`.claude` または settings.local.json が symlink の場合は他 worktree / home に書く恐れがあるので exit 1 にする。壊れた JSON や重複キーを含む設定は上書きしない。エラーは対象パスと原因だけ出し、設定全体（秘密値や権限の中身）を出さない。CLI は disk 上の値しか確認できず、実行中 Claude の実効値を確認できたとは出力しない。入力は通常の worktree 設定であり、別プロセスが同時に設定を書き換える場合の完全な排他や悪意あるファイル差し替えまで守る部品にはしない。

### 設定ファイルの自己統治と継続適用の一度の承認

`.claude/settings*.json` は permissions・hooks と同居する自己統治設定である。この PR の本文とリスク宣言に、次の同じ承認範囲を明記する: 「develop 開始時、現在の worktree の `.claude/settings.local.json` の `idleCompaction` だけを false にする。他の設定値は保持し、ホーム・共有設定には書かない」。設定が無いときの当該キーだけのファイル作成、以後の develop 開始（新しい worktree・新セッション・interactive / unmanned を含む）への継続適用、同じ worktree の他セッションにも残り自動復元しないことを添える。

主のマージ承認（この範囲を明記したリスク宣言の許容）を仕組みへの一度の明示承認として記録する。単なる issue の目的・R1 の APPROVE・PR 作成・エージェントのコメントは承認の代わりにしない。承認を受けた仕組みの適用後は、check が exit 2 なら範囲内の apply を行い、worktree ごとの承認確認・追加質問はしない。check が exit 0 なら書き込まない。部品自体に GitHub へ承認を照会する処理は持たせず、承認された入口指示が check/apply を呼ぶ。

範囲を超える他キー・別ファイル・symlink 先の書き込みはこの承認に含まない。部品は symlink を exit 1 にして追跡せず、範囲外の変更が必要なら本体は従来どおり具体的な差分で聖域承認を求める。permissions/hook を書き換えて通さない。承認前の実設定変更はしない（fixture の検証は別）。今回の spec 段でも実設定を変更しない。正式なリスク宣言と承認の記録は coordinator の通常のレビュー工程で扱い、この段で承認済みとは書かない。

### 反映を確かめ、未反映なら新セッションで始める

issue にある Claude Code 2.1.310 の動的読み取りはバイナリの観察であり、途中反映の実証ではない。設定を書いた直後、主が `/config` の Idle compaction が off であることを確認する。live で反映しなければ現在の状態を issue に残し、同じ worktree で新セッションを起動して develop を読み直す。再起動でも off を確認できない・CLI の設定が true を上書きする等なら、成功とせず開始を止め、理由を #1385 に残す。CLI オプションの優先順位を想像して false になったとは扱わない。これは事前に決めた失敗時の手順であり、途中反映があることを採用案の前提にしない。

### 親の例外を廃止し、記録から再開する

共通の idle 無効化を一つの説明にし、子だけの起動オプションは適用済みの補助経路として書く。親の 120,000・compact 後の継続・監視が続くので残すという方針を削除し、60 分以上の親は compact の有無や会話量によらず起動し直す。60 分未満は続ける。子の端末・会話量・時間の優先順は維持する。端末の操作や復元元が親子で異なるのは手順の違いで、idle を切る方針や 60 分以上の基準を分ける理由にしない。

親の状態表（回し方・終了した子・外したエピック・残した worktree・親の判断・主の返事待ち・残りの子）は残す。比較相手と手順書の品質に関する 2026-10-26 の主の指摘を根拠に記録し、監視停止が compact のせいだったとは断定しない。#1039/#1217 の古い費用は履歴としてリンクできるが、親の閾値・再集計を現在の作業として求めない。

### 親の起床では時間分類を最優先し、短い timeout だけ掛け直す

`epic.md` の別セッション方式の手順 3〜8 のイベント処理と、主の返事の処理より前に、`reply-after-idle.md` の親の時間分類を適用する。`timeout`、`closed` / `done` / `stopped` / `unrecorded` 等の通知、主の返事のいずれでも同じ順序とする。経過時間は起床時点と、起床の API リクエストを除いた待機前の最後のリクエスト時刻との差である。今回の起床で時刻を更新して 0 分と読まない。キャッシュを書いた行の時刻（TTL 選択用）とも区別する。

| 判定 | 旧セッションの処理 |
|---|---|
| 60 分以上 | イベント処理・返事の送信・wait の掛け直しより先に起動し直す。compact の有無・会話量・通知の種類で例外にしない |
| 60 分未満（時刻不明で長時間経過を確認できない場合を含む）で位置引数の子がある wait の timeout だけ | #1379 の手順 5 を維持。子 issue もエピックも読まず主に報告もせず、直前と同じ引数で wait を背景に 1 回掛け直してターンを終える。`--timeout` を追加せず TTL を読み直す。主への問いを繰り返さない |
| 60 分未満で通知・主の返事がある | 既存の対応手順で処理する。timeout の掛け直しで通知や返事を捨てない |

60 分以上の場合、旧親は既に持つ状態と受信内容だけから、エピックに回し方・worktree・直前の wait の引数・起床理由・未処理の出力行と stderr / exit code・未処理の主の返事と元セッション ID / 発言 uuid / 時刻・次の再開手順を追記し、同じ worktree の新セッションで `/develop <エピック番号>` として再開するよう主に案内して旧セッションを終える。子 issue を調べ直したり子へ送信したりせず、承認を要する返事をこの追記だけで主の許容と認定しない。記録に失敗したら再開可能と報告せず、エラーと未保存内容を主に示して止める。

新親は develop の入口と手順書を読み、エピックと子の状態から復元する（手順 7 の adopt・reap・pending-owner と停止記録 URL の照合を維持）。未処理の主の返事があれば元発言の真正性と対象を既存の確認手順で確かめて先に扱い、次に未処理通知を現在の状態と照合して既存の対応手順へ渡す。`stopped-seen` は pending-owner から拾い、同じ停止記録 URL に送信済みの判断は再送しない。既に記録済みの判断・完了も二重処理しない。両方を処理したあと、純粋な timeout は現在の対象で待ちを組み直す。起動し直しだけを理由に動いている子の監視を終了しない。

片付け待ちだけ（位置引数の子なし）の `--timeout 21600` は手順 5 の無条件掛け直しの対象に加えない。60 分以上なら同じく先に起動し直し、新親で元の timeout が **待ちをやめてよい条件 (d)** であることを保持し、既存の終了直前の確認を通してから終了可否を決める。復元しただけで新たな 6 時間待ちへ入り直さない。

### 親の待ちの費用はキャッシュ維持として説明する

wait の実装と TTL 選択は変えない。1h / unknown の上限 3000 秒は、通常のポーリング間隔なら約 45 分で起き、1 時間のキャッシュが切れる前に短く掛け直して読み出しで延ばすために残す。idle compaction は全 develop で無効なので、約 54 分の compact の前に起きることは現行の理由にしない。5m では短く起きても既にキャッシュが切れており、起床回数を減らすため 21600 秒を残す。その timeout では 60 分以上の再開規則が優先される。使用量超過・TTL 固定の説明と根拠 URL は残す。スリープで 60 分以上経過した場合も旧親で掛け直さず新セッションへ渡す。

## Risks / Trade-offs

- [同じ worktree の他セッションにも残る] → 適用範囲・自動復元しない理由・戻し方を入口と変更記録に書く。
- [動的反映しない / CLI が上書きする] → `/config` の確認と新セッションによる再確認を行い、未確認は失敗として記録する。
- [設定に権限や hooks がある] → 単一キー以外の意味を保持するテスト、読み取りの check、symlink 拒否。この PR で限定した継続適用だけに主の承認を一度受け、他キー・別ファイル・symlink 先には従来の聖域承認を残す。
- [#1379 の timeout と長時間再開が競合] → main を merge 済み。60 分以上の起動し直しを全起床理由より先に適用し、60 分未満の純粋な timeout だけ従来どおり短く掛け直す。未処理通知・返事を記録して新親に渡し、片付け待ちだけの timeout の終了条件も保持する。

## Migration Plan

1. R1 の承認後、テストを先に追加し実装する。spec 段の現物設定変更・実機検証は行わない。
2. Bats と strict validate を通し、変更記録を含む PR を通常のレビューへ渡す。PR 本文と正式なリスク宣言の両方に上記の継続適用の範囲を記載し、主のマージ承認（リスク宣言の許容）の記録を残す。承認までは実設定を変えず、マージ前に 60 分実機検証を済ませたとは記録しない。
3. マージ後、更新済み plugin を利用する主（oratta）が、最初の親エピックと別セッションの子、および単発 interactive の開始で適用を確認する。実装担当が #1385 に以下の実機確認チェックリストを残し、主が結果を追記する。完了していなければ issue の実機受け入れ条件は未達として追跡する。
4. #1264 には本方針でアイドル閾値の再集計が不要になった旨を実装担当がコメントする。主が #1385 の実機結果を確認したあと、#1264 を不要として閉じる。通常 compact や子の再起動閾値の集計に勝手に転用しない。今回の spec 段では閉じない。

### マージ後の実機確認チェックリスト

- 主が、Claude Code の版・plugin の適用 commit・設定確認方法と off の結果を #1385 に記録する。親・子を別々に書き、単発も開始確認する。子は `ps` 等で既存 `--settings` が渡ることも確認する。親は develop 前に Idle compaction が on のセッションから off へ変わる試験を含め、live 反映したか再起動したかを書く。
- 主は親・子それぞれの対象 jsonl と観測開始時刻・行位置、最後のリクエスト時刻、`subagent-context.sh --file` の会話量を記録する。`compact_boundary` の既存行は開始位置より後の差分で区別する。ログ自体や秘密値は repo に置かない。
- idle が有効なら compact の対象となる会話量（その機械の `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS`、未設定ならその Claude Code の既定値。旧規定の 120,000 を仮定しない）のセッションを使う。閾値に達していない低負荷セッションで印が出なかっただけでは合格にしない。PC を起こしたまま、API リクエストを挟まず最後のリクエストから 60 分以上待つ。経過秒・スリープ無し・リクエスト無しを記録する。
- 待機区間の jsonl の新規 `compact_boundary` が 0 件であることを親・子それぞれ報告する。行の抽出は JSON として type / subtype を読み、単に会話テキスト中の語を数えない。途中で通常 compact・手動 compact を行った試行は分類根拠が曖昧になるためやり直す。スリープした試行・会話量不足・リクエストを挟んだ試行も未検証扱い。
- 通常 compact の維持は、部品・起動コマンド・設定差分で `DISABLE_AUTO_COMPACT` 等を加えていないことを実装担当が検査し、主が会話が上限近くに達した通常利用時の自動 compact の発生と、既存 reread hook による SKILL の再読み込みを別の観測区間で記録する。通常 compact を起こすために実際の上限へ近づける確認は主の実機側で行う。

### Rollback

追跡コードは PR 差分を戻す。worktree-local 設定は自動復元しないため、主が当初の差分を確認・承認し、そのキーだけ元の値に戻すか元々無ければ削除する。他キーの後続変更を失う設定ファイル全体の復元はしない。ホームの設定や shell は変更していない。
