## Context

動機は proposal.md の Why を参照。1 本目の change（PR #1282）のあとの今の main では、`risk-carryover-check.sh` は次を出す。

- 終了コード 4（`CARRYOVER=if-judged`）: `NG:` が無く、根拠ファイルの PR 自身の差分（各 HEAD と base の merge-base からの差分）が前後で違うファイルがある
- `EVIDENCE_PR_CHANGED=<ファイル>`（1 行 1 件）と `EVIDENCE_DIFF_LINES=<行数>`（`EVIDENCE_PR_CHANGED=` のファイルの `git diff --numstat <前> <新>` の追加と削除の合計）
- 終了コード 4 のときも、許可リストの条件を満たさない衝突解消があれば `RESOLVED_OUTSIDE_ALLOWLIST=` の行を出す（優先順が 1 → 4 → 3 → 0 なので、4 は 3 を覆う）

`hold.md` 3-c は終了コード 4 を条件 1 を満たさないものとし、手順 6 で主に聞く。

develop の G はサブエージェント（`dev-workflow:gate-runner`）で、Agent ツールで決める役を起こせない。決める役が要る場面は、G が Status で返して本体が起こす形がすでに 2 つある（`needs-decider`: 仕分け表の順 6 の裁定、`needs-fix-check`: 2 周目以降の直し方の判定）。どちらも本体が決める役を起こし、結果を渡して次の G を新しく起こす。

## Goals / Non-Goals

**Goals:**

- 終了コード 4 で、ほかの引き継ぎの条件を満たし、差分が上限以下なら、作業の文脈を持たない判定役が「リスク宣言の中身が前と同じか」を判定し、「同じ」なら主に聞かずに引き継ぐ
- 判定の入力・返答の形・記録の形を固定し、G と本体が文面の読み取りで分岐しないようにする
- 「変わった」「判断できない」・上限超え・判定役を起こせない場合は今どおり主に聞く

**Non-Goals:**

- `risk-carryover-check.sh` の判定や出力を変えること
- 終了コード 1（`NG:` あり）を判定役に回すこと（履歴の書き換えなどは中身の比較では救えない）
- 終了コード 3 の扱い（PR 全体を見たレビューの確認）を変えること
- 従来経路の一括の G から判定役を起こす経路を作ること（呼び出し元が Status を受けて決める役を起こす約束が無い）

## Decisions

### 決定 1: 判定役を起こす経路は、develop では G が Status `needs-carryover-judge` で返し本体が起こす

合格処理の G は、3-c で判定役に回す条件をすべて満たしたら、宣言を投稿せず、`needs-approval` も付けずに Status `needs-carryover-judge`・`次の段: 合格処理` で返す。本体は判定役を起こし、判定の記録を PR にコメントし、判定とその URL を渡して合格処理の G を新しく起こす。新しい G は `declarations.md` の手順 3 から入り直し、3-c で判定の記録を読んで引き継ぐか主に聞くかを決める。

- 理由: `needs-fix-check` と同じ形で、本体は Status と `次の段:` だけで次の段を決められる（「Gate Result は段と次の段を持つ」の決まりのまま）。G は段ごとに新しく起こすので、判定のあとの合格処理を前の G の続きにできない
- `次の段:` を `合格処理` にする理由: 判定のあとに要るのは 3-c の続き（引き継ぐか主に聞くか）と手順 3-b・4・5 で、どれも合格処理の段の範囲。照合と振り分けに戻すと、レビューの仕分けを判定のたびに読み直すことになる
- 代わりの案 A: 合格処理の G が保留（`needs-approval`）で返し、保留の解除の G に判定を渡す。主への依頼が出ていないのに `needs-approval` を付けると、ラベルが主待ちを意味しなくなる
- 代わりの案 B: 本体が G を起こす前に自分でスクリプトを回し、判定役を先に起こす。3-c の条件（宣言の選び方・本文の一致・真正性）を本体が二重に持つことになり、G の判定と食い違いうる
- メインセッションで pr-review-gate を回すとき（develop の外）は、ゲート自身が Agent ツールで判定役を起こし、記録を投稿して 3-c を続ける。Status は使わない
- 従来経路の一括の G（`段: 一括（従来経路）`、`次の段: なし`）は判定役を起こさず、今どおり主に聞く

### 決定 2: 判定役に回すのは、ほかの条件をすべて満たしたあとだけ

3-c の条件 2（根拠ファイルの行）・条件 3（真正性）・条件 4（宣言の本文の一致）を先に確かめ、`RESOLVED_OUTSIDE_ALLOWLIST=` の行があれば条件 1 の終了コード 3 と同じ確認（新しい HEAD で PR 全体を見たレビュー）も先に確かめる。どれかを満たさなければ判定役を起こさず手順 6 で主に聞く。

- 理由: 判定が「同じ」でも引き継げない場合に判定役を起こすのは費用の無駄（1 回 20〜40 万トークンの見込み。issue #1238 本文）。判定役は根拠ファイルの差分しか見ないので、ほかの条件の代わりにはならない
- 終了コード 4 で許可リスト外の衝突解消もあるときに PR 全体のレビューを求めるのは、4 が 3 を覆うだけで、衝突解消の確認が要ることは変わらないため

### 決定 3: 渡すのは前後の HEAD の diff と前の宣言の本文だけ。上限は 100 行で `EVIDENCE_DIFF_LINES=` で見る

入力は `git diff --no-color --no-ext-diff --no-textconv <前 HEAD> <新しい HEAD> -- <EVIDENCE_PR_CHANGED のファイル>...` の出力と、前の宣言の本文（3-c の条件 4 と同じ範囲。末尾の `主の回答:` 以降の追記行を除く）だけにする。記録先の本文・レビューの指摘・W の return・作業の会話は渡さない。依頼文では、この 2 つだけから判定し、足りなければ「判断できない」と返すよう求める。`EVIDENCE_DIFF_LINES=` が 100 を超えたら判定役を起こさず主に聞く（100 ちょうどは判定させる）。

- 渡す範囲を前後の HEAD の diff にする理由: 判定の問いは「前に許容したときから、根拠ファイルで何が変わったか」で、それがそのまま出る。`EVIDENCE_DIFF_LINES=` も同じ範囲で数えているので、上限と渡す量が一致する（1 本目の NOTE の「渡す範囲と数え方を合わせる」を満たし、スクリプトを変えずに済む）
- 代わりの案 C: 各 HEAD の PR 自身の差分（merge-base からの差分）を前後 2 つ渡す。main から入った変更を除けるが、PR がそのファイルに入れた変更の全体を 2 回渡すので量が増え、行数の数え方も変える必要がある。前後の diff に main からの変更が混ざっても、判定役が「変わった」か「判断できない」に倒れて主に聞くだけ
- 作業の文脈を渡さない理由: 主の承認を省いてよいかを、作業した側の説明に引きずられずに決めるため（issue #1238 本文）
- 100 行の根拠: レビュー指摘や CI の直しは数行〜数十行で収まる。100 行を超える手直しはリスクの中身が変わっている見込みが高く、判定役の読み違いと費用の上振れも大きくなる。実測ではない（過去の引き継ぎの宣言で根拠ファイルの差分の大きさを数えれば確かめられる）
- 判定役はリポジトリのファイルを Read できるが、依頼文が 2 つの入力だけから判定するよう求める。読み足しを道具で禁じることはしない（`agents/decider.md` は変えない）

### 決定 4: 判定役は `dev-workflow:decider`・`model: opus` で起こし、返答の 1 行目を 3 形に固定する

モデルは残量モードによらず `opus` を明示する（Fable の枠を使わない。修正方針やマージ可否ほど重い判断ではないため。issue #1238 本文）。`SHARED_BUDGET_MODE=depleted`（全役割 sonnet 固定）のときは判定役を起こさず、判定の記録を `引き継ぎ判定: 判断できない`・理由「判定役を起こさなかった（共有枠 depleted）」で投稿して、主に聞く側に倒す。依頼は `agents/decider.md` の通常の 3 点（原因の分類・直し方・次のモデル）ではなく、1 行目を `引き継ぎ判定: 同じ`・`引き継ぎ判定: 変わった`・`引き継ぎ判定: 判断できない` のどれかちょうどにし、2 行目以降に理由（何が同じか、何が変わったか、何が足りないか）を書くよう指定する。1 行目が 3 形のどれにも一致しなければ「判断できない」として扱い、依頼し直さない。

- 「同じ」の意味: 差分によって、前の宣言のリスク内容・該当する観点・発生条件・影響範囲と戻し方のどれも変わらない
- 依頼し直さない理由: 「判断できない」は主に聞く側に倒れるだけで、取りこぼしは主の手間 1 回に留まる。`needs-fix-check` の「`不足:` なら 1 回だけ依頼し直す」を入れないのは、この判定には補える入力が無い（入力を 2 つに固定している）ため
- depleted で sonnet に落として判定させない理由: 主の承認を省く判定を、主が指定したより弱いモデルで行わない
- depleted の記録を投稿するのは判定役を起こす側（develop の外ではゲート自身、develop では本体）。develop では、合格処理の G が depleted でも `needs-carryover-judge` で返し、本体が「判断できない」の記録を投稿し、合格処理の G を起こし直してその G が手順 6 で主に聞く。この往復は意図した形で、G 側で短絡させない（G が自分で記録を投稿すると、本体の投稿と二重になるか、どちらも投稿しないかのずれが起きる）

### 決定 5: 判定の記録は PR にコメントし、1 行目と項目を固定する

本体（メインセッションではゲート自身）が判定役の返答を受け取ったら、PR に次のコメントを投稿する（判定役は投稿できないので代理投稿する）。1 行目は正規表現 `^引き継ぎ判定: (同じ|変わった|判断できない)$` に完全一致させる。2 行目以降は `項目名: 値` で、`前 HEAD:`（40 桁）・`新しい HEAD:`（40 桁）・`前の宣言:`（コメントのリンク）・`根拠ファイル:`（`EVIDENCE_PR_CHANGED=` のファイル）・`差分の行数:`（`EVIDENCE_DIFF_LINES=` の値）・`判定役:`（`dev-workflow:decider`・モデル・代理投稿した者）・`理由:`（判定役の 2 行目以降）を書く。`対象 HEAD:` の文字列は使わない（auto-merge の workflow が宣言の照合に使うため）。

- PR に置く理由: 段と段の間の受け渡しは PR コメントを正とする決まりで、新しい合格処理の G は PR コメントから読む。引き継ぎの根拠の行が指すリンク先も同じ PR に揃う
- 新しい合格処理の G は、`前 HEAD:` と `新しい HEAD:` が自分の 3-c の前 HEAD・新しい HEAD と一致し、`根拠ファイル:` がスクリプトの `EVIDENCE_PR_CHANGED=` と一致する最新の記録だけを使う。一致しなければ記録を使わず、もう一度 `needs-carryover-judge` で返す（HEAD が動いたあとの古い判定を使わない）。一致する記録があれば、同じ前後の組で `needs-carryover-judge` を返し直さない（判定の繰り返しを防ぐ）
- 「同じ」で引き継ぐときの引き継ぎの根拠の行は、今の行頭 `引き継ぎの根拠: risk-carryover-check.sh 終了コード ` のまま終了コード 4 を書き、`EVIDENCE_PR_CHANGED=` のファイル・差分の行数・判定の結果・判定の記録のリンクを足す。4 行の構造は変えない（`pass.md` の合格条件の表は 4 行が揃っているかだけを見る）

### 決定 6: Codex の G は変えない

Codex の phase `gate` は `gate-runner.md` と pr-review-gate の段のファイル（`hold.md`・`pass.md` を含む）を正本として受け取り、Gate Result を返す。Status を読んで次を決めるのは Claude の本体で、(4) に `needs-carryover-judge` の分岐を足せば Codex の G が返したものも同じに扱える。`codex-develop.py` の prompt の「独立した役が要るなら needs-reviewer/needs-decider を返す」は一般の言い方で、`needs-fix-check` も同じ扱いで動いている。今の main の `codex-develop.py` は、phase `gate` の正本一覧に `skills/develop/references/roles/gate-runner.md`（29 行目の対応表）と `stages/pass.md`・`stages/hold.md`（474〜476 行目）を入れていることを仕様づくりの時点で確かめた。実装時にもう一度確かめ、外れていたらこの change で足す。

### issue に無い本体側の補い（2 つ）

次の 2 つは issue #1238 の本文にも主の決定（issue #1238 のコメント、2026-10-23）にも書かれていない。仕様を書く側が、判定役を起こせない場面の扱いとして補ったもので、どちらも「判定役が判定しなかったときは今どおり主に聞く」という issue の受け入れ条件の側に倒している。仕様レビューで、主に聞くべき仕様の発明に当たるかを確かめてもらう。

- **`SHARED_BUDGET_MODE=depleted` のときは判定役を起こさず、「判断できない」の記録を投稿して主に聞く（決定 4）**: issue は判定役のモデルを `opus` と指定している。depleted は全役割を `sonnet` に固定する決まり（`develop/SKILL.md` のモデル節）なので、そのまま起こすと主が指定したより弱いモデルで主の承認を省く判定をすることになり、`opus` で起こすと共有枠の決まりを破る。どちらも避けるため、起こさずに主に聞く側に倒した。主の手間は今と同じ 1 回の質問に留まる
- **従来経路の一括の G（`段: 一括（従来経路）`）は判定役を起こさず主に聞く（決定 1）**: develop の外から `レビュー経路: 従来` で起こされた G はサブエージェントで、Agent ツールで決める役を起こせない。呼び出し元が Status を受けて決める役を起こす約束も無いので、Status で返しても判定役は起こされない。新しい約束を作らず、今どおり主に聞く側に倒した

## Risks / Trade-offs

- [判定役が差分を読み違え、変わったリスクを主に聞かずに通す] → issue #1238 で受け入れたリスク。起きるのは根拠ファイルへの PR 自身の修正がリスクの中身に触れた場合に限られ、条件 4（新しい HEAD のレビューから組み立てた宣言の本文の一致）は残る。頻度は確かめていない
- [引き継ぎが何度も続き、1 回ずつは小さい変更が積もってリスクが変わる] → 判定役は前の宣言の本文とその回の差分だけを見るので、積もった変化は見ない。各回で新しい HEAD のレビューと条件 4 が残る。守備範囲の外として書く
- [前後の diff に main からの変更が混ざり、判定役が「変わった」と答える] → 主に聞く側に倒れるだけ
- [判定 1 回の費用] → 1 回 20〜40 万トークン・1〜2 分の見込み（issue #1238 本文。実測ではない）。ほかの条件を先に確かめ（決定 2）、100 行で上限を切る（決定 3）
- [判定の記録をエージェントが捏造する] → G は協力的だが読み違える前提で、記録の HEAD とファイルの一致は確かめるが、記録が本当に判定役の返答かは確かめない。守備範囲の外として書く

## Migration Plan

- 手順書と bats を同じ PR で直す。スクリプトは変えない
- この PR より前の G（`needs-carryover-judge` を知らない本体）は無い（同じ PR で本体の (4) と G の指示書を両方直す）
- 既存の宣言・引き継ぎの記録は書き換えない
- 戻すときは PR を revert する（終了コード 4 は今どおり主に聞く扱いに戻る）
