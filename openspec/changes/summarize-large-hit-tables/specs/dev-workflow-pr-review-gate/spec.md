## ADDED Requirements

### Requirement: 件数の多い語の一周目の照合表は全ヒット要約で返す

`stages/reviewer-brief.md` のレビュアー向け指示ブロックは、一周目の `照合表` について、全ヒットが 50 行を超える語を全行の代わりに次の形で返すことを要求しなければならない（MUST）: `修正前 SHA: <40 桁>`、`検索コマンド: git grep -n <語の指定> <rev> -- .`、`全ヒット要約: <行数> 行 <ハッシュ>`。`<行数>` は固定した対象 HEAD で検索コマンドを実行した標準出力の行数、`<ハッシュ>` はその標準出力を `git hash-object --stdin` に渡した値とする（MUST）。食い違いの行は、共通一覧契約の 4 列の表にその行だけを載せ、`扱い` を `食い違い: <finding ID>` にする（MUST）。食い違いが無い語は 4 列の表を省いてよい（MAY）。

#### Scenario: 全ヒットが 2,000 行を超える語が返答に収まる

- **WHEN** 検索語の全ヒットが 2,100 行あり、レビュアーが要約を返す
- **THEN** その語の照合表は検索コマンド・行数・ハッシュと食い違いの行だけで、スクリプトは exit 0 を返す

### Requirement: 全ヒット要約は標準出力だけで作り件数の多い語を全件読みしない

`stages/reviewer-brief.md` のレビュアー向け指示ブロックは、全ヒット要約の手順がファイルへ書かず標準出力だけで完結することを含まなければならない（MUST）。語ごとの行数を本文より先に測り、件数の多い語は検索コマンドの全件を一度に読まず、ファイルごとの件数から入って、PR の差分に関わるファイルと用法が疑わしいファイルの本文を読むと書かなければならない（MUST）。読むときの絞り込みを `検索コマンド:` の行に持ち込んではならない（MUST NOT）。

#### Scenario: 指示ブロックの手順

- **WHEN** レビュアー向け指示ブロックの全ヒット要約の段落を読む
- **THEN** 行数とハッシュを作るコマンド、標準出力だけで完結すること、件数の多い語の読み方、下限の 50 行が書かれている

### Requirement: 共通照合スクリプトは全ヒット要約を再実行して照合する

`plugins/dev-workflow/scripts/review-hit-set.py` は、`全ヒット要約:` の行を持つ表を受け取ったら、共通一覧契約と同じ検査を通した検索コマンドを修正前 SHA で再実行し、標準出力の行数とハッシュを表の値と比べなければならない（MUST）。検索範囲を狭める指定は、全行の表と同じく契約違反として拒否しなければならない（MUST）。両方が一致し、4 列の表の行がすべて全ヒットに含まれるときに限り exit 0 を返す（MUST）。行数が違えば `summary: hit count differs: table <表の値>, actual <実際の値>`、ハッシュが違えば `summary: digest differs`、全ヒットに含まれない 4 列の行は `extra: <ファイル>:<行>` を標準出力に出して exit 1 を返す（MUST）。

#### Scenario: シェルで作った要約とスクリプトの再計算が一致する

- **WHEN** 指示ブロックに書かれたパイプで作った行数とハッシュを、書き込み不可の `.git` を持つリポジトリで求めて表に書く
- **THEN** スクリプトは同じ値を計算して exit 0 を返す

#### Scenario: 要約でも検索範囲を狭められない

- **WHEN** 要約の表の検索コマンドが `-- .` ではなく変更ディレクトリだけを起点にするか、ヒット件数を減らす option を含む
- **THEN** スクリプトは全行の表と同じ契約違反として exit 1 を返す

#### Scenario: 要約の値が実際の全ヒットと違う

- **WHEN** 表の行数が実際より少ない、または行数が同じでハッシュが違う
- **THEN** スクリプトは `summary:` の行を出して exit 1 を返す

#### Scenario: 全ヒットに無い食い違いの行

- **WHEN** 要約の下の 4 列の表に、固定 SHA の全ヒットに無い `file:line` を載せる
- **THEN** スクリプトは `extra: <ファイル>:<行>` を出して exit 1 を返す

### Requirement: 全ヒット要約の使える範囲を契約違反で守る

共通照合スクリプトは次の入力を契約違反として標準エラー出力に `contract: <message>` を 1 行出し exit 1 を返さなければならない（MUST）: `全ヒット要約:` の値の形式の不正、実際の全ヒットが 50 行以下の語の要約、`--head` 付きの呼び出しでの要約、`扱い` が `食い違い: <finding ID>` でない 4 列の行。

`全ヒット要約:` の行を持たない表の出力と終了コードを変えてはならない（MUST NOT）。要件「共通照合スクリプトが順 3 の 2 段目を機械照合する」の `--head` を付けない呼び出しの規定は、この行を持たない表を指す。順 3 の一覧は全行のままとし、要約で返してはならない（MUST NOT）。

#### Scenario: 件数の少ない語は要約にできない

- **WHEN** 実際の全ヒットが 50 行の語を要約で返す
- **THEN** スクリプトは `contract:` を標準エラー出力に出して exit 1 を返す

#### Scenario: 要約の下に一致の行を載せる

- **WHEN** 要約の下の 4 列の表に `扱い` が `一致` の行を載せる
- **THEN** スクリプトは `contract:` を標準エラー出力に出して exit 1 を返す

#### Scenario: 順 3 では要約を使えない

- **WHEN** `全ヒット要約:` の行を持つ表を `--head <HEAD>` 付きで照合する
- **THEN** スクリプトは `contract:` を標準エラー出力に出して exit 1 を返す

#### Scenario: 全行の表は変わらない

- **WHEN** `全ヒット要約:` の行を持たない 4 列の表を照合する
- **THEN** スクリプトの出力と終了コードはこの変更の前と同じで、50 行を超える語の全行の表も受け付ける

### Requirement: G は全ヒット要約の表を同じ照合に通す

`skills/develop/references/roles/gate-runner.md` の一周目の三表の機械照合は、`全ヒット要約:` の行を持つ表も同じコマンドに渡すことと、全行の本文が無いことを表の欠落として扱わないことを書かなければならない（MUST）。要約の照合が一致しないときの補足は、既存の補足の経路（`補足済み回数` と `review-incomplete`）をそのまま使わなければならない（MUST）。

#### Scenario: 要約の表の照合が一致しない

- **WHEN** 補足済み回数が 0 で、要約の表のスクリプトの照合が exit 1 を返す
- **THEN** G はその表を残差として `needs-reviewer` の補足を求め、補足後も一致しなければ `review-incomplete` で return する

## MODIFIED Requirements

### Requirement: レビュアーへの指示に全件列挙と再レビューの制限を含める

SKILL.md 手順 2-1 のレビュアー向け指示ブロックは、一周目に指摘を書く前に、次の三表を順に出すことを要求しなければならない（MUST）。

1. `変更点の一覧`: この PR が新しく決めたルール・判定・用語を ID 付きで列挙し、各項目に対応する受け入れ条件と検索語を書く。各受け入れ条件は 1 項目以上に対応させる
2. `照合表`: 変更点 ID ごとに、共通一覧契約の `修正前 SHA`（固定した対象 HEAD）、repository-wide な `git grep -n ... <rev> -- .`、diff 外を含む全ヒットのファイル・修正前 SHA での行・本文・`扱い`（`一致` または `食い違い: <finding ID>`）を書く。順 3 の grep の語の経路との差は第 4 列の値と、修正後 HEAD を検査する第 2 段が無いことだけとする。順 3 の場合分けの軸の経路にはこの共通一覧契約を適用しない。全ヒットが 50 行を超える語は、全行の代わりに要件「件数の多い語の一周目の照合表は全ヒット要約で返す」の形で書く
3. `ハンク被覆`: 固定した PR diff の各ハンクについて、ファイル・ハンクヘッダーと指摘 ID または `問題なし` を書く

レビュアーは `変更点の一覧 → 照合表 → ハンク被覆 → 三表の自己点検 → 指摘` の順で進め、三表を指摘より前に出さなければならない（MUST）。保証範囲は変更点の一覧に載った項目についてリポジトリ内の出現箇所をすべて照合したことまでとし、一覧自体に載らなかった暗黙の変更を発見したことを完了条件にしてはならない（MUST NOT）。全ヒット要約で返した語の保証範囲は、検索範囲と全ヒット集合の一致までとし、すべてのヒットの本文を読んだことを保証に含めてはならない（MUST NOT）。

同じ指示ブロックは、1 周目は対象範囲に該当する指摘を全部列挙するまで止まらないこと、差分限定の再レビューは前回指摘の閉鎖確認（状態欄の付与）に限り新規の指摘を出さないことを含まなければならない（MUST）。ただし例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる新規の指摘は、差分限定の周でも出してよい。方式の書き換え後の全体レビューでも新規に出してよい深刻度は `blocking` だけとし、前回の「直し方」どおりに直した箇所を再指摘してはならない（MUST NOT）。直し方自体が誤っていた場合はレビュアー側の誤りとして `wontfix` 相当の記録にする。差分限定の周に出た例外 3 種の新規指摘は、仕分け表の順 1 から通す（MUST）。

#### Scenario: 三表が指摘より前にある

- **WHEN** 一周目のレビュアー向け指示ブロックに従ってレビュー結果を作る
- **THEN** `変更点の一覧`・`照合表`・`ハンク被覆` がこの順で指摘より前に出力される

#### Scenario: 受け入れ条件と変更点を対応づける

- **WHEN** `変更点の一覧` を作る
- **THEN** 記録先の各受け入れ条件が 1 つ以上の変更点 ID に対応し、各変更点に検索語がある

#### Scenario: 照合表は diff 外を含む

- **WHEN** 変更点の検索語が diff 外のファイルにも現れる
- **THEN** `照合表` は再実行可能な検索コマンドと diff 外を含む全ヒット、その判定を記録する

#### Scenario: 全件列挙の一文がある

- **WHEN** SKILL.md のレビュアー向け指示ブロックを読む
- **THEN** 「該当する指摘を全部列挙するまで止まらない」旨の 1 文がある

#### Scenario: 再レビューで新規 nit を出さない

- **WHEN** SKILL.md のレビュアー向け指示ブロックを読む
- **THEN** 再レビューでは新規の `nit` を出さず、全体レビューに戻っても新規に出してよいのは `blocking` だけと書かれている

#### Scenario: 差分限定の周でも例外 3 種は出せる

- **WHEN** SKILL.md のレビュアー向け指示ブロックの、新規の指摘を出さない文を読む
- **THEN** 例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる新規の指摘は出してよいという但し書きがある

### Requirement: 順 3 の grep の語の経路と一周目照合は共通の全ヒット一覧契約を使う

SKILL.md は、仕分け表の順 3 のうち検索コマンドが grep の語である経路の第 1 段と、一周目レビューの `照合表` が共有する全ヒット一覧契約を 1 か所に定めなければならない（MUST）。共通部分は、`修正前 SHA: <40 桁>`、`検索コマンド: git grep -n <語の指定> <rev> -- .`、および `| ファイル | 行（修正前 SHA） | ヒットした行の本文 | 扱い |` の列とする（MUST）。一周目レビューでは固定した対象 HEAD を `修正前 SHA` とし、順 3 の grep の語の経路では W が修正に着手する直前の HEAD を使う（MUST）。

共通一覧契約は、本文の元の `\`、`|`、backtick をこの順で backslash escape し、escape 後の本文内の最長連続 backtick より長い backtick fence で本文全体を囲み、その逆変換で復号する規則を定めなければならない（MUST）。

検索起点はリポジトリルートで、固定 revision の追跡対象パスをすべて含めなければならない（MUST）。サブディレクトリだけへの限定や追跡対象パスの除外をしてはならない（MUST NOT）。`.git` のメタデータと固定 revision に含まれない untracked / ignored の生成物は対象外とするが、追加の追跡対象除外は設けない（MUST）。

共通照合スクリプトは、SHA・検索コマンド・表の共通列を受け取り、第 4 列の値を集合の同一性に使わず、固定 SHA での全ヒット集合と表の全行を比較しなければならない（MUST）。一周目レビューの `扱い` は `一致` / `食い違い: <finding ID>`、順 3 の grep の語の経路の `扱い` は `直した` / `該当しない: <理由>` とする（MUST）。全ヒットの表と全行を比較するこの規定は、要件「件数の多い語の一周目の照合表は全ヒット要約で返す」の `全ヒット要約:` の行を持つ表には適用しない。順 3 の grep の語の経路だけが、修正後 HEAD に対する本文・件数・削除行の照合を順 3 固有の第 2 段として維持し、一周目の同一 SHA 照合には適用してはならない（MUST NOT）。（第 2 段は同じスクリプトに `--head` を付けて回す。要件「共通照合スクリプトが順 3 の 2 段目を機械照合する」）

順 3 の場合分けの軸の経路はこの共通検索契約の対象外とし、既存 spec「一覧の一致で閉じる（順 3）」どおり、`検索コマンド:` の行に軸とその全域を書き、`| 軸の値 | 扱い |` の 2 列を使わなければならない（MUST）。G は表の行の集合と軸の全域との一致だけを検査し、grep の検索コマンド・4 列・修正後 HEAD の第 2 段を要求してはならない（MUST NOT）。

#### Scenario: grep の語の両経路が同じ共通入力を受理する

- **WHEN** 同じ修正前 SHA・repository-wide な検索コマンド・同じ 3 列のヒット集合を持ち、第 4 列だけが一周目用と順 3 の grep の語の経路用で異なる 2 表を照合する
- **THEN** 共通照合スクリプトは両方を同じヒット集合として受理し exit 0 を返す

#### Scenario: 別ディレクトリの未変更ファイルも対象にする

- **WHEN** 検索語が変更ファイルのほか別ディレクトリの未変更ファイルにも存在し、表が変更ファイルのヒットだけを載せている
- **THEN** 共通照合スクリプトは未変更ファイルのヒットを missing として出力し exit 1 を返す

#### Scenario: 検索範囲の限定を拒否する

- **WHEN** 検索コマンドが `-- .` ではなく変更ディレクトリだけを起点にするか追跡対象パスを除外する
- **THEN** 共通照合スクリプトは共通一覧契約違反として exit 1 を返す

#### Scenario: 場合分けの軸には grep 契約を適用しない

- **WHEN** 順 3 の一覧が軸とその全域、および `| 軸の値 | 扱い |` の全行を持つ
- **THEN** G は表の行の集合と軸の全域との一致だけを検査し、grep の検索コマンドまたは 4 列を要求しない
