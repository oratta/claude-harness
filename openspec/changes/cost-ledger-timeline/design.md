## Context

- いまの hook（`plugins/cost-ledger/scripts/gate-report.sh`、PostToolUse・matcher `Bash`）は、合格ラベル `agent-review:passed` の付与を見つけると、同期のまま `gh` を 3〜4 回と `cost_ledger.py cost <番号>` を呼び、目印付きのコメント 1 本を最新の合計で書き換える
- 台帳は `COST_LEDGER_PATH` で稼働済み。2026-10-06 に読み取りだけで測った値: 台帳は 156,888 行・67 MB。ブランチ名で行を絞る読み方（PR の経路）は 0.18 秒、全行を JSON として読む（いまの issue の経路）と 0.85 秒
- 主が決めた前提（#303 のコメント）: 1 本のコメントに行を積む。行には時刻・きっかけと、金額・入出力トークン・キャッシュトークンを「累計 (+増分)」で載せる。速さは台帳を読むことで出す
- エピック #272 の「全体の制約」: LLM のトークンを使わない。hook は出力しない。セッションを 1 秒以上止める処理は裏で走らせる。`gh` の呼び出し回数を実測する。1 行は短く保つ
- 動く環境の前提: `gh` が PATH にあり認証済みで、そのアカウントが対象の PR / issue にコメントを書けて、自分が書いたコメントを編集できること。`python3` が PATH にあること。Python の `fcntl.flock` が使える OS（macOS / Linux）であること。どれかが欠ける環境（`gh` が未認証、書き込み権限の無いリポジトリ、Windows）では、行を積まずに無出力で終わる（エラーにしない）

## Goals / Non-Goals

**Goals:**

- 7 種のコマンドと合格ラベルの付与のたびに、同じ 1 本のコメントへ 1 行積む（PR と issue の両方）
- hook がセッションを止める時間を、対象のコマンドでも 1 秒未満にする
- 数字と書式を `cost_ledger.py` の 1 か所に置き、1 行目が `/cost` と一致する性質を保つ

**Non-Goals:**

- issue を閉じたときの合算（#689）、エピックの内訳（#690）、auto-merge と自動クローズへの後追い（#691）、単価のずれ検出（#692）、OpenTelemetry（#693）
- 帰属の規則（区間の境界、issue 番号を拾うコマンド）の変更
- `gh api` の直叩きでのコメント投稿・状態変更、`gh pr create`、`gh pr reopen` をきっかけにすること（#303 の受け入れ条件が挙げる 7 種に限る）

## Decisions

### 1. hook は判定だけをして、残りは切り離した裏のプロセスで行う

1 行積むには `gh` を 3 回呼ぶ（決定 10）。`gh` は 1 回 0.3〜1 秒かかるので、集計をどれだけ速くしても合計は 1 秒を超える。エピックの制約「セッションを 1 秒以上止める処理は裏で走らせる」に当たるので、hook の同期部分はコマンド文字列の判定（`gh` も台帳も触らない）だけにして、対象が見つかったら Python の `subprocess.Popen(..., start_new_session=True)` で作業プロセスを起こし、すぐ `exit 0` する。作業プロセスの標準入出力はすべて `/dev/null` に向ける。

作業プロセスへ渡すのは対象の一覧（リポジトリの指定・番号・きっかけ・時刻・`cwd`）で、引数に JSON で載せる（短い値だけなので ARG_MAX の問題は無い）。再起動できる実体が要るので、いま `gate-report.sh` の中にヒアドキュメントで埋めてある Python 本体を `scripts/gate_report.py` に出す。`gate-report.sh` は fast path と `python3 gate_report.py` の起動だけになる。

時刻は同期部分で取る（小数つきの epoch 秒、ミリ秒まで）。行の時刻はコマンドを実行した時刻であって、裏の処理が終わった時刻ではない。この時刻は行の表示だけでなく、累計をどの時点で切るか（決定 5）と行の並び順（決定 3）も決める。

bats と実測のために、環境変数 `COST_LEDGER_HOOK_FOREGROUND=1` のときは切り離さずにその場で最後まで実行する。

**代替案**: (a) `hooks.json` の `async: true` — スクリプトは同期のまま書けるが、セッションが終わるときに実行中の hook がどう扱われるかが Claude Code 側の挙動で、こちらで保証できない。`gh pr merge` の直後にセッションが終わるのはよくある流れなので、自分で切り離す。子3 の design が `async` を退けた理由（完了を保証できない）もこの点。(b) 同期のまま速くする — `gh` の往復が残るので 1 秒未満にならない。(c) `gh` をやめて行を手元にためておき、あとでまとめて貼る — 貼るきっかけが別に要り、#691 の範囲と重なる。

### 2. コメントの構成: 1 行目に最新の合計、その下に表、最終行に行ごとの正確な値と目印

```
コスト: $39.62 / ¥5,943 @150 — PR #300 (oratta/token-optimize) 帰属: ブランチ

| 時刻 | きっかけ | 金額 | 入出力 | キャッシュ |
|---|---|---|---|---|
| 10/06 07:20 | PR コメント | $16.60 (+16.60) | 900K (+900K) | 33M (+33M) |
| 10/06 12:45 | Ready | $39.62 (+23.02) | 2.1M (+1.2M) | 81M (+48M) |

<!-- cost-ledger:timeline v1 1791238800.120:16.604000:900123:33000111 1791258300.450:39.624100:2100345:81000222 -->
```

- **1 行目は `headline()` の出力**（時刻がいちばん遅い行の累計）。節目のたびにここだけ差し替える。「1 行目だけを取れば `/cost` と同じ行になる」という子1・子3 の性質と、エピックの完了条件「ゲート通過時に PR へ自動で 1 行載る」を保つため。円とレート、対象の表記もここで 1 回だけ出る
- **行は Markdown の表。** 主のイメージは 1 行ごとに「入出力」「キャッシュ」のラベルを書く形だが、表にすればラベルは見出しの 1 回で済み、行が短くなる（読む側のトークンを増やさない制約）。GitHub 上でも桁が揃って見える。載る情報はイメージと同じ
- **行は時刻順に並べる。** 新しい行の時刻が既存のどの行よりも遅い（ふつうの場合）なら末尾に 1 行足し、既存の行は 1 文字も変えない。裏の処理の完了が前後して、後のきっかけの行が先に書かれていたときだけ、時刻順の位置に挿し込み、直後の行の増分だけを書き直す（決定 3）
- **最終行は、行ごとの正確な値と目印を兼ねる隠し行。** 決定 3

時刻は hook を実行したマシンのローカル時刻で `MM/DD HH:MM`（主のイメージどおり。年はコメント自体の作成日時で分かる）。

**代替案**: コードブロックに桁揃えの行を並べる — 全角文字が混ざると桁が揃わず、ラベルを毎行書くぶん長い。

### 3. 行ごとの正確な値をコメントの最終行に持ち、行は時刻順に挿し込む

増分は「その行の累計 − 1 つ前の行の累計」。前の値を表示用の丸めた数字（`2.1M`）から読み戻すと増分が狂うので、最終行の隠し行に丸める前の値を書き、次回はそこから読む。

隠し行は、表の行 1 行につき 1 つの記録 `<時刻>:<金額>:<入出力>:<キャッシュ>` を、表と同じ順に空白区切りで持つ（時刻は小数 3 桁の epoch 秒、金額は小数 6 桁、トークンは整数）。最新の値だけでなく行ごとに持つのは、裏の処理が終わる順番がきっかけの順と入れ替わりうるため。作業プロセスは「対象の確認」の `gh` を済ませてからロックを取る（リポジトリ名が応答で初めて分かるので、ロックの名前をその前に決められない）ので、先のきっかけの処理が `gh` で遅れると、後のきっかけの処理が先にロックを取って先に書く。最新の値しか持たないと、遅れて着いた行を正しい位置に入れたときに、次の行の増分を出し直せない。

行を足す手順は次のとおりで、同じきっかけの集合について、それぞれの処理が同じ内容の台帳を読んだかぎり、どの順で終わっても最終的な本文は同じになる。

1. 新しい行の累計は、きっかけの時刻以前の事実だけで数える（決定 5）。同じ内容の台帳を読めば、裏の処理が動いた時刻に関係なく同じ値になる
2. 新しい記録を、並びの鍵の昇順の位置に入れる。鍵は、きっかけの時刻（ミリ秒まで）、同じならきっかけの呼び名の文字列（UTF-8 のバイト順）、それも同じなら累計の金額・入出力・キャッシュの順。3 つとも同じ記録が既にあれば、同じ節目の二重実行とみなして行を足さず、本文を変えずに返す。既存の行の呼び名は表の「きっかけ」の欄から読む（記録には足さない。記録と行は 1 対 1 で同じ順に並んでいるので読め、隠し行の長さも変わらない）
3. 新しい行の増分は、1 つ前の記録との差。前の記録が無ければ累計と同じ値
4. 並びの上で新しい記録より後ろになる既存の記録があるとき（後のきっかけの処理が先に終わっていたとき）だけ、直後の 1 行の増分 3 項目を「その行の累計 − 新しい行の累計」に書き直す。その行の時刻・きっかけ・累計の表示と、それ以外の行は変えない
5. 1 行目は、いちばん最後の記録の金額から `headline()` で作り直す。遅れて着いた行を途中に挿したときは、1 行目の数字は変わらない

手元には状態を置かない。コメントそのものが状態なので、別のマシンや別のアカウントの置き場所から同じ PR に積んでも増分がつながる。ある節目の書き込みが失敗しても、次の行の増分は「最後に書けた行から」になり、増分の合計は累計と合い続ける。

隠し行が読めない（手で編集された、記録の形が崩れている）ときは、既存の表の行をそのまま残し、新しい行を末尾に足して増分を `(?)` と書く。0 として扱うと「この節目で全額増えた」という誤った行になるため。新しい隠し行は今回の記録 1 つから始める。以後、表の行数が記録の数より多いときは、先頭の余りの行を「記録の無い行」としてそのまま残し、最初の記録の行の増分は `(?)` のままにする。初回（コメントが無い）は前の値を 0 とし、増分は累計と同じになる。

受け入れること: 隠し行は 1 行あたり 45 文字前後ずつ伸びる（`gh pr view --comments` などでコメントを読む側の文字数が、表の行のほかにその分増える）。行ごとの値を持たない案では、終わる順番の入れ替わりを直せないので、この長さを取る。

**代替案**: (a) 台帳の隣に (リポジトリ, 番号) ごとの前回値を持つ — `COST_LEDGER_PATH` が無い環境で動かなくなり、マシンをまたぐと増分が切れる。(b) 最新の値だけを隠し行に持ち、遅れて着いた行は末尾に足す — 行が時刻順に並ばず、遅れた行の増分が「後の節目からの差」になって節目と合わない。(c) 遅れて着いた行を捨てる — 「きっかけ 1 回につき 1 行」が崩れる。(d) 同期部分で順番待ちの札を作って、処理が終わる順番をきっかけの順にそろえる — ロックの名前（リポジトリ名）が同期部分では分からない場合があり、札を持ったまま落ちたプロセスの後始末も要る。

### 4. 数字と書式は `cost_ledger.py timeline` だけが持つ

```
cost_ledger.py timeline (--pr <番号> --branch <ヘッドブランチ> | --issue <番号>) \
    --trigger <きっかけ> --at <epoch 秒> [--repo <cwd>] [--target-repo <owner/repo>]
```

標準入力で既存のコメント本文（無ければ空）を受け取り、行を足した新しい本文を標準出力に返す。hook の側は `gh` の読み書きとコマンドの判定だけを持ち、集計・単価・書式を持たない（子3 の決定を引き継ぐ）。

- 1 行目を作るのは引き続き `headline()` だけ。表の 1 行を作るのは新しい `timeline_row()` だけ（#689・#691 が同じ書式に乗るときの入口になる）
- PR か issue かの判別は hook が済ませて渡すので、`timeline` は `gh` を呼ばない（`cost` の中の判別と二重に問い合わせない）
- 積むものが無いとき（決定 6 の 2 つの場合）は何も出力せず終了コード 3 を返し、hook は何も書かない

トークンの合計は、単価が引けないモデルの行も含めて数える（量は単価と無関係に事実だから）。`summarise()` は未知モデルの行のトークンを数えないので、3 項目の合計は別の小さな関数で出す。

### 5. 累計の定義

| 対象 | 累計 | 同じ値になるもの |
|---|---|---|
| PR | ヘッドブランチに帰属する全行の合計（全セッション・サブエージェント込み） | `/cost <PR番号>` の 1 行目 |
| issue | 実行した作業ディレクトリのリポジトリで、その issue に帰属する区間の合計 | `/cost <issue番号>` の 1 行目 |

累計は**きっかけの時刻（`--at`）で切る**。会話ログの `timestamp` がその時刻以前の応答だけを数える（`timestamp` が読めない行は切れないので数える）。issue の区間分割も、切ったあとの行だけで行う。きっかけの時刻より後の応答は、裏の処理が遅れてそのあいだに台帳に入っていても数えない。保証するのは「同じ内容の台帳を読めば、裏の処理が動いた時刻に関係なく同じ値になる」ことまでで、読む時点で台帳の内容が違えば値は違いうる（決定 7 の書き出しの遅れ）。「同じ値になるもの」の欄は、その時刻より後の応答が無いときに一致する、という意味になる（きっかけの直後に `/cost` を叩いた値）。

入出力トークンは `input_tokens + output_tokens`、キャッシュトークンは `cache_write_5m_tokens + cache_write_1h_tokens + cache_read_tokens`。

issue の累計は区間分割による推定で、末尾の開いた区間は次の投稿までに別の issue を触ると寄せ先が変わる。そのため issue の累計は前の行より減ることがあり、そのときの増分は `(-1.20)` のように負で書く（エピックで主が飲んだ「誤配分」のリスクの現れ方で、新しいリスクではない）。issue を閉じた PR の分を合わせる定義の変更は #689 が行う。

### 6. 積まない場合

- **金額もトークン 2 項目（入出力・キャッシュ）もすべて 0 で、まだコメントが無いとき**は作らない。何も使っていない issue に `$0.00` の行だけのコメントを足しても通知が 1 件増えるだけになる（#303 本文の 5 点目）。既にコメントがあるときは 0 でも積む。金額が 0 でもトークンがあるとき（料金表に無いモデルだけが動いた節目）は積む。トークン量を載せる理由が「金額が動いた原因を量と単価で切り分ける」ことなので、単価が引けない節目こそ量を残す
- **issue の対象リポジトリが `cwd` のリポジトリと違うとき**は積まない。issue の集計は `cwd` のリポジトリで絞るので、`-R` で別リポジトリの issue に書いたときは別の issue の数字を貼ることになる。PR はブランチ名だけで引くので、この制限は無い（子3 と同じ）

### 7. 台帳に無い直近分は、読む前の差分追記で取り込む

`timeline` は他の集計系サブコマンドと同じ入口（`load_facts()`）を通る。`COST_LEDGER_PATH` があれば、会話ログの増えた分を台帳へ追記してから台帳を読む。hook が動くのは応答の途中（Stop hook より前）なので、この差分追記が無いと直近の応答が丸ごと落ちる。追記は差分だけなので 1 秒未満（`cost-ledger-persistence` の要件）。

行の数字は「きっかけのコマンドを呼んだ応答まで」を含む（その応答の `timestamp` はきっかけの時刻より前になる）。そのコマンドのあとの応答は、決定 5 の切り方で外れ、次の行の増分に入る。きっかけの時刻以前の `timestamp` を持つ応答が、裏の処理が台帳を読んだあとで会話ログに書かれた場合（書き出しの遅れ）は、その分はその行に入らず、そのあとで台帳を読んで積まれる行の増分に入る。累計はその行で合う。既に積んだ行の累計を、あとから書き直して合わせることはしない（積んだ行の累計を書き換えない性質を優先する）。

`COST_LEDGER_PATH` が未設定でも動く（会話ログを直接読む）。そのときは集計に数秒かかるが、裏で走るのでセッションは止まらない。

### 8. issue の集計は、その issue を触ったセッションの行だけを読む

いまの `cmd_issue` は全行を JSON として読んでから区間に切る（台帳 157,000 行で 0.85 秒、行数に比例して伸びる）。区間は `sessionId` ごとに切るので、その issue を触った行が 1 つも無いセッションは結果に関係しない。そこで台帳を 2 回なめる: 1 回目は `"issues": []` でない行だけを読んで、その issue 番号を含むセッションを集める。2 回目はそのセッションの行だけを JSON として読む。実測の見込みは 2 回合わせて 0.5 秒前後で、結果は全行を読んだ場合と同じになる。`/cost <issue番号>` も同じ読み方に乗せ、値が変わらないことを bats で固定する。

台帳が未設定のとき（会話ログの直読み）はこの絞り込みをしない。

### 9. きっかけの集合と呼び名、対象の解決

| コマンド | 行の「きっかけ」 | 積む前に確かめること |
|---|---|---|
| `gh pr comment` | `PR コメント` | PR が存在する |
| `gh issue comment` | `issue コメント` | issue が存在する |
| `gh pr ready` | `Ready` | `draft` が false（`--undo` は対象外） |
| `gh pr close` | `PR クローズ` | `state` が closed |
| `gh pr merge` | `マージ` | マージ済み |
| `gh issue close` | `issue クローズ` | `state` が closed |
| `gh issue reopen` | `issue 再オープン` | `state` が open |
| 合格ラベルの付与（既存の判定） | `ゲート通過` | ラベルが付いている |

- コマンドの読み取りは既存の字句解析（変数・`for`・サブシェルの扱い、評価も再実行もしない）をそのまま使う
- 対象の番号は、最初の位置引数が数字ならその番号、`https://github.com/<owner>/<repo>/(pull|issues)/<番号>` の URL ならそのリポジトリと番号。`gh pr comment` / `gh pr ready` / `gh pr merge` で位置引数が無いときは、`cwd` の現在のブランチの PR（`gh api 'repos/{owner}/{repo}/pulls?head={owner}:{branch}&state=all'` の先頭）。ブランチ名の位置引数など、それ以外は飛ばす
- リポジトリは gh と同じ順（`-R` / `--repo`、前置きの `GH_REPO`、どちらも無ければ `cwd`）。`cwd` の場合は `gh repo view` を別に呼ばず、問い合わせのパスを `repos/{owner}/{repo}/...` と書いて gh 自身に埋めさせ、応答の `base.repo.full_name`（issue は `repository_url`）からリポジトリ名を得る
- 1 つの Bash コマンドに同じ対象へのきっかけが複数あるときは 1 行にまとめ、きっかけを実行順に `+` でつなぐ（例: `PR コメント+Ready`）。累計は同じ時点の同じ値なので、行を分けても増分 0 の行が増えるだけ
- 状態変更は実測してから積む（子3 の「付与を実測してから貼る」と同じ理由。PostToolUse はツールが終わったことしか伝えず、複合コマンドの中のどれが成功したかは分からない）。コメントの投稿は確かめない: 確かめるにはコメントの一覧と時刻の突き合わせが要り、外れても余分な行が 1 行付くだけで数字は正しい
- `gh issue comment <番号>` の番号が PR だったときは PR として扱う（累計はブランチ合計、きっかけは `PR コメント`）。`gh issue close <番号>` は `PR クローズ` に読み替え、`gh issue reopen <番号>` は積まない（PR の再オープンは #697 の範囲）
- `ゲート通過` の対象は PR だけ。合格ラベルを PR でない issue に付けても積まない（対象の確認が `pulls/<番号>` なので、issue の番号は「存在しない」になる）
- トークンの表示は、四捨五入した結果が次の単位に届くときは次の単位で書く（999,999 は `1.0M`、9,999,999 は `10M`、999,999,999 は `1.0B`）

### 10. `gh` の呼び出しは対象 1 件あたり 3 回

1. 対象の確認: `gh api repos/<リポジトリ>/pulls/<番号>`（`gh issue ...` のきっかけは `issues/<番号>`）。存在・種別・状態・`draft`・マージ済みか・ラベル・ヘッドブランチ・リポジトリ名をこの 1 回で取る
2. 既存のコメント: `gh api --paginate 'repos/<リポジトリ>/issues/<番号>/comments?per_page=100'` で目印を含むコメントの id と本文を取る（100 件ごとに 1 ページ）
3. 書き込み: 既存があれば PATCH、無ければ POST

`gh issue ...` の番号が PR だったときだけ、ヘッドブランチを取るために `pulls/<番号>` をもう 1 回呼ぶ（4 回）。回数は PR の数にも行の数にも比例しない。いまのゲート通過時は 4〜5 回（ラベルの確認・`cost` の中の判別・コメントの検索・書き込み、`-R` 無しなら `gh repo view`）なので、1 回あたりは減る。

PATCH が失敗しても POST に切り替えない（コメントを増やさないことを優先する。子3 と同じ）。

### 11. 既存のゲート通過時のコメントとの関係

ゲート通過は、同じ 1 本のコメントに `ゲート通過` の行として積む。合計の行と時点の行だけを持つ古い形のコメント（目印 `<!-- cost-ledger:gate-report -->`）は作らなくなる。1 行目が `/cost` の 1 行目と一致する性質は、新しいコメントの 1 行目が引き継ぐ。

目印は新しくする（`<!-- cost-ledger:timeline`）。古い目印のコメントは探さず、書き換えも削除もしない。古い形の本文には状態の行が無く、表に変換する規則を足すほどの価値が無いため。切り替えの時点で古いコメントが付いている進行中の PR は、次の節目で新しいコメントがもう 1 本付く（古い方は最後の合計のまま残る）。

### 12. 同じコメントへの同時の書き込みはロックで直列にする

裏のプロセスは複数同時に走りうる（サブエージェントが続けてコメントする、`for` で複数の対象に書く）。同じコメントを読んでから書くまでの間に別のプロセスが書くと、片方の行が消える。対象ごとのロックファイル（`${TMPDIR:-/tmp}/cost-ledger-timeline/<owner>__<repo>__<番号>.lock`）に `flock` の排他ロックを取ってから、コメントの読み取り・`timeline`・書き込みを行う。子3 は「2 本できても次で直る」として受け入れたが、行を積む形では消えた行が戻らないので持つ。ロックは読んでから書くまでを直列にするだけで、取る順番はきっかけの順と入れ替わりうる。入れ替わっても結果が同じになるようにするのは決定 3 の挿し込み。

別のマシンから同時に書く場合は防げない（GitHub のコメント API に条件付き更新が無い）。そのときは片方の行が消えるが、次の行の増分が消えた分を含むので累計は合う。

### 13. 名前は据え置く

スクリプト `gate-report.sh`、緊急停止の環境変数 `COST_LEDGER_GATE_REPORT=off`、spec `cost-ledger-gate-report` の名前は変えない。役割は「ゲート通過の報告」より広がるが、名前を変えると `hooks.json`（聖域のパス）の変更と、利用者の `settings.json` の書き換えが要る。`COST_LEDGER_GATE_REPORT=off` は、積む処理すべてを止める。

## Risks / Trade-offs

- [裏のプロセスが途中で落ちる・`gh` が失敗すると、その節目の行が付かない] → 何も出力しない設計なので気づけないが、次の行の増分が落ちた分を含むので累計と増分の合計は合う。頻度は実機確認（tasks 5）で `gh` の失敗が無いことを見る
- [hook が起動する Bash 呼び出しが増える（`gh pr view` などは fast path で落とすが、7 種のコマンドでは python3 が起動する）] → 同期部分の所要時間を実測して PR に書く。目標は対象のコマンドで 0.2 秒以下、対象外で 50 ms 未満
- [コメントの本文は 65,536 文字までで、表の行と隠し行の記録を合わせて 1 行 115 文字前後なので、550 行前後で PATCH が失敗し、以後の行が付かなくなる] → 1 つの PR に 550 回の節目は現実の運用で起きない（多い PR で数十回）ので対処しない
- [コメントの投稿は確かめないので、`gh pr comment` が失敗した複合コマンドでも行が付く] → 行の数字は正しく、きっかけの名前だけが実際と合わない。Bash 全体が 0 以外で終わった場合は PostToolUse 自体が起動しない
- [issue の累計が前の行より減ることがある] → 決定 5。増分を負で書く
- [切り替え時に進行中の PR で、古い形のコメントと新しいコメントが 2 本並ぶ] → 決定 11。対象は切り替え時点でゲート通過済みかつ未マージの PR だけ
- [コメントの新規作成は PR / issue ごとに 1 回、通知が飛ぶ。編集で飛ぶかは未確認] → 受け入れ条件どおり実機で確かめて PR に書く（tasks 5）

## Migration Plan

- `hooks.json` は変えないので、反映は通常のプラグイン更新だけで済む
- 止めたいときは `COST_LEDGER_GATE_REPORT=off`。戻すときは PR を revert する（コメントは残るが、以後は積まれない）
