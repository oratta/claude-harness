### Requirement: epic-dispatch.sh の wait は止まった子を判断し、通すものには返事を送って待ちを続ける
`plugins/dev-workflow/scripts/epic-dispatch.sh wait` は `--resolve <epic>` を受け付けなければならない（MUST）。`<epic>` が数字でなければ使い方を出して exit 1 で終わる（MUST）。`--resolve` は `--watch-stopped` と位置引数の子が 1 件以上あるときだけ働き（SHALL）、それ以外では何もしない。`--resolve` の有無で止まりの検知の条件は変えず、違うのは判断を呼ぶかどうかだけである（MUST）。

`--resolve <epic>` が働くとき、`wait` はポーリングで止まった子（既存の要件のとおり記録の `stop` が `stopped-seen` に書き換えられた子）ごとに、次を行わなければならない（MUST）。

1. 判断のコマンド（環境変数 `EPIC_DISPATCH_JUDGE`。既定は `epic-dispatch.sh` と同じディレクトリの `stop-judge.sh`）を `<epic> <child> <止まりの JSON のパス>` を引数に 1 回呼ぶ。会話ログを読めなかった止まりは JSON が無いので `<epic> <child>` で呼ぶ
2. 判断の出力の 1 行目が `判断: 通す` で、3 行目が `返事: ` に続く空でない文なら、要件「epic-dispatch.sh reply は子の端末に送り手を付けた返事を届ける」の `--as parent` と同じ処理でその文を子に送る。結果が `sent` か `relaunched` なら、エピックに `親の判断: 子 #<child> 通した — <2 行目の 理由: のうしろ> 発言 <止まりの uuid か 不明>` の 1 行（4 行目の `記録:` のうしろが URL なら、末尾に空白とその URL を足す）をコメントする。投稿できたらその子を出力に含めない。投稿に失敗したら、その子を `unrecorded` に含め、stderr に投稿し直すコマンド（`gh issue comment <epic> --body <その 1 行>`）を出す（エピックへの記録は送信のあとに投稿する。送る前に投稿すると、送れなかったときに通していない判断が残るため）
3. 判断が `判断: 主に上げる` なら、子 issue に 1 行目 `親の判断: 主に上げる`、2 行目 `止まりの発言: <止まりの uuid か 不明>`、3 行目 `停止の記録: <4 行目の 記録: のうしろ>`、4 行目以降に判断の理由を書いたコメントを投稿し、その子を `stopped` に含める
4. 判断のコマンドが非 0 で終わった・出力が 1〜4 行目の形で読めない、または判断が `判断: 通す` で送れなかった（`failed`）なら、子 issue に 1 行目 `親の判断: 判断できなかった`（送れなかったときは `親の判断: 通すが送れなかった`。判断は通すで送信だけが失敗したことを事実どおりに書く）、2 行目 `止まりの発言: <止まりの uuid か 不明>`、3 行目 `停止の記録: <URL か なし>`（判断の出力から読めたときだけ。読めなければ `停止の記録: 不明`）、4 行目以降に何が失敗したかと（あれば）送るはずだった返事を書いたコメントを投稿し、その子を `stopped` に含める。判断の出力そのものはコメントに貼らない（MUST NOT。判断の入力には gitignore 済みの `.claude/casting/local.md` も入り、出力に引用されうるため。見たいときのために stderr にだけ出す）
5. 判断が `判断: 問いではない` なら、記録の `stop` を `resumed` に戻し（`stop_uuid` は残す）、stderr に `問いではない <child> <理由>` を出し、子にも issue にも何も送らず、その子を出力に含めずに待ちを続ける（MUST）

`--resolve` が働く `wait` の出力は、`closed <N>...`・`done <N>...`・`stopped <N>...`・`unrecorded <N>...` を該当するものだけこの順に（1〜4 行）出して exit 0 とする（MUST）。`unrecorded` は「返事は子に届いたが、エピックへの 1 行を残せなかった」子で、親を起こして記録させるために出す。この出力の規定は、`--resolve` が働く場合に限り、既存の要件「epic-dispatch.sh は子が止まった印を付け、wait が止まった子を返す」と「エピックの子の止まりの手順と、親が stopped を受けて報告する手順を規定する」が定める `closed`・`done`・`stopped` の 1〜3 行の規定に優先する。`--resolve` が働かない `wait` は、`unrecorded` を出さず、従来どおり 1〜3 行を出さなければならない（MUST）。ポーリングで `stopped` にも `unrecorded` にも含める子が 1 件も無く、閉じた子も完了の印の子もいなければ、`wait` は待ちを続けなければならない（MUST）。

子 issue への `親の判断:` のコメントの投稿に失敗しても、その子は `stopped` に含める（MUST）。stderr に投稿し直すコマンドを出す（SHALL）。親は子 issue の `親の判断:` のうち、2 行目の `止まりの発言:` が今の止まりの uuid と一致するもの（uuid が空の止まりは、3 行目の `停止の記録:` が最新の `子の停止: 主の返事待ち` のコメントの URL と一致するもの）だけを今回の判断として読む（要件「Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる」）ので、投稿に失敗して前回の判断が残っていても、親はそれを今回の判断と取り違えず、判断が無いものとして扱う（要件「Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる」の手順 8 で親が照らす）。

### Requirement: Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる
develop の `references/epic.md`「エピックの扱い」→「回し方」の Orca 経路の手順は、次を規定しなければならない（MUST）。この要件は、要件「エピックの子の止まりの手順と、親が stopped を受けて報告する手順を規定する」の親の側のうち、`stopped` で起こされたら記録を読んでユーザーに報告する規定と、止まった子への返事の仕方を #1034 で決めるとする規定に優先する。

- 動いている子を待つ `wait` には、`--watch-stopped` に加えて `--resolve <エピック番号>` を付ける（MUST）。通すと判断された止まりは `wait` の中で返事が送られ、親は起こされない
- `wait` の出力が `closed`・`done`・`stopped`・`unrecorded` の 1〜4 行であることを書く（MUST）。この 1〜4 行は `--resolve` を付けたときだけで、要件「エピックの子の止まりの手順と、親が stopped を受けて報告する手順を規定する」の `closed`・`done`・`stopped` の 1〜3 行とする規定に優先する。`--resolve` を付けない `wait` の出力は従来どおり 1〜3 行であることも書く（MUST）

### Requirement: 親が通してよい範囲の基準は、CI の見張りのやり直しの上限で止まった子の扱いを決める
`parent-pass-criteria.md` は、表でなく文章の節で、CI の見張りのやり直しの上限で止まった子を親が通すか主に上げるかを一通りに決めなければならない（MUST。条件表の 9 条件は増やさない。対象・通す場合・主に上げる場合・返事・同じ件の定義は下の場面で定める）。

この要件の守備範囲で入力として扱うのは、`stop-judge.sh` が集める止まりの JSON の子の最後の発言（更新前の版の子は最新の停止の記録）と過去の `親の判断:`、および手順 8 で親のセッションが読む同じ発言と記録である。拾いたい誤りは、差分に起因する失敗のやり直しを通し続けること、`job-timeout`・ランナーの確認を含む止まりを通すこと、やり直しの回数を使い切っただけの止まりを主に上げることの 3 つである。次は通ってよい: 子が差分に起因する失敗を「因果を持たない」と書き誤った記録を通すこと（損失は CI 1 周分で、再び止まれば次は主に上がる）／通してよい止まりを判断のモデルが主に上げること。すり抜けを塞ぎ切ることは完了条件としない。

#### Scenario: 基準のファイルが対象の止まりを子の停止の記録から見分けられる形で定めている
- **WHEN** `parent-pass-criteria.md` の CI の見張りのやり直しの上限の節を読む
- **THEN** 対象は、同じ HEAD のやり直しを使い切って見張りがやり直せないことが、子の最後の発言のどこに書かれていても（更新前の版の子は記録のどの項目に書かれていても）挙げている止まりで、`job-timeout` の `escalate`（落ちたチェックに `real` が混ざらず `job-timeout` を含むときの `escalate`）は記録にそう書かれていなくても常に対象とする（`pr-state.sh` の `decide` は、その場合に同じ HEAD のやり直しを使い切ったあとで返すため）。経路は `job-timeout` を含む失敗の `escalate` と `ci-watch.md` 7 の手順 7 で上げたものの 2 つ、修正回数の上限（3 回目の失敗）の `escalate` は対象外と書かれている

#### Scenario: 基準のファイルが通す場合と主に上げる場合を決めている
- **WHEN** 同じ節を読む
- **THEN** 手順 7 で上げた止まりは、9 条件に加えて失敗が差分と因果を持たない・推奨が再実行だけ・`cause` が `job-timeout` でない、のすべてを満たすとき通し、`job-timeout` の `escalate`・判断できないとき・確認してからの再実行は主に上げると書かれている

#### Scenario: 基準のファイルが返事の中身を決めている
- **WHEN** 同じ節を読む
- **THEN** 返事は、まず `ci-watch.md` 2 の重複の確認をし（別のセッションが見張り中なら何もせずに主に伝える）、落ちたチェックを同じ HEAD で 1 回だけ手でやり直し、次に、止まるときに付けた `needs-approval` を外すこと（手順 7 の経路で止まった子。付けたままだとやり直しが通ったあと見張りが待たずにオーナーへマージを頼んで終わるため。ただし外す前に PR の events で、最後の `needs-approval` の labeled が止まる前の最新の `CI 見張り開始:` のコメントより前なら、子が付けたものではないので外さず主に上げる）と、`CI 見張り開始:` の投稿をすること（開始の記録なしに始めると別のセッションが見張りを重ねうるため）を済ませ、そのうえで `ci-watch.md` 2 の `escalate` のあとの再開手順で見張りに戻ってよい、という内容で、`ci-watch.md` は変えないと書かれている。通すときの `理由:`（`親の判断: 子 #N 通した — <理由> <記録の URL>` の `<理由>` になる）には、PR 番号・落ちたチェック名・HEAD の短い SHA を、子の停止の記録から取って書くと定められている。記録に無い値は作らず `不明` と書き、HEAD が `不明` の過去の判断とは同じ件かを見分けられないものとして扱う（次の判断が、過去の `親の判断:` と同じ件かを見分けるため）

#### Scenario: 基準のファイルが「繰り返していない」との関係を決めている
- **WHEN** 同じ節を読む
- **THEN** 見張りの上限と「繰り返していない」が別の歯止めであること、同じ件は同じ PR の同じチェックで HEAD が変われば別の件であること、同じ HEAD で許したあとにまた止まった同じ件は主に上げること、条件表が 9 条件のままであることが書かれている

### Requirement: 子は声かけにだけ返し停止の状態を保つ

判定の守備範囲は要件「子への声かけ文と返事の形は一か所の定義を共有する」の「判定要件に共通の守備範囲」に従う。

子は、停止前に共通定義を読み、固定文の受信を通常の主の返事や親の判断より先に分類し、定義どおりの一行だけ返さなければならない（MUST）。声かけの受信ターンではツール・調査・作業・停止コメントの投稿を行ってはならない（MUST NOT）。固定文と完全一致しない実際の返事が届いた場合は従来の再開手順に従う（SHALL）。固定文は主が入力した場合も予約文として扱い、送信元の識別を追加しない（SHALL）。

#### Scenario: 主の返事待ちを継続する
- **WHEN** 質問して止まり、親が停止を受けて stop=stopped-seen になった子に固定文が届く
- **THEN** 子は指定の一行だけ返し、status/stop・最新の停止記録の URL と本文は変わらず、元の質問が未回答のまま残る

#### Scenario: 通常の返事は再開する
- **WHEN** 声かけ後に、固定文に完全一致しない主の直接の返事または正規の親からの返事が届く
- **THEN** 子は声かけの返事として扱わず、続きの作業に進む
