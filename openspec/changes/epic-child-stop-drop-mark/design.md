# Design

## Context

動機は `proposal.md` の Why。1 本目の Non-Goals と Risks に「2 本目で消える」「1 本目で子の `mark` を残す理由」と書いた分を、ここで片付ける。

今の子の手順（`references/epic-child-stop.md`）は、止まるたびに 7 項目の記録を投稿し、`mark stopped` を呼ぶ。親の側は、記録の `止まった理由:` の値の頭で次のように分岐している。

| 値の頭 | 親の分岐 | 読む箇所 |
|---|---|---|
| `PR のマージ待ち（` | 決める役に判断させ、印を付ける | `epic.md` マージ待ちの子、`parent-merge-criteria.md`:3 |
| `PR トークン上限（` | 親の権限に照らす。数字も値から読む | `epic.md` PR トークン上限の子 |
| 値の頭では見ない（CI の見張りの上限） | 記録の本文から PR・チェック名・HEAD を読み、基準の節で判断する | `parent-pass-criteria.md`:37-49 |

記録の無い止まりは 1 本目で扱えるようになった（`child-log --last` の全文を読み、問いでなければ `dismiss`、問いなら組み立てて主に上げる）。足りないのは、上の 3 種を記録なしで見分ける手段である。

## Goals / Non-Goals

**Goals:**

- 子の手順から、親に気づかせるためだけの義務をなくす
- マージ待ち・PR トークン上限・CI の上限の分岐を、記録なしで今と同じに動かす
- これらの止まりが `問いではない` で黙って落ちないようにする

**Non-Goals:**

- `pass.md` の親経由の受領と `owner-reply-check.sh --relayed` / `--delegated` の変更
- `wait` の検知の条件の変更
- `mark` サブコマンドの削除（決定 1）
- `references/epic-child-stop.md` を読むかどうかの 2 段の条件（`route` が `nested`）の変更。読まなかった子の害は、定型の止まりが普通の問いとして親に届くこと（下の Risks）と、リスク許容の親経由の受領が子のタブでの返事に倒れることで、どちらも安全側に止まる

## Decisions

### 1. `mark` は 4 種とも受け続け、`stopped` / `resumed` の呼び出しを手順書から消す

| 案 | 利点 | 欠点 |
|---|---|---|
| **採用: 受け付けを残し、手順書から呼ばない** | スクリプトの変更がコメントだけ。更新前の版の子が呼んでも今どおり動く。`wait` の印の子の処理も生きる | 新しい子からは呼ばれない経路が残る |
| 不採用: `stopped` / `resumed` を種別から消す | 経路が減る | 動いている更新前の子の `mark stopped` が exit 1 になる。`epic-dispatch.bats` の `mark` と印の子の検査の数十件を書き換える。残りの PR トークンに合わない |

`done` / `waiting` は親の完了と片付けの判定に要るので、義務も含めて変えない。再開は `wait` の `resume_moved` が会話ログの進みで書くので、`mark resumed` が無くても `stopped-seen` は `resumed` に戻る（`epic-dispatch.sh:1492-1506`）。親の見張りが動いていない間も、`pending-owner` と `keepalive` は会話ログの進みを見るので、再開した子を止まったままとは扱わない。

### 2. 定型の止まりは、最後の発言の末尾の `止まった理由:` の行で渡す

子は、定型の止まりでターンを終えるとき、最後の発言の末尾に行頭 `止まった理由: ` の行を書く。値の形は今の記録と同じにする。

```
止まった理由: PR のマージ待ち（human-merge）: <PR の URL>
止まった理由: PR トークン上限（合計 <合計> / 上限 <上限>）: 続けるか、範囲外として閉じるか
終わるまでの見込み: あと約 <残り>（合計の見込み <見込み>）
続けるべきか: <続ける／閉じる と理由>
次に絞る範囲: <残工程のうち何に絞るか>
止まった理由: CI の止まり（<PR の URL> / <落ちたチェック名> / <HEAD の短い SHA か HEAD 不明>）: <主にしてほしいこと>
```

末尾に置くのは、`child-log --last` と止まりの JSON が発言の末尾を残して切るため（上限 8000 文字）。

| 案 | 採らない理由 |
|---|---|
| 親が最後の発言の自由文から止まりの種類を読み取る | 分岐が読み手の解釈で揺れる。PR トークン上限は (a)(b) の数字を読むので、決まった形が要る |
| 定型の止まりだけ記録を残す | 記録の場面を絞る主の決定に反する。手順を読まない子には効かない点も同じ |
| PR のラベルや計測から親が機械で止まりの種類を判定する | `epic-dispatch.sh` に出力を足すことになる。既存の要件「epic-dispatch.sh にマージ待ちを返す出力を足さない」にも反する |

子がこの行を書かなかったときは、普通の問いとして親に届く。マージと PR トークン上限の引き上げは基準で通らないので主に上がり、害は親の判断を経ない分だけ主の手間が増えること。これは義務というより、親の自動の分岐に乗るための形である。

**今回の止まった理由。** 親の読み方を 1 か所に定義する: 今回の停止の記録があればその `止まった理由:` の値、無ければ `child-log --last` の `.text` の行のうち、行頭が `止まった理由: ` の最後の行の値。記録を先に見るのは、更新前の版の子が記録を残し続けるため。`epic.md`・`parent-merge-criteria.md` の分岐の文はこの語に置き換える。

**信用の扱い。** 記録には `author_association` の条件があったが、発言には無い。ただし発言も記録も書き手は同じ子のセッションで、外の文章を発言に引用すれば行が偽装される余地があるのは記録も同じだった。行を読んだあとの分岐は、どれも別の確かめを通る: マージ待ちは PR の本文の参照・ラベル・HEAD を `gh` で確かめて決める役が判断する。PR トークン上限は主が承認した権限の内しか通さない。CI は基準の節に照らす。よって親が読む入力として受け入れる。公開のコメントに発言を引用しない決まり（1 本目）は変えない。`親の判断:` の `理由:` には PR 番号・チェック名・SHA だけを書く。

### 3. `止まった理由:` の行がある止まりを `問いではない` に落とさない

1 本目では、記録のある止まりは `問いではない` が形の崩れになるので、マージ待ちなどが黙って落ちることは無かった。記録をなくすとこの守りも無くなる。

- `stop-judge.sh`: 止まりの JSON の `.text` に行頭 `止まった理由: ` の行があるのに `判断: 問いではない` を出したら、形の崩れとして exit 1 にする。`wait` の側で判断の失敗になり親が起きる（既存の経路）
- `epic.md` 手順 8: `dismiss` の条件に、最後の発言に `止まった理由:` の行が無いことを足す

基準の文の指示だけにしないのは、誤ったときの害（子がマージ待ちのまま誰にも上がらない）が大きく、検査が 1 行で済むため。

### 4. 記録を残す場面の定義

「PR のリスク許容で止まるとき」は、pr-review-gate 手順 3 の宣言に対する主の許容を待って止まるときを指す。`--delegated` の条件（`needs-approval` と `## リスク宣言` のコメント）と同じ止まりで、委任の 4 条件の文は変えない。

- 親経由の返事を確かめられず主に子のタブでの返事を頼むときの「止まる前の記録と印」は「止まる前の記録」にする。リスク許容の止まりなので記録は要る
- 引き継ぎを先に投稿する順序は、記録を残す場面でだけ効く。引き継ぎそのものの決まりは変えない
- 記録の 7 項目の説明のうち、CI の見張りと PR トークン上限の項は定型の行の説明へ移す。マージ待ちの 6 項目の例（`ci-watch.md`）は、最後の発言に書く内容の例に直す

記録を残さない止まりでも、親と主が読むのは最後の発言だけになるので、発言の中で質問・推奨・根拠を中身で書くことを 1 文残す。書き方の正本は `rules/communication-style.md`。

### 5. PR トークン上限の `停止の記録:` の行

`PR トークン上限:` の 4 行のコメントの `停止の記録:` は、今も `<URL か なし>` を許す。記録が無くなる子は `なし` を書く。書式は変えない。親の返事の URL は権限のコメントの URL なので影響しない。

## Risks / Trade-offs

- [会話ログの形が変わると、新しい子の止まりが見えなくなる] → 1 本目の Risks では `mark` の経路が残るとしていたが、この change でその経路は更新前の子だけになる。親は見張りを `timeout` で掛け直すだけになる。手順 2 の最初の通知、待ちをやめる前の `needs-approval` の確認は残る。ログの読み取りの検査は `epic-stop-from-log-scenario` と `child-log-read` の bats にある。起きる条件は Claude Code の更新でログの形が変わったときで、頻度は分からない。調べるには更新のたびに `child-log --last` が値を返すかを見る
- [背景のタスクの実行中に定型の止まりをすると、親に届くのが最大 30 分遅れる] → 今は `mark stopped` で印の子は待ち時間を飛ばしていた。定型の止まりはどれも見張りを終えてから止まるので、背景のタスクが残ることは少ない。遅れるだけで止まりは落ちない
- [親に届くまで最低 120 秒かかる] → 今の印の子はターンの終わりで返る。人の返事の時間に比べて小さいので受け入れる
- [`問いではない` の誤りで、記録があれば守られていた止まりが落ちる] → 定型の止まりは決定 3 で守る。それ以外の問いは 1 本目と同じ扱いで、迷えば主に上げ、親の状態表の最後の発言で見つかる
- [`stopped-seen` の子が親の見張りの外で再開すると、記録が `stopped-seen` のまま残る] → 次の `wait` が会話ログの進みで `resumed` に書く。`stop_uuid` が空のまま残るのは会話ログを読めない印の子だけで、更新前の子に限られる
- [判断の回数が増える] → 記録の有無は検知の条件に関係しないので増えない

## Migration Plan

互換の処理は作らない。動いているエピックの更新前の子は、記録と `mark` を今までどおり残し、親は「今回の止まった理由」の定義で記録を先に読む。戻すときは PR を revert する。
