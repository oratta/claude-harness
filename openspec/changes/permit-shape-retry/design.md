# Design

## Context

動機は proposal.md の Why を参照。今の仕組みの要点は次のとおり。

- 許可を書くスクリプト（`plugins/dev-workflow/scripts/git-guard-permit.sh`）は、記録の置き場所と中身を確かめたあと、共通ファイル `git-guard-scratchpad.py` の `check_command`（git 用の `check` か rm 用の `check_rm`）で一時領域の判定をし、落ちたら `git-guard-permit: 許可を書かない: 一時領域の判定を満たさない: <理由>` を stderr に書いて 1 で終わる。理由の文には、コマンドの形のもの（許していない文字・`&`・cd と git 以外のコマンド・`-C` の規則など）と、場所のもの（scratchpad の中にない・作業ディレクトリが無いなど）が混ざっている
- develop の本体は、そのスクリプトが 0 以外で終わったらオーナーに上げる（`skills/develop/SKILL.md`「1 ループ」の `returned no output` を含む段落）
- hook は子のコマンドを丸ごと拒否するので、`準備 && 破壊的な操作` の形では準備も走っていない。子への拒否の理由文は、すでに「変数を使わず実パスで単独のコマンドとして打つ」打ち方を案内している（hook は変えない）
- 子への拒否の回数は hook が数え、2 回目以降は子を打ち切る（`continue: false`）。回数を 0 に戻すのは許可を書けたときだけ
- 並列に動くエピック #1476 の兄弟: #1159 は `git-guard-scratchpad.py` の `check_rm` と cd の規則を直す。#1166 と自動消化の #1463 は `git-destructive-guard.sh` を直す

## Goals / Non-Goals

**Goals:**

- 親が、スクリプトの終了コードだけで「打ち直せば判定し直せる形の理由」と「それ以外」を見分けられる
- 形の理由で断られた操作を、親が 1 回だけ打ち直させ、新しい拒否の記録で許可の手順をやり直せる
- 判定の共通ファイルと hook に手を入れない（兄弟の子と差分を重ねない）

**Non-Goals:**

- 一時領域の判定（何を許可するか）を変えること。`cd <dir> && rm …` を許可できるようにするのは #1159
- 子への拒否の理由文や、拒否の回数・打ち切りの数え方を変えること
- rm の確認画面の hook（`rm-permission-guard.sh`）の振る舞いを変えること。ただし許可を書くスクリプトは rm の記録も扱うので、終了コード 3 の振り分けは rm の記録にも同じ規則で効く

## Decisions

### 決定 1: 形の理由かどうかは、許可を書くスクリプトがコマンドの形だけで決める

判定に落ちたとき、記録の `command` が「単独のコマンドの形」（使う判定が許す文字だけでできていて、`;`・`&`・改行を含まない）でなければ 3、そうなら 1 で終わる。使う判定が許す文字は、共通ファイルが持つ git 用と rm 用の文字の集合を、`check_command` と同じ決め方（`is_rm_command`）で選んで使う（スクリプトに文字の集合を書き写さない）。

検討した案:

- 案 A（採らない）: 共通ファイルの `check` / `check_rm` の戻り値か理由の文に、形か場所かの種類を付ける。理由を返す行をすべて書き換えることになり、#1159 が同じ関数を直すので差分が重なる。hook も同じ関数を使うので、hook 側の呼び出しにも影響する
- 案 B（採らない）: スクリプトが理由の文の書き出しで見分ける一覧を持つ。#1159 などが理由の文を変えると黙ってずれる（ずれたら、形の理由がオーナーに上がるか、場所の理由で打ち直しを頼むかのどちらか）
- 案 C（採る）: 理由の文を見ず、コマンドの形だけで決める。単独のコマンドに打ち直すと何が変わるかは、まさに「変数・引用符などの文字」と「区切り」の有無なので、指示の中身（実パスで単独のコマンド）とそのまま対応する。共通ファイルの関数は読むだけで、書き換えない

案 C では、形と場所の両方で落ちるもの（`cd <外> && git reset --hard` など）も 3 になり、打ち直したあとの場所の判定で 1 になってオーナーに上がる。往復が 1 回増えるが、許可は書かれない。

### 決定 2: 振り分けは打ち直しを頼むかの目安にとどめ、守りは今の判定に任せる

3 を受けた親は許可を書かず、子に打ち直しを頼むだけである。許可は、打ち直したコマンドの新しい拒否の記録に、今までと同じ判定をかけて満たしたときだけ書かれる。したがって、分類が外れても（形でない理由に 3 を返しても、その逆でも）、一時領域の外への許可は書かれない。分類の外れで起きるのは、余分な往復が 1 回増えるか、打ち直せたはずのものがオーナーに上がるかのどちらかだけである。

### 決定 3: 打ち直しは 1 つの W の 1 つの操作につき 1 回まで

打ち直したコマンドでスクリプトがまた 0 以外（3 を含む）で終わったら、オーナーに上げる。子が指示どおりに打ち直せない場合に、親と子の往復が続くのを止めるため。回数は本体が自分の手元で覚える（記録先やファイルには書かない。打ち直しの指示は同じ W を SendMessage で再開するので、本体のコンテキストに残る）。

### 決定 4: 準備は別の呼び出しで先に済ませるよう指示する

hook はコマンドを丸ごと拒否するので、`準備 && 破壊的な操作` の準備は走っていない。破壊的な操作だけを打ち直しても、対象の repo が無ければ判定に落ちる（`git の作業ディレクトリ … が無い`。単独の形なので 1）。そこで指示に「破壊的でない準備は別の Bash の呼び出しで先に済ませてよい」を入れる。

### 決定 5: 打ち直しで打ち切られた空の return には、報告を 1 回だけ求め直してよい

打ち直したコマンドも拒否されるので、子への拒否の回数は 2 以上になり、hook が子を打ち切る（`continue: false`）。子は報告を書けずに空の return で返りうる。既存の「空の return には報告を 1 回だけ求める」をこの打ち直しのあとにも使えるようにし、打ち直しの指示は「同じ指示での起こし直し」に数えない。拒否の回数を 3 で戻す案（スクリプトが 3 で終わるときに回数のファイルを消す）は採らない。回数を戻すのは許可を書けたときだけ、という今の要件を変えずに済むため。

### 決定 6: SKILL.md の書き場所

今の段落（`returned no output` を含む 1 段落）に、オーナーに上げる条件の「スクリプトが 0 以外で終わった」の例外（3 で打ち直しの条件を満たし、まだ指示していないとき）だけを足し、打ち直しの手順は直後の新しい段落に書く。今の段落はすでに長く、手順を足すと読み落としやすくなるため。既存の bats が今の段落に求める文字列（`0 以外で終わった` など）は残す。

## 実機確認の手順（implement の段で行う）

受け入れ条件の 2 件を、`claude -p --plugin-dir <worktree>/plugins/dev-workflow --permission-mode default` で確かめる（#1137 の完了条件の実機確認と同じ組み立て: https://github.com/oratta/claude-harness/issues/1137#issuecomment-6301780070 ）。親は develop の SKILL.md の該当の 2 段落どおりに判断するよう、プロンプトで段落を指して頼む。子は名前付きの general-purpose / sonnet。人は確認画面を押さない。

1. 中のケース: 子に、自分の scratchpad に `repoA`（`a.txt` を `orig` で commit し、`changed` に書き換える）を作る準備と `git -C <SP>/repoA checkout -- a.txt` を `&&` でまとめて 1 回で打たせる。期待: hook が拒否 → 親のスクリプトが 3 → 親が打ち直しを指示 → 子が準備を別に済ませ単独のコマンドで打って拒否 → 親のスクリプトが 0 → 再開した子のコマンドが通り、`a.txt` が `orig` に戻る。`permit-log.jsonl` に permit と use の行がある
2. 外のケース: 確認する側が先に scratchpad の外（作業ツリーにも scratchpad にも入らない一時の場所）に `repoC`（`c.txt` を `changed` にしたもの）を置く。子に、scratchpad の中に `repoC` を指す symlink `linkC` を作る準備と `git -C <SP>/linkC checkout -- c.txt` を `&&` でまとめて打たせる。期待: 1 回目は 3 → 打ち直しの指示 → 単独のコマンドの記録では 1（行き先が scratchpad の外）→ 親は許可を書かずオーナーに上げる文面を出す。`c.txt` は `changed` のまま、`permit-log.jsonl` に permit の行が無い

結果（各ケースの子の agent_id、スクリプトの終了コードの並び、permit-log の行、最終状態）は PR に記録する。外のケースで親が 3 を受けても「条件 3（子が作った）を満たさない」としてすぐオーナーに上げた場合は、許可が書かれていないことは満たすが打ち直しの経路を確かめていないので、プロンプトを直して取り直す。

## Risks / Trade-offs

- [3 と 1 の振り分けが判定の理由とずれる] → 決定 2 のとおり、ずれても許可は書かれない。bats で代表的な形（準備との `&&`・変数・引用符・`&`・cd との連結）が 3、単独の形（外・許していないサブコマンド・無いディレクトリ）が 1 になることを固定する
- [共通ファイルの文字の集合の名前が変わる] → スクリプトはそれを読めなければ 1 に倒す（打ち直しを頼まない側）。bats の 3 のケースが落ちて気づける
- [子が打ち直しで別のコマンドを打つ] → 新しい記録のコマンドと報告の全文を条件 1 で照合し直すので、許可は打った 1 本にしか書かれない。場所はスクリプトが判定し直す
- [打ち直しで子が打ち切られ、報告を取り直しても空] → 既存の扱いのとおり、空だったことと作業ツリーの状態をオーナーに上げる
