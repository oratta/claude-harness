## Context

`cost_ledger.py` は会話ログの行の `cwd` から `git rev-parse --git-common-dir` でリポジトリ識別子を求める（`RepoResolver.repo_id`）。`cwd` のディレクトリが無いと「不明」になる。識別子は台帳へ追記する時点で事実に入り（`build_fact`）、`cwd` そのものは台帳に残らない。issue の番号で引く集計（`cost <issue番号>`・エピック・番号なしの `cost`）は、識別子が実行した作業ディレクトリのリポジトリと一致する行だけを数え、不明の行は件数と額を別立てで出す。

issue #750 の本文は「追記時に焼き付ける」「同じセッションの他の行を使う」「ブランチ名で数える」を候補に挙げたが、上の実データではどれも効かない（下の「捨てた方式」）。直す対象は「台帳へ追記する前に `cwd` が消えていた行」で、issue の受け入れ条件 1 件目「追記したあとで `cwd` を消した行」は現状でも数えられる見込みなので回帰テストとして残す。

同時に #691（PR #744）と #697 が別のセッションで `cost_ledger.py` と周辺を変えている。

## Goals / Non-Goals

**Goals:**

- 削除済みの `cwd` の行のうち、パスからリポジトリが 1 つに決まるものを、そのリポジトリの行として数える
- 既に台帳にある不明の行を、台帳の既存の行を書き換えずに直す
- 推定で数えた分を、出力で確定の分と見分けられるようにする
- 別のリポジトリの同じ番号の issue の行を数えない

**Non-Goals:**

- 不明の行を全部なくすこと（条件を満たさない `cwd` は不明のまま残す。実データで $284.83）
- 補正行を取り消す専用のコマンド（取り消しは補正行を 1 行足す手作業で行う。下の決定 5）
- `cost_ledger.py report` に推定の行の表示を足すこと（リポジトリ別の内訳は、補正後の識別子で分かれるだけにする）
- 会話ログが既に消えた期間の不明の行を直すこと（`cwd` を知る手段が無い）
- hook や通常の `ledger-sync` から過去の行を自動で直すこと

## Decisions

### 決定 1: `cwd` の文字列からリポジトリを推定する

`cwd` がディレクトリとして存在しないときだけ、次の順で推定する。存在するのに git が失敗する `cwd` は今までどおり不明にする。

1. **`.claude/worktrees/` の規則**: `cwd` が `/.claude/worktrees/` を含むなら、最後のその並びの手前のディレクトリを持ち主とする。持ち主が存在すれば `git rev-parse` で決め（失敗すれば不明）、存在しなければ持ち主のパスにこの推定を初めからもう一度当てる
2. **置き場の規則**: 上に当たらなければ、`cwd` の祖先のうち現存する最も近いディレクトリを「置き場」とする。置き場の直下にある、リンクされた作業ツリー（`.git` がファイルであるディレクトリ）それぞれのリポジトリ識別子を `git rev-parse` で求め（求められないものは除く）、次の 2 つをどちらも満たすときだけ、そのリポジトリにする
   - 求まった識別子がちょうど 1 種類
   - 置き場のディレクトリ名が、そのリポジトリのメインの作業ツリーのディレクトリ名か、origin の URL のリポジトリ名（`owner/repo` の `repo`）と、大文字と小文字を区別して一致する
3. 次のときは不明にする: 置き場が `/`／置き場が git リポジトリの中（置き場で `git rev-parse` が成功する）／置き場の直下にリンクされた作業ツリーが 1 つも無い／上の 2 条件のどちらかを満たさない

結果は `cwd` ごとに、置き場の判定は置き場ごとに、プロセスの中で覚える（git の起動を置き場の子の数に抑える）。

**なぜこの規則か。** 実データの削除済み `cwd` の行 112,677 件 $8,176.47 のうち $7,933.55（97%）が決まり、誤りは観測していない。条件を緩めた 2 つの形は実データで外れた。

| 規則の形 | 実データでの結果 |
|---|---|
| 置き場の名前を見ない | 誤りが 2 件（42 行 $5.56）。`~/orca/workspaces` 直下に置かれた claude-harness の作業ツリーが marketing-harness に、`00_IndieDev` 直下のものが Uranai に寄る |
| 置き場の子が全部リンクされた作業ツリーであることを求める | `~/orca/workspaces/claude-harness` に git でないディレクトリが 1 つあり、claude-harness の $2,242 が決まらなくなる |
| 採用（子の作業ツリーが 1 リポジトリで、置き場の名前が一致） | 上の 2 件はどちらも不明に落ち、claude-harness の分は決まる |

### 決定 2: 推定で決めた行に `repo_inferred: true` を付ける

`build_fact` は、識別子を推定で決めたときだけ事実に `repo_inferred: true` を入れる。偽のときは欄そのものを書かない（既存の行と、`git rev-parse` で決まる行の出力を 1 バイトも変えないため）。`RepoResolver` に「この `cwd` は推定で決めたか」を返す口を足し、リポジトリを引かない `_NoRepo` には常に偽を返す同じ口を足す。

### 決定 3: 過去の行は `ledger-sync --rescan` が補正行を追記して直す

台帳は追記だけなので、既存の不明の行は書き換えない。`--rescan` のときだけ、次の手順で「補正行」を追記する。

1. 台帳を読み、識別子が不明の行（補正行を除く）を持つ（`session_id`, `branch`）の組を集める
2. `--rescan` が先頭から読む会話ログの `type` が `assistant` の行から、組（`sessionId`。無ければ事実と同じくファイルのパス, `gitBranch`）ごとに `cwd` の集合を集める。会話ログのファイルを開く回数は増やさない（`--rescan` が読み込んだバイト列を使う）
3. 1 の組のうち、`cwd` の集合が空でなく、すべての `cwd` が（`git rev-parse` か決定 1 の推定で）同じ 1 つのリポジトリに決まる組に、補正行を 1 行追記する。1 つでも不明の `cwd` があるか、2 つ以上のリポジトリに分かれる組には書かない

補正行の形（事実と同じ欄を持つ JSON の 1 行）:

| 欄 | 値 |
|---|---|
| `request_id` | `repo-fix#<session_id>#<branch>#<リポジトリ識別子>` |
| `session_id`・`branch` | 組の値 |
| `repo_id` | 決まったリポジトリ識別子 |
| `timestamp` | その組の不明の行のうち最も早い `timestamp` |
| `continuation` | `true` |
| `repo_fix` | `true` |
| トークンの 5 つの欄 | 0 |
| `issues`・`post_marker`・`model`・`is_sidechain` | 空の配列・印なし・空文字・偽 |

`uuid` と `source_offset` は持たない。同じ `request_id` が台帳の索引にあれば追記しないので、2 回目の `--rescan` と、控えを消したあとの `--rescan` は 0 行になる。

**なぜ組ごとに 1 行か。** 事実は `cwd` を持たないので、行ごとに直すには不明の 108,464 行と同じ数の補正行が要る。組ごとなら 2,105 組のうち 1,965 組（105,493 行 $7,665.99）を 1,965 行で直せる。残り 140 組（2,971 行 $284.83）は不明のまま。

**なぜ補足の事実の形に寄せるか。** この change より前の版の読み手（別の PC やキャッシュ済みの古いプラグイン）が同じ台帳を読んでも、補正行は「トークン 0・issue なし・印なしの補足の事実」に見え、金額も件数（補足は件数に数えない）も区間の切れ目も変えない。台帳の索引は `request_id` の最初の `#` より前（`repo-fix`）に出力 0 を足すだけで、ほかの応答の出力の数え方に触れない。

**なぜ hook から走らせないか。** `--rescan` は全履歴を読み直すので hook に入れるとセッションが止まる（既存の要件どおり）。主が手で 1 回実行する。新しく書かれる行は決定 1 と 2 で追記時に決まるので、`--rescan` を繰り返す必要は無い。

### 決定 4: 読むときに補正を当てる

`load_facts` は、台帳から読む経路でだけ、次を行う。会話ログを直接読む経路（台帳が未設定）は、全行が `build_fact` を通って決定 1 の推定が効くので、補正は要らない。

1. 台帳を 1 回読み通して補正行（`"repo_fix": true` を含む行だけを JSON として読む）を集め、組ごとに `repo_id` の集合を作る
2. 返す事実の列から補正行を取り除く
3. 識別子が不明の事実のうち、その組の補正の `repo_id` がちょうど 1 種類のものを、`repo_id` をその値に、`repo_inferred` を `true` にした写しに置き換える

台帳を読み通す回数は、`load_facts` の 1 回の呼び出しにつき 1 回増える（issue の数にも PR の数にも比例しない）。`load_branches_facts` は触らない: リポジトリで絞らずブランチ名だけで数える経路で、そこに混ざる補正行はトークン 0 の補足の事実なので、金額にも件数にも出ない。

**検討した別案: 補正を控え（`<台帳>.state.sqlite`）の表に持つ。** 台帳を読み通す回数は増えないが、`LedgerIndex.catch_up` と控えの形（古い形の作り直し）を変えることになり、#691・#697 と同じ時期に索引の形を動かす危険がある。読み通し 1 回は文字列の一致だけで済むので、まず単純な形を採る。実測で hook の所要時間（`timeline` が `load_facts` を呼ぶ）が既存の要件（1 秒）を超えたら、実装を止めて本体に報告する。

**区間単位の適用と直読みの差。** 台帳の経路は組ごと（組の全 `cwd` が一致するときだけ）、直読みと追記時は `cwd` ごとに決める。1 つの組に、推定できる `cwd` と推定できない `cwd` が混ざる場合、直読みは前者だけを決め、台帳の補正は組ごと不明のままにする。安全側の差なので許す。

### 決定 5: 取り消しは、同じ組に別のリポジトリの補正行を足す

同じ（`session_id`, `branch`）の組に `repo_id` の違う補正行が 2 種類以上あれば、その組は不明のまま読む。誤った補正を見つけたら、その組に `repo_id` を別の値にした補正行を 1 行追記すれば不明に戻る（台帳の行は消さない）。専用のコマンドは作らず、手順を README に書く。

### 決定 6: 推定で数えた件数と額を出力に出す

既存の spec は、リポジトリの絞り込みで起きることを「黙って除外しても黙って合算しても MUST NOT」としている。推定は外れうるので、合計に入れたうえで件数と額を別に出す。

- 対象は `cost <issue番号>`（`cmd_issue`）・エピックの `cost <番号>`（`cmd_epic`）・番号なしの `cost`（`cmd_branch`）。リポジトリ識別子の一致で数える 3 つの経路
- 数えるのは、リポジトリ識別子の一致で合計に入れた行のうち `repo_inferred` が真の行。エピックでは、ヘッドブランチの経路で数えた行は含めない（ブランチ名で数えていて、推定に依存しないため）
- 表示は「リポジトリ不明」の行の位置の直後に 1 行（0 件なら出さない）。`--json` は `inferred_repo_usd`・`inferred_repo_messages` を常に出す
- PR の経路（ブランチ名だけで引く）と `report` には出さない

### 触る関数と触らない関数

| 触る | 何をするか |
|---|---|
| `RepoResolver`（`repo_id` と新しい口） | 決定 1 の推定、推定で決めたかの問い合わせ |
| `build_fact`・`_NoRepo` | 決定 2 の印 |
| `_ledger_sync_locked`（と新しい関数） | 決定 3 の補正行の追記 |
| `load_facts`（と新しい関数） | 決定 4 の補正の適用 |
| `cmd_issue`・`assign_epic_rows`・`cmd_epic`・`cmd_branch` | 決定 6 の表示と `--json` |

触らない: `facts_from_lines`（hook の速度に効く）・`LedgerIndex`・`iter_ledger_issue_facts`・`iter_ledger_facts`・`load_branches_facts`・`split_intervals`・`_interval`。#691（PR #744）が変える `cmd_timeline`・`build_parser`・`timeline_has_trigger_near`・`gate_report.py`・`hooks.json`・README の 147〜216 行付近。#697 が変える `gate-report.sh`・`gate_report.py`。`--rescan` は既にある引数なので `build_parser` は変えない。README は台帳の節（262〜276 行付近）だけに足す。

### 捨てた方式

- **同じセッションの他の行のリポジトリを使う**: 実データで救える行が 0 件。同じブランチ名（`main`）で 2 つのリポジトリにまたがるセッションが 3 組あり、誤って寄せる恐れもある
- **ブランチ名が対象の PR のヘッドブランチと一致する行を数える**: 既にブランチの経路で数えている（1,596 件 $123.83 は不明に入っていない）。不明の行のブランチ名で判定を広げると、flatmate と claude-harness がどちらも `oratta/issue-7xx` の形で番号帯も重なるので衝突する
- **追記時に識別子を焼き付ける**: 既に実装済みで、過去の行には効かない

## Risks / Trade-offs

- **別のリポジトリの行を数える恐れ** — リポジトリ X の名前の置き場に、過去に別のリポジトリ Y の作業ツリーが置かれ、今は X の作業ツリーしか残っていない場合、Y の削除済み `cwd` の行が X に寄る。実データの 6 つの置き場では、名前の一致で 2 件を弾いたあと誤りを観測していない。ただし削除済みのディレクトリが何だったかは確かめる手段が無く、全数は検証できない。起こるのは置き場の使い方を途中で変えたときだけで、頻度は低いと見ている → 備え: 推定で数えた件数と額を出力に出す（決定 6）。誤りを見つけた組は補正行を 1 行足して不明に戻せる（決定 5）
- **補正行は消せない** — 台帳は追記だけなので、`--rescan` が書いた補正行は取り除けない。実データでは 1,965 行が増える → 備え: `--rescan` の前に台帳を `cp` で控える手順を README と tasks に入れる。控えへ戻せば実行前の状態になる（戻すと、そのあと追記された行も失われるので、戻したら通常の `ledger-sync` を 1 回流す）。個別の組は決定 5 で不明に戻せる
- **直らない分が残る** — 台帳で 140 組 2,971 行 $284.83 は不明のまま（置き場の名前がリポジトリ名と違う KG_Branding の $219.88 など）。会話ログが消えた期間の行も直らない → 今までどおり「リポジトリ不明」として件数と額が出る
- **台帳を読み通す回数が 1 回増える** — `load_facts` を通る集計と、hook が呼ぶ `timeline` が対象 → 変更の前後で所要時間を実測して PR に書く。hook が 1 秒を超えたら決定 4 の別案に切り替える判断を本体に上げる
- **`--rescan` のあと、見える額が変わる** — エピック #272 は合計 $373.09 → $432.15、不明 4,042 件 → 0 件になる見込み。issue のコメントに hook が積む累計の行も、補正された行の分だけ次の投稿で増える（差分の列に過去の分が 1 回だけ乗る）。これは直した結果そのものなので、PR の本文に書いて知らせる

## Migration Plan

1. マージ後、主が台帳を控える: `cp -p "$COST_LEDGER_PATH" "$COST_LEDGER_PATH.before-750"`
2. `python3 plugins/cost-ledger/scripts/cost_ledger.py ledger-sync --rescan` を 1 回実行する（hook からは走らない）
3. `cost 272` で不明の件数と合計を確かめる
4. 戻すとき: 控えを台帳の場所へ `cp -p` で戻し、`<台帳>.state.sqlite` を消してから `ledger-sync` を 1 回流す（控えは台帳から作り直される）

この change の実測と実機の確認は、実機の台帳の写しに対して行う（実機の台帳には補正行を書かない）。
