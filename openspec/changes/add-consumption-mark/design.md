## Context

読み取り側の契約の正本は flatmate の `openspec/specs/burn-consumption-ledger/spec.md`「工程・試行・アカウントを記録の印から読む」。この spec は W が `gh api repos/genetta-inc/flatmate/contents/...` で直接読んで照合した（レビュー時は接続エラーで読めなかった）。照合した点: 印の形（`[消費記録 工程=… 試行=… アカウント=<provider>:<登録名> 引継ぎ=…]`）・キー順不問・`引継ぎ=` 省略可・11 工程名の語彙・知らない工程名も捨てない・印が無いときは `G-<PR>-<段>-<n>` / `V-<記録先番号>-<n>` の名前からだけ工程と試行を読む・消費の単位が「Claude のサブエージェント 1 体 = 1 行」であること。印は 1 行の文字列で、キーの順は問わず、`引継ぎ=` は省ける。読み取り側は自由文から推測せず、印が無ければ工程・試行・アカウントを `"欠測"` にする。工程の値は印に書かれたとおりに出し、知らない値でも捨てない。

## Goals / Non-Goals

**Goals**
- 読み取り側の契約どおりの印を、3 か所に書く規約を SKILL.md に置く
- 印の形と置き場、工程名の語彙を bats で検査する

**Non-Goals**
- 印への時刻の追加（決定 3）
- `codex-worker.py` の CODEX_HOME 使い捨ての変更
- flatmate 側の変更

## Decisions

1. **印の形・工程名・キーの扱いは読み取り側の契約に一致させる。** 工程は `spec`・`spec-review`・`implement`・`impl-review`・`finish`・`gate-prepare`・`gate-triage`・`gate-pass`・`gate-hold`・`decide`・`screen-check`。アカウントは `claude:<登録名>` か `codex:<CODEX_HOME 対応表の登録名>`。工程名の語彙は SKILL.md に 1 か所で列挙し、3 か所の規約はそこを指す（同じ一覧を複数書かない）。
2. **試行と引継ぎの数え方。** 試行は、記録先ごと・工程ごとに 1 から数え、差戻しの修正で同じ工程をやり直すたびに増やす。引継ぎは、同じ工程と試行で手渡しにより起こし直した k 番目の担当にだけ `引継ぎ=<k>` を書く（最初の担当は書かない）。数える主体は本体（本体が spawn・再開・委譲を決めるため）。
3. **時刻（`開始=` `終了=`）は足さない。範囲外にする。** 理由: (a) 読み取り側の契約の印は工程・試行・アカウント・引継ぎの 4 キーだけで、時刻は rollout から読む設計。印に未知のキーを足したときの読み取り側の挙動は契約に無く、追従の変更が flatmate 側に要る。この issue は「読み取り側の契約に一致させる」ことが目的なので、契約を先に動かせない。(b) 時刻が無い場合の振る舞いは契約に既にある（`reset_unknown`、`started_at` が分からない行のアカウントは `"欠測"`）。欠測として出るだけで誤りは出ない。(c) 時刻は codex-worker の結果 JSON から書く別の経路（worker の出力に時刻があるかの確認を含む）で、規模が別。扱い: 両リポジトリで揃えて進める後続として、harness 側（`開始=` `終了=` を書く）と flatmate 側（印の契約に時刻を足す）の 2 件を、主の判断で起票する候補として return に挙げる。
4. **同じ W を SendMessage で再開するときの扱い（読み取り側が分けられない範囲を明記する）。** 既存の 1 ループ（`dev-workflow-develop`）では、同じ W を spec→implement や implement の差戻し修正（試行 1→2）で SendMessage により再開する。読み取り側の契約は、サブエージェント 1 体を 1 行にし、その行の工程・試行を description の印から 1 つだけ読む。再開の指示文や会話ログの途中の印は読まず、1 体の消費を再開の境目で分けることもできない。よって spawn 時の description に工程・試行を書くと、再開後の消費が起動時の工程・試行へ誤帰属する。誤帰属は欠測より重いので、次のとおりにする。
   - **工程・試行を description に書くのは、その 1 体が 1 つの工程・試行にしか使われないとき**に限る（G・V・決める役・R1 の 1 周ごとの spawn、手渡しで工程ごとに新しく起こした担当、など）。
   - **同じ W を別の工程・試行へ再開しうるとき（既定の W）は、description の印に `アカウント=`（と該当すれば `引継ぎ=`）だけを書き、`工程=` と `試行=` を書かない。** 読み取り側はその行の工程・試行を `"欠測"`（`missing_stage` / `missing_attempt`）にする。誤った工程に寄せない。
   - 再開のたびに、本体は再開の指示文の先頭に、その再開が担う工程・試行の印を 1 行置く。現在の読み取り側はこれを読まないが、会話ログ上の境目として残り、読み取り側が将来、再開の印でサブエージェントの消費を分けられるようにするための入力になる（その追従は flatmate 側の変更で、この change では行わない。後続の候補として return で報告する）。
   - 手渡し（新しい W を spawn）は新しい 1 体なので、`引継ぎ=<k>` を書き、その W が再開されない工程・試行なら工程・試行も書いてよい。
5. **G の工程名の決め方。** G 自身の消費の工程は、本体が自分の起こした段（G の名前 `G-<PR>-<prepare|triage|pass|hold>-<n>` の段）から `gate-<段>` と決める。Gate Result の `段:` は日本語名か `一括（従来経路）` を返すので、工程名の決定には使わない。G が full レビューで要求した Codex や Claude のレビュアーの消費は工程 `impl-review` とする（その `Codex 消費:` コメントの印と、レビュアーの description の印の両方）。試行は、同じ段の G を起こし直した回数（名前の `<n>`）に合わせる。
6. **Claude の登録名が取れないとき。** 印の `アカウント=` を推測で埋めず、`アカウント=` のキーごと省く。読み取り側はそれを `"欠測"` にする。`develop 開始` コメントの印には本体の起動アカウントを書き、`工程=` と `試行=` は省いてよい。

## 受け入れ条件の 2 つ目の扱い

読み取り側の `scripts/burn_consumption.py` は、flatmate の main に入っている（genetta-inc/flatmate#709 は closed、`scripts/burn_consumption.py` を `gh api` で確認）。よって「マージ後にしか確かめられない」のではなく、待つ外部依存は無い。未マージなのはこの change の SKILL.md だけで、それは `claude --plugin-dir <この worktree の plugins/dev-workflow>` で読ませて確かめられる（`docs/worktree-recovery.md`）。

- マージ前に実機確認する: 開発用 worktree の plugin を `--plugin-dir` で読ませ、印を書く develop を 1 回回し（小さな検証用 issue を記録先にする）、flatmate の `scripts/burn_consumption.py <記録先>` を実行して、`stage`・`attempt`・`account` が欠測でない行が 1 行以上あることを確かめる。結果は PR の動作確認ポイントと #1158 のコメントに書く
- 既定の W は再開されるので工程・試行が欠測になる（決定 4）。欠測でない行は、G・V・決める役・R1 の周ごとの spawn・Codex 消費コメントから出る。この確認で見る行はそれらである
- 実機確認が取れない事情（検証用 issue を回せない、`--plugin-dir` が使えない）があるときだけ、確認を後ろ倒しにし、その理由と、いつ誰が `burn_consumption.py` を実行するかを PR 本文に書く。その場合も PR 本文は `Refs #1158` とし、確認が取れてからオーナーが閉じる

## Risks / Trade-offs

- 既定の W は工程・試行が欠測で出る（決定 4）。読み取り側が再開の印を読むようになるまで、W の工程別の消費は分からない
- 本体が印を書き忘れる／試行を数え違える → 読み取り側は欠測か、別の試行として出す。誤りは欠測より重いが、数える主体を本体に 1 つに決めて低減する。完全な保証はこの change の完了条件にしない
- 時刻を足さないので、develop の Codex 行は当面 `reset_unknown` になる（決定 3 の後続で解く）

## flatmate 側の変更が要る後続（この change では行わない）

- 再開の指示文の先頭の印で、サブエージェント 1 体の消費を工程・試行ごとの行に分ける（契約の「1 体 = 1 行」を変える）
- 印への時刻の追加（決定 3）
- 本体が起票を決める
