## Context

読み取り側の契約の正本は flatmate の `openspec/specs/burn-consumption-ledger/spec.md`「工程・試行・アカウントを記録の印から読む」（archive 済みを確認）。印は 1 行の文字列で、キーの順は問わず、`引継ぎ=` は省ける。読み取り側は自由文から推測せず、印が無ければ工程・試行・アカウントを `"欠測"` にする。工程の値は印に書かれたとおりに出し、知らない値でも捨てない。

## Goals / Non-Goals

**Goals**
- 読み取り側の契約どおりの印を、3 か所に書く規約を SKILL.md に置く
- 印の形と置き場、工程名の語彙を bats で検査する

**Non-Goals**
- 印への時刻の追加（決定 3）
- `codex-worker.py` の CODEX_HOME 使い捨ての変更
- flatmate 側の変更

## Decisions

1. **印の形・工程名・キーの扱いは読み取り側の契約に一致させる。** 工程は `spec`・`spec-review`・`implement`・`impl-review`・`finish`・`gate-prepare`・`gate-triage`・`gate-pass`・`gate-hold`・`decide`・`screen-check`。アカウントは `claude:<登録名>` か `codex:<CODEX_HOME 対応表の登録名>`。工程名の語彙は SKILL.md に 1 か所で列挙し、3 か所の規約はそこを指す（同じ一覧を複数書かない）。
2. **試行と引継ぎの数え方。** 試行は、記録先ごと・工程ごとに 1 から数え、差戻しの修正で同じ工程をやり直すたびに増やす。引継ぎは、同じ工程と試行で手渡しにより起こし直した k 番目の担当にだけ `引継ぎ=<k>` を書く（最初の担当は書かない）。数える主体は本体（本体が spawn・再開・委譲を決めるため）。
3. **時刻（`開始=` `終了=`）は足さない。範囲外にする。** 理由: (a) 読み取り側の契約の印は工程・試行・アカウント・引継ぎの 4 キーだけで、時刻は rollout から読む設計。印に未知のキーを足したときの読み取り側の挙動は契約に無く、追従の変更が flatmate 側に要る。この issue は「読み取り側の契約に一致させる」ことが目的なので、契約を先に動かせない。(b) 時刻が無い場合の振る舞いは契約に既にある（`reset_unknown`、`started_at` が分からない行のアカウントは `"欠測"`）。欠測として出るだけで誤りは出ない。(c) 時刻は codex-worker の結果 JSON から書く別の経路（worker の出力に時刻があるかの確認を含む）で、規模が別。扱い: 両リポジトリで揃えて進める後続として、harness 側（`開始=` `終了=` を書く）と flatmate 側（印の契約に時刻を足す）の 2 件を、主の判断で起票する候補として return に挙げる。
4. **Claude の登録名が取れないとき。** 印の `アカウント=` を推測で埋めず、`アカウント=` のキーごと省く。読み取り側はそれを `"欠測"` にする。`develop 開始` コメントの印には本体の起動アカウントを書き、`工程=` と `試行=` は省いてよい。

## 受け入れ条件の 2 つ目の扱い（マージ後にしか確かめられない）

受け入れ条件 2（印を書いた develop を 1 回回した記録先で `burn_consumption.py` の出力に stage・attempt・account が欠測でない行がある）は、印を書く SKILL.md がマージされ、かつ flatmate の #709 が入ってからでないと確かめられない。PR のマージ前の合格条件には含めない。

- PR の「動作確認ポイント」には「マージ前: 受け入れ条件 1（SKILL.md の規約・`scripts/test.sh` exit 0）」と「マージ後の確認（この PR の合格条件ではない）: 次に印つきで回った develop の記録先に `burn_consumption.py <記録先>` を実行し、`stage`・`attempt`・`account` が欠測でない行が 1 行以上あること」を分けて書く
- マージ後の確認が取れるまで issue #1158 は閉じない。PR 本文には `Closes #1158` を書かず `Refs #1158` を使い、確認が取れてからオーナーが閉じる
- 確認の担い手: flatmate #709 が入ったあと最初に印つきで回った develop の本体が、確認結果を #1158 にコメントする

## Risks / Trade-offs

- 本体が印を書き忘れる／試行を数え違える → 読み取り側は欠測か、別の試行として出す。誤りは欠測より重いが、数える主体を本体に 1 つに決めて低減する。完全な保証はこの change の完了条件にしない
- 時刻を足さないので、develop の Codex 行は当面 `reset_unknown` になる（決定 3 の後続で解く）
