# Design

## Context

動機と読み合わせ結果は proposal.md「Why」と #1597 の仕様化判断コメントを参照。ci-watch.md 9 は再起動後の本体に `next` の結果を処理させるが、decision-criteria.md の通常経路は既存 W を把握している前提である。handover.md は主の返事待ちに限られる。

既存の手渡し許可は「前任の直近の return が工程完了」または「停止指示に対する停止確認」の二択である。前セッションの W を参照できないことや、オーナーの続行指示を第三の許可にできない。

## Goals / Non-Goals

- Goal: CI 見張りの本体が W を把握しなくても、記録された成果・許可の根拠を使って担当を用意するか、停止するかを選べる。
- Non-goal: 前セッションへの通信手段、新しいロックや状態ファイル項目、CI 分類、見張り重複の問題、#1583/#1590 や他の子の範囲の変更。
- Non-goal: 前任のトランスクリプトを読み直して履歴を復元すること、手渡し許可の緩和、実行先の選び直し。

## Decisions

### 既存の手渡し許可を持つ成果を、CI 見張りへ渡す

採用する設計判断は、W 不明を「新規の仕事」とせず、既存の手渡し契約で解決すること。handover.md に CI 用の節を足し、通常経路で見張りを始める前に、本体が PR コメントへ `引き継ぎ: CI 見張りの修正担当` を 1 行目として記録する。修正後に待ちへ戻る前にも最新の成果・対象で更新する。同じ見張りの続きなので CI 見張り開始／終了を増やさない。

主の返事待ちの書式は変更せず、CI 用は必要な項目だけを既存の項目名・意味から借りる。

| 項目 | 必要な内容 |
|---|---|
| 記録先 | issue または Draft PR の URL。最新の仕様化判断と、仕様化した場合の R1 APPROVE を読む先 |
| 対象 | PR 番号・HEAD の 40 桁 SHA・ブランチ・worktree パス |
| 前任 W | 直近の return 全文または全文を読める記録の URL。成果・残作業・読んだコードの要点を含める。手渡し可否と、工程完了の 1 行目または停止確認の報告も残す |
| 実行モード | interactive / channel / unmanned |
| 実行先 | 明示オプションと account-home の対応または自動選択、および開始済み phase の選択結果の記録 URL。既存 handover の実行先の継続規則を使う |
| 周回 | 仕様レビュー・G・W の修正の周回 |
| PR トークン上限 | 最新の上限と記録時点の合計 |

`前任 W` の許可の書き方は既存の `手渡し: 可（工程完了 | 停止確認済み）` / `手渡し: 不可（理由）` を使い、編集ファイルと commit SHA も記録する。根拠を確認できなければ不可と書く。未コミット差分があれば、既存の保留の引き継ぎと同様、前任が工程完了したか停止確認したあとに本体が commit してから記録する。新しいセッションで再開できない W の名前は引き継ぎ項目にしない。

W を把握しない本体は、PR コメント全ページから最新の CI 用引き継ぎを読み、記録先の最新判断を取り直す。古い引き継ぎに遡って可を探さない。対象 PR・HEAD・ブランチ・worktree を現在の PR とローカルの `git status` / `git diff` で確認し、差異や未コミット差分を見つけたら推測で解消せず停止する。全項目・成果・許可根拠を読めたときだけ、新しい W に `段: implement`、前任 return、記録先、PR、fix の観測と共有の直し方を渡す。通常経路の判断と必要な R1 APPROVE を維持し、CI fix のためだけに判断を再投稿しない。

比較した案:

- 担当不明なら新しい W を spec で起こす: 通常経路の継続を新規判断として扱い、無許可の交代と判断のやり直しになるため採らない。
- オーナーの続行指示や W が見えないことだけで implement 担当を起こす: 前任が動いている可能性を解消せず、既存の手渡し許可を迂回するため採らない。
- 常に停止する: 安全だが、許可の根拠と成果が既に揃っている通常経路まで進められない。採用案は必要な根拠を記録してこの場合だけ継続する。

### 情報不足時と既存経路への接続

情報不足・対象不一致・手渡し不可なら、本体も W も直しや push をせず、ci-watch.md 6 の `escalate` と同じく PR に `needs-approval` を付け、不足情報・PR/HEAD・fix の観測を記録して見張りを終える。終了コメントを残し、通常はオーナーへ、エピックの子なら既存の epic-child-stop.md に従う親への停止報告へ進む。親やオーナーの返事も前任の工程完了／停止確認の代用にはしない。

担当分岐の正本は decision-criteria.md、CI 用引き継ぎの書式・作成・読取りは handover.md に置く。ci-watch.md の 7 から見張り前の記録へ、9 の fix 処理から担当分岐へ短く接続する。W を把握している通常経路の implement 再開、軽い判断の新規 spec 起動は現状のまま。状態ファイル・修正回数は書き換えず、同じ PR の修正・再ゲートへ合流する。

## Risks / Trade-offs

- [旧 PR に CI 用の引き継ぎが無い] → W 不明なら停止して不足を報告する。前任を把握するセッションが成果と許可を記録するまで新しい W を起こさない。
- [HEAD は一致するが記録された成果や停止報告が誤っている] → 引き継ぎの事実自体の真正性までは検証しない。拾うのは必要項目・対象・許可根拠の欠落と、無許可の起動である。
- [文書テストは本体の読解ミスを完全には止めない] → 担当分岐・起動段・停止先・9 からの参照・既存経路の維持を関係 Bats で確かめる。エージェントを実起動する検証は完了条件にしない。
- [起動時文書の追記が必要になる] → 予定は reference 3 ファイルだけ。起動時予算の対象を追加編集する必要が出たら、周辺文を圧縮せず OWNER の #1586 付き指示に従う。

## Migration Plan

R1 APPROVE 後に手順・テスト・変更記録を実装する。verify 後の finish で delta を archive する。旧 PR の状態ファイルの移行は無い。今工程は artifact 一式の作成のみとし、実装・archive・PR 作成は進めない。
