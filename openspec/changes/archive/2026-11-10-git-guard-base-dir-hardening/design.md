# Design

## Context

動機は proposal.md の Why を参照。今のコードの形は次のとおり。

- `<base>`（`${TMPDIR:-/tmp}/dev-workflow-git-guard`）を、git ガードの回数（`git-destructive-guard.sh` の `count_child_deny`）と共通ファイル（`git-guard-scratchpad.py` の `append_log`・`write_json_atomic`）が `os.makedirs(exist_ok=True)` で作り、既にあれば種類・持ち主・モードを見ずに使う
- 回数のファイルは `open(f, "w")`、`permit-log.jsonl` は `open(..., "a")`、一時ファイルは `.<名前>.tmp.<pid>` という予測できる名前で `open(tmp, "w")`。どれも symlink を辿る
- 許可は `rename` で取ったあと、取った先を `open` で読む（symlink を辿る）
- 主の呼び出しは `<base>` に触れない。子の呼び出しは、判定のファイルを読む → 許可を使う → 回数を数える → 記録を書く、の順
- 判定のファイルの lstat による持ち主・モードの確かめは、すでに `_is_scratchpad` に手本がある

制約: hook は `python3 -I` で動き、標準ライブラリだけを使う。macOS と Linux の両方で動く（`os.O_NOFOLLOW` は両方にある）。

## Goals / Non-Goals

**Goals:**

- 別の uid が `<base>` を先に作る・symlink にする形で、許可の偽造・被害者の書けるファイルの上書きや追記・記録の盗み読み（新しく作る分）ができないこと
- 確かめに失敗しても、子への拒否が打ち切りの回数に数えられず、主の呼び出しの `ask` / `deny` が変わらないこと（エピック #1476 の「正当な作業を止めない」）

**Non-Goals:**

- 同じ uid のプロセス（子のサブエージェントを含む）から `<base>` を守ること。子が `permits/` に書く形（指摘 1）は別の change で扱う
- `<base>` の祖先（`TMPDIR` や `/tmp`、macOS の `/var` → `/private/var` のような symlink）を確かめること。祖先の symlink は OS の正常な形で、確かめると既存の環境が止まる
- 既にある `<base>` と中のファイルのモードを締め直すこと

## Decisions

### 確かめは「lstat の 4 条件」にし、HMAC などの署名は採らない

`<base>`・`denied/`・`permits/` のそれぞれを lstat で見て、symlink でない・ディレクトリ・自分の uid の持ち物・グループと他者に書き込み権が無い、を満たすときだけ使う。中のファイルは `O_NOFOLLOW` で開き、新しく作るものは `O_CREAT | O_EXCL | O_NOFOLLOW`・モード 0600・予測できない名前（`tempfile.mkstemp(dir=...)` と同じく乱数を含む名前）で作ってから `rename` で置く。回数のファイルも同じく一時ファイルからの `rename` で置く（`rename` は置き先が symlink でもその symlink 自体を置き換え、先を書き換えない）。

採らなかった案: 許可に秘密の鍵で HMAC を付け、hook が検証する。鍵はどこかのファイルに置くしかなく、同じ uid の子はそれを読めるので、子による偽造（指摘 1）は防げない。別の uid に対しては、置き場所を自分の持ち物に限ればその uid は中に書けないので、署名を足しても守れるものが増えない。鍵の置き場所の確かめという同じ問題が 1 つ増えるだけになる。

採らなかった案: `<base>` の名前に uid を入れる（`dev-workflow-git-guard-<uid>`）。uid は他のユーザーから見えるので、その名前も先に作れる。確かめは結局要り、許可を書くスクリプトの場所の規則（`BASE_NAME`）と既存の spec を変える分だけ損になる。また、1 台の Mac を別のユーザーアカウントの複数人が同時に使って git ガードを動かすことは想定しない（エピック #1476 の本文の節「条件の答え」の主の答え）ので、別の uid の正当な利用者同士が同じ `<base>` の名前を取り合う形を避けるために uid を名前に含める必要も無い。

### 確かめに失敗したら deny だけを返し、記録も回数も書かない

子の呼び出しで確かめを満たさないときは、許可を探さず、拒否の記録を書かず、回数を数えず、`deny` を返す。理由文に「拒否の記録を作れなかった」・`<base>` のパス・満たさなかった条件・報告にコマンドの全文を書くこと、を入れる。

理由:

- 確かめを満たさない場所に書くこと自体が、攻撃者の symlink の先を書き換える経路なので、記録も回数も書けない
- 回数を数えられないのに「2 回目以降」として打ち切ると、子の側に落ち度が無い環境の問題で作業を打ち切ることになる。打ち切りは子の打ち直しを止めるためのもので、ここで発火させる理由が無い（エピック #1476 の「正当な作業を止めない」）
- 打ち切らない代わりに、理由文で `<base>` の問題とその場所を示すので、親とオーナーは打ち直しではなく環境の問題だと分かる。今までも、判定のファイルを読めないとき・記録を書けないときは「拒否の記録を作れなかった」で返しており、同じ形に揃う

判定のファイルを読めないときも、確かめの処理がそのファイルにあるので `<base>` を確かめられない。今までは回数を数えていたが、同じ理由で数えないようにする（spec の destructive-git-hook「同じ子への拒否の繰り返しを打ち切る」の差分）。

主の呼び出しは今までも `<base>` を使わない。確かめも作成もしないことを spec で決めておき、`<base>` の状態で確認画面が出なくなることが無いようにする。

### 既にある 0755 の `<base>` は締め直さない

実機の `<base>` は 0755 で作られている（`os.makedirs` の既定）。確かめの条件は「グループと他者に書き込み権が無い」で、読み取り権は見ない。0755 は条件を満たすのでそのまま使い、モードも変えない。

理由: 条件に「0700 ちょうど」を入れると、今ある環境が全部確かめに失敗し、子の許可が通らなくなる。hook がモードを `chmod` で直す案も考えたが、hook が置き場所の持ち主の権限で黙って属性を変えるのは、拒否の判定をする部品の役目を越える。読み取り権が残ることで別のユーザーに読まれうるのは、すでにある拒否の記録（コマンドの全文と cwd）で、書き換えや偽造にはつながらない。新しく作る `<base>` は 0700、新しく作るファイルは 0600 なので、一時ディレクトリが片付けられたあとは自然に締まる。この点は spec の守備範囲で許した。

### 確かめの処理は `git-guard-scratchpad.py` の 1 か所に置く

git ガード・rm ガード・許可を書くスクリプトの 3 つは、すでにこのファイルを読んで key と一時領域の判定を共有している。確かめと「symlink を辿らずに開く・作る」の処理もここに置き、3 か所で書き分けない（書き分けると片方だけ直す事故が起きる）。git ガードの `count_child_deny` が直接ファイルを開いている部分も、このファイルの処理を使うように寄せる。そのため回数を数える処理も判定のファイルを読めたときだけ動く。

## Risks / Trade-offs

- [Linux で `TMPDIR` が未設定の機械では、別のユーザーが先に `/tmp/dev-workflow-git-guard` を作ると、その機械の全員の子が親の許可で通せなくなる（嫌がらせで止められる）。1 台を複数のユーザーで同時に使う形は想定しない前提なので、起きるのはその前提が崩れたときだけ] → 偽造や上書きよりは被害が小さい向きに倒した。主の呼び出しは止まらず、子は親に返って親か主が打てば進む。理由文に `<base>` のパスと満たさなかった条件が出るので、オーナーは自分の `TMPDIR` を自分だけの場所に設定すれば直せる。macOS は `TMPDIR` がユーザーごとの `/var/folders/...` なので起きにくい
- [確かめてから使うまでの間に同じ uid のプロセスが `<base>` を差し替える] → 同じ uid は守らない前提（Non-Goals）。別の uid は自分の持ち物の中に入れないので、この間に差し替えられない
- [既にある 0644 の拒否の記録を別のユーザーが読む] → 締め直さない決定のとおり許す。書き換えにはつながらない
- [`O_NOFOLLOW` の付け忘れが 1 か所でもあると穴が残る] → `<base>` の中のファイルを開く処理を共通ファイルの関数に集め、hook と許可を書くスクリプトからは直接 `open` しない。各ファイル（回数・記録・許可・`permit-log.jsonl`）を symlink にしたテストで先が変わらないことを確かめる

## Migration Plan

- 移行の手順は無い。既にある `<base>` は確かめを満たせばそのまま使われ、中の記録・許可・回数も読める
- 戻すときは PR を revert する。この change が作った 0700 の `<base>` と 0600 のファイルは、前のコードでもそのまま読み書きできる
- hook が実行するスクリプトを変えるので、PR は自動マージに乗せず主のマージ待ちにする（エピック #1476 の注意書き）
