## Context

develop の本体・W・G は、主に聞くかどうかを複数の面の規則から決めている。常時注入の `rules/perspective-casting.md`（返信前チェックの 5 手順。正本は `plugins/casting/skills/casting/SKILL.md`）、`rules/communication-style.md`（判断を求めるときの書き方）、develop の SKILL.md（本体の手順）、`skills/pr-review-gate/stages/triage.md`（G の振り分け）である。issue #1035 の 4 つの型は、どれもこれらの規則に「自分で決めてよい」と書かれていない場面で、安全側として主に聞いたものだった（proposal の表）。

主の意図の根拠は、主が過去に出した指示を残したメモリ 4 件にある。自分の誤りは差分が一意なら控えを取って戻し事後報告する（git の破壊的操作は除く）、範囲外の問題の起票は既存 issue を探して自分で決める、レビュー指摘は起きる場面と直すコストで受け入れを決め issue にするかは聞かない、後始末は自分でやるか主の操作をコマンドとタイミングで書く。

制約:

- 常時注入の合計は `tests/injection-budget.bats` が予算 40260 バイトと突き合わせる。2026-10-15 時点の実測は 38460 バイトで、余りは 1800 バイト
- エピック #1038 の兄弟が develop の SKILL.md の別の節（#1033 は「保留で止まるときの引き継ぎ」、#1030 は「エピックの扱い」）を直している。この change は新しい節と、「ループの終わり」「レビューの周を主に聞かずに続ける（直し方の判定）」の 2 節の中だけを直す

**Goals:**

**Non-Goals:**

- 仕様の発明の昇格トリップワイヤー（`worker/common.md`）を変えること。今回の 4 件のどれもこの経路で止まっていない

## Decisions

### 型ごとの規則の置き場所を develop SKILL.md の 1 つの新しい節にまとめる

4 つの型の決め方を、SKILL.md の新しい節「主に聞かずに決めること」に並べる。小さな実装の選択と閉じる操作は、既存の節（直し方の判定・ループの終わり）を正本にし、新しい節からはその節を指すだけにする。

- 代わりの案 A: 各型を、それが起きた節にばらばらに足す。自分の誤りの後始末と本体の起票には起きた節が無い（本体の役割の一般則）ので、置き場所が決まらない
- 代わりの案 B: `rules/` に新しいルールファイルを作る。常時注入の余りが 1800 バイトしかなく、4 つの型の中身を全部入れると足りない。develop の外のセッションで起きた例は 4 件の中に無い

### 常時注入の面には自分側の誤りを戻す 1 文だけを足す

`rules/perspective-casting.md` 手順 1 は「破壊的操作は無条件で人間承認」「回復コストが判定できない操作は回復不能側に倒す」と書いており、実ホームの設定ファイルから 1 件を消す操作もこの文で人間承認の側に入る。develop の SKILL.md だけを直しても、この文が毎ターン載る限り同じ判断が出うる。そこで手順 1 に「自分側（自分と自分が起こしたサブエージェント）が入れた誤りで、戻し先が差分から一意に決まるものを戻す操作は、控えを取れば回復可能として扱い、承認を求めない（git の破壊的操作と聖域への変更を戻す操作は除く）」の 1 文を足し、同じ文を正本の casting SKILL.md の手順 1 にも足す（正本と短い版の両方を直す規則が casting SKILL.md にある）。

- 代わりの案: `rules/` を直さず SKILL.md だけで済ませる。develop の外で起きたときに効かない
- 聖域（CLAUDE.md・hooks・権限設定）を除く理由: 手順 1 は聖域を観点判定より前に無条件で人間承認にしている。聖域への誤った変更を戻す操作も聖域の書き換えなので、差分が一意でも承認を求める側に残す。除かないと、戻すという名目で権限設定を承認なしに書き換える経路ができる
- 受け入れること: 常時注入が 1 文分（およそ 300〜400 バイト）増える。予算ファイルは動かさない

### 「一意に決まる」の判定は控えか変更前の状態との差分で行う

自分側の誤りかどうかと戻し先が一意かは、控え（`.bak` など）・git の履歴・自分のツール呼び出しの記録のどれかと今の状態を比べて決める。差分が自分の入れた分だけと確かめられないとき（主が後から手で足した変更と区別できないなど）は一意でないとして、主に聞く。戻す前に今の状態を控え（戻した操作を取り消せるようにするため）、事後報告には何を・どこから戻したか・控えの場所を書く。

- 代わりの案: 戻す前に必ず主に見せる。#977 で主が退けた形そのもの

### 小さな実装の選択は「直し方の判定」の定義①を広げて扱う

flatmate #1564 の選択は、仕様レビューの 2 周目以降の周の終わりに残った BLOCKER の直し方だった。いまの定義①は選択肢がある時点で「選び直しが要る」にする。定義①を「直し方が 1 つに決まる、または選択肢の違いが受け入れ条件と利用者に見える振る舞いを変えず、決める役が記録先と指摘から 1 つを選べる（選んだ直し方を判定の記録の指摘ごとの判定に書く）」に広げる。選択に主の側の情報（好み・事業判断・許容度）が要る、または受け入れ条件や利用者に見える振る舞いが選択肢で変わるなら、従来どおり「選び直しが要る」にする。

- 代わりの案: 新しい判定段を足す。決める役を 2 回起こすことになり、判定の記録の書式も増える
- 受け入れること: 決める役が選んだ直し方が外れることがある。それは定義③（前の周で決まっているとした直し方で閉じなかった）で次の周に拾うので、新しい歯止めは足さない

レビューの周の終わり以外で起きる実装の選択（W の作業中など）は、新しい節に「担い手が選び、選んだ理由を記録先に残す」とだけ書く。

### 本体の起票は triage.md の段の問いを借りて本体が当てる

本体が作業中に見つけた範囲外の問題（レビュー指摘以外。リハーサルで詰まった箇所など）は、`triage.md` の段 B・段 D・段 E の問い（エピックの子の記録先なら段 C も）と段 B の表を本体が借りて行き先を決め、起票したら URL を事後報告する。新しい表は作らない。`triage.md` は PR 番号・PR コメント・G の手順 3 を前提にしているので、丸ごとは当てず、PR を伴わない作業でも決まるように次の 3 つを develop の側で決める。

- 候補探し: 問題がファイルを指すなら `review-issue-candidates.sh` を `--exclude <記録先の番号>` で 1 回走らせる（スクリプトは PR 番号を要らず、`--exclude` は 0 回以上で動く）。ファイルを指さない問題（リハーサルで詰まった操作など）はスクリプトの検索語にならないので、`gh issue list --state open --search "<語>"` を 1 回走らせる
- 判断結果の記録先: PR コメントの代わりに、記録先（issue、または Draft PR）に 1 行目 `範囲外の問題の振り分け` のコメントを 1 件置き、問題ごとに当てた段と行き先を書く。1 行目の文字列は新しい書式で、G の仕分けの PR コメントと取り違えないように別の文字列にした
- 段 B の確認待ち: G と同じく、条件についての問いだけを主に聞き、`needs-approval` を付けず作業を止めない。答えは記録先（エピックの子ならエピック）の本文の節 `## 条件の答え` に足し、G の側と同じ置き場所を使う

エピックの親（OWNER）から新しい問題の置き場所についての注意書きがあるとき（エピック #1038 の「新しい問題はエピックに新しい子 issue として切る」）は、段 C の「同じエピックの子 issue に同じ場所を直すものがあれば、その子 issue の受け入れ条件に足す」より注意書きを優先する。並行して動く兄弟の子の範囲に、ほかの子が受け入れ条件を足し込むのを防ぐための注意書きなので、段 C の一般則より強い。

G の振り分け結果を主への報告にまとめるときも、行き先を「オーナーが決める」と書き換えない。issue にしたことで配布や後続の子の順番が変わる（「配り直しをこの表示ができるまで待つ」など）ときは、順番を変えるかが主の側の判断なので、起票は先に済ませ、順番だけを主に聞く。

### PR を伴わない記録先は本体が閉じる

「ループの終わり」に、PR を伴わない記録先 issue（調査だけの issue など）で受け入れ条件を満たしたら、本体が結果を記録先にコメントし `gh issue close <N> --reason completed` で閉じることを足す。受け入れ条件が「推奨を出す」なら、推奨を出した時点で満たしたと数え、主が推奨を採るかを閉じる条件にしない。閉じたあとは、PR がマージ済みのときと同じく最後のツール呼び出しで `epic-dispatch.sh mark` を呼ぶ。issue を閉じるのは reopen で戻せるので、破壊的な操作として扱わない。

## Risks / Trade-offs

- [自分の誤りと思って戻したものが主の変更だった] → 戻す前に差分が自分の入れた分だけかを控え・履歴・ツール呼び出しの記録で確かめ、確かめられなければ主に聞く。戻す前の状態の控えを残すので、取り消しは控えから戻せる
- [決める役が選んだ実装の選択が外れる] → 定義③で次の周に拾う。外れたときの損は 1 周分のトークンで、主の待ち時間より小さい
- [並行する兄弟の PR と SKILL.md で衝突する] → 触る節が重ならないので、衝突しても行単位の解消で済む
- [常時注入の予算] → 1 文だけ足す。兄弟の PR が同時に rules/ を増やして予算を超えたら、後にマージする側が予算の扱いを決める
