# Design

## Context

主に聞く理由の 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作）の正本は `output-styles/readable.md` の節 3 で、develop の `SKILL.md` の節「主に聞かずに決めること」と `references/parent-pass-criteria.md` がそれを使う。3 か所とも、主の手でしかできない操作の例に OAuth かログインを挙げている（parent-pass-criteria はダッシュボードの操作も）。動機は proposal.md の Why。

## Goals / Non-Goals

**Goals:**

- 主の手でしかできない操作を、エージェントの手では通せないもの（パスワード・MFA・CAPTCHA）に絞る
- ログイン済みのブラウザで押せる操作を外しても、主の名義で外へ出る・外部のアプリやサービスに権限を渡す・取り消せない操作の承認が抜けないようにする

**Non-Goals:**

- 主に聞く理由の数や、決まりで主の承認が要る操作の一覧を変えること
- 無人ループのラベル（issueify の `human-only`）や、ランナーの機械の操作の扱いを変えること

## Decisions

### 例の差し替えで直し、新しい区分を作らない

主の手でしかできない操作の例をパスワード・MFA・CAPTCHA に替え、「ログイン済みのブラウザで押せる操作は入らない」の 1 文を足す。別案は「ブラウザ操作」という区分を新しく作ることだが、主に聞く理由は 3 つだけという決まりを崩すので取らない。

### 承認の要否は手の問題と書き分ける

OAuth の認可ボタンを押すと、主の名義で外部のアプリに権限を渡すことがある。これは「手が要る」理由で聞くのではなく、「決まりで主の承認が要る」（主の名義で外へ公開・送信する・課金する・外部のアプリやサービスに権限を渡す（OAuth の認可を含む）・取り消せない）理由で聞く。OAuth の認可は取り消せるうえ公開・送信・課金のどれでもないので、権限を渡す操作を名指ししないと承認の側から抜ける（PR #1655 のゲートの指摘 P2-F1・P2-F2）。そこで次の 3 か所に同じ語で書く。SKILL.md の節の書き分けの 1 文、readable.md の「決まりで主の承認が要る」の項目（develop を使わないメインセッションにも効かせるため。元の「聖域・取り消せない操作」だけでは取り消せる権限の付与・公開・送信・課金が入らない）、parent-pass-criteria の条件「聖域でない」（元の外部への公開・送信・課金だけでは親の判定にも同じ穴が残る）。

### readable.md の例は製品名を書かない

readable.md は配る候補の 6 ファイルの 1 つで、固有名の制約がある（`harness-public-private-split`）。チャットの板の作成のような例は SKILL.md と proposal だけに置き、readable.md は「ログイン済みのブラウザで押せる操作（OAuth の認可ボタンなど）」に留める。

## Risks / Trade-offs

- [ログイン済みのブラウザが無い環境で、エージェントが自分で押そうとして詰まる] → その場合はログインが要り、パスワード・MFA のどちらかに当たるので主に回る。例の書き方で扱いが変わらない
- [OAuth の認可を、権限を渡す操作と気づかずに押す] → SKILL.md の書き分けの 1 文・readable.md の承認の項目・parent-pass-criteria の条件「聖域でない」で、外部のアプリやサービスに権限を渡す操作（OAuth の認可を含む）は承認の側で聞くと明記する
