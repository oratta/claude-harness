## Context

W の既定モデルは `sonnet` で、事前分類表に当たる実装だけが 1 周目から `opus` になる。表の正本は worker.md（`dev-workflow-develop` の要件が「1 周目列がすべて `opus`、`fable` 行なし」を規定）。判断は R1・G・決める役（`dev-workflow:decider`）が受け持つので、W を下げても読んで判断する役の品質は変わらない。

## Goals / Non-Goals

**Goals:**
- 3 件の再実行で、Sonnet 5.5 の W が Opus と同等かを判定規則どおりに決める
- 判定と根拠を changes の記録に残し、表を変える場合だけ表・テスト・説明文を揃えて変える

**Non-Goals:**
- R1・G・決める役のモデル、昇格ラダー（`templates/escalation-tripwires.md`）の変更
- W の上限（`opus`）の引き下げ
- Opus 側の再実行（過去の記録で比べる）

## Decisions

- **対象 PR は、issue の対象条件（聖域パス・スキル本文・hooks などに触れる）を満たし、W が opus で実装したものから選ぶ。** issue 本文はスキル本文を聖域パスの例に挙げているので、スキル本文に触れていることを根拠にする。候補の根拠: #607 は `skills/develop/references/roles/worker.md` と `decision-criteria.md`（スキル本文）、#462 は `skills/develop/SKILL.md`（スキル本文）、#568 は `commands/ci-watch.md`（コマンド定義。エージェントの行動を定義する）を編集している。auto-merge の SACRED 定義（`.github/workflows/`・`CLAUDE.md`・`.claude/`・憲法 doc）に当たる最近の PR は W が opus のものが無く、この定義に限ると 3 件揃わないので、対象条件は issue 本文のとおり（スキル本文を含む）とし、広げない
- **再実行は元の記録先と同じ指示で、GitHub に書かない条件で行う。** 再実行の W は push・issue/PR コメント・PR 作成・ラベル付けをせず、ローカル commit とテスト実行までに留める。既存の記録先を汚さず、費用と副作用を検証の範囲に閉じるため
- **比較は判定規則を先に固定する。** 「同等」は次の 3 項目がすべて成り立つこと。(a) 各 PR で追加・変更されたテストと `bats plugins/dev-workflow/tests` が、再実行でも exit 0 である（元も exit 0）。(b) 独立レビュアーが出した severity が `blocking` かつ status が `confirmed` の指摘件数が、元の件数以下である。(c) W のトリップワイヤー発火（規模超過・失敗ループ・仕様の発明）が、元に無ければ再実行にも無い。3 件とも同等なら表を変え、1 件でも成り立たなければ変えない。テストの失敗、元のログの欠測、再実行やレビューの実行不能など、証拠が足りない項目は「同等」と判定せず、「変えない」に倒す。結果を見てから規則を動かさない
- **ゲート指摘件数は、本体が独立レビュアーを起動して数える。** 本体はレビューを書かない（既存要件「本体はオーケストレータ専任」）ので、本体は再実行ごとに独立レビュアーを 1 体起動し、元の PR のゲートで使った指摘基準（severity `blocking`/`should`/`nit`、status `confirmed` など）を渡す。レビュアーは再実行の差分（マージ前 base との diff）を読み、指摘一覧をローカルの成果物（本体が指定するファイル）として返す。本体はその一覧から件数を集計するだけで、指摘の内容は判断しない。元の件数は PR コメントの仕分け・Gate Result から取る
- **spec の差分は 2 段に分ける。** 比較記録の要件は恒久要件として、合否にかかわらず今足す（記録先 issue 番号とモデル名は一般化した書き方にする）。表の 1 周目列や SKILL.md に関わる既存 3 要件（役割の指示書は references/roles/ に分かれている／役割のモデルは事前分類と残量モードで決める／W と G は役割ごとの種別で起こす）を変える差分は、合格したときだけ同じ change に追加し、表を変える前に R1 の再レビューで、worker.md・SKILL.md（86・240・246 行付近）・上記 3 要件を一緒に示して受ける

## Risks / Trade-offs

- 3 件では、まれにしか起きない失敗は見つからない → 表を変えたあとの品質低下は、W が失敗を報告したときの既存の昇格（Opus で再開）で拾う。この点は issue で受け入れ済み
- 再実行の W はゲート（G・レビュアー）を通らないので、ゲート指摘件数は独立レビュアーの一覧から数える。元のゲートのレビュアーと同じ人・同じ回数のレビューにはならず、件数は近似になる → 記録に、レビュアーの種別・model・渡した指摘基準を書く。近似であることは受け入れ、元の件数より多いかどうかだけを見る
- worker.md が #610 と衝突する → 表を変える段階で main を取り込み、表の位置を確かめてから編集する
