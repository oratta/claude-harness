# Design

## Context

動機は proposal.md の Why を参照。実装の前提は次の 3 つ。

- `照合表` は、語の検索コマンドごとに 1 表で、G が `review-hit-set.py` に 1 表ずつ渡す。スクリプトは `修正前 SHA:` と `検索コマンド:` を読み、固定 SHA で `git grep` を再実行して、表の `(ファイル, 行, 本文)` の集合と比べる
- Codex のレビュアーは read-only で、ファイルに書けない。結果は回答の本文でしか返せない。Claude のレビュアー（`dev-workflow:reviewer`）も Read と Bash だけで、ファイルを編集しない
- 同じ共通一覧契約を順 3 の第 1 段が使う。順 3 は W（書ける役）が PR コメントに投稿する表で、行ごとの `直した` / `該当しない` を `--head` の第 2 段が読む

このリポジトリで語 `pr-review-gate` を測った値: 全ヒットは 1,506 行・約 96 万バイト、ファイル数は 476、同じ本文をまとめて 120 バイトで切っても 1,133 行・約 21 万バイトある。flatmate #1779 の Codex の補足が載せられたのは 2,554 − 2,364 = 190 行だった。

## Goals / Non-Goals

**Goals:**

- ヒットが何行あっても、語 1 つの返答の量が検索コマンド 1 行と数値 2 つと食い違いの行だけに収まる
- 検索範囲の検査（`-- .` の固定、ヒットを減らす option の拒否）と、全ヒット集合の一致の検査を要約でも通す
- 読み取り専用のレビュアーが標準出力だけで作れる

**Non-Goals:**

- 順 3 の一覧の形を変えること（triage.md を変えない）
- `レビュー三表:` コメントが GitHub のコメント長の上限を超えたときの分け方（#1249）。要約は三表を小さくするだけで、#1249 が決める置き方と読み方の前提を変えない
- 読み取り専用レビュアーのテスト再実行（#1401）、手順書の短縮（#580）

## Decisions

### 語ごとの要約を返す形を選ぶ（ゲートが表を作る形を選ばない）

issue の 2 案のうち、レビュアーが語ごとの件数と食い違いの行だけを返し、全ヒットは機械照合に任せる形を選ぶ。

ゲートが全ヒット表を機械で作ってレビュアーに `扱い` の列だけを求める形は、3 つの理由で選ばない。検索語はレビュアーが `変更点の一覧` で決めるので、レビュアーより先にゲートが表を作れず、レビュアーを 2 回起こす流れになる。47 万字の表をレビュアーの入力に渡すと、Claude のレビュアーが打ち切られた原因（全ヒットを読むコンテキスト）が残る。`扱い` の列だけでも 2,554 行は返す必要がある。

### 全ヒットの出力のハッシュで集合の一致を見る

ファイルごとの件数の表や行番号の一覧も検討した。ファイルごとの表は語 1 つで 476 行になる例があり、複数の語を足すと #1779 で載った 190 行を超える。行番号の一覧は 1 文字ずつ写すので写し間違いが起き、照合が落ちて同じ `review-incomplete` に戻る。どちらも検索コマンドの出力から機械的に作る値で、ハッシュより強い証拠にならない。

ハッシュは `git grep -n <語の指定> <SHA> -- . | git hash-object --stdin` の値を使う。同じ SHA・同じコマンドの出力がバイト単位で同じなら全ヒット集合も同じなので、集合の一致の検査をそのまま保てる。語の数が増えても長さは変わらない。`git hash-object` は `-w` を付けなければオブジェクトを書かず、`.git` を書き込み不可にしても動くことを手元で確かめた。追加の道具が要らない。

行数は標準出力のバイト列の改行（`\n`）の数、ハッシュはそのバイト列を復号せずに渡した値とする。`wc -l` と揃えるためで、文字列にしてから `splitlines()` で数えると `\r` や `\x0c` でも分割されて食い違う。コマンドの `<rev>` は 40 桁の修正前 SHA をそのまま入れる。`git grep` の各行の先頭には打ち込んだ rev の文字列が出るので、短縮 SHA やブランチ名ではハッシュが変わる。`全ヒット要約:` の値の形式は「十進の行数 + ` 行 ` + 16 進の文字列」までを検査し、長さは固定しない。ただし `修正前 SHA:` の検査は 40 桁固定なので、object format が sha256 のリポジトリは今は `contract:` で止まる。

行数も別に持つ。一致しなかったときに G の補足要求へ差の大きさを書けるようにするため。差分の `file:line` は要約からは出せないので、補足ではレビュアーが検索コマンドを実行し直して要約を出し直す。

### 要約を使える下限を 10 行にし、スクリプトで強制する

全ヒットが 10 行以下の語で要約を使った表は契約違反にする。下限が無いと全部の語を要約で返せてしまい、語が少ない PR でも行ごとの判定が失われるため。返答の上限を決めるのは行数ではなく字数で、#1779 で載った 190 行は約 3.5 万字に当たる。このリポジトリの語は 1 行が 250〜300 字あり、PR #1501 のレビューの 1 区画に語が 10 個あったので、どの語も下限ちょうどでも 10 語 × 10 行 × 300 字 = 3 万字で収まる 10 を選ぶ。同じレビューの 27 語のうち 25 語は 10 行以下なので、語の大半で行ごとの判定が残る。下限はスクリプトの定数と reviewer-brief の 2 か所に書き、値が揃っていることをテストで固定する。

10 行を超える語を全行で返した表は拒否しない。正しい表を落とすと補足を 1 回無駄にするため。

### 形はスクリプトが表から判別する

`全ヒット要約:` の行があれば要約として照合する。新しい option を足さないので、G のコマンド（gate-runner.md の 2 か所の記述）は変わらず、順 3 の呼び出しにも影響しない。`--head` と要約の組み合わせは、順 3 が行ごとの `扱い` を要るので契約違反にする。

要約の表の下には、今の 4 列の表を食い違いの行だけで置く。行は全ヒットに含まれることを検査し、`扱い` は `食い違い: <finding ID>` だけを許す。食い違いが無ければ表を省いてよい。

### `Binary file` の行は 4 列の行の検査から除く

全ヒットに `Binary file ... matches` の行があると、全行の表の行の解析は `contract:` の即時停止になる。4 列の行の検査をこの解析に乗せると、語がバイナリに当たっただけで、正しい要約と本物の食い違いの行を持つ表が落ち、補足でも直らず `review-incomplete` になる。これはこの変更が直す止まり方そのものである。そこで全ヒットの行を解析せず、4 列の行から組み立てた `<SHA>:<パス>:<行>:<本文>` が全ヒットの行のどれかと同じ文字列かで判定する。バイナリの行には行番号が無く、4 列の行が指す先になれないので、除いても検査は弱くならない。コロンを含むパスも分割の誤りで止まらない。除くのは 4 列の行の検査だけで、行数とハッシュには含めるので全ヒット集合の一致の検査は保たれる。全行の表の経路は変えない。10 行以下の語は全行の表で返すので同じ止まり方が残る。変更前からある挙動で、検索コマンドに `-I` を足すと避けられる。CRLF のファイルの本文は行末に `\r` が付き、4 列の本文には写せないので、同じ検査では行末の `\r` を無視する。

### 順 3 は変えない

順 3 の表は W が書き、行ごとの `扱い` を第 2 段が読むので、要約にできない。triage.md を変えないことで #1401・#580 ほかとの重なりも増やさない。

### 読み方の手順を reviewer-brief に書く

要約にしても、レビュアーが `git grep -n` の全件を読めば打ち切りは残る。そこで、語ごとの行数を先に測り、件数の多い語は `git grep -c` のファイルごとの件数から入り、PR の差分に関わるファイルと用法が疑わしいファイルの本文を読むと書く。読むときに絞り込むのは読み方の話で、`検索コマンド:` の行は絞らない。

## Risks / Trade-offs

- [要約の語では全行を読んだことを保証しなくなる] → 保証範囲の文に、機械が保証するのは検索範囲と全ヒット集合の一致までで、一致の判定が全行の本文を読んだ結果とは限らないことを書く。全行の表でも `一致` の正しさは G が再レビューしないので、機械の保証は同じ強さに留まる
- [レビュアーとゲートの環境の違い（locale など）で `-i` や `-P` の検索結果が変わり、ハッシュが合わない] → 検索範囲の違いと同じく止まる側に倒れ、補足のあと `review-incomplete` になる。無言で通ることはない
- [10 行以下の語が多数あると全文の表の合計が返答に収まらない] → 下限は語ごとの判定で合計を見ないので、収まりは保証しない。1 行の長い repo では下限ちょうどの語が 12 個前後で 3.5 万字に届く。起きても今と同じく補足と `review-incomplete` で止まる
- [Codex の sandbox の中で `git hash-object --stdin` を実測していない] → 書き込み不可の `.git` では動くことを確かめた。実測は Codex が使えるときのレビューの周で分かり、動かなければ補足で止まる
- [一周目で要約の語に食い違いが出ると、順 3 で W が全行の表を PR コメントに投稿する必要があり、コメント長の上限に当たりうる] → この変更の範囲外。追跡先は #1249 で、順 3 の一覧の件はそこに記録した
- [レビュアーの指示どおりに作っても `<rev>` を短縮すると合わない] → 指示ブロックに 40 桁をそのまま入れると書き、テストで固定する。外れても補足で止まる

## Migration Plan

開いている PR のレビューには影響しない。全行の表は今までどおり受け付ける。戻すときはこの変更の revert だけでよい。
