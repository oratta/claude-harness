## Context

エピックの子（`epic-dispatch.sh route` が `nested` を返すセッション）は、主の返事を待って止まる前に、子 issue へ 1 行目 `子の停止: 主の返事待ち` の記録を投稿する（develop の SKILL.md の節「エピックの子が主の返事を待って止まるとき」。#1033・#1036）。この記録を読むのは 3 者で、どれも子の会話を読んでいない。

- 親の `wait --resolve` が呼ぶ `stop-judge.sh`（判断のモデル 1 回。基準は `parent-pass-criteria.md`）
- 親のセッション（判断が通せなかった止まりを、Orca 経路の手順 8 で主に上げる）
- 主（報告に添えた記録の URL から開く）

現状の実物で確かめたこと（2026-10-21 の main、71188f77）:

- `scripts/stop-judge.sh` は記録の項目名を解釈しない。81〜85 行で 1 行目が `子の停止: 主の返事待ち` の最新のコメント（投稿者が OWNER・MEMBER・COLLABORATOR）を選び、本文をまるごと判断のプロンプトに貼る（122〜126 行）。項目の有無で処理は分かれない
- `scripts/epic-dispatch.sh` も項目名を読まない。927〜931 行で 1 行目が一致するコメントの URL を取るだけ
- 項目名を読んでいるのは手順書の側だけ: SKILL.md の手順 8（「`止まった理由`・`推奨` を同じ項目名のまま含め」）と、その次の段落「マージ待ちの子」（`止まった理由:` が `PR のマージ待ち（` で始まるか）、`parent-merge-criteria.md`、`references/ci-watch.md` の例
- テストで項目名を固定しているのは `epic-dispatch.bats`（6 項目の並び 3159-3175、手順 8 と項目名の一致 3186-3192、基準のファイル 3246-3267）、`stop-judge.bats`（記録の例 35 行、そのまま渡ること 114-130）、`parent-merge.bats`（ci-watch の例の 5 項目 107-117）
- 既存の spec の要件「エピックの子の停止の記録は…」は「項目名 `止まった理由` と `推奨` は手順 8 の語と同じにする（MUST）」と決めている。#1176 が直したい「子の言葉の持ち込み」はこの規定から来ている

正本は `~/.claude/output-styles/readable.md` の節 3（PR #1179 でマージ済み）。6 段（質問 → 主に聞く理由 → いま困っていること → 推奨と根拠 → 受け入れるリスク → 答え方）と、主に聞く理由として成り立つ 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作）、どれにも当たらなければ聞かずに進めて事後報告すること、を決めている。

## Goals / Non-Goals

**Goals:**

- 親が記録だけを材料に、正本の 6 段で主への報告を書ける（主に聞く理由とリスクの頻度・根拠が記録にある）
- 主に聞く理由の無い止まりが主に上がらない（判断のモデルと親のセッションの両方で）
- 手順 8 が子の項目名をそのまま主に渡すことを求めない

**Non-Goals:**

- 正本（readable.md）と短い版（communication-style.md）の中身を変えること（#1179 で済み）
- 待ちに入る通知の答え方の位置（#1181）、言い直しの hook（#1184）
- `stop-judge.sh`・`epic-dispatch.sh` に記録の項目を解析させること（下の決定 4）
- `parent-merge-criteria.md`（マージ待ちの判断）の基準を変えること。マージは「決まりで主の承認が要る」側で、今の作りのまま

## Decisions

### 決定 1: `主に聞く理由:` を 2 番目の項目として足し、7 項目にする

並びは `止まった理由:` → `主に聞く理由:` → `前提:` → `推奨:` → `推奨の根拠:` → `受け入れるリスク:` → `再開に要る途中経過:`。

- 2 番目に置くのは、正本の 6 段が「質問 → 主に聞く理由」の順だから。親が上から順に置き直せる
- 値は 3 つの理由のどれかの語で始め、1 文で添える。「決まりで主の承認が要る」ときは、その決まりが何を守るためかまで書く（正本の 2 段目の決まり）
- どれにも当たらないとき、子はそもそも止まらず自分で進めて事後報告するのが正本の決まり。それでも子の側で進められない（hook に止められた・子の権限では打てない・待つしかない）ときは `主に聞く理由: なし（<子の側で進められない理由>）` と書く。親はこれを「主に上げずに通す候補」として読む

代案:
- 既存の `止まった理由:` に理由を書き足す案。採らない。判断のモデルも親も「主に聞く理由が成り立つか」を独立に確かめたいので、別の行に分けたほうが読み違えが少ない。また今の `止まった理由:` の「子の側でできない理由」は、主に聞く理由とは別物（子にはできないが親にはできる止まりがある。CI の再実行や子の起動し直し）で、混ぜるとこの区別が消える
- 項目名を正本の段の名前（`質問:`・`いま困っていること:`）に改める案。採らない。`止まった理由:` は「マージ待ちの子」の段落・`parent-merge-criteria.md`・ci-watch の spec が `PR のマージ待ち（` で始まる値として読む層間の契約で、改名は範囲を広げるだけで得が無い。置き直しは親がする（決定 3）

### 決定 2: `止まった理由:` を「主にしてほしいこと」に絞り、`受け入れるリスク:` に頻度と根拠を含める

- `止まった理由:` の定義から「それを子の側でできない理由」を外し、`主に聞く理由:` に移す
- `受け入れるリスク:` は正本の 5 段目と同じ 3 要素で書く: 何が起きるか（被害の大きさ・戻せるか）／どれくらい起きるか（起きる条件と頻度。確かめたのか見込みかの別）／分からないときは「分からない」と書き、何を調べれば分かるかを添える。SKILL.md には 3 要素を 1 文で書き、詳しくは正本を指す（書き方の文を写さない #1179 の方針のまま。ただし項目の中身として何を含めるかは記録の書式の一部なので、ここに書く）

### 決定 3: 手順 8 は記録を正本の 6 段に置き直し、主に聞く理由の無い止まりは親が通す

手順 8 の「`止まった理由`・`推奨` を同じ項目名のまま含め」を消し、次の対応で置き直すと書く。

| 記録の項目 | 正本の段 |
|---|---|
| `止まった理由:` | 1 質問（主にしてほしいことを問いの形に） |
| `主に聞く理由:` | 2 主に聞く理由 |
| `前提:` | 3 いま困っていること（主が見て分かる現象に直す） |
| `推奨:`・`推奨の根拠:` | 4 推奨と根拠 |
| `受け入れるリスク:` | 5 受け入れるリスク |
| （親が書く） | 6 答え方（今の手順 8 の親のタブ・子のタブの決まりのまま） |
| `再開に要る途中経過:` | 主には書かない（区切りの下に記録の URL を置けば足りる） |

- 項目名を見出しにせず、子が作業中に使った言葉は主の言葉に直す。記録の URL は今どおり本文に添える（子のゲートが親経由の許容を結び付けるのに使うので外せない）
- 止まった子が複数あるときも 1 通で上げるのは 1 件（正本の「1 通 1 件」）。残りは主の答えを受けてから次の報告で上げる。止まった子は動いている子から外さないので、待たせても検知は失われない
- **主に上げる前に、親は自分でも `parent-pass-criteria.md` に照らす。** 主に聞く理由の 3 つのどれにも当たらず、基準の他の条件も満たす止まりは、主に上げずに `epic-dispatch.sh reply --as parent` で通し、エピックに `親の判断: 子 #N 通した — <理由> <停止の記録の URL>` を残す。`wait --resolve` の判断が「主に上げる」とした止まり・判断できなかった止まり・一致する `親の判断:` が無い止まりも対象にする

代案:
- 判断のモデル（stop-judge.sh）だけに任せ、手順 8 では親が照らし直さない案。採らない。判断のモデルは sonnet で 1 回きり、入力も GitHub の記録だけなので、主に聞く理由が無いのに「主に上げる」に倒れることがある（基準が「迷ったら主に上げる」に倒す作りなので、倒れ方としては正しい）。主に上げる文面を書き始めた親が「主に聞く理由が書けない」と気づいた時点で止めるのが、正本の「理由が無ければ聞かない」をいちばん確実に効かせる場所である。親のセッションは判断のモデルより文脈を多く持つ
- 親が照らし直すとき、判断のモデルの「主に上げる」を覆せないようにする案。採らない。覆すのは「主に聞く理由が成り立たない」ときだけで、聖域・破壊的操作・マージ・既存の規則が主に聞く止まりは「決まりで主の承認が要る」に当たるので覆らない。安全側の歯止めは同じ基準の 9 条件で保たれる
- 繰り返しの歯止め: 親が通した止まりも `親の判断: 子 #N 通した` としてエピックに残るので、基準の「繰り返していない」条件と `stop-judge.sh` の過去の判断の読み取りがそのまま効く

### 決定 4: `stop-judge.sh`・`epic-dispatch.sh` の処理は変えない

どちらも記録の項目名を解釈していない（Context の確かめた事実）。`主に聞く理由:` の行は本文の一部として判断のモデルにそのまま渡る。受け入れ条件「新しい書式を読み、bats が通る」は、次の 2 つを bats で確かめて満たす。

- `stop-judge.bats`: 新しい形（7 項目）の記録の各行がモデルの入力にそのまま入る。以前の形（6 項目、`主に聞く理由:` が無い）の記録も、今どおりそのまま渡り、項目が欠けても exit 1 にならない
- `epic-dispatch.bats`: SKILL.md の記録の形が 7 項目をこの順で持つ・手順 8 に「同じ項目名のまま」が無く置き直しの規定がある・基準のファイルが原則と通る例を持つ

代案: stop-judge.sh のプロンプトに「`主に聞く理由:` を確かめよ」と 1 行足す案。採らない。判断の観点は基準のファイル（`parent-pass-criteria.md`）が正本で、プロンプトは「基準に照らせ」としか言っていない。観点をプロンプトに書くと正本が 2 つになる。

### 決定 5: `parent-pass-criteria.md` は原則を先に置き、9 条件を 3 つの理由に対応づける

- 冒頭に「主に聞く理由の 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作）に当たらない止まりは親が通す」を置く。9 条件は、その止まりが 3 つのどれにも当たらないことを確かめる手順として読む
- 表に「確かめる理由」の列を足す（例: 聖域でない・戻せる・既存の規則が主に聞く止まりでない → 決まりで主の承認が要る、推奨がある・範囲の内側・主の側の情報が要らない・配役表で主の観点が無い → 主の側にしか答えが無い、実機操作でない → 主の手でしかできない操作、繰り返していない → 親の判断が同じ止まりを回し続けないための歯止め）。条件の数は 9 のまま（既存の要件と bats の行数の検査を保つ）
- 子の `主に聞く理由:` は鵜呑みにしない。書かれた理由が 3 つに当たるかを判断が確かめ、当たらなければ通す側で読む。書かれていない（以前の形の記録）ときは、他の項目から判断する
- 通る例に 3 つ足す: 実機テストのための試しの issue 作成（作業中のリポジトリの中で、閉じれば戻せる。「外部への公開・送信」には当たらないと条件の文に添える）／止まった子の起動し直し（`reply --relaunch` で親ができる）／Mac が空いてからの CI の再実行（待って打ち直すだけ）
- 「迷ったら主に上げる」は残す。理由が成り立つか迷うときは成り立つ側に倒す

### 決定 6: ci-watch.md の例と spec を 1 項目ぶん足す

マージ待ちで止まる子の記録の例（`references/ci-watch.md` の「`ready` を受けたあと」の 1）は「残りの 5 項目」の例を並べ、spec `dev-workflow-ci-watch` がそれを MUST にしている。項目を足したのに例が古いままだと、子が `主に聞く理由:` を落とす。例に `主に聞く理由: 決まりで主の承認が要る（聖域のファイルに触れた PR は人がマージすると決まっている）。…` の形を足し、spec の「5 項目」を「6 項目」に直す。issue の「触るファイル」に無い 2 ファイル（ci-watch.md・parent-merge.bats）と ci-watch の spec が増えるが、同じ項目の追加から一意に決まる追随で、別の設計判断を含まない。

## Risks / Trade-offs

- [親が判断のモデルの「主に上げる」を覆し、主の承認が要る止まりを通す] → 覆せるのは主に聞く理由の 3 つのどれにも当たらないときだけで、聖域・破壊的操作・マージ・既存の規則が主に聞く止まりは「決まりで主の承認が要る」に当たる。通した判断はエピックに 1 行残り、主が事後に止められる（既存の作りのまま）。どれくらい起きるかは分からない。実機確認の 3 場面で、rm の許可の件が主に上がることを確かめ、どの条件（聖域でない・戻せる・主の側の情報が要らない など）で上がったかを記録する。rm は聖域の一覧には無く、上がるとすれば「戻せる」（消したものはブランチの中の取り消しで戻らない）の条件による
- [子が `主に聞く理由:` を形だけ埋め、どの止まりにも「主の側にしか答えが無い」と書く] → 判断のモデルと親は書かれた理由を鵜呑みにせず 3 つに照らす（決定 5）。子が書き方を外しても、主に上がる件が増えるだけで危険は無い
- [以前の形の記録を投稿する子が動いている間、親の置き直しで主に聞く理由の段が書けない] → 親は他の項目から主に聞く理由を考え、書けなければ通す側で判断する（主に聞く理由が書けないことは、正本の「聞かない」側の条件）。迷うときは基準どおり主に上げる
- [1 通 1 件にしたことで、止まった子が多いと主への報告が順番待ちになる] → 止まった子は動いている子から外さないので検知は失われない。複数の子が同時に主の判断を待つ件数は過去の記録で 1〜2 件で、待ちが長くなる見込みは小さい（見込み。実測していない）

## Migration Plan

- 手順書と基準のファイルの書き換えだけで、記録の書式は足すだけ（以前の形も読める）。動いている子は次に起動されたときから新しい形で書く
- 戻すときは、この change の commit を戻せば以前の 6 項目と手順 8 の文に戻る。スクリプトを変えないので、戻す範囲は文書とテストだけ

## 実機確認の進め方（受け入れ条件の最後の 1 つ）

`claude -p --plugin-dir <worktree>/plugins/dev-workflow` を使い、親の手順 8 の立場で次の 3 件の記録を入力にして、主への報告（または通す判断と `reply --as parent` の返事）を書かせる。記録は issue #1176 の背景にある 3 場面（rm の許可、CI が落ちた 2 件、初版の記録を配布の前提から外す件）を新しい 7 項目の形で書き起こしたもの。

- rm の許可: 主に上げ、報告が正本の 6 段（質問で始まり、主に聞く理由・いま困っていること・推奨と根拠・頻度と根拠付きのリスク・答え方）を満たし、項目名を見出しにしていない
- CI が落ちた 2 件（Mac が空いてから CI を再実行すれば足りる件）: 主に上げず、親が通す（`reply --as parent` の返事と `親の判断: 子 #N 通した` の 1 行を出す）
- 初版の記録を配布の前提から外す件: 推奨と主に聞く理由に応じて判定し、主に上げるなら 6 段を満たし、issue・PR の番号を主語にしていない

結果（入力・出力の全文と判定）を PR に貼る。
