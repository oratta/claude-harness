## Context

- `statusline.sh` は stdin の JSON を項目ごとに `jq -r '… // empty'` で読み（33〜42 行）、2 行目は `context_info`・`api_pace_info`・`session_cost_info` を `│` 区切りで連結する。空の区画は飛ばす（936〜950 行）
- 入力の `prompt_cache` の形は公式ドキュメント（https://code.claude.com/docs/en/statusline の Prompt cache fields）で確かめた
  - `prompt_cache` は 2.1.251 以降で、メイン会話の最初の API 応答までは無い。サブエージェントの分は数えない
  - `hit_ratio` は 0〜1。キャッシュ読み出しトークン ÷（読み出し＋書き込み＋非キャッシュ入力）のセッション累計で、分母が 0 の間は `null`
  - `last_miss_cause` は 2.1.260 以降のオブジェクトで、`causes` 配列に原因名（`tools_changed`・`system_prompt_changed`・`ttl_expired_5m`・`likely_server_side` など。ドキュメントは「such as」と書いており、全件の一覧は無い）が 1 つ以上入る。最初のミスまでと、原因を特定できなかったミスのあとは `null`
- **未確認**: 2.1.251〜2.1.259 の入力で `last_miss_cause` がキーごと無いのか `null` で来るのかはドキュメントに書かれていない。どちらでも「原因を出さない」で同じ結果になる要件にする
- 既存の区画はそれぞれ無効化の環境変数を持つ（`STATUSLINE_API_PACE`・`STATUSLINE_SESSION_COST`・`STATUSLINE_CODEX`）

## Goals / Non-Goals

**Goals:**
- キャッシュが効いているかを 2 行目の 1 区画で見せる
- `prompt_cache` を渡さない版・渡す前の描画で、標準出力を従来と同一に保つ
- 入力のどんな形でも statusline の描画を壊さない（fail-open）

**Non-Goals:**
- `warm`・`ttl`・`expires_at`・`misses`・`recache_tokens_if_cold` など、`hit_ratio` と `last_miss_cause` 以外の項目の表示（issue #714 の概要が挙げるのはこの 2 項目だけ）
- ヒット率の記録・集計（cost-ledger の台帳に列を足す案は #700 のあとで別に検討する、と issue の備考にある）
- サブエージェントのキャッシュの表示（入力に含まれない）
- `caching_observed` を見て区画を出し分けること。`caching_observed` は見ない。キャッシュのトークン数を報告しないプロバイダやゲートウェイでは、非キャッシュ入力だけが分母に積まれて `hit_ratio` が `0` になり、`Cache 0%` と出る（issue の範囲は `hit_ratio` と `last_miss_cause` の 2 項目。この表示が邪魔なら `STATUSLINE_PROMPT_CACHE=0` で消せる。README に書く）
- 入力の形の穴を塞ぎ切ること。入力の出どころは Claude Code 本体で、悪意のある入力は想定しない。何を拾い、何を通すかは spec の「対象の定義」に書く

## Decisions

### 1. 置き場所は 2 行目の `Context` の直後

`Context 91%  │  Cache 82%  │  API ¥1,446,038/mo  │  Session ¥1,240` の順にする。連結ループの対象に `cache_info` を先頭で足すだけで済む。

理由: `Context` とキャッシュはどちらも「今の会話の入力」の状態で、費用の区画（`API`・`Session`）より前にまとめたほうが読み分けやすい。行を増やす案は、キャッシュの情報が 1 区画で足りる量なので採らない（issue も「1 区画で出す」としている）。

### 2. 表記は `Cache <N>%`、N は `hit_ratio × 100` の四捨五入

`0.82` → `Cache 82%`、`0` → `Cache 0%`、`1` → `Cache 100%`。計算は `jq` の中で行う（`. * 100 | round`）。

理由: 既存の 2 行目は整数の百分率（`Context 91%`）で、小数を出す必要が無い。`jq` で計算すれば、小数点がカンマのロケールで `printf` や `awk` が狂う問題（既存テスト「amounts do not depend on the locale's decimal separator」が守っているもの）を避けられ、外部コマンドの起動も 1 回で済む。

### 3. 区画を出す条件は「`hit_ratio` が 0 以上 1 以下の数値」だけ

次のどれでも区画を出さず、標準出力は `prompt_cache` が無いときと同一にする: `prompt_cache` が無い／オブジェクトでない、`hit_ratio` が `null`・キー無し・数値でない・範囲外、`STATUSLINE_PROMPT_CACHE=0`。`hit_ratio` が出せないときは、`last_miss_cause` があっても区画を出さない。

理由: 受け入れ条件が「`prompt_cache` が無い JSON では従来と同じ出力」を求めている。`null` はドキュメント上「まだ数えるものが無い」状態なので、`0%` と出すと「キャッシュが効いていない」と読めてしまう。原因だけの区画は、何の原因かがヒット率なしでは伝わらないので出さない。

### 4. ヒット率の色はしきい値で変えない

ヒット率は固定の色（`Session` 区画と同じ `CYAN`）、原因の部分だけ `YELLOW` にする。

理由: `hit_ratio` はセッション累計で、最初のリクエストは全部が書き込みなので必ず低く始まる。「何 % 未満なら悪い」という根拠のある線がドキュメントにも無く、しきい値を置くとセッションの序盤が毎回警告色になる。注意を引くべきなのは「ミスが起きた」という出来事のほうなので、原因の表示だけ色を変える。

採らなかった案: `Context` と同じ赤・黄・緑の 3 段階。上の理由で誤警告が常態化する。

### 5. 原因は `causes` の先頭 1 つを短い名前で出し、残りは件数で示す

`last_miss_cause.causes` が 1 件以上の配列のとき、ヒット率のうしろに空白 1 つを置いて `miss:<短い名前>` を続ける。2 件以上あれば `+<残りの件数>` を付ける（`miss:tools+1`）。

| 原因名 | 短い名前 |
|---|---|
| `tools_changed` | `tools` |
| `system_prompt_changed` | `system` |
| `ttl_expired_5m` | `ttl5m` |
| `likely_server_side` | `server` |
| 上記以外 | 原因名をそのまま。16 文字を超える分は切る |

原因名が `[A-Za-z0-9_]` 以外の文字を含むとき、文字列でないとき、空のときは原因を出さない（ヒット率だけ出す）。`last_miss_cause` が `null`・キー無し・オブジェクトでない、`causes` が配列でない・空、のときも原因を出さない。`tools_added`・`tools_removed`・`system_char_delta` などの付随する数値は出さない。

理由: 原因名はそのままだと最長 21 文字あり、2 行目が端末幅を超えやすい。ドキュメントが名前を挙げている 4 つだけ対応表で短くし、表に無い名前（ドキュメントは全件を列挙していない）は読める形のまま長さだけ抑える。表に無い名前を捨てる案は、新しい原因が足されたときに黙って消えるので採らない。文字の種類を絞るのは、入力の文字列をそのまま端末に書くと制御文字が混ざりうるため。

採らなかった案:
- 全原因を並べる。2 行目が長くなりすぎる
- 直近のミスからの経過時間（`last_miss_at`）で古い原因を消す。issue の範囲（`hit_ratio` と `last_miss_cause` を出す）を超え、何分で消すかの根拠も無い。原因は次のミスか `null` に戻るまで出し続ける

### 6. 無効化の環境変数 `STATUSLINE_PROMPT_CACHE` を足す

`0` で区画を出さない。既定（未設定を含む `0` 以外）は表示。

理由: 2 行目の他の区画はすべて同じ形の変数を持つ。区画が 1 つ増えて 2 行目が端末幅を超える環境で、スクリプトを手で編集せずに消せるようにする。

### 7. 読み取りは `jq` 1 回、失敗は無表示

ヒット率と原因を 1 回の `jq` で取り出し、`jq` がエラーを返したら区画を出さない。標準エラーには何も出さず、終了コードも変えない。ファイルの読み書きとネットワークアクセスはしない。

`jq` の式は、原因の取り出しで型を先に確かめ（`last_miss_cause` がオブジェクトか、`causes` が配列か、先頭が文字列か）、原因の形が壊れていても式全体をエラーにしない。`causes` が文字列や数値のときにエラーでヒット率ごと消えると、spec の「原因の形が壊れていればヒット率だけ出す」に反する。

理由: statusline は描画のたびに走るので、起動するプロセスを増やさない。壊れた入力で 2 行目ごと消えるのは避ける。

## Risks / Trade-offs

- [`hit_ratio` はセッション累計なので、直近でキャッシュが切れてもすぐには下がらない] → 直近の出来事は `miss:` の表示で補う。直近の状態（`warm`）の表示は Non-Goals
- [原因は次のミスまで出し続けるので、何時間も前のミスが残る] → 表記を `miss:` として「直近のミス」であることを README に書く。経過時間で消す案は Decisions 5 のとおり採らない
- [キャッシュのトークン数を報告しないプロバイダでは `Cache 0%` が出続け、「キャッシュが効いていない」と読める] → `caching_observed` は見ない（Non-Goals）。README に書き、消したい場合は `STATUSLINE_PROMPT_CACHE=0`
- [ドキュメントに無い原因名が来ると、対応表を通らず長めに出る] → 16 文字で切る。対応表への追加は後から足せる
- [マージしても、`/statusline:setup` を再実行するまで表示されない] → 変更の記録に書く（`changes/692.md` と同じ注意書き）
