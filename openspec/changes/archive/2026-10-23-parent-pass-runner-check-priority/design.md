## Context

条件表の「実機操作でない」は「MFA・OAuth・ログイン・ダッシュボードの操作など、主の手が要る操作を含まない」。通る例の CI の再実行は原因の切り分けを通す条件にしない。節「CI の見張りのやり直しの上限で止まった子」（#1268）は、上限で止まった子に限って、確認が先の推奨と `job-timeout` の `escalate` を主に上げると書き、後者の理由を「ランナーの状態確認を求めるので実機操作に当たる」とする。節の外の読み方と、節と通る例・新しい段落の優先順位が空いている。`ci-watch.md` の `escalate` は「ランナーの状態を確かめてほしい」としか書かず、確認の手段を決めていない。

## Goals / Non-Goals

- Goals: ランナーの状態の確認を含む推奨を通すか主に上げるかと、節・通る例・新しい段落の優先順位が、基準を読んで一通りに決まる。
- Non-Goals: 見張りの上限自体の変更、条件表への条件追加、`ci-watch.md` と `stop-judge.sh` の変更。

## Decisions

用語は一つにそろえる: 「実機操作に当たる（条件『実機操作でない』を満たさない）」「実機操作に当たらない（満たす）」。

1. **確認の種類で実機操作かを分ける**: `gh api` や `gh run view` など、API で読むだけで済む確認（ランナーの登録状態・オンライン・ジョブの待ち時間）は主の手が要らないので、実機操作に当たらない。ランナーの機械に入る操作（ログイン、再起動、プロセスやディスクの確認と操作、設定変更）が要る確認は、主の手が要る操作として実機操作に当たる。種類が判断できなければ実機操作に当たる側に倒す（「迷ったとき」と同じ向き）。
2. **節の外（上限で止まっていない子）の読み方**:
   - 確認が `gh api` だけで済むなら、推奨をそのまま（確認を含めて）通し、返事にその確認を書いてよい。「`gh api` で確かめて、結果に応じて再実行」もこれに当たる（確認は実機操作に当たらず、再実行は戻せるに含まれる）。
   - 機械での確認が要る推奨は、再実行が確認の結果に依らず推奨の中に独立した再実行が書かれているときだけ、再実行だけを切り出して通す。返事は再実行だけを送り、機械での確認は求めない（原因の切り分けを通す条件にしない決まりと同じ）。
   - 再実行が機械での確認や操作の結果に依るとき（確認して結果に応じて、直してから、など）は切り出さず、主に上げる。
   - 「切り出しても同じ失敗を重ねるだけのとき」は切り出さない条件に入れない。子の記録から判定できず、通る例の「原因の切り分けを通す条件にしない」と食い違うため。
   - 却下案: 確認を含む推奨は常に主に上げる（通る例の趣旨と食い違い、主の手間だけが増える）、常に再実行へ書き換えて通す（推奨と違う返事を親が作る）。
3. **優先順位**: 子の記録の `止まった理由:` が見張りのやり直しの上限を挙げている止まり（節の対象全体。`job-timeout` に限らない）は、通る例の「CI の再実行」と D2 の新しい段落のどちらよりも節が先に効く。通る例の「原因の切り分けを通す条件にしない」と、D2 の切り出し・`gh api` の確認をそのまま通す読みは、節の対象の止まりには当てない。上限で止まった子の再実行は見張りが既に 1 回やり直した後の 2 回目で、因果の説明（失敗が差分と因果を持たない）が追加のやり直しを許す根拠になっているから。具体的に、(a) 子の記録が原因は断定できないと書いて再実行だけを勧めたときは、因果の説明が無いので主に上げる。(b) 手順 7 で上げた止まり（`cause` が `job-timeout` でない）で推奨が「`gh api` でランナーがオンラインか見てから再実行」のように確認が先のときは、確認が `gh api` だけで済む場合も主に上げる（節の既存の規則）。
4. **節の `job-timeout` の括弧の理由を書き換える**: 「ランナーの状態確認を求めるので実機操作に当たる」を「ランナーの側に原因があり、PR の差分でもやり直しでも直らないため」に直す。実機操作かの分け方（D1）に依らない理由にして、D1 と食い違わないようにする。
5. 条件表は増やさず、追加は文章の段落と節への追記に限る。`epic-dispatch.bats` が表の行数（見出し＋9 行）を数えるため。
6. 公開版の部品なので、他リポジトリの org 名や issue 番号を例に書かない。既存の bats は「Mac が空いてからの CI の再実行」という文字列が無いことを確かめているので、基準のファイルにその語順で書かない。通る例の行の先頭「CI の再実行（無関係なテストの時間切れ・ランナーの混雑・待って打ち直すだけで済むもの）」は grep -F で確かめられているので、括弧の中を変えず、添える文は行末に足す。

## Risks / Trade-offs

- 節の対象で原因が断定できない再実行や、`gh api` だけで済む確認が先の推奨を主に上げるので、主の手間が増える。ただし 1 回目のやり直しが既に済んでいるので、同じ失敗を重ねる前に主が見る価値がある。
- 子が機械での確認を `gh api` の確認と書き誤る記録は通りうる。損失は CI 1 周分で、守備範囲で許す。
