## ADDED Requirements

### Requirement: コメント長の上限を超える本文は親と部分のコメントに分ける

`stages/triage.md` は、`レビュー三表:` のコメントと `## 一覧（順 3）` のコメントが GitHub のコメント長の上限（65,536 字）を超えるときの共通の規則を持たなければならない（MUST）。長さは `wc -c` のバイト数で測る。コメント全体が 65,536 バイト以下なら、分けずにこれまでどおり 1 件に置かなければならない（MUST）。超えるときは次の形にしなければならない（MUST）。

- 親のコメント: 1 行目と見出しの行は分けないときと同じにし、本文（表）を置かず、続けて `部分 k/n: <コメントの URL>` の行を k の順に n 行置く
- 部分のコメント: 1 行目を `<種類>の部分 k/n`、2 行目を親と同じ SHA の行、3 行目を空行にし、4 行目以降に元の本文を置く。それぞれ 65,536 バイト以下にする

#### Scenario: 上限に収まるコメントは分けない

- **WHEN** 投稿する本文全体が 65,536 バイト以下である
- **THEN** コメントは 1 件で、`部分 k/n:` の行を持たず、読み手はこれまでどおり親の本文を読む

#### Scenario: 字数で収まってもバイト数で超えれば分ける

- **WHEN** 本文が 40,000 字で 120,000 バイトある
- **THEN** コメントは親と部分に分かれ、どの部分も 65,536 バイト以下である

### Requirement: 分けるコメントの切り方と投稿の順

本文は行の境界で切り、部分を k の順に連結すると元の本文の行の並びに戻るようにしなければならない（MUST）。表の見出しを部分ごとに繰り返してはならない（MUST NOT）。部分を空行で終えてはならない（MUST NOT。読むときに末尾の改行といっしょに落ちるので、空行は次の部分の先頭に送る）。部分をすべて投稿してから親を最後に投稿しなければならず（MUST）、親のない部分は読んではならない（MUST NOT）。1 行だけで部分に収まらない行があれば、そのコメントを投稿してはならない（MUST NOT）。

#### Scenario: 途中まで投稿して止まる

- **WHEN** 部分を 2 件投稿したところで投稿者が止まり、親が投稿されていない
- **THEN** 読み手はその部分を読まず、最新の親のコメントだけを見る

#### Scenario: 1 行で部分に収まらない

- **WHEN** 1 行だけで 65,536 バイトを超える行が本文にある
- **THEN** そのコメントは投稿されず、W の一覧なら W が、三表なら G が、それぞれの要件のとおり止まる

### Requirement: 分けたコメントの読み方

読み手は親のコメントに `部分 k/n:` の行が無ければ、これまでどおり親の本文を読まなければならない（MUST）。行があれば、k の順に各部分の本文を取得し、親と同じ PR のコメントであること、1 行目の k/n が親の行と一致すること、2 行目が親の SHA の行と一致することを確かめ、先頭の 3 行を除いて連結しなければならない（MUST）。連結では各部分の末尾の改行を 1 個に正規化し、部分の間の行区切りを 1 個残す（行同士を直接つながない・空行を入れない）。表ファイルは、親の見出しの行、空行、連結した本文の順に作り、`部分 k/n:` の行を入れてはならない（MUST NOT）。

#### Scenario: 末尾に改行が付いたまま取得される

- **WHEN** 部分の本文の末尾に改行があり、連結するとそこに空行が入りうる
- **THEN** 手順どおりに連結した表ファイルは、前の部分の最後の行と次の部分の最初の行が別の行のまま続き、表の途中に空行は入らない

### Requirement: 分けたコメントの規則の守備範囲

要件「分けるコメントの切り方と投稿の順」と「分けたコメントの読み方」の守備範囲は次のとおりとする（MUST）。

- 入力: 同じ PR の親のコメントと、親が URL で指す部分のコメント。投稿者は協力的だが、投稿の途中で止まる・部分の順や SHA を書き間違える前提で扱う
- 拾いたい誤り: 部分の欠落と順の取り違え、別の PR のコメントや別の SHA の部分を連結すること、途中まで投稿した組を読むこと、連結で表の途中に空行が入って以後の行が読まれなくなること
- 通ることを許す入力の例: 字数では上限に収まるがバイト数で超えるコメントが分かれること
- 範囲外: 親のコメントの偽造、1 行だけで上限を超える行を分けて載せること。これらの穴を塞ぎ切ることを本要件の完了条件にしない

#### Scenario: 別の PR のコメントを指している

- **WHEN** 親が指す URL の 1 つが別の PR のコメントである
- **THEN** 読み手はその部分を連結せず、親と対応しない部分として扱う

### Requirement: 三表の親と部分

三表が上限を超えるとき、親のコメントは 1 行目 `レビュー三表:` に続けて `固定 HEAD: <40 桁>`、`一周目の区画: <なし | n>`、`補足済み回数: <0 | 1>` の行を持たなければならない（MUST）。部分のコメントの 1 行目は `レビュー三表の部分 k/n`、2 行目は `固定 HEAD: <40 桁>` とし、本文は元の三表の全部としなければならない（MUST）。照合と振り分けの G は、補足の `needs-reviewer` を返す前に部分と親の投稿を終えなければならない（MUST）。最新の `レビュー三表:` のコメントを探す読み手は、1 行目が `レビュー三表:` のコメントだけを親として扱わなければならない（MUST）。

#### Scenario: 分けた三表を次の G が読む

- **WHEN** 三表が上限を超え、G が 3 つの部分と親を投稿して `needs-reviewer` を返し、新しい G が補足結果を受け取る
- **THEN** 新しい G は親から `補足済み回数: 1` と一周目の区画を読み、3 つの部分を連結して元の三表に戻し、補足結果を加えて同じ機械照合を再実行する

#### Scenario: 部分を親と取り違えない

- **WHEN** PR に `レビュー三表の部分 k/n` で始まるコメントが親と並ぶ
- **THEN** 読み手は 1 行目が `レビュー三表:` のコメントだけを最新の親として読む

### Requirement: 三表を置けない・読めないときは review-incomplete で止める

読み手は、三表の部分が読めない、または親と対応しないときは、元の三表の欠落として残差に記録し、Status `review-incomplete` で return しなければならない（MUST）。合格処理へ進んではならず、2 回目の `needs-reviewer` を返してはならない（MUST NOT）。

G は 1 行だけで部分に収まらない行のある三表を投稿できないときも、補足の `needs-reviewer` を返さず、Status `review-incomplete` で return しなければならない（MUST。補足済み回数の記録が残らないまま補足を頼むと、回数が 0 に戻るため）。

#### Scenario: 部分が読めない

- **WHEN** 親が指す部分の 1 つが取得できない、または 1 行目の k/n や `固定 HEAD:` の行が親と一致しない
- **THEN** G は残差を記録して `review-incomplete` で return し、合格処理へ進まない

#### Scenario: 三表を投稿できない

- **WHEN** 三表に 1 行だけで部分に収まらない行があり、G が補足を頼もうとしている
- **THEN** G は `needs-reviewer` を返さず、`review-incomplete` で return する

### Requirement: 順 3 の一覧の親と部分

順 3 の一覧（順 6 の裁定「全部列挙してから直す」の一覧を含む）が上限を超えるとき、要件「一覧の一致で閉じる（順 3）」の「1 つの PR コメントに投稿」の例外として、W は親と部分のコメントに分けて投稿しなければならない（MUST）。親のコメントは 1 行目 `## 一覧（順 3）` に続けて `修正前 SHA: <40 桁>` と `検索コマンド: <コマンド>` の行を持たなければならない（MUST）。部分のコメントの 1 行目は `一覧（順 3）の部分 k/n`、2 行目は `修正前 SHA: <40 桁>` とし、本文は主表と補助表の全行としなければならない（MUST）。全ヒット要約に置き換えてはならない（MUST NOT）。

#### Scenario: 分けた一覧の 1 行目と 2 行目

- **WHEN** W が順 3 の一覧を 3 つの部分に分ける
- **THEN** 部分の 1 行目は `一覧（順 3）の部分 k/3`、2 行目は `修正前 SHA: <40 桁>` で、親の 1 行目は `## 一覧（順 3）` である

### Requirement: W は分けた一覧を push の前に投稿する

W は部分と親の投稿を push より前に終えなければならない（MUST）。`stages/triage.md` の順 3 の節と `worker/implement.md` は、上限を超えるときにこの規則へ案内しなければならない（MUST）。W は 1 行だけで部分に収まらない行のある一覧を投稿できないとき、投稿も push もせず、そのことを return で本体に報告しなければならない（MUST）。

#### Scenario: 全行の表が上限を超える

- **WHEN** 順 3 の検索語の全ヒットの表が 65,536 バイトを超える
- **THEN** W は表を行の境界で部分に分けて投稿し、最後に親を投稿してから push する

#### Scenario: 一覧を投稿できない

- **WHEN** 一覧に 1 行だけで部分に収まらない行がある
- **THEN** W は投稿も push もせず、return で本体に報告する

#### Scenario: 案内と規則が読める

- **WHEN** `stages/triage.md` の順 3 の節と `worker/implement.md` を読む
- **THEN** 上限を超えるときの規則の節への案内があり、規則の節には親と部分の形・投稿の順・復元の手順・読めないときの扱いが書かれている

### Requirement: G は分けた一覧を復元して同じ照合に通す

G は順 3 の親と部分から要件「分けたコメントの読み方」の手順で表ファイルを作り、そのあとの照合は分けないときの経路をそのまま使わなければならない（MUST）。grep の語の経路は `review-hit-set.py` に渡し、場合分けの軸の経路はスクリプトへ渡さず、表の行の集合と軸の全域との一致だけを見て、grep の検索コマンド・4 列・第 2 段を要求してはならない（MUST NOT）。

親の `部分 k/n:` の行が n 行そろわない、部分が n 件取得できない、または部分が親と対応しないときは、G は照合を行わず W に表の出し直しを求めなければならない（MUST）。これは順 3 の差し戻し 1 回に数える。W が出し直すときは親と部分を投稿し直し、G は最新の親を読まなければならない（MUST）。

#### Scenario: 復元した表がスクリプトを通る

- **WHEN** grep の語の一覧で、分けた部分の末尾に改行が付いたまま取得され、G が手順どおり連結した表ファイルを `review-hit-set.py --head <HEAD の 40 桁 SHA>` に渡す
- **THEN** 分けなかったときと同じ照合結果になる

#### Scenario: 場合分けの軸の一覧を復元する

- **WHEN** `| 軸の値 | 扱い |` の表が親と部分に分かれている
- **THEN** G は連結した表をスクリプトへ渡さず、表の行の集合と軸の全域との一致だけを見る

#### Scenario: 部分の取得が親の数に足りない

- **WHEN** 親に `部分 k/3:` の行が 3 行あり、G が取得できた部分が 2 件である
- **THEN** G は照合を行わず W に表の出し直しを求め、差し戻し 1 回に数える

#### Scenario: 主表のヒット行が欠けた表をスクリプトが拾う

- **WHEN** 検索コマンドの行と主表の見出しを保ったまま、主表のヒット行の一部が欠けた表ファイルを `review-hit-set.py` に渡す
- **THEN** スクリプトは exit 1 で欠けたヒットを `missing:` として出力する
