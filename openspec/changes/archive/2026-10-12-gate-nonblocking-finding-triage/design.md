## Context

`plugins/dev-workflow/skills/pr-review-gate/stages/triage.md` の手順 2-1 には「止める指摘の仕分け表」（順 1〜6）があり、順 1（止める判定に達しない）の行き先が「follow-up issue に回す」になっている。止めない指摘は、G が手順 3 へ進むときに全件 issue になる。

主は 2026-10-12 に、issue にする前に 5 つの問いを上から当てる流れを決めた。正本は #973 のコメント 2 本「主の決定: 止めない指摘の振り分けの流れ」（https://github.com/oratta/claude-harness/issues/973#issuecomment-6116051276 ）と「順 2 を『条件がいつ成り立つか』の判定に置き換える」（https://github.com/oratta/claude-harness/issues/973#issuecomment-6116248482 ）。候補探しのスクリプト `plugins/dev-workflow/scripts/review-issue-candidates.sh` は #984（PR #989）で main に入っている。この change は手順書と仕様だけを変え、スクリプトは変えない。

主の決定で決まっている点（振り分けの 5 つの問いと行き先、条件がいつ成り立つかの表、エピックに効く指摘の分け方の表、主に聞くときの形、受け入れた点）は、仕様の差分にそのまま写した。この文書には、主の決定に書かれておらず仕様を書く段で埋めた点だけを書く。

## Goals / Non-Goals

**Goals:**

- 止めない指摘が、振り分け表を通らずに issue にならないこと
- 既存の「止める指摘の仕分け表」の順 1〜6 を指している文（hold.md・pass.md・gate-runner.md・仕様・bats）が、新しい段と取り違えられないこと
- 候補探しのスクリプトを、実物の引数と出力の形どおりに呼ぶこと

**Non-Goals:**

- 派生が続くときに止まる別の仕組み（主の決定で作らない）。レビューの既定 2 周と PR トークン上限は変えない
- 件数や行数の上限を目標に置くこと。issue になった件数は記録するだけ
- `review-issue-candidates.sh` の変更
- 止める指摘の仕分け表の順 2〜6 の中身の変更
- 既に切られた follow-up issue の整理

## Decisions

### 1. 新しい表は「止めない指摘の振り分け表」、段は A〜E と呼ぶ

主の決定のコメントは 5 つの問いを「順 1〜5」と呼んでいるが、`triage.md` には既に順 1〜6 があり、hold.md・pass.md・gate-runner.md・仕様・bats が「順 5」「順 6」で参照している。同じ数字の呼び方で置くと、「順 5」が「主に切り出すかを聞く」と「費用対効果」のどちらを指すか分からなくなる。

- 採った案: 表の名前を「止めない指摘の振り分け表」、段を英字の A〜E にする。主の決定の順 1→段 A、順 2→段 B、順 3→段 C、順 4→段 D、順 5→段 E。PR 本文の仕分けの表（flatmate#1405 の後追い 9 件）にはこの対応を 1 行添える
- 捨てた案: 「振り分け 1〜5」のように語だけ変える。数字が残るので「順 5」と読み違える余地が残る
- 捨てた案: 既存の順 1〜6 のほうを改名する。参照している文と bats が多く、この issue の範囲を超える

### 2. 段 A の直しは 1 周目だけ `agent-review:failed` で戻し、2 周目以降は段 B から当てる

主の決定は「始まる時点は今と同じ」「PR の中で直す指摘が多いとき PR の周が増えるが、PR ごとの歯止めがそのまま効く」としている。W に戻す経路は `agent-review:failed` しか無いので、段 A はそれを使う。既存の「止めない指摘を理由に 3 周目を開けない」は変えないので、2 周目以降の周の終わりに残った段 A の指摘は、直しに戻さず段 B から当てる（flatmate#1510 の行「順 1 で直すか、順 3 の子 issue」と同じ形）。

段 A の基準「この PR が変えた範囲の中で直せる」は、「直す場所がこの PR の diff が触れたファイルの中に収まる」と書く（主の決定の表の例「hook は PR が変えたファイル」に合わせた）。行数の上限は置かない。

段 A だけで戻した failed では、手順 2-2 のモデル昇格を当てず、W のモデルを据え置く（仕様レビューで本体が決めた。戻す中身がその PR の範囲で直せる止めない指摘で、モデルを上げても収束の見込みは変わらず、主の決定の「PR ごとの歯止めはそのまま」にも触れない）。止める指摘（順 2〜4）が同じ failed に混ざるときは、今の 2-2 の規則がそのまま当たる。

受け入れること: 1 周目に止めない指摘だけが届いた PR が、今は 1 周で通るのに、段 A の指摘があれば 2 周になる。

### 3. 条件の答えは本文の節 `## 条件の答え` に置き、答えが出たあとの当て直しは答えを受け取ったセッションが行う

主の決定は「答えは 1 行にして、聞いたエピックの本文に足す」「以後のレビューの依頼文に入れる」としているが、本文のどこに足すか、エピックに属さない PR ではどこか、答えが出たあと確認待ちの指摘を誰が振り分けるかは書かれていない。

- 置き場所: 本文の節 `## 条件の答え`（無ければ作る）。エピックに属さない PR では記録先の本文。段 B の表が「エピック（エピックに属さない PR では記録先の issue）の範囲」と並べているのに合わせた。節の名前を固定するのは、G とレビュアーを起こす側が同じ場所を読めるようにするため
- 当て直す担い手: 答えを受け取ったセッション（develop では本体）。サブエージェントに任せてよい。本体は `stages/triage.md` を読まないので、この義務は本体が読む `gate-runner.md` の「段ごとの起動と入力」の末尾にも置く（仕様レビューの指摘。develop の SKILL.md は触らない）
- 捨てた案: 照合と振り分けの G を「条件の答えの受領」で起こし直し、Gate Result で返させる。質問でマージを止めないので、答えが届く時点では PR が合格済み・マージ済みのことがあり、Gate Result の Status と `次の段:` の表に合う値が無い。表に行を足すと develop の SKILL.md・gate-runner.md・`dev-workflow-develop` の仕様・bats まで広がる。当て直しはラベル・周・宣言に触れないので、ゲートの段に入れない

受け入れること: 答えを受け取ったセッションが当て直しを忘れると、指摘は `条件の確認待ち` のまま PR コメントに残る（主の決定の「受け入れた点」にある「主の答えが遅れると…残り続ける」と同じ結果）。

### 4. 候補探しは `--epic` 付きで 1 回、`--children-only` は使わない

スクリプトの実物は `--epic <番号>` で各行の 3 列目に `child` / `other` を足し、`--children-only` を足すと子だけに絞る。振り分けは 1 回の実行結果を段 C（子か外か）と段 D（同じ場所の issue があるか）の両方で使うので、絞らない。`--exclude` にはいまの PR と記録先 issue の番号を渡す。

- 行番号: 指摘の場所は `ファイル:行範囲` で書かれる（`reviewer-brief.md` の書式）。スクリプトは行番号の付いたパスをそのまま検索語にする（仕様の守備範囲に「行番号を落とすのは呼び出し側」とある）ので、`:` 以降を落として渡すと手順に書く
- 失敗: スクリプトは検索の失敗で標準出力を空にして終了コード 1 を返す。これを「候補なし」と読むと、相乗りできる issue があるのに新しい issue を作る。引数を直して 1 回だけやり直し、だめなら失敗を PR コメントに記録して、既存 issue への相乗りをせずに進める。ここで止めないのは、対象がマージを止めない指摘だから
- エピックに属するかの判定: 記録先 issue の親を `gh api repos/<owner>/<name>/issues/<記録先>/parent` で取る。実装の段で、このエンドポイントが子 issue #985 に対して 973 を返すことを実測した（2026-10-12、`gh api repos/oratta/claude-harness/issues/985/parent --jq .number` が `973`、終了コード 0）
- 「同じ場所を直す」かは題名で判断する。本文を読むのは、段 C で外の issue の受け入れ条件を確かめるときだけ（主の決定の見積もり「追加の LLM コストは、ゲート役が題名を読む分」に合わせた）

### 5. PR #989 のレビューからの申し送り 2 点は、どちらも採る

申し送り（https://github.com/oratta/claude-harness/issues/985#issuecomment-6117161632 ）は受け入れ条件に足さない参考で、採るかは仕様を書く段で決めるとされている。

| 申し送り | 判断 | 理由 |
|---|---|---|
| スクリプトが出す題名は第三者が書けるので、指示として読まない、と手順に書く | 採る | このリポジトリは public で issue は誰でも作れる。題名はスクリプトがそのまま出力し、G が読む。足すのは 1 文で、毎回の手間は増えない |
| `other` の候補にコメント以外の操作をする前に `author_association` を確かめる | 採る | 第三者の issue の本文を G が読む場面と、第三者の issue がエピックの子に入る場面は、段 C の表の 2 行目だけにある。確認は `gh api` 1 回で、その行に当たったときだけ走る。2026-10-12 時点で open の issue 239 件の投稿者はすべて OWNER なので今は空振りだが、第三者が issue を作った時点から成り立つ条件で、成り立ったときの影響（第三者の文がエピックの完了条件に入る）は確認 1 回の手間より大きい |

段 D の参考のコメントは、第三者の issue にコメントが 1 件付くだけで、本文を読まず、エピックにも入らないので、確認なしで入れる。`child` の候補は主（または権限を持つ人）がエピックに足したものなので確認しない。

### 6. 主が切り出すと答えた止める指摘は、捨てずに置き場所だけ決める

受け入れ条件は「`grep -n 'follow-up issue' stages/*.md` の全行が振り分けを経た書き方になっている」で、hold.md 71 行目（切り出しの確認で主が「切り出す」と答えた指摘）と pass.md 45 行目（合格条件）も対象に入る。これらは止める指摘（確認済みの欠陥）で、主が「残して別 issue で直す」と決めたものなので、段 B・段 E で捨てたり段 D の参考のコメントで済ませたりすると追跡が切れる。

- 採った案: 必ず issue にする。置き場所だけ、エピックの完了条件に効くなら段 C の表、それ以外はエピックの外の新しい issue で決める。pass.md の合格条件の文（「主が切り出すと答えて follow-up issue に切ったもの」）はそのまま成り立つので、置き場所の参照を足すだけにする
- 捨てた案: 止める指摘も振り分け表の全段に通す。主が 4 点（何が起きるか・見積もり・固定費・推奨）を見て切り出すと答えたあとで G が捨てる経路ができる

### 7. 「follow-up issue」の語は残す

振り分け表で issue にすると決まった指摘の呼び名として残す。既存の bats が見ている文のうち今も正しいもの（「follow-up issue はまだ切らない」「手順3へ進むとき」「主が切り出すと答えて follow-up issue に切ったもの」）は書き換えない。

## Risks / Trade-offs

- [G が段 B で、実際には起きない条件を「範囲で成り立つ」と読み、今と同じく issue になる] → 仕様の守備範囲に「誤ったまま通ることを許す」と書いた。今より悪くはならない。レビュアーに条件を書かせることで、G が読む材料は増える
- [G が段 B・段 E で、直すべき指摘を捨てる] → 捨てた指摘は理由つきで PR コメントに残るので、あとから拾える。issue の一覧には出ない
- [受け入れ条件があいまいな外の issue を、G が「全部満たされる」と読み違えてエピックに引き込む] → 主の決定の「受け入れた点」。足した理由を issue にコメントするので、あとから外せる
- [エピックの序盤は、条件についての質問が主に続く] → 主の決定の「受け入れた点」。答えは本文に残り、同じ質問は繰り返されない
- [`triage.md` が長くなり、照合と振り分けの G のコンテキストが増える] → 表 2 つと段ごとの短い節にとどめ、主の決定の経緯は手順書に書かない。行数の上限は置かない

## Migration Plan

手順書と仕様の変更だけで、データの移行は無い。マージ後に起こされた G から新しい手順で動く。戻すときは PR の差分を戻す。既に切られた follow-up issue はそのままにする。
