## Context

`plugins/dev-workflow/scripts/git-destructive-guard.sh` は PreToolUse（Bash）で破壊的 git 操作 9 種を見つけ、主の呼び出しには `ask` / `deny`、子（payload の `agent_id` が空でない文字列）の呼び出しには必ず `deny` を返す（#1108、PR #1118）。子への拒否の回数は `${TMPDIR:-/tmp}/dev-workflow-git-guard/<sha256(session_id + NUL + agent_id)>` に数え、2 回目以降は `continue: false` で子を打ち切る。

#1118 の実機確認で分かっていること（`openspec/changes/archive/2026-10-19-subagent-git-guard-deny/design.md`「実機確認の結果」）:

- 子の payload には `agent_id` が入る。SendMessage で再開された子は同じ `agent_id` を持つ
- 子の `session_id` は親のセッションの ID と同じ（子の scratchpad も親のセッション ID の下にある。例: `/private/tmp/claude-501/<プロジェクトの slug>/<session_id>/scratchpad`）
- 子が `continue: false` で打ち切られると、親が受け取る結果は空になる

いま親が子の代わりに打つと、親は主の呼び出しなので主の確認画面が出る。子が自分の scratchpad に作った検証用 repo を戻すだけの操作でも主が画面を押すまで止まる。現行 spec の要件「子の定義に検証用 repo の戻し方を書く」は「scratchpad 内の repo への破壊的操作を hook が許可する仕組みを足してはならない（コマンドの中で変数を作ってから使う形を hook は展開できず、行き先を判定できないため）」と禁じている。この禁止の理由（hook がコマンドから行き先を判定できない）はこの change でも変わらないので、hook が場所を見て通すのではなく、**親が許可を書く時点で、行き先を判定できる形のコマンドだけを受け付ける**形にする。

前提: hook と許可を書くスクリプトは、payload の `cwd` を、そのコマンドが実行されるディレクトリとして扱う（Claude Code の Bash ツールは呼び出しをまたいで作業ディレクトリを持ち越すことがあるので、子が前の呼び出しで `cd` したあとの `cwd` が何になるかを実装段の実機確認で 1 回見る。食い違っていても、許可が一致しないか一時領域の判定が外れて止める向きに出る組み合わせが多いが、確認の結果は PR 本文に書く）。

守るもの（エピック #1137）: 一時領域の外への破壊的な操作は、親の判断にかかわらず人の許可が要る。守らないもの: 親が判断を誤って一時領域の中の別のファイルを消すこと。

## Goals / Non-Goals

**Goals:**

- 子が拒否されたコマンドを、親がその 1 回だけ通せるようにする（人を通さない）
- 許可を書けるのは、触る repo がすべてそのセッションの scratchpad の中にあると機械的に確かめられたコマンドだけにする
- 許可は session_id・agent_id・cwd・コマンドの全文に結び付け、1 回で消え、期限で切れる
- 許可のあとの別の拒否を 1 回目として数える
- 許可を書いたこと・使ったことを記録に残す

**Non-Goals:**

- Claude Code 本体の rm の確認画面への対応（#1134）
- develop の SKILL.md に、拒否されて返った子を親が許可して再開する手順を書くこと（#1135）。この change は仕組みとスクリプトだけを用意し、親がいつスクリプトを呼ぶかは書かない
- 2 回目の拒否で打ち切られた子の空の return の扱い（#1117）
- 主の呼び出しの振る舞いを変えること（`ask` / `deny` の規則は今までどおり。主の呼び出しは許可を見ない）
- セキュリティ境界にすること（今の hook と同じく、hook に当たらない書き方は通る）

## Decisions

### 1. 許可の単位は「拒否の記録」で、親は記録のパスを渡すだけにする

子に `deny` を返すたびに、hook が拒否の記録を書く。中身は `session_id`・`agent_id`・`cwd`（payload の値）・`command`（`tool_input.command` の全文）・当たった種類・時刻。置き場所は `<base>/denied/<key>.json`、`<base>` は回数のファイルと同じ `${TMPDIR:-/tmp}/dev-workflow-git-guard/`（TMPDIR が空でなければその下、未設定か空なら `/tmp`。`tempfile` の候補探しは使わない）。`<key>` は `session_id`・`agent_id`・`cwd`・`command` を NUL でつないだ文字列の sha256 の 16 進。子への拒否理由に記録のパスを書き、「親に返す報告にこのパスを書く」と案内する。

許可を書くスクリプトは `git-guard-permit.sh <拒否の記録のパス> <理由>` の 2 引数だけを取る。

- 親が agent_id・session_id・コマンドの全文を自分で書き写さなくて済む。親は Bash の環境から `session_id` を取る手段を持たず（環境変数に入っていない）、子の `agent_id` も Agent ツールの結果から読み取って書き写すことになる。コマンドの全文を書き写すと、1 文字の違いで許可が一致しない（または引用符の付け方で別のコマンドになる）
- hook と親の Bash で `TMPDIR` が違いうる（このセッションでも Bash の `TMPDIR` は `/var/folders/...` で、scratchpad は `/private/tmp/claude-501/...` にある。サンドボックスが Bash の環境を変えることがある）。記録のパスを受け取れば、スクリプトは hook が書いた場所 `<base>` を記録のパスから決められる（記録のパスの 2 つ上）。スクリプトは `TMPDIR` を見ない
- スクリプトは記録の中身から `<key>` を計算し直し、ファイル名と一致しなければ許可を書かない（別の場所に置いた・書き換えた記録を拒む）

採らなかった案: `--agent-id` `--session-id` `--command` を引数で渡す形（上の書き写しと TMPDIR の食い違いの問題がある）。親のセッションの transcript から子の最後の拒否を探す形（transcript の形式に依存する）。

子が `continue: false` で打ち切られて報告が空のとき、親は記録のパスを受け取れない。この場合の扱いは #1135 / #1117 で決める（この change ではスクリプトに「agent_id で最新の記録を探す」機能を足さない）。

### 2. 一時領域の判定: コマンドを「cd と git だけ」に限り、repo の置き場所を .git から辿る

一時領域の判定は `session_id`・`cwd`・`command` の 3 つを入力に取る関数で、共通ファイル（決定 7）に置く。許可を書くスクリプトは記録の 3 つの値で、hook は許可を使う時点の payload の 3 つの値で、同じ関数を呼ぶ（決定 3）。スクリプトは満たさなければ理由を stderr に書いて exit 1 で終わり、許可を書かない。判定の中身は次のとおり。

1. **文字の制限**: 英数字・空白・タブ・改行（LF だけ。CR は拒む。bash は CR を語の一部として読むので、見た目と読む単位がずれる）・`/ . _ , : = @ + % -` と、区切りの `;` と `&&` だけでできている。`$`・バッククォート・引用符・`~`・`*`・`?`・`[`・`|`・単独の `&`・`<`・`>`・`(`・`{`・`#`・`\` を 1 つでも含めば拒む。変数・置換・リダイレクト・グロブ・ホームの展開・コメント・行継続を持たないので、シェルが読む単位が空白と区切りだけで決まり、行き先をスクリプトで確定できる（hook の字句読みは使わない。字句読みは「通すかどうか」の判定には足りるが、展開後の行き先を確定することはできない）
2. **単純コマンドの制限**: `&&`・`;`・改行で区切った各単純コマンドの先頭の語が `cd` か `git` である。代入（`GIT_DIR=x git ...`）・`env` などの前置きは先頭の語が `cd` / `git` でなくなるので拒まれる
   - `cd` は引数をちょうど 1 つ取る（`cd` だけは拒む）。引数は `/`・`./`・`../` で始まるか `.`・`..` そのものでなければ拒む。シェルはそれ以外の引数を、オプション（`-P`・`-L`・`--`）・ディレクトリスタックの番号（`+1`・`-1`。`cd -` もここに入る）・zsh の `=` 展開（`=git` がコマンドのパスになる）・`CDPATH` や zsh の `cdpath` の探索として読み、判定と別の場所に移りうる（PR #1140 のレビュー。`cdpath` は export されない配列なので、環境変数の確認では見えない）。先頭の文字で拒む案（`-`・`+`・`=` で始まるものを拒む）より広いのは、パスの形で始まる引数ならこの 4 つのどれも働かないため。引数は今の作業ディレクトリ（最初は記録の `cwd`）からの相対か絶対のパスで、実在するディレクトリでなければ拒む。以降の作業ディレクトリをそこに移す
   - `git` は、サブコマンドの前に `-C <パス>` だけを置ける（`-C` は複数置けて、git と同じく左から順に適用する。ほかの大域オプション `-c`・`--git-dir`・`--work-tree`・`--exec-path` などは拒む）。サブコマンドは `checkout`・`restore`・`reset`・`clean`・`branch`・`switch`・`status`・`add`・`commit`・`rev-parse` のどれかに限る（`push` は行き先が remote で、`diff --output` や `archive -o` などはファイルを一時領域の外に書けるので、後始末に要るものだけを許す。`init` は後始末に要らず、`init <パス>` で外に repo を作れるので許さない）
3. **repo の置き場所**: 各 `git` について、作業ディレクトリに `-C` を順に適用したディレクトリを `realpath` で解決し、そこから親へ `.git` を探す。見つかった `.git` がディレクトリならそれを git ディレクトリとし、ファイルなら `gitdir: <パス>` を読んで（相対ならファイルのあるディレクトリから）解決する。共通の git ディレクトリは git ディレクトリの中の `commondir` ファイル（あれば。相対なら git ディレクトリから）、無ければ git ディレクトリ自身。作業ツリーの最上位（`.git` を持つディレクトリ）・git ディレクトリ・共通の git ディレクトリの `realpath` がすべて同じ scratchpad の中（scratchpad そのものを含む）になければ拒む。scratchpad の直下に `.git` がある場合は scratchpad 全体を作業ツリーとする repo として中に数える（`git clean -fdx` が消すのは scratchpad の中だけで、守らないものの範囲に収まる）。scratchpad の中で `.git` が見つからないまま scratchpad を出たら拒む（git はさらに上の repo を探しに行くので）。共通の git ディレクトリの `config` と git ディレクトリの `config.worktree` に `worktree` のキーか `[include` / `[includeIf` の節があれば拒む（作業ツリーを外に向けられるため）。節名とキーは大文字小文字を区別せずに見る（git は `[Core] WorkTree = ...` も `core.worktree` として読む）。加えて、git が受け入れない `.git` を拒む（git の `is_git_directory` と同じく、git ディレクトリ・共通の git ディレクトリ・その `objects` と `refs` がディレクトリで実行権限があり（git は `objects` と `refs` に `access(X_OK)` を求める）、git ディレクトリの `HEAD` が `ref: refs/` で始まるか 40 桁か 64 桁の 16 進でなければ拒む。`.git` ファイルと `commondir` は git と同じくファイル全体を読んで末尾の CR と LF だけを落とし、そのあとに CR・LF・NUL が残るものは拒む）。git は受け入れない `.git` を飛ばして上の階層の repo を使い、`.git` ファイルの中身は改行を含んだままパスとして使うので、中身の無い `.git`・CR 付きの `commondir`・権限を落とした `objects`・2 行目のある `.git` ファイルだと判定が見た repo と git が使う repo が割れる（PR #1140 のレビューとセキュリティレビュー）。それでもどこかで受け入れ方がずれたときに git が確かめていない repo を使わないよう、作業ツリーの最上位より上のどの階層（scratchpad の外を含め `/` まで）にも `.git` や git ディレクトリの形があれば拒む。scratchpad の親は子が書けるので、そこに外の repo を指す `.git` ファイルを置かれうる。止めすぎる向き（検証用 repo の中に入れ子の repo を作る形は許可できない）は受け入れる。git ディレクトリと共通の git ディレクトリの中に symlink が 1 つでもあるとき、`modules` があるとき、作業ツリーの最上位に `.gitmodules` があるとき、config に `submodule` の文字列があるときも拒む。`refs`・`index`・`objects` などの symlink は判定の時点で既に外を指していて（判定のあとで差し替える短い窓とは別）、サブモジュールへの再帰は `.git/modules/<name>` の先や、サブモジュールの `.git` が指す外の repo を触るため。止めすぎる向き（サブモジュールを持つ検証用 repo は許可できない）は受け入れる
4. **scratchpad の決め方**: ディレクトリ S が「記録の `session_id` のセッションの scratchpad」であるのは、`basename(S) == "scratchpad"`・`basename(dirname(S)) == session_id`・`basename(dirname(dirname(dirname(S)))) == "claude-<uid>"`（uid はスクリプトを動かすユーザーの ID）のとき。Claude Code が scratchpad を `<一時ディレクトリ>/claude-<uid>/<プロジェクトの slug>/<session_id>/scratchpad` に作る形に合わせる。形だけだと作業ツリーの中などに同じ形のフォルダを作れば通るので（実装後の自動セキュリティレビューの指摘）、加えて `claude-<uid>` の親の realpath が一時フォルダの置き場所の候補（`/tmp`・`/private/tmp`・判定する側の `TMPDIR`・`tempfile.gettempdir()` の realpath）のどれかであること、`claude-<uid>` の所有者が今の uid でグループ・他者に書き込み権が無いことを見る。候補を複数持つのは、hook と親の Bash で `TMPDIR` が違いうるため（実際の scratchpad は `/private/tmp/claude-<uid>` の下で、これは `TMPDIR` によらず候補に入る）。ただし許可を書くスクリプトは、自分の `TMPDIR` と `tempfile.gettempdir()` の代わりに `<base>` の親（hook が `<base>` を置いた `TMPDIR`）を候補にする。自分の `TMPDIR` で数えると、親の `TMPDIR` の下にだけある scratchpad に許可を書き、hook（`TMPDIR` が違う）がそれを使う時点の判定で捨てて子が 1 往復拒否される（PR #1140 のレビュー）。記録を任意の `<X>/dev-workflow-git-guard/denied/` に置けば `<X>` が候補に入るが、そこに書いた許可は hook が読まない場所にあるので通らない。`session_id` は英数字と `-` だけの空でない文字列でなければ拒む
5. `git` が 1 つも無ければ拒む

これで、許可が通すのは「その子のセッションの scratchpad の中にある repo への git 操作と、cd」だけになる。親が判断を誤っても、また許可ファイルが親を経ずに直接書かれても、hook が使う時点で同じ判定をかけるので、通るのは scratchpad の中だけに限られる。

git を動かして確かめる案（`git rev-parse --show-toplevel --git-common-dir`）は採らない。子が作った repo の設定（`core.fsmonitor` など）でコマンドが動きうるので、許可を書く前に子の repo の設定を実行しない。

### 3. 許可の中身・期限・1 回限り

許可は `<base>/permits/<key>.json` に、一時ファイルに書いてから `rename` で置く。中身は `session_id`・`agent_id`・`cwd`・`command`・`scratchpad`（S の realpath）・`repos`（確かめた作業ツリーの最上位の一覧）・`reason`・`created_at`・`expires_at`（UNIX 秒）。

- **期限は 15 分**。親が許可を書いてから SendMessage で子を再開し、子が同じコマンドを打ち直すまでの間に収まり、使われずに残った許可が長く効かないようにする長さ。環境変数での上書きは設けない（bats は許可のファイルの `expires_at` を過去に書き換えて期限切れを作る）
- **使う時点でも一時領域の判定をかける**: 許可ファイルは `<base>/permits/` に置いた JSON で、子や他のプロセスも直接書ける。スクリプトの判定だけに安全を預けると、直接書いた許可で作業ツリーへの操作が `allow` になる（仕様レビュー 1 周目の指摘）。そこで許可ファイルは親の同意だけを担い、安全は hook が担う: hook は許可を取って 4 つの値が一致し期限内だと確かめたあと、payload の `session_id`・`cwd`・`command` に一時領域の判定をその時点のファイルシステムでかけ、満たさなければ `deny` にし、理由に「許可はあるが行き先を確かめられない」を書く。許可を書いてから使うまでの間に repo の `.git` が外への symlink に差し替えられた場合もここで止まる。採らなかった案: 直書きの許可は外でも通ると守備範囲に書いて弱まりを受け入れる案（エピック #1137 の「守るもの」を弱めるので採らない）。許可ファイルに署名を付ける案（鍵の置き場所が同じ一時ディレクトリになり、子にも読めるので意味が無い）
- **1 回限り**: hook は、子の呼び出しで破壊的操作を見つけたら、同じ規則で `<key>` を計算し、`permits/<key>.json` を `permits/<key>.json.taken.<pid>` に `rename` してから読む（`rename` に成功した 1 つの呼び出しだけが使える。並列の呼び出しで 2 回使われない）。読んだ中身の 4 つの値が payload と一致し、期限内で、一時領域の判定を満たせば `allow` を返し、取ったファイルを消す。期限切れ・不一致・読めないときは取ったファイルを消して、今までどおり `deny`（回数も数える）。`rename` できない（許可が無い）ときも `deny`
- `allow` のときは拒否の回数を数えない。拒否の記録も書かない
- `allow` の理由文には、親が書いた許可に一致したのでこの 1 回だけ通すことを書く

### 4. 拒否の回数の数え直し

スクリプトは許可を書いたあと、その子の回数のファイル `<base>/<sha256(session_id + NUL + agent_id)>` を消す（無ければ何もしない）。#1118 と同じ名前の決め方なので、hook の側は変えなくてよい。これで「拒否 1 回 → 親が許可 → 許可した操作が allow → 別の操作が拒否」の最後の拒否は 1 回目になり、`continue: false` を含まない。

数え直すのは許可を書いた時点で、許可が使われた時点ではない。許可を書いた親は子を再開するつもりなので、再開後の最初の拒否で子が打ち切られないようにするのが目的。回数のファイルを消せなかったときは許可を書いたまま exit 0 で終わり、stderr に消せなかったことを書く（許可そのものは有効で、打ち切りが早く来るだけなので）。

### 5. 子の自己許可を止める

子が許可を書くスクリプトを自分で呼ぶと、親の判断を経ずに通せてしまう（効くのは scratchpad の中だけだが、親が見るという約束が崩れる）。hook は、子の呼び出しの単純コマンドの先頭の語の basename が `git-guard-permit.sh` であるもの、または先頭の語が `bash` / `sh` / `zsh` / `dash` / `ksh` / `source` / `.` で起動オプション（スクリプトより前にある、`-` か `+` で始まる語。`-o`・`+o`・`-O`・`+O` を含む語と `--rcfile`・`--init-file` は次の語を値として一緒に飛ばし、`-` と `--` でオプションが終わる）のうち、`-c` が無ければ引数のどれか（起動オプションの値を含む）の basename が `git-guard-permit.sh` のもの、`bash` / `sh` / `zsh` の `-c` があればコマンド文字列より前の語（起動オプションとその値）のどれかの basename がそうであるもの、およびどれかの語が `BASH_ENV=` / `ENV=` の代入でその値の basename がそうであるものを、破壊的操作と同じく `deny` にする（当たった種類の表示は「許可を書くスクリプトの子からの呼び出し」）。最初は「起動オプションを飛ばした最初の引数」だけを見ていたが、PR #1140 のレビューで `-o` の値・`+x`・スクリプトより後ろの `-c` の取り違えが、セキュリティレビューで `--rcfile <スクリプト>`・`BASH_ENV=<スクリプト>` の前置き・zsh の値を取らない `-O` と値をつなげた `-o` の取り違えが見つかった。値の取り方はシェルごとに違うので、オプションの読み方に頼らず、迷ったら止める側に倒す形にした（`-c` の無いシェルの引数にスクリプトのパスを書いただけのものも止めるが、子がそれをする用は無い）。`-c` のコマンド文字列はその中身を判定に回すので、文字列の中に名前があるだけのもの（`bash -c "echo …/git-guard-permit.sh"`）は止めない。名前に `git` を含むので、payload の前ふるい（`*git*`）を通って判定に来る。`cat` などでスクリプトを読むだけの呼び出しは止めない。主の呼び出しは止めない。

### 6. 記録を残す

スクリプトは許可を書く前に `<base>/permit-log.jsonl` に 1 行（`event: "permit"`、時刻・session_id・agent_id・cwd・command・scratchpad・repos・reason・expires_at）を追記する。追記できなければ許可を書かずに exit 1（記録の無い許可を作らない）。hook は許可を使ったとき `event: "use"`、期限切れで捨てたとき `event: "expired"`、4 つの値は一致し期限内だが使う時点の一時領域の判定で `deny` にしたとき `event: "rejected"`（満たさなかった理由を含む）を追記する。hook の追記の失敗は判定を変えない（`allow` を `deny` に変えない）。スクリプトは成功時に、許可したコマンド・cwd・scratchpad・確かめた repo・期限を stdout に書く（親が報告に引用できるように）。

一時ディレクトリに置くので、OS が一時ディレクトリを片付ければ記録も消える。記録先（issue / PR）へ親が書き残すかは #1135 で決める。

### 7. スクリプトの置き場所と書き方

`plugins/dev-workflow/scripts/git-guard-permit.sh` に置く。hook の本体と同じ `scripts/` にあり、develop の手順書から `scripts/...` で参照できる。中身は `git-destructive-guard.sh` と同じく、bash から `python3 -I -c` で Python の本体を動かす形（ヒアドキュメントで変数に読む。Python 3.9 で `/dev/fd/3` を使わない理由は #869）。hook の字句読みは使わないので、hook のスクリプトに許可を書くモードを足さない（hook の入口を 1 つに保つ）。

一時領域の判定（決定 2）・`<base>` と `<key>` の求め方・記録の追記は、共通ファイル `plugins/dev-workflow/scripts/git-guard-scratchpad.py` に関数として置き、hook とスクリプトの両方がこのファイルを読んで使う（判定を 1 か所に置く）。どちらも `python3 -I` で動くので、スクリプトのディレクトリは `sys.path` に入らない。bash 側が自分のディレクトリ（`$(dirname "$0")`）からこのファイルのパスを求めて引数で渡し、Python 側はその中身を読んで `exec` で関数を取り込む。hook は子の呼び出しで破壊的操作（決定 5 の自己許可を含む）を見つけたときにこのファイルを読む（`<key>` の計算と拒否の記録の追記もこのファイルにあるため）。主の呼び出しと、破壊的操作の無い呼び出しでは読まない（それらの判定の速さを変えない）。読めない・取り込めないときは `<key>` を出せないので、許可を探さず、拒否の記録も書かず、`deny` だけを返して回数を数える（`allow` の側に倒さない。子への理由文には記録のパスが載らない）

## Risks / Trade-offs

- [子の Bash の環境に `GIT_DIR` / `GIT_WORK_TREE` や `CDPATH` が入っていると、git や cd が scratchpad の外を触る] → 子の Bash は Claude Code の環境を受け継ぐので、判定する側（スクリプト・hook）の環境にこれらの変数（`CDPATH`・`GIT_DIR`・`GIT_WORK_TREE`・`GIT_COMMON_DIR`・`GIT_INDEX_FILE`・`GIT_OBJECT_DIRECTORY`・`GIT_ALTERNATE_OBJECT_DIRECTORIES`・`GIT_NAMESPACE`・`GIT_CEILING_DIRECTORIES`・`GIT_DISCOVERY_ACROSS_FILESYSTEM`・`GIT_CONFIG` で始まるもの）が 1 つでもあれば、スクリプトは許可を書かず hook は許可を使わない（実装後の自動セキュリティレビューの指摘で、受け入れる扱いから変えた）。子が自分の Bash の中だけで設定するものはスクリプトにも hook にも見えないので、hook に当たらない書き方と同じく守備範囲の外とし、spec の守備範囲に書く（同じ呼び出しの中の代入は単純コマンドの制限で拒む）
- [許可を書いてから使うまでの間に、子が scratchpad の中のディレクトリを外への symlink に差し替える] → hook が使う時点で同じ判定をかけ直すので止まる。残るのは hook の判定からコマンドの実行までの短い間の差し替えだけで、守備範囲に書く
- [子や他のプロセスが `permits/` に許可を直接書く] → 親の同意は経ないが、hook の判定で通るのは scratchpad の中だけ。守備範囲に書く
- [hook が子の破壊的操作のたびに共通ファイルを読む] → 読むのは子の呼び出しで破壊的操作を見つけたときだけで、主の呼び出しと破壊的操作の無い呼び出しの速さは変わらない。子の拒否はもともと回数のファイルを読み書きしており、1 ファイルの読み込みが足されるだけ
- [拒否の記録が拒否のたびに増える] → 同じ子・同じ cwd・同じコマンドは同じファイルを上書きする。一時ディレクトリの下なので OS の片付けに任せる
- [scratchpad のパスの形が Claude Code の版で変わる] → 形が変わると許可が書けなくなるだけで、外へ通る向きには壊れない（今の振る舞いに戻る）
- [子が SendMessage で再開されずに新しい子として起こされると agent_id が変わり、許可が一致しない] → 一致しないのは止める向きなので許す

## Migration Plan

hooks.json は変えない。この PR をマージすると、次に起動したセッションから子への拒否理由に記録のパスが載り、親が許可を書ける。戻すときはこの PR の差分を戻す。一時ディレクトリの `denied/`・`permits/`・`permit-log.jsonl` は残っても使われない。

## 実装段で確かめること

- 実機（`claude -p --plugin-dir`）で、子の PreToolUse に hook が `allow` を返したとき、確認画面も拒否も出ずにコマンドが実行されること。子に scratchpad の中に repo を作らせ、`git -C <その repo の絶対パス> checkout -- <ファイル>` を打たせて拒否され、親がスクリプトで許可を書き、子を SendMessage で再開して同じコマンドが通ることを確かめる（`-C` に絶対パスを書く形にするのは、payload の `cwd` の扱いに結果が左右されないようにするため）
- 同じ実機確認の中で、子が前の Bash 呼び出しで `cd` したあとの次の呼び出しの payload の `cwd` が、`cd` 先になるか起動時の作業ディレクトリのままかを 1 回見る（拒否の記録の `cwd` で読める）
- scratchpad の外の repo を対象にした記録には許可が書けないことを確かめる
- 結果を PR 本文に書く

## 実機確認の結果

2026-10-20、Claude Code 2.1.304 で確かめた。親は `claude -p --session-id <uuid> --setting-sources project,local --plugin-dir <worktree>/plugins/dev-workflow --permission-mode bypassPermissions --model sonnet`、子は `general-purpose`（`model: haiku`、`run_in_background: true`、名前付き）。`TMPDIR` は空のディレクトリに向けた。外側の Claude Code セッションから入れ子で起こすと子が外側の scratchpad を使って `session_id` が合わないので、`CLAUDECODE`・`CLAUDE_CODE_SESSION_ID` などの入れ子を示す環境変数を `env -u` で外して起動した。そうすると `claude -p` のシステムプロンプトに Scratchpad directory が出なかったので、`--session-id` で決めた値の scratchpad（`/private/tmp/claude-<uid>/<slug>/<その session_id>/scratchpad`）を先に作り、子にそのパスを渡した。

- **中の repo を戻す操作**: 子の `git -C <scratchpad>/v1 checkout -- a.txt` は確認画面なしで `deny`、拒否理由に記録のパスが載った。親（`claude -p` のメイン）が `git-guard-permit.sh <記録> <理由>` を打つと exit 0 で許可が書かれ、SendMessage で再開した子の同じコマンドは確認画面も拒否も無く実行された（`a.txt` が commit 時の中身に戻った）。`permit-log.jsonl` は `permit` → `use` の順で、`permits/` は空になった
- **外の repo を戻す操作**: 別の子が scratchpad の外の repo に同じ形のコマンドを打って拒否され、その記録で親がスクリプトを打つと exit 1（「git の作業ディレクトリ … がセッション … の scratchpad の中にない」）で許可は書かれなかった
- **cd のあとの payload の cwd**: 子が `cd <scratchpad>/v1` だけを打ったあと、次の Bash の `pwd` は起動ディレクトリのままで、その次の `git -C ...` の拒否の記録の `cwd` も起動ディレクトリだった。子の Bash は呼び出しをまたいで作業ディレクトリを持ち越さず、payload の `cwd` はコマンドが実行されるディレクトリと一致した（前提どおり）
- **再開の指示の書き方**: 再開の指示を「同じコマンドをもう一度 1 回だけ打つ」とだけ書くと、子は拒否理由の「打ち直さず」に従って打たなかった。「親が許可を書いた。『打ち直さない』は親が許可を書いて再実行を指示したこの 1 回には当てはまらない」と添えると打った。親がいつ・どう書いて再開するかは develop の手順書の範囲（#1135）なので、ここでは拒否理由の文面を変えない
