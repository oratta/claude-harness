# Design

## Context

動機は proposal.md の Why。

入力フック（`epic-child-state.sh` の Python 部の `mode == 'input'`）は、予約文を除いたあと、起動形なら `startup`、先頭が `親エピック #` / `主の返事（親エピック #` なら `parent`、残りを `owner` にする。入力フックが受け取るのは UserPromptSubmit の payload の `prompt` で、会話ログの `origin.kind` は見られない。この時点では、その入力より後ろの会話ログの行もまだ無い。

記録の `turn_input.sender` を読む側は次のとおりで、どれも `owner` / `parent` / `startup` の 3 値を前提にしている。

- 入力フック自身の記録の型の検査（`extension`）と、親の見張りの `valid_input`（`WAIT_TURN_DEFS`）: 3 値以外は型の誤り
- 親の止まりの判定 `stop_base`: `sender != "owner"` なら止まりの候補
- `owner_asked` / `owner_away`: `sender == "owner"` の返事待ちを時間で主に知らせる
- 作業待ちの声かけ `bg_turn`: `sender` が `parent` / `startup` のときだけ送る
- 古い受領済み記録の再開判定 `resume_moved`: `sender == "owner"` なら再開
- 子の手順 `child-background-wait.md`: 今の待ちを始めた入力の送り手が `parent` / `startup` のときだけ外部起こしを選ぶ

主の発言から外す接頭辞の一覧は `epic-dispatch.sh` の声かけの判定（`not_input`）にあり、`<task-notification` / `<local-command-` / `<bash-input>` / `<bash-stdout>` / `<bash-stderr>` の 5 つ（先頭の空白を除いて比べる）と、`<command-name>` を含み次の行が Claude Code の処理した出力である行。

## Goals / Non-Goals

**Goals:**

- 非主の接頭辞で始まる入力を `owner` と記録しない
- 親か起動時の指示から始まった作業の通知で起こされたターンの返事待ちを、親の見張りが `stopped` で拾う
- 主が子のタブで打った入力の記録と `owner-away` の扱いを変えない

**Non-Goals:**

- `epic-dispatch.sh`・`child-log-read.py` の見分けの変更や、接頭辞の一覧の共通化（今は 3 か所に同じ一覧があり、1 か所に集めるのは別の変更）
- 未登録の記録に対する移行通知（`scope-input` の `notify`）を通知の入力で出さないようにすること
- 記録済みの古い記録（`owner` と記録された通知のターン）の書き直し。次の入力で世代が進めば自然に新しい決め方になる

## Decisions

### 決定 1: 非主の接頭辞の入力は直前の送り手を引き継ぐ（新しい値を作らない）

通知の入力では、`sender` に同じセッションの直前の `turn_input.sender` をそのまま入れる。入力フックが送り手を決める段まで来た入力は、`target` の条件により、同じ `session_id` の `turn_input` がすでにある（起動形でない入力は登録済みのセッションでしか対象にならない）。だから引き継ぐ値は必ずある。

理由:

- 通知は前のターンで始めた作業の続きで、誰の依頼の作業かは前のターンの送り手が表している。親か起動時の指示から始まった作業なら親が見張るべき止まりで、主が子のタブで頼んだ作業なら主がそのタブにいる前提の `owner-away` が合う。引き継ぎはこの区別をそのまま保つ
- 3 値のまま済むので、記録の型の検査・`valid_input`・`stop_base`・`owner_away`・`bg_turn`・`resume_moved`・`child-background-wait.md` の送り手の条件をどれも変えずに正しく働く。以前の版の親の見張りも新しい記録を型の誤りにせず読める
- 作業待ち（`作業待ち:` の行）で止めた `parent` の作業が通知で起こされても `parent` のままなので、作業待ちの声かけと外部起こしの経路が途切れない

退けた案:

- **新しい値（例: `notification`）を足す**: 型の検査 2 か所と `bg_turn`・`child-background-wait.md` の条件を足し直す必要がある。さらに `stop_base` が `owner` 以外を止まりとみなすので、主が子のタブで頼んだ作業の通知のあとの問いまで親の止まりになり、`--resolve` の判断が主の見ている問いに親として答えてしまう。以前の版の親の見張りは新しい値を型の誤りとして読めなくなる
- **通知の入力を予約文と同じく無視する（記録を変えない）**: 世代が進まないので、前のターンの止まりを親がすでに受け取っていた（`stop_turn` が同じ世代）場合、通知のターンの新しい返事待ちを親が受け取り済みとみなして起こさない。通知のターンのあいだも前のターンの `turn_state`（作業待ちの行など）が有効なまま残り、作業中の子に声かけが送られうる

### 決定 2: 世代を進め、ほかの通常入力と同じく前の状態を無効にする

通知の入力も新しいターンの始まりなので、世代を 1 増やし、受付時刻・`transcript_offset` を更新し、`turn_state` を `null` にする（要件「新しい通常入力は前の終了状態を原子的に無効にする」の通常入力として扱う）。Stop の側の照合（同じ世代・`transcript_offset` より後の発言）はそのまま通知のターンの返事を拾える。

### 決定 3: 接頭辞は `epic-dispatch.sh` の 5 つにそろえ、`<command-name>` は含めない

一覧は `epic-dispatch.sh` の `not_input` と同じ 5 つで、比べ方も同じく先頭の空白を除いてから前方一致にする。`<command-name>` の見分けは「次の行が Claude Code の処理した出力か」で決まり、入力フックの時点ではその行がまだ無いので、判定できない。`<command-name>` を含むプロンプトは今までどおりの決め方（多くは `owner`）にし、モデルに渡るスラッシュコマンドは主の入力として扱う。

payload の `prompt` だけで見分ける（会話ログの `origin` を読まない）。入力フックは会話ログを読まずに速く終わる作りで、通知のプロンプトが `<task-notification>` で始まることは issue の実物で確かめてある。

## Risks / Trade-offs

- [主が子のタブで頼んだ作業の通知のあとの返事待ちは、今までどおり親を起こさない] → 意図した扱い（主がそのタブにいる前提）。`owner-away` で時間がたてば親が主に知らせる。エピック #1826 の `## 条件の答え` で、この止まりはエピックの完了条件の外と決まっている（完了条件の「裏の通知のあとに止まった子」は起動時の指示か親の返事から始まった作業の通知を指す）
- [通知のターンごとに世代が進むので、同じ主の作業で `owner-away` がターンごとに 1 回ずつ出うる] → 通知で起こされたターンはそれぞれ別の止まりなので、知らせ直すのは正しい。1 ターンで 1 回の決まりは変えない
- [主が本当に `<task-notification` などで始まる文を打つと引き継ぎになる] → 実用上起きない入力で、起きても直前の送り手が残るだけ（承認の権限には使われない。送り手は到着経路の分類）
- [3 か所に同じ接頭辞の一覧が並ぶ] → 共通化は Non-Goals。テストで 5 つすべてを確かめ、ずれたら落ちるようにする
