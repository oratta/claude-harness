## Context

仕様化判断は記録先のコメントに `仕様化判断: する` / `仕様化判断: しない` として残り、pr-review-gate の合格処理（`stages/pass.md` の手順 5）が、最新の 1 件を jq の正規表現 `^仕様化判断: (する|しない)$` で 1 行目だけ切り出して照合する。「する」の PR には、記録先の最新の `仕様レビュー:` コメントが `APPROVE` であることを求める。develop の本体は、R1 の APPROVE が記録されるまで W を実装に進めない。

主の決定（issue #973、2026-10-12）は、既存の仕様の文言を実装に合わせて直すだけの変更について、成果物を仕様の差分 1 ファイルだけにし、R1 を省くこと。当てる条件は、記録先の受け入れ条件に「どの仕様のどの文をどう直すか」が書けていること。実装後レビューは変えない。

この change 自体は新しい要件を足すので、文言合わせの通し方の対象ではない。artifact 一式を作り、R1 のレビューを受ける。

## Goals / Non-Goals

**Goals:**

- 文言合わせの変更が、仕様の差分 1 ファイルと実装後レビューだけで通る
- R1 を省いた PR を、ゲートの整合表が「仕様レビューを飛ばした PR」と区別して通す
- 既存の 2 つの 1 行目の契約（`仕様化判断:`・`仕様レビュー:`）と、それを読む既存の jq・bats を変えない

**Non-Goals:**

- 実装後レビューを軽くすること（主が「今のまま」と決めた）
- 受け入れ条件の文と `直す文:` の行の一致を機械で確かめること（W の判断に任せる。主が受け入れたリスクの範囲）
- 1 つの記録先を複数の change が共有するときに、判断の記録を change ごとに分けること（判断の記録は記録先ごとに最新 1 件、という既存の契約のまま）
- `plugins/dev-workflow/scripts/` へのスクリプトの追加（照合は `pass.md` のコマンド数行で足りる。issue #973 の別の change が同じディレクトリを触る）

## Decisions

### D1. R1 を省いた PR は、仕様化判断のコメントの 2 行目以降の行で見分ける

仕様化判断のコメントの 1 行目は `仕様化判断: する` のままにし、2 行目以降に次を書く。

```
仕様化判断: する
理由: 既存 capability の要件の文言を実装に合わせて直すだけ（新しい要件なし・設計の選択なし）
通し方: 文言合わせ
直す文: openspec/specs/<capability>/spec.md「<要件名>」— <どう直すか>
```

`通し方:` の行は正規表現 `^通し方: 文言合わせ$` に完全一致させる。`直す文:` の行は直す要件ごとに 1 行。

本体は W の (1) の return を受けたら、記録先の最新の仕様化判断のコメントにこの行があることを確かめ、あれば R1 を起こさず W を `段: implement` で再開する。ゲートは同じコメントから同じ行を読む。照合のコマンドは既存の「最新 1 件を選ぶ」jq の続きで書ける。

```bash
DEC=$(gh api --paginate --slurp repos/$R/issues/$REC/comments | jq -r 'add | [.[] | select(.body | split("\n")[0] | test("^仕様化判断: (する|しない)$"))] | last | .body')
printf '%s\n' "$DEC" | grep -cx '通し方: 文言合わせ'      # 1 以上なら文言合わせの通し方
printf '%s\n' "$DEC" | grep '^直す文: '                    # 要件名の突き合わせに使う
```

捨てた案:

| 案 | 捨てた理由 |
|---|---|
| 1 行目に 3 つ目の値を足す（`仕様化判断: 文言合わせ`） | 1 行目の正規表現は `spec-reviewer.md`・`worker/spec.md`・`pass.md` の jq・`declarations.md`・Codex の記録・bats 5 本が共有する完全一致の契約。値を増やすと全部を同時に直すことになり、古い版のゲートが「記録なし」と読む |
| `仕様レビュー: 省略` のような 3 つ目のレビュー結果を投稿する | `仕様レビュー:` の正規表現も共有の契約。加えて、投稿者が W になるので「レビュー結果は R1（か本体の代理）が投稿する」という前提が崩れる |
| PR の仕様宣言だけで見分ける | 仕様宣言は (3b) で W が書く。本体が (1) の直後に R1 を起こすかどうかを決める時点では存在しない。記録先に入口の判断が残らない |

### D2. ゲートは通し方の行がある PR に、仕様レビューの代わりに差分の形を求める

`仕様レビュー: APPROVE` を求めない代わりに、対象の定義（新しい要件を足さない・1 つの capability に収まる）のうち機械で見られる部分を実測する。

```bash
ls openspec/changes/archive/*-<change-name>/specs/*/spec.md          # ちょうど 1 行
grep -cE '^## (ADDED|REMOVED|RENAMED) Requirements' <そのファイル>    # 0
grep '^### Requirement: ' <そのファイル>                              # 各要件名が DEC の「直す文:」の行に「<要件名>」で現れる
```

要件名の突き合わせを入れる理由: 主が受け入れたリスクは「直す範囲より広く書き換える」ことで、起きる場面は受け入れ条件の指定があいまいなとき。仕様化判断のコメントに挙げた要件の外まで書き換えた差分は、コマンド 1 行で拾える。挙げた要件の中での書き換えすぎは拾えない（実装後レビューが見る）。

archive 済みであることを求める理由は D4。

不一致のときの直し方は 2 つ。差分か仕様化判断のコメントを直して満たすか、`通し方:` の行の無い仕様化判断を投稿し直して artifact 一式と R1 からやり直す（判断のやり直しは既存の「最新 1 件を正とする」規則で受けられる）。

### D3. 仕様宣言に 3 つ目の形を足す

```
## 仕様宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
仕様: 更新した — change <change-name>（archive 済み）／仕様レビュー: 省いた（文言合わせ。<仕様化判断のコメントの URL>）
```

既存の「更新した」形は `仕様レビュー: APPROVE（<URL>）` を書く。R1 を省いた PR がこの形を書くと、存在しない APPROVE を宣言することになる。レビュアーと主が宣言を読んだときに、省いたことと、その根拠のコメントに辿れる形にする。

### D4. 仕様の差分 1 ファイルだけの change の検証と archive（実測）

openspec CLI 1.2.0 で、捨てる一時の change を作業ツリーの外（セッションの一時ディレクトリに `openspec/schemas` と spec 1 本を写したもの）に作って測った。`openspec new change` が選んだスキーマは `spec-driven`（このリポジトリには `openspec/config.yaml` が無く、既存の archive 済み change の `.openspec.yaml` も `schema: spec-driven`）。一時ファイルは作業ツリーに置いていない。

| 操作 | 結果 |
|---|---|
| `openspec new change <name>` のあと `specs/<capability>/spec.md`（MODIFIED 1 件）だけを書く | `openspec status` は specs だけ完了（1/4）と表示。エラーにはならない |
| `openspec validate <name> --strict` | **終了コード 1**。`Unknown item '<name>'`。proposal.md が無いと名前から change を見つけられない |
| `openspec validate <name> --type change --strict` | 終了コード 0。`Change '<name>' is valid` |
| `openspec validate --changes --strict` | 終了コード 0。`No items found to validate.`（検査されていない） |
| Scenario の無い MODIFIED に `--type change --strict` | 終了コード 1。`must include at least one scenario` |
| 既存に無い要件名の MODIFIED に `--type change --strict` | 終了コード 0（検証は通る） |
| `openspec archive <name> --yes`（正しい差分） | 終了コード 0。`openspec/specs/` の要件が書き換わり、`openspec/changes/archive/<日付>-<name>/specs/<capability>/spec.md` だけが残る |
| `openspec archive <name> --yes`（既存に無い要件名） | **終了コード 0** で `Aborted. No files were changed.`。change は archive されない |

決めたこと:

- 通る最小の形は「`.openspec.yaml`（CLI が作る）＋ `specs/<capability>/spec.md` 1 ファイル」。proposal.md の最小版を足す必要は無い
- 検証コマンドは `openspec validate <change-name> --type change --strict` にする。`--type change` の無い形は使えず、`--changes` は黙って素通りするので使わない
- archive は終了コードで成否が分からないので、W は archive のあと `openspec/changes/archive/` に change のディレクトリがあることを確かめる。ゲートも D2 で archive 済みの差分ファイルを実測するので、archive されていない PR は合格しない

### D5. 当てるかどうかは W が決め、迷ったら当てない

当てる条件（受け入れ条件に「どの仕様のどの文をどう直すか」が書けている）は、W が仕様化判断のときに記録先を読んで判定する。「書けている」は、直す要件ごとに spec のパス（または capability 名）・要件名・直し方の 3 つが受け入れ条件から読み取れること、とする。迷ったら当てず、artifact 一式と R1 に倒す。interactive でも主に聞かない（聞くと、文言合わせの手間を減らすための通し方に質問の往復が入る）。unmanned も同じ条件で当てる。

R1 を一度起こした change は、あとから文言合わせに切り替えない。差し戻しを避ける手段にしないため。これは指示書の規則で、機械では止めない（1 つの記録先を複数の change が共有するので、どの `仕様レビュー:` コメントがどの change のものかをコメントの並びからは決められない）。

### D6. tasks.md が無いので、作業項目は W の return に置く

「仕様化しない」と判定したときの既存の扱い（作業項目ごとの `触る範囲:` を return に書く）と同じにする。(3a) の W は、tasks.md の代わりにこの return の作業項目を TDD で実装する。

## Risks / Trade-offs

- [主が受け入れたリスク] 挙げた要件の中で文を落とす・広く書き換える差分は、実装後レビューでしか見られない。そのレビュアーの指示書はコードと受け入れ条件の照合が中心 → D2 の要件名の突き合わせで、挙げていない要件への書き換えだけは機械で止める。当てる条件で、あいまいな指定の変更を対象から外す
- [W が条件を甘く読む] 受け入れ条件に直す文が書けていないのに `通し方:` の行を書いた PR は、ゲートを通る → `直す文:` の行が記録先に残るので、実装後レビューと主が後から受け入れ条件と見比べられる。機械では突き合わせない
- [記録先の共有] issue #973 のように 1 つの記録先を複数の change が使うと、最新の仕様化判断のコメントが別の change のものになることがある → 既存の契約の性質で、この change では変えない。文言合わせの PR をゲートに掛ける前に、その change の仕様化判断が最新であることを本体が確かめる
- [古い版のゲート] この change より前の版の pr-review-gate は `通し方:` の行を読まず、`仕様レビュー: APPROVE` が無い PR を不合格にする → 安全側に倒れる（通ってはいけない PR が通ることは無い）。プラグインの更新で解消する
- [CLI の版] D4 の結果は openspec 1.2.0 のもの。版が変わると `--type change` の要否が変わりうる → bats で `openspec` があるときだけ実測するテストを置き、変わったら落ちて分かるようにする

## Migration Plan

指示書とゲートの文面の変更だけで、データの移行は無い。この change のマージ前に記録された仕様化判断のコメントには `通し方:` の行が無いので、これまでどおり artifact 一式と R1 の扱いになる。戻すときは PR を revert する。
