## Context

hook（`gate_report.py`）が 1 行積む流れは、対象の確認（`gh api repos/<repo>/issues/<番号>`、1 回）→ 既存コメントの取得（1 回）→ `cost_ledger.py timeline`（`gh` を呼ばない）→ 書き込み（1 回）で、`gh` は 3 回。`issue クローズ` を含むときだけ、閉じた PR の問い合わせ（GraphQL、1 回）が加わり 4 回（#689）。

`timeline` は「hook は集計を持たず、`timeline` は `gh` を呼ばない」という決まりで、PR か issue か・閉じた PR は hook が調べて引数で渡す。#690 で `/cost <エピック>` は子孫を辿って合計を出すようになったが、`gh` を呼ぶ `fetch_epic_tree()` は `cost_ledger.py cost` の側にあり、`timeline` からは使えない。

### 実測（2026-10-09、`gh` を stub で包んで回数と時間を記録。書き込みは stub が握りつぶして GitHub には書いていない。ネットワーク往復を含み、1 回ごとにばらつく）

| 条件 | `gh` の回数 | 内訳（読み取り 1 回の時間） | hook 全体（裏のプロセス） |
|---|---|---|---|
| 子なしの issue にコメント（#745） | 3 | 対象の確認 0.5〜0.6 秒、コメント取得 0.4〜0.5 秒、書き込み 0.03 秒 | 2.7〜3.8 秒（3 回） |
| 子なしの issue を閉じる（#690） | 4 | 上に、閉じた PR の問い合わせ（GraphQL）0.65〜0.7 秒 | 3.6〜4.1 秒（3 回） |
| 子 1 件の issue を閉じる（#851） | 4 | 同上 | 4.0 秒（1 回） |
| 子 48 件・孫なしのエピック（#272）の子の問い合わせ（GraphQL、子と子ごとの閉じた PR を 1 回で取る） | 1 | 0.73 秒、応答 16.8 KB | （対象の issue が開いていて閉じる操作は流せないので、問い合わせだけ測った） |
| hook の同期の部分（セッションを止める分。裏の処理を切り離して返るまで） | 0 | — | 0.11 秒 |

hook 全体の差（2.7〜4.1 秒）の大部分は `gh` の往復（合計で約 1.5 秒）と、`timeline`（台帳の読み取り）。`gh` は 1 回あたり約 0.5〜0.7 秒。セッションを止めるのは同期の部分の 0.11 秒だけで、`gh` の分は切り離した裏のプロセスで走るので、`gh` が 1 回増えても止まる時間は変わらない。

## Goals / Non-Goals

**Goals:**
- 子を持つ issue に積む行（節目の行・合計の行）の額を、`/cost <番号>` の 1 行目と一致させる
- 子を持たない issue と PR は、積む行も `gh` の回数も変えない
- `timeline` は `gh` を呼ばないまま。LLM のトークンを使わない。積む行の長さを子の数に比例させない

**Non-Goals:**
- 別のリポジトリの子 issue を数える（`/cost` も数えていない）
- `/cost` の出力や `fetch_epic_tree()` の変更。`ISSUE_RE` と `attribution.bats` には触らない（別の子 #698 の持ち分）
- 既にコメントに積まれた行の書き換え

## Decisions

### 1. 子の分を入れるのは「毎回の行」か「閉じたときの合計の行だけ」か → 毎回の行（案 A）

| | 案 A: 毎回（節目の行も合計の行も子込み） | 案 B: 閉じたときの合計の行だけ |
|---|---|---|
| エピックを開いている間のコメント | 毎回、全体の額が見える | 区間だけ（ほぼ 0）のまま。#745 が直したい食い違いが、閉じるまで残る |
| `gh` の回数（子が全部葉のエピック） | コメント・再オープン等 4 回（+1）、閉じる 4 回（+0） | コメント等 3 回（+0）、閉じる 4 回（+0） |
| `gh` の回数（子なし・PR） | 変わらない | 変わらない |
| 増える時間 | 裏のプロセスで +0.7 秒前後（子の問い合わせ 1 回） | 閉じるとき 0 |
| セッションを止める時間 | 変わらない（0.11 秒） | 変わらない |
| 節目の行の意味 | 子ありだけ「子 issue 込み」に変わる | 変わらない |

選ぶのは案 A。理由: (1) 目的は「エピックの履歴だけで全体の額が分かる」ことで、案 B は閉じるまで履歴が 0 に見え続ける。(2) 増える `gh` は、子を持つ issue に積むときの 1 回（約 0.7 秒、裏のプロセス）だけで、子を持たない issue と PR では 0 回。エピックは数が少なく、コメントや状態変更の頻度も低い。(3) 閉じるときは、子の問い合わせの応答にエピック自身を閉じた PR も入っているので、`closing_prs()` の問い合わせを置き換えるだけで、回数は 4 回のまま増えない。

**これを選ぶと受け入れること**: 子を持つエピックでは、閉じる以外のきっかけでも `gh` が 3 回から 4 回になる。待ち時間は裏のプロセスで +0.7 秒前後で、セッションは止まらない。子を持つ issue の既存のコメントは、次に積む行の増分が一度だけ大きく出る（前の行が区間だけの累計だったため）。

### 2. 子の有無は、対象の確認の応答から取る（追加の `gh` 無し）

`resolve()` が呼ぶ `repos/<repo>/issues/<番号>` の応答に `sub_issues_summary.total` が入っている（`cost_ledger.py` の `resolve_number()` が既に使っている）。これが 1 以上のときだけ子孫を調べる。0・無い・整数でないときは今までの経路で、`gh` は 1 回も増えない（受け入れ条件の「子 issue を持たない issue では回数が同じ」）。

### 3. 子孫を辿るのは hook（`gate_report.py`）に新しい関数を足す

`timeline` に `gh` を持たせない決まりを守るため、`closing_prs()` と並べて `epic_tree(repo, number)` を足し、GraphQL を子を持つ issue 1 件につき 1 回呼ぶ（`SUB_ISSUES_QUERY` と同じ形で、子と子ごとの閉じた PR を 1 回で取る）。`cost_ledger.py` の `fetch_epic_tree()` は `gh` を `_gh()` 経由で呼ぶので共有しない（hook は `GH_HOST` を外した `gh_api()` で github.com に固定する別経路を持つ）。応答の読み方（ベースが同じリポジトリで fork でない PR だけを数える、別のリポジトリの子は数えず辿らない、100 件超・形の崩れは失敗）は `fetch_epic_tree()` と `closing_prs()` に揃え、同じデータで同じ集合が出ることを bats で突き合わせる。

呼び出し回数の上限: 子を持つ issue が多い木で hook の裏のプロセスが長引かないよう、GraphQL は 1 回の行につき 5 回までにする（6 回目が必要になったら失敗として扱う）。5 は、子を持つ子（孫の親）が 4 件までのエピックを 1 回で足りる範囲に収める値で、この repo のエピック（#272 は子 48 件・孫なし）は 1 回で足りる。回数は、子の数でも PR の数でもなく、子を持つ issue の数に比例する（#690 の `/cost` と同じ数え方）。

### 4. `timeline` への渡し方

- `--child-issue <番号>`（複数）: 子孫の issue の番号。`--issue` と一緒にだけ渡せる。1 つ以上あるとき、区間はエピック自身と子孫のすべての issue の分を 1 度にまとめて読む（`epic_rows()` と同じ。台帳の差分の追記は 1 回のまま）
- `--child-pr <PR番号>:<ヘッドブランチ>`（複数）: エピックと子孫を閉じた PR。`--closing-pr` と同じ書式・検査・同じヘッドブランチの重複除去
- 額は `issue_combined_total()` を、区間の行を「エピック自身と子孫の区間」に広げて呼ぶ。PR のブランチ上の行は PR 側へ、それ以外の区間の行は PR 外へ入り、1 つの行は 1 回しか数えない。結果は `assign_epic_rows()` の合計と同じ（どの issue に割り当てるかは合計に効かない）
- 節目の行は、`--child-issue` があれば `issue_combined_total()` の累計を使い、1 行目の帰属の種別を `子 issue 込み` にする（`/cost` のエピックの 1 行目と同じ）。無ければ今までどおり区間だけ
- 合計の行（`--closing-pr` があるとき）: 子込みの場合、きっかけの欄を `合計（子 issue <n> 件込み: PR <m> 件 $<額> + PR 外 $<額>）` にする。PR ごとの額を並べると子の数に比例して長くなる（コメントを読む側のトークンを増やしすぎない）。内訳は `/cost <番号>` で見る。この形は子込みのときだけで、子を持たない issue の合計の行の書式（PR ごとの額を並べる）は変えない

hook が `--closing-pr` を渡すのは `issue クローズ` を含む行だけ（今までどおり）。`--child-issue` と `--child-pr` は、子を持つ issue に積むすべての行に渡す。

### 5. 子の問い合わせが失敗したとき

従来どおりの引数（子なし）で積む。節目の行のきっかけの欄の最後に `子 issue 照会失敗` を足す（`PR 照会失敗` と同じ扱い。足すのは失敗したときだけ）。`issue クローズ` のときは、子込みの合計を作れないので合計の行も積まない。失敗の範囲は、`gh` の失敗・JSON でない・形の崩れ・100 件超（子の数でも閉じた PR の数でも）・深さ 8 段超・GraphQL の 6 回目が必要になった場合。一部しか読めていない結果を合計にしない。

### 6. 後追い（`--backfill`）

`backfill.py` は同じ `stack()` を通るので、子を持つ issue は同じ経路で子込みの行を積む（auto-merge や自動クローズで閉じた子を持つ issue も含む）。`stack()` の外に子の処理を足すので、`backfill.py` 側の変更は無い。

## Risks / Trade-offs

- [子を持つ issue に積むときだけ `gh` が 1 回増える] → 約 0.7 秒、裏のプロセス。同期の部分は 0.11 秒のまま。子を持たない issue と PR は変わらない（回数を bats で変更の前後で突き合わせる）
- [子を持つ issue が多い木で GraphQL が増える] → 1 行につき 5 回まで。超えたら失敗の印を付けて従来の行を積む
- [子込みの額は、子の issue 番号が 1 つ増えるたびに台帳の読み取りが重くなる] → 区間は番号の集合で 1 度に、PR の分はヘッドブランチすべてを 1 度に読む（`epic_rows()` と同じ。台帳を読み通す回数は子の数に比例しない）
- [既存のエピックのコメントは、次に積む行の増分が一度だけ大きく出る] → 増分は前の行の累計との差なので、過去の区間だけの行と子込みの行の差が出る。書き換えはしない
- [`fetch_epic_tree()` と hook の `epic_tree()` の二重管理] → 同じ形のデータで同じ集合になることを bats で固定する
- [積む行が長くなる] → 子込みの合計の行は PR ごとの額を並べず件数だけにする。節目の行は金額・トークンの 3 項目で、子の数に依らない

## Migration Plan

反映に `/reload-plugins` は要らない（`hooks.json` を変えない。スクリプトは実行のたびに読まれる）。戻すときは `gate_report.py` の子の分岐を外せば、従来の行に戻る（`timeline` の新しい引数は、渡さなければ従来と同じ）。
