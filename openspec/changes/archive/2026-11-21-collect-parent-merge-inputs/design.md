## Context

マージ待ちの子の手順は、前提 4 つの確認（`gh` 4 本前後）と、決める役への入力 12 項目前後の収集（`gh pr view`・`gh pr diff`・`gh pr checks`・`gh api` など）を、親が手順書の文章を読んで毎回手で行っている。同じ列挙が `parent-merge-criteria.md` の「守備範囲」にもある。`stop-judge.sh` は停止の入力を集める同じ形のスクリプトで、入力の信頼できる投稿者の確認（`read_trusted_body`）を持つ。

## Decisions

1. **スクリプトの名前は `parent-merge-inputs.sh`**。`stop-judge.sh` と同じ `scripts/` 直下に置く。issue の候補名 `collect-parent-merge-inputs` は change 名にだけ使う。
2. **モデルは呼ばない**。`stop-judge.sh` と違い、判断（決める役の起動）は親が `subagent_type: dev-workflow:decider` で行う（Bash を持たない決める役に入力文を貼る契約を保つため）。スクリプトは前提の確認と入力文の組み立てだけを行う。
3. **終了コードを 3 つに分ける**。0 = 入力文あり、3 = 前提を満たさず主に上げる（stdout に理由 1 行）、1 = 読めない・信頼できない。親は 3 と 1 の両方で決める役を起こさず主に上げるが、3 は理由を主への報告にそのまま使え、1 は調べ直しが要る点が違う。
4. **子の最後の発言と委任の確認の場所は引数で受ける**。前者は会話ログ（`child-log`）と停止の JSON から親が得るもので、`gh` だけでは集まらない。後者は主の発言の位置を親が確かめた結果で、機械的に決まらない。
5. **委任の有効性は判定しない**。`epic-delegation.md` の ①〜⑥（編集の有無の GraphQL 確認を含む）を移すと、委任の要件も動かすことになる。候補の本文と URL を出し、判定は親に残す。
6. **PR のコメントは信頼できる投稿者のものだけ**。今の手順書は「リスク宣言・動作確認・ゲートのコメント」と書くだけで投稿者を限っていない。ゲートは主の `gh` アカウントで投稿するので、3 種の投稿者に限っても漏れは出ない。`human-merge` の投稿は自動マージの処理が書くので、`🔒` の先頭の行で選ぶ。
7. **配役表は作業ツリーのもの**。別 repo の子（エピックと別のリポジトリ）では PR のリポジトリの配役表を読むべきかもしれないが、今の手順書は「あれば配役表」としか書かず場所を決めていない。今回は作業ツリーのものだけにし、挙動を増やさない。

## Risks / Trade-offs

- 手順書の文章が減る代わりに、入力の列挙の正本がスクリプトになる。列挙が漏れないことはテスト（節の見出しの突き合わせ）で守る。
- 差分が大きい PR では入力文が大きくなる。今も親が貼っているものと同じ量で、増えない。
