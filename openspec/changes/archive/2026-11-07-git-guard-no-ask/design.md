# Design

## Context

動機と影響範囲は proposal.md を参照。現在のガードは子（`agent_id` が空でない文字列）の許可確認・拒否回数・拒否記録を先に扱い、主は UNATTENDED → FORCE → permission mode の順に決める。理由文も子・UNATTENDED・通常の deny・ask に分かれている（スクリプト 879–965 行）。

別セッションで動くエピックの「子」は、そのセッション内では payload に `agent_id` の無い主でもある。サブエージェントの既存の規則と区別する必要がある。OWNER の指示により flatmate PR #2022・#2007 が子の環境に印を設定する。

## Goals / Non-Goals

**Goals:**

- 既存の破壊的操作の検出後に NO_ASK を読むことで、検出範囲・fail-open・処理コストを維持する。
- 既存の子の許可と繰り返し拒否を維持しつつ、主の拒否理由を画面やチャンネルのない経路に適合させる。

**Non-Goals:**

- harness の起動経路への印の自動設定・伝播、develop のモード判定の変更、親の停止判定ロジックの変更。
- NO_ASK の主への拒否回数の計測・`continue: false` による強制終了。ターンを終えることは理由文で案内する。
- 検出器・親の許可スクリプト・バージョン・常時注入予算の変更、実機の Claude セッションの起動。

## Decisions

### 起動する側がガード専用の印を設定する

`DEV_WORKFLOW_GIT_GUARD_NO_ASK` を hook のプロセスの環境から読む。値は UNATTENDED と同様に `.strip()` 後の空と `0` だけを印なしにする。実行するコマンドの前置きからは設定を変更しない。

UNATTENDED の流用は develop を channel に変えるため採らない。FORCE の恒久設定は検証用という契約に反し、理由文も今回の経路に合わないため採らない。harness の launch に既定で付ける案も採らない。flatmate 側が必要なセッションに設定でき、主が画面を見ている通常のエピックの子まで一律 deny にする必要がないためである。

### 判定と理由文の順は子 → NO_ASK → UNATTENDED → 既存の分岐

子の処理は先に決める。有効な許可は一度だけ allow、許可の無い拒否は数えて 2 回目に打ち切る既存の処理を維持する。主は NO_ASK があれば deny とし、UNATTENDED と両方付いても NO_ASK の理由を優先する。画面もチャンネルもないという新しい印の要求に反する案内を避けるため。NO_ASK の無い UNATTENDED の経路は既存のチャンネル案内のままとする。

`DEV_WORKFLOW_GIT_GUARD=off` の早期終了・入力を読めないときの fail-open・無害なコマンドの無出力は既存のまま維持する。NO_ASK を全 Bash 呼び出しの拒否に使わない。

### 理由は承認依頼の内容とターンの終了を案内する

既存の検出結果の head と再実行禁止の tail を使い、主の NO_ASK 用 body を追加する。全文・対象・なぜ要るか・止まった理由を報告して承認を求めること、ターンを終えること、承認後はオーナーが自分で実行することを記す。理由からは確認画面・`!`・チャンネル／Discord の案内を除く。子への理由・拒否記録・許可の案内はそのままとする。

### 常時注入の規範は変更しない

`rules/destructive-git-guard.md` の無人の印の案内は既存の UNATTENDED の経路を説明している。新しい環境変数の名前は起動側の設定であり、承認必須・拒否後は主が実行するという既存の規範は変わらない。この変更では rules とその README を編集せず、具体的な契約は spec と hook、親向けの注意は epic.md 手順 5 に置く。常時注入の増加と変更範囲の拡大を避ける。

## Risks / Trade-offs

- [印が起動側から届かなければ ask に戻る] → flatmate 側の設定を前提とし、harness の全起動経路への伝播は扱わない。手順 5 では印のない確認画面の限界も維持する。
- [拒否だけでは子のターン終了・親の検知を保証しない] → 理由文でターン終了を案内する。手順 5 は承認依頼でターンを終え、会話ログが読める場合の検知として書く。deny 自体が stopped を直接生成するとは書かない。
- [NO_ASK を誤って設定した対話セッションも deny になる] → 起動側の明示設定とし、未設定・空・`0` は従来どおりにする。
- [実行環境の NO_ASK がテストへ混入すると旧経路が壊れて見える] → bats の setup で既存の印と一緒に unset する。必要なテストだけ明示設定する。

## Migration Plan

実装段で bats の新しい入力行列と既存の全スイートを確認し、epic.md と changes/1582.md を更新する。版は上げず、マージは主の承認とする。起動側が新しい印を古いガードへ渡しても無視され従来の ask に戻るため、展開の前後に印だけを安全機能の保証と扱わない。
