# Design

## Context

動機は proposal.md「Why」を参照。#1775 の本文と #1744 の裁定コメント（https://github.com/oratta/claude-harness/issues/1744#issuecomment-7089341978）が生成側と消費側の境界を定めている。

`epic-child-state.sh` は shell の共通 Stop 入口と Python の検査・保存計画を持つ。`extension()` がターン拡張を検査し、現在のセッション・指定ログ・入力以後の最終発言と payload の対応を確かめてから状態を生成する。既存 Stop の拒否結果を受け、入力スナップショットを `es_modify` のロック内で再照合して状態を保存または `null` にする。通常入力も同じロックで世代を増やし `turn_state: null` を保存する。

`--dependency-wait` は既存の親が使う末尾述語で、正しい状態行を除いた最終非空行の依存待ち印を調べる。親の従来動作とこの CLI の互換を保ったまま、子の保存計画からも同じ末尾形式を利用する。

導入先は既存の別セッション方式の子（Orca / tmux）。既存環境の bash・jq・python3、schema=1 のローカル記録と hook payload の指定ログを使用し、依存パッケージや hook 登録は追加しない。

## Goals / Non-Goals

**Goals:**

- 検査済みの同一ターンの作業報告にだけ、依存待ちの任意 boolean を保存する。
- 子側の型検査・通常入力・Stop 差し戻し・世代競合を既存の更新経路に統合する。
- 旧記録と変更前の親を維持し、#1744 が後から読み取れる契約を作る。

**Non-Goals:**

- 親の検知・受領・依存照合・送信・再起動、および親向けの一般手順の変更。
- boolean による依存登録成功や依存解消の保証。登録・確認・停止コメントは既存手順の責務。
- 状態値の追加、`作業報告` の `主の返事待ち` への変更、ログやコメントからの旧記録の補完。

## Decisions

### 裁定済みの「作業報告＋任意 boolean」を生成側に実現する

`turn_state.dependency_wait` は省略可能な JSON boolean とする。存在するときに文字列・数・null・配列・オブジェクトを真偽値に変換しない。boolean の `false` は型としては正しいが依存待ちの証拠ではない。フック自身は条件を満たすときだけ `true` を書き、それ以外では項目を省く。`extension()` に検査を足し、型不正は既存の拡張不正の処理に従って有効状態として採用しない。既存の親用の読めない記録の検査は変えない。

この配置と状態値の維持は issue と裁定からの要件である。`summary` の自由文を読み直す案や `主の返事待ち` に変える案は、構造化した受け渡しと依存待ちの終了契約を崩すため採らない。

### 今回の検査済み全文で末尾形式を判定する

現在の発言であることと状態行を確認した保存計画で、`value == 作業報告` の場合だけ依存待ち述語を適用する。末尾の空白行と正しい最終状態行を除いた最終非空行が `止まった理由: 依存待ち: <依存先 URL>` の形式であり、引用・フェンス内の例でない場合に `true` を同じ state オブジェクトへ足す。印の行の既存の行頭契約（空白なし、または半角空白1個）を維持する。フェンス文脈は切り詰め前の全文から調べる。

共有できる末尾処理を関数化しても、親が使う `--dependency-wait` の旧形式（状態行なし）や終了コードは変えない。子の保存では状態行が必須で、古い印だけの発言から状態を捏造しない。既存 Stop が拒否した計画は保存せず、通常の差し戻しと同じ経路へ進む。boolean のための GitHub 呼び出しや送り手の追加分類はしない。

### 独立した印を残さず、終了状態の寿命に従わせる

新しい項目だけを別の更新で足したり消したりしない。入力で `turn_state: null` にする既存処理と、Stop 拒否時に同世代の state を `null` にする既存処理に含める。同じ世代で依存待ちから通常の作業報告へ書き直したときも、新しい state に項目を持ち越さない。

保存・無効化の直前の入力スナップショット照合と `.lock`、一時ファイルからの置き換えを維持する。入力が先行した古い Stop は新世代を保存も無効化もしない。予約文の往復は既存どおり無視する。保存失敗の初回拒否・再停止時の診断と停止許可を変更せず、置き換え失敗で古い JSON が残ることを新項目の保存・無効化成功と報告しない。

## Risks / Trade-offs

- boolean だけでは依存先や解消を証明できない → 依存先 URL と停止コメントは既存手順で残し、受領・照合・再起動は #1744 で実装する。
- 旧記録には印がない → 欠落を依存待ちと見なさず、更新済み子フックで終了状態を保存して初めて新契約に載せる。ログ補完や移行のための owner の子への自動入力を行わない。
- 述語の変更が旧親に波及しうる → 既存 CLI の互換テストと `epic-dispatch.bats` を保ち、新項目のある記録を旧親に渡す互換ケースを子側テストに追加する。
- ロックや保存の失敗では古い state が残りうる → 既存の処理失敗契約を優先し、診断と exit を検証する。停止許可を有効状態の保存成功と混同しない。

## Migration Plan

1. この新規 change の R1 APPROVE 後に子フック・回帰テスト・子向け手順を変更する。archive 済み change を書き換えない。
2. 変更前の親との互換を確認し、生成側を先行して導入する。この段階で親の依存待ち再開が復旧したとは扱わない。
3. #1744 がこの契約を取り込み、別の承認済み change で消費側を接続する。項目欠落の旧記録に遡及して `true` を補わない。
4. 生成側のロールバックはフックと手順を戻す。既存の親は任意拡張を無視するため、schema 更新や保存済み記録の一括変換・削除は不要。
