# Design: pr-review-gate-review-weight-triage

## 判定を「機械的な材料」に縛る理由

レビューの重さを LLM の印象（「軽そう」「大きく見える」）で決めると、
**急いでいるときほど light に倒れる**。判定材料を `gh pr diff --name-only` と行数に固定し、
条件表に当てはめる形にすることで、判定の再現性を確保する。
これは github-issue スキルの Step B（仕様化要否）と同じ型で、
判断者が変わっても同じ答えになることを狙っている。

## 既定を full にする（fail-closed）

pr-review-gate は「通過 = 主の承認なしに auto-merge されてよい」という意味を持つゲートなので、
判定の誤りは**片側だけ危険**である:

| 誤り | 帰結 |
|---|---|
| 本当は full なのに light にした | 独立性の低いレビューで重い変更が auto-merge に乗る（**危険**） |
| 本当は light なのに full にした | 10〜14 分余計に待つ（**コストのみ**） |

したがって既定は full とし、条件を**すべて**満たしたときだけ light に落とす。
「判断がつかない」は light の理由にならないことを明文化する
（手順3 のリスク宣言が「判断がつかないことは『リスクなし』の理由にならない」としているのと同じ構え）。

## md でも full になるファイル群を条件に埋め込む

「ドキュメントのみなら軽い」は素朴には正しいが、この開発ハーネスでは
`CLAUDE.md` / `.claude/` 配下 / `.github/workflows/` / スキル・コマンド・エージェント定義 /
憲法 doc は**読み物ではなく実行される規約**であり、md でありながら挙動を変える。
実際 auto-merge workflow はこれらを SACRED として扱い、passed でも自動マージしない。
そこで light の条件 (a) は「拡張子が md」ではなく
「md であり、かつ**エージェントの行動を定義するファイルを1つも含まない**」とする。

## light で省くのは Codex だけ（工程は省かない）

light は「レビューを軽くする」ではなく「**レビュー実行者を Codex から Task サブエージェントに替える**」。
省略されるのは Codex の呼び出しだけで、次はすべて残る:

- 実装と別コンテキストであること（自己レビュー禁止）
- 手順3 のリスク宣言（positive affirmation）
- 手順4 の動作確認証拠
- 手順5 の HEAD SHA 照合と合格前の API 実測
- 収束ルール（2周キャップ・差分限定再レビュー・blocking 定義の限定）

これにより「light にしたら通過基準まで緩んだ」という滑りを構造的に防ぐ。

## 事前判定と障害時フォールバックを混ぜない

既存のスキルには「Codex CLI が使えないとき（未導入・サブスク切れ・タイムアウト）は
Task サブエージェントに落とす」というフォールバック記述がある。今回追加する 2-0 は
これとは役割が違う:

| | いつ決まるか | 何を根拠に決めるか |
|---|---|---|
| 事前判定（2-0） | レビュー開始前 | **変更内容**（ファイル種別・行数） |
| 障害時フォールバック | full と判定した後、Codex 実行に失敗したとき | **Codex の可用性** |

同じ「Task サブエージェントで読んだ」でも意味が違う（前者は意図した設計、後者は迂回）ため、
PR コメントの1行にどちらの経路かを書き分けさせる。フォールバック記述自体は削らない。

## 判定結果を PR コメントに残す

判定は LLM が行うため、**後から誤判定を検出できる形**にしておく必要がある。
判定結果と根拠（ファイル種別・行数）を PR コメントに1行残せば、
「light 判定のサンプリング再判定」で形骸化を監査できる
（リスクなし宣言のサンプリング監査と同じ考え方）。

## 30 行という閾値について

(b) の 30 行は「diff 全体を読み切って挙動不変を確信できる上限」の目安として置いた保守的な値。
行数だけでは light にならない（挙動不変の読み取り判断が AND 条件）ため、
閾値が多少ずれても危険側には倒れない。実運用で light の取りこぼしが多ければ後から調整する。
