# Design

## Context

動機は proposal.md の Why を参照。共通入口は既存の主向け発言ガードを1回呼んだあと、対象の子のログと入力情報から `save` / `block` / `ignore` / 処理失敗を得る。現在は `fail()` が Stop で無条件に block し、Python 側の処理失敗も `ACTION=block` に合流する。

保存と拒否時の無効化は同じ `es_modify` を使う。ロック取得・原子的置き換えの失敗は処理失敗であり、世代の照合が外れた戻り値4は古い Stop を無視する正常経路である。

## Goals / Non-Goals

**Goals:**
- 子自身の出力で修正できる状態行の不備と、入力・記録・ログ・保存の処理失敗を Stop の出力で区別する。
- 後者は初回の診断を block として返し、再停止では stderr の診断を残して停止できるようにする。
- 成功した保存、成功した無効化、保存できなかった停止を混同しない。

**Non-Goals:**
- リトライ回数の永続化、ロックの強制解除、入力情報の推測作成、親側の見張りの変更。
- 状態行の意味検査や Claude Code 自体の差し戻し上限の実機検証。
- capability・schema・プラグイン版の追加や変更。

## Decisions

### 失敗の種類を保ち、処理失敗だけ再停止で通す

issue #1754 の案を採用する。`stop_hook_active` が JSON の真偽値 `true` の場合だけを再停止として扱う。欠落・false・文字列の `"true"` は停止許可の根拠にしない。状態行の不備による `block()` と、処理失敗による `fail()` を分け、Python の処理失敗を通常の形式不備に潰さず扱う。記録の複数一致・設定検査・予約文の読み取りなど、対象候補を発見した後に既存の `fail()` に入る経路にも同じ分岐を適用する。

全 block を再停止で免除すると状態行の修正を強制できなくなるため採用しない。全処理失敗を初回から通す案も、初回に問題を子へ知らせる既存契約を失うため採用しない。独自の再試行カウンタは不要で、同フラグが既に true の呼び出しは前回の失敗種別によらず再停止として扱う。

### 保存経路と既存ガードの合成を維持する

再停止フラグで入口全体を早期終了させない。処理失敗から復旧し、ログと状態行を確認できた再停止は同世代へ通常どおり保存する。不正な状態行の検査と、拒否時の同世代の無効化も継続する。保存・無効化に失敗した場合は処理失敗を優先し、再停止なら理由を stderr に出して停止を通す。

処理失敗時は新しい有効な `turn_state` を生成しない。既存の無効化を試みる経路は維持し、失敗しても元の JSON や親の項目、別世代を壊さない。書けないときに古い状態が残る可能性は従来どおりで、停止許可を保存成功や完了状態の根拠にしない。

既存 `owner-message-number-check.sh` の1回限定・解除・fail-soft と、対象外への出力・終了コード転送を保つ。処理失敗の再停止ではこのガードも既存契約により通るため、stdout は空で exit 0、失敗理由・記録パスは stderr とする。複数一致で1件の記録を確定できないときは、従来の状態保存ルートのパスを診断に使う。入力フックの処理失敗は exit 2 のままとする。

## Risks / Trade-offs

- 処理失敗の再停止では状態未公開のまま止まることがある → stderr に失敗理由とパスを残し、有効な終了状態を捏造しない。親側の復旧設計は本 change の範囲に含めない。
- 形式不備とロック失敗が同時に起きると無効化できない → 保存・無効化の失敗を処理失敗として扱い、無限の差し戻しを防ぐ。形式不備だけなら再停止でも block することを別に試験する。
- stdout と stderr の混合確認では契約の誤りを見逃す → Bats の分離取得で stdout 空・stderr の理由とパス・exit 0 を同時に検証する。

## Migration Plan

schema と既存記録の移行は不要。実装と回帰テスト、`plugins/dev-workflow/changes/1754.md` を同じ変更に含め、版は上げない。問題があればこの変更を revert する。OpenSpec の main spec への同期・archive は実装後の工程で行う。
