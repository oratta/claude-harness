## Why

2026-10-23、主はエピック #1038 の親のタブで「このエピックの子が求めるリスク許容は、親が全部答えて」と任せた（発言 11:02。親がそれを書いた記録は 11:03、コメントの作成 2026-10-23T11:03:32Z https://github.com/oratta/claude-harness/issues/1038#issuecomment-6363422938 ）。記録の 2 分後に子 #1245 が PR #1265 のリスク許容を求めて止まり（停止の記録 https://github.com/oratta/claude-harness/issues/1245#issuecomment-6363448774 、11:05:03）、親は委任の発言の場所を添えて「許容する」を送ったが、子の `owner-reply-check.sh --relayed` は `REASON=not-after` で落とした。`--relayed` は「主の発言が停止の記録より後」で「そのあいだに親がその停止の記録の URL を書いて主に報告した」ことを求めるので、止まる前に述べた包括的な委任は、どの子の停止に対しても必ず落ちる。

結果として、主は任せたあとも子が止まるたびに子のタブを開いて打ち直している。任せた意思を機械的に確かめられる形で一度受け取り、その後に止まった子へ効かせる経路が要る。ただしリスク許容はゲートの通過条件なので、委任が主本人の発言であること・効く範囲（どのエピックの・どの種類の止まりか）・期間・取り消しを、エージェントの判断に頼らず確かめられる形で決める。

## What Changes

- **委任の記録と主の確認**: 主が親のタブで任せる旨を述べたら、親はそれだけを委任として扱わず、エピックの issue に決まった書式の委任の記録（1 行目 `主の委任: リスク許容`。範囲と期間は仕様で決めた定型の文）を投稿し、その URL を本文に書いて主に確認を求める。主が親のタブでその直後に別の発言を挟まずに答えた発言（答え方の行で `任せる` を打たせる。任せる意思が読めなければ問い直す）を「委任の確認」とする。範囲は主が自由に述べた文ではなく、主が確認した定型の記録で決まる。親は確認の場所（セッション ID・uuid・記録の URL）を `委任の確認の場所:` の 1 行でエピックに残し、起動し直したあともそこから値を取る。取り消しは親が主の発言を受けた次のターンの最初のツール呼び出しでエピックに `主の委任: 取り消し` を投稿する（投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` なら効く）
- **`owner-reply-check.sh --delegated`** を足す: `--delegated <親のセッション ID> <uuid> <委任の記録の作成日時> <委任の記録の URL> <停止の記録の作成日時>`。その uuid の行が主の発言の 9 条件を満たすこと、委任の記録より後であること、そのあいだに親が委任の記録の URL を書いた発言があり、URL を書いた最後の親の発言とその行のあいだに別の主の発言が無いこと、その行が停止の記録より前であることを確かめる。落ちたときの理由は `not-found`・`not-owner`・`not-after`・`not-asked`・`not-direct`・`not-before`
- **親の送り方**（develop の `references/epic.md` 手順 8）: 委任が有効で（決まった 6 条件）、止まりに委任が効く（子の PR が `needs-approval` で、最新のリスク宣言が `主のリスク許容が必要。` の行を持ち `主の回答:` がまだ無く（G では、今確かめている委任の形の記録の行だけは除く）、停止の記録がその宣言と委任の確認より後で、停止の記録の `推奨:` の値が `許容する` で始まる）ときだけ、主に上げずに `reply --as owner` で `許容する（主の委任による。停止の記録: <URL>） [主の委任: セッション <ID> / uuid <uuid> / 記録 <委任の記録の URL>]` を送り、エピックに `委任で送った:` の 1 行残す。同じ止まりに二度送らない。それ以外は今どおり主に上げる
- **子の受け取り方**（develop の `references/epic-child-stop.md`）: 末尾が `[主の委任: …]` の返事は `--delegated` と委任の記録の GitHub 上の確認（委任が有効かの 6 条件と、委任が効く止まりの 4 条件。親・G と同じ文）を通したときだけ G に渡す。通らなければ今どおり主に子のタブで打ってもらう
- **ゲートの合格条件**（pr-review-gate `stages/pass.md` 手順 5・`stages/hold.md` の手順 3-c と手順 6）: 記録の形 `主の回答: 許容 — 親経由で受領（委任）（…）` と、その真正性確認（`--delegated` の終了コード 0 と GitHub 上の確認の再実行）を足す。引き継ぎのときは `--delegated` で確かめ直し（`--relayed` は使わない）、委任がまだ有効かを確かめ直す。回答行の形は 4 つになる
- 既存の `--relayed`（主が止まりへの報告を見て直接答えた経路）は変えない。委任より前に別の子・別の PR だけを名指しした主の発言は、どちらの経路でも今どおり落ちる
- `scripts/epic-dispatch.sh` は変えない（委任の返事も `reply --as owner` で送る）
