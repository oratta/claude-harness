## Context

dev-workflow の 1 ループは本体（オーケストレータ）が W / R1 / G を名前付きサブエージェントとして spawn し、SendMessage で再開する形で回る。サブエージェントは idle になると、自分が起動した背景タスクの完了では再起動されない（完了通知は `queued_command` として積まれるだけ）。再開できるのは親からの SendMessage だけで、実測では送れば 3〜16 秒で復帰した。

一方で手順書は逆のことを指示していた。`roles/gate-runner.md:17` は Codex レビューを `run_in_background` で起動して出力ファイルを読めと書いており、10 分より長く待つ方法は書かれていない。`pr-review-gate/SKILL.md:108` は companion の `status <job-id> --wait --timeout-ms 900000` を指示しているが、Claude Code の Bash ツールの前景上限は 600000 ms なので 1 回では完走しない。結果として G は「完了通知を待つ」と書いてターンを終え、親が気づくまで止まった（2026-09-08 に 5 件、合計約 4 時間）。

同種の事故は 2026-08-07 にも起きており、flatmate 側の `docs/agent-loop-steps.md` には正しい規則（完了待ちでターンを終えない・同一ターン内でポーリングする）が既にある。しかし G はそのファイルを読まないため、dev-workflow プラグイン側に正本が要る。

制約として、この harness の Bash ツールは前景 1 回あたり最大 600000 ms、行頭の裸の長時間 `sleep` は拒否される。ループ内の `sleep` は許可されることを本 change の作業中に実測で確認した（`until [ ... ]; do sleep 1; done` が前景で完走）。

## Goals / Non-Goals

**Goals:**

- サブエージェントが長時間処理（Codex レビュー・フルテスト）の完了を、ターンを終えずに待てる手順を dev-workflow の手順書に持たせる
- 待ちの終了条件と、待ちを打ち切る条件を一意に決める（実装者が検知方法や打ち切り方を発明しなくて済む状態にする）
- W / R1 / G のどの役割の指示書からも同じ規約に到達できるようにする
- 「前景上限を超える待ち値」を機械検出できるようにして、同じ退行が黙って戻らないようにする

**Non-Goals:**

- 親側の保険（親が idle のサブエージェントを検知して起こす仕組み）は扱わない。issue #255 が担当し、この change が効かなかったときだけ着手する
- flatmate や codex プラグインなど dev-workflow 以外のリポ・プラグインへの規約の波及は扱わない。このリポでの `--timeout-ms 900000` の出現は `gate-runner.md:17` と `pr-review-gate/SKILL.md:108` の 2 か所だけで、非目標は実測と一致している
- Codex レビューそのものの所要時間短縮（`model_reasoning_effort` の調整）は既存の規約のままとし、この change では変えない

## Decisions

### 1. 正本は `plugins/dev-workflow/references/subagent-waiting.md` に 1 本置き、各手順書からは 1 行で参照する

読み手は W / R1 / G の 3 つの指示書と pr-review-gate/SKILL.md の計 4 か所ある。同じ十数行を 4 か所に複製すると、片方だけ直って食い違う（`--timeout-ms 900000` が gate-runner.md と SKILL.md の両方にあり、片方だけ古い書き方で残っていたのが今回の事故の遠因でもある）。dev-workflow には「共有契約はプラグイン直下 `references/` に置く」という既存の規約（capability `dev-workflow-shared-references`）があり、`model-tiers.md` / `pr-body-format.md` / `self-verification.md` / `workflow-execution.md` が同じ形で置かれている。待ち方の契約もこれに並べて 5 本目にする。

既存要件は「他プラグインからも参照される契約」を置き場の条件にしており、待ち方の契約は dev-workflow 内の複数スキルが読むものなので条件が半歩ずれる。要件側を「dev-workflow 内の複数スキルが読む契約もここに置く」に広げる delta を出す。`plugins/dev-workflow/README.md:41-46` の表が 5 本を 1 行説明付きで持つことも同じ要件の MUST なので、README への 1 行追加を実装タスクに含める。

- 却下案 A: 4 か所にそのまま書く。file を開く回数は減るが、次に待ち方が変わったとき 4 か所を直す必要があり、今回と同じ食い違いが再発する
- 却下案 B: `templates/escalation-tripwires.md` に相乗りする。あれは「手を止めて本体に return する条件」の正本で、主題が違う
- 受け入れるコスト: サブエージェントが開くファイルが 1 つ増える。緩和として、各指示書に置く 1 行は参照だけでなく**禁止そのものを書き切る**（「完了通知を待つためにターンを終えない」）。詳しい待ち方が要るときだけ正本を開けばよい形にする

### 2. 禁止するのは「待つためにターンを終えること」であって、`run_in_background` での起動そのものではない

Codex レビューは 10 分を超えることがあり、前景 1 回では起動から完了まで到達できない。したがって起動は background のままにし、**完了の確認だけを同一ターン内の前景ポーリングで行う**。禁止語を「`run_in_background` を使うな」にすると Codex 経路が成立しなくなる。

- サブエージェントが禁止されるのは、Monitor や `run_in_background` の「完了したら続きが動く」に頼ること（起きないため）
- メインセッションは背景タスクの完了で再起動されるので、この禁止はサブエージェントに限定する。`pr-review-gate/SKILL.md` は本体とサブエージェント G の両方が読むため、この条件分岐を本文に書く
- `SKILL.md:106` の見出し文「フォアグラウンドで完了を待つ呼び方を禁止する」は、字面のままだと新方針の「前景ポーリングで待つ」と衝突して読み手が迷う。意味は「前景 1 回で起動から完了まで待ち切ろうとする呼び方の禁止」なので、その 2 つが区別できる形に書き直す

### 3. 完了シグナルを経路ごとに定める

待ちループの終了条件が無ければループは書けない。`codex exec` も `codex-companion.mjs` も出力に完了マーカーを書かないので、マーカーは起動側で付ける。

- **`codex exec` 直叩き経路**: 起動コマンドを `{ codex exec … ; echo "__CODEX_DONE__ rc=$?" ; } >> "$out" 2>&1` の形にし、終了条件を出力ファイル中の `__CODEX_DONE__` の出現にする。`rc=` の値で成否を判定できる
- **`codex-companion.mjs` 経路**: `status <job-id> --wait --timeout-ms 540000` の exit code と status 出力を終了条件にする。出力ファイルの中身を推測しない

これを要件に書かないと、実装者が検知方法を自分で発明することになる（最初の design 草稿にあった `grep -q 'DONE'` は、どちらの経路でも実際には一致しない）。

### 4. 待ちは Bash ツールの `timeout` パラメータで刻み、値は 540000 ms に統一する

ここでいう `timeout` は **Bash ツール呼び出しのパラメータ（ミリ秒）** であり、シェルの `timeout(1)` コマンドではない。両者は単位（ミリ秒 / 秒）が違ううえ、macOS の既定には GNU `timeout` が無く `gtimeout` になるため、シェルコマンド側は使わない。手順書の例も Bash ツールの入力の形（`command` と `timeout: 540000` の組）で示す。

```
command: until grep -q '__CODEX_DONE__' "$out"; do sleep 10; done
timeout: 540000
```

Bash ツールの前景上限は 600000 ms なので、上限ちょうどを指定するとループの後処理ごと切られる。9 分に揃えて 1 分の余裕を残す。`status --wait --timeout-ms` にも同じ 540000 を使う。

### 5. 総待ちの上限は前景ループ 3 回（27 分）とし、超過はフォールバックに落とす

「1 回で終わらなければもう一度呼ぶ」だけでは、ジョブが死んで出力が来ない場合と 30 分かかっている場合を区別できず、無限に回り続ける。既存の `pr-review-gate/SKILL.md:93` は Codex のフォールバック条件を「未導入・サブスク切れ・**タイムアウト**」と定めており、その「タイムアウト」は従来 900000 ms の一撃で切れることだった。前景ポーリングに変えるとその定義が消えるので、**総待ちの上限がフォールバックの発火点**だと明示して定義を置き換える。

- 上限に達したら G は待ちをやめて `needs-reviewer` を return し、根拠に「Codex タイムアウト（27 分）」と書く（そこから先は既存のフォールバック経路がそのまま動く）
- W / R1 は待ちをやめて本体に return する
- 27 分の根拠は 540000 ms × 3 回。Codex レビューの実測が 10 分超で、`model_reasoning_effort=medium` の規約と合わせれば 3 回で足りると見た。足りなければ回数だけを変える

### 6. 退行ガードは `plugins/dev-workflow/tests/subagent-waiting.bats` に置く

この change の成果物は手順書の文言なので、退行検出も文言に対して行う。置き場はリポの既存の分け方に合わせる。ルート `tests/` はリポ横断ガード（marketplace-sync / rules-sync / agents-md-sync / openspec-specs-format / shell-multibyte-expansion）で、プラグイン固有の内容ガードは `plugins/dev-workflow/tests/` 配下（`develop-roles.bats`・`pr-review-gate-skill.bats` など 22 本）にある。今回は dev-workflow の文言だけを見るので後者に置く。`scripts/test.sh` はどちらでも `git ls-files '*.bats'` で拾う。

検査するのは 3 点 — 待ちを完了通知や Monitor に委ねる指示が残っていないこと、`--timeout-ms <数値>` と `timeout: <数値>` の 2 パターンの数値がすべて 600000 未満であること、`references/roles/` 配下の各指示書に禁止行と正本への参照があること。`timeout` の裸の出現は `plugins/dev-workflow` 配下に現状 6 件あり大半が無関係なので、検査対象をこの 2 パターンに限定する。上限値はスイート内の 1 変数 `FOREGROUND_LIMIT_MS=600000` にまとめ、出典をコメントに書いて直し先を 1 か所にする。

- 受け入れるコスト: grep ベースなので、規約を守った書き換えでも語を含めば落ちる。テスト側に理由コメントと hint を書いて、落ちたときに何を直すかが分かるようにする

## Risks / Trade-offs

- **前景ポーリングはサブエージェントを最長 9 分ブロックする** → その間に親が SendMessage を送っても処理されない。ただし従来は無期限に止まっていたので悪化はしない。長い待ちの前に「1 回あたり 9 分・上限 27 分待つ」と出力してから入る
- **ハーネス側の `sleep` 制限が将来変わるとループが拒否されうる** → 正本にループ内 `sleep` が許可対象である根拠を明記し、拒否されたときの代替（ポーリング間隔を短く刻んで呼び出し回数を増やす）を 1 行添える
- **総待ち 27 分は当て推量** → 短すぎれば Codex レビューが取りこぼされて Task サブエージェントに落ちる（品質は落ちるが工程は進む）。長すぎれば停止時間が延びる。回数だけを変えられる形（540000 × N）にしておく
- **grep ベースのガードの偽陽性** → 正本ファイル自身と本テスト自身は禁止語を説明のために含むため、検査対象パスから除外する。除外の理由をテスト内にコメントで残す
- **新規 .bats は tracked にしないとテストランナーが発見しない** → `scripts/test.sh:43` が `git ls-files -- '*.bats'` で対象を集めるため、untracked のままだと Red ではなく「フィルタに一致するスイートが無い」で終わる。Red の確認前に `git add -N` する
- **受け入れ条件の 4 番目（develop 実行 1 回で G の idle 通知に「完了を待つ」文言が出ない）はテストで検証できない** → 実装後の動作確認として親のトランスクリプトで確認し、pr-review-gate の動作確認の証拠として PR に添える
