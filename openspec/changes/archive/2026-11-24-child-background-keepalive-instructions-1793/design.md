# Design

## Context

動機と範囲は proposal.md を参照。#1792 の共有 JSON はトップレベルに停止済み子向け、`background` に作業待ち向けの同じ4項目を持つ。固定文は `request_template` に、`separator` で `reply_prefix` と各 `fields` の欄名＋空白＋`<値>` を連結した型を展開して作る。生成用 CLI は `child-log-read.py --keepalive-text background`。今回はこの定義も CLI も変更しない。

`epic-keepalive.md:3-7` は停止前の読み込みと停止状態保持だけを説明する。`child-background-wait.md:47` は入力による待ち直しで既存タイマーを止めるため、作業待ち向け予約文をそこへ渡すと issue の保持条件に反する。既存仕様の該当要件を拡張して例外の順序を明記する。

## Goals / Non-Goals

**Goals:**

- 背景作業を待つ前に受信契約と作業待ち用の定義を保持し、受信ターンで読み直さず一行だけで終える。
- 通常入力・元作業の完了通知・自己タイマー通知から予約文を区別し、予約文だけで元作業やタイマーの寿命・実行を変えない。
- 旧停止中の受信契約を含めて手順の非退行を検証する。

**Non-Goals:**

- 親の送信、予約文の再定義、受信基盤の変更、自己タイマーの撤去、実機でのキャッシュ維持成功の宣言。#1777 の送信条件をこの change で決めない。

## Decisions

### 既存の共有正本を拡張し、作業待ち側から接続する

issue 指定どおり `epic-keepalive.md` に共通 JSON の種類選択・完全一致・応答生成・受信ターンの制限を集める。停止前に加え、`child-background-wait.md` を読んで待ちを始める／延長する前にも、受信正本と JSON の `background` を前もって読む。固定文全文・接頭辞・欄名の一覧は手順書へ複写しない。停止中は既存トップレベル定義と質問・停止記録保持をそのまま使う。

作業待ち側には参照とその状態で必要な分岐（元作業 ID・実行 ID・自己タイマー ID・初回設置時刻の保持、通常入力時の取消より先に分類）を書く。共通の生成規則を2つの文書に複写する案は既存の共有正本契約に反し、変更時の食い違いも生むため採らない。

### 予約文を通常入力による待ち直しから除外する

共有定義から生成した `background` の固定文に完全一致するときだけ、既に読んだ契約に従う一行応答でターンを終え、元の待ちを続ける。ツール呼び出し（定義再読、TaskStop、タイマーの再設置を含む）を行わず、タイマーの基点・12時間上限も延ばさない。主が同じ固定文を入力しても予約文として扱うのは既存の限界。

通常入力として毎回タイマーを取り消す案や、声かけを成功した自己通知とみなしてタイマーを置き直す案は、issue の「自己タイマーを保つ」に反するため採らない。完全一致しない入力は既存の主・親入力の手順へ、元作業やタイマーの通知は既存の ID・成功終了の照合へ渡す。元作業完了と自己通知の競合時の優先・取消も維持する。

以上は #1793 の受け入れ条件と既存の共有正本から導く接続方針で、記録先にない新たなプロトコルや送信判断は追加しない。

## Risks / Trade-offs

- 文書テストはモデルの実際の一行応答を保証しない → Bats の合格を手順の接続と非退行の証拠として報告し、実際の送信・会話ログ確認は #1777 に残す。
- 作業待ち側へ「型どおり」等の共有本文を複写すると場面テストの一意性も崩れる → 共通規則は受信正本に一度だけ置く。
- `epic-keepalive.md` の増加は複数場面の読込量に波及する → 元の意味を保つ簡潔な編集を優先し、`tests/develop-epic-scene-budget.bats` を実測する。予算を超えたら既存契約を削らずに表現を整理し、上限変更が必要なら増分・削減を試した内容・理由を明示して本体へ返す。予算の機械的な引き上げはこの計画に含めない。

## Verification

`child-background-wait.bats` に、待ち前の Read 接続、両定義の選択、完全一致による先行分類、一行応答だけで終了、ツール禁止と元作業・各 ID・自己タイマー・基点の保持、通常入力の既存取消経路、旧停止中の受信契約を検査するテストを追加する。文書の参照だけで中身が欠けても通らないよう、受信正本と作業待ち側の両方を検査する。

実装後は同スイート、既存 `child-log-read.bats` と `epic-child-state.bats`、場面予算、`tests/bats-assertion-guard.bats` を実行する。今回は artifact の strict validation と差分確認まで。

## Migration Plan

データ移行は不要。手順とテスト・変更記録だけを配布し、親は旧送信対象のままにする。戻す場合は本 change の実装差分を revert する。受信基盤 #1792 と自己タイマー #1743 の記録形式を変えない。
