## Context

develop の本体は、記録先のコメントとラベル、各役割の return の要約だけで次を決める設計になっているので、会話の履歴が無くても続けられるはずである。足りないのは、名前付きで起こした W の名前、実行先（profile・account・executor）の選択、周回の数、PR トークン上限の最新値のように、本体の会話の中にしか無い情報である。これを保留で止まる時点で記録先に書き出せば、新しいセッションの本体は履歴なしで再開できる。

## Goals / Non-Goals

**Goals:**

- 保留の全場面で、引き継ぎを同じ書式・同じ場所（記録先のコメント）に 1 種類だけ残す。
- 新しいセッションの本体が、そのコメントとラベルだけで続けられるようにする。
- 主に、返事の渡し方（新しいセッションで `/develop <記録先>` と一緒に）を毎回案内する。

**Non-Goals:**

- 保留の判定条件や、主に聞いてよい 4 分類を変えること。
- 同じセッションで続ける経路をやめること（1 時間以内に返事ができるなら続けてよい）。
- 本体のコンテキスト上限（`DEV_WORKFLOW_CONTEXT_CAP`）の規則を変えること。

## Decisions

### 引き継ぎは記録先のコメント 1 種類で、場面ごとに書式を作らない

1 行目は `引き継ぎ: 主の返事待ち`（正規表現 `^引き継ぎ: 主の返事待ち$` に完全一致。`仕様化判断:` と同型）。2 行目以降は次の項目を `項目名: 値` で 1 行ずつ書く。

| 項目 | 中身 |
|---|---|
| 待ち理由 | `リスク許容` / `動作確認` / `切り出しの確認` / `PR トークン上限` / `2 周キャップ超え` のどれか |
| 主への依頼 | 主に依頼したコメントの URL（PR のコメントでもよい。同じ内容を新しいセッションで主に見せ直せるように） |
| 対象 | PR 番号・HEAD の 40 桁 SHA・ブランチ・worktree のパス |
| 実行モード | interactive / unmanned |
| 実行先 | 明示した実行先オプションと account-home の対応（無ければ `自動選択`）と、開始済みの phase の選択結果のコメント URL（最初の phase は develop 開始コメント、以降は dispatch 記録） |
| 次に起こす役割 | 返事のあとに最初に起こす役割（例: `G 保留の解除`・`W 修正`・`W (3b)`）と、渡す入力の在り処（コメント URL） |
| 周回 | 仕様レビューと G の周回の数、W の修正の周回の数 |
| ラベルの付け先 | `needs-approval` を付けた先（`PR #N`、PR が無ければ記録先の issue） |
| 前任 W | 直近の return の 1 行目と要約または URL、手渡し可否（`可` / `不可` / `不要`）。W を起こしていなければ `なし` |
| PR トークン上限 | 最新の `PR トークン上限:` の値（無ければ既定値）と、止まった時点の合計 |
| 回し方 | エピックの子のとき、エピックの最新の `回し方:` の値。エピックの子でなければ `なし` |

理由: 本体が止まる場面は 3 つあるが、再開に要る情報は場面によらず同じで、違うのは待ち理由と次に起こす役割だけである。場面ごとに書式を作ると、新しいセッションの本体が書式を見分ける分岐を持つことになり、直すときに片方が漏れる。最新の 1 件を正とし（`仕様化判断:` と同じ）、再び止まるときは新しいコメントを書く。

W の名前は項目に入れない。新しいセッションでは前のセッションで起こした W に SendMessage できず、名前を書いても使えない。G は段ごとに新しく起こすので名前を持ち越さない。

### 前任 W の手渡し可否を、保留に入る前に確定して記録する

新しいセッションの本体は前任 W に停止を指示できない。そのため decision-criteria.md「手渡しの許可」（`工程完了:` か、停止指示後の停止確認）を、引き継ぎを書く前に本体が満たし、結果を引き継ぎの「前任 W」に `手渡し: 可 / 不可 / 不要` で記録する。前任の直近の return が `工程完了:` なら可。`工程中断:` なら、前任へ停止を指示して停止確認を受け取り、未コミット差分を本体が commit してから可と書く。PR トークン上限の exit 2 は SendMessage を禁じるので停止指示も送れず、前任が `工程中断:` のままなら `不可（理由）` と書く。新しいセッションの本体は `不可` のとき新しい W を起こさず、主に報告して指示を聞く。`不要`（前任 W がいない。最初の W を起こす前に止まった場合）のときは、前任がいないので手渡しではなく、引き継ぎの「次に起こす役割」の入力で初回の W を起こす。書いた本人（本体）が止まる時点で条件を確かめるので、新しいセッションには前任に確認する手段を要らなくできる。

### 保留の 3 場面で投稿の順序を揃える

引き継ぎの「主への依頼」は依頼コメントの URL なので、どの場面でも先に依頼のコメントを投稿する。置き場は、対象の PR があれば PR、無ければ記録先にする。`stages/hold.md` 手順 6 が依頼を PR に投稿するので、記録先が issue でも PR のコメントの URL を使ってよい（引き継ぎのコメント自体は常に記録先）。G の保留は G が投稿した依頼コメントを使い（無ければ本体が PR に投稿）、exit 2 と 2 周キャップ超えは本体が問いを PR（無ければ記録先）のコメントに書く。順序は依頼コメント → 引き継ぎ → 主への案内で、依頼より前に引き継ぎを投稿しない。

### コメントの記録先とラベルの付け先を分ける

`stages/hold.md` 手順 6 は `needs-approval` を PR に付ける。記録先が issue のとき、コメントは issue にあり、ラベルは PR にある。そこで引き継ぎに「ラベルの付け先」（PR があれば `PR #N`、無ければ記録先の issue）を書き、再開手順と入口の分岐はこの項目の指す先でラベルを見る。

### 実行先は開始済みの phase の選択結果を続け、未開始の phase だけ選び直す

develop/SKILL.md「Role profile の選択」は、自動選択を phase ごとに評価し直し、開始済みの role は途中で切り替えないと定めている。この境界を新しいセッションにもそのまま使う。引き継ぎの「実行先」には、明示した実行先オプションと account-home の対応（無ければ `自動選択`）と、開始済みの phase の選択結果のコメント URL を書く。最初の phase の選択結果は develop 開始コメントにあり、以降の phase は dispatch 記録にあるので、両方を参照先にする。新しいセッションの本体は、明示オプションはそのまま使い、自動選択では次に起こす役割の phase の選択結果がそのコメントにあれば構成・executor・account・model をそれで続け、どこにも選択結果が無い phase だけ開始時に adapter で自動選択を評価する（開始コメントを見落とすと、開始済みの最初の phase を選び直してしまうため）。

### 新しいセッションの再開手順（守備範囲は delta spec の「守備範囲」の段落が正本）

`/develop <記録先>` で起動した本体は、次の順で状態を組み立てる。

1. 記録先の最新の `引き継ぎ:` コメントを読む。無ければ通常の入口 0 に進む。入口（`commands/develop.md`）も同じ条件で、引き継ぎのコメントがあればラベルの有無によらずこの手順に進む。
2. 引き継ぎのコメントより後の主の回答（記録先または対象 PR のコメント、または `/develop` の引数の残り）を探す。あればそれを回答として使う。無ければ、引き継ぎの「主への依頼」を主に見せ直して返事を聞く（返事が来るまで役割を起こさない）。
3. 引き継ぎの「ラベルの付け先」に `needs-approval` がまだ付いていること、PR の HEAD が引き継ぎの HEAD と同じことを確かめる。ラベルが無ければ保留は解かれているので状態を組み立て直して報告する。HEAD が動いていれば、差分を主に報告して続けるかを聞く。
4. W は SendMessage を使わない。「前任 W」が `手渡し: 可` なら手渡しで、`不要` なら初回として新しい W を起こす。`不可` なら起こさず主に聞く。G は今までどおり段ごとに新しく起こす。
5. 実行先は上の決定のとおり続ける。
6. 計測の `--cap` には記録先の最新の `PR トークン上限:` の値を使う。待ち理由が `PR トークン上限` で主が「続ける」と答えたときは、今の手順どおり新上限のコメントを投稿する。

### 主への案内

本体は、待ち理由によらず主への依頼に「返事は新しいセッションで `/develop <記録先>` と一緒に渡す。1 時間以内に返事ができるなら、このセッションで続けてもよい」と書く。本体は返事がいつ来るかを知らないので、引き継ぎは必ず残し、どちらにするかは主に任せる。

### 受け入れ条件 2〜4 の扱い

条件 2（保留で止めた PR を新しいセッションで再開して合格まで進める）と条件 3（`--cap` を小さくした記録先で引き継ぎのコメントを残す）は、実装後に本体が実機で行い、PR 本文に記録する。条件 4（マージ後の 5 PR で 1 時間以上あいたあとの書き直し代が 1 PR あたり 0.5 ドル以下）はマージ後でないと測れないので、PR のマージ条件にせず、マージ後にエピック #511 へコメントして満たす。

## Risks / Trade-offs

- 引き継ぎの項目が足りず、新しいセッションの本体が会話の外にある事情を再現できない → 実機の再開（条件 2）で足りない項目が見つかれば、項目を足して同じ書式のまま直す。
- 引き継ぎが古いまま残り、別の状態のときに読まれる → 最新の 1 件を正とし、HEAD と `needs-approval` の現状と突き合わせる（手順 3）。
