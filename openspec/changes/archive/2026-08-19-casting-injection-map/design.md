# design — casting-injection-map

issue #122 の「決めること」5点に対する設計判断と、捨てた代案。

## 判断1: タイミング語彙は8分類（⑦起票・選定時・⑧設計時を追加。初版 — 判断6で「論点相談」を加えた9分類に改訂）

たたき台の6分類では、実在する2つの配線が収まらない:

- 優先順位・資源配分の配線は burn-select の論点ゲート（genetta-inc/flatmate#368、マージ済み）で、発火点は「どの issue に着手するかの選定時」。PR 時でもアクション直前でもない
- ユーザー価値・市場の配線は longrun plan の research agent（longrun-mvp-research 等）で、発火点は「plan・企画・仕様化の時点」

**採用（初版）**: ⑦起票・選定時、⑧設計時 を追加して8分類にする（最終形は判断6の9分類）。各タイミングが実装機構と1:1に対応する（①=rules/hooks、③=pr-review-gate、④=直前ゲート、⑦=burn-select/issueify、⑧=plan/proposal）状態を保つのが目的で、「亜種」注記で6分類に押し込むと点在の解消という issue の目的に反する。

**捨てた代案**: ③④⑤⑦⑧を「ワークフロー段階ゲート（段階=X）」の1分類に統合して語彙を4つに圧縮する案。語彙は小さくなるが、タイミングと実装機構の1:1対応が失われ、配線先を引くたびに段階パラメータの解釈が要る。

## 判断2: 置き場所はカタログの列追加ではなく別文書 `catalog/injection.md`

**採用**: `plugins/casting/catalog/injection.md` を新設し、カタログ本体（catalog.md）は変更しない。

理由（重い順）:

1. **5列はパース契約**: casting-check.sh の resolve（行単位合成）・project.md の行上書き（「行を書くなら5列すべて」）・既存テスト群が5列を前提にしている。列追加は catalog-project-files の全面改修＋重量ルート（version 増加・主承認・全導入 repo への影響確認）を強いる
2. **注入マップは配役（上書き）の対象ではない**: project.md/local.md が上書きするのは「担い手」と「移譲文書」であり、「法的・規制をどの機構が注入するか」は harness 全体の実装配線で repo ごとに変える性質のものではない。行単位継承システムに載せる必然がない
3. **ドリフトは機械検査で防げる**: 2ファイルに14観点が並ぶ重複リスクは、catalog_version の front matter 一致＋14観点全掲載＋タイミング語彙の定義済み検査を bats に持たせて塞ぐ

**捨てた代案**: catalog.md に「注入タイミング」「配線先」列を追加する案（上記1・2により棄却）。`docs/` 配下に置く案（カタログと同格の正本なので `catalog/` 配下に置き、正本性を明示する）。

## 判断3: 14観点の注入マップ（確定表の根拠）

たたき台からの変更は3行だけ:

- **優先順位・資源配分**: 「②の亜種」→ ⑦起票・選定時（burn-select 論点ゲートが実在する配線）
- **ユーザー価値・市場**: 「企画・plan 時（語彙未定）」→ ⑧設計時
- **事業方向性・戦略整合**: ②のまま（未移譲＝主に上げる）としつつ、フェーズ宣言文整備後の注入先を⑧設計時と明記（移譲の到達点を先に書いておく）

残りはたたき台どおり。⑤定期監査はどの観点にも割り当てない（候補: 財務・コストの使用量見回り、運用工数・維持の棚卸し。実運用の必要が出た時点で割当と実装 issue を起こす）。

## 判断4: 注入文書の置き場所規約

**採用**: `<repo>/.claude/casting/policies/<slug>.md`。配役表（project.md）と同じ `.claude/casting/` 配下に置くことで、「移譲に必要な文書」列からの参照が同一ディレクトリ内で閉じ、/casting:init の管轄に自然に収まる。slug は injection.md に固定表で定義する（regulation / budget / brand / phase / priority / maintenance）。

**捨てた代案**: repo ルートの `PHASE.md` 等の一点もの（発見性が repo ごとにバラける）。`docs/` 配下（配役表と物理的に離れ、移譲文書の有無確認が2箇所参照になる）。既存に PHASE.md 等がある repo は policies/ からの参照 stub でよい（実体の移動を強制しない）。

## 判断5: 実装 issue の切り出し範囲

切り出すのは未実装かつ実装形が見えている2件のみ:

1. **③の汎用化**: pr-review-gate のレビュー時に、対象 repo の `.claude/casting/policies/` に実在する方針文書（規制メモ・許容工数宣言等）をレビューレンズとして自動注入する機構
2. **④の汎用化**: sns-safety-reviewer（marketing 専用）を一般化し、「外に出る・不可逆・課金」アクションの直前に該当観点の専任サブエージェント確認を挟む汎用ゲート

⑤定期監査は割当なしのため issue 化しない。#119（auto-merge 脅威モデル）は資産・回復可能性観点の既存 issue として injection.md から参照するに留める（合流の強制はしない）。

## 判断6: 論点相談・仲裁・人格規約（2026-08-19 主フィードバック反映）

初版は「方針文があればメインセッションが自走で決める」を暗黙に許していたが、これはメインが policy 文書を読む＝バイアスとコンテキスト汚染を意味する。主の指摘を受けて次の3点を確定した:

1. **注入のサブエージェント限定**: 注入文書はメインセッションに読み込まない。読むのは観点を担う専任サブエージェントだけ
2. **論点相談タイミングの追加（9分類化）**: 主に上げたくなった瞬間（エスカレーション直前）に、移譲済み観点のスペシャリストへ相談する。意見が割れたら仲裁エージェント（フェーズ宣言文と双方の主張だけを受け取る新品コンテキスト）が裁定し、主へは事後報告。担い手が主の観点が絡む論点は相談に入らず主へ（catalog.md の担い手判定が常に先）
3. **人格規約**: policy 文書は判断基準＋人格ブロック（名前・スタンス・口調数行）を持ち、スペシャリストが纏う。狙いは①同調圧力への耐性（立場が保持されやすくレビューの独立性が上がる）②判例・仲裁報告の帰属可読性（主のフィードバック動線が観点単位で効く）③主の受容度。学習に見えるものは判例台帳経由で作る（起動時に同観点の過去判例を渡す）

実装は oratta/claude-harness#127 に切り出し（本 change は設計正本の更新まで）。
