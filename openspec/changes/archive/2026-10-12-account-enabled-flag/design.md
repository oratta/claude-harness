## Context

登録簿（`accounts.json`）は 5 か所で読まれている。`usage_view.py` の `read_registry`（`select-account.sh` と `build_view` が使う）、`usage-probe.sh` の `read_slots`、`statusline.sh` の埋め込み python、`accounts-init.sh`、そして `select-account.sh` 自身である。statusline は別プラグインなので dev-workflow のスクリプトを読まず、同じ規則を自分で持っている（`statusline-multi-account-usage` の既存の方針）。

自動選択は「週の経過率 − 週次使用率」が最大のスロットを選び、取得からの経過時間ではスロットを外さない（`usage-account-registry` の「古い・欠測・短期枠逼迫のスロットを候補から外す」）。この規則のもとで、使っていないスロットが選ばれる経路を着手時に 2 つ確かめた（記録は issue #976 のコメント）。

| 経路 | 使っていないスロットの値 | 余裕の出方 | 確かめた場所 |
|---|---|---|---|
| リセット時刻を過ぎた | 使用率 0% に読み替え、リセット時刻は 7 日単位で先へ送る | 送った先の週の経過率そのもの（0〜100 を週ごとに行き来する） | 一時ディレクトリ。`margins=a:10.00,b:14.29` で b |
| リセット時刻の前 | 最後の観測値を下限として使う | 使用率が増えないまま経過率だけ進む | 実機（読むだけ）。`margins=a:25.34,b:28.03` で b |

どちらも経過時間で外さない規則の帰結で、その規則自体は意図して決めたもの（使用量 API が 429 を返し続けても記録で選べるようにするため）なので変えない。使わないスロットを利用者が明示して外せるようにする。

## Goals / Non-Goals

**Goals:**

- スロットを登録簿に残したまま、自動選択・使用量の取得・ステータスラインから外せる
- `enabled` を書いていない登録簿では、5 か所すべての挙動が変わらない
- オンに戻せば、登録をやり直さずに元の状態から再開する

**Non-Goals:**

- オンとオフを切り替えるコマンド（#977）
- Codex 側のオフ（#978）
- 自動選択が経過時間でスロットを外さない規則の見直し
- `build_view` の出力に `enabled` を足すこと（読み手がいない）

## Decisions

### 1. オフになるのは `enabled` が JSON の `false` のときだけ

省略・`true` に加えて、真偽値でない値（`"false"`、`0`、`null`）もオンとして読み、スロットは捨てない。

検討した別案は 2 つある。真偽値でないスロットを不正として捨てる案は、`id` や `securestorage` の不正と同じ扱いになって規則は揃うが、書き損じ 1 つでアカウントがステータスラインからも選択からも黙って消える。偽とみなせる値（`0`、`"false"`）をオフに倒す案は、5 か所で「偽とみなせる」の定義を揃える必要があり、python と jq / bash で食い違いやすい。`false` との一致だけなら 5 か所とも 1 行で書ける。書き損じた場合はステータスラインに `off` が出ないので気づける。

### 2. オフのスロットはスロット一覧に残す

読み取り処理はオフのスロットを捨てず、オンかオフかの印を付けて返す。宣言順、8 個の上限、`id` の一意性、active の判定はこれまでどおり全スロットで数える。

捨てる実装にすると `usage_view.py` の変更は最小で済むが、ステータスラインが行を残せず、オフのアカウントで手動起動したセッションの active 判定が別のスロットへずれる。

`usage_view.py` では、オンかオフかを含む読み取り関数を足し、既存の `read_registry(path)`（`[(id, securestorage)]` を返す）はその結果から印を落として返す薄い関数として残す。`build_view` と `active_slot`、および既存のテストは `read_registry` の形に依存しているので、戻り値の形を変えない。

### 3. 自動選択: 候補から外し、`margins` には `off` と書く

オフのスロットは実効値を調べる前に外す。`missing` や `five-hour>=90` には数えないので、縮退の理由はオンのスロットだけで決まる。`margins` からは省かない。省くと、登録したはずのスロットが選ばれない理由を理由行から読めない。

候補が無いときの縮退先は、これまでどおり既定アカウント（空の `securestorage`）とし、`selected` の決め方も変えない（既定スロットが登録されていれば宣言順で最初のその id、無ければ `@unregistered-default`）。オンのスロットが 1 つも無いときだけ、理由を新しい値 `default-due-to-all-off` にする。既存の 2 つの理由（`default-due-to-missing-usage` / `default-due-to-five-hour-limit`）のどちらを流用しても、理由行を読んだ人が使用量の欠測や 5 時間枠を疑うことになるため。README の `cld` は selector の終了状態しか見ていないので、理由の値が増えても影響しない。

縮退先を「オンのスロットのうち最初のもの」に変える案は採らない。縮退は「選ぶ材料が無いので、何も設定していない状態で起動する」という既存の決まりで、既定スロットが未登録のときも同じく既定アカウントで起動している。ここだけ `enabled` で行き先を変えると、縮退の意味が 2 通りになる。

### 4. 明示選択はオフのスロットを拒否する

`select-account.sh <id>` はオフのスロットに対して stdout を空にして exit 2 で終わる。stderr の 1 行には id・オフであること・戻し方（読んだ登録簿のパスと `enabled` を `true` にするか消すこと）を入れる。未登録 id の診断（`unknown account id: <id>`）とは別の文面にする。#977 のコマンドができたら、戻し方の文面はそのコマンドの案内に差し替える。

### 5. probe はオフのスロットを叩く対象から外し、snapshot の値は引き継ぐ

叩くスロットを選ぶ段階（実行条件の判定）でオフのスロットを落とす。この段階より後ろで認証情報を読むので、ここで落とせば Keychain の読み出しも API 呼び出しも起きない。試行状態にも記録しない。

snapshot を組み立てる段階は変えない。取得しなかったスロットは前回値を引き継ぐ既存の経路（スロット単位の fail-open）に入るので、オフのスロットの項目は `fetched_at` 込みで残る。項目を消す案は、オンに戻した直後にステータスラインの行と自動選択の材料が無くなるので採らない。残した値はオフのあいだどこにも表示されず、選択にも使われない。

`--print-slots` は 4 列のまま変えず、オフのスロットも出す（既存のテストと、statusline 側のテストがこの出力を列番号で読んでいる）。オンかオフかは probe の内部の受け渡しにだけ足す。

### 6. ステータスラインは非 active のオフのスロットを `off` の 1 行にする

行頭は非 active 行と同じ（半角スペース 2 つ・`DIM` の label・詰め・半角スペース 2 つ）で、続けて `DIM` の `off`。既存の `取得待ち` の行と同じ組み立てになる。2 行（5h と 7d）ぶんの高さを保つ案は、情報の無い行が増えるだけなので採らない。

active のスロットがオフの場合は `off` を出さず、従来どおりライブ値で描く。オフのアカウントが active になるのは、`CLAUDE_SECURESTORAGE_CONFIG_DIR` を手で設定して起動したとき、オフにした既定アカウントへ自動選択が縮退して起動したとき、起動したあとでそのアカウントをオフにしたときで、どの場合もそのセッションでは残量がいちばん必要な情報になる。これにより、1 スロットだけの登録簿（常に active）は `enabled` の値にかかわらず出力が変わらず、既存のバイト同一の要件と衝突しない。

オフのスロットは、非 active スロットのセッション記録との突き合わせ（python の起動引数）にも載せない。描かない値を計算しないため。

### 7. `accounts-init.sh` は上書き時に `enabled` だけを引き継ぐ

同じ id の既存スロットに `enabled` があれば、その値のまま新しいスロットに写す。無ければ書かない。未知のキーをすべて引き継ぐ案は、将来のキーの意味を知らないまま保存することになるので、この change では `enabled` に限る。

## Risks / Trade-offs

- 既定スロットをオフにし、オンのスロットがすべて欠測か 5 時間枠 90% 以上のとき、縮退先はオフにした既定アカウントになる → 起きるのは「既定アカウントを解約した」うえで「残りのアカウントに一度も使用量の記録が無い、または 5 時間枠が詰まっている」場合に限られる。理由行に `margins=a:off,...` と縮退の理由が出るので原因は読める。縮退の規則を変えるのは、実際にこの組み合わせで困ってからにする
- 登録簿を読む 5 か所のうち 1 か所でも `enabled` の解釈がずれると、オフのアカウントが選ばれるか表示がずれる → 5 か所それぞれに「`false` だけがオフ」を確かめるテストを置く（dev-workflow 側 3 本と statusline 側 1 本）。statusline は実装を共有できないので、真偽値でない値のケースも statusline 側のテストに入れる
- オフのあいだ snapshot に古い値が残り続ける → オンに戻した直後は古い値で描かれ、選ばれうる。これは `enabled` を足す前から、使っていないスロットに起きていることと同じで、次の probe かそのアカウントでの起動で更新される

## Migration Plan

`schema` は `1` のままで、既存の登録簿は書き換え不要。マージ前に、実機の `~/.claude/accounts.json` の B に `"enabled": false` を手で足し、`select-account.sh` の標準エラーが `selected=a` になることを issue #976 にコメントする（受け入れ条件の最後の項目。実装後の工程で行う）。戻すときは `enabled` の行を消す。
