## Context

pr-review-gate 手順 5 は、主が会話で返したリスク許容を「会話で受領」の記録として受け、`owner-reply-check.sh <セッション ID> <原文>` でそのセッションの会話ログに主の発言として実在するかを確かめる（#721）。Orca 経路のエピックでは、子は独立した Claude Code セッションで、主は普段は親のセッションと話している。子が許容を求めて止まると、親は手順 8 で主に報告し、主の答えを `epic-dispatch.sh reply --as owner` で子の端末に `主の返事（親エピック #<E> 経由）: <答え>` として打ち込む。

2026-10-15 の実物の会話ログで確かめた事実:

- 子 #1034 の会話ログ（`71066a95-…`）では、親が打ち込んだ「親エピック #1038 から: 主が会話で『許容』と返した…」の行は `type: "user"`・`origin.kind: "human"` で残っていた。今の `owner-reply-check.sh` の 8 条件はこの行を主の発言として通す（spec の守備範囲にも「区別できない限界」と書いてある）
- 親のセッションの会話ログ（`-Users-oratta-orca-workspaces-claude-harness-epic/4b3c54eb-…`）には、主の「1034は許容」が `origin.kind: "human"`・uuid `56c1ea83-…` で残っていた。同じ uuid の行は、会話を引き継いだ別のセッションのファイル（`31ad8632-…`）にも写っていた
- その直前の親の報告（07:34）と主の答え（08:32）のあいだには、会話の圧縮の要約の行（`isCompactSummary`）が挟まっていた。圧縮しても元の行は jsonl から消えない
- 親と子はどちらも `~/.claude/projects/` に会話ログを書く（`cld` / `cld-account` が変えるのは資格情報の置き場 `CLAUDE_SECURESTORAGE_CONFIG_DIR` だけで、`CLAUDE_CONFIG_DIR` は変えない）

## Goals / Non-Goals

**Goals:**

- 主が親の会話にだけ書いたリスク許容で、子のゲートが合格できる
- 親の会話ログにある主の入力でない行（ツールの結果・親自身の発言・要約・hook の差し込み・さらに上の親からの打ち込み）を指した場合と、子が止まる前の主の発言を指した場合は通らない
- 確かめられないときは今の動き（主に子のタブで打ってもらう）に戻る

**Non-Goals:**

- リスク許容以外の返事（動作確認の結果・切り出しの確認への回答・聖域や破壊的操作の承認）を親経由で主本人の返事として扱うこと。これらの扱いは変えない
- 会話ログ（jsonl）の改変・追記を見破ること（既存の守備範囲と同じ）
- 親と子が別の PC、または別の `CLAUDE_CONFIG_DIR` で動く場合に通すこと（会話ログを読めないので exit 2、今の動きに戻る）
- `epic-dispatch.sh` の変更

## Decisions

### 1. 確かめる根拠は親の会話ログの主の発言で、子に届いた文は場所を指すだけにする

子の会話ログに残った親の打ち込みは主の発言と区別できない。そこで子に届いた文の中身は根拠にせず、文の末尾に添えた「親のセッション ID」と「主の発言の行の uuid」を手がかりに、親の会話ログの行そのものを読む。許容の意思も、子に届いた文ではなく親の会話ログの行の全文で読む。

- 代案: 親が GitHub に主の答えを書き写す → 投稿者は主のアカウントになり、主が書いたかを区別できない（今の規則が受け取らない理由そのもの）
- 代案: 原文の部分一致で親の会話ログを探す（今の `owner-reply-check.sh <セッション ID> <原文>` を親のセッション ID で回す） → 親のセッションは何件もの子の許容を扱うので、別の子への「許容」に当たりうる。uuid で 1 行に決め、下の結び付けで「この子のこの止まりへの返事」と確かめる

### 2. 送る文の形は `reply --as owner` の文の末尾に場所を添える（`epic-dispatch.sh` は変えない）

親は手順 8 で、`bash <plugin>/scripts/owner-reply-check.sh --locate "$CLAUDE_CODE_SESSION_ID" <主の答え>` を回し、出た `MATCH:` のうち全文が主の答えと同じで timestamp がいちばん新しい行の uuid を取り、次の形で送る:

```
epic-dispatch.sh reply --as owner <E> <N> '<主の答え> [主の発言: セッション <親のセッション ID> / uuid <uuid>]'
```

主の答えそのものは書き換えず、添え書きは末尾に足すだけにする（Orca 経路の親の要件の「主の答えをそのまま渡す」を、この形に直す）。子に届く文は `主の返事（親エピック #<E> 経由）: <主の答え> [主の発言: セッション <ID> / uuid <uuid>]` になる（起動し直すときは `/develop #<N> （エピック #<E> の子。返事を受けて起動し直し） ` のうしろにこの文が付く）。添え書きは 1 行の末尾に置く（端末への送信は改行を送らない前提を崩さない）。結び付け（決定 3）は親の発言の本文に停止の記録の URL があることで見るので、親は止まった子の報告を本文で書き、質問ツール（AskUserQuestion）で聞かない。質問ツールの問いは親の発言の `type: "text"` の本文に残らず、`not-asked` で落ちるためである。手順 8 の報告の文に「本文で報告する（質問ツールで聞かない）」を添える。

`--locate` で 1 行に決まらないとき（終了コードが 0 でない・該当行が無い）は添え書きを付けずに送り、主に「子のゲートは親経由の許容を確かめられないので、子のタブで打ってほしい」と伝える。

- 代案: `epic-dispatch.sh reply` に `--owner-session` / `--owner-uuid` を足す → エピック #1038 の並行する子（#1055 など）が同じスクリプトを触っており、変更を避けるよう注意書きがある。末尾の添え書きで足りるので変えない

### 3. 確かめる条件（`owner-reply-check.sh --relayed`）

`--relayed <親のセッション ID> <uuid> <停止の記録の作成日時> <停止の記録の URL>` は、親のセッションの会話ログ（`<projects>/*/<ID>.jsonl`。`subagents/` の下は読まない）で次をすべて確かめる。

| 条件 | 中身 | 落ちたとき |
|---|---|---|
| (a) 主の入力 | その uuid の行があり、主の発言の 9 条件（既存の 8 条件と下の 9 つ目）をすべて満たす | `REASON=not-found` か `REASON=not-owner`、exit 1 |
| (c) 止まったあと | その行の timestamp が停止の記録の作成日時より後 | `REASON=not-after`、exit 1 |
| 結び付け | 停止の記録の作成日時より後で、その行より前に、親の発言（`type: "assistant"`・`isSidechain` が true でない）の本文に停止の記録の URL がある | `REASON=not-asked`、exit 1 |

通れば `MATCH: <timestamp> <全文>` と `MATCHES=1` を出して exit 0。引数の不備・UUID でない ID・日時を読めない・会話ログが無い・読めないは exit 2（確かめられない）。

(b) 許容の語は、スクリプトではなく子の本体とゲートが `MATCH:` の全文で読む。今の「会話で受領」と同じ読み方で、`許容しない` への部分一致や、別の子・別の PR だけを名指しした返事（例: 子 #1030 の止まりに対する「1034は許容」）を落とす。読み方は「全文がこの子・この PR への許容と読め、別の子・別の PR だけを名指しした答えでない」で、この子とほかの子をまとめて名指しした「1034 も 1030 も許容」は通す。語の一覧で機械的に判定すると「OK、進めて」のような許容を落とし、「許容しない」を通すので採らない。

結び付けの条件は issue に無い 4 つ目の条件で、この change で足す。2 件の子が同時に止まって親が両方を主に報告しているとき、(a)(c) だけでは片方への許容をもう片方に流用できる。手順 8 は報告に停止の記録の URL を添えると定めているので、正しく動いている親では追加の手間が要らない。主が 2 件をまとめて「許容」と答えた場合と「1034 も 1030 も許容」と両方を名指しした場合は両方とも通り、全文が片方だけを名指ししていれば、名指しされていない側はゲートの全文の読みで落ちる。

- 代案: 主の答えの全文に子の番号か PR の番号を必須にする → 主に書き方を強いることになり、「許容」の一言では通らなくなる

### 4. 主の発言として数えない行を 1 つ足す（9 つ目の条件）

本文（先頭の空白を除く）が `主の返事（親エピック #` か `親エピック #` で始まる行と、`<command-args>` の中身が `#<数字> （エピック #<数字> の子。` で始まる行（`epic-dispatch.sh` の `launch` と `reply --relaunch` が打つ起動の指示）を、主の発言として数えない。既定の使い方・`--locate`・`--relayed` のすべてに効かせる。

- 子の会話ログでは、親の打ち込みが主の発言として通る穴を、決まった頭の文については塞ぐ（2026-10-15 の打ち込みもこの頭で始まっていた）
- 親自身がさらに上のエピックの子のとき、その親の会話ログに残る上の親からの打ち込みを、`--relayed` が主の入力として通さない
- 頭の無い自由な文の打ち込みは今までどおり区別できない（守備範囲に残す）
- `<command-args>` の頭 `#<数字> （エピック #<数字> の子。` は、`scripts/epic-dispatch.sh` の `launch` が打つ `/develop #$n （エピック #$epic の子。親ワークツリー $parent から Orca で起動）`（epic-dispatch.sh の cmd_launch の prompt=）と `reply --relaunch` が打つ `/develop #$n （エピック #$epic の子。返事を受けて起動し直し） $msg`（epic-dispatch.sh の deliver_reply の prompt=）の文字列に結び付いている。`owner-reply-check.sh` の冒頭の説明にこの出どころ（ファイルと関数と文字列）を書き、bats の入力はこの 2 つの文字列をそのまま写す。`epic-dispatch.sh` は変えない
- 要件「主の発言として数える行と数えない行」の⑨に合わせ、要件「owner-reply-check.sh は会話ログに主の発言が実在するかを終了コードで返す」も MODIFIED にする。引数が 2 個でないと exit 2 とする規定は既定の使い方だけに掛け、`--locate`・`--relayed` の引数は新しい要件に従うとする。守備範囲 ③ の「親の打ち込みは通りうる」は「決まった頭を付けずに打ち込んだ文は通りうる」に直し、呼び出し元の補足に「親は `--locate`、子と G は `--relayed`」を足す。pr-review-gate の 3 要件（会話で受けた許容の合格条件・引き継ぎの元・引き継いだ宣言の書式）の守備範囲 ③ の同じ文も同じに直す

### 5. 記録の形と G の確かめ方

子の本体は `--relayed` が exit 0 のときだけ、保留の解除の G に「親のセッション ID・uuid・`MATCH:` の timestamp・停止の記録の URL・`MATCH:` の全文（原文）」を渡す。G は宣言コメントに次の 1 行を追記する:

```
主の回答: 許容 — 親経由で受領（親セッション <セッション ID> / 発言 <uuid> / <日時>）停止の記録: <URL> 原文: <原文>
```

真正性確認で G は、①停止の記録のコメントを `gh api` で読み、1 行目が `子の停止: 主の返事待ち`・投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれか・コメントの issue がこの PR の記録先であることを確かめ、作成日時を取る ②`--relayed` を記録の値と ①の作成日時で回し、exit 0・`MATCH:` の timestamp が記録の日時と同じ・全文から許容の意思が読める・全文がこの子・この PR への許容と読め、別の PR・別の記録先・別の子・別のリスクだけを名指しした答えでない、を確かめる ③timestamp が宣言コメントの作成日時より後であることを確かめる（今の「会話で受領」と同じ）。通したら `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh --relayed 終了コード 0）` を追記する。

行頭は `主の回答: 許容` のままにし、手順 3-c の「前の宣言の選び方」がこの記録も主の直接の回答として拾えるようにする。引き継ぐときは元の記録の値で停止の記録のコメントと `--relayed` を確かめ直し、`MATCH:` の timestamp が元の記録を最初に追記した宣言の作成日時より後であることを確かめる。引き継いだ宣言の 1 行目の回答の部分は元の記録の `親経由で受領（…）停止の記録: <URL> 原文: <原文>` をそのまま書く（pr-review-gate の要件「引き継ぎの元は…」「引き継いだ宣言の書式と合格条件」を MODIFIED にして、3 つ目の形として足す）。

- 代案: 既存の `会話で受領（セッション <親のセッション ID> / <日時>）` に親のセッション ID を書くだけで済ませる → 部分一致で探すので別の子への「許容」に当たりうるうえ、停止の記録との結び付けを G が確かめ直せない

### 6. 実機の確認（受け入れ条件 (2)）の満たし方

自動テストで代えられる部分と、実機でしか確かめられない部分を分ける。

**自動テスト（bats。実装の段で W が回す）**: `owner-reply-check.bats` に、2026-10-15 の実物の行の形（親の会話ログの「1034は許容」の行、子の会話ログの「親エピック #1038 から: …」の行、ツールの結果、親の発言、圧縮の要約、`/develop #N （エピック #E の子。…）` の起動の指示）を写した入力で、`--locate` の出力、`--relayed` が通る場合と、`not-found`・`not-owner`（ツールの結果・親の発言・要約・親からの返事の頭・起動の指示の各 uuid）・`not-after`（停止より前の主の発言）・`not-asked`（停止の記録の URL を書いた親の発言が無い・停止より前にしか無い）・exit 2 の各場合を固定する。手順書の文は `pr-review-gate-skill.bats` と `develop-skill.bats` で固定する。

**手元の実物の会話ログでの読み取り確認（実装の段で W が回す。読むだけ）**: この PC の 2026-10-15 の会話ログに対して、①子 #1034 の会話ログで既定の使い方を原文「主が会話で『許容』と返した」で回すと、9 つ目の条件で一致しない（exit 1）②親の会話ログ `4b3c54eb-…` の uuid `56c1ea83-…`（主の「1034は許容」）を子 #1034 の、主が答えた止まりの停止の記録で `--relayed` に掛けると（主の答えより後に作られた停止の記録を使うと not-after で落ちる）、(a)(c) は通るが、当時の親の報告に停止の記録の URL が無いので `not-asked` で落ちる（手順 8 が URL を求める前の動きだった）③同じログの親の発言・ツールの結果の uuid を掛けると `not-owner` で落ちる、を確かめて結果を PR に書く。会話ログが手元に無ければこの確認は省き、その旨を書く。

**実機の Orca 経路（実機でしか確かめられない部分）**: 主が親の会話にだけ書いた許容で子のゲートが通ることは、Orca の端末と実際の Claude Code のセッションと主の入力が要るので、bats では代えられない。PR #1050 と同じく、ゲートの動作確認で「主に依頼」とし、親エピック #1038 のセッションが主の依頼で次を行う（主がするのは親のタブで「許容」と打つことだけ）。

プラグインの版: 子は何も指定しないと `cld` が読む main の版（marketplace のプラグイン）で動き、この PR の手順書もスクリプトも使わないので、合否の判定にならない。そこで次のように版を決める。

- 子は、この PR の worktree のプラグインで動かす。親は `launch` と `reply --relaunch` のどちらでも、`EPIC_DISPATCH_CLAUDE_CMD='cld --plugin-dir <PR の worktree>/plugins/dev-workflow'` を付けて `epic-dispatch.sh` を回す（`epic-dispatch.sh` は子の端末のコマンドの頭をこの環境変数から作る。epic-dispatch.sh の agent_setup の claude_cmd=）。起動し直しで付け忘れると、新しい子は main の版で動くので、その回の結果は採らずにやり直す
- 親（エピック #1038 のセッション）は main の版の手順書で動いているので、手順 8 の新しい送り方は手で行う。`--locate` は PR の worktree の `owner-reply-check.sh` を絶対パス（`<PR の worktree>/plugins/dev-workflow/scripts/owner-reply-check.sh`）で回す
- 結果の記録に、子を起動したときの `EPIC_DISPATCH_CLAUDE_CMD` の値（子が読んだ plugin dir）を 1 行入れる
- 試しの Draft PR を子のブランチに載せる順序: ①試しのエピックと子 issue を作る ②`origin/main` から試しのブランチを切って無害な 1 行の変更を commit・push し、本文に `Closes #<子>` を書いた Draft PR を作る ③その PR に `主のリスク許容が必要` の宣言コメントを置き `needs-approval` を付け、子 issue に、その PR とその HEAD を書いた `引き継ぎ: 主の返事待ち` のコメントを置く ④`epic-dispatch.sh launch --base <試しのブランチ>` で子を起動する（子のワークツリーは試しのブランチの先頭から作られ、HEAD が PR の HEAD と同じになるので、再開手順 3 の HEAD の照合が通る）
- 試しの Draft PR には `human-merge` を付けておく（auto-merge で main に入らないように）
- 合否は、試しの PR の宣言コメントに `主の回答: 許容 — 親経由で受領（…）` と `真正性確認: 済 …（owner-reply-check.sh --relayed 終了コード 0）` の 2 行が追記され、`needs-approval` が外れていることまでで判定する。そのあとの合格処理は試しの範囲外とする（保留の解除から合格処理への経路では push が走らないので、子のワークツリーのブランチ名が PR のブランチと違っても当たらない）
- 試しの前に `cld --plugin-dir <path> --version` が通るかを確かめる（通らなければ `claude --dangerously-skip-permissions --plugin-dir …` の形にする）
- `wait` に `--resolve` を付けても、`references/parent-pass-criteria.md` はリスク許容が要る止まりを通さないので、親の判断が先に返事を送ることはない

手順:

1. 上の順序で試しのエピック・子 issue・試しの Draft PR・引き継ぎのコメントを置き、子を `EPIC_DISPATCH_CLAUDE_CMD` を付けた `epic-dispatch.sh launch` で起動する（子は再開の手順で主の返事を待ち、停止の記録を残して `mark stopped` する）
2. 親は `wait --watch-stopped` で子の止まりを受け、停止の記録の URL を添えて主に本文で報告する（質問ツールで聞かない）
3. 偽の文を 2 つ先に送る: (i) 添え書きの uuid を親自身の発言かツールの結果の行にしたもの (ii) 停止より前の主の発言の uuid にしたもの。期待: 子は `--relayed` で落とし（`not-owner` / `not-after`）、G を起こさず、主に子のタブで打つよう頼む（停止の記録を出し直す）
4. 子が出し直した停止の記録を親が `wait --watch-stopped` で受け、その URL を添えて主に報告する。主が親のタブで「許容」と書き、親が手順 8 どおり添え書きを付けて送る（`reply-after-idle.md` の表で起動し直すことになったら、`--relaunch` にも同じ `EPIC_DISPATCH_CLAUDE_CMD` を付ける。起動し直された子は、引数の残りの親経由の許容を決定 7 どおり再開手順 2 より先に受ける）。期待: 子の `--relayed` が exit 0、保留の解除の G が宣言コメントに `親経由で受領` の記録と `真正性確認: 済 …（owner-reply-check.sh --relayed 終了コード 0）` を追記し、`needs-approval` を外す（ここまでで合否を判定する）。主は子のタブを開かない
5. 結果（子 issue と試しの PR のコメントの URL、子が読んだ plugin dir の 1 行）を PR に返し、試しの issue・PR・ワークツリーを片付ける

### 7. 起動し直しで届いた親経由の許容は、再開手順 2 より先に受ける

親が `reply --relaunch` で子を起動し直すと、返事は `/develop #<N> （エピック #<E> の子。返事を受けて起動し直し） 主の返事（親エピック #<E> 経由）: 許容 [主の発言: …]` の形で届く。記録先に `引き継ぎ: 主の返事待ち` があるので、子は「新しいセッションでの再開」の手順に入る。その手順 2 は `/develop` の引数の残りを自分のセッションの会話で受けた回答として `owner-reply-check.sh` に掛けるが、この行は⑨で主の発言として数えないので exit 1 になり、主に受け直しを頼むことに落ちる。

そこで「親から届いた返事」の箇条に、起動し直しの最初の指示に付いて届いたときも同じに扱い、再開手順 2 より先に当てる（引数の残りを自分のセッション ID で確かめない）と書く。develop の要件「保留の許容は会話の返事で受け、PR へのコメントを求めない」は、新しいセッションの再開手順で引数の残りを自分のセッション ID で確かめる規定を持つので、MODIFIED にして同じ旨の例外を足す。SKILL.md で触るのは「親から届いた返事」の箇条だけで、再開手順の本文は変えない（エピック #1038 の並行する子の範囲に出ない）。

- 代案: 再開手順 2 に分岐を足す → SKILL.md の 3 か所の外に出る。「親から届いた返事」の箇条は既に「起動し直されたセッションの最初の指示に付いて届いたときも」と書いており、そこに足せば範囲の中で済む

## Risks / Trade-offs

- [親が頭を付けずに自由な文で子に許容を打ち込む] → 子の会話ログでは今までどおり主の発言と区別できない（9 つ目の条件は決まった頭だけを落とす）。手順 8 は `reply --as owner` を使うと定めているので、通常の親は頭を付ける
- [親の報告より後に主が別の子について「許容」と言い、親がそれを取り違えて送る] → 結び付けは「停止より後・報告より後」までしか見ない。全文が別の子・別の PR を名指ししていればゲートの全文の読みで落ちる。名指しの無い「許容」は取り違えを区別できない（今の「会話で受領」の「PR もリスクも名指ししない許容は区別できない」と同じ限界）
- [会話ログの改変] → 検知しない（既存の守備範囲と同じ）
- [`epic-dispatch.sh` の `launch` の指示の文が変わる（エピック #1038 の子 #1055 など）] → ⑨の `<command-args>` の頭 `#<数字> （エピック #<数字> の子。` が合わなくなると、起動の指示の行が主の発言として通りうる（今の動きに戻るだけで、親経由の許容が誤って通るわけではない。`--relayed` は親の会話ログの行を読む）。`owner-reply-check.sh` の冒頭に出どころ（epic-dispatch.sh の cmd_launch と deliver_reply の prompt= の文字列）を書くので、両方を読む人は結び付きに気づける。bats は写した文字列を固定するだけで `epic-dispatch.sh` の実物と突き合わせないので、`epic-dispatch.sh` だけを変えても bats は落ちない
- [9 つ目の条件で、主が自分で `親エピック #…` と書き始めた発言が数えられなくなる] → 主がその書き出しで許容を書く場面は想定しにくい。落ちた場合は確かめられない側に倒れ、主に聞き直すだけで、誤って通すことはない

## Migration Plan

手順書とスクリプトの変更だけで、データの移行は無い。この変更より前の形で送られた親経由の返事（添え書きの無いもの）は、今どおり主に子のタブで打ってもらう。戻すときは PR を revert すれば、親経由の許容を受け取らない今の動きに戻る。
