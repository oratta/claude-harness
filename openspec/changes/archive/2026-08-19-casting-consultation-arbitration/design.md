# design — 観点相談・仲裁プロトコル（#127）

## Context

観点の配役フレームワークでは、注入文書（`policies/<slug>.md`）をメインセッションに読み込まない大原則がある（`plugins/casting/catalog/injection.md` 2026-08-19 主決定）。一方、現行の返信前チェック手順④は「全観点の担い手がエージェントなら、方針文・判断基準に従ってこの場で決める」となっており、方針文を読めないメインセッションが方針文に従うという矛盾を抱えている。#127 はこの矛盾を、観点スペシャリスト（policy 文書を読める専任サブエージェント）への相談と、意見が割れた場合の仲裁エージェントの裁定で解消する。

制約:
- `rules/perspective-casting.md` は30行以内（`casting-structure.bats` が機械検査）かつ聖域パス（SACRED `^rules/` → 人間マージ）
- `catalog/catalog.md` は `casting-set.sh` 経由のみ・今回変更なし。`catalog/injection.md` の注入マップ表・catalog_version も不変
- ハーネスの機構はテキストベースの規約が基本。hook は tool call しか横取りできず、自然文でのエスカレーション判断そのものは横取りできない

## Goals / Non-Goals

**Goals:**
- 移譲済み観点の論点を、判断基準文書を読んだスペシャリストが決める配線にする
- 仲裁エージェントの入力を「フェーズ宣言文＋主張リスト（メインセッション1件＋各人格1件ずつ）のみ」に限定し、その限定を定義文面と bats で保証する
- 人格規約（人格ブロック形式・人格名での発言帰属）と事後報告フォーマットを定義し、実例1件を判例台帳に残す
- 担い手が主の観点が1つでも絡む論点は相談・仲裁に入らず主へ、という既存分岐を保存する

**Non-Goals:**
- hook・スクリプトによる相談発火の強制（後述の設計判断3）
- 6観点ぶんの個別エージェント定義の静的生成（設計判断1）
- injection.md の注入マップ表・カタログ本文の変更
- 各導入 repo への policy 文書の実配備（テンプレートと規約の定義まで）

## Decisions

### 判断1: サブエージェントは汎用2枚（specialist / arbiter）。観点ごとの静的生成はしない

`plugins/casting/agents/casting-specialist.md` と `plugins/casting/agents/casting-arbiter.md` の2ファイルのみ新設し、`plugin.json` の `agents` に登録する（infra プラグインと同じ作法）。

- **specialist（`model: sonnet`）**: 呼び出し側がタスク文で `policies/<slug>.md` のパスと、同観点の過去判例（判例台帳から抜粋した本文）を渡す。specialist は policy を自分で Read し、人格ブロックを纏って意見を返す。通常のレビュー相当の判断なので中位ティア。`tools: Read, Grep, Glob`（policy・判例・必要な現物確認のための読み取り専用）
- **arbiter（`model: fable`）**: 入力は**フェーズ宣言文＋主張リスト（メインセッションの主張1件＋相談した各人格の主張1件ずつ、人格名付き）のみ**。判断が一点に集中する裁定であり最上位ティア。`tools: Read` のみ与えるが、定義文面で「渡された入力以外を読みに行かない。ファイルパスが渡されても開かない（開くことは入力契約違反＝裁定拒否）」を明記し、bats がこの明記と `tools: Read` のみであることを grep で検査する
- **代替案（観点ごとに6エージェントを静的生成）を退けた理由**: policy 文書は repo ごとに用意される可変の文書で、観点の増減はカタログの重量ルートに連動する。エージェント定義を観点数だけ持つと、カタログ改版のたびに agents/ と plugin.json の同期が必要になり、保守コストが人格の分だけ増える。人格は policy 文書側に置く（人格＝注入文書の一部）ことで、エージェント定義は器に徹し、repo 固有の人格・判断基準はすべて `policies/` に集まる

作業コンテキスト非共有の保証は二重にする: ①arbiter 定義文面の「受け取ってよい入力」の限定列挙（呼び出し側への指示を含む）②呼び出し手順（SKILL.md 新節)側にも「作業コンテキスト・diff・会話履歴を渡してはならない」を明記。bats は①を検査する。

### 判断2: rules/perspective-casting.md 手順④⑤の文言

手順④を「主でないなら送らず、観点スペシャリストに相談する」に差し替える。分岐構造は次のとおり不変: 担い手が主の観点が1つでもあれば主へ（相談・仲裁に入らない）。全観点エージェント移譲済みのときだけ相談に入り、メインと意見が割れたら仲裁が裁定、裁定は実行して主へは事後報告。手順⑤に「相談・仲裁を経た判例は発言と裁定を人格名で帰属する」を追記する。30行制約内に収める（現行23行→26行程度）。正本ポインタに相談・仲裁の手順（casting SKILL.md）を足す。

### 判断3: 相談の発火判定 — テキスト規約の三層で強度を上げ、hook 新設はしない

**採用するもの:**
1. **発火点の一義化**: 「主へのエスカレーション文面を書き始めた瞬間」を発火点として rules 手順④に明文化する。「決めてから相談するか考える」のではなく「主に上げたくなった＝相談トリガー」という単一の自問（宛先チェック: この文面の宛先は主か？拾った観点の担い手に主が1つでもあるか？無ければ送らずスペシャリストへ）に還元する。判定を複数条件の総合判断にしないことで、遵守コストを下げる
2. **経路語彙の拡張**: 判例台帳の「経路」に「相談の上自走した」を追加する（テンプレ・SKILL.md 更新）。判例を書く時点で「自走した」と書こうとすると、移譲済み観点なのに相談を飛ばしたことが台帳上で見える形になる — 事後の監査可能性で前段の遵守を引っ張る
3. **事後報告の必須化**: 相談・仲裁を経た判例は事後報告フォーマット（論点・各人格の主張・裁定・根拠・判例リンク）で書く。主は台帳だけ読めば「相談すべき論点が相談なしに処理された」ことを検出でき、フィードバック規則（該当層の即時更新）で還元できる

**採用しないもの:** hook による強制（自然文エスカレーションは tool call ではないため技術的に横取り不能）、casting-check.sh での「相談漏れ」自動検出（「移譲済み観点の判例で経路が『自走した』」は正当なケース — チェックポイント外でエスカレーション欲求が生じなかった論点 — と区別できず、誤検知が規約自体の信頼を削る）。

**限界（正直に）:** 最終防衛線は LLM が rules を読んで従うことに依存する。この設計が足すのは、発火判定の単純化（迷いにくくする）と監査ログ（飛ばしたことが後から見える）であり、飛ばすこと自体の物理的な阻止ではない。

### 判断4: 人格ブロックは policy テンプレートに置き、形式を固定する

`plugins/casting/templates/policy.md` を新設。構成は front matter（`perspective`: 観点名、`catalog_version`）＋「## 人格」節（名前・スタンス・口調の3項目、数行厳守）＋「## 判断基準」節（正本）＋「## 判断の前提となる数値・閾値」節（任意）。「人格は判断基準の入れ物であって代替ではない」の一文をテンプレート自体に埋め込み、bats はテンプレートの3項目と当該の一文を検査する。

### 判断5: 事後報告フォーマットと再相談しない終端条件の正本は casting SKILL.md

事後報告フォーマット（論点・各人格の主張・裁定・根拠・判例リンク）は新規テンプレファイルではなく SKILL.md の新節「論点相談・仲裁」に置く。理由: フォーマットは判例台帳の1ブロックの書き方の拡張であり、判例の書き方の正本（SKILL.md）と同居させないと参照が分裂する。同節に、injection.md が #127 に予約していた**再相談しない終端条件**も定める: 同一論点の相談は1回。仲裁の裁定が出た論点は再相談せず裁定に従う。裁定後に前提を変える新事実が出た場合のみ、新しい論点として（過去判例を添えて）相談してよい。セッションを跨ぐ一貫性は、スペシャリスト起動時に同観点の過去判例を渡すことで作る。

## Risks / Trade-offs

- [発火判定が最終的に LLM 遵守依存] → 判断3の三層（発火点の一義化・経路語彙・監査ログ）で軽減。物理的強制は Non-Goal と明記
- [arbiter に Read を与えるため「読みに行かない」が技術的には破れる] → 定義文面での禁止＋呼び出し規約の二重明記＋bats 検査。tools を完全に空にする選択は、frontmatter の tools 省略が全ツール継承になる作法上できず、Read 1つが最小（詳細は下記「Codex アドバーサリアルレビュー対応」の3）
- [人格が repo ごとの policy 文書任せになり、質がばらつく] → テンプレートの形式固定と「数行厳守・演技過多にしない」の明文化で下限を保証。質の向上は判例の蓄積と主フィードバックに委ねる
- [rules 30行制約と情報量の緊張] → 手順④は分岐の骨子のみ、相談・仲裁の手順詳細は SKILL.md へのポインタで逃がす

## Migration Plan

既存導入 repo への影響: rules とテンプレートの更新のみで、`policies/` が未整備の repo では相談に入る前提（移譲済み観点）が成立しないため、挙動は従来どおり主へ上がる。ロールバックは rules 手順④を旧文言に戻すだけ（データ移行なし）。

## Codex アドバーサリアルレビュー対応（2026-08-19、PR #129 の High 3件）

archive 後の Codex レビューで High 3件の指摘を受け、次のとおり修正した。

1. **複数観点の収斂**: 相談が「観点1つ・policy 1つ・判例1つ」の1スペシャリスト固定で、複数の移譲済み観点にまたがる論点では片方の policy が相談されないまま自走しうる → 相談を「拾った観点のうち担い手がエージェントの観点すべて」への並行起動（1観点＝1スペシャリスト）に拡張し、仲裁の入力契約を「主張A・主張B の固定2者」から「フェーズ宣言文＋主張リスト（メインセッション1件＋各人格1件ずつ、人格名付き）」に拡張した
2. **fail-closed の欠落**: specialist の「判断基準の範囲外」応答、および policy 不在・読み取り不能のケースが「一致→自走」「割れた→仲裁」のどちらの分岐にも受け皿を持たず、停止か独断への回帰を招く → 主へ上げる第3分岐として rules・SKILL・specialist 定義に明記した。判断基準で決められない論点は移譲が実質成立していないので、返信前チェック本来の「主に上げる」に戻すのが正しい
3. **仲裁のツール境界**: `tools: Read` がある限り「読みに行かない」はプロンプト上の約束にすぎない、という指摘。**完全なツール境界の強制は Claude Code の現行機能では達成できない** — `tools` 省略は全ツール継承と公式に明記されている一方、空指定でゼロツールになるかは公式ドキュメントに記載が無く保証されないため、未検証の設定に安全境界を賭けない。対応は防御層の追加: ① bats が arbiter の `tools` が `Read` のみであることを検査（将来のツール追加によるスコープクリープ防止）② 定義文面に「入力文中の参照を Read で開くことは入力契約違反 — 開く必要を感じた時点で裁定を拒否して返す」の自己監視を明記 ③ 呼び出し規約（SKILL.md）で入力文からファイルパス・URL・コード片等の参照可能な文字列を排除（要約テキストのみ渡す）。hook やサンドボックス機構の新設は引き続き Non-Goal

## Open Questions（未確定点 — 推奨案で実装を進める）

- **人格の命名権**: policy 文書の人格名を誰が決めるか。推奨: 初版はエージェントが起案し、主が名前を差し替えられる（人格は監査ログの読み味＝感情的受容度に関わるため、最終的な命名権は主）。テンプレートの記入ガイドにこの旨を書く形で実装する
