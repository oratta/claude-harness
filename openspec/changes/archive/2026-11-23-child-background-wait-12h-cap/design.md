# Design

## Context

動機は proposal.md を参照。調査対象 HEAD は `9505218f95b0e63af8f0851658238297c31d9d86`。手順書の「3. 通知を照合して待ち直す・取り消す」は、元作業が未完了で維持対象なら次のタイマーを置くが、経過時間の条件を持たない。

親の既存決定は `plugins/dev-workflow/changes/1556.md` にあり、停止済み子の声かけ期限を12時間（既定43200秒）にそろえている。今回はその値にそろえるという主の決定を適用する。親のコードや設定を実行中の子へ流用する変更は行わない。

## Goals / Non-Goals

**Goals:** 同じ元作業を待つ間の維持の基点を固定し、費用比較に対応する上限を再設置条件で守る。上限後も作業とその完了通知を回収できる状態を保つ。

**Non-Goals:** 元作業の実行時間上限、新しい停止状態、親への作業移管、45分タイマーの雛形や TTL 判定の変更、`SKILL.md` の変更、実機の維持成功宣言。

## Decisions

### 基点を初回設置時刻に固定し、再設置の出口に上限を置く

手順2で最初のタイマーを置いた時刻を、元作業とタイマーのIDに加えて保持する。手順3で元作業の未完了・維持対象という既存条件を確認する際、初回設置から12時間未満という条件を加える。ちょうど12時間に達した通知でも次を置かない。遅延して12時間を超えた通知でも同じ扱いとする。

再設置時刻を基点にすると上限が延び続けるため採らない。同じ元作業の待ち直しでは、入力や TTL の再確認によっても初回時刻を更新しない。元作業の完了と通知が同時なら既存どおり元作業を先に回収する。

### 上限で止めるのは維持だけとする

12時間以降は次のタイマーを置かず、元作業と実行IDを保持したまま完了通知を待つ。キャッシュが切れたあとに通知が届いたら、一度の書き直しを受け入れ、既存の結果処理へ戻る。上限を元作業の timeout・キャンセル・工程完了・子セッションの終了と解釈しない。一律の再起動は元作業を失うため採らない。

### 費用比較を新しいコメントで更新する

旧比較 https://github.com/oratta/claude-harness/issues/1743#issuecomment-7087935739 の記録済み単価を使い、新しいコメントから旧記録を参照する。追記は https://github.com/oratta/claude-harness/issues/1743#issuecomment-7089486648 。単価を調べ直す変更は含まない。

会話20万トークンで1h書込 $8 / MTok、hit $0.20 / MTok のとき、一度の書き直しは $1.60。45分ごとの維持を12時間で16回として、旧来の概算式 `(2k + 1) × 0.2 × hit` では約 $1.32 となる。上限到達時は再設置しないが、比較は既存の二回読み出しの数え方を用いた概算とする。24時間無上限の k=31・約 $2.52 は旧方針の比較として残し、新方針の維持費と混同しない。

上限で抑えるのは維持費であり、上限後にキャッシュが切れてから完了する場合には一度の書き直しが別途発生する。新規入力・出力、初回設置・取消・TTL確認などの工具往復、親の判断の呼び出しはこの旧会話部分の比較に含めない。総費用が常に $1.60 未満になる保証はしない。手順書末尾と `changes/1743.md` にも新しい結論と追記へのリンクを反映する。

## Risks / Trade-offs

- [上限後の cache miss] → 主の決定として一度の書き直しを受け入れ、元作業を保持する。
- [タイマー再設置で基点を更新して上限が消える] → 初回時刻の保持と更新禁止、12時間未満・到達時・超過時の条件を契約テストで検査する。
- [維持費と総費用の混同] → 約 $1.32 は旧会話部分の概算と明記し、追加費用と上限後の書き直しを区別する。マージ後の実機観測は別に残す。
- [手順の文言検査では実時間の成功を証明できない] → Bats は手順と既存タイマー雛形の検証とし、実機合格を宣言しない。

## Migration Plan

R1承認後のimplement段で手順・契約テスト・変更記録を更新する。新しい状態ファイルや設定の移行は不要。起動時・常時注入の予算テストを実行し、予算値は変更しない。戻す場合は本変更の上限と費用記述の差分を戻す。実行中の元作業の停止や破棄は行わない。
