## Context

pr-review-gate 手順 3 のリスク宣言は、表（「リスクなし」／「主のリスク許容が必要」の条件と後続）と、2 つのコメント雛形でできている。「主のリスク許容が必要」なら手順 6 で `needs-approval` を付け、auto-merge workflow はこのラベルが付いた PR をマージしない。auto-merge workflow と手順 5 が機械照合するのは、コメント 1 行目の見出し（`## リスク宣言`）と 2 行目の `対象 HEAD: <40 桁フル SHA>` だけで、宣言本文の語句は照合していない（`plugins/dev-workflow/templates/auto-merge/.github/workflows/auto-merge.yml`、`plugins/dev-workflow/tests/pr-review-gate-skill.bats` を grep して確認）。

## Goals / Non-Goals

**Goals:**
- 資格情報・安全ゲートの弱体化・エージェント権限の拡張に当たる PR が「リスクなし」で通らず、主の許容待ちになる
- 3 観点それぞれの線引きを手順書に書き、宣言者が迷わず判定できる

**Non-Goals:**
- auto-merge workflow に宣言本文の語句照合を足すこと（本文の判定は宣言者の positive affirmation に任せる現行方式を変えない）
- 聖域パスの定義（SACRED）や worker.md の事前分類（モデル選択用の 4 分類）を変えること
- 既存 4 観点の定義を変えること

## Decisions

1. **新観点は既存の「主のリスク許容が必要」の条件に並べ、別の宣言種別を作らない。** 宣言が 3 種類になると手順 5 の合格表・手順 6 の復帰表・auto-merge の説明をすべて直すことになる。issue の要求も「既存の『リスクあり』と同じ経路」なので、表の条件列に 3 観点を足すだけにする。
2. **「リスクなし」の定型文は 7 観点を列挙し直す。** 形は `リスクなし — この変更でプロダクトのユーザーに及ぶ影響・データ喪失・課金/法務・外部公開面の変化・資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張はいずれも無い。` とする。行頭 `リスクなし — ` と見出し・`対象 HEAD:` 行は変えない。定型文を観点ごとの 7 行チェックリストにする案もあるが、宣言が長くなり、既存の宣言コメントとの見た目の連続性が切れるので採らない。
3. **3 観点の線引きを表のすぐ下に定義として書く。**
   - 資格情報: ID・パスワード・API の鍵・トークンを取得・保管・利用・受け渡しするコードや設定を足す・変える。秘密の値そのものを含まない文書上の言及だけなら当たらない
   - 安全ゲートの弱体化: レビュー必須・投稿前チェック（hook）・auto-merge の判定条件・permission の deny・ブランチ保護など、止め具を外す・条件を緩める・迂回路を作る変更。止め具を増やす・厳しくする変更は当たらない
   - エージェント権限の拡張: permission の allow の追加、新しい外部サービス・MCP・ツールの利用、新しい書き込み先（リポ・ラベル・チャネル・ファイルの置き場）など、エージェントにできることを増やす変更
   迷ったら「許容が必要」側に倒す既存の原則をそのまま適用する。
4. **許容が必要な場合の雛形に `- 該当する観点: <7 観点のうち当たったもの>` の行を足す。** 主が「なぜ自分に来たか」を 1 行で読めるようにする。形骸化監査で新観点による保留を数えられるようにする目的もある。

## Risks / Trade-offs

- [harness のように行動ルールが製品のリポでは、新観点に当たる PR が増え、主への確認が増える] → 「止め具を増やす・厳しくする変更は当たらない」と明記して対象を絞る。それでも増える分は issue の備考どおり「主が読む材料が増えるだけ」として受け入れる
- [宣言本文は機械照合されないので、宣言者が新観点を見落とせば「リスクなし」で通る] → 現行 4 観点と同じ前提（positive affirmation と形骸化監査のサンプリング）で扱う。機械照合は Non-Goals
