# Design

## Context

動機は proposal.md を参照。基準 HEAD は `9a459b51d916ad24d68b1854512b0e62becb619c`。#1323（PR #1376）後の `decide_relaunch` は、一意に見つかった子のトランスクリプトの最後の assistant の時刻だけを読み、60 分以上なら起動し直す。古い `EPIC_DISPATCH_RELAUNCH_MIN_TOKENS` は廃止されている。

`resolve_stopped` は状態の記録の `worktree` を使って判定し、既存の `deliver_reply` に起動し直すかを渡す。送れたあとにエピックに判断の記録を残す。子の再開に要る途中経過は停止の記録から復元する既存の `/develop` の起動経路に委ねる。

## Goals / Non-Goals

- 既存の時間条件に独立した会話量条件を加え、親が読む子の表と自動判定を揃える。
- トランスクリプトの選択・起動部品・停止の記録からの再開・送ったあとに記録する順序を維持する。
- #1324 の子への声かけ・親の待ち直しと #1085 の CI 見張り再開には手を出さない。親の表、アイドル時のコンパクト、通常の自動コンパクトも変更しない。

## Decisions

### 会話量と時間を独立した起動し直しの条件にする

子の表は上から、端末が無い → 起動し直す、会話量が新閾値以上 → 起動し直す、60 分未満 → そのまま送る、60 分以上 → 起動し直す、とする。会話量の行に `EPIC_DISPATCH_RELAUNCH_FORCE_TOKENS` と既定値 `150000` を書く。時間だけで起動し直す条件は #1323 のまま残す。

自動判定は、一意のトランスクリプトから確認できた `context_tokens >= FORCE_TOKENS` OR `経過秒 >= IDLE_SEC` である。`compact_boundary` を除外条件にしない。compact の後に有効な usage があればその最新値を使い、compact 前のピーク値を最大値として使わない。AND に戻す案は、返事が早く届いた大きい会話を救えず、#1323 の時間だけの条件も弱めるので採らない。

### 既定値は #1046 の 150000 に揃える

[完了した再集計](https://github.com/oratta/claude-harness/issues/1046#issuecomment-6358891346) は、待っている間の自動コンパクトを子・親とも 120000、起動し直す境目を 60 分・150000 のままと結論した。子の起動し直しの平均費用は入力換算 270k、従来の費用比較の境目は 135k で、150k との差を標本の揺れの範囲としている。

#1150 本文の 200000 前後は検討用の値であり、#1046 に揃えるという指示と完了済みの結論を優先して 150000 を採用する。120000 は自動コンパクト用の閾値なので転用しない。#1046 はキャッシュ有効中の再開を比較した実験ではなく、新条件の最適値を実証してはいない。ここでの採用は、大きい会話を繰り返し読む使用量と判断品質に対処するための初期設定であり、後の計測で変更できる。

新変数は既存の `EPIC_DISPATCH_RELAUNCH_IDLE_SEC` と同じく未設定時だけ既定を使い、数字だけの非負整数を受け付ける。0 なら計測できた会話量はすべて条件を満たす。空・負数・単位付きの値は、有効な `--resolve` があるとき待つ前に変数名と使い方を出して exit 1。旧 `EPIC_DISPATCH_RELAUNCH_MIN_TOKENS` は引き続き無視し、検査もしない。

### 既存の会話量の測り方と不明時の扱いを使う

子の状態の記録の `worktree` と既存の `transcript_dir` で、`${CLAUDE_PROJECTS_DIR:-${CLAUDE_CONFIG_DIR:-~/.claude}/projects}` 直下の対応ディレクトリの `*.jsonl` を探す。ちょうど 1 本のときだけ使い、0 本・複数・ファイルを読めない場合は自動で起動し直す根拠にしない。端末が無い場合の起動し直しは既存の送信処理に残る。

会話量は `subagent-context.sh --file <file>` の JSON の `context_tokens` を使う。値は最後の有効な assistant usage の `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` で、出力トークンや累計ではない。末尾の API エラーや usage が全部 0 の記録を飛ばす既存の測り方もそのまま使う。このスクリプトの exit 0 と 2 はどちらも計測成功として JSON の値で比較する。`over_cap` と exit 2 は `>` の条件であり、新条件の `>=` の代わりにはできない。サブエージェント用の `DEV_WORKFLOW_CONTEXT_CAP` や停止確認の設定を、新しい閾値として流用しない。

有効な usage を読めなければ会話量の条件だけを不明とし、時刻が分かっていて 60 分以上なら起動し直す。時刻が読めなくても会話量が新閾値以上なら起動し直す。どちらも真と確認できなければそのまま送る。両方の計測の成功を必須にすると、会話量計測の障害で #1323 の時間条件まで失われるので採らない。計測スクリプトを改修せず、呼び出し側で終了コードと JSON を扱う。

## Verification

`tests/epic-dispatch.bats` の既存 fixture を使い、60 分未満で N が 149999 / 150000 / 150001 の境界、compact 行を挟んだ有効 usage、input/cache_creation/cache_read の合計、末尾の API エラーを検証する。60 分以上・小さい N・usage 不明、時刻不明・大きい N、どちらも不明、ファイル 0 本・複数、閾値上書き・0・不正値・旧変数の無視も確かめる。時間閾値の既存テストは会話量を新閾値未満にし、時間条件だけで起動し直したと分かる形にする。

issue の受け入れ条件の `sent <child>` / `relaunched <child>` は、既存の `deliver_reply` の結果に対応する。現行 `resolve_stopped` はこの出力を内部で受け、成功した子を待ち受けの出力から外すため、`wait` の stdout にこの行を新設しない。端末の作成・既存端末への送信・送信文（起動し直しなら `/develop #11` と返事）・送信後のエピックの記録を確かめ、結果が一致すると検証する。stdout と `stopped` / `unrecorded` 等の契約は維持する。

実装工程では対象を絞った `bats plugins/dev-workflow/tests/epic-dispatch.bats --filter 'wait --resolve relaunch:|reply-after-idle:'` を回す。全体テストは CI に任せる。仕様工程では `openspec validate relaunch-child-by-context-size --type change --strict` と差分検査だけを行い、実装の合格とは扱わない。

## Risks / Trade-offs

- キャッシュが有効な子でも起動し直しの費用と判断の復元が必要になる → #1150 の目的として受け入れ、閾値の根拠と集計の限りを残す。
- 計測できない大きい会話はそのまま送られうる → 既存の不明時の扱いを保ち、確認できた時間条件を妨げない。
- 起動し直しで CI の見張りが消える問題は別途残りうる → #1085 に委ね、ここで復旧処理を追加しない。

## Migration Plan

新変数の設定は不要。マージ後は既定 150000 で適用される。旧変数を復活させず、版を上げず `plugins/dev-workflow/changes/1150.md` に挙動・根拠・不明時の扱い・戻し方を記録する。戻す場合はこの変更の判定・表・テストの差分を戻し、#1323 の時間条件を残す。
