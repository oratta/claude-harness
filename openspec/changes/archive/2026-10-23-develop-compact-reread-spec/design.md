# Design

## Context

実装はマージ済みで、この change は仕様を後から書き起こすだけである（proposal.md の Why）。設計判断は #1217 のときに下されており、ここではその判断と理由を決定履歴として残す。

SessionStart(compact) の hook が呼ばれる時点では、今回のコンパクトの `compact_boundary` も `invoked_skills` もまだ会話記録（stdin の `transcript_path` の jsonl）に書かれていない（#1217 の実機確認）。書かれているのはコンパクト前の記録だけである。

## Goals / Non-Goals

**Goals:**
- マージ済みの hook の振る舞いを、実装とテストに食い違わない要件と Scenario にする
- 待っている間の自動コンパクトの下限 120,000 を、読み直しの費用を入れても変えなかった根拠を、既存の要件の「根拠と限り」に足す

**Non-Goals:**
- 実装・テスト・手順書の変更（今の実装が満たさない MUST は書かない）
- 読み直しの費用を両方足した想定での下限の計算し直し（#1264 で行う）

## Decisions

### 「develop を呼んでいた」をコンパクト前の 3 種類の記録で判定する

assistant の Skill 呼び出し（`input.skill` が `dev-workflow:develop`）、user の発言の `<command-name>/dev-workflow:develop</command-name>`、前のコンパクトのあとの `invoked_skills` の記録のどれか 1 つで「呼んでいた」とみなす。
- 代わりの案: 今回のコンパクトの `invoked_skills` を見る。hook の時点ではまだ書かれていないので使えない
- 代わりの案: 行に `develop` の文字列があれば数える。文中で名前に触れただけの会話や、`codex-develop` などの別のスキルで誤って差し込むので採らない

### 名前空間の無い `develop` は数えない

プラグインのコマンドは `/develop` と打っても `/dev-workflow:develop` と記録されるので、名前空間の無い名前で拾えるのは利用者の別のスキルやコマンドだけになる。

### 判定できないときは何も出さない（fail-open）

stdin が JSON でない・会話記録が無い・`CLAUDE_PLUGIN_ROOT` が空・`python3` が無いときは何も出さず、常に exit 0 で終わる。差し込みが漏れても、従来どおり読み直さずに進むだけで、セッションの開始を止めるより被害が小さい。形の違う行は 1 行ずつ飛ばし、走査を続ける（1 行の想定外の形で、そのあとにある本物の呼び出しを見落とさないため）。

### 差し込む文は 2 つの要素を持つ

SKILL.md の絶対パスを示して Read で読み直させる（1 回では上限に当たるので offset と limit で 2 回に分ける）ことと、エピックの親か子かを記録先の issue から確かめ直すこと。親か子かで従う節が違い、要約の上の自己認識が外れていると別の手順に進むため。

### 下限 120,000 は変えない

読み直しは 1 回約 39k トークンで、#1039 の集計の控えめの想定で足した 40k（issue やコメントの読み直しの分）とは別にかかる。両方を足した想定は計算し直していない（#1264）。控えめの想定でも 120,000 は最良と差が小さく、既定の 200,000 より子で 8.1M 安いので値は変えない（計算: https://github.com/oratta/claude-harness/issues/1217#issuecomment-6359110216 ）。

## Risks / Trade-offs

- [Claude Code が会話記録の形を変えると判定が外れる] → fail-open なので外れても差し込まないだけ。テストの fixture は #1217 の実機の形に合わせてある
- [両方の読み直しを足した想定で 120,000 が最良でなくなる] → #1264 で計算し直し、そこで値を見直す
