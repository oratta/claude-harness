## MODIFIED Requirements

### Requirement: リスク宣言は 7 観点で判定し、新 3 観点も主のリスク許容待ちに流す

pr-review-gate SKILL.md 手順 3 のリスク宣言は、プロダクトのユーザーへの影響・データ喪失・課金/法務・外部公開面の変化の 4 観点に、資格情報・安全ゲートの弱体化・エージェント権限の拡張の 3 観点を加えた 7 観点で判定しなければならない（SHALL）。新 3 観点それぞれについて、何が当たり何が当たらないかの線引きを手順 3 に書かなければならない（SHALL）。7 観点のどれか 1 つでも当たる PR は「主のリスク許容が必要」と宣言しなければならない（MUST）。宣言が `論点あり — ` の行を持つときは、手順 6 で `needs-approval` を付けて主の許容を待たなければならない（MUST）。宣言が `論点なし — ` の行を持つときは、手順 6 で主に聞く前に、要件「論点なしのリスク宣言は、決める役の確認で合格処理に進める」の確認に回し、同じ HEAD の `論点なしの確認: 通す` の記録を得たら手順 6 に入らず手順 4・5 へ進む（MUST）。確認で `論点あり` か `判断できない` になったときと、確認に回せない経路（要件「論点なしのリスク宣言は、決める役の確認で合格処理に進める」の従来経路の一括の G）では、手順 6 で `needs-approval` を付けて主の許容を待つ（MUST）。ただし、要件「issue が目的として書いた効果は issue で承認済みとして主に聞き直さない」の条件をすべて満たす宣言は、論点の有無によらず手順 6 に入らず手順 4・5 へ進む（SHALL）。「リスクなし」の定型文は 7 観点すべてが無いことを述べる文でなければならない（SHALL）。宣言コメントの 1 行目 `## リスク宣言` と 2 行目 `対象 HEAD: <40 桁フル SHA>` の規約、および行頭 `リスクなし — ` / `主のリスク許容が必要。` の文言は変えてはならない（MUST NOT）。

#### Scenario: 「リスクなし」の定型文が 7 観点を述べる

- **WHEN** SKILL.md 手順 3 の「リスクなし」のコメント雛形を読む
- **THEN** `リスクなし — ` で始まる行に、プロダクトのユーザーに及ぶ影響・データ喪失・課金/法務・外部公開面の変化・資格情報・安全ゲートの弱体化・エージェント権限の拡張の 7 つがすべて現れ、それらが「いずれも無い」と述べている

#### Scenario: 新 3 観点のどれかに当たると needs-approval の経路に入る

- **WHEN** 資格情報・安全ゲートの弱体化・エージェント権限の拡張のどれかに当たる PR で、「issue で承認済み」の条件を満たさないまま手順 3 を回す
- **THEN** 手順 3 の表により「主のリスク許容が必要」となり、論点ありなら後続が手順 6（`agent-review:passed` を付けず `needs-approval` を付ける）、論点なしなら手順 6 の前に決める役の確認に回り、`論点なしの確認: 通す` を得れば手順 4・5、得なければ手順 6 であることが手順書に明記されている

#### Scenario: 新 3 観点の線引きが書かれている

- **WHEN** SKILL.md 手順 3 を読む
- **THEN** 資格情報（ID・パスワード・API の鍵・トークンの取得・保管・利用を変えるコード・設定・エージェントへの行動指示）、安全ゲートの弱体化（止め具を外す・緩める変更。厳しくする変更は当たらない）、エージェント権限の拡張（新しい権限・外部サービス・書き込み先）の定義が書かれている

#### Scenario: 許容が必要な場合の雛形が当たった観点を書かせる

- **WHEN** SKILL.md 手順 3 の「主のリスク許容が必要」の雛形を読む
- **THEN** 当たった観点を書く行（`該当する観点:`）がある

#### Scenario: 宣言の 1 行目・2 行目の規約が変わらない

- **WHEN** 変更後の SKILL.md 手順 3 の 2 つの雛形を読み、`plugins/dev-workflow/tests/pr-review-gate-skill.bats` を実行する
- **THEN** どちらの雛形も 1 行目が `## リスク宣言`、2 行目が `対象 HEAD: <$HEAD_SHA 40桁フル>` のままで、テストが exit 0 で終わる

### Requirement: 主のリスク許容が必要な宣言は、論点の有無で書き分け、リスクを作文しない
pr-review-gate の `declarations.md` の手順 3 は、「主のリスク許容が必要」の雛形の、`主のリスク許容が必要。` のあとの空行に続く行を次の 2 つの形のどちらか 1 つにしなければならない（MUST）。論点なしの行は主の OK を求める文にしてはならない（MUST NOT。論点なしの宣言は要件「論点なしのリスク宣言は、決める役の確認で合格処理に進める」の確認で通り、主に上がるのは確認で通らなかったときだけ）。

- `論点なし — 分類に当たったが、この変更を入れることで新たに生じるリスクは無い。決める役の確認で通す。`: 7 観点の分類に当たっただけで、この変更を入れることで新たに生じるリスク（他の案や見送った場合には無いもの）が無いとき。リスク内容を作文しない
- `論点あり — この変更を入れることで新たに生じるリスク: <誰に何が起きうるか>`: 新たに生じるリスクがあるとき

#### Scenario: 分類に当たっただけの変更
- **WHEN** 資格情報の分類に当たるが、変更を入れることで新たに生じるリスクが無い PR の宣言を書く
- **THEN** 宣言は `主のリスク許容が必要。` の行のあとに `論点なし — ` の行を持ち、リスク内容を書かず、「決まりで主の OK が要る」の文を持たない

## ADDED Requirements

### Requirement: 論点なしのリスク宣言は、決める役の確認で合格処理に進める

`declarations.md` の手順 3 と `stages/hold.md` の手順 6 は、`論点なし — ` の行を持つ「主のリスク許容が必要」の宣言を、主の許容を待つ前に決める役（`dev-workflow:decider`、`model: opus` を明示）に確認させ、同じ HEAD の `論点なしの確認: 通す` の記録を得たら手順 4・5 に進める経路を書かなければならない（MUST）。確認者はエピックの子でも子でないセッションでも決める役とし、親（エピック）が確認する経路は置かない（MUST NOT）。`論点あり — ` の行を持つ宣言は、この経路で通してはならない（MUST NOT）。この経路はマージの経路を変えない。

#### Scenario: エピックの子でも決める役が確認する

- **WHEN** エピックの子（`scripts/epic-dispatch.sh route` が `nested`）の develop の G が、`論点なし — ` の行を持つ宣言を書く
- **THEN** G は停止の記録を残さず、`needs-approval` を付けずに `needs-no-point-check` で子の本体に返し、子の本体が決める役を起こす。親は確認に関わらない

#### Scenario: develop の G は本体に返す

- **WHEN** develop の G が `論点なし — ` の行を持つ宣言を投稿する
- **THEN** G は `needs-approval` を付けず、Status `needs-no-point-check`・`次の段: 合格処理` と、宣言の URL・対象 HEAD・該当する観点・変更ファイルを返す

#### Scenario: 論点ありの宣言は主に上がる

- **WHEN** 宣言が `論点あり — ` の行を持つ
- **THEN** この経路は使われず、手順 6 で主の許容を待つ

#### Scenario: 確認で論点ありになったら書き直して主に上げる

- **WHEN** 決める役が `判定: 論点あり` を返す
- **THEN** G は宣言を `論点あり — ` の形で投稿し直し、手順 6 で主の許容を待つ

#### Scenario: 聖域に触れた PR のマージは人間に残る

- **WHEN** 論点なしの確認で合格した PR が聖域のパスに触れている
- **THEN** マージは `auto-merge.yml` のパスによる判定のまま `human-merge` で人間のマージに回る。例外は、エピックの子で親が既存の `parent-merge-approved` の経路の条件と `主の委任: 論点なしの止まり` の委任を確かめて印を付けたときだけ（dev-workflow-develop の要件「親は論点なしの止まりの委任で、マージ待ちの子の PR に判断の印を付ける」）。auto-merge 未配備のリポジトリではマージは今どおり主の操作

### Requirement: 論点なしの確認を起こす役を、ゲートの回り方で分ける

`stages/hold.md` は、論点なしの確認を起こす役を次のとおり書かなければならない（MUST）。develop の G は判定役を起こせないので、宣言を投稿し、`needs-approval` を付けずに Status `needs-no-point-check`・`次の段: 合格処理` で、宣言の URL・対象 HEAD・該当する観点・変更ファイルを返す（本体の動きは dev-workflow-develop の要件「G の needs-no-point-check を受けた本体の動き」）。develop の外のゲートは自分で決める役を起こす。従来経路の一括の G（手順 1〜5 を 1 体で回す G）は確認に回さず、手順 6 で主に聞く。

#### Scenario: develop の外のゲートは自分で起こす

- **WHEN** develop の外のメインセッションがゲートを回し、宣言が `論点なし — ` の行を持つ
- **THEN** そのセッションが決める役を起こし、記録を投稿してから手順 4・5 か手順 6 へ進む

#### Scenario: 従来経路の一括の G は主に聞く

- **WHEN** 従来経路の一括の G が `論点なし — ` の行を持つ宣言を書く
- **THEN** 確認に回さず、手順 6 で `needs-approval` を付けて主の許容を待つ

### Requirement: 論点なしの確認は宣言と差分だけで判定し、結果で後続を分ける

決める役には宣言の本文と PR の差分だけを渡し（会話の経緯や G の判断の理由は渡さない）、出力を 1 行目 `判定: 論点なし`・`判定: 論点あり`・`判定: 判断できない` のどれかと 2 行目 `理由: <1 行>` にしなければならない（MUST）。後続は、`論点なしの確認: 通す` なら手順 4・5、`論点あり` なら G が宣言を `論点あり — ` の形で投稿し直して手順 6、`判断できない` なら宣言を変えずに手順 6 とする（MUST）。

#### Scenario: 判断できないときは主に聞く

- **WHEN** 決める役が `判定: 判断できない` を返す
- **THEN** 宣言は変えず、G は手順 6 で `needs-approval` を付けて主の許容を待つ

### Requirement: 論点なしの確認の記録を PR に残す

決める役の判定は、宣言コメントへの追記ではなく、PR の別のコメントとして記録しなければならない（MUST）。develop では本体が、develop の外ではゲートを回すセッションが投稿する。本文は次の形にする（MUST）。

```
論点なしの確認: 通す|論点あり|判断できない
対象 HEAD: <40 桁フル SHA>
宣言: <宣言コメントの URL>
確認者: dev-workflow:decider（<エージェント名>）
根拠: <決める役の理由の 1 行>
```

記録の 1 行目は `主の回答:` で始まらないので、手順 3-c はこの記録を主の直接の回答として引き継ぎの元にしてはならない（MUST NOT）。

#### Scenario: 通した記録が残る

- **WHEN** 決める役が `判定: 論点なし` を返す
- **THEN** PR に 1 行目 `論点なしの確認: 通す` で、`対象 HEAD:`・`宣言:`・`確認者: dev-workflow:decider（…）`・`根拠:` の行を持つコメントが投稿される

#### Scenario: 共有枠が depleted のとき

- **WHEN** `SHARED_BUDGET_MODE=depleted` で論点なしの確認に回る
- **THEN** 決める役を起こさず、1 行目 `論点なしの確認: 判断できない` の記録を投稿し、G は手順 6 で主に聞く

### Requirement: 合格条件は同じ HEAD の論点なしの確認を許容済みとして扱い、引き継がない

`stages/pass.md` の手順 5 の合格条件の表は、「主のリスク許容が必要」＋ `論点なし — ` の行 ＋ 同じ HEAD・同じ宣言の URL の `論点なしの確認: 通す` の記録、を許容済みとして扱わなければならない（MUST）。HEAD が動いたら、手順 3-c はこの記録を引き継ぎの元にしてはならず（MUST NOT）、新しい HEAD の宣言で確認を取り直さなければならない（MUST）。

#### Scenario: HEAD が動いたら確認を取り直す

- **WHEN** `論点なしの確認: 通す` の記録のあとに HEAD が動く
- **THEN** 手順 3-c はこの記録を引き継ぎの元にせず、新しい HEAD の宣言で確認を取り直す

#### Scenario: bats で経路と記録を確かめる

- **WHEN** `bats plugins/dev-workflow/tests/` を実行する
- **THEN** exit 0 で、`declarations.md`・`stages/hold.md`・`stages/pass.md` に論点なしの経路（確認者が決める役だけであること・Status `needs-no-point-check` と返す欄・記録の書式・1 行目が `主の回答:` でないこと・論点ありは主に上がること・引き継がないこと）が書かれていることを確かめるテストがある

### Requirement: 論点なしの確認の経路の守備範囲

論点なしの確認の経路（この capability の、要件名に「論点なしの確認」「論点なしのリスク宣言」を含む要件）は、次の守備範囲で読まなければならない（MUST）。①入力の出どころは、G が投稿した宣言コメント（`## リスク宣言` で始まる、投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` のもの）、PR の差分、本体かゲートのセッションが投稿した `論点なしの確認:` の記録、PR の今の HEAD。G は協力的だが、論点ありを論点なしと書き誤る前提で扱う ②拾いたい誤りは、論点ありの宣言をこの経路で通すこと、決める役の確認を経ずに合格処理に進むこと、別の HEAD か別の宣言への記録で合格させること、記録を主の回答として引き継ぐこと ③④は要件「論点なしの確認の経路で通ってよい入力と完了条件」に置く。

#### Scenario: 別の HEAD の記録では合格しない

- **WHEN** `論点なしの確認: 通す` の記録の `対象 HEAD:` が PR の今の HEAD と違う
- **THEN** 合格条件の表はその記録を許容済みとして扱わず、確認を取り直す

### Requirement: 論点なしの確認の経路で通ってよい入力と完了条件

論点なしの確認の経路の守備範囲は、次も含めて読まなければならない（MUST）。③通ってよい入力は、決める役が論点なしと判定した宣言の、同じ HEAD・同じ宣言の URL の記録。決める役の判定が主の判断とずれることは、この経路では止めない（主は PR であとから見て止める） ④決める役の判定の誤りを機械で検知することと、穴を塞ぎ切ることは、この要件の完了条件にしない（MUST NOT）。

#### Scenario: 決める役が論点なしと判定した宣言は通る

- **WHEN** 同じ HEAD・同じ宣言の URL の `論点なしの確認: 通す` の記録がある
- **THEN** 合格条件の表は許容済みとして扱い、主の判断とのずれはこの経路では止めない
