## Context

`usage-probe.sh` は Anthropic の OAuth usage API を叩き、`parse()` が使用率だけを取り出して `~/.claude/.usage-snapshot`（schema 2）に書く。statusline は jq 1 回で snapshot を読む。Codex の行は `statusline-codex.py` のキャッシュを読み、`statusline.sh` の中で `リセットN回・最短あと…` を組み立てている。ダッシュボード（genetta-inc/flatmate#1654）は snapshot の `accounts.<id>.reset_grants` を読み、数え方（`paused` の束と `resets_left` が 0 の束を除く）は自分で行う。その形は issue #1115 のコメントで決まっている。

制約:
- 実機の応答をまだ誰も見ていない（調査 #1114 は Claude Code のバイナリ内の schema から形を読んだ）。形が合わないときは欄を出さないだけにする
- refresh_token は使わない（既存方針）。非 active アカウントは期限切れで取れないのが常態
- 429 の別枠を避けるため、呼び出し回数と User-Agent は今のまま

## Goals / Non-Goals

**Goals:** ダッシュボードが読む `reset_grants` 欄を契約どおりに書く。statusline の Claude の行に Codex と同じ見た目で出す。欄が無ければ出力が 1 バイトも変わらない。

**Non-Goals:** リセット権を使う操作（`reset_rate_limits`）を叩かない。トークンの更新をしない。ダッシュボード側の実装。`cedar_ember` の他の欄（`cooldown_until` など）を写さない。

## Decisions

### 1. 呼び出しは 1 回のまま、既定の URL にクエリを足す
`ENDPOINT` の既定を `…/api/oauth/usage?cedar_ember=1&skip_spend=1` にする。`USAGE_PROBE_ENDPOINT` で上書きできる点は変えない。代案は使用率用に今の URL、リセット権用に `cedar_ember=1` の 2 回呼ぶ形だが、スロットごとに呼び出しが倍になり 429 の連続を招きやすい。応答に使用率が残るかは未確認。使用率が全部欠ける応答は `parse()` が失敗扱いにして前回値を守るが、一部だけ残る応答は成功扱いで、欠けた使用率を `null` に更新してしまう。そこで検証条件を決める: テストで「`cedar_ember` だけの応答」（失敗扱い）と「使用率が一部欠ける応答」（従来どおり欠けた分が null）を固定し、マージ前の実機確認で、新しい URL の応答が従来の URL の応答と同じ使用率（`five_hour` / `seven_day` / `limits`）を保つことを確かめる。**保てなければ URL の切り替えを進めず、取得方式（2 回呼びなど）を作り直す**。この change では 2 回呼びは実装しない。

### 2. `parse()` が `reset_grants` を返し、欄の寿命は呼び出し側で決める
`parse()` の戻り値に `reset_grants`（欄を出さないときはキー自体を入れない）を足す。写すのは `resets_left`・`ends_at`・`paused` の 3 つだけで、値は変えない。束が dict でなければその束だけ捨てる。条件（`cedar_ember` が dict、`eligible` が true、`grants` が list）を満たさなければ欄を出さない。`grants` が元から空の配列なら `[]` を出すが、空でないのに写せる束（オブジェクト）が 1 つも無いときは確定した 0 回と区別するため欄を出さない（一部だけ不正なら写せる束だけ）。`FIELDS`（前回値を引き継ぐ対象）には入れず、引き継ぎは明示的に書く。

欄の寿命は次の 3 通り。
| スロットの状態 | `reset_grants` |
|---|---|
| 取得に成功し、パースできた | 応答から作る（条件を満たさなければ欄なし） |
| 取得を試みて失敗した（`<id>.status` が残り、パースできない） | 欄なし。前回の値を写し直さない |
| 取得を試みなかった（間隔内・オフ。`<id>.status` が無い） | 前回の snapshot の値をそのまま保つ（他の項目と同じ。`fetched_at` が古いまま残るので読み手は鮮度が分かる） |

**全件失敗の例外**: 既存の終了処理は、新しい値が 1 つも得られなければ snapshot を書かない（`usage-probe.sh` の `any_new` の判定と、組み立て python の `if not fresh`）。このままだと全スロットが失敗したとき、試みて失敗したスロットの前回の欄が残り、表の 2 行目と両立しない。そこで `fresh` が空のとき、既存 snapshot が読めて、試みて失敗した（`.status` がある）スロットに `reset_grants` があれば、その欄だけを除いた snapshot を書く（使用率・`fetched_at`・トップレベルのミラー・未試行スロットの欄は変えない）。除く欄が無い・既存 snapshot が無いときは従来どおり何も書かない。他スロットの取得が成功した場合は通常経路（成功したスロットがあるので snapshot は書かれる）、成功が 0 件なら例外経路（1 スロット構成の失敗もこちら）。

代案は「失敗も試みなしも欄なし」だが、probe は 3 時間に 1 回しか叩かず、1 スロットの取得のたびに他スロットの欄が消えてダッシュボードの表示が点滅する。「試みて失敗」だけを欄なしにするのは、ダッシュボードの契約（取得に失敗したとき前回の値を写し直さない）を守りつつ、これを避ける最小の切り分け。

### 3. statusline は snapshot の欄だけを読み、別のキャッシュを持たない
jq の 1 回の読み出しに、スロットごとの「残数」と「最短期限（epoch）」の 2 列を足す。jq の中で、`resets_left` が 0 より大きい整数で `paused` が true でない束だけを数え、残数は和、最短期限は `ends_at`（小数秒を落として epoch に直す。直せない値は期限なしの扱い）の最小値。有効な束が 1 つも無い場合: `grants` が空配列なら `リセット0回`、束があるのにすべて読めない・使えないなら残数 0 として扱わず区画を出さない（欠測を 0 回と扱わない、という Codex の規則と同じ）。欄が無い・配列でないときも区画を出さない。

代案は statusline 側にもキャッシュを持ち、取得に失敗したら前回の値に取得時刻を添える形（Codex と同じ）。採らない理由: ダッシュボードの契約（flatmate#1654 のコメントで決まった「取得に失敗したら欄を出さない」）が主の後のコメントで優先され、statusline が別のキャッシュで前回の値を出すと、同じ snapshot を読む 2 つの表示が食い違うため。採った契約は「snapshot に欄がある間だけ表示し、取得に失敗している間は区画を出さない」。issue 本文の「取得に失敗したら前回の値に取得時刻を添える」からの意図的なずれで、理由はこの記録に残す。

区画自体は取得時刻を持たない。非 active 行の経過時間は、セッション記録と突き合わせた後の値で、必ずしも snapshot の取得時刻ではない（取得時刻の無い active 行は経過時間そのものが付かない）。したがって「古い値にも経過時間が付いて読める」とは言えない。鮮度は、欄が成功した取得の後（または取得を試みていない間）にしか残らない契約と、期限を過ぎたときの `期限経過（更新待ち）` で担保する。区画専用の取得時刻の表示は足さない。

### 4. 書式は関数に切り出し、Codex の行も同じ関数を使う
`fmt_reset_credits <残数> <最短期限 epoch または 0>` が、表示文字列と色（DIM / YELLOW / RED）を返す。`期限不明`・`期限経過（更新待ち）`・`あとXdYh`・`あとXhYm` と、24 時間以内は赤・3 日以内は黄の規則は、いま Codex の行の中にある分をそのまま移す。Codex の行の出力は変えない（既存のテストで固める）。

### 5. 置き場所は、そのアカウントの最後の行の末尾
7d の行があるアカウントはその行、5h の行だけのアカウントはその行の末尾。経過時間（`ago`）のあとに ` │ ` 区切りで付ける（Codex の行と同じ並び）。1 スロット構成でも同じ。

### 6. 守備範囲
probe の抽出は型の崩れだけを拾い、値の意味の検証と数え方は読み手に委ねる。statusline の集計は期限欠落を残数付きで許容し、使える束が無ければ区画を出さない。未知の穴を塞ぎ切ることは完了条件にしない（各 spec の守備範囲の段落が正本）。

### 7. 単一スロットの出力契約
既存の「スロットが 1 つのときは現行と同一の出力」は、区画が出ない場合のバイト一致と、区画が出る場合の区画の追加だけが差、と書き分ける（MODIFIED）。名前列・active の目印を出さない制約は維持する。

## Risks / Trade-offs

- 実応答の形が想定とずれていると、欄が出ない（区画が出ないだけで他は止まらない）。使用率が応答から消える場合は 1 回呼びが使えなくなる → マージ前に実機で確認する
- 取得失敗で欄が消えるあいだ、statusline の区画も消える（上の Decision 3）
