# Design

## Context

`memory-tripwire.sh` は SessionStart（matcher `startup|clear|compact`）ごとに `session-tripwires.sh` から呼ばれ、メモリの索引の大きさと放置の日数を測って、閾値を超えたら `[memory]` の 1 行を出す。今はネットワークを使わず、ファイルも書かない。動機は proposal.md の Why。

## Goals / Non-Goals

**Goals:**

- `patches:` の issue が閉じたら、遅くとも閉じたあと 2 回目のセッションで `[memory]` が出る
- SessionStart の追加の待ち時間を、いつも 0.5 秒未満にする（GitHub への照会を待たない）
- `gh` が使えない環境でも、セッションの開始を止めず何も表示しない

**Non-Goals:**

- メモリを自動で消すこと（消すのは memory-refresh で主の承認を得てから）
- issue 以外（PR・他のホスティング）の直し先を読むこと
- 実ホームの既存のメモリに `patches:` を書き足すこと

## Decisions

### 1. `patches:` は `metadata:` の下とトップレベルの両方を読み、値は issue の URL 1 本

実在するメモリは Claude Code の書き方に合わせて `metadata:` の下に `type:` を置いている。書く側がどちらに置いても読めるようにする。読む費用は変わらない。値を 1 本に限るのは、1 件のメモリは 1 つの事実で、直し先も 1 つになるため。

### 2. 控えは全プロジェクト共通の 1 ファイルで、メモリディレクトリの外に置く

issue の状態はプロジェクトによらないので、URL ごとに 1 行（URL・確かめた日・状態・閉じ方）の共通ファイルにする。既定の場所は `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/.memory-patches-cache.tsv`（`.usage-sessions` などと同じ並び）。メモリディレクトリの中に置くと、memory-refresh の件数の照合（索引の項目行の数とファイル数の一致）が崩れ、「メモリを変えない」約束も破る。書き込みは一時ファイルに書いて `mv` で置き換え、同時に走る SessionStart が書きかけを読まないようにする。

### 3. 開始は控えだけを読み、確かめるのは裏のプロセスで行って時間で打ち切る

最初は、その日の最初のセッションで照会を待つ案を採った。しかし実測では `gh issue view` 1 回が 0.37〜0.73 秒かかり（gh の起動は 0.01〜0.03 秒で、残りは GitHub の認証付き API の応答待ち）、開始を 0.5 秒未満に収める期限を付けると照会のかなりの割合が時間切れになる。主の決定（https://github.com/oratta/claude-harness/pull/1655#issuecomment-6941172238 ）で、待たずに裏で確かめ、結果は次のセッションから使う案に替えた。閉じたことが分かるのは 1 セッション遅れ、閉じたあと 2 回目のセッションになることがある（受け入れ条件 AC2 もこの形に改めた）。

開始の処理は控えだけを読んで知らせる。当日に閉じたと控えた URL のほか（控えの無いもの・当日に開いているか「不明」と控えたもの・前の日の控え）は、標準入力・標準出力・標準エラーを閉じた裏のプロセスで確かめ直し、控えを書き換える。開いたままにすると、hook を走らせる側がパイプの終わりを待ち、開始が裏の確認の分だけ延びる。裏の確認が走っている間は控えのパスに `.lock` を付けた目印のディレクトリを置き、同時に 2 つ走らせない（打ち切りより 60 秒以上古い目印は、途中で止まった確認の残りとして取り直す）。控えを書く直前に控えを読み直し、確かめた URL の行だけを差し替える。裏の確認は `DEV_WORKFLOW_MEMORY_PATCHES_TIMEOUT`（既定 3 秒）で打ち切る。URL ごとの `gh issue view <URL> --json state,stateReason` を並べて走らせ、期限を過ぎたら自分が起こしたプロセスだけを止める（PID で止める。プロセス名では止めない）。macOS の標準の bash 3.2 でも動く書き方にする（`timeout` コマンドと `EPOCHREALTIME` に頼らない）。

### 4. 失敗はその日の「不明」として控え、次のセッションで確かめ直す

確かめられなかった URL はその日の日付で「不明」と書く。裏で確かめるので開始は待たず、次のセッションの裏の確認で確かめ直す。「不明」は閉じたとして扱わない。`gh` が無いときは控えを書かない（入れたあとすぐ確かめられるようにする）。

### 5. 通知は既存の `[memory]` の 1 行に足す

`[memory]` は条件の数によらず 1 行という約束がある。閉じた issue の件数と「ファイル名 ← URL」の組を条件の 1 つとして足し、`/memory-refresh` に誘う既存の結びをそのまま使う。閉じ方は通知では分けない。

### 6. memory-refresh は完了で閉じたものだけを削除に決め打ちする

完了（`COMPLETED`）で閉じた issue は直し先が直ったので削除する。`NOT_PLANNED`・`DUPLICATE` で閉じたものは直っていないことがあるので、メモリが補っていた動きが直ったかを確かめてから分類し、直っていなければ維持して `patches:` を新しい直し先に書き換えるか消す。

### 7. メモリを書くときの規則は `rules/plugin-editing.md` に置く

規則が効くべきなのはメモリを書く瞬間で、そのとき常に読まれているのは rules だけ。memory-refresh の SKILL.md は整理のときにしか読まれない。新しい rules のファイルを作るより、プラグインの直し方を決める既存の `plugin-editing.md` に 1 行足す方が常時読み込みの増え方が小さい。ハーネスに限らず、どのプラグインの指摘にも当てはまる書き方にする（「その部品を持つリポジトリ」）。この規則は全プロジェクトのセッションに効く。書き方の詳細（置き場所・値）の正本は memory-refresh の SKILL.md に置き、rules には要点だけを書く。

## Risks / Trade-offs

- [閉じたことの知らせが 1 セッション遅れる] → 裏で確かめる案を選んだ結果として受け入れる（主の決定）。閉じたあと 2 回目のセッションで出る
- [セッションのたびに `gh` を呼ぶ] → 呼ぶのは当日に閉じたと控えた URL 以外だけで、裏で走り開始を待たせない。`DEV_WORKFLOW_MEMORY_PATCHES_TIMEOUT=0` で止められる
- [裏の確認が途中で止まり目印が残る] → 打ち切りより 60 秒以上古い目印は取り直す
- [テストが実ホームの控えに書く] → テストは `DEV_WORKFLOW_MEMORY_PATCHES_CACHE` と偽の `gh` を必ず一時ディレクトリに向ける。既存のテストも同じ変数で切り離す
- [gh が別アカウントで、非公開リポジトリの issue を読めない] → 失敗として「不明」になり、何も出ない（誤って消す候補にはしない）

## Migration Plan

`patches:` を持つメモリが無ければ動きは変わらない。戻すときはこの差分を戻し、控えのファイルを消す（残っても読まれないだけで害は無い）。

実機の確かめ方: 一時ディレクトリの `CLAUDE_CONFIG_DIR` と `DEV_WORKFLOW_MEMORY_DIR` に、実際に閉じた issue の URL を `patches:` に書いたメモリと前の日の控えを置き、本物の `gh` で `session-tripwires.sh` を通し、1 回目で裏の確認が控えを書き、2 回目で `[memory]` が出ることを見る。実ホームには触らない。
