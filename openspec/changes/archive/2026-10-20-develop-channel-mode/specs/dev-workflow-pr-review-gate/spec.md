## MODIFIED Requirements

### Requirement: 保留処理の依頼文は新しいセッションでの再開を案内する

`skills/pr-review-gate/stages/hold.md` の手順 6（保留処理）の主への確認依頼は、依頼の中身（許容の可否・動作確認の 3 点セット・切り出しの確認）に加えて、develop の本体が止まる場合の返事の渡し方を、G の起動指示の実行モードで分けて含めなければならない（MUST）。

- interactive（起動指示に実行モードが無いときを含む）では、返事を新しいセッションで `/develop <記録先>` と一緒に渡せることを含める（MUST）
- channel では、このチャンネルで記録先の番号を添えて返事をすれば続けること（例: `#<記録先> 許容する`）を含め、新しいセッションを開く案内と `/develop <記録先>` の打ち方を書いてはならない（MUST NOT。channel の主は住人の新しいセッションを開けず、チャンネルだけを見ている）

引き継ぎのコメント（`引き継ぎ: 主の返事待ち`）は develop の本体が書くので、G の依頼文は書式を再掲せず、`dev-workflow-develop` の要件を指すだけにする（MUST）。`stages/hold.md` は引き継ぎの項目一覧を持ってはならない（MUST NOT）。

リスク許容の依頼では、主が会話で返事をすればよく、PR へのコメントは要らないと書かなければならない（MUST）。ただし channel で、起動指示の `チャンネルの返事の確認:` の行が `可` でないとき（`不可` のときと、行が無いとき）は、チャンネルの返事を `owner-reply-check.sh` で確かめられないので、リスク許容の依頼に限り「PR #<N> にコメントで `許容する` と書く」と案内し、PR のフル URL を添えなければならない（MUST。行が無いときを不可に倒すのは、PR のコメントならどの環境でも確かめられるため）。会話（channel ではチャンネル）で返事を受け、それを確かめられたときは、主に PR へのコメントを求めてはならない（MUST NOT）。

#### Scenario: 依頼文に案内がある

- **WHEN** `plugins/dev-workflow/tests/` の bats が `stages/hold.md` の手順 6 を検査する
- **THEN** interactive の案内として新しいセッションで `/develop <記録先>` と一緒に返事を渡す案内があり、引き継ぎの項目名（`前任 W` など）の一覧は無い

#### Scenario: 会話の返事に PR へのコメントを求めない

- **WHEN** `plugins/dev-workflow/tests/pr-review-gate-skill.bats` が `stages/hold.md` を検査する
- **THEN** 会話で返事を受けたときは主に PR へのコメントを求めないという文がある

#### Scenario: channel の依頼文はチャンネルの返事を案内する

- **WHEN** 起動指示の実行モードが channel の G が、リスク許容の保留で依頼文を書き、起動指示に `チャンネルの返事の確認: 可` がある
- **THEN** 依頼文は「このチャンネルで記録先の番号を添えて返事をすれば続ける」を案内し、新しいセッションと `/develop <記録先>` の案内を含まない

#### Scenario: channel でチャンネルの返事を確かめられない

- **WHEN** 起動指示の実行モードが channel の G が、リスク許容の保留で依頼文を書き、起動指示の `チャンネルの返事の確認:` が `不可` か行が無い
- **THEN** 依頼文は PR #<N> にコメントで `許容する` と書くよう案内し、PR のフル URL を添える
