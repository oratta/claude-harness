## Context

セッション記録（`~/.claude/.usage-sessions/<鍵>.json`）は 1 アカウント 1 ファイルで、そのアカウントの全セッションの statusline が上書きする。読み手は dev-workflow（`usage_view.py`）と statusline（自前の写し）の 2 実装。

## Decisions

### D1: 同じ窓の値は取得時刻が新しいほうを採る（大きいほうをやめる）
- 採用理由: 手動リセットでは同じリセット時刻のまま使用率が下がる。「同じ窓では使用率は下がらない」前提が崩れる。
- 却下案: 「0% のときだけ新しいほうを採る」「記録が snapshot より新しければ記録を採る」。前者は手動リセット以外の下がり方（例: 使用量集計の補正）に対応できず、規則が増える。後者は実質同じ規則を片方向だけに書くことになる。
- タイブレーク: 取得時刻が等しい、またはどちらか無いときは `pct` が大きいほう（従来どおり。使用量を多く見積もる安全側）。
- リセット時刻と取得時刻は採った値の情報源のものを使う（取得時刻で選んだときは新しい方、タイブレークで選んだときは大きい方の情報源）。
- 受け入れる弱点: 取得時刻が実際の受け取り時刻より新しく付く書き手が残れば、古い値が勝つ。D2 でこれを書き手側で防ぐ。

### D2: 取得時刻は「値を新しく受け取った時刻」にする（書き手が前回値を覚える）
- statusline の動作契機は API 応答だけではないため、`date +%s` を毎回 `observed_at` にすると D1 と組み合わせたとき古い値が勝つ。
- 覚える単位はセッション。覚える先は記録ディレクトリ内のセッション ID ごとのファイル（`.sessions/<セッション ID を JSON 文字列として引用符付きのまま sha256 した先頭 16 桁>` に、5 時間枠の使用率・リセット時刻、週次の使用率・リセット時刻を `|` でつないだ署名 1 行を置く）。セッション ID は文字列で任意の文字を含みうるのでハッシュをファイル名にする。
- 判定: 署名が前回と同じなら記録を書かない。違えば記録を書き（`observed_at` = 今）、書けたら署名を保存する。
- 却下案: 記録ファイルの中身と比べる。別セッション Y が記録を上書きしたあと、止まっていた X が古い値で描き直すと、ファイルとは違うので書いてしまい、Y の新しい値を古い値で潰す。`.rate-limit-snapshot` が `obs_sig` + `session_id` で同じことをしている（statusline.sh 99〜113 行目）のと同じ考え方。
- 却下案: 値が同じでも取得時刻を前回のまま書く。書く動作が残り、別セッションの新しい値を潰す。
- セッション ID が無い描画は覚える先が無いので従来どおり毎回書く（Claude Code は常に渡すので実害は想定しない）。
- 受け入れる弱点: 同じセッションが、他セッションの書き込みを挟んだあとで、前回と全く同じ値を本当に受け取り直した場合は書かれない。その間の記録は他セッションの新しい値か snapshot なので、使用量を多く見積もる側にしか倒れない。古い覚えのファイルは 7 日超で書き込みのついでに消す。

### D3: `select-account.sh` は変更しない
`select-account.sh` は `usage_view.build_view` の実効値を使う（`usage_view.py` 1 か所の実装）ので、`_combine` を直せば反映される。テストで固定する。

### D4: statusline の写しも同じ規則に直す
statusline は他プラグインのスクリプトを実行時に読まない契約なので、`combine` / `larger` を同じ規則に直し、同じ入力の fixture で両実装が同じ値を出すことをテストで固定する。
