## Context

pr-review-gate の合格処理（`skills/pr-review-gate/stages/pass.md` 手順 5）は、「主のリスク許容が必要」の宣言に主の許容回答リンクが追記され、そのリンクの真正性確認（GitHub コメントなら `gh api ... --jq '.user.login'` で投稿者を実測）が済んでいるときだけ合格させる。会話での返事にはリンクが無いため、セッションによって「会話の返事を PR に書いて進める」と「主本人の PR コメントを求める」に対応が割れ、主は PR を開いて許容を書き直す作業を頼まれている（issue #721）。

一方、`gh` は主のアカウントで認証されているので、エージェントが投稿したコメントも `user.login` は主になる。いまの真正性確認は書き手を区別できていない。Claude Code の会話ログ（`${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/<プロジェクト>/<セッション ID>.jsonl`）は 1 行 1 イベントの JSON で、主が打った発言とそれ以外（アシスタント・ツールの結果・サブエージェント・他のセッションからの転送・hook などが差し込む `isMeta` の行）を行の属性で区別できる。

実物で確かめた事実（2026-10-07、手元の会話ログ直近 2 週間分）:

- サブエージェントの中でも `CLAUDE_CODE_SESSION_ID` は親セッションの ID で、`projects/<プロジェクト>/<ID>.jsonl` が親の会話ログ、`projects/<プロジェクト>/<ID>/subagents/` がサブエージェントの会話ログである。G（ゲート担当のサブエージェント）は本体と同じセッション ID で親の会話ログを読める
- 新しい版の会話ログでは、主が打った行に `origin.kind: "human"` が付く。古い行や `<bash-input>` の行には `origin` が無い
- 他のセッションからの転送（`Another Claude session sent a message`）は `origin.kind: "peer"` かつ `isMeta: true` の行もあるが、`origin` が無く `isMeta` も false の行のほうが多い（624 行対 34 行）。属性だけでは除けず、本文の先頭で除く必要がある
- `/develop 721 許容する` は `<command-name>/dev-workflow:develop</command-name>` と `<command-args>721 許容する</command-args>` を含む文字列 1 行として残る。`!` で打ったシェルの入力は `<bash-input>...</bash-input>` を含む行、その出力は `<bash-stdout>` などを含む別の行として残る

## Goals / Non-Goals

**Goals:**

- 主が会話で返した許容（同じセッションの返事、または新しいセッションの `/develop <番号> 許容する`）を、PR へのコメントなしでゲートの正式な回答にする
- 会話ログに主の発言として実在するかを、G が目で読むのではなくスクリプトの終了コードで確かめる
- 会話ログを読めないときは通さない側に倒し、これまでの PR コメントの経路に戻す

**Non-Goals:**

- Discord など外部サービスの回答リンク（目視確認）の扱いは変えない
- 既存の GitHub コメントの回答リンクの真正性確認（`gh api` で投稿者を実測）はそのまま残す（会話ログが無い PC での経路として要る）
- 別の PC の会話ログを取りに行く仕組みは作らない
- 引き継ぎの条件を緩める（#694）・初めてのリスク宣言の確認を絞る（#723）・3 周目の確認（#722）・依頼の出し直し（#724）は扱わない

## Decisions

### 1. 確認スクリプトの入出力

`owner-reply-check.sh <セッション ID> <原文>` とする。

- 会話ログは `${OWNER_REPLY_PROJECTS_DIR:-${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects}/*/<セッション ID>.jsonl` だけを読む（`<ID>/subagents/` の下は読まない）。`OWNER_REPLY_PROJECTS_DIR` はテスト用の差し替え口
- セッション ID が UUID の形（`^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`）でない、原文が空白を除いて空、会話ログが 1 つも見つからない、`python3` が無い、のどれかなら exit 2（通さない側）
- 原文と各発言の本文は、連続する空白（改行を含む）を 1 個の空白にまとめ、前後の空白を落としてから部分一致で比べる。会話の返事を PR に書き写すときの改行や字下げの違いで落とさないため
- 一致したら exit 0 で、一致した発言ごとに `MATCH: <その行の timestamp> <空白をまとめた本文の全文>` を出す。最後に `MATCHES=<件数>` を出す。一致が無ければ `MATCHES=0` で exit 1
- 実装は bash の入口と、埋め込みの `python3` による JSONL の読み取り（`context-tripwire.sh` と同じ形）。jq より壊れた行・複数行の本文・Unicode の扱いを書きやすい

代替案: セッション ID を省いて全会話ログを走査する案は、他プロジェクト・他セッションの発言に一致してしまい、記録の「どの会話で受けたか」が検証されなくなるので採らない。

### 2. 主の発言として数える行（属性による除外 + 本文による除外）

次のすべてを満たす行だけを主の発言として数える。

1. `type` が `"user"`
2. `isSidechain` が true でない（サブエージェントの会話を除く）
3. `isMeta` が true でない（hook・スキル本文の差し込み、`peer` の転送の一部を除く）
4. `origin` があるなら `origin.kind` が `"human"`（`peer`・`task-notification`・`channel` などを除く）。`origin` が無い行は次の本文の条件で判定する
5. `message.content` が文字列、または `type: "text"` の要素だけからなる配列（`tool_result` を含む配列はツールの結果なので除く）。配列のときは text 要素を改行でつないで本文とする
6. 本文が `Another Claude session sent a message` で始まらず、`<teammate-message` を含まない（他のセッション・チームメイトからの転送を除く）
7. 本文が `<bash-stdout>`・`<bash-stderr>`・`<local-command-stdout>`・`<local-command-stderr>` で始まらない（`!` のシェルやローカルコマンドの出力は主の言葉ではない）

`<command-args>`（`/develop <番号> 許容する` の引数）と `<bash-input>`（主が `!` で打った `gh pr comment ...`）を含む行は、上の条件を満たすので主の発言として数える。タグは外さずに本文として比べる（原文が引数の部分だけでも部分一致で通る）。

代替案: `origin.kind == "human"` の行だけを通す（許可リストだけにする）案は、`origin` の無い古い行と `<bash-input>` の行（実物で `origin` 無し）を落とすので採らない。逆に属性を見ず本文の除外だけにする案は、`isMeta` の差し込みや `peer` の転送を本文の形で網羅しきれないので採らない。

### 3. 許容の意思は記録の原文ではなく、一致した発言の全文で読む

原文は部分一致でよいので、エージェントが「許容しない」の一部である「許容」だけを原文に書いても一致してしまう。G は記録の原文ではなく、スクリプトが出す `MATCH:` の行のうち、記録の日時と同じ timestamp を持つ発言の全文を読んで許容の意思を判定する（手順 5 の ② の確認）。記録の日時と同じ timestamp の `MATCH:` が無ければ通さない。

### 4. 記録の書式と書き手

会話で受けた許容は、手順 3 の宣言コメントに次の 1 行で追記する（従来の `主の回答: 許容 — <回答リンク>（<日時>）` と同じ位置・同じ「追記だけで本文は書き換えない」規則）:

```
主の回答: 許容 — 会話で受領（セッション <セッション ID> / <日時>）原文: <原文>
```

`<日時>` は会話ログのその発言の `timestamp` の値をそのまま書く。真正性確認の行は `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh 終了コード 0）` とする。

書き手: 主の返事を受けるのは develop の本体なので、本体がセッション ID（`$CLAUDE_CODE_SESSION_ID`）・発言の日時・原文を保留の解除の G に渡し、G が宣言コメントに追記してからスクリプトを回す（従来の回答リンクの追記を G が行う流れに合わせる。issue #721 の概要は「本体が PR に書く」としているが、手順 6 の復帰表が追記を G の仕事にしているので、書き手を 2 つにしない）。

### 5. 会話ログを読めないとき

スクリプトの exit 2（会話ログが無い PC・環境の不備）と exit 1（実在しない）は、どちらも合格させない。exit 2 のときは主に「会話の返事をこの PC では確かめられない」ことを伝え、PR のコメントか、ゲートと同じ PC での `/develop <記録先> 許容する` で受け直す。exit 1 は記録の誤りか捏造なので、記録を直さずに主に再確認する。

### 6. 引き継ぎ（手順 3-c）の元が会話で受けた回答のとき

条件 3 の「元の回答リンクに対して手順 5 の真正性確認をやり直す」を、元の回答が会話で受けたものなら「元の記録のセッション ID と原文でスクリプトを回し直し、exit 0 と同じ timestamp の `MATCH:` を確かめる」と読む。引き継いだ宣言の `主の回答: 許容（引き継ぎ） — ` の後ろには、元の記録の `会話で受領（セッション ... / ...）原文: ...` をそのまま書く。別の PC で exit 2 になったら引き継がず、手順 6 で主に聞く。

## Risks / Trade-offs

- [会話ログはローカルのファイルで、エージェントが書き換えられる] → 改変・追記は検知しない（仕様の守備範囲に限界として明記する）。主の発言の偽造は、ファイルへの書き込みという目に見える操作を要する。いまの PR コメントの経路はエージェントが `gh pr comment` を打つだけで投稿者が主になるので、それより悪くはならない。偽造の検知はこの変更では足さない
- [Orca の親セッションが子のターミナルに打ち込んだ文（例:「【親セッションから連絡】」）は `origin.kind: "human"` で残り、主の発言と区別できない] → これは塞げない限界として扱う。親が「許容する」と打ち込めば、一致した発言の全文を読んでも主が打った文と区別できず、合格の根拠として通りうる。親が許容を打ち込まないことは保証されていない。仕様の守備範囲（③通ることを許す入力）にこの限界を明記し、この変更では追加の対策をしない。区別が必要になったら別 issue にする
- [Claude Code が会話ログの形式（`origin`・`isMeta`・タグ名）を変えると、主の発言を落とす（exit 1）か、転送を通す] → 落とす側は PR コメントの経路に戻れるだけで安全側。通す側を防ぐため、除外の条件は属性と本文の両方で重ねて持つ。bats は実物から抜いた行の形で固定し、形式が変わったら bats の入力を取り直す
- [会話ログが無い PC では会話の返事が使えない] → 備考のとおり PR コメントの経路を残す（exit 2 で通さない側に倒す）

## Migration Plan

文書とスクリプトの追加だけで、既存の回答リンクの経路はそのまま動く。戻すときはこの PR を revert する。
