## Context

main の pr-review-gate は、`SKILL.md` が索引（10,000 バイト以下・コードブロック禁止・`description` 固定を bats が検査）、手順の本文が `stages/` と `declarations.md` にある。通過の必須点は 4 点で、手順 5 は 3 見出しを実測する。止めない指摘は振り分け表（段 A〜E）に通り、段 A 以外は別 issue か破棄になる。

PR #174 のブランチは分割前の `SKILL.md` を書き換えているので、衝突は main 版を採り、整合確認は main の形へ書き直す。

## Goals / Non-Goals

**Goals:** issue #166 の受け入れ条件 3 つを main の今の構成で満たす。食い違いを残したまま合格する経路を塞ぐ。

**Non-Goals:** 食い違いの自動検出。前からある食い違いの掃除。auto-merge のワークフローの照合の追加。issue #166 の「補足」の pre-push の件。

## Decisions

### 1. 手順 4 の小節にする（レビュアーの照合表の観点にはしない）

照合表に観点を足す案は読む量が少ないが、一周目のレビューにしか効かず修正の周の変更が漏れる。受け入れ条件は「合格の必須条件の手順」を求めるので、合格の直前に G が実行する手順 4-2 にする。

### 2. 必須点は 4 点のまま

`SKILL.md` の③の行は書き換えず、③に整合確認を含むことは足す節に書く（受け入れ条件 3 は `SKILL.md` の差分が追加のみであることを求める）。

5 点目を足すと、必須点の数を参照する仕様と文書を広く変える。整合確認は動作を確かめる証拠の一部なので③に含め、手順 5 の見出しの実測だけ 4 つにする。

### 3. 不合格は failed で W に戻し、周に数えない

G はコードを直せない。主に聞く理由も無い。手順 4 の不合格で failed を返す先例（軽い通し方の確かめ方の失敗）がある。周に数えると、2 周目のあとに見つかった食い違いで収束ルールの「3 周目を開ける 3 条件」と衝突し、直せないまま止まる。周に数えない扱いは、CI の見張りのあとの取り直しと「軽い通し方の条件外」に先例がある。原因分類は新しい値を作らず `段 A だけ（昇格なし）` を使い、取り直しの行で見分ける。再レビューは省かない（直しの commit が未レビューのまま合格しないように）。

### 4. レビューの指摘は段 A に足す

足さないと、レビュアーが見つけた食い違いの `should` が段 B 以降で別 issue になり、そのあと 4-2 が同じものを不合格にする。1 周目は段 A の通常の経路で戻し、2 周目以降は段 B に回さず 4-2 が止める。

### 5. 受け入れ条件は字面どおり `SKILL.md` で満たし、詳しい手順は pass.md に置く

`SKILL.md` に節 `## ドキュメント文字列の整合確認（合格の必須条件）` を行の追加だけで足す。見出しは手順番号を持たないので、段の表・手順番号の対応表・見出しの重複の検査に影響しない。コードブロックは使わずインラインのコマンドにする。索引が持ってよいものの要件は delta でこの節を足す形に変える。検索の例 1 つは pass.md の 4-2 の例と重なるが、受け入れ条件 2 が `SKILL.md` に求めるので置く。

| 受け入れ条件 | 検証（issue の文のまま） |
|---|---|
| 1 手順が存在し必須条件 | `grep -n "usage\|JSDoc\|ドキュメント文字列" plugins/dev-workflow/skills/pr-review-gate/SKILL.md` が 1 件以上ヒットし、節が合格の必須条件と書く |
| 2 検索コマンドの例 | `SKILL.md` の節に `git grep -n -- '<変えたシンボル名>'` がある |
| 3 既存の手順を削らない | `git diff origin/main -- plugins/dev-workflow/skills/pr-review-gate/SKILL.md` が追加のみ（削除行が無い） |

分割後のほかのファイルの削除行は、置き換え後が条件を緩めていないことを一覧で示す。

### 6. Scenario「3 見出しの実測が規定されている」の名前は残す

名前を変えた delta は、openspec が archive でシナリオの欠落として拒否する。Scenario の名前を変える手段が無いので名前は残し、本文（THEN）で整合確認の見出しも要求する。`dev-workflow-develop` の要件「入口 0 は記録先を決める」の「3 見出し」は本文なので「4 見出し」に更新する。

## Risks / Trade-offs

- [G が読む量が増える] → 4-2 は短く書き、`tests/gate-reading-budget.txt` を実測に合わせて上げる
- [言い換えの説明は検索に当たらない] → 守備範囲に拾えないと明記し、レビューに任せる
- [周に数えない取り直しが繰り返る] → PR トークン上限で止まる
- [一般的な語で一致が多すぎる] → パスで絞ってよく、指定を記録する
- [聖域の変更] → 人間がマージする。主の依頼もマージしないことを指定している

## Migration Plan

main を merge して衝突を解消し（rebase・force push はしない）、この change を実装して archive する。戻すときは PR の revert。
