# Proposal

## Why

#1729 の再集計では、大きい子がキャッシュ切れ後に再開した原因の最多は、自分の背景作業の終了通知だった（9 件、約 170 万トークン）。停止済みの子への声かけや親の起動し直しでは、実行中の作業を持つ子を保護できない。

## What Changes

- nested の子の本体が 60 分を超えうる待ちに入る前に、記録から再開できる依存待ちと、同じセッションを保持する必要がある作業待ちを分ける。
- セッションに属する作業は保持し、TTL 1h を確認できる場合だけ、45 分で終了する背景タイマーで本体のキャッシュ読み出しを促す。実際の作業の終了とは区別する。
- 長い外部依存待ちは既存の依存待ち手順へ渡す。自分の PR の CI 待ちは既存の CI 手順のまま保持する。
- 費用比較と選択理由を #1743 に記録し、手順の入口・雛形・例外をテストで守る。

## Capabilities

### New Capabilities

- `dev-workflow-child-background-wait`: nested の子の本体が所有する長い作業待ちの継続性とキャッシュ維持。既存の「停止済み子への声かけ」と対象を分ける。

### Modified Capabilities

なし。既存の停止済み子の送受信、親の再起動判定、CI の結果分類は変更しない。

## Impact

- 実装予定: develop の SKILL.md の条件付き入口、新しい待機 reference、契約と雛形の Bats テスト、`plugins/dev-workflow/changes/1743.md`（4 ファイル）。
- `child-cache-keepalive.json`、epic-state、hooks、モデル・account 選択、バージョン、常時注入の予算は変更しない。
- 単一 change とする。受け入れ条件 1・2 は同じ長時間待機方針の決定と記述であり、独立してマージする機能ではない。条件 3 はマージ後の実機確認として残す。
