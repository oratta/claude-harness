# Design

## Context

動機は proposal.md を参照。調査対象 HEAD は `486fbaa72b2f9571894c7698ac1442cf371b4855`。

- `epic-keepalive.md` / `child-cache-keepalive.json` は停止済み子の予約文と返事の共有正本。実行中の子に自己送信すると「主の返事待ち」と取り違える。
- 親の送信条件は `epic-keepalive-watch.md`。大きい子（既定 150k 以上）を除外するため、20 万トークンの作業待ちには流用できない。
- `epic-child-stop.md` は背景作業の完了待ちに停止コメントを残さない。依存待ちは blocked_by の確認と途中経過の記録を済ませて終了する。自分の PR のマージ待ちは別の定型がある。
- CI の現行正本は **`plugins/dev-workflow/references/ci-watch.md`**（依頼に挙がった develop/references 側には無い）。wait は背景起動、既定上限 3600 秒。timeout は上限到達であり、キャッシュ維持用の通知には転用しない。
- `reply-after-idle.md` の親の 3000 秒 wait は親専用。子の native agent・Monitor・Codex コマンドは子セッションに属し、そのまま親に移せない。
- Codex adapter は前景コマンドを起動する契約で、終了 JSON と終了コードで transport の決着を受け取る。新しい job transport や再接続は追加しない。

## Goals / Non-Goals

**Goals:** nested の子の本体が所有する作業を失わず、TTL 1h の長い待ちでキャッシュを維持する。再開可能な外部依存は既存手順に戻す。待機専用のコストと本来の作業の結果を区別する。

**Non-Goals:** worker 自身の待ち方の変更、親の送信判定の変更、5m TTL の維持、idle compaction 設定の変更、hook・epic-state の新設、マージ後の実機合格宣言。版と注入予算は動かさない。

## Decisions

### 一つの方針: 再開可能性に応じて待ち方を選ぶ

60 分を超えうる待ちを見つけた時点（開始前、または当初短い見込みだった待ちの延長時）で以下を適用する。

| 待つもの | 扱い |
|---|---|
| 別 issue / PR の完了で再開でき、子所有の実行中作業が残らない外部依存 | `epic-child-stop.md` の依存待ちへ移行し、親の既存 wait と起動し直しに任せる。対応 issue の特定・依存登録・記録が成功するまで移行済みとしない |
| 自分の PR の CI / マージ確認、実行中の agent、Codex コマンド、親が既存の待ち受けで扱えない Monitor | セッションと元の実行 ID を保持し、下の本体用キャッシュ維持を適用する。CI の重複監視禁止・next・timeout の意味を変えない |

数時間〜日単位の単なる外部依存を子の Monitor で待ち続ける形は選ばない。ただし既存の依存待ちに表せない条件を、親が自動監視できると捏造しない。実行中の作業が一つでもあれば、それを終了・回収して安全に移行できるまで、起動し直すだけのためにセッションを終了しない。

### 本体用の有限タイマーを、必要な場合にだけ一つ置く

正本は新規 `skills/develop/references/child-background-wait.md`。SKILL.md に「nested の本体が自分の agent・CI・Monitor・Codex コマンドの待ちに入る前」の Read 入口を一つ設ける。既存 reference の受信契約や CI の分類を複写しない。

1. 対象は Claude の本体である nested セッション。委譲された worker はタイマーを起動しない。固定された Codex model/account/effort や adapter の前景起動契約を変更しない。
2. 自分の現行 CLI 会話の最後の有効な cache creation の `ephemeral_1h_input_tokens` / `ephemeral_5m_input_tokens` と、最後の成功リクエスト（cache-read を含む）の時刻を確認する。サブエージェントの usage や別セッションの TTL を根拠にしない。読めない・曖昧なら unknown。書き込み時刻とリクエスト時刻は分ける（既存 `cache_ttl_of` と同じ意味）。
3. TTL 1h と確認でき、最後の成功リクエストから 3600 秒未満で、別の作業通知や有限待ちが 45 分以内に本体へ返る保証が無い場合だけ、Bash の **`run_in_background: true`** で 45 分の有限タイマーを起動し、返った task ID を本来の作業 ID と別に覚える。前景の長時間呼び出しは本体へ 60 分未満で制御が戻る呼び出しを使う。利用環境でそれができなければキャッシュ維持可能と報告しない。
4. タイマーの雛形は以下。ループ内 sleep は共有 `subagent-waiting.md` でも扱う許可形だが、そのサブエージェント用の回数上限等は本体へ流用しない。これは作業をポーリングするコマンドではなく、一度だけ本体を起こすタイマーである。

   ```bash
   remaining=45
   while [ "$remaining" -gt 0 ]; do
     sleep 60 || exit 1
     remaining=$((remaining - 1))
   done
   printf '%s\n' 'child-background-cache-refresh'
   ```

5. 自分が保持したタイマー ID の成功通知で起きた本体は、モデルのリクエスト自体でキャッシュを読み出す。元の未完了作業が残り、現在も 1h と確認できる場合だけ次の一回を起動する。それ以外の作業・調査・GitHub 投稿・親への報告・停止記録の変更はしない。状態行が必要なターンは既存の `状態: 作業報告 — …` を付けるが、依存待ち・承認待ち・工程完了とは宣言しない。
6. 作業の本来の通知や主・親からの入力が届いたらそちらを先に処理する。既存タイマーを止めて必要なら待ち直す。一つの子でタイマーは最大一つ。作業を全て回収したとき、主の返事待ち・依存待ちへ移る前、終了前に自分のタイマーだけ TaskStop で取り消す。キャンセル後に遅れて届いた通知は無視し、再起動しない。
7. 出力文字列が同じというだけではタイマー通知とみなさない。task ID と成功した終了を照合する。起動失敗・sleep 失敗・通知失敗や停止失敗では元作業を成功扱いせず、二重起動や再送をせず、維持できなかった事実を次の通常報告で示す。

ここで本体がターンを終えて背景通知を待つことと、依存待ちとして子セッションを終了して親へ渡すことは別である。前者はセッションと実行 ID を保持したままの実作業待ちで、`epic-child-stop.md` の主の返事待ち・依存待ちの停止コメントを投稿しない。後者だけを停止と再起動の経路へ渡す。サブエージェントのターン終了禁止を本体へ移さない。

API のキャッシュ寿命は応答の終了ではなく読み書きするリクエスト開始から測る。45 分はスケジューラ遅延への余裕であって保証ではない。スリープ復帰や長い前景呼び出しで 60 分以上あいた場合、元の作業が生きている間はキャッシュのためだけに起動し直さない。最初の書き直しは取り戻せないと記録し、現在のリクエストから有効な待ちに戻す。

TTL 5m / unknown にはタイマーを置かず、元の完了待ちを継続する。5 分ごとの声かけ・TTL 設定の強制変更はしない。overage による 5m への切替を次の書き込み観測まで検知できず、一回の miss が起きうる。

### 既存の機構を使う範囲

- `epic-keepalive.md` / JSON: 変更しない。本体のタイマーに予約文を使わない。主の返事待ちになった時点で従来の正本に渡す。
- `reply-after-idle.md`: 親や停止済み子の既存の再起動規則を参照するだけ。実行中作業を持つ子への無条件な適用はしない。
- CI: 正本 `references/ci-watch.md` の wait を一つだけ保持する。タイマー通知で wait を完了・timeout 扱いせず、途中出力も読まない。新しい CI の見張りを重ねない。
- Monitor: 既存 watch が 45 分以内の期限で本体に返るならその通知を利用し、タイマーを重ねない。公開仕様の現行上限は 30 分で、期限通知から必要な watch だけを継続する。Monitor を別の追跡済み作業の完了ポーリングやタイマーのために新設しない。
- ScheduleWakeup: 自律 `/loop` の次回反復用。背景作業の完了の代用、自己声かけ用の新しい `/loop` や Cron は作らない。
- Codex: 前景コマンドの有限の返りがあるならその API リクエストで維持され、追加タイマーは不要。ホストが背景に回した場合はホストの task ID を元作業として扱う。返った transport JSON の評価は現行正本どおりで、タイマー成功を委譲成功としない。

### 費用比較と選択理由（API 定価換算）

2026-11-23 に確認した一次資料:

- [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing): USD / MTok。Opus 5.5 は input 4、5m write 5、1h write 8、hit 0.20、output 20。#1729 と同じ旧 Opus 4.6 系単価は 5 / 6.25 / 10 / 0.50 / 25。
- [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching): ヒットで期限が延び、再書き込み料金は発生しない。新規 suffix と出力は別料金。
- [Claude Code の TTL](https://code.claude.com/docs/en/prompt-caching): サブスク内の本体は 1h、従量や超過は 5m になりうる。これはサブスクの枠消費率の公式な換算ではない。
- [Tools reference](https://code.claude.com/docs/en/tools-reference) / [scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks): Monitor の期限と ScheduleWakeup の用途。TaskOutput は現行では削除済みなので前提にしない。
- 実績の出典は [#1729 の分類](https://github.com/oratta/claude-harness/issues/1729#issuecomment-7052968395)。そこでの約 $10.6 は 1.7M × $6.25 であり、1h 書き込み価格ではない。

比較する旧会話を N=200,000 とし、待ち開始までの既払い費用と本来の作業費を除く。

| 候補 | 計算 | Opus 5.5 | 旧単価 |
|---|---|---:|---:|
| 毎回 60 分以上あけ、同じ会話を書き直す（1h TTL） | 0.2 × write1h | $1.60 / 再開 | $2.00 / 再開 |
| 同上、5m TTL の書き直し | 0.2 × write5m | $1.00 / 再開 | $1.25 / 再開 |
| キャッシュを保って読む | 0.2 × hit | $0.04 / リクエスト | $0.10 / リクエスト |
| 引き継ぎから一度起動し直す（過去の平均、入力換算 270k） | 0.27 × input | 約 $1.08 / 回 | 約 $1.35 / 回 |

起動し直しの入力換算 270k は [#1046](https://github.com/oratta/claude-harness/issues/1046#issuecomment-6358891346) の 42 本の平均で、20 万会話の確定費用ではない。現在の手順書・引き継ぎの量で変わる。新しい 20k トークンを一回 1h で書くという仮定なら $0.16 / $0.20 だが、その量を実測値としては使わない。引き継ぎ作成と追加読み直しも別途かかる。

維持通知の受信で一回、タイマー再設置ツールの結果を受けた応答でさらに一回、少なくとも旧会話を読む。維持 k 回と最後の再開一回なら `(2k + 1) × 0.2 × hit` を見込む。2 時間では 45・90 分の維持（k=2）で $0.20 / $0.50（旧会話部分）。60・120 分に書き直すなら $3.20 / $4.00、最後の一回だけ再開なら $1.60 / $2.00。24 時間では 45 分ごとに k=31 で $2.52 / $6.30、毎時の書き直しは $38.40 / $48.00。一日黙って最後に一回だけ書き直すなら $1.60 / $2.00 で、両単価とも維持の方が高い。

維持の各ターンには suffix と出力、初回設置・取消・TTL の追加確認ツール等の費用が足される。追加費用は `(新規1h書込tokens × write1h + 非cached入力tokens × input + 出力tokens × output) / 1,000,000` と上で数えていない cache-read の和。上の表と例はこの部分を除いた下限で、常に安いという主張ではない。単に毎時キャッシュが消えるだけでは課金されず、API リクエストで再開して初めて書き直し費用が発生する。

採用理由: 再起動できない実作業の数時間の待ちでは、失う作業を作らず 1 回の miss より十分小さい読み出しで保護できる。日単位の外部依存は再開記録へ移すことで維持を続けない。既存の短い通知がある場合は無料の追加タイマーを装わず、単にタイマーを作らない。5m に頻回の起床を加える案と、実作業を失う一律の再起動は採らない。

## Risks / Trade-offs

- [PC のスリープ・API 遅延・prefix 変更で miss] → 回避を保証せず、実機 usage で確かめる。元作業を壊して取り戻そうとしない。
- [作業の完了とタイマーの競合] → ID を別管理し、本来のイベントを優先、終了時にタイマーだけ取り消し、遅延通知から再設置しない。
- [維持の API 往復と会話の増加] → 45 分に一回以下、既存の短い待ち戻りは再利用、外部依存へ移行できる場合は終了。会話量による通常の管理は既存のまま。
- [モデルへの手順指示は実行を強制しない] → Bats は入口・契約・雛形の実行を確かめる。削減成功はマージ後のログでしか宣言しない。

## Migration Plan

R1 の承認後にタスクの範囲だけ実装し、通常のゲートに渡す。公開前は `claude --plugin-dir` の確認を本体が必要に応じて行う。マージ後は #1743 条件 3 に従って実子の 60 分超の待ちを観測し、会話量・モデル・TTL・実行 ID・維持通知の時刻・通知後の cache_read_input_tokens または終了と再起動を issue に記録する。観測はこの spec 工程で行わない。戻す場合は本体用の待機入口と reference を戻し、実行中セッションでは自分のタイマーを止める。元の作業・状態記録は消さない。
