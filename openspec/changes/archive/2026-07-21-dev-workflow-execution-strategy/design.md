## Context

issue #26。Lance Martin「Cost effective harnesses with Fable」の実験結果が土台:

- 事前プラン/事前ランキングは結果と逆相関。効いたのは中間チェックポイントでの再ランク付け（Parameter Golf: Sonnet 実行 + Fable checkpoint で改善幅 ~90% をコスト ~34%）
- 小タスクの委譲はコーディネーションコストで確実に損（BrowseComp: 小タスクで 60% 割増）。委譲が得なのは吸収トークンがハンドオフ毎の固定コストを上回る大タスクのみ

サブスク前提により目的関数が「コスト最小化」から「枠の有効活用」に変わり、残量モードという第2の軸が加わる。現状の `github-issue` スキルは Step A〜D のパイプラインを持つが、実行主体は常にメインセッション solo で、モデル・実行形態の選択機構が無い。

## Goals / Non-Goals

**Goals:**

- タスクを4象限（トークン量 × 判断の分布）で捉え、実行戦略（solo / delegate+verify / workflow 型）を自動選択する判定系を dev-workflow に実装する
- 事前分類の精度に頼らず、実行中の昇格トリップワイヤーで誤分類を自動修正する
- ユーザーが記事のナレッジを覚えて使い分ける必要を無くす（interactive / unmanned 両対応）

**Non-Goals:**

- 残量の自動検知（v0 は手動宣言のみ）
- longrun:exec テンプレートのモデル割り当て更新（別 change `longrun-exec-model-allocation`）
- loop-dev-agent 憲法テンプレートへの組み込み（別 change `loop-dev-agent-tripwires`）
- longrun ブランドの解体・スキルのリネーム（issue #28）
- 実際のモデル切替 API の実装（Agent tool の model 指定・/model 操作はハーネス既存機能を使う）

## Decisions

1. **事前分類ではなく常駐トリップワイヤーを中心に据える**。記事自身が事前ランキングの逆相関を示しているため、入口判定は粗く安く（既存 Step B/C に相乗り）、投資は実行中の昇格条件に行う。代替案「入口での精密分類（専用サブエージェント）」は、分類のためだけにハンドオフ固定コストを払う点と、精度がそもそも出ない点で却下。

2. **トリップワイヤーは行為ベースの数えられる条件にする**。「難しかったら抜ける」のような曖昧な常駐ルールは momentum 中の LLM に発火しない。「ユーザーが言っていない仕様決定を自分で埋めた回数」のような、行為の瞬間に必ず認識できるカウンタに変換する。閾値（ファイル5個・2回など）は初期値であり運用調整前提。

3. **2段構えの配線**: 常駐ルールテンプレートは「いつ手を止めるか」のみを持ち、発火時のアクションは必ずスキル呼び出し（/lr:e、/lr:p 等）にする。理由: (a) Workflow ツールはポリシー上ユーザーの明示オプトインかスキル経由の起動が必要、(b) 常駐テキストは短いほど長セッションで効き続ける。

4. **4象限の役割分担**: 縦軸（トークン量）が分業の有無を決め、横軸（判断の分布）がモデルを決める。上の行（トークン小）は絶対に分業しない。記事の配置原則（判断点=賢いモデル、実行=安いモデル）が意味を持つのは下の行だけ。

5. **残量モードは環境変数 `FABLE_BUDGET_MODE`**（`abundant` / `conserve` / `reserve`、未設定は `conserve` 扱い = 安全側）。settings.json の env ブロックで永続化できる。モードが動かすのは solo の推奨モデルと委譲閾値だけで、構造は変えない。モード不変ルール2本（結果が変わらない大量トークン仕事は常に安いモデル / 判断が集中する場所は常に賢いモデル）を判定表に明記する。代替案「専用設定ファイル」は参照実装が env より複雑になるため v0 では見送り。
   - **`reserve` の追加理由（2026-07-21 ユーザー要望）**: 週次の全体枠は残っているが Fable 枠だけ枯渇しそうな時、残りの Fable をユーザーの interactive 利用のために温存したい。`reserve` は `conserve` の振る舞いに加えて**自動実行（unmanned / cron / loop 経由）では Fable を一切使わない**制約を課す。unmanned の昇格ラダーは Opus が上限になり、Fable が必要なほどの問題は needs-approval で人間に返す。interactive セッションでは `conserve` と同じ扱い（人間が使う分は妨げない）。

6. **Step B の重心移動**: spec の2機能（コンテキスト圧縮 / 意図・決定の記録）を分離し、Fable の探索能力で価値が目減りするのは前者のみという判断に基づき、「設計判断・トレードオフを含むか」を一次基準にする。テストは無条件維持——トリップワイヤー②の信号源であり、弱くするとハーネス全体が壊れる。unmanned の「迷ったら spec 化に倒す」は維持。

## Risks / Trade-offs

- [常駐ルールが長セッションで無視される] → テンプレートを短く保ち（トリップワイヤー3本のみ）、条件を数値化する。効果が不足する場合は hooks による機械的リマインドを次段で検討
- [閾値の初期値（ファイル5個・2回）が実運用と合わない] → 「初期値であり運用調整前提」をテンプレートと判定表の両方に明記し、調整をブロックしない
- [トリップワイヤー③（仕様の発明カウンタ）の発火漏れ] → 「決定を埋めた瞬間に1カウント」という行為の定義を具体例付きでテンプレートに書く（例:「DB は SQLite でいいだろう」と書く瞬間）
- [delegate+verify で安い実行役の成果物が低品質のまま verify を通過する] → verify は賢いモデルが受け入れ条件とテスト結果の両方を見る。テスト2連続失敗で昇格するため品質底割れは昇格側で吸収
- [残量モードを env にしたことで、セッション起動後の変更が次セッションまで反映されない] → v0 の制約として文書化。モード切替は頻度が低い（週単位）ため許容
