## Context

作業中かの判定（`develop 開始` か `実行モード:` の行があるコメント、または本文に `Closes` / `Fixes` / `Refs #<番号>` がある open の PR）は `in-progress-issue-scope` が正本。G の振り分けだけが対象外になっていた。

## Decisions

- **足す先の確認は段 C の子の行だけに置く。** `other` の行は受け入れ条件を足さず（エピックの子に足すか、新しい子を作る）、段 D は参考コメントで条件に足さないので、受け入れ条件に足す行は子の行だけである
- **作業中なら新しい子 issue を作る。** 主には聞かない（G は振り分けで主に聞かない決まりのため）。新しい子は同じエピックの子にし、作業中の子の番号を本文に書く
- **主が切り出すと答えた止める指摘の置き場所にも確認を読ませる。** 既存の要件は表に委ねているが、読み落とさないよう triage.md の段落に 1 句足し、spec の同名要件のシナリオも作業中でない場合に限定する（MODIFIED）
- **判定のスクリプトは作らない。** G が `gh issue view <番号> --json comments` と `gh pr list --state open --search "<番号> in:body" --json url,body` を打てば足りる
- **既存シナリオと衝突するので段 C の要件を MODIFIED にする。** 「同じ場所を直す子 issue がある」と置き場所のシナリオは作業中かを問わず足すと書いているため、作業中でない場合に限定する。要件全文は main のものをそのまま使い、変えるのはシナリオの追記経路だけ。#1513 も段 C の要件を MODIFIED で書き換えるので、後からマージする側が取り込む。#1513 の親の取得の文言は先取りしない

## Risks

- 作業中の子が複数の指摘で増える。指摘ごとに新しい子を作るので、同じ場所を直す子が並ぶ。互いの番号を書くことで重なりを見えるようにする（既存の段 C の決まりと同じ扱い）
