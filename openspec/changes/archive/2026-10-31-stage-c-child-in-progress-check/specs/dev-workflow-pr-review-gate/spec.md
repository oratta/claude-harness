## MODIFIED Requirements

### Requirement: エピックの完了条件に効く指摘は既存 issue との関係で分ける（段 C）

エピックに属する PR で、段 B の「いまの範囲で成り立つ」に当たった指摘について、G はその指摘がエピックの完了条件に効くか（出荷物を使う人の体験が変わるか）を、エピックの本文の完了条件を根拠に決めなければならない（MUST）。効く指摘は、候補探しの結果で次の表のとおりに分ける（MUST）。効かない指摘は段 D へ進める（MUST）。

| 候補探しの結果 | 扱い |
|---|---|
| 同じエピックの子 issue（`child`）に、同じ場所を直すものがある | その子 issue の受け入れ条件に足す（その子が作業中でないとき。作業中なら新しい子 issue を作る） |
| エピックの外の issue（`other`）に当たり、その issue の受け入れ条件が、この指摘を直せば全部満たされる | その issue をエピックの子に足す。新しい子は作らない。足した理由をその issue にコメントする |
| エピックの外の issue に当たるが、満たされない項目が 1 つでも残る。または受け入れ条件が書かれていない | この指摘だけの新しい子 issue を作る。外の issue には「この部分は子 issue で直す」と番号を書き、エピックには足さない |
| 当たる issue が無い | 新しい子 issue を作る |

外の issue に open の PR が付いているときは、新しい子 issue に「外の PR のマージ後に着手」と書く（MUST）。エピックの中と外に同じファイルを直す issue が並ぶときは互いの番号を書く（MUST。重なりそのものは防がない）。

エピックに属するかは、記録先 issue の親（`gh api repos/<owner>/<name>/issues/<記録先>/parent`）で決め、親が取れなければエピックに属さない PR として扱う（MUST）。

守備範囲: 入力は、エピックの本文の完了条件、候補探しのスクリプトが返した番号・題名・3 列目、投稿者を確かめた外の issue の本文に限る。拾いたい誤りは、エピックの完了条件に効く指摘がエピックの外の issue になって配布の前に直されないこと、同じ場所を直す子 issue があるのに新しい子 issue を作ること。次は誤ったまま通ることを許す: 受け入れ条件があいまいな外の issue を G が「全部満たされる」と読み違えてエピックの子に足すこと（足した理由をその issue にコメントするので、あとから外せる）／完了条件に効かない指摘を G が効くと読んで子 issue が 1 件増えること／題名だけでは同じ場所を直すと分からない子 issue を見落とすこと。これらを塞ぎ切ることは完了条件にしない。

#### Scenario: 同じ場所を直す子 issue がある

- **WHEN** エピックの完了条件に効く指摘の場所のパスについて、スクリプトが 3 列目 `child` の候補を返し、その題名が同じ場所を直すもので、その子 issue が作業中でない
- **THEN** G はその子 issue の受け入れ条件に指摘を足し、新しい issue を作らない（作業中なら足さない。「段 C の子の行で足す前に、その子が作業中かを確かめる」要件）

#### Scenario: 外の issue の受け入れ条件が全部満たされる

- **WHEN** `other` の候補の投稿者が `OWNER` で、その issue の受け入れ条件が、この指摘を直せば全部満たされる
- **THEN** G はその issue をエピックの子に足し、足した理由をその issue にコメントし、新しい子 issue を作らない

#### Scenario: 外の issue に満たされない項目が残る

- **WHEN** `other` の候補の受け入れ条件のうち 1 項目が、この指摘を直しても満たされない
- **THEN** G はこの指摘だけの新しい子 issue を作り、外の issue に子 issue の番号を書き、外の issue をエピックの子に足さない

### Requirement: 主が切り出すと答えた止める指摘は捨てずに置き場所だけ決める

切り出しの確認（順 5）で主が「切り出す」と答えた止める指摘、および決める役の裁定を経て主が切り出すと答えた指摘について、G はその指摘を必ず issue で追跡しなければならない（MUST。新しい issue を作るか、段 C の表のとおり既存 issue の受け入れ条件に足す。足す前の作業中の確認も段 C のとおり通る）。段 B・段 E で捨ててはならず、段 D の参考のコメントで済ませてはならない（MUST NOT。主が残すと決めた確認済みの欠陥で、追跡が切れると直されないため）。

この件で「follow-up issue に切る」と言うときは、新しい issue を作る場合と、段 C の表のとおり既存 issue で受ける場合の両方を指す（MUST。`stages/hold.md` と `stages/pass.md` の同じ語もこの意味で読む）。既存 issue で受けたときも、PR コメントには「follow-up issue に切った」と書いて URL を添えなければならない（MUST。合格処理の G は `stages/pass.md` の「follow-up issue に切ったもの」を PR コメントで数えるため）。

置き場所は次で決める（MUST）: エピックに属する PR で、その欠陥がエピックの完了条件に効くなら、候補探しのスクリプトを走らせて段 C の表のとおりに分ける。それ以外はエピックの外の新しい issue にする。

#### Scenario: 主が切り出すと答えた欠陥がエピックに効く

- **WHEN** エピックに属する PR で、主が切り出すと答えた止める指摘がエピックの完了条件に効き、当たる issue が無い
- **THEN** G は新しい子 issue を作り、URL を PR コメントに記録し、`needs-approval` を外す

#### Scenario: エピックに属さない PR で主が切り出すと答えた

- **WHEN** エピックに属さない PR で、主が切り出しの確認に「切り出す」と答える
- **THEN** G はその指摘を新しい issue にし、捨てることも既存 issue への参考のコメントで済ませることもしない

#### Scenario: 主が切り出すと答えた欠陥を直す子 issue が既にある

- **WHEN** エピックに属する PR で、主が切り出すと答えた止める指摘がエピックの完了条件に効き、同じ場所を直す子 issue が既にあり、段 C の表がその子の受け入れ条件に足すと示し、その子が作業中でない
- **THEN** G は新しい子 issue を作らず、その子の受け入れ条件に足して URL を PR コメントに記録する（追跡は切れない。作業中なら下の別シナリオのとおり新しい子 issue にする）

## ADDED Requirements

### Requirement: 段 C の子の行で足す前に、その子が作業中かを確かめる

G は、段 C の表の子の行（同じエピックの子 issue の受け入れ条件に足す）で足す前に、その子 issue が作業中かを `in-progress-issue-scope` の判定で確かめなければならない（MUST）。作業中なら、受け入れ条件に足さず、この指摘だけの新しい子 issue を同じエピックの子として作り、本文に作業中の子の番号を書く（MUST）。主には聞かない（MUST NOT。G は指摘の扱いを主に聞かない決まりである）。作業中でなければ、これまでどおり受け入れ条件に足す。

主が切り出すと答えた止める指摘の置き場所は、段 C の表を通る経路なので、同じ確認を通る（MUST）。


#### Scenario: 同じ場所を直す子が作業中

- **WHEN** 段 C の表が子 #A の受け入れ条件に足すと示し、#A に open の PR があり、その本文に `Closes #A` がある
- **THEN** G は #A の受け入れ条件に足さず、この指摘だけの新しい子 issue を同じエピックの子として作り、本文に #A の番号を書く

#### Scenario: 同じ場所を直す子が作業中でない

- **WHEN** 段 C の表が子 #A の受け入れ条件に足すと示し、#A に `develop 開始` か `実行モード:` の行があるコメントも、開いた紐づく PR も無い
- **THEN** G は #A の受け入れ条件に指摘を足す

#### Scenario: 主が切り出すと答えた欠陥を直す子が作業中

- **WHEN** エピックに属する PR で、主が切り出すと答えた止める指摘について、段 C の表がある子の受け入れ条件に足すと示し、その子が作業中である
- **THEN** G はその子に足さず、新しい子 issue を作り、PR コメントに「follow-up issue に切った」と書いて URL を添える（追跡は切れない）

### Requirement: 作業中かの確かめ方は gh の 2 回の呼び出しにする

G は、子 issue が作業中かを `gh issue view <番号> -R <owner>/<name> --json comments`（`develop 開始` か `実行モード:` の行があるコメント）と `gh pr list -R <owner>/<name> --state open --search "<番号> in:body" --json url,body`（本文に `Closes` / `Fixes` / `Refs #<番号>`、大文字小文字不問、がある PR）で確かめなければならない（MUST）。issue の本文だけで作業中でないと判断してはならない（MUST NOT）。判定のためのスクリプトは作らない（MUST NOT）。


#### Scenario: 本文に作業中と書かれていない

- **WHEN** 子 issue の本文に作業中である旨が無い
- **THEN** G は上の 2 つの呼び出しで確かめてから足すかを決める

### Requirement: 段 C の作業中の確認の守備範囲

入力の出どころは、`gh` が返す子 issue のコメントと open の PR の本文である。拾いたい誤りは、作業中の子の受け入れ条件に足して、レビューを通った PR が足した条件を見ないままマージされ追跡が切れることである。通してよい例は、番号が本文に現れない PR で進む作業、PR も開始のコメントも無い作業、放置された子を作業中と読むことである。穴を塞ぎ切ることは完了条件にしない。判定の定義は `in-progress-issue-scope` の守備範囲を適用する（MUST）。

#### Scenario: 番号が本文に現れない PR で進む作業

- **WHEN** 子 issue の作業が、本文に番号が現れない PR と開始のコメントの無い状態で進んでいる
- **THEN** G はその子を作業中と読めなくてよく、この要件はその取りこぼしを直すことを求めない
