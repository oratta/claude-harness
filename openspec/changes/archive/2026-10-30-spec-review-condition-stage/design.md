# Design

## Context

背景は proposal.md の Why のとおり。手本は `skills/pr-review-gate/stages/triage.md` の段 B で、G は PR コメントと保留を持つが、R1 は読み取り専用で、`APPROVE` が記録されるまで実装に進めない点が違う。直し方の判定の節は issue の起票後に SKILL.md から `references/fix-check.md` へ移っている。SKILL.md は開いた PR が 4 本触っていて、`tests/develop-startup-budget.txt` の予算ちょうどの大きさである。

## Goals / Non-Goals

**Goals**

- R1 が全周で条件の段を当て、起きない場面の指摘を BLOCKER に残さない
- 主の答えが後から入ったとき、直し方の判定の前に捨てられる

**Non-Goals**

- PR のレビュー側（G の `needs-fix-check`）の変更。`triage.md` を変えない制約があり、判定を受け取った G は仮の順どおりに指摘を W に戻すので、本体が捨てても G 側に届かない
- 新しいスクリプト、機械照合する新しいコメント書式

## Decisions

### D1: 条件を判定するのは R1 だけにする

直し方の判定の前の段でも、条件を決めるのは R1 にし、本体は R1 の結果を読んで当て直しを依頼するだけにする。

- 案: 本体が表に当てる。本体はコードを読まず、fix-check.md の「G・本体・レビュアーの申告を判定の代わりにしない」とも合わない
- 案: 決める役の依頼に条件の問いを足す。問いを 1 つに保つ依頼の契約が崩れ、受け入れ条件の「判定に回さず」にも合わない
- 採用: R1 の当て直し。判定の場所が spec-reviewer.md の 1 か所で済み、`APPROVE` を投稿する役も既存のまま R1 になる

### D2: R1 が決められない条件は BLOCKER に残し、W を再開する前に主に聞く

`triage.md` の段 B は `needs-approval` を付けず作業を止めないが、それは止めない指摘の話である。仕様レビューでは `APPROVE` が無いと実装に進めないので、次の案を比べた。

- 案: BLOCKER から外して NOTE に問いを書き、実装に進める。条件が成り立つ場合に欠陥が実装へ持ち込まれる
- 案: BLOCKER に残して W に直させる。起きない場面のために artifact を直す手間が残り、この issue の目的に反する
- 採用: BLOCKER に残し、周によらず W を再開する前に条件だけを主に聞く。1 周目から聞くのは、#702 のように 2 周目まで引きずらないため

### D3: 当て直しは周に数えない

W が何も直していないのに周が進むと、1 周目の問いのあとすぐ「2 周目の終わり」の直し方の判定に入ってしまう。結果コメントは最新 1 件を正とする既存の契約があるので、同じ書式で投稿し直すだけで照合は変わらない。PR トークン上限の計測は残すので、当て直しが無限に続いても止まる。

### D4: `## 条件の答え` は本体が依頼文に入れる

`reviewer-brief.md` の入口と同じく、起こす側が入れる。R1 に親エピックを探させる案は `dev-workflow:decider` の経路で `gh` が無く使えない。SKILL.md の (2) に 1 行足して、2 経路で同じにする。

### D5: 正本の置き場

条件の表と根拠は R1 が読む spec-reviewer.md に、本体の手順は本体が読む fix-check.md に置く。受け入れ条件の「SKILL.md に書かれている」は、(2) に短く書いて fix-check.md の新しい節を指す形で満たす。節を分けるのは、fix-check.md の既存の節が R1 と G の共通の手順で、新しい段は R1 だけに当てるから。既存の節の「主に聞くのは 2 つだけ」は方針の問いの数だと 1 文足す。

### D6: 表の後で成り立つ行は NOTE に出し、行き先は本体が決める

R1 は issue を作れないので、段 D・段 E を自分では通さない。SKILL.md の「範囲外の問題の起票」の対象文は「レビュー指摘ではないもの。G の振り分けを経た指摘は G の振り分けのまま扱う」で、R1 の指摘は G の振り分けを経ていない。そこで、その節の対象文は変えず、行き先の決め方（段 B の表・段 D・段 E の問い。エピックの子なら段 C も）だけを借りると fix-check.md の節に書く。

### D7: unmanned の条件の問いは引き継ぎの場面を 1 つ足す

既存の要件は `needs-approval` で待つすべての場面に引き継ぎを求める。再開で主の答えを探すのは `references/handover.md` の再開の手順 2 だけなので、引き継ぎが無いと、次のサイクルの本体が答えを拾えず同じ問いを出す。場面に「仕様レビューの条件の問い（unmanned で `条件の問い:` を主に聞くとき）」を足し、`待ち理由` の値に `条件の問い` を足す。書式は 1 種類のままで、「主への依頼」は本体が投稿する条件の問いのコメントとする。interactive は AskUserQuestion でその場で答えが返るので、`needs-approval` も引き継ぎも要らない。

- 案: 場面を増やさない。既存の要件と衝突し、答えを拾う経路が無い

場面の数を書いた SKILL.md の「引き継ぎを書く 3 つの場面」の 1 行も同じ変更で直す。残すと本体が handover.md を読む条件が食い違う。

## Risks / Trade-offs

- [R1 が「決められない」を多用して主への問いが増える] → 答えは `## 条件の答え` に残り、同じエピックの以後のレビューでは聞かれない。問いは 1 行で答えられる条件に限る
- [R1 が「いまの範囲で成り立つ」と誤判定して主に上がる] → 防がない。主が条件を答えたら節に足して当て直す
- [SKILL.md の予算を動かす] → 増えた分だけ動かし、理由を PR に書く。ほかの開いた PR と同じ行で衝突しうるが、数値 1 行で解ける
- [文書だけの規則で、R1 の実際の判定はテストできない] → bats は文書の語と表を固定する。実際の効き目は次の仕様レビューの結果で見る

## Migration Plan

文書の変更だけで移行は要らない。戻すときはこの PR の差分を戻す。エピックの本文に足された `## 条件の答え` の行はそのまま残る。
