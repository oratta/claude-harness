## Context

pr-review-gate の手順 2-1 は、レビュアーに「落とせる欠陥を探す」姿勢と「欠陥ありなら failed」だけを課している。Codex に渡す指示文は `references/subagent-waiting.md` の雛形が `<レビュー指示をそのまま書く>` だけで、中身は G が毎回組み立てる。Task サブエージェントをレビュアーにする経路（`gate-runner.md` の needs-reviewer）も、渡すのは受け入れ条件の所在と diff の範囲だけ。

#351（#281 PR-A）は収束ルールを「2 周目の終わりに G が違反文を引用して仕分ける」手順にし、143 行目に「一般則は 1 周目に適用、2 周目からは収束ルールが優先」の一文を足した。主と確認した方針（issue #349 のコメント「判定は全周で同じにする」）はこの周ごとの判定の分け方を改め、判定を全周共通にする。周で変わるのは、止める指摘が残ったときの動き方（1 周目は failed、2 周目以降は `needs-approval`）だけ。

## Goals / Non-Goals

**Goals:**

- 指摘 1 件が、深刻度・検証済みか・根拠の引用・場所・発生条件・直し方を揃えた状態で届くようにする
- マージを止めるかの判定を 1 か所に書き、1 周目の分岐・2 周目以降の仕分け・G の再開節・合格条件がすべてそれを参照する
- Codex 経路と Task サブエージェント経路で同じ書式を渡す

**Non-Goals:**

- R1 の観点に守備範囲を足す（#287）、PR 単位のトークン累計（#288）
- 新 Codex モード（App Server）の review thread の指示文（`references/codex-develop.md`）。従来モードの exec と needs-reviewer だけを対象にする
- 手順 2-2（failed の原因分類とモデル昇格）、決める役の出力契約
- 周回キャップ（既定 2 周・3 周目は主の続行指示のみ・方式の書き換え後の全体レビュー）の変更

## Decisions

**書式の正本は SKILL.md 手順 2-1 に 1 か所だけ置き、他の経路は「そのブロックをそのまま貼る」と参照する。** Codex はレビュー対象リポの中で動き、プラグインの SKILL.md を読めないので、指示文には書式そのものが入っていなければならない。一方で雛形と needs-reviewer に書式を再掲すると片方だけ古くなる（2026-09 の書き換え漏れと同じ構造）。そこで SKILL.md に貼り付け用のブロック（固定書式・深刻度の定義・全件列挙の 1 文・再レビュー時の制限）を置き、`subagent-waiting.md` の雛形は「SKILL.md 手順 2-1 のレビュアー向け指示ブロックをそのまま貼る」＋全件列挙の 1 文、`gate-runner.md` の needs-reviewer payload は「レビュアーに渡す指示: SKILL.md 手順 2-1 のブロック」の行を持つ。全件列挙の 1 文は受け入れ条件が雛形への記載を求めているので雛形にも書く（同じ 1 文の複写で、定義の言い換えではない）。

**書式に「根拠」欄を足す（issue 本文の提案に無い欄）。** issue の運用ルール 5 と主のコメントは「G が引用を確認する」ことを求め、#351 の引き継ぎコメントは「書式に引用欄を持たせれば G が組み立てずに済む」としている。`blocking` のときだけ必須で、値は受け入れ条件または PR が触れる spec の原文の引用、または例外 3 種（安全機構の穴・データ破壊・無言の機能不全）のどれか。

**判定（全周共通）は SKILL.md に 1 か所だけ書く。** 文: 「マージを止めるのは、深刻度が `blocking` で、根拠の引用を G が記録先の受け入れ条件または PR が触れる spec（delta spec を含む）の原文と照合できた（または例外 3 種に当たる）、かつ検証が `confirmed` の指摘だけ。それ以外は follow-up issue。レビュアーの深刻度ラベルは参考にとどめる」。143 行目の一文はこの判定への参照と「周で変わるのは動き方だけ」に置き換え、収束ルールの「2周目の終わりにやること」の手順 1 は引用元の範囲と記録の義務を残しつつ、止めるかどうかの基準は判定を参照する形にする。

**例外 3 種でも `confirmed` は要る。** 主のコメントは例外を「引用できなくても `blocking` として止める」と書いており、緩めているのは引用の要件だけと読む。`plausible` の安全機構の穴は follow-up issue に回るが、同じ PR が failed で W に戻るなら W がその場で直すか反証してよい。代案の「例外は `plausible` でも止める」は、推測だけの指摘で周回を開けることになり、#281 の往復の原因（レビュアーのラベルがそのまま周回を開けた）を再び持ち込むので採らない。

**follow-up issue を切るのは、G が手順 3 へ進むとき。** 1 周目で failed にするときは、止めない指摘を failed の PR コメントに一覧で残すだけにして issue は切らない（W が同じ周で直すことがあり、先に切ると重複する）。手順 3 へ進む時点で未解決の止めない指摘を follow-up issue にし、URL を仕分けの PR コメントに記録する。2 周目以降の仕分けは #351 どおり。

**再レビューの制限は深刻度で書く。** 差分限定の再レビューでは前回指摘の状態（`fixed` / `unresolved` / `wontfix`）を付けて閉鎖を確認するだけで、新規指摘は出さない（収束ルールの差分限定と同じ）。方式の書き換えで全体レビューに戻った周でも、新規に出してよい深刻度は `blocking` だけ。「直し方」どおりに直した箇所は再指摘せず、直し方自体が誤っていたならレビュアー側の誤りとして `wontfix` 相当の記録にする。

**Codex ルーブリックの実測を tasks の先頭に置き、結果で分岐する。** 実測は `codex exec -c approval_policy=never -c model_reasoning_effort=medium -` に、書式を指定しない短いレビュー指示と小さな diff を渡し、出力に `[P0]`〜`[P3]` の見出し・`priority`・`confidence_score` のどれかが現れるかを見る。
- 適用されない（見込み）: 指示文に書式を書く（上のブロックを貼る経路がそのまま答えになる）。対応表は置かない
- 適用される: 書式ブロックは貼ったまま（根拠・検証の欄は Codex のルーブリックに無いため）、SKILL.md に Codex の JSON（`priority` / `confidence_score` / `code_location`）から固定書式への対応表を置く。`confidence_score` は `confirmed` の代わりにしない（`confirmed` は実行・テストでの裏取りを指す）
実測結果は change 内の `codex-rubric-measurement.md` に残し、(3b) で PR コメントに転記する。

**#352 を同梱し、要約受領の分岐は再開節の 1 か所に置く。** needs-reviewer 節の「手順 3 以降を続ける」は、再開節の「レビュアーの要約受領」を参照する 1 文に置き換える。再開節の分岐は「指摘が無ければ手順 3 以降。残っていれば判定を通し、止める指摘が無ければ follow-up issue に切って手順 3 以降、あれば 1 周目は failed、2 周目と続行指示の周は保留」に書き換える（1周目・failed・2周目・仕分けの語は残るので #281 の既存テストはそのまま通る）。

## Risks / Trade-offs

- [1 周目でも `should` や `plausible` が failed にならず、本物の欠陥が follow-up issue に流れる] → 例外 3 種は引用なしでも止める。流れた指摘は follow-up issue として残るので消えない。主が承認済みの方針
- [レビュアーが根拠欄を埋めずに `blocking` を付ける] → G が照合し、照合できない `blocking` は止めない側に回す。判定の基準は G の照合で、レビュアーのラベルではない
- [書式ブロックが長くなり Codex の指示文と実行時間が伸びる] → ブロックは書式と定義表だけに絞る。実行時間の上限は既存の待ち方の正本が扱う
- [実測の結果が「部分的に適用」のように分岐のどちらにも当てはまらない] → 書式ブロックを貼る経路は両分岐で共通なので、対応表を置くかだけの判断になる。どちらとも言えない出力なら対応表は置かず、実測結果を PR コメントに残す
