## Context

develop の 1 ループは、W が仕様化判断を記録先に記録し（`仕様化判断: する|しない`）、「しない」ならテストを先に書いて実装し、PR を Draft で作って仕様宣言を投稿し、そのあと本体が pr-review-gate の G を段ごとに起こす。本体は Edit でコードを書かない（SKILL.md「本体の役割」）。テスト作成はどの判定でも必須で（`decision-criteria.md`「どの判定でも変えないもの」、`dev-workflow-execution-strategy` の「Step B 基準の重心移動」の MUST NOT）、1 語の typo にも W の起動と回帰テストが付く。

主の決定（issue #1584。テスト必須を緩めることは 2026-11-07 に主が承認）: 「仕様化しない」の一覧のうち typo・lint・コメント・フォーマット・ワンライナー fix・挙動を変えない設定値に当たり、既存のテストかチェックで確かめられる変更は、新しいテストと W の起動を省き、本体が直接直してよい。記録先・判断の記録・pr-review-gate は残す。どこまでを「軽い」に入れるかは「仕様化しない」の一覧を使い、新しい線引きを作らない。

同じ並びの先例は文言合わせの通し方（archive `2026-10-12-spec-wording-sync-light-path`）で、判断のコメントの 1 行目を変えず 2 行目以降の行で通し方を見分け、ゲートの照合コマンドを文書に書いて bats が fixture で走らせる、という形を取った。この change もその形に揃える。

## Goals / Non-Goals

**Goals:**

- typo 相当の修正が、W を起こさず、新しいテストを書かず、記録先・判断の記録・pr-review-gate を通って PR まで進む
- 条件を外れる変更に `通し方: 軽い` を書いた PR を、ゲートがレビュアーを起こす前に failed で止める
- 仕様化判断の 1 行目の契約（`^仕様化判断: (する|しない)$`）と、それを読む既存の jq・bats を変えない
- `skills/develop/SKILL.md` の起動時の予算（`tests/develop-startup-budget.txt`）を動かさない

**Non-Goals:**

- develop のコマンドの説明文を、会話で頼まれた修正でも必ず通すと読める文にすること（#1583 の範囲。親エピック #1585 の注意書き）
- 「仕様化しない」の一覧を広げる・狭めること。内部リファクタ・依存の版上げ・受け入れ条件が明記された機械的な振る舞い変更は軽い通し方に入れない（issue が挙げた 6 種類に限る）
- レビュー重量（light / full）の判定・三表の照合・リスク宣言・合格処理の整合表を変えること
- 受け入れたリスク（入れてよくない修正がテスト無しでマージされうる）を機械で塞ぎ切ること。導入後の記録の見直しで確かめる（issue の備考）
- `plugins/dev-workflow/scripts/` へのスクリプトの追加（照合は文書のコマンド数行で足り、bats が文書から抜き出して fixture で走らせる。先例と同じ）

## Decisions

### D1. 判定と記録は本体が行い、判断のコメントの 2 行目以降の 3 行で見分ける

W を起こさないので、仕様化判断の記録は本体が投稿する。1 行目は `仕様化判断: しない` のまま、2 行目以降に次の 3 行を足す。

```
仕様化判断: しない
理由: typo の修正だけ（decision-criteria.md Step B「仕様化しない」の 1 つ目）
通し方: 軽い
種類: typo
確かめ方: bash plugins/casting/scripts/casting-check.sh
```

- `通し方:` の行は正規表現 `^通し方: 軽い$` に完全一致させる
- `種類:` の値は `typo` / `lint` / `コメント` / `フォーマット` / `ワンライナー fix` / `設定値` のどれか 1 つちょうど（`^種類: (typo|lint|コメント|フォーマット|ワンライナー fix|設定値)$`）。2 種類以上が混ざる変更は軽い通し方に入れない（1 つの種類に収まることを G が差分で確かめられるようにするため）
- `確かめ方:` の行は空でないコマンド 1 つ（`^確かめ方: .+`）。変更を確かめる既存のテストかチェックで、本体が直したあとに走らせて終了コード 0 を見たもの

捨てた案:

| 案 | 捨てた理由 |
|---|---|
| 1 行目に 3 つ目の値を足す（`仕様化判断: 軽い`） | 1 行目の正規表現は `spec-reviewer.md`・`worker/spec.md`・`pass.md` の jq・`declarations.md`・bats が共有する完全一致の契約。値を増やすと全部を同時に直すことになり、古い版のゲートが「記録なし」と読む（先例 D1 と同じ理由） |
| `種類:` の行を持たない | ワンライナー fix の「1 行」を機械で測る手がかりが無くなり、条件外の典型（2 ファイル以上で挙動が変わる変更）を G の読み取りだけに頼ることになる |
| `確かめ方:` を記録先ではなく PR 本文に書く | 記録先が issue のとき、判断の根拠が 2 か所に分かれる。照合側は既に最新の仕様化判断のコメントの本文を読んでいる |

### D2. 当てるかどうかは本体が W を起こす前に決め、迷ったら当てない

本体は W を `段: spec` で起こす前に、記録先の本文から当てる条件を判定する。記録先がまだ無い会話の依頼では、記録先を作るより先に、本体が依頼から受け入れ条件を整理してその受け入れ条件で判定する（当てるなら本体が Draft PR を作る。当てないなら Draft PR を作らずに W を起こし、これまでどおり W が作る）。順序を「整理 → 判定 → Draft PR → 判断の記録」の 1 通りにするのは、当てない依頼で本体と W が二重に Draft PR を作らないためと、入口 0 の「判断の記録より先に記録先がある」を崩さないため。入口 0 の「W が Draft PR を作る」には、軽い通し方のときだけ本体が作る例外を足す（`dev-workflow-develop` の「入口 0 は記録先を決める」の MODIFIED）。迷ったら当てず、これまでどおり W を起こす（interactive でも主に聞かない。先例と同じく、手間を減らすための通し方に質問の往復を入れない）。interactive・channel・unmanned で同じ条件を使う。unmanned では、本体（憲法のメイン）が W の (3b) の代わりに Draft PR の作成と `agent-review:pending` の付与を行う。

### D3. 軽い通し方の本体の手順

1. 記録先が無ければ（D2 の判定で当てると決めたあと）、`worker/spec.md`「記録先の用意」と同じ手順で Draft PR を作り、整理した受け入れ条件を本文に書く（判断の記録より先）
2. 仕様化判断（D1 の 5 行）を記録先に投稿する。投稿の前に直さない
3. 直す。変更の記録の決まりがあるリポでは、その記録も書く（claude-harness では `plugins/<name>/changes/<番号>.md`）
4. `確かめ方:` のコマンドを走らせ、終了コード 0 を確かめる
5. commit・push し、PR を Draft のまま用意する（issue が記録先なら `gh pr create --draft`、本文に `Closes #<issue>`）
6. 仕様宣言を `仕様: 変更なし — 理由: 軽い通し方（<種類>）。…` の形で PR コメントに投稿する（`declarations.md` の「変更なし＋理由」形のまま）
7. (4) の G を起こす（以降は今の 1 ループと同じ）

直す途中か確かめる途中で条件を外れると分かったら（2 種類以上が要る・ワンライナー fix 以外の種類で挙動が変わる・ワンライナー fix で 1 ファイルの 1 行に収まらないか直し方に選択肢がある・`確かめ方:` のコマンドが 0 で終わらない・確かめられる既存のチェックが無い）、本体は手を止め、ここまでの編集を commit してから W を `段: spec` で起こし、起動指示に外れた理由を書く。W は `通し方:` の行の無い仕様化判断を投稿し直し（「する」か「しない」かは W が決め直す）、テストを書いて通常の通し方で進める。

### D4. ゲートは前提確認と重さ判定の段で条件を確かめる

確かめる場所は、`stages/prepare.md` の手順 1（前提を揃える）の最後、対象 HEAD を固定した直後とする。

捨てた案:

| 案 | 捨てた理由 |
|---|---|
| 合格処理の段（`stages/pass.md` の手順 5 の整合表）に行を足す | レビュアーを起こしたあとになり、条件外の PR にもレビューの費用が掛かる。合格処理の段は返しうる Status に failed を持たない |
| 照合と振り分けの段（`stages/triage.md`）で確かめる | ここもレビュアーのあと。仕分け表はレビュアーの指摘を扱う表で、記録先の通し方の検査は性質が違う |

前提確認と重さ判定の段は今 `needs-reviewer` / 保留 / `重複で降りた` しか返さないので、返しうる Status に failed を足す（`gate-runner.md` の段の表と `dev-workflow-develop` の段の表の Requirement）。failed の `次の段:` は既存の規則（戻した指摘が順 3 だけでなければ `前提確認と重さ判定`）のままで足りる。

### D5. 機械で測る点と G が読んで判断する点を分ける

最新の仕様化判断のコメント（`DEC`）に `^通し方: 軽い$` の行があるときだけ、G は次を確かめる。1 つでも外れたら条件外。

機械で測る点（文書にコマンドを書き、bats が抜き出して fixture で走らせる）:

```bash
DEC=$(gh api --paginate --slurp repos/$R/issues/$REC/comments | jq -r 'add | [.[] | select(.body | split("\n")[0] | test("^仕様化判断: (する|しない)$"))] | last | .body')
LIGHT=$(printf '%s\n' "$DEC" | grep -cx '通し方: 軽い')     # 1 以上なら軽い通し方
printf '%s\n' "$DEC" | head -1                               # 「仕様化判断: しない」ちょうど
KIND=$(printf '%s\n' "$DEC" | sed -n 's/^種類: //p' | head -1)  # 6 種類のどれかちょうど
printf '%s\n' "$DEC" | grep -c '^確かめ方: .'                # 1 以上
FILES=$(gh api --paginate repos/$R/pulls/$N/files --jq '.[] | "\(.additions) \(.deletions) \(.filename)"' | grep -vE ' ([^ ]*/)?changes/[0-9]+\.md$')
printf '%s\n' "$FILES" | grep -c ' openspec/'                # 0
printf '%s\n' "$FILES" | awk '{n++; a+=$1; d+=$2} END {print n+0, a+0, d+0}'   # KIND がワンライナー fix なら「1 a d」で a ≤ 1・d ≤ 1
```

- 変更の記録のファイル（パスが `changes/<数字>.md` で終わるもの）は数えない。リポの決まりで足す記録で、軽い通し方の差分そのものではない
- `REC` は手順 1 の 3 で解決した記録先（issue 参照が無い PR では PR 自身）。合格処理の段の解決と同じ規則
- grep の 0 件は終了コード 1 になるので、終了コードではなく出力の値で判定する（先例と同じ）

G が差分（`gh pr diff $N`）を読んで判断する点: 変更の記録のファイルを除くすべての変更が `種類:` の種類に収まること。判断の中身は種類で 2 つに分かれる。typo・lint・コメント・フォーマット・設定値は、プログラムの挙動を変えないこと（設定値なら、値を変えても挙動が変わらないこと）。ワンライナー fix は Step B「仕様化しない」の定義どおり明白なバグの 1 行修正で、挙動を変えるのが本来なので、挙動不変は求めず、直し方に選択肢がないことを判断する（例: 比較の向きの取り違えを直す 1 行は条件内、既定値を選び直す 1 行は直し方に選択肢があるので条件外）。

ワンライナー fix 以外の種類にファイル数や行数の上限を置かない。issue の「新しい線引きを作らない」に従い、typo を何か所直すかの上限は決めない。条件外の典型（2 ファイル以上で挙動が変わる変更）は、`種類: ワンライナー fix` と書けば機械の点で、それ以外の種類と書けば G の判断の点（挙動を変えない）で止まる。

捨てた案:

| 案 | 捨てた理由 |
|---|---|
| どの種類も変更ファイルを 1 つに限る | 「仕様化しない」の一覧に無い新しい線引きになる。複数ファイルの typo の直しを軽い通し方から外す理由が無い |
| G の判断を置かず、機械の点だけにする | 「挙動が変わらない」は差分の行数からは決まらない。typo と書いて関数の中身を変えた PR が通る |
| 照合をスクリプトにする | 先例と同じく文書のコマンド数行で足り、`scripts/` を増やさない。bats は文書からコマンドを抜き出して走らせる |

### D6. 結果は PR コメントに残し、条件外は failed で返す

G は確かめた結果を PR コメントに残す。1 行目は `^軽い通し方の確認: (条件内|条件外)$` に完全一致させ、2 行目は `対象 HEAD: <40 桁フル SHA>`、そのあとに確かめた点ごとの結果（条件外なら外れた点）を書く。

- 条件内: 手順 2-0（レビュー重量の判定）へ進む
- 条件外: `agent-review:pending` を外して `agent-review:failed` を付け、develop の G は Status failed・`次の段: 前提確認と重さ判定`・`原因: 軽い通し方の条件外` で返す。develop 以外の呼び出し元は、PR コメントの結果を見て通常の通し方に戻す
- `通し方: 軽い` の行が無い PR では、この確認をせず、コメントも投稿しない

本体は `原因: 軽い通し方の条件外` の failed を受けたら、原因分類でモデルを上げず、W を `段: spec` で新しく起こす（D3 の外れたときと同じ。起動指示に G の確認コメントの URL を書く）。W は `通し方:` の行の無い仕様化判断を投稿し直し、テストを書いて同じ PR に積む。同じ記録先で、条件外と判定されたあとに `通し方: 軽い` を投稿し直さない（差し戻しを避ける手段にしないため。先例の「R1 を一度起こした change は切り替えない」と同じ考え方）。

条件内で通ったあと、通常のレビューで G が修正を求める failed を返したとき（照合と振り分けの段でも保留の解除の段でも）は、W がまだ起きていないので今の「W を再開する」には入れない。本体も自分では直さない（本体が直してよいのは軽い通し方の最初の修正だけで、レビューの指摘への修正まで広げると、本体がテスト無しで直す範囲がレビューの結果しだいで広がるため）。本体は W を `段: spec` で新しく起こし、起動指示に failed の Gate Result と仕分けコメントの URL を書く。W の model は既存の原因分類の規則で決める。W は `通し方:` の行の無い仕様化判断を投稿し直してテストを書き、同じ PR に積む（W が起こされる経路ではテスト必須のまま、という `dev-workflow-spec-review` の要件と揃える）。W が起きた PR は以後通常の通し方で、そのあとの G は failed の `次の段:` によらず前提確認と重さ判定の段から起こす（判断の記録が変わったので、照合と振り分けから再開すると新しい判断が前提確認で読まれないため）。

捨てた案:

| 案 | 捨てた理由 |
|---|---|
| レビューの指摘も本体が直す | 本体がテスト無しで直す範囲がレビューの結果しだいで広がる。修正後の差分が軽い通し方の条件に収まるかを誰も確かめない |
| W を `段: implement` で起こし、`通し方: 軽い` の判断のまま直させる | W が起こされる経路のテスト必須とぶつかる。W が「しない」でテストを書くのか書かないのかが判断の記録から決まらない |

### D7. 動作確認では `確かめ方:` のコマンドを G が走らせる

合格処理の段の手順 4（動作確認）で、軽い通し方の PR は `確かめ方:` のコマンドを G が PR の HEAD の作業ツリーで走らせ、表の 1 行（手順＝そのコマンド、結果＝終了コードと出力の要点）にする。新しいテストが無い代わりに、既存のチェックが実際に走ったことを証拠に残す。ただしそのコマンドが全体のテスト（claude-harness の `scripts/test.sh` のように、テストランナーを絞らずに起動するもの）なら、既存の規則どおり CI の結果で扱う。

### D8. SKILL.md の起動時の予算を動かさない

`skills/develop/SKILL.md` は予算 86400 バイトに対し 86392 バイトで、残りは 8 バイト。足すのは 4 か所（禁止事項の例外・入口 0 の例外・(1) の前の分岐・(4) の failed の戻し方）で、それぞれ `references/decision-criteria.md` Step B を指す短い文にする。足した分と同じ以上のバイト数を、同じファイルの中の文言合わせの通し方の記述（(1) の 3 行と (4) の 2 行）を、正本（`decision-criteria.md` Step B と `worker/spec.md`）を指す短い文に言い換えて削る。言い換えたあとも、`spec-wording-sync-light-path.bats` と `develop-skill.bats` が見ている語句は残す。

## Risks / Trade-offs

- [入れてよくない修正がテスト無しでマージされうる] → 主が受け入れたリスク。G の判断の点（5 種類は挙動を変えない、ワンライナー fix は直し方に選択肢がない）と、レビュー重量の判定・レビュアーのレビューは今どおり掛かる。導入後数週間、`通し方: 軽い` の記録を見直す
- [`確かめ方:` のコマンドが変更を本当に確かめているかは機械で見ない] → 本体の判断に任せる。G は動作確認でそのコマンドを走らせ、レビュアーが差分と一緒に見る
- [変更の記録のファイルを `changes/<数字>.md` の形で除くので、その形の別のファイルも数えない] → 変更の記録のファイルは機械の点と G の判断の点の両方から外すので、軽い通し方の確認ではその中身を見ない。その形のファイルに変更の記録以外の中身を書いて通り抜けた場合は、レビュアーが差分全体と一緒に見る（`dev-workflow-pr-review-gate` の「軽い通し方の確認の守備範囲」）
- [前提確認と重さ判定の段に failed が増える] → 本体の failed の扱いに、原因が「軽い通し方の条件外」のときの分岐を足す。ほかの failed の扱いは変えない
- [SKILL.md の文言合わせの通し方の記述を短くする] → 規則は正本（`decision-criteria.md`・`worker/spec.md`）にあり、SKILL.md は正本を指すだけになる。bats が見ている語句は残す

## Migration Plan

文書とテストだけの変更。マージ後、次に develop が起動したときから効く。戻すときはこの PR の差分を戻す。マージ前後に本体が実機で 2 件を確かめる（typo 相当の修正を軽い通し方で回す、条件外の変更で G が failed を返す）。
