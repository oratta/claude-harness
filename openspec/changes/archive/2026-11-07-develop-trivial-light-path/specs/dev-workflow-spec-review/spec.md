## ADDED Requirements

### Requirement: 些細な修正は軽い通し方で新しいテストと W の起動を省く
develop スキルは、仕様化判断が「しない」になる変更のうち、typo・lint 指摘の修正・コメントの修正・フォーマットの変更・ワンライナー fix・挙動を変えない設定値の変更のどれか 1 種類だけでできていて、既存のテストかチェックのコマンドで確かめられる変更に、新しいテストの作成と W の起動を省く通し方（以下「軽い通し方」）を持たなければならない（MUST）。記録先・仕様化判断の記録・pr-review-gate は省いてはならない（MUST NOT）。当てる条件・省くもの・残すものの正本は `references/decision-criteria.md` の Step B の小節に置き（MUST）、記録の書式の正本は `references/roles/spec-reviewer.md` の「判断記録の契約」に置く（MUST）。


#### Scenario: Step B に軽い通し方の小節がある
- **WHEN** `references/decision-criteria.md` の Step B を読む
- **THEN** 「仕様化しない（コード直行）」の小節と同じ並びに軽い通し方の小節があり、当てる条件（6 種類のどれか 1 つだけ・既存のテストかチェックで確かめられる）・省くもの（新しいテストの作成と W の起動）・残すもの（記録先・判断の記録・pr-review-gate）の 3 点が書かれている

#### Scenario: 6 種類に入らない「しない」の変更には当てない
- **WHEN** 変更が振る舞いの変わらない内部リファクタ、依存の版上げ、または受け入れ条件が明記された機械的な振る舞い変更である
- **THEN** 軽い通し方は当たらず、これまでどおり W を起こし、テストを書く

#### Scenario: 確かめる既存のチェックが無い変更には当てない
- **WHEN** 変更は typo の修正だけだが、変更を確かめる既存のテストもチェックのコマンドも無い
- **THEN** 軽い通し方は当たらず、これまでどおり W を起こし、テストを書く

### Requirement: 軽い通し方の 6 種類は挙動を変えないものとワンライナー fix に分けて判定する
軽い通し方の 6 種類は 2 つに分けて判定しなければならない（MUST）。typo・lint 指摘の修正・コメントの修正・フォーマットの変更・設定値の変更の 5 種類は、プログラムの挙動を変えないことを条件にする（設定値なら、値を変えても挙動が変わらないこと）。ワンライナー fix は Step B「仕様化しない」の定義どおり明白なバグの 1 行修正で、1 ファイルの 1 行（追加 1 行以下・削除 1 行以下。変更の記録のファイルは数えない）に収まり、直し方に選択肢がなく、既存のテストかチェックで直ったことを確かめられることを条件にする。ワンライナー fix では、挙動が変わることを条件外の理由にしてはならない（MUST NOT）。

#### Scenario: 既存のチェックで確かめられる明白な 1 行のバグ修正は当たる
- **WHEN** 変更が、明白なバグを直し方の選択肢なく直す 1 ファイルの 1 行の修正で、挙動は変わるが、既存のテストかチェックのコマンドで直ったことを確かめられる
- **THEN** 軽い通し方が `種類: ワンライナー fix` で当たり、挙動が変わることは条件外の理由にならない

#### Scenario: 直し方に選択肢があるバグの修正には当てない
- **WHEN** 変更は 1 行のバグ修正だが、直し方が複数考えられる
- **THEN** 軽い通し方は当たらず、これまでどおり W を起こし、テストを書く

### Requirement: 軽い通し方の分類の守備範囲
「些細な修正は軽い通し方で新しいテストと W の起動を省く」と、6 種類を分けて判定する要件の守備範囲を、次のとおりとする（MUST）。入力は記録先の本文（記録先が無い会話の依頼では本体が整理した受け入れ条件）と本体が直す差分で、本体は「些細だ」と甘く読むことがある前提で扱う。拾う誤りは、6 種類に入らない変更・2 種類以上が混ざる変更・確かめる既存のチェックが無い変更・直し方に選択肢があるバグ修正に当てること。`確かめ方:` のコマンドが変更を本当に確かめているかと、明白と読んだが直し方が他にもあった 1 行修正は通ることを許す（レビュアーが差分と一緒に見る。主が受け入れたリスク）。穴を塞ぎ切ることは完了条件にしない。

#### Scenario: 確かめ方が変更を確かめていなくても分類は通す
- **WHEN** 本体が `確かめ方:` に、変更した箇所を通らない既存のチェックのコマンドを書いた
- **THEN** 分類はこれを止めず、pr-review-gate のレビュアーが差分と一緒に見る

### Requirement: テスト作成の必須の例外は軽い通し方だけにする
`references/decision-criteria.md` の「どの判定でも変えないもの」は、テスト作成が必須であることを残したうえで、例外が軽い通し方だけであることと、軽い通し方では `確かめ方:` の既存のテストかチェックを走らせることが新しいテストの代わりになることを書かなければならない（MUST）。W が起こされる経路では、どの判定でもテスト作成を省いてはならない（MUST NOT）。

#### Scenario: 必須の行に例外が書かれている
- **WHEN** `references/decision-criteria.md` の「どの判定でも変えないもの」を読む
- **THEN** 「テスト作成は全経路で必須」の文と同じ段落に、例外が軽い通し方だけであることと、`確かめ方:` のコマンドを走らせることが代わりになることが書かれている

### Requirement: 軽い通し方の判断は本体が判断のコメントの 2 行目以降に 3 行を足して記録する
軽い通し方では W が起こされないので、本体が仕様化判断を記録先に投稿しなければならない（MUST）。1 行目は `仕様化判断: しない` のまま変えてはならず（MUST NOT）、2 行目以降に `^通し方: 軽い$` に完全一致する行、`^種類: (typo|lint|コメント|フォーマット|ワンライナー fix|設定値)$` に完全一致する行、`^確かめ方: .+` に当たる行（変更を確かめる既存のテストかチェックのコマンド 1 つ）を 1 行ずつ書かなければならない（MUST）。本体は投稿する前に直してはならない（MUST NOT）。

#### Scenario: 判断記録の契約に軽い通し方の行の書式がある
- **WHEN** `references/roles/spec-reviewer.md` の「判断記録の契約」を読む
- **THEN** `通し方: 軽い` の行と `種類:` の行（6 つの値）と `確かめ方:` の行の書式が書かれ、この行がある判断は本体が投稿し、照合側（pr-review-gate の前提確認の段）が最新の仕様化判断のコメントの本文から読むことが書かれている

#### Scenario: 行の無い「しない」はこれまでどおり
- **WHEN** 記録先の最新の仕様化判断のコメントが `仕様化判断: しない` で、`通し方: 軽い` の行を持たない
- **THEN** これまでどおり W がテストを先に書いて実装する判断として扱う

### Requirement: 軽い通し方では本体が直し、仕様宣言までを行ってから G を起こす
軽い通し方では、本体は (1)〜(3) の W を起こさず、判断の記録のあとに自分で直し、`確かめ方:` のコマンドを走らせて終了コード 0 を確かめ、commit・push し、PR を Draft のまま用意し（issue が記録先なら `Closes #<issue>` を本文に書く）、仕様宣言を「変更なし＋理由」形で投稿してから (4) の G を起こさなければならない（MUST）。手順の正本は `references/decision-criteria.md` の Step B の軽い通し方の小節に置く（MUST）。

#### Scenario: 本体の手順が書かれている
- **WHEN** `references/decision-criteria.md` の軽い通し方の小節を読む
- **THEN** 判断の記録・直す・`確かめ方:` のコマンドを走らせる・commit と push・Draft の PR・「変更なし＋理由」形の仕様宣言・G を起こす、の順の手順が書かれている

### Requirement: 記録先がまだ無い会話の依頼では、本体が軽い通し方を決めてから Draft PR を作る
記録先がまだ無い会話の依頼では、本体は次の順に進めなければならない（MUST）: ①依頼から受け入れ条件を整理する ②その受け入れ条件で軽い通し方を当てるかを決める（何も作る前に決める） ③当てるなら本体が Draft PR を記録先として作り、受け入れ条件を PR 本文に書く（作り方と本文の決まりは `references/roles/worker/spec.md`「記録先の用意」と同じ） ④判断を Draft PR のコメントに記録する。当てないなら Draft PR を作らずに W を `段: spec` で起こし、これまでどおり W が Draft PR を作る（SHALL）。

#### Scenario: 記録先が無い会話の依頼を軽い通し方で通す
- **WHEN** issue の無い会話の依頼が typo の修正で、本体が整理した受け入れ条件で軽い通し方が当たる
- **THEN** 本体が受け入れ条件を整理し、当てると決めてから Draft PR を作って受け入れ条件を本文に書き、そのあと判断を Draft PR のコメントに記録する。W は起こさない

#### Scenario: 記録先が無い会話の依頼で軽い通し方が当たらない
- **WHEN** issue の無い会話の依頼で、本体が整理した受け入れ条件では軽い通し方が当たらない
- **THEN** 本体は Draft PR を作らずに W を `段: spec` で起こし、W がこれまでどおり Draft PR を作る

### Requirement: 軽い通し方を途中で外れたら W を起こして通常の通し方に戻す
本体が直す途中か確かめる途中で軽い通し方の条件を外れると分かったとき（2 種類以上が要る・ワンライナー fix 以外の種類で挙動が変わる・ワンライナー fix で 1 ファイルの 1 行に収まらないか直し方に選択肢がある・`確かめ方:` のコマンドが 0 で終わらない・確かめる既存のチェックが無い）、本体は手を止め、ここまでの編集を commit してから W を `段: spec` で起こし、起動指示に外れた理由を書かなければならない（MUST）。W は `通し方:` の行の無い仕様化判断を投稿し直し、テストを書いて通常の通し方で進める（SHALL）。条件外と分かった記録先で `通し方: 軽い` を投稿し直してはならない（MUST NOT）。

#### Scenario: 確かめ方のコマンドが落ちた
- **WHEN** 本体が直したあと `確かめ方:` のコマンドを走らせ、終了コードが 0 でない
- **THEN** 本体は編集を commit して W を `段: spec` で起こし、W は `通し方:` の行の無い仕様化判断を投稿し直してテストを書く

### Requirement: 軽い通し方はどのモードでも同じ条件で当て、迷ったら当てない
本体は、W を `段: spec` で起こす前に、記録先の本文（記録先がまだ無い会話の依頼では、本体が依頼から整理した受け入れ条件）から軽い通し方を当てるかを決めなければならない（MUST）。当てるか迷ったら当ててはならず（MUST NOT）、これまでどおり W を起こす。当てるかどうかを主に聞いてはならない（MUST NOT）。interactive・channel・unmanned で同じ条件を使い（SHALL）、unmanned では本体が Draft PR の作成と `agent-review:pending` の付与を行う（SHALL）。

#### Scenario: 迷ったら W を起こす
- **WHEN** 本体が、変更が 6 種類のどれか 1 つに収まるか、既存のチェックで確かめられるかを決めきれない
- **THEN** 本体は主に聞かず、軽い通し方を当てずに W を `段: spec` で起こす

#### Scenario: unmanned でも同じ条件で当たる
- **WHEN** `references/decision-criteria.md` の軽い通し方の小節を読む
- **THEN** interactive・channel・unmanned で同じ条件を使うことと、unmanned では本体が Draft PR の作成と `agent-review:pending` の付与を行うことが書かれている
