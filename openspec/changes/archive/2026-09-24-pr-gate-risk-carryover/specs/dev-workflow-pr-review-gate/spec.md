## ADDED Requirements

### Requirement: 許容が必要な宣言は根拠ファイルを列挙する

pr-review-gate SKILL.md 手順 3 の「主のリスク許容が必要」の雛形は、許容を求めるリスクの発生源になっているファイルを列挙する行 `- 根拠ファイル: <パス>, <パス>` を持たなければならない（SHALL）。宣言の 1 行目・2 行目・行頭の文言の規約は「リスク宣言は 7 観点で判定し、新 3 観点も主のリスク許容待ちに流す」Requirement に従う。

#### Scenario: 雛形に根拠ファイルの行がある

- **WHEN** SKILL.md 手順 3 の「主のリスク許容が必要」の雛形を読む
- **THEN** `- 根拠ファイル:` の行がある

### Requirement: 前の HEAD の許容を新しい HEAD に引き継いでよい条件

pr-review-gate SKILL.md は、手順 3 で「主のリスク許容が必要」と判定したとき、手順 6 で主に聞く前に、前の HEAD で得た許容を引き継げるかを確かめる手順（手順 3-c。3-b の後ろに置く）を持たなければならない（SHALL）。前の HEAD の宣言は、同じ PR の `## リスク宣言` コメントのうち `主の回答: 許容` で始まる行（引き継ぎの形を含む）と `真正性確認: 済` の行の両方を持つ最新 1 件とし、その `対象 HEAD:` の SHA をスクリプトの前 HEAD に渡さなければならない（MUST）。引き継げるのは次のすべてを満たすときに限る（MUST）: ①`risk-carryover-check.sh` に前の HEAD・新しい HEAD・前の宣言の根拠ファイルを渡して終了コード 0 が返る ②前の HEAD の宣言に根拠ファイルの行がある ③引き継ぎの元の回答が「引き継ぎの元は真正性確認済みの主の直接の回答に限る」Requirement を満たす ④新しい HEAD のリスク宣言の本文が、`対象 HEAD:` 行を除いて前の HEAD の宣言の本文（末尾の `主の回答:` 以降の追記行を除いた部分）と同一である（リスク内容・該当する観点・発生条件・影響範囲と戻し方・根拠ファイルがすべて同じであることをこの一致で確かめる）。1 つでも満たさなければ、従来どおり手順 6 で主に聞かなければならない（MUST）。引き継ぎで省けるのは主への質問だけで、レビュー・動作確認証拠・仕様宣言の取り直しと手順 5 の実測は省いてはならない（MUST NOT）。これは手順 1 の「手順 1 から全工程をやり直す（前回の合格部分を流用しない）」と `gate-runner.md` の再レビューの同趣旨の文に対する唯一の例外であることを、3-c に書かなければならない（SHALL）。

この引き継ぎの判定（スクリプトと G の確認を合わせたもの）の守備範囲は次のとおりとする:

- 入力: G 自身が手順 1 で `git fetch` と main の取り込みを済ませたローカルの git リポジトリ（前の HEAD・新しい HEAD・base）、同じ PR の前の宣言コメント（`- 根拠ファイル:`・`主の回答:`・`真正性確認:` の行）、元の直接の回答リンク。G は協力的だが、列挙漏れと読み違いをする前提で扱う
- 拾いたい誤り: main 以外の commit（W の修正・rebase・force-push による履歴の書き換え）、許可リスト外のファイルでの衝突解消、許可リスト内のファイルでの版の行・並べ直し以外の変更、根拠ファイルの変更、根拠ファイルの行が無い宣言からの引き継ぎ、引き継ぎの記録そのものを回答リンクにする自己参照、真正性確認のやり直しの省略
- 通ることを許す入力の例: main 側が根拠ファイル以外の PR が触ったファイルを衝突なしで変えた取り込み（リスクの中身が変わるかは条件④で見る）、G が根拠ファイルを列挙し損ねた宣言、`"version"` を含む行の中身、CHANGELOG の並べ直しで項目の属する見出しが変わるもの、主のアカウントで代理投稿された元の回答
- 範囲外: 代理投稿の見分け、根拠ファイルの列挙の妥当性、merge の仕方の違いによる誤検出（引き継げない側に倒れるだけ）。これらを塞ぐことは本要件の完了条件にしない

#### Scenario: main の取り込みだけで HEAD が動いた

- **WHEN** 主が許容した PR で、G が手順 1 で main を取り込んで HEAD が動き、スクリプトが終了コード 0 を返し、新しい HEAD のリスクの中身が前と同じである
- **THEN** G は `needs-approval` を付けずに、引き継いだ宣言を投稿して手順 4・5 へ進む

#### Scenario: 根拠ファイルが変わった

- **WHEN** 前の HEAD と新しい HEAD の間で根拠ファイルの diff が空でない
- **THEN** 引き継げず、G は手順 6 で主に聞き直す。質問にはスクリプトの `NG:` 行を添える

#### Scenario: レビューで新しいリスクが見つかった

- **WHEN** スクリプトは終了コード 0 を返したが、新しい HEAD のレビューで観点や根拠ファイルが増え、宣言の本文が `対象 HEAD:` 行を除いて前の宣言と一致しない
- **THEN** 引き継げず、G は手順 6 で主に聞き直す

#### Scenario: 根拠ファイルの行が無い古い宣言

- **WHEN** 前の HEAD の宣言に `- 根拠ファイル:` の行が無い
- **THEN** 引き継げず、G は手順 6 で主に聞き直す

#### Scenario: 引き継いでもレビューは省かない

- **WHEN** SKILL.md の引き継ぎの手順を読む
- **THEN** 省けるのは主への質問だけで、手順 2 のレビュー・手順 4 の証拠・手順 3 の仕様宣言を新しい HEAD で出し直すこと、これが手順 1 の「前回の合格部分を流用しない」の唯一の例外であることが書かれている

#### Scenario: 前の HEAD の宣言の選び方

- **WHEN** 同じ PR に `## リスク宣言` コメントが複数あり、最新のものには `主の回答:` の行が無い
- **THEN** G は `主の回答: 許容` 系の行と `真正性確認: 済` の行の両方を持つ最新 1 件を前の宣言とし、その `対象 HEAD:` の SHA を前 HEAD としてスクリプトに渡す

### Requirement: risk-carryover-check.sh が差分の範囲と根拠ファイルの無変更を判定する

`plugins/dev-workflow/scripts/risk-carryover-check.sh [--base <ref>] <前 HEAD> <新 HEAD> <根拠ファイル>...` は、ローカルの git リポジトリだけを読み、次をすべて満たすとき終了コード 0、1 つでも外れたら終了コード 1 を返さなければならない（SHALL）: ①前の HEAD が新しい HEAD の祖先である ②`git rev-list <新> ^<前> ^<base>` の全件が 2 親の merge commit で、第 2 親が base の祖先、第 1 親が前の HEAD かこの集合の別の commit である ③各 merge commit の衝突解消したファイル（`git merge-tree --write-tree <第1親> <第2親>` の tree と merge commit の tree で差のあるファイル）が許可リストに入り中身の条件を満たす ④根拠ファイルそれぞれについて `git diff <前> <新> -- <ファイル>` が空である。許可リストは、`.claude-plugin/marketplace.json` と `plugins/*/.claude-plugin/plugin.json`（`"version"` を含む行を除いた本文が第 1 親か第 2 親の版と一致する）、および `CHANGELOG.md` とサブディレクトリの `CHANGELOG.md`（merge commit の版のすべての行が第 1 親か第 2 親の版に存在する）に限る（MUST）。`--base` の既定は `origin/main` とする。判定の守備範囲は「前の HEAD の許容を新しい HEAD に引き継いでよい条件」Requirement の守備範囲の段落に従う（スクリプトが担うのは、そこに挙げた誤りのうち commit・衝突解消・根拠ファイルの変更に関わるもの）。出力は `CARRYOVER=yes|no`・`MAIN_MERGES=<件数>`・`RESOLVED_FILES=<ファイル。無ければ none>` と、不可の理由ごとの `NG: <理由>` 行とする。引数不足・SHA が解決できない・根拠ファイルが 1 つも無い・git が `merge-tree --write-tree` に対応しないときは終了コード 2 を返さなければならない（SHALL）。

#### Scenario: main の取り込みだけで衝突なし

- **WHEN** 前の HEAD に main を衝突なしでマージした commit だけが積まれ、根拠ファイルは変わっていない
- **THEN** 終了コード 0、`CARRYOVER=yes`、`MAIN_MERGES=1`、`RESOLVED_FILES=none` を出す

#### Scenario: 版番号と CHANGELOG の衝突解消だけ

- **WHEN** main のマージで plugin.json の `"version"` 行と CHANGELOG.md が衝突し、版の行の選び直しと CHANGELOG の項目の並べ直しだけで解消した
- **THEN** 終了コード 0 を返し、`RESOLVED_FILES` にその 2 ファイルを出す

#### Scenario: main 側の変更で根拠ファイルが変わった

- **WHEN** main のマージで根拠ファイルの中身が変わった
- **THEN** 終了コード 1、`CARRYOVER=no` と、そのファイルを示す `NG:` 行を出す

#### Scenario: main 以外の commit が積まれた

- **WHEN** 前の HEAD と新しい HEAD の間に、merge commit でない commit（W の修正など）がある
- **THEN** 終了コード 1 と、その commit を示す `NG:` 行を出す

#### Scenario: 許可リスト外のファイルで衝突解消した

- **WHEN** merge commit が許可リストに無いファイルで自動マージの結果と違う中身になっている
- **THEN** 終了コード 1 と、そのファイルを示す `NG:` 行を出す

#### Scenario: 許可リストの JSON で版以外の行を変えた

- **WHEN** merge commit の plugin.json が、`"version"` 行を除いても第 1 親・第 2 親のどちらの版とも一致しない
- **THEN** 終了コード 1 を返す

#### Scenario: CHANGELOG に新しい文を足した

- **WHEN** merge commit の CHANGELOG.md に、第 1 親にも第 2 親にも無い行がある
- **THEN** 終了コード 1 を返す

#### Scenario: 前の HEAD が祖先でない

- **WHEN** 新しい HEAD が前の HEAD を含まない（rebase や force-push で履歴が書き換わった）
- **THEN** 終了コード 1 を返す

#### Scenario: 根拠ファイルが渡されない

- **WHEN** 根拠ファイルを 1 つも渡さずに呼ぶ
- **THEN** 終了コード 2 を返す

### Requirement: 引き継ぎの元は真正性確認済みの主の直接の回答に限る

pr-review-gate SKILL.md は、引き継ぎで主の許容を捏造できないように、次を条件として書かなければならない（SHALL）: ①前の HEAD の宣言に `主の回答: 許容` または `主の回答: 許容（引き継ぎ）` の行と `真正性確認: 済` の行がある ②引き継いだ宣言の回答リンクは、主が許容を述べた元の直接の回答を指し、引き継ぎの記録（エージェントが書いた宣言コメント）を指さない。引き継ぎが 2 回以上続いても元の直接の回答のままとする ③引き継ぐたびに、元の回答リンクに対して手順 5 の真正性確認をやり直し、新しい宣言に `真正性確認: 済` を追記する。

#### Scenario: 捏造防止の条件が書かれている

- **WHEN** SKILL.md の引き継ぎの手順を読む
- **THEN** 元の回答が真正性確認済みであること・回答リンクが元の直接の回答を指すこと・引き継ぐたびに真正性確認をやり直すことが条件として書かれている

#### Scenario: 引き継ぎが続く

- **WHEN** 引き継いだ宣言の HEAD から、さらに main の取り込みで HEAD が動いた
- **THEN** 新しい宣言の回答リンクは最初の直接の回答を指し、その回答に対して真正性確認をやり直す

### Requirement: 引き継いだ宣言の書式と合格条件

引き継いだ宣言は、前の宣言と同じ本文（行頭 `主のリスク許容が必要。` を含む）を新しい `対象 HEAD:` で出し直し、末尾に `主の回答: 許容（引き継ぎ） — <元の直接の回答リンク>（<日時>）`・`引き継ぎ元: <前の HEAD の 40 桁フル SHA> の宣言 <リンク>`・`引き継ぎの根拠: risk-carryover-check.sh 終了コード 0 — …`・`真正性確認: 済 — …` の 4 行を追記しなければならない（SHALL）。手順 5 の合格条件の表は、この 4 行が揃った宣言を許容済みとして扱う行を持たなければならない（SHALL）。手順 6 の復帰の表と `gate-runner.md` の取り直しの節は、手順 3 の引き継ぎの小節を参照しなければならない（SHALL）。

#### Scenario: 書式が SKILL.md にある

- **WHEN** SKILL.md の引き継ぎの小節を読む
- **THEN** `主の回答: 許容（引き継ぎ） — ` で始まる行と、引き継ぎ元・引き継ぎの根拠・真正性確認の行の書式がある

#### Scenario: 手順 5 が引き継いだ宣言を許容済みとして扱う

- **WHEN** SKILL.md 手順 5 の合格条件の表を読む
- **THEN** 引き継ぎの 4 行が揃った「主のリスク許容が必要」の宣言を合格可とする行がある

#### Scenario: G の指示書が引き継ぎを参照する

- **WHEN** `gate-runner.md` の取り直しの節を読む
- **THEN** 許容済みの PR で HEAD が動いたときは、主に聞く前に pr-review-gate 手順 3 の引き継ぎの小節を試すことが書かれている
