# Design

## Context

動機は proposal.md の Why を参照。現在の `epic_tree()` はルートと子を持つ子孫を毎回取得する。`SUB_ISSUES_QUERY` は子の一覧と閉じた PR をまとめて取得しているが、変更信号の `updatedAt` と `subIssuesSummary.completed` は取っていない。

`work()` と `backfill.py` は、対象を確認してから `lock()` → `stack()` → ロック fd の close を行う。`lock()` はディレクトリを fd で検査してファイルを開くが、ディレクトリ fd は返す前に閉じている。保存を足す際は、この検査済み fd をロック区間まで保持する必要がある。

## Goals / Non-Goals

**Goals:**
- 前回の取得が成功していれば、変わっていない部分木の問い合わせを省く。ルートの取得は省かない。
- 保存と現在の応答を混ぜる場合も、全体の深さ制限・重複排除・リポジトリの絞り込みを維持する。
- 保存の破損を GitHub の取得失敗と区別し、保存だけの障害では失敗表示にしない。

**Non-Goals:**
- 金額や台帳の行を保存して使い回すこと。保存するのは問い合わせで得た issue / PR の関連だけで、額は毎回 `timeline` が計算する。
- GitHub が親へ伝えない深い変更の完全検知、TTL や追加の問い合わせによる検知。
- `/cost` の全件取得、`cost_ledger.py` の `ISSUE_RE`、`attribution.bats` の変更。

## Decisions

### 子の変更信号を比較して部分木を再利用する

本体の指定どおり、`SUB_ISSUES_QUERY` の各子に `updatedAt` と `subIssuesSummary { total completed }` を加える。毎回ルートを取得し、子ごとにこれらの値と `closedByPullRequestsReferences` の一覧を保存した値と比較する。PR 一覧は番号・ヘッドブランチ・ベースのリポジトリ・fork の別を含め、順番だけの違いで再取得しない比較にする。

子を持つ子について、信号が一致し完全な保存済み部分木があればその先の GraphQL を省く。不一致・未保存ならその子を問い合わせ、返った孫にも同じ判定を適用する。葉は親の応答だけで処理する。現在の応答から消えた子の保存は集計に入れず、子が増減したときは現在の一覧を使う。ルート自身と直接の子を閉じた PR は毎回の応答を使う。

代案の毎回全件取得は変更を検出できるが #882 の回数条件を満たさない。ルートまで保存で省く方式は、直接の子の変化さえ確認できないので採らない。信号の限界は仕様の「穴を許す」節へ記す。

### 対象ロックと同じ安全な置き場に保存する

`${TMPDIR:-/tmp}/cost-ledger-timeline` の検査済みディレクトリ fd と対象ロックを、読み取りから保存完了まで保持する。ファイルはリポジトリとルート番号で区別し、形式の版・対象・確認時刻・比較信号・部分木の関連情報を保存する。別対象や別形式の保存を再利用しない。

保存ファイルの open・作成・置換はこの fd を基準とする。シンボリックリンクを辿らず、通常ファイル・所有者・権限を検査する。ロックの置き場自体が不安全なら既存どおり何も書かない。`lock()` と解放処理でディレクトリ fd の寿命を明示し、`work()` と `backfill.py` の呼び出し元の両方を対応させる。通常の hook と後追いが同じ対象の保存を同じ排他区間で扱う。

保存が無い・読めない・壊れている・形式や対象が違う場合は、その回の保存を使わず全件取得する。保存の検査では部分木の完全性と応答に必要な形も確かめ、一部だけ有効な保存から集計しない。取得全体に成功した結果だけを一時ファイルへ書き、fd 基準の置換で公開する。失敗した取得の途中結果は保存せず、前回の正常な保存を残す。保存の書き込みができなくても、取得済みの正常な結果は使う。

代案の作業ツリー内の保存や絶対パスの開き直しは、インストール成果物への書き込みや検査後のパス差し替えを招くため採らない。

### 上限と失敗の扱いを維持する

実際に呼ぶ GraphQL だけを `EPIC_MAX_QUERIES = 5` に数える。6 回目が必要なら呼ぶ前に `None` を返す。保存の再利用時もルートから数えた深さを検査し、別のリポジトリの子は辿らず、issue と PR は全体で重複を除く。保存する木はその時点の全体の重複排除で削った集合だけにはしない（次回の別の経路で欠落を生まないため）。

現在の GitHub の応答が取得不能・JSON でない・形が崩れている・100 件超なら、正常な保存があってもその失敗を隠さず `None`。部分結果や古い全体へ差し戻して成功に見せない。`stack()` の `子 issue 照会失敗`・子の引数を渡さない・合計行を積まない挙動はそのまま。

## Risks / Trade-offs

- [子より深い変更が子の信号に出ない] → 保存の関連情報が古くなり、額が古くなりうることを仕様の守備範囲に明記する。`/cost <番号>` は保存を使わない全件取得で正しい額を確認できる。既存の行は補正しない。
- [保存が消える・使えない] → 従来の全件取得と 5 回上限に戻る。保存がない状態で 6 回以上要る木は従来どおり失敗する。
- [保存の統合で重複・深さの検査を飛ばす] → 偽 `gh` と合成ログで未変更・変更・付け替え・重複と制限を検証し、`/cost` と額を比較する。
- [ロック資源の寿命を変えて後追いが壊れる] → `backfill.bats` と `timeline.bats` も回帰確認する。

## Migration Plan

既存の保存は無いので初回は全件取得。読めない版の保存も全件取得へ戻るため変換は不要。元の実装に戻しても保存は参照されない。hook の配線や依存パッケージは変えない。
