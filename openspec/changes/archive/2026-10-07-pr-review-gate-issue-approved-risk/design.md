## Context

pr-review-gate 手順 3（`skills/pr-review-gate/declarations.md`）は 7 分類のどれかに当たる PR を一律に「主のリスク許容が必要」とし、手順 6（`stages/hold.md`）で `needs-approval` を付けて主の返事を待つ。手順 5（`stages/pass.md`）の合格条件は、主の許容が回答リンク・会話で受領（#721）・引き継ぎ（3-c）のどれかで記録され、真正性確認が済んでいることを求める。

#721 で、会話ログに主の発言が実在するかを確かめる `plugins/dev-workflow/scripts/owner-reply-check.sh <セッション ID> <原文>` が入った（出力 `MATCH: <timestamp> <全文>` / `MATCHES=<件数>`、終了コード 0 = 実在 / 1 = 実在しない / 2 = 確かめられない）。

実物で確かめた事実（2026-10-07）:

- `/develop 723` は会話ログに `<command-name>/dev-workflow:develop</command-name>\n<command-args>723</command-args>` を含む文字列 1 行として残る（空白をまとめると `<command-name>/dev-workflow:develop</command-name> <command-args>723</command-args>`）。引数の後ろに自由文が続くこともある
- Orca 経路でエピックの子を起こすと、`epic-dispatch.sh launch` が子のセッションを `EPIC_DISPATCH_PARENT_EPIC=<エピック番号>` 付きで起動し、親が子のターミナルに `/develop #<N>` を打ち込む。この行は `origin.kind: "human"` で残り、主の打ち込みと区別できない。`EPIC_DISPATCH_PARENT_EPIC` はサブエージェント（G）にも引き継がれる（この issue の W で `725` を実測）
- サブエージェントの `CLAUDE_CODE_SESSION_ID` は親（本体）のセッション ID で、G は本体の会話ログを読める（#721 の design）
- issue 本文の最終編集日時は `gh api graphql -f query='{repository(owner:"<o>",name:"<r>"){issue(number:<N>){createdAt lastEditedAt}}}'` で取れる（未編集なら `lastEditedAt: null`）
- issue を起票したセッションの会話ログは、ゲートが動く PC に無いことがある（#723・#725 を起票したセッションのログはこの PC の `~/.claude/projects` に無かった）
- `issueify` は、主がその場で承認しなかった（「あとで見る」）issue に `agent-proposed` を付けて起票する

## Goals / Non-Goals

**Goals:**

- 主が書いたか承認した issue に目的として書いてある効果（資格情報・安全ゲート・エージェント権限の 3 分類）について、PR のたびに許容を聞かない
- 承認の証拠を、エージェントの自己申告ではなく会話ログのスクリプト確認で取る
- 合格したら主に 1 回だけ事後報告し、主が後から気づけるようにする

**Non-Goals:**

- 外部公開面の変化・データ喪失・課金/法務・プロダクトのユーザーに及ぶ影響は、issue に書いてあっても従来どおり聞く
- `owner-reply-check.sh` は変えない
- 引き継ぎ（#694）・3 周目の確認（#722）・依頼の出し直し（#724）は扱わない
- 起票したセッションの会話ログを別の PC から取りに行く仕組みは作らない（読めなければ当てずに主に聞く）

## Decisions

### 1. 宣言は「主のリスク許容が必要。」のまま残し、追記で状態を表す

「issue で承認済み」は第 3 の宣言文ではなく、「主のリスク許容が必要」の宣言に末尾 3 行を追記した状態とする:

```
issue で承認済み — issue #<N> の目的: 「<本文からの引用>」
承認の証拠: <起票の承認 | /develop の打ち込み>（セッション <セッション ID> / <日時>）原文: <原文>
真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh 終了コード 0）
```

当たった分類が 2 つ以上なら、1 行目を分類ごとに並べてよい（`issue で承認済み — <分類>: issue #<N> の目的: 「…」`）。宣言本文の `- 検知時点:` は `issue 記載済み` でなければならない。

理由: 「リスクなし宣言は本当にリスクが無い場合にしか出ない」という前提（手順 5 の書き換え禁止）を崩さないため。行頭を `主の回答: 許容` にしないのは、手順 3-c の「前の宣言の選び方」（`主の回答: 許容` と `真正性確認: 済` の両方を持つ最新 1 件）に拾われ、主の直接の回答ではない記録が引き継ぎの元になるのを避けるため。

代替案: 宣言表に 3 つ目の宣言文（`issue で承認済み — …`）を足す案は、auto-merge workflow と形骸化監査が見ている行頭の 2 文言の規約に第 3 の形を持ち込むので採らない。

### 2. 当てられるのは 3 分類だけで、1 つでも外れれば全体を主に聞く

宣言の `- 該当する観点:` が資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張だけで、そのすべてに issue 本文の引用が付くときだけ当てる。外部公開面の変化・データ喪失・課金/法務・プロダクトのユーザーに及ぶ影響が 1 つでも含まれる、または引用が付かない分類が 1 つでもあれば、宣言全体を従来どおり手順 6 で主に聞く（分類ごとに分けて一部だけ保留にする書式は作らない）。

理由: 一部だけ承認済みにすると、主が見る宣言と通った宣言が分かれ、事後報告と保留の依頼が 2 本になる。混ざった PR は頻度が低く、全体を聞いても主の手数はほぼ増えない。

### 3. 承認の証拠は 2 形で、どちらも `owner-reply-check.sh` の exit 0 と全文の読み取りで確かめる

**(a) `/develop` の打ち込み**: セッションは G の `$CLAUDE_CODE_SESSION_ID`（本体のセッション）。原文は `<command-args><N>` または `<command-args>#<N>`。exit 0 で、`MATCH:` の全文が `<command-name>/dev-workflow:develop</command-name>`（または `/develop`）を含み、`<command-args>` の直後が `<N>` または `#<N>` で、その後ろが空白か `</command-args>` であることを確かめる（`7234` への部分一致を通さない）。次のときは数えない:

- `EPIC_DISPATCH_PARENT_EPIC` が空でない（Orca の親が子に打ち込んだ `/develop`）
- `<command-args>` に `--unmanned` を含む（無人ループの起動）

**(b) 起票の承認**: 起票したセッション S の会話ログで、issue の URL（`https://github.com/<R>/issues/<N>`）が最初に現れる行より前にある主の発言のうち最後のものを、起票を承認した発言とする。G は URL を含む会話ログを `grep -l` で `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/*/*.jsonl` から探し（`subagents/` の下は見ない）、そのうち **URL の初出行が、その直前の tool_use（`gh issue create` または `gh api -X POST repos/<R>/issues`）に対応する tool_result であるログだけ**を S とする。初出行がそれ以外（`gh issue view` の出力・主の発言・`/develop` の引数など）のログは、issue を参照しただけのセッション（この develop のセッション、Orca の子のセッションを含む）なので S にしない。S の候補が 0 件（別の PC で起票した、など）なら (b) は使わず主に聞く。承認の発言は `<command-name>` を含まない行に限る（スラッシュコマンドは (b) の証拠にしない。`/develop` は (a) の経路だけで扱い、(a) の除外を通す）。その発言の原文で `owner-reply-check.sh S <原文>` を回して exit 0 と同じ timestamp の `MATCH:` を確かめ、全文から起票の承認（「起票して」「epic にして」「OK」など）が読めることを確かめる。保留・却下（「あとで見る」「やめて」など）と読めるときは数えない。

エピックの子について: 主がエピックの起票を承認した発言は、同じセッション S でそのあと続けて起票された子の (b) の証拠になる（子の URL の初出行の前の主の最後の発言がその承認になる）。別のセッションで親が自動で起こした子は、そのセッションに主の承認の発言が無いか、あっても起票の承認と読めないので証拠にならない。

理由（S の決め方）: URL を含むログは、起票したセッションのほかに参照しただけのセッションが複数あり、`grep -l` だけでは取り違える。起票コマンドの tool_result に URL が初めて出るのは起票したセッションだけである。

どちらの形でも、issue 本文の `lastEditedAt` が null か、証拠の発言の timestamp より前であること（承認のあとに本文が書き換えられていないこと）を確かめる。

理由: #721 と同じく `gh` は主のアカウントで認証されていて、issue の作者や PR コメントの投稿者では書き手を区別できない。会話ログの主の発言が使える一番確かな証拠である。

代替案: issue の作者が主のアカウントであることを証拠にする案は、エージェントが起票した issue も作者が主になるので採らない。エピックの親で主が `/develop <エピック番号>` を打ったことを子の承認とみなす案は、親が子を自動で起こすときに主の承認が無い子まで通すので採らない（エピックを起票したセッションで子も起票されていれば (b) で通る）。

### 4. `agent-proposed` と主の承認の記録が無い issue には当てない

issue に `agent-proposed` ラベルが付いていれば、証拠の有無に関わらず当てない。エージェントが起こした issue（エピックの親が自動で起こした子など）は、(a) か (b) の証拠が取れない限り当てない。この除外は Decision 3 の証拠の条件から導けるが、`agent-proposed` は会話ログに承認らしい発言が残っていても主が「あとで見る」と言った印なので、明示の除外として書く。

### 5. 合格処理と事後報告

手順 5 の合格条件の表に「issue で承認済み」の行を足す: 「主のリスク許容が必要」を投稿済み ＋ 上の 3 行が同コメントに揃っている ＋ 手順 5 で条件を確かめ直した（G は追記を読むだけで通さず、`owner-reply-check.sh` を回し直し、ラベル・`lastEditedAt`・`EPIC_DISPATCH_PARENT_EPIC`・`--unmanned`・(b) の S の決め方・引用が本文にあることを確かめる）。確かめ直したら、同じ宣言コメントに `確かめ直し: 済 — 確認者 <エージェント名> / <日時>（手順 5）` を 1 行追記する（`真正性確認: 済` の行は足さない。3-c の「前の宣言の選び方」が見る行を増やさないため。追記するのは、後から見て手順 5 で確かめ直したかが分かるようにするため）。

合格したら主に 1 回だけ事後報告する。中身は宣言コメントの URL と、引用した issue の文と、当たった分類。ゲートをメインセッションで回しているならその場で伝え、develop の G なら passed の return に `issue で承認済み:` の行（宣言 URL・分類・引用）を足し、本体が CI の見張りを始める前に主へその行を 1 回伝える（`skills/develop/SKILL.md` の (4) の passed の行に足す。auto-merge 配備リポではマージまで主との会話が起きないので、本体の手順に無いと報告が起きない）。主が後から許容しないと答えたら、手順 6 の「不許容」の行と同じ扱い（revert を含む代替案の検討）になる。

**無人運用と事後報告の届け先が無い経路では当てない。** develop の `--unmanned`（無人ループ）では (4) を回さず、無人ループのゲートは憲法のレビューモードが回すので、そのゲートでは当てない。同じく、主に事後報告を届ける先が無い経路（メインセッションで主と会話していない・develop の G でもない）でも当てず、従来どおり手順 6 で保留にする。無人で権限を広げる変更が通る経路を増やさないため。

代替案（unmanned）: 記録先のコメントに事後報告を書いて当てる案は、主が気づく保証が無いまま無人でゲートを緩める経路になるので採らない。

### 6. 手順 6 と 3-c との関係

- 「issue で承認済み」を当てた宣言は手順 6 に入らない（`needs-approval` を付けない）
- 3-c の引き継ぎの元にしない（行頭が `主の回答: 許容` でないので「前の宣言の選び方」に拾われない）。HEAD が動いたら新しい HEAD で手順 3 を回し、同じ条件で判定し直す（主に聞かないので引き継ぐ必要が無い）
- 当てる条件を満たさなかったときは、従来どおり 3-c → 手順 6 へ進み、主への依頼に満たさなかった条件を 1 行添える
- 試す順（`declarations.md` の出口に書く）: 「主のリスク許容が必要」と判定したら、前の HEAD に主の直接の許容（`主の回答: 許容` と `真正性確認: 済`）があればまず 3-c の引き継ぎを試す。引き継げないか前の許容が無ければ「issue で承認済み」を試す。どちらも当たらなければ手順 6。3-c を先にするのは、主が実際に見て答えた許容のほうが証拠として強く、引き継げれば `owner-reply-check.sh` による起票の証拠探しが要らないため。両方を書き込まない（先に当たったほうだけを追記する）

## Risks / Trade-offs

- 主が一度も見ないまま、権限を広げる変更やゲートを緩める変更が main に入る機会が増える。事後報告で気づけるが、事前には止まらない → 主が 2026-10-07 の会話で受け入れた（issue #723 の備考）。外に及ぶ 4 分類は対象外に置き、`agent-proposed` と承認の記録が無い issue を除く
- 証拠 (a) は、Orca 以外の仕組みが本体のターミナルに `/develop` を打ち込む場合（`EPIC_DISPATCH_PARENT_EPIC` を付けない自動起動）を主の打ち込みと区別できない → #721 の守備範囲と同じ限界として spec に書く。`--unmanned` は除く
- 証拠 (b) は、起票したセッションのログが別の PC にあると使えない → 当てずに従来どおり主に聞く（緩める側に倒さない）
- 証拠 (a) は、`/develop` のあとに issue 本文が編集されると `lastEditedAt` の条件で使えなくなる。W が着手時に受け入れ条件を直す運用があるので、主に聞く側に倒れる頻度は高いかもしれない → 安全側なので直さず、`changes/723.md` に書いて後から混乱しないようにする
- 引用は「目的として書いている」かを G が読んで判断する。背景や備考に触れただけの文を目的と読み違える余地がある → 引用を宣言に残すので、事後報告で主が確かめられる
