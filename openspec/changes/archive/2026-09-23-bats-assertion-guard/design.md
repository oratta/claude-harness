## Context

素通りの原因は「bats がテスト本体を関数として実行するから」ではなく、**bash のバージョン依存の `set -e` の挙動**である。bash 4.1 で `[[` と `((` の非ゼロ終了が `errexit`（`set -e`）の対象に含まれるよう変更された。bats はテスト本体を `set -e` 下で実行するため、bash 4.1 未満（macOS 標準の `/bin/bash` は 3.2.57）ではテスト本文途中の `[[ ... ]]` が偽でも `set -e` が効かず素通りする。ローカルの `/bin/bash 3.2.57` で実際に再現を確認した一方、CI（`.github/workflows/ci.yml` の `ubuntu-latest`、bash 5 系）ではこの穴は既に発生しない（ガード無しでも途中の偽 `[[ ]]` でテストが落ちる）。つまりこのバグは「macOS でローカル実行したときにだけ静かに起きる」性質を持つ。cost-ledger は #273 で `|| return 1` を全アサーションに付けて対処済み。本 change はそれ以外の 24 ファイルに同じ対処を広げる。

## Goals / Non-Goals

**Goals:**
- 対象 24 ファイルの、単独の文として置かれた `[[ ... ]]` すべて（本文中の位置を問わず。最後の文も含む）に、偽なら即座にテストを失敗させるガード（`|| return 1`）を付ける。
- ガードの有無を bash のバージョンに依存せず機械的に検査できる常設テストを追加し、同じ穴の再発を検知できるようにする。

**Non-Goals:**
- 本文途中の `! cmd`（否定検査）の扱いは対象外（issue #283 が別途 `run` + status 比較で対処する）。
- ガードを付けた結果として露呈した実装側の不具合の修正（別途 issue を切る）。
- bats 以外のテストランナー・テスト規約の変更。
- `if`/`while` の条件式に使われる `[[ ]]`、同一行で `&&`/`||` により他の `[[ ]]` や実行文と連結された `[[ ]]`、複数行にまたがる `[[ ]]` の扱い（対象外。理由は「Decisions」）。

## Decisions

**採用1: 各アサーションに `|| return 1` を付ける（bats-assert は導入しない）**

検討した案:
1. **`|| return 1` を付ける**（採用） — cost-ledger が #273 で既に採った形。追加の依存が要らず、対象行の直後にトークンを足すだけの機械的な差分になる。24 ファイル・約380箇所という規模でも、既存の書き方から逸脱しないため diff が読みやすく、レビューコストが低い。
2. **`bats-assert`（`bats-support` 込み）を導入し `assert_equal` 等に置き換える** — 見た目は読みやすくなるが、(a) 新しい git submodule / vendoring の追加が要り CI・`scripts/test.sh` 側の導入手順も増える、(b) 対象箇所を `[[ ]]` から `assert_*` の呼び出し形式に書き換える必要があり機械的な置換で済まない、(c) 同じエピック（#402）の子である issue #283 は `! cmd` を `run` + status 比較に直す方針で、これも新しい依存を持ち込まない。片方だけ bats-assert に寄せると、同じテストスイート内でアサーションの書き方が二重に混在する。

規模（24 ファイル、`[[ ` で始まる行が約380）に対して、実績のある機械的な変換を選ぶほうが失敗コストが低いと判断し、案 1 を採用する。

**採用2: ガード対象は「本文中の位置」ではなく「単独の文として置かれた `[[ ]]` かどうか」で定義する（最後の文も含めて全部ガードする）**

当初案は「テスト本文の最後の文以外」を対象としていたが、この定義は grep だけでは判定できない（bats の `@test` 本文のどこが「最後の文」かは、コメント・空行・複数行にまたがる文を考慮したパースが要る）。実装者と G（PR レビュー）で件数が食い違う原因になるため、**最後の文かどうかを問わず、単独の文として置かれた `[[ ... ]]` はすべてガードする**と定め、grep 1本で機械照合できるようにする。最後の文にもガードを付けることの副作用（冗長に見える）より、判定の一意性を優先する。

対象の絞り込み（grep コマンドは spec 参照）:
- 対象: 行頭（空白のみ）から始まり `[[ ` で始まり、行末（末尾コメント可）が `]]` で終わる行。
- 対象外: `if`/`while` の条件式（`if [[` は行頭が `if` になるため grep の対象外に自然に外れる）。同一行で `&&`/`||` により他の `[[ ]]` や実行文と連結された行（`]] &&` / `]] ||` を含む行）。複数行にまたがる `[[ ]]`（行末が `]]` で終わらないため対象外に自然に外れる）。
- 対象外（別 issue が対応）: 行頭が `!` で始まる否定形 `! [[ ... ]]`。`plugins/statusline/tests/statusline-multi-account.bats:215,216,303` に実在するが、対象定義（行頭が `[[ `）に一致しないため grep の対象外に自然に外れる。`!` 付きは `[[` 単体と壊れ方が異なり（bash のバージョンを問わず set -e が効かない）、本来は塞ぐべき穴だが、対応は issue #283（`! cmd` の扱いを `run` + status 比較で直す）の範囲とする。本 change ではこの 3 箇所を変更しない。
- 対象 24 ファイルを実測した結果、`&&`/`||` で連結された行は `plugins/infra/tests/infra-fixes.bats:534` の `[[ "$output" == *"# TODO"* ]] || { echo "unexpected output for: $bad"; return 1; }` の 1 件のみで、これは既に `|| return 1` 相当のガードが付いているため対象grep（ガード無し行を探す grep）には影響しない。複数行にまたがる `[[ ]]` は 0 件だった。もう一つの近い例は `plugins/casting/tests/casting-structure.bats:418` の `[[ -n "${m[key]}" ]] && cat <<EOF` だが、これはヒアドキュメント本体としてシェルスクリプトの fixture を書いているテストコードで、grep の対象パターン自体に一致しない。

**採用3: 見張りテスト自身が常設スコープ検査に引っかからないよう、ガード無し fixture はソース上に `[[ ` 行として書かない**

`tests/bats-assertion-guard.bats` 自体も `git ls-files '*.bats'` の対象に含まれるため、常設スコープ検査（Requirement「単独文の `[[ ]]` アサーションはすべてガードされている」）の対象でもある。task 2.2 の「ガード無し fixture が bash 4.1 未満でだけ素通りする」ことを確認するテストは、検証対象として「ガード無しの `[[ ... ]]`」を子プロセスの bats に食わせる必要があるが、これをソースにそのまま `[[ "$x" == "y" ]]` のような単独行として書くと、その行が常設スコープ検査の grep に恒久的にヒットし、常に red になる。除外リストで `tests/bats-assertion-guard.bats` 自身を対象外にする案は、スコープ検査が「対象ファイル全部に一律で効く」という前提を崩す（除外がある常設検査は、除外リストの保守漏れという別の穴を生む）ため採らない。代わりに、ガード無し fixture の `[[ ... ]]` を `printf` で組み立てて子プロセス用の一時ファイルへ書き出す形にし、`tests/bats-assertion-guard.bats` のソースコード上には行頭 `[[ ` で始まる行が一切現れないようにする。これにより常設スコープ検査はすべての対象ファイルに例外なく効き続ける。

**見張りテストの構成（2種類、役割を分ける）**

BLOCKER: 当初案は「ガード無しの fixture が bats 上で素通りすること」を見張りテストで確認する設計だったが、これは CI（bash 5）では成立しない（ガード無しでも落ちる）。bash バージョンに依存しないテストと依存するテストを分離する。

1. **常設の静的スコープ検査（bash バージョン非依存・本 change の TDD の Red/Green そのもの）**: 新規ファイル `tests/bats-assertion-guard.bats` に、対象ファイル群に対して spec の grep コマンドを実行し出力が空であることを確認するテストを書く。ガード適用前は 378 件ヒットするため Red、24 ファイルへの適用が完了すると 0 件になり Green になる。今後のテスト追加でガード漏れが再発した場合もこのテストが検知する（SHOULD_FIX への対応）。
2. **実行時の挙動確認（bash バージョン依存・参考実演）**: 同じファイルに、子プロセスとして bats を起動し (a) ガード付き fixture は実行した bash のバージョンに関わらず `not ok` になること、(b) ガード無し fixture は `${BASH_VERSINFO[0]}` が 4 未満、または 4 かつ `${BASH_VERSINFO[1]}` が 1 未満のときだけ `ok`（素通り）になることを確認し、それ以外のバージョンでは `skip` する（`tests/test-sh-residual-guard.bats` の bats 子プロセス起動パターンを踏襲）。この (b) はこの穴が実在した根拠を残す目的で、TDD の Red/Green の判定には使わない。(b) のガード無し fixture は「採用3」のとおり `printf` で組み立てて子プロセス用の一時ファイルに書き出し、`tests/bats-assertion-guard.bats` のソース上に単独行の `[[ ` を出現させない。

## Risks / Trade-offs

- [Risk] ガードを付けた結果、これまで見逃されていた本物のバグに当たり、対象テストが赤くなる可能性がある → Mitigation: 受け入れ条件で明記済み（実装の欠陥として別 issue を切る。本 change の受け入れ条件は変えない）。
- [Risk] 24 ファイルにまたがる機械的編集は、対象行の見落とし（ガード追加漏れ）の可能性がある → Mitigation: spec のスコープ検査 grep を常設テストにし、`git ls-files` ベースで対象ファイルを動的に列挙するため新規ファイル追加時も自動で拾う。
- [Risk] スコープ検査 grep が今後の書き方（ヒアドキュメント内・複数行 `[[`・`&&`/`||` 連結）を正しく除外し続けられる保証はない → Mitigation: 対象 24 ファイルでは実測でヒアドキュメント内・複数行 `[[` が 0 件、`&&`/`||` 連結は `infra-fixes.bats:534` の 1 件のみ（既にガード済みで対象grepには影響しない）であることを確認済み。将来これらの書き方が増えて grep の誤検知/見逃しが問題になったら、その時点で別途 issue を切ってスコープ検査を強化する（本 change のスコープ外）。
- [Risk] `! [[ ... ]]`（否定形）は本 change のガード対象定義に一致せず素通りしたままになる → Mitigation: 実在は `statusline-multi-account.bats` の 3 箇所のみで、対応は issue #283 の範囲と明記した（「Decisions」）。本 change の受け入れ条件（単独文 `[[ ]]` の全数ガード）はこの 3 箇所を含まない。
