# Design

## Context

動機は proposal.md「Why」を参照。現在の軽い通し方は W を起こさず、G の failed からは新しい W を `段: spec` で起こして通常経路へ戻す。一方 passed 後の CI 見張りでは SKILL.md が全 PR に既存 W の `段: implement` の再開を求めている。

共有の ci-watch.md は直し手を「PR の実装者（develop では W）」とし、ラベル・Draft 化・状態ファイル・再ゲートのタイミングを担う。develop 固有の W の用意は develop の正本に置ける。

## Goals / Non-Goals

- Goal: 最新の仕様化判断と既存 W の有無に矛盾しない担当・段・記録を定める。
- Goal: 最初の fix と通常経路に戻った後の fix の両方を同じ PR の継続として扱う。
- Non-goal: CI の分類・再実行や修正の回数上限・状態ファイルの形式・ゲートの合否条件を変えること。
- Non-goal: #1583 の入口説明文や #1590、常時注入予算、周辺文の重複整理。

## Decisions

### 軽い通し方は spec から新しい W を起こして通常経路へ戻す

採用するのは G の failed と同じ復帰方式。最新の仕様化判断に `通し方: 軽い` がある PR では、CI 失敗でも競合でも本体が同じ worktree に W を `段: spec` で新しく起こす。PR・記録先・fix の観測（状態と失敗したチェック／run など）を渡し、W が `通し方:` のない判断を同じ記録先に投稿し直す。「する／しない」は修正内容を見た W が選び直す。「する」なら artifact 一式と R1、どちらでもテスト作成を経て同じ PR に積む。古い軽い判断は削除せず、最新の判断を正とする既存契約を使う。

比較した案:

- 本体が続けて直す: 軽い通し方が省いた W・新しいテストを CI 修正にも適用することになり、条件を外れた修正の設計判断が記録されない。
- 新しい W を implement から起こす: 最新の判断が `通し方: 軽い` のままで、W 起動後に通常経路へ戻す判断記録と仕様レビューの要否を解決できない。
- 採用案: spec 工程の追加コストはあるが、G の failed と同じ通常復帰の契約を使え、競合の場合だけの例外も要らない。

通常経路の既存 W は従来どおり `段: implement` で再開し、手渡し可否はコンテキスト上限の正本に従う。CI の fix だけを理由に判断記録は投稿し直さない。軽い通し方から一度通常へ戻った PR の次の fix も、この既存 W の分岐になる。

### 正本の配置と既存接続

詳細は decision-criteria.md Step B の軽い通し方の節に足し、SKILL.md の passed/fix と共有 ci-watch.md「7. 直し方」から辿れるようにする。共有 reference に develop の判定を複製せず、develop を使わない呼び出し側の実装者起動は現状を保つ。

既存の `dev-workflow-ci-watch` 要件は develop の直し手を W と定めており、その W をどの段で用意するかを規定していない。変更する要件は `dev-workflow-develop` の passed 後の分岐に限定する。既存のループ要件の G failed 復帰は変更しない。

どちらの W の修正も共有 reference の passed 解除・Draft 化・pending 付与を経て push する。本体は同じ PR・同じ見張り状態ファイルで `wait` → `next` を続け、`ready` 後に前提確認と重さ判定の G を新しく起こす。通常経路への復帰で見張りの開始記録や修正回数をリセットしない。ログ確認で差分に無関係と判明した場合の、push せず `--unrelated ... --after-fix` へ返す既存の扱いも変わらない。

## Risks / Trade-offs

- [古い軽い判断を見て spec を再起動する] → 最新の仕様化判断を使うことを明記し、通常復帰後の再 fix と既存の最新判断選択テストで確認する。
- [共有 reference と develop で担当が食い違う] → 詳細の正本を 1 か所に置き、両方からの参照と既存 W の implement 段を Bats で検査する。
- [文書テストではエージェントの実際の判断ミスまでは止められない] → 機械的に確認できる担当・段・記録・参照先を回帰テストにし、仕様の妥当性は R1 に委ねる。
- [起動時の文書が増える] → 現状の SKILL.md の余裕は 3 bytes。超過時は OWNER の指示どおり増加分まで該当予算を上げる。既存文の圧縮はせず、PR 本文で理由と #1586 を残す。

## Migration Plan

仕様レビュー後に手順・テストを実装し、verify 後の finish 工程で delta を archive して主仕様へ反映する。既存 PR の状態ファイル移行は不要。今工程では artifact 一式のみを commit/push し、実装と archive は行わない。
