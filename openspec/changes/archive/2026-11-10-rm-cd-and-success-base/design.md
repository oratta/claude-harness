# Design

## Context

動機は proposal.md の Why。rm 用の判定は、コマンドを `&&`・`;`・改行で単純コマンドに割り、0 個か 1 個の `cd` のあとに `rm` が続く形だけを受け付ける。`cd` があれば、削除先ごとに「`cd` の移り先」と「`cwd`」の 2 つの基準で解決し、どちらでも一時領域の中に収まることを求めている。区切りの種類は見ていない。

`||`・`|`・単独の `&` は使える文字や区切りの規則で既に判定を満たさないので、区切りとして残るのは `&&`・`;`・改行の 3 つだけである。

## Goals / Non-Goals

**Goals:**

- 区切りが `&&` だけで `cd` を含む形を、`cd` が成功した場合の基準だけで判定する
- `;` や改行が混じる形は今までどおり 2 つの基準で判定する（`cd` が失敗すると後ろの `rm` が元の `cwd` で走るため）

**Non-Goals:**

- 使える文字・`cd` の引数の規則・`rm` のフラグの規則・削除先の解決の仕方は変えない
- hook の答え方・許可の形・拒否の記録・git 用の判定は変えない
- `cd` を 2 つ以上含む形や、`rm` のあとの `cd` を受け付けるようにはしない

## Decisions

### 区切りが `&&` だけのときに限り、`cd` が成功した場合の基準だけを使う

`a && b` では `a` が失敗すると `b` は走らない。`cd d && rm x && rm y` のように区切りがすべて `&&` なら、どの `rm` も `cd` が成功したときしか走らないので、失敗側の基準（`cwd`）で削除先を見る必要はない。1 つでも `;` か改行があれば、その後ろは前の結果によらず走る。`cd` が失敗すれば元の `cwd` で走るので、今の 2 つの基準のまま見る。

判別は、コマンド文字列に `;` か改行が含まれるかで行う。git 用の判定が `cd` を含むコマンドで `;` や改行を拒むときと同じ見方である。

検討した別案:

- **`rm` ごとに、手前の区切りの並びから走る条件を求める**（`cd d && rm a; rm b` で `rm a` は成功側だけ、`rm b` は両方）。もっと細かく許せるが、区切りの並びの解釈を判定に足すことになる。`&&` と `;` を混ぜて後始末する場面は少なく、混ぜた形を止めすぎる向きに倒しても困る場面は少ない。採らない
- **`cd` を含むなら区切りを `&&` だけに限る**（git 用の判定の規則 1 と同じ）。単純になるが、今は満たしている `cwd` が一時領域の中の `cd ./tbl; rm -rf x/*`（spec のシナリオにある形）が満たさなくなり、止めすぎる向きに振る舞いが変わる。採らない

### 判定の中だけで変え、hook と許可を書くスクリプトはそのまま

どちらも同じ `check_rm` を呼ぶので、許可を書く側と使う側の判定が食い違うことはない。直すのは判定の 1 か所だけにする。

## Risks / Trade-offs

- [`cd` が成功したあとの移り先が、判定で見た場所と違う] → `cd` の引数は `/`・`./`・`../` で始まるか `.`・`..` だけに限っていて（CDPATH を引かない形）、字句で畳んだ道筋と `realpath` が同じ所に着くことを確かめている。この規則は変えないので、成功側の基準は今と同じだけ確かである
- [判定から実行までの間に移り先が symlink に差し替えられる] → 今の守備範囲で既に許している穴（hook は使う時点で判定をかけ直す）。この変更で広がらない
- [`;` と `&&` を混ぜた形は、`&&` の側の `rm` も 2 つの基準で見るので止めすぎる] → 許す。絶対パスで書けば基準によらず判定できる

## Migration Plan

判定の変更だけで、置き場所やファイルの形は変わらない。戻すときはこの変更の commit を revert する。
