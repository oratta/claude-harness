## Context

別セッション方式（Orca・tmux）のエピックでは、子は自分のループの最後に `epic-dispatch.sh mark done` を呼び、親の `wait --watch-done` がその印（記録の `status` が `done`）を見て `done <N>` で起き、`reap` でワークツリーを片付ける。子が PR のマージを主に頼んで見張りを終えると（`references/ci-watch.md`「`ready` を受けたあと」の 1・3、`--until-merged` の `timeout`）、マージは子のセッションの外で起きるので、子は `mark done` を呼ぶ機会を失う。止まった印を付けた子なら親の `notify-closed` が子に完了を促すが、主に直接頼んで見張りを終えた子は止まった印を付けていないので届かない。親は印を待ち続ける。

使える事実は 3 つある。記録先 issue の `state` と `state_reason`（`gh`）、記録の `status` と `stop`、子のトランスクリプト（`wait --resolve` の起動し直しの判定と同じ求め方: `${CLAUDE_PROJECTS_DIR:-${CLAUDE_CONFIG_DIR:-~/.claude}/projects}/<ワークツリーのパスの英数字以外を - にした名前>/*.jsonl`）。

## Goals / Non-Goals

**Goals:**

- 記録先が completed で閉じて子のセッションが止まっている子を、親の `wait` が LLM なしで完了とし、今の `done` の経路（手順 3 の `reap`）で片付ける
- 子が主に「マージしたら教えて」と頼む往復をなくす
- 子がまだ動いているとき・子が自分で印を選んだとき（`waiting`）・止まった印の経路（`notify-closed`）に割り込まない

**Non-Goals:**

- `reap` の安全確認を変えること（推定の `done` も同じ確認を通る）
- `waiting` の子（マージ後の依頼を主に残した子）の完了を推定すること
- 1 回のツール呼び出しを閾値より長く動かしている子を、トランスクリプトの外の事実（プロセスや端末）で見分けること
- 推定したことをエピックや子 issue にコメントすること

## Decisions

### 推定の条件は 6 つすべて

1. `--watch-done` で渡された子で、記録が 1 件読め、`status` が `running`
2. `stop` が `stopped` でも `stopped-seen` でもない（空か `resumed`）
3. 記録の `worktree` が空でなく、そのトランスクリプトが 1 本以上
4. トランスクリプトの最後の活動が `EPIC_DISPATCH_DONE_IDLE_SEC` 秒以上前
5. 子 issue の `state` が `closed` で `state_reason` が `completed`
6. 子 issue の `closed_at` から `EPIC_DISPATCH_DONE_IDLE_SEC` 秒以上たった（`closed_at` が無ければ満たさない）

`status` が `waiting` の子を外すのは、子が「主の確認待ち」と自分で選んだ印で、主の返事で `done` にすると決まっているため（推定で上書きすると、主がそのタブで確認を返す前にワークツリーが消える）。`stop` が止まった印の子を外すのは、その子には `notify-closed` が完了を促す経路が既にあり、推定と促しが同時に走ると、完了報告を書いている途中の子を片付けうるため。`state_reason` を `completed` に絞るのは、`not_planned` などで閉じた子は親が手順 4 で主に報告する件で、作業されていない件を完了と書かないため（手順 4 の `notify-closed` を `completed` に絞っているのと同じ線）。

6 を足すのは、自動マージ待ちの背景の `ci-watch.sh wait --until-merged` を閾値より長く動かしている子は、その間トランスクリプトに行が増えず、マージで記録先が閉じた直後（子が背景のコマンドの終わりを受けて完了報告を書く前）に推定されうるため。閉じてから同じ閾値を待てば、子が `mark done` を呼ぶ時間が残る。`closed_at` は 5 と同じ 1 回の `gh` で読むので、呼び出しの回数は増えない。

案として「`status` が `done` でなければ全部」も考えたが、上の 2 つの割り込みを生むので採らない。

### 最後の活動はトランスクリプトの全ファイル・全行の `timestamp` の最大値

`decide_relaunch` は「最後の assistant の `timestamp`」を見るが、ここで知りたいのは「子のセッションに何か起きたか」なので、種類を問わず `timestamp` を持つ行の最大値を使う（主がそのタブに打った user の行も活動に数える）。置き場の `*.jsonl` が 1 本以上あれば、そのセッションのサブエージェントのトランスクリプト（`<置き場>/<セッション>/subagents/*.jsonl`）も含めて全ファイルを通した最大値をとる（サブエージェントが動いている間は本体のトランスクリプトに行が増えないため。起動し直した子や、同じワークツリーで別に開いた claude のトランスクリプトも活動に数える。どれか 1 本でも新しければ推定しない）。0 本・`timestamp` を持つ行が 1 つも無い・読めない・`python3` が無いときは推定しない。ファイルの mtime は使わない（他の処理が触っても変わり、活動と一致しない）。

トランスクリプトの置き場のディレクトリの求め方は `decide_relaunch` と同じにし、置き場を求める部分を 1 つの関数にまとめて両方から使う。その関数はディレクトリを返すまでにし、「ちょうど 1 本」の判定は `decide_relaunch` の側に残す（起動し直しの判定は 1 本のセッションの文脈の大きさを測るので、2 本以上では決められない。完了の推定は「どれも動いていない」を見るだけなので本数を問わない）。

### 閾値は `EPIC_DISPATCH_DONE_IDLE_SEC`、既定 1800 秒

主がマージしてから子のタブを閉じるまでの間に子が動くこと（完了報告を書き足す等）を待つ幅で、`wait` の既定の間隔 300 秒の 6 回分。`EPIC_DISPATCH_RELAUNCH_IDLE_SEC`（3600）より短くしたのは、片付けの判断は「動いていない」だけで足り、文脈の大きさを問わないため。名前は既存の `EPIC_DISPATCH_RELAUNCH_IDLE_SEC` に合わせた。`--watch-done` が 1 つ以上ある `wait` で、値が空か数字でなければ使い方を出して exit 1（ポーリングの前、`gh` を呼ぶ前）。

### 読む順は安いものから、`gh` は最後

1〜4（記録とローカルのファイル）を先に確かめ、通った子にだけ `gh api <issue_api の形>` を 1 回呼び、`--jq` で `state`・`state_reason`・`closed_at` からの秒数（`now - (.closed_at | fromdateiso8601)`。`closed_at` が無ければ空）を 1 行で読む（5 と 6）。動いている子・`waiting` の子には `gh` を呼ばないので、既存の `--watch-done` の `gh` の呼び出しの回数は、推定の候補にならない限り変わらない。この `gh` が失敗したら、そのポーリングでは推定せず、失敗したポーリングにも数えない（推定は付け足しの経路で、今の終わり方（`error gh`・`error workspaces`）を変えない）。

### 書くのは排他つき、項目を 2 つ足す

`es_modify` で、排他の中で 1・2 を確かめ直してから `status` を `done` にし、`done_inferred_at`（書いた時刻、UTC の `YYYY-MM-DDTHH:MM:SSZ`）と `done_inferred_last_activity`（トランスクリプトの最後の活動の `timestamp` をそのまま）を足す。確かめ直しで外れたら（その間に子が `mark done` や `mark stopped` を付けた）書かず、そのポーリングでは推定しない（子が `done` を付けていれば次のポーリングの通常の経路で `done` になる）。排他が取れない・書けないときは、`--watch-stopped` の書き換えと同じく失敗したポーリングに数える。書けたら `mirror_state <記録> <記録の worktree> done` で Orca の印へ写し（tmux の記録の子は何もしない）、stderr に `inferred done <N>: issue closed as completed, no transcript activity since <最後の活動>` を出して、印が付いた子に加える。

`done_by` のような列挙の項目にしなかったのは、子の `mark done` が値を書かない今の形を変えずに済み、推定したことは項目の有無で分かるため。`reap` は記録を消すので、推定の跡は `wait` の stderr にも残す。

### stdout は今の `done <N>` のまま

親から見て、推定の `done` と子の付けた `done` の扱いは同じ（手順 3 の `reap`）なので、出力の行を増やさない。

### 子の側の文面

エピックの子のセッション（`route` が `nested`）で主にマージを頼んで見張りを終える箇所（`ci-watch.md`「`ready` を受けたあと」の 1 と 3、4 の表の `--until-merged` の `timeout`）に、「マージしたら教えてください」と頼まず、「マージしたらこのタブは放っておいてよい。記録先が閉じれば親が完了にしてワークツリーを片付ける」と書くことを 1 か所にまとめて書く。develop SKILL.md「ループの終わり」の、PR がマージされていないときは `mark` を呼ばない項にも同じことを書く（完了報告の 1 行目 `主がこのセッションで次にすること:` は、マージのお願いだけなら PR のマージで、そのあとの連絡を求めない）。

## Risks / Trade-offs

- [主がマージしたあと、同じタブで子に追加の作業を頼むつもりだった] → 主が打てばトランスクリプトに活動が残り、閾値の間は推定されない。30 分以上空けてから戻ると、ワークツリーが片付いている。`reap` は未コミットの変更・マージ済み PR の HEAD に入っていない commit・`LLM/` があれば残すので、作業の喪失にはならない（`kept <N> ...` で残る）
- [時計のずれでトランスクリプトの `timestamp` が未来] → 経過が負になり閾値に届かないので推定しない（今の挙動のまま待つ）
- [記録先が閉じたあと、子が 1 回のツール呼び出し（長いテストなど）を閾値より長く動かしている] → その間トランスクリプトに行が増えないので推定され、親が `reap` を呼ぶ。`reap` の確認（git がきれい・HEAD がマージ済み PR と一致など）は変えないので、未コミットの変更やマージに入っていない commit があれば残る。失うのは後片付けの途中だけで、この穴を塞ぎ切ることは完了条件にしない
- [マージ後の依頼（動作確認など）を完了報告に書いてマージを主に頼んだ子] → PR が未マージのうちは `mark` を呼べず `waiting` を付けられないので、記録先が閉じて閾値を過ぎると推定され、主の返事の前にタブが閉じる。依頼は完了報告と記録先に残るので、主は記録先から辿れる。`reap` の確認は変えないので作業の喪失にはならない
- [トランスクリプトが 2 本以上の子] → 全ファイルを通した最大値で見るので、どれか 1 本でも閾値より新しい行があれば推定しない。別のセッションが同じワークツリーで動いていれば待つ側に倒れる

## Migration Plan

スクリプトと手順書の差し替えだけで、記録の書式の版（`schema` 1）は変えない（足す項目は読み手が無視してよい知らない項目）。戻すときは PR を revert する。
