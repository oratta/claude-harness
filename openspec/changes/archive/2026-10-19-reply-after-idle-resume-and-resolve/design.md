## 判断

1. **主の返事待ちの子の集め方（手順 7）**: 「まだ再開していない」は子 issue のコメントの新旧では決めない（停止後に親が投稿する `親の判断:` 自体で除外されてしまうため）。再開を示す実在の記録は、子が返事を受けて最初に呼ぶ `mark resumed` が Orca のワークツリーのコメント欄に書く `epic-resumed` である（`epic-dispatch.sh` の `cmd_mark`。止まった印があるときだけ付く）。そこで、`launch` に渡したことのある開いた子のうち、次を全部満たす子を出し直す。
   - 子のワークツリーのコメント欄が `epic-stopped-seen` のまま（`epic-resumed` なら再開済み。`epic-stopped` は `wait` が拾うので対象外）。読むのは `orca` の一覧なので、手順書には orca のコマンドを書かず、スクリプト経由にする（下の判断 5）
   - 最新の `子の停止: 主の返事待ち` に一致する最新の `親の判断:` が「通した」以外（`主に上げる` / `判断できなかった` / 一致なし）。`親の判断:` のコメントは再開の記録として数えない
   - `通すが送れなかった` は手順 8 と同じく送り直す
   - 却下: `epic-stopped-seen` を `epic-stopped` に戻して `wait` に再度拾わせる。印の意味（親が一度受けた）が壊れ、主が答えるまで毎回起こされる。
2. **`--relaunch` の判定（resolve_stopped）**: `deliver_reply` を呼ぶ前に、同じスクリプト内の補助関数が表を当てる。端末の有無は `deliver_reply` が既に扱う（端末が無ければ起動し直す）ので、補助関数は端末ありの前提で「最後のリクエストから 60 分以上、かつ待ちの間のコンパクトなし、かつ会話量 N が 150,000 以上」のときだけ `relaunch=1` を返す。それ以外はすべて 0。
3. **判定の事実の読み方**:
   - トランスクリプト: 子のワークツリーのパス（`orca worktree list --json` の `path`）の英数字以外をすべて `-` にした名前のディレクトリ `${CLAUDE_PROJECTS_DIR:-~/.claude/projects}/<名前>/*.jsonl`。ちょうど 1 本のときだけ使う。0 本・2 本以上は「読めない」。
   - 最後のリクエストの時刻: 最後の `type == "assistant"` の行の `timestamp`。
   - コンパクトの有無: 最後の assistant の行より後に `subtype == "compact_boundary"` の行がある。
   - 会話量 N: `subagent-context.sh --file <トランスクリプト>` の `context_tokens`。
   - どれか 1 つでも読めない・解釈できない・コマンドが失敗したときは `relaunch=0`（表の「扱いが揺れる子」と同じ）。
4. 閾値は表と同じ値を定数にし、`EPIC_DISPATCH_RELAUNCH_IDLE_SEC`（既定 3600）・`EPIC_DISPATCH_RELAUNCH_MIN_TOKENS`（既定 150000）で変えられる。
5. **印を読む入口**: 手順書に orca のコマンドを書かない既存要件に従い、`epic-dispatch.sh` に読み取り専用のサブコマンド `pending-owner <子>...` を足す。各子について、同じ repoId・linkedIssue が一致・archive されていないワークツリーのコメント欄が `epic-stopped-seen` なら `pending <N>` を 1 行ずつ出す（orca を読むだけで書かない）。手順 7 はこの出力の子についてだけ GitHub の記録を照合する。
6. **既存要件との関係**: 既存要件「時間がたった子・親への返事は…」は返事前の分類を本体が行いスクリプトはしないと規定している。この change はそれを MODIFIED にし、`wait --resolve` が通す返事だけはスクリプトが分類する例外を明記する。
