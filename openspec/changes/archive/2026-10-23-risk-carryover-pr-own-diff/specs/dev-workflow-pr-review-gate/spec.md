## MODIFIED Requirements

### Requirement: 前の HEAD の許容を新しい HEAD に引き継いでよい条件

pr-review-gate SKILL.md は、手順 3 で「主のリスク許容が必要」と判定したとき、手順 6 で主に聞く前に、前の HEAD で得た許容を引き継げるかを確かめる手順（手順 3-c。3-b の後ろに置く）を持たなければならない（SHALL）。前の HEAD の宣言は、同じ PR の `## リスク宣言` コメントのうち `主の回答: 許容` で始まる行（引き継ぎの形を含む）と `真正性確認: 済` の行の両方を持つ最新 1 件とし、その `対象 HEAD:` の SHA をスクリプトの前 HEAD に渡さなければならない（MUST）。3-c の冒頭には、この手順の目的を「main の取り込みや PR 自身の修正で HEAD が動いても、リスク宣言の中身（リスク内容・発生条件・影響範囲と戻し方）が前と同じなら、一度許容したリスクを主に聞き直さない」と書き、判定の基準がファイルが変わったかではなくリスクの中身が同じかであることを示さなければならない（SHALL）。引き継げるのは次のすべてを満たすときに限る（MUST）: ①`risk-carryover-check.sh` に前の HEAD・新しい HEAD・前の宣言の根拠ファイルを渡して終了コード 0 が返る、または終了コード 3 が返り、新しい HEAD で取り直したレビューが PR 全体を見た周である（最新の `レビュー重量:` コメントの `固定 HEAD:` が新しい HEAD の 40 桁 SHA と一致し、その周がゲートの開始・CI の見張りのあとの取り直し・方式の書き換え後の全体レビューのどれかで、W の修正後の差分限定の再レビューでも、戻した指摘が順 3 だけでレビューをせずに閉じた周でもない。G が周の種類を前の段の Gate Result と PR のコメントから読めないときは満たさないものとする） ②前の HEAD の宣言に根拠ファイルの行がある ③引き継ぎの元の回答が「引き継ぎの元は真正性確認済みの主の直接の回答に限る」Requirement を満たす ④新しい HEAD のリスク宣言の本文が、`対象 HEAD:` 行を除いて前の HEAD の宣言の本文（末尾の `主の回答:` 以降の追記行を除いた部分）と同一である（リスク内容・該当する観点・発生条件・影響範囲と戻し方・根拠ファイルがすべて同じであることをこの一致で確かめる）。1 つでも満たさなければ、従来どおり手順 6 で主に聞かなければならない（MUST）。スクリプトが終了コード 4（根拠ファイルの PR 自身の差分が前後で違う）を返したときは①を満たさないものとし、引き継がず手順 6 で主に聞き、`EVIDENCE_PR_CHANGED=` の行（どの根拠ファイルの PR 自身の差分が変わったか）を引き継げなかった理由として質問に添えなければならない（MUST）。終了コード 4 を判定役に比べさせて引き継ぐ経路は、この Requirement では定めない。引き継ぎで省けるのは主への質問だけで、レビュー・動作確認証拠・仕様宣言の取り直しと手順 5 の実測は省いてはならない（MUST NOT）。これは手順 1 の「手順 1 から全工程をやり直す（前回の合格部分を流用しない）」と `gate-runner.md` の再レビューの同趣旨の文に対する唯一の例外であることを、3-c に書かなければならない（SHALL）。

この引き継ぎの判定（スクリプトと G の確認を合わせたもの）の守備範囲は次のとおりとする:

- 入力: G 自身が手順 1 で `git fetch` と main の取り込みを済ませたローカルの git リポジトリ（前の HEAD・新しい HEAD・base）、同じ PR の前の宣言コメント（`- 根拠ファイル:`・`主の回答:`・`真正性確認:` の行）、元の直接の回答リンク。G は協力的だが、列挙漏れと読み違いをする前提で扱う
- 拾いたい誤り: rebase・force-push による履歴の書き換え、main 以外のブランチの merge、PR 全体を見たレビューを経ていない、許可リストの条件を満たさない衝突解消（許可リスト外のファイルでの衝突解消、許可リスト内のファイルでの版の行・並べ直し以外の変更、衝突していないファイルへの手入れ）、根拠ファイルの PR 自身の差分の変更（PR 自身の修正や衝突解消が根拠ファイルの PR の変更を変えたもの）、バイナリの根拠ファイルの変更、前後どちらの HEAD にも無い根拠ファイル、根拠ファイルの行が無い宣言からの引き継ぎ、引き継ぎの記録そのものを回答リンクにする自己参照、真正性確認のやり直しの省略
- 通ることを許す入力の例: main 側が根拠ファイル以外の PR が触ったファイルを衝突なしで変えた取り込み（リスクの中身が変わるかは条件④で見る）、main 側が根拠ファイルを変えたが PR 自身の差分（変えた行の並び）は前後で同じ取り込み（main の変更はそれぞれのゲートを通っている）、根拠ファイルに触れない PR 自身の commit（W の修正・CI の直し。リスクの中身が変わるかは新しい HEAD のレビューから組み立てた宣言の本文を条件④で比べて見る）、G が根拠ファイルを列挙し損ねた宣言、`"version"` を含む行の中身、CHANGELOG の並べ直しで項目の属する見出しが変わるもの、主のアカウントで代理投稿された元の回答、新しい HEAD で PR 全体を見たレビューを経た許可リストの条件を満たさない衝突解消（衝突解消の結果は PR の base との差分に現れ、そのレビューで読まれる）
- 範囲外: 代理投稿の見分け、根拠ファイルの列挙の妥当性、merge の仕方の違いによる誤検出（引き継げない側に倒れるだけ）、PR 全体を見たレビューが衝突解消の中身を見落とすこと（レビュー一般の精度の問題として扱う）、差分限定の再レビューの周で main を取り込んだときに引き継げないこと（主に聞く側に倒れるだけ）、main 側の変更が PR のリスクの前提を変えること（主の決定で、main から入った変更だけなら聞き直さない）、PR 自身の差分の比べ方が変えた行の位置を見ないため、同じ行の並びをファイルの別の場所へ動かしても同じと判定されること、main が PR の変えた行の近くを変えて差分の切れ目が変わり、中身が同じでも終了コード 4 になること（主に聞く側に倒れるだけ）。これらを塞ぐことは本要件の完了条件にしない

### Requirement: risk-carryover-check.sh が差分の範囲と根拠ファイルの無変更を判定する

`plugins/dev-workflow/scripts/risk-carryover-check.sh [--base <ref>] <前 HEAD> <新 HEAD> <根拠ファイル>...` は、ローカルの git リポジトリだけを読み、pathspec をリポジトリのルート相対で解釈し（実行時の cwd によらない）、次の 4 つの条件を判定しなければならない（SHALL）: ①前の HEAD が新しい HEAD の祖先である ②`git rev-list <新> ^<前> ^<base>` のうち merge commit であるものがすべて 2 親で、第 2 親が base の祖先、第 1 親が前の HEAD かこの集合の別の commit である（merge commit でない commit は PR 自身の commit として数え、②を外れたとはしない） ③各 merge commit の衝突解消したファイル（`git merge-tree --write-tree <第1親> <第2親>` の tree と merge commit の tree で差のあるファイル。rename 検出をせず `git diff --no-renames --name-only` で列挙し、消したファイルと作ったファイルを別々に数える）が許可リストに入り中身の条件を満たす ④根拠ファイルそれぞれについて、`git diff <前> <新> -- <ファイル>` が空であるか、空でなくても**根拠ファイルの PR 自身の差分**が前後で同じである。許可リストは、`.claude-plugin/marketplace.json` と `plugins/*/.claude-plugin/plugin.json`（`"version"` を含む行を除いた本文が第 1 親か第 2 親の版と一致する）、および `CHANGELOG.md` とサブディレクトリの `CHANGELOG.md`（merge commit の版のすべての行が第 1 親か第 2 親の版に存在する）に限る（MUST）。`--base` の既定は `origin/main` とする。

根拠ファイルの PR 自身の差分は、その HEAD と base の merge-base からその HEAD までの、そのファイルの差分とする（前は `<merge-base(前, base)>..<前>`、新は `<merge-base(新, base)>..<新>`）。前後の比較は、文脈を付けない差分（`-U0`）の、最初のハンクの見出しより後ろにある削除の行・追加の行・改行なしの印の行だけを、出てくる順のまま比べ、ハンクの見出し（行番号）と差分の頭の行は比べない（MUST）。前の HEAD か新しい HEAD のどちらかで base との merge-base が 1 つに決まらないときは `NG:` 行を出さなければならない（SHALL）。前後の diff が空でない根拠ファイルのうち、前後どちらかの HEAD でバイナリとして扱われるもの（`git diff --numstat` の行数が `-` になるもの）は、PR 自身の差分を比べずに `NG:` 行を出さなければならない（SHALL）。前後の diff が空でなく PR 自身の差分が同じ根拠ファイルは `EVIDENCE_MAIN_ONLY=<ファイル>` の行で、PR 自身の差分が違う根拠ファイルは `EVIDENCE_PR_CHANGED=<ファイル>` の行で、それぞれファイルごとに 1 行出さなければならない（SHALL）。

①②のどれかが外れたとき、または④でバイナリか merge-base で `NG:` が出たときは、外れた理由ごとに `NG: <理由>` 行を出し、`CARRYOVER=no` で終了コード 1 を返さなければならない（SHALL）。`NG:` 行が無く `EVIDENCE_PR_CHANGED=` の行が 1 つでもあるときは、`CARRYOVER=if-judged` で終了コード 4 を返さなければならない（SHALL）。終了コード 4 は「根拠ファイルの PR 自身の差分が前後で違うので、リスクの中身が同じかを git の履歴だけでは決められない」を意味し、スクリプトは引き継げるかを決めない。`NG:` 行も `EVIDENCE_PR_CHANGED=` の行も無く③だけが外れたとき（許可リストの条件を満たさない衝突解消があるとき）は、`NG:` 行にせず、許可リストの条件を満たさないファイルごとに `RESOLVED_OUTSIDE_ALLOWLIST=<ファイル>` の行（重複は除く）を出し、`CARRYOVER=if-rereviewed` で終了コード 3 を返さなければならない（SHALL）。ここで「許可リストの条件を満たさない」は、許可リストに無いファイル・許可リストのファイルで中身の条件を満たさないもの・衝突していないファイルへの手入れのすべてを指す。終了コード 1 と 4 のときも、③を満たさないファイルは `RESOLVED_OUTSIDE_ALLOWLIST=` の行に出す。4 つすべてを満たすときは `CARRYOVER=yes` で終了コード 0 を返さなければならない（SHALL）。終了コードの優先順は 1・4・3・0 とする（MUST）。終了コード 3 は「新しい HEAD で PR 全体を見たレビューを経ていれば引き継げる」を意味し、その確認は G が手順 3-c で行う（スクリプトはレビューの有無を見ない）。

判定の守備範囲は「前の HEAD の許容を新しい HEAD に引き継いでよい条件」Requirement の守備範囲の段落に従う（スクリプトが担うのは、そこに挙げた誤りのうち commit・衝突解消・根拠ファイルの PR 自身の差分と存在に関わるもの）。出力は `CARRYOVER=yes|if-rereviewed|if-judged|no`・`MAIN_MERGES=<件数>`・`PR_COMMITS=<merge commit でない commit の件数>`・`RESOLVED_FILES=<衝突解消したファイル全件のカンマ区切り。無ければ none>`・`RESOLVED_OUTSIDE_ALLOWLIST=<ファイル>`（該当ファイルごとに 1 行。無ければ出さない）・`EVIDENCE_MAIN_ONLY=<ファイル>`（該当ファイルごとに 1 行。無ければ出さない）・`EVIDENCE_PR_CHANGED=<ファイル>`（該当ファイルごとに 1 行。無ければ出さない）・`EVIDENCE_DIFF_LINES=<行数>`（`EVIDENCE_PR_CHANGED=` に出たファイルについての `git diff --numstat <前> <新>` の追加と削除の行数の合計。無ければ 0）と、不可の理由ごとの `NG: <理由>` 行とする。引数不足・SHA が解決できない・根拠ファイルが 1 つも無い・根拠ファイルが前の HEAD にも新しい HEAD にも無い・git が `merge-tree --write-tree` に対応しないときは終了コード 2 を返さなければならない（SHALL）。

#### Scenario: main の取り込みだけで衝突なし

- **WHEN** 前の HEAD に main を衝突なしでマージした commit だけが積まれ、根拠ファイルは変わっていない
- **THEN** 終了コード 0、`CARRYOVER=yes`、`MAIN_MERGES=1`、`RESOLVED_FILES=none` を出す

#### Scenario: 版番号と CHANGELOG の衝突解消だけ

- **WHEN** main のマージで plugin.json の `"version"` 行と CHANGELOG.md が衝突し、版の行の選び直しと CHANGELOG の項目の並べ直しだけで解消した
- **THEN** 終了コード 0 を返し、`RESOLVED_FILES` にその 2 ファイルを出す

#### Scenario: main 側の変更で根拠ファイルが変わった

- **WHEN** PR が根拠ファイルの一部の行を変えており、main のマージで同じ根拠ファイルの別の場所（PR の変えた行と離れた行）が変わった
- **THEN** 終了コード 0、`CARRYOVER=yes`、そのファイルを示す `EVIDENCE_MAIN_ONLY=<ファイル>` の行を出し、`NG:` 行も `EVIDENCE_PR_CHANGED=` の行も出さない

#### Scenario: PR が触れていない根拠ファイルを main が変えた

- **WHEN** PR 自身の差分に根拠ファイルが含まれず（前後とも PR はそのファイルを変えていない）、main のマージでそのファイルが変わった
- **THEN** 終了コード 0 と、そのファイルを示す `EVIDENCE_MAIN_ONLY=<ファイル>` の行を出す

#### Scenario: PR の変えた行の近くを main が変えた

- **WHEN** main のマージで、PR が変えた行から 2 行離れた行（既定の差分なら文脈の 3 行に入る行）だけが衝突なしで変わり、PR が足した行・消した行そのものは前後で同じである
- **THEN** 終了コード 0 と `EVIDENCE_MAIN_ONLY=<ファイル>` の行を出す（文脈の行は比べない）

#### Scenario: main 以外の commit が積まれた

- **WHEN** 前の HEAD と新しい HEAD の間に、根拠ファイルに触れない merge commit でない commit（W の修正など）がある
- **THEN** 終了コード 0、`CARRYOVER=yes`、`PR_COMMITS=1` を出し、`NG:` 行を出さない

#### Scenario: PR 自身の commit が根拠ファイルの PR の変更を変えた

- **WHEN** 前の HEAD のあとに積んだ merge commit でない commit が、根拠ファイルの PR が変えた行を書き換えた
- **THEN** 終了コード 4、`CARRYOVER=if-judged`、そのファイルを示す `EVIDENCE_PR_CHANGED=<ファイル>` の行と、前後の diff の追加と削除の合計を示す `EVIDENCE_DIFF_LINES=<行数>` を出し、`NG:` 行を出さない

#### Scenario: PR 自身の commit が根拠ファイルの変更を元に戻した

- **WHEN** 前の HEAD のあとに、根拠ファイルを一度変えてから同じ中身に戻す 2 つの commit を積んだ
- **THEN** 前後の diff が空なので終了コード 0 を返す

#### Scenario: 衝突解消が根拠ファイルの PR の変更を変えた

- **WHEN** main のマージで根拠ファイルの PR が変えた行が衝突し、解消した結果、PR が足した行の中身が前と変わった
- **THEN** 終了コード 4 と、そのファイルを示す `EVIDENCE_PR_CHANGED=<ファイル>` の行を出す

#### Scenario: バイナリの根拠ファイルが変わった

- **WHEN** 根拠ファイルがバイナリで、前後の HEAD で中身が違う
- **THEN** 終了コード 1、`CARRYOVER=no` と、そのファイルを示す `NG:` 行を出す

#### Scenario: merge-base が 1 つに決まらない

- **WHEN** PR に main をマージし、main にも PR の commit をマージして（criss-cross merge）、新しい HEAD と base の merge-base が 2 つになり、main 側の変更で根拠ファイルが前後で変わった
- **THEN** 終了コード 1、`CARRYOVER=no` と、merge-base が 1 つに決まらないことを示す `NG:` 行を出す

#### Scenario: 根拠ファイルの PR 自身の差分の変更と許可リスト外の衝突解消が重なった

- **WHEN** `EVIDENCE_PR_CHANGED=` に当たる根拠ファイルがあり、同じ取り込みで許可リストに無いファイルでも衝突を解いた
- **THEN** 終了コード 4 を返し、`EVIDENCE_PR_CHANGED=` の行と `RESOLVED_OUTSIDE_ALLOWLIST=` の行の両方を出す

#### Scenario: main 以外のブランチの merge が積まれた

- **WHEN** 前の HEAD のあとに、第 2 親が base の祖先でない merge commit がある
- **THEN** 終了コード 1、`CARRYOVER=no` と、その merge commit を示す `NG:` 行を出す

#### Scenario: 許可リスト外のファイルで衝突解消した

- **WHEN** merge commit が許可リストに無いファイル（例 `openspec/specs/x/spec.md`）で自動マージの結果と違う中身になっており、根拠ファイルの diff は空で、ほかに `NG:` に当たるものが無い
- **THEN** 終了コード 3、`CARRYOVER=if-rereviewed`、そのファイルを示す `RESOLVED_OUTSIDE_ALLOWLIST=<ファイル>` の行を出し、`NG:` 行を出さない

#### Scenario: 許可リスト外の衝突解消と根拠ファイルの変更が重なった

- **WHEN** merge commit が許可リストに無いファイルで衝突を解き、同じ取り込みで main 側の変更により根拠ファイルの中身も変わったが、根拠ファイルの PR 自身の差分は前後で同じである
- **THEN** 終了コード 3、`CARRYOVER=if-rereviewed` を出し、`RESOLVED_OUTSIDE_ALLOWLIST=` の行と `EVIDENCE_MAIN_ONLY=` の行の両方を出す

#### Scenario: 衝突していないファイルに merge commit の中で手を入れた

- **WHEN** merge commit が、衝突していないファイルを自動マージの結果と違う中身にしている
- **THEN** 終了コード 3 と、そのファイルを示す `RESOLVED_OUTSIDE_ALLOWLIST=` の行を出す

#### Scenario: 許可リストの JSON で版以外の行を変えた

- **WHEN** merge commit の plugin.json が、`"version"` 行を除いても第 1 親・第 2 親のどちらの版とも一致しない
- **THEN** 終了コード 3 と、その plugin.json を示す `RESOLVED_OUTSIDE_ALLOWLIST=` の行を出す

#### Scenario: CHANGELOG に新しい文を足した

- **WHEN** merge commit の CHANGELOG.md に、第 1 親にも第 2 親にも無い行がある
- **THEN** 終了コード 3 と、その CHANGELOG.md を示す `RESOLVED_OUTSIDE_ALLOWLIST=` の行を出す

#### Scenario: 許可リスト外のファイルを消して似たファイルを作った

- **WHEN** merge commit の中で許可リストに無いファイルを消し、それとよく似た中身のファイルを別の名前で作った（git の rename 検出なら 1 件の rename に見える）
- **THEN** 消したファイルも `RESOLVED_FILES` と `RESOLVED_OUTSIDE_ALLOWLIST=` の行に出る

#### Scenario: 根拠ファイルがどちらの HEAD にも無い

- **WHEN** 前の HEAD にも新しい HEAD にも存在しないパスを根拠ファイルとして渡す（誤字など）
- **THEN** 終了コード 2 を返し、標準エラーにそのパスを出す

#### Scenario: サブディレクトリから実行する

- **WHEN** リポジトリのサブディレクトリを cwd にして、ルート相対の根拠ファイルのパスを渡して呼ぶ
- **THEN** ルートから呼んだときと同じ判定になる（根拠ファイルの PR 自身の差分が変わっていれば終了コード 4）

#### Scenario: 前の HEAD が祖先でない

- **WHEN** 新しい HEAD が前の HEAD を含まない（rebase や force-push で履歴が書き換わった）
- **THEN** 終了コード 1 を返す

#### Scenario: 根拠ファイルが渡されない

- **WHEN** 根拠ファイルを 1 つも渡さずに呼ぶ
- **THEN** 終了コード 2 を返す

### Requirement: 引き継いだ宣言の書式と合格条件

引き継いだ宣言は、前の宣言と同じ本文（行頭 `主のリスク許容が必要。` を含む）を新しい `対象 HEAD:` で出し直し、末尾に `主の回答: 許容（引き継ぎ） — <元の回答>（<日時>）`・`引き継ぎ元: <前の HEAD の 40 桁フル SHA> の宣言 <リンク>`・`引き継ぎの根拠: risk-carryover-check.sh 終了コード <0 または 3> — …`・`真正性確認: 済 — …` の 4 行を追記しなければならない（SHALL）。引き継ぎの根拠の行は、終了コード・main の取り込みの件数・PR 自身の commit の件数（`PR_COMMITS=` の値）・衝突解消したファイル・許可リスト外のファイル（`RESOLVED_OUTSIDE_ALLOWLIST=` に出たもの。無ければ none）・根拠ファイルの前後の diff が空か、main から入った変更だけで PR 自身の差分は同じか（後者は `EVIDENCE_MAIN_ONLY=` に出たファイルを書く）・取り直しのレビュー（終了コード 3 のときは、そのレビューの固定 HEAD の 40 桁フル SHA・周の種類・その `レビュー重量:` コメントのリンク。終了コード 0 のときは「不要」）を書く書式でなければならない（SHALL）。1 行目の `<元の回答>（<日時>）` は、元の直接の回答が回答リンクなら `<元の直接の回答リンク>（<元の回答の日時>）`、会話で受けた回答なら元の記録の `会話で受領（セッション <セッション ID> / <日時>）原文: <原文>` をそのまま書いた形、エピックの親経由で受けた回答なら元の記録の `親経由で受領（親セッション <セッション ID> / 発言 <uuid> / <日時>）停止の記録: <URL> 原文: <原文>` をそのまま書いた形としなければならない（SHALL）。どの形でも 4 行の構造は変えない（MUST）。手順 5 の合格条件の表は、この 4 行が揃った宣言を許容済みとして扱う行を持たなければならない（SHALL）。手順 6 の復帰の表と `gate-runner.md` の取り直しの節は、手順 3 の引き継ぎの小節を参照しなければならない（SHALL）。

#### Scenario: 書式が SKILL.md にある

- **WHEN** SKILL.md の引き継ぎの小節を読む
- **THEN** `主の回答: 許容（引き継ぎ） — ` で始まる行と、引き継ぎ元・引き継ぎの根拠・真正性確認の行の書式がある

#### Scenario: 引き継ぎの回答行が会話の記録の形も持つ

- **WHEN** `stages/hold.md` の手順 3-c の追記の書式を読む
- **THEN** `主の回答: 許容（引き継ぎ） — ` の後ろに回答リンクを書く形と `会話で受領（セッション … / …）原文: …` を書く形と `親経由で受領（親セッション … / 発言 … / …）停止の記録: … 原文: …` を書く形の 3 つが規定され、追記は 4 行のままである

#### Scenario: 引き継ぎの根拠行に取り直しのレビューの固定 HEAD を書く

- **WHEN** 手順 3-c の追記 4 行の書式を読む
- **THEN** 引き継ぎの根拠の行は `引き継ぎの根拠: risk-carryover-check.sh 終了コード ` で始まり、終了コード 0 と 3 の両方を書ける形で、許可リスト外のファイルと、終了コード 3 のときの取り直しのレビューの固定 HEAD・周の種類・`レビュー重量:` コメントのリンクを書く欄がある

#### Scenario: 引き継ぎの根拠行に PR 自身の commit と main からの変更を書く

- **WHEN** 手順 3-c の追記 4 行の書式を読む
- **THEN** 引き継ぎの根拠の行に、PR 自身の commit の件数を書く欄と、根拠ファイルの前後の diff が空か、main から入った変更だけ（`EVIDENCE_MAIN_ONLY=` のファイル）かを書く欄がある。終了コード 4 を書く形は無い（終了コード 4 では引き継がない）

#### Scenario: 手順 5 が引き継いだ宣言を許容済みとして扱う

- **WHEN** SKILL.md 手順 5 の合格条件の表を読む
- **THEN** 引き継ぎの 4 行が揃った「主のリスク許容が必要」の宣言を合格可とする行がある

#### Scenario: G の指示書が引き継ぎを参照する

- **WHEN** `gate-runner.md` の取り直しの節を読む
- **THEN** 許容済みの PR で HEAD が動いたときは、主に聞く前に pr-review-gate 手順 3 の引き継ぎの小節を試すことが書かれている
