# Design

## Context

動機は proposal.md を参照。基準 HEAD は `d188693f771cb72d149946b5ebce971e1b8769b5`。#1696 の調査・分割記録で、対象は `dev-workflow-develop/spec.md` の 4313 行と 4337 行の 2 段落と確定している。どちらも最初の Scenario より後ろにあり、CLI 1.14.1 はシナリオの `rawText` に取り込む。#1695 の配置テストは `tests/openspec-specs-format.bats:85-155` にある。

## Goals / Non-Goals

**Goals:** 規則段落が対応する要件の `text` にそれぞれ 1 回現れ、全シナリオの `rawText` には現れない状態にする。既存要件を全文含む MODIFIED delta によって archive 時の脱落を防ぐ。

**Non-Goals:** 60 分・会話量の閾値・起動し直しの判断、手順書、CLI の解析方法、要件名、シナリオの条件・期待値は変えない。MUST / SHALL を含まない説明段落は今回移動せず、過去の archive delta も編集しない。

## Decisions

1. **同じ要件の最初の Scenario の直前へ段落全体を移す。** #1696 の判断記録どおり、文言を変えず、必要な段落区切りだけを整える。末尾の規則を別の要件にする案は要件名と構成を変えるため採らず、シナリオ行に書き換える案も規則本文として読めないため採らない。隣接する MUST / SHALL の無い説明段落は元の位置に残す。
2. **#1695 と同じ境界検査を用いる。** Bats 内の Python で既存のケース表に 2 要件と対象段落の全文を加え、要件見出しで切り出し、最初の `#### Scenario:` で本文とシナリオを分ける。本文の完全一致段落が 1 回・シナリオ側が 0 回であることを検査する。CLI を CI の依存にせず、実装時のローカル検証では `openspec show dev-workflow-develop --type spec --json` でも同じ帰属を確かめる。
3. **change 単位で検証し、1 PR に順次載せる。** 2 change に仕様上の依存は無い。本体が記録した順で実装し、後続の memory-refresh の change が全 spec 再走査を担当する。両者が同じテスト表を追記するため順次実行する。

## Risks / Trade-offs

- [MODIFIED delta を部分引用すると、archive 時に既存の規則やシナリオが失われる] → 2 要件の全文をコピーし、対象段落を除いた前後の内容が同一であることを照合する。
- [部分文字列や位置だけの検査では、段落の改変・重複を見逃す] → 段落の全文一致と回数を検査し、差分が段落移動と必要な空行だけであることも確認する。
- [行番号が後続編集でずれる] → tasks の行番号と要件名を案内にし、実装前に読み直す。

## Migration Plan

R1 の承認後に配置テストを加え、移動前にその 2 ケースが失敗することを確かめてから本体 spec を移す。配置テスト・CLI の帰属・全体のテストと lint・spec 検証を確認する。戻す場合はこの change による段落移動とテストのケース追加を対で revert する。後続 change の差分は保持する。
