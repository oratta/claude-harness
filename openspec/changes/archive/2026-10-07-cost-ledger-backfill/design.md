## Context

`cost-ledger-timeline`（#303）と issue の合計（#689）で、PR / issue の 1 本のコメントに節目ごとの行が積まれるようになった。積むのは PostToolUse の hook で、手元の Bash で `gh pr merge` や `gh issue close` が走ったときだけ動く。auto-merge のマージと `Closes` による issue の自動クローズは GitHub の側で起きるので、`マージ` と `issue クローズ`（と issue の合計の行）が付かない。`gh pr merge --auto` を実行した時点ではまだマージされていないので、その hook も積まない（「状態の変更は実測してから積む」）。

使えるものは次のとおり。

- `gate_report.py` の裏の処理: 対象ごとのロック `lock()`、既存コメントの取得 `existing_comment()`、issue を閉じた PR の問い合わせ `closing_prs()`、読み取りから書き込みまでの `stack()`、github.com に固定した `gh_api()` / `gh_json()`
- `cost_ledger.py timeline`: `--at` の時刻で累計を切り、行を時刻順の位置に入れ、時刻・きっかけ・累計が同じ行は足さない。`--target-repo` が `--repo` の場所の origin（ホストは github.com）と違えば終了コード 3
- 台帳の隣に控えを置く前例: `<COST_LEDGER_PATH>.lock` と `<COST_LEDGER_PATH>.state.sqlite`（`cost-ledger-persistence`）

エピック #272 の「全体の制約」: LLM のトークンを使わない（hook は何も出力しない）、セッションを 1 秒以上止める処理は裏で走らせる、`gh` の呼び出しは前回見た以降の分だけに絞る、待ち時間と `gh` の回数は実測して PR に書く。

## Goals / Non-Goals

**Goals:**

- そのリポジトリで次にセッションが始まったときに、手元から見えなかったマージと issue のクローズへ最後の行を付ける
- 同じものに 2 回追記しない（控えが消えても、同時に 2 つ走っても）
- セッションの開始を待たせない（同期部分は 1 秒未満を目標にし、実測する）
- 新しいマージ・クローズが無いセッション開始で呼ぶ `gh` は 1 回にする

**Non-Goals:**

- マージされずに閉じられた PR・GitHub の画面でのコメント・`Ready`・再オープン・ゲート通過の後追い
- 行の書式・並び順・増分・合計の行の中身を変えること
- 他の子 issue の範囲（proposal の「やらないこと」）

## Decisions

### 決定 1: きっかけは SessionStart の `startup` と `resume`。同期部分は切り離すだけ

`hooks.json` に `SessionStart`・matcher `startup|resume`・`timeout: 10` の hook を足し、`scripts/backfill.sh` を呼ぶ。`clear` と `compact` は同じセッションの続きなので対象にしない（issue の言う「次にセッションが始まったとき」に当たらない）。サブエージェントの起動は SessionStart を起こさない。matcher に加えて、`backfill.py` の同期部分も JSON の `source` を見て、`clear` と `compact` なら何もせずに終わる（matcher を通らずに直接流された場合と、`hooks.json` の matcher が書き換えられた場合の二重の確認）。`source` がそれ以外の値・値が無いときは、matcher を通った以上は起動として扱う。

`backfill.sh` は緊急停止と `COST_LEDGER_PATH` の有無を見て、`python3` と `gh` があれば `backfill.py` に標準入力を渡す。`backfill.py` の同期部分は hook の JSON から `cwd` を読み、自分自身を `--work` で切り離して起こし、すぐ終わる（`gate_report.py` の `main()` と同じ形。`start_new_session=True` で hook のプロセスグループから外す）。`COST_LEDGER_HOOK_FOREGROUND=1` のときは切り離さずその場で最後まで実行する（テストと実測）。

SessionStart の hook の stdout は会話の文脈に入るので、同期部分も裏のプロセスも stdout・stderr に何も出さず、どの失敗でも終了コード 0 で終わる。

採らなかった案: シェルから `python3 ... &` で直接切り離す。python の起動（実測で約 50 ms）を同期部分から外せるが、hook のプロセスグループごと止められたときに裏の処理が残るかどうかを新しく確かめる必要がある。#303 で実績のある形を使い、同期部分の時間は実測して PR に書く。

### 決定 2: 候補は issues の一覧 1 回で探す

`gh api --paginate "repos/<owner>/<repo>/issues?state=closed&since=<前回見た時刻>&sort=updated&direction=asc&per_page=100"` を 1 回呼ぶ。この一覧は issue と PR の両方を返し、PR は `pull_request.merged_at` を持つ。`since` は更新時刻で絞るので、前回見た時刻より後にクローズ・マージされたものは必ず入る（クローズすると更新時刻も進む）。

`gh api --paginate` の出力は、複数ページだとページごとの JSON 配列が連結されたもので、全体を 1 つの JSON として読むと 2 ページ目がある時点で失敗する。`gate_report.py` の `existing_comment()` と同じく `--jq` を付け、ページごとに要素を 1 件 1 行の JSON にして読む（`.[] | {number, state, updated_at, closed_at, is_pr: has("pull_request"), merged_at: (.pull_request.merged_at // null)} | tojson`）。使う項目だけを取り出すので、本文などの大きい項目を読み込まない。空でない行が 1 行でも JSON として読めない・形が崩れている（`number` が整数でない、`updated_at` が時刻として読めない）ときは、一覧が失敗したものとして扱う（何も積まず、控えも変えない）。途中のページまでで `seen_until` を進めると、読めなかったページの出来事を見ないまま先へ進むため。ページが増えても `gh` の起動は 1 回のまま（決定 8）。

採らなかった読み方: `--slurp` で全ページを 1 つの配列の配列にまとめてから平坦化する。`--slurp` は `--jq` と一緒に使えず、応答の全項目（issue の本文を含む）を読み込むことになり、`gh` の版も新しいものが要る。既存コメントの取得と同じ読み方に揃えた。

一覧のうち候補にするのは次の 2 つで、どちらも「出来事の時刻」が前回見た時刻より後のものだけ。

| 種類 | 条件 | 出来事の時刻 | 積む行のきっかけ |
|---|---|---|---|
| PR | `pull_request.merged_at` がある | `pull_request.merged_at` | `マージ` |
| issue | `pull_request` が無く、`state` が closed | `closed_at` | `issue クローズ` |

更新時刻が進んだだけ（クローズ済みの issue にコメントが付いた、後追い自身がコメントを書いた）のものは、出来事の時刻が前回見た時刻以前なので、`gh` を追加で呼ばずに落ちる。

採らなかった案:

- GraphQL 1 回で PR のヘッドブランチと issue を閉じた PR まで取る。候補 1 件あたりの `gh` が 3 回から 2 回に減るが、PR の一覧には更新時刻で絞る引数が無く、2 つの一覧のページ送りと応答の検証を新しく書くことになる。候補 1 件あたり 3 回は #303 の 1 行あたりの回数と同じで、新しいマージ・クローズが無いときの回数はどちらも 1 回なので、既存の関数をそのまま使える REST の一覧にした
- `pulls` の一覧と `issues` の一覧の 2 回。PR のヘッドブランチが一覧で取れるが、いちばん多い「新しいものが無い」場合が 2 回になる

### 決定 3: 前回見た時刻は GitHub の時刻だけで進める

控えに持つ値はリポジトリごとに 1 つ（`seen_until`）で、「この時刻以前の出来事は見終えた」を表す。一覧の `since` にも、候補の絞り込み（出来事の時刻が `seen_until` より後）にも同じ値を使う。

進め方:

- 一覧が成功し、候補を全部処理したとき: 一覧に現れたものの更新時刻の最大値まで進める（一覧が空なら動かさない）
- 候補が 1 回の上限（決定 5）を超えたとき: 最後に処理した候補の出来事の時刻まで進める
- 一覧が失敗したとき: 動かさない（次のセッション開始でやり直す）
- 戻すことはしない（今の値より前には動かさない）

手元の時計を使わないのは、手元の時計が GitHub より進んでいると、そのずれの間に起きた出来事を見落とすから。一覧に現れた更新時刻は GitHub の時計なので、次の一覧と同じ基準で比べられる。

受け入れる穴: 一覧を取った直後の同じ秒のうちに起きた出来事は、出来事の時刻が `seen_until` と同じ秒になり、「より後」に当たらず落ちる（時刻は秒単位）。同じ秒のものも候補にすると、最後に処理した 1 件が次の回にもう一度候補になり、`gh` を 2 回余分に呼ぶ。毎回の余分な呼び出しより、1 秒未満の窓の取りこぼしを選んだ。auto-merge のマージと、それによる issue のクローズは同じ秒になることが多いが、両方とも同じ一覧に入るので、この穴には当たらない。

### 決定 4: 控えは台帳の隣。`COST_LEDGER_PATH` が無ければ動かない

置き場所は `<COST_LEDGER_PATH>.backfill.json`、排他のためのロックは `<COST_LEDGER_PATH>.backfill.lock`。`cost-ledger-persistence` の「台帳の場所は環境変数で解決する。既定のパスを持たない」と、控えを台帳の隣に置く前例（`.lock`・`.state.sqlite`）に合わせた。新しい環境変数も既定のパスも作らない。

`COST_LEDGER_PATH` が未設定なら、`backfill.sh` は `python3` を起動せずに抜ける（Stop hook の `ledger-hook.sh` と同じ）。置き場所が決まらないことに加えて、台帳が無いと `timeline` が会話ログを全部読み直し、候補 1 件ごとに約 20 秒かかるため。台帳の場所がプラグインのリポジトリの配下を指しているとき（`cost_ledger.py` が書くのを断る場所）も、控えを書かず何もしない。

形:

```json
{"version": 1, "repos": {"oratta/claude-harness": {"seen_until": "2026-10-07T02:17:54Z"}}}
```

鍵は GitHub の `owner/repo`（小文字に揃える）。worktree が違っても同じリポジトリなら同じ値を使う。書き込みは同じディレクトリの一時ファイルに書いてから置き換える。読めない・形が崩れているときは、控えが無いものとして扱う（決定 5 の初回と同じ）。

戻し方: 控えファイルを消せば初回の状態に戻る。消しても、決定 6 の判定で同じ行は 2 回積まれない。

### 決定 5: 初回は 24 時間さかのぼる。1 回の実行は 20 件まで

控えにそのリポジトリの値が無いとき、`seen_until` を「今の時刻の 24 時間前」として扱う（ここだけ手元の時計を使う）。さかのぼらない（今から始める）と、入れる直前にマージされたものが永久に付かず、この change 自身のマージにも行が付かない。全履歴をさかのぼると、過去のクローズ済みの issue と PR すべてが候補になり、`gh` の呼び出しが件数に比例する。24 時間は、入れた日の作業分を拾える長さとして選んだ。

1 回の実行で処理する候補は、出来事の時刻の古い順に 20 件まで。21 件目以降は次のセッション開始に回す（`seen_until` を最後に処理した候補の時刻で止める）。ただし、最後に処理した候補と出来事の時刻が同じ候補は、上限を超えても同じ回で処理する（時刻で区切るので、同じ秒のものを分けると後ろが落ちる）。これで 1 回のセッション開始が呼ぶ `gh` に上限ができる（決定 8）。

候補ごとの失敗（`gh` の失敗・タイムアウト・ロックが取れない）では `seen_until` を止めない。その 1 件には最後の行が付かないまま先へ進む（この change の前と同じ状態になるだけ）。失敗した 1 件で止めると、コメントを書けない issue（ロックされた会話など）が 1 件あるだけで、それ以降が毎回やり直しになる。通信が切れている場合は最初の一覧が失敗するので、その回は何も進まず、次のセッション開始でやり直せる。

### 決定 6: 2 回追記しない判定は `timeline --backfill` が持つ

後追いが積む行のきっかけは、手で実行したときと同じ `マージ` と `issue クローズ`（後追いだと分かる別の呼び名にしない）。合計の行の判定（きっかけに `issue クローズ` を含む）と並び順の規則をそのまま使え、読む側にとっても「最後の行」が 1 種類で済む。

`--at` には出来事の時刻（`merged_at` / `closed_at`）を渡す。行の時刻と累計を切る時刻がマージ・クローズの時点になり、セッションを始めた時刻にならない。同じ出来事をもう一度積もうとしても、時刻・きっかけ・累計が同じなので、`timeline` の既存の規則で行は増えない。

それだけでは、手で `gh pr merge` / `gh issue close` を実行して積まれた行（時刻は hook が動いた時刻で、出来事の時刻と数秒ずれる）と重なるので、`timeline` に `--backfill` を足す。

- 既存の本文に、今回のきっかけの呼び名を `+` 区切りの要素として含む行があり、その行の記録の時刻が「`--at` の 300 秒前」以降なら、本文を変えずに返す。記録と対応しない行（最終行が壊れたあとの先頭の行）は、呼び名だけで判定する
- 節目の行の累計 3 項目がすべて 0 で、合計の行を積む場合はその累計もすべて 0 なら、既存の本文があっても何も出さず終了コード 3

1 つ目の 300 秒は、手元の時計と GitHub の時計のずれを見込んだ幅。issue が再オープンされてもう一度クローズされた場合は、前のクローズの行は 300 秒より前にあるので、新しいクローズの行が積まれる。

2 つ目は、別の PC で作業した PR に、作業していない PC が `$0.00 (-39.62)` のような行を積まないためのもの。控えは PC ごとなので、作業した PC が次にセッションを始めたときに、その PC の値で積まれる。

判定を hook でなく `timeline` に置くのは、表の行と記録を読むのが `cost_ledger.py` だけだから（「hook は集計・単価・書式を自分で持たない」）。

### 決定 7: 対象の確認と書き込みは `gate_report.py` の関数を使う

`backfill.py` は `gate_report.py` を import して、次の順で処理する。

- `GH_HOST`: hook が引き継いだ環境変数 `GH_HOST` が空でも github.com でもないときは、同期部分で何もせずに終わる（裏のプロセスを起こさず、`gh` を 1 回も呼ばない）。`gate_report.py` の `build_job` と同じ扱いで、積む対象は github.com だけ。`gh_api()` は `--hostname github.com` に固定して `GH_HOST` を環境から外すので、ここで止めないと、別のホストに向けたセッションから github.com へ書くことになる
- リポジトリ: `cwd` の origin を `cost_ledger.py` の `RepoResolver.origin()` で読む。ホストが github.com でない・origin が無い・git リポジトリでないときは `gh` を 1 回も呼ばない
- PR の候補: `gh_json("repos/<repo>/pulls/<番号>")` でマージ済みであること・ヘッドブランチ・ベースとヘッドのリポジトリを確かめる。ヘッドが別のリポジトリ（fork）の PR は積まない。後追いは他人の PR も自動で拾うので、fork の `main` や `patch-1` のようなブランチ名で手元の同じ名前のブランチのコストを引き込まないため（#689 の「閉じた PR」と同じ絞り方）
- issue の候補: 一覧が `state: closed` を返しているので、対象の確認の問い合わせは足さない。issue を閉じた PR は `stack()` の中の `closing_prs()` が問い合わせる
- どちらも `lock()` で対象ごとのロックを取ってから `stack()` を呼ぶ。`stack()` には `timeline` へ渡す追加の引数（`--backfill`）を受け取る引数を 1 つ足す。既定は空で、PostToolUse の hook の動きは変わらない

### 決定 8: `gh` の呼び出し回数

| 場合 | 回数 |
|---|---|
| 動かない条件（緊急停止・`COST_LEDGER_PATH` 未設定・github.com のリポジトリでない・別の後追いが実行中） | 0 回 |
| 新しいマージ・クローズが無い | 1 回（一覧） |
| 候補の PR 1 件 | 一覧 1 回 + 3 回（PR の確認・既存コメントの取得・書き込み） |
| 候補の issue 1 件 | 一覧 1 回 + 3 回（閉じた PR の問い合わせ・既存コメントの取得・書き込み） |
| 1 回の実行の上限 | 一覧 1 回 + 3 回 × 20 件 = 61 回（同じ秒の候補が上限を超えた分を除く） |

一覧と既存コメントの取得が 100 件ごとに 1 ページ増える分は、#303 と同じく回数に含めない。手元にコストが無い候補（別の人の PR など）は、書き込みの前で止まるので 2 回で、`seen_until` が進むので次の回には候補にならない。

### 決定 9: 同時に 1 つだけ走らせる。間隔での間引きはしない

裏のプロセスは `<COST_LEDGER_PATH>.backfill.lock` に待たない排他ロックを取り、取れなければ（別の後追いが実行中）何もせずに終わる。子セッションが同時にいくつも始まったときに、同じ候補を重ねて問い合わせないため。ロックは PC に 1 つで、別のリポジトリのセッションが同時に始まったときは片方が飛ばされ、次のセッション開始で処理される。

採らなかった案: 前回の一覧から一定時間（たとえば 5 分）たっていなければ一覧を省く。新しいものが無いときの `gh` は 1 回で、裏で走るのでセッションを待たせない。省くと「次のセッション開始で付く」が成り立たない場合ができ、実機での確認も間隔に左右される。回数を実測して多すぎると分かったら、そのときに足す。

### 決定 10: 緊急停止は 2 つ

`COST_LEDGER_GATE_REPORT=off`（GitHub へ書く処理すべてを止める既存の停止）でも、`COST_LEDGER_BACKFILL=off`（後追いだけ）でも、`python3` も `gh` も起動せずに抜ける。有効・無効を切り替える設定項目は持たない（`cost-ledger-gate-report` と同じ）。

## Risks / Trade-offs

- [入れた直後の最初のセッション開始で、過去 24 時間のマージ・クローズにまとめて行が付く] → 1 回 20 件まで。既に積み先のコメントがある PR / issue では編集になり、購読者の通知は増えない（#303 の実測）。コメントが無かったものには新しいコメントが 1 本でき、その分の通知が出る
- [候補ごとの失敗は取り戻さない] → その 1 件に最後の行が付かないだけで、この change の前と同じ状態。README に書く
- [手元の時計が GitHub と 300 秒以上ずれていると、手で積んだ行と後追いの行が 2 行並ぶ] → 数字はどちらも正しく、行が 1 行多くなるだけ。守備範囲に書く
- [別の PC と手元の両方で作業した PR / issue では、後追いの行の累計が手元の分だけになる] → 複数の PC から同じコメントに積む場合の既存の性質（前の行より累計が小さければ負の増分になる）
- [同じリポジトリの他人の PR でも、手元に同じ名前のブランチのコストがあれば、その PR に行が付く] → `/cost <PR番号>` と行の累計がブランチ名だけで引く既存の性質（#285 の決定）。fork の PR は積まない
- [`hooks.json` を変える] → 聖域なので人間のマージになる。反映に `/reload-plugins` が要る
- [この change 自身は auto-merge に乗らない] → 受け入れ条件の実機確認（auto-merge でマージされた PR に行が付く）は、マージ前に `claude -p --plugin-dir <worktree>/plugins/cost-ledger` で、既に auto-merge でマージ済みの別の PR を対象にして行う
