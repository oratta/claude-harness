# Design

## Context

正本は `output-styles/readable.md` の節 3、短い版は `rules/communication-style.md` の 3 番目。新しい形の中身（8 項目・4 つのまとまり・使う場所の表）は issue https://github.com/oratta/claude-harness/issues/1671 の本文で決まっている。issue に無いのは、既存の決まり（主に聞く理由の 3 つ・論点・1 行目の書き分け・論点なしの行数・1 通 1 件・配る候補の制約）を新しい形のどこに置くかで、この design で決める。後続の change B（`owner-message-title-first-line`）と C（`owner-number-check-title-form`）は、ここでの決定に揃える。

制約:
- 常時注入の予算（`tests/injection-budget.txt` = 42300、今の合計 42298）を動かさない。節 3 と短い版の 3 番目の合計バイト数を、今（節 3 が 5336、3 番目が 1650）以下にする
- readable.md と communication-style.md は配る候補なので、固有名を書かない。Harness のプラグインには「入っていれば」の条件つきで触れる
- spec `dev-workflow-owner-message-number-check` は、節 3 に `ほかの決まり` で始まる行・`番号は末尾の URL にだけ置く`・`主がすること: なし` があることを求めている。この 3 つは残す

## Goals / Non-Goals

**Goals:** 8 項目・まとまり・表を正本にする／旧い決まりのうち残すものを新しい形の中に置き直す／短い版と正本を食い違わせない

**Non-Goals:** 依頼を並べる画面の実装（flatmate 側）／親と channel の発言の文面（change B）／hook の見分け方（change C）

## Decisions

### 主に聞く理由の 3 つと論点は、書く前の判定と論点の項目に置く

主に聞く理由の 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作）は、8 項目の前に「聞くかどうか」の判定として置く。どれにも当たらなければ書かずに進めて事後報告する決まりも、設計の分かれ目を 3 つに数えない決まりもそのまま残す。判定の結果は論点の項目に書く。論点ありなら論点を書き、論点なし（決まりで聞いている）なら推奨どおりでよい旨と、その決まりが何を守るためかを書く。主の手でしかできない操作だけで聞くときは、論点なしの扱いになる。

他の案: 「主に聞く理由」を 9 個目の項目にする。issue の 8 項目から外れ、依頼の画面の側と項目が食い違うので採らない。

### 1 行目は題名、2 行目はアクション。`主がすること: なし` は残す

判断・確認・操作を求める発言は、1 行目を題名（依頼の形。例「〜をマージしてほしい」。質問にしない）にし、2 行目を `アクション:` で始まるアクションの行（どこで何を打つ・押すか。リンク付き）にする。旧い「最後の行を答え方にする」は無くす（答え方はアクションに入る）。主の操作も判断も要らない報告は 1 行目を `主がすること: なし` にし、主の質問への答えは対象外で 1 行目に答えを書く。この 2 つは変えない。

2 行目の行頭を `アクション:` に固定するのは、change C の hook が機械的に依頼を見分ける手がかりにするため。1 行目が質問でなくなるので、旧い「1 行目が ？で終わる」では見分けられない。

他の案: アクションを旧い答え方と同じく最後の行に置く。issue の表は「してほしいこと」のまとまり（題名・アクション）を先に読ませる順で、オーナーが最初に何を求められているかを読む目的に反するので採らない。

### 項目の書き方: 題名以外は `<項目名>: <中身>` の 1 行

題名だけは項目名を付けない（1 行目そのものが題名）。他の項目は `アクション:`・`目的:`・`詳細:`・`論点:`・`推奨:`・`リスク:`・`緊急度:`・`ブロック:` で始める。対話のセッションでは空の項目は書かず、固定の欄がある場所（チャットの 1 件ずつの依頼・画面）では「—」と書く。区切り（`---`）の下に背景と元の記録の URL を置く決まりは残す。

### 使う場所の表は issue のとおり。「1 通 1 件」は 1 件ずつの依頼に効かせる

表の行と長さは issue 本文のとおり。「1 通で聞くのは 1 件」は、対話のセッションとチャットで 1 件ずつ出す依頼に効く。何件かまとめて出す一覧は、各行が 1 件の依頼へのリンクで、一覧の中では答えを求めないので「1 通 1 件」に反しない、と節に書く。

### 使う場所の表を優先し、論点なしの依頼を短く省くのは対話のセッションだけ

旧い「論点なしの確認は 3〜4 行」は、項目の数が場所で変わらない前提の決まりだった。新しい形では使う場所の表が項目と長さを決めるので、表を優先する。論点なしの依頼を短く省くのは、表が「空の項目は書かない」とする対話のセッションだけにし、題名・アクション・論点・推奨の 4 行にする。題名だけでは目的が伝わらないときは、目的の行をアクションの次に足して 5 行にする。どちらも区切りより上の行数で数える。

チャットで 1 件ずつ出す依頼と依頼を並べる画面の詳細は、表が「全部」と決めているので、論点なしでも全部の項目を書く。緊急度とブロックはオーナーが手を付ける順を決める欄で、論点の有無と関わりなく要るため。書けない項目は「—」にし、論点の項目に論点なしの旨と決まりが守るものを書く。まとめて出す一覧と画面の行は、もともと表の決めた項目だけなので変わらない。

要件の名前は「論点の無い確認は 3〜4 行に収める」から「論点の無い依頼は、対話のセッションでは区切りより上を 4〜5 行に収める」に変える（RENAMED）。行数も当てる場所も変わり、旧い名前のままだと名前と中身が食い違うため。旧い名前を引いているのは同じ spec の 1 か所だけで、この change で直す。

他の案: 論点なしなら場所を問わず 4 行にする。チャットの依頼から緊急度とブロックが消え、オーナーが一覧から手を付ける順を決められなくなるので採らない。

他の案: 対話で目的が要るときも 4 行に収める（目的を題名に含める）。題名が長くなり、依頼を並べる画面の題名 40 字の制限と同じ題名を使えなくなるので採らない。

### pr-review-gate の論点なしの依頼は行数を自前で持たず正本を指す

spec `dev-workflow-pr-review-gate` は、`stages/hold.md` に「論点なしの 3〜4 行」と「答え方の行」を書くよう求めている。行数を二か所で決めると正本と食い違うので、hold.md は論点なしの短い形で書くとだけ定め、行数は正本の節 3 を指す形に直す。`declarations.md` と `stages/pass.md` の旧い型の語（`答え方`・`3〜4 行`・`OK すると何が起きるかを中身で書いた質問`）も同じ change で消す。

### 固有の名前の言い換え

issue の表の「Discord」は「チャット」、「タスクの画面」は「依頼を並べる画面（ある環境では）」、「住人」は「頼んだエージェント」と書く。配る候補の制約（固有名を書かない）のため。flatmate の側では、チャットが Discord、画面がタスクの画面、頼んだエージェントが住人に当たる。

### 項目の数え方

issue の表と flatmate の決定は「8 項目」と書くが、名前を数えると題名・アクション・目的・詳細・論点・推奨と根拠・リスク・緊急度・ブロックの 9 つになる（「どこで答えるか」はアクションに付けるリンクで、項目を増やさない）。正本には数を書かず、名前を並べる。見出しの名前（題名・アクション）と表の中身は issue のとおりにする。

### 例

3 つ（論点あり 1、論点なしの実例の書き直し 2）を新しい形に書き直す。論点なしの例は 4 行以内で、見出しに「論点なし。実例」を残す（既存のテストと要件の数え方を変えない）。

## Risks / Trade-offs

- [予算に余裕が 2 バイトしかない] → 旧い 6 段の説明と「OK すると何が起きるか」の説明を消した分で表を書く。収まらなければ実装の段で止めて返す
- [1 行目の決まりが変わると、change B と C が入るまで親の発言と hook が旧い形のまま] → 3 つの change を同じ PR に積み、同時にマージする
- [Draft PR https://github.com/oratta/claude-harness/pull/1655 と同じ箇所を書き換える] → 先にマージされた側に合わせて書き直す。主に聞く理由の 3 つの中身（例の文）はあちらの決定に従う
