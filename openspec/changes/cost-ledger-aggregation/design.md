## Context

Claude Code の会話ログ（`~/.claude/projects/**/*.jsonl`）は、アシスタントの 1 メッセージが 1 行の JSONL で、`gitBranch`・`cwd`・`message.model`・`message.usage`・`requestId`・`message.content[].input.command` を持つ。この構造は 2026-09-09〜10 のセッションで実測済みで、再現手段が `plugins/cost-ledger/prototypes/`（5 本のスクリプトと README）に残っている。ログ構造を調べ直す必要はない。

実測で分かっていること:

| 事実 | 数値 |
|---|---|
| 全履歴の規模 | 2,977 ファイル / 492,850 メッセージ（約 6 か月ぶん） |
| 全履歴 1 パスの所要時間 | 8.4 秒 |
| API 換算の総額 | $9,245 |
| サブエージェントの行に `gitBranch` が入る件数（直近 30 日） | 238,436 件 |

main 上の作業の割合はリポジトリによって 2% から 100% まで振れる。flatmate では全体の 45%（$2,808）が main 上にあり、そのうち 69%（$1,950）は `gh issue view/comment/edit <番号>` を実行したセッションの中にある。issue 番号を第 2 の鍵にすると、宙に浮くのは 45% ではなく 14%（$858）まで下がる。

制約は 3 つある。会話ログは既定 30 日で消える（この change では扱わず #274 が扱う）。このリポジトリはプラグインの配布元なので、新しいプラグインは plugin.json と marketplace.json の両方に登録し、変更時はバージョンを bump する規約がある。ログや台帳のパスをリポジトリ内に固定で書いてはならない。

## Goals / Non-Goals

**Goals:**

- 追加の記録を仕込まずに、過去にさかのぼって PR / issue 単位の API 換算コストを出せること
- 帰属をブランチと issue 番号の 2 本立てにして、main 上の作業が宙に浮く割合を下げること
- 料金表を 1 か所に集約し、新モデルの追記が 1 ファイルの編集で済むこと
- 全履歴 1 パスが数十秒で終わり、LLM のトークンを 1 つも使わないこと

**Non-Goals:**

- 台帳への焼き付けと hook による差分追記（`cost-ledger-persistence` #274 が担当）
- pr-review-gate 通過時の自動投稿（`cost-ledger-gate-report` #276 が担当）
- 200K 超のコンテキストの割増のモデル化（主が飲んだリスクとして未対応のまま残す）
- ステータスバーへの表示（statusline は描画のたびに走るので全履歴スキャンを混ぜない）
- 実際の課金額の再現。出すのは API 換算の推定値であって請求額ではない

## Decisions

**独立したプラグインにする（statusline にも dev-workflow にも混ぜない）。** statusline は描画のたびに走るので 8〜28 秒のスキャンを混ぜられない。dev-workflow は PR 運用のリポでしか効かないが、コストを一番知りたいのは PR を作らない main 上の作業。両者に相乗りする案は、この 2 つの理由で落ちた。

**帰属の鍵を 2 本立てにする。** ブランチ 1 本だけにする案は、main 上の作業がすべて宙に浮くため落ちた（flatmate で 45%）。第 2 の鍵に issue 番号を選んだのは、`gh issue view/comment/edit <N>` がツール呼び出しとしてログに残っており、追加の記録を仕込まずに拾えるから。セッション ID を鍵にする案は、セッションと作業単位が 1 対 1 でないため落ちた。

**区間分割は投稿から投稿までにする。** 1 セッションが複数 issue を触るのが実際に起きる（flatmate で最も高い $197 のセッションは 4 つの issue を触っていた）。セッション全体を最後に触った issue に寄せる案は、その 1 件に全額が乗るので落ちた。区間の境界に投稿を選んだのは、投稿が「その作業単位の区切り」として実際に打たれているから。区間ごとに直近に触った issue へ寄せる。

**worktree は親リポジトリに畳む。** `cwd` から `git -C <cwd> rev-parse --git-common-dir` で親を引く。worktree ごとに分けると、同じ作業が worktree の作り直しで分断されるため。

**重複排除は `requestId`。** 同じ行が複数ファイルに現れることが実測で確認されている。行の内容でハッシュを取る案より、`requestId` が既に一意の鍵として入っているぶん確実で速い。

**料金表は 1 ファイルに集約する。** プロトタイプでは 5 本のスクリプトそれぞれの `P` に手で書かれていて、追記漏れが起きる。集約先を 1 つにして、`/cost` はそこだけを読む。

**未知モデルは黙って 0 円にしない。** 単価を手で書いている以上、新モデルが出てから追記するまでの空白は必ず発生する。その間ぶんが 0 円として静かに落ちると、下がった数字を正しいものと読んでしまう。未知モデルの名前と行数を出力に出す。

## Risks / Trade-offs

**誤配分**（1 セッションが複数 issue を触るため、区間分割は推定でしかない）→ issue 単位の数字は「だいたいこのくらい」として読むものと明示する。出力に区間の内訳を出して、どの区間がどの issue に寄ったかを利用者が確かめられるようにする。PR 単位は commit がブランチに紐づくぶん確かなので、そちらを主に使う。主が承認済みのリスク。

**料金表のずれ**（新モデルの追記が遅れると、そのぶんが落ちる。200K 超の割増も未モデル化）→ 未知モデルを出力に出して、落ちていることが見えるようにする。割増は今回モデル化しない。主が承認済みのリスク。

**全履歴スキャンの所要時間**（8.4 秒。ログが増えれば伸びる）→ この change では許容する。`/cost` は手で叩くコマンドで、描画のたびには走らない。伸びが問題になるなら #274 の台帳が先に効く。

**未帰属のコストが残る**（ブランチも issue も持たない行）→ 0 として消さず、未帰属として集計に残す。合計が総額と合うことをテストで押さえる。

## Migration Plan

新規プラグインなので移行は無い。`plugins/cost-ledger/prototypes/` は削除せずに残す（削除は #276）。プロトタイプの出力が本番実装の期待値になるので、この change のあいだは並存させて突き合わせに使う。
