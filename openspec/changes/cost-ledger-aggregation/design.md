## Context

Claude Code の会話ログ（`${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/**/*.jsonl`）は、アシスタントの 1 メッセージが 1 行の JSONL で、`gitBranch`・`cwd`・`sessionId`・`timestamp`・`isSidechain`・`message.model`・`message.usage`・`requestId`・ツール呼び出しの入力を持つ。この構造は 2026-09-09〜10 のセッションで実測済みで、再現手段が `plugins/cost-ledger/prototypes/`（5 本のスクリプトと README）に残っている。ログ構造を調べ直す必要はない。

実測で分かっていること:

| 事実 | 数値 |
|---|---|
| 全履歴の規模 | 2,977 ファイル / 492,850 メッセージ（約 6 か月ぶん） |
| 全履歴 1 パスの所要時間 | 8.4 秒 |
| API 換算の総額 | $9,245 |
| サブエージェントの行に `gitBranch` が入る件数（直近 30 日） | 238,436 件 |

main 上の作業の割合はリポジトリによって 2% から 100% まで振れる。flatmate では全体の 45%（$2,808）が main 上にあり、そのうち 69%（$1,950）は `gh issue view/comment/edit/close/develop <番号>` を実行したセッションの中にある。issue 番号を第 2 の鍵にすると、宙に浮くのは 45% ではなく 14%（$858）まで下がる。

### 前提環境

| 前提 | 内容 |
|---|---|
| 実装言語 | **python3 を採る**（実装時に確定）。このリポジトリの他プラグインは bash と jq が主で、python はテスト補助 1 本しか無いため、python3 は**実行時依存として plugin.json の description と README に明記する**。JSONL の 1 パス処理と辞書集計を bash と jq でやり直すのは実装量と速度の両方で不利 |
| `gh` | 認証済みであること。番号が PR か issue かの判別に使う |
| ネットワーク | GitHub へ到達できること。到達できないと番号の判別ができない（コスト計算そのものはオフラインで完結する） |
| `git` | **2.31 以上**。`rev-parse --path-format=absolute --git-common-dir` を使う。無印の `--git-common-dir` はメイン worktree で相対の `.git` を返し、リポジトリ識別子が cwd ごとに割れる |
| 会話ログ | `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects` 配下。既定 30 日で消える |

### 制約

会話ログは既定 30 日で消える（この change では扱わず #274 が扱う）。このリポジトリはプラグインの配布元なので、新しいプラグインは plugin.json と marketplace.json の両方に登録し、変更時はバージョンを bump する規約がある。ログや台帳のパスをリポジトリ内に固定で書いてはならない。

## Goals / Non-Goals

**Goals:**

- 追加の記録を仕込まずに、過去にさかのぼって PR / issue 単位の API 換算コストを出せること
- 帰属をブランチと issue の 2 本立てにして、main 上の作業が宙に浮く割合を下げること
- 料金表と換算レートを 1 か所に集約し、新モデルの追記が 1 ファイルの編集で済むこと
- 全履歴 1 パスが数十秒で終わり、LLM のトークンを 1 つも使わないこと
- 後続の台帳（#274）とゲート連携（#276）が乗れる形にしておくこと

**Non-Goals:**

- 台帳への焼き付けと hook による差分追記（`cost-ledger-persistence` #274 が担当）
- pr-review-gate 通過時の自動投稿（`cost-ledger-gate-report` #276 が担当）
- 200K 超のコンテキストの割増のモデル化（主が飲んだリスクとして未対応のまま残す）
- ステータスバーへの表示（statusline は描画のたびに走るので全履歴スキャンを混ぜない）
- 実際の課金額の再現。出すのは API 換算の推定値であって請求額ではない

## Decisions

**独立したプラグインにする（statusline にも dev-workflow にも混ぜない）。** statusline は描画のたびに走るので 8〜28 秒のスキャンを混ぜられない。dev-workflow は PR 運用のリポでしか効かないが、コストを一番知りたいのは PR を作らない main 上の作業。両者に相乗りする案は、この 2 つの理由で落ちた。

**事実の抽出と帰属の導出を分ける。** 各行から抽出するのは事実だけ（`requestId`・`timestamp`・`sessionId`・`isSidechain`・リポジトリ識別子・`gitBranch`・モデル・トークン 5 種・触った issue 番号の列・投稿の印）で、区間分割はその事実の列に対する純粋な関数として書く。区間の帰属は次の投稿が来るまで確定しないので、1 行ずつ追記する経路には導いた帰属を書けない。#274 の hook が台帳へ書くのは事実の側になる。ここを混ぜて実装すると #274 で書き直しになる。

**帰属の鍵を 2 本立てにする。** ブランチ 1 本だけにする案は、main 上の作業がすべて宙に浮くため落ちた（flatmate で 45%）。第 2 の鍵に issue を選んだのは、`gh issue` の呼び出しがツール呼び出しとしてログに残っており、追加の記録を仕込まずに拾えるから。セッション ID を鍵にする案は、セッションと作業単位が 1 対 1 でないため落ちた。

**第 2 の鍵は（リポジトリ識別子, issue 番号）の組にする。** issue 番号はリポジトリ内でしか一意でない。実際、このリポジトリの marketplace.json の中だけでも flatmate の #178 と claude-harness の #108 のように別リポジトリの番号が並ぶ。番号だけを鍵にすると `/cost 108` が全リポジトリの同じ番号を合算する。worktree の畳み込みで既にリポジトリ識別子を求めているので、それを鍵にも `/cost` の絞り込みにも使う。

PR の経路はブランチ名だけで引く。PR のヘッドブランチが main になることはないので、リポジトリで絞らなくても他リポジトリの行を拾わない。絞らないことで、`cwd` が削除済みでリポジトリ識別子が不明に落ちた行も落とさずに済む。

**リポジトリ不明の行は黙って扱わない。** `cwd` が削除済みで `git rev-parse` が失敗した行は、除外しても合算しても数字が静かにずれる。件数と金額を「リポジトリ不明」として出力に別立てで出す。未知モデルを黙って 0 円にしないのと同じ方針。

**issue 番号を拾うコマンドは 5 つ。** `gh issue view` / `comment` / `edit` / `close` / `develop`。設計の根拠になった 14% という数字は `prototypes/issue-rescue.py` が出したもので、その正規表現がこの 5 つを拾っている。仕様を 3 つに絞ると、根拠にした数字と実装が食い違う。

**区間の境界は 4 つ。** `gh pr comment` / `gh issue comment` / `gh pr create` / `gh pr ready`。`prototypes/per-post-cost.py` が境界にしている集合と同じ。このリポジトリは Draft PR を作って作業し、終わったら `gh pr ready` で切り替える運用なので、`gh pr ready` を落とすと区間の切れ目がプロトタイプとずれる。

**区間は `sessionId` ごとに切る。** ブランチ全体を時刻順に並べて切る案は、利用者が複数セッションを並行して走らせるため、別セッションの行が互いの区間に混ざる。`sessionId` ごとに `timestamp` 順で切り、ブランチの総額はセッションの区間の合計を足したものとする。

**リポジトリ識別子は git-common-dir の絶対パスそのものにし、`owner/repo` は表示だけに使う**（実装時に確定）。`git rev-parse --path-format=absolute --git-common-dir` が返す絶対パスを `realpath` で正規化した文字列を識別子とする。`owner/repo` を識別子にする案は、remote を持たないリポジトリと、`cwd` が削除済みで remote を引けない行で識別子が作れなくなるため落ちた。表示名は識別子から origin の URL を引いて `owner/repo` に直し、remote が無ければリポジトリのディレクトリ名に落とす。`/cost` の 1 行目に出るのはこの表示名で、集計の鍵はあくまで絶対パスの側。

**円換算レートの上書きは環境変数 `COST_LEDGER_USD_JPY`**（実装時に確定）。名前は `pricing.json` の `usd_jpy_rate_env` にも書いてあり、後続の台帳（#274）とゲート連携（#276）はそこを読めば同じ名前に揃う。

**worktree は親リポジトリに畳む。** `cwd` から `git -C <cwd> rev-parse --path-format=absolute --git-common-dir` で親を引く。worktree ごとに分けると、同じ作業が worktree の作り直しで分断される。

**重複排除は `requestId`。** 同じ行が複数ファイルに現れることが実測で確認されている。行の内容でハッシュを取る案より、`requestId` が既に一意の鍵として入っているぶん確実で速い。

**料金表と換算レートは同じ 1 ファイルに、データ形式で置く。** 置き場所は `plugins/cost-ledger/pricing.json`。プロトタイプでは 5 本のスクリプトそれぞれの `P` に手で書かれていて、追記漏れが起きる。コードではなくデータにしておくと、実装言語を後で変えても、bash と jq からも読める。

**単価は最長一致の前方一致で引く。** ログのモデル名は `claude-haiku-4-5-20251001` のように日付が付くので前方一致が要る。プロトタイプは辞書を順に走査して最初に一致した鍵を採っており、`claude-fable-5` と `claude-fable-5-1` のように一方が他方の接頭辞になる鍵があるため、表の並び順に結果が依存していた。最長一致にすると並び順から独立し、「未知モデル」の定義も「どの鍵にも前方一致しない」で一意になる。

**円換算は固定レートにする。** 取得レートだと日によって円が変わり、bats テストがネットワークに依存し、#274 の台帳と #276 の PR への投稿が同じ PR に同じ数字を再現できない。固定レートを料金表と同じファイルに置き、環境変数で上書きでき、出力にレートを必ず添える（プロトタイプの `¥16,235 @150` と同じ形）。

**番号なしで呼んだら現在のブランチを見る。** 使い方を出して終わる案より、作業中にその場で叩く用途に合う。`gh` の都合で作業ディレクトリのリポジトリが前提になっているので、ブランチも同じところから取るのが一貫する。この振る舞いは外部から観測できるので design だけでなく spec の Scenario にも残す（archive 後は spec が正本になる）。

**出力の 1 行目を固定書式にする。** 例: `コスト: $108.23 / ¥16,235 @150 — PR #271 (oratta/token-optimize) 帰属: ブランチ`。#276 が PR に貼るときに 1 行目だけを取ればよくなる。このリポジトリには「コメントの 1 行目を完全一致で照合する」規約（`仕様化判断: する` など）が既にあり、同じ考え方に揃う。

**テストは合成した fixture jsonl で行う。** 本物の会話ログは 30 日で消え、内容も環境ごとに違うのでテストの入力にできない。experience-to-skill に `tests/fixtures/sample-session.jsonl` と「fixture は PII と秘密を含まない」要件の前例があるので、それに倣う。sidechain の行・重複した `requestId`・削除済み `cwd`・複数 issue への投稿を含む fixture を作る。

## Risks / Trade-offs

**誤配分**（1 セッションが複数 issue を触るため、区間分割は推定でしかない）→ issue 単位の数字は「だいたいこのくらい」として読むものと明示する。出力に区間の内訳を出して、どの区間がどの issue に寄ったかを利用者が確かめられるようにする。PR 単位は commit がブランチに紐づくぶん確かなので、そちらを主に使う。主が承認済みのリスク。

**料金表のずれ**（新モデルの追記が遅れると、そのぶんが落ちる。200K 超の割増も未モデル化）→ 未知モデルの名前と行数を出力に出して、落ちていることが見えるようにする。割増は今回モデル化しない。主が承認済みのリスク。

**固定レートは実勢と離れる** → 円は目安であって請求額ではない。出力にレートを添えることで、読み手が「このレートでの換算だ」と分かる。実勢に合わせたいときは環境変数で上書きできる。

**全履歴スキャンの所要時間**（8.4 秒。ログが増えれば伸びる）→ この change では許容する。`/cost` は手で叩くコマンドで、描画のたびには走らない。伸びが問題になるなら #274 の台帳が先に効く。

**未帰属のコストが残る**（ブランチも issue も持たない行、リポジトリ識別子が不明な行）→ 0 として消さず、未帰属および「リポジトリ不明」として集計に残す。合計が総額と合うことをテストで押さえる。

**python3 を実行時依存に加える**（このリポジトリの他プラグインは bash と jq が主）→ プロトタイプが python3 で、JSONL の 1 パス処理と辞書集計を bash と jq でやり直すのは実装量と速度の両方で不利。依存を明記して受け入れる。

## Migration Plan

新規プラグインなので移行は無い。`plugins/cost-ledger/prototypes/` は削除せずに残す（削除は #276）。プロトタイプの出力が本番実装の期待値になるので、この change のあいだは並存させて突き合わせに使う。

突き合わせは**同時に実行して比べる**。会話ログは既定 30 日で消えるため古い行から抜けて絶対値は下がっていくが、実装とプロトタイプは同じログを読むので、同じ時点で走らせれば一致する。受け入れ条件の「$108 ± $1」はこの読み方をする。

## Open Questions

無し。円換算のレート（固定レートを採用）と、番号を渡さなかったときの既定動作（作業ディレクトリの現在のブランチを見る）は、いずれも Decisions で決めて spec の Requirement に落とした。
