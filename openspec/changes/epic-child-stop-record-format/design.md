## Context

#1033（PR #1044）で、Orca 経路で起動されたエピックの子（`epic-dispatch.sh route` が `nested` を返すセッション）は、主の返事を待って止まる前に記録先の issue へ 1 行目 `子の停止: 主の返事待ち` の記録を投稿し、`mark stopped` で印を付けるようになった。記録の 2 行目以降には止まった理由・推奨とその根拠・推奨を選ぶと受け入れるリスク・再開に要る途中経過の 4 つを書くが、項目名・並び・改行の形は #1036 に委ねられている。

読み手は 3 者いる: 親のセッション（Orca 経路の手順 8 で、止まった理由と推奨を主に報告する）、親の決める役（#1034 で、エピックの目的・完了条件・子 issue・この記録だけを読んで進めてよいかを決める）、主（記録へのリンクから開く）。どれも子の会話を読んでいない。#1034 は並行して動いていて、この記録の形を前提にする。

子の完了報告は、主が子のタブを開いたときに最初に目に入る文で、今は主が次に何をすればよいかを書く決まりが無い。

## Goals / Non-Goals

**Goals:**

- 記録の 2 行目以降を、読み手が項目名で拾える決まった形にする
- 「前提」（子が作業中に分かった事実のうち判断に要るもの）を独立した項目にし、読み手が子の会話を読まずに判断できるようにする
- エピックの子の完了報告に、主がこのセッションで次にすることの有無を必ず書かせる

**Non-Goals:**

- 親が主への説明を書き直す手順と、親の手順 8 の動き（#1034）
- 子でないセッションの完了報告や、`引き継ぎ: 主の返事待ち` の書式の変更
- 聞き返しの件数の計測（マージ後に 2 週間待つ。エピックへのコメントは本体が後で扱う）
- 記録の中身（理由・推奨・リスク）の正しさの検査

## Decisions

### 記録の項目は 6 行の `項目名:` で固定し、並びも固定する

並び: `止まった理由:` → `前提:` → `推奨:` → `推奨の根拠:` → `受け入れるリスク:` → `再開に要る途中経過:`。

- 推奨と根拠を別の項目にするのは、親の手順 8 が「推奨」だけを主に報告し、親の決める役が根拠まで読む、という読み方の違いに合わせるため。1 項目にまとめると、報告に根拠の長文が混ざるか、推奨だけを切り出す判断が親に残る
- 並びは `rules/communication-style.md` の「判断を求めるときは、背景から書いて、推奨まで出す」の順（何が起きたか → 判断に要る事実 → 推奨 → リスク）に合わせる。読み手が上から読めば判断の材料がそろう
- 項目名 `止まった理由` と `推奨` は親の手順 8 の文（「止まった理由・推奨・そのコメントの URL を報告する」）と同じ語にする。これで手順 8 の文を変えずに済み、#1034 の範囲に入らない
- 「決めてほしいこと」を別の項目にする案は採らない。止まる理由には判断を求めるもの以外（実機の操作・動作確認）もあるので、`止まった理由` を「主にしてほしいこと（決めること 1 つ、または操作）と、それを子の側でできない理由」と定義して 1 項目に収める。issue の挙げた 5 つの情報から項目を増やさない

代案: Markdown の見出し（`## 止まった理由`）で区切る案。GitHub 上では読みやすいが、`引き継ぎ: 主の返事待ち` が `項目名: 値` の行で書いていて、子・親・決める役が読む書式を 1 種類にそろえるほうが読み間違いが少ない。見出し案は採らない。

### 値は複数行を許し、該当が無いときは `なし` と書く

- 各項目は行頭の `項目名:` で始め、値は同じ行に書く。前提のように箇条書きが要る値は、次の項目の行まで複数行に続けてよい（`引き継ぎ` の書式は 1 行 1 項目だが、前提と途中経過は 1 行に収まらないことが多い）
- 6 項目は省かない。判断に要る事実が無ければ `前提: なし`。推奨を出せない（主の側にしか無い情報が要る）ときは `推奨: なし（<足りない情報>）` と書き、根拠とリスクは `なし`。項目の有無で読み手が「書き忘れ」と「該当なし」を区別できるようにする
- 「保留で止まるときの引き継ぎ」を書く場面では、#1033 のとおり `再開に要る途中経過:` に引き継ぎのコメントの URL を書く。ほかの 5 項目も省かない（親の決める役は引き継ぎを読まずに判断する）

### 書き方の決まりは読み手が子の会話を読んでいないことから来るものに絞る

記録の書き方として次の 3 つを SKILL.md に書く: 子が作業中に振ったラベル・番号・略称や「上記」「前回」で指さず中身を書く／PR・issue・コメントはフル URL を添える／専門用語は初出で一言の言い換えを添える。経緯で挙がった聞き返し（「起票って何？」「何この 1 行足す検定」）がこの 3 つで防げる種類だから。文章全般の書き方は `rules/communication-style.md` が正本で、ここに写さない。

### 完了報告の 1 行目はエピックの子に限り、`mark` の `done` / `waiting` と対応させる

- 対象は記録と同じく `route` が `nested` を返すセッション（エピックの子）に限る。issue の目的が「子のタブを主が開いたとき」で、それ以外のセッションは主が会話の前にいる。範囲を広げると子でないセッションの振る舞いが変わり、記録先の範囲を超える
- 書式は 1 行目 `主がこのセッションで次にすること: なし` か `主がこのセッションで次にすること: <どの画面で何をするか>`。1 行目に置くのは結論から書くため（タブを開いた主が最初に読む）
- マージ済みで `mark <done|waiting>` を呼ぶときは、1 行目が `なし` なら `done`、中身があれば `waiting` にする。既存の「完了報告にマージ後の依頼を書いたなら `waiting`」と同じ判断で、1 行目を見れば印の選び方が決まるので、報告と印が食い違わない
- 置き場所は SKILL.md の節「ループの終わり」の、`mark` の項の前に 1 項目足す。並行する PR #1042（#1035）が同じ節の「PR がマージされていないとき」の項を書き換えているので、その項と隣り合わない位置にして衝突を避ける

### テストで項目名と並びを固定する

#1033 は「記録の 2 行目以降の項目名は文言のテストで固定しない」とした（形が決まっていなかったため）。この change で形が決まり、親の決める役（#1034）が項目名で読むので、`tests/epic-dispatch.bats` で SKILL.md の 6 つの項目名がこの並びで書かれていることを確かめる。#1036 への委任の文を確かめていた行は外す。

## Risks / Trade-offs

- [#1034 が並行して、別の項目名を前提に親の手順を書く] → 項目名 `止まった理由` / `推奨` は手順 8 の既存の語と同じにした。#1034 はこの change のマージ後に記録の形を SKILL.md で読める
- [PR #1042 と節「ループの終わり」で文が衝突する] → 足す位置を #1042 が書き換える項と隣り合わない場所にする。衝突したら後からマージする側が直す
- [6 項目を毎回書くと短い停止でも記録が長くなる] → 該当が無い項目は `なし` の 1 語で済む。項目を省ける形にすると読み手が書き忘れと区別できない

## Migration Plan

SKILL.md の文とテストの変更だけで、スクリプトや既存の記録には触れない。既に投稿された形の違う記録は、最新の 1 件を正とする規定のままなので、次に止まったときに新しい形になる。戻すときはこの PR を revert する。
