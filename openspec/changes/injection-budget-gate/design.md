## Context

claude-harness は「全セッションに載る文書」そのものを製品にしているリポジトリで、`rules/*.md` は `scripts/sync.sh` が `~/.claude/rules/` へ symlink して全プロジェクトのセッション冒頭に注入され、リポジトリ直下の `CLAUDE.md` はこのリポジトリで作業する全セッションに注入され、`plugins/*/skills/*/SKILL.md` の frontmatter `description` は skill 一覧として全セッション・全サブエージェントに載る。つまりこの 3 種は編集した瞬間に全リクエストの固定費になる。

現状の実測（バイト、2026-09-09 時点）:

| 対象 | 定義 | 実測 |
|---|---|---|
| rules | `rules/*.md` から `README.md` を除いた 9 本 | 23,274 |
| CLAUDE.md | リポジトリ直下の 1 本 | 5,252 |
| SKILL.md description | `plugins/*/skills/*/SKILL.md` の frontmatter 17 本 | 8,640 |
| 合計 | | **37,166** |

既存のテストランナー `scripts/test.sh` は `git ls-files '*.bats'` で対象を動的に発見するため、`tests/` に bats を 1 本置くだけで全件実行の経路に乗る。

## Goals / Non-Goals

**Goals:**
- 固定分の合計サイズが予算を超えたら `scripts/test.sh` が fail し、「削るか、予算を上げるか」を PR の diff として主の前に出す
- 超過時に 3 種の内訳と超過量を出し、どこが増えたかを読めばわかる状態にする
- 予算値の変更が単独の diff 行として現れ、レビューで見逃せない形にする
- エピック #257 の #260（固定分の削減）が同じ物差しで削減量を測れるようにする

**Non-Goals:**
- 実行時にルールを切り捨てる仕組み（どのルールが落ちたか誰も気づけないので作らない。エピック #257 で確定済みの判断）
- PR の diff に現れない固定分（`MEMORY.md`・接続コネクタ名・output style・Claude Code 組み込みの skill 一覧）の計測。これは実行時監視 #259 の役割
- トークン数での計測（tokenizer への外部依存が要る。#259 の usage 監査側で扱う）
- rules の path スコープ frontmatter への対応（#260 で扱う。現状該当ファイルが 0 件なので、使われない分岐を先に書かない）

## Decisions

### 1. 予算値は独立ファイル `tests/injection-budget.txt` に置く

**採用**: 数値 1 行だけのプレーンテキストファイル。bats はこれを読んで比較する。

**代替案**: bats スクリプト内の定数（`BUDGET=39000`）。

**理由**: 受け入れ条件が「予算値を上げると pass に戻る（値の変更だけで diff に現れる）」を求めている。bats 内の定数だと、テストロジックの修正と予算の引き上げが同じファイルの diff に混ざり、レビューで「値を上げただけ」と「判定を緩めた」を見分けにくい。独立ファイルなら `git diff --stat` に `tests/injection-budget.txt | 2 +-` として単独で出る。また聖域扱いの対象をパスで指定できる（auto-merge の SACRED 判定・レビューの注意対象がファイル名で表現できる）。

### 2. 測定単位はバイト（`wc -c`）

**採用**: `wc -c` によるバイト数。

**代替案**: 文字数（`wc -m`）、トークン数。

**理由**: `wc -m` はロケール依存で、CI の Linux ランナーのように `LC_ALL` が未設定・`C` の環境では実質バイト数に化ける。手元（`en_US.UTF-8`）と CI で同じ日本語ファイルが違う値になると、予算超過が環境で変わるという最悪の壊れ方をする。このリポジトリには既に `tests/shell-multibyte-expansion.bats` というマルチバイトの罠の退行ガードがあり、同じ罠を新しいテストで踏み直さない。バイト数はロケール非依存でどこでも同じ値になる。トークン数はコストの実体に近いが tokenizer への外部依存が必要で、テストを `bats` だけで完結させられなくなる。予算の目的は絶対量の管理ではなく「増分に気づくこと」なので、バイト数で足りる。

### 3. rules の測定対象は `scripts/sync.sh` が symlink するものに一致させる

**採用**: `rules/*.md` のうち `README.md` を除く（sync.sh の除外規則と同じ）。

**代替案**: `rules/*.md` 全件を数える、テスト側に独自の除外リストを持つ。

**理由**: 「何が全セッションに注入されるか」の正本は `scripts/sync.sh`（`~/.claude/rules/` へ張る symlink）であり、`tests/rules-sync.bats` の `README.md is not symlinked` が既にその規則を固定している。`rules/README.md` は目次であって注入されないので、数えると予算が実態より 1,835 バイト厚くなり、README を書き足すと無関係に予算が減る。除外リストを新しいテストに独自に書くと定義が 2 か所になるので、除外規則そのものを sync.sh と同じ 1 条件（basename が `README.md`）に揃え、テストのコメントに「正本は sync.sh」と書く。

### 4. 予算は合計 1 本。内訳は fail 時の出力のみ

**採用**: 3 種を足した合計に対して 1 つの予算。fail メッセージで内訳を表示する。

**代替案**: 3 種それぞれに予算を持つ。

**理由**: #260 の削減は「rules に書いてある内容を skill の reference に移す」「CLAUDE.md から docs/ へ出す」のように 3 種の間を移動する形になる。カテゴリ別予算だと移動のたびに 2 か所の予算を同時に直す必要があり、移動と増加の区別がつかなくなる。合計 1 本なら移動は合計を変えないので、予算が動くのは本当に増えたときだけになる。どこが増えたかは内訳表示で足りる。

### 5. `CLAUDE.md` は数え、`AGENTS.md` は数えない

`AGENTS.md` はタイトル行と同期宣言行を除いて `CLAUDE.md` と同一内容であることを `tests/agents-md-sync.bats` が強制している複製で、セッションに注入されるのは片方だけ。両方数えると同じ文が二重計上され、予算が実態の 2 倍動く。

### 6. 予算引き上げの規約は `rules/plugin-editing.md` ではなく `CLAUDE.md` に置く

**採用**: リポジトリ直下の `CLAUDE.md` に 1 行（`AGENTS.md` も同期して更新する）。

**代替案**: `rules/plugin-editing.md` に 1 行。

**理由**: `rules/*.md` は全プロジェクトに配布されて全セッションに注入される。claude-harness というリポジトリ 1 個の予算ファイルの話をそこに書くと、他プロジェクトのセッション全部にこの 1 行が乗り続ける — まさにこの change が減らそうとしている固定分を、この change 自身が増やすことになる。`CLAUDE.md` はこのリポジトリで作業するときだけ読まれるので、規約の適用範囲と注入範囲が一致する。

## Risks / Trade-offs

- **予算を上げるのが簡単すぎて形骸化する** → 予算ファイルの変更を聖域扱い（`CLAUDE.md` / `rules` と同じ）とし、PR 本文に「何を削ろうとして、なぜ超えるままにするか」を書く規約を `CLAUDE.md` に置く。強制は機械ではなくレビュー（pr-review-gate）が担う。テストが機械的にできるのは「値が動いたことを diff に出すこと」までで、そこで止めるのが分担として正しい
- **バイト数はトークン数の代理でしかない**（日本語は 1 トークンあたり 1.5〜3 バイト程度で振れる） → 予算の目的は絶対量の管理ではなく増分の検出。トークン換算での実測は #259 の usage 監査が持つ
- **予算に入らない固定分が増えても止まらない**（`MEMORY.md`・コネクタ名・組み込み skill 一覧） → 非目標として明記済み。実行時監視 #259 が担当する。編集時ゲートは「このリポジトリの PR で増える分」だけを守る
- **プラグインが増えると自動で対象が広がる**（`plugins/*/skills/*/SKILL.md` の glob） → 意図した挙動。新しい skill を足せば固定分が増えるのは事実なので、予算が反応するのが正しい
- **導入直後に他の PR が予算超過で落ちる** → 初期値を現状値 37,166 に約 5% の余裕を足した 39,000 とし、導入時点では pass する状態にする
