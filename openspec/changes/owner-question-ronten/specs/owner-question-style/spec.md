## ADDED Requirements

### Requirement: 主に聞く理由に論点の有無を書き、論点の無い確認を短くする
`output-styles/readable.md` の節 3 と `rules/communication-style.md` の 3 番目は、どちらも次を持たなければならない（MUST）。

- 論点の定義: 主が持っていて自分（エージェント）が持っていない観点を足すと結論がよくなる点。判断材料が自分の側にあるもの（コードや設定の細部、長い背景説明が要るもの）に論点は無く、自分で決める
- 書き分け: 論点ありなら論点を書く。論点なし（決まりで聞いている）なら、推奨どおりでよい旨と、その決まりが何を守るためかを書く
- 1 行目は、OK すると何が起きるかを中身で書いた質問にする。手続きの言葉（「リスク宣言を許容するか」）で聞かない
- 困りごとは、止めているのが自分の側だけで主の困りごとが無いときは書かない
- 受け入れるリスクは、推奨を選ぶことで新たに生じるもの（他の案や何もしない場合には無いもの）だけを書く。どの変更にも当てはまるもの（「見落としがあると壊れる」）は書かない
- 論点なしの確認は 3〜4 行に収める

正本の節 3 は、2026-10-22 の実例 2 つ（ゲートの決まりでトークンの扱いを変える PR の OK を求めた確認、エピックの親が子の PR の許容を求めた報告）を論点なしの形で書き直した例を持ち、どちらも 4 行以内でなければならない（MUST）。

#### Scenario: 両方の文書に論点の定義と書き分けがある
- **WHEN** `readable.md` の節 3 と `communication-style.md` の 3 番目を読む
- **THEN** どちらにも論点の定義、論点あり／論点なし（決まりで聞いている）の書き分け、1 行目の質問・番号を末尾の URL にだけ置くこと・困りごとが無いときは書かないこと・新たに生じるリスクだけを書くことが書かれている

#### Scenario: 実例の書き直しは 4 行以内
- **WHEN** 節 3 の「論点なし。実例」と見出しの付いた例を数える
- **THEN** 2 つあり、どちらも 4 行以内である

## MODIFIED Requirements

### Requirement: 主に問いを返す文章の書き方の正本は readable.md の節 3 に置く

`output-styles/readable.md` の「3. 判断を求めるときは」の節は、主に判断・確認・操作を求める文章の書き方の正本でなければならない（MUST）。節は次を含まなければならない（MUST）。

- 次の 6 段の順で、1 文に 1 つのことを書く: ①質問 ②主に聞く理由（1 文） ③いま困っていること（主が見て分かる現象で） ④推奨と根拠（何を基準に決めたかが分かる形で） ⑤受け入れるリスク ⑥答え方（区切りより上の本文の最後に置く）
- 主に聞く理由として成り立つのは次の 3 つだけ。どれにも当たらなければ聞かずに自分で決めて進め、事後報告する
  - 主の側にしか答えが無い（好み・事業判断・どこまでの被害を許せるか）
  - 決まりで主の承認が要る（聖域・取り消せない操作）。その決まりが何を守るためかまで書く
  - 主の手でしかできない操作（MFA・ログイン・人が押すと決まっているマージ）
- 受け入れるリスクは 3 つの要素で書く: 何が起きるか（被害の大きさ・戻せるか）／どれくらい起きるか（起きる条件と頻度。確かめたのか見込みかの別）／分からないときは「分からない」と書き、何を調べれば分かるかを添える
- 1 通で聞くのは 1 件
- issue・PR の番号で物を指さず（主語かどうかを問わない）中身で書き、番号は末尾の URL にだけ置く
- 背景の詳しい説明と元の記録の URL は、区切って下に置く（読まなくても答えられる位置）
- 確認作業の細部（テストの件数・レビューの周回）は書かず、「確かめ済み」とリンクで足りる
- 6 段の順で書いた例を 1 つ置く。例は 6 段がそれぞれ 1 文で見える短いもの（目安 600 バイト前後）にする
- 「主」（この会話で判断を下す人間のオーナー）と「聖域」（人の承認なしに変えてはならない設定や決まり）には、初出で一言の言い換えを添える
- どの理由に当たるかの判定は条件つきで指す: 観点の配役（`casting:casting`）が入っていれば、判定の詳細と、主に上げる前の相談の手順はその返信前チェックに従う。入っていなければ、上の 3 つの理由だけで判定する

`output-styles/readable.md` は、要件「配る候補の規則は環境固有の記述を持たず、プラグインの前提を条件つきにする」（`harness-public-private-split`）の対象の 6 ファイルの 1 つなので、この節（例を含む）もその制約に従わなければならない（MUST）。固有名とオーナーの環境のパスを書かず、Harness のプラグインに触れる文は「入っていれば」の条件つきで書く。

旧い型（目的 → いま取り組んでいる場所 → 起きた事実 → 決めてほしいこと → 推奨とリスク）と、「結論はA。ただしAは…これを飲めるならAで進める」の形式は、節に残してはならない（MUST NOT）。

この要件の守備範囲は、正本の節が上の決まりを持つことである。個々の発言が型を守っているか、推奨が正しいかは、この要件では止めない。

#### Scenario: 正本の節が 6 段と 3 つの理由を持つ
- **WHEN** `output-styles/readable.md` の節 3 を読む
- **THEN** 質問 → 主に聞く理由 → いま困っていること → 推奨と根拠 → 受け入れるリスク → 答え方の順、主に聞く理由の 3 つ、どれにも当たらなければ聞かずに進めて事後報告すること、リスクの 3 要素、1 通 1 件、番号で物を指さないことが書かれ、論点ありの例が 1 つと、論点なしの例が 2 つある

#### Scenario: 観点の配役への言及が条件つきで、配る候補の制約に従う
- **WHEN** `output-styles/readable.md` の `casting` を含む行を読み、6 ファイルを `grep -n -i -E 'oratta|genetta|suimei|flatmate|fmtoken|Dropbox|marketplaces/'` で検索する
- **THEN** `casting` を含む行に「入っていれば」があり、検索は 0 件である

#### Scenario: 旧い型が残っていない
- **WHEN** `output-styles/readable.md` を `目的 → いま取り組んでいる場所` と `これを飲めるならAで進める` で検索する
- **THEN** どちらも見つからない
