## Context

develop の本体は W を名前付きで spawn し、SendMessage で再開してコンテキストを引き継ぐ。コンテキスト量を測れるのは「再開する直前」だけで、それは実質「W が return した直後」に等しい。したがって **return の区切りの数がそのまま計測点の数**になる。

いまの区切りは 2 つ（(1) 仕様化まで／(3) 実装から）で、(3) は TDD 実装 → verify → archive → PR → 仕様宣言の 5 段階を束ねている。膨張が最も大きいのは実装区間（テストの読み書き・失敗ログ・grep）で、その区間が終わったところに計測点が無い。エピック #257 の別の子（#261）が W の起動の途中でも hook が測る経路を足したが、hook は「今の工程を締めて return せよ」と促すだけで、締める先の工程の粒度はこの change が決める。

親エピック #257 の子として、#261（途中計測 hook）がマージされた main から切る。隣の子 #263（手渡しの規則の本文を `decision-criteria.md` 1 箇所に集める）が同じファイル群を触るため、この change は手渡しの規則の本文を増やさない。

## Goals / Non-Goals

**Goals:**

- W の (3) を (3a) 実装＋verify と (3b) archive＋PR＋仕様宣言 の 2 回の return に分け、実装を終えた区切りで本体がコンテキスト量を測れるようにする
- (3a) の return に、手渡し先が verify をやり直さずに (3b) から続けられるだけの情報（実行したテストコマンドと exit code）を必ず載せる
- `工程完了:` の 1 行目に載る工程名を 3 つ（`仕様化まで` / `実装＋verify` / `archive＋PR＋仕様宣言`）に確定させる

**Non-Goals:**

- 手渡しの手順そのものを変えること。上限超を検知したあとの扱い・宣言の書式・前任が動作中のときの交代手順は `references/decision-criteria.md`「コンテキスト上限（サブエージェントの手渡し）」が正本のままで、本文をこの change で増やさない（#263 の担当）
- (3) をタスク単位にさらに細かく切ること（下の Decisions を参照）
- 計測の閾値・環境変数・hook の挙動を変えること（#261 の成果を据え置く）
- develop を 1 issue 分実機で回してトランスクリプトに残すこと。これはエピック #257 の完了条件側で確認する

## Decisions

### 1. 分割は 2 段で止め、タスク単位には切らない

**採用**: (3a) 実装＋verify ／ (3b) archive＋PR＋仕様宣言 の 2 段。

**代案（不採用）**: `tasks.md` の項目ごと、または「実装／verify／archive／PR／仕様宣言」の 5 段に切る。

**理由**: 手渡しは無料ではない。手渡しが 1 回起きるたびに、後任は指示書（`worker.md` と正本の節）を読み直し、記録先を取り直し、`git status` / `git diff` でファイルの現状を確認し、前任の埋めた決定を読み直す。この固定分は工程の大きさに依存しないので、区切りを増やすほど 1 区切りあたりの実質作業比が下がる。また区切りが実装の途中に落ちると、後任は「Red のまま止まったテスト」から再出発することになり、前任が頭の中に持っていた設計意図を再発明する危険が最も高い地点で交代することになる。**コードが緑になった地点**は、成果が git とテスト結果という機械可読な形で完結している唯一の区切りなので、そこを境にする。

さらに、2 段より細かい分割が実際に要るかどうかを判断する材料がまだ無い（(3a) 終了時のコンテキスト量の実測は #259 の監視が出す）。分割数を増やす提案はその実測を見てから扱う。

### 2. 境界は archive の手前に置く（verify は (3a) 側）

**採用**: `/opsx:apply` → `/opsx:verify` までを (3a)、`/opsx:archive` 以降を (3b)。

**代案（不採用）**: verify を (3b) 側に置き、(3a) を実装だけにする。

**理由**: verify は「実装が artifact と一致するか」の検証で、失敗したら実装に戻る。実装と verify を別の担い手に割ると、verify の失敗が即座に手渡し直後の巻き戻しになる。逆に archive 以降（archive・PR・仕様宣言）は実装内容に手を入れない事務手続きの束で、テスト結果を受け取れば別の担い手でも完遂できる。「戻る可能性がある区間」を 1 人に閉じ込め、「戻らない区間」を切り離す。

### 3. (3a) の return にテストコマンドと exit code を必須にする

**採用**: (3a) の return に、実行したテストコマンド・exit code・失敗件数を含める（MUST）。

**理由**: (3b) の担い手は仕様宣言（`仕様: 更新した` / `仕様: 変更なし`）と PR 本文に動作確認の証拠を書く。これは pr-review-gate 手順 5 が照合する対象で、証拠が無ければゲートを通らない。手渡しが起きた場合、後任はその証拠を前任の return からしか得られない（履歴は読めない）。ここを任意にすると、後任はフルテストを回し直すか、証拠なしで宣言するかのどちらかになる。前者は分割で削ったぶんのコンテキストを取り戻してしまい、後者はゲートで落ちる。

### 4. SKILL.md の `(3)` という見出しは残し、その下に (3a)/(3b) を置く

**採用**: 1 ループの疑似コードは `(3)` の行を残し、その内側に `(3a)` と `(3b)` を並べる。

**理由**: 工程番号 (0)〜(4) の並びは「W→R1→W→G の順序」を規定する既存要件で、(3) を消すと (2) と (4) のあいだの工程が消える。(3) を「W の実装以降の工程全体」の名前として残し、その内訳として 2 つの return を置くほうが、既存の順序規定と衝突しない。

## Risks / Trade-offs

- **手渡しの発生頻度が上がり、往復の固定費が増える** → 手渡しは「上限超が検知されたとき」だけ起きるもので、区切りが増えても手渡しが増えるわけではない。増えるのは計測の機会だけ。上限超でなければ本体はそのまま SendMessage で (3b) を指示する
- **(3a) と (3b) のあいだで W が止まったまま放置される** → (3a) の return は `工程完了: 実装＋verify` で、本体はその直後に測って必ず次の行動（再開 or 手渡し）を取る。放置は既存の「`工程中断:` を受け取ったら本体が未コミット差分を引き取る」規則と同じ経路で扱う
- **工程名の文字列がテストとドキュメントに散らばる** → 工程名の列挙は `worker.md` のコンテキスト上限の節 1 箇所に置き、SKILL.md の疑似コードはそれと同じ語を使う。テストは両面で同じリテラルを固定する
- **#263 との衝突** → この change では手渡しの規則の本文を増やさず、(3a)/(3b) の分割に必要な記述だけを足す。`decision-criteria.md` への変更は工程名の例（`工程完了: 実装から` → 分割後の工程名）に限る
