## Context

#521 の `pr-state.sh` が PR の観測と次の一手を分類し、#522 の `ci-watch.sh` と `references/ci-watch.md` が待機・再実行・修正の共通手順を持つ。共有手順には #523 の入口から呼ばれる余地と、呼び出し側が決める `ready` の差し込み口が既にある。入口だけが未実装である。

既存の `git-commit-policy.md` はマージに明示承認を要し、ゲート未通過 PR の無承認マージを禁じる。`destructive-git-guard.md` は main への push 等に方法とタイミングを含む事前承認を要する。共有 `ci-watch.md` は呼び出し側による直接の `gh pr merge` と merge API を禁じている。

## Goals / Non-Goals

**Goals:**

- オーナーが指定した PR の CI をメインセッションが見張り、失敗したら共有手順どおり `rerun` / `fix` / `escalate` に進む。
- マージ依頼の有無を `--merge` 引数で受け取り、依頼がある見張りだけ `ready` 後に既存ゲートを通して合格後のマージ経路へ接続する。依頼が無い見張りは `ready` で終える。
- 「マージして」の承認範囲を入口に明示する。
- ゲート未通過の PR で CI を落とす実機確認と、PR への結果記録を実装タスクに含める。

**Non-Goals:**

- `ci-watch.sh` / `pr-state.sh` の待機・分類規則を作り直すこと。
- ゲートの合格条件、自動マージ workflow、禁止されている直接マージ操作を変えること。
- サブエージェントに背景の CI 待機をさせること。

## Decisions

### `/ci-watch <PR>` を薄い入口にする

issue #523 が示す `/ci-watch <PR>` の形に、マージ依頼を表す `--merge` 引数を足した `/ci-watch <PR> [--merge]` を採用する。PR の URL または番号を既存の GitHub CLI の対象 PR に解決し、入口は `references/ci-watch.md` の開始判定・コメント・`wait`・`next`・一手の実行をメインセッションで呼ぶ。`wait` の観測で `ci-fail` かつ `retry=false` なら、同 reference の 2 条件を確認し、該当チェック名だけ `next --unrelated` に渡す。これがエピック #512 の「たまに落ちるテストなら 1 回やり直す」の呼び出し側責務である。`pr-state.sh` の同一 HEAD で 1 回という上限を再定義しない。

### 失敗の直しはメインセッションが起こす実装者が担う

`next` が `fix` を返したら、メインセッションが実装者のサブエージェント（model は sonnet）を起こし、共有 reference「7. 直し方」の手順で直させる。見張りと直しを別のコンテキストに保つためで、メインセッションは自分で直さない。これは同節の「develop を使わずメインセッションで pr-review-gate を回したとき」と同じ担い手で、入口のための新しい役割は作らない。実装者がログを読んで PR の差分と関係ない失敗だと返したら、メインセッションは直さず push もせずに `ci-watch.sh next <owner/repo> <PR番号> --unrelated <チェック名> --after-fix` を 1 回だけ実行し、その一手に従う。

代替の新しい待機スクリプトや仕分け実装は #522 と二重になり、入口とゲート後で結果がずれるため採らない。新しいスキルも追加せず、コマンドから既存手順を読む。

### マージ依頼の有無は `--merge` 引数で決める

入口は PR の URL か番号しか受け取らないので、そのままでは「マージして」と頼まれたかを知る手段が無い。このリポジトリでは `agent-review:passed` が付くと auto-merge.yml が自動でマージするため、見張りだけを頼まれた PR でゲートを回すと、オーナーの承認なしにマージされうる。そこで、マージ依頼はオーナーが `/ci-watch <PR> --merge` と引数で明示したときだけ有るとし、`--merge` が無ければ、依頼文にマージを思わせる言葉があっても依頼は無いとして扱う。

依頼文の自由文から判定する案は採らない。「CI 見てて、良さそうならマージかな」のような曖昧な言い方を取り違えると、承認の無いマージか、頼まれたマージの取りこぼしのどちらかになり、前者は取り返せない。引数なら有無が機械的に決まり、テストで確かめられる。

### `--merge` が無い見張りは `ready` で終える

`--merge` が無い見張りで `ready` を受けたら、ゲートを実施せず、ラベルも付け外ししない。1 行目が `CI 見張り終了:` のコメント（理由は「CI が通った。マージ依頼が無いのでゲートとマージには進まない」）を PR に投稿し、CI が通ったことを PR の URL を添えてオーナーに伝えて見張りを終える。ゲートやマージへ進めたいときは、オーナーが改めて頼む。

### `--merge` 付きの `ready` はゲートに接続する

`--merge` 付きの見張りはゲート未通過 PR を受け入れるが、CI の `ready` だけをマージ可能の証拠としない。`ready` になったら `pr-review-gate` を実施し、合格した場合だけ共有手順の「`ready` を受けたあと」にあるラベル確認・自動マージ待ちまたは人間へのマージ依頼へ進む。ゲートが failed / 保留なら、その通常の修正・保留手順に従う。修正の push 後は同じ見張りの状態ファイルで CI を見張り直す。

### 条件付きマージ依頼の承認範囲

オーナー本人が当該 PR に対して `/ci-watch <PR> --merge` で「CI が通ったらマージして」と直接依頼した事実は、**その PR が CI 成功と既存ゲート・リポジトリ運用の条件を満たした後にマージへ進める意思**として扱う。別の PR、別の HEAD に対するリスク許容、ゲート省略、main への直接 push、rebase・force-push、LLM による `gh pr merge` / merge API の実行を承認したものとは扱わない。自動マージが使えない場合とブロックラベルがある場合は、共有手順どおり PR URL を添えて人間にマージを依頼する。これは既存の権限規則を入口に適用したもので、新しいマージ経路は作らない。

## Risks / Trade-offs

- [共有手順の背景待機はメインセッションの生存に依存する] → 既存の開始・終了コメントで見張り中を可視化し、閉じたセッションからの再開は `ci-watch.md` の中断した一手の確認に従う。
- [関係ない失敗を誤判定する] → ログと変更ファイルの 2 条件が揃わなければ `--unrelated` を渡さない。再実行は同じ HEAD で 1 回に限る。
- [CI green をゲート合格と取り違える] → `--merge` 付きの見張りでは `ready` 差し込み口でゲートを必ず実施し、合格が確定するまでマージ待ち・依頼に進まない。
- [オーナーが自由文でマージを頼み `--merge` を付け忘れる] → 見張りは `ready` で終わり、CI が通ったことだけがオーナーに伝わる。マージが 1 回の往復分遅れるが、承認の無いマージは起きない。
