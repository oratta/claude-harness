## Context

エピックの親（エピックを回すセッション）は `epic-dispatch.sh launch` で子ごとに Orca のワークツリーと端末を作り、子セッションを `EPIC_DISPATCH_PARENT_EPIC=<epic> <cmd> --model <model>` で起動する（`plugins/dev-workflow/scripts/epic-dispatch.sh` の `cmd_launch`）。子も親も、止まってから 1 時間以上たって返事を受けることがある。会話のキャッシュは 1 時間で切れるので、そのまま返事を送ると会話全体 N を書き込み直す（入力換算 2N）。

Claude Code には待っている間の自動コンパクト（最後のリクエストから約 54 分で、会話が `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` 以上なら要約に置き換える）がある。既定は 200,000、下限は 100,000、54 分は変えられない。手元のログ（子 1,592 本・親 37 本）から測った値と損益は #1039 のコメント https://github.com/oratta/claude-harness/issues/1039#issuecomment-6182988861 にある。要点は次のとおり。

- 1 時間以上たってから返事が来た割合（会話 100k 以上の止まった点）: 子 3.2%、親 40.6%
- 返事の直前の会話 N の中央値: 子 159k、親 152k。既定の 200k ではほとんどがコンパクトの対象外
- 閾値を変えたときの費用の増減（期間合計、入力換算）: 子は 120k で −41.3M（基本）・−12.4M（控えめ）、親は 100k で −26.8M（基本）・−9.5M（控えめ）。既定 200k は子 −16.1M・親 −3.6M
- 起動し直しの費用 2C0 + R' は子で中央値 197k・平均 258k。コンパクトが走ったあとの返事は 2C + R で約 140k

止まった子を親が解決する手順は #1034 が develop の SKILL.md に書く。同じエピック #1038 の子が並行して `epic-dispatch.sh` と SKILL.md の他の節を直している。

## Goals / Non-Goals

**Goals:**

- 子セッションの待っている間の自動コンパクトの閾値を、主の手元のセッションに影響させずに 120,000 にする
- 親の閾値 100,000 と、それを付ける場所（主が親を起動するコマンド）を規則として残す
- 時間がたった子に「そのまま送る」か「起動し直す」かを分ける条件を、観測できる事実で書き、#1034 が参照できる場所に置く
- 1〜2 週間後に同じ集計をやり直して値を見直すことを規則に残す

**Non-Goals:**

- 子への返事の送り方・起動し直し方の手順本体（#1034 が書く）
- 親が通した判断をエピックのコメントに残す形（#1034 のやること 5）
- `idleCompaction` の有効・無効の切り替えや、54 分の時刻を変えること（Claude Code 側で変えられない）
- 再集計の自動化（集計スクリプトはリポジトリに入れない。再集計は手で行う）
- 件数・金額を合否の条件にすること

## Decisions

### 子の閾値は `launch` の起動コマンドの前置きで付ける

`CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS=<値>` を `EPIC_DISPATCH_PARENT_EPIC=<epic>` のうしろ、`<cmd>` の前に置く。コマンド全体は `EPIC_DISPATCH_PARENT_EPIC=<epic> CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS=<値> <cmd> --model <model>` になる。作り直しのコマンド（`recreate_hint`）は組み立てたコマンドをそのまま出すので、同じ前置きが自動で入る。

- 代わりの案: `~/.claude/settings.json` の `env` に置く → 主の手元の全セッションに効くので採らない。Orca に設定したエージェントのコマンドに書く → ハーネスから読めず、`launch` は Orca の設定を使わないので効かない
- 前置きの順は `EPIC_DISPATCH_PARENT_EPIC` を先にする。既存の Scenario「端末の作り直しのコマンドにも前置きが入る」の期待値（`--command 'EPIC_DISPATCH_PARENT_EPIC=420 ` を含む）を変えずに済む

### 値は子 120,000・親 100,000、子は環境変数で変えられる

子の既定 120,000 は、基本の想定で最良（100k の −41.4M とほぼ同じ）、控えめの想定でも最良（140k の −12.5M）とほぼ同じで、最悪の想定での損（+10.5M）が 100k（+14.4M）より小さい。親は返事なしで終わる割合が低く、基本で下限の 100k が最良。

子の値は `EPIC_DISPATCH_IDLE_COMPACT_MIN_TOKENS` で上書きできる（再集計で値を動かすとき、コードを直さずに試すため）。上書き値が空文字か数字だけでない文字列なら、使い方を出して exit 1 で止める（`EPIC_DISPATCH_MODEL` の空文字検査、`EPIC_DISPATCH_SUBMIT_WAIT` の数字検査と同じ扱い）。100,000 未満の値は検査しない（下限の扱いは Claude Code 側が持つ）。この検査が拾うのは、`120k` や `120,000` のような値が子の起動コマンドに入って子が閾値を読めず既定の 200,000 で動くことと、空白や記号でコマンドが壊れることだけで、大きすぎる値や先頭に 0 の付いた数字は通す。分ける条件（下の節）はスクリプトでは判定せず、本体が規則のファイルを読んで判定する。60 分や 150,000 の境目付近で扱いが揺れる子は止めない。どちらも、すり抜ける入力が見つかるたびに塞ぐことは完了条件にしない（守備範囲の正本は delta spec の新しい要件）。

### 親の値は主が親を起動するコマンドで付ける

親は主が起動するセッションなので、ハーネスからは環境変数を付けられない。規則のファイルに、主が親を起動するコマンドの先頭に `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS=100000` を付けることを書く。`settings.json` の `env` に置かない理由は子と同じ。

### 「そのまま送る」か「起動し直す」かは、端末・経過時間・コンパクトの有無・会話量で分ける

| 子の状態 | 扱い | 根拠 |
|---|---|---|
| 端末が無い | 起動し直す | ほかに手がない |
| 最後のリクエストから 60 分未満 | そのまま送る | キャッシュが生きている（0.1N） |
| 60 分以上で、その間にコンパクトが走った | そのまま送る | 2C + R で約 140k。起動し直し（平均 258k）より安く、子の判断も残る |
| 60 分以上・コンパクト無し・N が 150,000 以上 | 起動し直す | 2N が 300k 以上になり、起動し直しの平均 258k を超える |
| 60 分以上・コンパクト無し・N が 150,000 未満 | そのまま送る | 2N が起動し直しより安い |

判定に使う事実は、子の端末の有無（`orca terminal list --worktree path:<子> --json`）、子のワークツリーのセッションのトランスクリプト（`~/.claude/projects/` 配下の jsonl）の最後のリクエストの時刻とその後の `compact_boundary` の有無、会話量 N（`plugins/dev-workflow/scripts/subagent-context.sh --file <トランスクリプト>`）。規則のファイルにこれらを書く。親自身が長く待ったあとも同じ表で「続ける」か「起動し直す」かを決める（親の端末は主が持っているので、端末が無い行は当たらない）。

- 代わりの案: 一律に起動し直す → 60 分以上の返事のほとんどで 2C0 + R' を払い、子が積んだ判断も捨てる。一律にそのまま送る → PC が寝ていてコンパクトが走らなかった大きな会話で 2N を払う

### 規則は references の新しいファイル 1 つに置き、SKILL.md は指すだけにする

`plugins/dev-workflow/skills/develop/references/reply-after-idle.md` を新設し、値・分ける条件・判定に使う事実・親への適用・親の状態の復元・再集計を置く。develop の SKILL.md「回し方」には、子の起動コマンドに閾値が付くことを 1 文、時間がたった子・親に返事を送る前にこのファイルの規則で決めることを短い段落で足すだけにする。

- 代わりの案: SKILL.md に規則を全部書く → 常時読まれる量が増え、並行する #1034 が同じ節を直すので衝突する。#1034 は送り方の手順からこのファイルを指せばよい
- SKILL.md の「`nested` を受けたセッション」の段落と、「`epic-dispatch.sh` が足すのは `--model` だけ」の文は触らない（後者はコマンドの引数の話で、前置きの環境変数は引数ではない）

## Risks / Trade-offs

- [要約で落ちた情報の読み直し R が実測より大きい] 待っている間の自動コンパクトの実績は 14 回だけで、S・C・R は少ない例から出した → 控えめの想定（S を 3 倍、R に 40k 足す）でも 120k は既定より安い。1〜2 週間後の再集計で値を見直す
- [返事が来ないまま端末が開いていると、コンパクトの費用 0.1N + 5S が無駄になる] → Orca 経路の子は `reap` で端末が閉じるので当たりにくい。最悪の想定（端末が全部開いたまま）では既定より損になる（+10.5M）ことを規則のファイルに書き、再集計で確かめる
- [PC が寝ているとコンパクトが走らない] 効果は見積もりより小さくなる（損得の向きは変わらない）→ 分ける条件の「コンパクト無し・N 150k 以上は起動し直す」で拾う
- [この変更より前に起動された子には前置きが無い] 既定の 200,000 のまま動く → 起動し直したときに新しい前置きが付く。それ以上の手当てはしない

## Migration Plan

マージ後の `launch` から子に前置きが付く。動いている子は起動し直すまで従来どおり。親の値は主が次に親を起動するときから付ける。戻すときは `EPIC_DISPATCH_IDLE_COMPACT_MIN_TOKENS=200000` を付けて `launch` すれば既定と同じ値になる。
