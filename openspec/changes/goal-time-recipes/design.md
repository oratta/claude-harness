# Design: goal-time-recipes

## Context

本 change は run「anthropic-knowledge-reflect」の change-3 であり、公式記事「Getting started with loops」の 4 ループタイプのうち**ゴールベース**と**タイムベース**を、ユーザーの定常業務に落とした初期シードレシピ 6 本として実装する。

前提となる公式の立場: ループのランタイムはネイティブプリミティブ（/goal・/loop・/schedule・skill・Workflow・auto mode）であり、ループはその合成で作る。ハーネスの責務は**レシピ（設計図）の提供**であって実行系の再発明ではない。

依存: **change-1 (loops-plugin)** が先行し、レシピ形式の固定見出し規約（ループ型 / 目的 / 起動コマンド / 停止基準 / 前提 / コスト注意 / エスカレーション）、置き場所 `plugins/loops/recipes/`、および実行機構との責務分離の宣言（`references/loop-types.md`）を整備済みであること。本 change はその規約の最初の消費者となる。

一次ソース（迷ったらここに立ち返る）:

- `_longruns/2026-07-04_anthropic-knowledge-reflect/research/loop-engineering.md` 冒頭の公式記事セクション — /goal は「定量的な基準（テスト合格数・スコア閾値）が最も効果的」、公式例 `/goal get the homepage Lighthouse score to 90 or above, stop after 5 tries`、`/loop 5m check my PR, address review comments, and fix failing CI`、トークン管理（頻度最小化・決定論部分のスクリプト化・パイロット実行）

## Goals / Non-Goals

**Goals:**

- goal レシピ 3 本（tests-green / acceptance-pass / lighthouse）: 機械検証可能な成功基準（コマンド + 期待値）+ 最大試行数を必須とするゴールベースの初期シード
- time レシピ 3 本（pr-babysit / daily-report / weekly-report）: 保守的な頻度デフォルト + 停止基準 + 実行環境制約を宣言するタイムベースの初期シード
- 全レシピが change-1 の固定見出し規約に準拠し、コピペで動くネイティブコマンド文字列を第一級の成果物とする
- レシピ規約準拠（見出し・停止基準・ネイティブ起動）を bats + grep で機械検証できるようにする

**Non-Goals:**

- 定期実行の機構・配線一式（セッション内 cron 登録スキル・SessionStart 復元 hook・session-host supervisor・launchd 設定・`claude -p` 配線）。実行側は別セッションの Pikke プロセス整理が担い、レシピは実行方法非依存に書く
- 独自ループランタイム（loop-definition schema・driver スクリプト・常駐プロセス）。反復・スケジュール・停止判定はネイティブ（/goal の最大試行・/loop /schedule のキャンセル）に任せる
- daily-report / weekly-report プラグイン本文の変更（レシピはあくまで登録・運用手順）
- プロアクティブ合成ルーチン（change-4）とレシピ棚の成長・実測チューニング（change-4 の recipe-miner が担う）
- レシピの schema 化・機械検証の高度化（markdown 見出し規約 + grep で足りる。必要になったら backlog）

## Decisions

### D1: レシピは markdown のみ。起動コマンド文字列を第一級の成果物とする

- **選択肢**: (a) レシピを YAML/JSON schema で構造化し機械検証する / (b) markdown 固定見出し規約 + コピペ可能なコマンド文字列
- **決定**: (b)
- **理由**: 公式路線は「ネイティブプリミティブの合成」であり、レシピは人間とエージェントが読む設計図。schema 化は前版 plan で廃案になった独自ランタイム路線への逆戻りの入口になる。config.yaml rule「レシピはネイティブコマンド文字列を第一級の成果物とする（コピペで動くこと）。独自 CLI やラッパースクリプトを作らない」をそのまま適用する。規約準拠の検証は grep ベースの bats で十分

### D2: goal レシピの成功基準は「コマンド + 期待値」形式を必須とし、主観基準を禁止する

- **選択肢**: (a) 自然言語の目標記述を許容する / (b) 検証コマンドと期待値（exit code・PASS 件数・スコア閾値）の組を必須とする
- **決定**: (b)
- **理由**: 公式記事の「定量的な基準（テスト合格数・スコア閾値）が最も効果的」に直接従う。エバリュエータモデルが成功を判定するため、曖昧な基準は報酬ハッキング（検証なき成功宣告）の余地を生む。「完了は主張であり証明ではない」の原則をレシピレベルで強制する

### D3: 全 goal レシピに最大試行数のデフォルト値を具体的な数値で書き込む

- **選択肢**: (a) 最大試行数をプレースホルダ（N 回）のまま利用者に委ねる / (b) 保守的なデフォルト値を書き込み、変更箇所を併記する
- **決定**: (b)。goal-lighthouse は公式例どおり 5 回。goal-tests-green / goal-acceptance-pass も 5 回をデフォルトとし、起動コマンド文字列中のどこを書き換えれば変更できるかを併記する
- **理由**: プレースホルダのままだとコピペで動かず「コピペで動くこと」の規約に反する。また打ち切り条件の無いまま起動される事故（無限リトライ）を構造的に防ぐ。優先順位「安全性 > レシピの本数」に従い、迷ったら保守的な値に倒す

### D4: time レシピの頻度デフォルトは保守的に固定し、変更方法を併記する

- **選択肢**: (a) 利用者に頻度を都度決めさせる / (b) 保守的デフォルト（pr-babysit は 5〜10 分、レポート系は日次/週次）+ 変更方法併記
- **決定**: (b)
- **理由**: config.yaml rule そのまま。公式トークン管理の第一項目「ルーチン実行頻度を必要最小限に」をデフォルト値として焼き込む。頻度を上げる判断は利用者が明示的に行う（変更方法は書いてあるので摩擦は低い）

### D5: cron レシピは「発火時プロンプト・推奨頻度・停止基準・実行環境制約」の 4 点のみを宣言し、スケジューラ登録に踏み込まない

- **選択肢**: (a) /schedule への登録コマンドや launchd 設定例まで含める / (b) 実行方法非依存のインターフェース宣言に留める
- **決定**: (b)
- **理由**: 定期実行の配線は別セッション（Pikke プロセス整理）の責務であり、本 plan の明示的なスコープ外。レシピに登録手順を書くと実行側の設計変更のたびにレシピが陳腐化する。change-1 が `references/loop-types.md` に明記する責務分離（レシピ = 発火時プロンプト + 推奨頻度 + 停止基準 + 実行環境制約まで）に従う。ローカルデータ（Vault・セッション jsonl）依存という制約はレシピ固有の事実なのでレシピ側に書く

### D6: loop-pr-babysit の外向きアクションは Draft PR 更新までに制限する

- **選択肢**: (a) 公式例のまま（CI 修正・コメント対応のみ指示）/ (b) このリポジトリの CLAUDE.md 運用に合わせ、非破壊境界（merge 禁止・Ready for Review 切り替え禁止・main 直 push 禁止）を明文化する
- **決定**: (b)
- **理由**: 全体方針「ループの外向きアクションは非破壊デフォルト。不可逆操作は人間へエスカレーション」。/loop は人間不在時間帯にも回るため、境界をプロンプト（起動コマンド文字列）自体に埋め込み、エスカレーション条件の節と二重化する

### D7: レシピ準拠検証は plugins/loops/tests/ の bats に集約する

- **選択肢**: (a) 検証スクリプトを scripts/ に新設する / (b) 既存のテスト実行系（`find plugins -name '*.bats' -print0 | xargs -0 bats`）に乗る bats ファイル 1 本
- **決定**: (b)。`plugins/loops/tests/recipes-seed.bats` に固定見出し・停止基準・最大試行数・ネイティブ起動・モデル ID 不在の grep 検証をまとめる
- **理由**: 受け入れ条件 2 のテスト実行コマンドがそのまま拾う場所に置くことで、統合検証（受け入れ条件 4）で追加の配線が不要になる

### D8: モデル ID はレシピに書かない

- **選択肢**: (a) レシピ内でモデルを指定する / (b) モデル指定を一切書かない
- **決定**: (b)
- **理由**: 制約「モデル ID 直書き禁止（`plugins/longrun/references/model-tiers.md` が唯一のソース）」。レシピの起動コマンドはネイティブプリミティブであり、モデル解決は実行側（セッション設定・agent 定義）の責務。grep 検証（`claude-` ヒット 0 件）をテストに含める

## Risks / Trade-offs

- [change-1 の固定見出し規約の文言が本 change の想定とずれる（例: 「必要な前提」vs「前提」）] → 実装開始時に change-1 の成果物（レシピ形式規約）を必ず読み、見出し文字列は change-1 の規約を正とする。bats の grep パターンも change-1 の規約文字列から取る
- [/goal・/loop のコマンド構文がドキュメント想定と実機で異なる] → 実装時にパイロット実行（goal-tests-green をこのリポジトリで 1 回起動）して構文を確認する。plan の動作確認手順 3 がこのデモを要求している
- [goal-lighthouse はこのリポジトリ（CLI プラグイン集）では実測できない] → Web プロジェクト汎用レシピとして前提の節に「Web プロジェクトで使用。Lighthouse 実行手段（例: `npx lighthouse`）が必要」と明記し、検証はレシピ規約準拠（見出し・基準形式）の grep に留める。公式例の忠実な移植であることを本文に記す
- [cron レシピが参照する daily/weekly-report の非対話モードの起動文字列が将来変わる] → レシピの前提の節に対象スキルのバージョン前提を記載する。レシピ本文の実測チューニングは change-4 の recipe-miner の責務（(d) 既存レシピの実行痕跡からのチューニング候補抽出）に委ねる
- [pr-babysit の 5 分間隔が長時間放置されるとトークンを浪費する] → 停止基準に PR マージ/クローズ検知での終了を必須化し、コスト注意にパイロット実行（まず 1 PR で数サイクル観察）を明記する

## Migration Plan

1. bats テスト（`plugins/loops/tests/recipes-seed.bats`）を先に書く（RED）→ goal レシピ 3 本 → time レシピ 3 本の順で実装し GREEN 化する
2. **後方互換**: 新規ファイルのみの追加であり、既存プラグインの動作に影響しない。daily/weekly-report は無変更
3. **ロールバック**: `plugins/loops/recipes/` の 6 ファイルと bats を削除するだけで完全に元に戻る（他ファイルへの参照追加が無いため）
4. version bump・marketplace.json 同期は change-5 が一括して行う（本 change では行わない）

## Open Questions

- /goal の最大試行数の指定構文（`stop after 5 tries` の自然言語指定で足りるか、オプション引数があるか）は実装時のパイロット実行で確定する。どちらでもレシピの停止基準の記述形式（デフォルト値 + 変更箇所の併記）は変わらない
- cron-daily-report の発火時プロンプトに `--with-album` 等のオプションを含めるかは実装時にユーザーの現用フローを確認して決める（デフォルトはオプション無しの保守的構成とする）
