## Context

- W は工程ごと（(1) 仕様化まで／(3a) 実装＋verify／(3b) archive＋PR＋仕様宣言）に return し、コンテキストが上限を超えると本体は同じ役割の新しい W を起こして前任の return と記録先を渡す（手渡し。規則の正本は `decision-criteria.md`「コンテキスト上限（サブエージェントの手渡し）」）。後任は前任の履歴を読めないので、return の成果一覧が手渡しの唯一の入力になる
- 成果一覧は今「編集済みファイル・通ったテスト・判明した事実・埋めた決定・残作業」で、コードの場所が無い。後任は同じファイルを探して読み直す
- 読み直しの割合は `plugins/dev-workflow/scripts/subagent-context-audit.sh --by-role` の `W.reread_pct` で測れる（#552、PR #563 でマージ済み）。ただしこの値は走査した期間の全 issue にまたがる中央値で、issue 1 本だけの値を出すオプションは無い
- 同じ worker.md を段ごとのファイルに分ける #556 が open。先にマージした側に合わせて後の側が直す

## Goals / Non-Goals

**Goals:**

- 後任 W が、前任の読んだ場所を案内にして必要な範囲だけを読めるようにする
- 実装の担い手が、仕様づくりの段で決めた「どこを触るか」を探し直さずに済むようにする

**Non-Goals:**

- 前任の要点を後任の判断の根拠にすること（要点は案内に限る）
- G・R1 の return の中身を変えること（G は #554 で段ごとに新しく起こし、手渡しの形を取らない）
- `reread_pct` を issue 単位で出すようにツールを直すこと
- 途中計測 hook の通知文・トリップワイヤーのテンプレートの文言を変えること

## Decisions

### 決定 1: 欄の書式は 1 行 1 件・上限 20 行

`読んだコードの要点` の見出しの下に、1 行 1 件で `<リポジトリ相対パス>:<開始行>-<終了行> — <そこから分かったこと>` を書く。上限は 20 行で、超えるときは次の工程で読む必要が高いものを残す。

- 選ばなかった案: 上限なし。return が長くなると本体・後任のコンテキストを食い、読み直しを減らす目的と逆になる
- 選ばなかった案: ファイル名だけ。後任がファイル全体を読み直す動きが残る（今の読み直しの大半はファイル単位で起きている）
- 20 は issue の当たり値。多すぎた・少なすぎたは事後計測（決定 6）の値と一緒に見直す

### 決定 2: 書式の正本は worker.md、decision-criteria.md は欄の名前と参照だけ

欄を書くのは W で、後任への注意（編集前に自分で読んで確かめる）も W の役割固有の動作なので、書式と注意は worker.md の「コンテキスト上限と手渡し」の節に置く。`decision-criteria.md` の成果一覧（`工程完了:` の説明と、通知を受けたときの振る舞いの 2 箇所）には欄の名前を足し、W の書式は worker.md を指す。

- 理由: 既存要件「コンテキスト上限の規則の本文は decision-criteria.md 1 箇所に置く」が decision-criteria.md に置くよう求めるのは計測の 2 経路・閾値・振る舞い・1 行目の書き分けで、W の return の書式はその対象ではない。書式を両方に書くと、上限行数を変えたときに片方が取り残される

### 決定 3: `tasks.md` の各タスクに `触る範囲:` を書く。行番号は着手時点の値

(1) で `tasks.md` を書くとき、各タスクの末尾に `触る範囲: <パス>:<開始行>-<終了行>`（複数なら読点で並べる。新しく作るファイルは `<パス>（新規）`）を書く。行番号は仕様づくりの時点の値で、前のタスクの編集でずれうる。節の見出しや関数名が分かるときは添える。

- 選ばなかった案: 見出し・関数名だけ。Markdown の手順書が大半のこのリポジトリでは見出しが長く、同じ見出しが複数のファイルにある
- ずれは許容する。案内であって、実装の担い手は編集前に該当範囲を読む（決定 4 と同じ扱い）

### 決定 4: 仕様化しない経路では、(1) の return に同じ内容を書く

コード直行では `tasks.md` が無いので、(1) の「仕様化しない」return に、作業項目ごとの `触る範囲:` を書く。本体はこれを (3a) の指示に写すか、同じ W をそのまま再開する。

### 決定 5: 途中計測 hook の通知文とトリップワイヤーのテンプレートは変えない

`scripts/context-tripwire.sh` の通知文は成果の項目を列挙しているが、ここに欄を足すと `dev-workflow-execution-strategy` の MUST（通知文が含む内容）とスクリプトの両方に手が入る。W は return を書く前に `decision-criteria.md` の節を読む指示が worker.md にあり（既存）、その節と worker.md の手渡しの節に欄があれば足りる。worker.md の昇格トリップワイヤーの節（W が発火時に列挙する成果）には欄を足す。`templates/escalation-tripwires.md` は本体向けのラダーで、W の return の書式を持たないので変えない。

- 受け入れること: 途中計測の通知を受けた W が通知文だけを見て return を書くと、欄を落とすことがある。落としても後任が読み直すだけで、今と同じ状態に戻るだけ

### 決定 6: 受け入れ条件の PR 内と事後の分担

| 受け入れ条件 | この PR の中で | 事後 |
|---|---|---|
| 1. worker.md と decision-criteria.md に欄がある（bats） | 満たす | — |
| 2. 交代が起きた develop 1 本の `reread_pct` を PR 本文に記録 | 満たす（下の手順） | — |
| 3. マージ後 5 本で `reread_pct` 25% 以下、#511 にコメント | 満たせない（マージ後の develop が要る） | 追跡用の子 issue を作り、計測してエピック #511 にコメントする |
| 4. `./scripts/test.sh` と `./scripts/lint.sh` が exit 0 | 満たす | — |

**受け入れ条件 2 の測り方**: この issue #555 の develop 自体を対象にする。(1) の W は本体の指示で return に「読んだコードの要点」を既に載せているので、本体が (3a) を手渡し（新しい W に (1) の return を渡す）で始めれば「交代が起きた develop」になる。PR を作る前に、#555 の W のトランスクリプトだけを入れた一時ディレクトリ（`<一時dir>/<project>/<session>/subagents/` にシンボリックリンクを置く）を `--projects` に渡して `subagent-context-audit.sh --by-role --refresh --cache <一時ファイル>` を実行し、`W.reread_pct` と W の件数を PR 本文に書く。ツールは直さない（issue 単位の絞り込みは `--projects` に渡す母集団で行う）。

- 注意として PR 本文に書くこと: この issue は編集対象が worker.md と decision-criteria.md そのもので、後任は編集前に必ず読むので、ファイル名一致の `reread_pct` は高く出やすい。値は記録するが合否には使わない
- 本体が (3a) を手渡しで始めなかった場合（同じ W を再開した場合）は交代が起きないので、PR 本文に「交代なし、受け入れ条件 2 は事後計測の 1 本目で代える」と書く。どちらを選ぶかは本体の判断

**受け入れ条件 3 の扱い**: (3b) で PR を作るとき、「マージ後に develop で通した PR 5 本の `W.reread_pct` を測り、エピック #511 にコメントする」子 issue を #511 の下に作り、PR 本文の受け入れ条件 3 の行にその issue の URL を書く（チェックは付けない）。PR は `Closes #555` のままにする（#555 の残りは子 issue に移すので、#555 を開けたまま待たせない）。測り方は受け入れ条件 2 と同じ（5 本の issue 番号の W だけを一時ディレクトリに入れる）。25% は比べるための目安として記録し、上回ったときは決定 1 の上限行数や書き方を見直す issue を立てる入力にする。

## Risks / Trade-offs

- [前任の要点が間違っていて、後任が読むべき場所を読み飛ばす] → 要点は案内と明記し、編集前に該当範囲を自分で読んで確かめる指示を worker.md に置く
- [行番号が前の編集でずれ、案内が外れる] → 範囲の読み直しは安く、外れても今と同じ探し方に戻るだけ。見出し・関数名を添えられるときは添える
- [欄が増えて return が長くなる] → 上限 20 行。1 行は 1 件の場所と一言に限る
- [#556 と同じ worker.md を触る] → 先にマージされた側に合わせ、後の側がリベースで直す。この change は節単位の追記なので、段ごとに分けたファイルへの移し替えは機械的にできる
