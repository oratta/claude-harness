## Context

`subagent-context-audit.sh` は母集団の統計（`count` / `first_median` / `last_median` / `over_cap_pct` / `sources.isolated` / `sources.non_isolated`）を出すが、内訳は隔離の有無だけである。2026-09-27 に flatmate / claude-harness の直近 10 日を手作業で集計したところ、担当（W / R1 / G / G のレビュアー / decider）ごとの中央値・上限超過率は次のとおり大きく違っていた（基準値としてエピック [#511](https://github.com/oratta/claude-harness/issues/511) に記録する。恒久の仕様値ではない）。

| 担当 | 傾向 |
|---|---|
| G（マージ前の検査） | 上限 150K を 52%〜53% の頻度で超えていた |
| decider（決める役） | 0%〜30% |

隔離の有無（`isolation: "worktree"`）は役割と相関するが役割そのものではなく、隔離ありの中に W も decider も混在するため、既存の `sources` 内訳ではこの担当差が見えない。この change は `--by-role` フラグで担当別の内訳を追加する。

## Goals / Non-Goals

**Goals:**
- `--by-role` を付けたときだけ、担当ごとの `count` / `first_median` / `docs_median` / `last_median` / `over_cap_pct`（`W` のみ `reread_pct` も）を出す
- 既存の呼び出し（`--by-role` なし）の出力・走査コストを変えない
- 実データでの基準値をエピック #511 に記録する

**Non-Goals:**
- 閾値による強制停止・警告（既存同様、観測専用のまま）
- `subagent-context.sh`（1 体の実測、再開前の上限判定）側の変更
- `SessionStart` hook（`session-tripwires.sh`）への出力追加
- 母集団の走査経路・隔離分類・キャッシュ TTL・fail-open 方針など既存要件の変更

## Decisions

### D1: 担当分類の優先順位 — `agentType` を `description` より優先する

隣の `agent-<id>.meta.json` から次の順で分類する。

1. `agentType` が `dev-workflow:decider` なら常に `decider`（`description` の先頭が `R1:` のように別役割を示していても上書きする）
2. それ以外は `description` の先頭コロン区切りトークン（例: `W: #552 ...` の `W`）が `W` / `R1` / `G` / `Reviewer` のいずれかに完全一致すればそれを使う
3. どちらにも当たらない（`description` が無い・コロンが無い・未知のトークン・`meta.json` が無い/壊れている）場合は `unknown` に寄せる

**なぜ `agentType` を先に見るか**: `dev-workflow:decider` は「決める役」という起動種別そのものであり、`description` は呼び出し側が自由に書く文字列なので、R1 の判断を decider に委譲したケースなど `description` が別役割の体裁を取ることがある。起動種別が確定情報である以上、それを自由記述より優先する。

**分類できない件を欠番にしない**: `unknown` も `by_role` の合計に含める（母集団の一部として残し、既存の「分類できないことを理由に `count` から落とさない」方針（`サブエージェントのコンテキスト量の母集団集計` Requirement）と一貫させる）。

**`Reviewer` の接頭辞は規約未確定**: develop の紐付け規約（`plugins/dev-workflow/skills/develop/SKILL.md:153`）は `W:` と `G:` の例しか示しておらず、「G のレビュアー」の `description` が `Reviewer:` で始まる保証は無い。実データでは `Reviewer` がほぼ 0 件で「G のレビュアー」が `unknown` に落ちる可能性がある。この change では分類ロジック側に手を入れず、実データ集計（tasks.md のエピック #511 コメント）で偏りが大きければ、紐付け規約側に接頭辞を追加する別 issue を起こす前提を spec に明記する。

### D2: `docs_median`（指示書の読み込み量の中央値）の計測単位

「1 ホップ」を、`Read`（`file_path` が harness の指示書格納パス `plugins/cache/oratta-claude-harness/.*\.md$` に一致するもの）または `Skill` の `tool_use` を含む assistant ターンから、対応する `tool_result` を経て次の `usage` 付き assistant レコードまでの区間と定義し、その区間の `usage` の差分（次 − 現。負なら 0 に丸める）を「指示書 1 回分の読み込みコスト」とする。

集約は次の 2 段階で行う（個体内で合計してから担当内で中央値を取る。1 ホップずつ担当内で中央値を取るのではない）。

1. 個体（1 トランスクリプト）ごとに、そのトランスクリプト内の全ホップの計上値を合計し、その個体の「指示書読み込み量」とする。対象ホップが 1 つも無い個体も合計 0 として扱い、母数から除外しない
2. 担当内の全個体の①の値を中央値に集約したものが `docs_median` となる（既存の中央値の丸め方＝偶数件は中央 2 値の平均を四捨五入、と同一）

1 ホップに複数の `tool_use` が混在する場合（例: `Read` と他の道具呼び出しが同じターンに並ぶ）は、ホップ全体を docs 側に丸めて計上する近似を取る。ホップ単位で厳密に「指示書だけが伸ばした分」を分離するには、後続の応答が指示書のどの断片を実際に使ったかまで見る必要があり、費用対効果に合わないため、粗い近似で足りるとする。

`--by-role` を付けたときだけこの走査を行う（全文を前方から順に走査する必要があるため、既定呼び出しの部分読みより重い。手動監査専用でセッション起動経路には載らないため許容する）。

### D3: `reread_pct`（作業担当 `W` の読み直し割合）のグループ化と母数

`description` に含まれる `#N`（記録先の issue/PR 番号）で、同じ記録先を担当した `W` を時系列でグループ化する（`timestamp` で開始順を判定）。`description` に `#N` が複数出現する場合は、最も左（最初）に出現するものを記録先番号として使う（例: `W: gate for PR #400 (#288)` は `#400` を使う。develop の紐付け規約は記録先番号を先頭側に書く運用のため、複数出現時は最初の 1 個が記録先を指している可能性が高い）。

各グループの 2 番目以降の `W` について、「先行する全 `W`（自分より前に開始したグループ内の全員）が読んだ `Read` の `file_path` の和集合」に対する「自分が読み直した割合」を求め、担当 `W` 内の中央値として出す。単位は既存の `over_cap_pct` と同様に 0〜100 のパーセントとする（0〜1 の比率にしない）。

- ファイル一致は**ベースネーム一致**（`file_path` の末尾のファイル名のみ）とし、フルパス一致では判定しない（内容が同一かも見ない）。worktree ごとに絶対パスの先頭ディレクトリが変わるため、フルパス一致では同じ指示書を読み直していても別ファイル扱いになってしまう。手渡しでは同じ指示書を読み直すこと自体が「前任の履歴を読めないことのコスト」の指標であり、内容差分の追跡は目的に対して過剰
- 各グループの最初の `W`（先行がいない個体）は、割合の分母が定義できないためこの中央値の母数から除く
- `#N` が取れない `W`（`description` に記録先番号が無い）は `reread_pct` の対象から除く。グルーピングできない個体を無理に単独グループにすると、母数 0 の割り算が起きるか、常に対象外（先行なし）になり、値の意味が薄まるため

`reread_pct` は `W` にだけ付く（R1 / G / decider は手渡しで再開される設計ではないため、この指標が意味を持たない）。対象が 1 件も無い場合（全個体がグループ最初か記録先番号なし）は `null` とする。

### D4: 出力形状と後方互換

`--by-role` を付けない既定の呼び出しは、この change の前後で完全に同じ出力になる（既存キーの形も走査コストも変えない）。`--by-role` を付けたときだけ、トップレベルに `by_role` キーを追加する。`by_role` は 6 個の担当名（`W` / `R1` / `G` / `Reviewer` / `decider` / `unknown`）を常にキーとして持つオブジェクトで、該当件数が 0 の担当でもキー自体は省略しない（呼び出し側が「どの担当が母集団に含まれるか」を事前に知らなくても全担当を同じ形で参照できるようにするため）。各値は `count` / `first_median` / `docs_median` / `last_median` / `over_cap_pct` を持ち、`W` のみ追加で `reread_pct` を持つ。`count` が 0 の担当は `first_median` / `docs_median` / `last_median` を `null`、`over_cap_pct` を `0.0` とする（`sources.isolated` / `sources.non_isolated` が 0 件のときの既存の扱いと揃える）。

`--by-role` 指定時に `python3` が使えず既存の fail-open（`count: 0` の固定文字列）に落ちる場合、`by_role` キーは出力しない（分類・集計そのものが `python3` の実行を前提とするため、fail-open 応答の形は既存と変えない）。`python3` は使えるがトランスクリプトが 0 件の場合は fail-open ではなく正常系の 0 件応答なので、`by_role` の 6 キーはすべて上記の `count: 0` の形（`null` / `0.0`）で出す。

### D5: キャッシュファイルの衝突回避

`--by-role` は既定呼び出しと集計内容が異なるため、同じキャッシュファイルを共有すると片方の結果がもう片方の TTL 内で誤って返る。`--cache` を明示しない場合、`--by-role` 指定時は既定パス（`${SUBAGENT_CONTEXT_AUDIT_CACHE:-~/.claude/.subagent-context-audit}`）に `.by-role` サフィックスを足したパスを使う。`--cache` を明示した場合はそのパスをそのまま使う（サフィックスを足さない。呼び出し側が衝突を自分で管理する前提）。

## Risks / Trade-offs

- **フルスキャンのコスト**: `--by-role` は担当分類・`docs_median`・`reread_pct` のためにトランスクリプトの全文を前方から順に走査する。既定呼び出し（先頭/末尾の部分読み）より重いが、手動監査専用でセッション起動経路（`session-tripwires.sh`）には載らないため許容する。
- **`docs_median` の近似精度**: 1 ホップに複数 `tool_use` が混在する場合の丸め計上は、指示書以外の道具呼び出しのコストを docs 側に混ぜる方向の誤差を持つ。傾向監視（増えていないかの確認）が目的であり、単一ホップの厳密な内訳までは求めない。
- **`reread_pct` のベースネーム一致**: 内容差分を見ないため、同名で内容が更新された指示書を「読み直した」とみなす（実際には最新版を初めて読んだだけの場合を含む）。手渡しコストの粗い指標として割り切る。
- **`unknown` の混入**: `meta.json` 欠損・壊れたトランスクリプトは `unknown` に寄せるため、`unknown` の中央値は担当別の傾向として意味を持たない（合計件数の整合性を保つためだけに存在する）。
