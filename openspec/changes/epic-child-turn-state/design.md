# Design

## Context

動機と分割の根拠は proposal.md を参照。現状の `epic-state.sh` は schema=1 の子ごとの記録を持ち、未知項目を保持し、`mkdir <record>.lock` と同一ディレクトリの一時ファイルからの `mv` で更新する。`session` は端末のハンドルであり Claude のセッションIDではない。`stop_uuid` / `stop_at` は親が受けた止まりの情報なので、子が上書きできない。

UserPromptSubmit は `prompt`・`session_id`・`cwd`・`transcript_path`、Stop は同じセッション情報と `last_assistant_message`・`stop_hook_active` を使える。既存の Stop は `agent_id` のある入力を除外している。新フックもこの区別に従う。会話ログの検索や送信の API を新設せず、イベントが指定したログ1本だけを使う。

## Goals / Non-Goals

**Goals:** 入力を受けた時点から前ターンの状態を無効にし、終了時にその入力に対応する状態だけを保存する。後続の親側が入力の送り手と状態を同じ世代として読める契約を残す。

**Non-Goals:** 親の wait / resolve / reply・再起動判定・通知期限・Orca の印・サブエージェント方式の変更。状態文の意味が実作業と一致するかの自動判定や、親経由の返事の承認権限の判定も行わない。

## Decisions

### 1. 子側の情報を schema=1 の任意拡張に閉じる

`turn_input` と `turn_state` を既存の記録に追加する。旧記録で両方が無いことは正常。既存の `ES_VALID` に新項目の検証を加えず、子側用の読み取りで拡張の型を検証する。壊れた拡張は子側の処理失敗となるが、旧親が本体の記録まで読めなくなる変更にはしない。

`turn_input` は次の形で、通常入力を受けるたび全体を置き換える。

| 項目 | 型・値 |
|---|---|
| `generation` | 1以上の整数。既存値に1を足す。初回は1。セッションが変わっても記録の存続中は巻き戻さない |
| `session_id` | 空でない文字列。hook payload の Claude セッションID |
| `sender` | `owner` / `parent` / `startup` の文字列 |
| `received_at` | フックが受け付けた UTC `YYYY-MM-DDTHH:MM:SSZ`。入力日時の正本。時計の比較で世代を決めない |
| `transcript_path` | payload が示す会話ログの絶対パス。端末ハンドルから組み立てない |
| `transcript_offset` | 入力受付時のログのバイト数（0以上の整数。新規ログがまだ無ければ0）。古い最終発言を識別するための境界 |

`turn_state` は未終了では JSON の `null`、通常の Stop 成功後は次のオブジェクトにする。

| 項目 | 型・値 |
|---|---|
| `generation` / `session_id` | 対応する `turn_input` と同じ値 |
| `value` | `主の返事待ち` / `作業報告` / `完了` |
| `summary` | ` — ` の後ろの中身。前後の空白を除いた空でない一行 |
| `recorded_at` | Stop が保存した UTC `YYYY-MM-DDTHH:MM:SSZ` |

有効条件は、両オブジェクトが型どおりで、`generation` と `session_id` がそれぞれ一致すること。片方の欠落・`null`・型不正・不一致は有効な終了状態ではない。この条件は #1744 向けの読み取り契約であり、この change で親の判定に組み込まない。

`summary` は子の一行の申告の写しであり、既存の停止コメントや `止まった理由:` の本文の正本を置き換えない。既存の `status` / `stop` / `stop_uuid` / `stop_at` / `told_uuid` / `keepalive` / `session` は新フックが書かない。共通の更新で `updated_at` だけは変わる。独立した状態ファイルや schema=2 への移行は、旧親との互換性と5ファイルの境界を損なうため採用しない。

### 2. 送り手は到着した入力の形から分類する

優先順は次のとおり。

1. 共有正本から組み立てた声かけ固定文との完全一致は予約文。通常入力に数えず、世代・時刻・旧状態を保つ。
2. その `session_id` で初めて受けた入力で、既存 launcher の `/develop #<子> （エピック #<親> の子。…）` の起動形（別repo表記と再起動の形を含む）に該当し、記録の子・親と一致するときは `startup`。再起動時に返事が埋め込まれていても `startup` とする。
3. 入力の先頭が `親エピック #` または `主の返事（親エピック #` なら `parent`。別repoの括弧付き表記も同じ。
4. その他は `owner`。新しいセッションの初回でも、直接の通常入力なら `owner`。

ここでの送り手は輸送経路である。主の返事を親が中継したものは `parent`、起動指示に含まれたものは `startup`。許容・委任の証明の取り扱いは既存手順のまま。本文の途中の引用やモデルの自己申告から送り手を決めない。

### 3. 入力受付と Stop は同じ記録を排他して世代を照合する

入口は新規の `epic-child-state.sh` 1本で、payload の `hook_event_name` により UserPromptSubmit / Stop を分ける。`hooks.json` に両方を command hook として登録し、ロックの既定10秒を待てる timeout（30秒）を設定する。SessionStart では通常入力を作らず、compact / resume 自体では世代も送り手も更新しない。

`cwd` の git 最上位パスと一致する `worktree` を既存関数で探す。読める記録がちょうど1件で `launcher` が `orca` / `tmux`、かつ `agent_id` の無い主セッションだけが対象。環境変数 `EPIC_DISPATCH_PARENT_EPIC` だけでは対象にしない。記録が無い一般セッションは無出力 exit 0。複数一致は勝手に選ばず処理失敗とする。

通常の UserPromptSubmit はロック内で再読し、世代を増やした `turn_input` と `turn_state: null` を1回の置き換えで保存する。これが成功してから入力を処理させる。失敗は exit 2 と stderr の理由で入力受付を拒否する。無効化に失敗したのに新しい入力だけが処理される fail-open は選ばない。

Stop は現在の `turn_input` を写し、payload のセッションとログパスの一致を確認する。指定ログにある主セッションの最後のテキスト発言が `last_assistant_message` に対応し、その発言の行の開始位置が `transcript_offset` 以降であることを確認する。古い発言が同じ文でも、受付前の位置なら採用しない。ログが示す後続の通常入力があるときも古い発言を採用しない。ログ上の `isSidechain` の行とツール結果を最終発言に使わない。入力がログに記録される前後どちらで UserPromptSubmit が呼ばれても、終了発言が境界より後にあることを使うので区別不要。

検査後に再び同じ記録のロックを取り、`session_id`・`generation`・ログの境界が写しと一致するときだけ `turn_state` 全体を書き込む。照合失敗の遅い Stop は無出力 exit 0 で捨て、新世代を上書きしない。入力の追記と Stop が前後するケースは、ログの境界とロック内の再照合の両方で試験する。現在世代の入力情報やログを確認できないときは正常終了扱いにせず、Stop を block して理由を出す。

時刻だけの照合は同秒の連続入力に弱く、`stop_hook_active` だけの通過は未修正の行を受け入れるので使わない。Stop の再試行は同じ世代を保ち、修正済みの発言だけで保存する。停止拒否のたびに入力世代を増やさない。

### 4. 状態行と予約文を別の入力契約として扱う

通常の Stop では `last_assistant_message` の末尾の空白行だけを除き、最終行に `状態: <値> — <中身>` があることを求める。行頭の装飾・引用・リスト・コードフェンス内の例は認めない。値は3つとの完全一致、区切りは半角空白を含む ` — `、中身は空白だけでは不可。内容の意味は判定しない。欠落・不正なら exit 0 の `{"decision":"block","reason":"…"}` で有効な型と修正対象を返す。`stop_hook_active=true` の再停止でも同じ検査を行う。

声かけ予約文の構築は `child-log-read.py --keepalive-text` を再利用する。UserPromptSubmit では保存を行わず、Stop も payload が指定したログの現在の入力が予約文なら検査・保存とも行わない。正常な一行応答だけでなく、予約文への型違いの応答でもこのフックは旧状態を消さない（既存の逸脱の扱いを拡大しない）。`child-cache-keepalive.json` / `epic-keepalive.md` は編集しない。状態行を声かけの応答に付けさせる案は、現行の親がその応答を除外できなくなるため採用しない。

### 5. 子の文書には状態行を最後に追加する

`epic-child-stop.md` の読む場面を別セッションの子の通常ターン全体に広げる。主の答え・承認・操作が必要なら `主の返事待ち`、待たせる問いのない区切りや依存待ちは `作業報告`、子の用が済めば `完了`。背景タスクだけを待つために終了してよいという意味にはしない。

定型の止まりの `止まった理由:` と PR トークン上限の見込み3行は既存の形で末尾部分に残し、そのあとに短い状態行を置く。依存待ちは `止まった理由: 依存待ち: …` の次に `状態: 作業報告 — <依存先と再開条件の短い要約>` とする。移行失敗で主に操作を頼むなら `主の返事待ち`。既存の7項目の停止コメントや依存登録の手順は保つ。末尾という既存要件は末尾部分を指し、状態行はその部分の最後の1行を占める。親は既存どおり行頭の `止まった理由:` を読むため、この段で親側の変更は要らない。

## Risks / Trade-offs

- 会話ログの形式に依存する → payload のログ1本と最終発言だけに限り、不明なら保存を拒否する。バイト境界を含む fixture で検証する。
- 保存先が書けない・ロックが残ると対象の子が進めない → 理由と記録パスを示す。自動でロックを消さず、既存の排他の復旧手順を使う。
- 更新前から走っている子では入力フック未実行の Stop がある → 入力記録を捏造せず block し、通常入力を送り直すよう知らせる。一般セッションには適用しない。
- 同じworktreeの別セッションが交互に入力する → 最後に受けた通常入力だけを正にする。セッションと世代が違う Stop は保存しない。
- 子側だけの導入中は親が従来のログ推定を続ける → この change の合格を主との対話保護の完成とは扱わない。保護の振る舞いは #1744 の受け入れ条件で確認する。

## Migration Plan

この工程では仕様のみを commit する。実装・R1 承認後の導入は子側を先に行う。旧 schema=1 記録の手動移行は不要で、次の通常入力で拡張が作られる。旧親は未知項目として保持する。ロールバックは新フックの登録と実装を戻せばよく、任意拡張が残っても旧親の検証を変えない。#1744 はこの spec の有効条件を読み取りの契約として使用し、#1745 はその後に扱う。
