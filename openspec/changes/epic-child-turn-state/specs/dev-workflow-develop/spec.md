## MODIFIED Requirements

### Requirement: 子は途中で見つかった依存を登録し再開手順を残して終了する

別セッション方式の子（`route` が `nested`）が別 issue・PR の完了を待つ必要を見つけたときは、自分の issue に `dependencies/blocked_by` を張り、登録を確認してから終了しなければならない（MUST）。子 issue に `子の停止: 依存待ち` で始まるコメントを残し、依存先の URL、待つ理由、再開条件、ブランチ・commit・PR・残作業、再開時の具体的な操作を書く（MUST）。最後の発言の末尾部分には `止まった理由: 依存待ち: <依存先 URL>` を置き、新しいターン状態フックを使う子は、その直後の非空行を `状態: 作業報告 — <依存先と再開条件の短い要約>` として発言を終えなければならない（MUST）。旧形式の子は従来どおり依存待ちマーカーを最後の非空行とする。主の返事待ちとせず、待機用の背景タスクや質問ツールでセッションを占有し続けてはならない（MUST NOT）。

#### Scenario: 作業途中で main の CI 修正待ちが判明する
- **WHEN** 子 #1693 が修正 issue #1713 の完了後に main を取り込んでゲートを取り直す必要を見つける
- **THEN** #1693 の blocked_by に #1713 を登録したことを確認し、子 issue のコメントに再開手順と途中経過を残してターンを終え、依存先が閉じるまで待機用の子ターンを起こさない

#### Scenario: 状態行と依存待ちマーカーを両立する
- **WHEN** ターン状態フックを使う子が依存の登録・確認・再開記録の投稿に成功して終了する
- **THEN** 最後の非空行は `状態: 作業報告 — <依存先と再開条件の短い要約>`、その直前の非空行は `止まった理由: 依存待ち: <依存先 URL>` である。移行失敗で主の操作が必要なら成功のマーカーで終えず、失敗の理由と `主の返事待ち` の状態行を残す

#### Scenario: PR の完了を待つ
- **WHEN** 子が別 PR の完了を待つ必要を見つける
- **THEN** 完了を表す対応 issue を依存先として特定し、PR と issue の URL および再開条件を記録する。自分の PR のマージ待ちは既存の定型の止まりを使う

#### Scenario: 依存先の登録または記録が失敗する
- **WHEN** 対応 issue を特定できない、依存を登録・確認できない、または再開記録を投稿できない
- **THEN** 子は依存待ちへの移行が完了したと報告せず、失敗した操作・理由・未保存の途中経過を親に返す。範囲外の修正や新しい子 issue が必要なら自分で直さず報告する

### Requirement: wait は依存待ちの終了を自動判断で再開に戻さず親へ返す

`wait --watch-stopped --resolve` が、子の今回の最後の発言の末尾の空白行・CR を除き、最後の非空行が `止まった理由: 依存待ち: ` で始まる旧形式、または最終状態行の直前の非空行が同じマーカーで始まる新形式の止まりを検知したときは、停止状態を維持して `stopped <N>` に含めなければならない（MUST）。この子に自動判断の返事を送ったり、「問いではない」として `resumed` に戻したりしてはならない（MUST NOT）。新形式の状態行は `状態: <主の返事待ち|作業報告|完了> — <空白だけでない中身>` の構文を満たし、行頭の装飾・引用・リストやコードフェンス内の例ではないものとする（MUST）。マーカー自体の先頭空白の許容は既存どおりとする。マーカーの後ろに不正な状態行・複数の状態行・別の文章があれば、本文検索で依存待ちに格上げしてはならない（MUST NOT）。これは依存待ちに限って既存の自動解決の規定に優先する。マーカーは親の確認に回す合図であり、依存が登録済み・解消済みであることの証拠に使ってはならない（MUST NOT）。

#### Scenario: 終了記録の子を通常の親の wait が受ける
- **WHEN** 起動済みの子の `stop` が空または `resumed` で、依存待ちの記録と末尾マーカーを持つ会話ログがあり、既存のログによる停止検知条件を満たして `wait --resolve` が読む
- **THEN** `stop` は `stopped-seen`、`stop_uuid` は今回の発言の uuid となり、stdout に `stopped <N>` が出て exit 0 となる。自動判断を呼ばず、子への送信と `resumed` への変更を行わない

#### Scenario: 状態行を追加した依存待ちも自動判断へ流さない
- **WHEN** 依存待ちマーカーの直後の非空行が有効な状態行で、末尾に空白行や CR がある発言を `wait --watch-stopped --resolve` が読む
- **THEN** 旧形式と同じく自動判断を呼ばず `stopped <N>` と exit 0 を返し、停止記録を維持し、子への送信と `resumed` への変更を行わない。状態記録の有無や状態値で停止を決めない

#### Scenario: 本文中のマーカーだけでは依存待ちにしない
- **WHEN** マーカーの後ろに別の文章、不正な状態行、または複数の状態行があり、上の末尾契約を満たさない
- **THEN** 依存待ちマーカーの特例にはせず、既存の自動判断経路に渡す

#### Scenario: 依存待ち以外の問いでない報告
- **WHEN** 末尾マーカーが無い報告を自動判断が「問いではない」と判定する
- **THEN** 既存どおり `resumed` に戻し、子への返事を送らず待ちを続ける

この要件と要件「親は依存待ちの子を動いている子から外し既存操作で再起動する」に共通する守備範囲: 入力元は、wait が既存の停止検知で読む子の今回の最後の発言とローカルの停止記録、親が読む GitHub の子 issue の依存待ちコメントと現在の `blocked_by`・依存先の状態、および既存の `wait`・`pending-owner`・起動操作の出力と送信結果である。拾いたい誤りは、末尾マーカーのある停止を自動判断で `resumed` に戻すこと、マーカーだけで依存の登録・解消を認定すること、依存待ちを動いている子や主の返事待ちに混ぜること、依存が残る間に子を起こすこと、依存待ちだけが残ったときに `clear` して停止記録と見張りを失うこと、起動失敗や `skipped` を再起動成功とすることである。次は通してよく、この2要件では止めない: 旧形式・新形式のどちらの末尾契約にも合わない問いでない報告が既存どおり `resumed` に戻ること／マーカーはあるが依存登録や記録に不足がある停止を、成功扱いせず親の確認へ返すこと／依存待ちコメントの項目の並びや説明の表現が違っても、親が依存先・再開条件・途中経過・再開操作を読み取れること／エピック外の依存先を子として起動せず閉じる通知だけ見張ること。マーカーを使わない言い換えの網羅的な検出や、親の実行時の読み違いまで保証せず、入力の分類の穴を塞ぎ切ることをこの2要件の完了条件にしない。今回の互換変更では、状態記録だけによる停止判断や親の送信抑止を追加しない。
