## MODIFIED Requirements

### Requirement: 仕様宣言を通過の必須点に加える
pr-review-gate スキルは、手順 3 に「仕様宣言」を positive affirmation として追加しなければならない（MUST）。仕様宣言は `## 仕様宣言` 見出しと 1 行目 `対象 HEAD: <40 桁フル SHA>` を持つ PR コメントで、本文は次の 3 形のどれかちょうどとする（MUST）: ①「仕様を更新した（change 名・archive 済み・`仕様レビュー: APPROVE` の所在）」 ②「仕様を更新した（change 名・archive 済み・文言合わせの通し方で仕様レビューを省いたことと、仕様化判断のコメントの所在）」 ③「仕様変更なし＋理由」。②の形の行は `仕様: 更新した — change <change-name>（archive 済み）／仕様レビュー: 省いた（文言合わせ。<仕様化判断のコメントの URL>）` とする（MUST）。②を使ってよいのは、記録先の最新の仕様化判断のコメントに `^通し方: 文言合わせ$` に完全一致する行がある PR だけである（MUST。通し方の定義は `dev-workflow-spec-review` の「仕様の文言合わせは仕様の差分 1 ファイルだけで通し仕様レビューを省く」Requirement）。「書かない」を選んではならず（MUST NOT）、スキル冒頭の必須点の列挙に仕様宣言を含めなければならない（MUST）。

#### Scenario: 手順 3 に仕様宣言の 3 形がある
- **WHEN** `declarations.md` の手順 3-b を読む
- **THEN** `## 仕様宣言` 見出し・`対象 HEAD:` 1 行目・「更新した」形（`仕様レビュー: APPROVE` の所在つき）・「更新した」形（`仕様レビュー: 省いた（文言合わせ。` で始まる所在つき）・「変更なし＋理由」形の 3 つのテンプレートが書かれている

#### Scenario: 冒頭の必須点に仕様宣言が入っている
- **WHEN** SKILL.md 冒頭の「通過の必須」の列挙を読む
- **THEN** リスク宣言・動作確認の証拠・`agent-review:passed` に加えて仕様宣言が挙がっている

### Requirement: 合格処理は仕様宣言の実在と issue 記録との整合を実測する
手順 5 は、現在の HEAD SHA を含むコメントの 1 行目一覧に「リスク宣言」「動作確認」「仕様宣言」の 3 見出しがすべて現れることを確認してからでなければ `agent-review:passed` を付けてはならない（MUST NOT）。さらに、PR 本文で最初に現れる `Closes` / `Fixes` / `Refs #N` から元 issue を解決し、その最新の `^仕様化判断: (する|しない)$` コメントと照合しなければならない（MUST）: 「する」で、そのコメントに `^通し方: 文言合わせ$` に完全一致する行が無いなら、PR の変更ファイルに `openspec/` が含まれる**または**仕様宣言の「更新した」形が指す change が base ブランチで archive 済み（`openspec/changes/archive/*-<name>/` の実在を実測。スタック PR で仕様が先行 PR に入っている場合）であり、かつ issue に `^仕様レビュー: APPROVE$` で始まるコメントがあること（MUST）。「しない」なら仕様宣言が「変更なし＋理由」形であり、PR に `openspec/` 差分が**無い**こと（差分があれば「しない」と矛盾するので合格しない。判断を「する」に取り直すか差分を外す）（MUST）。記録が無い場合は合格処理をせず、判断を記録してからやり直す（MUST）。PR コメントへの記録は PR 本文に issue 参照が無い場合に限り（MUST）、issue 参照があれば issue 側が正で、issue 側に記録が無ければ issue に投稿する（MUST）。

「する」で、最新の仕様化判断のコメントに `^通し方: 文言合わせ$` に完全一致する行があるなら、`仕様レビュー:` のコメントは照合せず（MUST。この通し方では R1 を起こさないので、コメントが無いことを不合格の理由にしてはならない）、代わりに次の 4 つをすべて実測しなければならない（MUST）: ①仕様宣言が `仕様レビュー: 省いた（文言合わせ。` を含む「更新した」形である ②PR の HEAD で `openspec/changes/archive/*-<change-name>/specs/*/spec.md` に当たるファイルがちょうど 1 つある（archive 済みで、差分が 1 ファイル） ③そのファイルに `## ADDED Requirements` / `## REMOVED Requirements` / `## RENAMED Requirements` の見出しが無い ④そのファイルの `### Requirement: <要件名>` の要件名がすべて、同じ仕様化判断のコメントの `直す文:` で始まるどれかの行に `「<要件名>」` の形で現れる。1 つでも満たさなければ合格処理をしてはならない（MUST NOT）。そのときの直し方は、差分か仕様化判断のコメントを直して①〜④を満たすか、`通し方:` の行の無い仕様化判断を投稿し直して artifact 一式と仕様レビューからやり直すかのどちらかとする（MUST）。手順 5 の整合表は、この場合を「する」の行と別の行として持たなければならない（MUST）。

文言合わせの通し方の照合の守備範囲は次のとおりとする。①入力の出どころは、記録先の最新の仕様化判断のコメント（W が書く）と、PR の HEAD にある archive 済みの change の差分ファイルである。W は協力的だが、対象を広く取りすぎることがある前提で扱う。②拾いたい誤りは、通し方の行があるのに差分が新しい要件を足している・要件を消している・要件の名前を変えていること、差分が 2 つ以上の capability に広がっていること、仕様化判断のコメントに挙げていない要件を書き換えていること、archive が済んでいないこと、通し方の行が無い PR が仕様レビューを省いた形の宣言で通ることである。③次はこの照合を通ることを許す: 挙げた要件の中で、文を落とす・直す範囲より広く書き換える・Scenario を足す差分（見るのは実装後レビューのレビュアーである）。受け入れ条件に直す文が書けていないのに W が通し方の行を書いた PR（受け入れ条件と `直す文:` の行の突き合わせは機械では行わない）。同じ記録先を 2 つ以上の change が共有していて、最新の仕様化判断のコメントが別の change のものである場合（判断の記録は記録先ごとに最新 1 件という既存の契約による）。④ここに挙げた以外の通り方は見つけるたびに検査を足し、穴を塞ぎ切ることを完了条件にしない。

#### Scenario: 3 見出しの実測が規定されている
- **WHEN** SKILL.md の手順 5 を読む
- **THEN** SHA 照合の出力に仕様宣言の見出しも現れることを要求し、欠けていれば合格処理をしない旨が書かれている

#### Scenario: 記録との整合表がある
- **WHEN** `stages/pass.md` の手順 5 を読む
- **THEN** 「する → openspec 差分（または archive 済み change の実測）と `仕様レビュー: APPROVE`」「する＋`通し方: 文言合わせ` → 仕様レビューを照合せず、archive 済みの差分 1 ファイル・MODIFIED だけ・要件名が `直す文:` の行にある」「しない → 変更なし＋理由、かつ openspec 差分なし」「記録なし → 合格しない・記録してからやり直す」の 4 行を含む表が書かれている

#### Scenario: issue の無い PR の逃げ道がある
- **WHEN** SKILL.md の手順 5 を読む
- **THEN** PR コメントへの記録は PR 本文に issue 参照が無い場合に限り、issue 参照があれば issue 側が正である旨が書かれている

#### Scenario: 文言合わせの通し方の PR は仕様レビューのコメントが無くても通る
- **WHEN** 記録先の最新の仕様化判断のコメントが `仕様化判断: する` で `通し方: 文言合わせ` の行と `直す文:` の行を持ち、PR の HEAD に archive 済みの差分が 1 ファイルあり、その見出しが `## MODIFIED Requirements` だけで、要件名がすべて `直す文:` の行にあり、記録先に `仕様レビュー:` のコメントが 1 件も無い
- **THEN** 仕様宣言と記録の照合は合格する

#### Scenario: 通し方の行があるのに差分が要件を足している
- **WHEN** 記録先の最新の仕様化判断のコメントに `通し方: 文言合わせ` の行があり、archive 済みの差分ファイルに `## ADDED Requirements` の見出しがある
- **THEN** 合格処理をせず、差分を直すか、`通し方:` の行の無い仕様化判断を投稿し直して仕様レビューからやり直す

#### Scenario: 仕様化判断のコメントに無い要件を書き換えている
- **WHEN** archive 済みの差分ファイルの `### Requirement:` の要件名のうち 1 つが、仕様化判断のコメントのどの `直す文:` の行にも `「<要件名>」` の形で現れない
- **THEN** 合格処理をしない

#### Scenario: 通し方の行が無い PR は仕様レビューを省けない
- **WHEN** 記録先の最新の仕様化判断のコメントが `仕様化判断: する` で `通し方:` の行を持たず、記録先に `仕様レビュー: APPROVE` のコメントが無い
- **THEN** 仕様宣言が `仕様レビュー: 省いた` の形であっても合格処理をしない
