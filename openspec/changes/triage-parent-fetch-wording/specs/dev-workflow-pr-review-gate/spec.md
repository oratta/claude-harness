### Requirement: エピックの完了条件に効く指摘は既存 issue との関係で分ける（段 C）

エピックに属する PR で、段 B の「いまの範囲で成り立つ」に当たった指摘について、G はその指摘がエピックの完了条件に効くか（出荷物を使う人の体験が変わるか）を、エピックの本文の完了条件を根拠に決めなければならない（MUST）。効く指摘は、候補探しの結果で次の表のとおりに分ける（MUST）。効かない指摘は段 D へ進める（MUST）。

| 候補探しの結果 | 扱い |
|---|---|
| 同じエピックの子 issue（`child`）に、同じ場所を直すものがある | その子 issue の受け入れ条件に足す（その子が作業中でないとき。作業中なら新しい子 issue を作る） |
| エピックの外の issue（`other`）に当たり、その issue の受け入れ条件が、この指摘を直せば全部満たされる | その issue をエピックの子に足す。新しい子は作らない。足した理由をその issue にコメントする |
| エピックの外の issue に当たるが、満たされない項目が 1 つでも残る。または受け入れ条件が書かれていない | この指摘だけの新しい子 issue を作る。外の issue には「この部分は子 issue で直す」と番号を書き、エピックには足さない |
| 当たる issue が無い | 新しい子 issue を作る |

外の issue に open の PR が付いているときは、新しい子 issue に「外の PR のマージ後に着手」と書く（MUST）。エピックの中と外に同じファイルを直す issue が並ぶときは互いの番号を書く（MUST。重なりそのものは防がない）。

エピックに属するかは、記録先 issue の親を `gh api repos/<owner>/<name>/issues/<記録先>/parent --jq '{number,repository_url}' 2>&1` で番号とリポジトリ（`repository_url`）の両方を取って決める（MUST。`HTTP 404` は標準エラーにしか出ないので、末尾の ` 2>&1` で標準出力にまとめる）。この取得は段 B の前に済ませる（MUST。段 B の範囲の読みと候補探しの `--epic` が親で決まるため）。判定は終了コードでなく出力で行い（404 も 5xx も終了コードは 1 のため）、出力に `HTTP 404` を含むときだけエピックに属さない PR として段 C を飛ばす（MUST）。それ以外の失敗（レート制限・5xx・通信断など）は 1 回だけやり直し、やり直しの出力も同じ判定にかける（MUST）、それでも取れなければ、仕分けの PR コメントに親の取得の失敗を書き（MUST）、エピックに属さない PR とは読まない（MUST NOT）。このときは、段 C を飛ばし、候補探しは `--epic` を付けずに走らせ、段 B の範囲は記録先の issue で読み、「範囲で成り立つ」に当たった指摘は段 D の参考コメントで済ませず、段 E の判定もせず、エピックの外の新しい issue にする（MUST）。このときの答えは記録先の本文に足す（MUST）。親のリポジトリ（`repository_url` の末尾の `<owner>/<name>`）が、小文字にそろえて `<owner>/<name>` と違うときは、エピックの本文と `## 条件の答え` を親のリポジトリで読み書きし、候補探しは `--epic` を付けずに走らせて全候補を `other` として読む（MUST）。表の「エピックの子に足す」操作は、既存の issue も新しい子 issue も `repos/<親のリポジトリ>/issues/<親の番号>/sub_issues` に対して行い（足す要求は `-X POST repos/<親のリポジトリ>/issues/<親の番号>/sub_issues -F sub_issue_id=<id>`。`<id>` は番号でなく issue の `id`）、新しい issue そのものは `<owner>/<name>` に作る（MUST）。親のリポジトリの本文を読めない・書けないときは、親の取得の失敗と同じに扱う（MUST）。全候補を `other` と読むので、すでに親の子である `<owner>/<name>` の issue も「外の issue」に当たりうる。その確かめはしない（子に足す操作が拒否されたら、仕分けの PR コメントに書く）。

守備範囲: 入力は、親の取得の応答（HTTP の状態・`number`・`repository_url`）、エピックの本文の完了条件、候補探しのスクリプトが返した番号・題名・3 列目、投稿者を確かめた外の issue の本文に限る。拾いたい誤りは、エピックの完了条件に効く指摘がエピックの外の issue になって配布の前に直されないこと、同じ場所を直す子 issue があるのに新しい子 issue を作ること、別リポジトリの親の番号を `<owner>/<name>` の番号と読むこと、一時的な失敗を親が無いと読むこと。次は誤ったまま通ることを許す: 受け入れ条件があいまいな外の issue を G が「全部満たされる」と読み違えてエピックの子に足すこと（足した理由をその issue にコメントするので、あとから外せる）／完了条件に効かない指摘を G が効くと読んで子 issue が 1 件増えること／題名だけでは同じ場所を直すと分からない子 issue を見落とすこと／記録先 issue 自体が見えない 404、および親が private リポジトリにあり G のトークンが読めず 404 になる場合を「親が無い」と読むこと（`No parent issue found` かの区別はしない）／リポジトリ名の変更で `repository_url` が `<owner>/<name>` と違って見え、`--epic` なしで走ること／別リポジトリの親で、すでに親の子である issue を子に足そうとして拒否されること／別リポジトリの親で、すでに親の子である同じ場所の issue があっても新しい子 issue ができること。これらを塞ぎ切ることは完了条件にしない。

#### Scenario: 同じ場所を直す子 issue がある

- **WHEN** エピックの完了条件に効く指摘の場所のパスについて、スクリプトが 3 列目 `child` の候補を返し、その題名が同じ場所を直すもので、その子 issue が作業中でない
- **THEN** G はその子 issue の受け入れ条件に指摘を足し、新しい issue を作らない（作業中なら足さない。「段 C の子の行で足す前に、その子が作業中かを確かめる」要件）

#### Scenario: 外の issue の受け入れ条件が全部満たされる

- **WHEN** `other` の候補の投稿者が `OWNER` で、その issue の受け入れ条件が、この指摘を直せば全部満たされる
- **THEN** G はその issue をエピックの子に足し、足した理由をその issue にコメントし、新しい子 issue を作らない

#### Scenario: 外の issue に満たされない項目が残る

- **WHEN** `other` の候補の受け入れ条件のうち 1 項目が、この指摘を直しても満たされない
- **THEN** G はこの指摘だけの新しい子 issue を作り、外の issue に子 issue の番号を書き、外の issue をエピックの子に足さない

#### Scenario: 親が別リポジトリにある

- **WHEN** 記録先 issue の親の取得が `{"number":896,"repository_url":"https://api.github.com/repos/genetta-inc/flatmate"}` を返し、`<owner>/<name>` が `oratta/claude-harness` で、候補が当たらない指摘がエピックの完了条件に効く
- **THEN** G はエピックの本文を `genetta-inc/flatmate#896` で読み、`## 条件の答え` もそのリポジトリの本文に書き、候補探しを `--epic` なしで走らせて全候補を `other` として読み、新しい issue を `oratta/claude-harness` に作って `repos/genetta-inc/flatmate/issues/896/sub_issues` に足す。`oratta/claude-harness#896` をエピックとして扱わない

#### Scenario: 親が無い

- **WHEN** 親の取得の出力が `HTTP 404`（`No parent issue found`）を含む
- **THEN** G はエピックに属さない PR として段 C を飛ばす

#### Scenario: 親の取得が 404 以外で失敗し続ける

- **WHEN** 親の取得がレート制限・5xx・通信断のいずれかで失敗し、1 回やり直しても取れず、段 B で「範囲で成り立つ」に当たった指摘の場所に、同じ場所を直す open の issue の候補がある
- **THEN** G はエピックに属さない PR と読まず、仕分けの PR コメントに親の取得の失敗を書き、段 C を飛ばし、候補探しを `--epic` なしで走らせ、その指摘を段 D の参考コメントで済ませず段 E の判定もせずに、エピックの外の新しい issue にする

#### Scenario: 親のリポジトリの本文を読めない

- **WHEN** 親が別リポジトリにあり、そのリポジトリのエピックの本文をトークンの権限で読めない
- **THEN** G は親の取得の失敗と同じに扱い、エピックに属さない PR とは読まない
