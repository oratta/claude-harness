## Context

- develop の (4) では、G（ゲート実行者）が手順 1 と 2-0 まで済ませて `needs-reviewer` を返し、本体が phase `review` で投げ先を選び直してレビュアーを起こす（adapter 経路）。レビュアーは一周目に三表（`変更点の一覧`・`照合表`・`ハンク被覆`）と指摘を返し、照合と振り分けの G が三表を機械照合する（`gate-runner.md`「一周目の三表を機械照合する」）
- 三表は差分全体の通読と、変更点ごとのリポジトリ全体の grep を要する。直近 10 日の 1 周目 full レビュアー 69 体では、差分 600 行未満で上限超えが 41 体中 4 体、600 行以上で 28 体中 20 体（71%）だった。3,000 行を超える PR は 10 日間に 1 本も無い（測り直しの記録: https://github.com/oratta/claude-harness/issues/514#issuecomment-5882781960 ）
- PR #440（約 3,800 行・46 ファイル）では、レビュアーが差分の 6 割で上限に当たり、手で差分を区画に分けて並列に起こし直した。このとき照合表の検索コマンドに SHA を書かせて `review-hit-set.py` の書式（末尾 `<rev> -- .`）違反が全件で出た
- 上限超えを測る `subagent-context-audit.sh --by-role` は、Agent の `description` の先頭トークンが `Reviewer` のものをレビュアーに数える。今の紐付け規約はレビュアーの接頭辞を決めていない
- `review-hit-set.py` は照合表 1 つ（1 つの検索コマンド）を受け取り、固定 SHA での repository-wide な grep の全ヒット集合と比べる。照合表は変更点 ID ごとに独立している

## Goals / Non-Goals

**Goals:**

- 差分が 600 行を超える PR の一周目レビューで、Claude のレビュアー 1 体に渡す差分を 400 行前後に抑え、最初から上限に届かない大きさで起こす
- 区画に分けても、G の三表照合の保証（全受け入れ条件の被覆・全ハンクの被覆・照合表の全ヒット一致）を PR 全体で保つ
- 区画の計算を機械的にし、G・本体・補足のレビュアーが同じ区画を見る

**Non-Goals:**

- G の三表を全文読まない手順（G は #553・#554・#330 のあと上限に届いていない）
- 3,000 行超の PR で G が交代しないことの確認（そうした PR が出ていない）
- W（作業者）の交代（#253 で「工程完了のときだけ手渡す」に決まっている）
- 二周目以降の差分限定の再レビューと、方式の書き換え後の全体レビューを区画に分けること（三表を作るのは一周目だけで、上限超えの実測も一周目のレビュアーのもの）
- `review-hit-set.py` の変更、仕分け表・止める判定・合格処理の変更

## Decisions

### 決定 1: 区画はファイル単位で、ファイルの並び順に 400 行まで詰める。計算はスクリプトで行う

区画に分ける条件は、PR の差分の行数（ファイルごとの追加＋削除の合計）が 600 行を超えること。分け方は、GitHub の PR files API が返す順（パス順）にファイルを 1 つずつ見て、次の規則を上から順に当てはめる。

1. 変更行 0 のファイル（バイナリ・改名のみ）は直前のファイルと同じ区画に入れる。直前が 400 行超の単独の区画でもそこに入れる。先頭から続く 0 行のファイルは区画 1 に入れる
2. 1 ファイルで 400 行を超えるものは、新しい区画を始めてそれだけを入れ、その区画を閉じる
3. それ以外は、開いている区画に足して 400 行を超えないなら足し、超えるなら（または開いている区画が無ければ）新しい区画を始める

例: 100・500・0・100 行の順なら、区画 1 は 100 行、区画 2 は 500 行と 0 行、区画 3 は 100 行になる。

- 0 行を直前の区画に入れる理由: 0 行のファイルはレビュアーに渡す差分を増やさない。「単独」は「他の変更行を持つファイルと同じ区画にしない」という意味なので崩れない。0 行のファイルで新しい区画を始めると、変更行の無い区画（レビュアーを起こしても読むものが無い区画）ができうる
- 選ばなかった案: 0 行のファイルを次のファイルの区画に入れる。末尾が 0 行のファイルのとき、入れる先が無くなる

入力に行数の列が数でない行やタブの無い行があれば、スクリプトは何も出さず終了コード 2 で止まる。jq の式の誤りや別の形式の出力を渡した誤りを、黙って誤った区画にしないためである。守備範囲（通してよい入力と範囲外）は pr-review-gate の delta spec の段落に書く。

計算は新しいスクリプト `plugins/dev-workflow/scripts/review-partitions.sh` が行う。入力は標準入力の `<追加＋削除>\t<パス>` の行（`gh api repos/$R/pulls/$N/files --paginate --jq '.[] | "\(.additions + .deletions)\t\(.filename)"'` の出力）で、出力は 1 行目 `合計: <N> 行`、2 行目 `区画: なし` か `区画: <n>`、区画があれば区画ごとに `区画 <k>/<n>（<M> 行）` の見出しと、その下に `- <パス>（<L> 行）` の行。PR コメントにそのまま貼れる形にする。

- 理由: 区画の境界を G・本体・補足のレビュアーの 3 者が同じに見る必要があり、手で詰めると人ごとに境界がずれる。ゲートのたびに繰り返す計算なので、手作業の一覧ではなくスクリプトにする
- 選ばなかった案: ディレクトリ単位でまとめる。1 ディレクトリで 400 行を大きく超えることが多く（`skills/develop/` 配下など）、結局ファイル単位に落ちる。パス順に詰めれば同じディレクトリのファイルは隣り合うので、関連の近さはおおむね保てる
- 選ばなかった案: 手順 2-0 の `gh pr diff $N | grep -c '^[+-][^+-]'` の行数を閾値の判定に使う。ファイルごとの行数が取れないので区画の計算に使えず、閾値と区画で数え方が 2 つになる。閾値も files API の合計で判定し、2-0 の light / full の判定の数え方は変えない（2 つの数え方は `+++`・`---` で始まる本文行の扱いで数行ずれうるが、600 行の閾値にとっては無視できる）
- 400・600 は測り直しの値（600 行未満で上限超え 4/41、600 行以上で 20/28）と PR #593 の実測（区画 2 つに分けても片方が 152K）から置いた目安。事後計測（受け入れ条件 5）の値と一緒に見直す

### 決定 2: 区画に分けるのは Claude のレビュアーだけ。Codex のレビュアーは差分全体を 1 体に渡す

区画に分けるのは、従来モードの Task サブエージェント、`dev-workflow:decider` のレビュアー、adapter 経路で phase `review` の executor が claude のレビュアー。Codex のレビュアー（従来モードの Codex CLI、adapter 経路で executor が codex）は区画に分けず、今までどおり差分全体を 1 体に渡す。

- 理由 1: 手当ての対象である 150,000 トークンの上限は、Claude のサブエージェントに掛かる hook（`subagent-context.sh` と途中計測）の上限で、Codex のスレッドには掛からない。測り直しの上限超えもすべて Claude のレビュアーのもの
- 理由 2: Codex のレビューは 1 回 10 分を超えることがあり、区画ごとにスレッドを起こすと、スレッドごとの固定分（指示・受け入れ条件・固定 HEAD の読み込み、テストの再実行）と待ちが区画の数だけ増える
- 理由 3: Codex が差分全体で三表を出し切れなかったときは、G の機械照合が残差として検出し、補足 1 回のあと `review-incomplete` で止まる（今の fail-closed の経路がそのまま効く）。上限に当たって黙って欠けることにはならない
- 選ばなかった案: 実行者によらず区画に分ける。規則は 1 つで済むが、Codex では払う必要の無い固定分と待ちを増やす
- 見直す条件: Codex のレビューで三表の欠落（補足要求・`review-incomplete`）が 600 行を超える PR に偏って出たら、Codex にも区画を適用する

### 決定 3: 区画をまたいで ID が衝突しないよう、変更点 ID と finding ID に `P<k>-` を付ける

区画 k のレビュアーは、変更点 ID と finding ID の頭に `P<k>-` を付ける（例: `P2-C3`、`P2-F1`）。G は和集合で照合するので、区画ごとに 1 から振った ID がぶつかると、どの区画の変更点か・どの指摘かを取り違える。

### 決定 4: 受け入れ条件の被覆とハンク被覆は区画の和集合で満たし、照合表は区画ごとに今のまま照合する

- 区画のレビュアーは、受け入れ条件のうちその区画のファイルに関わるものだけを `変更点の一覧` で被覆する。受け入れ条件は全区画に全文を渡し、自分の区画に関わらないものは `変更点の一覧` の外に `区画の対象外: <受け入れ条件 ID>` と書く
- `ハンク被覆` は区画のファイルの全ハンクを被覆する
- G は、全区画の `変更点の一覧` の和集合で各受け入れ条件が 1 回以上対応すること、全区画の `ハンク被覆` の和集合が PR diff の全ハンクを含むことを集合比較する。`照合表` はリポジトリ全体の grep で 1 表ごとに完結しているので、区画ごとの表をそれぞれ `review-hit-set.py` に渡す（スクリプトは変えない）
- G は照合の前に、`レビュー重量:` コメントの区画の数と受け取った三表の区画の数が一致することを確かめる。足りない区画は残差とする。これは一周目のレビュアーが区画ごとに起こされたとき（本体が渡す要約に `区画 <k>/<n>` の見出しがあるとき）だけで、Codex が差分全体を 1 体で見たときは今までどおり 1 組の三表として照合する
- G は区画 k の三表の ID が `P<k>-` で始まることを確かめ、外れた ID をその区画の残差にする。接頭辞の付け忘れを通すと、和集合で ID が衝突して決定 3 の目的が崩れる
- 既存要件「レビュアーへの指示に全件列挙と再レビューの制限を含める」の「各受け入れ条件は 1 項目以上に対応させる」「各ハンクについて」は、区画に分けたときは区画の和集合で満たすものとして読む（この change で ADDED の要件として明記する）
- 選ばなかった案: 区画ごとにも全受け入れ条件の被覆を求める。自分の区画に無い変更を探して差分の外まで読みに行くことになり、区画に分けた意味が薄れる

### 決定 5: 照合表の検索コマンドは文字どおり `<rev>` と書かせる

区画の指示に「`検索コマンド:` には SHA を書かず、文字どおり `<rev>` と書く（固定 HEAD は `修正前 SHA:` の行に書く）」を足す。共通一覧契約は既に `<rev> -- .` を求めているが、PR #440 で区画に分けたレビュアーが SHA を書いて全件で書式違反になったので、区画の指示の中で改めて書く。

### 決定 6: テスト・lint の再実行は区画 1 のレビュアーだけが行う

レビュアー向け指示は「テスト・lint は報告を信用せず自分で再実行する」を求めている。区画の数だけ同じテストを回すと、待ちと出力の読み込みが区画の数だけ増える。再実行は区画 1 のレビュアーだけが行い、他の区画のレビュアーは再実行しなかったことを要約に書く。

### 決定 7: 区画の計算は G が手順 2-0 で行い、`レビュー重量:` コメントと `needs-reviewer` の payload に載せる

G は手順 2-0 で `review-partitions.sh` を回し、結果を `レビュー重量:` の PR コメント（3 行目以降）と `needs-reviewer` の payload の `区画:` の欄に載せる。本体は payload の区画を使い、executor が claude のときだけ区画ごとに起こす。照合と振り分けの G は、区画の一覧を `レビュー重量:` コメントから読む（段と段の間で渡すものは PR コメントを正とする既存の規則に従う）。

- 理由: G は 2-0 で差分の行数を既に測っていて、本体に差分を読ませずに済む。区画の一覧を PR コメントに残せば、段ごとに新しく起こされる G も補足のレビュアーも同じ一覧を読める
- 従来モード（develop 以外の本体、`レビュー経路: 従来` の G）では、Task サブエージェントを起こす側が同じスクリプトで区画を出す

### 決定 8: 区画ごとのレビュアーは並列に起こし、1 体の照合と振り分けの G に全区画の要約を渡す。補足は残差のある区画だけ

- 本体は区画ごとのレビュアーを 1 つのメッセージで並列に起こす。`description` は `Reviewer: 区画 <k>/<n> for PR #<N> (#<issue>)` にする（`subagent-context-audit.sh --by-role` が先頭トークン `Reviewer` でレビュアーに数え、受け入れ条件 5 の事後計測に使えるようにするため）
- 全区画の要約が揃ってから、照合と振り分けの G を 1 体だけ起こして全区画の要約を渡す（区画ごとに G を起こすと、和集合の照合ができない）
- 補足要求の残差は、G が次の規則で補足先の区画を決める: 足りない区画はその区画、ハンク被覆の残差はそのハンクのファイルが属する区画、照合表と ID の接頭辞の残差はそれを出した区画、受け入れ条件の被覆の残差（全区画が `区画の対象外:` とした、またはどの区画も触れなかった受け入れ条件）は区画 1。本体は残差のある区画だけに補足のレビュアーを起こし、その区画の元の三表と残差を渡す。補足済み回数は PR で 1 つだけ数え、区画ごとには数えない（補足は 1 回まで、という今の上限を区画の数で増やさない）
- 受け入れ条件の被覆の残差には変更点 ID も所属ファイルも無いので、ID の接頭辞とファイルでは補足先が決まらない。区画 1 に寄せるのは、区画 1 がテスト・lint の再実行も担っていて、区画に固有でない仕事の置き場を 1 つに揃えられるからである。区画 1 の補足はこのときだけ、その受け入れ条件の全文・全区画のファイル一覧・それらのファイルの PR diff のハンクを読んでよく、補った変更点 ID は `P1-` で始める。対応する変更が PR diff に無ければ `P1-` の finding として返す
- 選ばなかった案: 受け入れ条件の被覆の残差を全区画に補足させる。区画の数だけ同じ受け入れ条件を探し、補足が PR で 1 回という上限の意味（補足の総量を抑える）が崩れる
- 選ばなかった案: 補足だけ区画に分けない 1 体に差分全体を渡す。上限に届く大きさの差分を 1 体に渡すことになり、区画に分けた理由と食い違う

### 決定 9: 補足は一周目の区画の構成のまま行い、executor の選び直しで構成を変えない

補足でも本体は phase `review` の投げ先を選び直す（既存要件）。選び直しで executor が一周目と変わっても、補足は一周目の区画の構成と ID のまま行い、区画を計算し直したり差分全体のレビューを始めたりしない。一周目の構成は G が `レビュー三表:` のコメントと補足 payload に `一周目の区画: なし` または `一周目の区画: <n>` と書き、補足の受領で G はその構成で照合をやり直す。

- claude（区画あり）→ codex: 1 つの request に、残差のある区画ごとに番号・ファイル一覧・元の三表・残差を分けて載せ、区画ごとに `P<k>-` の ID で補わせる。補足の対象は残差だけで差分全体ではないので、Codex に区画を渡しても決定 2 の理由（区画ごとのスレッドの固定分と待ち）には当たらない
- codex（区画なし）→ claude: 補足のレビュアーを 1 体だけ起こし、1 組の三表と残差を渡して接頭辞の無い ID で補わせる。payload の `区画:` に区画があっても区画ごとに起こさない。元の三表に接頭辞が無く、区画への対応が決められないためである。補足は残差の項目だけを読むので、差分全体を 1 体で読むことにはならない
- 理由: 補足は「元の三表を置き換えず不足分だけを補う」ものなので、一周目と違う構成で出し直すと元の三表と ID が合わず、和集合の照合ができない
- 選ばなかった案: 補足の executor に合わせて区画を組み直す。codex なら差分全体、claude なら区画に分け直すことになり、補足がレビューのやり直しになる
- 選ばなかった案: 補足では executor を選び直さず一周目と同じにする。既存要件（補足要求も本体の選び直しを通る）を変えることになり、この change の範囲を超える

## Risks / Trade-offs

- [区画をまたぐ食い違いを見落とす] 区画 1 の変更と区画 2 の変更が互いに矛盾していても、それぞれのレビュアーは自分の区画しか読まない → 照合表はリポジトリ全体の grep なので、変更点の検索語が他の区画のファイルに出れば照合表に載る。一覧に載らない暗黙の食い違いの発見は、今の保証範囲（変更点の一覧に載せた項目まで）の外で、区画に分ける前と変わらない
- [区画の数だけ固定分が増える] 区画ごとに指示・受け入れ条件・固定 HEAD を読み込む → 1 体あたりの差分が減るぶん上限超えによる交代（起動と読み直しの固定分を払い直す）が減るので、600 行を超える PR では差し引きで減る見込み。受け入れ条件 5 で交代の件数と最大コンテキストを記録する
- [照合と振り分けの G が全区画の三表を読む] 区画の数だけ G の読む量が増える → G は今上限に届いておらず（#330 のあと最大 81K 以下）、G の三表を全文読まない手順は範囲外にした。受け入れ条件 5 の計測で G の交代が出たら別 issue で扱う
- [files API と 2-0 の行数がずれる] 閾値付近で 2-0 の行数と区画の合計が数行ずれうる → 閾値の判定は files API の合計だけで行い、2-0 の light / full の判定には使わない
- [Codex が大きい差分で三表を欠く] → 決定 2 の理由 3 のとおり fail-closed で止まる。偏って出たら Codex にも区画を適用する
- [全区画が対象外とした受け入れ条件の補足が区画 1 に集まる] 区画 1 の補足は他の区画のファイルのハンクも読む → 読むのは残差の受け入れ条件に関わるハンクを探すためだけで、差分全体の三表は作らない。区画 1 の補足が上限に届いたら、受け入れ条件 5 の事後計測で見える
