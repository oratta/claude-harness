## MODIFIED Requirements

### Requirement: エピックの子の停止の記録は、子の会話を読んでいない読み手が 1 通で読める形で書く
develop の SKILL.md の節「エピックの子が主の返事を待って止まるとき」は、1 行目 `子の停止: 主の返事待ち` の記録の 2 行目以降の形を次のとおり規定しなければならない（MUST）。読み手は親のセッション・親の決める役・主で、どれも子の会話を読んでいない前提で書く。

- 2 行目以降は次の 7 つの項目をこの並びで書く（MUST）。どの項目も省いてはならない（MUST NOT）
  1. `止まった理由:` — 主にしてほしいこと（決めること 1 つ、または操作）
  2. `主に聞く理由:` — 主に聞く理由の 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作。正本は `~/.claude/output-styles/readable.md` の節 3）のどれに当たるかを、その語で始めて 1 文で書く。「決まりで主の承認が要る」ときは、その決まりが何を守るためかまで書く。どれにも当たらないのに子の側で進められないときは `主に聞く理由: なし（<子の側で進められない理由>）` と書く
  3. `前提:` — 子が作業中に分かった事実のうち、判断に要るもの
  4. `推奨:` — 子が勧める答え
  5. `推奨の根拠:` — その推奨を選ぶ理由
  6. `受け入れるリスク:` — 推奨を選ぶと受け入れることになるリスク。何が起きるか（被害の大きさ・戻せるか）、どれくらい起きるか（起きる条件と頻度）、その根拠（確かめたのか見込みか）を含める。分からないときは「分からない」と書き、何を調べれば分かるかを添える
  7. `再開に要る途中経過:` — 返事を受けて再開するのに要る途中経過（作業の状態・コミット・PR など）。「保留で止まるときの引き継ぎ」を書く場面では引き継ぎのコメントの URL を含める
- 主に聞く理由の 3 つのどれにも当たらない止まりは、子がそもそも止まらずに自分で進めて事後報告するのが正本の決まりであることを書く（MUST）。`主に聞く理由: なし（…）` は、子の側で進められないときだけに使う
- 各項目は行頭の `<項目名>:` で始め、値を同じ行に書く（MUST）。値は次の項目の行まで複数行に続けてよい（MAY）
- 該当が無い項目は値を `なし` と書く（MUST）。推奨を出せない（主の側にしか無い情報が要る）ときは `推奨: なし（<足りない情報>）` と書き、`推奨の根拠:` と `受け入れるリスク:` は `なし` と書く（MUST）
- 書き方として、子が作業中に振ったラベル・番号・略称や「上記」「前回」で指さず中身を書くこと、PR・issue・コメントにはフル URL を添えること、専門用語は初出で一言の言い換えを添えることを規定する（MUST）。文章全般の書き方は `rules/communication-style.md` を正本とし、SKILL.md に写さない（MUST NOT）
- 親は記録の項目を正本の段に置き直して主に報告し、項目名をそのまま主に渡さないことを書く（MUST。親の側の規定は要件「Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる」）。項目名 `止まった理由` は、Orca 経路の「マージ待ちの子」の段落と `references/parent-merge-criteria.md` が値の頭（`PR のマージ待ち（`）で読むので変えない（MUST）
- CI の見張り（`references/ci-watch.md`）で止まったとき（6 の表の `escalate` と、7 の直し方の手順 7 で直せずに上げたとき）は、`再開に要る途中経過:` に PR の URL・落ちたチェック名・止まった時点の PR の HEAD の短い SHA を書く（MUST）。短い SHA は PR の HEAD のコミット SHA の先頭 7 文字とし（MUST）、`ci-watch.sh next` の出力の `obs.head` か `gh pr view` の `headRefOid` から取る。取れなかったときは値を作らずに `HEAD 不明` と書く（MUST）。項目の数は 7 つのままとし、HEAD のための項目を足してはならない（MUST NOT）。`references/ci-watch.md` の `escalate` の行は、エピックの子のセッションが止まる前にこの記録を残し、書き方はこの節に従うことを指す（MUST。同じ規定を `ci-watch.md` に写さない）

この要件の守備範囲で入力として扱うのは、SKILL.md の記録の項の文と、子が投稿する記録のコメントの本文である。拾いたい誤りは、項目が欠けて読み手が書き忘れと該当なしを区別できないこと、子の会話の中でしか通じない呼び名で書かれて読み手が聞き返すこと、主に聞く理由とリスクの頻度・根拠が無くて親が正本の型で書けないこと、`止まった理由:` の値の頭を読む箇所と項目名が食い違うことの 4 つと、CI の見張りのやり直しの上限で止まった子の記録に HEAD が無くて、親が過去の `親の判断:` と同じ件かを見分けられないことの 5 つである。次は通ってよく、この要件では止めない: 値の長さや改行の違い／`なし` の後ろに短い補足が付くこと／同じ止まりで記録を投稿し直すこと（最新の 1 件を正とする）／この変更の前に起動された子が以前の 6 項目の形で書くこと（判断と親はほかの項目から読む）／CI の見張りで止まった子が HEAD の短い SHA を書き忘れること、HEAD を書く規定の前に起動された子が書かないこと（親は `parent-pass-criteria.md` のとおり `不明` と扱い、同じ件かを見分けられないものとして主に上げる側に倒れる）。記録の中身（理由・推奨・リスク）の正しさを確かめることと、書き方の穴が見つかるたびに検査や決まりを足して塞ぎ切ることは、この要件の完了条件としない。

#### Scenario: SKILL.md に記録の 7 つの項目名がこの並びで書かれている
- **WHEN** SKILL.md の節「エピックの子が主の返事を待って止まるとき」を読む
- **THEN** `止まった理由:`・`主に聞く理由:`・`前提:`・`推奨:`・`推奨の根拠:`・`受け入れるリスク:`・`再開に要る途中経過:` がこの順で書かれ、どの項目も省かないこと、該当が無いときは `なし`、推奨を出せないときは `推奨: なし（<足りない情報>）` と書くことが書かれている

#### Scenario: 主に聞く理由とリスクの中身が書かれている
- **WHEN** SKILL.md の同じ節の記録の形を読む
- **THEN** `主に聞く理由:` に 3 つの理由のどれかを書くこと、どれにも当たらないときは止まらずに進めるのが決まりで、子の側で進められないときだけ `主に聞く理由: なし（<子の側で進められない理由>）` と書くことが書かれ、`受け入れるリスク:` に頻度と根拠（確かめたのか見込みか）を含めることが書かれている

#### Scenario: 記録の書き方の決まりが書かれている
- **WHEN** SKILL.md の同じ節を読む
- **THEN** 子の会話を読んでいない読み手に向けて書くこと、子が振ったラベル・番号や「上記」「前回」で指さないこと、フル URL を添えること、専門用語に言い換えを添えることが書かれ、`rules/communication-style.md` を指している

#### Scenario: 項目名をそろえる規定が置き直しの規定に替わっている
- **WHEN** SKILL.md の同じ節を読む
- **THEN** 項目名を親の手順 8 の語と同じにしてあるという文が無く、親が記録を正本の段に置き直して主に報告することが書かれている

#### Scenario: CI の見張りで止まったときの書き方が記録の形の節に書かれている
- **WHEN** `epic-child-stop.md` の「記録の形」を読む
- **THEN** CI の見張りの `escalate` と直し方の手順 7 で止まったときは、`再開に要る途中経過:` に PR の URL・落ちたチェック名・止まった時点の PR の HEAD の短い SHA を書くこと、短い SHA は PR の HEAD のコミット SHA の先頭 7 文字で `obs.head` か `headRefOid` から取ること、取れなければ `HEAD 不明` と書くことが書かれ、項目の数は 7 つのままである

#### Scenario: CI の見張りの escalate がエピックの子の記録の規定を指している
