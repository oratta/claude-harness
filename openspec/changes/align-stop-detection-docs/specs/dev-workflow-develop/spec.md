## MODIFIED Requirements

### Requirement: epic-dispatch.sh の wait は止まった子を判断し、通すものには返事を送って待ちを続ける
`plugins/dev-workflow/scripts/epic-dispatch.sh wait` は `--resolve <epic>` を受け付けなければならない（MUST）。`<epic>` が数字でなければ使い方を出して exit 1 で終わる（MUST）。`--resolve` は `--watch-stopped` と位置引数の子が 1 件以上あるときだけ働き（SHALL）、それ以外では何もしない。`--resolve` の有無で止まりの検知の条件は変えず、違うのは判断を呼ぶかどうかだけである（MUST）。

以下の停止の処理と各 Scenario は、要件「wait は子の状態の記録だけで止まった子を検知する」の対象であることを前提とする。判断の入口（長い待ちの再判断も含む）と返事・端末終了・再起動の処理に入る前に、同じ入力世代・セッションで対象条件を満たすか再確認しなければならない（MUST）。owner の入力、状態の無効化や更新を確認したら古い判断を送ってはならない（MUST NOT）。

`--resolve <epic>` が働くとき、`wait` はポーリングで止まった子（既存の要件のとおり記録の `stop` が `stopped-seen` に書き換えられた子）ごとに、次を行わなければならない（MUST）。

1. 判断のコマンド（環境変数 `EPIC_DISPATCH_JUDGE`。既定は `epic-dispatch.sh` と同じディレクトリの `stop-judge.sh`）を `<epic> <child> <止まりの JSON のパス>` を引数に 1 回呼ぶ。会話ログを読めなかった止まりは JSON が無いので `<epic> <child>` で呼ぶ
2. 判断の出力の 1 行目が `判断: 通す` で、3 行目が `返事: ` に続く空でない文なら、要件「epic-dispatch.sh reply は子の端末に送り手を付けた返事を届ける」の `--as parent` と同じ処理でその文を子に送る。結果が `skipped <child> not-stopped`（送る直前に子が再開済みだった。主が子のタブで先に答えたとき）なら、何も送らず、エピックにも `親の判断:` を投稿せず、その子を出力に含めずに待ちを続ける（MUST）。結果が `sent` か `relaunched` なら、エピックに `親の判断: 子 #<child> 通した — <2 行目の 理由: のうしろ> 発言 <止まりの uuid か 不明>` の 1 行（4 行目の `記録:` のうしろが URL なら、末尾に空白とその URL を足す）をコメントする。投稿できたらその子を出力に含めない。投稿に失敗したら、その子を `unrecorded` に含め、stderr に投稿し直すコマンド（`gh issue comment <epic> --body <その 1 行>`）を出す（エピックへの記録は送信のあとに投稿する。送る前に投稿すると、送れなかったときに通していない判断が残るため）
3. 判断が `判断: 主に上げる` なら、子 issue に 1 行目 `親の判断: 主に上げる`、2 行目 `止まりの発言: <止まりの uuid か 不明>`、3 行目 `停止の記録: <4 行目の 記録: のうしろ>`、4 行目以降に判断の理由を書いたコメントを投稿し、その子を `stopped` に含める
4. 判断のコマンドが非 0 で終わった・出力が 1〜4 行目の形で読めない、または判断が `判断: 通す` で送れなかった（`failed`）なら、子 issue に 1 行目 `親の判断: 判断できなかった`（送れなかったときは `親の判断: 通すが送れなかった`。判断は通すで送信だけが失敗したことを事実どおりに書く）、2 行目 `止まりの発言: <止まりの uuid か 不明>`、3 行目 `停止の記録: <URL か なし>`（判断の出力から読めたときだけ。読めなければ `停止の記録: 不明`）、4 行目以降に何が失敗したかと（あれば）送るはずだった返事を書いたコメントを投稿し、その子を `stopped` に含める。判断の出力そのものはコメントに貼らない（MUST NOT。判断の入力には gitignore 済みの `.claude/casting/local.md` も入り、出力に引用されうるため。見たいときのために stderr にだけ出す）
5. 判断が `判断: 問いではない` なら、記録の `stop` を `resumed` に戻し（`stop_uuid` は残す）、stderr に `問いではない <child> <理由>` を出し、子にも issue にも何も送らず、その子を出力に含めずに待ちを続ける（MUST）

`--resolve` が働く `wait` の出力は、`closed <N>...`・`done <N>...`・`stopped <N>...`・`unrecorded <N>...`・`owner-away <N>...` を該当するものだけこの順に（1〜5 行）出して exit 0 とする（MUST。`owner-away` は要件「主が打った返事待ちは時間がたったら親が主に知らせる」の行で、`unrecorded` の次に出る）。`unrecorded` は「返事は子に届いたが、エピックへの 1 行を残せなかった」子で、親を起こして記録させるために出す。この出力の規定は、`--resolve` が働く場合に限り、既存の要件「epic-dispatch.sh は子が止まった印を付け、wait が止まった子を返す」と「エピックの子の止まりの手順と、親が stopped を受けて報告する手順を規定する」が定める `closed`・`done`・`stopped` の 1〜3 行の規定に優先する。`--resolve` が働かない `wait` は、`unrecorded` を出さず、`closed`・`done`・`stopped`・`owner-away` を該当するものだけこの順に（1〜4 行）出さなければならない（MUST）。この 1〜4 行は、要件「epic-dispatch.sh は子が止まった印を付け、wait が止まった子を返す」が定める `closed`・`done`・`stopped` の 1〜3 行の規定にも優先する。ポーリングで `stopped` にも `unrecorded` にも `owner-away` にも含める子が 1 件も無く、閉じた子も完了の印の子もいなければ、`wait` は待ちを続けなければならない（MUST）。`owner-away` の子が 1 件でもあれば、ほかの語の行が無くても `wait` は待ちを終えて出力し exit 0 で終わる（MUST）。

子 issue への `親の判断:` のコメントの投稿に失敗しても、その子は `stopped` に含める（MUST）。stderr に投稿し直すコマンドを出す（SHALL）。親は子 issue の `親の判断:` のうち、2 行目の `止まりの発言:` が今の止まりの uuid と一致するもの（uuid が空の止まりは、3 行目の `停止の記録:` が最新の `子の停止: 主の返事待ち` のコメントの URL と一致するもの）だけを今回の判断として読む（要件「Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる」）ので、投稿に失敗して前回の判断が残っていても、親はそれを今回の判断と取り違えず、判断が無いものとして扱う（要件「Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる」の手順 8 で親が照らす）。

`plugins/dev-workflow/scripts/stop-judge.sh <epic> <child> [<止まりの JSON のパス>]` は、次の入力だけを集めてモデルを 1 回呼び、stdout に 4 行を出さなければならない（MUST）。

- 入力: エピックの本文と子 issue の本文（どちらも、その issue の投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のときだけ）、子 issue の `親エピックからの注意書き:` で始まるコメントのうち投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のもの、子 issue の 1 行目が `子の停止: 主の返事待ち` のコメントのうち投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` の最新のものの本文と URL（止まりの JSON があるときは、`created_at` が最後の入力の時刻以降のものに限る。今回の止まりより古いリスク許容の記録を読まないため）、止まりの JSON（最後の子の発言の全文（末尾を残す。上限は要件「child-log --last は親に最後の発言の全文を出す」の `EPIC_DISPATCH_STOP_TEXT_MAX`）・未回答の質問ツールの問い・背景のタスクの有無・最後の入力の時刻・印の有無）、エピックのコメントのうち投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` で `親の判断: 子 #<child> ` で始まるもの、`plugins/dev-workflow/skills/develop/references/parent-pass-criteria.md` の本文、リポジトリの `.claude/casting/project.md`・`.claude/casting/local.md`（あるものだけ）
- 呼び方: 既定は `claude -p --model <モデル> --tools "" --no-session-persistence`。モデルは `EPIC_DISPATCH_JUDGE_MODEL`（既定 `sonnet`）、コマンド全体は `EPIC_DISPATCH_JUDGE_CMD` で変えられる。ツールを渡してはならない（MUST NOT）
- 出力: 1〜3 行目はモデルの出力の 1 行目 `判断: 通す`・`判断: 主に上げる`・`判断: 問いではない` のどれか、2 行目 `理由: <1 行>`、3 行目 `返事: <1 行>`。4 行目は `stop-judge.sh` 自身が付ける `記録: <今回の停止の記録のコメントの URL か なし>`。モデルの出力が 1〜3 行目の形で読めなければ、stdout に何も出さず exit 1 で終わる（MUST）。`判断: 問いではない` は、止まりの JSON が無い・今回の停止の記録がある・未回答の質問ツールの問いがある・止まった印が付いている・今回の止まりより前の未回答の停止の記録がある（要件「stop-judge.sh は未回答の停止の記録が残る止まりを問いではないとして通さない」）、のどれかのときは形の崩れとして扱う（MUST。子が止まると宣言した件を判断のモデルが黙って流さないため）
- 止まりの JSON が無く停止の記録のコメントも見つからない・`gh` が失敗した・エピックか子 issue の投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれでもないか読めないときは、モデルを呼ばずに exit 1 で終わる（MUST）。exit 1 は `wait` の側で判断の失敗になり、子は主に上がる（issue は誰でも立てられるので、ほかの投稿者の本文で判断を誘導されないようにする）
- `orca` の語を含んではならない（MUST NOT。既存要件「develop の手順書に orca のコマンドを書かず、orca を呼ぶスクリプトは 1 本にする」）

`plugins/dev-workflow/tests/epic-dispatch.bats` と `plugins/dev-workflow/tests/stop-judge.bats` は、判断のコマンドとモデルのコマンドをスタブにして、上の振る舞い（通して送れたら出力に含めずエピックに 1 行残すこと、送れたがエピックへの投稿に失敗すると `unrecorded` を出すこと、主に上げると `stopped` を出し子 issue のコメントに `停止の記録:` の行があること、子 issue への投稿に失敗しても `stopped` を出すこと、判断の失敗・形の崩れ・送信の失敗で `stopped` を出すこと、`--resolve` なしでは判断を呼ばないこと、入力の集め方と出力の形の検査、問いではないと判断した子を親に返さず何も投稿しないこと、今回の記録・質問ツールの問い・印のある止まりの問いではないを形の崩れとして扱うこと、最後の入力より古い記録を入力に入れないこと）を確かめなければならない（MUST）。

この要件の守備範囲で入力として扱うのは、`wait` では判断のコマンドの終了コードと stdout、`reply` と同じ処理の結果で、`stop-judge.sh` では `gh` の出力（エピック・子 issue・コメント）と、`wait` が渡す止まりの JSON、モデルのコマンドの stdout である。拾いたい誤りは、判断に失敗した止まりや主に上げる止まりを親に知らせずに待ち続けること、判断の結果を読み違えて通さない件を子に送ること、通した件がエピックに残らないまま親が起こされないこと、親が前回の止まりへの判断を今回の判断と取り違えること、判断の入力に親の会話が混ざって費用が増えること、今回の止まりより古い記録で判断すること、問いでない発言で親を起こし続けることの 7 つである。次は通ってよく、この要件では止めない: モデルの理由や返事の文の中身の良し悪し（基準の当てはめの正しさはこの要件の完了条件にしない）／1 回のポーリングで複数の子が止まり、判断を子の数だけ順に呼ぶこと／エピックへの投稿が一時的に失敗し、親が `unrecorded` で起こされて投稿し直すこと。モデルが基準を当てはめ損ねる入力や、投稿の失敗の組み合わせが見つかるたびに塞ぎ切ることは、この要件の完了条件としない。

- `stopped <N>...` で起こされたら、止まった子ごとに`child-log --last` の最後の発言と、あれば子 issue の今回の停止の記録（1 行目が `子の停止: 主の返事待ち` のコメントのうち最後の入力以降のもの）を読み、子の番号・止まった理由・推奨（記録があればコメントの URL）をユーザーに報告し、残りの動いている子（止まった子を含む）で再び `wait` する（MUST）。止まった子を動いている子から外してはならない（MUST NOT）。止まった子への返事の仕方は #1034 で決める
- `wait` の出力の説明を、`closed`・`done`・`stopped` の 1〜3 行とする（MUST。`owner-away` を含む形は要件「Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる」が優先する）

#### Scenario: 親が stopped を受けたときの手順が書かれている
- **WHEN** `references/epic-stop.md` の Orca 経路の手順を読む
- **THEN** `wait` に `--watch-stopped` を付けること、出力が `closed`・`done`・`stopped` の 1〜3 行（`owner-away` を含む形は 1〜4 行）であること、`stopped` で起こされたら最後の発言と、あれば今回の停止の記録を読んでユーザーに報告し、止まった子を外さずに再び `wait` することが書かれている
