# Design: 主への判断依頼を論点のあるものに絞る

## Context

動機は proposal.md の Why。今の仕組みで関係するのは次の 4 か所で、どれも「主に聞く理由の 3 つ」（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作。正本は `output-styles/readable.md` 節 3）を参照しているが、使い方がそろっていない。

- ゲート（`pr-review-gate`）の手順 3 は、7 観点の分類に当たれば宣言を「主のリスク許容が必要」にし、論点なしでも手順 6 で主の OK を待つ（`declarations.md` の「論点なし — 分類に当たったので決まりで主の OK が要る」）
- 親が通す基準（`parent-pass-criteria.md`）は、9 条件のどれかを満たすか判断できなければ主に上げ、「主に聞く理由が成り立つか迷うときは成り立つ側に倒す」「通してよい止まりを判断のモデルが主に上げることは止めない」と書く
- 主の委任（`epic.md`「主の委任」、#1293）は、定型の委任の記録への主の確認で始まり、効く止まりは「推奨が許容する」のリスク許容待ちだけ。記録の範囲の文が「聖域の変更・破壊的な操作・マージの承認・不許容は含まない」と書く
- `owner-reply-check.sh --delegated` は、委任の記録の URL を書いた最後の親の発言と確認の発言のあいだに別の主の発言があると `not-direct` で落とす（`--relayed` と共通の判定）

2026-11-09 の flatmate #2058（エピック #1995）の実物: 主は親のタブで「任せる。今回の件も許容する。」と打った。親はまず `--relayed` の形で送り、子は `not-asked`（親がその発言の前に見せた文に最新の停止の記録の URL が無かった）で落とした。親は続いて委任の記録を投稿して委任の形で送り直し、子は `not-direct`（親が記録の URL を最後に見せた発言から主の確認までのあいだに主の別の発言があった）で落とした。主は子のタブで「許容する」と打ち直した。

制約: 対象のファイルの多くが聖域で、`rules/communication-style.md` は常時注入（`tests/injection-budget.bats` の予算）。`.github/workflows/auto-merge.yml` と hooks は変えない。

## Goals / Non-Goals

**Goals**
- 主に上がる止まりを「3 つの理由のどれかを根拠つきで示せたもの」に限る
- 論点なしのリスク宣言と、委任のある論点なしの止まりを、主の手を経ずに通す。通した記録を PR とエピックに残し、主があとから見て止められる形にする
- 主の指摘が効く観点（運用の形・構造の分け方・将来の拡張）を、主を止めずに報告で渡す

**Non-Goals**
- 聖域に触れた PR のマージ経路を変えない（`auto-merge.yml` のパスによる `human-merge` と、既存の `parent-merge-approved` の印のまま）
- hook が確認画面や拒否で止める破壊的な git 操作を、主の手なしで実行できるようにしない（委任で親が「進めてよい」と答えても、hook が主の手を求めるならその止まりは「主の手でしかできない操作」として主に上がる）
- `rules/destructive-git-guard.md` と `rules/perspective-casting.md` は変えない
- 判例台帳の既存の判例を書き換えない

## Decisions

### D1: 1 つの change に 4 つの capability の差分を載せる

Step C の基準に照らすと、4 つの capability に跨り、独立に見える設計判断が 4 つ（D2〜D5）あるので、形の上では「複数 change に割れる」に当たる。それでも 1 つにする。

- どの差分も同じ 1 つの規則（主に上げるのは 3 つの理由を示せたときだけ。論点なしは親か決める役が引き取る）を別の面に書くもので、互いに同じ文を参照する（委任が効く止まりの文は親・子・G が「同じ文で確かめる」契約）。片方だけ先に入れると、ゲートは親の OK を受けるのに親の基準は主に上げる、のような食い違った中間の状態がマージされる
- issue 本文の理由: 直す先が同じファイルに集中して並べると衝突し、どれも聖域で、分けると主のレビューとマージが本数分になる。1 本あたりの固定のコストは約 $5
- 代わりの案（ゲート／親の基準と委任／論点の定義、の 3 change に分け、論点の定義 → ゲート → 親の基準の順に入れる）は、上の食い違いを順序で避けられるが、主のレビューが 3 回になる。採らない

実装では編集するファイルが 5 個を超えるので、W の規模超過のトリップワイヤーが必ず発火する。tasks.md のグループごとに return する前提で組む（本体が発火の扱いを決める）。

### D2: 論点なしのリスク宣言を通す担い手と記録

- エピックの子（`route` が `nested`）: 今の停止の記録（`子の停止: 主の返事待ち`）の流れのまま親が判断する。親の基準で通すときの返事は `親エピック #<E> の判断（主の承認ではない）: 論点なしの確認として通す` の形で送り、子の本体は G に渡す
- エピックの子でないセッション（develop の本体、develop の外でゲートを回すメインセッション）: 手順 6 で主に聞く前に、決める役（`subagent_type: dev-workflow:decider`）を起こし、宣言の本文と根拠ファイルの差分だけを渡して「論点なしか」を判定させる。develop の G は判定役を起こせないので、3-c の `needs-carryover-judge` と同じく本体に返して本体が起こす
- 記録: 宣言コメントに `論点なしの確認: 通す — 確認者 <親エピック #<E> のセッション <ID> か dev-workflow:decider> / <日時> 根拠: <1 文>` を追記する。行頭を `主の回答:` にしない（3-c の引き継ぎが主の直接の回答として拾わないため）。HEAD が動いたら引き継がず、確認を取り直す
- 確認者が「論点あり」と判定したら、宣言を論点ありに書き直して今までどおり主に上げる
- 通す対象は「論点なし」の行を持つ宣言だけ。7 観点のどれに当たったかは問わない（聖域に触れた PR は、マージの段で `auto-merge.yml` が人間のマージに回す）

代わりの案: 論点なしなら誰の確認も取らずに通す。宣言を書いた G 自身の判定だけになり、論点ありを論点なしと書き誤ったときの歯止めが無くなるので採らない。

### D3: 親の基準の「迷ったとき」を、理由を示す責任に置き換える

- 消す: 「主に聞く理由が成り立つか迷うときは、成り立つ側に倒す」と、守備範囲の「通してよい止まりを判断のモデルが主に上げること…は止めない」の 2 か所
- 足す: `判断: 主に上げる` の `理由:` は、3 つの理由のどれに当たるかと、その根拠（どの記録・どのファイルの何）を書く。示せなければ通す
- 残す: 委任の無いセッションでは「聖域でない」「戻せる」「実機操作でない」の 3 条件は、判断できなければ満たさない側に読む（危険側の取り違えを防ぐ歯止めで、主に聞く理由の有無の判定とは別）
- 誤判定の防止: 「主の側にしか答えが無い」とする前に (a) ログ・リポジトリ・手順書で調べれば分かる事実でないか (b) 主の手が要る操作かを手順書で確かめたか (c) 推奨と根拠がそろっていないか、を確かめる。通らない例: 11/16（調べれば分かる事実を聞いた）、11/12（主の作業でないものを主の作業として転送した）、11/13（推奨のそろった順序の入れ替え）。同じ確かめを `epic-child-stop.md` の `主に聞く理由:` の書き方にも置く

### D4: `--delegated` の並び順の判定を緩める（主の確認が要る）

11/9 の 2 回目は `not-direct` で落ちた。受理させる案は 3 つある。

- 案 A（推奨）: `--delegated` に限り `not-direct` を外す。残す判定は、確認の行が主の発言であること・委任の記録より後・その前に記録の URL を書いた親の発言があること（`not-asked`）・停止の記録より前（`not-before`）。挟まった主の発言は数えない。`--relayed` は今のまま
- 案 B: 挟まった主の発言が任せる意思の語（`任せ`）を含まないときだけ通す。語の判定が増えるわりに、偽の受理を防ぐ力は案 A と大差がない
- 案 C: スクリプトは変えず、親の手順で「記録の URL を見せ直してから確認を受ける」を強める。11/9 の形の会話ログは受理されないままで、受け入れ条件を満たさない

案 A で新たに生じるリスク: 親が記録の URL を見せたあと、主が別の話で「任せる」と打った発言を委任の確認として拾いうる。G は全文から任せる意思を読むので、別の話と読める全文は今どおり落ちる。これはゲートの確かめを緩める変更（安全ゲートの弱体化）なので、PR のリスク宣言は論点ありになる。

### D5: 委任の範囲を論点の有無で引き直す

- 委任の記録の 1 行目に新しい種類 `主の委任: 論点なしの止まり` を足す。範囲の文は「このエピックの子の止まりのうち、子の停止の記録の `主に聞く理由:` が論点なしと書き、推奨と根拠があるもの。種類（リスク許容・聖域の変更・マージ・破壊的な git 操作）は問わない。論点ありの止まりと不許容は含まない」
- 既存の `主の委任: リスク許容` の記録は、種類の範囲（リスク許容だけ）を広げずに有効なままにする。ただし論点ありの止まりは、どちらの種類の記録でも効かない（受け入れ条件「委任があっても論点ありの止まりは主に上がる」）
- 委任が効く止まりの文（親・子・G が同じ文で確かめる）に、新しい種類のときの条件を足す: ④ の `推奨:` の条件に加え、`主に聞く理由:` が論点なしと書いている。リスク許容待ちのときは、最新の `## リスク宣言` が `論点なし — ` の行を持つ
- 止まりの種類ごとの送り方: リスク許容は今の委任の返事。マージ待ちは、聖域接触だけで `human-merge` が付いた PR に親が `parent-merge-approved` を付ける既存の経路（`docs/auto-merge.md`）。聖域の変更・破壊的な git 操作は `親エピック #<E> の判断（主の委任による）:` の返事で進めさせ、返事にコマンドの全文と実行の時機を書く（`destructive-git-guard.md` の「タイミングと方法まで」を返事で満たす）。hook が主の手を求めて止めたら主に上げる
- PR とエピックに残す記録: 今の `委任で送った: 子 #<N> <停止の記録の URL>` に委任の記録の URL を足す

### D6: 主の観点を論点の定義に足し、止めずに報告する

`readable.md` 節 3 と `communication-style.md` の 3 に、「運用の形・構造の分け方・将来の拡張に効く設計の分かれ目」は主の指摘が効く観点であること、扱いは主を止めず、決めた内容と他の案を報告（完了報告・親の報告）に載せることを足す。`communication-style.md` は常時注入なので 1 文に収め、予算の値は動かさない（動かす必要が出たら PR 本文に理由を書く）。

### D7: 判例の記録の契機は `epic.md` に置く

casting の SKILL.md の返信前チェックは手順 5 で判例を記録すると既に書いているが、エピックの親は手順 8 でこれを通らない。`epic.md` の手順 8 に「主に上げた件に主が答えたとき、主の聞き返し（論点は？・なぜ主に聞くか）を受けたときは、そのターンで `.claude/casting/precedents.md` に 1 判例を追記する（書式は casting の SKILL.md「判例の書き方」）」を足す。casting の SKILL.md は変えない。

### D8: 親の報告に「親の判断で通した PR・止まり」の一覧を載せる

`epic.md` の報告の形（状態表の上）に、前回の報告からあとに親の判断で通したもの（`親の判断: 子 #N 通した`・`委任で送った:`・`論点なしの確認: 通す`）を 1 件 1 行（中身と URL）で並べる節を足す。0 件なら節ごと書かない。D6 の設計の分かれ目もここに載せる。

## Risks / Trade-offs

- [論点ありを論点なしと書き誤った宣言が親か決める役の確認だけで通る] → 確認者は G と別の役で、宣言と差分だけから判定する。親の報告の一覧で主があとから見られる。聖域に触れた PR は人間のマージに残る
- [案 A で別の話の「任せる」を委任の確認と拾う] → G が全文を読む。委任の記録の範囲と期間は変えない。リスク宣言を論点ありにして主に判断を仰ぐ
- [規模超過のトリップワイヤーが実装で毎回発火する] → tasks.md のグループを return の単位にする
- [常時注入の予算を超える] → `communication-style.md` は 1 文の追加に抑え、`tests/injection-budget.bats` をグループ 5 で回す

## Migration Plan

既存の `主の委任: リスク許容` の記録とその受け取りは変えないので、進行中のエピックはそのまま動く。戻すときは PR を revert する（スクリプトの判定と文書だけで、データの移行は無い）。
