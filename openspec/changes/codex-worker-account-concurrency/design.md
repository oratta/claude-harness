## Context

`plugins/dev-workflow/scripts/codex-worker.py` は、Codex へ委譲した仕事を親プロセスから切り離して実行する台帳付きの worker である。排他は 2 箇所にある。

ひとつは台帳の中で、`submit` が `SELECT 1 FROM jobs WHERE acked=0 AND (cwd=? OR account=?)` を引き、1 件でも当たれば `cwd_or_account_locked` で拒否する（`codex-worker.py:405` 付近）。もうひとつは state-dir をまたぐグローバル予約 `reserve_global`（97 行〜）で、`~/.local/state/claude-harness-codex/ownership.sqlite` の `owners` テーブルに `account:<hash>` と `cwd:<hash>` の 2 キーを入れ、先行ジョブが TERMINAL かつ受領済みでなければ `global_account_or_cwd_locked` で拒否する。アカウント側を緩めるには、この 2 箇所の両方を変える必要がある。

アカウント側を 1 件に絞っている理由は残枠の確認にある。`quota_available`（169 行〜）が `usedPercent < 100` を要求し、`worker()` がターン開始の直前に `account/rateLimits/read` の結果をこれに渡す（297 行付近）。同じアカウントで 2 本同時に走ると、後から始まる方が読む使用率に先行ジョブの消費が入っていない。

認証プロファイルの奪い合いは理由ではない。ジョブごとに専用の `runtimes/<ジョブID>/` を作り、そこから共有の `auth.json` へシンボリックリンクを張るので、認証ファイルは書き換わらない。

## Goals / Non-Goals

**Goals:**
- 同じアカウントで、別々の作業ディレクトリの仕事を設定した上限まで同時に実行できる。
- 残枠の判定が、同時に占有されている本数を見込んでも上限を超えないものになる。
- 受領されないまま終わったジョブがスロットを握り続けたとき、それを外す手段がある。
- サーバー側が同時実行を拒否したときに、理由を残して止まる。

**Non-Goals:**
- 複数アカウントの登録・巡回・配分（親エピックの別の子）。
- 作業ディレクトリ単位の排他の変更。
- 実行中のジョブへの追加指示（`send` / steer）や、unknown からの自動復旧。
- 別ホスト・別 OS ユーザー・別 HOME をまたぐ排他（従来どおり対象外）。

## Decisions

### 上限と余裕の幅は、register 時にアカウントの属性として台帳へ入れる

`accounts` テーブルに `max_concurrent` と `quota_margin_pct` の 2 列を足し、`register` の任意引数 `--max-concurrent`（既定 3）・`--quota-margin-pct`（既定 5）で決める。既存の行は `ALTER TABLE ... ADD COLUMN ... DEFAULT` で既定値を得る。

`submit` の引数や環境変数にしなかったのは、同じアカウントに違う上限が混ざると判定が呼び出し側の裁量になるためである。環境変数は、worker が子プロセスへ渡す変数を allowlist で絞っている（`clean_env`）設計と噛み合わず、submit する側のシェルごとに値が変わる。上限は「そのアカウントで何本流してよいか」というアカウントの性質なので、アカウントの登録情報と同じ場所に置く。

### グローバル予約は、アカウントキーを 1 行からスロット N 行に変える

`ownership.sqlite` に `account_slots(account_key TEXT, slot INTEGER, ledger TEXT, job TEXT, PRIMARY KEY(account_key, slot))` を足す。作業ディレクトリ側は今までどおり `owners` の 1 行のままにする。

`owners` の主キーは `key` 単独なので、`ALTER TABLE` ではスロットを持てない。既存の `owners` を作り直すと、いま走っているジョブのロックが消える。そこで作業ディレクトリ側は触らず、アカウント側だけ新しいテーブルへ移す。移行は予約の `BEGIN IMMEDIATE` の中で行い、`owners` に `account:<hash>` の行が残っていれば `account_slots` のスロット 0 へ写して `owners` から消す。

スロットの状態は 1 つの読み取り専用の判定にまとめ、`reserve_global` と後述の占有本数の数え上げの両方がそれを使う。スロット 0 から N-1 を順に見て、次のように分類する。

| スロットの状態 | 扱い |
|---|---|
| 行が無い | 空き |
| 参照先ジョブが TERMINAL かつ受領済み | 空き（再利用してよい） |
| 参照先ジョブが queued / running / unknown | 占有中 |
| 参照先ジョブが TERMINAL だが未受領 | 占有中 |
| 参照先の台帳ファイルが無い | **占有中**（空きとして扱わない） |

確保は最初の空きスロットを取り、全部が占有中なら `account_slots_exhausted` で拒否する。台帳の中の `submit` の判定も `cwd=?` だけの拒否（`cwd_locked`）に変え、アカウント側は `reserve_global` の結果に委ねる。台帳をまたぐ作業ディレクトリの重複は `global_cwd_locked` で拒否する（現行の `global_account_or_cwd_locked` の後継。アカウント側と理由が分かれるので名前も分ける）。

参照先の台帳ファイルが無いスロットを「占有中」に倒すのは、現行コードの `require(Path(old[0]).is_file(), 'global_owner_unknown')`（`codex-worker.py:111`）からの変更点である。現行はこの状態で投入そのものを落とすが、スロットが N 個あるのに 1 個のゾンビで全部の投入が止まるのは強すぎる。一方で「台帳が無い＝実行の終わりを観測できない」なので、空きとして再利用してもいけない。占有中として飛ばすのが両方を満たす。

この分類は、台帳の `status` / `result` 照会が持つ昇格規則（30 秒以上更新の無い `queued` / `running` を `unknown` に上げる）を適用しない。分類は他の state-dir の台帳を読み取り専用で開くので、昇格させても書き戻せないためである。結果として、worker プロセスが死んだ `running` のスロットは「占有中」のまま残り、後述の `reap` でも外れない。外すには、その台帳を持つ側で `status` / `result` を引いて `unknown` へ昇格させ、既存の経路で `ack` する。書き戻しのために他の state-dir の台帳を読み書きで開く案は採らない。「各台帳は private で、その state-dir の worker だけが書く」という現行の前提が崩れ、排他の根拠が 1 つ増えるためである。仕様はこの場合に触れていないので、解放しない側（安全側）に倒す。

別の state-dir が別の上限を登録していても整合を取らない。上限が食い違えば大きい方を登録した側が多くスロットを取るが、後述の残枠判定は実際に占有されているスロット数を数えるので、超過して取られたぶんもその判定の対象に入る。硬い上限ではなく、使用率が高いときだけ効く緩い抑えである。ownership 側に上限を持たせて食い違いを拒否する案も考えたが、片方の state-dir で登録し直しただけで全部の投入が止まるため採らない。

### 残枠は「使用率 + 見込み消費率 × 同時本数」で判定する

`quota_available` が `usedPercent < 100` を要求しているのを、次の 2 段に変える。判定は primary / secondary の両方の窓に同じように掛ける。

1. `usedPercent >= 100` なら従来どおり `quota_exhausted`（既存テスト `test_exhausted_quota_never_starts_turn` の振る舞いを保つ）。
2. 100% 未満のとき、`usedPercent + quota_margin_pct * inflight <= 100` を要求する。満たさなければ `quota_headroom_insufficient` で止める。100% 到達と余裕不足を混同しないよう、理由を分ける。

`inflight` は「そのアカウントのスロットのうち、参照先ジョブが TERMINAL かつ受領済み**ではない**もの」の数で、自分を含む。上のスロット状態の表の「占有中」の行数がそのまま `inflight` になる。単にスロット行の数を数えると、完了して受領済みのスロットも数に入る（スロット行は `reap` まで残る）。3 件を完了・受領したあとの 1 件は、スロット 0 を再利用するのに行数は 3 のままなので、使用率 85% 超で止まってしまう。判定を予約と同じ分類に寄せることで、この食い違いを作らない。

受領時に ownership 側のスロット行を消して「行数＝占有数」にする案も考えたが、台帳の commit と ownership の削除のあいだで落ちるとスロットが漏れ、`reap` を打つまで戻らない。台帳を唯一の根拠にしておけば、この書き込み順の問題が生まれない。

旧版で投入されたジョブは `owners` 側にアカウント行を持つだけで `account_slots` に行が無く、占有本数が 0 と数えられうる。実装では自分を必ず 1 本と数える（`max(count, 1)`）。

既定の 3 本・5% では、使用率 85% を超えた時点で 3 本目が止まる。余裕の幅を「1 本あたりの見込み消費率」に置いたのは、ターン開始前には実際の消費量が分からないので、定数で見積もるしかないためである。開始前後の使用率の差分から実測する案は、ターンの長さと内容で大きく振れるうえ、先行ジョブの差分がまだ取れていない 1 本目に適用できない。

`quota_unknown`（窓が読めない・不正）の扱いは変えない。

### サーバー側の拒否は、エラー応答と切断を分けて扱う

現行の `worker()` は、`turn/start` を送る前に `turn_submitted = True` を立て（`codex-worker.py:308`）、その後の例外をすべて `unknown` にする（`:369`）。`Rpc.request` はエラー応答を `Rejected('rpc_error_<code>')` として投げるだけで（`:231-232`）、応答が来たのか来なかったのかを呼び出し側が区別できない。このままでは、サーバーが「受け付けない」と明示的に答えた場合まで `unknown` になり、受領も再投入もできないジョブが残る。

そこで 2 つに分ける。

- **id 付きのエラー応答**（`thread/start` / `turn/start` に対して、サーバーが明示的に拒んだ）はターンが受理されていない証拠なので `failed` にする。`Rpc.request` がエラー応答のときだけ `Rejected` の下位クラス（例 `ServerRejected`）を投げ、エラーコードを持たせる。`worker()` は `turn/start` が正常応答を返した時点でフラグ（例 `turn_accepted`）を立て、`ServerRejected` かつ `turn_accepted` が偽のときだけ `failed` にする。ターン受理後の `turn/interrupt` や `thread/read` へのエラー応答は従来どおり `unknown` で、走っているかもしれないターンを `ack` できる状態にしない。
- **切断・タイムアウト・応答なし**は従来どおり `unknown` のまま。受理されたかどうかが分からないので、`add-codex-worker` の要件「不明な実行を再投入しない」を維持する。

`error_kind` は既定で `server_rejected_start_<エラーコード>` とし、サーバーの応答をそのまま理由として残す。issue の完了条件「その理由を残して停止する」はこれで満たす。

そのうえで「同時実行が理由」と判別できたときだけ `server_rejected_concurrent_turn` に置き換える。判別規則は `CODEX-WORKER.md` に、対象のエラーコードとメッセージの一致条件として書く。**Codex app-server が同時実行を拒むときに返すコードとメッセージは、この change の時点では未確認である。** 実装時に確認できなければ判別規則は空のまま置き、全件を `server_rejected_start_<コード>` として残す（同時実行を静かに直列へ戻さないという完了条件は、コードを残す側で満たされる）。

どちらの場合も、再試行しない。別アカウントへ振り替えない。スロットは他の TERMINAL なジョブと同じく、受領されるまで保持する（証拠を残したまま次を詰め込まないため）。

### 放置されたアカウント側のスロットは `reap` コマンドで外す

`codex-worker.py --state-dir <dir> reap [--older-than <秒>] [--account <名前>]` を追加する。**外すのはアカウント側のスロットだけ**で、`owners` の作業ディレクトリ行にも台帳の `acked` にも触らない。同じ作業ディレクトリへ再投入できるようにするには、従来どおり結果を回収して `ack` する。

各スロットについて参照先の台帳を読み、次の 2 つのときだけ解放する。

- ジョブが TERMINAL かつ受領済み（`acked`）。
- ジョブが TERMINAL だが未受領で、最終更新から `--older-than`（既定 86400 秒）を超えている（`stale_unacked`）。

解放しないのは次の 3 つで、これらは理由付きで出力に載せる。

- `unknown`（実行の終わりを観測できていない）。
- `ledger_missing`（参照先の台帳ファイルが無い）。
- `not_stale`（TERMINAL かつ未受領だが、まだ `--older-than` に達していない）。

`ledger_missing` を解放理由にしなかったのは、参照先の台帳が無い状態はまさに「実行の終わりを観測できない」状態だからである。現行コードもこれを `global_owner_unknown` と名付けており（`codex-worker.py:111`）、`CODEX-WORKER.md` は「参照先喪失はunknownとして拒否する」「共有所有台帳と参照先job台帳を削除してはいけない」と書いている。これを解放理由に入れると、「台帳を消して `reap` を打つ」が unknown のロックを外す抜け道になり、`add-codex-worker` の要件「不明な実行を再投入しない」を壊す。消えた state-dir のゾンビは、スロット確保の側で「占有中」として飛ばすことで、投入全体を止めない形に留める。

`unknown` のスロットを解放したい場合は、運用者が状況を確かめたうえで当該ジョブを `ack` する（既存の契約どおり、`ack` は TERMINAL でないと通らないので、実質は状況の確認が先に要る）。

自動解放にしなかったのは、未受領のまま終わったジョブは結果が読まれていないことを意味し、時間だけを根拠に黙って捨てると結果の取りこぼしに気づけなくなるためである。明示コマンドにすれば、外した事実が実行ログに残る。

## Risks / Trade-offs

- 見込み消費率は定数の見積もりなので、実際の消費がそれを上回ると使用率が 100% に達しうる → 既定を 5% と保守的に置き、`register` で上げられるようにする。100% に達した場合の振る舞いは既存の `quota_exhausted` のままで、次のターン開始が止まる。
- 同じアカウントの 3 本が同時にサーバーへ投げるため、サーバー側の同時実行制限に当たる可能性が上がる → 当たったらエラー応答を根拠に `failed` で止め、理由をコードごと残す。黙って直列に戻さない。運用者は全件を `ack` してから `register --max-concurrent` を下げて調整する。
- 同時実行を拒むときに Codex app-server が返すコードとメッセージが未確認 → 判別できないうちは全件を `server_rejected_start_<コード>` として残す。判別規則が分かったら `CODEX-WORKER.md` の一致条件に足す。エラー応答を `failed` にする変更自体は、規則が空でも成立する。
- `ownership.sqlite` にテーブルを足し、アカウント行を移す → 移行は予約の排他トランザクションの中で行い、作業ディレクトリ側の `owners` は触らない。古い版の `codex-worker.py` を同じ HOME で併用すると、新しい版が取ったスロットを古い版が見ないので排他が壊れる。併用しない。
- 未アーカイブの change `add-codex-worker` の delta に「同じ account/cwd は別台帳からも重複実行を拒否する（MUST）」が残っており、この change の要件と正面からぶつかる → 新しい capability の要件本文に、アカウント側の扱いをこちらが上書きすると明記する。あわせて、この change をアーカイブする直前に文面を突き合わせるタスク（tasks.md の 7 章）を置き、「範囲外」で流さない。
- `reap` が外すのはアカウント側のスロットだけなので、作業ディレクトリ側のロックが残ったままだと思われうる → 要件文と `CODEX-WORKER.md` の両方に「作業ディレクトリを空けるには結果を回収して `ack` する」と書く。

## Migration Plan

1. `accounts` に 2 列を足す（既定値付きの `ADD COLUMN` なので既存の登録は動き続ける）。
2. `ownership.sqlite` に `account_slots` を作り、予約のたびに `owners` のアカウント行をスロット 0 へ写して消す。
3. 上限の既定は 3。従来どおり 1 本で運用したい場合は `register --max-concurrent 1` で戻す（ロールバック経路）。

`register` は同じアカウント名への再登録を `ON CONFLICT DO UPDATE` で受けるので、`--max-concurrent` / `--quota-margin-pct` を**省略したときは既定値で上書きする**（前の値を保たない）。spec の要件文が「そのアカウントの登録時に決めた上限」であり、登録のたびに値が確定する方が読み方が一意になるためである。前の値を保ちたい場合は毎回明示する。

ただし `register` は未受領ジョブがあると `account_has_unacknowledged_jobs` で拒否される（`codex-worker.py:388`）。走行中に上限を下げることはできず、ロールバックは全件を `ack` したあとにしか打てない。この制約は既存のもので、この change では変えない。`CODEX-WORKER.md` にもこの 2 点を書く。
