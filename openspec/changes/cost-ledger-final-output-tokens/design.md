## Context

`facts_from_lines`（`plugins/cost-ledger/scripts/cost_ledger.py`）は、同じ `requestId` の最初の行（先頭の行）から通常の事実を 1 つ作り、後続行は issue 番号か投稿の印があるときだけ、トークン 0 の補足の事実（`continuation: true`、鍵 `<requestId>#<uuid>`）にする（#695）。先頭の行の `usage.output_tokens` をそのまま事実の出力トークンにしている。

実ログを調べると、Claude Code は 1 回の応答を、書き始めたブロックごとに行へ書き、各行の `usage.output_tokens` はその行を書いた時点の値である。`stop_reason` が付く最後の行にだけ応答全体の確定値が入る。サブエージェントのログでは、先頭の行が途中の値（2〜8 など）のまま確定行との差が大きい。メインのログでは全部の行が同じ値で、ずれない。

## Goals / Non-Goals

**Goals:**
- 確定値が会話ログにある応答は、その出力トークンで額を出す
- 台帳の append-only を保つ。既存の行を書き換えない
- 既に台帳へ書いた途中の値を、会話ログが残る範囲で `--rescan` で直せる
- 直せない応答（確定値が無い）の存在と規模を README に書く
- LLM のトークンも `gh` の呼び出しも増やさず、hook を 1 秒未満に保つ

**Non-Goals:**
- 確定値が無い応答の値を推定で埋める（根拠のある値が無い。推定は #692 の「本体の値とのずれ」の側で見える）
- `cost-state` の本体の値を取り込んで合計を合わせる（セッション単位で 1 応答に割れず、台帳の事実の形に合わない）
- #692 の閾値や出力の変更
- 会話ログが既に消えた期間の補完（元データが無い）

## Decisions

### 1. 確定値は、補足の事実が持つ出力トークンの差分として足す

後続行が `stop_reason` を持ち、その `output_tokens` が、その応答について台帳に数えた出力トークン（先頭の事実の出力 + 補足の事実の出力の合計）を上回るとき、差分を `output_tokens` に持つ補足の事実を 1 つ作る。ほかのトークン 4 種は 0。鍵・`continuation`・`source_offset` は #695 のまま。同じ行が issue 番号か投稿の印を持つなら、同じ 1 つの補足の事実が持つ（行ごとに補足の事実は 1 つ）。差分が 0 以下なら補足の事実を作らない（その行に issue も印も無い場合）。

**理由**: 台帳は append-only で、先頭の行の事実は書いたら直せない。差分を持つ補足の事実なら、(a) 台帳・区間分割・集計は今の事実の列をそのまま読み、金額は出力トークンの合計から自然に出る、(b) 同期が途中で切れて先頭の行だけ台帳にあっても、確定行が後で来たときに差分だけ足せる、(c) 複製された会話ログ・複数回の読み込みでは、差分が 0 になるので増えない（冪等）、(d) すでに途中の値で書いた既存の台帳は `--rescan`（#695 の仕組み）で同じ形に直せる。

**却下した案**:
- 先頭の事実の `output_tokens` を確定値で書き換える。append-only に反し、既存の行を直せない
- 確定行が来るまで先頭の事実を台帳に書かない。Stop hook が応答の途中を読んだときに応答の事実が丸ごと遅れ、確定行が来ない応答（確定値が無い 7〜19%）は永久に台帳に出ない。応答の行が会話ログから消えるまでの間、金額が落ちる
- 後続行の `output_tokens` をそのまま足す。同じ応答で先頭の行・途中の行・確定行が全部値を持つので二重に数える

### 2. 「確定行」は `stop_reason` が付く行。値が減る行は無視する

行の `message.stop_reason` が空でない文字列のとき確定行とする（`null`・欠落・文字列以外・空文字列は確定行とみなさない。spec と同じ）。差分は `max(0, 確定行の output_tokens − 台帳に数えた出力トークン)`。1 応答に確定行が複数ある場合は、最大の値に収束する（先に小さい値、後で大きい値が来ても、差分が足されるだけ）。

**確定値が無い応答**（`stop_reason` 付きの行が無い）は、先頭の行の値のまま。推定で埋めない（調べたこと 4・5・6 のとおり、ログのどこにも確定値が無い）。ずれの規模は README に書く。

### 3. 台帳に数えた出力トークンは、台帳から作り直せる索引で持つ

差分を出すには、応答ごとに「台帳に数えた出力トークン」が要る。控え（sqlite）に応答ごとの合計を持たせる（`counted`: requestId → 出力トークン）。台帳の差分を取り込む処理（`LedgerIndex.catch_up`）が、先頭の事実の出力と、`<requestId>#<uuid>` の補足の事実の出力を、元の `requestId` に足し込む。控えを消すか台帳が縮んだときは台帳から作り直すので、台帳が正で控えは速さのためだけ（今の `ids`・`heads` と同じ）。同じ呼び出しの中の応答は、`facts_from_lines` が先頭の行の出力と、この呼び出しで足した差分を覚える。

控えの形が変わる（`counted` を足す）ので、古い形の控えは捨てて台帳から作り直す。作り直しは 1 回だけ（台帳は約 16 万行。所要時間は実測してタスク 4.2 で PR に書く）。

台帳の行から出力トークンを取り出すとき、既存の `requestId`・`uuid` の取り出しと同じく、固定の欄の順に対する文字列の読み取りを使い、読めない行だけ JSON として読む（索引を作るたびに全行を `json.loads` しない）。

### 4. 確定行は「後続行」の扱いの中で見る

後続行の絞り込み（今は文字列に `"Bash"` が無ければ読み飛ばす）に、`stop_reason` が空でない行を足す。後続行のうち `stop_reason` を持つ行だけを JSON として読むので、全履歴 1 パスの読み取りは増える。確定行は応答に 1 つなので、読む行は応答数程度に収まる。全履歴 1 パスの所要時間と hook 1 回の所要時間を変更の前後で実測する（タスク 1.2・4.2）。1 秒を超えるなら hook の経路で読む範囲を狭める。

先頭の行がすでに `stop_reason` を持つ（1 行だけの応答、メイン側の応答）ときは、先頭の事実がそのまま確定値なので、後続行に確定行が無ければ何も足さない。

### 5. 差分は確定行の位置で区間に入る

補足の事実は確定行の `timestamp` と `source_offset` を持つので、区間分割では確定行の時刻の区間に入る。確定行は応答の最後のブロック（ツール呼び出しか本文）なので、同じ応答の投稿の印と同じ行になることが多く、その場合は同じ 1 つの補足の事実が印と差分を持つ。応答の途中の行に印があって区間が切れる場合、差分は印より後の区間に入る（金額の合計は変わらない。区間に寄せる金額が応答の中でずれるだけ）。

### 6. メッセージ数・合計・`--rescan`

補足の事実はメッセージ数に数えない（#695）。出力トークンと金額の合計には足される。`ledger-sync --rescan` は索引にない補足の事実を追記する（#695 の経路）ので、途中の値で書いた既存の応答の差分も、会話ログが残っていれば追記で直る。実環境の台帳には流さず、写しで追記行数と所要時間を測って PR に書く。

## Risks / Trade-offs

- **確定値が無い応答は直らない**（サブエージェント側の 7〜19%）。本体の合計との差は残る（調べたこと 8: 残りは fable 12%・opus 6%・sonnet 5%・haiku 65%。会話ログに行を持たない呼び出しの分を含む）。haiku は確定値が無い応答が多く、改善は 3% → 35% にとどまる。README と PR に残りの規模を書き、#692 が「単価表のずれ」とみなさないようにする
- **台帳の行が増える**。補足の事実がサブエージェントの応答ごとに最大 1 行増える（今の約 16 万行に対して、複数行の応答の確定行の分）。ディスクの増加と全履歴 1 パスの所要時間は実測する
- **控えの形が変わる**。初回の 1 回だけ、台帳から作り直す
- **`--rescan` を流さないと、過去の分は直らない**。#695 と同じ手順（実行前に台帳を控え、1 回だけ流す）。会話ログが消えた期間は補えない
