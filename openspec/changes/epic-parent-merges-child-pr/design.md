## Context

主の決定（#1030「決定（主、2026-10-15）」）は、見送りラベル付きの子の PR を、マージ条件そのものに触れるものを除いて「親が合理性と危険の低さを見てマージしてよい」とした。#1030 の仕様化判断（https://github.com/oratta/claude-harness/issues/1030#issuecomment-6186181970 ）で、親は直接マージせず、自動マージの処理（`.github/workflows/auto-merge.yml`）が親の判断の印を受け取る形に決まり、その受け取り側は PR #1056（change `automerge-accepts-parent-merge-judgment`）でマージ済みになった。受け取り側の契約は次のとおり（`docs/auto-merge.md` の「親の判断」の節が正本）。

- ラベル `parent-merge-approved`（付いた瞬間にラベル即応の判定が走る）
- PR コメント。1 行目がちょうど `親のマージ判断: 可`、どこかの行がちょうど `親が見た HEAD: <今の HEAD の 40 桁 SHA>`。投稿者が OWNER・MEMBER・COLLABORATOR のものだけを数える
- 外すのは `human-merge` だけ。ほかの見送りラベル（`needs-human-merge`・`human-only`・`needs-approval`）があれば見送る。触れたパスが聖域（`SACRED`）に当たらないのに付いた `human-merge`（人が手で付けた留保）や、マージ条件そのもの（`MERGE_CONDITION`）に触れる PR は、印があっても見送る
- CI green・合格の HEAD 束縛・`AUTOMERGE_PAUSED`・SHA ピン・マージ直前の取り直しはそのまま効く

#1034（PR #1050）で、Orca 経路の親は止まった子を `epic-dispatch.sh wait --resolve` で判断し（`stop-judge.sh` が `parent-pass-criteria.md` を読む）、通せなかった止まりで `stopped` として起こされ、手順 8 で主に上げる作りになった。`parent-pass-criteria.md` は「PR のマージの可否は、この基準で通さない（#1030 の手順に任せる）」と書き、マージの承認を通らない例に置いている。

この change で決めるのは、親がマージ待ちの子にいつ気づき、何を見て、どう印を付けるか（とその基準のファイル）、子がそのとき何をするか。

制約:
- epic-dispatch.sh、develop の SKILL.md の手順 2・手順 8・子の側の「親から届いた返事」の行は変えない（エピック #1038 の他の子が並行して動いているため。親エピックの注意書き https://github.com/oratta/claude-harness/issues/1054#issuecomment-6205337297 ）
- 子の側の「親から届いた返事」の行は、`親エピック #<E> の判断（主の承認ではない）:` を聖域の変更や破壊的な操作の承認として扱わないと定めている。マージ待ちの子の PR は聖域に触れているので、親の返事が子に何かを承認させる形にはできない
- LLM が `gh pr merge` や merge API を直接叩くのは禁止（`docs/auto-merge.md`・`rules/git-commit-policy.md`・`ci-watch.md`）。この change はそれを変えない

## Goals / Non-Goals

**Goals:**
- `human-merge` だけで止まった子の PR を、親が基準に照らして判断し、通してよいものは主の手を使わずに自動マージの処理へ回す
- 親の判断が誤っても、マージ条件そのものに触れる PR と、判断のあとに push されたコミットは、処理の側の判定でマージされない状態を保つ
- 判断できないものは、今までどおり手順 8 の形で主に上げる

**Non-Goals:**
- epic-dispatch.sh の変更（マージ待ちを別の出力で返すなど）
- `human-merge` 以外の見送りラベルを親の判断で外すこと（受け取り側が外さない）
- エピックに属さない単発の PR のマージ（gene 側。#1030 の範囲外）
- 原本を使う他のリポへの展開し直し
- `stop-judge.sh` と `parent-pass-criteria.md` の変更

## Decisions

### 1. 親が気づく経路は、既存の「子の停止」と手順 8 の `stopped` に乗せる

子はゲート合格後の見張り（`ci-watch.md`「`ready` を受けたあと」の 1）で見送りラベルが `human-merge` だけのとき、主に直接頼む代わりに、既存の「エピックの子が主の返事を待って止まるとき」の記録を `止まった理由: PR のマージ待ち（human-merge）: <PR の URL>` で残して `mark stopped` で止まる。`wait --resolve` の判断はマージを通さないので、親は既存の `stopped` で起こされる。親は手順 8 で主に上げるどちらの経路（一致する `親の判断:` が無いとき、と、それ以外）でも、報告の前に、記録の `止まった理由:` が `PR のマージ待ち（` で始まる子についてこの change の手順を行う（手順 8 の文は変えず、Orca 経路の手順のあとに段落を足す）。

代わりの案:
- epic-dispatch.sh の `wait` にマージ待ちの出力（例 `merge-wait <N>`）を足す → epic-dispatch.sh を変えることになり、並行する子（#1043・#1045・#1055）と同じファイルを触る。`stop-judge.sh` の空振り 1 回分の費用を減らせるだけで、気づく早さは変わらない
- 親が動いている子の PR のラベルを定期的に見に行く → 親が起きている間しか見られず、待ち方（背景の `wait` で起こされる）と合わない

採った形で受け入れること: マージ待ちの止まり 1 件ごとに `stop-judge.sh` のモデル呼び出しが 1 回空振りする（主に上げる側に倒れることが基準に書かれているので、結果は変わらない）。`stop-judge.sh` が誤って「通す」と判断した場合、子には判断の返事が届くが印は付いていないので、子の `wait --until-merged` は上限時間で `timeout` になり、子は改めて止まる（下の 5）。親は印が無いので通常どおり判断する。マージはされない側に倒れる。

### 2. 親は機械で見られる前提を先に確かめ、残りを決める役に判断させる

親は決める役を起こす前に、次を `gh` で確かめる。どれかを満たさなければ決める役を起こさずに手順 8 の形で主に上げる。

- 対象リポの PR の base ブランチの `.github/workflows/auto-merge.yml`（`gh api "repos/<owner>/<repo>/contents/.github/workflows/auto-merge.yml?ref=<PR の base ブランチ>" --jq .content | base64 -d`） に `parent-merge-approved` の語がある（原本を展開し直していないリポでは印が効かないため）
- PR が open で、付いている見送りラベル（`human-merge`・`needs-human-merge`・`human-only`・`needs-approval`）が `human-merge` だけ
- 記録の PR の本文で最初に現れる `Closes #N`・`Fixes #N`・`Refs #N` の `N` が子 issue の番号である（ほかの issue の PR を取り違えて印を付けないため）
- PR に、今の HEAD を `親が見た HEAD:` に持つ `親のマージ判断: 可` のコメントがまだ無い（あるのにマージされていないなら、自動マージの処理の側が止めている。緊急停止・CI・マージ条件のパスなど。親が同じ判断を繰り返さず、`docs/auto-merge.md` の「親の判断の印を付けたのにマージされないとき」の調べ方を添えて主に上げる）

そのうえで `subagent_type: dev-workflow:decider` を起こし、`parent-merge-criteria.md` で判断させる。決める役は `Bash` を持たないので、親が次を集めて入力文に貼る: エピックの本文、子 issue の本文と OWNER・MEMBER・COLLABORATOR の `親エピックからの注意書き:`、子の停止の記録、PR の本文とラベルと今の HEAD の SHA、PR の変更ファイルの一覧と差分（`gh pr diff`）、PR のリスク宣言・動作確認・ゲートのコメント、CI の結果（`gh pr checks`）、取得した `auto-merge.yml` の `# >>> sacred-paths` 〜 `# <<< merge-condition-paths` の行（聖域とマージ条件そのもののパスの正規表現）、PR のコメントのうち自動マージの処理が `human-merge` を付けた旨の投稿（`🔒 **auto-merge 対象外（聖域パス接触）**` で始まるもの）、あれば配役表。差分が大きすぎて貼れないときは変更ファイルの一覧だけを貼り、決める役が `不足:` を返したら主に上げる。

判断を親自身にさせないのは、マージの可否が決める役の仕事（`rules/subagent-model-selection.md`）で、親の大きな文脈を使わないため（#1030 の仕様化判断）。

### 3. 基準は別ファイルにし、条件名と「迷ったら主に上げる」を `parent-pass-criteria.md` にそろえる

`parent-merge-criteria.md` の 6 条件（すべて満たすときだけ `裁定: 可`）:

| 条件 | 中身 | `parent-pass-criteria.md` との対応 |
|---|---|---|
| 見送りが聖域接触だけ | 見送りラベルが自動マージの処理が付けた `human-merge` だけで、変更ファイル（rename 元を含む）がマージ条件そのもののパスに触れていない | 「聖域でない」をマージ用に置き換えたもの |
| ゲートが今の HEAD で済んでいる | `agent-review:passed` と、今の HEAD の宣言・証拠のコメントがあり、CI が green | 「既存の規則が主に聞く止まりでない」 |
| 主の側の情報が要らない | リスク宣言が「リスクなし」か、主の許容が今の HEAD について記録済み | 同名 |
| 範囲の内側 | 差分が子 issue の受け入れ条件とエピックの目的を広げず、逆向きにもしない | 同名 |
| 戻せる | revert PR で元に戻り、マージから戻すまでの間にリポジトリの外へ戻せない作用（外部公開・送信・課金・データ削除・秘密情報）が出ない | 同名 |
| 配役表で主の観点が無い | 配役表が渡されたとき、この変更に要る観点の担い手が主でない | 同名 |

出力は 1 行目 `裁定: 可`・`裁定: 否`・`不足: <足りないもの>` のどれか、2 行目 `理由: <1 行>`。`agents/decider.md` の「verify・マージ可否で呼ばれたときは可否と根拠を返す」を、この基準の中で行の形に固めたもの。形が崩れた出力は可として扱わない（主に上げる）。

別ファイルにする理由: `parent-pass-criteria.md` は `stop-judge.sh` がそのまま読むプロンプトで、「マージはこの基準で通さない」と定めている。マージの条件を同じファイルに足すと、止まりの判断がマージを通す側に倒れうる。

### 4. 印はコメント → ラベルの順に、判断した HEAD に結びつけて付ける

`裁定: 可` を受けたら、親は PR の今の HEAD（`gh pr view --json headRefOid`）を取り直し、決める役に渡した HEAD と一致することを確かめる。一致しなければ印を付けずに主に上げる（判断していないコミットを入れないため。受け取り側の `親が見た HEAD:` の一致でも止まるが、空の印を残さない）。

一致したら、次の順に行う。

1. PR に判断のコメントを投稿する（1 行目 `親のマージ判断: 可`、2 行目 `親が見た HEAD: <40 桁 SHA>`、3 行目 `理由: <決める役の理由>`）
2. PR に `parent-merge-approved` ラベルを付ける。ラベルが付いた瞬間にラベル即応の判定が走るので、コメントを先に置く（逆だと最初の判定が印を数えず、次のきっかけまで待つ）
3. `epic-dispatch.sh reply --as parent <エピック番号> <N> <返事>` で子に伝える。返事は「PR を自動マージの処理に回した。`ci-watch.sh wait --until-merged` で見届ける。子は何も承認せず、マージも印も付けない」の趣旨
4. エピックに `親の判断: 子 #N マージに回した — <理由> <PR の URL>` の 1 行を残す。語を `通した` にしないのは、`stop-judge.sh` が同じ子への過去の `親の判断: 子 #N 通した` を「繰り返していない」の判定に使うため（マージに回した件を止まりを通した件と数えさせない）

`reply` が `failed` を返したら、印は付いたままでよい（マージされても子は `closed` で検知される）。主に報告する。

子が直しで push して HEAD が変わったら、古い印のコメントは処理に数えられない（`親が見た HEAD:` が一致しない）。ラベルは残っても害が無いので外さない。子は取り直したゲートの合格後に再び止まり、親が新しい HEAD で判断し直す。

### 5. 子は親の返事を承認として扱わず、見届けるだけにする

子の側（`ci-watch.md`）は、親から返事が届いたら `ci-watch.sh wait --until-merged` を起動して見届ける。結果の扱いは既存の 4 の表のまま（`merged` で見張りを終える、`settled` は `next` に進む、`timeout` はマージされなかったとして主に頼む＝エピックの子なので改めて子の停止の記録を残す。このときの `止まった理由:` は `PR のマージ待ち（human-merge、親の返事のあともマージされない）: <PR の URL>` とする。印の有無は子からは断定しない。親の側では 2 通りに分かれる: 今の HEAD の判断のコメントがあれば、2 の前提の「判断のコメントがまだ無い」を満たさないので主に上げる（自動マージの処理の側が止めている）。無ければ（`stop-judge.sh` が誤って通し、印が付かないまま返事だけが届いた経路）、通常どおり前提を確かめて決める役に判断させる）。子は `parent-merge-approved` ラベルも `親のマージ判断:` のコメントも付けない。親の返事は聖域の変更や破壊的な操作の承認ではなく、子はその返事で聖域のファイルを変えたりマージしたりしない。見届けることは承認を要しないので、子の側の「親から届いた返事」の行と矛盾しない。

対象はエピックの子のセッション（`epic-dispatch.sh route` が `nested`）で見送りラベルが `human-merge` だけのときに限る。ほかの見送りラベルがあるとき、エピックの子でないとき、PR の base ブランチの `auto-merge.yml` に `parent-merge-approved` の語が無いときは、今までどおり PR の URL を添えて主にマージを頼む（エピックの子なら頼み方が子の停止の記録になるのは既存の規則どおり）。

### 6. 仕様の差分は、既存の要件の書き換えと新しい要件で書く

- dev-workflow-develop「エピックの条件・作り方・回し方・完了条件を規定する」は、最後の文「本体が自動でマージしてはならない（MUST NOT）」と、シナリオ「Orca 経路の本体は wait の出力で次を決める」の「子の PR を本体が自動でマージしないこと」だけを書き換える（MODIFIED。ほかの文は main の今の文のまま写す）
- 親の手順と基準のファイルは、新しい要件 2 つとして足す（ADDED）。親の手順の要件は、要件「Orca 経路の親は止まった子を解決し、解決できないものを主に分かる形で上げる」の「それ以外は主に上げる」に、マージ待ちの子について優先すると書く
- dev-workflow-ci-watch は、既存の「CI の見張りの手順は共有 reference に 1 本置く」を書き換えず、エピックの子の場合に限ってその見送りラベルの扱いに優先する要件を足す（ADDED。#1050 が `--resolve` のときだけ既存の規定に優先すると書いた形と同じ）

## Risks / Trade-offs

- [親の判断が誤ってマージされる] → マージ条件そのものに触れる PR、判断のあとに push されたコミット、CI が赤い PR は受け取り側が止める。残るのは聖域（`rules/`・`CLAUDE.md`・hooks など）のうちマージ条件でないファイルの変更で、主の決定でこれは親に任された。戻すのは revert PR
- [子が自分で印を付ける] → 技術的には止められない（#1030 で主が受け入れた）。`ci-watch.md` と SKILL.md に、印を付けるのは親だけと書く
- [並行する子との衝突] → dev-workflow-develop の書き換える要件は大きく、#1043（手順 6）など並行する子も同じ要件を MODIFIED で書き換えうる。archive は要件の塊ごと置き換えるので、後から archive する側は main の今の文に自分の差分を載せ直してから archive する（tasks に入れる）
- [`stop-judge.sh` の空振り] → マージ待ち 1 件ごとにモデル呼び出し 1 回。受け入れる
- [`epic-dispatch.bats` の 1 行] → 既存の検査が SKILL.md の「自動でマージしない」を見ているので、その 1 行だけを新しい文に差し替える（epic-dispatch.sh は変えない）。並行する子も同じ bats に検査を足しうるが、行が離れていれば衝突しない

## Migration Plan

1. この PR は `plugins/dev-workflow/skills/develop/SKILL.md` などに触れるが、マージ条件そのもののパス（`.github/workflows/`・`plugins/dev-workflow/skills/pr-review-gate/`・`plugins/dev-workflow/templates/auto-merge/`）には触れない。聖域に触れるかは自動マージの処理の判定に任せる
2. マージ後、次に起動・再開されたエピックの親と子から新しい手順が効く。動いている子のセッションは起動時の手順書を読んでいるので、マージ前に始まった子は今までどおり主に頼む
3. 戻すときは revert PR で戻す。戻したあとは、子は主に直接頼み、親は印を付けない
