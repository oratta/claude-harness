## Requirements

### Requirement: 主に問いを返す文章の書き方の正本は readable.md の節 3 に置く

`output-styles/readable.md` の「3. 判断を求めるときは」の節は、主に判断・確認・操作を求める文章の書き方の正本でなければならない（MUST）。節は次を含まなければならない（MUST）。

- 次の 6 段の順で、1 文に 1 つのことを書く: ①質問 ②主に聞く理由（1 文） ③いま困っていること（主が見て分かる現象で） ④推奨と根拠（何を基準に決めたかが分かる形で） ⑤受け入れるリスク ⑥答え方（区切りより上の本文の最後に置く）
- 主に聞く理由として成り立つのは次の 3 つだけ。どれにも当たらなければ聞かずに自分で決めて進め、事後報告する
  - 主の側にしか答えが無い（好み・事業判断・どこまでの被害を許せるか）
  - 決まりで主の承認が要る（聖域・取り消せない操作）。その決まりが何を守るためかまで書く
  - 主の手でしかできない操作（MFA・ログイン・人が押すと決まっているマージ）
- 受け入れるリスクは 3 つの要素で書く: 何が起きるか（被害の大きさ・戻せるか）／どれくらい起きるか（起きる条件と頻度。確かめたのか見込みかの別）／分からないときは「分からない」と書き、何を調べれば分かるかを添える
- 1 通で聞くのは 1 件
- issue・PR の番号で物を指さず（主語かどうかを問わない）中身で書き、番号は末尾の URL にだけ置く
- 背景の詳しい説明と元の記録の URL は、区切って下に置く（読まなくても答えられる位置）
- 確認作業の細部（テストの件数・レビューの周回）は書かず、「確かめ済み」とリンクで足りる
- 例を 3 つ置く: 論点ありの例を 1 つ（質問・主に聞く理由（論点）・推奨と根拠・受け入れるリスク・答え方が見える短いもの（目安 600 バイト前後）。主の困りごとが無いので困りごとの段は置かない）と、論点なしの例を 2 つ（要件「論点の無い確認は 3〜4 行に収める」のとおり）
- 「主」（この会話で判断を下す人間のオーナー）と「聖域」（人の承認なしに変えてはならない設定や決まり）には、初出で一言の言い換えを添える
- どの理由に当たるかの判定は条件つきで指す: 観点の配役（`casting:casting`）が入っていれば、判定の詳細と、主に上げる前の相談の手順はその返信前チェックに従う。入っていなければ、上の 3 つの理由だけで判定する

`output-styles/readable.md` は、要件「配る候補の規則は環境固有の記述を持たず、プラグインの前提を条件つきにする」（`harness-public-private-split`）の対象の 6 ファイルの 1 つなので、この節（例を含む）もその制約に従わなければならない（MUST）。固有名とオーナーの環境のパスを書かず、Harness のプラグインに触れる文は「入っていれば」の条件つきで書く。

旧い型（目的 → いま取り組んでいる場所 → 起きた事実 → 決めてほしいこと → 推奨とリスク）と、「結論はA。ただしAは…これを飲めるならAで進める」の形式は、節に残してはならない（MUST NOT）。

この要件の守備範囲は、正本の節が上の決まりを持つことである。個々の発言が型を守っているか、推奨が正しいかは、この要件では止めない。

#### Scenario: 正本の節が 6 段と 3 つの理由を持つ
- **WHEN** `output-styles/readable.md` の節 3 を読む
- **THEN** 質問 → 主に聞く理由 → いま困っていること → 推奨と根拠 → 受け入れるリスク → 答え方の順、主に聞く理由の 3 つ、どれにも当たらなければ聞かずに進めて事後報告すること、リスクの 3 要素、1 通 1 件、番号で物を指さないことが書かれ、論点ありの例が 1 つと、論点なしの例が 2 つある

#### Scenario: 観点の配役への言及が条件つきで、配る候補の制約に従う
- **WHEN** `output-styles/readable.md` の `casting` を含む行を読み、6 ファイルを `grep -n -i -E 'oratta|genetta|suimei|flatmate|fmtoken|Dropbox|marketplaces/'` で検索する
- **THEN** `casting` を含む行に「入っていれば」があり、検索は 0 件である

#### Scenario: 旧い型が残っていない
- **WHEN** `output-styles/readable.md` を `目的 → いま取り組んでいる場所` と `これを飲めるならAで進める` で検索する
- **THEN** どちらも見つからない

### Requirement: 主への発言の 1 行目の書き分けを正本で 1 か所に決める

`output-styles/readable.md` の節 3 は、主への発言の 1 行目を次のとおり書き分けると決めなければならない（MUST）。

- 判断・確認・操作を求める発言は、1 行目を質問にし、区切りより上の本文の最後の行を答え方（どこで何を打つ・押すか）にする
- 主の操作も判断も要らない報告は、1 行目を `主がすること: なし` にする

ほかの文書は、1 行目の決まりを自前で定めてはならない（MUST NOT）。この決まりを参照し、その場所に固有の事柄（答え方の行に書く返事の場所・条件）だけを書く。`主がすること: <どこで> <何を>` の形は、どの文書にも残してはならない（MUST NOT。変更の記録 `changes/` と `openspec/changes/archive/` は除く）。子の完了報告の 1 行目（`主がこのセッションで次にすること:`）は、この要件の対象外とする。主の質問に答える発言も対象外で、節 3 はそのことを 1 文で書き、節 4（結論から書く）のとおり 1 行目に答えを書くと示さなければならない（MUST）。

#### Scenario: 書き分けが正本にある
- **WHEN** `output-styles/readable.md` の節 3 を読む
- **THEN** 判断・確認・操作を求める発言は 1 行目が質問で最後が答え方、操作も判断も要らない報告は 1 行目が `主がすること: なし`、と書かれている

#### Scenario: 他の文書に自前の 1 行目の形が残っていない
- **WHEN** `plugins/` と `rules/` を `主がすること: このチャンネルで`・`主がすること: PR #`・`主がすること: 親のタブで`・`主がすること: 子のタブで`・`主がすること: <どの画面` で検索する（`changes/` と `openspec/changes/archive/` は除く）
- **THEN** どれも見つからない

### Requirement: 短い版は正本の要点を持ち、正本と矛盾しない

`rules/communication-style.md` の 3 番目は、正本の要点を持たなければならない（MUST）。要点は次のとおり: 6 段の順、主に聞く理由の 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作）と理由が無ければ聞かずに進めること、主に聞く理由に論点の有無を書くこと（論点の定義は 1 文目だけでよい）、リスクは被害と頻度（分からなければその旨と調べ方）で書くこと、1 通 1 件、1 行目の書き分け。例は置かず、例と詳細は正本にあると案内する（MUST）。短い版は正本と矛盾してはならない（MUST NOT）。`rules/communication-style.md` も配る候補の 6 ファイルの 1 つなので、同じ制約（固有名とオーナーの環境のパスを書かない・プラグインには条件つきで触れる）に従う（MUST）。

#### Scenario: 短い版に順と理由が残る
- **WHEN** `rules/communication-style.md` の 3 番目を読む
- **THEN** 質問 → 主に聞く理由 → 困りごと → 推奨と根拠 → リスク（被害・頻度） → 答え方の順、主に聞く理由の 3 つ、理由が無ければ聞かずに進めること、論点の有無を書くことが書かれ、旧い 5 段の順と「これを飲めるならAで進める」は無い

### Requirement: 主に問いを返す各所は正本を参照し、固有の事柄だけを残す

次のファイルは、問いの書く順やリスクの書き方を自前で決めた文を持ってはならない（MUST NOT）。正本（`output-styles/readable.md` の節 3。サブエージェント向けには `rules/communication-style.md` の 3 番目）を参照し、その場所に固有の事柄（記録の書式・投稿先・URL の添え方・返事の場所）だけを残す（MUST）。正本を指すパスは、リポジトリの外からも辿れる形 `~/.claude/output-styles/readable.md`（Output Style `readable`）で書かなければならない（MUST）。リポジトリ相対パス（`output-styles/readable.md` だけ）で指してはならない（MUST NOT。プラグインは他のリポジトリから読まれるので、リポジトリ相対パスは辿れない）。

### Requirement: 主に聞く理由に論点の有無を書く
`output-styles/readable.md` の節 3 と `rules/communication-style.md` の 3 番目は、どちらも論点の定義と書き分けを持たなければならない（MUST）。

- 論点の定義: 主が持っていて自分（エージェント）が持っていない観点を足すと結論がよくなる点。判断材料が自分の側にあるもの（コードや設定の細部、長い背景説明が要るもの）に論点は無く、自分で決める
- 書き分け: 論点ありなら論点を書く。論点なし（決まりで聞いている）なら、推奨どおりでよい旨と、その決まりが何を守るためかを書く

短い版 `rules/communication-style.md` は、論点の定義の 1 文目だけを持てばよい（MAY。除外の 2 文目は正本にだけ置く。常時注入の予算のため）。

#### Scenario: 両方の文書に論点の定義と書き分けがある
- **WHEN** `readable.md` の節 3 と `communication-style.md` の 3 番目を読む
- **THEN** どちらにも論点の定義と、論点あり／論点なし（決まりで聞いている）の書き分けが書かれている

### Requirement: 主への確認の 1 行目・困りごと・リスクは中身で書き、作文しない
`output-styles/readable.md` の節 3 と `rules/communication-style.md` の 3 番目は、どちらも次を持たなければならない（MUST）。

- 1 行目は、OK すると何が起きるかを中身で書いた質問にする。手続きの言葉（「リスク宣言を許容するか」）で聞かない
- issue・PR の番号で物を指さない（主語かどうかを問わない）。番号は末尾のフル URL にだけ置く
- 困りごとは、止めているのが自分の側だけで主の困りごとが無いときは書かない
- 受け入れるリスクは、推奨を選ぶことで新たに生じるもの（他の案や何もしない場合には無いもの）だけを書く。どの変更にも当てはまるもの（「見落としがあると壊れる」）は書かない

#### Scenario: 両方の文書に 1 行目・困りごと・リスクの決まりがある
- **WHEN** `readable.md` の節 3 と `communication-style.md` の 3 番目を読む
- **THEN** どちらにも、1 行目の質問・番号を末尾の URL にだけ置くこと・困りごとが無いときは書かないこと・新たに生じるリスクだけを書くことが書かれている

### Requirement: 論点の無い確認は 3〜4 行に収める
`output-styles/readable.md` の節 3 と `rules/communication-style.md` の 3 番目は、論点なしの確認を 3〜4 行（質問・論点なしの旨と決まり・推奨・答え方）に収めると書かなければならない（MUST）。3〜4 行は区切りより上の本文の行数で、記録の URL・返事の渡し方の補足・満たさなかった条件は、答え方の行に畳むか区切りの下に置く。正本の節 3 は、2026-10-22 の実例 2 つ（ゲートの決まりでトークンの扱いを変える PR の OK を求めた確認、エピックの親が子の PR の許容を求めた報告）を論点なしの形で書き直した例を持ち、どちらも 4 行以内でなければならない（MUST）。

#### Scenario: 実例の書き直しは 4 行以内
- **WHEN** 節 3 の「論点なし。実例」と見出しの付いた例を数える
- **THEN** 2 つあり、どちらも 4 行以内である
