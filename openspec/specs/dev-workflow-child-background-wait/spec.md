# dev-workflow-child-background-wait Specification

## Purpose
エピックの nested の子の本体が自分の背景作業を長時間待つとき、作業を失わずに会話キャッシュを維持し、記録から再開できる外部依存は既存の停止と再起動に渡すための契約を定める。

## Requirements

### Requirement: 長い待ちの入力判定の守備範囲を共有する

長い待ちの入力判定は次の守備範囲に従わなければならない（MUST）。①入力元は本体の現行 CLI 会話の usage・リクエスト時刻、保持した元作業とタイマーの task ID・届いた通知、依存登録・途中経過・再開条件の保存結果。②拾う誤りは他セッションの usage や不明な TTL の流用、書込時刻と成功リクエスト時刻の混同、文字列一致・別 ID・失敗通知による自己通知成功や元作業完了の誤認、未確認・失敗した依存登録や保存の成功扱い、子所有の実行中作業や親が扱えない条件を残した停止。③通してよい例は、最後の有効な書込が 1h で、その後の 5m 切替が次の観測まで現れない usage。この値での判定は許すが miss を防げたと報告しない。保持したタイマー ID と成功終了が一致する通知も維持通知として通すが、元作業の完了根拠にしない。④観測できない TTL 切替やスリープによる miss の完全防止、判定の穴を塞ぎ切ることは完了条件にしてはならない（MUST NOT）。

#### Scenario: 観測後の TTL 切替は維持の保証にしない
- **WHEN** 現行会話の最後の有効な書き込みは 1h だが、その後の 5m への切替はまだ usage に現れていない
- **THEN** 本体は観測時点の値で待ち方を判断してよいが、miss を防げたと断定せず、次の観測で判明した TTL に従う

### Requirement: 子の本体は長い待ちの前に再開可能性を確認する

nested の子の本体は、自分の作業者・CI・Monitor・Codex コマンドを 60 分以上待つ見込みになったら、待ちを開始または延長する前に専用手順を読まなければならない（MUST）。記録から再開できる外部依存と、セッションを保持する必要がある実作業の待ちを区別しなければならない（MUST）。判定の守備範囲は「長い待ちの入力判定の守備範囲を共有する」に従う。

#### Scenario: 見込みが途中で長くなる
- **WHEN** 当初短時間の見込みだった作業者の待ちが延び、全体で 60 分以上になりうる
- **THEN** 本体は既に待っているという理由で手順を省かず、次の長い待ちに入る前に扱いを確認する

#### Scenario: worker は本体のタイマーを起動しない
- **WHEN** 委譲された worker が自分の長時間コマンドを待つ
- **THEN** worker は従来のサブエージェント用の待機契約に従い、本体用の自己通知を起動しない

### Requirement: 再開可能な外部依存は既存の停止手順へ移す

別 issue・PR の完了待ちが既存の依存待ちで表せ、子が所有する実行中作業が残らないなら、本体は依存登録・途中経過・再開条件を既存手順で保存し、親の待ち受けに渡して終了しなければならない（MUST）。保存に失敗した状態や、親が扱えない監視条件を移行成功と扱ってはならない（MUST NOT）。判定の守備範囲は「長い待ちの入力判定の守備範囲を共有する」に従う。

#### Scenario: 日単位の別 issue 待ち
- **WHEN** 別 issue の完了が前提で、その条件を既存の依存待ちで表せ、実行中の子所有作業が無い
- **THEN** 子は blocked_by と保存結果を確認して依存待ちの形で終了し、Monitor や自己通知を維持し続けない

#### Scenario: 自分の CI の途中では外部依存に偽装しない
- **WHEN** 自分の PR の CI 見張りが実行中、または元作業を失わずに移せると確認できない
- **THEN** 子はセッションと実行 ID を保持し、自分自身への依存登録や未確認の親への委譲で終了しない

### Requirement: 実作業の待ちは一時間キャッシュを確認して維持する

セッションを保持する子の本体は、自分の現行会話の TTL が 1h、最後の成功リクエストから 3600 秒未満と確認でき、既存の待ちが 45 分以内に本体へ返らない場合に、45 分の有限な自己通知を一つだけ用意しなければならない（MUST）。最初のタイマーを置いた時刻をその待ちの基点として保持し、同じ待ちの再設置で更新してはならない（MUST NOT）。維持の上限はこの基点から12時間とする。本体へ制御が戻らない前景呼び出しやツールが使えない環境で維持を保証してはならない（MUST NOT）。判定の守備範囲は「長い待ちの入力判定の守備範囲を共有する」に従う。

#### Scenario: 大きい会話の agent 待ち
- **WHEN** 会話 20 万トークン、TTL 1h の nested 本体が、60 分を超えうる実行中の agent を保持して待つ
- **THEN** 停止済み子の 150k の除外条件を流用せず、本体自身の有限な自己通知を使い、元の agent を終了・再起動しない

#### Scenario: 既存の期限通知を利用する
- **WHEN** Monitor の期限や有限の前景コマンドが 45 分以内に本体へ返り、次のモデルリクエストが発生する
- **THEN** その通知や返りを利用し、同じ待ちに追加のタイマーを重ねない

#### Scenario: 再設置で維持の基点を延ばさない
- **WHEN** 同じ元作業を待つ間に自己通知を受け、次のタイマーを置く
- **THEN** 最初のタイマーを置いた時刻を保持し、12時間の計測をその再設置時刻からやり直さない

### Requirement: 自己通知と元作業の決着を区別する

自己通知は起動時に保持した ID と成功した終了で識別しなければならない（MUST）。受信では元の作業が未完了で現在も維持対象、かつ最初のタイマーを置いた時刻から12時間未満の場合だけ次の一回を用意しなければならない（MUST）。12時間以上なら次のタイマーを置かず、元作業と実行IDを保持して完了通知を待ち続け、届いたときに一度の書き直しを受け入れなければならない（MUST）。上限到達を理由に元作業を捨てたり止めたりしてはならない（MUST NOT）。自己通知では通常の調査・実装・投稿・停止状態の変更を行ってはならない（MUST NOT）。通知だけで工程完了、CI 決着、Codex 委譲成功を宣言してはならない（MUST NOT）。判定の守備範囲は「長い待ちの入力判定の守備範囲を共有する」に従う。

#### Scenario: CI がまだ実行中の維持通知
- **WHEN** 本体の自己通知が成功し、元の CI wait は未完了で、最初のタイマーから12時間未満かつ現在も維持対象である
- **THEN** 本体は CI の途中出力を読まず、別の CI wait を起動せず、CI の timeout や settled と解釈せず、キャッシュ維持に必要な待ち直しだけを行う

#### Scenario: 通知の文字列が一致しても別作業
- **WHEN** 別タスクの出力や引用が自己通知と同じ文字列を含むが、保持した ID と一致しない
- **THEN** 自己通知とみなさず、元の作業の通知として従来の処理へ渡す

#### Scenario: 12時間に達した通知では再設置しない
- **WHEN** 自己通知を受け、元作業は未完了だが最初のタイマーから12時間に達している、または12時間を超えている
- **THEN** 現在の TTL が 1h でも次のタイマーを置かず、元作業と実行IDを保持し、元作業の完了通知を待ち続ける

#### Scenario: 上限後に元作業の完了通知が届く
- **WHEN** 12時間上限により維持を終えたあと、キャッシュが切れてから元作業の完了通知が届く
- **THEN** 一度の書き直しを受け入れて元作業の結果を回収し、キャッシュのために作業を停止・再起動せず、維持タイマーも再開しない

### Requirement: 元作業の通知を優先して自己通知を終了する

本体は元作業の通知と主・親からの入力を自己通知より優先し、作業の回収・停止への移行・終了の前に自分のタイマーだけを取り消さなければならない（MUST）。取り消し後や待ちの終了後に届いた遅い通知から新しいタイマーを作ってはならない（MUST NOT）。起動や取り消しの失敗を維持成功や作業完了と報告してはならない（MUST NOT）。判定の守備範囲は「長い待ちの入力判定の守備範囲を共有する」に従う。

#### Scenario: 作業の完了とタイマーが競合する
- **WHEN** 元作業の完了通知と自己通知が同時に届く
- **THEN** 本体は元作業の結果を先に回収し、その待ちが終われば自己通知を再設置しない。止めるのは自分のタイマーだけである

#### Scenario: 主の返事待ちへ移行する
- **WHEN** 実作業の結果を受けて主の承認が必要になった
- **THEN** 本体は自分のタイマーを取り消してから既存の停止手順へ渡し、既存の停止済み子への声かけと二重に維持しない

### Requirement: 五分キャッシュや期限切れでは維持成功を仮定しない

TTL は本体の現行 CLI 会話の最後の有効な書き込みから確認し、書き込み時刻と最後の成功リクエスト時刻を区別しなければならない（MUST）。5m または不明なら維持用の自己通知を置かず、五分ごとの声かけや TTL の強制変更を行ってはならない（MUST NOT）。期限切れでも実行中の作業をキャッシュのためだけに捨ててはならない（MUST NOT）。判定の守備範囲は「長い待ちの入力判定の守備範囲を共有する」に従う。

#### Scenario: 他セッションの TTL は使わない
- **WHEN** 親や作業者の usage は 1h だが、本体の現行会話は 5m または不明である
- **THEN** 本体は自己通知を起動せず、元の作業の完了待ちを続ける

#### Scenario: スリープや TTL 切替で miss が起きる
- **WHEN** スリープで 60 分を過ぎる、または overage 等で観測後に 5m へ切り替わる
- **THEN** 最初の書き直しを防げたと報告せず、実行中の元作業を保持し、新たに観測した TTL とリクエストを基点に待ち方を判断する

### Requirement: 維持用の通知は停止済み子の予約文と分離する

本体の維持用通知に停止済み子の予約文を自己送信してはならない（MUST NOT）。ScheduleWakeup を背景作業の完了の代用として使わず、維持のために新しい loop・Cron・Monitor の監視を作ってはならない（MUST NOT）。既存 CI wait の結果分類、停止済み子の声かけの共有正本、Codex の起動契約を変更してはならない（MUST NOT）。

#### Scenario: 元作業の実行方法を保つ
- **WHEN** 既存の CI・Monitor・前景またはホストが背景に回した Codex コマンドがある
- **THEN** 本体はその実行 ID と結果の契約を保ち、キャッシュ維持のために ScheduleWakeup や予約文で実行結果を代替しない

### Requirement: 費用の見積もりと実機確認を分けて記録する

実装前に、会話 20 万トークンの再書き込み・維持・停止と再起動の費用、単価の根拠、選択と理由を #1743 に記録しなければならない（MUST）。12時間上限を反映した比較を新しいコメントで追加し、手順書と変更記録の費用の結論を合わせなければならない（MUST）。TTL と API 定価換算の前提、維持の tool 往復と新規入力・出力の追加費用を示し、見積もりやテスト合格を実機の削減成功と扱ってはならない（MUST NOT）。

#### Scenario: 通知が無い一日待ちとも比べる
- **WHEN** 24 時間の維持と書き直しを比較する
- **THEN** 無上限で維持した旧会話部分の約 $2.52 と、12時間で維持を打ち切る新方針を区別する。毎時再開する場合と最後に一回だけ再開する場合を分け、キャッシュの失効だけでは課金されないことを明記する

#### Scenario: 12時間上限の費用比較を追記する
- **WHEN** 初回タイマーを基点とする12時間の維持費を見積もる
- **THEN** 記録済みの単価と会話20万トークンの前提で、維持16回と最後の再開を `(2 × 16 + 1) × 0.2 × $0.20 = $1.32` と概算し、一度の1h書き直し `0.2 × $8 = $1.60` を超えないと示す。これは旧会話部分の比較とし、追加の入出力・ツール往復や上限後の書き直しを含む総費用の保証にしない

#### Scenario: マージ前の契約テストが合格する
- **WHEN** 手順の参照・タイマーの雛形・例外のテストが通る
- **THEN** 合格は手順と雛形の検証として報告し、マージ後の実子の 60 分超の usage 観測は未実施として残す
