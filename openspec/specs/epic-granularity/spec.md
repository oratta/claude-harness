# epic-granularity Specification

## Purpose
エピックの作業項目を、関係の近さと見積もった消費、現在の作業者の空き枠から子にまとめる。子ごとにかかる手間を減らしながら、文脈と記録先累計の容量および分離すべき境界を確認できる、再現可能な計画を提供する。

## Requirements

### Requirement: 計算スクリプトは作業項目と実効上限を JSON で受け取る

計算スクリプトは schema_version=1 の入力として、各項目の id、repo、capabilities、depends_on、sanctuary、approval_wait、読む／直すファイルの予定読取出力量と出典、変更行数、追加保持 tokens・出典を受け取らなければならない（MUST）。files[] の各要素は path、access（read/edit）、read_id、read_scope、tokens、source を必須とする（SHALL）。起動 tokens、文脈の余裕、実効文脈／累計上限と出典、W 上限と使用枠数も必須とし、既存 issue URL は任意とする（SHALL）。上限の既定値を計算器に内蔵してはならない（MUST NOT）。path・access を維持し、編集競合はファイル単位で判定する（SHALL）。

#### Scenario: 読む予定の出力を特定して申告する
- **WHEN** files[] の一つの読取出力を入力する
- **THEN** read_id は複数項目で共有する予定の一つの読取出力を識別する空でない文字列、read_scope は固定 revision の行範囲、diff の対象 revision と hunk、検索条件など、読む出力を特定する空でない文字列である。tokens はその出力の非負整数の量であり、全文を読む場合だけ全文量となる

#### Scenario: 既存 issue を項目に展開して入力する
- **WHEN** 1 件の既存 issue から得た 2 項目に、同じ source_issues URL と別々の読む／直すファイル、capability、依存、変更行数を与える
- **THEN** 計算器はその 2 項目を個別に扱い、元 issue 1 本を必ず子 1 本に固定する制約を加えない

#### Scenario: 未知の量を省略しない
- **WHEN** files[] の read_id、read_scope、tokens、または変更行数、起動 tokens、余裕、実効上限のいずれかを欠いた入力を渡す
- **THEN** 計算器は不足フィールドを示して exit 1 になり、0 や内蔵の上限で置き換えない

### Requirement: 計算スクリプトは不正な入力を計画にしない

計算器は欠落、重複 id、未知／自己／循環依存、不正 repo／path、空 capability、不正な量・枠数、空の read_id／read_scope、および入力内の同一読取キー (repo, path, read_id) の read_scope または tokens の矛盾を診断して exit 1 にしなければならない（MUST）。非有限値、負数、整数欄の bool、occupied > max_parallel を許してはならない（MUST NOT）。正常入力では並び順によらず同じ計画を返す（SHALL）。

**守備範囲（入力検査）**: 入力の出どころは、本体／LLM が issue の作業を洗い出し、予定読取出力量・変更行数・上限・枠数と出典を申告した JSON である。拾う誤りは、この要件に列挙した形式・値・入力内の参照関係や同一読取キーの不整合である。形式と参照関係が正しく、申告 tokens が実物と違う入力は通してよい。CLI は範囲の意味や実物を照合せず、repo ファイルや会話ログを読み直して申告の真偽を検証しない。作業の列挙漏れや出典の内容まで突き合わせ、すり抜ける入力の穴を塞ぎ切ることは、この入力検査の完了条件にしない。

#### Scenario: 同一読取キーの申告が矛盾する
- **WHEN** 同じ (repo, path, read_id) に対して read_scope または tokens が異なる入力を渡す
- **THEN** exit 1 になり、矛盾したキーとフィールドを診断する。最大値でまとめたり、別の子に配置して続行したりしない

#### Scenario: 循環依存を渡す
- **WHEN** A が B、B が A に依存する入力を渡す
- **THEN** exit 1 になり、循環に含まれる id を診断する

#### Scenario: 不正値を渡す
- **WHEN** tokens=true、負の変更行数、未知の依存 id、絶対パスまたは `..`、occupied が max_parallel 超の入力をそれぞれ渡す
- **THEN** それぞれ exit 1 になり、不正フィールドを診断する

#### Scenario: 入力順を変える
- **WHEN** 同じ項目、files、依存配列の順番だけを変えて実行する
- **THEN** group id、所属、依存、数値、選択理由を含む JSON 出力が同一になる

### Requirement: 計算スクリプトは総消費と累計計測対象を区別する

計算器は #1799 の確定コメントを出典に、総消費 T=ceil(9,900,000+49.9×F)、累計 E=ceil(8,200,000+18,650×L)、計画用累計 S=ceil(1.6×E) を別々に出さなければならない（MUST）。F は子内の (repo, path, read_id) ごとに重複排除した予定読取出力 tokens の和、L は追加＋削除行数の和とする（SHALL）。同じファイルの別範囲・部分的に重なる別出力も加算し、同じ出力を再取得する予定は別 read_id で計上する（SHALL）。T を累計上限と比較したり、対数回帰の未記載係数や総消費用 1.37 を累計へ使ってはならない（MUST NOT）。

#### Scenario: 同じ読取出力を共有する項目をまとめる
- **WHEN** 2 項目が同一 (repo, path, read_id) と同じ read_scope の 1,000 tokens の読取出力を共有し、変更行数が合計 100、係数は既定設定である
- **THEN** F=1,000、T=9,949,900、E=10,065,000、S=16,104,000 を返し、その読取出力を 2 回加算しない

#### Scenario: 同じファイルの異なる読取出力を使う
- **WHEN** 同じ repo/path に異なる read_id の 1,000 tokens と 2,000 tokens の読取出力を与える
- **THEN** 別範囲や部分的に重なる範囲でも F=3,000 になり、同じ出力の再取得を別 read_id で申告した場合も加算する

#### Scenario: 計測対象を表示する
- **WHEN** 計算結果を読む
- **THEN** T は本体＋Claude サブエージェント、E/S は本体を除く Claude サブエージェント＋Codex と識別でき、回帰の外挿と不確かさが明記される。読取量と共有は計画上の仮定であり、過去の実測量や #1799 と同じ予測精度が検証済みとは表示しない

### Requirement: 計算スクリプトは W の保持文脈を見積もる

計算器は C=起動 tokens＋余裕 tokens＋F＋項目の追加保持 tokens の和を出さなければならない（MUST）。ファイル数ではなく予定読取出力量を使い、同一読取キーだけを子内で 1 回数える（SHALL）。文字数から入力を準備する手順には Read 0.77、Bash 0.65 tokens/文字を切上げ換算し、revision、範囲、出力文字数、換算方法を source に残す例を用意する（SHALL）。生成した本文などの保持出力は F と追加保持量で二重計上してはならない（MUST NOT）。

#### Scenario: 起動分と出力分も含める
- **WHEN** 起動 40,000、余裕 10,000、F=30,000、項目の追加保持量の和が 15,000 である
- **THEN** C=95,000 を返し、予定読取出力量 30,000 だけを文脈見積もりとして使わない

### Requirement: 計算スクリプトは出典付き設定と余裕で容量を判定する

係数は出典 URL・版付きの設定から読み、上限の値は入力だけから読まなければならない（MUST）。既定の計画用上限は実効上限の 0.8 倍を切り捨て、C と S の両方がそれぞれ以下の子だけを配置可能にする（SHALL）。0.8 は政策値、1.6 は停止例の中央値に基づく計画係数であり、精度保証と表示してはならない（MUST NOT）。

**守備範囲（設定検査と容量判定）**: 入力の出どころは、検査済み JSON の申告量・実効上限・出典と、版・出典付きの係数設定である。拾う誤りは、設定の出典欠落・不正な係数や余裕率、C/S と各計画用上限の比較の取り違え、および超過した組の配置である。たとえば形式が正しい申告 tokens が実物より小さくても、その申告から求めた C/S が上限以下なら容量判定を通してよい。出典 URL の内容や申告上限の権限の真偽は本体が確認し、CLI は取得・照合しない。実際の消費が常に収まる保証や、申告と実物の差によるすり抜けの穴を塞ぎ切ることは、この設定検査・容量判定の完了条件にしない。

#### Scenario: 文脈だけが余裕を超える
- **WHEN** context_cap=150,000、C=120,001 で、S は累計の計画用上限以下である
- **THEN** その組を配置せず、文脈の計画用上限 120,000 に対する超過 1 を示す。C=120,000 なら文脈条件を通す

#### Scenario: 累計だけが余裕を超える
- **WHEN** record_cap=30,000,000、C は容量内、S=24,000,001 の組を評価する
- **THEN** 累計の計画用上限 24,000,000 に対する超過 1 を示してその組を配置しない。S=24,000,000 なら累計条件を通す

#### Scenario: 上限と係数を独立して変更する
- **WHEN** 出典付きの別の実効上限を入力する、または係数設定を差し替える
- **THEN** 指定された値で再計算し、出力にその出典と係数版を示す。既存上限の設定元は書き換えない

#### Scenario: 出典のない設定は使わない
- **WHEN** 設定に source URL がない、余裕率が 0/1 以上、係数が負／非有限である
- **THEN** exit 1 になり、内蔵の係数で続行しない

### Requirement: 計算スクリプトは三つの意味上の分離境界を守る

計算器は repo が異なる項目、聖域に触る項目と触らない項目、主の承認待ちで止まる項目を分けなければならない（MUST）。承認待ち項目は単独の子にする（SHALL）。この三つ以外の capability 数・設計判断数・受け入れ条件数・ファイル数を強制分割の理由としてはならない（MUST NOT）。容量超過による分割は別途適用する（SHALL）。

#### Scenario: 小さい項目でも境界を越えない
- **WHEN** 量が十分小さい項目に、別 repo、sanctuary の真偽の相違、approval_wait=true をそれぞれ含める
- **THEN** 別 repo／聖域と非聖域は同じ子にならず、承認待ちの各項目は単独の子になる

#### Scenario: 個数が多くても容量内ならまとめる
- **WHEN** 6 ファイル、6 受け入れ条件、複数 capability の項目が同じ repo・同じ聖域区分・承認待ちなしで、併合後も容量内かつ W 空き枠が 1 である
- **THEN** 個数を理由に分けず、同じ子にまとめる

### Requirement: 計算スクリプトは関係の近い項目を先にまとめる

計算器は容量内の併合で、直接依存、同じ capability、前提の共有をこの順の関係値として優先し、その後に無関係な項目を量で詰めなければならない（MUST）。同値は併合後の T、項目 id 順で決める（SHALL）。全項目を一度ずつ配置し、縮約後の依存を失ったり循環させたりしてはならない（MUST NOT）。

#### Scenario: 容量の最後の一枠に関係のある項目を入れる
- **WHEN** A と直接依存のある B と、無関係な C があり、A+B と A+C は入るが 3 項目全部は容量に収まらない
- **THEN** A+B を先にまとめ、C を別の子にし、理由に直接依存を示す

#### Scenario: 離れた依存項目だけの併合で循環を作らない
- **WHEN** A→B→C の依存があり A+C の量だけは容量内だが、全項目の併合は容量外である
- **THEN** A と C だけをまとめて子間依存を循環させる案は採用しない

### Requirement: 計算スクリプトは空き W 枠がある場合だけ並列分離を優遇する

計算器は max_parallel−occupied が 2 以上のときだけ、関係を優先した部分を保った無関係な構成部分の分離を評価しなければならない（MUST）。直接／推移依存または共有 edit ファイルがある組を並列候補にしてはならない（MUST NOT）。子ごとの T と依存・空き枠で計算した所要量の代理 makespan が改善するときだけ分離を採用し、同値なら子数の少ない案を選ぶ（SHALL）。

#### Scenario: 枠が空いていない
- **WHEN** 全部まとめて容量内の独立項目 A/B に対し、空き W 枠が 0 または 1 である
- **THEN** 並列化を理由に分けず、空き 0 なら起動許可を出さない

#### Scenario: 枠が二つ空いている
- **WHEN** A/B は無関係で依存も共有 edit ファイルもなく、空きが 2、分離による代理 makespan が併合案より小さい
- **THEN** 容量内の 2 子を並列候補として返し、固定分を再計上した比較値と理由を示す

#### Scenario: 依存や編集競合を並列化しない
- **WHEN** 空きが 2 でも A/B が推移依存を持つ、または同じファイルを edit する
- **THEN** その組を独立の並列候補として表示しない

### Requirement: 計算スクリプトは配置不能と実行可能を区別する

計算器は全項目が容量内に配置された場合だけ exit 0 とし、単独でも収まらない項目があれば exit 2 と unplaced を返さなければならない（MUST）。JSON には所属、外部依存、各見積もり、実効／計画用上限との差、分離理由、W 枠、係数版、不確かさを含める（SHALL）。超過診断には寄与した path・read_id・読取量も示す（SHALL）。配置不能項目を捨てたり上限を緩和したりしてはならない（MUST NOT）。再入力は必要情報を保存した作業・読取範囲・依存の再設計後だけとし、同じ担当が読む全範囲の名目上の分割や tokens の切詰めで通してはならない（MUST NOT）。分離できなければ未完了のまま返す（SHALL）。

#### Scenario: 巨大な単一項目を渡す
- **WHEN** 単独項目の C または S が計画用上限を超える
- **THEN** exit 2 とし、unplaced に項目 id・超過の種類と量・寄与した path/read_id/読取量を示し、必要情報を保存した作業・読取範囲・依存の再設計後の再入力が必要と診断する。部分計画だけで全体の成功を宣言しない

#### Scenario: 巨大なファイルの必要範囲だけを読む
- **WHEN** ファイル全文は 120,000 tokens 超だが、必要な読取出力は 1,000 tokens で、起動 40,000、余裕 10,000、追加保持 0、context_cap=150,000、S も計画用上限以下である
- **THEN** C=51,000 として配置でき、全文量を理由に配置不能にしない

#### Scenario: 必要な読取出力自体が上限を超える
- **WHEN** context_cap=150,000 で、一つの必要な読取出力自体が 120,000 tokens 超、S は計画用上限以下である
- **THEN** exit 2 と unplaced を返し、計画用文脈上限 120,000 を満たすために読取量を切り詰めない。起動分などを含めた C だけが超える場合も配置不能とする

### Requirement: 計算スクリプトの過去エピックへの適用を再現できる

細かく分割された過去のエピック 2 件以上について、GitHub の実データから構成した、読取計画の仮定付き再計画の入力・出力と比較記録を残さなければならない（MUST）。当時の実読取量・最大文脈の復元や、当時の消費・上限遵守の実証とは表示してはならない（MUST NOT）。比較は元と計算後の子数、項目対応・依存・W 枠、全子の T/E/S/C、実効／計画用上限と余裕、減らない場合の理由、再実行コマンドと exit code を含む（SHALL）。子数の減少自体は必須にしない（SHALL）。#1799 の会話ログを再測定せず、固定した fixture だけで再実行できなければならない（MUST）。

#### Scenario: 元の全子と根拠を固定する
- **WHEN** #1701 と #1732 から再計画入力を準備する
- **THEN** #1701 の元 3 子と #1732 本文の元 21 子を対応表にすべて残し、#1799 の測定 PR だけに縮めない。子本文・結論、対応するすべてのマージ PR、base/head SHA、変更ファイル、追加・削除行数を固定する。PR のない調査・実機検証・不要判定の子も作業と根拠を対応表に残し、必要情報・保持出力を申告する

#### Scenario: diff と必要な周辺読取から出力量を固定する
- **WHEN** 対応する PR から読取範囲と F/L を準備する
- **THEN** 初期案は各 PR のファイル別 diff 出力とし、必要な関数・仕様節・共通手順の周辺読取を別途加える。全文読取は一律要求しない。追加・削除・コンテキスト・ヘッダーを含む固定出力文字列を Bash 0.65 で切上げ換算し、L には追加＋削除だけを用いる。ファイル数・変更行数から F を求める係数を新設しない

#### Scenario: API の patch が欠落または打ち切られる
- **WHEN** API の patch が欠落・打切りになり、完全な diff または必要範囲を取得できない
- **THEN** 空文字や 0 に置換せず、入力作成は未完了とする

#### Scenario: 比較用の仮定と上限の出典を揃える
- **WHEN** 両 fixture の起動・余裕・保持量・W 枠・実効上限を準備する
- **THEN** 起動 40,000 と reserve 10,000 は現行 reference 由来の比較用仮定として共通使用できるが、#1799 の実測値とは表示しない。追加保持量 0 は reserve が扱う内容を説明できる場合だけ使用する。W 枠は両方とも max_parallel=2, occupied=1 に固定し、文脈上限は対象の実効値と出典を用いる。累計 60M は既存の権限記録を確認できる場合だけ使用し、fixture を通すために付与しない

#### Scenario: 二つのエピックをオフラインで再実行する
- **WHEN** 固定した #1701 と #1732 の作業項目入力を同じ設定・W 枠で計算する
- **THEN** exit 0 で比較記録および期待 JSON と同じ子数・所属・見積もりが出て、元 3 子／21 子との対応、全項目保存、境界、依存の保存と非循環、全子の文脈／累計の余裕を確認できる。配置不能があれば成果完了とせず、必要情報を保存した作業・読取範囲・依存の再設計後に再検証する
