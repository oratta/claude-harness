# インシデント対応手順書（ドラフト）

> **この文書は LLM が生成したドラフトであり、法務・専門家のレビュー前である。**
> 個人情報の漏えいには法定の報告期限があり、期限を落とすと事業者の義務違反になる。
> 本文書の期限・要件は条文とガイドラインの数値をそのまま写したもので、**該当性の判断と
> 運用上の解釈は人間と専門家が行う**。エージェントは判断材料の整理までを担当する。

## 使い方

`{{PRODUCT_NAME}}` `{{SUPPORT_EMAIL}}` を置換し、6 節の連絡先一覧を人間が埋める。
プライバシーポリシー（`../legal/privacy-policy.md` 7 節）と窓口設計（`../support-desk.md` の
エスカレーション表）はこのファイルを参照する。展開先で置き場所を変えたら両方の参照も直す。

## 1. 検知

インシデントの入口は次のどれか。どこから来ても 2 節の初動に合流させる。

| 入口 | 例 |
|---|---|
| 監視・アラート | 稼働監視の失敗、エラー率の急上昇、不審なアクセスログ |
| 利用者からの連絡 | {{SUPPORT_EMAIL}} への申告（「他人のデータが見える」等） |
| 内部の気づき | デプロイ後の異常、誤送信・誤公開の発見、委託先からの連絡 |
| 外部からの指摘 | セキュリティ研究者・決済事業者・行政からの連絡 |

検知した時点で、**個人データが関わる可能性があるか**を最初に切り分ける。
可能性があれば「個人情報インシデント」として扱い、確定を待たずに 4 節の期限の起算を始める
（起算点は「発覚」であり、影響範囲が確定した時点ではない）。

## 2. 初動（封じ込め）

目的は被害の拡大を止めることで、原因究明はその後。

1. **記録を始める** — 発覚日時・発覚経路・第一報の内容を時刻つきで残す（後の報告の材料になる）
2. **止める** — 影響のある機能の停止、漏えい経路の遮断、認証情報のローテーション
3. **証拠を保全する** — ログ・DB スナップショットを、上書きされる前に退避する
4. **人間に上げる** — 個人情報インシデントは常に人間へ。`support-desk.md` のエスカレーション表どおり即時

エージェントが自走してよいのは 1〜3 のうち、可逆で影響が局所的な操作だけ。
サービス全体の停止・データの削除・外部への連絡は人間の判断を待つ。

## 3. 影響範囲の特定

報告と通知の要否は影響範囲で決まる。次を洗い出す。

- 漏えい等した情報の種類（氏名・メール・決済情報・要配慮個人情報など）
- 影響を受けた本人の数（確定値と、確定できない場合の推定範囲）
- 期間（いつからいつまで露出していたか）
- 原因（不正アクセス・設定ミス・誤送信・委託先の事故など）
- 第三者に取得された事実の有無

## 4. 報告と通知（誰が・いつまでに・どこへ）

### 4.1 個人情報保護委員会への報告（個人情報保護法 26 条）

次のいずれかに該当する（またはそのおそれがある）漏えい・滅失・毀損は、**個人情報保護委員会への
報告が義務**になる（個人情報保護法施行規則 7 条）。

1. 要配慮個人情報が含まれる個人データの漏えい等
2. 不正に利用されることにより財産的被害が生じるおそれがある個人データの漏えい等（決済情報等）
3. 不正の目的をもって行われたおそれがある行為による個人データの漏えい等（不正アクセス等）
4. 本人の数が 1,000 人を超える個人データの漏えい等

**該当性の判断は人間と専門家が行う。** エージェントは 3 節の材料を揃えるまで。

| 報告 | 期限（起算点は発覚日） | 根拠 |
|---|---|---|
| 速報 | 概ね **3〜5 日以内** | 施行規則 8 条・個人情報保護委員会ガイドライン |
| 確報 | **30 日以内**。不正の目的をもって行われたおそれがある場合（上の 3）は **60 日以内** | 施行規則 8 条 |

速報は判明している範囲で出し、不明な項目は不明のまま出してよい（確報で埋める）。
報告の窓口・様式は個人情報保護委員会の案内に従う（提出方法は運用時点で要確認）。

### 4.2 本人への通知（個人情報保護法 26 条 2 項）

4.1 の報告対象に該当する場合、**本人にも通知する義務**がある。通知の内容・時期・方法の細目は
法令とガイドラインに従う（本人への連絡が困難な場合の代替措置を含め、要件は専門家レビューで要確認）。
通知文は 7 節の雛形を使い、**送信前に必ず人間が文言を最終確認する**。

### 4.3 その他の連絡先

| 宛先 | 条件 |
|---|---|
| 決済事業者 | 決済情報が関わる場合。契約上の通知義務があることが多い（契約書で要確認） |
| 委託先・委託元 | 委託先で起きた事故、または自社の事故が委託元のデータに及ぶ場合 |
| 警察 | 不正アクセスが疑われる場合 |
| 利用者全体への告知 | 障害・漏えいの公表判断と最終文言は人間が承認する |

## 5. 事後対応と再発防止

インシデントを閉じる条件は「止まった」ではなく「原因と再発防止が記録された」。
次の見出しでポストモーテムを書き、教訓ログ（`autonomy-lessons.md`）にも要点を残す。

- **事実経過** — 時刻つき。検知から封じ込め、報告、通知まで
- **根本原因** — 直接原因と、それを許した構造
- **再発防止** — 実装した対策と、実装していない残課題（issue 化）
- **補償判断への引き継ぎ** — 利用者への補償が要るなら返金ポリシー（`../legal/refund-policy.md`）の
  「当社に起因する障害があった場合の補償」に沿って人間が判断する
