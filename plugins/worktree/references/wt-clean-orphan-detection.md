# 居残り（孤児）プロセスを稼働シグナルから外す判定（issue #98）

wt-clean の絶対禁則 3（稼働シグナル）の**唯一の例外**についての背景と設計。実行時に毎回読む必要はない。
判定そのもの（2 条件 AND・fail-closed・根拠の表示義務）は `plugins/worktree/skills/wt-clean/SKILL.md` の禁則 3 と
`detect_active_procs_under` に書かれており、**そちらが正本**である。ここは「なぜその形なのか」を残すための資料。

## 何が起きたか

2026-08-10 に flatmate リポで全件実行したとき、**11 件中 Pass 1 で自動処理できたのは 0 件**だった。判断バッチ（Pass 2）に
11 件全部が積まれ、うち 5 件は squash マージ済み・working tree clean で、本来なら 🟢 / 🟡 として自動削除できるものだった。

原因は、`detect_active_procs_under` が `lsof +D` でプロセスの**実在**だけを見て、そのプロセスが**使われているか**を
見ていなかったこと。worktree ごとに codex / claude セッションを開く運用では、セッションを閉じてもプロセスがデタッチして
残るため、稼働シグナルが恒久的に立ちっぱなしになる。

| worktree | 起動 | 最後の実作業 | 居残り | PPID |
|---|---|---|---|---|
| moko-status | 08-04 15:36 | 08-06 11:11 | 7 日 | 1 |
| codex-cli | 08-08 18:23 | 08-08 21:40 | 3 日 | 1 |
| epic-widget | 08-10 19:14 | 08-10 20:22 | 1 日 | 1 |

```
  PID  PPID STAT  ELAPSED
13955     1 Ss   03-00:04:50   node .../codex/scripts/...
13975 13955 S    03-00:04:50   codex app-server
13977 13975 S    03-00:04:50   codex
```

先頭が `PPID=1`（起動した親セッションが既に居ない）で、3 日間 `S`（スリープ）のまま。加えて `lsof +D` は cwd が配下に
あるだけの無関係プロセス（ChatGPT.app の `cua_node`、Pencil.app の MCP サーバー）まで拾う。

## 設計上の捻れ

同じ `lsof +D` の結果に、SKILL.md は 2 つの逆向きの意味を与えている。

- `kill_devserver_under`（issue #39 対策）: 配下プロセス = **始末すべき残骸**なので削除前に止める
- 稼働シグナル（issue #77 対策）: 配下プロセス = **作業中の証拠**なので削除を止める

両者を意図的に同じ基準で結んだのは「`kill_devserver_under` が停止する対象が居るなら、それは自動削除してよい worktree
ではない」という対応関係を作るため。守りたかったのは対話中の claude セッション（壁打ちの誤削除）だが、**孤児化した残骸も
同じ網に入る**ため、残骸しか無い環境では自動処理が全滅した。

## 2 条件を AND にしている理由

| 条件 | 単独で使うと壊れるもの |
|---|---|
| 1. プロセスツリーの最上位が `PPID=1`（かつその最上位も削除対象パス配下で検出されている） | `launchd` 常駐の住人セッションは正当に `PPID=1` になる。これだけで居残り判定すると、稼働中の常駐セッションを消す |
| 2. worktree の更新もセッションログの更新も 24 時間以上前 | 「24 時間黙っているだけの対話セッション」を消す。プロセスが生きていて親も居るなら、それは作業の続きである |

逆向きに見ると、それぞれが守るケースはこうなる。

- issue #77 で消してしまった壁打ちセッションは**親プロセス（端末・シェル）が生きていた**ため、条件 1 で引き続き守られる
- `launchd` 常駐の住人セッションは自分の workspace で動きセッションログが常時更新されるため、条件 2 で守られる

**AND を崩さないことが安全側の担保**であり、片方だけで居残り判定してはならない（SHALL NOT）。

## 実装上の注意

- **最上位が「配下で検出されている」ことまで要求する**: 祖先を遡れば全プロセスが最終的に PID 1 に行き着くので、「最上位が
  `PPID=1`」だけでは常に真になり判定にならない。生きた端末やシェルから起動されたプロセスは、最上位が端末アプリ側
  （= 削除対象パス配下では検出されないプロセス）になる。この差が「起動元セッションが生きているか」の実体である。
- **痕跡スキャンから `.git` を除外する**: 診断中に自分が撃つ `git status` が index の mtime を動かすため、除外しないと
  どの worktree も常に「最近更新あり」に見え、居残り判定が永久に効かなくなる（修正が自分で自分を無効化する）。
  依存物・ビルド生成物（`node_modules` / `.next` / `dist` / `build` / `.venv` / `target`）も人の作業痕跡ではないので除外する。
- **fail-closed を維持する**: `ps` が引けない・ヘルパが未定義・セッションログ検査不能・ディレクトリを見られない、の
  いずれでも居残りと断定せず稼働シグナルとして扱う。除外に進むのは 2 条件の成立を**確認できたとき**だけ。
- **除外を黙って行わない**: 除外したプロセスは stderr のノート（`ℹ️ 居残りプロセスとして稼働シグナルから除外: …`）に残し、
  Pass 1 の診断表示・Pass 2 の提示・Step C の完了レポートで読めるようにする。無人モードのログでは、なぜ止まらずに
  消えたのかを後から追える唯一の手がかりになる。

## 誤検出コストの見積もりの改訂

旧版の SKILL.md は「稼働シグナルの誤検出が起こしうる最悪は Pass 2 で 1 問聞かれるだけ」と書いていた。これが成り立つのは
**シグナルがいずれ消える場合に限る**。恒久的に立ちっぱなしのシグナルでは、コストは「その worktree が永久に自動処理されない」
に変わる。ガードが効いているのではなく自動化が死んでいる状態であり、居残りプロセスの除外はこの一点のためだけにある。
それ以外の誤検出（短命プロセス・無関係アプリの cwd 等）は従来どおり許容する。
