# wt-clean 自己検証の詳細手順

`wt-clean` スキルの `## 自己検証` 節から参照される検証詳細。共通原則は `plugins/dev-workflow/references/self-verification.md`。

wt-clean は worktree を診断（🟢🟡🔴）して Pass 1（自動処理）/ Pass 2（判断バッチ）で処理する破壊的操作を含むため、完了宣言の前に「削除・退避が意図どおりに行われた evidence」を必ず確認する。

## 診断・処理後に確認する evidence

- **削除された worktree が登録から消えている**: `git worktree list` の出力に、削除対象として選んだパスが現れないことを確認する。
- **自動削除（🟢/🟡）の直前に診断根拠を表示している**: マージ済み判定の根拠（branch --merged / squash 検証結果）を表示せずに削除していないこと（無音削除の禁止）。
- **🟡（LLM あり）の退避検証が削除に先行している**: 退避先ファイル（LLM 退避物）が実在し空でないことを**検証してから** worktree を削除したことを確認する。検証失敗のまま削除していないこと。
- **🔴 / dirty の破壊操作が Pass 2 の回答後に実行されている**: マージ / スキップ / 破棄 / dirty 破棄のいずれを選んだかと、その結果（マージ commit の有無・ブランチの残存）が一致し、AskUserQuestion の回答を受け取った後の別ターンで実行されていることを確認する。
- **無害 dirty で自動処理した根拠が出ている**: dirty があるのに 🟢 相当として自動処理した worktree について、削除直前の表示に `dirty=lockfileのみ` と対象ファイル名が含まれていることを確認する。lockfile 以外の変更を 1 つでも含む worktree が自動処理に回っていないことも確認する（安全側の判定が働いていること）。
- **`--unattended` で対話していない**: 無人モードで実行した場合、`AskUserQuestion` を一度も呼んでいないこと、Pass 2 の破壊分岐（dirty 破棄・🔴 破棄削除・🔴 マージ）を実行していないこと、残件が「番号・パス・ブランチ名・分類・理由」付きで列挙されていることを確認する。件数だけの要約は PASS としない（cron ログを人間が読んで判断できることが唯一の出口のため）。
- **`--repo` が cwd のリポジトリを汚していない**: `--repo` を指定した場合、操作対象が指定リポジトリのメイン worktree に解決されていること、および cwd 側のリポジトリの `git worktree list` / ブランチ一覧が実行前後で不変であることを確認する。
- **孤児の整理**: パスが既に存在しない worktree は `git worktree prune` で整理し、`git worktree list` がクリーンになったことを確認する。
- **Step 0 の同期**: `origin/<main>` の同期を行った場合、`--no-sync` でない限り同期が成功した exit code を確認する。
- **稼働シグナルのある worktree を自動処理していない**: 削除対象パス配下に非シェルプロセス（`claude` / `node` / `next` 等）が稼働していた、または `~/.claude/projects/<worktree-path-slug>/` に 24 時間以内更新の `.jsonl` があった worktree について、Pass 1 の自動削除・自動再利用化に入れず Pass 2 の判断バッチへ回したことを確認する。Pass 2 の提示に検出内容（PID・コマンド名／セッションログの更新時刻）が含まれていたことも確認する（絶対禁則 3・issue #77: git がクリーンな壁打ちセッションの worktree を 🟢 Safe と誤判定して削除した事故）。
- **居残り（孤児）プロセスの除外が 2 条件 AND を満たしている**: 稼働シグナルから外したプロセスがある場合、(1) プロセスツリーの最上位が `PPID=1` で、その最上位も削除対象パス配下で検出されていた、(2) worktree 配下のファイル更新も対応するセッションログの更新も 24 時間以上前だった、の**両方**が成立していたことを確認する。片方だけで除外した形跡があれば FAIL とする（issue #77 のガードが壊れるため）。除外根拠（PID・コマンド名・親セッション消滅・痕跡なし）が Pass 1 の表示・Pass 2 の提示・完了レポートに出ていることも確認する（issue #98: 孤児プロセスを稼働シグナルと誤検出し、11 件中 Pass 1 の自動処理が 0 件になった事象）。
- **削除対象 worktree 配下のプロセス残留なし**: `git worktree remove` を実行する全ての箇所で、その直前に `kill_devserver_under` によるプロセス検出・停止（SIGTERM→SIGKILLフォールバック）を行い、停止した PID・コマンド名または「プロセスなし」がログに表示されていることを確認する。停止対象は削除対象パス配下に限定され、メインリポや他 worktree のプロセスを誤って止めていないことも確認する。
- **シェル/エディタを止めていない**: `kill_devserver_under` の出力に `⚠️ シェル/エディタと判定してスキップ: <PID>(<comm>)` の行があるとき、止めたもの（`🔪`）と見送ったもの（スキップ）の両方が読めることを確認する。対象 worktree に cd しているだけのターミナルのタブは停止対象ではない。comm が空で表示される（`<PID>()`）行が 1 つでもあれば、コマンド名の取り出しが壊れているサインなので、削除を続けずに原因を確認する（かつて macOS の `ps -o comm=` が返すログインシェルの argv[0] `-/bin/zsh` を `basename` が処理できず、空文字に潰れてタブを SIGKILL した）。

## 判定が「マージ済み」側に倒れていないことの確認（fail-closed）

2026-08-10 に flatmate で、PR が OPEN のままの未マージブランチ 6 本が「squash 済み」と誤判定された。
原因は squash 検出の実ツリー差分に JS/TS 前提のパスフィルタが掛かっており、Markdown 中心のリポジトリでは
対象ファイルが一致せず差分が常に空になっていたこと。加えて、各検査の**失敗が例外なく「マージ済み」を示す側に
倒れる**構造だった。以下は再発防止のための確認項目で、いずれも「検査が失敗したときに削除許可へ倒れていないか」を見る。

- **実ツリー差分にパスフィルタを掛けていない**: `git diff <main> <branch> --stat` を全 tracked ファイル対象で取っていること。`-- 'src/**' '*.ts'` のような言語別フィルタが付いていないことを確認する。フィルタが付くと、そのパスにファイルを持たないリポジトリでは差分が常に空＝常に「マージ済み」になる。
- **ツリー差分の非対称性を守っている**: 「差分が空」は削除して安全であることの十分条件として使ってよいが、「差分がある」を未マージ判定の根拠に使っていないこと（main が先行しただけでも差分は出るため）。
- **マージ済み PR の件数を根拠にしていない**: マージ済み PR を根拠に削除した場合、その PR の `headRefOid` と現在の branch tip が一致することまで確認していること。件数だけでは、マージ後に同じブランチへ積んだコミットを取りこぼす。
- **`gh` の失敗と「PR なし」を区別している**: `gh ... | grep -c` の形になっていないこと（パイプの終了コードは末尾の `grep` のもので、`gh` の未認証・通信断を 0 件と区別できず、OPEN PR の拒否権が黙って消える）。変数代入の終了コードで成否を判定し、GitHub リポジトリなのに取得できなかった対象を自動削除していないことを確認する。
- **`cherry` を削除許可の根拠にしていない**: squash では patch-id が変わって `+` が出るため未マージの証明にならず、コマンド失敗時も 0 になるためマージ済みの証明にもならない。Pass 2 の表示にのみ使っていることを確認する。
- **ロック検出を空白区切りで解析していない**: `git worktree list --porcelain` を `awk '{print $2}'` 系で解析していないこと（パスに空白がある worktree のロックを取りこぼす）。worktree 専用の gitdir から `locked` を直接読み、一覧取得に失敗した対象を「ロックなし」として自動削除していないことも確認する。
- **`realpath -m` を使っていない**: GNU 専用オプションで macOS では必ず失敗し、`abs` が空文字に潰れて `lsof +D ""` が空振りし「プロセスなし」と表示される silent no-op になる。`abs_path` を使い、プロセス残留チェックの表示に実際のパスが出ていることを確認する。
- **Pass 1 で `git worktree unlock` を実行していない**: ロック解除は Pass 2 でユーザーが削除を選んだ対象に限る。解除に失敗した場合に `git worktree remove` へ進んでいないことも確認する。
- **Step 0 の `fetch` / `pull` の終了コードを検査している**: 失敗しても「✅ pulled」と表示され、古い `<main>` を基準に削除判定へ進む経路が無いことを確認する。

## PASS 条件

上記の各確認が期待どおり（対象パスが消えている / 退避物が実在する / 選択と結果が一致する / 稼働シグナルのある worktree を自動処理していない / プロセス残留がない）であることを evidence として提示できたときのみ、クリーンアップ完了を宣言する。
