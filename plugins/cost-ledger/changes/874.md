# ロックファイルの作成が ENOENT を返す原因を特定し、同じ `dir_fd` の再試行を検査で固定する（#874）

#705 で置き場を fd で開いてロックファイルをその `dir_fd` 基準で作るようにした後、同時に流した 2 本のうち 1 本が作成で `ENOENT` になり、書かずに終わることがあった。#873 は同じ `dir_fd` のまま 20 ms 空けて最大 5 回試す形にした。原因を実測で切り分けた: macOS（26.7）では、同じ名前を 2 つのプロセスが `dir_fd` 基準の `O_CREAT` で同時に開くと、片方が `ENOENT` で返ることがある。その瞬間も置き場は在り、fd が指す inode はパスの inode と同じで、ロックファイルは相手が作成済み。同じ `dir_fd` のまま開き直せば取れる一過性のもので、パス指定の open・別々のファイル名では出ない（再現手順と数字は PR #920 の本文）。

- `plugins/cost-ledger/scripts/gate_report.py` の `lock()` の動きは #873 のまま（同じ `dir_fd` で最大 5 回・20 ms 間隔）。コメントだけを実測に合わせて直した。実測では 1 回の `lock()` の中で `ENOENT` は最大 1 回で、2 本・8 本を同時に流して取りこぼしは 0 件（再試行なしだと 600 回中 141 件）
- 置き場は開き直さない。開き直すと、ロックを取っている側がいる間に置き場が消されて作り直されたとき、別の inode をロックして同時に読み書きに入る。fd で開いた後に置き場が消えた場合は `None`（書かない）
- 5 回とも `ENOENT` なら `None`（取れなかったものとして書かない。spec cost-ledger-timeline の排他ロックの要件に反しない）。例外は外へ出さない
- 検査は `plugins/cost-ledger/tests/gate-report.bats`（4 回 ENOENT のあと同じ `dir_fd` で取れる・5 回とも ENOENT で `None`・開いた後に置き場が消えたら作り直さず `None`）
- 戻し方: `gate_report.py` のコメントと上の 3 本のテストを戻す（動きは変えていない）
