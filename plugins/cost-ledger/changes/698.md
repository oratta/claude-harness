# issue の帰属の鍵に `gh issue reopen` と `gh api` の issues endpoint を足す（#698）

`ISSUE_RE`（`scripts/cost_ledger.py`）の定義だけを書き換えた。`scan_tool_calls` など他の行は変えていない。

- `gh issue reopen <番号>` を拾う
- コマンドの位置（行頭、または `;` `&&` `||` `|` `(` の直後。前に `VAR=値` の代入が付く形も可）にある `gh api` で、`-X`・`--method` とその値を除いた最初の語が `repos/<owner>/<repo>/issues/<番号>` で始まり、番号の直後が英数字・`_` でないものを拾う。定義に `re.M` を付けた
- 直前がバックスラッシュの区切り（`echo x\; gh api ...`・`echo x\| gh api ...`）と、行末のバックスラッシュで続けた次の行の行頭は、コマンドの位置としない。`gh api`・`-X`/`--method`・その値の後ろは同じ行の空白だけを許し、`gh api` で終わる行の次の行の `repos/.../issues/<番号>` を endpoint として読まない（PR #880 のゲート 1 周目の指摘 F1・F2）
- 拾わない（読み落とす）形: `issues/comments/<id>`・`gh api graphql`・`issues/42abc`・完全な URL・`-H` など他のオプションが先に来る形・`xargs gh api`・`time gh api`・`if gh api ...; then`・エスケープしたバックスラッシュの直後の本当の区切り（`echo x\\; gh api ...`）・`gh api \` の行継続で次の行に書いた endpoint。読み落とした区間はその issue に寄らないだけで、別の issue へは寄らない
- `-f body="gh api repos/a/b/issues/99"` のような引数の値の中の文字列は拾わない（42 だけ拾う）
- 既知の例外: 引用符の中の `;` `&` `|` `(` の直後に `gh api repos/.../issues/<番号>` が続く文字列は拾う。塞ぐには引用符を読む解析器が要るので範囲外。`gh issue comment 42 --body "gh issue view 99"` が 99 にも寄る既存の誤りと合わせ、子 issue #879 で扱う
- 既知の例外: シェルのコメントの中の区切りの直後に続く同じ形（`echo ok #; gh api repos/a/b/issues/99` の 99）も拾う。同じ行のそれより前の `#` は Python の固定長の後読みでは見られず、行頭から読ませると同じ行の 2 つ目以降のコマンドを読み落とすため、正規表現の範囲では塞がない
- 過去に台帳へ書いた行は書き換えない。`reopen` と `gh api` だけで操作した過去の区間は、これまでどおり帰属せず、数字は小さく出る方向にずれるだけ
- 検査は `tests/attribution.bats` の `issue key:` で始まるテスト
- 実測（3000 行の合成ログ、`ledger-sync` 20 回の中央値）: 待ち時間 変更前 0.160〜0.164 秒 / 変更後 0.156〜0.159 秒（差は誤差）。`gh` の呼び出しは前後とも 0 回（PATH 先頭に呼ばれたら記録する `gh` を置いて数えた）
- 戻し方: `ISSUE_RE` を `re.compile(r"gh issue (?:view|comment|edit|close|develop)\s+(\d+)")` に戻す。台帳の既存の行は事実の列なので、戻した後も読める
