# 691: auto-merge のマージと `Closes` による自動クローズに、次のセッション開始で最後の行を後追いして積む

auto-merge でマージされた PR と、PR の `Closes` で自動クローズされた issue には、手元でコマンドが走らないので PostToolUse の hook から見えず、`マージ` / `issue クローズ` の行が付かなかった。そのリポジトリで次にセッションを始めたとき（起動と再開）に、GitHub から閉じられたものの一覧を 1 回取り、行が無いものに後追いで積むようにした。

- SessionStart（matcher `startup|resume`、timeout 10 秒）の hook `scripts/backfill.sh` を足した。`backfill.sh` は判定だけをして `scripts/backfill.py` を起こし、`backfill.py` は自分を切り離して裏で処理する。hook は stdout・stderr に何も出さず（SessionStart の hook の stdout は会話の文脈に入る）、どの失敗でも終了コード 0。LLM のトークンは使わない
- 行の時刻と累計は、GitHub が記録したマージ・クローズの時刻で切る。issue には合計の行も付く（#689 と同じ）
- 候補は「前回見た時刻以降に閉じられたもの」の一覧（`repos/<owner>/<repo>/issues?state=closed&since=...`）1 回で探す。1 回の実行は 20 件まで（20 件目と同じ秒の候補は分けない）
- 積まないもの: マージされずに閉じられた PR・fork からの PR・手元にコストが無い PR / issue（累計がすべて 0）・同じきっかけの行が出来事の時刻の 300 秒前以降に既にあるもの（手で `gh pr merge` などをして積んだ行と重ねない。もう一度流しても、控えを消しても増えない）
- `cost_ledger.py timeline` に `--backfill` を足した（上の 2 つの「積まない」判定）。付けなければ今までと同じ。`gate_report.py` の `stack()` に、`timeline` に渡す追加の引数 `extra=()` を足した（PostToolUse の hook からの呼び出しは変えていない）
- 手元に増えるファイル: 控え `<COST_LEDGER_PATH>.backfill.json`（リポジトリごとの `seen_until`）とロック `<COST_LEDGER_PATH>.backfill.lock`。控えを消せば初回の状態に戻る
- 入れた直後: 控えが無い最初のセッション開始では、過去 24 時間に閉じられた分にまとめて行が付く（1 回 20 件まで。残りは次のセッション開始で積む）
- 緊急停止: `COST_LEDGER_BACKFILL=off`（後追いだけ）、`COST_LEDGER_GATE_REPORT=off`（GitHub へ書く処理すべて）。`COST_LEDGER_PATH` が未設定なら動かない
- 書き込み先は許可の一覧（#775 の `write-repos`）に載っているリポジトリだけ。セッションを始めたディレクトリの origin のリポジトリが一覧に無ければ、書き込みも、閉じられた PR / issue の一覧の取得もしない（`gh` を 1 回も呼ばない）。一覧が無ければどこにも書かない。この変更を入れても、一覧を作るまで後追いの行は付かない（下の「許可の一覧に従わせた」）
- 反映に `/reload-plugins` が要る（`hooks.json` を変えた）
- 仕様: `openspec/specs/cost-ledger-backfill/spec.md`（新規）、`openspec/specs/cost-ledger-timeline/spec.md`（`--backfill`）
- テスト: `plugins/cost-ledger/tests/backfill.bats`（新規、66 本）

## 実装で決めたこと

- `--backfill` の判定の位置: 既存の検証（`--pr` に `--branch` が無い、issue のリポジトリが分からない）のあと、累計を出してから見る。早く返すとその検証を飛ばすため
- リポジトリ名の確認: origin の `owner/repo` が `gate_report.full_name()` を通らなければ何もしない。`gh api` のパスに置けない名前を渡さないため。リポジトリ名の検証そのもの（#703）とは別の、最低限の確認にとどめた
- ディレクトリの作成: `backfill.py` は台帳のディレクトリが無ければ作る（`ledger_sync` と同じ）。そのうえで `.backfill.lock` を開く
- 壊れた控えと空の一覧: 控えが壊れていて一覧が 0 件なら、控えは壊れたまま残す。spec の「一覧が 0 件なら変えない」を優先し、手元の時計で値を書かないようにした
- 一覧の要素の形: `merged_at` と `closed_at` が null でないのに時刻として読めない要素も、形の崩れとして一覧全体を失敗にする
- `--at` の形: `"%.3f" % 出来事の時刻` で渡す。PostToolUse の hook と同じ形
- `backfill.sh` の止め方: 緊急停止と `COST_LEDGER_PATH` 未設定のときは、標準入力を読まずに抜ける（`gate-report.sh` と同じ）

## 許可の一覧に従わせた（2026-10-08、main の #775・#795 を取り込んだあと）

一周目のレビューで、後追いが作業していないリポジトリや他人の公開リポジトリの PR / issue にもコメントを書きうることが分かった。そのあと main に入った許可の一覧（#775）は「後から足される後追いにも適用する」と決めているので、この PR の中で従わせた。

- `backfill.sh`: 緊急停止と `COST_LEDGER_PATH` の確認のあとに、一覧のファイルが無いか大きさ 0 なら抜ける近道を足した（`gate-report.sh` と同じ形。`python3` を起動しない）。`write_allow.py` が隣に無いときも抜ける
- `backfill.py`: `write_allow` を読み込み、origin の `owner/repo` が決まった直後・控えを読む前に `write_allow.allowed(repo, cwd)` を通す。後追いが `gh` を呼ぶ相手は origin のリポジトリだけなので、判定は 1 回で足りる。通らなければ `gh` を 1 回も呼ばず、控えも変えない。一覧の読み方はここに書き写していない
- `backfill.py` を直接起動したときも止まるよう、裏の処理の入口で `COST_LEDGER_GATE_REPORT=off` / `COST_LEDGER_BACKFILL=off` を見るようにした（`gate_report.py` の `work()` と同じ）
- main の取り込みに合わせた分: `gate_report.pr_checks()` が `at` を取るようになったので、マージの時刻を渡す（`マージ` の判定は `at` を使わない）。`hooks.json` の `backfill.sh` のコマンドを、main の他の 2 つの hook と同じく引用符で囲んだ
- 残るもの（直していない。#761 の範囲）: 一覧に載せたリポジトリの中では、別のリポジトリの同名ブランチのコストが混ざることと、セッションが見ただけの issue にコメントが付くことは変わらない。リポジトリが改名・移管されて GitHub が別の名前へ転送する場合、issue の候補では転送先の名前を確かめずに積む（PR の候補はベースのリポジトリ名が origin と違えば積まない）
- 下の「実測」の同期部分の時間は一覧を足す前の値。足したのはシェルのファイル検査 1 回で、測り直していない
- テスト: `backfill.bats` に 8 本足した（一覧に無いリポジトリ・一覧のファイルが無い・大きさ 0・有効な行が無い・既定の場所・作業中のリポジトリの中の一覧・`backfill.py` の直接起動・`write_allow` の読み込み）。既存のテストは `HOME` と `COST_LEDGER_WRITE_REPOS_FILE` をテスト用の場所に向け、利用者の一覧を読まない
- 戻し方: `backfill.sh` の `write_repos` の 3 行と `backfill.py` の `write_allow.allowed()` の 2 行を外す

## 実測（2026-10-07、macOS、oratta/claude-harness の worktree で計測）

測り方: SessionStart の JSON（`source: startup`、`cwd` は worktree）を `backfill.sh` に流し、Python の `time.perf_counter` で所要時間を測った。`COST_LEDGER_PATH` は実際の台帳の写し（控えとロックもその隣に置き、実際の控えは作っていない）。`PATH` の先頭に、`gh` の呼び出しを記録し、読み取りは本物の `gh` へ通し、書き込み（`-X POST` / `-X PATCH`）は捨てるラッパーを置いた（実機の PR / issue は書き換えていない）。候補 1 件の測定では、ラッパーが一覧の出力を対象の番号の 1 行に絞った。各 5 回の中央値。

- PR #742 の 1 回目の 24 秒は、台帳の写しに `ledger.jsonl.state.sqlite` を写さなかったため、最初の `ledger_sync` が会話ログを頭から読み直した分。実際の台帳には state があるので、この時間はかからない
- 同期部分の 1 回目（645 ms）は Python の初回起動。目標の 1 秒未満に収まる

`gh` の呼び出し回数（記録用のラッパーで数えた。変更前は hook が無いので 0 回）:

| 条件 | 回数 | 内訳 |
|---|---|---|
| 新しいマージ・クローズなし | 1 | 一覧 |
| PR 1 件 | 4 | 一覧・PR の問い合わせ・既存コメントの取得・書き込み（PATCH） |
