# hook のリポジトリ名の検証が . と .. を通さない・ロックの置き場の検査と作成の間を差し替えられない（#703・#705）

`plugins/cost-ledger/scripts/gate_report.py` の 2 つの直し。

- **#703**: `-R` / `--repo` / `GH_REPO` から取り出した owner と repo のどちらかが `.` または `..` のときは、解決できない対象として扱い、`gh` を呼ばない（`valid_parts()`。`repo_values()` と、GitHub の応答の名前を読む `full_name()` が共有する）。`my.org/my.repo` のように名前の中に `.` を含むだけの指定は今までどおり通る
- **#705**: `lock()` は置き場を `O_DIRECTORY | O_NOFOLLOW` で開き、その fd を `fstat()` して所有者・権限を確かめ、ロックファイルはその fd を `dir_fd` にして名前だけで開く。検査と作成の間にパスの解決が入らない。確認項目（ディレクトリ・所有者が自分・group/other に書けない）は従来どおりで、検査用の fd は開いた直後に閉じる
- 同時に流した 2 本のうち 1 本が、置き場を作った直後の `dir_fd` 基準の作成で `FileNotFoundError` になり、ロックを取れず書かずに終わることがあった（macOS で `two triggers at once` が 20 回中 4 回落ちた）。ロックファイルを開く呼び出しだけ、`FileNotFoundError` のときに 20 ms 空けて最大 5 回試す。原因のカーネル側の挙動は未確定で、再試行は対症
- 検査は `tests/gate-report.bats`（`.` / `..` を含む指定で `gh` が呼ばれないこと、`my.org/my.repo` は対象の確認が行われること、`lock()` の `os.open` が `dir_fd` 付きで呼ばれ置き場のパスに `lstat` しないこと）
- `gh` の呼び出し回数と hook 1 回の所要時間は変えていない（実測は PR 本文）
- 戻し方: `valid_parts()` を `all(PART_RE.fullmatch(...))` に、`lock()` を `os.lstat` + パス指定の `os.open` に戻す
