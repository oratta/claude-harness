# 保留 — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/prepare.md`（手順 1・2・2-0）、`stages/triage.md`（2-1 の止める判定と仕分け・2-2）、`declarations.md`（手順 3・3-b）、`stages/pass.md`（手順 4・5）。

## 入口

手順 3 で「主のリスク許容が必要」と判定したとき（まず 3-c の引き継ぎを試し、宣言が `論点なし — ` の行を持つなら手順 6 の前に 6-0 の確認に回す）、手順 4 で主に動作確認を依頼したとき、`stages/triage.md` の仕分け表の順 5 に当たったとき、保留中の PR を再開するときに読む。手順 3 の issue で承認済みを当てた宣言はこの段に来ない（`needs-approval` を付けず、`stages/pass.md` の手順 4・5 へ進む）。

## 前提と理由（この段で使うもの）

- **リポ固有の仕組み**: このスキルはリポ非依存。保留の主向けミラーや投稿規約などのリポ固有の仕組みは「**存在すればそれに従い、無ければ各手順の縮退手順**」で扱う。

## 手順

前 HEAD の宣言に主の直接の許容と真正性確認があるときは、主に聞く前に `stages/carryover.md` を読む。

### 6. 保留処理（リスク許容待ち / 動作確認依頼 / 切り出しの確認）

引き継ぎと issue 承認の両方が当たらず、論点なしの行があるときだけ `stages/no-point-check.md` を読む。

主へ依頼する前に、承認を求めてよい 4 分類として `stages/hold-categories.md` を読む。

1. `agent-review:passed` は**付けない**。`needs-approval` を付ける（`gh api -X POST repos/$R/issues/$N/labels -f 'labels[]=needs-approval'`）。
2. リポに保留を主へミラーする仕組み（pending 管理ファイルとその同期スクリプト等）が**あればそれに従って記録する**。無ければ、PR の `needs-approval` ラベルと宣言コメントが保留の正本になる。
3. 主への確認依頼は、リポ/運用環境に投稿規約があればそれに従う。無ければ PR コメントに依頼を書き、利用可能な連絡チャネルで主に PR リンクを渡す。依頼の文面（項目と順・聞く理由・リスクの書き方・1 行目の題名と 2 行目のアクションの行）は `~/.claude/output-styles/readable.md` の節 3（主に問いを返す文章の書き方の正本）の型で書き、ここには投稿先と案内の中身だけを置く。リスク宣言が論点なし（分類に当たっただけで、新たに生じるリスクが無い）のときは、依頼も論点なしの短い形で書き（行数は `~/.claude/output-styles/readable.md` の節 3 の論点の無い依頼の決まりに従い、自前で決めない）、宣言を写さない（返事の渡し方の案内はアクションの行に畳み、満たさなかった条件は区切りの下に置く）（宣言の書き分けは `declarations.md` の手順 3）。依頼の前に自力調査（プリフライト）を通す。リスク許容の依頼には「返事は会話で返せばよく、PR へのコメントは要らない」ことを含める。会話で返事を受けたときは、主に PR へのコメントを求めない（手順5の「会話で受領」の形で記録する）。develop の本体が止まる場合は、起動指示の実行モードで返事の渡し方の案内を分ける。interactive（起動指示に実行モードが無いときを含む）では、依頼に「返事は新しいセッションで `/develop <記録先>` と一緒に渡せる」ことを含める。channel では、依頼に「このチャンネルで記録先の番号を添えて返事をすれば続ける（例: `#<記録先> 許容する`）」ことを含め、新しいセッションを開く案内と `/develop` の打ち方は書かない（channel の主はチャンネルだけを見ていて、住人の新しいセッションを開けない）。channel のリスク許容の依頼では、起動指示の `チャンネルの返事の確認:` の行が `可` でない（`不可` か、行が無い）ときに限り、「会話で返せばよく、PR へのコメントは要らない」の代わりに「末尾の PR にコメントで `許容する` と書く」と案内して PR のフル URL を添える（チャンネルの返事を `owner-reply-check.sh` で確かめられないため。行が無いときを不可に倒すのは、PR のコメントならどの環境でも確かめられるため）（引き継ぎのコメントは本体が書く。書式は develop/references/handover.md が正本でここには書かない）。資格情報・安全ゲートの弱体化・エージェント権限の拡張に当たったのに手順 3 の issue で承認済みを当てられずにリスク許容を聞くときは、満たさなかった条件（4 分類を含む・引用できる目的の文が無い・承認の証拠が取れない・`agent-proposed`・実装中に発覚・無人運用や事後報告の届け先が無い経路、など）を依頼に 1 行添える。
4. **リスク承認を待つ間に手順4（動作確認）を並行して済ませておく**（承認が来た時点で手順5に直行できる。証拠の HEAD SHA が古くならないよう、待機中に push した場合は出し直す）。
主の回答を受領し保留を解除するときは `stages/hold-resume.md` を読む。

## G として動くとき（develop）

この節は develop の G（`skills/develop/references/roles/gate-runner.md` の指示で動くゲート実行者）だけに関係する。develop 以外の読み手は読み飛ばしてよい。

### return の書式（保留・needs-carryover-judge・needs-no-point-check）

`gate-runner.md`「return の書式」の共通欄（`## Gate Result` から `周回:` まで）のうしろに続ける。

```markdown
### 保留のとき
- 切り出しの確認（仕分け表の順 5。全周共通の判定で止める指摘が残り、順 1〜4 と順 6 のどれにも当たらない。周の数に関係なく、受け取ったその周で返す）: 引用した違反文（または例外 3 種のどれか）と対応する指摘、主への質問「この欠陥を残して切り出すか」と 4 点（欠陥がマージ後に何を起こすか・直す見積もり（行数・触るファイル・spec を変えるか）・別 issue にする固定費・推奨）。4 点は記録の項目で、本体が主に出す質問の文面は `~/.claude/output-styles/readable.md` の節 3 の型で書く。W の再開や3周目を提案しない。同じ周に順 2〜4 の指摘が混ざっていれば、それらも仕分け欄に載せて保留を先にする。1 周目の段 A に当たる指摘が混ざっていれば、仕分けの PR コメントと仕分け欄に「段 A・この PR で直す」と印を付ける。順 6 の指摘が混ざっていれば、主への質問には含めず仕分け欄に「順 6・未裁定」として載せる（この PR で裁定を使い切っていれば「切り出す」として質問に含める。処理順は pr-review-gate 手順 2-1 の混在の段落）
- needs-approval の理由と、オーナーに依頼する 1 アクション（リスク許容の可否 / 動作確認の 3 点セット）

### needs-carryover-judge のとき
（手順 3-c の「終了コード 4 の判定役」の回す条件を満たし、使える判定の記録が無い。宣言は投稿せず、`needs-approval` も付けない。`次の段: 合格処理`）
- 前 HEAD: <40 桁フル SHA> / 新しい HEAD: <40 桁フル SHA>
- 前の宣言のコメントのリンク: <URL>
- EVIDENCE_PR_CHANGED=: <ファイル>, <ファイル>
- EVIDENCE_DIFF_LINES=: <値>

### needs-no-point-check のとき
（手順 6-0 の論点なしの確認に回す。宣言は投稿済みで、`needs-approval` は付けない。`次の段: 合格処理`）
- 宣言のコメントのリンク: <URL>
- 対象 HEAD: <40 桁フル SHA>
- 該当する観点: <宣言の `- 該当する観点:` の値>
- 変更ファイル: <PR の変更ファイル>, <ファイル>
```

### この段で起こされたときの入力

保留の解除の G は、起動指示の前の段の `## Gate Result` ブロック（`次の段: 保留の解除`）と主の回答を受け取り、前の段の会話は持たない前提で PR コメントから保留の中身を読む。

- **許容済みの PR で HEAD が動いたとき**: 取り直しの手順 3 で再び「主のリスク許容が必要」になったら、主に聞く前に pr-review-gate 手順 3-c（前の HEAD の許容の引き継ぎ）を試す（条件と書式は 3-c が正本。この場合は合格処理の G がこのファイルを読んで試す）。スクリプトが終了コード 4 を返し、3-c の「終了コード 4 の判定役」の回す条件を満たし、使える判定の記録が無いときは、合格処理の G は判定役を起こせないので Status `needs-carryover-judge` で返す（欄は上の「needs-carryover-judge のとき」）
- **保留の解除**: オーナーの回答（許容する／しない・動作確認の結果・切り出しの確認への回答（切り出す／この PR で直す））を受けて pr-review-gate の復帰手順に従う。復帰手順が別の段の作業に進むときは、その作業を自分で行わず Status `次の段へ` で返す。許容したとき・切り出して残りが無いとき（ほかに止める指摘も、1 周目の段 A に当たる未解決の指摘も無いとき）は `次の段: 合格処理`、許容せず代替案に切り替えて作り直すとき・切り出したあとに 1 周目の段 A に当たる未解決の指摘が残っているときは `agent-review:failed` に付け替えて failed（`次の段: 前提確認と重さ判定`）で返す。1 周目かは前の段の Gate Result の `周回:` で、段 A の有無は仕分けの PR コメントの「段 A・この PR で直す」の印で読み、印が無ければ段 A の指摘は無いものとして扱う（判定をやり直さない）。段 A が残って failed で返すときの欄は `stages/triage.md` の「failed のとき」を使い、残りが段 A だけなら原因分類は「段 A だけ（昇格なし）」、順 2〜4 も残っていれば手順 2-2 の表どおりとする。`次の段へ`・`次の段: 前提確認と重さ判定` は W の修正が要らないときだけに使う。未処理の順 6 が残っていれば failed に進まない（`needs-approval` を外して `needs-decider` で返す。処理順は pr-review-gate 手順 2-1 の混在の段落）

## 出口

- 手順 6 の復帰手順の表に従う。表が「手順5へ」とする行は `stages/pass.md`、「手順2からやり直す」「手順3以降へ」とする行はそれぞれ `stages/prepare.md`・`declarations.md`、修正サイクルへ戻す行は `stages/triage.md`（failed の return）へ進む。
