# 保留 — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/prepare.md`（手順 1・2・2-0）、`stages/triage.md`（2-1 の止める判定と仕分け・2-2）、`declarations.md`（手順 3・3-b）、`stages/pass.md`（手順 4・5）。

## 入口

手順 3 で「主のリスク許容が必要」と判定したとき（まず 3-c の引き継ぎを試す）、手順 4 で主に動作確認を依頼したとき、`stages/triage.md` の仕分け表の順 5 に当たったとき、保留中の PR を再開するときに読む。

## 前提と理由（この段で使うもの）

- **リポ固有の仕組み**: このスキルはリポ非依存。保留の主向けミラーや投稿規約などのリポ固有の仕組みは「**存在すればそれに従い、無ければ各手順の縮退手順**」で扱う。

## 手順

#### 3-c. 前の HEAD の許容の引き継ぎ

手順 3 で「主のリスク許容が必要」と判定し、同じ PR の前の HEAD の宣言に主の許容が記録済みのときは、手順6で主に聞く前にその許容を新しい HEAD に引き継げるかを確かめる（main の取り込みだけで HEAD が動いたときに、同じリスクを主に聞き直さないため）。

前の宣言の選び方: 同じ PR の `## リスク宣言` コメントのうち、`主の回答: 許容` で始まる行（`主の回答: 許容（引き継ぎ）` を含む）と `真正性確認: 済` の行の両方を持つ最新 1 件を前の宣言とし、その `対象 HEAD:` の SHA を前 HEAD とする（最新の宣言が回答待ちでも、それを選ばない）。

```bash
bash <plugin>/scripts/risk-carryover-check.sh <前 HEAD> <新しい HEAD> <前の宣言の根拠ファイル>...   # --base の既定は origin/main。手順 1 の fetch と main の取り込みの後に回す
# 出力: CARRYOVER=yes|no / MAIN_MERGES=<件数> / RESOLVED_FILES=<衝突解消したファイル。無ければ none> / NG: <引き継げない理由>
# 終了コード: 0 = 引き継げる / 1 = 引き継げない / 2 = 引数・環境の不備（引き継げない側に倒す）
```

引き継げるのは次のすべてを満たすときだけ:

1. スクリプトが終了コード 0 を返す（差分が main の取り込みと版の行・CHANGELOG の並べ直しの衝突解消だけで、根拠ファイルが前後の HEAD で同一）
2. 前の宣言に `- 根拠ファイル:` の行がある。この行の無い宣言からは引き継げない（この手順より前の宣言を含む）
3. 引き継ぎの元が主の直接の回答で、捏造でない。前の宣言に `主の回答: 許容` 系の行と `真正性確認: 済` の行がある。引き継いだ宣言の回答リンクは主が許容を述べた元の直接の回答を指し、引き継ぎの記録（エージェントが書いた宣言コメント）を指さない。引き継ぎが 2 回以上続いても元の直接の回答のままにする。引き継ぐたびに、元の回答リンクに対して手順5の真正性確認（リンク先を開く・許容の意思を読む・GitHub コメントなら author を実測する）をやり直す
4. 新しい HEAD のレビュー結果から組み立てたリスク宣言の本文が、`対象 HEAD:` 行を除いて前の宣言の本文（末尾の `主の回答:` 以降の追記行を除いた部分）と同一である。比較は新しい HEAD の宣言を投稿する前に組み立てた本文で行う（リスク内容・該当する観点・発生条件・影響範囲と戻し方・根拠ファイルが同じかを、文の一致で確かめる）

引き継げるなら、前の宣言と同じ本文を新しい `対象 HEAD:` で投稿し、末尾に次の 4 行を追記する（`needs-approval` は付けずに手順4・5へ進む）:

```
主の回答: 許容（引き継ぎ） — <元の直接の回答リンク>（<元の回答の日時>）
引き継ぎ元: <前の HEAD の 40 桁フル SHA> の宣言 <前の宣言コメントのリンク>
引き継ぎの根拠: risk-carryover-check.sh 終了コード 0 — main の取り込み <件数> 件、衝突解消 <none またはファイル>、根拠ファイルの diff は空
真正性確認: 済 — 確認者 <エージェント名> / <日時>（元の回答を再確認）
```

1 つでも満たさなければ引き継がず、手順6で主に聞く。主への質問には、スクリプトの `NG:` 行（本文の不一致なら何が変わったか）を引き継げなかった理由として添えて手順6へ進む。

引き継ぎで省けるのは主への質問だけで、手順 2 のレビュー・手順 4 の証拠・手順 3-b の仕様宣言は新しい HEAD で出し直し、手順5の実測も省かない。これが手順1の「前回の合格部分を流用しない」と gate-runner.md の再レビューの「手順 1 から全工程をやり直す」に対する唯一の例外である。

### 6. 保留処理（リスク許容待ち / 動作確認依頼 / 切り出しの確認）

1. `agent-review:passed` は**付けない**。`needs-approval` を付ける（`gh api -X POST repos/$R/issues/$N/labels -f 'labels[]=needs-approval'`）。
2. リポに保留を主へミラーする仕組み（pending 管理ファイルとその同期スクリプト等）が**あればそれに従って記録する**。無ければ、PR の `needs-approval` ラベルと宣言コメントが保留の正本になる。
3. 主への確認依頼は、リポ/運用環境に投稿規約があればそれに従う。無ければ PR コメントに依頼を書き、利用可能な連絡チャネルで主に PR リンクを渡す。依頼の前に自力調査（プリフライト）を通す。develop の本体が止まる場合は、依頼に「返事は新しいセッションで `/develop <記録先>` と一緒に渡せる」ことを含める（引き継ぎのコメントは本体が書く。書式は develop/SKILL.md「保留で止まるときの引き継ぎ」が正本でここには書かない）。
4. **リスク承認を待つ間に手順4（動作確認）を並行して済ませておく**（承認が来た時点で手順5に直行できる。証拠の HEAD SHA が古くならないよう、待機中に push した場合は出し直す）。
5. 主の回答が来たら、**保留の種類ごとに次の復帰手順を踏む**（どちらも最後は手順5の合格条件を再確認してから合格処理する）:

| 保留の種類 | 主の回答 | 復帰手順 |
|---|---|---|
| **リスク許容待ち**（手順3） | 許容 | 許容を記録したあとに HEAD が動いたときは、主に聞き直す前に手順 3-c の引き継ぎを試す（条件は 3-c が正本）。回答をそのまま記録するときは、手順3の宣言コメントに `主の回答: 許容 — <回答リンク>（<日時>）` を**追記**する（宣言本文は書き換えない）→ 手順5の真正性確認を実施 → `needs-approval` を外して手順5へ |
| | 不許容 | 代替案へ切り替えて手順2からやり直すか、PR をクローズする。合格処理はしない。**`needs-approval` の扱い**: 代替案でリスク自体が消えるなら外す（＝保留理由の解消）／作り直し後も同じリスクが残るなら**付けたまま**にして再度許容を確認する。PR をクローズするならラベル状態は問わない |
| **動作確認代行待ち**（手順4） | 確認結果あり | 主の確認結果を**手順4の動作確認証拠として PR に記録**する（`対象 HEAD` / `実施者: 主` / 観測された結果 / 実施日時 / 主の回答リンク。受け入れ条件との対応も手順4の表と同じ形式で書く）→ `needs-approval` を外して手順5へ |
| | 期待どおりでない | `agent-review:failed` に付け替え、報告された症状を再現手順として書いて修正サイクルへ戻す。**`needs-approval` は外す**（主の代行は完了しており、保留理由は「主待ち」から「実装の欠陥」に変わったため。付けたままだと修正後も永久にマージされない） |
| **切り出しの確認**（手順2-1の仕分け表の順 5） | 切り出す | その指摘を follow-up issue に切って URL を PR コメントに記録する → **`needs-approval` を外す** → 未処理の順 6 の指摘が残っていれば `agent-review:failed` を付けずに Status `needs-decider` で return する（手順2-1の順 5 と順 6 の混在の段落）→ ほかに止める指摘が無ければ手順3以降へ |
| | この PR で直す | 主の回答リンクを PR コメントに記録する → **`needs-approval` を外す** → 未処理の順 6 の指摘が残っていれば failed にせず Status `needs-decider` で return する（裁定のあとにまとめて 1 回の failed で戻す）→ 残っていなければ `agent-review:failed` に付け替えて修正サイクルへ戻す（2周目以降なら次の周に入る。その周の終わりにも仕分け表を適用する） |

- 動作確認代行の場合、3点セットの3点目（自力検証できるようにする改善提案）は**復帰時に着手または issue 化まで進める**。出しただけで放置しない。
- **`needs-approval` を黙って持ち越さない。** 上の表のどの経路を通っても、その時点で
  「保留理由が解消したか」を必ず判断し、**外す / 付けたままにする のどちらかを明示的に選ぶ**。
  判断を書かずに次の工程へ進むことを禁じる（放置すると、合格しても auto-merge されないスタック PR になる）。

## 主に承認を求めてよい4分類（これ以外は設計違反）

| # | 分類 | 具体 |
|---|---|---|
| 1 | リスク許容の確認 | 手順3。実装中に発覚したものも発覚時点で確認する。手順2-1の仕分け表の順 5（この欠陥を残して切り出すか。推奨と見積もり付き）もここに入る |
| 2 | 動作確認の代行 | 手順4。自力検証不能時のみ・3点セット必須 |
| 3 | 好み・事業判断 | 答えがコードにも市場にも無く主の中にしかないもの（コピー・デザイン方向・価格） |
| 4 | 主名義の操作と聖域 | 外部アカウント・支払い・allowlist、マージ条件自体・憲法の変更 |

**やらないこと**:
- 「念のため確認」「マージしていいですか」「この方針で進めていいですか」——4分類のどれでもない確認を主に出さない。調べれば決まることは調べて決める。
- 選択肢を並べて主に判断を丸投げしない。推奨を出し、残リスクの許容だけを問う。
- リスク宣言を書かずに `agent-review:passed` を付けない。宣言の投稿と合格ラベルの順序を入れ替えない。
- 主の回答を待たずに保留 PR をマージしない。

## G として動くとき（develop）

この節は develop の G（`skills/develop/references/roles/gate-runner.md` の指示で動くゲート実行者）だけに関係する。develop 以外の読み手は読み飛ばしてよい。

### return の書式（保留）

`gate-runner.md`「return の書式」の共通欄（`## Gate Result` から `周回:` まで）のうしろに続ける。

```markdown
### 保留のとき
- 切り出しの確認（仕分け表の順 5。全周共通の判定で止める指摘が残り、順 1〜4 と順 6 のどれにも当たらない。周の数に関係なく、受け取ったその周で返す）: 引用した違反文（または例外 3 種のどれか）と対応する指摘、主への質問「この欠陥を残して切り出すか」と 4 点（欠陥がマージ後に何を起こすか・直す見積もり（行数・触るファイル・spec を変えるか）・別 issue にする固定費・推奨）。W の再開や3周目を提案しない。同じ周に順 2〜4 の指摘が混ざっていれば、それらも仕分け欄に載せて保留を先にする。順 6 の指摘が混ざっていれば、主への質問には含めず仕分け欄に「順 6・未裁定」として載せる（この PR で裁定を使い切っていれば「切り出す」として質問に含める。処理順は pr-review-gate 手順 2-1 の混在の段落）
- needs-approval の理由と、オーナーに依頼する 1 アクション（リスク許容の可否 / 動作確認の 3 点セット）
```

### この段で起こされたときの入力

保留の解除の G は、起動指示の前の段の `## Gate Result` ブロック（`次の段: 保留の解除`）と主の回答を受け取り、前の段の会話は持たない前提で PR コメントから保留の中身を読む。

- **許容済みの PR で HEAD が動いたとき**: 取り直しの手順 3 で再び「主のリスク許容が必要」になったら、主に聞く前に pr-review-gate 手順 3-c（前の HEAD の許容の引き継ぎ）を試す（条件と書式は 3-c が正本。この場合は合格処理の G がこのファイルを読んで試す）
- **保留の解除**: オーナーの回答（許容する／しない・動作確認の結果・切り出しの確認への回答（切り出す／この PR で直す））を受けて pr-review-gate の復帰手順に従う。復帰手順が別の段の作業に進むときは、その作業を自分で行わず Status `次の段へ` で返す。許容したとき・切り出して残りが無いときは `次の段: 合格処理`、許容せず代替案で手順 2 からやり直すときは `次の段: 前提確認と重さ判定` と書く。未処理の順 6 が残っていれば failed に進まない（`needs-approval` を外して `needs-decider` で返す。処理順は pr-review-gate 手順 2-1 の混在の段落）

## 出口

- 手順 6 の復帰手順の表に従う。表が「手順5へ」とする行は `stages/pass.md`、「手順2からやり直す」「手順3以降へ」とする行はそれぞれ `stages/prepare.md`・`declarations.md`、修正サイクルへ戻す行は `stages/triage.md`（failed の return）へ進む。
