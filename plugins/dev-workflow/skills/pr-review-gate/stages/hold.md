## 入口

手順 3 で「主のリスク許容が必要」と判定し 3-c の引き継ぎが成り立たなかったとき、手順 4 で主に動作確認を依頼したとき、仕分け表の順 5 に当たったとき、保留中の PR を再開するときに読む。手順 3 の issue で承認済みを当てた宣言はこの段に来ない（手順 4・5 へ進む）。

## 手順

### 6. 保留処理（リスク許容待ち / 動作確認依頼 / 切り出しの確認）

1. `agent-review:passed` は**付けない**。`needs-approval` を付ける（`gh api -X POST repos/$R/issues/$N/labels -f 'labels[]=needs-approval'`）。
2. リポに保留を主へミラーする仕組み（pending 管理ファイルとその同期スクリプト等）が**あればそれに従って記録する**。無ければ、`needs-approval` ラベルと宣言コメントが保留の正本。
3. 主への確認依頼は、リポ/運用環境に投稿規約があればそれに従う。無ければ PR コメントに依頼を書き、利用可能な連絡チャネルで主に PR リンクを渡す。依頼の文面は `~/.claude/output-styles/readable.md` の節 3 の型で書く。リスク宣言が論点なしのときは、依頼も論点なしの 3〜4 行で書き、宣言を写さない。依頼の前に自力調査（プリフライト）を通す。リスク許容の依頼には「返事は会話で返せばよく、PR へのコメントは要らない」ことを含める。会話で返事を受けたときは、主に PR へのコメントを求めない（手順5の「会話で受領」の形で記録する）。develop の本体が止まる場合は、起動指示の実行モードで返事の渡し方の案内を分ける。interactive（実行モードが無いときを含む）では、依頼に「返事は新しいセッションで `/develop <記録先>` と一緒に渡せる」ことを含める。channel では、依頼に「このチャンネルで記録先の番号を添えて返事をすれば続ける（例: `#<記録先> 許容する`）」ことを含め、新しいセッションを開く案内と `/develop` の打ち方は書かない。channel のリスク許容の依頼では、起動指示の `チャンネルの返事の確認:` の行が `可` でない（`不可` か、行が無い）ときに限り、「会話で返せばよく、PR へのコメントは要らない」の代わりに「末尾の PR にコメントで `許容する` と書く」と案内して PR のフル URL を添える（チャンネルの返事を `owner-reply-check.sh` で確かめられないため）（引き継ぎのコメントは本体が書く。書式は develop/references/handover.md が正本）。資格情報・安全ゲートの弱体化・エージェント権限の拡張に当たったのに手順 3 の issue で承認済みを当てられずにリスク許容を聞くときは、満たさなかった条件（4 分類を含む・引用できる目的の文が無い・承認の証拠が取れない・`agent-proposed`・実装中に発覚・無人運用や事後報告の届け先が無い経路、など）を依頼に 1 行添える。
4. **リスク承認を待つ間に手順4（動作確認）を並行して済ませておく**（承認が来た時点で手順5に直行できる。証拠の HEAD SHA が古くならないよう、待機中に push した場合は出し直す）。
5. 主の回答が来たら、保留の種類ごとの復帰手順（表と、`needs-approval` を黙って持ち越さない規則）は `stages/hold-resume.md` に従う。保留を返すだけの G は読まない。


## 主に承認を求めてよい4分類（これ以外は設計違反）

| # | 分類 | 具体 | 正本の主に聞く理由 |
|---|---|---|---|
| 1 | リスク許容の確認 | 手順3。実装中に発覚したものも発覚時点で確認する。手順2-1の仕分け表の順 5（この欠陥を残して切り出すか。推奨と見積もり付き）もここに入る | 主の側にしか答えが無い（どこまでの被害を許せるか） |
| 2 | 動作確認の代行 | 手順4。自力検証不能時のみ・3点セット必須 | 主の手でしかできない操作 |
| 3 | 好み・事業判断 | 答えがコードにも市場にも無く主の中にしかないもの（コピー・デザイン方向・価格） | 主の側にしか答えが無い |
| 4 | 主名義の操作と聖域 | 外部アカウント・支払い・allowlist、マージ条件自体・憲法の変更 | 主名義の操作は主の手でしかできない操作、聖域は決まりで主の承認が要る |

**やらないこと**:
- 「念のため確認」「マージしていいですか」「この方針で進めていいですか」——4分類のどれでもない確認を主に出さない。調べれば決まることは調べて決める。
- 選択肢を並べて主に判断を丸投げしない。推奨を出す（問いの書き方は `~/.claude/output-styles/readable.md` の節 3 の型）。
- リスク宣言を書かずに `agent-review:passed` を付けない。宣言の投稿と合格ラベルの順序を入れ替えない。
- 主の回答を待たずに保留 PR をマージしない。

## G として動くとき（develop）

### return の書式（保留）

```markdown
### 保留のとき
- 切り出しの確認（仕分け表の順 5。全周共通の判定で止める指摘が残り、順 1〜4 と順 6 のどれにも当たらない。周の数に関係なく、受け取ったその周で返す）: 引用した違反文（または例外 3 種のどれか）と対応する指摘、主への質問「この欠陥を残して切り出すか」と 4 点（欠陥がマージ後に何を起こすか・直す見積もり（行数・触るファイル・spec を変えるか）・別 issue にする固定費・推奨）。4 点は記録の項目で、本体が主に出す質問の文面は `~/.claude/output-styles/readable.md` の節 3 の型で書く。W の再開や3周目を提案しない。同じ周に順 2〜4 の指摘が混ざっていれば仕分け欄に載せて保留を先にする。順 6 の指摘が混ざっていれば、主への質問には含めず仕分け欄に「順 6・未裁定」として載せる（この PR で裁定を使い切っていれば「切り出す」として質問に含める。処理順は pr-review-gate 手順 2-1 の混在の段落）
- needs-approval の理由と、オーナーに依頼する 1 アクション（リスク許容の可否 / 動作確認の 3 点セット）

```

保留の解除の段で起こされたときの入力は `stages/hold-resume.md`。
