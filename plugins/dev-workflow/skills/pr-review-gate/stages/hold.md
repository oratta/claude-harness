# 保留 — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/prepare.md`（手順 1・2・2-0）、`stages/triage.md`（2-1 の止める判定と仕分け・2-2）、`declarations.md`（手順 3・3-b）、`stages/pass.md`（手順 4・5）。

## 入口

手順 3 で「主のリスク許容が必要」と判定したとき（まず 3-c の引き継ぎを試す）、手順 4 で主に動作確認を依頼したとき、`stages/triage.md` の仕分け表の順 5 に当たったとき、保留中の PR を再開するときに読む。手順 3 の issue で承認済みを当てた宣言はこの段に来ない（`needs-approval` を付けず、`stages/pass.md` の手順 4・5 へ進む）。

## 前提と理由（この段で使うもの）

- **リポ固有の仕組み**: このスキルはリポ非依存。保留の主向けミラーや投稿規約などのリポ固有の仕組みは「**存在すればそれに従い、無ければ各手順の縮退手順**」で扱う。

## 手順

#### 3-c. 前の HEAD の許容の引き継ぎ

手順 3 で「主のリスク許容が必要」と判定し、同じ PR の前の HEAD の宣言に主の許容が記録済みのときは、手順6で主に聞く前にその許容を新しい HEAD に引き継げるかを確かめる。目的は、main の取り込みや PR 自身の修正で HEAD が動いても、リスク宣言の中身（リスク内容・発生条件・影響範囲と戻し方）が前と同じなら、一度許容したリスクを主に聞き直さないこと。判定の基準はファイルが変わったかではなく、リスクの中身が同じかである。ただし前の HEAD のあとに積まれたのが main を取り込む merge commit だけのとき（スクリプトが終了コード 0 と `PR_COMMITS=0` を返す）は、衝突解消・根拠ファイルの差分・取り直しのレビューの範囲・判定役・新しい HEAD の宣言本文によらず引き継ぐ（主の判断、#1329）。

前の宣言の選び方: 同じ PR の `## リスク宣言` コメントのうち、`主の回答: 許容` で始まる行（`主の回答: 許容（引き継ぎ）` を含む）と `真正性確認: 済` の行の両方を持つ最新 1 件を前の宣言とし、その `対象 HEAD:` の SHA を前 HEAD とする（最新の宣言が回答待ちでも、それを選ばない）。

issue で承認済みの宣言（`declarations.md` 手順 3 の 3 行を追記したもの）は引き継ぎの元にしない（行頭が `主の回答: 許容` でないので上の選び方には拾われない。手順 5 の `確かめ直し: 済` の行も `真正性確認: 済` ではないので拾われない）。HEAD が動いたら、新しい HEAD で手順 3 を回し、同じ条件で issue で承認済みを判定し直す（主に聞いていないので、引き継ぐ回答が無い）。

```bash
bash <plugin>/scripts/risk-carryover-check.sh <前 HEAD> <新しい HEAD> <前の宣言の根拠ファイル>...   # --base の既定は origin/main。手順 1 の fetch と main の取り込みの後に回す
# 出力: CARRYOVER=yes|if-rereviewed|if-judged|no / MAIN_MERGES=<件数> / PR_COMMITS=<merge commit でない PR 自身の commit の件数>
#       / RESOLVED_FILES=<衝突解消したファイル。無ければ none>
#       / RESOLVED_OUTSIDE_ALLOWLIST=<許可リストの条件を満たさない衝突解消のファイル。1 行 1 件>
#       / EVIDENCE_MAIN_ONLY=<前後で変わったが PR 自身の差分は同じで、PR 自身の commit が触れていない根拠ファイル。1 行 1 件>
#       / EVIDENCE_PR_CHANGED=<PR 自身の差分が前後で違うか、PR 自身の commit が触れた根拠ファイル。1 行 1 件>
#       / EVIDENCE_DIFF_LINES=<EVIDENCE_PR_CHANGED のファイルの前後の diff の追加と削除の合計。無ければ 0> / NG: <引き継げない理由>
# 終了コード: 0 = 無条件で引き継げる（PR_COMMITS=0 = main の取り込みだけなら、許可リスト外の衝突解消があっても 0。根拠ファイルは比べず EVIDENCE_MAIN_ONLY・EVIDENCE_PR_CHANGED の行を出さない）
#             / 3 = PR 全体を見た取り直しのレビューを経ていれば引き継げる（下の条件 1）
#             / 4 = 根拠ファイルの PR 自身の差分が前後で違うか、PR 自身の commit が根拠ファイルに触れた（下の「終了コード 4 の判定役」に比べさせる）
#             / 1 = 引き継げない / 2 = 引数・環境の不備（引き継げない側に倒す）
# PR 自身の差分 = 各 HEAD と base の merge-base からのそのファイルの差分（main から入った変更を含まない）。比べ方は行の位置を見ないので、
#   PR 自身の commit が根拠ファイルに触れたら差分が同じでも 4 にする（行を動かしただけの修正を main 由来と取り違えないため）
```

引き継げるのは次のすべてを満たすときだけ:

1. スクリプトが終了コード 0 を返す（`PR_COMMITS` が 1 以上なら、積まれた merge commit が main の取り込みと版の行・CHANGELOG の並べ直しの衝突解消だけで、根拠ファイルの PR 自身の差分が前後で同じ。根拠ファイルに触れない PR 自身の commit はあってよい。`PR_COMMITS=0` なら、積まれたのが main を取り込む merge commit だけで、衝突解消の中身と根拠ファイルの差分は見ていない）。または終了コード 3 を返し（根拠ファイルの PR 自身の差分は前後で同じで、許可リストの条件を満たさない衝突解消がある）、新しい HEAD で取り直したレビューが PR 全体を見た周である。衝突解消の結果は PR の base との差分に現れるので、PR 全体を見たレビューがそれを読んでいれば許可リストの制限は要らない。確かめ方は次の 2 つ:
   - 最新の `レビュー重量:` コメントの `固定 HEAD:` が新しい HEAD の 40 桁 SHA と一致する
   - 受け取った前の段の Gate Result の `周回:` が `1` か、`（全体レビュー: …）` が添えられている。PR 全体を見る周はゲートの開始・CI の見張りのあとの取り直し・方式の書き換え後の全体レビューだが、取り直しは `周回:` を引き継ぐので、`周回:` が 2 以上で全体レビューの注記が無い周は W の修正後の差分限定の再レビューと見分けられない。見分けられない周は PR 全体を見た周として扱わない。HEAD の一致・`レビュー重量: full`・仕分けコメントが無いことだけから、PR 全体を見たレビュー済みと推定しない（どれも差分限定の再レビューや、戻した指摘が順 3 だけでレビューをせずに閉じた周でも成り立つ）
   終了コード 4（根拠ファイルの PR 自身の差分が前後で違うか、PR 自身の commit が根拠ファイルに触れた）は、下の「終了コード 4 の判定役」の判定の記録が `引き継ぎ判定: 同じ` のときだけ条件 1 を満たす。`RESOLVED_OUTSIDE_ALLOWLIST=` の行もあるときは、終了コード 3 と同じ確認（新しい HEAD で取り直したレビューが PR 全体を見た周である）も満たす必要がある。判定が「変わった」「判断できない」のとき、判定役に比べさせなかったときは条件 1 を満たさない。
   終了コード 0 で `PR_COMMITS=0` なら、`RESOLVED_OUTSIDE_ALLOWLIST=` の行があっても PR 全体を見た取り直しのレビューを求めない（新しい HEAD のレビューは差分限定の周でよい）。判定役も起こさない
2. 前の宣言に `- 根拠ファイル:` の行がある。この行の無い宣言からは引き継げない（この手順より前の宣言を含む）
3. 引き継ぎの元が主の直接の回答で、捏造でない。前の宣言に `主の回答: 許容` 系の行と `真正性確認: 済` の行がある。引き継いだ宣言の回答リンクは主が許容を述べた元の直接の回答を指し、引き継ぎの記録（エージェントが書いた宣言コメント）を指さない。引き継ぎが 2 回以上続いても元の直接の回答のままにする。引き継ぐたびに、元の回答リンクに対して手順5の真正性確認（リンク先を開く・許容の意思を読む・GitHub コメントなら author を実測する）をやり直す。元の直接の回答は会話で受けた回答（`会話で受領` の記録）でもよい。そのときは元の記録のセッション ID と原文で `owner-reply-check.sh` を回し直し、終了コード 0 で、記録の日時と同じ timestamp の `MATCH:` があり、その全文から許容の意思が読め、その timestamp が元の記録を最初に追記した宣言（`引き継ぎ元:` をたどった最初の宣言）の作成日時より後で、全文が別の PR・別のリスクを名指ししていないときだけ引き継ぐ（終了コード 0 でも同じ timestamp の `MATCH:` が無い、全文が `許容しない` への部分一致だった、などは引き継がない）。終了コードが 0 でなければ（この PC に会話ログが無い exit 2 を含む）引き継がず手順6で主に聞く。元の直接の回答はエピックの親経由で受けた回答（`親経由で受領` の記録）でもよい。そのときは元の記録の値で手順5の「親経由で受けた許容（親経由で受領）の真正性確認」の 1〜3（停止の記録のコメントの確かめ方・`owner-reply-check.sh --relayed` の終了コード 0 と記録の日時と同じ timestamp の `MATCH:`・全文から読む許容の意思と名指し）を確かめ直し、その timestamp が元の記録を最初に追記した宣言（`引き継ぎ元:` をたどった最初の宣言）の作成日時より後であるときだけ引き継ぐ。どれかを満たさないとき（`--relayed` の終了コードが 0 でないときを含む）は引き継がず手順6で主に聞く。元の直接の回答は主の委任で親経由に受けた回答（`親経由で受領（委任）` の記録）でもよい。`親経由で受領（委任）（親セッション ` で始まる行は委任の形、`親経由で受領（親セッション ` で始まる行は従来の形として見分ける。委任の形のときは、元の記録の値で手順5の「主の委任で親経由に受けた許容（親経由で受領（委任））の真正性確認」の 4（`owner-reply-check.sh --delegated` の終了コード 0・記録の日時と同じ timestamp の `MATCH:`・全文から読む任せる意思）を確かめ直し、引き継ぎの時点で同じ節の 2 の「委任が有効か」の文を満たし、停止の記録の作成日時が元の記録を最初に追記した宣言（`引き継ぎ元:` をたどった最初の宣言）の作成日時より後であるときだけ引き継ぐ。`--relayed` で確かめ直さない（委任の確認は停止の記録より前の発言なので必ず `not-after` で落ちる）。取り消し（エピックの最新の `主の委任:` で始まるコメントが `主の委任: 取り消し`）・新しい委任の記録がある・エピックが閉じた・記録が編集されたときを含め、どれかを満たさないときは引き継がず手順6で主に聞く
4. 新しい HEAD のレビュー結果から組み立てたリスク宣言の本文が、`対象 HEAD:` 行を除いて前の宣言の本文（末尾の `主の回答:` 以降の追記行を除いた部分）と同一である。比較は新しい HEAD の宣言を投稿する前に組み立てた本文で行う（リスク内容・該当する観点・発生条件・影響範囲と戻し方・根拠ファイルが同じかを、文の一致で確かめる）。終了コード 0 で `PR_COMMITS=0` ならこの条件は求めない

引き継げるなら、前の宣言と同じ本文を新しい `対象 HEAD:` で投稿し、末尾に次の 4 行を追記する（`needs-approval` は付けずに手順4・5へ進む）。終了コード 0 で `PR_COMMITS=0` のとき（条件 4 を求めないとき）も、投稿する本文は前の宣言の本文のままにし、新しい HEAD のレビューから組み立てた本文に置き換えない:

```
主の回答: 許容（引き継ぎ） — <元の直接の回答リンク>（<元の回答の日時>）
引き継ぎ元: <前の HEAD の 40 桁フル SHA> の宣言 <前の宣言コメントのリンク>
引き継ぎの根拠: risk-carryover-check.sh 終了コード <0・3・4 のどれか> — main の取り込み <件数> 件、PR 自身の commit <PR_COMMITS の値> 件、衝突解消 <none またはファイル>、許可リスト外 <none またはファイル>、根拠ファイル <diff は空のファイル / main からの変更だけ: EVIDENCE_MAIN_ONLY のファイル / 終了コード 4 のとき: PR 自身の差分が変わったか PR 自身の commit が触れた EVIDENCE_PR_CHANGED のファイル、差分 <EVIDENCE_DIFF_LINES の値> 行、判定 同じ <判定の記録のリンク> / PR_COMMITS=0 のとき: 比べず（PR 自身の commit 0 件）。該当するものを並べて書く>、取り直しのレビュー <終了コード 3 のとき・終了コード 4 で許可リスト外があるとき: 固定 HEAD <40 桁フル SHA>（周回 <値と注記>） <その レビュー重量 コメントのリンク>。終了コード 0 のとき: 不要。終了コード 4 で許可リスト外が none のときも不要>
真正性確認: 済 — 確認者 <エージェント名> / <日時>（元の回答を再確認）
```

元の回答が会話で受けたものなら、4 行の構造はそのままにして、1 行目の `<元の直接の回答リンク>（<元の回答の日時>）` の部分を元の記録の `会話で受領（セッション <セッション ID> / <日時>）原文: <原文>` に置き換える（`主の回答: 許容（引き継ぎ） — 会話で受領（セッション … / …）原文: …`）。元の回答が親経由で受けたものなら、同じく 1 行目の `<元の直接の回答リンク>（<元の回答の日時>）` の部分を元の記録の `親経由で受領（親セッション <セッション ID> / 発言 <uuid> / <日時>）停止の記録: <URL> 原文: <原文>` に置き換える（`主の回答: 許容（引き継ぎ） — 親経由で受領（親セッション … / 発言 … / …）停止の記録: … 原文: …`）。元の回答が主の委任で親経由に受けたものなら、同じく 1 行目の `<元の直接の回答リンク>（<元の回答の日時>）` の部分を元の記録の `親経由で受領（委任）（親セッション <セッション ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <原文>` に置き換える（`主の回答: 許容（引き継ぎ） — 親経由で受領（委任）（親セッション … / 委任の確認 … / …）委任の記録: … 停止の記録: … 原文: …`）。1 行目の形は回答リンク・`会話で受領`・`親経由で受領`・`親経由で受領（委任）` の 4 つで、どの形でも追記は 4 行のままにする。

1 つでも満たさなければ引き継がず、手順 3 の issue で承認済みを試し（`declarations.md` の出口の順）、それも当たらなければ手順6で主に聞く。主への質問には、スクリプトの `NG:` 行（本文の不一致なら何が変わったか）を引き継げなかった理由として添えて手順6へ進む。終了コード 4 のときは、`EVIDENCE_PR_CHANGED=` の行（どの根拠ファイルの PR 自身の差分が変わったか、PR 自身の commit が触れたか）と、判定の理由（判定の記録が `引き継ぎ判定: 変わった` か `引き継ぎ判定: 判断できない` のときはその `理由:`）か判定役に比べさせなかった理由（ほかの条件を満たさない・差分が 100 行を超えた・従来経路の一括の G で判定役を起こせない、など）を添えて手順6へ進む。終了コード 3 で条件 1 の取り直しのレビューを確かめられなかったときは、`RESOLVED_OUTSIDE_ALLOWLIST=` の行と、PR 全体を見たレビューを確かめられなかったこと（`周回:` の値）を理由に添える。

引き継ぎで省けるのは主への質問だけで、手順 2 のレビュー・手順 4 の証拠・手順 3-b の仕様宣言は新しい HEAD で出し直し、手順5の実測も省かない。これが手順1の「前回の合格部分を流用しない」と gate-runner.md の再レビューの「手順 1 から全工程をやり直す」に対する唯一の例外である。

##### 終了コード 4 の判定役

終了コード 4 は、根拠ファイルの PR 自身の差分が前後で違うか、PR 自身の commit が根拠ファイルに触れたことしか示さない。リスク宣言の中身が前と同じかは、作業の文脈を持たない判定役に比べさせる。

- **回す条件**: スクリプトが終了コード 4 を返し、条件 2〜4 を満たし、`RESOLVED_OUTSIDE_ALLOWLIST=` の行があるときは条件 1 の終了コード 3 と同じ確認（新しい HEAD で取り直したレビューが PR 全体を見た周である）も満たし、`EVIDENCE_DIFF_LINES=` が 100 以下（100 ちょうどは判定させる）で、下の記録の選び方で使える記録が無いときだけ回す。どれかを満たさなければ判定役を起こさず手順6で主に聞く（使える記録があるときは、判定役を起こさずその記録で条件 1 を決める）
- **判定役**: `subagent_type: dev-workflow:decider`・`model: opus` で起こす（残量モードで上げも下げもしない）
- **起こすセッションの区別**: develop の外のメインセッションでは、ゲート自身が Agent ツールで判定役を起こし、判定の記録を PR に投稿して 3-c を続ける。develop の合格処理の G は判定役を起こせないので、回す条件を満たしたら宣言を投稿せず `needs-approval` も付けずに、Status `needs-carryover-judge`・`次の段: 合格処理` で返す（本体が判定役を起こして記録を投稿し、合格処理の G を新しく起こす。return の欄は下の「G として動くとき（develop）」節）。従来経路の一括の G（`段: 一括（従来経路）`）は判定役を起こさず手順6で主に聞く（呼び出し元が Status を受けて決める役を起こす約束が無いため）
- `SHARED_BUDGET_MODE=depleted` のときは判定役を起こさず、判定役を起こす側（develop の外のメインセッションではゲート自身、develop では本体）が `引き継ぎ判定: 判断できない`・`理由: 判定役を起こさなかった（共有枠 depleted）` の記録を投稿し、手順6で主に聞く側に倒す。develop の合格処理の G は depleted でも `needs-carryover-judge` で返し、この記録を自分で投稿しない（本体の投稿と二重になるのを避ける。記録を受けて起こされた次の合格処理の G が手順6で主に聞く）
- **渡すもの**: `git diff --no-color --no-ext-diff --no-textconv <前 HEAD> <新しい HEAD> -- <EVIDENCE_PR_CHANGED のファイル>...` の出力と、前の宣言の本文（末尾の `主の回答:` 以降の追記行を除いた部分）の 2 つだけ。記録先の本文・レビューの指摘・W の return・作業の会話は渡さない（主の承認を省いてよいかを、作業した側の説明に引きずられずに決めるため）
- **依頼文**: `agents/decider.md` の通常の 3 点（原因の分類・直し方・次のモデル）ではなく、次を求める。渡した 2 つだけから判定し、リポジトリを読み足さず、足りなければ「判断できない」と返す。返答の 1 行目は `引き継ぎ判定: 同じ`・`引き継ぎ判定: 変わった`・`引き継ぎ判定: 判断できない` のどれかちょうどにし、2 行目以降に理由（何が同じか・何が変わったか・何が足りないか）を書く。`agents/decider.md` の入力契約の 4 点（記録先の本文・失敗の出力・対象ファイルのパス・実行役の return）はこの依頼には当てはまらず、渡した 2 つだけが入力であることも依頼文に書き、不足を理由に `不足:` で返さず 1 行目を必ず上の 3 形のどれかにするよう求める（入力契約に従って `不足:` で返されると、毎回「判断できない」に倒れてこの経路が一度も効かないため）
- 「同じ」は、差分によって前の宣言のリスク内容・該当する観点・発生条件・影響範囲と戻し方のどれも変わらないことを指す
- 返答の 1 行目が 3 形のどれにも一致しなければ「判断できない」として記録し、依頼し直さない（主に聞く側に倒れるだけで、補える入力も無いため）
- **判定の記録**: 判定役を起こしたセッション（develop では本体）が、返答を次の書式で PR にコメントする（判定役は投稿できないので代理投稿する）。1 行目は正規表現 `^引き継ぎ判定: (同じ|変わった|判断できない)$` に完全一致させる。`根拠ファイル:` は `EVIDENCE_PR_CHANGED=` のファイルを 1 行にカンマ区切りで並べる。`対象 HEAD:` の文字列は使わない（auto-merge の workflow が宣言の照合に使うため）

```text
引き継ぎ判定: <同じ|変わった|判断できない>
前 HEAD: <40 桁フル SHA>
新しい HEAD: <40 桁フル SHA>
前の宣言: <前の宣言コメントのリンク>
根拠ファイル: <EVIDENCE_PR_CHANGED のファイル>, <ファイル>
差分の行数: <EVIDENCE_DIFF_LINES の値>
判定役: dev-workflow:decider / <モデル。起こさなかったときは「起こさず」> / 代理投稿 <投稿したセッションか本体の名前>
理由: <判定役の返答の 2 行目以降。起こさなかったときはその理由>
```

- **記録の選び方**: 同じ PR の 1 行目が `引き継ぎ判定:` のコメントのうち、`前 HEAD:` と `新しい HEAD:` が今回の前 HEAD・新しい HEAD の 40 桁と一致し、`根拠ファイル:` のファイルがスクリプトの `EVIDENCE_PR_CHANGED=` の行のファイルと（カンマで区切った各要素の前後の空白を除いたうえで）順序を問わず同じ集合のものの最新 1 件だけを使う。一致しない記録は使わない（HEAD が動いたあとの古い判定を使わない）。一致する記録があれば、同じ組で判定役を起こし直さない（develop の G は `needs-carryover-judge` を返し直さない）。1 行目が上の正規表現に一致しない記録は「判断できない」と同じに扱う。記録が `引き継ぎ判定: 同じ` なら条件 1 を満たし、引き継ぎの根拠の行にその記録のリンクを書く。判定を受けて起こされた合格処理の G（前の Gate Result が `段: 合格処理`・Status `needs-carryover-judge`）が今回の組に一致する記録を見つけられないときは、`needs-carryover-judge` を返し直さず「判断できない」と同じに扱い、本体が投稿した記録のリンク（見つからなければその旨）と、その HEAD か根拠ファイルが今回の組と一致しないことを理由に添えて手順6で主に聞く（同じ組で判定役を何度も起こさないため）
- 守備範囲: 判定役が差分を読み違えて変わったリスクを「同じ」と判定すること、1 回ずつは小さい引き継ぎが積もってリスクの中身が変わること、記録が本当に判定役の返答かどうか（G は記録の HEAD と根拠ファイルの一致だけを確かめる）、判定役の返答の 2 行目以降（理由）の妥当性は、この手順では止めない。条件 4 の本文の一致と新しい HEAD のレビューは引き継いでも残る

### 6. 保留処理（リスク許容待ち / 動作確認依頼 / 切り出しの確認）

1. `agent-review:passed` は**付けない**。`needs-approval` を付ける（`gh api -X POST repos/$R/issues/$N/labels -f 'labels[]=needs-approval'`）。
2. リポに保留を主へミラーする仕組み（pending 管理ファイルとその同期スクリプト等）が**あればそれに従って記録する**。無ければ、PR の `needs-approval` ラベルと宣言コメントが保留の正本になる。
3. 主への確認依頼は、リポ/運用環境に投稿規約があればそれに従う。無ければ PR コメントに依頼を書き、利用可能な連絡チャネルで主に PR リンクを渡す。依頼の文面（問いの順・聞く理由・リスクの書き方・1 行目と答え方の行）は `~/.claude/output-styles/readable.md` の節 3（主に問いを返す文章の書き方の正本）の型で書き、ここには投稿先と案内の中身だけを置く。リスク宣言が論点なし（分類に当たっただけで、新たに生じるリスクが無い）のときは、依頼も論点なしの 3〜4 行で書き、宣言を写さない（返事の渡し方の案内は答え方の行に畳み、満たさなかった条件は区切りの下に置く）（宣言の書き分けは `declarations.md` の手順 3）。依頼の前に自力調査（プリフライト）を通す。リスク許容の依頼には「返事は会話で返せばよく、PR へのコメントは要らない」ことを含める。会話で返事を受けたときは、主に PR へのコメントを求めない（手順5の「会話で受領」の形で記録する）。develop の本体が止まる場合は、起動指示の実行モードで返事の渡し方の案内を分ける。interactive（起動指示に実行モードが無いときを含む）では、依頼に「返事は新しいセッションで `/develop <記録先>` と一緒に渡せる」ことを含める。channel では、依頼に「このチャンネルで記録先の番号を添えて返事をすれば続ける（例: `#<記録先> 許容する`）」ことを含め、新しいセッションを開く案内と `/develop` の打ち方は書かない（channel の主はチャンネルだけを見ていて、住人の新しいセッションを開けない）。channel のリスク許容の依頼では、起動指示の `チャンネルの返事の確認:` の行が `可` でない（`不可` か、行が無い）ときに限り、「会話で返せばよく、PR へのコメントは要らない」の代わりに「末尾の PR にコメントで `許容する` と書く」と案内して PR のフル URL を添える（チャンネルの返事を `owner-reply-check.sh` で確かめられないため。行が無いときを不可に倒すのは、PR のコメントならどの環境でも確かめられるため）（引き継ぎのコメントは本体が書く。書式は develop/references/handover.md が正本でここには書かない）。資格情報・安全ゲートの弱体化・エージェント権限の拡張に当たったのに手順 3 の issue で承認済みを当てられずにリスク許容を聞くときは、満たさなかった条件（4 分類を含む・引用できる目的の文が無い・承認の証拠が取れない・`agent-proposed`・実装中に発覚・無人運用や事後報告の届け先が無い経路、など）を依頼に 1 行添える。
4. **リスク承認を待つ間に手順4（動作確認）を並行して済ませておく**（承認が来た時点で手順5に直行できる。証拠の HEAD SHA が古くならないよう、待機中に push した場合は出し直す）。
5. 主の回答が来たら、**保留の種類ごとに次の復帰手順を踏む**（どちらも最後は手順5の合格条件を再確認してから合格処理する）:

| 保留の種類 | 主の回答 | 復帰手順 |
|---|---|---|
| **リスク許容待ち**（手順3） | 許容 | 許容を記録したあとに HEAD が動いたときは、主に聞き直す前に手順 3-c の引き継ぎを試す（条件は 3-c が正本）。回答をそのまま記録するときは、手順3の宣言コメントに `主の回答: 許容 — <回答リンク>（<日時>）` を**追記**する（宣言本文は書き換えない）。会話で受けた回答なら、主に PR へのコメントを求めず、本体から渡されたセッション ID・日時・原文で `主の回答: 許容 — 会話で受領（セッション <セッション ID> / <日時>）原文: <原文>` を追記する。エピックの親経由で受けた回答（develop の本体が `owner-reply-check.sh --relayed` の終了コード 0 を確かめて渡したもの）なら、渡された親のセッション ID・uuid・日時・停止の記録の URL・原文で `主の回答: 許容 — 親経由で受領（親セッション <セッション ID> / 発言 <uuid> / <日時>）停止の記録: <URL> 原文: <原文>` を追記してから手順5の親経由で受けた許容の真正性確認に進む。主の委任で親経由に受けた回答（develop の本体が `owner-reply-check.sh --delegated` の終了コード 0 を確かめて渡したもの）なら、渡された親のセッション ID・確認の uuid・日時・委任の記録の URL・停止の記録の URL・原文で `主の回答: 許容 — 親経由で受領（委任）（親セッション <セッション ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <原文>` を追記してから手順5の主の委任で親経由に受けた許容の真正性確認に進む → 手順5の真正性確認を実施 → `needs-approval` を外して手順5へ |
| | 不許容 | 代替案へ切り替えて手順2からやり直すか、PR をクローズする。合格処理はしない。**`needs-approval` の扱い**: 代替案でリスク自体が消えるなら外す（＝保留理由の解消）／作り直し後も同じリスクが残るなら**付けたまま**にして再度許容を確認する。PR をクローズするならラベル状態は問わない |
| **動作確認代行待ち**（手順4） | 確認結果あり | 主の確認結果を**手順4の動作確認証拠として PR に記録**する（`対象 HEAD` / `実施者: 主` / 観測された結果 / 実施日時 / 主の回答リンク。受け入れ条件との対応も手順4の表と同じ形式で書く）→ `needs-approval` を外して手順5へ |
| | 期待どおりでない | `agent-review:failed` に付け替え、報告された症状を再現手順として書いて修正サイクルへ戻す。**`needs-approval` は外す**（主の代行は完了しており、保留理由は「主待ち」から「実装の欠陥」に変わったため。付けたままだと修正後も永久にマージされない） |
| **切り出しの確認**（手順2-1の仕分け表の順 5） | 切り出す | その指摘を捨てずに follow-up issue に切って URL を PR コメントに記録する（置き場所は `stages/triage.md` 手順2-1の「主が切り出すと答えた止める指摘の置き場所」の段落で決める。エピックの完了条件に効くなら段 C の表、それ以外はエピックの外の新しい issue）→ **`needs-approval` を外す** → 未処理の順 6 の指摘が残っていれば `agent-review:failed` を付けずに Status `needs-decider` で return する（手順2-1の順 5 と順 6 の混在の段落）→ ほかに止める指摘が無ければ手順3以降へ |
| | この PR で直す | 主の回答リンクを PR コメントに記録する → **`needs-approval` を外す** → 未処理の順 6 の指摘が残っていれば failed にせず Status `needs-decider` で return する（裁定のあとにまとめて 1 回の failed で戻す）→ 残っていなければ `agent-review:failed` に付け替えて修正サイクルへ戻す（2周目以降なら次の周に入る。その周の終わりにも仕分け表を適用する） |

- 動作確認代行の場合、3点セットの3点目（自力検証できるようにする改善提案）は**復帰時に着手または issue 化まで進める**。出しただけで放置しない。
- **`needs-approval` を黙って持ち越さない。** 上の表のどの経路を通っても、その時点で
  「保留理由が解消したか」を必ず判断し、**外す / 付けたままにする のどちらかを明示的に選ぶ**。
  判断を書かずに次の工程へ進むことを禁じる（放置すると、合格しても auto-merge されないスタック PR になる）。

## 主に承認を求めてよい4分類（これ以外は設計違反）

4 分類は、`~/.claude/output-styles/readable.md` の節 3 の「主に聞く理由」の 3 つのどれに当たるかを、ゲートの場面に合わせて細かく決めたものである（右端の列）。

| # | 分類 | 具体 | 正本の主に聞く理由 |
|---|---|---|---|
| 1 | リスク許容の確認 | 手順3。実装中に発覚したものも発覚時点で確認する。手順2-1の仕分け表の順 5（この欠陥を残して切り出すか。推奨と見積もり付き）もここに入る | 主の側にしか答えが無い（どこまでの被害を許せるか） |
| 2 | 動作確認の代行 | 手順4。自力検証不能時のみ・3点セット必須 | 主の手でしかできない操作 |
| 3 | 好み・事業判断 | 答えがコードにも市場にも無く主の中にしかないもの（コピー・デザイン方向・価格） | 主の側にしか答えが無い |
| 4 | 主名義の操作と聖域 | 外部アカウント・支払い・allowlist、マージ条件自体・憲法の変更 | 主名義の操作は主の手でしかできない操作、聖域は決まりで主の承認が要る |

**やらないこと**:
- 「念のため確認」「マージしていいですか」「この方針で進めていいですか」——4分類のどれでもない確認を主に出さない。調べれば決まることは調べて決める。
- 選択肢を並べて主に判断を丸投げしない。推奨を出す（問いの書き方は `~/.claude/output-styles/readable.md` の節 3 の型）。
- リスク宣言を書かずに `agent-review:passed` を付けない。宣言の投稿と合格ラベルの順序を入れ替えない。
- 主の回答を待たずに保留 PR をマージしない。

## G として動くとき（develop）

この節は develop の G（`skills/develop/references/roles/gate-runner.md` の指示で動くゲート実行者）だけに関係する。develop 以外の読み手は読み飛ばしてよい。

### return の書式（保留・needs-carryover-judge）

`gate-runner.md`「return の書式」の共通欄（`## Gate Result` から `周回:` まで）のうしろに続ける。

```markdown
### 保留のとき
- 切り出しの確認（仕分け表の順 5。全周共通の判定で止める指摘が残り、順 1〜4 と順 6 のどれにも当たらない。周の数に関係なく、受け取ったその周で返す）: 引用した違反文（または例外 3 種のどれか）と対応する指摘、主への質問「この欠陥を残して切り出すか」と 4 点（欠陥がマージ後に何を起こすか・直す見積もり（行数・触るファイル・spec を変えるか）・別 issue にする固定費・推奨）。4 点は記録の項目で、本体が主に出す質問の文面は `~/.claude/output-styles/readable.md` の節 3 の型で書く。W の再開や3周目を提案しない。同じ周に順 2〜4 の指摘が混ざっていれば、それらも仕分け欄に載せて保留を先にする。順 6 の指摘が混ざっていれば、主への質問には含めず仕分け欄に「順 6・未裁定」として載せる（この PR で裁定を使い切っていれば「切り出す」として質問に含める。処理順は pr-review-gate 手順 2-1 の混在の段落）
- needs-approval の理由と、オーナーに依頼する 1 アクション（リスク許容の可否 / 動作確認の 3 点セット）

### needs-carryover-judge のとき
（手順 3-c の「終了コード 4 の判定役」の回す条件を満たし、使える判定の記録が無い。宣言は投稿せず、`needs-approval` も付けない。`次の段: 合格処理`）
- 前 HEAD: <40 桁フル SHA> / 新しい HEAD: <40 桁フル SHA>
- 前の宣言のコメントのリンク: <URL>
- EVIDENCE_PR_CHANGED=: <ファイル>, <ファイル>
- EVIDENCE_DIFF_LINES=: <値>
```

### この段で起こされたときの入力

保留の解除の G は、起動指示の前の段の `## Gate Result` ブロック（`次の段: 保留の解除`）と主の回答を受け取り、前の段の会話は持たない前提で PR コメントから保留の中身を読む。

- **許容済みの PR で HEAD が動いたとき**: 取り直しの手順 3 で再び「主のリスク許容が必要」になったら、主に聞く前に pr-review-gate 手順 3-c（前の HEAD の許容の引き継ぎ）を試す（条件と書式は 3-c が正本。この場合は合格処理の G がこのファイルを読んで試す）。スクリプトが終了コード 4 を返し、3-c の「終了コード 4 の判定役」の回す条件を満たし、使える判定の記録が無いときは、合格処理の G は判定役を起こせないので Status `needs-carryover-judge` で返す（欄は上の「needs-carryover-judge のとき」）
- **保留の解除**: オーナーの回答（許容する／しない・動作確認の結果・切り出しの確認への回答（切り出す／この PR で直す））を受けて pr-review-gate の復帰手順に従う。復帰手順が別の段の作業に進むときは、その作業を自分で行わず Status `次の段へ` で返す。許容したとき・切り出して残りが無いときは `次の段: 合格処理`、許容せず代替案で手順 2 からやり直すときは `次の段: 前提確認と重さ判定` と書く。未処理の順 6 が残っていれば failed に進まない（`needs-approval` を外して `needs-decider` で返す。処理順は pr-review-gate 手順 2-1 の混在の段落）

## 出口

- 手順 6 の復帰手順の表に従う。表が「手順5へ」とする行は `stages/pass.md`、「手順2からやり直す」「手順3以降へ」とする行はそれぞれ `stages/prepare.md`・`declarations.md`、修正サイクルへ戻す行は `stages/triage.md`（failed の return）へ進む。
