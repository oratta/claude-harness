# no-point-check — pr-review-gate

#### 論点なしの確認（論点なしの宣言を決める役が確かめる）

`論点なし — ` の行を持つ「主のリスク許容が必要」の宣言は、手順6で主に聞く前に、決める役（`subagent_type: dev-workflow:decider`・`model: opus`）に論点なしで合っているかを確かめさせる（論点なしの確認）。宣言を書いた G の判定だけで通すと、論点ありを論点なしと書き誤ったときの歯止めが無くなるためである。エピックの子でも決める役が確かめ、親は確かめない。`論点あり — ` の行を持つ宣言はこの確認に回さず、手順6で主の許容を待つ。この確認はマージの経路を変えない（聖域のパスに触れた PR は、合格しても `auto-merge.yml` が `human-merge` で人間のマージに回す）。

誰が決める役を起こすか・渡すもの・PR に投稿する記録の書式は `stages/no-point-check.md` の「6-0. 論点なしの宣言の確認」が正本。確認の結果ごとの後続は次のとおり。

- 通す → 手順 4・5（同じ HEAD・同じ宣言の URL の `論点なしの確認: 通す` の記録が、手順 5 の合格条件の表で許容済みとして扱われる）
- 論点あり → 宣言を `論点あり — ` の形で投稿し直して手順 6
- 判断できない → 宣言を変えずに手順 6


#### 6-0. 論点なしの宣言の確認（主に聞く前）

「主のリスク許容が必要」の宣言が `論点なし — ` の行を持つとき（3-c で引き継げず、issue で承認済みも当たらなかったとき）は、下の 1 に進む前にこの確認を回す。`論点あり — ` の行を持つ宣言はこの確認に回さない（下の 1 から主の許容を待つ）。確認者は決める役（`subagent_type: dev-workflow:decider`・`model: opus` を明示。残量モードで上げも下げもしない）だけで、エピックの子でも同じにする。親（エピック）は確かめない。

- **起こす役**: develop の G は決める役を起こせないので、宣言を投稿したら `needs-approval` を付けずに Status `needs-no-point-check`・`次の段: 合格処理` で返す（return の欄は下の「G として動くとき（develop）」節。本体が決める役を起こし、記録を投稿して合格処理の G を新しく起こす）。develop の外のゲートは自分で決める役を起こす（Agent ツール）。従来経路の一括の G（`段: 一括（従来経路）`）は確認に回さず、手順 6 で主に聞く（呼び出し元が Status を受けて決める役を起こす約束が無いため）
- **渡すもの**: 宣言の本文と PR の差分だけ（`gh pr diff $N --repo $R`）。会話の経緯・G の判断の理由・W の return は渡さない（作業した側の説明に引きずられずに決めるため）
- **依頼文**: 渡した 2 つだけから、7 観点の分類に当たっただけで、この変更を入れることで新たに生じるリスクが無いかを判定させる。リポジトリを読み足させず、`不足:` で返させない（`agents/decider.md` の入力契約はこの依頼に当てはまらない）。返答は次の 2 行にさせる。1 行目は `判定: 論点なし`・`判定: 論点あり`・`判定: 判断できない` のどれかちょうどで、どれにも一致しなければ `判断できない` として扱い、依頼し直さない

```text
判定: 論点なし|論点あり|判断できない
理由: <1 行>
```

- **記録**: 決める役を起こしたセッション（develop では本体、develop の外ではゲートを回すセッション）が、宣言コメントへの追記ではなく PR の別のコメントとして次の本文を投稿する（`判定: 論点なし` は `通す` と書く）。1 行目は `主の回答:` で始まらないので、手順 3-c はこの記録を引き継ぎの元にしない。`対象 HEAD:` は宣言と同じ 40 桁を書く

```text
論点なしの確認: 通す|論点あり|判断できない
対象 HEAD: <40 桁フル SHA>
宣言: <宣言コメントの URL>
確認者: dev-workflow:decider（<エージェント名>）
根拠: <決める役の理由の 1 行>
```

- `SHARED_BUDGET_MODE=depleted` のときは決める役を起こさず、起こす側が `論点なしの確認: 判断できない`・`根拠: 決める役を起こさなかった（共有枠 depleted）` の記録を投稿する。develop の G は depleted でも `needs-no-point-check` で返し、記録を自分で投稿しない
- **結果ごとの後続**: `通す` なら手順 6 に入らず `stages/pass.md` の手順 4・5 へ進む（同じ HEAD・同じ宣言の URL の記録が合格条件の表で許容済みとして扱われる）。`論点あり` なら G は宣言を `論点あり — ` の形で投稿し直して手順 6（下の 1 から）。`判断できない` なら宣言を変えずに手順 6
- **記録の選び方**: 同じ PR の 1 行目が `論点なしの確認:` で、投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれかのコメントのうち、`対象 HEAD:` が今の HEAD の 40 桁と、`宣言:` が今の HEAD の宣言コメントの URL と一致する最新 1 件だけを使う。一致する記録があれば決める役を起こし直さない（develop の G は `needs-no-point-check` を返し直さない）。記録を受けて起こされた合格処理の G（前の Gate Result が `段: 合格処理`・Status `needs-no-point-check`）が一致する記録を見つけられないときは、`needs-no-point-check` を返し直さず手順 6 で主に聞く（同じ宣言で決める役を何度も起こさないため）


needs-no-point-check の return の欄は `stages/hold.md` の同名節にある。
