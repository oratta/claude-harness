# 前の HEAD の許容の引き継ぎ（手順 3-c）— pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。

## 入口

手順 3 で「主のリスク許容が必要」と判定し、同じ PR の前の HEAD の宣言に主の許容が記録済みのときに読む（まず 3-c の引き継ぎを試す）。引き継げなければ `stages/hold.md` の手順 6 へ進む。手順 3 の issue で承認済みを当てた宣言はこの手順に来ない。

## 手順

#### 3-c. 前の HEAD の許容の引き継ぎ

手順 3 で「主のリスク許容が必要」と判定し、同じ PR の前の HEAD の宣言に主の許容が記録済みのときは、手順6で主に聞く前にその許容を新しい HEAD に引き継げるかを確かめる。目的は、main の取り込みや PR 自身の修正で HEAD が動いても、リスク宣言の中身（リスク内容・発生条件・影響範囲と戻し方）が前と同じなら、一度許容したリスクを主に聞き直さないこと。判定の基準はファイルが変わったかではなく、リスクの中身が同じかである。ただし前の HEAD のあとに積まれたのが main を取り込む merge commit だけのとき（スクリプトが終了コード 0 と `PR_COMMITS=0` を返す）は、衝突解消・根拠ファイルの差分・取り直しのレビューの範囲・判定役・新しい HEAD の宣言本文によらず引き継ぐ（主の判断、#1329。条件 2 の根拠ファイルの行と条件 3 の真正性確認のやり直しは残る）。

前の宣言の選び方: 同じ PR の `## リスク宣言` コメントのうち、`主の回答: 許容` で始まる行（`主の回答: 許容（引き継ぎ）` を含む）と `真正性確認: 済` の行の両方を持つ最新 1 件を前の宣言とし、その `対象 HEAD:` の SHA を前 HEAD とする（最新の宣言が回答待ちでも、それを選ばない）。

issue で承認済みの宣言（`declarations.md` 手順 3 の 3 行を追記したもの）は引き継ぎの元にしない（行頭が `主の回答: 許容` でも `真正性確認: 済` でもないので上の選び方に拾われない）。HEAD が動いたら、新しい HEAD で手順 3 を回し、同じ条件で issue で承認済みを判定し直す。

```bash
bash <plugin>/scripts/risk-carryover-check.sh <前 HEAD> <新しい HEAD> <前の宣言の根拠ファイル>...   # --base の既定は origin/main。手順 1 の fetch と main の取り込みの後に回す
# 出力: CARRYOVER=yes|if-rereviewed|if-judged|no / MAIN_MERGES=<件数> / PR_COMMITS=<merge commit でない PR 自身の commit の件数>
#       / RESOLVED_FILES=<衝突解消したファイル。無ければ none>
#       / RESOLVED_OUTSIDE_ALLOWLIST=<許可リストの条件を満たさない衝突解消のファイル。1 行 1 件>
#       / EVIDENCE_MAIN_ONLY=<前後で変わったが PR 自身の差分は同じで、PR 自身の commit が触れていない根拠ファイル。1 行 1 件>
#       / EVIDENCE_PR_CHANGED=<PR 自身の差分が前後で違うか、PR 自身の commit が触れた根拠ファイル。1 行 1 件>
#       / EVIDENCE_DIFF_LINES=<EVIDENCE_PR_CHANGED のファイルの前後の diff の追加と削除の合計。無ければ 0> / NG: <引き継げない理由>
# 終了コード: 0 = 無条件で引き継げる（PR_COMMITS=0 = main の取り込みだけなら、許可リスト外の衝突解消があっても 0。根拠ファイルは比べず EVIDENCE_MAIN_ONLY・EVIDENCE_PR_CHANGED の行を出さない）
#             / 3 = PR 全体を見た取り直しのレビューを経ていれば引き継げる（下の条件 1）
#             / 4 = 根拠ファイルの PR 自身の差分が前後で違うか、PR 自身の commit が根拠ファイルに触れた（下の「終了コード 4 の判定役」に比べさせる）
#             / 1 = 引き継げない / 2 = 引数・環境の不備（引き継げない側に倒す）
# PR 自身の差分 = 各 HEAD と base の merge-base からのそのファイルの差分（main から入った変更を含まない）。比べ方は行の位置を見ないので、
#   PR 自身の commit が根拠ファイルに触れたら差分が同じでも 4 にする（行を動かしただけの修正を main 由来と取り違えないため）
```

引き継げるのは次のすべてを満たすときだけ:

1. スクリプトが終了コード 0 を返す（`PR_COMMITS` が 1 以上なら、積まれた merge commit が main の取り込みと版の行・CHANGELOG の並べ直しの衝突解消だけで、根拠ファイルの PR 自身の差分が前後で同じ。根拠ファイルに触れない PR 自身の commit はあってよい。`PR_COMMITS=0` なら、積まれたのが main を取り込む merge commit だけで、衝突解消の中身と根拠ファイルの差分は見ない）。または終了コード 3 を返し（根拠ファイルの PR 自身の差分は前後で同じで、許可リストの条件を満たさない衝突解消がある）、新しい HEAD で取り直したレビューが PR 全体を見た周である。確かめ方は次の 2 つ:
   - 最新の `レビュー重量:` コメントの `固定 HEAD:` が新しい HEAD の 40 桁 SHA と一致する
   - 受け取った前の段の Gate Result の `周回:` が `1` か、`（全体レビュー: …）` が添えられている。`周回:` が 2 以上で全体レビューの注記が無い周は W の修正後の差分限定の再レビューと見分けられないので、PR 全体を見た周として扱わない。HEAD の一致・`レビュー重量: full`・仕分けコメントが無いことだけから、PR 全体を見たレビュー済みと推定しない
   終了コード 4（根拠ファイルの PR 自身の差分が前後で違うか、PR 自身の commit が根拠ファイルに触れた）は、下の「終了コード 4 の判定役」の判定の記録が `引き継ぎ判定: 同じ` のときだけ条件 1 を満たす。`RESOLVED_OUTSIDE_ALLOWLIST=` の行もあるときは、終了コード 3 と同じ確認（新しい HEAD で取り直したレビューが PR 全体を見た周である）も満たす必要がある。判定が「変わった」「判断できない」のとき、判定役に比べさせなかったときは条件 1 を満たさない。
   終了コード 0 で `PR_COMMITS=0` なら、`RESOLVED_OUTSIDE_ALLOWLIST=` の行があっても PR 全体を見た取り直しのレビューを求めない（新しい HEAD のレビューは差分限定の周でよい）。判定役も起こさない
2. 前の宣言に `- 根拠ファイル:` の行がある。この行の無い宣言からは引き継げない（この手順より前の宣言を含む）
3. 引き継ぎの元が主の直接の回答で、捏造でない。前の宣言に `主の回答: 許容` 系の行と `真正性確認: 済` の行がある。引き継いだ宣言の回答リンクは主が許容を述べた元の直接の回答を指し、引き継ぎの記録（エージェントが書いた宣言コメント）を指さない。引き継ぎが 2 回以上続いても元の直接の回答のままにする。引き継ぐたびに、元の回答リンクに対して手順5の真正性確認（リンク先を開く・許容の意思を読む・GitHub コメントなら author を実測する）をやり直す。元の直接の回答は会話で受けた回答（`会話で受領` の記録）でもよい。そのときは元の記録のセッション ID と原文で `owner-reply-check.sh` を回し直し、終了コード 0 で、記録の日時と同じ timestamp の `MATCH:` があり、その全文から許容の意思が読め、その timestamp が元の記録を最初に追記した宣言（`引き継ぎ元:` をたどった最初の宣言）の作成日時より後で、全文が別の PR・別のリスクを名指ししていないときだけ引き継ぐ（終了コード 0 でも同じ timestamp の `MATCH:` が無い、全文が `許容しない` への部分一致だった、などは引き継がない）。終了コードが 0 でなければ（この PC に会話ログが無い exit 2 を含む）引き継がず手順6で主に聞く。元の直接の回答はエピックの親経由で受けた回答（`親経由で受領` の記録）でもよい。そのときは元の記録の値で手順5の「親経由で受けた許容（親経由で受領）の真正性確認」の 1〜3（停止の記録のコメントの確かめ方・`owner-reply-check.sh --relayed` の終了コード 0 と記録の日時と同じ timestamp の `MATCH:`・全文から読む許容の意思と名指し）を確かめ直し、その timestamp が元の記録を最初に追記した宣言（`引き継ぎ元:` をたどった最初の宣言）の作成日時より後であるときだけ引き継ぐ。どれかを満たさないとき（`--relayed` の終了コードが 0 でないときを含む）は引き継がず手順6で主に聞く。元の直接の回答は主の委任で親経由に受けた回答（`親経由で受領（委任）` の記録）でもよい。`親経由で受領（委任）（親セッション ` で始まる行は委任の形、`親経由で受領（親セッション ` で始まる行は従来の形として見分ける。委任の形のときは、元の記録の値で手順5の「主の委任で親経由に受けた許容（親経由で受領（委任））の真正性確認」の 4（`owner-reply-check.sh --delegated` の終了コード 0・記録の日時と同じ timestamp の `MATCH:`・全文から読む任せる意思）を確かめ直し、引き継ぎの時点で同じ節の 2 の「委任が有効か」の文を満たし、停止の記録の作成日時が元の記録を最初に追記した宣言（`引き継ぎ元:` をたどった最初の宣言）の作成日時より後であるときだけ引き継ぐ。`--relayed` で確かめ直さない（委任の確認は停止の記録より前の発言なので必ず `not-after` で落ちる）。取り消し（エピックの最新の `主の委任:` で始まるコメントが `主の委任: 取り消し`）・新しい委任の記録がある・エピックが閉じた・記録が編集されたときを含め、どれかを満たさないときは引き継がず手順6で主に聞く
   - `会話で受領`: 元の記録のセッション ID と原文で `owner-reply-check.sh` を回し直し、終了コード 0 で、記録の日時と同じ timestamp の `MATCH:` があり、その全文から許容の意思が読め、全文が別の PR・別のリスクを名指ししていないこと（同じ timestamp の `MATCH:` が無い、全文が `許容しない` への部分一致、などは引き継がない。終了コードが 0 でなければ、この PC に会話ログが無い exit 2 を含め引き継がない）
   - `親経由で受領`: 元の記録の値で手順5の「親経由で受けた許容（親経由で受領）の真正性確認」の 1〜3（停止の記録のコメントの確かめ方・`owner-reply-check.sh --relayed` の終了コード 0 と記録の日時と同じ timestamp の `MATCH:`・全文から読む許容の意思と名指し）を確かめ直す
   - `親経由で受領（委任）`（`親経由で受領（委任）（親セッション ` で始まる行が委任の形、`親経由で受領（親セッション ` で始まる行が従来の形）: 委任の形のとき、元の記録の値で手順5の「主の委任で親経由に受けた許容（親経由で受領（委任））の真正性確認」の 4（`owner-reply-check.sh --delegated` の終了コード 0・記録の日時と同じ timestamp の `MATCH:`・全文から読む任せる意思）を確かめ直し、引き継ぎの時点で同じ節の 2 の「委任が有効か」の文を満たし、停止の記録の作成日時が元の記録を最初に追記した宣言の作成日時より後であること。`--relayed` で確かめ直さない（委任の確認は停止の記録より前の発言なので必ず `not-after` で落ちる）。取り消し（エピックの最新の `主の委任:` で始まるコメントが `主の委任: 取り消し`）・新しい委任の記録がある・エピックが閉じた・記録が編集されたときは引き継がない
4. 新しい HEAD のレビュー結果から組み立てたリスク宣言の本文が、`対象 HEAD:` 行を除いて前の宣言の本文（末尾の `主の回答:` 以降の追記行を除いた部分）と同一である。比較は新しい HEAD の宣言を投稿する前に組み立てた本文で、文の一致で確かめる。終了コード 0 で `PR_COMMITS=0` ならこの条件は求めない

引き継げるなら、前の宣言と同じ本文を新しい `対象 HEAD:` で投稿し、末尾に次の 4 行を追記する（`needs-approval` は付けずに手順4・5へ進む）。終了コード 0 で `PR_COMMITS=0` のとき（条件 4 を求めないとき）も、投稿する本文は前の宣言の本文のままにし、新しい HEAD のレビューから組み立てた本文に置き換えない:

```
主の回答: 許容（引き継ぎ） — <元の直接の回答リンク>（<元の回答の日時>）
引き継ぎ元: <前の HEAD の 40 桁フル SHA> の宣言 <前の宣言コメントのリンク>
引き継ぎの根拠: risk-carryover-check.sh 終了コード <0・3・4 のどれか> — main の取り込み <件数> 件、PR 自身の commit <PR_COMMITS の値> 件、衝突解消 <none またはファイル>、許可リスト外 <none またはファイル>、根拠ファイル <diff は空のファイル / main からの変更だけ: EVIDENCE_MAIN_ONLY のファイル / 終了コード 4 のとき: PR 自身の差分が変わったか PR 自身の commit が触れた EVIDENCE_PR_CHANGED のファイル、差分 <EVIDENCE_DIFF_LINES の値> 行、判定 同じ <判定の記録のリンク> / PR_COMMITS=0 のとき: 比べず（PR 自身の commit 0 件）。該当するものを並べて書く>、取り直しのレビュー <終了コード 3 のとき・終了コード 4 で許可リスト外があるとき: 固定 HEAD <40 桁フル SHA>（周回 <値と注記>） <その レビュー重量 コメントのリンク>。終了コード 0 のとき: 不要。終了コード 4 で許可リスト外が none のときも不要>
真正性確認: 済 — 確認者 <エージェント名> / <日時>（元の回答を再確認）
```

元の回答が会話で受けたものなら、4 行の構造はそのままにして、1 行目の `<元の直接の回答リンク>（<元の回答の日時>）` の部分を元の記録の `会話で受領（セッション <セッション ID> / <日時>）原文: <原文>` に置き換える（`主の回答: 許容（引き継ぎ） — 会話で受領（セッション … / …）原文: …`）。元の回答が親経由で受けたものなら、同じく 1 行目の `<元の直接の回答リンク>（<元の回答の日時>）` の部分を元の記録の `親経由で受領（親セッション <セッション ID> / 発言 <uuid> / <日時>）停止の記録: <URL> 原文: <原文>` に置き換える（`主の回答: 許容（引き継ぎ） — 親経由で受領（親セッション … / 発言 … / …）停止の記録: … 原文: …`）。元の回答が主の委任で親経由に受けたものなら、同じく 1 行目の `<元の直接の回答リンク>（<元の回答の日時>）` の部分を元の記録の `親経由で受領（委任）（親セッション <セッション ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <原文>` に置き換える（`主の回答: 許容（引き継ぎ） — 親経由で受領（委任）（親セッション … / 委任の確認 … / …）委任の記録: … 停止の記録: … 原文: …`）。1 行目の形は回答リンク・`会話で受領`・`親経由で受領`・`親経由で受領（委任）` の 4 つで、どの形でも追記は 4 行のままにする。

1 つでも満たさなければ引き継がず、手順 3 の issue で承認済みを試し（`declarations.md` の出口の順）、それも当たらなければ手順6で主に聞く。主への質問には、スクリプトの `NG:` 行（本文の不一致なら何が変わったか）を引き継げなかった理由として添えて手順6へ進む。終了コード 4 のときは、`EVIDENCE_PR_CHANGED=` の行（どの根拠ファイルの PR 自身の差分が変わったか、PR 自身の commit が触れたか）と、判定の理由（判定の記録が `引き継ぎ判定: 変わった` か `引き継ぎ判定: 判断できない` のときはその `理由:`）か判定役に比べさせなかった理由（ほかの条件を満たさない・差分が 100 行を超えた・従来経路の一括の G で判定役を起こせない、など）を添えて手順6へ進む。終了コード 3 で条件 1 の取り直しのレビューを確かめられなかったときは、`RESOLVED_OUTSIDE_ALLOWLIST=` の行と、PR 全体を見たレビューを確かめられなかったこと（`周回:` の値）を理由に添える。

引き継ぎで省けるのは主への質問だけで、手順 2 のレビュー・手順 4 の証拠・手順 3-b の仕様宣言は新しい HEAD で出し直し、手順5の実測も省かない。これが手順1の「前回の合格部分を流用しない」と gate-runner.md の再レビューの「手順 1 から全工程をやり直す」に対する唯一の例外である。

##### 終了コード 4 の判定役

終了コード 4 は、根拠ファイルの PR 自身の差分が前後で違うか、PR 自身の commit が根拠ファイルに触れたことしか示さない。リスク宣言の中身が前と同じかは、作業の文脈を持たない判定役に比べさせる。

- **回す条件**: スクリプトが終了コード 4 を返し、条件 2〜4 を満たし、`RESOLVED_OUTSIDE_ALLOWLIST=` の行があるときは条件 1 の終了コード 3 と同じ確認（新しい HEAD で取り直したレビューが PR 全体を見た周である）も満たし、`EVIDENCE_DIFF_LINES=` が 100 以下（100 ちょうどは判定させる）で、下の記録の選び方で使える記録が無いときだけ回す。どれかを満たさなければ判定役を起こさず手順6で主に聞く（使える記録があるときは、判定役を起こさずその記録で条件 1 を決める）
- **判定役**: `subagent_type: dev-workflow:decider`・`model: opus` で起こす（残量モードで上げも下げもしない）
- **起こすセッションの区別**: develop の外のメインセッションでは、ゲート自身が Agent ツールで判定役を起こし、判定の記録を PR に投稿して 3-c を続ける。develop の合格処理の G は判定役を起こせないので、回す条件を満たしたら宣言を投稿せず `needs-approval` も付けずに、Status `needs-carryover-judge`・`次の段: 合格処理` で返す（本体が判定役を起こして記録を投稿し、合格処理の G を新しく起こす。return の欄は下の「G として動くとき（develop）」節）。従来経路の一括の G（`段: 一括（従来経路）`）は判定役を起こさず手順6で主に聞く
- `SHARED_BUDGET_MODE=depleted` のときは判定役を起こさず、判定役を起こす側（develop の外のメインセッションではゲート自身、develop では本体）が `引き継ぎ判定: 判断できない`・`理由: 判定役を起こさなかった（共有枠 depleted）` の記録を投稿し、手順6で主に聞く側に倒す。develop の合格処理の G は depleted でも `needs-carryover-judge` で返し、この記録を自分で投稿しない（二重投稿を避ける）
- **渡すもの**: `git diff --no-color --no-ext-diff --no-textconv <前 HEAD> <新しい HEAD> -- <EVIDENCE_PR_CHANGED のファイル>...` の出力と、前の宣言の本文（末尾の `主の回答:` 以降の追記行を除いた部分）の 2 つだけ。記録先の本文・レビューの指摘・W の return・作業の会話は渡さない
- **依頼文**: `agents/decider.md` の通常の 3 点（原因の分類・直し方・次のモデル）ではなく、次を求める。渡した 2 つだけから判定し、リポジトリを読み足さず、足りなければ「判断できない」と返す。返答の 1 行目は `引き継ぎ判定: 同じ`・`引き継ぎ判定: 変わった`・`引き継ぎ判定: 判断できない` のどれかちょうどにし、2 行目以降に理由（何が同じか・何が変わったか・何が足りないか）を書く。`agents/decider.md` の入力契約の 4 点はこの依頼には当てはまらず、渡した 2 つだけが入力であることも依頼文に書き、不足を理由に `不足:` で返さず 1 行目を必ず上の 3 形のどれかにするよう求める（`不足:` で返されると毎回「判断できない」に倒れるため）
- 「同じ」は、差分によって前の宣言のリスク内容・該当する観点・発生条件・影響範囲と戻し方のどれも変わらないことを指す
- 返答の 1 行目が 3 形のどれにも一致しなければ「判断できない」として記録し、依頼し直さない（主に聞く側に倒れるだけで、補える入力も無いため）
- **判定の記録**: 判定役を起こしたセッション（develop では本体）が、返答を次の書式で PR にコメントする（判定役は投稿できないので代理投稿する）。1 行目は正規表現 `^引き継ぎ判定: (同じ|変わった|判断できない)$` に完全一致させる。`根拠ファイル:` は `EVIDENCE_PR_CHANGED=` のファイルを 1 行にカンマ区切りで並べる。`対象 HEAD:` の文字列は使わない（auto-merge の workflow が宣言の照合に使うため）

```text
引き継ぎ判定: <同じ|変わった|判断できない>
前 HEAD: <40 桁フル SHA>
新しい HEAD: <40 桁フル SHA>
前の宣言: <前の宣言コメントのリンク>
根拠ファイル: <EVIDENCE_PR_CHANGED のファイル>, <ファイル>
差分の行数: <EVIDENCE_DIFF_LINES の値>
判定役: dev-workflow:decider / <モデル。起こさなかったときは「起こさず」> / 代理投稿 <投稿したセッションか本体の名前>
理由: <判定役の返答の 2 行目以降。起こさなかったときはその理由>
```

- **記録の選び方**: 同じ PR の 1 行目が `引き継ぎ判定:` のコメントのうち、`前 HEAD:` と `新しい HEAD:` が今回の前 HEAD・新しい HEAD の 40 桁と一致し、`根拠ファイル:` のファイルがスクリプトの `EVIDENCE_PR_CHANGED=` の行のファイルと（カンマで区切った各要素の前後の空白を除いたうえで）順序を問わず同じ集合のものの最新 1 件だけを使う。一致しない記録は使わない。一致する記録があれば、同じ組で判定役を起こし直さない（develop の G は `needs-carryover-judge` を返し直さない）。1 行目が上の正規表現に一致しない記録は「判断できない」と同じに扱う。記録が `引き継ぎ判定: 同じ` なら条件 1 を満たし、引き継ぎの根拠の行にその記録のリンクを書く。判定を受けて起こされた合格処理の G（前の Gate Result が `段: 合格処理`・Status `needs-carryover-judge`）が今回の組に一致する記録を見つけられないときは、`needs-carryover-judge` を返し直さず「判断できない」と同じに扱い、本体が投稿した記録のリンク（見つからなければその旨）と、HEAD か根拠ファイルが今回の組と一致しないことを理由に添えて手順6で主に聞く
- 守備範囲: 判定役が差分を読み違えて変わったリスクを「同じ」と判定すること、小さい引き継ぎが積もってリスクの中身が変わること、記録が本当に判定役の返答かどうか、判定役の理由の妥当性は、この手順では止めない。条件 4 の本文の一致と新しい HEAD のレビューは引き継いでも残る


## G として動くとき（develop）

この節は develop の G だけに関係する。`gate-runner.md`「return の書式」の共通欄のうしろに続ける。

- **許容済みの PR で HEAD が動いたとき**: 取り直しの手順 3 で再び「主のリスク許容が必要」になったら、主に聞く前に pr-review-gate 手順 3-c（前の HEAD の許容の引き継ぎ）を試す（この場合は合格処理の G がこのファイルを読んで試す）。スクリプトが終了コード 4 を返し、「終了コード 4 の判定役」の回す条件を満たし、使える判定の記録が無いときは、合格処理の G は判定役を起こせないので Status `needs-carryover-judge` で返す（欄は次）

```markdown
### needs-carryover-judge のとき
（手順 3-c の「終了コード 4 の判定役」の回す条件を満たし、使える判定の記録が無い。宣言は投稿せず、`needs-approval` も付けない。`次の段: 合格処理`）
- 前 HEAD: <40 桁フル SHA> / 新しい HEAD: <40 桁フル SHA>
- 前の宣言のコメントのリンク: <URL>
- EVIDENCE_PR_CHANGED=: <ファイル>, <ファイル>
- EVIDENCE_DIFF_LINES=: <値>
```

## 出口

- 引き継げたら宣言を投稿して合格処理の G に渡す（Status `次の段へ`・`次の段: 合格処理`）。引き継げなければ `stages/hold.md` の手順 6 へ進む。
