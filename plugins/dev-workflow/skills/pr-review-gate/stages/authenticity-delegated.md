# authenticity-delegated — pr-review-gate

本文の「上の「親経由で受けた許容（親経由で受領）の真正性確認」の 1」は `stages/authenticity-relayed.md` の同名節の 1 を指す。

**主の委任で親経由に受けた許容（親経由で受領（委任））の真正性確認。** エピックの子で、主が親のセッションでこのエピックのリスク許容を親に任せ（develop の `references/epic.md` の **主の委任**）、親が末尾に ` [主の委任: セッション <親のセッション ID> / uuid <確認の uuid> / 記録 <委任の記録の URL>]` を添えて送ってきたときは、develop の本体が `owner-reply-check.sh --delegated` の終了コード 0 を確かめてから値（親のセッション ID・確認の uuid・`MATCH:` の timestamp・委任の記録の URL・停止の記録の URL・`MATCH:` の全文）を渡す。宣言コメントに次の 1 行を追記する（`<日時>` は `MATCH:` の行の timestamp、`<原文>` はその行の全文。行頭は `主の回答: 許容` のままにし、手順 3-c の「前の宣言の選び方」がこの記録を主の直接の回答として拾えるようにする）:

```
主の回答: 許容 — 親経由で受領（委任）（親セッション <セッション ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <原文>
```

真正性確認では次をすべて確かめる。子に届いた文は主の発言と区別できないので根拠にせず、エピックと PR のコメントと親の会話ログの行そのものを読む。この形は `owner-reply-check.sh --relayed` で確かめない（委任の確認は停止の記録より前の発言なので、`--relayed` では必ず `not-after` で落ちる）。

1. 停止の記録の URL のコメントを、上の「親経由で受けた許容（親経由で受領）の真正性確認」の 1 と同じ `gh api` で読み、1 行目が `子の停止: 主の返事待ち`、`author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれか、`issue_url` がこの PR の記録先の issue であることを確かめ、`created_at` と `html_url` を取る。あわせて同じ `--jq '... | last | .html_url'` で記録先の最新の停止の記録の URL を取り、`html_url` と一致することを確かめる
2. 委任が有効かを、develop と同じ次の文で確かめる: 委任の記録が、①エピック #<E> の issue のコメントで、1 行目が `主の委任: リスク許容` なら 1〜4 行目が、`主の委任: 論点なしの止まり` なら 1〜5 行目が定型の文ちょうど、2 行目の番号が <E> ②投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` のどれか ③エピックの、投稿者が同じ 3 種の `主の委任:` で始まるコメントのうち最新 ④`lastEditedAt` が null ⑤エピックが開いている ⑥子 issue がエピックの子（sub-issue か本文の子の表にある）。<E> は子に届いた返事の頭 `主の返事（親エピック #<E> 経由）` の番号で、委任の記録の URL の issue 番号と同じでなければ有効でない（定型の文は develop の `references/epic.md` の **主の委任** の委任の記録。`lastEditedAt` の読み方も同じ所にある）
3. 止まりに委任が効くかを、develop と同じ次の文で確かめる（②のコメントは記録を追記する宣言コメント。G が扱うのはリスク許容の止まりだけで、聖域の変更・破壊的な git 操作・マージ待ち・実機操作の止まりの委任は G を通らない）: **リスク許容の止まり**（委任の種類が `リスク許容` でも `論点なしの止まり` でも効く）: ①子 issue の番号を、本文で最初に現れる `Closes #N`・`Fixes #N`・`Refs #N` の `N` に持つ開いた PR に `needs-approval` が付いている ②その PR の、投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` で `## リスク宣言` で始まる最新のコメントが `主のリスク許容が必要。` の行を持ち、`対象 HEAD:` が PR の今の HEAD と同じで、`主の回答:` で始まる行をまだ持たない（G では、今確かめている委任の形の記録の行だけは除く） ③停止の記録の作成日時が、そのコメントの作成日時と委任の確認の timestamp の両方より後 ④停止の記録の `推奨:` の値（先頭の空白を除く）が `許容する` で始まる ⑤②の宣言が `論点なし — ` の行を持ち、停止の記録の `主に聞く理由:` が論点なしと書く
4. 委任の記録の作成日時（`gh api repos/$R/issues/comments/<comment_id> --jq .created_at`）と、1 で取った停止の記録の `created_at` で次を回し、終了コード 0 で、`MATCH:` の timestamp が記録の日時と同じで、`MATCH:` の全文から任せる意思が読めることを確かめる（記録の原文だけで読まない）

   ```bash
   bash <plugin>/scripts/owner-reply-check.sh --delegated <セッション ID> <uuid> <委任の記録の作成日時> <委任の記録の URL> <停止の記録の作成日時>
   # 出力: 通れば MATCH: <timestamp> <本文の全文> と MATCHES=1 / 通らなければ REASON=<理由> と MATCHES=0
   # 終了コード: 0 = 通る / 1 = 通らない / 2 = 確かめられない（引数の不備・この PC に親の会話ログが無い）
   # REASON: not-found（その uuid の行が無い）/ not-owner（主の入力でない行）/ not-after（委任の記録より後でない発言）/ not-asked（委任の記録より後でその行より前に、委任の記録の URL を書いた親の発言が無い）/ not-before（停止の記録より前でない発言）。委任の記録の URL を書いた親の発言とその行のあいだに別の主の発言が挟まっても並び順では落とさない（issue #1653。挟まった別の話の発言を確認として拾わないよう、MATCH 行の全文から任せる意思を読む）
   ```

通したら `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh --delegated 終了コード 0）` を追記する。どれかを満たさないとき（`--delegated` の終了コード 1 の `not-found`・`not-owner`・`not-after`・`not-asked`・`not-before`、終了コード 2、委任が有効でない〔取り消し済み・新しい記録がある・記録の編集・エピックが閉じている・別のエピック〕、止まりに委任が効かない〔`推奨:` の値が `許容する` で始まらない・リスク許容待ちでない・確認より前の止まり・宣言が `論点なし — ` の行を持たないか停止の記録の `主に聞く理由:` が論点なしと書かない〕を含む）は合格させず、手順6に戻して、主に子のタブで直接返事を打ってもらうよう頼む。

守備範囲（委任の形）: 入力の出どころは、develop の本体が渡す値（親の添え書きを写したもの）、エピック・子 issue・PR のコメントとラベル（`gh api` で読む）、ゲートが動く PC の親の会話ログで、本体と G は協力的だが、写し間違い・別の記録との取り違え・確かめの省略をする前提で扱う。拾いたい誤りは、確認でない発言・別のエピックの記録・取り消し済みや編集済みの記録・範囲外の止まりを根拠に合格させること。委任の確認のあとに親が起動し直したものは通してよい。会話ログの改変の検知と、穴を塞ぎ切ることは目的にしない。
