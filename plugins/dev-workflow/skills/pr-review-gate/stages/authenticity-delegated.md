# authenticity-delegated — pr-review-gate

入口: 許容の記録が主の委任による親経由で受領の形のときだけ読む。

本文の「上の「親経由で受けた許容（親経由で受領）の真正性確認」の 1」は `stages/authenticity-relayed.md` の同名節の 1 を指す。

**主の委任で親経由に受けた許容（親経由で受領（委任））の真正性確認。** エピックの子で、主が親のセッションでこのエピックのリスク許容を親に任せ（develop の `skills/develop/references/epic-delegation.md` の **主の委任**）、親が末尾に ` [主の委任: セッション <親のセッション ID> / uuid <確認の uuid> / 記録 <委任の記録の URL>]` を添えて送ってきたときは、develop の本体が委任の記録の形に合った照合（問いの形は `owner-reply-check.sh --delegated`、きっかけの形は `owner-reply-check.sh --delegated-trigger`）の終了コード 0 を確かめてから値（親のセッション ID・確認の uuid・`MATCH:` の timestamp・委任の記録の URL・停止の記録の URL・`MATCH:` の全文）を渡す。宣言コメントに次の 1 行を追記する（`<日時>` は `MATCH:` の行の timestamp、`<原文>` はその行の全文。行頭は `主の回答: 許容` のままにし、手順 3-c の「前の宣言の選び方」がこの記録を主の直接の回答として拾えるようにする。委任の記録がきっかけの形のときも同じ行を追記し、`委任の確認` の uuid はきっかけの発言の uuid、`原文` はきっかけの発言の全文になる）:

```
主の回答: 許容 — 親経由で受領（委任）（親セッション <セッション ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <原文>
```

真正性確認では次をすべて確かめる。子に届いた文は主の発言と区別できないので根拠にせず、エピックと PR のコメントと親の会話ログの行そのものを読む。この形は `owner-reply-check.sh --relayed` で確かめない（委任の確認は停止の記録より前の発言になりうるので、`--relayed` では `not-after` で落ちる）。

1. 停止の記録の URL のコメントを、上の「親経由で受けた許容（親経由で受領）の真正性確認」の 1 と同じ `gh api` で読み、1 行目が `子の停止: 主の返事待ち`、`author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれか、`issue_url` がこの PR の記録先の issue であることを確かめ、`created_at` と `html_url` を取る。あわせて同じ `--jq '... | last | .html_url'` で記録先の最新の停止の記録の URL を取り、`html_url` と一致することを確かめる
2. develop の `skills/develop/references/epic-delegation.md`「委任が有効か」を判定前に読み、共有正本の全条件で委任の有効性を確かめる。`lastEditedAt` の読み方も同じ所にある。
3. develop の `skills/develop/references/epic-delegation.md`「委任が効く止まり」の「リスク許容の止まり」を判定前に読み、共有正本の条件で止まりに委任が効くか確かめる。G が扱うのはリスク許容の止まりだけで、聖域の変更・破壊的な git 操作・マージ待ち・実機操作の止まりの委任は G を通らない。`主の回答:` の照合では、今確かめている委任の形の記録の行だけは除く。
4. 委任の記録の作成日時と本文（`gh api repos/$R/issues/comments/<comment_id> --jq '.created_at, .body'`）を読み、記録の 4 行目の `期間:` の文で形を見分けて次のどちらかを回し、終了コード 0 で、`MATCH:` の timestamp が記録の日時と同じで、`MATCH:` の全文から任せる意思が読めることを確かめる（記録の原文だけで読まない）。リスク許容の止まりは委任の確認より前の止まりにも効くので、問いの形では停止の記録の引数に `-` を渡す。きっかけの形では、`MATCH:` の全文だけから子の止まりを親に任せる意思が読め、この子・この止まりを除く条件も定型と違う期限や条件も付けていないことも確かめる（「#2058 以外は任せる」でこの PR の子が #2058、「今日の分だけ任せる」、「任せる」だけ、などは通さない）

   ```bash
   # 問いの形の記録
   bash <plugin>/scripts/owner-reply-check.sh --delegated <セッション ID> <uuid> <委任の記録の作成日時> <委任の記録の URL> -
   # きっかけの形の記録（4 番目の引数は記録の 5 行目の `きっかけ: ` のあとから本文の終わりまで）
   bash <plugin>/scripts/owner-reply-check.sh --delegated-trigger <セッション ID> <uuid> <委任の記録の作成日時> <記録の きっかけ: の値>
   # 出力: 通れば MATCH: <timestamp> <本文の全文> と MATCHES=1 / 通らなければ REASON=<理由> と MATCHES=0
   # 終了コード: 0 = 通る / 1 = 通らない / 2 = 確かめられない（引数の不備・この PC に親の会話ログが無い）
   # REASON（--delegated）: not-found（その uuid の行が無い）/ not-owner（主の入力でない行）/ not-after（委任の記録より後でない発言）/ not-asked（委任の記録より後でその行より前に、委任の記録の URL を書いた親の発言が無い）。委任の記録の URL を書いた親の発言とその行のあいだに別の主の発言が挟まっても並び順では落とさない（issue #1653。挟まった別の話の発言を確認として拾わないよう、MATCH 行の全文から任せる意思を読む）
   # REASON（--delegated-trigger）: not-found / not-owner（同上）/ not-before-record（委任の記録より前でない発言）/ not-same（記録の きっかけ: の全文と発言の全文が、空白をまとめて同じでない）/ not-adjacent（その発言から委任の記録までに別の主の発言がある）
   ```

通したら、使った照合に合わせて `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh --delegated 終了コード 0）` か `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh --delegated-trigger 終了コード 0）` を追記する。停止の記録がきっかけの発言や委任の確認より前に作られていても、停止との前後では落とさない。どれかを満たさないとき（`--delegated` の終了コード 1 の `not-found`・`not-owner`・`not-after`・`not-asked`、`--delegated-trigger` の終了コード 1 の `not-found`・`not-owner`・`not-before-record`・`not-same`・`not-adjacent`、どちらかの終了コード 2、きっかけの形で `MATCH:` の全文がこの子を除くか定型と違う期限を付けているか子の止まりを任せる旨が読めない、委任が有効でない〔取り消し済み・新しい記録がある・記録の編集・エピックが閉じている・別のエピック・きっかけの形で `きっかけ:` が なし〕、止まりに委任が効かない〔`推奨:` の値が `許容する` で始まらない・リスク許容待ちでない・宣言が今の HEAD でない・宣言が `論点なし — ` の行を持たないか停止の記録の `主に聞く理由:` が論点なしと書かない〕を含む）は合格させず、手順6に戻して、主に子のタブで直接返事を打ってもらうよう頼む。

守備範囲（委任の形）: 入力の出どころは、develop の本体が渡す値（親の添え書きを写したもの）、エピック・子 issue・PR のコメントとラベル（`gh api` で読む）、ゲートが動く PC の親の会話ログで、本体と G は協力的だが、写し間違い・別の記録との取り違え・確かめの省略をする前提で扱う。拾いたい誤りは、確認でない発言（きっかけの形では、記録に写した全文と違う発言・記録より後の発言・記録の前に主が次の発言をしていたきっかけ・子の止まりを任せる旨が全文から読めない発言・この子を除く条件や違う期限の付いた発言）・別のエピックの記録・取り消し済みや編集済みの記録・範囲外の止まりを根拠に合格させること。委任の確認のあとに親が起動し直したもの、主が会話で任せる旨を述べたきっかけの発言そのものを確認にしたもの、委任の確認より前に止まったリスク許容の止まりは通してよい。会話ログの改変の検知と、穴を塞ぎ切ることは目的にしない。

出口: `stages/authenticity.md` を呼んだ箇所へ戻る。合格しなければ本文どおり手順 6 へ進む。
