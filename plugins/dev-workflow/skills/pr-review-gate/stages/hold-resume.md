# 保留の復帰手順 — pr-review-gate

`stages/hold.md` の手順 6 の 5。保留の解除の G（主の回答が届いたとき）が `stages/hold.md` と合わせて読む。保留を返す側の G は読まない。以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。

5. 主の回答が来たら、**保留の種類ごとに次の復帰手順を踏む**（どちらも最後は手順5の合格条件を再確認してから合格処理する）:

| 保留の種類 | 主の回答 | 復帰手順 |
|---|---|---|
| **リスク許容待ち**（手順3） | 許容 | 許容を記録したあとに HEAD が動いたときは、主に聞き直す前に手順 3-c の引き継ぎを試す（条件は `stages/carryover.md` が正本）。回答をそのまま記録するときは、手順3の宣言コメントに `主の回答: 許容 — <回答リンク>（<日時>）` を**追記**する（宣言本文は書き換えない）。会話で受けた回答（セッション ID・日時・原文は本体から渡される）は `主の回答: 許容 — 会話で受領（セッション <セッション ID> / <日時>）原文: <原文>` を追記し、主に PR へのコメントを求めない。エピックの親経由で受けた回答（develop の本体が `owner-reply-check.sh --relayed` の終了コード 0 を確かめて渡したもの）は `主の回答: 許容 — 親経由で受領（親セッション <セッション ID> / 発言 <uuid> / <日時>）停止の記録: <URL> 原文: <原文>` を追記してから手順5の親経由で受けた許容の真正性確認に進む。主の委任で親経由に受けた回答（`--delegated` の終了コード 0 を本体が確かめて渡したもの）は `主の回答: 許容 — 親経由で受領（委任）（親セッション <セッション ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <原文>` を追記してから手順5の主の委任で親経由に受けた許容の真正性確認に進む → 手順5の真正性確認を実施 → `needs-approval` を外して手順5へ |
| | 不許容 | 代替案へ切り替えて手順2からやり直すか、PR をクローズする。合格処理はしない。**`needs-approval` の扱い**: 代替案でリスク自体が消えるなら外す（＝保留理由の解消）／作り直し後も同じリスクが残るなら**付けたまま**にして再度許容を確認する。PR をクローズするならラベル状態は問わない |
| **動作確認代行待ち**（手順4） | 確認結果あり | 主の確認結果を**手順4の動作確認証拠として PR に記録**する（`対象 HEAD` / `実施者: 主` / 観測された結果 / 実施日時 / 主の回答リンク。受け入れ条件との対応も手順4の表と同じ形式で書く）→ `needs-approval` を外して手順5へ |
| | 期待どおりでない | `agent-review:failed` に付け替え、報告された症状を再現手順として書いて修正サイクルへ戻す。**`needs-approval` は外す**（主の代行は完了しており、保留理由は「主待ち」から「実装の欠陥」に変わったため。付けたままだと修正後も永久にマージされない） |
| **切り出しの確認**（手順2-1の仕分け表の順 5） | 切り出す | その指摘を捨てずに follow-up issue に切って URL を PR コメントに記録する（置き場所は `stages/triage.md` 手順2-1の「主が切り出すと答えた止める指摘の置き場所」の段落で決める。エピックの完了条件に効くなら段 C の表、それ以外はエピックの外の新しい issue）→ **`needs-approval` を外す** → 未処理の順 6 の指摘が残っていれば `agent-review:failed` を付けずに Status `needs-decider` で return する（手順2-1の順 5 と順 6 の混在の段落）→ ほかに止める指摘が無ければ手順3以降へ |
| | この PR で直す | 主の回答リンクを PR コメントに記録する → **`needs-approval` を外す** → 未処理の順 6 の指摘が残っていれば failed にせず Status `needs-decider` で return する（裁定のあとにまとめて 1 回の failed で戻す）→ 残っていなければ `agent-review:failed` に付け替えて修正サイクルへ戻す（2周目以降なら次の周に入る。その周の終わりにも仕分け表を適用する） |

- 動作確認代行の場合、3点セットの3点目（自力検証できるようにする改善提案）は**復帰時に着手または issue 化まで進める**。出しただけで放置しない。
- **`needs-approval` を黙って持ち越さない。** 上の表のどの経路を通っても、その時点で
  「保留理由が解消したか」を必ず判断し、**外す / 付けたままにする のどちらかを明示的に選ぶ**。
  判断を書かずに次の工程へ進むことを禁じる（放置すると、合格しても auto-merge されないスタック PR になる）。

## G として動くとき（develop）

### この段で起こされたときの入力

保留の解除の G は、起動指示の前の段の `## Gate Result` ブロック（`次の段: 保留の解除`）と主の回答を受け取り、前の段の会話は持たない前提で PR コメントから保留の中身を読む。

- **保留の解除**: オーナーの回答（許容する／しない・動作確認の結果・切り出しの確認への回答（切り出す／この PR で直す））を受けて pr-review-gate の復帰手順に従う。復帰手順が別の段の作業に進むときは、その作業を自分で行わず Status `次の段へ` で返す。許容したとき・切り出して残りが無いときは `次の段: 合格処理`、許容せず代替案で手順 2 からやり直すときは `次の段: 前提確認と重さ判定` と書く。未処理の順 6 が残っていれば failed に進まない（`needs-approval` を外して `needs-decider` で返す。処理順は pr-review-gate 手順 2-1 の混在の段落）
