# 合格処理 — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/prepare.md`（手順 1・2・2-0）、`stages/triage.md`（2-1 の止める判定と仕分け・2-2）、`declarations.md`（手順 3・3-b）、`stages/hold.md`（手順 3-c・6）。

## 入口

`declarations.md` の手順 3（リスク宣言）と 3-b（仕様宣言）を投稿したあとに読む。手順 3 で「主のリスク許容が必要」と宣言したときは `stages/hold.md` が先で、許容を得てからこの段に戻る。ただし手順 3 の issue で承認済みを当てた宣言は保留を通らず、そのままこの段に来る。

## 前提と理由（この段で使うもの）

- **auto-merge の配備状況**: auto-merge workflow（dev-workflow プラグインの `templates/auto-merge/` を展開したもの）が配備済みのリポでは、passed 付与でロボットが機械判定してマージする。**未配備のリポでは passed 付与後のマージは人間の操作**になる（ゲートの手順自体は変わらない）。どちらの場合も、LLM が `gh pr merge` や REST の merge API を直接叩いてマージすることは**禁止**（聖域・CI green・SHA ピン・緊急停止の判定を素通りするため）。

## 手順

### 4. 動作確認

**自力で検証し、証拠（手順＋結果）を PR コメントに添付する。** ブラウザ実機・CLI 実行・スクリプト実行いずれでもよい。受け入れ条件と 1:1 で対応させる。

```
## 動作確認
対象 HEAD: <$HEAD_SHA 40桁フル>

| 受け入れ条件 | 実行した手順 | 結果 |
|---|---|---|
| <条件> | <再現可能な手順> | ✅ <観測した実際の出力/画面> |
```

「テストが通った」だけは証拠にならない（テスト自体が変更対象のことがある）。実際に動かした痕跡を書く。

**全体のテストは CI の結果で扱う。** ゲートの担当はテストの全体実行を手元で行わない（テストランナーをファイルで絞らずに起動するもの。claude-harness では `scripts/test.sh`）。受け入れ条件が全体のテストの合格を求めるとき（例: 「`bash scripts/test.sh` が通る」）は、対象 HEAD の CI の結果（`gh pr checks $N --repo $R` と run の URL）を証拠にし、結果の欄を次のとおり書く。

| 対象 HEAD の CI | 結果の欄 |
|---|---|
| 成功 | ✅ と run の URL |
| 結論がまだ無い（実行中、または Draft のため未実行） | 状態（と run があればその URL）と、合格後の CI の見張り（`plugins/dev-workflow/references/ci-watch.md`）で結論を確かめること。このまま手順 5 へ進んでよい |
| 既に失敗 | 成功の印を付けず、失敗した run の URL と、合格後の CI の見張りで直しに回すこと。合格処理は止めない |

結論の無い CI や失敗した CI を成功として書かない。関係するテストと lint の結果は、作業者が PR に載せた証拠（コマンドと exit code）を使ってよい（その場合、結果の欄にはその証拠があるコメントの URL とコマンド・exit code を写し、自分で動かした形に書かない）。

**自力検証が不能なときのみ**、3点セットを揃えて主に依頼し、手順6へ（マージ保留）:

```
## 動作確認: 主に依頼
1. 自力検証できなかった理由: <何が足りなかったか。「面倒」「時間」は理由にならない>
2. 主にやってほしい具体的手順: <URL・クリック順・期待される結果まで書く>
3. 次回から自力検証できるようにする改善提案: <テスト整備・認証情報の登録・seed データ等。issue 化するならリンク>
```

この 3 点は PR に残す記録の項目である。主に出す依頼の文面は `~/.claude/output-styles/readable.md` の節 3 の型で書く。主に聞く理由は「主の手でしかできない操作」で、2 の手順は型の「答え方」に入れる。

3点目は必須。これが無い依頼は主の負担を減らす方向に働かないので出さない。

### 5. 合格処理

前提として、**最後のレビュー結果に、全周共通の判定で止まる指摘（`blocking` かつ `confirmed`、G が引用を照合済みまたは例外 3 種に当たるもの）のうち、主が切り出すと答えて follow-up issue に切ったものと、G が順 3 の集合一致で閉じたもの（閉じた PR コメント URL を仕分け欄に残す）以外が 0 件であること**（判定は手順2-1「マージを止めるかの判定（全周共通）」。切り出す経路は手順6の表の「切り出しの確認」行で、切った issue の置き場所は手順2-1の「主が切り出すと答えた止める指摘の置き場所」の段落、集合一致で閉じる経路は手順2-1の仕分け表の順 3）。そのうえで、**手順4の動作確認証拠を投稿済み、かつ手順3のリスク宣言が次のどちらかの状態のときだけ**実行する。

| リスク宣言の状態 | 合格処理 |
|---|---|
| 「**リスクなし**」を投稿済み | 可 |
| 「**主のリスク許容が必要**」を投稿済み ＋ **主の許容回答リンクを同コメントに追記済み**（手順6経由）＋ **下の真正性確認済み** | 可 |
| 「**主のリスク許容が必要**」を投稿済み ＋ **会話で受領の記録を同コメントに追記済み**（`主の回答: 許容 — 会話で受領（…）原文: …`。手順6経由）＋ **下の会話の回答の真正性確認済み** | 可 |
| 「**主のリスク許容が必要**」を投稿済み ＋ **親経由で受領の記録を同コメントに追記済み**（`主の回答: 許容 — 親経由で受領（…）停止の記録: … 原文: …`。手順6経由）＋ **下の親経由で受けた許容の真正性確認済み** | 可 |
| 「**主のリスク許容が必要**」を投稿済み ＋ **親経由で受領（委任）の記録を同コメントに追記済み**（`主の回答: 許容 — 親経由で受領（委任）（…）委任の記録: … 停止の記録: … 原文: …`。手順6経由）＋ **下の主の委任で親経由に受けた許容の真正性確認済み** | 可 |
| 「**主のリスク許容が必要**」を投稿済み ＋ **引き継ぎで許容済み**（手順 3-c の 4 行 `主の回答: 許容（引き継ぎ）`・`引き継ぎ元:`・`引き継ぎの根拠:`・`真正性確認: 済` が同コメントに揃っている） | 可 |
| 「**主のリスク許容が必要**」を投稿済み ＋ **issue で承認済み**（`declarations.md` 手順 3 の 3 行 `issue で承認済み — …`・`承認の証拠:`・`真正性確認: 済` が同コメントに揃っている）＋ **下の issue で承認済みの確かめ直し済み** | 可 |
| 宣言が未投稿 / 許容が必要なのに上記いずれの許容済み条件も満たさない | **不可**（手順6へ） |

**リスク宣言の文言を後から書き換えることを禁じる。** 主が許容しても「リスクなし」に書き換えず、
「主のリスク許容が必要」のまま残して追記だけする（形式: `主の回答: 許容 — <回答リンク>（<日時>）`）。
「リスクなし宣言は本当にリスクが無い場合にしか出ない」という前提が崩れると、
形骸化監査（リスクなし宣言のサンプリング再判定）が本来の抽出対象を取り逃がすため。

**許容リンク経由の合格では、リンクの真正性を確認する。** リンク先を実際に開き、
①**主のアカウントによる発言**であること ②**許容の意思が読み取れる**こと、の両方を確認し、
結果を宣言コメントに追記する（形式: `真正性確認: 済 — 確認者 <エージェント名> / <日時>`）。
リンクが GitHub コメントの場合は author を実測する:

```bash
gh api repos/$R/issues/comments/<comment_id> --jq '.user.login'   # 主のアカウント名と一致すること
```

Discord 等の外部サービスのリンクは目視確認でよい（確認記録は同じ形式で残す）。
リンク先が開けない・主本人の発言と確認できない場合は合格処理をしない（手順6に戻して主に再確認する）。

**会話で受けた許容（会話で受領）の真正性確認。** 主が会話で許容を返したとき（同じセッションの返事、または新しいセッションの `/develop <記録先> 許容する`）は回答リンクが無いので、PR へのコメントを求めず、宣言コメントに次の 1 行を追記する（値は develop の本体が渡したセッション ID・発言の日時・原文。`<日時>` は会話ログのその発言の timestamp の値をそのまま書く）:

```
主の回答: 許容 — 会話で受領（セッション <セッション ID> / <日時>）原文: <原文>
```

真正性確認は、会話ログにその発言が主の発言として実在するかをスクリプトで確かめることとする（`gh` は主のアカウントで認証されているので、GitHub コメントの投稿者より会話ログのほうが書き手を区別できる）:

```bash
bash <plugin>/scripts/owner-reply-check.sh <セッション ID> <原文>
# 出力: 一致した主の発言ごとに MATCH: <timestamp> <本文の全文> / 最後に MATCHES=<件数>
# 終了コード: 0 = 主の発言として実在する / 1 = 実在しない / 2 = 確かめられない（引数の不備・この PC に会話ログが無い）
```

終了コード 0 で、記録の日時と同じ timestamp を持つ `MATCH:` の行があり、その行の全文から許容の意思が読めるときだけ通す（①主の発言 ②許容の意思、の確認に当たる）。許容の意思は記録の原文ではなく、同じ timestamp の `MATCH:` の全文で読む（原文は部分一致なので、`許容しない` の一部の `許容` だけを記録しても一致してしまう）。あわせて、その発言がこの PR のこの宣言への返事であることを確かめる: 同じ timestamp が、記録を追記する宣言コメントの作成日時（`gh api repos/$R/issues/comments/<comment_id> --jq '.created_at'`）より後であり、全文が別の PR・別の記録先・別のリスクを名指ししていないこと（同じセッションで先に別の PR へ返した `許容する` を流用しないため）。通したら `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh 終了コード 0）` を追記する。

- 終了コード 0 でも、記録の日時と同じ timestamp の `MATCH:` が無いとき、または全文が `許容しない` のように許容の意思を示さないときは合格させない（手順6に戻して主に再確認する）
- 同じ timestamp が宣言コメントの作成日時より後でないとき、または全文が別の PR・別のリスクへの返事と読めるときは合格させない（手順6に戻して主に再確認する）
- 終了コード 1 は記録の誤りか捏造なので合格させない。記録を書き換えて通そうとせず、手順6に戻して主に再確認する
- exit 2（この PC に会話ログが無い・引数の不備）は確かめられないので合格させない。主に「会話の返事をこの PC では確かめられない」ことを伝え、PR のコメントか、ゲートと同じ PC での `/develop <記録先> 許容する` で受け直す

守備範囲: 会話ログの改変・追記は検知しない。別セッション方式の親セッションが決まった頭（`主の返事（親エピック #` / `親エピック #`）を付けて子のターミナルに打ち込んだ文は、`owner-reply-check.sh` が主の発言として数えない。頭の無い自由な文で打ち込んだ許容は `origin.kind` が human で残り、全文を読んでも主の発言と区別できないので、今までどおり通りうる。この経路は「エージェントが投稿した PR コメントも投稿者が主になる」従来の経路より弱くしないためのもので、偽造の経路を塞ぎ切ることを目的にしない。

**親経由で受けた許容（親経由で受領）の真正性確認。** エピックの子で、主が親のセッションの会話にだけ許容を返し、親が `epic-dispatch.sh reply --as owner` で末尾に ` [主の発言: セッション <親のセッション ID> / uuid <uuid>]` を添えて送ってきたときは、develop の本体が `owner-reply-check.sh --relayed` の終了コード 0 を確かめてから値（親のセッション ID・uuid・`MATCH:` の timestamp・停止の記録の URL・`MATCH:` の全文）を渡す。宣言コメントに次の 1 行を追記する（`<日時>` は `MATCH:` の行の timestamp、`<原文>` はその行の全文。行頭は `主の回答: 許容` のままにし、手順 3-c の「前の宣言の選び方」がこの記録を主の直接の回答として拾えるようにする）:

```
主の回答: 許容 — 親経由で受領（親セッション <セッション ID> / 発言 <uuid> / <日時>）停止の記録: <URL> 原文: <原文>
```

真正性確認では次をすべて確かめる。子に届いた文は主の発言と区別できないので根拠にせず、親の会話ログの行そのものを読む。

1. 停止の記録の URL のコメントを `gh api repos/$R/issues/comments/<comment_id> --jq '{body, author_association, issue_url, html_url, created_at}'` で読み、1 行目が `子の停止: 主の返事待ち`、`author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれか、`issue_url` がこの PR の記録先の issue であることを確かめ、作成日時（`created_at`）と URL（`html_url`）を取る。あわせて `gh api repos/$R/issues/<記録先>/comments --paginate --jq '[.[] | select(.author_association == "OWNER" or .author_association == "MEMBER" or .author_association == "COLLABORATOR") | select((.body | split("\n")[0]) == "子の停止: 主の返事待ち")] | last | .html_url'` で記録先の最新の停止の記録の URL を取り、`html_url` と一致することを確かめる（一致しなければ別の止まりの記録を渡されているので、合格させず手順6で主に聞く）
2. 記録のセッション ID・uuid と、1 で取った `created_at`・`html_url` で次を回し（記録の URL が `html_url` と文字列で違うときは `html_url` で回し、記録の URL を `html_url` に揃えた 1 行を宣言コメントに追記する）、終了コード 0 で、`MATCH:` の timestamp が記録の日時と同じであることを確かめる

   ```bash
   bash <plugin>/scripts/owner-reply-check.sh --relayed <セッション ID> <uuid> <停止の記録の作成日時> <停止の記録の URL>
   # 出力: 通れば MATCH: <timestamp> <本文の全文> と MATCHES=1 / 通らなければ REASON=<理由> と MATCHES=0
   # 終了コード: 0 = 通る / 1 = 通らない / 2 = 確かめられない（引数の不備・この PC に親の会話ログが無い）
   # REASON: not-found（その uuid の行が無い）/ not-owner（主の入力でない行。ツールの結果・親の発言・要約・hook の差し込み・決まった頭の打ち込み）/ not-after（停止の記録より前の発言）/ not-asked（停止の記録より後でその行より前に、URL を書いた親の発言が無い）/ not-direct（URL を書いた最後の親の発言とその行のあいだに、別の主の発言がある）
   ```

3. `MATCH:` の全文から許容の意思を読む（記録の原文だけで読まない）。全文がこの子・この PR への許容と読め、別の PR・別の記録先・別の子・別のリスクだけを名指しした答えでないことを確かめる。名指しが無い許容と、この子とほかの子をまとめて名指しした答え（例: `1034 も 1030 も許容`）は通す
4. その timestamp が、記録を追記する宣言コメントの作成日時より後であることを確かめる

通したら `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh --relayed 終了コード 0）` を追記する。どれかを満たさないとき（終了コード 1 の `not-found`・`not-owner`・`not-after`・`not-asked`・`not-direct`、終了コード 2 を含む）は合格させず、手順6に戻して、主に子のタブで直接返事を打ってもらうよう頼む。

守備範囲: 親の会話ログの改変・追記と、親のターミナルに決まった頭を付けずに打ち込まれた文（`origin.kind` が human で残る）は、この確認でも主の発言と区別できない。目的は従来の経路より弱くしないことで、偽造の経路を塞ぎ切ることではない。

**主の委任で親経由に受けた許容（親経由で受領（委任））の真正性確認。** エピックの子で、主が親のセッションでこのエピックのリスク許容を親に任せ（develop の `references/epic.md` の **主の委任**）、親が末尾に ` [主の委任: セッション <親のセッション ID> / uuid <確認の uuid> / 記録 <委任の記録の URL>]` を添えて送ってきたときは、develop の本体が `owner-reply-check.sh --delegated` の終了コード 0 を確かめてから値（親のセッション ID・確認の uuid・`MATCH:` の timestamp・委任の記録の URL・停止の記録の URL・`MATCH:` の全文）を渡す。宣言コメントに次の 1 行を追記する（`<日時>` は `MATCH:` の行の timestamp、`<原文>` はその行の全文。行頭は `主の回答: 許容` のままにし、手順 3-c の「前の宣言の選び方」がこの記録を主の直接の回答として拾えるようにする）:

```
主の回答: 許容 — 親経由で受領（委任）（親セッション <セッション ID> / 委任の確認 <uuid> / <日時>）委任の記録: <URL> 停止の記録: <URL> 原文: <原文>
```

真正性確認では次をすべて確かめる。子に届いた文は主の発言と区別できないので根拠にせず、エピックと PR のコメントと親の会話ログの行そのものを読む。この形は `owner-reply-check.sh --relayed` で確かめない（委任の確認は停止の記録より前の発言なので、`--relayed` では必ず `not-after` で落ちる）。

1. 停止の記録の URL のコメントを、上の「親経由で受けた許容（親経由で受領）の真正性確認」の 1 と同じ `gh api` で読み、1 行目が `子の停止: 主の返事待ち`、`author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれか、`issue_url` がこの PR の記録先の issue であることを確かめ、`created_at` と `html_url` を取る。あわせて同じ `--jq '... | last | .html_url'` で記録先の最新の停止の記録の URL を取り、`html_url` と一致することを確かめる
2. 委任が有効かを、develop と同じ次の文で確かめる: 委任の記録が、①エピック #<E> の issue のコメントで、1〜4 行目が定型の文ちょうど、2 行目の番号が <E> ②投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` のどれか ③エピックの、投稿者が同じ 3 種の `主の委任:` で始まるコメントのうち最新 ④`lastEditedAt` が null ⑤エピックが開いている ⑥子 issue がエピックの子（sub-issue か本文の子の表にある）。<E> は子に届いた返事の頭 `主の返事（親エピック #<E> 経由）` の番号で、委任の記録の URL の issue 番号と同じでなければ有効でない（定型の文は develop の `references/epic.md` の **主の委任** の委任の記録。`lastEditedAt` の読み方も同じ所にある）
3. 止まりに委任が効くかを、develop と同じ次の文で確かめる（②のコメントは記録を追記する宣言コメント）: ①子 issue の番号を、本文で最初に現れる `Closes #N`・`Fixes #N`・`Refs #N` の `N` に持つ開いた PR に `needs-approval` が付いている ②その PR の、投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` で `## リスク宣言` で始まる最新のコメントが `主のリスク許容が必要。` の行を持ち、`対象 HEAD:` が PR の今の HEAD と同じで、`主の回答:` で始まる行をまだ持たない（G では、今確かめている委任の形の記録の行だけは除く） ③停止の記録の作成日時が、そのコメントの作成日時と委任の確認の timestamp の両方より後 ④停止の記録の `推奨:` の値（先頭の空白を除く）が `許容する` で始まる
4. 委任の記録の作成日時（`gh api repos/$R/issues/comments/<comment_id> --jq .created_at`）と、1 で取った停止の記録の `created_at` で次を回し、終了コード 0 で、`MATCH:` の timestamp が記録の日時と同じで、`MATCH:` の全文から任せる意思が読めることを確かめる（記録の原文だけで読まない）

   ```bash
   bash <plugin>/scripts/owner-reply-check.sh --delegated <セッション ID> <uuid> <委任の記録の作成日時> <委任の記録の URL> <停止の記録の作成日時>
   # 出力: 通れば MATCH: <timestamp> <本文の全文> と MATCHES=1 / 通らなければ REASON=<理由> と MATCHES=0
   # 終了コード: 0 = 通る / 1 = 通らない / 2 = 確かめられない（引数の不備・この PC に親の会話ログが無い）
   # REASON: not-found（その uuid の行が無い）/ not-owner（主の入力でない行）/ not-after（委任の記録より後でない発言）/ not-asked（委任の記録より後でその行より前に、委任の記録の URL を書いた親の発言が無い）/ not-direct（URL を書いた最後の親の発言とその行のあいだに、別の主の発言がある）/ not-before（停止の記録より前でない発言）
   ```

通したら `真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh --delegated 終了コード 0）` を追記する。どれかを満たさないとき（`--delegated` の終了コード 1 の `not-found`・`not-owner`・`not-after`・`not-asked`・`not-direct`・`not-before`、終了コード 2、委任が有効でない〔取り消し済み・新しい記録がある・記録の編集・エピックが閉じている・別のエピック〕、止まりに委任が効かない〔`推奨:` の値が `許容する` で始まらない・リスク許容待ちでない・確認より前の止まり〕を含む）は合格させず、手順6に戻して、主に子のタブで直接返事を打ってもらうよう頼む。

守備範囲（委任の形）: 入力の出どころは、develop の本体が渡す値（親の添え書きを写したもの）、エピック・子 issue・PR のコメントとラベル（`gh api` で読む）、ゲートが動く PC の親の会話ログで、本体と G は協力的だが、写し間違い・別の記録との取り違え・確かめの省略をする前提で扱う。拾いたい誤りは、確認でない発言・別のエピックの記録・取り消し済みや編集済みの記録・範囲外の止まりを根拠に合格させること。委任の確認のあとに親が起動し直したものは通してよい。会話ログの改変の検知と、穴を塞ぎ切ることは目的にしない。

**issue で承認済みの確かめ直し。** issue で承認済みの 3 行が揃った宣言は、追記を読むだけで通さず、合格処理の前に `declarations.md` 手順 3 の条件を確かめ直す: `owner-reply-check.sh` を記録のセッション ID と原文で回し直し、終了コード 0 と同じ timestamp の `MATCH:` の全文から承認（`/develop <番号>` なら番号の境界）を読む／引用が issue 本文にある／issue に `agent-proposed` が無い／`lastEditedAt` が null か証拠の発言の timestamp より前／`EPIC_DISPATCH_PARENT_EPIC` と `--unmanned` の除外に当たらない／起票の承認なら S の決め方（URL の初出行が起票コマンドの tool_result であるログ）に合い、返事が答えた起票の提案を会話から特定でき、その提案が issue の目的と引用した各効果を含む（エピックの子なら、子の目的と効果が承認された提案の範囲内）／主に事後報告を届ける先がある（メインセッションで主と会話している、または develop の G として return で本体に渡せる）。どれかを満たさなければ合格させず、手順6で主に聞く（依頼に満たさなかった条件を添える）。確かめ直したら、同じ宣言コメントに次の 1 行を追記する:

```
確かめ直し: 済 — 確認者 <エージェント名> / <日時>（手順 5）
```

このとき `真正性確認: 済` の行は足さない（`stages/hold.md` の 3-c の「前の宣言の選び方」が見る行を増やさないため）。追記するのは、後から見て手順 5 で確かめ直したかが分かるようにするため。

無人運用（loop-dev-agent）と、主に事後報告を届ける先が無い経路（メインセッションで主と会話していない・develop の G でもない）では issue で承認済みを当てない（`declarations.md` 手順 3）。その経路でこの追記を見つけたら合格させず、手順6で保留にする。

**合格したら主に 1 回だけ事後報告する。** issue で承認済みで合格したら、宣言コメントの URL と、引用した issue の文と、当たった分類を 1 回で主に伝える（主が一度も見ないまま通った変更に、後から気づけるようにするため）。ゲートをメインセッションで回しているならその場で伝え、develop の G なら passed の return の `issue で承認済み:` の行に書き、本体が主に伝える。主が後から許容しないと答えたら、手順6の表の「不許容」の行と同じ扱い（revert を含む代替案の検討）にする。

**「投稿したつもり」を信用しない。** 合格処理の前に、**現在の PR HEAD と一致する SHA を含む宣言コメントと
証拠コメントが実在すること**を API で実測確認する（投稿失敗・旧 HEAD 向けコメントの流用を両方とも塞ぐ。
`gh api -X POST .../comments` は静かに失敗しうるので、投稿直後のレスポンスだけを根拠にしない）:

```bash
HEAD_SHA=$(gh api repos/$R/pulls/$N --jq '.head.sha')
gh api repos/$R/issues/$N/comments --jq \
  "[.[] | select(.body | contains(\"$HEAD_SHA\")) | .body | split(\"\n\")[0]]"
```

出力に**リスク宣言・仕様宣言・動作確認の 3 見出しがすべて**現れることを確認する。
1 つでも欠けていれば**合格処理をしない**（コメントを出し直してから再確認する）。

**仕様宣言は記録先の記録と突き合わせる。** 記録先は PR 本文で最初に現れる `Closes #N` / `Fixes #N` / `Refs #N`（大文字小文字不問）が指す元 issue で、**issue 参照が無い PR では PR 自身**（`$REC` を PR 番号に切り替える。PR のコメントも `issues/<番号>/comments` で読める）。そこから最新の `仕様化判断:` コメント（1 行目が `^仕様化判断: (する|しない)$`）を取る。このコメントは 1 行目だけでなく、2 行目以降の `通し方:` の行と `直す文:` の行も読む（文言合わせの通し方で仕様レビューを省いた PR を見分けるため）。PR コメントへの記録が許されるのは **PR 本文に issue 参照が無い場合に限る**（issue 参照があれば issue 側が正。issue 側に記録が無ければ issue に投稿する）。`$ISSUE` が空のまま `issues/$ISSUE/comments` を叩くと `issues//comments` で 404 になるので、必ず `$REC` を経由する:

```bash
ISSUE=$(gh api repos/$R/pulls/$N --jq '.body' | grep -oiE '(closes|fixes|refs) #[0-9]+' | head -1 | grep -oE '[0-9]+')
REC=${ISSUE:-$N}   # 記録先の番号: issue 参照があればその issue、無ければ PR 自身
# jq の ^ $ は行頭・行末に掛からない（文字列全体の先頭・末尾）ので、1 行目を split で切り出してから照合する。
# コメントは 30 件でページが切れるので --paginate --slurp で全ページを取り（--slurp は --jq と併用不可なので jq へパイプ）、add で 1 配列にしてから「最新 1 件」を選ぶ
gh api --paginate --slurp repos/$R/issues/$REC/comments | jq -r 'add | [.[] | select(.body | split("\n")[0] | test("^仕様化判断: (する|しない)$"))] | last | .body | split("\n")[0]'
gh api --paginate --slurp repos/$R/issues/$REC/comments | jq -r 'add | [.[] | select(.body | split("\n")[0] | test("^仕様レビュー: (APPROVE|REQUEST_CHANGES)$"))] | last | .body | split("\n")[0]'
# 2 つ目の出力が「仕様レビュー: APPROVE」ちょうどであること（最新のレビュー結果が正。古い APPROVE の後に REQUEST_CHANGES が出ていれば不合格）
bash <plugin>/scripts/spec-touch-check.sh $R $N   # SPEC_TOUCH / OPENSPEC_DIFF / 触れた規範パス。終了コード 2 = 規範パスに触れて openspec 差分なし
# 文言合わせの通し方かどうかは、同じ最新の仕様化判断のコメントの本文（2 行目以降）で見分ける
DEC=$(gh api --paginate --slurp repos/$R/issues/$REC/comments | jq -r 'add | [.[] | select(.body | split("\n")[0] | test("^仕様化判断: (する|しない)$"))] | last | .body')
WAY=$(printf '%s\n' "$DEC" | grep -cx '通し方: 文言合わせ')   # 1 以上なら文言合わせの通し方。0 件のとき grep の終了コードは 1 になるので、終了コードではなく出力の値で判定する
FIXES=$(printf '%s\n' "$DEC" | grep '^直す文: ')             # 直す要件ごとに 1 行
echo "$WAY"; printf '%s\n' "$FIXES"
# ここから下の 3 本は WAY が 1 以上のときだけ実行する。場所は PR の HEAD の作業ツリー（git rev-parse HEAD の出力が $HEAD_SHA と一致すること）。CHANGE には仕様宣言が指す change 名を入れる
ls openspec/changes/archive/*-"$CHANGE"/specs/*/spec.md | wc -l          # ちょうど 1（archive 済みで、差分が 1 ファイル）
grep -cE '^## (ADDED|REMOVED|RENAMED) Requirements' openspec/changes/archive/*-"$CHANGE"/specs/*/spec.md   # 0（ここも終了コードではなく出力の値で判定する）
grep -h '^### Requirement: ' openspec/changes/archive/*-"$CHANGE"/specs/*/spec.md | sed 's/^### Requirement: //' | while IFS= read -r REQ; do printf '%s\n' "$FIXES" | grep -qF "「${REQ}」" || echo "直す文に無い要件: ${REQ}"; done   # 何も出力されなければ、要件名はすべて直す文の行にある
```

| 記録先（issue、無ければ PR 自身）の記録 | 合格に必要な状態 |
|---|---|
| `仕様化判断: する`（`通し方: 文言合わせ` の行なし） | PR の変更ファイルに `openspec/` が含まれる、**または**宣言が指す change が base で archive 済み（`openspec/changes/archive/*-<change-name>/` の実在を実測。スタック PR で仕様が先行 PR に入っている場合）。**かつ** 記録先の最新の `仕様レビュー:` コメントが `APPROVE`（古い APPROVE の後に REQUEST_CHANGES があれば不可）。仕様宣言は「更新した」形 |
| `仕様化判断: する`＋`通し方: 文言合わせ` の行あり | `仕様レビュー:` のコメントは照合しない（この通し方では R1 を起こさないので、コメントが無いことを不合格の理由にしない）。代わりに次の 4 点をすべて実測する: ①仕様宣言が `仕様レビュー: 省いた（文言合わせ。` を含む「更新した」形 ②PR の HEAD で `openspec/changes/archive/*-<change-name>/specs/*/spec.md` に当たるファイルがちょうど 1 つ（archive 済みで、差分が 1 ファイル） ③そのファイルに ADDED / REMOVED / RENAMED の見出しが無い ④そのファイルの `### Requirement:` の要件名がすべて、`直す文:` で始まるどれかの行に `「<要件名>」` の形で現れる。1 つでも満たさなければ合格しない。直し方は、差分か仕様化判断のコメントを直して 4 点を満たすか、`通し方:` の行の無い仕様化判断を投稿し直して artifact 一式と仕様レビューからやり直すかのどちらか |
| `仕様化判断: しない` | 仕様宣言は「変更なし＋理由」形。PR に `openspec/` 差分が**無い**こと（差分があれば「しない」と矛盾＝合格しない。判断を「する」に取り直すか差分を外す）。`spec-touch-check.sh` が終了コード 2 なら、理由に規範パス接触への言及があること |
| 記録なし | **合格しない**。今から判断して記録先に `仕様化判断:` を投稿する（「する」なら仕様化・仕様レビューからやり直す）。issue が無い PR に限り PR 自身のコメントに同書式で記録してよい（`gh api -X POST repos/$R/issues/$REC/comments`） |

最新の仕様化判断のコメントに `通し方: 文言合わせ` の行が無い PR は、仕様宣言が `仕様レビュー: 省いた` の形でも「行なし」の行で照合する（`仕様レビュー: APPROVE` を求める）。4 点の照合は差分の形だけを見る。挙げた要件の中での書き換えすぎと、受け入れ条件と `直す文:` の行の食い違いは実装後レビューが見る。

**`needs-approval` が付いていないことを、Ready 化より前に確認する。** auto-merge は `needs-approval` を
BLOCKING_LABELS に含むため無審査マージにはならないが、**passed と併存すると
「合格済みなのに永久にマージされないスタック」**になり、Ready 化だけ済ませると保留中の PR が Draft でなくなる。
保留理由が解消しているなら `gh api -X DELETE repos/$R/issues/$N/labels/needs-approval` で外してから進む。
解消していないなら**そもそも合格処理をしない**（手順6に戻る）。

**PR が Draft なら Ready にしてから `agent-review:passed` を付ける**（この順序を入れ替えない）。
passed を先に付けると、その labeled イベントは PR が draft なので auto-merge workflow にスキップされる。
Ready 化で CI が走るリポでは CI 完了で拾い直されるが、CI を Draft 中に済ませて Ready 化では走らせないリポでは
次の判定が日次の schedule まで来ず、合格からマージまで最大 24 時間待つ。
Draft でない PR（人間が作った PR など）には Ready 化を行わない。
**Ready 化に失敗したら passed を付けずに止まる**（下の断片は非 0 で終わる）。draft のまま passed を付けると
その labeled イベントはスキップされて消費され、あとで Ready 化をやり直しても新しい labeled は起きないため、
Ready 化で CI が走らないリポでは日次の schedule まで拾われない。`draft` が取れなかったときも同じく止まる。

```bash
gh api repos/$R/issues/$N --jq '.labels[].name'   # needs-approval が無いことを確認（あれば上のとおり）
DRAFT=$(gh api repos/$R/pulls/$N --jq .draft)
case "$DRAFT" in true|false) ;; *) echo "draft を取得できない（$DRAFT）。passed を付けずに中断する" >&2; exit 1 ;; esac
if [ "$DRAFT" = true ]; then   # Draft なら Ready にする。失敗したら passed を付けずに中断する
  gh pr ready $N --repo $R || { echo "gh pr ready に失敗。passed を付けずに中断する" >&2; exit 1; }
fi
gh api -X POST repos/$R/issues/$N/labels -f 'labels[]=agent-review:passed'
gh api -X DELETE repos/$R/issues/$N/labels/agent-review:pending
gh api repos/$R/issues/$N --jq '.labels[].name'   # 実測確認（ラベル）
gh api repos/$R/pulls/$N --jq .draft              # 実測確認（Draft）
```

最後の実測確認は次の**4点すべて**を満たすこと（`gh` は静かに失敗することがある）:

| 確認項目 | 期待 |
|---|---|
| `agent-review:passed` | **ある** |
| `agent-review:pending` | **ない** |
| `needs-approval` | **ない** |
| PR の `draft` | **`false`** |

`needs-approval` が残っていたら合格処理は未完了（上の Ready 化前の確認に戻る）。
途中で止まったときは、passed が付いているかで復旧を分ける:

| 止まった状態 | 復旧 |
|---|---|
| Ready 化に失敗して止まった（`draft` が `true`、passed なし） | 失敗の原因（権限・ネットワーク等）を記録先に報告し、解消してから手順5の断片を再実行する |
| Ready 化は済んだが passed を付ける前に止まった（`draft` が `false`、passed なし） | 手順5の断片をそのまま再実行する（Draft でないので Ready 化は飛ばされ、passed の labeled で判定される） |
| passed は付いたが auto-merge が判定を取り逃がした（`draft` が `false`、passed あり、マージされない） | `docs/auto-merge.md` の手動実行（`workflow_dispatch` の `pr` 入力）で再判定する |
| `draft` が `true` のまま passed が付いている（旧手順や手動操作の残骸） | passed を外し、`gh pr ready` で Ready にしてから passed を付け直す（付け直しで新しい labeled が起きる） |

聖域パス（auto-merge workflow の SACRED 定義。例: `.github/workflows/` `CLAUDE.md` `.claude/` 憲法 doc）に
触れる PR は passed でも auto-merge されず人間マージになる — 判定の正本は auto-merge workflow 側。
触れている自覚があればコメントに1行書き添える。auto-merge 未配備のリポでは、合格処理の後に
「マージは人間の操作待ち」であることを PR コメントに1行残す。対象 HEAD の CI が失敗か未決着のときは、
その1行に CI の状態と、合格後の CI の見張りが結論を出すまでマージしない旨を添える
（例: 「マージは人間の操作待ち。CI は実行中 <run の URL>。見張りが結論を出すまでマージしない」）。

**合格後の CI の見張り**（上の実測確認が済んでから。手順 6 で合格しなかった PR には始めない）:

- ゲートをメインセッションで回している場合: `plugins/dev-workflow/references/ci-watch.md` の手順で、`scripts/ci-watch.sh wait` を Bash ツールの `run_in_background` で起動して見張りを始める
- ゲートをサブエージェント（develop の G など）が回している場合: 見張りを始めずに `passed` を return し、呼び出し側の本体に見張りを任せる（サブエージェントは背景タスクの完了で起こされない）

待ち方・`--unrelated` の基準・一手ごとの動き・直し方は `references/ci-watch.md` が正本で、ここには再掲しない。直しで commit が積まれたら、`agent-review:passed` を外したまま見張りを続けて CI のやり直し・再度の直しを済ませ、`ready` になってから、この PR のゲートを手順 1 から取り直す。取り直したゲートに合格するまでマージ待ち・マージ依頼に進まない。

## G として動くとき（develop）

この節は develop の G（`skills/develop/references/roles/gate-runner.md` の指示で動くゲート実行者）だけに関係する。develop 以外の読み手は読み飛ばしてよい。

### return の書式（passed）

`gate-runner.md`「return の書式」の共通欄（`## Gate Result` から `周回:` まで）のうしろに続ける。

```markdown
### passed のとき
G は CI の見張りを始めずに `passed` を return する（背景タスクの完了で起こされないため。見張りは本体が `references/ci-watch.md` で行う）。
- 付与ラベル: agent-review:passed（手順 5 の API 実測の結果）
- Ready 化: 実施した | 対象外（元から非 Draft）（手順 5 で `draft` が `false` になったことを実測した結果）
- コメント URL: リスク宣言 / 仕様宣言 / 動作確認証拠
- issue で承認済み: <宣言コメントの URL> / <当たった分類> / 「<引用した issue の文>」（issue で承認済みで合格したときだけ書く。無ければ行ごと省く）
```


### この段で起こされたときの入力

合格処理の G は、起動指示の前の段の `## Gate Result` ブロックを受け取り、前の段の会話は持たない前提で PR コメントから固定 HEAD と仕分けを読む。

- **照合と振り分けのあと**（前の Gate Result が `段: 照合と振り分け`）: `declarations.md` の手順 3 から入る。宣言の前に前の HEAD の許容があれば、`stages/hold.md` を読んで手順 3-c の引き継ぎを試す
- **保留の解除のあと**（前の Gate Result が `段: 保留の解除`）: 今の HEAD の `対象 HEAD:` を持つ `## リスク宣言` コメントがあれば、宣言を出し直さず手順 5 の真正性確認から入る。無ければ（切り出しの確認を解除した場合）`declarations.md` の手順 3 から入る。HEAD が動いていて前の HEAD の許容があるときは、宣言の前に `stages/hold.md` の 3-c を試す
- 保留を返すときは `stages/hold.md` の「G として動くとき（develop）」節の書式で返す（`次の段: 保留の解除`）
## 出口

- 手順 4 で主に動作確認を依頼したとき、手順 5 の照合で主の許容待ちが残ったときは `stages/hold.md`（手順 6）へ進む。
- 手順 5 で `agent-review:passed` を付けたら、ゲートは終わる（CI の見張りは手順 5 のとおり）。
