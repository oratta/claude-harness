# triage-epic — pr-review-gate

入口: 親を取得済みで段 C を当てるときだけ読む。

**段 C（エピックの完了条件に効く指摘を、既存 issue との関係で分ける）**: 親の探索は `stages/triage-nonblocking.md` で段 B より先に済ませる。

親のリポジトリ（`repository_url` の末尾の `<owner>/<name>`）が、小文字にそろえて `$R` と違うときは、エピックの本文と `## 条件の答え` を親のリポジトリで読み書きし、候補探しは `--epic` を付けずに走らせて全候補を `other` として読む。下の表の「エピックの子に足す」操作は、既存の issue も新しい子 issue も `repos/<親のリポジトリ>/issues/<親の番号>/sub_issues` に対して行い（足す要求は `-X POST repos/<親のリポジトリ>/issues/<親の番号>/sub_issues -F sub_issue_id=<id>`。`<id>` は番号でなく issue の `id`）、新しい issue そのものは `$R` に作る。親のリポジトリの本文を読めない・書けないときは、親の取得の失敗と同じに扱う。全候補を `other` と読むので、すでに親の子である `$R` の issue も「外の issue」に当たりうる。その確かめはしない（子に足す操作が拒否されたら、仕分けの PR コメントに書く）。守備範囲の許す誤り: 親が見えず 404 になる場合（親が private リポジトリにあり G のトークンが読めないとき）を「親が無い」と読むこと（`No parent issue found` かの区別はしない）、別リポジトリの親で、すでに親の子である同じ場所の issue があっても新しい子 issue ができること。エピックに属する PR で、段 B の「範囲で成り立つ」に当たった指摘について、エピックの完了条件に効くか（出荷物を使う人の体験が変わるか）を、エピックの本文の完了条件を根拠に決める。効かない指摘は段 D へ進める。効く指摘は、候補探しの結果で次の表のとおりに分ける。

| 候補探しの結果 | 扱い |
|---|---|
| 同じエピックの子 issue（`child`）に、同じ場所を直すものがある | その子 issue の受け入れ条件に足す（その子が作業中でないとき。作業中なら新しい子 issue を作る） |
| エピックの外の issue（`other`）に当たり、その issue の受け入れ条件が、この指摘を直せば全部満たされる | その issue をエピックの子に足す。新しい子は作らない。足した理由をその issue にコメントする |
| エピックの外の issue に当たるが、満たされない項目が 1 つでも残る。または受け入れ条件が書かれていない | この指摘だけの新しい子 issue を作る。外の issue には「この部分は子 issue で直す」と番号を書き、エピックには足さない |
| 当たる issue が無い | 新しい子 issue を作る |

子の行で受け入れ条件に足す前に、その子 issue が作業中かを確かめる（`develop 開始` か `実行モード:` の行があるコメントと、本文に `Closes` / `Fixes` / `Refs #<番号>`（大文字小文字不問）のある open の PR のどちらか。判定の正本は `openspec/specs/in-progress-issue-scope/spec.md`）。`gh issue view <番号> -R $R --json comments` と `gh pr list -R $R --state open --search "<番号> in:body" --json url,body` の 2 回で足り、issue の本文だけで作業中でないと判断しない。作業中なら足さず、この指摘だけの新しい子 issue を同じエピックの子として作り、本文に作業中の子の番号と「作業中の子の PR のマージ後に着手」を書き、作業中の子には新しい子の番号をコメントで書く（受け入れ条件は編集しない）。主に聞かない。どちらかの呼び出しが 0 以外で終わったら 1 回だけやり直し、それでも取れなければ作業中と同じに扱って新しい子 issue を作る。判定のスクリプトは作らない。

3 列目が `other` の候補（`--epic` を付けない実行ではすべての候補）に対して、コメント以外の操作（本文を読んで受け入れ条件が全部満たされるかを判定する・エピックの子に足す・受け入れ条件に足す）をする前に、`gh api repos/$R/issues/<番号> --jq .author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれかであることを確かめる。それ以外の値のとき、または取得に失敗したときは、その候補を「当たる issue が無い」と同じに扱う（本文を読まない）。外の issue に open の PR が付いているときは、新しい子 issue に「外の PR のマージ後に着手」と書く。エピックの中と外に同じファイルを直す issue が並ぶときは、互いの番号を書く。

出口: `stages/triage-nonblocking.md` の段 C を呼んだ箇所へ戻る。
