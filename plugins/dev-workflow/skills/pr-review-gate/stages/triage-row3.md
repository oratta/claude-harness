# 順 3 の一覧の照合 — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。`## 一覧（順 3）` の PR コメントを照合するときに読む。一覧の書式は `stages/row3-list-format.md`。

**順 3（一覧の一致で閉じる）**: G はレビューをせず、最初に `git fetch` で W の push を取り込み、`git cat-file -e <修正前 SHA>^{commit}` で修正前 SHA のコミットが実在することを確かめる（解決できないときだけ、照合の起点が失われているので W に表の出し直しを求める。祖先であることまでは求めない）。そのうえで次の 2 段で照合する（「該当しない理由」の正否を判定しない。書き換えの妥当性も判定せず集合だけを見る）。grep の語は 2 段とも `plugins/dev-workflow/scripts/review-hit-set.py --head <HEAD の 40 桁 SHA> --repo <repo> <table-file>` の 1 回の実行で回す（`<HEAD の 40 桁 SHA>` は `git fetch` で W の push を取り込んだあとの HEAD の 40 桁フル SHA。`<repo>` はリポジトリルートのパスで、GitHub のリポジトリ名 `<owner>/<repo>` ではない。`--head` を付けないと 1 段目だけを行う）:
1. 修正前 SHA で検索コマンドを実行したヒット集合が表の全行（扱いを問わない）と一致するかを見る。ここでの表は主表で、補助表はこの段で使わない
2. HEAD で同じ検索コマンドを実行し、残ったヒットがすべて、扱いが「該当しない」の行に対応するかを見る。各「該当しない」行の照合に使う本文は、補助表に載っていれば修正後の本文、載っていなければ主表の本文とする。対応は「ファイル」と「ヒットした行の本文」の組で取り、行番号では取らない。同じ組が複数あるときは件数で照合する。書き換えで検索語を含まなくなった「該当しない」行が HEAD に現れないことは不一致としない。ただし、修正前 SHA で同じファイル・同じ本文の組に「直した」と「該当しない」の両方があるとき（扱いが混在する組）は、件数の一致だけでは直し忘れを見分けられないので、あわせて `git diff <修正前 SHA> HEAD -- <ファイル>` の出力のうち `-` で始まりその本文が続く行の件数が、その組の「直した」の件数と、その組のうち補助表に載った「該当しない」の件数の和以上であることを見る。足りなければ、その組の「直した」の行を「直したはずが残った」差分として W に返す

場合分けの軸のときは、ヒットの集合がコミットによらず軸の全域で決まるので、1 段目として表の行の集合が軸の全域と一致するかだけを見て、2 段目を行わない。どちらの段でも一致しなければ、その差分（表に無いヒット、ヒットに無い表の行、「該当しない」の行に対応しない HEAD のヒット、扱いが混在する組で削除行が足りない「直した」の行、主表の「該当しない」行を指さない補助表の行、重複した補助表の行、書き換えていない補助表の行）だけを W に返す。差し戻しは 1 回まで（表の出し直しを求めた場合を含む）で、2 回目も一致しなければ順 6 に落とす。順 3 の照合はレビューの周に数えない（G はレビューをしないので、周回キャップとは別に差し戻しの上限で止める）。同じ failed で戻した指摘が順 3 だけなら、集合が一致して閉じたあとに差分限定の再レビューは行わず、周を消費しない（閉じた PR コメント URL を仕分け欄に残す）。順 2・順 4 の指摘が同じ failed に含まれていれば、それらの差分限定の再レビューは通常どおり行い、周を 1 つ消費する。

**戻した指摘が順 3 だけの修正のあと**: 照合と振り分けの G は `stages/prepare-step1.md` で新しい HEAD を固め、前の重さ判定を写した `レビュー重量:` コメントを `固定 HEAD: <新しい HEAD>` 付きで投稿してから、再レビューをせず一覧表のコメントの修正前 SHA と HEAD の 2 段で集合を照合して閉じ、周を消費しない。
