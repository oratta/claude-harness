# issue-approved — pr-review-gate

#### issue で承認済み（「主のリスク許容が必要」の宣言に追記する状態）

記録先の issue が目的として書いた効果は、主が issue を書くか承認した時点で受け入れている。その効果のために PR のたびに許容を聞き直さないよう、「主のリスク許容が必要」と判定した宣言に下の 3 行を追記した状態を「issue で承認済み」と呼ぶ。第 3 の宣言文ではない（宣言の行頭の 2 文言は変えない）。

当てられるのは資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張の 3 分類だけである。外部公開面の変化・データ喪失・課金/法務・プロダクトのユーザーに及ぶ影響は、issue に書いてあっても主に聞く。宣言の `- 該当する観点:` にこの 4 分類のどれかが 1 つでも含まれる、または引用の付かない分類が 1 つでもあるときは、宣言全体を手順6で主に聞く（一部の分類だけを承認済みにしない）。

無人運用（loop-dev-agent の憲法がレビューモードで回すゲート。`stages/triage.md` が「無人運用（loop-dev-agent）」と呼ぶもの）と、主に事後報告を届ける先が無い経路（メインセッションで主と会話していない・develop の G でもない）では、下の条件をすべて満たしても「issue で承認済み」を当てない。従来どおり手順6で `needs-approval` を付けて保留にする（主との会話が無く、合格後の事後報告を載せる先が無いため）。

当てるのは次の 3 条件をすべて満たすときだけ:

1. 記録先の issue の本文が、当たった分類の効果をその issue の目的として書いている。該当の文を分類ごとに宣言へ引用する（背景や備考で触れただけの文は目的ではない）
2. 主がその issue を承認した証拠が会話ログにあり、`owner-reply-check.sh` の終了コード 0 で確かめられる。証拠は下の起票の承認か、主が自分で打った `/develop <番号>` のどちらか。どちらの形でも、issue 本文の `lastEditedAt`（`gh api graphql -f query='{repository(owner:"<o>",name:"<r>"){issue(number:<N>){createdAt lastEditedAt}}}'`。未編集なら null）が null か、証拠の発言の timestamp より前であること（承認のあとに本文が書き換えられていないこと）
3. 実装中に発覚した影響ではない（宣言の `- 検知時点:` が `issue 記載済み`）

証拠の確かめ方（`owner-reply-check.sh` は `bash <plugin>/scripts/owner-reply-check.sh <セッション ID> <原文>` で回す。出力と終了コードの意味は `stages/pass.md` の手順 5「会話で受けた許容」の段落にある）:

- **`/develop <番号>`**: セッション ID は `$CLAUDE_CODE_SESSION_ID`（develop の G では本体のセッション）、原文は `<command-args><番号>` または `<command-args>#<番号>`。終了コード 0 で、`MATCH:` の全文が `<command-name>/dev-workflow:develop</command-name>`（または `/develop`）を含み、`<command-args>` の直後が `<番号>` または `#<番号>` で、その後ろが空白か `</command-args>` であることを確かめる（`7234` の中の `723` のような番号の部分一致を通さない）
- **起票の承認**: 起票したセッション S の会話ログで、issue の URL（`https://github.com/<R>/issues/<N>`）が最初に現れる行より前にある主の発言のうち、最後のものを起票を承認した発言の候補とする（候補のままでは証拠にしない。下の提案の照合を通ったものだけを起票を承認した発言とする）。S を探すには、URL を含む会話ログを `grep -l '<URL>' "${OWNER_REPLY_PROJECTS_DIR:-${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects}"/*/*.jsonl` で集める（`owner-reply-check.sh` が読むのと同じ場所。`subagents/` の下は見ない）。
  - S にするのは、URL の初出行が、その直前の tool_use（`gh issue create` または `gh api -X POST repos/<R>/issues`）に対応する tool_result であるログだけ。初出行がそれ以外（`gh issue view` の出力・主の発言・`/develop` の引数など）のログは、issue を参照しただけのセッション（この develop のセッションや別セッション方式の子のセッションを含む）なので S にしない
  - S の候補が 0 件（別の PC で起票した、など）なら、起票の承認の証拠は使わず手順6で主に聞く
  - 起票の承認には `<command-name>` を含む行（スラッシュコマンド）を使わない（`/develop` は `/develop <番号>` の証拠としてだけ扱い、下の除外を通す）。選んだ発言の原文で `owner-reply-check.sh <S のセッション ID> <原文>` を回し、終了コード 0 と同じ timestamp の `MATCH:` を確かめ、その全文から起票の承認（「起票して」「epic にして」「OK」など）が読めることを確かめる
  - 候補の発言が何への返事かを確かめる。返事が答えた起票の提案（候補より前のエージェントの発言で、起票する issue の題名・目的・効果を示したもの）を S の会話から特定し、その提案が対象 issue の目的と、条件 1 で引用した各効果をすべて含むことを確かめる。提案を特定できない、または issue の目的や引用した各効果のどれかが提案に無いなら、証拠にせず手順6で主に聞く（依頼に満たさなかった条件を添える）。`owner-reply-check.sh` は発言の実在だけを確かめ、何への返事かは見ないので、この照合は G が会話を読んで行う
    - 負例: 「README の誤字修正を起票しますか」への「OK、起票して」のあとに、安全ゲートを撤去する issue が起票された。返事が答えた提案に issue の目的が無いので、起票の承認の証拠にならない
    - 正例: 「安全ゲート X を撤去する issue を起票しますか（目的と効果: …）」への「OK、起票して」のあとに、その issue が起票された。提案が issue の目的と引用した効果を含むので、起票の承認の証拠になる
  - 主のエピックの起票の承認は、同じセッション S でそのあと続けて起票された子の起票の承認の証拠になる（子の URL の初出行より前の主の最後の発言がその承認になる）。ただし子の目的と引用した各効果が、主が承認したエピックの提案に含まれる（承認された提案の範囲内である）ことを上と同じく確かめ、範囲外なら証拠にせず手順6で主に聞く。別のセッションでエピックの親が自動で起こした子の証拠にならない

当てない issue と数えない証拠: `agent-proposed` ラベルが付いた issue（主が「あとで見る」と言った印なので、会話ログに承認らしい発言があっても当てない）と、主の承認の記録が無いままエージェントが起こした issue（エピックの親が自動で起こした子を含む）には当てない。`EPIC_DISPATCH_PARENT_EPIC` が空でないセッション（別セッション方式の親が子のターミナルに打ち込んだもの）の `/develop`、`<command-args>` に `--unmanned` を含む `/develop`（無人ループの起動）、全文が保留や却下（「あとで見る」「やめて」など）と読める発言は証拠として数えない。

当てたときの書き方: 宣言の本文（行頭 `主のリスク許容が必要。`）は書き換えない。末尾に次の 3 行を追記し、`needs-approval` を付けずに手順4・5へ進む（手順 5 で G が条件を確かめ直す）:

```
issue で承認済み — issue #<N> の目的: 「<本文からの引用>」
承認の証拠: <起票の承認 | /develop の打ち込み>（セッション <セッション ID> / <日時>）原文: <原文>
真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh 終了コード 0）
```

当たった分類が 2 つ以上なら、1 行目を分類ごとに並べてよい（`issue で承認済み — <分類>: issue #<N> の目的: 「…」`）。追記の行頭を `主の回答: 許容` にしない（`stages/hold.md` の 3-c の「前の宣言の選び方」に拾われ、主の直接の回答ではない記録が引き継ぎの元になるのを避けるため）。条件を 1 つでも満たさなければ当てず、手順6で主に聞く（依頼に満たさなかった条件を添える）。

守備範囲: ①入力の出どころは、記録先の issue（本文・ラベル・`lastEditedAt`）と、ゲートが動いている PC の会話ログと、G の環境変数（`CLAUDE_CODE_SESSION_ID`・`EPIC_DISPATCH_PARENT_EPIC`）。G は協力的だが、目的でない文を目的として引用する・別の issue の `/develop` を拾う前提で扱う ②拾いたい誤りは、issue に書かれていない効果や 4 分類の影響を承認済みにすること、別の起票の提案への返事を対象 issue の承認として数えること、エージェントが起こしただけの issue を承認済みにすること、別セッション方式の親や無人ループの `/develop` を主の打ち込みとすること、番号の部分一致、承認のあとに書き換えられた本文の引用 ③通ることを許す入力は、別セッション方式の起動部品以外の仕組みが `EPIC_DISPATCH_PARENT_EPIC` を付けずに本体のターミナルへ打ち込んだ `/develop`（主の打ち込みと区別できない）と、ローカルの会話ログの改変・追記 ④ここに挙げた以外の経路は見つけるたびに検査を足し、穴を塞ぎ切ることを完了条件にしない。


**issue で承認済みの確かめ直し。** issue で承認済みの 3 行が揃った宣言は、追記を読むだけで通さず、合格処理の前に `declarations.md` 手順 3 の条件を確かめ直す: `owner-reply-check.sh` を記録のセッション ID と原文で回し直し、終了コード 0 と同じ timestamp の `MATCH:` の全文から承認（`/develop <番号>` なら番号の境界）を読む／引用が issue 本文にある／issue に `agent-proposed` が無い／`lastEditedAt` が null か証拠の発言の timestamp より前／`EPIC_DISPATCH_PARENT_EPIC` と `--unmanned` の除外に当たらない／起票の承認なら S の決め方（URL の初出行が起票コマンドの tool_result であるログ）に合い、返事が答えた起票の提案を会話から特定でき、その提案が issue の目的と引用した各効果を含む（エピックの子なら、子の目的と効果が承認された提案の範囲内）／主に事後報告を届ける先がある（メインセッションで主と会話している、または develop の G として return で本体に渡せる）。どれかを満たさなければ合格させず、手順6で主に聞く（依頼に満たさなかった条件を添える）。確かめ直したら、同じ宣言コメントに次の 1 行を追記する:

```
確かめ直し: 済 — 確認者 <エージェント名> / <日時>（手順 5）
```

このとき `真正性確認: 済` の行は足さない（`stages/hold.md` の 3-c の「前の宣言の選び方」が見る行を増やさないため）。追記するのは、後から見て手順 5 で確かめ直したかが分かるようにするため。

無人運用（loop-dev-agent）と、主に事後報告を届ける先が無い経路（メインセッションで主と会話していない・develop の G でもない）では issue で承認済みを当てない（`declarations.md` 手順 3）。その経路でこの追記を見つけたら合格させず、手順6で保留にする。

**合格したら主に 1 回だけ事後報告する。** issue で承認済みで合格したら、宣言コメントの URL と、引用した issue の文と、当たった分類を 1 回で主に伝える（主が一度も見ないまま通った変更に、後から気づけるようにするため）。ゲートをメインセッションで回しているならその場で伝え、develop の G なら passed の return の `issue で承認済み:` の行に書き、本体が主に伝える。主が後から許容しないと答えたら、手順6の表の「不許容」の行と同じ扱い（revert を含む代替案の検討）にする。
