# 照合と指摘の振り分け — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/prepare.md`（手順 1・2・2-0）、`stages/reviewer-brief.md`（2-1 のレビュアー向け指示）、`declarations.md`（手順 3・3-b）、`stages/hold.md`（手順 3-c・6）。

## 入口

レビュー結果に指摘が残っているとき（develop の G は `gate-runner.md` の三表の機械照合を済ませたあと）、W の修正後の再レビュー、決める役の裁定を受け取ったときに読む。

## 手順

#### 2-1. レビューの実行（止める判定と仕分け）

**マージを止めるかの判定（全周共通）**: マージを止めるのは、深刻度が `blocking` で、根拠の引用を G が記録先（issue または Draft PR 本文）の受け入れ条件、またはこの PR が触れる openspec の spec（change の delta spec を含む）の原文と照合できた（または根拠が例外 3 種＝安全機構の穴・データ破壊・無言の機能不全に当たる）、かつ検証が `confirmed` の指摘だけ。それ以外（`should`・`nit`・`plausible`・照合できない `blocking`）はマージを止めず、follow-up issue に回す。レビュアー（Codex・Task サブエージェント）の深刻度ラベルは参考にとどめ、判定の根拠は G の照合にする。この判定は 1周目・2周目・主の続行指示で開いた周の全周で同じ。

止める指摘が残ったら、動き方は下の「止める指摘の仕分け表」に従う（判定は「マージを止めるかの判定（全周共通）」のまま。周によって変わるのは、表のどの順を使えるかだけ）。

1周目で failed にするとき、止めない指摘は failed の PR コメントに一覧で残し、follow-up issue はまだ切らない（W が同じ周で直すことがあり、先に切ると重複する）。止める指摘が無い周は failed にせず、G が手順3へ進むときに、未解決の止めない指摘を follow-up issue に切って URL を PR コメントに記録する。

**止める指摘の仕分け表**（G は周回の数に関係なく、指摘が届くたびに上から当てる。表はここにだけ置き、他の節とファイルは順番号と見出しで参照する）:

| 順 | 当てる条件 | 動き | 主に聞くか |
|---|---|---|---|
| 1 | 止める判定に達しない（上の全周共通の判定で止まらない） | follow-up issue に回す（1周目は上の段落どおり failed の一覧に残す） | 聞かない |
| 2 | 受け入れ条件の中（根拠の引用元が記録先の受け入れ条件、またはこの PR の change の delta spec） | W が直す。`agent-review:failed` で W に戻す | 聞かない |
| 3 | 一覧の一致で閉じられる型（「同じ文が別の場所に残っている」「N 件のうち k 件しか直っていない」） | W に一覧を作らせ、G は検索結果の集合一致で閉じる。`agent-review:failed` で W に戻す | 聞かない |
| 4 | 今直す 3 条件を満たす | W がその場で直し、仕分け欄に記録する。`agent-review:failed` で W に戻す | 聞かない |
| 5 | 順 1〜4 に当たらず、順 6 の条件にも当たらない | 主に「この欠陥を残して切り出すか」を聞く。`needs-approval` を付けて保留で return | 聞く |
| 6 | 同じ型の再発、または順 3・順 4 からの落とし込み | 決める役が方式を裁定する。Status `needs-decider` で本体に return | 聞かない（裁定が「切り出す」なら順 5 と同じ経路） |

2 周目以降の周の終わり（2周目の終わりと、主の回答または決める役の裁定で開いた周の終わり）に止める指摘が残っていれば、順 2〜4 を使わない。前の周と同じ型の再発に当たる指摘は順 6、それ以外は順 5 に当てる。仕分けの結果（指摘ごとに当てた順とその根拠）は PR コメントに記録する。

同じ周に順 5 の指摘と順 2〜4 の指摘が混ざったら、保留を先にする。G は全件の仕分けを PR コメントに記録して保留で return し、主の回答後に、切り出さない指摘をまとめて 1 回の `agent-review:failed` で W に戻す。主の回答が来るまで、W は順 2〜4 の指摘の修正にも着手しない。`needs-approval` と `agent-review:failed` を同時に付けない。

同じ周に順 5 の指摘と順 6 の指摘が混ざったら（順 2〜4 の指摘を含んでもよい）、これも保留を先にし、次の順で処理する（主の回答を先にするのは、主が「切り出す」と答えた指摘に触れる順 6 の指摘があれば裁定の対象が変わるためで、裁定は PR ごとに 1 回までなので対象が減ってから使う）:
1. G は全件の仕分けを PR コメントに記録し、`needs-approval` を付けて保留で return する。主への質問は順 5 の指摘についてだけ出し、順 6 の指摘は仕分け欄に「順 6・未裁定」として載せる
2. 主の回答が来たら、G は順 5 の指摘を手順 6 の表の「切り出しの確認」行どおりに処理して `needs-approval` を外す。未処理の順 6 の指摘が残っていれば、`agent-review:failed` を付けずに Status `needs-decider` で return する
3. 裁定が「全部列挙してから直す」なら、主が「この PR で直す」と答えた指摘・順 6 の指摘・順 2〜4 の指摘をまとめて、1 回の `agent-review:failed` で W に戻す。裁定が「切り出す」なら、順 6 の指摘について順 5 と同じ経路で主に聞き（再び保留）、その回答が来てから残る修正を 1 回の `agent-review:failed` で W に戻す

この PR で決める役の裁定が既に 1 回あれば（順 6 の数え方で 1 件以上）、順 6 の指摘は最初から「切り出す」として順 5 の経路に入るので、1 の質問に含めて 1 回の保留にまとめる（主に 2 回に分けて聞かない）。主の回答と裁定の両方が済むまで、W は順 2〜4 を含むどの指摘の修正にも着手しない。

**順 3（一覧の一致で閉じる）**: W は、修正前 SHA・検索コマンド・全ヒットに「直した／該当しない理由」を付けた表を 1 つの PR コメントに投稿してから push する。修正前 SHA は、W が修正に着手する直前の HEAD（G が `agent-review:failed` を付けた周の対象 HEAD）の 40 桁フル SHA とする。一覧表の PR コメントの書式は`stages/reviewer-brief.md` の共通一覧契約を正本とする（worker.md と照合表はこれに揃える）:
- 1 行目 `## 一覧（順 3）`、続けて `修正前 SHA: <40 桁>` の行と `検索コマンド: <コマンド>` の行を置き、その下に表を置く
- grep の語のときは共通一覧契約（`stages/reviewer-brief.md`）どおり `<rev> -- .` と全追跡対象パスを使う（G が `<rev>` を修正前 SHA と HEAD に置き換えて実行する）。作業ツリーに対する `grep -rn`、検索起点の限定、追跡対象パスの除外は使わない
- 場合分けの軸のときも `修正前 SHA:` の行は同じく書き、共通一覧契約の対象外とする。`検索コマンド:` の行には軸とその全域（例: 先頭バイトなら 0x00〜0xFF）を書き、表の列は `| 軸の値 | 扱い |` とする
- grep の語のとき、主表の本文列は常に修正前 SHA での本文とする。扱いが「該当しない」の行の本文を同じ周の修正で書き換えたなら、主表の下に見出し `### 書き換えた該当しない行` と表 `| ファイル | 行（修正前 SHA） | 修正後の本文 |` を置き、書き換えた「該当しない」行をすべて載せる（補助表）。補助表の各行は、主表で扱いが「該当しない」の行を `(ファイル, 行（修正前 SHA）)` でちょうど 1 つ指す。同じ `(ファイル, 行（修正前 SHA）)` を補助表に 2 回載せない。修正後の本文が主表の本文と等しい行（書き換えていない行）は載せない。修正後の本文の escape と fence は主表の本文列と同じ規則とする。書き換えた行が無ければ補助表は省略してよい
- 扱いの欄は `直した` か `該当しない: <理由>` のどちらかちょうどにする
- 順 6 の裁定「全部列挙してから直す」で W が作る一覧も、同じ見出し `## 一覧（順 3）` と同じ書式を使う

G はレビューをせず、最初に `git fetch` で W の push を取り込み、`git cat-file -e <修正前 SHA>^{commit}` で修正前 SHA のコミットが実在することを確かめる（解決できないときだけ、照合の起点が失われているので W に表の出し直しを求める。祖先であることまでは求めない）。そのうえで次の 2 段で照合する（「該当しない理由」の正否を判定しない。書き換えの妥当性も判定しない。集合の一致だけを見る）。grep の語は 2 段とも `plugins/dev-workflow/scripts/review-hit-set.py --head <HEAD の 40 桁 SHA> <table-file>` の 1 回の実行で回す（`<HEAD の 40 桁 SHA>` は `git fetch` で W の push を取り込んだあとの HEAD の 40 桁フル SHA。`--head` を付けないと 1 段目だけを行う）:
1. 修正前 SHA で検索コマンドを実行したヒット集合が表の全行（扱いを問わない）と一致するかを見る。ここでの表は主表で、補助表はこの段で使わない
2. HEAD で同じ検索コマンドを実行し、残ったヒットがすべて、扱いが「該当しない」の行に対応するかを見る。各「該当しない」行の照合に使う本文は、補助表に載っていれば修正後の本文、載っていなければ主表の本文とする。対応は「ファイル」と「ヒットした行の本文」の組で取り、行番号では取らない（修正で前後の行が増減すると行番号がずれるため）。同じ組が複数あるときは件数で照合する。書き換えで検索語を含まなくなった「該当しない」行が HEAD に現れないことは不一致としない。ただし、修正前 SHA で同じファイル・同じ本文の組に「直した」と「該当しない」の両方があるとき（扱いが混在する組）は、件数の一致だけでは直し忘れを見分けられないので、あわせて `git diff <修正前 SHA> HEAD -- <ファイル>` の出力のうち `-` で始まりその本文が続く行の件数が、その組の「直した」の件数と、その組のうち補助表に載った「該当しない」の件数の和以上であることを見る。足りなければ、その組の「直した」の行を「直したはずが残った」差分として W に返す

場合分けの軸のときは、ヒットの集合がコミットによらず軸の全域で決まるので、1 段目として表の行の集合が軸の全域と一致するかだけを見て、2 段目を行わない。どちらの段でも一致しなければ、その差分（表に無いヒット、ヒットに無い表の行、「該当しない」の行に対応しない HEAD のヒット、扱いが混在する組で削除行が足りない「直した」の行、主表の「該当しない」行を指さない補助表の行、重複した補助表の行、書き換えていない補助表の行）だけを W に返す。差し戻しは 1 回まで（表の出し直しを求めた場合を含む）で、2 回目も一致しなければ順 6 に落とす。検索コマンドや軸の全域を W が書けない指摘は順 3 に当てない。順 3 の照合はレビューの周に数えない（G はレビューをしないので、周回キャップとは別に差し戻しの上限で止める）。同じ failed で戻した指摘が順 3 だけなら、集合が一致して閉じたあとに差分限定の再レビューは行わず、周を消費しない（閉じた PR コメント URL を仕分け欄に残す）。順 2・順 4 の指摘が同じ failed に含まれていれば、それらの差分限定の再レビューは通常どおり行い、周を 1 つ消費する。

**順 4（今直す 3 条件）**: 直し方が行レベルで 30 行以内、spec を変えない、この PR でその場で直した累計が 30 行以内、の 3 つをすべて満たすとき W がその場で直す。閾値は手順 2-0 と同じ 30 行を使い、別の数字を足さない。W は直したら仕分け欄に「受け入れ条件の外・その場で直した・直し方 N 行」と記録する。順 4 で直した指摘が 1 回で閉じなかったら、2 回目は順 6 に落とす。

**順 5（主に切り出すかを聞く）**: 主への質問は「この欠陥を残して切り出すか」の形にし、次の 4 点を必ず書く: 欠陥がマージ後に何を起こすか、直す見積もり（行数・触るファイル・spec を変えるか）、別 issue にする固定費、推奨。2 周目の終わりまで待たず、指摘を受け取ったその周で聞く。G は PR に `needs-approval` を付けて保留で return し、復帰は手順6の表の「切り出しの確認」行に従う。無人運用（loop-dev-agent）でも同じく止まる。

**順 6（決める役が方式を裁定する）**: 当てるのは次のどちらか。2 周目以降の周の終わりに止める指摘が残り、前の周と同じ型が別の場所・別の場合で再発しているとき。または、順 3 の照合が差し戻し後の 2 回目も一致しない、あるいは順 4 で直した指摘が 1 回で閉じないとき（順 3・順 4 からの落とし込み。周の終わりを待たず、その時点で順 6 に当てる）。決める役（`dev-workflow:decider`）が裁定するのは方式（全部列挙してから直す／切り出す）だけで、止めるかどうかの判定は G が全周共通の判定で行う。G はサブエージェントを起こせないので Status `needs-decider` で return し、本体が決める役を起こして可否と根拠の形で裁定を受け取り、それを渡して照合と振り分けの G を新しく起こす（本体の動きは develop スキルの (4)）。G は裁定を 1 行目 `決める役の裁定: 全部列挙してから直す` または `決める役の裁定: 切り出す` の PR コメントとして記録し、仕分け欄にも同じ内容を書く。裁定は PR ごとに 1 回まで。回数は G のコンテキストに持たせず、照合と振り分けの G が起こされるたびに、1 行目が `^決める役の裁定: (全部列挙してから直す|切り出す)$` に完全一致する PR コメントの件数を全ページから数える（`gh api --paginate --slurp repos/$R/issues/$N/comments | jq '[add[] | select(.body | split("\n")[0] | test("^決める役の裁定: (全部列挙してから直す|切り出す)$"))] | length'`）。1 回目の裁定が「切り出す」だった場合もこの 1 回に数え、2 回目の順 6 は決める役を起こさず「切り出す」として扱う（厳しい側に倒す）。裁定が「全部列挙してから直す」なら `agent-review:failed` に付け替え、W に順 3 と同じ形の一覧を作らせて次の周に入る。ただし、同じ周の順 5 の指摘に主がまだ回答していなければ、failed に付け替えずに保留のまま待つ（処理順は上の順 5 と順 6 の混在の段落）。裁定が「切り出す」なら順 5 と同じ経路で主に聞く。本体から「裁定なし（入力不足）」が返ったら（決める役が 2 回続けて入力不足を返したとき。develop スキルの (4)）、G は `決める役の裁定:` の PR コメントを残さず（裁定の回数に数えない）、仕分け欄に「決める役の裁定なし（入力不足）」と書き、その指摘を「切り出す」として順 5 と同じ経路で主に聞く。

**収束ルール（レビュー周回のキャップ）**:

- レビューは**既定2周**（初回レビュー＋再レビュー1回）で確定する。**3周目を自動で開けない**（G も本体も開けない）。3周目以降の周を開けるのは、主が順 5 に「この PR で直す」と答えたときと、決める役が順 6 で「全部列挙してから直す」と裁定したとき（PR ごとに 1 回まで）だけ。
- **再レビューは差分限定**: 前回指摘が閉じたかの確認に限る。再レビューでの新規探索はしない。再レビュー中の新規の気づきは follow-up issue に切り出す。ただし例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる新規の指摘は差分限定の周でも受け取り、仕分け表に当てる。
- **例外: 方式の書き換えの後は全体レビューにする。** G は再レビューを始める前に、W の修正差分の行数と前周の指摘の対象行数を比べ、修正差分が大きく超えていれば（方式の書き換え）、次の再レビューを差分限定ではなく PR 全体のレビューにする。判定に使った 2 つの行数を PR コメントに記録する。**周回は数え続ける**（1周目に戻さない。2周目が全体レビューになったら、その結果に下の仕分けをそのまま適用する）。
- **blocking の定義を限定する**: マージ後に issue で直せるものは blocking にしない。follow-up issue 化してマージを通す。止めるかどうかは全周で「マージを止めるかの判定（全周共通）」で決め、2周目の終わりには次の手順で仕分ける。

**2周目の終わりにやること（G が、2周目の結果を受け取った直後に）**:

1. **残った指摘ごとに、違反する文を引用する。** 引用元は記録先（issue または Draft PR 本文）の受け入れ条件と、この PR が触れる openspec の spec（change の delta spec を含む）に限る。止めるかどうかは「マージを止めるかの判定（全周共通）」で決め、**レビュアー（Codex・Task サブエージェント）の深刻度ラベルは参考にとどめる**（「高深刻度」と付いていても、判定で止まらなければ止める指摘ではない）。**引用元が無い**とき（PR が openspec に触れず、記録先にも受け入れ条件の文が無い）は、引用元を広げず、残った指摘を全件「引用なし」として扱う。仕分けの結果（指摘ごとの引用・例外 3 種のどれか、または「引用なし」）を PR コメントに記録する。
2. **止めない指摘（引用できない指摘を含む）は follow-up issue に切って `passed` の判定へ進む。** 各指摘を follow-up issue にし、URL を仕分けの PR コメントに記録して、手順3以降へ進む。止めない指摘を理由に3周目を開けない。
3. **止める指摘が1件でも残ったら、3周目に入らず止まる**（引用できる指摘でも、判定で止まらないものは上の follow-up issue 側に回す）。仕分け表の順 2〜4 を使わない。前の周と同じ型の再発に当たる指摘は順 6（決める役が方式を裁定する）、それ以外は順 5（主に切り出すかを 4 点付きで聞く）に当てる。無人運用（loop-dev-agent）でも同じく止まる。**主の回答または決める役の裁定で開いた周の終了時にも同じ仕分けを適用し**、止める指摘が残れば再び順 5・6 に当てる（主の回答なしに次の周へ進まない。決める役の裁定で周を開けるのは PR ごとに 1 回まで）。

**決める役（`dev-workflow:decider`）は順 6 の方式だけを裁定する。** 止めるかどうかは全周共通の判定で G が決める。3周目以降の周を開けるかどうかは主の回答か順 6 の裁定で決まる。順 6 以外で決める役を挟まない（修正サイクルでの原因分類・直し方・次のモデルの裁定は手順2-2の出力契約のまま）。

#### 2-2. 修正サイクルのモデル昇格（failed → 修正実装）

`agent-review:failed` に付け替えて修正サイクルへ戻すときは、**修正を書くサブエージェントのモデルを決めてから戻す**（Agent ツールの `model` パラメータ。PR を持っているセッション本体のモデルは変えない）。

| failed の原因 | 戻し方 |
|---|---|
| **実装品質起因**（テスト不足・エッジケース漏れ・既存コードとの不整合・安全機構の穴） | 失敗の原因が判断側（指示を解釈できなかった・指示自体が外れていた）か実行側（指示どおりやって結果が違う）かで、**決める役と実行役のどちらか一方だけ**を上げる（両方同時に上げない）。実行側なら実行役を `opus` で spawn し、判断側なら `subagent_type: dev-workflow:decider` を立てて修正方針を作らせ、実行役は据え置く（残量モードと共有枠モードの上限内） |
| **仕様が曖昧**（受け入れ条件から一意に決まらない） | モデル昇格ではなく仕様修正で返す。issue の受け入れ条件を確定させてから修正に入る（unmanned なら `needs-approval` を付けて主に返す） |
| **レビュアーの誤検出**（指摘が事実と違う） | モデル昇格ではなく反証で返す。該当コード・テスト結果を PR コメントに書いて指摘を閉じる |

**昇格は実装品質起因のときだけ。** 原因が仕様側・レビュアー側にあるのに最強モデルを当てても、同じ往復をもう1周するだけになる。

**実行役の上限は `opus`。** 修正実装を `model: fable` で spawn しない（`scripts/agent-model-guard.sh` が PreToolUse で拒否する）。Fable が消費するのはターン数（会話履歴の cache 読込）で、修正ループは数十〜数百ターン回るため、実行役を Fable にすると週次枠が溶ける。Fable を使うのは決める役（`subagent_type: dev-workflow:decider`。`Bash` を持たないので、その return を PR に書くのは呼び出し側）だけで、決める役はどの段階でも種別を固定して `model`（`opus` → `fable`）だけを切り替える。ラダーの正本は develop スキルの `templates/escalation-tripwires.md`。

**なぜ 1 回目の failed で上げるのか**: G のレビューループは 2 周キャップで**2 周目が最終周**にあたるため、1 回目の failed の時点で原因側を一方だけ上げてキャップ内での収束確率を上げる（昇格トリップワイヤーの「1 回目の失敗では誰も上げない」は同じテストの 2 連続失敗を数える別の発火条件で、こちらとは数え方が違う）。

**収束ルール（2周キャップ）との関係**: 再レビューは既定2周なので**2周目が最終周**にあたる。最終周の修正に最強モデルを当てることで、キャップ内で収束する確率を最大化する（3周目へ持ち越さないための配分）。

**Fable が使えないときのフォールバック**: レート制限・週次枠切れ（`FABLE_BUDGET_MODE=exhausted` 相当）で決める役を Fable で立てられない場合は、種別は `dev-workflow:decider` のまま `model: opus` に落として進め、その旨を PR コメントに1行残す（レビュー実行者行と同形式。この記録形式がフォールバック記録の正本）:

```bash
gh api -X POST repos/$R/issues/$N/comments \
  -f body='決める役モデル: opus（fable レート制限のためフォールバック。subagent_type は dev-workflow:decider のまま）'
```

1周目からモデルを上げる「重要実装」の事前分類（聖域パス・マージ権限・層間契約・課金/法務。実行役はどの分類でも `opus` 止まりで、読んで判断する役が分類に当たるときは `subagent_type: dev-workflow:decider`）は **develop スキルの references/roles/worker.md が正本** — このゲートでは再掲しない。

## G として動くとき（develop）

この節は develop の G（`skills/develop/references/roles/gate-runner.md` の指示で動くゲート実行者）だけに関係する。develop 以外の読み手は読み飛ばしてよい。

### return の書式（failed / needs-decider / review-incomplete と仕分け）

`gate-runner.md`「return の書式」の共通欄（`## Gate Result` から `周回:` まで）のうしろに続ける。

```markdown
- 仕分け（指摘を受け取ったすべての周の return で必須。Status によらず書く）: pr-review-gate 手順 2-1 の仕分け表で指摘ごとに当てた順とその根拠（順 1・2 は違反文の引用・例外 3 種のどれか（安全機構の穴・データ破壊・無言の機能不全）、または follow-up issue の URL。順 3 は集合一致で閉じた PR コメント URL。順 4 は W の記録「受け入れ条件の外・その場で直した・直し方 N 行」。順 6 の裁定を受けたら `決める役の裁定:` の内容）と、その PR コメント URL。全件を follow-up issue に切って passed で返すときもここに書く。全周共通の判定で止める指摘が残り、順 5 に当たる場合は failed ではなく保留で返す（下）
- 効果測定（二周目以降に新しく出た、または未解決で残った各指摘に必須）: `同じ文が複数か所` / `場合分けの漏れ` / `直したつもりで直っていない` / `直しで新しく入った` のいずれか 1 つ。同じ指摘 ID と分類を仕分けの PR コメントにも記録し、その PR コメント URL を return に添える。この分類は記録だけに使い、全周共通の停止判定と仕分け順を変えない
### failed のとき
- 原因分類（pr-review-gate 手順 2-2）: 実装品質起因 | 仕様が曖昧 | レビュアーの誤検出
- 指摘一覧（再現手順・修正点）と PR コメント URL
- 本体への提案: 実装品質起因なら、失敗の原因が実行側（指示どおりやって結果が違う）か判断側（指示を解釈できなかった・指示自体が外れていた）かを書き添えて、実行側なら W を `opus` で再開、判断側なら `subagent_type: dev-workflow:decider`（`model` は `opus` → `fable`。種別は固定して `model` だけ切り替える）を立てて修正方針を作らせるよう提案する（**決める役と実行役のどちらか一方だけ**を上げる。W を `fable` にはしない。残量モードと共有枠モードの上限内）。仕様が曖昧なら受け入れ条件の確定（unmanned は needs-approval）、誤検出なら反証コメントの投稿
### needs-decider のとき
- 本体に渡すもの（仕分け表の順 6）: 同じ型の指摘と前の周の指摘の原文、対象ファイルのパス、仕分け欄、順 6 に当てた理由（同じ型の再発／順 3 の差し戻し後の不一致／順 4 の 2 回目）。本体は決める役を起こして裁定を受け取り、照合と振り分けの G を新しく起こして渡す（下の「決める役の裁定受領」）。この PR で裁定が既に 1 回あれば needs-decider で返さず「切り出す」として扱う。順 5 と順 6 の混在で保留にした PR で、主の回答のあとに未処理の順 6 が残っているときもここに当たる（`needs-approval` を外し、failed を付けずに返す）
### review-incomplete のとき
- 固定 HEAD・元の三表・補足後の三表・残差・`補足済み回数: 1` と、それらを記録した PR コメント URL。terminal なので reviewer の再起動・合格処理を提案しない
```

failed の return には**必ず原因分類**を含める（本体はこれを見て、決める役と実行役のどちらを上げるかを決める。分類の定義は pr-review-gate 手順 2-2 が正本。モデルを上げるのは実装品質起因のときだけ）。

### この段で起こされたときの入力

照合と振り分けの G は、起動指示の前の段の `## Gate Result` ブロックと、段に固有の入力（レビュアーの要約・補足レビューの結果・決める役の裁定・W の修正内容の要約）を受け取る。前の段の会話は持たず、固定した HEAD は最新の `レビュー重量:` コメントの `固定 HEAD:` の行から、三表と補足済み回数は最新の `レビュー三表:` のコメントから、前の周の振り分けは仕分けコメントから読む。起動指示と PR コメントが食い違ったら PR コメントを正とする。

- **レビュアーの要約受領**: まず下の「レビュー実行者:」の PR コメントを投稿し、そのあとは `gate-runner.md` の「段ごとの起動と入力」の「レビュアーの要約受領」の分岐に従う。補足の `needs-reviewer` を返す前には、元の三表と `補足済み回数: 1`（補足を頼んだ時点で 1 と数える。reviewer への payload は `補足済み回数: 0` のまま）の行を持つ 1 行目 `レビュー三表:` のコメントを投稿する
- **止める指摘が残らなかったとき**: 止めない指摘（順 1）を follow-up issue に切ってから、Status `次の段へ`・`次の段: 合格処理` で返す。宣言（手順 3）は合格処理の G が行う
- **failed の `次の段:`**: 戻した指摘が順 3 だけなら `照合と振り分け`、それ以外（順 2・4 が混ざる場合を含む）は `前提確認と重さ判定` と書く。順 3 と順 2・4 が同じ failed に混ざったときは、W の修正後に起こされる前提確認と重さ判定から続く照合と振り分けの G が、再レビューの要約と一緒に順 3 の一覧表のコメントも照合する

レビュー要約を受け取った G は、「レビュー実行者:」の PR コメント（`レビュー実行者: Task サブエージェント（light 判定のため）` / `（full・実測した Codex 不可: <条件>）`。adapter 経路では `レビュー実行者: <executor>/<model>（adapter 経路・<light|full>・dispatch 記録: <URL>）` とし、本体から渡された executor / model と dispatch 記録のコメント URL を写し、`<light|full>` には手順 2-0 の判定を書く。Codex の `<model>` は worker 結果の `execution.model_resolution.requested` と `execution.model_resolution.resolved` による `<requested>→<resolved>` として書く。resolved が null なら未観測と明示し、要求値や dispatch 時の model から補完しない。Claude の `<model>` は従来の値を使う。モデルと根拠を添え、full では対象 HEAD と上の同じ証拠を記録する。終了コードは取得できた場合のみ記し、架空の終了コードを書かない。light は事前判定として記録する）を **G が投稿**する。そのあとの分岐は、`gate-runner.md` の「段ごとの起動と入力」の「レビュアーの要約受領」に従う。

- **W の修正後の再レビュー**（前提確認と重さ判定の G が読む。戻した指摘が順 3 だけのときは照合と振り分けの G が読む）: 手順 1 から全工程をやり直す（`failed` を外して `pending` に戻す）。再レビューの範囲は差分限定。ただし W の修正が方式の書き換え（修正差分の行数が前周の指摘の対象行数を大きく超える）なら全体レビューにし、2 つの行数を PR コメントに記録する。周回は数え続ける（2 周キャップ。3 周目に入るのは主の回答または決める役の裁定があったときだけ）。戻した指摘が順 3 だけなら、再レビューをせず一覧表のコメントの修正前 SHA と HEAD の 2 段で集合を照合して閉じ、周を消費しない（grep の語は `git fetch` で W の push を取り込んだあと、`plugins/dev-workflow/scripts/review-hit-set.py --head <HEAD の 40 桁 SHA> <table-file>` で 2 段を回す。差し戻しは 1 回まで。書式と照合の正本は pr-review-gate 手順 2-1 の仕分け表の順 3）
- **決める役の裁定受領**: 本体から裁定（全部列挙してから直す／切り出す）を受け取ったら、1 行目 `決める役の裁定: 全部列挙してから直す` または `決める役の裁定: 切り出す` の PR コメントとして記録し、仕分け欄にも書く。裁定の回数は G のコンテキストに持たせず、G を起こすたびに PR コメントから数える（起動指示の記述から数えない）（数え方は pr-review-gate 手順 2-1 の仕分け表の順 6）。全部列挙してから直すなら `agent-review:failed` に付け替えて W に順 3 と同じ形の一覧を作らせ、切り出すなら順 5 と同じく保留で返す。同じ周に主が未回答の順 5 が残っていれば failed に進まない（処理順は pr-review-gate 手順 2-1 の混在の段落）。本体から「裁定なし（入力不足）」を受け取ったら、`決める役の裁定:` のコメントを残さず（回数に数えない）、仕分け欄に「決める役の裁定なし（入力不足）」と書いて「切り出す」として順 5 と同じく保留で返す

## 出口

- 止める指摘が残らなければ（順 1 だけなら follow-up issue に切って）`declarations.md`（手順 3・3-b）へ進む。
- 順 2〜4 は `agent-review:failed` で修正サイクルへ戻す。修正後の再レビューは `stages/prepare.md` の手順 1 から始める。
- 順 5（主に切り出すかを聞く）は `stages/hold.md`（手順 6）へ進む。
- 順 6 は決める役の裁定を待ち、裁定を受け取ったらこの段に戻る。
