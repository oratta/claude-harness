# 照合と指摘の振り分け — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/prepare.md`（手順 1・2・2-0）、`stages/reviewer-brief.md`（2-1 のレビュアー向け指示）、`stages/triage-escalation.md`（2-2）、`declarations.md`（手順 3・3-b）、`stages/carryover.md`（手順 3-c）、`stages/hold.md`（手順 6）。

## 入口

レビュー結果に指摘が残っているとき（develop の G は `stages/gate-triage.md` の三表の機械照合を済ませたあと）、W の修正後の再レビュー、決める役の裁定または直し方の判定を受け取ったときに読む。

要約・補足の受領では `stages/gate-triage.md` を読む。

## 手順

#### 2-1. レビューの実行（止める判定と仕分け）

**マージを止めるかの判定（全周共通）**: マージを止めるのは、深刻度が `blocking` で、根拠の引用を G が記録先（issue または Draft PR 本文）の受け入れ条件、またはこの PR が触れる openspec の spec（change の delta spec を含む）の原文と照合できた（または根拠が例外 3 種＝安全機構の穴・データ破壊・無言の機能不全に当たる）、かつ検証が `confirmed` の指摘だけ。それ以外（`should`・`nit`・`plausible`・照合できない `blocking`）はマージを止めず、`stages/triage-nonblocking.md` の「止めない指摘の振り分け表」に通す（表を通さずに issue にしない）。レビュアー（Codex・Task サブエージェント）の深刻度ラベルは参考にとどめ、判定の根拠は G の照合にする。この判定は 1周目・2周目・主の続行指示で開いた周の全周で同じ。

止める指摘が残ったら、動き方は下の「止める指摘の仕分け表」に従う（判定は「マージを止めるかの判定（全周共通）」のまま。周によって変わるのは、表のどの順を使えるかだけ）。

1周目で failed にするとき、止めない指摘は failed の PR コメントに一覧で残し、段 A に当たる指摘には「段 A・この PR で直す」と印を付け、follow-up issue はまだ切らない（W が同じ周で直すことがあり、先に切ると重複する）。止める指摘も、1周目の段 A に当たる指摘も無い周は failed にせず、G が手順3へ進むときに、未解決の止めない指摘を振り分け表の段 B 以降に当て、指摘ごとの段と行き先を PR コメントに記録する。

**止める指摘の仕分け表**（G は周回の数に関係なく、指摘が届くたびに上から当てる。表はここにだけ置き、他の節とファイルは順番号と見出しで参照する）:

| 順 | 当てる条件 | 動き | 主に聞くか |
|---|---|---|---|
| 1 | 止める判定に達しない（上の全周共通の判定で止まらない） | `stages/triage-nonblocking.md` の「止めない指摘の振り分け表」に回す（1周目は上の段落どおり failed の一覧に残す） | 聞かない |
| 2 | 受け入れ条件の中（根拠の引用元が記録先の受け入れ条件、またはこの PR の change の delta spec） | W が直す。`agent-review:failed` で W に戻す | 聞かない |
| 3 | 一覧の一致で閉じられる型（「同じ文が別の場所に残っている」「N 件のうち k 件しか直っていない」） | W に一覧を作らせ、G は検索結果の集合一致で閉じる。`agent-review:failed` で W に戻す | 聞かない |
| 4 | 根拠が例外 3 種で、今直す 3 条件を満たす | W がその場で直し、仕分け欄に記録する。`agent-review:failed` で W に戻す | 聞かない |
| 5 | 順 1〜4 に当たらず、順 6 の条件にも当たらない | 主に「この欠陥を残して切り出すか」を聞く。`needs-approval` を付けて保留で return | 聞く |
| 6 | 同じ型の再発、または順 3・順 4 からの落とし込み | 決める役が方式を裁定する。Status `needs-decider` で本体に return | 聞かない（裁定が「切り出す」なら順 5 と同じ経路） |

二周目以降の周の終わり・混在の条件付き処理は `stages/triage-convergence.md` を読む。

順 3 または順 6 の全列挙の一覧を扱うときは `stages/triage-row3.md` を読む。

**順 4（今直す 3 条件）**: 当てられるのは、止める判定の根拠が例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる指摘だけ。例外 3 種に当たるかは、根拠欄の書き方によらず G が決める（印と同じく参考）。根拠が例外 3 種でない指摘は、直し方の行数によらず順 4 に当てず、順 2・順 3 に当たらなければ順 5 に当てる。直し方が行レベルで 30 行以内、spec を変えない、この PR でその場で直した累計が 30 行以内、の 3 つをすべて満たすとき W がその場で直す。閾値は手順 2-0 と同じ 30 行を使い、別の数字を足さない。W は直したら仕分け欄に「受け入れ条件の外・その場で直した・直し方 N 行」と記録する。G は仕分け欄に、当てた例外 3 種のどれかもあわせて書く。順 4 で直した指摘が 1 回で閉じなかったら、2 回目は順 6 に落とす。

**順 5（主に切り出すかを聞く）**: 主への質問は「この欠陥を残して切り出すか」の形にし、次の 4 点を必ず書く: 欠陥がマージ後に何を起こすか、直す見積もり（行数・触るファイル・spec を変えるか）、別 issue にする固定費、推奨。2 周目の終わりまで待たず、指摘を受け取ったその周で聞く。G は PR に `needs-approval` を付けて保留で return し、復帰は手順6の表の「切り出しの確認」行に従う。無人運用（loop-dev-agent）でも同じく止まる。

**順 6（決める役が方式を裁定する）**: 当てるのは次のどちらか。2 周目以降の周の終わりに止める指摘が残り、前の周と同じ型が別の場所・別の場合で再発しているとき。または、順 3 の照合が差し戻し後の 2 回目も一致しない、あるいは順 4 で直した指摘が 1 回で閉じないとき（順 3・順 4 からの落とし込み。周の終わりを待たず、その時点で順 6 に当てる）。決める役（`dev-workflow:decider`）が裁定するのは方式（全部列挙してから直す／切り出す）だけで、止めるかどうかの判定は G が全周共通の判定で行う。G はサブエージェントを起こせないので Status `needs-decider` で return し、本体が決める役を起こして可否と根拠の形で裁定を受け取り、それを渡して照合と振り分けの G を新しく起こす（本体の動きは develop スキルの (4)）。G は裁定を 1 行目 `決める役の裁定: 全部列挙してから直す` または `決める役の裁定: 切り出す` の PR コメントとして記録し、仕分け欄にも同じ内容を書く。裁定は PR ごとに 1 回まで。回数は G のコンテキストに持たせず、照合と振り分けの G が起こされるたびに、1 行目が `^決める役の裁定: (全部列挙してから直す|切り出す)$` に完全一致する PR コメントの件数を全ページから数える（`gh api --paginate --slurp repos/$R/issues/$N/comments | jq '[add[] | select(.body | split("\n")[0] | test("^決める役の裁定: (全部列挙してから直す|切り出す)$"))] | length'`）。1 回目の裁定が「切り出す」だった場合もこの 1 回に数え、2 回目の順 6 は決める役を起こさず「切り出す」として扱う（厳しい側に倒す）。裁定が「全部列挙してから直す」なら `agent-review:failed` に付け替え、W に順 3 と同じ形の一覧を作らせて次の周に入る。ただし、同じ周の順 5 の指摘に主がまだ回答していなければ、failed に付け替えずに保留のまま待つ（処理順は `stages/triage-convergence.md` の順 5 と順 6 の混在の段落）。裁定が「切り出す」なら順 5 と同じ経路で主に聞く。本体から「裁定なし（入力不足）」が返ったら（決める役が 2 回続けて入力不足を返したとき。develop スキルの (4)）、G は `決める役の裁定:` の PR コメントを残さず（裁定の回数に数えない）、仕分け欄に「決める役の裁定なし（入力不足）」と書き、その指摘を「切り出す」として順 5 と同じ経路で主に聞く。

止めない指摘が残る、または主が切り出すと答えたときは `stages/triage-nonblocking.md` を読む。

W の修正後の再レビュー、または二周目以降の周の終わりには `stages/triage-convergence.md` を読む。

failed の原因分類と戻し方を決めるときは `stages/triage-escalation.md` を読む。

## G として動くとき（develop）

この節は develop の G（`skills/develop/references/roles/gate-runner.md` の指示で動くゲート実行者）だけに関係する。develop 以外の読み手は読み飛ばしてよい。

### return の書式（failed / needs-decider / needs-fix-check / review-incomplete と仕分け）

`gate-runner.md`「return の書式」の共通欄（`## Gate Result` から `周回:` まで）のうしろに続ける。

```markdown
- 仕分け（指摘を受け取ったすべての周の return で必須。Status によらず書く）: pr-review-gate 手順 2-1 の仕分け表で指摘ごとに当てた順とその根拠（順 1・2 は違反文の引用・例外 3 種のどれか（安全機構の穴・データ破壊・無言の機能不全）。順 1 の指摘は、止めない指摘の振り分け表で当てた段と行き先も書く: 段 A は「この PR で直す」と、要る受け入れ条件の ID か delta spec の要件名、または当たる例外 3 種のどれか、捨てたなら理由の 1 行、issue にした・コメントで入れたなら follow-up issue またはコメントの URL、条件の確認待ちなら質問文。順 3 は集合一致で閉じた PR コメント URL。順 4 は W の記録「受け入れ条件の外・その場で直した・直し方 N 行」と当たる例外 3 種のどれか。順 6 の裁定を受けたら `決める役の裁定:` の内容）と、その PR コメント URL。止める指摘が無く、全件を振り分け表に通して `次の段へ` で返すときもここに書く。全周共通の判定で止める指摘が残り、順 5 に当たる場合は failed ではなく保留で返す（下）
- 効果測定（二周目以降に新しく出た、または未解決で残った各指摘に必須）: `同じ文が複数か所` / `場合分けの漏れ` / `直したつもりで直っていない` / `直しで新しく入った` のいずれか 1 つ。同じ指摘 ID と分類を仕分けの PR コメントにも記録し、その PR コメント URL を return に添える。この分類は記録だけに使い、全周共通の停止判定と仕分け順を変えない
### failed のとき
- 原因分類（pr-review-gate 手順 2-2）: 実装品質起因 | 仕様が曖昧 | レビュアーの誤検出 | 段 A だけ（昇格なし）
- 指摘一覧（再現手順・修正点）と PR コメント URL
- 本体への提案: 実装品質起因なら、失敗の原因が実行側（指示どおりやって結果が違う）か判断側（指示を解釈できなかった・指示自体が外れていた）かを書き添えて、実行側なら `codex-develop.py request --phase implement --failure executor` を呼んで `request` が返した model で W を起こし（model が変わるなら SendMessage で再開せず、新しい thread に手渡す。細目の正本は `plugins/dev-workflow/references/codex-develop.md`）、判断側なら `request --phase decider --failure first`（そのゲートの 1 回目の failed）または `--failure judgment`（そのゲートの 2 回目以降の failed。1 回目の原因が実行側だったときも含む）を呼んで `request` が返した model で `subagent_type: dev-workflow:decider` を立てて修正方針を作らせるよう提案する（**決める役と実行役のどちらか一方だけ**を上げる。`request` が返した model と違う model を独自に指定せず、実行役を最上位の格に上げない。残量モードと共有枠モードの上限は `request` の返り値に効いている）。仕様が曖昧なら受け入れ条件の確定（unmanned は needs-approval）、誤検出なら反証コメントの投稿
### needs-decider のとき
- 本体に渡すもの（仕分け表の順 6）: 同じ型の指摘と前の周の指摘の原文、対象ファイルのパス、仕分け欄、順 6 に当てた理由（同じ型の再発／順 3 の差し戻し後の不一致／順 4 の 2 回目）。本体は決める役を起こして裁定を受け取り、照合と振り分けの G を新しく起こして渡す（下の「決める役の裁定受領」）。この PR で裁定が既に 1 回あれば needs-decider で返さず「切り出す」として扱う。順 5 と順 6 の混在で保留にした PR で、主の回答のあとに未処理の順 6 が残っているときもここに当たる（`needs-approval` を外し、failed を付けずに返す）
### needs-fix-check のとき
- 本体に渡すもの（手順 2-1 の周の終わりの段落の直し方の判定）: 判定に回す指摘ごとの仮の順（1 周目なら当たる順 2〜4 のどれか）とその根拠、仕分けの PR コメント URL、順 6 に当てた未裁定の指摘があればその一覧（仕分け欄に「順 6・未裁定」と載せたもの）。本体は決める役を起こして判定を受け取り、判定の記録を記録先に投稿してから、照合と振り分けの G を新しく起こして判定と判定の記録の URL を渡す（下の「直し方の判定の受領」）。`needs-approval` も `agent-review:failed` も付けずに返し、同じ return で `needs-decider` を指示しない
### review-incomplete のとき
- 固定 HEAD・元の三表・補足後の三表・残差・`補足済み回数: 1` と、それらを記録した PR コメント URL。terminal なので reviewer の再起動・合格処理を提案しない
```

failed の return には**必ず原因分類**を含める（本体はこれを見て、決める役と実行役のどちらを上げるかを決める。分類の定義は pr-review-gate 手順 2-2 が正本。モデルを上げるのは実装品質起因のときだけで、「段 A だけ（昇格なし）」では W のモデルを据え置く）。

### この段で起こされたときの入力

照合と振り分けの G は、起動指示の前の段の `## Gate Result` ブロックと、段に固有の入力（レビュアーの要約・補足レビューの結果・決める役の裁定・直し方の判定とその記録の URL・W の修正内容の要約）を受け取る。前の段の会話は持たず、固定した HEAD は最新の `レビュー重量:` コメントの `固定 HEAD:` の行から、三表と補足済み回数は最新の `レビュー三表:` のコメントから、前の周の振り分けは仕分けコメントから読む。起動指示と PR コメントが食い違ったら PR コメントを正とする。

- **レビュアーの要約受領**: まず下の「レビュー実行者:」の PR コメントを投稿し、そのあとは `stages/gate-triage.md` の「段ごとの起動と入力」の「レビュアーの要約受領」の分岐に従う。補足の `needs-reviewer` を返す前には、元の三表と `固定 HEAD: <40 桁>`・`一周目の区画: <なし | n>`・`補足済み回数: 1`（補足を頼んだ時点で 1 と数える。reviewer への payload は `補足済み回数: 0` のまま）の行を持つ 1 行目 `レビュー三表:` のコメントを投稿する（見出しの行は `stages/comment-parts.md` の「コメント長の上限を超えるとき（三表と順 3 の一覧）」の表の三表の行と同じ）
- **止める指摘が残らなかったとき**: 止めない指摘（順 1）を止めない指摘の振り分け表に通す。1周目に段 A に当たる指摘があれば `agent-review:failed` で返す。無ければ段 B 以降の結果を PR コメントに記録してから、Status `次の段へ`・`次の段: 合格処理` で返す。宣言（手順 3）は合格処理の G が行う
- **failed の `次の段:`**: 戻した指摘が順 3 だけなら `照合と振り分け`、それ以外（順 2・4 または段 A が混ざる場合と、段 A だけで戻した場合を含む）は `前提確認と重さ判定` と書く。順 3 と順 2・4 または段 A が同じ failed に混ざったときは、W の修正後に起こされる前提確認と重さ判定から続く照合と振り分けの G が、再レビューの要約と一緒に順 3 の一覧表のコメントも照合する

レビュー要約を受け取った G は、「レビュー実行者:」の PR コメント（`レビュー実行者: Task サブエージェント（light 判定のため）` / `（full・実測した Codex 不可: <条件>）` / `（full・Codex オフ）`。adapter 経路では `レビュー実行者: <executor>/<model>（adapter 経路・<light|full>・dispatch 記録: <URL>）` とし、本体から渡された executor / model と dispatch 記録のコメント URL を写し、`<light|full>` には手順 2-0 の判定を書く。Codex の `<model>` は worker 結果の `execution.model_resolution.requested` と `execution.model_resolution.resolved` による `<requested>→<resolved>` として書く。resolved が null なら未観測と明示し、要求値や dispatch 時の model から補完しない。Claude の `<model>` は従来の値を使う。モデルと根拠を添え、full では対象 HEAD と `stages/prepare-reviewer.md` の needs-reviewer の payload の証拠欄と同じ証拠を記録する。終了コードは取得できた場合のみ記し、架空の終了コードを書かない。light は事前判定として記録する）を **G が投稿**する。そのあとの分岐は、`stages/gate-triage.md` の「段ごとの起動と入力」の「レビュアーの要約受領」に従う。

W の修正後の再レビューの入力は `stages/triage-convergence.md` を読む。

- **決める役の裁定受領**: 本体から裁定（全部列挙してから直す／切り出す）を受け取ったら、1 行目 `決める役の裁定: 全部列挙してから直す` または `決める役の裁定: 切り出す` の PR コメントとして記録し、仕分け欄にも書く。裁定の回数は G のコンテキストに持たせず、G を起こすたびに PR コメントから数える（起動指示の記述から数えない）（数え方は pr-review-gate 手順 2-1 の仕分け表の順 6）。全部列挙してから直すなら `agent-review:failed` に付け替えて W に順 3 と同じ形の一覧を作らせ、切り出すなら順 5 と同じく保留で返す。同じ周に主が未回答の順 5 が残っていれば failed に進まない（処理順は `stages/triage-convergence.md` の混在の段落）。本体から「裁定なし（入力不足）」を受け取ったら、`決める役の裁定:` のコメントを残さず（回数に数えない）、仕分け欄に「決める役の裁定なし（入力不足）」と書いて「切り出す」として順 5 と同じく保留で返す
- **直し方の判定の受領**: 本体から直し方の判定（決まっている／選び直しが要る）と判定の記録の URL を受け取ったら、URL を仕分け欄に書く（判定の記録は本体が投稿済みなので G は投稿しない。`決める役の裁定:` のコメントも残さない）。「決まっている」なら、前の G が仕分けの PR コメントに記録した仮の順どおりに順 2〜4 の扱いで指摘を W に戻す（`agent-review:failed` に付け替える。仮の順 3 なら一覧を作らせ、仮の順 4 なら今直す記録を求める。`needs-approval` を付けない）。ただし仕分け欄に「順 6・未裁定」の指摘があれば、failed を付けずに Status `needs-decider` で返し、裁定のあとでまとめて 1 回の failed にする（`stages/triage-convergence.md` の直し方の判定と順 6 の混在の段落）。「選び直しが要る」なら、それらの指摘を順 5 に当てて `needs-approval` を付け、順 5 の 4 点を書いて保留で返す（順 6・未裁定の指摘があれば`stages/triage-convergence.md` の順 5 と順 6 の混在の処理順に従う）
