# レビュー担当向けの指示 — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/triage.md`（2-1 の止める判定と仕分け・2-2）、`declarations.md`（手順 3・3-b）。

## 入口

レビュアー（Codex・Task サブエージェント）を起こす側が指示を組み立てるときと、レビュー担当が自分に渡された指示の書式を確かめるときに読む。起こす側は、下のレビュアー向け指示ブロックをそのまま貼る。

区画がある一周目は区画ごとに 1 体を起こし、固定 HEAD・受け入れ条件の全文・区画の番号と総数・その区画のファイル一覧・下の指示ブロックを渡す。全区画の結果を照合と振り分けの G にまとめて渡す。

## 手順

#### 2-1. レビューの実行（レビュアー向け指示）

姿勢: **受け入れ条件を根拠に「落とせる欠陥を探す」**。実装者がやったことの追認ではなく、やっていない角度（エッジケース・既存コードとの整合・失敗時の戻し方）を突く。テスト・lint は**報告を信用せず自分で再実行**する。

**レビュアー向け指示ブロック**（Codex の指示文と Task サブエージェントへの指示に、下の `text` ブロックをそのまま貼る。指摘の書式と深刻度の定義はここにだけ置き、他のファイルには再掲しない）:

```text
指摘は 1 件ごとに次の書式で書く。1 周目は、対象範囲で該当する指摘を全部列挙するまで止まらない。

1 周目は指摘を書く前に、`変更点の一覧` → `照合表` → `ハンク被覆` → 三表の自己点検 → 指摘の順で出力する。

1. `変更点の一覧`: この PR が新しく決めたルール・判定・用語を安定した変更点 ID 付きで列挙する。各変更点に対応する受け入れ条件 ID と検索語を書き、すべての受け入れ条件を 1 項目以上で被覆する。
2. `照合表`: 変更点 ID ごとに下の共通一覧契約を使い、diff 外を含む全ヒットを書く。第 4 列の `扱い` は `一致` または `食い違い: <finding ID>` とする。
3. `ハンク被覆`: 固定した PR diff の全ハンクを、ファイル・ハンクヘッダー・finding ID または `問題なし` の行で 1 回以上被覆する。

区画を渡されたときは、その区画のファイルの全ハンクを読み、三表には自分の区画のファイルだけを載せる。受け入れ条件は全文を読み、その区画に関わるものを `変更点の一覧` で被覆し、関わらないものは一覧の外に `区画の対象外: <受け入れ条件 ID>` と書く。すべての受け入れ条件の被覆と PR diff の全ハンクの被覆は、全区画の和集合で満たす。区画 k の変更点 ID と finding ID は `P<k>-` で始める。`検索コマンド:` には固定 HEAD の SHA を書かず文字どおり `<rev>` を書き、SHA は `修正前 SHA:` に書く。テスト・lint の再実行は区画 1 だけが行い、ほかの区画は再実行しなかったことを要約に書く。区画 1 が受け入れ条件の被覆の残差を補足するときだけ、残差の受け入れ条件の全文・全区画のファイル一覧とそれらのハンクを読んでよい。対応する変更は `P1-` の変更点 ID で補い、対応が無ければ `P1-` の finding を返す。

**共通一覧契約（`照合表` と、`stages/triage.md` の仕分け表の順 3 の grep の語の経路の第 1 段）**: `修正前 SHA: <40 桁>`、`検索コマンド: git grep -n <語の指定> <rev> -- .`、`| ファイル | 行（修正前 SHA） | ヒットした行の本文 | 扱い |` を必須とする。検索起点はリポジトリルートで固定 revision の全追跡対象パスを含め、サブディレクトリへの限定や追跡対象パスの除外を禁止する。本文は、元の `\` を `\\`、次に `|` を `\|`、次に backtick を `\` + backtick に escape し、本文全体を backtick fence で囲む。fence は escape 後の本文内に現れる最長の連続 backtick より 1 個長くし、この逆順でだけ復号する。検索語には照合方式と論理結合の option だけを使い、`--max-count` / `--max-depth` などヒット件数・範囲を狭める option は禁止する。一周目は固定した対象 HEAD を修正前 SHA とし、第 4 列を `一致` / `食い違い: <finding ID>` にする。順 3 は W が修正に着手する直前の HEAD を修正前 SHA とし、第 4 列だけを `直した` / `該当しない: <理由>` に変える。両経路とも `plugins/dev-workflow/scripts/review-hit-set.py` で第 4 列を除く全ヒット集合を照合する。順 3 固有の修正後 HEAD に対する本文・件数・削除行の第 2 段も、同じスクリプトに `--head <HEAD の 40 桁 SHA>` を付けて回す（規則は順 3 の節）。順 3 の場合分けの軸は共通一覧契約の対象外で、`検索コマンド:` に軸と全域、`| 軸の値 | 扱い |` を書き、軸の全域との一致だけを検査する。

三表を自己点検してから指摘へ進む。保証範囲は `変更点の一覧` に載せた項目についてリポジトリ内の出現箇所をすべて照合したことまでで、一覧に載らなかった暗黙の変更を発見したことまでは保証しない。

- 見出し: 命令形 1 行・80 字以内
- 深刻度: `blocking` | `should` | `nit`（下の表）
- 検証: `confirmed`（実行・テストで裏取り済み） | `plausible`（推測・未検証）
- 根拠: 深刻度が `blocking` のとき必須。受け入れ条件、または PR が触れる openspec spec の原文を引用する。引用できないときは、例外 3 種（安全機構の穴・データ破壊・無言の機能不全）のどれに当たるかを書く
- 場所: `file:line-range`（diff と重なる範囲で 10 行以内。ただし `照合表` で見つけた食い違いの指摘は、変更箇所と diff 外の既存箇所の 2 か所を書いてよく、少なくとも一方を diff と重ねる）
- 何が起きるか: どの入力・状態のときに、何が誤動作するか（発生条件）
- 直し方: 行レベルの置換コード、または 3 行以内の手順。そのとおりに直せばこの指摘が閉じるもの
- 状態: 再レビューのときだけ付ける。`fixed` | `unresolved` | `wontfix`

| 深刻度 | 定義 |
|---|---|
| `blocking` | 受け入れ条件または仕様の文に違反し、マージすると壊れる |
| `should` | 直すべきだが、マージ後に issue で直せる |
| `nit` | 好み・スタイル |

再レビュー（差分限定）は、前回の指摘ごとに状態を付けて閉じたかを確かめるだけにし、新規の指摘を出さない（新規の `nit` も出さない。ただし例外 3 種＝安全機構の穴・データ破壊・無言の機能不全に当たる `blocking` は差分限定の周でも出してよい）。方式の書き換えのあとに PR 全体を見直す周でも、新規に出してよいのは `blocking` だけ。前回の「直し方」どおりに直した箇所を再指摘しない。直し方自体が誤っていたなら、レビュアー側の誤りとして前回の指摘を `wontfix` にし、理由を書く。
```

**Codex が優先度付きの形で返したときの読み替え**: 書式を指定しない `codex exec` は、指摘に `[P1]` のような優先度の見出しを付けて返す（2026-09-21 に実測。#349 の PR コメントに記録）。書式ブロックを貼っても Codex がこの形や JSON で返したときは、次の表で固定書式に読み替える。

| Codex の出力 | 固定書式の欄 | 読み替え |
|---|---|---|
| `[P0]`〜`[P3]` の見出し、JSON の `priority` | 深刻度 | 参考にとどめる。`[P0]`・`[P1]` は `blocking` の候補、`[P2]` は `should`、`[P3]` は `nit` として読み、止めるかどうかは `stages/triage.md` の「マージを止めるかの判定（全周共通）」で決める |
| `file:line` のリンク、JSON の `code_location` | 場所 | そのまま使う |
| JSON の `confidence_score` | 検証 | `confidence_score` を `confirmed` の代わりにしない（`confirmed` は実行・テストで裏取りしたことを指す）。裏取りの記述が無い指摘は `plausible` として扱う |
| （対応する欄が無い） | 根拠 | Codex のルーブリックには無いので、書式ブロックを貼った指示文で書かせる |

`変更点の一覧`・`照合表`・`ハンク被覆` のいずれかが無い優先度付き出力は、完全なレビュー結果へ読み替えない。不足したレビュアー出力として扱い、一周目の照合を完了扱いにしない。

## 出口

- レビュアーは `変更点の一覧`・`照合表`・`ハンク被覆` と指摘の一覧を、起こした側に返す。
- 起こした側は、結果を受け取ったら、指摘が残っていれば `stages/triage.md`、残っていなければ `declarations.md`（手順 3・3-b）へ進む。develop の G は先に `gate-runner.md` の「一周目の三表を機械照合する」を行う。
