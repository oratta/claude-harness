# 宣言の書式（リスク宣言・仕様宣言） — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/pass.md`（手順 4・5）、`stages/carryover.md`（手順 3-c）、`stages/hold.md`（手順 6）。

## 入口

レビューで止める指摘が残らなかったあと（`stages/triage.md` を通った場合は、止める指摘が無くなったあと）、合格処理（`stages/pass.md`）の前に読む。develop の W は、(3b) で仕様宣言を投稿するときにこのファイルだけを読む。

## 前提と理由（この段で使うもの）

- **HEAD SHA**: リスク宣言・仕様宣言（手順3）と動作確認証拠（手順4）のコメントには対象 HEAD の 40 桁フル SHA を必ず記載する。どのコミットに対する宣言かを機械的に照合できるのは SHA だけで、手順5は「現在の HEAD と一致する SHA を含むコメントの実在」を実測してから合格処理する。レビュー中に新たなコミットを push したら、その時点で HEAD_SHA を取り直し、宣言・証拠を出し直す（古い SHA のコメントは合格根拠にならない）。**この `対象 HEAD:` 規約は auto-merge workflow（`templates/auto-merge/`）の合格条件そのものでもある** — workflow は判定時の HEAD と一致する「対象 HEAD: <40桁フル SHA>」コメントの実在を機械照合し、無ければマージしない。コメント 1 行目の文言形式（`対象 HEAD: ` ＋ 40 桁フル SHA）を変えると配備済み全リポの機械マージが止まるため、規約の変更は必ずテンプレート側と同時に行う。
- **仕様宣言**: 「仕様（openspec）を更新したか／不要と判断したか」は、develop スキルの W（`references/roles/worker/spec.md`）が記録先（元 issue。issue が無い依頼では Draft PR 自身）に `仕様化判断: する|しない` として記録する（契約の正本は develop スキルの `references/roles/spec-reviewer.md`「判断記録の契約」）。スキルを通らずに実装された PR はこの記録を持たないので、出口のこのゲートで手順3の仕様宣言と手順5の照合で fail-closed に止める。仕様宣言も `対象 HEAD:` 規約に乗せてあるので auto-merge workflow の合格条件に組み込めるが、配備済みリポへの伝播を伴うため**本スキルの範囲外（別 issue）**とし、当面はこのスキルの手順5だけが照合する。

## 手順

### 3. リスク宣言（positive affirmation・必須）

レビュー出力は**必ず次のどちらか**を PR コメントとして残す。「書かない」は選べない。

| 宣言 | 条件 | 後続 |
|---|---|---|
| **リスクなし** | プロダクトのユーザーに及ぶ影響・データ喪失・課金/法務・外部公開面の変化・資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張が**いずれも無い** | 手順4へ |
| **主のリスク許容が必要** | 上記のいずれかが1つでもある（issue 時点で見えず**実装中に発覚したもの**を含む） | 論点ありなら手順6へ（`agent-review:passed` は付けない）。論点なしなら手順6の前に決める役の確認に回し（下の「論点なしの確認」の節）、同じ HEAD の `論点なしの確認: 通す` の記録を得たら手順4へ、得なければ手順6へ。issue で承認済みなら手順 4 へ（論点の有無によらない。下の「issue で承認済み」の節） |

後ろの 3 観点は、行動ルールの変更をエージェントがマージするリポで、主が見るべき変更を拾うための問いである。何が当たるかは次のとおり。

- **資格情報**: ID・パスワード・API の鍵・トークンの取得・保管・利用・受け渡しを変えるコード・設定・エージェントへの行動指示（SKILL.md・ルール等。いつ取得するか・どう再利用するかの指示を含む）を足す・変える。実際の取り扱いを変えず、秘密の値そのものも含まない説明上の言及だけなら当たらない
- **安全ゲートの弱体化**: レビュー必須・投稿前チェック（hook）・auto-merge の判定条件・permission の deny・ブランチ保護などの止め具を外す・条件を緩める・迂回路を作る。コード・設定・エージェントへの行動指示（SKILL.md・ルール等）のどれで行うかを問わない。止め具を増やす・厳しくする変更は当たらない
- **エージェント権限の拡張**: permission の allow の追加、新しい外部サービス・MCP・ツールの利用、新しい書き込み先（リポ・ラベル・チャネル・ファイルの置き場）など、エージェントにできることを増やす。コード・設定・エージェントへの行動指示（SKILL.md・ルール等）のどれで行うかを問わない

資格情報・安全ゲートの弱体化・エージェント権限の拡張のどれか 1 つでも当たれば、既存 4 観点と同じく「主のリスク許容が必要」と宣言する。論点ありなら手順6で `needs-approval` を付けて主の許容を待ち、論点なしなら下の「論点なしの確認」に回す（下の「issue で承認済み」に当たるときを除く）。

判断に迷ったら「許容が必要」側に倒す。**判断がつかないことは「リスクなし」の理由にならない。**

コメント文面（`gh api -X POST repos/$R/issues/$N/comments -F body=@<file>` で投稿する）。ファイル名・書き込み・投稿前後の確認は `SKILL.md` の「コメント本文ファイルの共通規約」に従う。**2 行目の `対象 HEAD:` は必須**:

```
## リスク宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
リスクなし — この変更でプロダクトのユーザーに及ぶ影響・データ喪失・課金/法務・外部公開面の変化・資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張はいずれも無い。
根拠: <変更範囲が何で、なぜ外部影響が閉じているか。1〜3行>
```

許容が必要な場合のテンプレート（`主のリスク許容が必要。` のあとの空行に続く行は 2 つの形のどちらか 1 つ）:

```
## リスク宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
主のリスク許容が必要。

論点なし — 分類に当たったが、この変更を入れることで新たに生じるリスクは無い。決める役の確認で通す。
論点あり — この変更を入れることで新たに生じるリスク: <誰に何が起きうるか>
- 該当する観点: <7 観点のうち当たったもの>
- 発生条件: <いつ起きるか。論点なしなら「なし」>
- 起きたときの影響範囲と戻し方: <revert 可否・データが戻るか。論点なしなら「なし」>
- 根拠ファイル: <パス>, <パス>
- 検知時点: issue 記載済み / 実装中に発覚
```

`主のリスク許容が必要。` のあとの空行に続く行は次のとおり選ぶ。論点は、主が持っていて自分が持っていない観点（どこまでの被害を許せるか・事業判断）を足すと結論がよくなる点で、正本は `~/.claude/output-styles/readable.md` の節 3。

- **論点なし**: 7 観点の分類に当たっただけで、この変更を入れることで新たに生じるリスク（他の案や見送った場合には無いもの）が無いとき。リスク内容を作文しない。どの変更にも当てはまること（「見落としがあると壊れる」）はリスクに数えない。主の OK を求める文（「決まりで主の OK が要る」の類）を書かない。論点なしの宣言は下の「論点なしの確認」で通り、主に上がるのは確認で通らなかったときだけである
- **論点あり**: この変更を入れることで新たに生じるリスクがあるとき。そのリスクだけを中身で書く

`- 根拠ファイル:` には、分類に当たった変更、またはリスクの発生源になっているファイルを列挙する（HEAD が動いたときに手順 3-c がこのファイルの PR 自身の差分が前後で同じかを確かめ、違えば判定役にリスクの中身が同じかを比べさせる。main を取り込む merge commit だけが積まれたとき（PR_COMMITS=0）は比べない）。論点なしの宣言では、分類に当たった変更のファイルを書く。

宣言は PR に残す記録で、主に出す依頼文ではない。主への依頼文は宣言を写さず、`~/.claude/output-styles/readable.md` の節 3 の型で書く（論点なしの宣言を確認で通せずに主に聞くときは、論点なしの短い形で書き、行数は正本の節 3 の論点の無い依頼の決まりに従う）。返事の照合（手順 5 の `主の回答: 許容`）は変わらない。

論点なしの確認は引き継ぎ・issue 承認の両方が当たらないときだけ `stages/no-point-check.md` を読む。

issue で承認済みの候補は資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張。外部公開面の変化・データ喪失・課金/法務・プロダクトのユーザーに及ぶ影響は除外する。候補を判定するときは `stages/issue-approved.md` を読む。

#### 3-b. 仕様宣言（positive affirmation・必須）

リスク宣言とは**別のコメント**として、仕様宣言を必ず投稿する（リスク宣言の文言は書き換え禁止なので、仕様宣言だけを出し直せるよう分ける）。「書かない」は選べない。本文は次の 3 形のどれかちょうど。

以下「記録先」は元 issue、issue 参照が無い PR では PR 自身（手順5の解決手順と同じ）。

仕様を更新した場合（記録先に `仕様化判断: する` がある PR）:

```
## 仕様宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
仕様: 更新した — change <change-name>（archive 済み）／仕様レビュー: APPROVE（<issue コメントの URL>）
```

仕様を更新し、文言合わせの通し方で仕様レビューを省いた場合（記録先に `仕様化判断: する` があり、同じコメントに通し方の行がある PR）:

```
## 仕様宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
仕様: 更新した — change <change-name>（archive 済み）／仕様レビュー: 省いた（文言合わせ。<仕様化判断のコメントの URL>）
```

この形を使ってよいのは、記録先の最新の仕様化判断のコメントに `^通し方: 文言合わせ$` に完全一致する行がある PR だけ（通し方の定義は develop の `references/spec-decision.md` Step B。行が無い PR がこの形で宣言しても、手順5は `仕様レビュー: APPROVE` を求める）。

仕様変更なしの場合（記録先に `仕様化判断: しない` がある PR）:

```
## 仕様宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
仕様: 変更なし — 理由: <なぜ spec が不要か。規範を持ちうるパス（docs/・.claude/ 等）に触れているなら、それでも規範が変わらない理由>
```

記録先に `仕様化判断:` の記録が無い PR は、**先に判断を記録してから**宣言する（手順5の整合表を参照）。

## 出口

- 手順 3 で「主のリスク許容が必要」と判定したら、次の順に試す: 前の HEAD に主の直接の許容（`主の回答: 許容` と `真正性確認: 済`）があれば、まず `stages/carryover.md` の手順 3-c の引き継ぎ。引き継げないか前の許容が無ければ、手順 3 の issue で承認済み。どちらも当たらなければ `stages/hold.md` の手順 6。先に当たったほうだけを追記し、両方を書き込まない。3-c の引き継ぎか issue で承認済みが当たったら `stages/pass.md` へ進む。
- そうでなければ `stages/pass.md`（手順 4 の動作確認と手順 5 の合格処理）へ進む。
- develop の W は仕様宣言を投稿したら (3b) の手順に戻る。
