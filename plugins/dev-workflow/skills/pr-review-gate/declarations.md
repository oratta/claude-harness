# 宣言の書式（リスク宣言・仕様宣言） — pr-review-gate

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。段の一覧と手順番号の対応表は索引 `SKILL.md`（pr-review-gate の直下）にある。

このファイルが番号で指す他の段の手順は次のファイルにある（パスは pr-review-gate の直下から）: `stages/pass.md`（手順 4・5）、`stages/hold.md`（手順 3-c・6）。

## 入口

レビューで止める指摘が残らなかったあと（`stages/triage.md` を通った場合は、止める指摘が無くなったあと）、合格処理（`stages/pass.md`）の前に読む。develop の W は、(3b) で仕様宣言を投稿するときにこのファイルだけを読む。

## 前提と理由（この段で使うもの）

- **HEAD SHA**: リスク宣言・仕様宣言（手順3）と動作確認証拠（手順4）のコメントには対象 HEAD の 40 桁フル SHA を必ず記載する。どのコミットに対する宣言かを機械的に照合できるのは SHA だけで、手順5は「現在の HEAD と一致する SHA を含むコメントの実在」を実測してから合格処理する。レビュー中に新たなコミットを push したら、その時点で HEAD_SHA を取り直し、宣言・証拠を出し直す（古い SHA のコメントは合格根拠にならない）。**この `対象 HEAD:` 規約は auto-merge workflow（`templates/auto-merge/`）の合格条件そのものでもある** — workflow は判定時の HEAD と一致する「対象 HEAD: <40桁フル SHA>」コメントの実在を機械照合し、無ければマージしない。コメント 1 行目の文言形式（`対象 HEAD: ` ＋ 40 桁フル SHA）を変えると配備済み全リポの機械マージが止まるため、規約の変更は必ずテンプレート側と同時に行う。
- **仕様宣言**: 「仕様（openspec）を更新したか／不要と判断したか」は、develop スキルの W（`references/roles/worker/spec.md`）が記録先（元 issue。issue が無い依頼では Draft PR 自身）に `仕様化判断: する|しない` として記録する（契約の正本は develop スキルの `references/roles/spec-reviewer.md`「判断記録の契約」）。スキルを通らずに実装された PR はこの記録を持たないので、出口のこのゲートで手順3の仕様宣言と手順5の照合で fail-closed に止める。仕様宣言も `対象 HEAD:` 規約に乗せてあるので auto-merge workflow の合格条件に組み込めるが、配備済みリポへの伝播を伴うため**本スキルの範囲外（別 issue）**とし、当面はこのスキルの手順5だけが照合する。

## 手順

### 3. リスク宣言（positive affirmation・必須）

レビュー出力は**必ず次のどちらか**を PR コメントとして残す。「書かない」は選べない。

| 宣言 | 条件 | 後続 |
|---|---|---|
| **リスクなし** | プロダクトのユーザーに及ぶ影響・データ喪失・課金/法務・外部公開面の変化・資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張が**いずれも無い** | 手順4へ |
| **主のリスク許容が必要** | 上記のいずれかが1つでもある（issue 時点で見えず**実装中に発覚したもの**を含む） | 手順6へ（`agent-review:passed` は付けない）。issue で承認済みなら手順 4 へ（下の「issue で承認済み」の節） |

後ろの 3 観点は、行動ルールの変更をエージェントがマージするリポで、主が見るべき変更を拾うための問いである。何が当たるかは次のとおり。

- **資格情報**: ID・パスワード・API の鍵・トークンの取得・保管・利用・受け渡しを変えるコード・設定・エージェントへの行動指示（SKILL.md・ルール等。いつ取得するか・どう再利用するかの指示を含む）を足す・変える。実際の取り扱いを変えず、秘密の値そのものも含まない説明上の言及だけなら当たらない
- **安全ゲートの弱体化**: レビュー必須・投稿前チェック（hook）・auto-merge の判定条件・permission の deny・ブランチ保護などの止め具を外す・条件を緩める・迂回路を作る。コード・設定・エージェントへの行動指示（SKILL.md・ルール等）のどれで行うかを問わない。止め具を増やす・厳しくする変更は当たらない
- **エージェント権限の拡張**: permission の allow の追加、新しい外部サービス・MCP・ツールの利用、新しい書き込み先（リポ・ラベル・チャネル・ファイルの置き場）など、エージェントにできることを増やす。コード・設定・エージェントへの行動指示（SKILL.md・ルール等）のどれで行うかを問わない

資格情報・安全ゲートの弱体化・エージェント権限の拡張のどれか 1 つでも当たれば、既存 4 観点と同じく「主のリスク許容が必要」と宣言し、手順6で `needs-approval` を付けて主の許容を待つ（下の「issue で承認済み」に当たるときを除く）。

判断に迷ったら「許容が必要」側に倒す。**判断がつかないことは「リスクなし」の理由にならない。**

コメント文面（`gh api -X POST repos/$R/issues/$N/comments -F body=@<file>` で投稿する）。**2 行目の `対象 HEAD:` は必須**:

```
## リスク宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
リスクなし — この変更でプロダクトのユーザーに及ぶ影響・データ喪失・課金/法務・外部公開面の変化・資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張はいずれも無い。
根拠: <変更範囲が何で、なぜ外部影響が閉じているか。1〜3行>
```

許容が必要な場合のテンプレート（**この形式以外で主にリスク承認を求めない**）:

```
## リスク宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
主のリスク許容が必要。

この実装により <リスク内容: 誰に何が起きうるか> というリスクが生まれる。
（プロダクトのユーザーへの影響・返金/訴訟等の最終責任は主にある）
- 該当する観点: <7 観点のうち当たったもの>
- 発生条件: <いつ起きるか>
- 起きたときの影響範囲と戻し方: <revert 可否・データが戻るか>
- 根拠ファイル: <パス>, <パス>
- 検知時点: issue 記載済み / 実装中に発覚
これを許容するか。許容できないなら <代替案 or 見送り> に切り替える。
```

`- 根拠ファイル:` には、リスクの発生源になっているファイルを列挙する（HEAD が動いたときに手順 3-c がこのファイルの無変更を確かめる）。

#### issue で承認済み（「主のリスク許容が必要」の宣言に追記する状態）

記録先の issue が目的として書いた効果は、主が issue を書くか承認した時点で受け入れている。その効果のために PR のたびに許容を聞き直さないよう、「主のリスク許容が必要」と判定した宣言に下の 3 行を追記した状態を「issue で承認済み」と呼ぶ。第 3 の宣言文ではない（宣言の行頭の 2 文言は変えない）。

当てられるのは資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張の 3 分類だけである。外部公開面の変化・データ喪失・課金/法務・プロダクトのユーザーに及ぶ影響は、issue に書いてあっても主に聞く。宣言の `- 該当する観点:` にこの 4 分類のどれかが 1 つでも含まれる、または引用の付かない分類が 1 つでもあるときは、宣言全体を手順6で主に聞く（一部の分類だけを承認済みにしない）。

無人運用（loop-dev-agent の憲法がレビューモードで回すゲート。`stages/triage.md` が「無人運用（loop-dev-agent）」と呼ぶもの）と、主に事後報告を届ける先が無い経路（メインセッションで主と会話していない・develop の G でもない）では、下の条件をすべて満たしても「issue で承認済み」を当てない。従来どおり手順6で `needs-approval` を付けて保留にする（主との会話が無く、合格後の事後報告を載せる先が無いため）。

当てるのは次の 3 条件をすべて満たすときだけ:

1. 記録先の issue の本文が、当たった分類の効果をその issue の目的として書いている。該当の文を分類ごとに宣言へ引用する（背景や備考で触れただけの文は目的ではない）
2. 主がその issue を承認した証拠が会話ログにあり、`owner-reply-check.sh` の終了コード 0 で確かめられる。証拠は下の起票の承認か、主が自分で打った `/develop <番号>` のどちらか。どちらの形でも、issue 本文の `lastEditedAt`（`gh api graphql -f query='{repository(owner:"<o>",name:"<r>"){issue(number:<N>){createdAt lastEditedAt}}}'`。未編集なら null）が null か、証拠の発言の timestamp より前であること（承認のあとに本文が書き換えられていないこと）
3. 実装中に発覚した影響ではない（宣言の `- 検知時点:` が `issue 記載済み`）

証拠の確かめ方（`owner-reply-check.sh` は `bash <plugin>/scripts/owner-reply-check.sh <セッション ID> <原文>` で回す。出力と終了コードの意味は `stages/pass.md` の手順 5「会話で受けた許容」の段落にある）:

- **`/develop <番号>`**: セッション ID は `$CLAUDE_CODE_SESSION_ID`（develop の G では本体のセッション）、原文は `<command-args><番号>` または `<command-args>#<番号>`。終了コード 0 で、`MATCH:` の全文が `<command-name>/dev-workflow:develop</command-name>`（または `/develop`）を含み、`<command-args>` の直後が `<番号>` または `#<番号>` で、その後ろが空白か `</command-args>` であることを確かめる（`7234` の中の `723` のような番号の部分一致を通さない）
- **起票の承認**: 起票したセッション S の会話ログで、issue の URL（`https://github.com/<R>/issues/<N>`）が最初に現れる行より前にある主の発言のうち、最後のものを起票を承認した発言とする。S を探すには、URL を含む会話ログを `grep -l '<URL>' "${OWNER_REPLY_PROJECTS_DIR:-${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects}"/*/*.jsonl` で集める（`owner-reply-check.sh` が読むのと同じ場所。`subagents/` の下は見ない）。
  - S にするのは、URL の初出行が、その直前の tool_use（`gh issue create` または `gh api -X POST repos/<R>/issues`）に対応する tool_result であるログだけ。初出行がそれ以外（`gh issue view` の出力・主の発言・`/develop` の引数など）のログは、issue を参照しただけのセッション（この develop のセッションや Orca の子のセッションを含む）なので S にしない
  - S の候補が 0 件（別の PC で起票した、など）なら、起票の承認の証拠は使わず手順6で主に聞く
  - 起票の承認には `<command-name>` を含む行（スラッシュコマンド）を使わない（`/develop` は `/develop <番号>` の証拠としてだけ扱い、下の除外を通す）。選んだ発言の原文で `owner-reply-check.sh <S のセッション ID> <原文>` を回し、終了コード 0 と同じ timestamp の `MATCH:` を確かめ、その全文から起票の承認（「起票して」「epic にして」「OK」など）が読めることを確かめる
  - 主のエピックの起票の承認は、同じセッション S でそのあと続けて起票された子の起票の承認の証拠になる（子の URL の初出行より前の主の最後の発言がその承認になる）。別のセッションでエピックの親が自動で起こした子の証拠にならない

当てない issue と数えない証拠: `agent-proposed` ラベルが付いた issue（主が「あとで見る」と言った印なので、会話ログに承認らしい発言があっても当てない）と、主の承認の記録が無いままエージェントが起こした issue（エピックの親が自動で起こした子を含む）には当てない。`EPIC_DISPATCH_PARENT_EPIC` が空でないセッション（Orca の親が子のターミナルに打ち込んだもの）の `/develop`、`<command-args>` に `--unmanned` を含む `/develop`（無人ループの起動）、全文が保留や却下（「あとで見る」「やめて」など）と読める発言は証拠として数えない。

当てたときの書き方: 宣言の本文（行頭 `主のリスク許容が必要。`）は書き換えない。末尾に次の 3 行を追記し、`needs-approval` を付けずに手順4・5へ進む（手順 5 で G が条件を確かめ直す）:

```
issue で承認済み — issue #<N> の目的: 「<本文からの引用>」
承認の証拠: <起票の承認 | /develop の打ち込み>（セッション <セッション ID> / <日時>）原文: <原文>
真正性確認: 済 — 確認者 <エージェント名> / <日時>（owner-reply-check.sh 終了コード 0）
```

当たった分類が 2 つ以上なら、1 行目を分類ごとに並べてよい（`issue で承認済み — <分類>: issue #<N> の目的: 「…」`）。追記の行頭を `主の回答: 許容` にしない（`stages/hold.md` の 3-c の「前の宣言の選び方」に拾われ、主の直接の回答ではない記録が引き継ぎの元になるのを避けるため）。条件を 1 つでも満たさなければ当てず、手順6で主に聞く（依頼に満たさなかった条件を添える）。

守備範囲: ①入力の出どころは、記録先の issue（本文・ラベル・`lastEditedAt`）と、ゲートが動いている PC の会話ログと、G の環境変数（`CLAUDE_CODE_SESSION_ID`・`EPIC_DISPATCH_PARENT_EPIC`）。G は協力的だが、目的でない文を目的として引用する・別の issue の `/develop` を拾う前提で扱う ②拾いたい誤りは、issue に書かれていない効果や 4 分類の影響を承認済みにすること、エージェントが起こしただけの issue を承認済みにすること、Orca の親や無人ループの `/develop` を主の打ち込みとすること、番号の部分一致、承認のあとに書き換えられた本文の引用 ③通ることを許す入力は、Orca 以外の仕組みが `EPIC_DISPATCH_PARENT_EPIC` を付けずに本体のターミナルへ打ち込んだ `/develop`（主の打ち込みと区別できない）と、ローカルの会話ログの改変・追記 ④ここに挙げた以外の経路は見つけるたびに検査を足し、穴を塞ぎ切ることを完了条件にしない。

#### 3-b. 仕様宣言（positive affirmation・必須）

リスク宣言とは**別のコメント**として、仕様宣言を必ず投稿する（リスク宣言の文言は書き換え禁止なので、仕様宣言だけを出し直せるよう分ける）。「書かない」は選べない。本文は次の 2 形のどちらかちょうど。

以下「記録先」は元 issue、issue 参照が無い PR では PR 自身（手順5の解決手順と同じ）。

仕様を更新した場合（記録先に `仕様化判断: する` がある PR）:

```
## 仕様宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
仕様: 更新した — change <change-name>（archive 済み）／仕様レビュー: APPROVE（<issue コメントの URL>）
```

仕様変更なしの場合（記録先に `仕様化判断: しない` がある PR）:

```
## 仕様宣言
対象 HEAD: <$HEAD_SHA 40桁フル>
仕様: 変更なし — 理由: <なぜ spec が不要か。規範を持ちうるパス（docs/・.claude/ 等）に触れているなら、それでも規範が変わらない理由>
```

記録先に `仕様化判断:` の記録が無い PR は、**先に判断を記録してから**宣言する（手順5の整合表を参照）。

## 出口

- 手順 3 で「主のリスク許容が必要」と判定したら、次の順に試す: 前の HEAD に主の直接の許容（`主の回答: 許容` と `真正性確認: 済`）があれば、まず `stages/hold.md` の手順 3-c の引き継ぎ。引き継げないか前の許容が無ければ、手順 3 の issue で承認済み。どちらも当たらなければ `stages/hold.md` の手順 6。先に当たったほうだけを追記し、両方を書き込まない。3-c の引き継ぎか issue で承認済みが当たったら `stages/pass.md` へ進む。
- そうでなければ `stages/pass.md`（手順 4 の動作確認と手順 5 の合格処理）へ進む。
- develop の W は仕様宣言を投稿したら (3b) の手順に戻る。
