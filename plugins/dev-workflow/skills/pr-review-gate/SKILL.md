# PR レビューゲート

主駆動型開発（主が席を外している間も PR がマージまで到達する）の品質ゲート。
**通過 = 主の承認なしに auto-merge されてよい**という意味なので、通過判定は保守的に出す。

- 通過の必須4点: **①リスク宣言 ②仕様宣言 ③動作確認の証拠（or 3点セット依頼） ④`agent-review:passed` ラベル**
- **fail-closed**: ①②③が**現在の PR HEAD の SHA を明記した PR コメントとして実在する**ことを API で実測するまで④を付けない。手順5以外の経路で `agent-review:passed` を付けることを禁じる。
- 実行は**サブエージェントに委譲**する（診断・diff 読み込みは本体セッションに流し込まない）。

以下 `$R` = `<owner>/<repo>`、`$N` = PR 番号。

## 前提と理由（各手順で繰り返さない。ここが正本）

- **auto-merge の配備状況**: auto-merge workflow（dev-workflow プラグインの `templates/auto-merge/` を展開したもの）が配備済みのリポでは、passed 付与でロボットが機械判定してマージする。**未配備のリポでは passed 付与後のマージは人間の操作**になる（ゲートの手順自体は変わらない）。どちらの場合も、LLM が `gh pr merge` や REST の merge API を直接叩いてマージすることは**禁止**（聖域・CI green・SHA ピン・緊急停止の判定を素通りするため）。
- **リポ固有の仕組み**: このスキルはリポ非依存。保留の主向けミラーや投稿規約などのリポ固有の仕組みは「**存在すればそれに従い、無ければ各手順の縮退手順**」で扱う。

---

## 手順

**マージを止めるかの判定（全周共通）**: マージを止めるのは、深刻度が `blocking` で、根拠の引用を G が記録先（issue または Draft PR 本文）の受け入れ条件、またはこの PR が触れる openspec の spec（change の delta spec を含む）の原文と照合できた（または根拠が例外 3 種＝安全機構の穴・データ破壊・無言の機能不全に当たる）、かつ検証が `confirmed` の指摘だけ。それ以外（`should`・`nit`・`plausible`・照合できない `blocking`）はマージを止めず、follow-up issue に回す。レビュアー（Codex・Task サブエージェント）の深刻度ラベルは参考にとどめ、判定の根拠は G の照合にする。この判定は 1周目・2周目・主の続行指示で開いた周の全周で同じ。

止める指摘が残ったら、動き方は下の「止める指摘の仕分け表」に従う（判定は「マージを止めるかの判定（全周共通）」のまま。周によって変わるのは、表のどの順を使えるかだけ）。

1周目で failed にするとき、止めない指摘は failed の PR コメントに一覧で残し、follow-up issue はまだ切らない（W が同じ周で直すことがあり、先に切ると重複する）。止める指摘が無い周は failed にせず、G が手順3へ進むときに、未解決の止めない指摘を follow-up issue に切って URL を PR コメントに記録する。

**止める指摘の仕分け表**（G は周回の数に関係なく、指摘が届くたびに上から当てる。表はここにだけ置き、他の節とファイルは順番号と見出しで参照する）:

| 順 | 当てる条件 | 動き | 主に聞くか |
|---|---|---|---|
| 1 | 止める判定に達しない（上の全周共通の判定で止まらない） | follow-up issue に回す（1周目は上の段落どおり failed の一覧に残す） | 聞かない |
| 2 | 受け入れ条件の中（根拠の引用元が記録先の受け入れ条件、またはこの PR の change の delta spec） | W が直す。`agent-review:failed` で W に戻す | 聞かない |
| 3 | 一覧の一致で閉じられる型（「同じ文が別の場所に残っている」「N 件のうち k 件しか直っていない」） | W に一覧を作らせ、G は検索結果の集合一致で閉じる。`agent-review:failed` で W に戻す | 聞かない |
| 4 | 今直す 3 条件を満たす | W がその場で直し、仕分け欄に記録する。`agent-review:failed` で W に戻す | 聞かない |
| 5 | 順 1〜4 に当たらず、順 6 の条件にも当たらない | 主に「この欠陥を残して切り出すか」を聞く。`needs-approval` を付けて保留で return | 聞く |
| 6 | 同じ型の再発、または順 3・順 4 からの落とし込み | 決める役が方式を裁定する。Status `needs-decider` で本体に return | 聞かない（裁定が「切り出す」なら順 5 と同じ経路） |

2 周目以降の周の終わり（2周目の終わりと、主の回答または決める役の裁定で開いた周の終わり）に止める指摘が残っていれば、順 2〜4 を使わない。前の周と同じ型の再発に当たる指摘は順 6、それ以外は順 5 に当てる。仕分けの結果（指摘ごとに当てた順とその根拠）は PR コメントに記録する。

同じ周に順 5 の指摘と順 2〜4 の指摘が混ざったら、保留を先にする。G は全件の仕分けを PR コメントに記録して保留で return し、主の回答後に、切り出さない指摘をまとめて 1 回の `agent-review:failed` で W に戻す。主の回答が来るまで、W は順 2〜4 の指摘の修正にも着手しない。`needs-approval` と `agent-review:failed` を同時に付けない。

同じ周に順 5 の指摘と順 6 の指摘が混ざったら（順 2〜4 の指摘を含んでもよい）、これも保留を先にし、次の順で処理する（主の回答を先にするのは、主が「切り出す」と答えた指摘に触れる順 6 の指摘があれば裁定の対象が変わるためで、裁定は PR ごとに 1 回までなので対象が減ってから使う）:
1. G は全件の仕分けを PR コメントに記録し、`needs-approval` を付けて保留で return する。主への質問は順 5 の指摘についてだけ出し、順 6 の指摘は仕分け欄に「順 6・未裁定」として載せる
2. 主の回答が来たら、G は順 5 の指摘を手順 6 の表の「切り出しの確認」行どおりに処理して `needs-approval` を外す。未処理の順 6 の指摘が残っていれば、`agent-review:failed` を付けずに Status `needs-decider` で return する
3. 裁定が「全部列挙してから直す」なら、主が「この PR で直す」と答えた指摘・順 6 の指摘・順 2〜4 の指摘をまとめて、1 回の `agent-review:failed` で W に戻す。裁定が「切り出す」なら、順 6 の指摘について順 5 と同じ経路で主に聞き（再び保留）、その回答が来てから残る修正を 1 回の `agent-review:failed` で W に戻す

この PR で決める役の裁定が既に 1 回あれば（順 6 の数え方で 1 件以上）、順 6 の指摘は最初から「切り出す」として順 5 の経路に入るので、1 の質問に含めて 1 回の保留にまとめる（主に 2 回に分けて聞かない）。主の回答と裁定の両方が済むまで、W は順 2〜4 を含むどの指摘の修正にも着手しない。

**順 3（一覧の一致で閉じる）**: W は、修正前 SHA・検索コマンド・全ヒットに「直した／該当しない理由」を付けた表を 1 つの PR コメントに投稿してから push する。修正前 SHA は、W が修正に着手する直前の HEAD（G が `agent-review:failed` を付けた周の対象 HEAD）の 40 桁フル SHA とする。一覧表の PR コメントの書式は上の共通一覧契約を正本とする（worker.md と照合表はこれに揃える）:
- 1 行目 `## 一覧（順 3）`、続けて `修正前 SHA: <40 桁>` の行と `検索コマンド: <コマンド>` の行を置き、その下に表を置く
- grep の語のときは共通一覧契約どおり `<rev> -- .` と全追跡対象パスを使う（G が `<rev>` を修正前 SHA と HEAD に置き換えて実行する）。作業ツリーに対する `grep -rn`、検索起点の限定、追跡対象パスの除外は使わない
- 場合分けの軸のときも `修正前 SHA:` の行は同じく書き、共通一覧契約の対象外とする。`検索コマンド:` の行には軸とその全域（例: 先頭バイトなら 0x00〜0xFF）を書き、表の列は `| 軸の値 | 扱い |` とする
- grep の語のとき、主表の本文列は常に修正前 SHA での本文とする。扱いが「該当しない」の行の本文を同じ周の修正で書き換えたなら、主表の下に見出し `### 書き換えた該当しない行` と表 `| ファイル | 行（修正前 SHA） | 修正後の本文 |` を置き、書き換えた「該当しない」行をすべて載せる（補助表）。補助表の各行は、主表で扱いが「該当しない」の行を `(ファイル, 行（修正前 SHA）)` でちょうど 1 つ指す。同じ `(ファイル, 行（修正前 SHA）)` を補助表に 2 回載せない。修正後の本文が主表の本文と等しい行（書き換えていない行）は載せない。修正後の本文の escape と fence は主表の本文列と同じ規則とする。書き換えた行が無ければ補助表は省略してよい
- 扱いの欄は `直した` か `該当しない: <理由>` のどちらかちょうどにする
- 順 6 の裁定「全部列挙してから直す」で W が作る一覧も、同じ見出し `## 一覧（順 3）` と同じ書式を使う

G はレビューをせず、最初に `git fetch` で W の push を取り込み、`git cat-file -e <修正前 SHA>^{commit}` で修正前 SHA のコミットが実在することを確かめる（解決できないときだけ、照合の起点が失われているので W に表の出し直しを求める。祖先であることまでは求めない）。そのうえで次の 2 段で照合する（「該当しない理由」の正否を判定しない。書き換えの妥当性も判定しない。集合の一致だけを見る）。grep の語は 2 段とも `plugins/dev-workflow/scripts/review-hit-set.py --head <HEAD の 40 桁 SHA> <table-file>` の 1 回の実行で回す（`<HEAD の 40 桁 SHA>` は `git fetch` で W の push を取り込んだあとの HEAD の 40 桁フル SHA。`--head` を付けないと 1 段目だけを行う）:
1. 修正前 SHA で検索コマンドを実行したヒット集合が表の全行（扱いを問わない）と一致するかを見る。ここでの表は主表で、補助表はこの段で使わない
2. HEAD で同じ検索コマンドを実行し、残ったヒットがすべて、扱いが「該当しない」の行に対応するかを見る。各「該当しない」行の照合に使う本文は、補助表に載っていれば修正後の本文、載っていなければ主表の本文とする。対応は「ファイル」と「ヒットした行の本文」の組で取り、行番号では取らない（修正で前後の行が増減すると行番号がずれるため）。同じ組が複数あるときは件数で照合する。書き換えで検索語を含まなくなった「該当しない」行が HEAD に現れないことは不一致としない。ただし、修正前 SHA で同じファイル・同じ本文の組に「直した」と「該当しない」の両方があるとき（扱いが混在する組）は、件数の一致だけでは直し忘れを見分けられないので、あわせて `git diff <修正前 SHA> HEAD -- <ファイル>` の出力のうち `-` で始まりその本文が続く行の件数が、その組の「直した」の件数と、その組のうち補助表に載った「該当しない」の件数の和以上であることを見る。足りなければ、その組の「直した」の行を「直したはずが残った」差分として W に返す

場合分けの軸のときは、ヒットの集合がコミットによらず軸の全域で決まるので、1 段目として表の行の集合が軸の全域と一致するかだけを見て、2 段目を行わない。どちらの段でも一致しなければ、その差分（表に無いヒット、ヒットに無い表の行、「該当しない」の行に対応しない HEAD のヒット、扱いが混在する組で削除行が足りない「直した」の行、主表の「該当しない」行を指さない補助表の行、重複した補助表の行、書き換えていない補助表の行）だけを W に返す。差し戻しは 1 回まで（表の出し直しを求めた場合を含む）で、2 回目も一致しなければ順 6 に落とす。検索コマンドや軸の全域を W が書けない指摘は順 3 に当てない。順 3 の照合はレビューの周に数えない（G はレビューをしないので、周回キャップとは別に差し戻しの上限で止める）。同じ failed で戻した指摘が順 3 だけなら、集合が一致して閉じたあとに差分限定の再レビューは行わず、周を消費しない（閉じた PR コメント URL を仕分け欄に残す）。順 2・順 4 の指摘が同じ failed に含まれていれば、それらの差分限定の再レビューは通常どおり行い、周を 1 つ消費する。

**順 4（今直す 3 条件）**: 直し方が行レベルで 30 行以内、spec を変えない、この PR でその場で直した累計が 30 行以内、の 3 つをすべて満たすとき W がその場で直す。閾値は手順 2-0 と同じ 30 行を使い、別の数字を足さない。W は直したら仕分け欄に「受け入れ条件の外・その場で直した・直し方 N 行」と記録する。順 4 で直した指摘が 1 回で閉じなかったら、2 回目は順 6 に落とす。

**順 5（主に切り出すかを聞く）**: 主への質問は「この欠陥を残して切り出すか」の形にし、次の 4 点を必ず書く: 欠陥がマージ後に何を起こすか、直す見積もり（行数・触るファイル・spec を変えるか）、別 issue にする固定費、推奨。2 周目の終わりまで待たず、指摘を受け取ったその周で聞く。G は PR に `needs-approval` を付けて保留で return し、復帰は手順6の表の「切り出しの確認」行に従う。無人運用（loop-dev-agent）でも同じく止まる。

**順 6（決める役が方式を裁定する）**: 当てるのは次のどちらか。2 周目以降の周の終わりに止める指摘が残り、前の周と同じ型が別の場所・別の場合で再発しているとき。または、順 3 の照合が差し戻し後の 2 回目も一致しない、あるいは順 4 で直した指摘が 1 回で閉じないとき（順 3・順 4 からの落とし込み。周の終わりを待たず、その時点で順 6 に当てる）。決める役（`dev-workflow:decider`）が裁定するのは方式（全部列挙してから直す／切り出す）だけで、止めるかどうかの判定は G が全周共通の判定で行う。G はサブエージェントを起こせないので Status `needs-decider` で return し、本体が決める役を起こして可否と根拠の形で裁定を受け取り、それを渡して G を再開する（本体の動きは develop スキルの (4)）。G は裁定を 1 行目 `決める役の裁定: 全部列挙してから直す` または `決める役の裁定: 切り出す` の PR コメントとして記録し、仕分け欄にも同じ内容を書く。裁定は PR ごとに 1 回まで。回数は G のコンテキストに持たせず、G が再 spawn・再開されたときに、1 行目が `^決める役の裁定: (全部列挙してから直す|切り出す)$` に完全一致する PR コメントの件数を全ページから数える（`gh api --paginate --slurp repos/$R/issues/$N/comments | jq '[add[] | select(.body | split("\n")[0] | test("^決める役の裁定: (全部列挙してから直す|切り出す)$"))] | length'`）。1 回目の裁定が「切り出す」だった場合もこの 1 回に数え、2 回目の順 6 は決める役を起こさず「切り出す」として扱う（厳しい側に倒す）。裁定が「全部列挙してから直す」なら `agent-review:failed` に付け替え、W に順 3 と同じ形の一覧を作らせて次の周に入る。ただし、同じ周の順 5 の指摘に主がまだ回答していなければ、failed に付け替えずに保留のまま待つ（処理順は上の順 5 と順 6 の混在の段落）。裁定が「切り出す」なら順 5 と同じ経路で主に聞く。本体から「裁定なし（入力不足）」が返ったら（決める役が 2 回続けて入力不足を返したとき。develop スキルの (4)）、G は `決める役の裁定:` の PR コメントを残さず（裁定の回数に数えない）、仕分け欄に「決める役の裁定なし（入力不足）」と書き、その指摘を「切り出す」として順 5 と同じ経路で主に聞く。

**収束ルール（レビュー周回のキャップ）**:

- レビューは**既定2周**（初回レビュー＋再レビュー1回）で確定する。**3周目を自動で開けない**（G も本体も開けない）。3周目以降の周を開けるのは、主が順 5 に「この PR で直す」と答えたときと、決める役が順 6 で「全部列挙してから直す」と裁定したとき（PR ごとに 1 回まで）だけ。
- **再レビューは差分限定**: 前回指摘が閉じたかの確認に限る。再レビューでの新規探索はしない。再レビュー中の新規の気づきは follow-up issue に切り出す。ただし例外 3 種（安全機構の穴・データ破壊・無言の機能不全）に当たる新規の指摘は差分限定の周でも受け取り、仕分け表に当てる。
- **例外: 方式の書き換えの後は全体レビューにする。** G は再レビューを始める前に、W の修正差分の行数と前周の指摘の対象行数を比べ、修正差分が大きく超えていれば（方式の書き換え）、次の再レビューを差分限定ではなく PR 全体のレビューにする。判定に使った 2 つの行数を PR コメントに記録する。**周回は数え続ける**（1周目に戻さない。2周目が全体レビューになったら、その結果に下の仕分けをそのまま適用する）。
- **blocking の定義を限定する**: マージ後に issue で直せるものは blocking にしない。follow-up issue 化してマージを通す。止めるかどうかは全周で「マージを止めるかの判定（全周共通）」で決め、2周目の終わりには次の手順で仕分ける。

**2周目の終わりにやること（G が、2周目の結果を受け取った直後に）**:

1. **残った指摘ごとに、違反する文を引用する。** 引用元は記録先（issue または Draft PR 本文）の受け入れ条件と、この PR が触れる openspec の spec（change の delta spec を含む）に限る。止めるかどうかは「マージを止めるかの判定（全周共通）」で決め、**レビュアー（Codex・Task サブエージェント）の深刻度ラベルは参考にとどめる**（「高深刻度」と付いていても、判定で止まらなければ止める指摘ではない）。**引用元が無い**とき（PR が openspec に触れず、記録先にも受け入れ条件の文が無い）は、引用元を広げず、残った指摘を全件「引用なし」として扱う。仕分けの結果（指摘ごとの引用・例外 3 種のどれか、または「引用なし」）を PR コメントに記録する。
2. **止めない指摘（引用できない指摘を含む）は follow-up issue に切って `passed` の判定へ進む。** 各指摘を follow-up issue にし、URL を仕分けの PR コメントに記録して、手順3以降へ進む。止めない指摘を理由に3周目を開けない。
3. **止める指摘が1件でも残ったら、3周目に入らず止まる**（引用できる指摘でも、判定で止まらないものは上の follow-up issue 側に回す）。仕分け表の順 2〜4 を使わない。前の周と同じ型の再発に当たる指摘は順 6（決める役が方式を裁定する）、それ以外は順 5（主に切り出すかを 4 点付きで聞く）に当てる。無人運用（loop-dev-agent）でも同じく止まる。**主の回答または決める役の裁定で開いた周の終了時にも同じ仕分けを適用し**、止める指摘が残れば再び順 5・6 に当てる（主の回答なしに次の周へ進まない。決める役の裁定で周を開けるのは PR ごとに 1 回まで）。

**決める役（`dev-workflow:decider`）は順 6 の方式だけを裁定する。** 止めるかどうかは全周共通の判定で G が決める。3周目以降の周を開けるかどうかは主の回答か順 6 の裁定で決まる。順 6 以外で決める役を挟まない（修正サイクルでの原因分類・直し方・次のモデルの裁定は手順2-2の出力契約のまま）。

#### 2-2. 修正サイクルのモデル昇格（failed → 修正実装）

`agent-review:failed` に付け替えて修正サイクルへ戻すときは、**修正を書くサブエージェントのモデルを決めてから戻す**（Agent ツールの `model` パラメータ。PR を持っているセッション本体のモデルは変えない）。

| failed の原因 | 戻し方 |
|---|---|
| **実装品質起因**（テスト不足・エッジケース漏れ・既存コードとの不整合・安全機構の穴） | 失敗の原因が判断側（指示を解釈できなかった・指示自体が外れていた）か実行側（指示どおりやって結果が違う）かで、**決める役と実行役のどちらか一方だけ**を上げる（両方同時に上げない）。実行側なら実行役を `opus` で spawn し、判断側なら `subagent_type: dev-workflow:decider` を立てて修正方針を作らせ、実行役は据え置く（残量モードと共有枠モードの上限内） |
| **仕様が曖昧**（受け入れ条件から一意に決まらない） | モデル昇格ではなく仕様修正で返す。issue の受け入れ条件を確定させてから修正に入る（unmanned なら `needs-approval` を付けて主に返す） |
| **レビュアーの誤検出**（指摘が事実と違う） | モデル昇格ではなく反証で返す。該当コード・テスト結果を PR コメントに書いて指摘を閉じる |

**昇格は実装品質起因のときだけ。** 原因が仕様側・レビュアー側にあるのに最強モデルを当てても、同じ往復をもう1周するだけになる。

**実行役の上限は `opus`。** 修正実装を `model: fable` で spawn しない（`scripts/agent-model-guard.sh` が PreToolUse で拒否する）。Fable が消費するのはターン数（会話履歴の cache 読込）で、修正ループは数十〜数百ターン回るため、実行役を Fable にすると週次枠が溶ける。Fable を使うのは決める役（`subagent_type: dev-workflow:decider`。`Bash` を持たないので、その return を PR に書くのは呼び出し側）だけで、決める役はどの段階でも種別を固定して `model`（`opus` → `fable`）だけを切り替える。ラダーの正本は develop スキルの `templates/escalation-tripwires.md`。

**なぜ 1 回目の failed で上げるのか**: G のレビューループは 2 周キャップで**2 周目が最終周**にあたるため、1 回目の failed の時点で原因側を一方だけ上げてキャップ内での収束確率を上げる（昇格トリップワイヤーの「1 回目の失敗では誰も上げない」は同じテストの 2 連続失敗を数える別の発火条件で、こちらとは数え方が違う）。

**収束ルール（2周キャップ）との関係**: 再レビューは既定2周なので**2周目が最終周**にあたる。最終周の修正に最強モデルを当てることで、キャップ内で収束する確率を最大化する（3周目へ持ち越さないための配分）。

**Fable が使えないときのフォールバック**: レート制限・週次枠切れ（`FABLE_BUDGET_MODE=exhausted` 相当）で決める役を Fable で立てられない場合は、種別は `dev-workflow:decider` のまま `model: opus` に落として進め、その旨を PR コメントに1行残す（レビュー実行者行と同形式。この記録形式がフォールバック記録の正本）:

```bash
gh api -X POST repos/$R/issues/$N/comments \
  -f body='決める役モデル: opus（fable レート制限のためフォールバック。subagent_type は dev-workflow:decider のまま）'
```

1周目からモデルを上げる「重要実装」の事前分類（聖域パス・マージ権限・層間契約・課金/法務。実行役はどの分類でも `opus` 止まりで、読んで判断する役が分類に当たるときは `subagent_type: dev-workflow:decider`）は **develop スキルの references/roles/worker.md が正本** — このゲートでは再掲しない。

#### 3-c. 前の HEAD の許容の引き継ぎ

手順 3 で「主のリスク許容が必要」と判定し、同じ PR の前の HEAD の宣言に主の許容が記録済みのときは、手順6で主に聞く前にその許容を新しい HEAD に引き継げるかを確かめる（main の取り込みだけで HEAD が動いたときに、同じリスクを主に聞き直さないため）。

前の宣言の選び方: 同じ PR の `## リスク宣言` コメントのうち、`主の回答: 許容` で始まる行（`主の回答: 許容（引き継ぎ）` を含む）と `真正性確認: 済` の行の両方を持つ最新 1 件を前の宣言とし、その `対象 HEAD:` の SHA を前 HEAD とする（最新の宣言が回答待ちでも、それを選ばない）。

```bash
bash <plugin>/scripts/risk-carryover-check.sh <前 HEAD> <新しい HEAD> <前の宣言の根拠ファイル>...   # --base の既定は origin/main。手順 1 の fetch と main の取り込みの後に回す
# 出力: CARRYOVER=yes|no / MAIN_MERGES=<件数> / RESOLVED_FILES=<衝突解消したファイル。無ければ none> / NG: <引き継げない理由>
# 終了コード: 0 = 引き継げる / 1 = 引き継げない / 2 = 引数・環境の不備（引き継げない側に倒す）
```

引き継げるのは次のすべてを満たすときだけ:

1. スクリプトが終了コード 0 を返す（差分が main の取り込みと版の行・CHANGELOG の並べ直しの衝突解消だけで、根拠ファイルが前後の HEAD で同一）
2. 前の宣言に `- 根拠ファイル:` の行がある。この行の無い宣言からは引き継げない（この手順より前の宣言を含む）
3. 引き継ぎの元が主の直接の回答で、捏造でない。前の宣言に `主の回答: 許容` 系の行と `真正性確認: 済` の行がある。引き継いだ宣言の回答リンクは主が許容を述べた元の直接の回答を指し、引き継ぎの記録（エージェントが書いた宣言コメント）を指さない。引き継ぎが 2 回以上続いても元の直接の回答のままにする。引き継ぐたびに、元の回答リンクに対して手順5の真正性確認（リンク先を開く・許容の意思を読む・GitHub コメントなら author を実測する）をやり直す
4. 新しい HEAD のレビュー結果から組み立てたリスク宣言の本文が、`対象 HEAD:` 行を除いて前の宣言の本文（末尾の `主の回答:` 以降の追記行を除いた部分）と同一である。比較は新しい HEAD の宣言を投稿する前に組み立てた本文で行う（リスク内容・該当する観点・発生条件・影響範囲と戻し方・根拠ファイルが同じかを、文の一致で確かめる）

引き継げるなら、前の宣言と同じ本文を新しい `対象 HEAD:` で投稿し、末尾に次の 4 行を追記する（`needs-approval` は付けずに手順4・5へ進む）:

```
主の回答: 許容（引き継ぎ） — <元の直接の回答リンク>（<元の回答の日時>）
引き継ぎ元: <前の HEAD の 40 桁フル SHA> の宣言 <前の宣言コメントのリンク>
引き継ぎの根拠: risk-carryover-check.sh 終了コード 0 — main の取り込み <件数> 件、衝突解消 <none またはファイル>、根拠ファイルの diff は空
真正性確認: 済 — 確認者 <エージェント名> / <日時>（元の回答を再確認）
```

1 つでも満たさなければ引き継がず、手順6で主に聞く。主への質問には、スクリプトの `NG:` 行（本文の不一致なら何が変わったか）を引き継げなかった理由として添えて手順6へ進む。

引き継ぎで省けるのは主への質問だけで、手順 2 のレビュー・手順 4 の証拠・手順 3-b の仕様宣言は新しい HEAD で出し直し、手順5の実測も省かない。これが手順1の「前回の合格部分を流用しない」と gate-runner.md の再レビューの「手順 1 から全工程をやり直す」に対する唯一の例外である。

### 4. 動作確認

**自力で検証し、証拠（手順＋結果）を PR コメントに添付する。** ブラウザ実機・CLI 実行・スクリプト実行いずれでもよい。受け入れ条件と 1:1 で対応させる。

```
## 動作確認
対象 HEAD: <$HEAD_SHA 40桁フル>

| 受け入れ条件 | 実行した手順 | 結果 |
|---|---|---|
| <条件> | <再現可能な手順> | ✅ <観測した実際の出力/画面> |
```

「テストが通った」だけは証拠にならない（テスト自体が変更対象のことがある）。実際に動かした痕跡を書く。

**自力検証が不能なときのみ**、3点セットを揃えて主に依頼し、手順6へ（マージ保留）:

```
## 動作確認: 主に依頼
1. 自力検証できなかった理由: <何が足りなかったか。「面倒」「時間」は理由にならない>
2. 主にやってほしい具体的手順: <URL・クリック順・期待される結果まで書く>
3. 次回から自力検証できるようにする改善提案: <テスト整備・認証情報の登録・seed データ等。issue 化するならリンク>
```

3点目は必須。これが無い依頼は主の負担を減らす方向に働かないので出さない。

### 5. 合格処理

前提として、**最後のレビュー結果に、全周共通の判定で止まる指摘（`blocking` かつ `confirmed`、G が引用を照合済みまたは例外 3 種に当たるもの）のうち、主が切り出すと答えて follow-up issue に切ったものと、G が順 3 の集合一致で閉じたもの（閉じた PR コメント URL を仕分け欄に残す）以外が 0 件であること**（判定は手順2-1「マージを止めるかの判定（全周共通）」。切り出す経路は手順6の表の「切り出しの確認」行、集合一致で閉じる経路は手順2-1の仕分け表の順 3）。そのうえで、**手順4の動作確認証拠を投稿済み、かつ手順3のリスク宣言が次のどちらかの状態のときだけ**実行する。

| リスク宣言の状態 | 合格処理 |
|---|---|
| 「**リスクなし**」を投稿済み | 可 |
| 「**主のリスク許容が必要**」を投稿済み ＋ **主の許容回答リンクを同コメントに追記済み**（手順6経由）＋ **下の真正性確認済み** | 可 |
| 「**主のリスク許容が必要**」を投稿済み ＋ **引き継ぎで許容済み**（手順 3-c の 4 行 `主の回答: 許容（引き継ぎ）`・`引き継ぎ元:`・`引き継ぎの根拠:`・`真正性確認: 済` が同コメントに揃っている） | 可 |
| 宣言が未投稿 / 許容が必要なのに回答リンクが無い | **不可**（手順6へ） |

**リスク宣言の文言を後から書き換えることを禁じる。** 主が許容しても「リスクなし」に書き換えず、
「主のリスク許容が必要」のまま残して追記だけする（形式: `主の回答: 許容 — <回答リンク>（<日時>）`）。
「リスクなし宣言は本当にリスクが無い場合にしか出ない」という前提が崩れると、
形骸化監査（リスクなし宣言のサンプリング再判定）が本来の抽出対象を取り逃がすため。

**許容リンク経由の合格では、リンクの真正性を確認する。** リンク先を実際に開き、
①**主のアカウントによる発言**であること ②**許容の意思が読み取れる**こと、の両方を確認し、
結果を宣言コメントに追記する（形式: `真正性確認: 済 — 確認者 <エージェント名> / <日時>`）。
リンクが GitHub コメントの場合は author を実測する:

```bash
gh api repos/$R/issues/comments/<comment_id> --jq '.user.login'   # 主のアカウント名と一致すること
```

Discord 等の外部サービスのリンクは目視確認でよい（確認記録は同じ形式で残す）。
リンク先が開けない・主本人の発言と確認できない場合は合格処理をしない（手順6に戻して主に再確認する）。

**「投稿したつもり」を信用しない。** 合格処理の前に、**現在の PR HEAD と一致する SHA を含む宣言コメントと
証拠コメントが実在すること**を API で実測確認する（投稿失敗・旧 HEAD 向けコメントの流用を両方とも塞ぐ。
`gh api -X POST .../comments` は静かに失敗しうるので、投稿直後のレスポンスだけを根拠にしない）:

```bash
HEAD_SHA=$(gh api repos/$R/pulls/$N --jq '.head.sha')
gh api repos/$R/issues/$N/comments --jq \
  "[.[] | select(.body | contains(\"$HEAD_SHA\")) | .body | split(\"\n\")[0]]"
```

出力に**リスク宣言・仕様宣言・動作確認の 3 見出しがすべて**現れることを確認する。
1 つでも欠けていれば**合格処理をしない**（コメントを出し直してから再確認する）。

**仕様宣言は記録先の記録と突き合わせる。** 記録先は PR 本文で最初に現れる `Closes #N` / `Fixes #N` / `Refs #N`（大文字小文字不問）が指す元 issue で、**issue 参照が無い PR では PR 自身**（`$REC` を PR 番号に切り替える。PR のコメントも `issues/<番号>/comments` で読める）。そこから最新の `仕様化判断:` コメント（1 行目が `^仕様化判断: (する|しない)$`）を取る。PR コメントへの記録が許されるのは **PR 本文に issue 参照が無い場合に限る**（issue 参照があれば issue 側が正。issue 側に記録が無ければ issue に投稿する）。`$ISSUE` が空のまま `issues/$ISSUE/comments` を叩くと `issues//comments` で 404 になるので、必ず `$REC` を経由する:

```bash
ISSUE=$(gh api repos/$R/pulls/$N --jq '.body' | grep -oiE '(closes|fixes|refs) #[0-9]+' | head -1 | grep -oE '[0-9]+')
REC=${ISSUE:-$N}   # 記録先の番号: issue 参照があればその issue、無ければ PR 自身
# jq の ^ $ は行頭・行末に掛からない（文字列全体の先頭・末尾）ので、1 行目を split で切り出してから照合する。
# コメントは 30 件でページが切れるので --paginate --slurp で全ページを取り（--slurp は --jq と併用不可なので jq へパイプ）、add で 1 配列にしてから「最新 1 件」を選ぶ
gh api --paginate --slurp repos/$R/issues/$REC/comments | jq -r 'add | [.[] | select(.body | split("\n")[0] | test("^仕様化判断: (する|しない)$"))] | last | .body | split("\n")[0]'
gh api --paginate --slurp repos/$R/issues/$REC/comments | jq -r 'add | [.[] | select(.body | split("\n")[0] | test("^仕様レビュー: (APPROVE|REQUEST_CHANGES)$"))] | last | .body | split("\n")[0]'
# 2 つ目の出力が「仕様レビュー: APPROVE」ちょうどであること（最新のレビュー結果が正。古い APPROVE の後に REQUEST_CHANGES が出ていれば不合格）
bash <plugin>/scripts/spec-touch-check.sh $R $N   # SPEC_TOUCH / OPENSPEC_DIFF / 触れた規範パス。終了コード 2 = 規範パスに触れて openspec 差分なし
```

| 記録先（issue、無ければ PR 自身）の記録 | 合格に必要な状態 |
|---|---|
| `仕様化判断: する` | PR の変更ファイルに `openspec/` が含まれる、**または**宣言が指す change が base で archive 済み（`openspec/changes/archive/*-<change-name>/` の実在を実測。スタック PR で仕様が先行 PR に入っている場合）。**かつ** 記録先の最新の `仕様レビュー:` コメントが `APPROVE`（古い APPROVE の後に REQUEST_CHANGES があれば不可）。仕様宣言は「更新した」形 |
| `仕様化判断: しない` | 仕様宣言は「変更なし＋理由」形。PR に `openspec/` 差分が**無い**こと（差分があれば「しない」と矛盾＝合格しない。判断を「する」に取り直すか差分を外す）。`spec-touch-check.sh` が終了コード 2 なら、理由に規範パス接触への言及があること |
| 記録なし | **合格しない**。今から判断して記録先に `仕様化判断:` を投稿する（「する」なら仕様化・仕様レビューからやり直す）。issue が無い PR に限り PR 自身のコメントに同書式で記録してよい（`gh api -X POST repos/$R/issues/$REC/comments`） |

**`needs-approval` が付いていないことを、Ready 化より前に確認する。** auto-merge は `needs-approval` を
BLOCKING_LABELS に含むため無審査マージにはならないが、**passed と併存すると
「合格済みなのに永久にマージされないスタック」**になり、Ready 化だけ済ませると保留中の PR が Draft でなくなる。
保留理由が解消しているなら `gh api -X DELETE repos/$R/issues/$N/labels/needs-approval` で外してから進む。
解消していないなら**そもそも合格処理をしない**（手順6に戻る）。

**PR が Draft なら Ready にしてから `agent-review:passed` を付ける**（この順序を入れ替えない）。
passed を先に付けると、その labeled イベントは PR が draft なので auto-merge workflow にスキップされる。
Ready 化で CI が走るリポでは CI 完了で拾い直されるが、CI を Draft 中に済ませて Ready 化では走らせないリポでは
次の判定が日次の schedule まで来ず、合格からマージまで最大 24 時間待つ。
Draft でない PR（人間が作った PR など）には Ready 化を行わない。
**Ready 化に失敗したら passed を付けずに止まる**（下の断片は非 0 で終わる）。draft のまま passed を付けると
その labeled イベントはスキップされて消費され、あとで Ready 化をやり直しても新しい labeled は起きないため、
Ready 化で CI が走らないリポでは日次の schedule まで拾われない。`draft` が取れなかったときも同じく止まる。

```bash
gh api repos/$R/issues/$N --jq '.labels[].name'   # needs-approval が無いことを確認（あれば上のとおり）
DRAFT=$(gh api repos/$R/pulls/$N --jq .draft)
case "$DRAFT" in true|false) ;; *) echo "draft を取得できない（$DRAFT）。passed を付けずに中断する" >&2; exit 1 ;; esac
if [ "$DRAFT" = true ]; then   # Draft なら Ready にする。失敗したら passed を付けずに中断する
  gh pr ready $N --repo $R || { echo "gh pr ready に失敗。passed を付けずに中断する" >&2; exit 1; }
fi
gh api -X POST repos/$R/issues/$N/labels -f 'labels[]=agent-review:passed'
gh api -X DELETE repos/$R/issues/$N/labels/agent-review:pending
gh api repos/$R/issues/$N --jq '.labels[].name'   # 実測確認（ラベル）
gh api repos/$R/pulls/$N --jq .draft              # 実測確認（Draft）
```

最後の実測確認は次の**4点すべて**を満たすこと（`gh` は静かに失敗することがある）:

| 確認項目 | 期待 |
|---|---|
| `agent-review:passed` | **ある** |
| `agent-review:pending` | **ない** |
| `needs-approval` | **ない** |
| PR の `draft` | **`false`** |

`needs-approval` が残っていたら合格処理は未完了（上の Ready 化前の確認に戻る）。
途中で止まったときは、passed が付いているかで復旧を分ける:

| 止まった状態 | 復旧 |
|---|---|
| Ready 化に失敗して止まった（`draft` が `true`、passed なし） | 失敗の原因（権限・ネットワーク等）を記録先に報告し、解消してから手順5の断片を再実行する |
| Ready 化は済んだが passed を付ける前に止まった（`draft` が `false`、passed なし） | 手順5の断片をそのまま再実行する（Draft でないので Ready 化は飛ばされ、passed の labeled で判定される） |
| passed は付いたが auto-merge が判定を取り逃がした（`draft` が `false`、passed あり、マージされない） | `docs/auto-merge.md` の手動実行（`workflow_dispatch` の `pr` 入力）で再判定する |
| `draft` が `true` のまま passed が付いている（旧手順や手動操作の残骸） | passed を外し、`gh pr ready` で Ready にしてから passed を付け直す（付け直しで新しい labeled が起きる） |
聖域パス（auto-merge workflow の SACRED 定義。例: `.github/workflows/` `CLAUDE.md` `.claude/` 憲法 doc）に
触れる PR は passed でも auto-merge されず人間マージになる — 判定の正本は auto-merge workflow 側。
触れている自覚があればコメントに1行書き添える。auto-merge 未配備のリポでは、合格処理の後に
「マージは人間の操作待ち」であることを PR コメントに1行残す。

**合格後の CI の見張り**（上の実測確認が済んでから。手順 6 で合格しなかった PR には始めない）:

- ゲートをメインセッションで回している場合: `plugins/dev-workflow/references/ci-watch.md` の手順で、`scripts/ci-watch.sh wait` を Bash ツールの `run_in_background` で起動して見張りを始める
- ゲートをサブエージェント（develop の G など）が回している場合: 見張りを始めずに `passed` を return し、呼び出し側の本体に見張りを任せる（サブエージェントは背景タスクの完了で起こされない）

待ち方・`--unrelated` の基準・一手ごとの動き・直し方は `references/ci-watch.md` が正本で、ここには再掲しない。直しで commit が積まれたら、`agent-review:passed` を外したまま見張りを続けて CI のやり直し・再度の直しを済ませ、`ready` になってから、この PR のゲートを手順 1 から取り直す。取り直したゲートに合格するまでマージ待ち・マージ依頼に進まない。

### 6. 保留処理（リスク許容待ち / 動作確認依頼 / 切り出しの確認）

1. `agent-review:passed` は**付けない**。`needs-approval` を付ける（`gh api -X POST repos/$R/issues/$N/labels -f 'labels[]=needs-approval'`）。
2. リポに保留を主へミラーする仕組み（pending 管理ファイルとその同期スクリプト等）が**あればそれに従って記録する**。無ければ、PR の `needs-approval` ラベルと宣言コメントが保留の正本になる。
3. 主への確認依頼は、リポ/運用環境に投稿規約があればそれに従う。無ければ PR コメントに依頼を書き、利用可能な連絡チャネルで主に PR リンクを渡す。依頼の前に自力調査（プリフライト）を通す。
4. **リスク承認を待つ間に手順4（動作確認）を並行して済ませておく**（承認が来た時点で手順5に直行できる。証拠の HEAD SHA が古くならないよう、待機中に push した場合は出し直す）。
5. 主の回答が来たら、**保留の種類ごとに次の復帰手順を踏む**（どちらも最後は手順5の合格条件を再確認してから合格処理する）:

| 保留の種類 | 主の回答 | 復帰手順 |
|---|---|---|
| **リスク許容待ち**（手順3） | 許容 | 許容を記録したあとに HEAD が動いたときは、主に聞き直す前に手順 3-c の引き継ぎを試す（条件は 3-c が正本）。回答をそのまま記録するときは、手順3の宣言コメントに `主の回答: 許容 — <回答リンク>（<日時>）` を**追記**する（宣言本文は書き換えない）→ 手順5の真正性確認を実施 → `needs-approval` を外して手順5へ |
| | 不許容 | 代替案へ切り替えて手順2からやり直すか、PR をクローズする。合格処理はしない。**`needs-approval` の扱い**: 代替案でリスク自体が消えるなら外す（＝保留理由の解消）／作り直し後も同じリスクが残るなら**付けたまま**にして再度許容を確認する。PR をクローズするならラベル状態は問わない |
| **動作確認代行待ち**（手順4） | 確認結果あり | 主の確認結果を**手順4の動作確認証拠として PR に記録**する（`対象 HEAD` / `実施者: 主` / 観測された結果 / 実施日時 / 主の回答リンク。受け入れ条件との対応も手順4の表と同じ形式で書く）→ `needs-approval` を外して手順5へ |
| | 期待どおりでない | `agent-review:failed` に付け替え、報告された症状を再現手順として書いて修正サイクルへ戻す。**`needs-approval` は外す**（主の代行は完了しており、保留理由は「主待ち」から「実装の欠陥」に変わったため。付けたままだと修正後も永久にマージされない） |
| **切り出しの確認**（手順2-1の仕分け表の順 5） | 切り出す | その指摘を follow-up issue に切って URL を PR コメントに記録する → **`needs-approval` を外す** → 未処理の順 6 の指摘が残っていれば `agent-review:failed` を付けずに Status `needs-decider` で return する（手順2-1の順 5 と順 6 の混在の段落）→ ほかに止める指摘が無ければ手順3以降へ |
| | この PR で直す | 主の回答リンクを PR コメントに記録する → **`needs-approval` を外す** → 未処理の順 6 の指摘が残っていれば failed にせず Status `needs-decider` で return する（裁定のあとにまとめて 1 回の failed で戻す）→ 残っていなければ `agent-review:failed` に付け替えて修正サイクルへ戻す（2周目以降なら次の周に入る。その周の終わりにも仕分け表を適用する） |

- 動作確認代行の場合、3点セットの3点目（自力検証できるようにする改善提案）は**復帰時に着手または issue 化まで進める**。出しただけで放置しない。
- **`needs-approval` を黙って持ち越さない。** 上の表のどの経路を通っても、その時点で
  「保留理由が解消したか」を必ず判断し、**外す / 付けたままにする のどちらかを明示的に選ぶ**。
  判断を書かずに次の工程へ進むことを禁じる（放置すると、合格しても auto-merge されないスタック PR になる）。

## 主に承認を求めてよい4分類（これ以外は設計違反）

| # | 分類 | 具体 |
|---|---|---|
| 1 | リスク許容の確認 | 手順3。実装中に発覚したものも発覚時点で確認する。手順2-1の仕分け表の順 5（この欠陥を残して切り出すか。推奨と見積もり付き）もここに入る |
| 2 | 動作確認の代行 | 手順4。自力検証不能時のみ・3点セット必須 |
| 3 | 好み・事業判断 | 答えがコードにも市場にも無く主の中にしかないもの（コピー・デザイン方向・価格） |
| 4 | 主名義の操作と聖域 | 外部アカウント・支払い・allowlist、マージ条件自体・憲法の変更 |

**やらないこと**:
- 「念のため確認」「マージしていいですか」「この方針で進めていいですか」——4分類のどれでもない確認を主に出さない。調べれば決まることは調べて決める。
- 選択肢を並べて主に判断を丸投げしない。推奨を出し、残リスクの許容だけを問う。
- リスク宣言を書かずに `agent-review:passed` を付けない。宣言の投稿と合格ラベルの順序を入れ替えない。
- 主の回答を待たずに保留 PR をマージしない。
