# 保留で止まるときの引き継ぎ（develop）

develop の SKILL.md から移した節。読むのは、本体が主の返事を待って止まる前のうち、引き継ぎを書く 4 つの場面（pr-review-gate の保留・SKILL.md の「PR トークン上限」の exit 2・レビューの 2 周キャップ超え・仕様レビューの条件の問い）と、記録先に `引き継ぎ: 主の返事待ち` のコメントがある保留中の記録先を再開するとき（`/develop` の入口で見つかったときと、channel で `#<番号>` を添えた返事を受けたときを含む）。パスの書き方は SKILL.md と同じ。

## 保留で止まるときの引き継ぎ（主の返事を待つ前に書く）

本体が `needs-approval` を付けて主の返事を待つと、1 時間以上あいてから同じ会話を再開したときに会話全体のキャッシュを書き直す代金がかかる（#515）。これを避けるため、止まる前に記録先へ引き継ぎのコメントを 1 種類の書式で残し、主には新しいセッションで再開するよう案内する（channel では新しいセッションを案内せず、チャンネルの返事で再開する。下の「channel の主への案内」）。場面は pr-review-gate の保留（リスク許容・動作確認・切り出しの確認）・SKILL.md の「PR トークン上限」の exit 2・レビューの 2 周キャップ超え（仕様レビューで、直し方の判定が「選び直しが要る」とされたとき）・仕様レビューの条件の問い（`条件の問い:` を主に聞くとき）の 4 つで、場面ごとに別の書式を作らない。

**投稿の順序**: ①主への依頼のコメントを投稿して URL を得る。置き場は対象の PR があれば PR、無ければ記録先（`stages/hold.md` 手順 6 は依頼を PR に投稿するので、記録先が issue でも PR のコメントの URL でよい）。G の保留では G が投稿した依頼コメントを使い、無ければ本体が投稿する。exit 2 と 2 周キャップ超えと条件の問いは本体が問いを書く。②その URL を書いた引き継ぎを記録先に投稿する。③主に案内する。依頼より前に引き継ぎを投稿しない。

**依頼の出し直し**: 保留の依頼を主に出したあと、同じ保留についてゲート担当の終了通知や報告の再送が届いても、新しい情報が無ければ主への依頼を書き直さない。主に返すのは「変化なし」の 1 行まで。新しい情報があって出し直すときは、依頼の全文（`~/.claude/output-styles/readable.md` の節 3 の型の全文とリンク）を省略せずに書き、前のメッセージを指さない（主は前のメッセージを読み返さずにこの 1 通だけで判断できる状態にする）。
- 新しい情報とみなす例: PR の HEAD が動いた／ゲートの判定や保留の理由が変わった／主が判断するときに効く事実（リスクの中身・CI の結果・動作確認の結果）が増えた・変わった／保留の種類が変わった。
- 新しい情報とみなさない例: 同じゲート担当からの同じ内容の終了通知や報告の再送／「状況は変わっていません」と書かれた報告／文面だけが違い、判定・理由・事実が前と同じもの。

**書式**: 1 行目は `^引き継ぎ: 主の返事待ち$` に完全一致（太字・全角コロン・末尾句点を付けない）。2 行目以降に次の項目を `項目名: 値` で 1 行ずつ書く。

| 項目 | 中身 |
|---|---|
| 待ち理由 | `リスク許容` / `動作確認` / `切り出しの確認` / `PR トークン上限` / `2 周キャップ超え` / `条件の問い` のどれか |
| 主への依頼 | ①の依頼コメントの URL（PR のコメントでもよい） |
| 対象 | PR 番号（まだ無ければ `なし`）・HEAD の 40 桁 SHA・ブランチ・worktree のパス |
| ラベルの付け先 | `needs-approval` を付けた先。PR があれば `PR #N`、無ければ記録先（`issue #N`） |
| 実行モード | interactive / channel / unmanned |
| 実行先 | 実行先オプションと account-home の対応（明示したときだけ。無ければ `自動選択`）と、開始済みの phase の選択結果のコメント URL。最初の phase は develop 開始コメント、以降は dispatch 記録。両方書く（無ければ `なし`） |
| 次に起こす役割 | 返事のあとに最初に起こす役割と、渡す入力の在り処。役割が W なら起動指示に書く `段:` の値も（`段: spec` / `段: implement` / `段: finish`）。R1（当て直し）なら残った BLOCKER を載せた結果コメントの URL も |
| 周回 | 仕様レビューと G の周回の数・W の修正の周回の数 |
| 前任 W | 直近の return の 1 行目と要約または URL、手渡し可否（次の段落）。W を起こしていなければ `なし` |
| PR トークン上限 | 最新の値と、止まった時点の合計 |
| 回し方 | エピックの子のときだけ。それ以外は `なし` |

W の名前は書かない（新しいセッションでは SendMessage できない）。再び止まるときは新しいコメントを投稿し、最新の 1 件を正とする。

**前任 W の手渡し可否**: 新しいセッションから前任に停止を指示できないので、引き継ぎを書く前に本体が `references/decision-criteria.md`「コンテキスト上限（サブエージェントの手渡し）」の「手渡しの許可」を満たす。前任の直近の return の 1 行目が `工程完了:` なら満たしている。`工程中断:` なら前任に停止を指示して停止確認を受け取り、未コミット差分があれば本体が commit してから書く。満たしたら `手渡し: 可（工程完了 | 停止確認済み）` と確認結果（編集ファイル・commit の SHA）を書く。満たせないとき（exit 2 で SendMessage を送れない・停止確認が返らない）は `手渡し: 不可（理由）`、W を起こしていなければ `手渡し: 不要` と書く。

**主への案内**: 依頼の最後の答え方の行（1 行目と最後の行の書き分けは `~/.claude/output-styles/readable.md` の節 3）に「返事は新しいセッションで `/develop <記録先>` と一緒に渡す。1 時間以内に返事ができるなら、このセッションで続けてもよい」と書く。リスク許容なら「このセッションの会話で返すか、新しいセッションで `/develop <記録先> 許容する` と打てばよく、PR へのコメントは要らない」と添える。返事がいつ来るかは本体が知らないので引き継ぎは必ず残し、どちらで続けるかは主が決める。この案内は interactive のもの。

**channel の主への案内**: 引き継ぎは同じ書式で `実行モード: channel` として残し、案内は「このチャンネルで記録先の番号を添えて返事をすれば続ける（例: `#<記録先> 許容する`）」にしてチャンネルに送る（この案内は依頼の最後の答え方の行に書く。1 行目と最後の行は`references/channel.md` の「channel の主への発言」に従う）。新しいセッションを開く案内と `/develop <記録先> 許容する` の案内は出さない（オーナーは住人の新しいセッションを開けない）。リスク許容の案内は`references/channel.md` の「channel のリスク許容」に従う（`チャンネルの返事の確認: 不可` なら PR のコメントを案内する）。返事が同じセッションに届いたらそのセッションで続ける（1 時間以上あいてからのキャッシュの書き直しの代金は、住人には別のセッションで返事を渡す経路が無いので受け入れる）。セッションが入れ替わっていたら、返事を受けたセッションが次の「新しいセッションでの再開」の手順で続ける。番号の無い返事は、このセッションが関わった開いている引き継ぎ（`needs-approval` のある記録先）が 1 件ならそれへの返事として扱い、0 件か 2 件以上なら、記録先の番号を添えて返すようチャンネルで聞き直す。

**会話で受けた返事の日時の取り方**: 主の返事（リスク許容など）を会話で受けて G に渡すときは、その発言の日時（会話ログの timestamp）を自分で作らず、本体が先に `owner-reply-check.sh` を回して取る（呼び方は pr-review-gate 手順 5）。MATCH: 行の timestamp をそのまま使う。MATCH: が複数出たら、いま受けた返事の行（全文が返事と同じで timestamp がいちばん新しい行。出力は時刻順とは限らない）の timestamp を使う。どの行もいま受けた返事でなければ、MATCH: が出ないときと同じに扱う。MATCH: が出なければ時刻を作らない。終了コード 1 なら原文を主の発言どおりに写し直して回し直し、それでも出ないとき、および終了コード 2（確かめられない。写し直しても直らない）のときは、pr-review-gate 手順 5 の終了コード 1・2 の扱いどおり主に受け直しを頼む（1 は手順6に戻して主に再確認、2 は PR のコメントか、ゲートと同じ PC での `/develop <記録先> 許容する`）。

### 新しいセッションでの再開

記録先に `引き継ぎ: 主の返事待ち` のコメントがあれば、`needs-approval` の有無によらずこの手順で始める（`commands/develop.md` の入口も同じ条件）。

channel で、`#<番号>` を添えたチャンネルの返事を受けたセッションが develop を読み込んでいない（再起動などでセッションが入れ替わった）ときは、develop を記録先 `<番号>` で起動して本体になり、その記録先に `引き継ぎ: 主の返事待ち` があることを確かめてからこの手順で続ける（返事を受けて develop を起動するきっかけは、チャンネルを運用するリポジトリの CLAUDE.md などに置く）。モードは決め直さず、引き継ぎの `実行モード` の値を使う。

1. 記録先の最新の引き継ぎのコメントを読む。
2. そのコメントより後の主の回答（記録先または対象 PR のコメント、または `/develop` の引数の残り）を探して使う。`/develop` の引数の残り（`許容する` など）は会話で受けた回答として扱い、このセッションのセッション ID（`$CLAUDE_CODE_SESSION_ID`）・その発言の日時（会話ログの timestamp。取り方は上の「会話で受けた返事の日時の取り方」）・原文を保留の解除の G に渡す（主に PR へのコメントを求めない）。引き継ぎの `実行モード` が `channel` のときは、このセッションが受けた `#<記録先>` を添えたチャンネルの返事（番号の無い返事は「channel の主への案内」の扱い）を `/develop` の引数の残りの代わりの回答として扱う。リスク許容の返事を G に渡すときは、セッション ID と、このセッションの会話ログでその返事の行（`<channel source=` で始まる、主の発言として数えられる行）の、開きタグと閉じタグを外した中身（`owner-reply-check.sh` の `MATCH:` 行に出る本文と同じもの。タグごと渡すと照合が一致せず、PR の宣言に user_id 入りのタグが写る）を原文とし、その行の timestamp とあわせて渡し、本体が要約・書き直した文やチャンネルのメッセージの別の表示から取らない（確かめ方と `チャンネルの返事の確認: 不可` のときの扱いは`references/channel.md` の「channel のリスク許容」）。無ければ、引き継ぎの「主への依頼」を主に見せ直して返事を聞き、返事が来るまで役割を起こさない。
3. 引き継ぎの「ラベルの付け先」に `needs-approval` があることと、PR の HEAD が引き継ぎの HEAD と同じことを確かめる（ラベルは記録先ではなくこの項目の指す先で見る）。ラベルが無ければ保留は解かれているので、記録先のコメントから今の状態を組み立て直して主に報告する。HEAD が動いていれば差分を主に報告し、続けるかを聞く（channel ではこの報告と問いをチャンネルに送る。1 行目は質問にし、最後の答え方の行にこのチャンネルで何を返すかを書く。`references/channel.md` の「channel の主への発言」に従う）。
4. 次に起こす役割が R1（当て直し）なら、また待ち理由が `2 周キャップ超え` で手順 2 の答えが条件についての答えのときも、手順 2 の答えを `references/fix-check.md` の節「残った指摘の条件を確かめる」どおり `## 条件の答え` に足し、ラベルの付け先から `needs-approval` を外し、先に R1 を起こし、W はその結果に従って起こす（`APPROVE` なら `段: implement`、BLOCKER が残れば同じ節の「判定に回す指摘」どおりで、W を起こすなら `段: spec`）。W は SendMessage しない。「前任 W」が `手渡し: 可` なら手渡し（前任の return と記録先を渡して新しい W を起こす）、`手渡し: 不要` なら「次に起こす役割」の入力で初回の W を起こす。どちらも起動指示の `段:` の行は「次に起こす役割」に書かれた値を使う（R1 のあとに起こす W は上の値を使う）。`手渡し: 不可` なら W を起こさず、理由を主に報告して指示を聞く（channel ではチャンネルに送る）。G は従来どおり段ごとに新しく起こす。
5. 実行先: 明示の実行先オプションが引き継ぎにあれば再推測せずそのまま使う。自動選択では、次に起こす役割の phase の選択結果が引き継ぎの「実行先」の指すコメント（develop 開始コメントか dispatch 記録）にあればその構成・executor・account・model を続け、選び直さない。どちらにも無い（未開始の）phase だけ、開始時に adapter で自動選択を評価する。
6. SKILL.md の「PR トークン上限」の計測の `--cap` には、記録先の最新の `PR トークン上限:` コメントの値を使う。
7. 前任の G や W を立て直す前に生存を確認する。このセッションが起こした担当は `ListAgents` で確かめる。前のセッションの担当はこのセッションの `ListAgents` には出ず、生きているかを確かめることも止めることもできない（参照できないことは、止まっていることを意味しない）ので、確認は pr-review-gate の `stages/prepare.md` 手順 1 の冒頭の重複チェックに任せる。前提確認の G が `重複で降りた` を返したら（同じ HEAD に前のセッションの担当が着手済みの印）、取り直さず `roles/gate-runner.md` の段の表どおり主に報告する。

**守備範囲**: 読む入力は記録先のコメント・主の返事（記録先または対象 PR のコメントか `/develop` の引数）・ラベル・PR の HEAD で、出どころは GitHub の記録先と PR と、`/develop` の引数を打ったこのセッションの会話と、引き継ぎの `実行モード` が `channel` のときのチャンネルの返事（このセッションの会話に届いた主の発言）だけ。拾いたい誤りは、引き継ぎが最新でないまま読むこと・返事が無いまま役割を起こすこと・保留が解かれているのに進めること・HEAD が動いているのに気づかず続けること・手渡し不可の前任に代えて W を起こすことの 5 つ。通してよい入力は、項目の並び順が違うコメント・値の前後の空白・返事が引数でなく記録先か PR のコメントで来たもの・channel の返事がチャンネルで来たもの・HEAD が引き継ぎと同じ PR。守らないのは、引き継ぎの値（周回の数・要約）の事実確認と、主の返事の真正性（pr-review-gate 手順 5 が正本）。この 5 つ以外の不備を見つけるたびに検査を足し続けることを、完了条件にしない。前のセッションの会話・名前付き W への SendMessage・引き継ぎに無い実行先の推測に頼らない。

## CI 見張りの修正担当の引き継ぎ

通常経路では、本体が CI 見張りを始める前と修正後の待ちへ戻る前に、PR コメントへ次の書式で新しい引き継ぎを投稿する。「修正後の待ちへ戻る前」は、今回の W が無関係と判断して push せず工程完了を返した後の `next --unrelated <チェック名> --after-fix` 前も含む。next の前に今回の工程完了を根拠とする新しい手渡し可を投稿する。主の返事待ちの書式とは別であり、同じ見張りの開始／終了を増やさず、同じ PR・状態ファイルを使い、修正回数をリセットしない。

1 行目は `引き継ぎ: CI 見張りの修正担当` に完全一致させ、以下を `項目名: 値` で残す。

| 項目 | 中身 |
|---|---|
| 記録先 | issue または Draft PR の URL。最新の仕様化判断と、仕様化した場合の R1 APPROVE を読む先 |
| 対象 | PR 番号・HEAD の 40 桁 SHA・ブランチ・worktree パス |
| 前任 W | 直近の return 全文または全文を読める記録の URL（成果・残作業・読んだコードの要点を含む）。手渡し可否とその根拠、編集ファイル・commit SHA |
| 実行モード | interactive / channel / unmanned |
| 実行先 | 明示オプションと account-home の対応または自動選択、および開始済み phase の選択結果の記録 URL（無ければ `なし`）。上の「新しいセッションでの再開」手順 5 の継続規則を使う |
| 周回 | 仕様レビュー・G・W の修正の周回 |
| PR トークン上限 | 最新の上限と記録時点の合計。再開時の計測は記録先の最新の `PR トークン上限:` を使う |

W の名前は書かない。手渡し許可の正本は `references/decision-criteria.md`「コンテキスト上限（サブエージェントの手渡し）」。直近 return の 1 行目が `工程完了: <工程名>` に完全一致するか、停止指示に対する停止確認（編集・投稿内容の報告）がある場合だけ `手渡し: 可（工程完了 | 停止確認済み）` と根拠を記録する。確認できなければ `手渡し: 不可（理由）` とし、参照不能を停止済みとは扱わない。未コミット差分があれば工程完了または停止確認後に本体が commit してから記録する。

### 起動／再開前の無効化と再許可

CI 用引き継ぎが最新の可である間に W を起動・再開するとき（CI fix とゲート failed の直しを含む）は、次の順序を守る。

1. decision-criteria.md の再開／手渡しの許可条件を確認し、確認した成果と許可根拠を今回の依頼入力として保持する。
2. 起動／再開前に、上の 1 行目と必要項目を継承した新しい引き継ぎを PR に投稿する。値は `手渡し: 不可（W を起動／再開するため、今回の工程完了または停止確認待ち）` とする。投稿成功を確認してから起動／再開を指示する。投稿失敗なら起動／再開せず、下の停止先へ報告する。
3. 可へ戻せるのは、今回起動／再開した W の `工程完了: <工程名>` の return、またはその W への停止指示に対する停止確認を受け取ったあとだけ。今回の成果・編集ファイル・commit SHA と完了 return または編集・投稿内容を含む停止確認を根拠に、新しい手渡し可の引き継ぎを投稿する。差分があれば本体が commit してから記録する。以前の完了／停止確認や push・idle、オーナーの続行指示だけでは可へ戻さず、今回の完了／停止確認が無ければ不可のままにする。

既存 W の再開後も新しい W の起動後も、HEAD・作業ツリーがまだ変わらない間に本体が交代し、2 の中断済み fix に戻る場合がある。HEAD 一致・差分なしでも最新の不可が有効であり、古い可へ遡らない。以前の完了／停止確認から二人目の W を起こさない。今回の完了または停止確認に基づく新しい可を待つ。この順序は既存の見張り重複判定に代わるロックではない。

### W を把握しない本体の読取りと停止先

1. `gh api --paginate repos/<owner/repo>/issues/<PR番号>/comments` で PR コメントを全ページ読み、上の 1 行目に一致する最新の 1 件だけを使う。古い可へ遡らない。記録先の最新の仕様化判断を取り直し、通常経路であることを確認する（軽い経路なら decision-criteria.md の新規 spec 起動へ）。
2. 全項目、前任 return の全文、手渡し可の根拠を読む。現在の PR とローカルの `git status` / `git diff` で PR・HEAD・ブランチ・worktree の一致と差分なしを確かめる。
3. 揃っている場合だけ、上の順序で可を無効化してから、新しい W に `段: implement`、前任 return、PR・記録先、失敗したチェック・run を含む fix の観測、`ci-watch.md 7` の直し方を渡す。実行モード・実行先・周回・上限を継承する。W は git status / git diff と既存判断・必要な R1 APPROVE を実装前に確認する。CI fix だけを理由に spec へ戻したり判断を再投稿したりしない。存在しない W の再開や本体の直接修正はしない。
4. 引き継ぎ無し・必要項目不足・return 参照不能・工程中断で停止確認無し・手渡し不可や根拠不明・対象不一致・未コミット差分のどれかなら、W を起こさず、本体も直接修正・push もせず停止する。差分を戻して対象を合わせることもしない。起動前の投稿失敗も同じ停止先とする。PR に `needs-approval` を付け、不足情報・PR/HEAD・fix の観測を記録し、`ci-watch.md` 6 の `escalate` と同じく `CI 見張り終了:` を投稿して報告する。通常はオーナーへ、エピックの子は `references/epic-child-stop.md` に従って親への停止報告へ進む。オーナーや親の続行指示、経過時間を工程完了／停止確認の代わりにしない。

**守備範囲**: 入力元は GitHub の PR/記録先のコメント（return・工程完了／停止確認の報告を含む）、現在の PR とローカルの作業ツリー、fix の観測。拾う誤りは必要項目・読める return・今回の許可根拠の欠落、対象不一致、未コミット差分、最新の不可を無視した起動、起動／再開前の無効化漏れ。最新記録に必要項目と今回の完了／停止確認が揃い対象も一致するが、編集ファイルや成果の説明が事実と違う入力は通ることを許す。記録内容の真正性、実エージェントの読解ミス、既存の見張り重複判定が許す穴を全て塞ぐことは完了条件にしない。関係 Bats でこの接続を確かめ、エージェントの実起動は完了条件にしない。
