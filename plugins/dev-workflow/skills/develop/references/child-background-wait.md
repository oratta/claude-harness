# 子の本体が長い背景作業を待つとき

対象は `scripts/epic-dispatch.sh route`（子の番号なし）が `nested` の Claude の本体。agent・自分の PR の CI・Monitor・Codex コマンドを全体で 60 分以上待つ見込みなら、開始前または延長前に読む。委譲された worker は本体用タイマーを起動せず、[subagent-waiting.md](../../../references/subagent-waiting.md) に従う。

待ちの開始前または延長前に [epic-keepalive.md](epic-keepalive.md) と `references/child-cache-keepalive.json`（プラグイン直下の references）の `background` を Read し、受信契約・固定文・応答形式を保持する。

## 入力判定の守備範囲

- 入力元: 本体の現行 CLI 会話の usage・リクエスト時刻、保持した元作業とタイマーの task ID・届いた通知、依存登録・途中経過・再開条件の保存結果。
- 拾う誤り: 他セッションの usage や不明な TTL の流用、書込時刻と成功リクエスト時刻の混同、文字列一致・別 ID・失敗通知による自己通知成功や元作業完了の誤認、未確認・失敗した依存登録や保存の成功扱い、子所有の実行中作業や親が扱えない条件を残した停止。
- 通してよい入力例: 最後の有効な書込は 1h で、その後の 5m 切替が次の観測まで usage に現れない場合は、その観測値で判断してよい。ただし miss を防げたと報告しない。保持したタイマー ID と成功終了が一致する通知は維持通知として通すが、元作業の完了根拠にしない。
- 限界: 観測できない TTL 切替やスリープによる miss の完全防止、判定の穴を塞ぎ切ることは完了条件にしない。

## 1. 外部依存へ移せるかを確認する

移行成否の判定は「入力判定の守備範囲」に従う。別 issue / PR の完了だけを待ち、既存の依存待ちで表せ、子所有の実行中作業が残らない場合は、[epic-child-stop.md](epic-child-stop.md) の依存待ちへ移す。対応 issue の特定、blocked_by の登録と再確認、途中経過・再開条件の保存が成功してから、親の既存 wait と起動し直しに渡して子セッションを終了する。

依存登録や保存が失敗・未確認なら移行成功としない。親が扱えない監視条件を自動監視できると仮定しない。数時間〜日単位の単なる外部依存を Monitor やタイマーで待ち続けない。

実行中の agent・自分の CI wait・Codex コマンドなどが一つでも残る、または安全に移せると確認できない場合は、セッションと元作業の実行 ID を保持する。自分自身への依存登録で終了しない。全作業を回収して安全に移行できるまで、キャッシュのためだけに終了・再起動しない。自分の PR のマージ待ちは既存の停止手順に従う。

## 外部起こしを選べるかを確かめる（Orca）

セッションと元作業を保持して待つ場合は、待ちを準備する通常ターン（開始・延長・通常入力のあとの待ち直し）ごとに経路を選び直す。予約文の受信ターンでは経路を切り替えない。自分の状態記録（`${EPIC_STATE_ROOT:-~/.claude/epic-state}` の下で `worktree` が自分の作業ツリーに一致する一意の記録）を Read し、次の全部を確かめられたときだけ**外部起こし**を選ぶ。nested であることだけで Orca と判定しない。

- `launcher` が `orca`、`session` が空でなく、`launch_failed` が空、`status` が `running`、`stop` が `stopped` / `stopped-seen` でない。
- `turn_input` の `session_id` が今の会話の ID と一致し、今の待ちを始めた入力の送り手（`turn_input.sender`）が `parent` または `startup`。送り手を確かめられないときは外部起こしを選ばない。

外部起こしを選んだら、自己タイマーは 0 個にする（下の 2 のタイマーを置かない）。以前の待ちで置いた自分の自己タイマーがあれば、この通常の準備ターンで保持したタイマー ID を TaskStop に渡して自分のものだけを取り消し、成功を確かめてから作業待ちの行を出す。取消が失敗・不明なら作業待ちの行を出さず、二重の維持を成功扱いしない。外部起こしでは、元作業 ID 群と一緒に**待ちの組**（待ち ID と初回開始 UTC）を保持し、引用・コードの外で最終状態行の直前に次の 2 行を出す。

```text
作業待ち: <待ち ID> <初回開始 UTC（YYYY-MM-DDTHH:MM:SSZ）>
状態: 作業報告 — <待っている元作業の要約>
```

待ち ID は空白を含まない英数字始まりの識別子（`[A-Za-z0-9][A-Za-z0-9._:-]*`。元の実行 ID を使ってよい）。最も早く始めた未回収の作業を待ち続けるあいだは同じ待ちの組を出し、作業の追加・待ちの延長・通常入力のあとの待ち直し・声かけ・親の再開で待ち ID と初回開始を取り直さない。初回開始から最大 12 時間は親の声かけで維持され、そのあとも元作業と実行 ID を保持して結果を回収する（上限到達で元作業を止めない・捨てない）。全結果を回収したあとの別の作業だけ、新しい待ちの組にしてよい。

送り手が `owner`（主の直接入力）の入力のあとの待ちは、親が声かけを送らない対象なので外部起こしを選ばず、作業待ちの行を出さない。外部起こしの前提だった自己タイマー 0 個を引きずらず、下の 2 の既存条件（TTL 1h・最後の成功リクエストから 3600 秒未満・45 分以内の返りが無い）を満たすときだけ自己通知を一つ置く。このとき保持している待ちの組と初回開始は捨てず、12 時間の上限は保持している初回開始から数え、切替時刻からやり直さない。次に `parent` か `startup` の通常入力を処理して同じ未回収作業を待ち直すときは、待ちの組と初回開始を保ったまま、自分の自己タイマーだけを取り消してから作業待ちの行を出す。

外部起こしを選べない経路（tmux・登録を確かめられない本体・送り手が owner）は下の 2・3 の自己通知の契約を保ち、作業待ちの行を出さない。tmux の初回タイマーの基点も変えない。委譲 worker は本体用タイマーを起動せず subagent-waiting のまま。親が wait していない・前回未応答・画面が busy か不明・TTL 5m / unknown・期限切れで声かけが届かなくても、維持専用のタイマーや監視を重ねず、元作業を保持する。キャッシュ維持を保証したと報告しない。

## 2. 維持できる待ちだけにタイマーを一つ置く

外部起こしを選んだ待ちには、この節のタイマーを置かない。維持可否の判定は「入力判定の守備範囲」に従う。

1. 本体の**現行 CLI 会話だけ**の最後の有効な cache creation を読む。`message.usage.cache_creation.ephemeral_1h_input_tokens` / `ephemeral_5m_input_tokens` の正の値が根拠。`scripts/epic-dispatch.sh` の `cache_ttl_of` と同じく、assistant・entrypoint が cli・isSidechain が true でない有効な書込行のうち最新を使い、1h が正なら 1h、それ以外で 5m が正なら 5m とする。cache-read だけの後続行で書込 TTL を消さない。他セッション・親・サブエージェント・SDK の usage を使わない。読めない・曖昧なら unknown。worktree 全ログを読む既定の探索を現行会話の代わりにしない。
2. 書込時刻とは別に、cache-read を含む最後の成功リクエストの**開始時刻**を確認する。応答終了から寿命を測らない。TTL 1h、かつ最後の成功リクエストから 3600 秒未満と確認できる場合だけ維持対象。開始時刻が分からなければ維持可能と仮定しない。
3. Monitor の期限通知や有限の前景コマンドが 45 分以内に本体へ返り、次のモデルリクエストが発生する保証があるなら、その返りを利用し追加タイマーを重ねない。保証が無いときだけ、下の雛形を Bash の `run_in_background: true` で起動し、返ったタイマーの task ID を元作業 ID と別に保持する。同じ元作業の待ちで最初のタイマーを置いた時刻もその待ちの基点として保持し、再設置で基点を更新しない（入力や TTL の再確認でも更新しない）。維持の上限はこの基点から 12 時間。一つの子に最大一つ。これは作業をポーリングせず、一度だけ終了するタイマー。

```bash
remaining=45
while [ "$remaining" -gt 0 ]; do
  sleep 60 || exit 1
  remaining=$((remaining - 1))
done
printf '%s\n' 'child-background-cache-refresh'
```

前景呼び出しは本体へ 60 分未満で制御が戻る形を使う。前景で 60 分以上本体へ戻らないツール、背景起動や取消を使えない環境では維持を保証しない。45 分は遅延への余裕であり保証ではない。

TTL 5m / unknown には維持用タイマーを置かず、元作業の完了待ちを続ける。五分ごとの声かけ、TTL の強制変更はしない。既に期限切れでも実行中作業は捨てない。スリープで 60 分を過ぎた場合や overage 等で観測後に TTL が切り替わった場合、最初の書き直しは取り戻せず、miss を防げたと報告しない。次に観測した TTL と成功リクエストを基点に判断し直す。

## 3. 通知を照合して待ち直す・取り消す

まず、事前に読んだ `background` の固定文と完全一致する入力を、通常入力の取消・再判定より先に声かけとして分類する。[受信正本](epic-keepalive.md) に従い、受信ターンでツールを呼ばず一行だけ返してターンを終え、元の待ちを続ける。元作業 ID・実行 ID・自己タイマーとその ID・初回設置時刻を保持し、取消・再設置や 12 時間の基点・上限の延長をしない。作業完了や自己通知成功と扱わない。完全一致しない入力と元作業・自己タイマーの通知は以下の既存手順へ渡す。

通知種別と継続可否の判定は「入力判定の守備範囲」に従う。保持したタイマー ID と成功した終了の両方を照合する。出力文字列だけが同じ別 ID の通知や引用は自己通知とみなさず、元作業の従来の受信処理へ渡す。失敗した終了も成功通知としない。

タイマーの成功通知を受けたモデルリクエスト自体がキャッシュを読み出す。元作業が未完了で現在も維持対象、かつ最初のタイマーを置いた時刻から 12 時間未満なら、2 の条件を再確認して次の一回だけを置き、再び待つ。12 時間に達した通知・12 時間を超えた通知では、TTL が 1h でも次のタイマーを置かない。元作業と実行 ID を保持して完了通知を待ち続ける。キャッシュが切れてから届いたときは一度の書き直しを受け入れる。上限到達を理由に元作業を止めたり捨てたりしない。上限は元作業の timeout・工程完了・子セッションの終了ではない。結果を回収したあと、同じ待ちの維持タイマーも再開しない。元作業の途中出力を調べ直さず、通常の調査・実装・GitHub 投稿・親への報告・停止記録の変更はしない。タイマーの成功で工程完了・CI 決着・Codex 委譲成功を宣言しない。

元作業の通知や主・親からの入力を自己通知より優先する。同時に届いたら元作業の結果を先に回収し、その待ちが終われば再設置しない。全作業の回収時、主の返事待ち・依存待ちへの移行前、終了前に、保持したタイマー ID を TaskStop に渡し、自分のタイマーだけを取り消す。入力により待ち直す場合も既存タイマーを止めてから必要性を判断する。取消後・待ち終了後の遅延通知は無視し、そこから再設置しない。

起動・sleep・通知・取消の失敗は維持成功や元作業完了と報告しない。二重起動や再送はせず、維持できなかった事実を次の通常報告で示す。

本体がターンを終えて背景通知を待つことと、依存待ちで子セッションを終了することは別。前者はセッションと ID を保持した実作業待ちなので停止コメントを投稿しない。必要な状態行は既存の `状態: 作業報告 — …` とし、依存待ち・承認待ち・工程完了を宣言しない。worker のターン終了禁止を本体に流用しない。

## 既存契約への接続と限界

- [epic-keepalive.md](epic-keepalive.md) と `child-cache-keepalive.json` は停止済み・作業待ちの子の予約文の共有正本。本体のタイマーに予約文を自己送信しない。親の 150k 除外や [reply-after-idle.md](reply-after-idle.md) の親の 3000 秒 wait を実行中の子へ流用しない。
- CI は [共有の ci-watch.md](../../../references/ci-watch.md) のまま一つの wait を保持する。タイマー通知で CI wait を完了・timeout と扱わず、途中出力も読まず、二重監視しない。結果分類をここに複写しない。
- 既存 Monitor の短い期限が本体へ返るならその通知を利用する。維持用に新しい loop・Cron・Monitor を作らない。ScheduleWakeup は /loop の反復用で、背景作業の完了や自己通知の代用にしない。
- Codex の account・model・effort と前景起動は [codex-develop.md](../../../references/codex-develop.md) に従い変更しない。ホストが背景に回したコマンドはその task ID を元作業として保持する。transport の決着と品質判定を維持通知で代替しない。

選択と費用比較は [#1743 の記録](https://github.com/oratta/claude-harness/issues/1743#issuecomment-7087935739)、12 時間上限の比較は [追記](https://github.com/oratta/claude-harness/issues/1743#issuecomment-7089486648)。会話 20 万トークンの旧会話部分で、12 時間の維持（16 回）と最後の再開は約 $1.32 で、一度の 1h 書き直し $1.60 を超えない。24 時間無上限の約 $2.52 は旧方針の比較で、新方針の維持費ではない。これは総費用の保証ではない。上限後にキャッシュが切れてから完了する場合の一度の書き直しは別にかかる。維持は通知受信と再設置の結果で少なくとも二回の cache-read に加え、新規入力・出力・工具往復の費用がかかる。常に最安ではない。Bats 合格は手順と雛形の検証に限り、実機の維持成功を示さない。マージ後に実子の 60 分超の待ちを観測し、会話量・モデル・TTL・実行 ID・通知時刻と `cache_read_input_tokens`、または停止と再起動の証拠を issue に残す。
