# 軽い通し方（本体だけが読む）

仕様化判断（Step B）で「仕様化しない」になる変更のうち、本体が W を起こさずに直す通し方と、G の failed や CI 見張りの fix から通常の通し方へ戻す手順。本体だけが読む。仕様化判断と分割判定の基準は `references/spec-decision.md`、記録の行の書式は `references/roles/spec-reviewer.md`「判断記録の契約」。

## 仕様化しないが軽く通す（軽い通し方）

**当てる条件**: 「仕様化しない」のうち、typo・lint・コメント・フォーマット・ワンライナー fix・設定値のどれか 1 つだけでできていて、既存のテストかチェックのコマンドで確かめられる変更。本体が W を起こす前に記録先の本文から判断する。

- typo・lint・コメント・フォーマット・設定値の 5 種類は、プログラムの挙動を変えないこと（設定値も値を変えて挙動が変わらないものだけ）。
- ワンライナー fix は明白なバグの 1 ファイルの 1 行（追加 1 行以下・削除 1 行以下）の修正で、直し方に選択肢がないこと。挙動が変わることを条件外の理由にしない。変更の記録（`changes/<数字>.md`）は数えない。
- 内部リファクタ・依存の版上げ・受け入れ条件が明記された機械的な振る舞い変更には当てない。ワンライナー fix 以外の種類にファイル数・行数の上限は足さない。

**省くもの**: 新しいテストと W の起動。本体が直接直す。**残すもの**: 記録先・判断の記録・pr-review-gate（レビュー重量の判定も今どおり）。

記録先がまだ無い会話の依頼では、依頼から受け入れ条件を整理し、その条件で当てるかを決める。順序は **整理 → 判定 → Draft PR → 判断の記録**。当てないなら Draft PR を作らずに W を `段: spec` で起こし、W が従来どおり記録先を用意する。迷ったら当てず、主に聞かない。interactive・channel・unmanned で同じ条件を使い、unmanned でも本体が Draft PR の作成と `agent-review:pending` の付与を行う。

本体は直す前に対象専用の worktree（1 issue = 1 worktree）に入る。無ければ `/wt-setup` で作り、元の checkout では編集しない。途中離脱・G の failed からの戻り経路の W も同じ worktree で起こす。

**本体の手順**（記録の行の書式は `references/roles/spec-reviewer.md`「判断記録の契約」）:

1. 記録先が無ければ、判定後に本体が Draft PR を作り、整理した受け入れ条件を本文に書く（`references/roles/worker/spec.md`「記録先の用意」と同じ手順・本文の決まり）。
2. 直す前に、記録先へ仕様化判断を投稿する。1 行目は `仕様化判断: しない`、理由に続けて `通し方: 軽い`・`種類: <6 種類のどれか>`・`確かめ方: <既存のテストかチェックのコマンド 1 つ>` を各 1 行で書く。
3. 本体が直す。変更の記録の決まりがあるリポでは記録も書く（claude-harness は `plugins/<name>/changes/<番号>.md`）。
4. `確かめ方:` のコマンドを走らせ、終了コード 0 を確かめる。
5. commit・push し、PR を Draft のまま用意する（issue が記録先なら `gh pr create --draft`、本文に `Closes #<issue>`）。unmanned では `agent-review:pending` を付ける。
6. PR コメントに `仕様: 変更なし — 理由: 軽い通し方（<種類>）。…` と仕様宣言を書く（`declarations.md` の「変更なし＋理由」形）。
7. interactive・channel では (4) の G を起こす。レビュー・宣言・合格処理は従来どおり行う。unmanned では G を起こさずサイクルを終える（SKILL.md「実行モード」）。

**途中で外れたとき**: 2 種類以上が要る・5 種類で挙動が変わる・ワンライナー fix が 1 ファイルの 1 行に収まらないか直し方に選択肢がある・既存のチェックが無い・コマンドが非 0 で終わると分かったら、手を止め、編集を commit してから W を `段: spec` で新しく起こし、外れた理由を渡す。W は `通し方:` の行の無い仕様化判断を投稿し直してテストを書く。同じ記録先に `通し方: 軽い` を投稿し直さない。

**G の failed からの戻し方**: `原因: 軽い通し方の条件外` ならモデルを上げず、W を `段: spec` で新しく起こし、G の確認コメントの URL を渡す。条件内を通ったあとの通常のレビューが修正を求める failed を返した場合も、本体は直さず W を再開せず、W を `段: spec` で新しく起こす（model は既存の原因分類で決める）。起動指示に failed の Gate Result と仕分けコメントの URL を渡す。どちらも W は `通し方:` の行の無い判断を投稿し直してテストを書き、同じ PR に積む。以後は通常の通し方とし、そのあとの G は failed の `次の段:` によらず前提確認と重さ判定から起こす。ただしレビュアー起動前の条件外の failed はレビューの周に数えず、本体は次の G を前の Gate Result を貼らずにゲートの開始として起こし、`周回: 1` の全体レビューにする（W の修正後の再レビューとして扱わない）。

**CI 見張りの fix からの戻し方**: G の passed 後の `fix` は、記録先の最新の仕様化判断と本体が把握している W の状態で次のように分ける。`ci-fail` と `conflict` は同じ分岐を使う。

- 最新の仕様化判断に `通し方: 軽い` があれば、本体は直接直さず、存在しない W を再開しない。同じ worktree に新しい W を `段: spec` で起こし、PR・記録先・fix の観測（状態と失敗したチェック・run などの修正材料）を渡す。起動指示に `plugins/dev-workflow/references/ci-watch.md`「7. 直し方」に従うこと（最初の push の前に手順 3 の passed 解除・Draft 化・pending 付与）と、`ci-fail` の関係確認を仕様化判断の再投稿より先に行うことを入れる。
  W は `ci-fail` では仕様化判断の手順に入る前に、共有手順「7. 直し方」手順 2 の失敗ログと PR 差分の関係確認を行う。同文書「5. `--unrelated` を渡す基準」で差分と無関係と判断できた場合は、仕様化判断を投稿し直さず、artifact 作成・修正・push をせずにチェック名と根拠を本体へ返す。最新の `通し方: 軽い` の判断を保持し、手順 3 の passed 解除・Draft 化・pending 付与にも進まない。本体は同じ PR・同じ状態ファイルで `next --unrelated <チェック名> --after-fix` を 1 回だけ実行し、その一手に従う。
  関係がある、または無関係と判断できない場合は、確認のあと、実装前に同じ記録先へ `通し方:` の行の無い仕様化判断を投稿し直す。「する」か「しない」かは W が決め直す。「する」なら artifact 一式と R1 の APPROVE を経て実装し、どちらの判断でもテストを書き、同じ PR に積む。以後は通常の通し方とし、同じ記録先に `通し方: 軽い` を投稿し直さない。`conflict` はこの無関係返却の対象とせず、従来どおり仕様化判断を投稿し直す。
- 通常経路の既存 W は `段: implement` で再開する。再開か手渡しかは `references/decision-criteria.md`「コンテキスト上限（サブエージェントの手渡し）」の許可条件に従う。CI の `fix` だけを理由に `段: spec` へ戻したり仕様化判断を投稿し直さない。軽い通し方から通常へ戻った後の再 fix もこの分岐であり、過去の軽い判断から新しい spec 段の W を重ねて起こさない。
- 通常判断で W を把握しない本体は、`references/handover.md`「CI 見張りの修正担当の引き継ぎ」の「W を把握しない本体の読取りと停止先」に従う。軽い経路から通常復帰後の再 fix も最新判断でこの分岐に入る。

通常経路の既存 W の再開と新しい W への手渡しの両方で、起動／再開の前後は `references/handover.md`「CI 見張りの修正担当の引き継ぎ」の「起動／再開前の無効化と再許可」に従う。

両経路の W は `plugins/dev-workflow/references/ci-watch.md`「7. 直し方」に従い、passed 解除・Draft 化・pending 付与を経て push する。本体は同じ PR・同じ状態ファイルを使う。軽い通し方から戻した W の仕様化途中の push では見張りに戻らず、通常経路の (1) → R1（仕様化する場合）→ (3a) → (3b) を進め、(3b) の return を受けてから `wait` → `next` を続ける。通常経路の既存 W は修正 push 後に `wait` → `next` を続け、`ready` 後に前提確認と重さ判定の G を新しく起こす。見張りの開始記録や修正回数はリセットしない。ログ確認で差分と無関係と判明した失敗は、共有手順どおり修正・push せず返す。

復帰判定の入力は fix の観測、記録先の最新判断、W の有無と再開・手渡しの可否。存在しない W の再開、本体の直接修正、軽い判断のままの implement 起動、通常復帰後の spec 再起動を拾う。見張りが fix と判定しても、W がログから無関係と判断して共有手順の `next --unrelated <チェック名> --after-fix` へ返すことを許す。軽い通し方から起きた新しい W では関係確認を通常判断の再投稿より前に行い、無関係な失敗で最新判断だけを通常化しない。接続を手順と関係テストで確かめることを完了条件とし、観測や W の判断の穴を塞ぎ切ることは完了条件にしない。

**守備範囲**: 入力は記録先の本文（記録先が無い会話の依頼では整理した受け入れ条件）と本体が直す差分。6 種類以外・複数種類・既存のチェック無し・直し方に選択肢がある修正への誤適用を拾う。本体は甘く読むことがある。`確かめ方:` が変更した箇所を通らない例や、明白と読んだが他の直し方もあった 1 行修正は通ることを許す（主が受け入れたリスク。レビュアーが差分と一緒に見る）。穴を塞ぎ切ることは完了条件にしない。
