# 仕様化判断と分割判定（develop スキル）

W が `段: spec` で読み、本体も読む。仕様化判断（Step B）と分割判定（Step C）の判定基準。W の手順（記録のコマンド・`openspec new change` の進め方）は `references/roles/worker/spec.md`、記録の行の書式は `references/roles/spec-reviewer.md`「判断記録の契約」。

**事前判定は仮決めにすぎない**。誤分類は昇格トリップワイヤー（`plugins/dev-workflow/templates/escalation-tripwires.md`）が実行中に修正するので、入口で精密に当てようとしない。

## Step B: 仕様化（opsx / openspec）するかどうか

**一次基準: 設計判断・トレードオフを含むか**。spec の本体価値は「意図と決定の記録」（なぜこう作ったか、何を捨てたか）であり、これはソースコードのどこにも残らない。一方「コンテキスト圧縮」（コードを読まずに把握する要約）としての価値は、モデルの探索能力で代替が利く。前者を含むものだけを spec 化する。

### 仕様化する（opsx に乗せる)

以下のいずれかに該当する:

- 複数案からのトレードオフの選択・採用理由など、後から「なぜこう作ったか」を決定履歴として残す価値のある設計判断を含む
- 外部から観測可能な振る舞いの追加・変更のうち、実装方針に選択肢が残っているもの
- `openspec/specs/` の既存 capability の要件を変える、またはユーザー向け docs の更新を伴う

### 仕様化しない（コード直行）

以下のみに該当する場合:

- typo・lint 指摘・コメント修正・フォーマット変更のみ
- 振る舞いが変わらない内部リファクタリング（関数分割・命名変更・デッドコード削除）
- ワンライナー fix（明白なバグの1行修正で、修正方針に選択肢がない）
- 挙動を変えない設定値の変更
- 依存パッケージのバージョン上げのみ（挙動変更を伴わない）
- **受け入れ条件が記録先（issue または Draft PR 本文）に明記された機械的な振る舞い変更**（設計判断を含まない）。記録先とテストが記録として十分なため spec は省略できる

軽い通し方（「仕様化しない」のうち、本体が W を起こさずに直す通し方）は本体だけが使う手順で、正本は `references/light-path.md`。

### 仕様化するが軽く通す（仕様の文言合わせ）

仕様化「する」のうち、既存の仕様の文言を実装に合わせて直すだけの変更は、成果物を仕様の差分 1 ファイルだけにし、R1 の仕様レビューを省く（以下「文言合わせの通し方」）。対象・当てる条件・省くものの正本はこの小節。

**対象**（すべて満たす変更に限る）:

- `openspec/specs/` の既存の要件の文を、実装に合わせて直すだけである
- 新しい要件を足さない・要件を消さない・要件の名前を変えない（差分が `## MODIFIED Requirements` だけで書ける）
- 設計の選択が無い（直し方が 1 つに決まっている）
- 直す要件が 1 つの capability の spec に収まる（差分が 1 ファイルになる）

**当てる条件**: 記録先の受け入れ条件（issue 本文。Draft PR が記録先なら PR 本文）に「どの仕様のどの文をどう直すか」が書けていること。直す要件ごとに、spec のパス（または capability 名）・要件名・直し方の 3 つが受け入れ条件から読み取れるときに「書けている」とする。

**省くもの**: proposal・design・tasks と、R1 の仕様レビュー。W は `openspec/changes/<change-name>/specs/<capability>/spec.md` の 1 ファイルだけを書き、作業項目は return に置く（手順は `references/roles/worker/spec.md`）。仕様の差分は実装後レビュー（pr-review-gate）が PR diff の一部として見る。実装後レビューとテスト作成は省かない。

**記録**: 仕様化判断のコメントの 1 行目（`仕様化判断: する`）は変えず、2 行目以降に `通し方: 文言合わせ` の行と、直す要件ごとの `直す文:` の行を書く。本体とゲートはこの行で見分ける（行の書式の正本は `references/roles/spec-reviewer.md`「判断記録の契約」）。`通し方:` の行が無い「する」は、これまでどおり artifact 一式と R1 のレビューを要する。

**当てないとき**: 受け入れ条件に直す文が書けていない変更と、対象のどれかを満たすか迷う変更には当てず、これまでどおり artifact 一式（proposal / design / tasks / specs）を作って R1 のレビューを受ける。当てるかどうかは W が決め、interactive でも主に聞かない（聞くと、手間を減らすための通し方に質問の往復が入る）。unmanned も同じ対象・同じ当てる条件で当てる。

**途中で対象から外れたとき**: 仕様を書く途中か実装の途中で対象のどれかを満たさないと分かったら（新しい要件が要る・設計の選択が出た・2 つ以上の capability に広がった）、W は手を止めて return し、`通し方:` の行の無い仕様化判断を投稿し直してから artifact 一式を作り、R1 のレビューを受ける。R1 を一度起こした change は、あとから文言合わせの通し方に切り替えない（差し戻しを避ける手段にしないため）。

**守備範囲**: 機械で止めるのは、pr-review-gate の合格処理が実測する 4 点（仕様宣言の形・archive 済みの差分がちょうど 1 ファイル・ADDED / REMOVED / RENAMED の見出しが無い・差分の要件名がすべて `直す文:` の行にある。正本は `skills/pr-review-gate/stages/pass-wording.md` の手順 5）だけ。受け入れ条件と `直す文:` の行の突き合わせ、挙げた要件の中での書き換えすぎ、R1 の差し戻しのあとの切り替えは機械では止めない（見るのは実装後レビューと主）。

### 判定したら必ず記録する

判定結果は記録先に `仕様化判断: する` / `仕様化判断: しない`（1 行目・完全一致）＋理由のコメントで残す。書式と照合規則の正本は `references/roles/spec-reviewer.md`「判断記録の契約」。文言合わせの通し方を当てるときは、同じコメントの 2 行目以降に `通し方: 文言合わせ` の行と `直す文:` の行を足す（上の小節の「記録」）。

### どの判定でも変えないもの

**テスト作成は全経路で必須**。例外は軽い通し方だけで、`確かめ方:` の既存のテストかチェックのコマンドを走らせることが新しいテストの代わりになる。W が起こされる経路ではどの判定でもテストを書く。テストはドキュメントであると同時に、昇格トリップワイヤー（失敗ループ検知）の信号源であり、これを緩めるとハーネス全体が機能しなくなる。

### 判定に迷ったら

- **軽い通し方で迷ったら**: どのモードでも主に聞かず、当てない側（W を起こしてテストを書く）に倒す。

- **interactive モード**: W は本体に return し、本体が「これは仕様として残しますか、それともコード修正だけで済ませますか？」と聞く。
- **unmanned モード**: 判断がつかない場合は**仕様化する側に倒す**（過剰な spec 化のコストより、無人ループが判断ミスで仕様の裏付けなしに振る舞いを変えるリスクの方が高い）。
- **文言合わせの通し方を当てるかどうかで迷ったら**: どちらのモードでも主に聞かず、当てない側（artifact 一式と R1 のレビュー）に倒す。

## Step C: 単一 change か複数 change か

分割の根拠は**記録先の記述**（受け入れ条件・機能単位）に限る。本文の長さやラベルのような機械的シグナルは使わない。

### 単一 change で足りる

すべてを満たす:

- 単一の capability（機能領域）に閉じる
- 受け入れ条件が概ね1〜5個程度で、1 PR で完結する分量
- 独立した設計判断（トレードオフの選択）が1つ以内

### 複数 change に割れる

いずれかに該当する:

- 複数の独立した capability に跨る（例: 「認証を追加し、かつ管理画面にログイン状態を表示する」は認証capabilityと表示capabilityの2つ）
- 受け入れ条件が多く、明確な順序依存を持つサブタスクに割れる（例: 「スキーマ変更 → API 実装 → UI 実装」のように前工程が終わらないと後工程が着手できない）
- 1 実装サイクルで完結しない規模（loop-dev-agent の `size:large` 相当の分量）

**境界の一言定義**: 「opsx change が2つ以上必要になりそうなら複数 change」。複数 change が独立してマージできる PR に割れるなら、`references/epic.md`「エピックの扱い」の条件にも当たる。

### 複数 change に割れた場合の分割方法

1. 記録先の受け入れ条件・記述されている機能単位を根拠に、独立した capability ごとに change 候補を機械的に列挙する（想像で機能を足さない。記録先に書かれている範囲でのみ分割する）。
2. 各 change 候補間の依存関係を見る（後工程が前工程のファイル・API に依存するか）。依存があれば順序を付ける。依存がなければ並列実行候補としてよい。
3. 各 change 候補は、それ単体で「単一 change で足りる」の基準を満たすように切る（1つの change がさらに複数に割れそうなら、その change 自体をもう一段分割する）。

### 割り方が判断できないほど曖昧な場合

- **interactive モード**: W は本体に return し、本体が AskUserQuestion で聞く（例: 「issue に書かれている内容は、A と B の2つの独立した変更に見えます。分けて進めてよいですか、それとも1つの change として扱いますか？」）。
- **unmanned モード**: W は子 issue を作らず、質問文・理由と `needs-approval` を return に含め、記録先に `needs-approval` を付けて経緯をコメントし、作業を止めて本体へ return する。W は Discord（MCP・CLI とも）へ直接送信しない。本体が代理送信してサイクルを終了する手順は SKILL.md「実行モード」を参照。

## 判定に使わない材料（注意）

- `docs/agent-loop.md` の有無 — これは loop-dev-agent（無人ループ）が導入済みかどうかの判定材料であり、wt-setup 済みかどうかや仕様化要否の判定には使わない。
- issue に付いているラベルの種類 — `agent-ready` 等のラベルは loop-dev-agent 側の運用状態を表すものであり、Step B・Step C の判定基準そのものではない（unmanned モードで呼ばれた時点で、着手可否の判定は既に呼び出し側=loop-dev-agent の Step 0.9 が済ませている）。`size:large` は「分割の方向性を人間に委ねる」印で、分割判定の入力ではない。
- issue 本文の長さ・チェックリスト数・言及ファイル数 — 分割判定の入力にしない。分割判定は記録先の記述内容で行う。
