# 親の開始と通常進行（develop）

エピックの親が開始・復元するときに読む。経路が subagent のときは `references/epic-subagent.md` を読んでその方式へ進む。別リポジトリの子を扱う前に `references/epic-multirepo.md` を読む。

**経路の決め方**: 本体は子 issue の依存グラフ（`gh api repos/<owner>/<repo>/issues/<N>/dependencies/blocked_by`）を読み、blocked されていない子の番号を `scripts/epic-dispatch.sh route <子>...` に渡す。返る値は 3 つで、`orca`（`orca` が PATH にあり、本体が Orca 管理のワークツリーにいる）・`tmux`（Orca 管理外で、環境変数 `TMUX` が空でなく `tmux` が PATH にある）・`subagent`（どちらでもない。**サブエージェント方式**）。`orca` と `tmux` は子を別の Claude Code セッションとして起こす**別セッション方式**で、起動部品（子のワークツリーとセッションを扱う `scripts/epic-launch-<名前>.sh`）が違うだけ。環境変数 `EPIC_DISPATCH_LAUNCHER=orca` か `tmux` を付けて呼ぶとその部品に固定でき（その部品が使えなければ `subagent`。`orca`・`tmux` 以外の値は使い方を出して exit 1）、付けなければ上の順（Orca が先）で決まる。着手できる子が 0 件（`route` に子を渡さない）のときは、Orca・tmux のどちらの管理下でも `subagent` が返る（エピックの子のセッションでは件数によらず `nested`）。経路は `/develop <エピック番号>` の最初の開始時に 1 回だけ決めて途中で変えない。決めたらエピックに 1 行コメント（`回し方: Orca（並列可能な子 k 件）`・`回し方: tmux（並列可能な子 k 件）`・`回し方: サブエージェント（並列可能な子 k 件）` のどれか）を残す。別セッションで同じエピックを再開したときは、`回し方:` で始まる最新のコメントから経路を引き継ぎ、`route` をやり直さない（コメントが無いときだけ `route` で決める）。最新の `回し方:` が `Orca` か `tmux` のときは、`launch` と `adopt` に環境変数 `EPIC_DISPATCH_LAUNCHER=<そのコメントの部品名（小文字の orca か tmux）>` を付けて呼ぶ（付けないと部品を今の環境から選び直し、前のセッションが記録した子と別の部品で新しい子が起動しうる）。その部品が今の環境で使えず `launch`・`adopt` が exit 1 で終わったら、別の部品にもサブエージェント方式にも振り替えず、stderr を添えて主に報告して止まる（部品の違う子の混在を作らない）。`reply`・`notify-closed`・`reap`・`wait --resolve` は子の記録の `launcher` で部品が決まるので、部品名を渡さない。unmanned（`--unmanned`）は `route` を呼ばず、サブエージェント方式で進める（背景で待って起こされる動きが 1 サイクル 1 仕事と合わないため）。channel も `route` を呼ばず、サブエージェント方式で進め、エピックに `回し方: サブエージェント（channel モード）` を残す。channel で再開したエピックの最新の `回し方:` が Orca なら、または tmux なら、`launch` もサブエージェント方式も使わず、その旨をチャンネルで主に報告して止まる（channel は別セッション方式を引き継がない）。channel の本体は develop の手順のために別の Claude Code セッション（Orca・tmux など）を起こさない（別に起こしたセッションには印 `DEV_WORKFLOW_UNATTENDED` が届かず、その画面を誰も見ていないので、子が主の返事待ちで止まっても誰も気づかない。サブエージェントなら主に聞くのは本体なので、聞く先はチャンネルのまま）。経路を決めて `回し方:` を残したら（unmanned・channel を含む）、あわせてエピックに、1 行目が `子の PR トークン権限: 60000000`（子 1 件あたりの PR トークンの権限。数字だけ）のコメントを投稿する（既にあれば投稿しない）。interactive と channel では主に「子 1 件 6,000 万トークンで回す。広げたければ声をかけて」と伝え、unmanned ではコメントだけを残す。権限は、投稿者の `author_association` が OWNER・MEMBER・COLLABORATOR のコメントのうち最新の 1 件を正とする。主が広げたら、親が新しい値で同じ形のコメントを投稿し直し、2 行目に `主の発言: <要旨>` を書く。親の判断では広げない。止まる上限（既定 30,000,000）は変えない。権限の使い方は`references/epic-stop.md` の **PR トークン上限の子**

**エピックである子を外す**: 本体は blocked されていない子のうち、sub-issue を持つ子（`gh api repos/{owner}/{repo}/issues/<N> --jq .sub_issues_summary.total` が 1 以上。`null` や空は 0 とみなす）をエピックとして外し、`route`・`launch`・サブエージェント方式のどれにも渡さない。経路が `nested` でないと確定したら（`route` が `nested` 以外を返したとき。`route` を呼ばない unmanned と channel と、`回し方:` のコメントから経路を引き継いだ再開を含む）、外した子ごとにエピックへ `後で別に起動するエピック: #N` と 1 行コメントする。外した結果、渡す子が 0 件になっても `route` は呼ぶ（unmanned と channel を除く）。`回し方:` のコメントから経路を引き継いで再開したときも、`launch` に渡す前に同じ確認で外す。

**別セッション方式**（起動部品は Orca か tmux。以下の手順 1〜8 は部品によらず共通で、部品で違う点は下の「部品ごとの欄」）: 子は独立した Claude Code セッションとして `/develop #<N>` の 1 ループを丸ごと回し、本体は子の W / R1 / G を起こさない。本体は子セッションに SendMessage できないので、子への指示はすべて起動プロンプト（`--note`）で渡す。子ごとに違う注意書き（「後続の範囲に手を出さない」など）が要るときは子ごとに `launch` を分けて呼ぶ。`launch` は `--note` の文を、子 issue に `親エピックからの注意書き: #<エピック番号>` で始まるコメントとしても残す。注意書きの子側の検査は `references/epic.md`。

**子の状態の正本**: 別セッション方式の子の状態（完了の印・レビュー待ちの印・主の返事待ちで止まった印とその受け取り）の正本は、`epic-dispatch.sh` が書く状態の記録（`${EPIC_STATE_ROOT:-~/.claude/epic-state}/<owner>.<repo>-<エピック番号>/` に子ごと 1 ファイル。親の `launch` と再開時の `adopt` が作り、子の `mark` と親の `wait`・`dismiss` が書き換え、`reap` と待ちを終えるときの `clear` が消す。`wait` は子の会話ログから見つけた止まりも、発言の uuid〔`stop_uuid`〕と時刻〔`stop_at`〕つきでここに書く）である。Orca の部品の子では、Orca のボードの列とコメント欄は、記録を書いたあとに写したものにすぎない（tmux の部品に画面への写しは無い）。Orca の部品の子で、Orca の画面で印を手で変えても、親の見張り（`wait`・`reap`・`pending-owner`）には効かない。

**部品ごとの欄**: 手順 1〜8 と完了条件は、起動部品が Orca でも tmux でも同じに行い、状態は記録から読む。部品で違うのは次の点だけ。サブエージェント方式は `references/epic-subagent.md`。

| 点 | Orca の部品（`epic-launch-orca.sh`） | tmux の部品（`epic-launch-tmux.sh`） |
|---|---|---|
| 子の起こし方 | Orca の子ワークツリーを作り、端末に起動コマンドと最初の指示を送る | `<リポジトリ>/.claude/worktrees/issue-<N>` にワークツリーを作り、新しい tmux ウィンドウに起動コマンドを打ち、入力待ちの画面になってから最初の指示を打つ。送信は子の会話ログに指示が現れたことで確かめる |
| 使える条件 | `orca` が PATH にあり Orca 管理下 | 親が tmux の中にいる（`TMUX` が空でない）。リポジトリの登録は要らず、別のリポジトリの子も clone があれば起こせる |
| `kept <N> <理由>` を確かめたあとで消す操作 | Orca の worktree を消す（`--force` なし。コマンドは手順 3 に書いた） | `bash <epic-dispatch.sh と同じディレクトリ>/epic-launch-tmux.sh remove <path>`（`git worktree remove`。`--force` なし）。確かめる 2 点、残すときのコメント、`ambiguous`・`close-failed` で消さない扱いは Orca と同じ |
| 止まった子への `reply`・完了を促す返事 | Orca の部品が端末へ送る | `send-keys -l` で子のペインへ打つ。シェルだけのペインには送らず、起動し直す |
| 画面への写し | Orca のボードの列とコメント欄に写る | 無い |
| 設定の誤りの報告 | `not in an Orca-managed worktree` は「親ワークツリーで開き直す」と報告する | 該当しない（`wait` は記録だけを読む）。stdout に何も出さず exit 1 で終わったときは stderr を添えて主に報告して止まり、開き直しを案内しない |

## 主への報告

親が別セッション方式でターンを終えるときに主に出す発言すべて（手順 2 で `wait` を背景で起動して待ちに入る通知と、手順 3・4・8 を処理して 2 に戻るたびの発言、手順 4 の見送りの報告、手順 6 の `error`・`failed` の報告、手順 7 と完了条件で待ちを終えるときの報告、**マージ待ちの子** の `reply` の `failed` の報告、手順 4 の `notify-closed` の `failed` の報告、手順 8 の止まった子の報告を含む。`reply-after-idle.md`「親への適用」で続行する純粋な `timeout` で起こされたときは主に発言を書かない。長時間後の再開案内と記録失敗時の停止報告はこの発言一覧から除外しない）と、サブエージェント方式の主への報告の両方は、1 行目と 2 行目を `~/.claude/output-styles/readable.md` の節 3 の書き分けに従わせる（以下、手順からは「「主への報告」の規定」と呼ぶ）。主の操作も判断も要らない報告（待ちに入るときは普通これ）は 1 行目を `主がすること: なし` にする。判断・確認・操作を求める発言は 1 行目を題名（依頼の形。質問にしない）にし、2 行目を `アクション:` で始まるアクションの行にして、どの画面・入力欄で何を打つ・押すかを書く。1 行目のあとに各手順の説明を続ける。子の完了報告の 1 行目（`主がこのセッションで次にすること:`。子のタブを開いた主向け）とは別である。

**状態表**（`references/reply-after-idle.md` の親の表で起動し直す旧親の案内（記録失敗時の停止報告を含む）に限り、状態表と `child-log` 確認を省略する。通常の報告や短時間の通知・返事の処理後の報告では省略しない。それ以外は親が主に出す報告すべての最後に付ける。別セッション方式の上の発言すべてと、サブエージェント方式の主への報告の両方に当てる。主が最新の 1 通だけで、まだ閉じていない子が今どうなっていて自分が何をすればよいかを読めるようにするため）: 表と、その下の URL と、前回の報告から片付いたものは、報告の区切りより下に置く。複数の依頼があるときも区切りより上で上げるのは今回いちばん先に答えてほしい 1 件だけ。依頼が無い報告に `アクション:` の行は書かない（番号検査の hook が依頼として拾うため）。

- 表の上に、確かめた時刻（JST）を書く
- 行は、まだ閉じていない全部の子 issue と、親自身（エピックの番号）を 1 行ずつ
- 列は `issue 番号・内容・ステータス・確認内容・推奨・答え方` の 6 つ。確認内容は主に聞いていることの中身、答え方はどの画面で何を打つか。答えが要らない行は `なし`
- 表の下に、答えが要る子の issue の URL を 1 行 1 本で置く。子の停止の記録の URL は、1 行目で聞く 1 件にだけ書き、聞いていない子の分は並べない（親が誤って別の子に返事を送っても、子の側の結び付けの確認が報告の URL だけで通らないようにするため）
- その下に「前回の報告から片付いたもの」を書く（子のタブで答え済みの件を含む）
- channel モードでは、答え方の列もチャンネルで返す内容にし、チャンネル以外の画面やタブは書かない

**親の判断で通した PR・止まり**: 前回の報告からエピックに残した `親の判断: 子 #N 通した` と `委任で送った:` の行を、1 件 1 行で、通した中身（何を進めたか）と子 issue か PR の URL を添えて報告の節に並べる。運用の形・構造の分け方・将来の拡張に効く設計の分かれ目を親か子が決めた件は、決めた内容と他の案も書く。`論点なしの確認: 通す` の記録はこの節に載せない。0 件なら節ごと書かない。

表を書く前に、別セッション方式の親は、`references/reply-after-idle.md` の親の表で起動し直す旧親の案内（記録失敗時の停止報告を含む）に限り状態表と `child-log` 確認を省略する。義務は新親へ移し、手順 7 の復元後にログを確認してから状態表を書く。通常の報告や短時間の通知・返事の処理後の報告では省略しない。それ以外は、`launch` に渡した子ごとに会話ログの末尾を `scripts/epic-dispatch.sh child-log <子>...`（別のリポジトリの子は `<owner>/<repo>#N` で渡す）で読み、子のタブで進んだ分を表に反映する（子のタブで主が直接答えても、子は子 issue の停止の記録を書き直さないので、記録だけを見て書くと表が子の実際の状態とずれる）。出力の列は `--help` に書いてある。親からの判断の返事（頭が `親エピック #`）とツールの結果は主の発言に数えない。会話ログの末尾と子 issue の記録が食い違うときは会話ログを優先する。まだ起動していない子（後回し・依存待ちで `launch` に渡していない子）には状態の記録も会話ログも無いので `child-log` に渡さず、ステータスは `未起動（<理由>）` と書く。`launch` に渡した子で `unreadable <子>` が返った子（記録が無い・読めない・一意に決まらない、会話ログが読めない）のステータスは `確かめられなかった` と書き、記録から推測して書かない。冒頭だけで状態が取れないときは、親が会話ログを自分で読む。サブエージェント方式の子には独立した会話ログが無いので `child-log` は使わず、本体が自分の会話から子の状態を書く。

書き分けの規定の守備範囲と同じく、表の文の良し悪しや、書き方の穴を塞ぎ切ることはこの規定の完了条件にしない。

## 起床の入口

手順 3〜8 と主の返事の処理より先に `references/reply-after-idle.md`「親への適用」を読む。時間分類・時刻の測り方・優先順の正本はその節だけとする。停止済み子の声かけを扱う前に `references/epic-keepalive-watch.md` を読む。

**依存待ちの照合（通常進行・手順 4・7 に優先）**: `stopped` / `pending` は主の返事待ちより先に、子 issue の最新の `子の停止: 依存待ち` コメント・今回の発言・現在の `dependencies/blocked_by` を照合する。マーカーだけで登録・解消を認定しない。依存待ちは動いている子から外す。`pending-owner` でも同様に復元し、主への問い・`told` を作らない。worktree・停止記録・途中経過を保持し、`mark done` / `reap` をせず、`--watch-stopped` / `--watch-done` の対象から外す。

前提を既存 `wait` の位置引数（別リポジトリは `owner/repo#N`）で見張る。エピック外の前提は子として起動せず、その `closed` は依存再評価だけに使い、子のマージ報告・notify-closed / reap に回さない。依存待ちが残る間は、動く子・片付け待ちが 0 件でも `clear` せず見張り続ける（下の 3・4・7・待ちの終了条件・完了時の片付けより優先）。

手順 4 の closed 後と手順 7 の復元時に依存と保存した再開条件を読み直し、全て解けた未起動の子は `launch`、既存 worktree の子は `scripts/epic-dispatch.sh reply --relaunch --as parent <epic> <child> '<依存先の完了と保存した再開手順>'` で起こす。`skipped` を再起動成功とせず、`relaunched <N>` と送信結果（`/develop #<子>`・続行指示）を確認して動いている子へ戻す。`not_planned` は手順 4 の見送りで後続を起こさず報告し、依存を読めなければ未解消とする。再起動の `failed` / `not-stopped` は手順 6 のエラー経路で報告し、終了記録を保持して原因と次の操作を残す。

**clear の扱い**（手順 3・4・7 と完了時に共通）: エピックの状態ディレクトリを消す。`cleared`・`none` は何もせず、exit 1 は stderr を添えて主に報告する。エピックを閉じるのは待たない。

## 通常進行の手順

**出力語の分類**（語の意味は `scripts/epic-dispatch.sh --help`。ここは受けた本体が止まるか進むかだけを示す）:

| サブコマンド | 進む | 止まって主に報告する |
|---|---|---|
| `launch` | `launched`・`skipped`・`deferred` | `failed`（手順 6）、exit 1 で `failed` の行が無いとき |
| `reply` | `sent`・`relaunched` | `failed` |
| `notify-closed` | `notified`・`skipped`・`unrecorded`（エピックに 1 行を残す） | `failed` |
| `wait` | `closed`・`done`・`unrecorded`・`timeout`（手順 5） | `stopped`（手順 8）・`expired`（手順 9）・`error` |
| `reap` | `reaped`・`gone`・`kept`（手順 3 で本体が確かめる） | exit 1 |
| `adopt` | `adopted`・`skipped`・`none`・`failed <N> ambiguous`／`state-unreadable` | 理由の無い `failed`、stdout が空の exit 1 |
| `pending-owner`・`child-log`・`mark`・`dismiss`・`told`・`clear` | 各行（`unreadable` の子は `確かめられなかった` と書く） | stdout が空の exit 1 |

1. `scripts/epic-dispatch.sh launch [--note <text>] [--base <branch>] <エピック番号> <子>...` で子を起動する。出力は子ごとに 1 行（語の意味は `scripts/epic-dispatch.sh --help`、止まるか進むかは上の分類表）。`deferred <N>` は枠が無く起動しなかった**後回しの子**（上限は下の **同時に動く子の上限**）。再開時も、依存が解けた open の子をそのまま `launch` に渡し、起動済みの子は `skipped` で見分ける。stderr に `note not posted to #<N>` があれば、注意書きのコメントを残せていないので、本体が stderr に出た本文をその子 issue に投稿する。起点は `origin/main`。既定ブランチが `main` でないリポジトリでは `--base <既定ブランチ>` を付ける（環境変数 `EPIC_DISPATCH_BASE` でも既定を変えられ、`--base` が優先する）。`--base` と `EPIC_DISPATCH_BASE` は 1 回の `launch` の全部の子に掛かる。別のリポジトリの子の起点と混在時の呼び方は、先に `references/epic-multirepo.md` を読む。
2. `launched` と `skipped` の子を動いている子とする（後回しの子は動いている子にも片付け待ちの子にも入れない。`wait` の位置引数にも `--watch-done` にも渡さない）。`launch` のあと動いている子も片付け待ちの子も 0 件なのに後回しの子が残るときは、`wait` を呼ばずに主に報告する（親の知らないワークツリーが枠を塞いでいる。報告には `launch` の stderr の `max parallel <上限> (<出どころ>); in use <数>: #<N>...` の行を添え）。動いている子か片付け待ちの子があれば、`scripts/epic-dispatch.sh wait --watch-done <片付け待ちの子> ... --resolve <エピック番号> --watch-stopped <動いている子>...` を Bash の `run_in_background: true` で起動してターンを終える（背景タスクが終わると本体が起こされる）。動いている子が 0 件で片付け待ちの子だけを渡すとき（手順 3・7 から 2 に戻った場合を含む）は、手順 4 と同じく `--timeout 21600` を付ける（既定では 3000 秒で timeout しうる）。片付け待ちの子は、`launch` に渡して `deferred` 以外を返したことのある子（閉じた子を含む）から、エピックに `子 #N のワークツリーを残した` で始まる行がある子と、このセッションで `reap` が `reaped <N>`（`branch-kept` を含む）か `gone <N>` を返した子と、本体が確かめて消した子（3）を除いたもの（除いたあとにこのセッションの `launch` が `launched <N>` を返した子は戻す。ワークツリーを作り直した子だから）で、1 件ごとに `--watch-done <N>` を付ける。`wait` は片付け待ちの子のうち、完了の印の無いまま記録先が `completed` で閉じてから `EPIC_DISPATCH_DONE_IDLE_SEC`（秒・既定 1800）以上たち、子のトランスクリプト（サブエージェントのものを含む）の最後の活動もそれ以上前の子を、LLM なしで完了と推定して `done <N>` を返す（`status` が `waiting` の子・止まった印の子・トランスクリプトが無い子は推定しない。主にマージを頼んで見張りを終えた子は、主がマージしても `mark done` を呼ぶ機会が無いため）。`--resolve <エピック番号>` を付けると、`wait` は止まった子ごとに判断（`scripts/stop-judge.sh` がモデルを 1 回呼ぶ。基準は `references/parent-pass-criteria.md`）を呼び、通すと判断された止まりは子に返事を送ってエピックに `親の判断: 子 #N 通した` の 1 行を残し、本体を起こさない。通せなかった止まりは子 issue に `親の判断:` のコメントを残して `stopped` で返す。出力は該当する語の行だけ（複数なら全部を処理する）。`--resolve` を付けないときは `unrecorded` は出ない。`unrecorded <N>...` で起こされたら、主に上げず、`wait` が stderr に出した投稿し直しのコマンドでエピックに `親の判断: 子 #N 通した` の 1 行を残す。stderr を読めなければ `親の判断: 子 #N 通した — 理由は記録できなかった 発言 <止まりの uuid か 不明>`（今回の停止の記録があれば末尾に URL を足す。uuid は手順 8 の `child-log --last` で読む）を投稿する。そのあと 2 に戻る。待ちに入るときの通知は普通 `主がすること: なし`。同じターンで主に問いを出したとき（手順 4〜6・8）は、待ちに入る通知を `主がすること: なし` で始めず、1 行目に問いの題名を、2 行目にアクションの行を繰り返す（直前の問いを `なし` で上書きしない）。手順 1 の `launch` のあと、このセッションで最初に待ちに入る通知には、権限確認の画面で止まった子と、会話ログを読めない子には親が気づけないので、子のタブも見るよう主に一度だけ伝える文を足す（親を起動し直したセッションでも、そのセッションの最初の通知で一度伝える）。手順 5 の掛け直しのたびには伝えない。
3. `done <N>...` で起こされたら（子が「用が済んだ」の印を付けた）、`scripts/epic-dispatch.sh reap <N>...` を Bash で 1 回呼ぶ。wt-clean は呼ばず、子ごとの確認もオーナーに取らない（子が印を付けたことを片付けの承認として扱う）。2 の `wait` が推定の `done` を返した子も、子が付けた `done` と区別せず同じに `reap` に渡す（片付けの安全確認は `reap` が行う）。同じ子が `closed` と `done` の両方の行に出たら、4 を処理してからこの `reap` を呼ぶ。出力は子ごとに 1 行で、`reaped <N>` と `gone <N>` はワークツリーに何もせず、その子を以後の片付け待ちから外す。`reaped <N> branch-kept` はエピックに `子 #N のローカルブランチを残した` と 1 行コメントする。`kept <N> not-done` は待ちを続ける。それ以外の `kept <N> <理由>` は、主に聞かずに本体が次の 2 つを確かめて消すか残すかを決める（主には判断材料が無い）。(a) `reap` が残した理由が解消していて、未コミットの変更が無い（`git -C <path> status --porcelain` が空、かつ `<path>/LLM` が無い。`LLM/` は `status` に出ないので別に見て、消さない）。(b) HEAD が `launch` の起点ブランチ（`EPIC_DISPATCH_BASE`／`--base`、既定 main）のリモートの先端に含まれるか、マージ済み PR の HEAD に入っている（`headRefOid` と同じか、HEAD の tree が `headRefOid` の tree と同じ。squash は tree の一致）。`ambiguous` は対象を特定できないので確かめず残す。`state-unreadable` は子の状態の記録を読めないので確かめず残し、`子 #N のワークツリーを残した（state-unreadable） — <reap の stderr に出た記録のパス>` と 1 行コメントする。`close-failed` は `reap` が 1 回閉じ直しても端末を閉じられず、子のターンがまだ動いている見込みがあるので確かめず残し、`子 #N のワークツリーを残した（close-failed） — <reap の stderr の owner action の行>` と 1 行コメントする（どの画面で何をするかを主に渡す）。両方を満たせば、部品の欄の操作（Orca は `orca worktree rm --worktree path:<path>`、tmux は `epic-launch-tmux.sh remove <path>`。どちらも `--force` なし）で消し、エピックに `子 #N のワークツリーを確かめて消した（<理由>）` と 1 行コメントして片付け待ちから外す（この行は `子 #N のワークツリーを残した` で始めない）。満たさないか `rm` が失敗したら残し、`子 #N のワークツリーを残した（<理由>） — <満たさなかったこと／rm 失敗／特定できない>` と 1 行コメントする。どちらも主に消すかを聞かない。そのあと、後回しの子が残っていれば、2 に戻る前に依存の解けた開いた子を、最初に渡したときと同じ `--note` を付けて `launch` に渡し直す（後回しの子には注意書きが投稿されていない。起動済みの子は `skipped`、枠がまだ無ければまた `deferred`）。動いている子か片付け待ちの子があれば 2 に戻る。どちらも 0 件なら `scripts/epic-dispatch.sh clear <エピック番号>` を 1 回呼んでから（上の **clear の扱い**）`wait` を呼ばずに待ちを終える（完了条件の確認・報告も行う。後回しの子だけなら 2 の報告）。
4. `closed <N>...` で起こされたら、閉じた子ごとに `gh api repos/{owner}/{repo}/issues/<N> --jq .state_reason` を読む。`completed` ならエピックへ `子 #N マージ → 残り k 件` とコメントし、`launch` より先に、`completed` の子ごとに、`references/reply-after-idle.md` の表で起動し直すかを決めて `scripts/epic-dispatch.sh notify-closed <エピック番号> <N>`（起動し直すなら `--relaunch` を足す）を 1 回呼ぶ（主が子のタブの外で PR をマージして子が主の返事待ちで止まったまま閉じたとき、子に「記録先は閉じた。完了報告を書き、mark done で終える」を送り、エピックに `親の判断: 子 #N 通した` の 1 行を残す。止まった印の無い子・既に完了の印を付けた子には何も送らない）。出力の `notified <N>` と `skipped <N> <理由>` は何もしない。`skipped <N> not-stopped` の子（止まった印を付けずに見張りを終えた子。主に直接マージを頼んだ子など）は、片付け待ちとして `--watch-done` に渡しておけば、子のセッションが止まって閾値を過ぎたあとの `wait` が完了と推定して `done <N>` で返すので、主に子のステータスを変えるよう頼まない。`unrecorded <N>` は主に上げず、stderr に出た投稿し直しのコマンドでエピックに 1 行を残す。`failed <N> <段>` は主に報告する（stderr に送り直しか作り直しのコマンドが出る）。`completed` 以外の子には `notify-closed` を呼ばない（作業されていない件に完了を促さない）。そのあとで依存グラフを読み直して解けた子を件数にかかわらず `launch` する（後回しの子も同じ `--note` で渡す。枠を超えればまた `deferred`。通知を先に送るのは `launch` の `failed` 後の送り漏れを防ぐため。親は 6 で止まり、再開の 7 は `notify-closed` を呼ばない）。`completed` 以外（`not_planned` など）ならエピックへ `子 #N 見送り（<state_reason>）→ 残り k 件` とコメントし、その子を前提にしていた子は起動せずにユーザーに報告する（依存 API は前提が閉じれば理由を問わず後続の blocked を外すので、理由を見ないと作業されていない前提の上に後続が起動する）。この場合も枠は空くので、後回しの子が残っていれば、見送りの子を前提にしていた子を除いて、依存の解けた開いた子を `launch` に渡し直す（3 と同じ）。残りの動いている子があれば 2 に戻る。開いている子が無くなったら、片付け待ちの子（2 と同じ集合）で `reap` を 1 回呼んで 3 と同じに扱い、`kept <N> not-done` の子だけを `--watch-done` に渡して（位置引数の子なしで、`--timeout 21600` を付けて）待ちを続ける（上限の明示は手順 2 と同じ理由）。その子が 0 件なら `scripts/epic-dispatch.sh clear <エピック番号>` を 1 回呼んでから（上の **clear の扱い**）`wait` を呼ばずに待ちを終える（完了条件の確認・報告も行う。後回しの子だけなら 2 の報告）。エピックの完了条件の確認と報告は、この待ちを理由に遅らせない。この待ちが `timeout` で終わったら、下の **待ちをやめてよい条件** の確認を通してから、残っている子の番号をユーザーに報告して待ちをやめる（停止が見つかれば手順 8 などで処理して待ちに戻る）。
5. `timeout <N>...` で起こされたら、`references/reply-after-idle.md`「親への適用」を先に読み、純粋な timeout を掛け直す行に当たるときだけ（位置引数の子がある `wait` が上限に達した。手順 2・4 の片付け待ちの子だけを待つ `wait`（位置引数の子なし）の `timeout` はここに当たらない）、子 issue もエピックも読まず、主に報告もせず、直前と同じ引数の `wait` を `run_in_background: true` で再び 1 回起動してターンを終える。`--timeout` は足さない（足すと、掛け直しのたびに `wait` が親の会話キャッシュの有効期限から上限を決め直すのが効かなくなる。上限の既定と理由は `references/reply-after-idle.md` の「親の待ちの費用（#1324）」）。主への発言は書かない。書くなら「主への報告」の規定に従う `主がすること: なし` の 1 行だけにする。主への問いが未回答のあいだは、その 1 行も書かず、問いを繰り返しもしない（問いを済んだものと誤読させるため）。子セッションは interactive の `/develop` なので、子が記録（`子の停止: 主の返事待ち`）を残さずに子のタブでユーザーに質問して止まることがある。この止まりは `wait --watch-stopped` が子の会話ログから検知する。起動側が `DEV_WORKFLOW_GIT_GUARD_NO_ASK=1` を付けた別セッションの子は git ガードの確認画面で止まらず、拒否後に承認を求めてターンを終えた止まりを、親から会話ログが読めるときに `wait --watch-stopped` が検知する。印が無く権限確認の画面で止まった子と、会話ログを読めない子は、`wait` でもこの手順でも検知できない（主への注意は手順 2 の最初の通知で一度だけ出す）。動いている子が残るあいだは、`timeout` が何度続いても待ちをやめない（下の **待ちをやめてよい条件**）。位置引数の子が全員、主に伝え済みの止まり（手順 8 で `told` を呼び、そのあと再開も新しい止まりも無い子）だけのあいだは、`wait` は上限で `timeout` を返さずに待ち続け、`EPIC_DISPATCH_OWNER_WAIT_SEC`（秒。既定 43200＝12 時間）たつと `expired <N>...` で返る（手順 9）。そのあいだに主が子のタブで答えて子が再開すれば、今までどおり上限で `timeout` が返る。
6. `wait` の `error gh ...`・`error workspaces` と `launch` の `failed <N>` はユーザーに報告して止まる。`failed` の子をサブエージェント方式にも別の部品にも自動で振り替えない（途中の worktree が残り二重起動しうるため）。指示が届かなかった `failed` の子は、報告に stderr の送り直しのコマンドを添え、stderr に出た確認のコマンドで届いていないことを確かめて送り直し、動き出したのを確かめてから再開する（送らないと未稼働の子を待ち続ける）。端末を作れなかった `failed` の子は、stderr に出た確認のコマンドでそのワークツリーに既存の端末が無いことを確かめ（あるのに作ると同じ子が二重に走る）、stderr の作り直しのコマンドで端末を作り、返ったハンドルに stderr の送信のコマンドを送って、動き出したのを確かめてから再開する（作り直さないと端末の無い子を待ち続ける）。tmux の部品の作り直しのコマンド（`epic-launch-tmux.sh start`）は起動と最初の指示の送信までを行うので、続けて送らない。`launch` が exit 1 で子を 1 件も作らなかったとき（`failed` の行が無い）と、`adopt` が stdout に何も出さず exit 1 で終わったときは、stderr を添えて報告する。`--watch-done` か `--watch-stopped` を付けた `wait`・`reap`・`pending-owner` が stdout に何も出さず exit 1 で終わったとき（stderr に `jq is not on PATH` か `not in a git worktree` が出る）も、stderr を添えて設定の誤りとして報告して止まる。stderr が `not in an Orca-managed worktree` を含む（Orca の部品で始めたエピックを Orca 管理外のワークツリーで再開した。tmux の部品では出ない）ときは報告に「親ワークツリーで開き直す」と書き、`cannot read the epic repository from origin` を含むときは「親ワークツリーの origin を GitHub の URL にする」と書く。stderr が `usage:` を含むときは、stderr を添えて設定の誤りとして報告して止まる。別のリポジトリの子の `failed` は、`references/epic-multirepo.md` の「epic-loop.md 手順６の読み替え」を読んで扱う。

に渡したことのある子（エピックの状態ディレクトリ `${EPIC_STATE_ROOT:-~/.claude/epic-state}/<owner>.<repo>-<エピック番号>/` にある記録の子と、エピックのコメントから分かる子を合わせたもの。閉じた子を含む）で `scripts/epic-dispatch.sh adopt <エピック番号> <子>...` を 1 回呼ぶ（未記録の子を起動部品の印から取り込む）。`adopted`・`skipped`・`none` は何もしない。`failed <N> ambiguous` は主に聞かずにその子を残して進み、エピックに `子 #N の記録を取り込めなかった（ambiguous）` と 1 行コメントする。`failed <N> state-unreadable`（その子の記録が読めない）も同じに、止まらずにその子を残して進み、`子 #N の記録を取り込めなかった（state-unreadable）` と 1 行コメントする。理由の無い `failed <N>`（記録を書けなかった）は、stderr を添えて主に報告して止まる（6 と同じ）。`adopt` が stdout に何も出さず exit 1 の報告）。後回しの子の一覧はどこにも保存しない。起動し直した親は、依存の解けた開いた子を `launch` に渡した出力の `deferred` で後回しの子を知る。再開したエピックに `子の PR トークン権限:` のコメントが無ければ（権限の仕組みより前に起動したエピック）、「経路の決め方」と同じく既定値で投稿して主に伝える。新セッションで長時間後の引き継ぎから戻ったときは、develop の入口と手順書を読み、この手順の adopt・reap・pending-owner と止まりの uuid（空なら停止記録 URL）の照合で復元する。復元→ログ確認→状態表の順とし、別セッション方式では child-log で会話ログ末尾を確認して結果を反映した状態表を区切りより下に置いて報告する（未起動・unreadable・ログ優先は上記の規定を維持する）。未処理の主の返事は保存した元セッション ID・uuid と最新の停止記録 URL で元発言の真正性と対象を手順 8 の照合で確認し、返事→通知→純粋な timeout の順で扱う。引き継ぎコメントの写しだけを主の許容と認定せず、旧親へ返事を打ち直すことも再開条件にしない。stopped-seen は pending-owner で拾い、同じ止まりの uuid（空なら同じ停止記録 URL）に送信済みの判断は再送しない。記録済みの完了も二重処理せず、closed / done / stopped / unrecorded を現在の状態と照合する。起動し直しだけを理由に監視を終了しない。位置引数の子なしの片付け待ち timeout は条件 (d) と終了直前の確認を保持し、復元だけで新たな 6 時間待ちへ入り直さない。

依存待ちは上の照合で先に扱う。残った主の返事待ちについて、8 の停止処理はここでは行わない。`stopped` または `pending` の処理前に `references/epic-stop.md` の手順 8 を読む。

9. `expired <N>...` で起こされたら（主に伝え済みの止まりだけが残ったまま、`EPIC_DISPATCH_OWNER_WAIT_SEC` 秒（既定 12 時間）主の返事が無かった）、子を調べ直さず、返事を送らず、`wait` を掛けない。`reply-after-idle.md`「親への適用」の項目で再開の記録（起床理由は `expired <N>...`）をエピックに追記し、主に 1 通だけ「見張りを止めた。子 #N の問いに子のタブで答えたら、`/develop <エピック番号>` で親を再開する」と伝えてターンを終える（下の **待ちをやめてよい条件** の (f)）。記録に失敗したら再開できるとは伝えず、エラーと未保存の内容を主に示して止まる。

`closed` で起こされたときの確認では、エピックに `後で別に起動するエピック: #N` の行がある子を動いている子から外す（起動前にも外すが念のため。子エピックは閉じず待ち続けになる）。

**待ちをやめてよい条件**: 親が `wait` を呼ばずにターンを終える（見張りを自分からやめる）のは、次のどれかのときだけで、それ以外ではやめない。(a) 動いている子も片付け待ちの子も 0 件になり、`clear` まで済ませたとき（手順 3・4・7 と完了条件。下の確認は `clear` の前に行う）。(b) 手順 2 の、動いている子も片付け待ちの子も 0 件で後回しの子だけが残るとき（主に報告して止まる）。(c) 手順 6 と 7 の `error`・`failed` や `adopt` の失敗を主に報告して止まるとき。(d) 手順 2・4 の、片付け待ちの子だけを待つ `wait`（位置引数の子なし）が `timeout` で終わったとき。(e) 主がやめるよう言ったとき。(f) `wait` が `expired <N>...` で返り、手順 9 を済ませたとき（伝え済みの止まりだけが残っているので、下のやめる直前の (1)(2) の確認は要らない）。次は、やめる理由にならない: `timeout` が何度続いても（手順 5。動いている子が残るあいだは再び待つ）、変化が無い、待ちが長い、主に上げた（手順 8 のあとは 2 に戻る）、主の返事待ちの子が残っている、親の側の予算や時間。(a)〜(d) でやめる直前に、`launch` に渡したことのある子のうち issue が開いている子（閉じた子は除く。以下、開いた子）で、主の返事待ちで止まった子が無いことを確かめる。開いた子が 0 件なら (1)(2) を呼ばない（(a) と (d) はふつうこれに当たる。子を渡さずに呼ぶと、どちらも stdout が空のまま使い方を出して exit 1 で終わり、手順 6 の設定の誤りと見分けられない）。このときは、やめるときの報告に「確かめる子が無かった」と書く。開いた子が 1 件以上なら、次の 2 つを順に呼ぶ。(1) `scripts/epic-dispatch.sh wait --interval 0 --timeout 0 --watch-stopped <開いた子>...`（1 回だけ見る。`--resolve` は付けない。`--watch-done` を付けないので `done` の行は出ない。子が止まった印を付けたのに `wait` がまだ受けていない件を受けた印に書き換えて `stopped <N>...` で、閉じていた子を `closed <N>...` で返して exit 0。どちらも無ければ `timeout <開いた子>...` を返して exit 2 で、この `timeout` の行が止まった子なしの意味になる。記録を読めない・排他を取れない・書けないなどで確かめられなかった子があっても同じ `timeout` の行と exit 2 で終わり、その理由は stderr に出る）。(2) `scripts/epic-dispatch.sh pending-owner <開いた子>...`（親が受けたまま子が再開していない子を `pending <N>` で返して exit 0）。加えて、開いた子の issue に `needs-approval` ラベルが付いていないかを見る（子が停止の記録を残さずに止まったときの手がかり）。止まった子が無いとみなすのは、(1) が `timeout <子>...`（exit 2）で、(2) が exit 0 で手順 7 の照合で外さなかった `pending <N>` を返さず、(1)(2) の stderr が空で、`needs-approval` の子もいないときだけである。(1) が `stopped`・`closed` の行を返した、(2) が手順 7 の照合で外さなかった `pending <N>` を返した、または `needs-approval` の子がいたときは、(a)(b)(d) ではやめずに、返った行を手順 4・8 で処理して 2 に戻る（`pending` の子は手順 7 の `pending` の子と同じに扱う。主に上げても待ちに戻る）。(c) では確かめるだけで手順 2 に戻らず、見つかった `stopped`・`pending` の子と `needs-approval` の子を、止まる報告に書く（(1) が受けた印に書き換えた止まりは、親を起こし直した手順 7 の `pending-owner` が拾い直す）。2 に戻るのは (a)(b)(d) だけである。(1) か (2) が exit 1 で終わった、または (1)(2) の stderr に何か出たときは、確かめられなかったとして、やめるときの報告に、確かめられなかった子の番号（stderr の記録のパスから分かる子。分からなければ開いた子のすべて）と stderr を書く。止まった子が無いとみなせたときは、やめるときの報告に、確かめたことと、残っている子の番号を書く。

子セッションは `launch` が起動コマンドに `--model` と `--settings '{"idleCompaction":false}'` を付けて起動する（組み立ては `scripts/epic-dispatch.sh --help`）。idleCompaction は、子のアイドル時のコンパクト（待っている間の自動コンパクト）をそのプロセスだけ切る（通常の自動コンパクトは止めない。根拠は `references/reply-after-idle.md`）。Orca を使う場合、Orca に設定したエージェントのコマンドはハーネスから読めないので、Orca 側のコマンドを変えたら `EPIC_DISPATCH_CLAUDE_CMD` も合わせて変える。端末を作れずに `failed` になった子には、既存の端末が無いことの確認・端末の作り直し・最初の指示の送信のコマンドが stderr に出る（使い方は手順 6）。

**同時に動く子の上限**: `launch` は、同時に枠を使う子が上限に達したら残りを `deferred` で後回しにする。上限は環境変数 `EPIC_DISPATCH_MAX_PARALLEL`（1 以上の整数。空・0・数字以外なら `launch` は使い方を出して exit 1）で、無ければ既定値は物理メモリの GiB を 4 で割って切り捨てた値（最小 1。メモリ量を読めなければ 2）。実際の値は `scripts/epic-dispatch.sh max-parallel` が出す。Linux の `MemTotal` は物理メモリより少し小さく報告されるので、4 の倍数ちょうどの機では 1 段下がる（16 GiB 機で 3）。重いビルドを子ごとに同時に走らせるリポジトリでは値を下げる。枠を使っている子は、今の親ワークツリーから `launch` が作った子のうち、完了の印（`done`）の子・閉じた子・主の返事待ちで止まった子を除いたもの（issue の state を読めない子は数える）。止まった子は入力待ちでサブエージェントもテストも動かさず、数えると主の返事が遅れるあいだ全体が止まるので数えない。別セッション方式では止まった子が戻るのは子のセッションの中で親は止められないので、戻った子の分だけ一時的に上限を超えうる（超えるのは止まっていた子の数まで）。サブエージェント方式では再開を本体が行い、再開の前に空き枠を確かめるので上限を超えない。

子セッションの `--dangerously-skip-permissions` は環境変数 `CLD_DEFAULT_ARGS`（`bin/cld` が `claude` の引数の先頭に置く既定フラグ）から来る。`launch` と、子の端末を作るすべての経路（`reply`・`notify-closed`・`wait --resolve` の起動し直し）が親の環境の `CLD_DEFAULT_ARGS` を子の起動コマンドへ代入として渡すので、親の環境（`.zshrc` の環境変数の行）に `CLD_DEFAULT_ARGS=--dangerously-skip-permissions` を置くことが前提になる（親に値が無ければ子には渡らず、子は許可の確認画面で止まる）。`epic-dispatch.sh` 自身が足すのは `--settings '{"idleCompaction":false}'` と `--model` だけで、`--dangerously-skip-permissions` を持つ子は許可の確認画面が出ない（hooks は効く）。マージを止めているのは確認画面ではなく develop と pr-review-gate の規則と hooks である。本体は子の PR を `gh pr merge` や merge API で直接マージしない。子の PR のマージは子セッションの中の人の承認か自動マージの処理（`.github/workflows/auto-merge.yml`）が行い、`human-merge` の付いた子の PR は、本体が`epic-merge-wait.md`「マージ待ちの子」 の手順で判断の印を付けたときに限って自動マージの処理がマージする。

止まってから時間がたった子に返事を送る前（親自身が長く待ったあとも）、そのまま送るか起動し直すかを `references/reply-after-idle.md` の規則で決める（全 develop は `SKILL.md` の共通開始手順で worktree-local の idleCompaction を false にする。親・子・単発を分けず、子の既存 --settings も維持する）。送り方と起動し直し方の手順は止まった子を解決する手順に従う。

## 完了時の片付けと報告

別セッション方式では、動いている子が無くなったときの報告の前に、エピックの状態ディレクトリ（`${EPIC_STATE_ROOT:-~/.claude/epic-state}/<owner>.<repo>-<エピック番号>/`）が `clear` で消えていることを確かめる（残っていれば `scripts/epic-dispatch.sh clear <エピック番号>` を呼ぶ。上の **clear の扱い**。exit 1 は stderr を添えて主に報告する）。

動いている子が無くなったときの報告（エピックへのコメントとユーザーへの完了報告）には、エピックに記録した `後で別に起動するエピック:` の番号をすべて載せる。子エピックが閉じるまで全子 PR のマージは満たされないので、親エピックは閉じない。
