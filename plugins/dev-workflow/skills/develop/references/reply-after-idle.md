# 時間がたった子・親への返事

エピックの子（別セッション方式の子セッション）と親（エピックを回すセッション）に、止まってから時間がたって返事を送るときの規則。すべての develop セッションは開始時に worktree-local の idleCompaction を false にする（`SKILL.md`「開始時の idle compaction 設定」）。通常の自動コンパクトは維持する。

子は会話量が閾値以上、または 60 分以上止まったら起動し直す。コンパクトされた子は develop の `SKILL.md` の中身を持たずに進むためである（#1039 の決定を #1323 で覆した）。親も 60 分以上なら記録から起動し直す（「親への適用」）。

送り方と起動し直し方の手順本体はここに書かない。止まった子を親が解決する手順（#1034。develop の `references/epic.md`「回し方」の別セッション方式の手順 8 と `scripts/epic-dispatch.sh reply`）と、止まったまま completed で閉じた子に完了を促す手順（#1093。同じ節の手順 4 と `scripts/epic-dispatch.sh notify-closed`）が書き、ここを参照する。

## 開始時の設定

Claude の本体は、role 選択・工程・返事待ちより前に、現在の git worktree root を `<worktree>` として `python3 <plugin>/scripts/develop-idle-compaction.py --check <worktree>` を実行する（`<plugin>` はこの reference から `../../..` の絶対パス）。親・子・単発、interactive / unmanned を分けず、新セッションでの引き継ぎ・compact 後の再読でも同じ入口を使う。委譲された Codex worker は Claude の実設定を変更せず、本体が適用する。

- exit 0: disk 上は false 済み。書き込まない
- exit 2: `python3 <plugin>/scripts/develop-idle-compaction.py --apply <worktree>` で `.claude/settings.local.json` の最上位 `idleCompaction` だけを boolean false にする。無ければそのキーだけのファイルを作る
- exit 1 または apply 失敗: 対象パスと原因を記録して開始を止める。壊れた JSON・重複キー・非 object・読めない設定・symlink を上書きせず、部品は symlink を追わない

これは #1385 の PR に記す「develop 開始時、現在の worktree の `.claude/settings.local.json` の idleCompaction だけを false にする。他の設定値は保持し、ホーム・共有設定には書かない」という継続適用への、主のマージ承認（リスク宣言の許容）を一度の承認とする仕組み。承認後は新しい worktree でも操作の承認確認・追加質問はしない。他キー・別ファイル・symlink 先は範囲外で、従来の聖域承認を要する。R1 APPROVE やエージェントの投稿を主の承認に代えず、マージ承認前の実設定には apply しない。部品の検証は一時 git repo で行う。

設定は同じ worktree の他セッションにも残り、終了時に自動復元しない。通常の自動 compact（会話が上限近くに達したとき）と既存の compact 後の手順書再読み込み hook は維持する。子の既存 `--settings '{"idleCompaction":false}'` も残す。戻すときは主が差分を確認・承認し、このキーだけ元の値に戻すか、元々無ければ削除する。設定ファイル全体を復元しない。

disk 上の成功を live 反映済みとは扱わない。check / apply の後は次の機械確認で判断し、確認した根拠と限界を記録する。

- 新規 worktree の子でも、現在のプロセスの起動引数を確認して `--settings '{"idleCompaction":false}'` が渡っており、矛盾する上書き指定が無ければ主に聞かず進む。local ファイルが無く check が exit 2 でも承認済み apply 後にこの経路を使う
- 既存 local false（check exit 0）は書き込まない。起動前から false で、矛盾する起動引数が無いと機械確認できた新セッション、または実効値を機械確認して off だったセッションも主に聞かず進む。起動時の値が不明、起動後の apply だけ、または上書き指定と矛盾する場合は disk false だけで現在の実効 off を断定しない
- 上の根拠が得られた場合は interactive / unmanned とも追加確認を求めない。主の `/config` 確認は初回の実機検証に限る
- 機械確認で off を確かめられず、on の証拠も無いとき（起動時の値が不明、起動後の apply だけ）は、interactive / unmanned とも再起動を求めず、主にも聞かず、止まらずに進む。「未確認」と develop 開始コメントに記録する。起きうるのは待機中のコンパクト 1 回で、compact 後の手順書再読み込み hook で戻せる
- on と判明した場合（矛盾する上書き指定は on 判明として扱う）は未反映として再起動する。on 判明の記録がある再起動後のセッションでなお off を確認できなければ開始を止める

機械確認した設定・起動引数を超えて「live で off」とは報告しない。マージ後の親・子・単発の初回の実機検証と 60 分観測は `changes/1385.md` のチェックリストに従う。

## アイドル時のコンパクトの扱い

| セッション | 扱い | 付ける場所 |
|---|---|---|
| 子 | 切る | `epic-dispatch.sh launch` が子の起動コマンドの `<cmd>` と `--model` のあいだに `--settings '{"idleCompaction":false}'` を付ける（端末が無い子を起動し直す `reply` も同じ）。そのプロセスだけに効き、通常の自動コンパクト（会話が上限に近づいたときのもの）は止めない。Claude Code v2.1.290 以降が要る |
| 親 | 切る | `SKILL.md` の共通入口で worktree の `.claude/settings.local.json` の idleCompaction を false にする。単発も同じ |

どちらも `~/.claude/settings.json` には置かない。worktree の `.claude/settings.local.json` だけを使い、承認範囲・反映確認・戻し方は共通入口に従う。子の既存の起動オプションは補助として残す。この変更より前に起動された子は従来の設定でコンパクトされうる。

## そのまま送るか、起動し直すか（子）

子に返事を送る前に、上から順に当てはめて決める。

| 子の状態 | 扱い | 理由 |
|---|---|---|
| 子の端末が無い | 起動し直す | ほかに手がない |
| 子の会話量 N が `EPIC_DISPATCH_RELAUNCH_FORCE_TOKENS`（既定 150000）以上 | 起動し直す | 経過時間とコンパクトの有無によらず、大きい会話を繰り返し読む使用量と判断品質に対処する |
| 子の最後のリクエストから 60 分未満 | そのまま送る | キャッシュが生きている（入力換算 0.1N）。子が積んだ判断も残る |
| 子の最後のリクエストから 60 分以上 | 起動し直す | コンパクトの有無と会話量によらず起動し直す。コンパクトされた子は `SKILL.md` の中身を持たずに進み、コンパクトされていない子もキャッシュが切れている。起動し直しとの費用の差は 1 回あたり約 $0.5 |

判定に使う事実:

- **子の端末の有無**: 子のワークスペースに端末が残っているか（確かめるのは `scripts/epic-dispatch.sh reply` で、端末が無ければ起動し直して返事を付ける。#1034）
- **会話量 N**: 同じトランスクリプトを `plugins/dev-workflow/scripts/subagent-context.sh --file <トランスクリプト>` で測った `context_tokens`。最後の有効な assistant usage の input・cache_creation・cache_read の合計で、出力や累計や compact 前の最大値ではない。末尾の API エラーや全部 0 の usage は飛ばす。exit 0 と 2 はどちらも計測成功として値を比較する
- **最後のリクエストの時刻**: 子のワークツリーのセッションのトランスクリプト（`~/.claude/projects/` 配下の jsonl）の最後のリクエストの時刻

`wait --resolve` が親の代わりに通す返事は、本体ではなく `epic-dispatch.sh` が同じ子の表で決める。会話量条件と時間条件は独立した OR で、`compact_boundary` の有無は除外条件にしない。会話量を読めなくても時間条件が真なら起動し直し、時刻を読めなくても会話量条件が真なら起動し直す。どちらも真と確認できなければそのまま送る。トランスクリプトが無い・2 本以上ある・読めない場合もそのまま送る（端末が無いときは既存の送信処理に従う）。

会話量の閾値は `EPIC_DISPATCH_RELAUNCH_FORCE_TOKENS`（既定 150000）、60 分は `EPIC_DISPATCH_RELAUNCH_IDLE_SEC`（既定 3600 秒）で変えられる。未設定時だけ既定を使い、数字だけの非負整数を受け付ける。0 なら計測できた値はすべて条件を満たす。空・負数・単位付きなら、有効な `--resolve` が待つ前に変数名と使い方を出して exit 1。サブエージェント用の閾値は子の起動し直しの閾値に流用しない。

60 分前後で扱いが揺れる子、トランスクリプトが複数あってどれが子のものか分からない子は、そのまま送ってよい。

### 停止中の子へのキャッシュ維持（#1383）

親の通常の `wait --watch-stopped` が、主の返事待ちの停止記録があり未回答、stop=stopped-seen、TTL 1h の子だけに固定の声かけを送る。最後の成功した CLI リクエスト（cache-hit を含む）から 3000 秒以上 3600 秒未満、停止コメントの作成から 86400 秒未満のときに限る。TTL は最後の書き込みから読み、リクエスト時刻とは分ける。既存の会話量による再起動条件、計測不能・複数セッション、前の声かけの返事未着、実際の回答ありも対象外。

起動部品は既存の一意な前景の入力待ち・空欄にだけ送り、声かけのために起動し直さない。声かけも異常な返事も停止の印や停止コメント、24 時間の基点を延ばさない。3600 秒以上たったスリープ復帰後と 24 時間後は送らず、実際の返事が来たときに上の通常の再開判定へ渡す。

TTL 5m/unknown には送らない。overage 等で 5m に変わっても、キャッシュ書き込みによる切替を観測するまで検知できないため、切替直後の一回の書き直し費用を防げない場合がある。五分ごとの声かけはしない。

### 子を起動し直す根拠

- 会話量の既定 150000 は [#1046 の完了した再集計](https://github.com/oratta/claude-harness/issues/1046#issuecomment-6358891346) の結論に揃えた。起動し直しの平均費用は入力換算 270k、従来の費用比較の境目は 135k で、150k との差は標本の揺れの範囲として維持された。120000 は自動コンパクト用なので転用しない。この集計はキャッシュ有効中の起動し直しの最適値を実証していない。長い会話を繰り返し読む使用量と判断品質への初期設定として採用し、後の計測で変更できる

- 2026-10-23 の issue-1244 の子のログで、アイドル時のコンパクトのあとに残ったのは `SKILL.md` のファイル名と `/develop` の入口だけで、再開したあとも `SKILL.md` を読み直さずに、要約だけを頼りにゲートの実行まで進んでいた。コンパクトが安く済むのはこの読み直しを省いているからで、手順を守る前提と合わない
- 費用の差は小さい。#1039 の実測では、コンパクトされた子への返事が約 140k トークン、起動し直しが平均約 258k トークンで、差は 1 回あたり Opus 5.5 で約 $0.5。1 時間以上たってから返事が来る止まり方は子全体の 3.2%
- 子の再開は、issue に残した引き継ぎから起動し直す形がもともとの設計である
- この 3 点から、子の閾値を 120,000 にしてコンパクトされた子にはそのまま返事を送るという #1039 の決定を、#1323 で覆した

## 親への適用

親自身が長く待ったあと（背景の `wait` の終わりで起こされたときを含む）は、timeout・子の通知・主の返事の処理より時間分類を最優先する。手順は `references/epic.md`「親の起床時の時間分類」と手順 5・7。

| 親の状態 | 扱い | 理由 |
|---|---|---|
| 親の最後のリクエストから 60 分未満 | そのまま続ける | 短い待ちの掛け直しと通知・返事の既存処理を維持する |
| 親の最後のリクエストから 60 分以上 | 起動し直す | compact の有無と会話量によらず、同じ worktree の新セッションで手順書と記録を読む |

最後のリクエストは、親のトランスクリプトの起床の API リクエストを除いた待機前の時刻を使う。TTL 選択用のキャッシュを書いた行の時刻とは混同しない。60 分前後で時刻が曖昧なら続けてよく、時刻不明から長時間経過を捏造しない。60 分以上なら既知の状態と未処理イベントをエピックに記録し、同じ worktree の新セッションで `/develop <エピック番号>` として再開するよう主に案内して旧セッションを終える。記録失敗時は再開可能と報告せず、エラーと未保存内容を示して止める。

親を起動し直したら、状態はエピックのコメントと依存グラフから復元する。

| 状態 | 復元元 |
|---|---|
| 回し方 | エピックの `回し方:` のコメント |
| 終わった子 | `子 #N マージ → 残り k 件` / `子 #N 見送り` のコメント |
| 外した子エピック | `後で別に起動するエピック:` のコメント |
| 残したワークツリー | `子 #N のワークツリーを残した` のコメント |
| 親が通した判断 | `親の判断: 子 #N 通した` のコメントと停止記録 URL の対応 |
| 主の返事待ちの子 | 子の状態の記録の `stop` が `stopped-seen` のまま（`scripts/epic-dispatch.sh pending-owner`）で、子 issue の最新の `子の停止: 主の返事待ち` に対応する `親の判断:` が「通した」以外で、エピックの `親の判断: 子 #N 通した` の行の停止の記録の URL が子の最新の停止の記録と一致するものが無い |
| 残りの子 | 依存グラフと子 issue の状態から求め直す |

## 親の待ちの費用（#1324）

親（Orca・tmux の別セッション方式）は `scripts/epic-dispatch.sh wait` を背景で起動して待つ。上限を明示しない `wait` は、起動の時点で親のワークツリーの会話が最後にキャッシュを書いた行の有効期限を読み、上限を決める。決めた上限は stderr に `wait limit <秒> (parent cache <5m|1h|unknown>)` の 1 行で出る。

| 親の会話のキャッシュ | 上限 | 理由 |
|---|---|---|
| 1 時間で書いている、または判定できない | 3000 秒 | `wait` は「経過 + 間隔 > 上限」で眠らずに終わるので、通常のポーリング間隔では約 45 分で起きる。1 時間のキャッシュが切れる前にキャッシュを読み出しで延ばすため。idle compaction は共通で無効にする |
| 5 分だけで書いている | 21600 秒 | 短く起きてもキャッシュは残っておらず、起きるたびに会話全体を書き直すので、起きる回数を減らすほど安い |

上限で起きた親は、先に親の時間分類を適用する。60 分未満（時刻不明で長時間経過を確認できない場合を含む）の純粋な timeout だけ、子 issue もエピックも読まず、同じ引数の `wait` を背景で掛け直すだけでターンを終える（`references/epic.md` の手順 5）。掛け直しで最後のリクエストの時刻が進むので、会話のキャッシュは読み出しで延び、書き直しは起きない。`--timeout` を足さないので、掛け直しのたびに有効期限を読み直す。

- **使用量の超過中**: 使用量の上限を超えて追加の使用量で払っている間は、会話のキャッシュの有効期限が Claude Code によって 5 分に縮む（https://code.claude.com/docs/en/prompt-caching ）。トランスクリプトの書き込みが 5 分だけになるので、`wait` は 21600 秒に戻す。超過が明けると次のリクエストから 1 時間で書かれ、次の掛け直しから 3000 秒に戻る
- **有効期限を固定した人**: `CLAUDE_CODE_PROMPT_CACHE_TTL=1h` か設定 `promptCacheTtl` で 1 時間に固定していれば、超過中でも 1 時間で書かれるので 3000 秒で起きて延ばす。5 分に固定した人と、API キーの利用で 5 分になる人は常に 21600 秒になる
- **PC が寝ている間は効かない**: `wait` の経過時間（bash の `SECONDS`）は寝ていた時間も数えるので、起きた直後に `timeout` で親が起き、そのときキャッシュは切れている。60 分以上なら短い wait を掛け直すより先に記録から新セッションで再開する。5m の 21600 秒の長い timeout も時間分類を優先する
- **片付け待ちの子だけを待つ `wait`**（手順 2・4。位置引数の子なし）は `--timeout 21600` を付けて今までどおり最長 6 時間待つ。この待ちは `timeout` で終わったら待ちをやめるので、45 分でやめさせないため
- 戻すときは、親の環境で `EPIC_DISPATCH_TIMEOUT=21600` を付ければ上限は今までどおりになる

## 根拠と、この数字の限り（親の値）

比較する相手は、手順書と引き継ぎを読む新セッションである。要約と `scripts/develop-compact-reread.sh` による手順書再読み込み（約 39k）を二重に払う親の方針を、2026-10-26 の主の指摘を受け #1385 で覆した。監視停止が compact のせいだったとは断定しない。


旧費用集計は履歴として [#1039](https://github.com/oratta/claude-harness/issues/1039#issuecomment-6182988861)、[読み直し費用の指摘 #1217](https://github.com/oratta/claude-harness/issues/1217#issuecomment-6359110216) に残す。親の idle 閾値の再集計 #1264 は現行の宿題にせず、#1385 の実機確認後に不要として閉じる。通常 compact と子の再起動閾値の集計には転用しない。復元元の記録自体の誤りや欠落は時間分類だけでは防がず、追加封鎖を完了条件にしない。

子への声かけは既存 wait の中で行い、親 LLM の追加の呼び出しを作らない。親の TTL 別上限と、60 分未満の純粋な timeout 後の一回の掛け直しを維持する。60 分以上なら時間分類を優先し、記録から新セッションで再開する。子の維持費用に加え親の定期起床の費用も #1383 の実エピック比較で測る。送信開始の確認だけで、親子の書き直し削減や維持費込みの削減が実証されたとは扱わない。
