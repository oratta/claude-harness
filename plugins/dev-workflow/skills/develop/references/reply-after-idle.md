# 時間がたった子・親への返事

エピックの子（別セッション方式の子セッション）と親（エピックを回すセッション）に、止まってから時間がたって返事を送るときの規則。会話のキャッシュは 1 時間で切れるので、そのまま送ると会話全体 N を書き込み直す（入力換算で 2N）。Claude Code の待っている間の自動コンパクト（以下「アイドル時のコンパクト」）は、最後のリクエストから約 54 分で、会話が `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS`（既定 200,000、下限 10 万）以上なら会話を要約に置き換え、この費用を減らす。54 分は変えられず、PC が寝ている間は走らない。

子はアイドル時のコンパクトを切って起動し、60 分以上止まった子には返事をそのまま送らず起動し直す。コンパクトされた子は develop の `SKILL.md` の中身を持たないまま要約だけを頼りに進むためである（#1039 の決定を #1323 で覆した。根拠は「子を起動し直す根拠」）。親はアイドル時のコンパクトを残し、親の表で続けるか起動し直すかを決める（「親への適用」）。

送り方と起動し直し方の手順本体はここに書かない。止まった子を親が解決する手順（#1034。develop の `references/epic.md`「回し方」の別セッション方式の手順 8 と `scripts/epic-dispatch.sh reply`）と、止まったまま completed で閉じた子に完了を促す手順（#1093。同じ節の手順 4 と `scripts/epic-dispatch.sh notify-closed`）が書き、ここを参照する。

## アイドル時のコンパクトの扱い

| セッション | 扱い | 付ける場所 |
|---|---|---|
| 子 | 切る | `epic-dispatch.sh launch` が子の起動コマンドの `<cmd>` と `--model` のあいだに `--settings '{"idleCompaction":false}'` を付ける（端末が無い子を起動し直す `reply` も同じ）。そのプロセスだけに効き、通常の自動コンパクト（会話が上限に近づいたときのもの）は止めない。Claude Code v2.1.290 以降が要る |
| 親 | 閾値 120,000 | 親は主が起動するセッションなので `launch` は付けられない。主が起動するセッションは、主の起動コマンド（例: `cld`）が `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` の未設定のときだけ `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS=120000` を入れる（外から渡された値は上書きしない） |

どちらの指定も `~/.claude/settings.json` には置かない（主の手元の全セッションに効くため）。子のプロセスの環境には主の起動コマンドが入れた閾値も入るが、アイドル時のコンパクトを切った子では効かない。この変更より前に起動された子は、従来の閾値でコンパクトされうる。主の起動コマンドが値を入れずに起動した親は既定の 200,000 のまま動く。

## そのまま送るか、起動し直すか（子）

子に返事を送る前に、上から順に当てはめて決める。

| 子の状態 | 扱い | 理由 |
|---|---|---|
| 子の端末が無い | 起動し直す | ほかに手がない |
| 子の最後のリクエストから 60 分未満 | そのまま送る | キャッシュが生きている（入力換算 0.1N）。子が積んだ判断も残る |
| 子の最後のリクエストから 60 分以上 | 起動し直す | コンパクトの有無と会話量によらず起動し直す。コンパクトされた子は `SKILL.md` の中身を持たずに進み、コンパクトされていない子もキャッシュが切れている。起動し直しとの費用の差は 1 回あたり約 $0.5 |

判定に使う事実:

- **子の端末の有無**: 子のワークスペースに端末が残っているか（確かめるのは `scripts/epic-dispatch.sh reply` で、端末が無ければ起動し直して返事を付ける。#1034）
- **最後のリクエストの時刻**: 子のワークツリーのセッションのトランスクリプト（`~/.claude/projects/` 配下の jsonl）の最後のリクエストの時刻

`wait --resolve` が親の代わりに通す返事は、本体ではなく `epic-dispatch.sh` が同じ子の表で決める（60 分は `EPIC_DISPATCH_RELAUNCH_IDLE_SEC` 既定 3600 で変えられ、空か数字でなければ `wait` は使い方を出して exit 1）。事実を読めなければ（トランスクリプトが無い・2 本以上ある・時刻を読めない）そのまま送る。

60 分前後で扱いが揺れる子、トランスクリプトが複数あってどれが子のものか分からない子は、そのまま送ってよい。

### 子を起動し直す根拠

- 2026-10-23 の issue-1244 の子のログで、アイドル時のコンパクトのあとに残ったのは `SKILL.md` のファイル名と `/develop` の入口だけで、再開したあとも `SKILL.md` を読み直さずに、要約だけを頼りにゲートの実行まで進んでいた。コンパクトが安く済むのはこの読み直しを省いているからで、手順を守る前提と合わない
- 費用の差は小さい。#1039 の実測では、コンパクトされた子への返事が約 140k トークン、起動し直しが平均約 258k トークンで、差は 1 回あたり Opus 5.5 で約 $0.5。1 時間以上たってから返事が来る止まり方は子全体の 3.2%
- 子の再開は、issue に残した引き継ぎから起動し直す形がもともとの設計である
- この 3 点から、子の閾値を 120,000 にしてコンパクトされた子にはそのまま返事を送るという #1039 の決定を、#1323 で覆した

## 親への適用

親自身が長く待ったあと（背景の `wait` の終わりで起こされたときを含む）は、親の表で、そのまま続けるか起動し直すかを決める。親の端末は主が持っているので、端末が無い行は無い。

| 親の状態 | 扱い | 理由（入力換算の費用） |
|---|---|---|
| 親の最後のリクエストから 60 分未満 | そのまま続ける | キャッシュが生きている（0.1N） |
| 60 分以上で、その間に待っている間の自動コンパクトが走った | そのまま続ける | 要約後の会話の書き込みで約 140k。起動し直し（平均約 258k）より安く、親の判断も残る |
| 60 分以上で、コンパクトが走っておらず、会話量 N が 150,000 以上 | 起動し直す | 2N が 300k 以上になり、起動し直しの平均を超える |
| 60 分以上で、コンパクトが走っておらず、会話量 N が 150,000 未満 | そのまま続ける | 2N が起動し直しより安い |

判定に使う事実は、親のセッションのトランスクリプトの最後のリクエストの時刻と、そのあとに `compact_boundary` の行があるか、会話量 N（同じトランスクリプトを `plugins/dev-workflow/scripts/subagent-context.sh --file <トランスクリプト>` で測る）。60 分前後や 150,000 前後で扱いが揺れるときは、そのまま続けてよい。

親を子と分けるのは、親の監視の `wait` はコンパクトのあとも動き続け、通知を受けた親はそのまま作業を続けられるからである（2026-10-23 のエピックの親で確かめた）。起動し直すと、この監視が途切れる。

親を起動し直したら、状態はエピックのコメントと依存グラフから復元する。

| 状態 | 復元元 |
|---|---|
| 回し方 | エピックの `回し方:` のコメント |
| 終わった子 | `子 #N マージ → 残り k 件` / `子 #N 見送り` のコメント |
| 外した子エピック | `後で別に起動するエピック:` のコメント |
| 残したワークツリー | `子 #N のワークツリーを残した` のコメント |
| 親が通した判断 | `親の判断: 子 #N 通した` のコメント |
| 主の返事待ちの子 | 子の状態の記録の `stop` が `stopped-seen` のまま（`scripts/epic-dispatch.sh pending-owner`）で、子 issue の最新の `子の停止: 主の返事待ち` に対応する `親の判断:` が「通した」以外で、エピックの `親の判断: 子 #N 通した` の行の停止の記録の URL が子の最新の停止の記録と一致するものが無い |
| 残りの子 | 依存グラフと子 issue の状態から求め直す |

## 親の待ちの費用（#1324）

親（Orca・tmux の別セッション方式）は `scripts/epic-dispatch.sh wait` を背景で起動して待つ。上限を明示しない `wait` は、起動の時点で親のワークツリーの会話が最後にキャッシュを書いた行の有効期限を読み、上限を決める。決めた上限は stderr に `wait limit <秒> (parent cache <5m|1h|unknown>)` の 1 行で出る。

| 親の会話のキャッシュ | 上限 | 理由 |
|---|---|---|
| 1 時間で書いている、または判定できない | 2700 秒 | キャッシュは最後のリクエストから 1 時間で切れ、待っている間の自動コンパクトは約 54 分で走る。2700 秒なら最後のリクエストから約 45〜46 分で起き、コンパクトの前に約 8 分の余裕が残る。3000 秒ではその余裕が約 4 分で、`--resolve` の判断や gh の遅れで超えうる |
| 5 分だけで書いている | 21600 秒 | 短く起きてもキャッシュは残っておらず、起きるたびに会話全体を書き直すので、起きる回数を減らすほど安い |

上限で起きた親は、子 issue もエピックも読まず、同じ引数の `wait` を背景で掛け直すだけでターンを終える（`references/epic.md` の手順 5）。掛け直しで最後のリクエストの時刻が進むので、会話のキャッシュは読み出しで延び、書き直しは起きない。`--timeout` を足さないので、掛け直しのたびに有効期限を読み直す。

- **使用量の超過中**: 使用量の上限を超えて追加の使用量で払っている間は、会話のキャッシュの有効期限が Claude Code によって 5 分に縮む（https://code.claude.com/docs/en/prompt-caching ）。トランスクリプトの書き込みが 5 分だけになるので、`wait` は 21600 秒に戻す。超過が明けると次のリクエストから 1 時間で書かれ、次の掛け直しから 2700 秒に戻る
- **有効期限を固定した人**: `CLAUDE_CODE_PROMPT_CACHE_TTL=1h` か設定 `promptCacheTtl` で 1 時間に固定していれば、超過中でも 1 時間で書かれるので 2700 秒で起きて延ばす。5 分に固定した人と、API キーの利用で 5 分になる人は常に 21600 秒になる
- **PC が寝ている間は効かない**: `wait` の経過時間（bash の `SECONDS`）は寝ていた時間も数えるので、起きた直後に `timeout` で親が起き、そのときキャッシュは切れている。この 1 回は書き直しになり、そのあとは短い間隔に戻る
- **片付け待ちの子だけを待つ `wait`**（手順 4。位置引数の子なし）は `--timeout 21600` を付けて今までどおり最長 6 時間待つ。この待ちは `timeout` で終わったら待ちをやめるので、45 分でやめさせないため
- 戻すときは、親の環境で `EPIC_DISPATCH_TIMEOUT=21600` を付ければ上限は今までどおりになる

## 根拠と、この数字の限り（親の値）

親の値と条件は、手元のログ（子 1,592 本・親 37 本、2026-09-16〜10-15）の集計から決めた。集計の全体:
https://github.com/oratta/claude-harness/issues/1039#issuecomment-6182988861

- 1 時間以上たってから返事が来た割合（会話 100k 以上の止まった点）: 子 3.2%、親 40.6%
- 返事の直前の会話の中央値: 子 159k、親 152k。既定の 200,000 ではほとんどがコンパクトの対象外
- 起動し直しの費用（起動時の読み込みの書き込みと作業の組み立て直し）: 子で中央値 197k・平均 258k
- 閾値ごとの費用の増減（期間合計、入力換算）: 親は 120k で −24.7M（基本の想定）・−10.4M（控えめの想定）、100k なら −26.8M・−9.5M、既定の 200k は −3.6M
- 親を 120k にした理由: 親は 100k と 120k で差が小さい（基本で 2.1M、控えめでは 120k のほうが 0.9M 小さい）。開いたまま放置されるセッションでは最悪の想定で損の小さい 120k が合う
- 待っている間の自動コンパクトの実績は 14 回だけで、要約の大きさと読み直しの量はその少ない例から出した。PC が寝ていたかはログから分からず、寝ていると効果は小さくなる
- コンパクトのあと、develop を呼んでいた会話には SessionStart の hook（`scripts/develop-compact-reread.sh`）が `SKILL.md` の読み直しを差し込む。読み直しは 1 回約 39k トークンで、集計の控えめの想定で R に足した 40k（issue やコメントの読み直しの分）とは別にかかる。両方を足した想定（R に約 80k）は計算し直しておらず、#1264 で計算する。それまで親の値は変えない（#1217。計算: https://github.com/oratta/claude-harness/issues/1217#issuecomment-6359110216 ）
