# エピックの子が止まるとき（develop）

読む場面は `scripts/epic-dispatch.sh route`（子の番号なし）が `nested` の子で、主の返事待ち・途中で判明した依存待ちで終える前と、`親エピック #` / `主の返事（親エピック #` の入力を受けたとき（再起動時の指示を含む）。

## 依存待ちで終了する

`route` が `nested` の子が別 issue・PR の完了待ちを見つけたら、前提 issue の数値 id を `gh api repos/<前提-owner>/<前提-repo>/issues/<前提> --jq .id` で得る。自分の `repos/<child-owner>/<child-repo>/issues/<child>/dependencies/blocked_by` を `gh api` で GET し、未登録なら `-X POST -F issue_id=<数値 id>` で追加して再度 GET で確認する。PR 待ちは完了を表す対応 issue を特定し、両方の URL を残す。自分の PR のマージ待ちは定型の止まりを使う。

次を子 issue に投稿（主の返事待ちの 7 項目とは別）。

```
子の停止: 依存待ち
依存先: <issue と、PR 待ちなら PR の URL>
待つ理由: <何の完了が必要か>
再開条件: <続行できる条件>
再開に要る途中経過: <ブランチ・commit・PR・残作業・引き継ぎ URL>
再開手順: <main の取り込み・ゲートの取り直し等>
```

成功後、最後の発言の末尾を `止まった理由: 依存待ち: <依存先 URL>` として終了する。待機用の背景タスクや質問ツールで占有し続けない。停止の印を付ける操作は不要（親が会話ログから検知する）。対応 issue が不明、登録・確認・投稿が失敗なら移行成功とせず、失敗した操作・理由・未保存の途中経過を親へ返し、最後の行を `止まった理由: 依存待ちへの移行の失敗: <失敗した操作>` とする。範囲外の修正や新しい子 issue も自分で直さず報告する。

## エピックの子が主の返事を待って止まるとき

**キャッシュ維持の声かけの例外**: 子は停止前に `references/epic-keepalive.md` と `references/child-cache-keepalive.json`（プラグイン直下）を読み、共有正本の予約文と受信契約を覚える。

Orca・tmux の子が主の返事を待って止まる手順。親に気づかせる操作は無い（親の `wait` が子の会話ログから検知する）。子は親が読む中身だけを残す。別 issue・PR の完了待ちは先に「依存待ちで終了する」を使い、主の返事待ちの記録とは区別する。対象は `scripts/epic-dispatch.sh route`（子の番号なし）が `nested` を返すセッションだけで、それ以外のセッションでは記録を残さない（読む親がいない）。背景タスクの完了待ちも記録しない。

- **質問の仕方**: 主の返事を待つとき、子は質問ツール（AskUserQuestion）を呼ばず、本文で質問してターンを終える（質問ツールには声かけも親の返事も届かない）。選択肢を見せたいときは本文に番号つきで書く。主は子のタブで文字で答えても、親のタブで答えて親が `reply --as owner` で届けてもよい。develop と develop から読む文書の「interactive は AskUserQuestion で聞く」（候補を提示して選ばせる・承認を得る・判断を仰ぐを含む）は、`route` が `nested` のエピックの子ではこの聞き方に読む（各文書には書き足さず、子でないセッションは変えない）
- **記録を残す止まり**: PR のリスク許容の返事を待って止まるとき（pr-review-gate 手順 3 の宣言に対する主の許容を待つとき）と、聖域の変更の承認・破壊的な git 操作の承認を待って止まるときだけ、記録先の issue に、1 行目が `子の停止: 主の返事待ち` のコメントを投稿する。それ以外の止まり（マージ待ち・実機操作など）では記録を残さない。聖域の変更の承認の記録は `止まった理由:` を `聖域の変更の承認: <変更するファイルと中身>` で、破壊的な git 操作の承認の記録は `止まった理由:` を `破壊的な git 操作の承認: <コマンドの全文>` で始め、どちらも推奨が進めることなら `推奨:` を `進める` で始める（親と子が委任が効くかを確かめる入力になる）。質問より先に投稿する。2 行目以降は下の「記録の形」の 7 つの項目で書く。止まるたびに新しいコメントを投稿し、最新の 1 件を正とする。`references/handover.md` の引き継ぎを書く場面では、引き継ぎを先に投稿してから記録を投稿し、`再開に要る途中経過:` に引き継ぎのコメントの URL を書く（ほかの 6 項目も省かない。引き継ぎの書式は変えない）
- **定型の止まり**: PR のマージ待ち・PR トークン上限・CI の見張りで止まるときは、記録を残さず、最後の発言の末尾に行頭 `止まった理由: ` の行を書く。親が読む発言は末尾を残して切られるため。親はこの行で手順を分ける（`references/epic-stop.md` の手順 8）
  - マージ待ち: `止まった理由: PR のマージ待ち（human-merge）: <PR の URL>` と書く。`--until-merged` の `timeout` で改めて止まるときは `止まった理由: PR のマージ待ち（human-merge、親の返事のあともマージされない）: <PR の URL>` と書く。発言に書く内容は `references/ci-watch.md` の「`ready` を受けたあと」
  - PR トークン上限の exit 2: `止まった理由: PR トークン上限（合計 <合計> / 上限 <上限>）: 続けるか、範囲外として閉じるか` と書き、続けて `終わるまでの見込み: あと約 <残り>（合計の見込み <見込み>）`・`続けるべきか: <続ける／閉じる と理由>`・`次に絞る範囲: <残工程のうち何に絞るか>` の 3 行を書く。親はこれを親の権限に照らす（`references/epic-stop.md` の **PR トークン上限の子**）
  - CI の見張り: `references/ci-watch.md` の 6 の表の `escalate`、`obs.state` が `wait` でない `none`（同じ状態・HEAD で決着済み。追加のやり直し後の同じ HEAD の失敗も含む）、7 の直し方の手順 7（直せないので上げる）のどれかで止まったときは、`止まった理由: CI の止まり（<PR の URL> / <落ちたチェック名> / <HEAD の短い SHA か HEAD 不明>）: <主にしてほしいこと>` と書く。短い SHA は PR の HEAD のコミット SHA の先頭 7 文字で、`ci-watch.sh next` の出力の `obs.head` から取る（手元に無ければ `gh pr view <PR番号> --repo <owner/repo> --json headRefOid --jq '.headRefOid[0:7]'`）。手元の作業ツリーの HEAD は PR の HEAD とずれることがあるので使わない。取れなければ値を作らずに `HEAD 不明` と書く。親が `references/parent-pass-criteria.md` の上限で止まった子の節で `理由:` に写し、過去の `親の判断:` と同じ件かを見分けるため
- **そのほかの止まり**: 記録を残さない止まりでも、読み手は親と主で、どちらも子の会話を読んでいない。発言で質問・推奨・根拠を中身で書く（書き方の正本は `rules/communication-style.md`）。定型の止まりの発言も同じに書く
- **親から届いた返事**: `親エピック #<E> の判断（主の承認ではない）:` か `主の返事（親エピック #<E> 経由）:` で始まる入力（エピックが別のリポジトリにあるときは、番号のあとに `（<owner>/<repo>）` が付く `親エピック #<E>（<owner>/<repo>）の判断（主の承認ではない）: ` と `主の返事（親エピック #<E>（<owner>/<repo>）経由）: ` の形。先頭の `親エピック #` / `主の返事（親エピック #` で判定し、同じ手順で受ける）が届いたら（起動し直されたセッションの最初の指示に付いて届いたときも）、止まった件への返事として受け取り、続きから進む。`親エピック #<E> の判断（主の承認ではない）:` で進めた件は、親の判断だったことを完了報告に書く。親の判断は主の承認ではないので、聖域（`CLAUDE.md`・hooks・権限設定など）の変更や破壊的な操作の承認として扱わない（その件は改めて主に聞く）。PR トークン上限への `続ける。新しい上限 <権限>（親の権限。<URL>）` の返事は、主が権限のコメント（`子の PR トークン権限:`）で先に承認した範囲の執行なので、聖域の承認にも基準の聖域の「課金」にも当たらない。受信後は主に聞き直さず、次の計測前に記録先へ `PR トークン上限:` の 4 行（`決めた人:`・`権限:` に権限の URL・`停止の記録:` は記録を残さない止まりなので `なし`。書式の正本は SKILL.md「PR トークン上限」）を投稿してから再開する。この形でなければ上限の引き上げとせず主に聞く。`主の返事（親エピック #<E> 経由）:` で始まる入力が止まった件のリスク許容への返事で、末尾に `[主の発言: セッション <ID> / uuid <uuid>]` があるときは、記録先の最新の `子の停止: 主の返事待ち` のコメント（投稿者の `author_association` が PR・別のリスクだけを名指しした答えでないときだけ、保留の解除の G に親のセッション ID・uuid・`MATCH:` の timestamp・停止の記録の URL・`MATCH:` の全文を渡す（正本: pr-review-gate 手順 5「親経由で受領」）。終了コード 0 で、`MATCH:` の全文から不許容の意思が読め、全文がこの子・この PR への答えと読め、別の子・別の `owner-reply-check.sh` に掛けない）。末尾が `[主の委任: セッション <ID> / uuid <uuid> / 記録 <URL>]` の返事（正本: `references/epic-delegation.md` の **主の委任**）は、止まった件が記録を残す止まり（リスク許容・聖域の変更の承認・破壊的な git 操作の承認の返事待ち）のときだけ受け、上の <plugin>/scripts/owner-reply-check.sh --delegated <ID> <uuid> <委任の記録の作成日時> <URL> <最新の停止の記録の作成日時>` を回す。終了コード 0 で、`MATCH:` の全文から任せる意思が読め、委任が有効で、止まりに委任が効くときだけ受け、受けたあとは止まりの種類で分ける。リスク許容の止まりは、保留の解除の G に親のセッション ID・確認の uuid・`MATCH:` の timestamp・委任の記録の URL・停止の記録の URL・`MATCH:` の全文を渡す（pr-review-gate 手順 5 の「親経由で受領（委任）」が正本）。聖域の変更・破壊的な git 操作の止まりは、G を起こさず、停止の記録に書いた操作（変更するファイルかコマンドの全文）だけを返事の `実行の時機:` 条件と「委任が効く止まり」の種類別条件を確かめる（マージ待ち・実機操作の止まりには子の側で受ける委任は無い）。`--delegated` が終了コード 0 でない（`REASON=not-after` などで 1、または 2）、全文から任せる意思が読めない、委任が有効でない、止まった件が記録を残す止まりでない（マージ待ち・実機操作などで止まった）、または止まりに委任が効かないときは G を起こさず、確かめられなかった理由（`REASON=` の値か満たさなかった条件）を添えて、主に子のタブで直接返事を打ってもらうよう頼む。記録を残す止まりでは止まる前の記録をこの節の手順どおり残してから頼み、記録を残す止まりでない止まりでは記録を残さず、最後の発言で理由付きで頼む。守備範囲: ①入力の出どころは、子に届いた返事の頭と末尾の添え書き（親が書く）、エピック・子 issue・PR のコメントとラベル、同じ PC の親の会話ログ。親は写し間違い・別のエピックや別の記録との取り違えをする前提で扱う ②拾いたい誤りは、確認でない発言・別のエピックの記録・取り消し済みや編集済みの記録・範囲外の止まりでの委任を主の許容として G に渡すこと ③親と子が同じ PC で動き、委任の確認のあとに親が起動し直したものは通してよい ④会話ログの改変の検知と、穴を塞ぎ切ることは完了条件にしない

**記録の形**: PR のリスク許容の返事を待つ止まりの記録の形。定型の止まりは記録を残さず、上の `止まった理由:` の行で渡す。読み手の親・決める役・主は子の会話を読んでいない。2 行目以降に次の 7 つの項目をこの並びで書き、どの項目も省かない。各項目は行頭の `<項目名>:` で始めて値を同じ行に書き、値は次の項目の行まで複数行に続けてよい。

```
子の停止: 主の返事待ち
止まった理由: <主にしてほしいこと（決めること 1 つ、または操作）>
主に聞く理由: <主の側にしか答えが無い／決まりで主の承認が要る／主の手でしかできない操作 のどれかで始めて 1 文。論点の有無を添える>
前提: <子が作業中に分かった事実のうち、判断に要るもの>
推奨: <子が勧める答え>
推奨の根拠: <その推奨を選ぶ理由>
受け入れるリスク: <推奨を選ぶことで新たに生じるリスク。何が起きるか・どれくらい起きるか・その根拠>
再開に要る途中経過: <返事を受けて再開するのに要る作業の状態・コミット・PR など>
```

- `主に聞く理由:` は、主に聞く理由の 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作。正本は `~/.claude/output-styles/readable.md` の節 3）のどれに当たるかを、その語で始めて 1 文で書く。「決まりで主の承認が要る」ときは、その決まりが何を守るためかまで書く。続けて論点（主が持っていて子が持っていない観点を足すと結論がよくなる点）の有無を書く。論点があればその論点を書き、決まりで聞いているだけなら `論点なし（決まりで聞いている）` と書く。3 つのどれにも当たらない止まりは、そもそも止まらずに自分で進めて事後報告するのが正本の決まり。それでも子の側で進められない（読み取りを止めた hook・権限不足・待つしかない場合。破壊的操作や聖域は承認待ちに当たる）ときだけ `主に聞く理由: なし（<子の側で進められない理由>）` と書く
- `主に聞く理由:` を書く前に `references/parent-pass-criteria.md`「例」を読む。「主の側にしか答えが無い」で書く前に、次の 3 つを確かめる。(a) ログ・リポジトリ・手順書で調べれば分かる事実でないか。(b) 主の手が要る操作かを手順書で確かめたか（「主の作業」と書いただけでは主の手が要る操作に当たらない）。(c) 推奨と根拠がそろっていないか（そろっていれば、主に聞いても主の側の情報は増えない）。どれかで答えが出るなら止まらずに進め、事後報告する。
- `受け入れるリスク:` には、推奨を選ぶことで新たに生じるもの（他の案や何もしない場合には無いもの）だけを書き、無ければ `なし` と書く。どの変更にも当てはまるもの（「見落としがあると壊れる」）は書かない。書くときは、何が起きるか（被害の大きさ・戻せるか）、どれくらい起きるか（起きる条件と頻度）、その根拠（確かめたのか見込みか）を含める。分からないときは「分からない」と書き、何を調べれば分かるかを添える
- 該当が無い項目は値を `なし` と書く。推奨を出せない（主の側にしか無い情報が要る）ときは `推奨: なし（<足りない情報>）` と書き、`推奨の根拠:` と `受け入れるリスク:` は `なし` と書く
- 子が作業中に振ったラベル・番号・略称や「上記」「前回」で指さず、中身を書く。PR・issue・コメントにはフル URL を添える。専門用語は初出で一言の言い換えを添える。文章全般の書き方は `rules/communication-style.md` に従う
- 親は記録の項目を正本の段に置き直して主に報告する（手順 8）。項目名 `止まった理由` は、最後の発言の定型の行と同じ語で、親が「今回の止まった理由」として読むので変えない

親の側の手順は `references/epic-stop.md` の手順 8。
