# エピックの子が止まるとき（develop）

対象は `scripts/epic-dispatch.sh route`（子の番号なし）が `nested` の別セッションの子。毎ターン読む。

## 毎ターンの入力と状態行

`turn_input.session_id` と同じ ID の通常入力は送り手・受付時刻を記録し、世代を増やして状態を無効化する。送り手は `owner`（主）、`parent`（先頭が `親エピック #` / `主の返事（親エピック #`）、`startup`（登録・切替）。引用は除く。権限の証明ではない。許容・委任は下で確認する。

別セッションは記録を保ち、Stop は既存検査だけを返す。未登録の旧記録や誤った ID は、本来の子へ launcher の `/develop #<子> （エピック #<親> の子。…）` を送り直す。親子番号とエピックのリポジトリを一致させる（repo 省略は子と同じ repo のときだけ）。初回は世代1、切替は旧世代+1、同 ID への再送は `owner`。任意入力・Stop では登録しない。起動形は認証ではなく、別セッションへの意図的な一致指示でも切り替わる。

予約文の完全一致は入力・世代・時刻・状態を保つ（逸脱応答も）。共有正本の一行だけ返す。1文字でも違えば通常入力。

対象の子は毎ターン、引用・コード外の最終非空行に次を書く。中身は空でない一行。背景タスク待ちだけで終了しない。

```text
状態: 主の返事待ち — 主の答え・承認・操作が必要なこと
状態: 作業報告 — 問いのない区切り・依存待ちの再開条件
状態: 完了 — 完了した子の用
```

欠落・不正は再停止でも Stop が差し戻す。既存 Stop が拒否した発言は公開しない。入力の記録・保存が失敗したら理由を確認して通常入力を送り直す。


## 依存待ちで終了する

`route` が `nested` の子が別 issue・PR の完了待ちを見つけたら、前提 issue の数値 id を `gh api repos/<前提-owner>/<前提-repo>/issues/<前提> --jq .id` で得る。自分の `repos/<child-owner>/<child-repo>/issues/<child>/dependencies/blocked_by` を `gh api` で GET し、未登録なら `-X POST -F issue_id=<数値 id>` で追加して再度 GET で確認する。PR 待ちは完了を表す対応 issue を特定し、両方の URL を残す。自分の PR のマージ待ちは定型の止まりを使う。

次を子 issue に投稿（主の返事待ちの 7 項目とは別）。

```
子の停止: 依存待ち
依存先: <issue と、PR 待ちなら PR の URL>
待つ理由: <何の完了が必要か>
再開条件: <続行できる条件>
再開に要る途中経過: <ブランチ・commit・PR・残作業・引き継ぎ URL>
再開手順: <main の取り込み・ゲートの取り直し等>
```

成功後、最後の発言の末尾部分に `止まった理由: 依存待ち: <依存先 URL>`、次の最終非空行に `状態: 作業報告 — <依存先と再開条件の短い要約>` を書いて終了する。待機用の背景タスクや質問ツールで占有し続けない。停止の印を付ける操作は不要（親が会話ログから検知する）。対応 issue が不明、登録・確認・投稿が失敗なら移行成功とせず、失敗した操作・理由・未保存の途中経過を親へ返し、末尾部分を `止まった理由: 依存待ちへの移行の失敗: <失敗した操作>` とし、主の操作が必要なら最終非空行に `状態: 主の返事待ち — <必要な操作>` を置く。範囲外の修正や新しい子 issue も自分で直さず報告する。

## エピックの子が主の返事を待って止まるとき

**キャッシュ維持の声かけの例外**: 子は停止前に `references/epic-keepalive.md` と `references/child-cache-keepalive.json`（プラグイン直下）を読み、共有正本の予約文と受信契約を覚える。

Orca・tmux の子は親が読む中身だけを残す。親の `wait` が子の会話ログから検知するので通知操作は不要。別 issue・PR 待ちは上の依存待ち手順を使う。対象外セッションと背景タスクの完了待ちでは記録しない。

- **質問の仕方**: 主の返事を待つとき、子は質問ツール（AskUserQuestion）を呼ばず、本文で質問してターンを終える（質問ツールには声かけも親の返事も届かない）。選択肢を見せたいときは本文に番号つきで書く。主は子のタブで文字で答えても、親のタブで答えて親が `reply --as owner` で届けてもよい。develop と develop から読む文書の「interactive は AskUserQuestion で聞く」（候補を提示して選ばせる・承認を得る・判断を仰ぐを含む）は、`route` が `nested` のエピックの子ではこの聞き方に読む（各文書には書き足さず、子でないセッションは変えない）
- **記録を残す止まり**: PR のリスク許容（pr-review-gate 手順 3 の宣言）と聖域の変更の承認・破壊的な git 操作の承認を待って止まるときだけ、記録先 issue に `子の停止: 主の返事待ち` で始まるコメントを質問より先に投稿する。それ以外の止まり（マージ待ち・実機操作など）では記録を残さない。聖域なら `止まった理由:` を `聖域の変更の承認: <変更するファイルと中身>` で、破壊的操作なら `止まった理由:` を `破壊的な git 操作の承認: <コマンドの全文>` で始める。進める推奨なら `推奨:` を `進める` で始める（委任の照合に使う）。下の7項目を省かず、止まるたび新規投稿し最新を正とする。`references/handover.md` が必要なら引き継ぎを先に投稿し、`再開に要る途中経過:` に引き継ぎのコメントの URL を書く（ほかの 6 項目も省かない）。引き継ぎの書式は変えない。
- **定型の止まり**: PR のマージ待ち・PR トークン上限・CI の見張りで止まるときは、記録を残さず、最後の発言の末尾に行頭 `止まった理由: ` の行を書く。親が読む発言は末尾を残して切られるため。`止まった理由:` と見込み3行のあとに、最終非空行として状態行を置く。親はこの行で手順を分ける（`references/epic-stop.md` の手順 8）
  - マージ待ち: `止まった理由: PR のマージ待ち（human-merge）: <PR の URL>` と書く。`--until-merged` の `timeout` で改めて止まるときは `止まった理由: PR のマージ待ち（human-merge、親の返事のあともマージされない）: <PR の URL>` と書く。発言に書く内容は `references/ci-watch.md` の「`ready` を受けたあと」
  - PR トークン上限の exit 2: `止まった理由: PR トークン上限（合計 <合計> / 上限 <上限>）: 続けるか、範囲外として閉じるか` と書き、続けて `終わるまでの見込み: あと約 <残り>（合計の見込み <見込み>）`・`続けるべきか: <続ける／閉じる と理由>`・`次に絞る範囲: <残工程のうち何に絞るか>` の 3 行を書く。親はこれを親の権限に照らす（`references/epic-stop.md` の **PR トークン上限の子**）
  - CI の見張り: `references/ci-watch.md` の 6 の表の `escalate`、`obs.state` が `wait` でない `none`（同じ状態・HEAD で決着済み。追加のやり直し後の同じ HEAD の失敗も含む）、7 の直し方の手順 7（直せないので上げる）のどれかで止まったときは、`止まった理由: CI の止まり（<PR の URL> / <落ちたチェック名> / <HEAD の短い SHA か HEAD 不明>）: <主にしてほしいこと>` と書く。短い SHA は PR の HEAD のコミット SHA の先頭 7 文字で、`ci-watch.sh next` の出力の `obs.head` から取る（手元に無ければ `gh pr view <PR番号> --repo <owner/repo> --json headRefOid --jq '.headRefOid[0:7]'`）。手元の作業ツリーの HEAD は PR の HEAD とずれることがあるので使わない。取れなければ値を作らずに `HEAD 不明` と書く。親が `references/parent-pass-criteria.md` の上限で止まった子の節で `理由:` に写し、過去の `親の判断:` と同じ件かを見分けるため
- **そのほかの止まり**: 記録を残さない止まりでも、読み手は親と主で、どちらも子の会話を読んでいない。発言で質問・推奨・根拠を中身で書く（書き方の正本は `rules/communication-style.md`）。定型の止まりの発言も同じに書く
- **親から届いた返事**: `親エピック #<E> の判断（主の承認ではない）:` か `主の返事（親エピック #<E> 経由）:` で始まる入力（エピックが別のリポジトリにあるときは、番号のあとに `（<owner>/<repo>）` が付く `親エピック #<E>（<owner>/<repo>）の判断（主の承認ではない）: ` と `主の返事（親エピック で進めた件は、親の判断だったことを完了報告に書く。親の判断は主の承認ではないので、聖域（`CLAUDE.md`・hooks・権限設定など）の変更や破壊的な操作の承認として扱わない（その件は改めて主に聞く）。PR トークン上限への `続ける。新しい上限 <権限>（親の権限。<URL>）` の返事は、主が権限のコメント（`子の PR **記録の形**: 記録を残す止まりは次の形。定型の止まりは記録を残さず発言の `止まった理由:` で渡す。読み手は子の会話を知らない。7 つの項目は順序固定、どの項目も省かない。行頭の `<項目名>:` と同じ行から値を書き、次の項目の行まで複数行可。

```
子の停止: 主の返事待ち
止まった理由: <主にしてほしいこと（決めること 1 つ、または操作）>
主に聞く理由: <主の側にしか答えが無い／決まりで主の承認が要る／主の手でしかできない操作 のどれかで始めて 1 文。論点の有無を添える>
前提: <子が作業中に分かった事実のうち、判断に要るもの>
推奨: <子が勧める答え>
推奨の根拠: <その推奨を選ぶ理由>
受け入れるリスク: <推奨を選ぶことで新たに生じるリスク。何が起きるか・どれくらい起きるか・その根拠>
再開に要る途中経過: <返事を受けて再開するのに要る作業の状態・コミット・PR など>
```

- `主に聞く理由:` は `~/.claude/output-styles/readable.md` 節 3 の「主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作」で始め、1文で書く。承認の決まりなら何を守るかも示す。主だけが持つ観点で結論がよくなる論点を書き、無ければ `論点なし（決まりで聞いている）`。どれにも当たらないなら止まらず進めて事後報告。hook・権限不足・待機などで進めない場合だけ `主に聞く理由: なし（<子の側で進められない理由>）` とする（破壊的操作や聖域は承認待ちに当たる）。
- 記入前に `references/parent-pass-criteria.md`「例」を読む。「主の側にしか答えが無い」なら、(a) ログ・repo・手順書で調べれば分かる事実か、(b) 主の手が要る操作と手順書で確かめたか（「主の作業」だけでは不足）、(c) 推奨と根拠がそろい主の情報が増えないか、を確認。答えが出れば進めて事後報告する。
- `受け入れるリスク:` は推奨で新たに生じるものだけ。無ければ `なし`。一般的な見落としの危険は書かない。被害・戻せるか・発生条件と頻度・根拠（確かめたのか見込みか）を書く。不明なら「分からない」と調べ方を書く
- 該当が無い項目は値を `なし` と書く。推奨を出せない（主の側にしか無い情報が要る）ときは `推奨: なし（<足りない情報>）` と書き、`推奨の根拠:` と `受け入れるリスク:` は `なし` と書く
- 子が作業中に振ったラベル・番号・略称や「上記」「前回」で指さず、中身を書く。PR・issue・コメントにはフル URL を添える。専門用語は初出で一言の言い換えを添える。文章全般の書き方は `rules/communication-style.md` に従う
- 親は記録を正本の段に置き直して主に報告する（手順 8）。`止まった理由` は親が「今回の止まった理由」として読むので変えない

親の側の手順は `references/epic-stop.md` の手順 8。
