# エピックの子が主の返事を待って止まるとき（develop）

develop の SKILL.md から移した節。読むのは、`scripts/epic-dispatch.sh route`（子の番号なし）が `nested` を返すエピックの子のセッションが、主の返事を待って止まる前（質問でターンを終える・質問ツールで待つ・`needs-approval` の保留で止まる）と、`親エピック #` か `主の返事（親エピック #` で始まる入力が届いたとき（起動し直されたセッションの最初の指示に付いて届いたときを含む）。パスの書き方は SKILL.md と同じ。

## エピックの子が主の返事を待って止まるとき

**キャッシュ維持の声かけの例外**: 子は停止前に `references/child-cache-keepalive.json`（プラグイン直下の references）を読み、`separator` で `reply_prefix` と順序付きの `fields`（各欄名の後ろに空白と `<値>`）を連結した型を `request_template` の `{reply_format}` に入れた固定文を覚える。固定文と完全一致する入力を、通常の主の返事や親の判断より先に声かけとして扱う。主が同じ文を入力しても予約文として扱い、送信元の識別はしない。受信ターンではツールを呼ばない（定義の読み直しも含む）。会話だけから各欄の短い値を選び、専用の接頭辞と順序付きの欄を定義の区切りでつないだ一行だけ返す。値に改行や区切り文字を入れない。調査・作業・停止コメントの投稿は行わず、元の質問・停止状態・停止記録を保って待ち続ける。欄の意味の確定や失敗の検出は #1374 に残す。完全一致しない実際の返事は以下の通常の再開手順に従う。

別セッション方式（Orca・tmux）で起動されたエピックの子のセッションが主の返事を待って止まるときの手順。親に止まりを気づかせる手順は無い（親の `wait` が子の会話ログから止まった子に気づく）。子が残すのは、親が読む中身だけで、止まり方で 3 つに分かれる。対象は `scripts/epic-dispatch.sh route`（子の番号なし）が `nested` を返すセッションだけで、それ以外のセッションでは記録を残さない（読む親がいない）。背景のタスクの終わりを待ってターンを終えるだけのときも残さない。

- **記録を残す止まり**: PR のリスク許容の返事を待って止まるとき（pr-review-gate 手順 3 の宣言に対する主の許容を待つとき）だけ、記録先の issue に、1 行目が `子の停止: 主の返事待ち` のコメントを投稿する。それ以外の止まりでは記録を残さない。本文で質問してターンを終えるときも質問ツール（AskUserQuestion）の中で待つときも、質問より先に投稿する。2 行目以降は下の「記録の形」の 7 つの項目で書く。止まるたびに新しいコメントを投稿し、最新の 1 件を正とする。`references/handover.md` の引き継ぎを書く場面では、引き継ぎを先に投稿してから記録を投稿し、`再開に要る途中経過:` に引き継ぎのコメントの URL を書く（ほかの 6 項目も省かない。引き継ぎの書式は変えない）
- **定型の止まり**: PR のマージ待ち・PR トークン上限・CI の見張りで止まるときは、記録を残さず、最後の発言の末尾に行頭 `止まった理由: ` の行を書く。末尾に置くのは、親が読む発言が末尾を残して切られるため。親はこの行で手順を分ける（`references/epic.md` の「回し方」の別セッション方式の手順 8）
  - マージ待ち: `止まった理由: PR のマージ待ち（human-merge）: <PR の URL>` と書く。`--until-merged` の `timeout` で改めて止まるときは `止まった理由: PR のマージ待ち（human-merge、親の返事のあともマージされない）: <PR の URL>` と書く。発言に書く内容は `references/ci-watch.md` の「`ready` を受けたあと」
  - PR トークン上限の exit 2: `止まった理由: PR トークン上限（合計 <合計> / 上限 <上限>）: 続けるか、範囲外として閉じるか` と書き、続けて `終わるまでの見込み: あと約 <残り>（合計の見込み <見込み>）`・`続けるべきか: <続ける／閉じる と理由>`・`次に絞る範囲: <残工程のうち何に絞るか>` の 3 行を書く。親はこれを親の権限に照らす（`references/epic.md` の **PR トークン上限の子**）
  - CI の見張り: `references/ci-watch.md` の 6 の表の `escalate`、`obs.state` が `wait` でない `none`（前回と同じ状態・同じ HEAD の決着。親が追加のやり直しを許したあと同じ HEAD でまた落ちたときはこれになる）、7 の直し方の手順 7（直せないので上げる）のどれかで止まったときは、`止まった理由: CI の止まり（<PR の URL> / <落ちたチェック名> / <HEAD の短い SHA か HEAD 不明>）: <主にしてほしいこと>` と書く。短い SHA は PR の HEAD のコミット SHA の先頭 7 文字で、`ci-watch.sh next` の出力の `obs.head` から取る（手元に無ければ `gh pr view <PR番号> --repo <owner/repo> --json headRefOid --jq '.headRefOid[0:7]'`）。手元の作業ツリーの HEAD は PR の HEAD とずれることがあるので使わない。取れなければ値を作らずに `HEAD 不明` と書く。親が `references/parent-pass-criteria.md` の上限で止まった子の節で `理由:` に写し、過去の `親の判断:` と同じ件かを見分けるため
- **そのほかの止まり**: 記録を残さない止まりでも、読み手は親と主で、どちらも子の会話を読んでいない。最後の発言の中で質問・推奨・根拠を中身で書く（書き方の正本は `rules/communication-style.md`）。定型の止まりの発言も同じに書く
- **親から届いた返事**: `親エピック #<E> の判断（主の承認ではない）:` か `主の返事（親エピック #<E> 経由）:` で始まる入力（エピックが別のリポジトリにあるときは、番号のあとに `（<owner>/<repo>）` が付く `親エピック #<E>（<owner>/<repo>）の判断（主の承認ではない）: ` と `主の返事（親エピック **記録の形**: PR のリスク許容の返事を待つ止まりの記録の形。定型の止まりは記録を残さず、上の `止まった理由:` の行で渡す。読み手は親のセッション・親の決める役・主で、どれも子の会話を読んでいない。2 行目以降に次の 7 つの項目をこの並びで書き、どの項目も省かない。各項目は行頭の `<項目名>:` で始めて値を同じ行に書き、値は次の項目の行まで複数行に続けてよい。

```
子の停止: 主の返事待ち
止まった理由: <主にしてほしいこと（決めること 1 つ、または操作）>
主に聞く理由: <主の側にしか答えが無い／決まりで主の承認が要る／主の手でしかできない操作 のどれかで始めて 1 文。論点の有無を添える>
前提: <子が作業中に分かった事実のうち、判断に要るもの>
推奨: <子が勧める答え>
推奨の根拠: <その推奨を選ぶ理由>
受け入れるリスク: <推奨を選ぶことで新たに生じるリスク。何が起きるか・どれくらい起きるか・その根拠>
再開に要る途中経過: <返事を受けて再開するのに要る作業の状態・コミット・PR など>
```

- `主に聞く理由:` は、主に聞く理由の 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作。正本は `~/.claude/output-styles/readable.md` の節 3）のどれに当たるかを、その語で始めて 1 文で書く。「決まりで主の承認が要る」ときは、その決まりが何を守るためかまで書く。続けて論点（主が持っていて子が持っていない観点を足すと結論がよくなる点）の有無を書く。論点があればその論点を書き、決まりで聞いているだけなら `論点なし（決まりで聞いている）` と書く。3 つのどれにも当たらない止まりは、そもそも止まらずに自分で進めて事後報告するのが正本の決まり。それでも子の側で進められない（ファイル名が理由で読み取りを止めた hook など。破壊的操作や聖域を止めた hook は「決まりで主の承認が要る」に当たる・子の権限では打てない・待つしかない）ときだけ `主に聞く理由: なし（<子の側で進められない理由>）` と書く
- `受け入れるリスク:` には、推奨を選ぶことで新たに生じるもの（他の案や何もしない場合には無いもの）だけを書き、無ければ `なし` と書く。どの変更にも当てはまるもの（「見落としがあると壊れる」）は書かない。書くときは、何が起きるか（被害の大きさ・戻せるか）、どれくらい起きるか（起きる条件と頻度）、その根拠（確かめたのか見込みか）を含める。分からないときは「分からない」と書き、何を調べれば分かるかを添える
- 該当が無い項目は値を `なし` と書く。推奨を出せない（主の側にしか無い情報が要る）ときは `推奨: なし（<足りない情報>）` と書き、`推奨の根拠:` と `受け入れるリスク:` は `なし` と書く
- 子が作業中に振ったラベル・番号・略称や「上記」「前回」で指さず、中身を書く。PR・issue・コメントにはフル URL を添える。専門用語は初出で一言の言い換えを添える。文章全般の書き方は `rules/communication-style.md` に従う
- 親は記録の項目を正本の段に置き直して主に報告する（手順 8）。項目名 `止まった理由` は、最後の発言の定型の行と同じ語で、親が「今回の止まった理由」として読むので変えない

親の側の手順は `references/epic.md` の「回し方」の別セッション方式の手順 8。
