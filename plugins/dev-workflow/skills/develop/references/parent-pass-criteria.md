# 親が通してよい範囲の基準（案）

別セッション方式（起動部品は Orca か tmux）のエピックで、子が主の返事を待って止まったとき（子 issue に 1 行目 `子の停止: 主の返事待ち` の記録がある）、親の側で「通す」（子に返事を送って進めさせる）か「主に上げる」かを決める基準。判断は `scripts/stop-judge.sh` が呼ぶモデルがこのファイルを読んで行い、`scripts/epic-dispatch.sh wait --resolve` が結果に従って返事を送るか親を起こす。起こされた親のセッションも、develop の SKILL.md の別セッション方式の手順 8 で主に上げる前に、同じ記録をこのファイルに照らす。

この基準は案で、中身の最終決定は主が PR で行う。#1030（子の PR のマージ）の「合理性があり危険が低い」は、この基準を参照する。

## 原則

主に聞く理由の 3 つ（主の側にしか答えが無い・決まりで主の承認が要る・主の手でしかできない操作。正本は `~/.claude/output-styles/readable.md` の節 3）のどれにも当たらない止まりは親が通す。主に聞く理由が無いまま主に上げると、主は「なぜ聞かれたのか」を聞き返すことになる。下の通す条件は、その止まりが 3 つのどれにも当たらないことを確かめる手順で、表の「確かめる理由」の列が、条件ごとにどの理由に当たらないことを確かめるかを示す。

## 通す条件

次の 9 つを**すべて**満たすときだけ通す。

| 条件 | 中身 | 確かめる理由 |
|---|---|---|
| 既存の規則が主に聞く止まりでない | PR トークン上限の計測が exit 2 のときの続けるか止めるか、レビューの周の終わりの直し方の判定が「選び直しが要る」とき、PR のマージのように、既存の規則が主に聞くと定めている止まりでない（既存の規則を変えるのはこの基準の範囲外。PR トークン上限の止まりは判断のモデルでは通さず、起こされた親が `epic.md` の手順 8 で親の権限に照らす） | 決まりで主の承認が要る |
| 推奨がある | 子の記録に推奨とその根拠がある（推奨の無い止まりは、主の好みや事業判断を聞いている） | 主の側にしか答えが無い |
| 範囲の内側 | 推奨が、エピックの目的と子 issue の受け入れ条件の範囲を広げず、逆向きにもしない | 主の側にしか答えが無い（範囲を変えるのはエピックと子 issue を決めた主） |
| 聖域でない | 自己統治物件（`CLAUDE.md`・hooks・権限設定・`rules/`・常時注入の予算ファイル）、破壊的な git 操作（`rules/destructive-git-guard.md` の一覧）、秘密情報の値、外部への公開・送信・課金、PR のマージに触れない。作業中のリポジトリの中に試しの issue を作って閉じることは、外部への公開・送信に当たらない | 決まりで主の承認が要る |
| 戻せる | 推奨どおり進めて誤りだったとき、そのブランチの中の commit の取り消しや設定の戻しで戻せる。戻すのにかかる手間が判断できなければ戻せない側に倒す | 決まりで主の承認が要る（回復コストが判断できない操作は主の承認が要る側に倒す決まり） |
| 主の側の情報が要らない | 好み・事業判断・主しか知らない事実・リスクの許容が要らない。記録の「受け入れるリスク」は、エピックや子 issue に既に許容と書かれているか、その子のブランチの中に閉じるものに限る。エピック本文が推奨を決めているときの読み方は、表の下の「エピックの目的・原則から推奨が決まるとき」 | 主の側にしか答えが無い |
| 実機操作でない | MFA・OAuth・ログイン・ダッシュボードの操作など、主の手が要る操作を含まない | 主の手でしかできない操作 |
| 配役表で主の観点が無い | 配役表（`.claude/casting/project.md`・`.claude/casting/local.md`）が渡されたとき、その止まりに要る観点の担い手が主でない | 主の側にしか答えが無い |
| 繰り返していない | このエピックで同じ子の同じ件を既に一度通していて（渡された過去の `親の判断: 子 #N 通した` の行で分かる）、子がまた同じ件で止まっているのでない | 理由ではなく、親の判断が同じ止まりを回し続けないための歯止め |

**子の `主に聞く理由:` の読み方**: 子の記録の `主に聞く理由:` は鵜呑みにしない。書かれた理由が 3 つのどれかに当たるかを確かめ、書かれたことをそのまま通さない理由・主に上げる理由にしない。`主に聞く理由: なし（…）` や、3 つのどれにも当たらない理由は、通す側で読む（子の側で進められないだけで、主に聞く理由は無い）。項目の無い記録（`主に聞く理由:` を足す前の形）は、ほかの項目から判断する。

**エピックの目的・原則から推奨が決まるとき**: エピック本文の目的・原則・決まった方針が子の推奨を一意に決める（推奨以外の選び方が、その目的・原則・方針に反する）ときは、それを根拠に「主の側の情報が要らない」を満たすと読む。主はエピックを書いた時点でその答えを出していて、子の止まりで聞き直しても主の側にしか無い情報は増えないからである。根拠にできるのは、判断に渡されたエピックの本文に書かれた文だけで、親や子が推し量った意図・会話で出た話・子の記録にしか書かれていない原則は根拠にしない。通すときの `理由:` には、根拠にしたエピック本文の文を短く引く。この読み方が効くのは「主の側の情報が要らない」の 1 条件だけで、ほかの 8 条件は今までどおりすべて満たす必要がある。推奨が聖域や破壊的操作に触れるとき、推奨どおり進めるとエピックや子 issue に許容と書かれておらず、その子のブランチの中にも閉じないリスクを受け入れることになる（リスクの許容が要る）ときは、目的・原則が推奨を決めていても通さない。目的・原則から推奨が 1 つに決まらない（2 つ以上の選び方が両立する、原則どうしがぶつかる、原則の語が 2 通り以上に読め、読み方で推奨が変わる）ときはこの読み方を使わず、下の「迷ったとき」に従う。

**迷ったとき**: 1 つでも満たさないか、満たすか判断できなければ「主に上げる」。主に聞く理由が成り立つか迷うときは、成り立つ側に倒す。通してよい止まりを主に上げても主の手間が増えるだけで危険は無いが、通してはいけない止まりを通すと主の承認なしに進む。

PR のマージの可否は、この基準で通さない（#1030 の手順に任せる）。既存の規則が主に聞くと定めている止まりも、この基準で通さない。

## 例

2026-10-01〜10-14 の止まり 35 件から（通る例のうち試しの issue 作成・子の起動し直し・CI の再実行の 3 つは、#1176 の背景にある、主が「なぜ聞かれたのか」と聞き返した場面から。エピック本文の原則が推奨を決めていた例は、2026-10-19〜20 の夜に親が主に上げた止まりから）。

通る例:

- hook が止めたファイルの読み取り（リポジトリの中のソースで、ファイル名が理由で止められたもの）
- 手順外の判断を推奨どおり受け入れること（推奨と根拠があり、子のブランチの中で戻せるもの）
- 自分の実行の配下で暴走したプロセスの停止（他のプロジェクトのプロセスは含まない）
- 実機テストのための試しの issue 作成（作業中のリポジトリの中で、閉じれば戻せる）
- 止まった子の起動し直し（親が `scripts/epic-dispatch.sh reply --relaunch` でできる）
- Mac が空いてからの CI の再実行（待って打ち直すだけで、主の判断も主の手も要らない）
- エピック本文の原則「オーナーと客の環境で仕組みを分けない」が、子の推奨をそのまま決めていた止まり（分ける案は原則に反し、推奨は原則から 1 つに決まる。聖域にも破壊的操作にも触れず、子のブランチの中で戻せる）

通らない例:

- PR のトークン上限の引き上げ。判断のモデルには親の権限（エピックの `子の PR トークン権限:` のコメント）が渡らないので通さない。起こされた親が `epic.md` の手順 8 の専用の手順（**PR トークン上限の子**）で権限に照らし、権限の内なら親が続けさせる
- レビューの周の終わりで、直し方の判定が「選び直しが要る」ときの続行（既存の規則が主に聞く止まり）
- マージの承認（#1030 の手順に任せる）
- 聖域のファイルの変更（`CLAUDE.md`・hooks・権限設定・`rules/`・常時注入の予算ファイル）
- 実機操作（MFA・OAuth・ログイン・ダッシュボードの操作）
- 主しか知らない設計意図を聞いている止まり
- 通る例の最後と同じ型でも（エピック本文の原則が推奨を決めていても）、推奨どおり進めるとエピックや子 issue に許容と書かれておらず、その子のブランチの中にも閉じないリスクを受け入れることになる止まりや、聖域・破壊的操作に触れる止まり（例: 環境をそろえる原則に沿うために、本番のデータを消す・秘密情報の値を入れ替える）

## 出力の形

判断は次の 3 行だけを出す。前置き・説明・コードブロックを付けない。

```
判断: 通す
理由: <1 行。どの条件をどう満たしたか、または満たさなかったか>
返事: <1 行。通すときに子へ送る文。主に上げるときは空でよい>
```

1 行目は `判断: 通す` か `判断: 主に上げる` のどちらか。`stop-judge.sh` がこのうしろに 4 行目 `記録: <停止の記録のコメントの URL>` を付ける。形が崩れた出力は通さず、親を起こす側に倒れる。

## 守備範囲

判断に渡すのは、`stop-judge.sh` が集めるものだけ（エピックの本文、子 issue の本文と投稿者が OWNER・MEMBER・COLLABORATOR の `親エピックからの注意書き:`、子の最新の停止の記録、同じ子への過去の `親の判断:`（この 2 つも投稿者が OWNER・MEMBER・COLLABORATOR のもの）、このファイル、あれば配役表）。親や子の会話は入らない。

拾いたい誤りは、主の承認が要る止まり（聖域・破壊的操作・既存の規則が主に聞くと定めたもの・マージ）を通すこと、推奨の無い止まりや主の側の情報が要る止まりを通すこと、戻せない操作を通すこと、同じ件を通し続けること、主に聞く理由の 3 つのどれにも当たらない止まりを主に上げることの 5 つ。子の記録の 2 行目以降の項目名や並びの違い（形は #1036。`主に聞く理由:` の無い以前の形の記録を含む）、通してよい止まりを判断のモデルが主に上げること（手順 8 の親がもう一度照らす）、通した判断があとで主に止められることは、この基準では止めない。基準をすり抜ける止まりが見つかるたびに条件を足して塞ぎ切ることは目的にしない（主が PR と 2 週間後の再集計で見直す）。
