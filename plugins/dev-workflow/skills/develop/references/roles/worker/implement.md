# W（作業者）の指示書 — 実装と検証（`段: implement`）

(3a) と、G の `agent-review:failed` や CI の見張りの `fix` を受けた修正で読む。全段で要る規則は `worker/common.md`。

## (3a) 実装＋verify（TDD 徹底）

単一 change 1 つ分の実装手順。仕様化する場合と直行する場合で入口が違うだけで、**テストを先に書く**のは共通。**この節は verify までで終わる**（archive 以降は `worker/finish.md` の (3b)）。

**仕様化する場合**: `tasks.md` を上から TDD で実装し、終えた項目を `[x]` にする。`openspec validate <change-name> --strict` を実行し、担当した項目のチェックボックスを確認する。(3a) は verify までで return し、`openspec archive <change-name> --yes` は (3b) で行う。

**文言合わせの通し方の場合**（記録先の最新の仕様化判断のコメントに `通し方: 文言合わせ` の行がある）: `tasks.md` が無いので、(1) の return に書いた作業項目（手渡しで起こされたときは本体から渡された作業項目）を TDD で実装する。検証は `openspec validate <change-name> --type change --strict` で行う（change に proposal.md が無いので、`--type change` を付けない形は change を見つけられず `Unknown item` で終了コード 1 になる。`openspec validate --changes --strict` はこの change を検査せずに終了コード 0 を返すので使わない）。チェックボックスの確認は行わない。実装の途中で対象から外れると分かったら（新しい要件が要る・設計の選択が出た・2 つ以上の capability に広がった）、手を止めて return する（そのあとの扱いは `worker/spec.md`「仕様化する場合（(1) の終わり）」）。

**コード直行する場合（仕様化不要）**:
1. 実装前に必ず codebase を grep して既存実装を確認する（二重実装しない）
2. 受け入れ条件・期待動作を**テストとして先に書く**（Red）
3. テストが通る最小実装を書く（Green）
4. リファクタする（Refactor）
5. 下の「全経路共通の大原則」に従って検査を実行し、**exit code と出力の要約をターン内に表示してから**「完了」を宣言する。自己申告のみの完了宣言は禁止

**全経路共通の大原則**:

CLI 経路とコード直行の両方に適用する。
- 実装後、対象リポジトリの `.github/workflows/*.yml` / `*.yaml` を読み、`pull_request` / `push` で起動するジョブの `run:` ステップから検査コマンド（lint・test・ビルド等）を収集し、種類ごとに次のとおり扱う。環境セットアップ（依存インストール等。例: `sudo apt-get install`）と判別し、検査として実行しない。`pull_request` / `push` 以外で起動する運用系ワークフロー（例: `auto-merge.yml`、`revert-pr.yml`）は対象外。コマンド名をこのリポジトリ固有の値に固定しない。手元にツールが無く実行できない検査は「未導入」として実行結果と区別し、合格扱いしない
  - lint・型検査などの静的検査は手元で実行する。ツールがファイルを引数に取れるなら変えたファイルに当て、取れないなら CI と同じ形で実行する
  - テストの全体実行（テストランナーをファイルで絞らずに起動するもの）とビルドは手元で実行しない。全体は CI に任せる。代わりに、変えたファイルに関係するテストだけをテストランナーにファイルを渡して実行する
  - 関係するテストは次の和集合: この変更で足した・変えたテストのファイル、テストのファイルのうち変えたファイルのパスかファイル名を含むもの（`git grep -l` 等で探し、探したコマンドを return に書く）、テストランナーが変えたファイルから関係するテストを選ぶ機能を持つならその結果（例: `jest --findRelatedTests`）、CI の見張りの `fix`（`plugins/dev-workflow/references/ci-watch.md` 7）で直すときは、落ちた run のログ（`gh run view <run> --log-failed`）に出たテストのファイル
  - PR・push で起動して全体のテストを回すジョブが無い（workflow が無い、テストのジョブが無い、検査コマンドを判別できない）ときは、全体のテストを CI に任せられないので、手元で全体を実行する（`scripts/test.sh` 等の慣例コマンドへのフォールバックを許す）。Draft では CI を走らせないリポジトリは、Ready にした時点で CI が走るので CI に任せられる側に数える
- この指示の守備範囲の入力は、PR・push で起動する workflow の `run:` ステップと変えたファイルの一覧。拾いたい誤りは、CI が流す静的検査の取りこぼし（PR #489 の shellcheck）と、変えたファイルを名前で参照するテストの失敗をゲートより後まで持ち越すこと。変えたファイルを別のスクリプト経由で間接的に読むテストを拾えないことはこの要件で止めない（CI とゲート合格後の CI の見張りが拾う）。`matrix` / `services` / `env` / `if:` 条件による CI と手元の再現差、ランナー依存の検査、環境セットアップの `run:` ステップの誤実行もこの要件で止めない。取りこぼしを塞ぎ切ることを完了条件にしない。CI が実際に落ちるかどうかは、G が pr-review-gate 手順 4 で対象 HEAD の CI の結果を証拠として見ることに加え、ゲート合格後の CI の見張り（`plugins/dev-workflow/references/ci-watch.md`）が拾う。最後の防波堤は合格後の CI の見張りで、auto-merge を配備したリポジトリでは必須チェックが緑になるまでマージされない
- **長時間処理（フルテスト・ビルド）の完了を待つ目的でターンを終えない。** 待ちは同一ターン内の前景ポーリングで行う（正本: `plugins/dev-workflow/references/subagent-waiting.md`。雛形と上限はそこにあり、ここには再掲しない。総待ちの上限に達したら待ちをやめて本体に return する）
- プレースホルダ・空実装・コンパイルを通すだけの実装で済ませない
- 完了・合格の宣言には必ず証拠（実行コマンドと exit code）を付ける
- 作業の節目ごとに commit → push（記録先が Draft PR なら PR が逐次更新される）

**G から一覧を求められた指摘（仕分け表の順 3・順 6 の「全部列挙してから直す」）**: 修正前 SHA（修正に着手する直前の HEAD の 40 桁。G はこのコミットと HEAD の 2 段で照合する）、検索コマンド（grep の語なら修正前 SHA と HEAD に差し替えて実行できる `<rev>` を含む形、または場合分けの軸とその全域）と、全ヒットごとに「直した／該当しない理由」を付けた表を PR コメントに投稿してから push する。grep の語で、「該当しない」とした行の本文を同じ周の修正で書き換えたなら、主表の本文は修正前のまま残し、その行を修正後の本文とあわせて補助表 `### 書き換えた該当しない行` に載せる（G はその検索コマンドを自分で実行して集合の一致だけを見るので、投稿が push より後だと照合できない）。書式の正本は pr-review-gate の SKILL.md 手順 2-1 の仕分け表の順 3 で、ここには再掲しない。

**(3a) の return に書くこと**（1 行目は `工程完了: 実装＋verify`）:

- **収集した検査コマンドの一覧、手元で実行した検査（関係するテスト・静的検査）のコマンドと各 exit code、関係するテストを探したコマンド、手元で実行せず CI に任せた検査とその CI のジョブ名**（未導入の検査は「未導入のため未実行」と明記し、合格扱いしない。失敗が残っていればその件数も。CI に任せた検査は合格扱いしない）
- **`openspec validate <change-name> --strict` の exit code**（仕様化した場合。直行した場合は「仕様化しないため verify なし」と書く）
- 編集したファイルの一覧・自分で埋めた決定・昇格トリップワイヤーの発火有無・読んだコードの要点（書式は `worker/common.md`「コンテキスト上限と手渡し」）・残作業
- `画面確認: 不要` または `画面確認: 要る — <開く URL か起動手順> / <見る点>` を 1 行。受け入れ条件または記録先の動作確認ポイントが画面観測を求めるかで決める。要る場合は URL か起動手順と見る点の両方を書く。W 自身は画面で確認しない
- 仕分け表の順 4（今直す 3 条件）で直した指摘があれば、指摘ごとに「受け入れ条件の外・その場で直した・直し方 N 行」の記録（G が仕分け欄に写す）

この 2 つ（検査コマンドと各 exit code、`openspec validate --strict` の exit code）を必ず載せるのは、(3b) の担い手が pr-review-gate 手順 5 が照合する動作確認の証拠を書くための唯一の入力になるためである。手渡しが起きると後任は前任の履歴を読めないので、証拠が return に無ければ関係するテストを選び直して回し直すか証拠なしで宣言するかのどちらかになる。
