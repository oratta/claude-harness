# 親が子の停止を扱うとき（develop）

止まった子の処理前に読む。主への発言は `references/epic-loop.md`「主への報告」を先に読む。子の記録の形は `references/epic-child-stop.md`、声かけの扱いは `references/epic-keepalive-watch.md` を読む。別 repo の子なら `references/epic-multirepo.md` も先に読む。

## 主が子のタブで話している子（`owner-away`）

`wait --watch-stopped` が `owner-away <N>...` で起こしたら、子 `<N>` は主が子のタブで打った入力から始まったターンが `主の返事待ち` のまま `EPIC_DISPATCH_OWNER_AWAY_SEC`（既定 3600 秒）以上たっている。主に「子 #N のタブで問いが残っている」と知らせる（問いは `child-log --last <N>` の `.text`。書き方は `references/epic-loop.md`「主への報告」）。**子に返事を送らず、端末を閉じず、`reply --relaunch` も呼ばず**、手順 8 の判断・委任にも回さない。知らせたら、同じ出力のほかの行を `references/epic-loop.md` の手順どおりに処理し終えてから手順 2 に戻って掛け直す。`owner-away` の行だけなら同じ引数で掛け直す（同じ出力に `closed <N>` や `stopped <N>` が並ぶのに先に掛け直すと、閉じた子を位置引数に残したまま待ちに戻り、その処理が抜ける）。同じターンでは二度出ない。

## pending-owner の復元

`pending` の子ごとに、手順 8 と同じ照合で最新の `親の判断:` が「通した」以外（`主に上げる`・`判断できなかった`・一致なし）なら、手順 8 と同じに扱い（照らして通すか、報告を本文で出し直す）、待ちに入る（最新の `親の判断:` が `親の判断: 親の操作が要る` の子は、手順 8 の **親の操作が要る子** と同じく操作をしてから返事を送り、照らし直さず出し直さない。今回の停止の記録・未回答の停止の記録・`.questions`・`unreadable` が無く、最後の発言に `止まった理由:` の行も無く、主への問いでもなければ、手順 8 と同じく `dismiss` で戻して出し直さない。`親の判断: 通すが送れなかった` は手順 8 と同じく送り直す。子 issue のコメントの新旧では再開を判定しない）。報告を出し直した子には、待ちに入る前に手順 8 と同じく `scripts/epic-dispatch.sh told <N> <止まりの uuid>` を呼ぶ。ただし、エピックのコメントの `親の判断: 子 #N 通した`（手順 8 と同じ author_association の条件）で、その行の `発言 <uuid>` が記録の `stop_uuid` と一致するもの（`stop_uuid` が空の止まりは、行の停止の記録の URL が子の最新の `子の停止: 主の返事待ち` の URL と一致するもの）がある子は、通して送った解決済みの件（子の会話ログがまだ進んでいないだけ）なので再報告から外す。

**PR トークン上限の子**: 手順 8 で、今回の止まった理由が `PR トークン上限（` で始まる子は、`parent-pass-criteria.md` に照らし直さず、親の権限に照らす（判断のモデルには権限が渡らないのでこの止まりを通さず、起こされた親が扱う）。権限は、エピックの 1 行目が `子の PR トークン権限: <値>` のコメントのうち、投稿者の `author_association` が OWNER・MEMBER・COLLABORATOR の最新の 1 件の値。照らす前にそのコメントが無ければ、`references/epic-loop.md` の「経路の決め方」と同じく既定値で投稿して主に伝えてから（値は 60000000。unmanned はコメントだけ）、その値で照らす。コメントはあるのに値が数字として読めないときは主に上げる。次の 2 つをどちらも満たすときだけ通す: (a) 合計の見込みが権限以下（`止まった理由:` の行に続く `終わるまでの見込み:` の行の「合計の見込み」。更新前の版の子は記録の `前提:` の中の同じ行）、(b) 今回の止まった理由の上限が権限より小さい（`上限 <上限>`）。見込みが書かれていない・読めないときは主に上げる。(b) があるので、権限まで上げてもまた止まった子は主に上がり、主が権限を広げない限り同じ子を二度通すことは起きない（基準の「繰り返していない」はここでは照らさない）。主の承認は主が権限を決めたこと（既定値を伝えたこと、または主が広げたこと）で済んでいるので、基準の聖域の「課金」にも照らさない。通すときは `scripts/epic-dispatch.sh reply --as parent <エピック番号> <N> '続ける。新しい上限 <権限>（親の権限。<権限のコメントの URL>）'` で送り、送れたらエピックに `親の判断: 子 #N 通した — PR トークン上限を親の権限 <権限> まで上げた（合計の見込み <Y>） 発言 <止まりの uuid> <停止の記録の URL>` の 1 行を残す（uuid が空なら `発言 <止まりの uuid> ` を書かない。今回の停止の記録が無ければ `<停止の記録の URL>` を書かない）（`PR トークン上限:` は返事を受けた子の本体が記録先に書く。書式の正本は `references/pr-token-budget.md`「記録先がエピックの子のとき」の 4 行の上限コメント書式）。通さないときは手順 8 の形で主に上げ、権限の値と権限を広げる選び方（新しい権限の値を答える）を添える。主が権限を広げて答えたら、親は新しい値で権限のコメントを `主の発言: <要旨>` の行つきで投稿し直し、同じ止まりを (a)(b) に照らし直して、満たせば `reply --as parent` で新しい上限 ＝ 新しい権限を送り、満たさなければもう一度主に上げる。主が権限を広げずに「続ける」とだけ答えたら、手順 8 のとおり `reply --as owner` で届け、子の本体は今の式（合計 ＋ 直前の上限）で新しい上限を書く。サブエージェント方式では、親を兼ねる本体がこの段落の権限の読み方と (a)(b) を使い、子の記録先の計測の exit 2 で主に聞く前に照らす（手順は `references/pr-token-budget.md`「記録先がエピックの子のとき」）

**主の委任**（手順 8 の続き。別セッション方式の親だけ。受ける／取り消す／適用する前に `references/epic-delegation.md` を読む）: 主が一度確かめた委任で、子の止まり（PR のリスク許容は確認より前に止まったものも含む。委任の種類によっては、確認のあとに止まった聖域の変更・破壊的な git 操作・論点なしの確認で通ったマージ待ち）を、主に上げずに親が送る経路。委任の返事を子がどう確かめるかは `references/epic-child-stop.md` の「親から届いた返事」、ゲートの記録と真正性確認の正本は pr-review-gate の `stages/authenticity-delegated.md` 手順 5 の「主の委任で親経由に受けた許容（親経由で受領（委任））の真正性確認」。

- **委任の受け方**: 主が親のタブで子の止まりを任せる旨を述べたら（例「このエピックの子の許容は全部答えて」）、その発言だけを委任として扱わない。エピックの issue に `references/epic-delegation.md` の 3 つの形のどれかの定型の委任の記録を投稿する（`主の委任: リスク許容` は問いの形もきっかけの形も 1〜4 行目が、`主の委任: 論点なしの止まり` は 1〜5 行目が、この文字列ちょうど。`<E>` はエピックの番号）。主が任せた範囲がリスク許容だけか論点なしの止まり全体か読めないときは、狭い側の `主の委任: リスク許容` を投稿する。**きっかけの形**（`主の委任: リスク許容` だけ）: 次の 3 つをすべて満たす発言だけをきっかけの形で受ける。①発言の全文だけから、子の止まり（リスク許容）を親に任せる旨が読める（対象を書かない「任せる」だけの短い発言は当たらない） ②任せる対象が、親が報告した 1 件の止まりや親の問いの件に限られない（「この件は任せる」「それでいい」のように、直前の親の発言を読まないと対象が決まらない発言は当たらない。親が 1 件の止まりを報告した直後の発言でも、全文だけから①が読めれば当たる） ③任せる範囲から子・止まりを除いたり、期限や条件を付けたりしていない。当たる発言を受けたら、そのターンのうちに（主の次の発言より前に）、4 行目をきっかけの形の `期間:` にし、5 行目の `きっかけ:` にその発言の全文を書いた記録を投稿し、問わない。きっかけの発言そのものを委任の確認とし、下の「委任の確認の場所」を残し、「委任で送る」の同じターンに送る子に送ってから、本文で、記録の URL と記録の `範囲:` と `期間:` の文と、取り消すときは取り消す旨を述べればよいことと、同じターンで委任を当てて送った子（子の番号と停止の記録の URL。無ければ無い旨）を、`~/.claude/output-styles/readable.md` の節 3 の主がすることは無い報告の型（1 行目 `主がすること: なし`）で書く（主に `任せる` と打たせない）。主の次の発言より前に記録を投稿できなかったとき、または「委任の確認の場所」の `--delegated-trigger` が通らなかったときは、きっかけの形を使わず、問いの形で受け直す。3 つのどれかを満たさない発言はきっかけの形にせず、全文が子の止まり全般を任せる旨とも読める発言（「#2058 以外の子の許容は任せる」「今日の分だけ子の許容は任せる」など）だけを問いの形で受け、ほかは元の問い・報告への答えとして扱う。除外・期限・条件の付いた発言で問うときは、問いの本文に、定型の範囲と期間には主の付けた除外・期限・条件が入らず、確認すると除いた子や期限のあとにも効くことを書く。**問いの形**（`主の委任: 論点なしの止まり` と、きっかけの形で受けられなかった `主の委任: リスク許容`）: 投稿したら本文で（質問ツールで聞かない）、記録の URL と、記録の `範囲:` と `期間:` の文を書いて、この範囲で子の止まりを任せてよいかを問う。問いは `~/.claude/output-styles/readable.md` の節 3 の型で書き、アクションの行に、親のタブで `任せる` と打つことを書く。問いのあとの主の発言のうち、全文から任せる意思が読める最初の発言を委任の確認とし、確認を受けるまで委任で返事を送らない。問いと確認のあいだに主の別の発言が挟まっただけでは問い直さない（子の `--delegated` も挟まった主の発言では落とさない）。挟まった発言が委任を取り消すか範囲を変える内容なら（「マージは除いて」など）、委任を使わず、範囲を直した記録を投稿して問いを本文で出し直す。問いのあとの主の発言のどれからも任せる意思が読めないとき（「ちょっと待って」など）も、委任を使わず問いを出し直す。主が `任せる` 以外の語で答えても、全文から任せる意思が読めれば確認として受ける


- **委任の確認の場所**: 確認を受けたら（きっかけの形では記録を投稿したら）、`bash <plugin>/scripts/owner-reply-check.sh --locate "$CLAUDE_CODE_SESSION_ID" <確認の全文>`（きっかけの形ではきっかけの発言の全文）を回し、`MATCH:` のうち全文が確認と同じ（どちらも連続する空白を 1 個にまとめて比べる）で timestamp がいちばん新しい行の uuid を取る。きっかけの形では、次の行を投稿する前に `bash <plugin>/scripts/owner-reply-check.sh --delegated-trigger "$CLAUDE_CODE_SESSION_ID" <uuid> <委任の記録の作成日時> <きっかけ: の値>` を回す（4 番目の引数は、投稿した記録を `gh api repos/{owner}/{repo}/issues/comments/<comment_id> --jq .body` で読み直した `きっかけ:` の値で、5 行目の `きっかけ: ` のあとから本文の終わりまで。会話の発言から写し直さない）。exit 0 でなければその記録を使わず、次の行を残さず、問いの形で受け直す。通ったら、エピックに `委任の確認の場所: セッション <親のセッション ID> / uuid <uuid> / 記録 <委任の記録の URL>` の 1 行を投稿する（`主の委任:` で始めない。期間の「次のコメント」に数えないため）。uuid を引けないときは委任を使わない。起動し直したあとは、最新の `主の委任:` で始まるコメント（投稿者が `OWNER`・`MEMBER`・`COLLABORATOR` のもの）の URL を `記録` に持つ最新の `委任の確認の場所:` の行からセッション ID と uuid を取り、引けなければ委任を使わない
- **取り消し**: 主が委任の取り消しを述べたら、親はその発言を受けた次のターンの最初のツール呼び出しで、エピックに 1 行目 `主の委任: 取り消し` のコメントを投稿し、以後は委任で返事を送らない（止まった子は今どおり主に上げる）。失効と投稿者の条件は `references/epic-delegation.md`。

- **委任で送る**: 手順 8 で、今回の停止の記録があり、委任が有効で止まりに委任が効くときだけ、主に上げずに `scripts/epic-dispatch.sh reply --as owner <エピック番号> <N> <返事>` で返事を送る。返事は止まりの種類で分け、リスク許容の止まりは `許容する（主の委任による。停止の記録: <URL>） [主の委任: セッション <親のセッション ID> / uuid <確認の uuid> / 記録 <委任の記録の URL>]`、聖域の変更・破壊的な git 操作の止まりは `進める（主の委任による。停止の記録: <URL>）: <変更するファイルかコマンドの全文>。実行の時機: <いつ> [主の委任: セッション <親のセッション ID> / uuid <確認の uuid> / 記録 <委任の記録の URL>]`（`rules/destructive-git-guard.md` の「タイミングと方法まで」を返事で満たす）にする（セッション ID と uuid は `委任の確認の場所:` の行の値。起動し直すかは `reply` が表で自動判定する）。出力が `sent` か `relaunched` なら、エピックに `委任で送った: 子 #<N> <停止の記録の URL> 委任の記録: <委任の記録の URL>` の 1 行を残す（`親の判断:` で始めない。`stop-judge.sh` と手順 8 の `親の判断:` の照合に混ざらないため）。`failed <N> <段>` なら主に報告する。委任が有効でないか止まりに委任が効かないときは委任で送らず、手順 8 の形で主に上げる。**確認の直後に送る**: `委任の確認の場所:` の行を投稿した同じターンで、エピックの子のうち `scripts/epic-dispatch.sh pending-owner <子>...` が `pending <N>` を返す子（`wait` が止まりとして受け、そのあと会話ログが進んでいない子）について、手順 8 と同じ今回の停止の記録（子 issue の `子の停止: 主の返事待ち` で始まるコメントのうち、作成時刻が `child-log --last <N>` の `.last_input_at` 以降の最新のもの）を読み、それがリスク許容の止まりで委任が効けば同じ返事を送り、`委任で送った:` の行を残す（`wait` は報告済みの止まりを返し直さないため。委任の確認より前に止まった子にも効く）。今回の停止の記録が無い子と、`pending <N>` が返らない子（主が子のタブで話し始めた子など）には送らない
- **二重送信の防止**: 子が委任の返事を受けて G を起こすまでのあいだ、手順 7・8 で同じ子が再び挙がりうる。手順 7・8 で同じ子が再び挙がったとき、その子の `委任で送った:` の行の URL が今回の停止の記録の URL と同じなら送り直さず子の再開を待つ。子が止まり直して停止の記録の URL が変われば、その止まりに委任が効くかを確かめ直して送る
- **守備範囲**: ①入力の出どころは、親の会話の主の発言、エピックと子 issue と PR のコメント・ラベル（`gh` で読む）、同じ PC の親の会話ログ。親は協力的だが、主の雑談を委任と読み違える・別の子の止まりと取り違える前提で扱う ②拾いたい誤りは、確認の無い発言での委任（きっかけの形では、きっかけの全文が主の発言と違う・記録より前に主が次の発言をしていた・直前の親の発言を読まないと対象が決まらない発言（「この件は任せる」「それでいい」など）をきっかけにした・除外や期限や条件の付いた発言をきっかけにした）、範囲外の止まり（論点ありの止まり・推奨が許容でも進めるでもない止まり・委任の種類が効かない種類の止まり・論点なしの確認の無いマージ待ち・実機操作・確認より前の聖域の変更と破壊的な git 操作の止まり）への送信、取り消し後の送信、二重送信 ③確認に `任せる` 以外の語で任せる意思が読める答えと、問いと確認のあいだに委任を取り消しも範囲を変えもしない主の発言が挟まった確認と、主が会話で任せる旨を述べたきっかけの発言そのものを確認にしたリスク許容の委任と、委任の確認より前に止まったリスク許容の止まりへの送信は通してよい ④穴を塞ぎ切ることは完了条件にしない
