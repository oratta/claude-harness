# 親がマージ待ちの子を扱うとき（develop）

処理前に `references/epic-loop.md`「主への報告」、`references/epic-stop.md` 手順 8 を読む。委任がある場合は `references/epic-delegation.md`、別 repo の子なら `references/epic-multirepo.md` を先に読む。

**マージ待ちの子**: 手順 8 で主に上げることになった子（一致する `親の判断:` が無いときと、それ以外のときのどちらも）のうち、今回の止まった理由が `PR のマージ待ち（` で始まる子は、主に上げる前に次を行う（子の側の手順は `references/ci-watch.md` の「`ready` を受けたあと」。それ以外の止まりは手順 8 のとおり）。まず前提を `gh` で確かめ、1 つでも満たさなければ決める役を起こさずに`references/epic-stop.md` の手順 8 の形で主に上げる: PR の base ブランチの `auto-merge.yml`（`gh api "repos/<owner>/<repo>/contents/.github/workflows/auto-merge.yml?ref=<PR の base ブランチ>" --jq .content | base64 -d`）に `parent-merge-approved` の語がある（原本を展開し直していないリポでは印が効かない）／PR が open で、見送りラベル（`human-merge`・`needs-human-merge`・`human-only`・`needs-approval`）のうち付いているのが `human-merge` だけ／`止まった理由:` の行の PR の本文で最初に現れる `Closes #N`・`Fixes #N`・`Refs #N` の `N` が子 issue の番号である／PR に、今の HEAD を `親が見た HEAD:` に持つ `親のマージ判断: 可` のコメントがまだ無い（あれば自動マージの処理の側が止めているので、対象リポの `docs/auto-merge.md` のトラブルシュートの項目 10 を添えて上げる）。前提を満たしたら `subagent_type: dev-workflow:decider` を起こし、`references/parent-merge-criteria.md` で判断させる（本体は自分で可否を決めない）。決める役は `Bash` を持たないので、エピックの本文、子 issue の本文と投稿者が OWNER・MEMBER・COLLABORATOR の `親エピックからの注意書き:`、子の最後の発言の全文（更新前の版の子は停止の記録）、PR の本文とラベルと今の HEAD の SHA（`gh pr view --json headRefOid`）、変更ファイルの一覧と差分、PR のリスク宣言・動作確認・ゲートのコメント、CI の結果（`gh pr checks`）、取得した `auto-merge.yml` の `# >>> sacred-paths` 〜 `# <<< merge-condition-paths` の行、`human-merge` を付けた自動マージの処理の投稿（`🔒 **auto-merge 対象外（聖域パス接触）**` で始まるもの）、あれば配役表、有効な `主の委任: 論点なしの止まり` があれば、その記録の本文と URL、親が確かめた `委任の確認の場所:` の行を入力文に貼る（委任が無いと、決める役は「主の側の情報が要らない」の委任の条件を確かめられない）。`裁定: 可` なら、古い HEAD の判断で付けた `parent-merge-approved` が PR に残っていれば先に外し（`gh api -X DELETE "repos/<owner>/<repo>/issues/<PR番号>/labels/parent-merge-approved"`。付いたままでは付け直しても新しい `labeled` が起きず、自動マージの処理には `issue_comment` のきっかけが無いので日次の判定まで走らない）、そのあと PR の今の HEAD を `headRefOid` で取り直して決める役に渡した HEAD と一致することを確かめ（一致しなければ印を付けずに主に上げる）、PR に 1 行目 `親のマージ判断: 可`・2 行目 `親が見た HEAD: <40 桁 SHA>`・3 行目 `理由: <決める役の理由>` のコメントを投稿してから `parent-merge-approved` ラベルを付ける（ラベルが付いた瞬間に自動マージの判定が走るので、コメントを先に置く）。続けて `scripts/epic-dispatch.sh reply --as parent <エピック番号> <N> <返事>` で、自動マージの処理に回したこと・子は `ci-watch.sh wait --until-merged` で見届けること・子は何も承認せず印も付けないことを伝え、エピックに `親の判断: 子 #N マージに回した — <理由> <PR の URL>` の 1 行を残す（`通した` と書かない。`stop-judge.sh` が同じ子の `通した` を繰り返しの判定に使うため）。`reply` が `failed` なら主に報告する（印は外さない）。否・不足・形が崩れた出力・迷ったときは、印を付けずに`references/epic-stop.md` の手順 8 の形で主に上げ、PR の URL と決める役の理由（`不足:` なら足りないもの）を含める。判断の印（ラベルとコメント）を付けるのは本体だけで、子は付けない。印が数えられるのは、`gh` の認証アカウントが対象リポの OWNER・MEMBER・COLLABORATOR のときだけ。
