# レビューの周を主に聞かずに続ける（develop）

develop の SKILL.md から移した節。読むのは本体で、SKILL.md の 1 ループの (2) で R1 の結果の BLOCKER に `条件の問い:` の行があるときと NOTE に `後で成り立つ:` の行（後で成り立つ指摘）があるとき（周によらず）、R1 が 2 周目以降の周の終わりに `REQUEST_CHANGES` を返したときと、(4) で G が `needs-fix-check` を返したとき（その分岐の手順に入る前に Read する）。指摘が返らなかったサイクルでは読まない。パスの書き方は SKILL.md と同じ。

## 残った指摘の条件を確かめる

仕様レビュー（R1）の残った BLOCKER の条件を確かめる本体の手順（#1121）。この節が正本。条件を判定するのは R1 だけで（表と根拠は `references/roles/spec-reviewer.md` の節「指摘の条件を決める段」）、本体は自分で判定せず、R1 の結果を読んで当て直しを依頼する。

**通す時点**: 次の 3 つの時点でこの節の手順を通す。R1 の NOTE に `後で成り立つ:` の行があるときは、周と結果によらず段落「NOTE の後で成り立つ指摘」だけを当て、手順は通さない。

1. R1 の `REQUEST_CHANGES` の BLOCKER に `条件の問い:` の行があるとき、周によらず W を再開する前
2. 2 周目以降の周の終わりに BLOCKER が残ったとき、決める役を起こす前
3. 直し方の判定が「選び直しが要る」で主に聞いた問いへの答えが条件についての答えのとき、W を再開する前

**手順**: 次のどれかに当たる限り、W を再開せず決める役も起こさず、R1 に指摘の当て直しをさせる。どれにも当たらなければ主に聞かず R1 も起こさず、2 周目以降の周の終わりに BLOCKER が残っていれば直し方の判定に進み、それ以外は通常の流れに戻る。

- `条件の問い:` の行がある BLOCKER がある。本体は問いを主に聞き、答えを 1 行にしてエピックの本文（エピックの子でなければ記録先の本文）の節 `## 条件の答え` に足す（節が無ければ作る）。引き継ぎを残して止まったあと新しいセッションで再開したときは、再開の手順 2 で得た答えを本体が同じ節に足して R1 に当て直させる（手順 3 の確認のあとで足す）。本体は答えを節に足したら、ラベルの付け先から `needs-approval` を外す
- 直し方の判定が「選び直しが要る」で主に聞いた問いへの答えが条件についての答えである（例:「その場面は起きない」）。本体は聞き直さず、答えを 1 行にして同じ節に足し、ラベルの付け先から `needs-approval` を外す
- 2 周目以降の周の終わりで、条件の判定が書かれていない BLOCKER がある
- 最新の `仕様レビュー:` のコメントより後に `## 条件の答え` へ行が足された

**当て直し**: R1 を起こすとき、節 `## 条件の答え` の行と、残った BLOCKER を載せた最新の `仕様レビュー:` のコメントの URL（`gh` を持たない経路は本文）を依頼文に入れ（`references/roles/spec-reviewer.md`「レビュアーへの入力」）、「artifact の差分を見ず、残った BLOCKER に節「指摘の条件を決める段」だけを当て直す。前の結果の SHOULD_FIX・NOTE・`捨てた指摘:` は同じ本文に写す」と書く。R1 は同じ書式で結果を記録先に投稿する（投稿者は通常の周と同じ）。当て直しは周に数えない（結果コメントの周の欄は同じ周のまま、当て直しである旨を書く）。主に聞かずに回した周に当て直しが入ったら、事後報告はその周の最後の結果のあとに 1 回書く。R1 を起こす前の PR トークン上限の計測は省かない。

**判定に回す指摘**: 成り立つ予定が無い指摘は判定に回さず捨てる。この節を通したあとの最新の結果に BLOCKER として残った指摘だけを、直し方の判定の「残った指摘の原文」に入れる。当て直しの結果が `APPROVE` なら直し方の判定を起こさず (3) へ進む。BLOCKER が残れば、周の扱いは通常どおり（1 周目は W を再開し、2 周目以降は直し方の判定を通す）。

**主への問い**: 聞くのは条件についての問いだけで、指摘を直すか・捨ててよいかを聞かない。主がいつ答えるかを本体は知らないので、どのモードでも、答えを待つ前に `needs-approval` を付けて問いを PR（無ければ記録先）のコメントに書き、そのコメントを「主への依頼」として `references/handover.md` の引き継ぎを待ち理由 `条件の問い`、次に起こす役割 R1（当て直し）で残す。そのうえで interactive は AskUserQuestion で聞き、unmanned はそのサイクルを終える。

**NOTE の後で成り立つ指摘**: R1 の NOTE の後で成り立つ指摘（`後で成り立つ:` の行）は G の振り分けを経ていないので、SKILL.md「範囲外の問題の起票」の行き先の決め方（段 B の表・段 D・段 E の問い。エピックの子なら段 C も）を借りて本体が決める。起票してよいかを主に聞かない。

**PR のレビュー**: この節は G の `needs-fix-check` には当てない。PR のレビューの指摘の条件は `stages/triage.md` の段 B が持つ。

この手順の守備範囲は、仕様レビューで起きる予定の無い場面への BLOCKER が、直し方の判定と主への確認に進むことを防ぐことである。想定する入力の出どころは R1 の結果の BLOCKER で、拾いたい誤りは、運用上成り立たない条件の指摘を「どの直し方か」の問いに回してしまうことである。通ることを許す入力の例として、R1 が「いまの範囲で成り立つ」と判定した指摘は本体が疑わずに判定へ回す（本体は条件を自分で判定しない）。その指摘が「選び直しが要る」で主に上がり、主が条件を答えたときは、答えを節に足して当て直す。判定の誤りが 1 件も無いことをこの手順の完了条件にしない。

## レビューの周を主に聞かずに続ける（直し方の判定）

仕様レビュー（R1）と PR のレビュー（G）の両方で、2 周目以降の周の終わりに止める指摘が残ったときの本体の手順（#722）。この節が正本で、`references/roles/spec-reviewer.md` と `skills/pr-review-gate/stages/triage.md` は規則を短く書いてここを指す。判定の記録と事後報告の書式はこの節にだけ置く。

**規則**: 2 周目以降の周の終わりに残った止める指摘（仕様レビューは R1 の `REQUEST_CHANGES` の BLOCKER、PR のレビューは G が `needs-fix-check` で渡した指摘）がすべて直し方が決まっているもので、PR トークン上限の計測が exit 2 でなければ、本体は主に聞かず次の周を回し、記録先に事後報告を残す。主に聞くのは、方針の選び直しが要るとき（直し方の判定が「選び直しが要る」。入力不足で判定が出なかったときを含む）と、PR トークン上限を超えたとき（`pr-token-budget.sh` が exit 2）の 2 つだけ。この 2 つは方針を聞くときの数で、指摘の条件を聞く問い（節「残った指摘の条件を確かめる」）は数えない。interactive と unmanned で同じに扱う。主に聞かずに回す周の回数に上限は置かない（止めるのは PR トークン上限・直し方の判定・PR 側の順 6 の「PR ごとに 1 回まで」）。

**判定役**: 本体が決める役を `subagent_type: dev-workflow:decider` で起こす。モデルは仕分け表の順 6 の決める役と同じく残量モードどおりにし、`model` を明示する。description には記録先番号 `#N` を入れる（PR トークン上限の計測に含めるため）。起こす前に SKILL.md の「PR トークン上限」の節の計測を行い、exit 2 なら起こさず exit 2 の手順で止まる。G・本体・レビュアーの申告を判定の代わりにしない（レビュアーの申告は決める役への入力として渡す）。

**依頼の契約**: 依頼は、順 6 の裁定とマージ可否を問うときと同じ `agents/decider.md` の「可否と根拠」の出力契約で出し、問いを「残った指摘はすべて直し方が決まっているか（可）、1 件でも選び直しが要るか（否）」の 1 つにする。決める役が通常の 3 点（原因の分類・直す箇所と方法・次の実行役のモデル）で返す取り違えを防ぐため、依頼文に「3 点ではなく可否と根拠で返す」と書く。`agents/decider.md` は変えない。

**「直し方が決まっている」の定義**: 指摘ごとに次の 3 つをすべて満たすとき「決まっている」とする。1 件でも満たさなければ、その周の判定は「選び直しが要る」。

1. 直し方が 1 つに決まる。選択肢が残っていても、どれを選んでも受け入れ条件と利用者に見える振る舞いが変わらず、選ぶのに主の側にしか無い情報（好み・事業判断・許容度）が要らないなら、決める役が記録先と指摘から 1 つを選び、選んだ直し方とその理由を返答の指摘ごとの直し方に書いたうえで「決まっている」に数える
2. 記録先の範囲（受け入れ条件・issue の範囲）を変えない
3. 前の周で「決まっている」と判定した直し方を当てたのに閉じなかった指摘ではない

**入力**: 決める役は `Bash` を持たないので、本体が次を入力文に貼る。

- 記録先の本文と関連コメント（受け入れ条件・`仕様化判断:` の記録・それまでの `直し方の判定:` の記録）
- 残った指摘の原文（仕様レビューは最新の `仕様レビュー: REQUEST_CHANGES` のコメント、PR のレビューは G の仕分けの PR コメントとレビュアーの要約）
- 前の周の指摘の原文
- 対象ファイルのパス（change の artifact、または PR の変更ファイル）
- W の直近の return

**返答の 1 行目**: 依頼文で 1 行目を `裁定: 可`（すべて決まっている）・`裁定: 否`（1 件でも選び直しが要る）・`不足: <足りないもの>` のどれかちょうどに指定し、2 行目以降に指摘ごとの直し方（1 行）か、選び直しが要る理由（選択肢、または変わる範囲）を書かせる。本体は 1 行目だけで分岐する（本文の読み取りで分岐しない）。1 行目が `不足:` か 3 形のどれにも一致しなければ、足りないものを補って同じ問いで 1 回だけ依頼し直し、2 回目も同じなら「選び直しが要る」として扱う（3 回目の依頼はしない）。

**判定の記録**: 返答を受け取ったら、本体が記録先に判定の記録のコメントを投稿する（決める役は投稿できないので代理投稿する。PR のレビューでも G ではなく本体が投稿する）。1 行目は正規表現 `^直し方の判定: (決まっている|選び直しが要る)$` に完全一致させ（太字・全角コロン・末尾句点を付けない）、2 行目以降に次を `項目名: 値` で書く。

| 項目 | 中身 |
|---|---|
| 対象 | `仕様レビュー` または `PR レビュー（PR #N）` |
| 周 | 何周目の終わりか |
| 判定役 | `dev-workflow:decider`・モデル・本体が代理投稿 |
| 指摘ごとの判定 | 続く行に 1 行 1 件で、指摘の要約と原文の URL、直し方か選び直しの理由 |
| 入力不足 | `なし`、または 2 回目も不足で「選び直しが要る」とした場合の足りなかったもの |

**続行と事後報告**: 判定が「決まっている」なら、仕様レビューでは W を `段: spec` で再開して artifact を直させ、R1 に次の周の差分再レビューをさせる。PR のレビューでは判定と判定の記録の URL を渡して照合と振り分けの G を新しく起こす（G が仮の順どおりに W に戻す）。各 spawn・再開の前の PR トークン上限の計測は省かない。主に聞かずに回した周の結果を受け取ったら（仕様レビューは R1 の結果、PR のレビューはその周の照合と振り分けの G の return）、記録先に事後報告のコメントを投稿する。1 行目は正規表現 `^主に聞かずに回した周: [0-9]+ 周目$` に完全一致させ、2 行目以降に次を `項目名: 値` で書く。

| 項目 | 中身 |
|---|---|
| 対象 | 判定の記録の `対象` と同じ |
| 残っていた指摘 | 前の周の終わりに残った指摘の要約を 1 行 1 件、またはそれを載せたコメントの URL |
| 判定の根拠 | 判定の記録のコメント URL |
| 使ったトークン | 周の前の合計 → 周のあとの合計、その差、上限 |
| 周の結果 | その周のレビュー結果 |

`使ったトークン` の 2 つの値は、本体が spawn・再開の前に毎回とる PR トークン上限の計測の値を使う（周の前は直し方の判定の決める役を起こす前の計測、周のあとは周の結果を受け取ったあと最初の計測）。新しい計測の仕組みは足さない。

**主に聞くとき**: 判定が「選び直しが要る」なら、仕様レビューでは記録先に `needs-approval` を付けて経緯をコメントし、interactive は AskUserQuestion で判断を仰ぎ、unmanned はそのサイクルを終える。そのときの引き継ぎは `references/handover.md` の場面「レビューの 2 周キャップ超え」として書き、待ち理由は `2 周キャップ超え` とする。PR のレビューでは判定と判定の記録の URL を渡して照合と振り分けの G を新しく起こし、G がその指摘を順 5 に当てて主に聞く。PR トークン上限が exit 2 なら SKILL.md の「PR トークン上限」の節の exit 2 の手順に従う。

この判定の守備範囲は、2 周目以降の周の終わりに残った指摘について、主の判断が要る指摘を主に聞かずに進めてしまうことを防ぐことである。拾いたいのは、選ぶのに主の側にしか無い情報が要る、または選択肢によって受け入れ条件や利用者に見える振る舞いが変わる設計の選択肢から選ぶ必要がある指摘・記録先の範囲を変える指摘・前の周で決まっているとした直し方で閉じなかった指摘で、これらは主に上げる。直し方が 1 つに決まる指摘（例: 受け入れ条件の文と artifact の 1 文が食い違い、artifact 側を受け入れ条件に合わせれば閉じる BLOCKER。同じ文言が別の場所に残っている指摘）と、選択肢の違いが受け入れ条件と利用者に見える振る舞いを変えない指摘（例: BLOCKER を閉じるテストを、外から親を一時停止して書くか、本体にテスト用の待ちを入れて書くか。どちらでも実装の振る舞いは同じ）は主に聞かずに通す。判定が「決まっている」とした直し方が外れることは防がない（次の周の終わりの判定の 3 つ目の条件で拾う）ので、判定の誤りが 1 件も無いことをこの手順の完了条件にしない。
