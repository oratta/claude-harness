# rm-permission-guard: 子の rm の確認画面に、親が一時領域の中と確かめた 1 回だけの許可を効かせる（#1134）

#1133 で子（サブエージェント）の破壊的 git 操作には親の 1 回だけの許可が効くようになったが、Claude Code 本体の rm の確認画面（Dangerous rm operation on statically-unresolvable target など）は PreToolUse hook の allow では通せず、子の `rm` は止まり続けていた（flatmate #701）。#1132 の実機確認で、この確認画面には `PermissionRequest` hook が答えられると分かったので、それで作った。

- `scripts/rm-permission-guard.sh`（新規、`hooks/hooks.json` に `PermissionRequest` matcher `Bash` で登録）: `agent_id` が空でない文字列で、単純コマンドのどれかの先頭の語が `rm` のときだけ答える。#1133 と同じ key の許可（`${TMPDIR:-/tmp}/dev-workflow-git-guard/permits/<key>.json`）が一致し、期限内で、使う時点の rm 用の判定も満たせば `decision.behavior: allow`。それ以外は `deny` と、何を・なぜを報告に書いて親に返し打ち直さない旨の message。拒否の記録 `denied/<key>.json`（`kinds: ["rm"]`）を書けたときだけ message にそのパスを載せる（共通ファイルを読めない・書けないときは「作れなかった」と案内する）。主の呼び出し・rm でない確認・読めない payload には何も出力しない。deny の回数は数えない
- `scripts/git-guard-scratchpad.py`: rm 用の判定 `check_rm` と、記録のコマンドで rm 用か git 用かを振り分ける `check_command` を足した。`cd`（最初の rm の前に 1 つまで）と `rm`（フラグは `-r -R -f` の組み合わせだけ）に限り、削除先は末尾の要素の 1 つ前までを `realpath` で解決して scratchpad の中かを見る（末尾の symlink は辿らない）。`cd` が失敗して `rm` が元の cwd で走る場合に備え、相対の削除先は `cd` の移り先と cwd の両方を基準に解決して両方が中であることを求める。scratchpad そのもの・その直下の `*` は拒む。`rm` も `git` も実行しない
- `scripts/git-guard-permit.sh`: 判定の呼び出しを `check_command` にした。git のコマンドの扱いは変えていない
- `tests/rm-permission-guard.bats`（新規）、`tests/hook-python-invocation.bats`（新しい hook を python3 の渡し方の検査に足した）
- 実機確認（`claude -p --plugin-dir`、2.1.304）: 許可の無い子の rm は deny されて子が報告に記録のパスを書いて返り、親が許可を書いて SendMessage で再開した同じコマンドは確認画面なしで通って消え（scratchpad の外の他のファイルは残った）、主の rm には hook が何も返さず今までの確認のままだった。結果の表は PR に載せる
- 範囲外: 拒否されて返った子を親が判断して許可・再開する develop の手順（#1135）
- 受け入れること: cwd が scratchpad の外のとき、`cd <dir>; rm … <rel>/*` は `cd` が失敗した場合の基準で外に出るので許可を書けない（削除先を絶対パスで書くか、cwd が scratchpad の中で打つ）。#1133 と同じく、`permits/` への直接書き込みや判定後の symlink の差し替えは見ない
- 戻し方: この PR の差分を戻す。一時ディレクトリの `denied/`・`permits/` は残っても使われない
