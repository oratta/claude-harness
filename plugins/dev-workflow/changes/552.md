# subagent-context-audit.sh に担当別の内訳 --by-role を足す（#552）

`subagent-context-audit.sh` は母集団の統計を隔離の有無（`sources.isolated` / `sources.non_isolated`）でしか分けておらず、develop ワークフローの担当（W / R1 / G / G のレビュアー / decider）ごとの傾向が見えなかった。隔離の有無は役割と相関するが役割そのものではなく（隔離ありの中に W も decider も混在する）、エピック [#511](https://github.com/oratta/claude-harness/issues/511) の施策が効いたかを担当別に確かめる手段が無かった。

- `--by-role` フラグを追加した。指定時のみ出力のトップレベルに `by_role` キーを足す。既存キー（`count` / `first_median` / `sources` 等）の形・走査コストは変えない（`--by-role` を付けない既定呼び出しはこの change の前後で完全に同じ出力になることをテストと実機の両方で確認済み）
- 担当分類は隣の `agent-<id>.meta.json` を `agentType`（`dev-workflow:decider` を最優先）→ `description` の先頭コロン区切りトークン（`W` / `R1` / `G` / `Reviewer`）→ `unknown` の優先順位で見る。分類できない件も `unknown` として合計に含め、母集団から落とさない
- `by_role` は 6 担当を常にキーとして持ち、各値は `count` / `first_median` / `docs_median` / `last_median` / `over_cap_pct` を持つ。`docs_median`（指示書 `Read` / `Skill` 呼び出しを含むホップの `usage` 差分）は個体ごとに合計してから担当内で中央値を取る 2 段階集約
- `reread_pct`（`W` のみ）: `description` の `#N`（記録先番号。複数出現時は最も左を使う）で同じ記録先を担当した `W` を時系列でグループ化し、先行する全 `W` が読んだファイルのうち後続が読み直した割合を担当内の中央値として出す。ファイル一致はベースネーム一致（フルパス一致ではない。worktree ごとに絶対パスの先頭が変わるため）。グループ最初の `W` と `#N` の取れない `W` は母数から除く
- `--by-role` は担当分類・`docs_median`・`reread_pct` の計上のためトランスクリプト全文を前方から走査する（既定呼び出しの部分読みより重い。手動監査専用でセッション起動経路には載らないため許容する）。`--cache` を省略した場合、`--by-role` 指定時だけ既定パスに `.by-role` サフィックスを足し、既定呼び出しとキャッシュファイルが衝突しないようにした
- `docs/usage-audit.md` に「6. `--by-role`（担当別の内訳）」を追記した（実行例・6 担当の分類規則・`docs_median` / `reread_pct` の定義・走査経路が違うことによる既定呼び出しとの微小なずれの注意）
- 実機（claude-harness、直近 10 日、母集団 1426 件）で実行した結果を着手前の基準値としてエピック #511 にコメントした（G が cap 超過率 62.0% と突出し、design.md に書いた事前の手作業集計と同じ傾向であることを確認）
- 受け入れたリスク: `docs_median` は 1 ホップに複数 `tool_use` が混在する場合、ホップ全体を docs 側に丸めて計上する近似（指示書以外の道具呼び出しのコストが混ざる方向の誤差）。`reread_pct` のベースネーム一致は内容差分を見ないため、同名で内容が更新された指示書を「読み直した」とみなす。`unknown` の中央値は `meta.json` 欠損・develop 以外のサブエージェントが混在するため、担当別の傾向としては意味を持たない（合計件数の整合性のためだけに存在する）
