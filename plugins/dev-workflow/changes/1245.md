# develop: エピックの子の PR トークン上限を、親が持つ子 1 件あたりの権限の内なら親が続けさせる（#1245）

エピックの子の PR が既定のトークン上限（30,000,000。`DEV_WORKFLOW_PR_TOKEN_CAP`）を超えると、今までは毎回主の「続ける」を待っていた。2026-10-17〜19 の 5 件はどれも主の答えが「続ける」で、夜のあいだ合わせて約 48 時間止まった。主の決定（https://github.com/oratta/claude-harness/issues/1245#issuecomment-6359136416 ）に従い、エピックの親に子 1 件あたりの PR トークンの権限を持たせ、子の見込みがその内に収まるなら親が続けさせる。

- 権限の置き場: エピックの issue の 1 行目が `子の PR トークン権限: <値>` のコメント（既定 60000000）。投稿者が OWNER・MEMBER・COLLABORATOR の最新の 1 件を正とする。親は経路を決めたとき（unmanned・channel を含む）、手順 7 の再開、手順 8 とサブエージェント方式の本体が照らす前に、コメントが無ければ既定値で投稿し、interactive と channel では主に「子 1 件 6,000 万トークンで回す。広げたければ声をかけて」と伝える。主が広げたら `主の発言:` の行つきで投稿し直す。親の判断では広げない（`references/epic.md`「経路の決め方」・手順 7）
- 別セッション方式の子は今までどおり止まり、停止の記録の `止まった理由:` を `PR トークン上限（合計 <合計> / 上限 <上限>）` で始め、`前提:` に終わるまでの見込み・続けるべきか・次に絞る範囲の 3 行を書く（`references/epic-child-stop.md`）
- 起こされた親は、この止まりを `parent-pass-criteria.md` に照らし直さず、(a) 合計の見込みが権限以下・(b) 記録の上限が権限より小さい、の両方を満たせば `reply --as parent` で `続ける。新しい上限 <権限>（親の権限。<URL>）` を送る。満たさなければ権限の値と広げる選び方を添えて主に上げ、主が広げて答えたら照らし直す。広げずに「続ける」だけなら今までどおり `reply --as owner` で届ける（`references/epic.md` 手順 8 と **PR トークン上限の子**）
- 返事を受けた子の本体は、主に聞き直さず、記録先に `PR トークン上限: <権限>` と `決めた人:`・`権限:`・`停止の記録:` の 4 行を投稿して `--cap <権限>` で続ける。親の返事は主が権限で先に承認した範囲の執行として扱う（`skills/develop/SKILL.md`「PR トークン上限」、`references/epic-child-stop.md`）
- サブエージェント方式（unmanned・channel を含む）では、親を兼ねる本体が見込みを子の記録先にコメントしてから同じ条件で照らし、同じ書式で書く（`skills/develop/SKILL.md`「PR トークン上限」）
- `references/parent-pass-criteria.md`: 通す条件の 1 行目に、PR トークン上限の止まりは判断のモデルでは通さず起こされた親が手順 8 で権限に照らすことを添え、通らない例の理由を、判断のモデルには親の権限が渡らないからに直した
- 変えないもの: 既定の上限 30,000,000（止まることで工程の中の無駄に気づく機会を残すため）、エピックの子でない記録先の「続ける」の扱い、スクリプト（`stop-judge.sh`・`epic-dispatch.sh`・`pr-token-budget.sh`）、常時注入の文。部品を足さないので `docs/public-private-split.md` の表は変えない
- 戻し方: この PR の差分を戻す。残った `子の PR トークン権限:` のコメントは読まれなくなるだけ
