# usage-probe の古いロックの取り直しで 2 本が同時に走らないようにする（#442 の 1 つ目）

古いロック（120 秒超）が残っているところへ probe が 2 本ほぼ同時に来ると、後の 1 本が先の 1 本の取り直した新しいロックを `rm -rf` で消し、2 本が同時に API を叩いていた（先の 1 本の終了時の `rmdir` が後の 1 本のロックも外す）。

- `usage-probe.sh`: 古いロックの取り直しは、別の排他ディレクトリ `${LOCK}.takeover` を `mkdir` で取れた 1 本だけが行う。排他の中でロックの mtime を測り直し、新しければ（別の probe が取り直した）何もせず引く。古いままなら消して `mkdir` に進む。新しいロックは移しも消しもしない（初版の `mv` で退避する案は、退避中に正規のパスが空いて別の probe が `mkdir` に成功する穴があり、レビューで指摘されて採らなかった）。排他が 120 秒を超えて残っていたら外して今回は引く
- テスト 2 件: 古さの判定（stat）の直後に待たせる足場で、(1) 4 本を同時に起動、(2) 0.3 秒ずらして起動し 2 本目が「古い」の判定を持ったまま取り直し済みのロックに行き当たる、のどちらも curl の呼び出しが 1 回だけで、ロックと排他が残らないことを固定する。どちらも修正前のコードでは落ちることを確認した
- 戻すときは古いロックの取り直しのブロックを `rm -rf "$LOCK"` に戻す

## 3 つ目: Codex 側の自動選択も、古い値をリセット時刻で読む

Claude 側は #417 で「取得から 300 秒を過ぎたら捨てる」をやめてリセット時刻で読む実効値になったが、Codex 側（`codex-develop.py` の `usage_margin`）には 300 秒の鮮度判定と「リセット時刻が 7 日以内」の検査が残っていた。API の取得が一時的に失敗して値が数分古くなるだけで Codex が欠測になり、Claude だけが選ばれていた。

- `usage_margin`（Codex 専用に整理。`codex` 引数と Claude 用の枝を削除）: `fetched_at` の経過時間（300 秒）で捨てない。週次窓のリセット時刻を過ぎていれば使用率 0%・リセット時刻は 1 週間単位で先へ送り、過ぎていなければ取得した使用率を下限としてそのまま使う。リセット時刻が 7 日より先でも欠測にしない（週経過率が負になり余裕が負になって選ばれないだけ）。欠測のまま残すのは、週次窓なし・使用率が有限の 0..100 でない・リセット時刻が整数でない・`fetched_at` が整数でない／未来時刻
- 取得失敗で前回値を使うときも同じ規則で読む（前回値の古さでは除外しない）
- spec `codex-role-profiles` の 2 要件（snapshot の鮮度と週次窓の検証・複数 Codex account の代表選び）、`docs/codex-develop.md`、`references/codex-develop.md`、`skills/develop/SKILL.md`、`decision-criteria.md` の「age 300 秒」の記述を実効値に直した
- テスト: 古い値（301 秒・1 日・5 日）がリセット前なら下限として使われる／リセット後は 0% で 1 週間単位に送られる／7 日より先でも欠測にならない／不正入力は欠測のまま、を固定。修正前のコードでは落ちることを確認した
- 戻すときは `usage_margin` に `age > 300` と `now < reset <= now + WEEK_SECONDS` の検査を戻す
