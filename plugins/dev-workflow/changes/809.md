# エピックの子への注意書きと「子であること」を、起動し直したセッションにも引き継ぐ（#809）

`/develop <エピック番号>` を Orca 経路で回すと、親が `launch --note` で渡した注意書き（「後続の範囲に手を出さない」など）は子に最初に送る指示の文面にしか無く、「エピックの子である」ことは子の端末に付けた環境変数にしか無かった。子のセッションを閉じて同じワークツリーで `/develop #N` だけを打ち直すと両方が消え、注意書きは守られず、自分を子だと知らないセッションが孫のワークツリーを作りえた。同じ箇所を触る #532・#487・#498・#499 も合わせて閉じた。

- `scripts/epic-dispatch.sh launch --note <text>` は、子のワークツリーを作れた子ごとに 1 回、端末を作る前に、子 issue へ `親エピックからの注意書き: #<エピック番号>` で始まるコメントを投稿する。`skipped` の子とワークツリーを作れなかった子には投稿しない。投稿に失敗しても起動の結果（stdout の 1 行と exit code）は変えず、stderr に `note not posted to #<N>` と手で投稿するコマンドを出す
- `route` は、環境変数 `EPIC_DISPATCH_PARENT_EPIC` が無くても、今のワークツリーに issue の付いた親ワークツリーがあれば `nested` を返す。子の件数によらず最初に判定する。`nested` のときは stderr に `parent epic: #<N>` を出す。`jq` が無いか一覧を読めないときは子ではないとして進み、stderr に `could not read the parent worktree` を出す
- `launch` も同じ判定を `git fetch` と今のワークツリーへの issue の紐付けより前に行い、子のセッションでは子ワークツリーを作らずに exit 1 で終わる。理由の文は、環境変数による拒否と同じく `child epics are not expanded here` を含む
- 指示を送り直す案内のハンドルを単一引用符で囲んだ（#487）。端末を作り直す案内の前に、そのワークツリーで端末がすでに動いていないことを確かめるコマンドを出すようにした（#498）。冒頭コメントの「route は子 0 件でも subagent」に `nested` が優先することを書いた（#532）
- develop の SKILL.md「エピックの扱い」に、`親エピックからの注意書き:` で始まるコメントに従い W・R1・G に必ず渡すこと、`note not posted to` が出たら本体が投稿すること、親エピックの番号を `route` の stderr から読むこと、環境変数が無いまま `nested` になったときは親を持たないワークツリーで起動するよう伝えること、端末を作れなかった `failed` の子の再開手順（既存の端末が無いことを確かめ、作り直して送り、動き出したのを確かめてから再開する。#499）を書いた
- `tests/epic-dispatch.bats` に、`gh issue comment` の回数・本文・順序、親子関係による `nested` と `launch` の拒否、案内の文、SKILL.md の記述のテストを足した
- 受け入れた制約: `launch` 以外の方法で、issue の付いたワークツリーを親にして作ったワークツリーでは、エピックは `nested` になり展開されない（親を持たないワークツリーで起動すれば展開できる）。この変更の前に起動された子の issue には注意書きのコメントが無い。注意書きのコメントは子 issue を読める人すべてに見える
- PR #834 の一周目レビューを受けた直し（#835）: `親エピックからの注意書き:` で始まるコメントは、投稿者の `author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` のどれかのものだけに従う。それ以外の投稿者のものと値を読めなかったものには従わず、W・R1・G にも渡さず、URL と投稿者をユーザーに報告する。リポジトリが公開で issue には誰でもコメントでき、子のセッションは確認画面なしで動くため。検査するのは注意書きのコメントだけで、記録先のほかのコメントの読み方は変えていない
- PR #834 の一周目レビューを受けた直し（#836）: `launch` は、今のワークツリーに親があるのにワークツリーの一覧を読めないとき、`git fetch` と今のワークツリーへの issue の紐付けより前に exit 1 で止まる（stderr に `could not read the parent worktree`）。直す前は、起動し直した子のセッションでこれが起きると、子のワークツリーの issue をエピック番号で書き換えてから止まっていた。親を持たないワークツリーでの呼び出しの順序は変えていない。`route` は今までどおり子ではないとして進む
