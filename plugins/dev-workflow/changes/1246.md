# develop: エピックの目的や原則から答えが決まる子の止まりを、親がそれを根拠に通す（#1246）

2026-10-19〜20 の夜、別のリポジトリのエピックで、親は止まった子を 10 件前後主に上げ、主が起きるまで止まった。大半はトークン上限・聖域・実機操作で主が本当に要ったが、1 件はエピック本文の原則「オーナーと客の環境で仕組みを分けない」が子の推奨をそのまま決めていた。`parent-pass-criteria.md` には、目的や原則を根拠に積極的に通す規則が無く、「範囲の内側」（範囲を広げず逆向きにもしない）だけでは「主の側の情報が要らない」を満たすと読めなかった。

- `skills/develop/references/parent-pass-criteria.md`: 表の下に段落「エピックの目的・原則から推奨が決まるとき」を足した。エピック本文の目的・原則・決まった方針が子の推奨を一意に決める（推奨以外の選び方がそれに反する）ときは、それを根拠に「主の側の情報が要らない」を満たすと読む。根拠にできるのは判断に渡されたエピックの本文の文だけで、推し量った意図・会話・子の記録にしか無い原則は根拠にしない。通すときの `理由:` に根拠の文を短く引く。効くのはこの 1 条件だけで、ほかの 8 条件は今までどおりすべて満たす必要がある。聖域・破壊的操作に触れるもの、許容と書かれていないリスクを受け入れるものは通さない。推奨が 1 つに決まらないときは「迷ったとき」に従う。表の「主の側の情報が要らない」の行からこの段落を指した
- 同じファイルの「例」: 通る例に上の原則が推奨を決めていた型を、通らない例に同じ型でもリスクの許容や聖域・破壊的操作に触れるものを足した。公開版なので、作業先のリポジトリ名と issue 番号は書いていない
- `tests/epic-dispatch.bats`: 上の規則と例の文言を確かめる `criteria:` のテストを足した
- 条件の数（9 つ）と出力の形は変えていない。`stop-judge.sh` も変えていない
- 仕様（openspec の `dev-workflow-develop`「親が通してよい範囲の基準を 1 つのファイルに置く」）は直していない。作業した環境に openspec CLI が無く、仕様化しない判定にしたため（記録先 #1246 のコメント）。条件は増減していないので、今の要件の文とは食い違わない
- 主が寝る前に推奨をまとめて承認しておく仕組みは作っていない。承認の印を子のゲートが信頼する話になり主の観点が要るので、#725 にコメントして候補として渡した
- 受け入れること: 判断のモデルが「推奨が一意に決まる」を緩く読むと、主に上げるべき止まりを通しうる。歯止めは、根拠をエピック本文の文に限ることと、`理由:` に引いた文がエピックの 1 行に残って主が事後に見られること
- 戻し方: この PR の差分を戻す
