# エピックの親が human-merge の付いた子の PR を基準で判断し、判断の印を付ける（#1054）

#1030 で自動マージの処理は親の判断の印（`parent-merge-approved` ラベルと `親のマージ判断: 可` のコメント）を受け取れるようになったが、印を付ける側の手順が無く、聖域接触だけで `human-merge` が付いた子の PR は今までどおり主のマージを待っていた。親が直接マージすると CI green・SHA ピン・緊急停止・マージ直前の取り直しを素通りするので、親は基準で判断して印を付けるだけにし、マージは自動マージの処理に任せる形にした。

- develop の `references/parent-merge-criteria.md` を新しく置いた。可の条件は 6 つ（見送りが聖域接触だけ・ゲートが今の HEAD で済んでいる・主の側の情報が要らない・範囲の内側・戻せる・配役表で主の観点が無い）で、迷ったら主に上げる。判断は親が起こす `dev-workflow:decider` が行い、出力は `裁定: 可`・`裁定: 否`・`不足:` と `理由:` の 2 行。`parent-pass-criteria.md` にはマージの条件を足していない
- develop の SKILL.md の Orca 経路に **マージ待ちの子** の段落を足した。手順 8 で主に上げる前に、PR の base ブランチの `auto-merge.yml` に `parent-merge-approved` があるか・見送りラベルが `human-merge` だけか・PR 本文の最初の `Closes/Fixes/Refs #N` が子 issue か・今の HEAD の印がまだ無いかを確かめ、決める役が可と言えば HEAD を取り直してからコメント → ラベルの順で印を付け、子に `reply --as parent` で伝え、エピックに `親の判断: 子 #N マージに回した` を残す。「本体は自動でマージしない」の文は「本体は `gh pr merge` や merge API で直接マージしない」に書き換えた
- 親が気づく経路は `epic-dispatch.sh` を変えず、既存の `stopped` に乗せた。子は `ci-watch.md` の分岐で、`nested` かつ見送りが `human-merge` だけかつ base ブランチの `auto-merge.yml` に `parent-merge-approved` があるとき、オーナーに頼まず `止まった理由: PR のマージ待ち（human-merge）: <PR の URL>` で止まる。親の返事のあとは `--until-merged` で見届け、子は印を付けない
- `commit-and-pr-operations.md` の「唯一のマージ経路」の段落に、親の判断の印で `human-merge` が外れる経路を足した（LLM の直接マージの禁止は変わらない）
- 印が効かないリポ（原本を展開し直していない、または `gh` の認証アカウントが OWNER・MEMBER・COLLABORATOR でない）では、親は印を付けずに主に上げる
- 戻し方: この PR を revert する。戻したあとは子が `human-merge` で止まると今までどおりオーナーに直接マージを頼む
