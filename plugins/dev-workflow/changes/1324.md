# epic-dispatch.sh wait の上限を親の会話キャッシュの有効期限で決め、上限で起きた親は掛け直すだけにする（#1324）

エピックの親（Orca・tmux の別セッション方式）は、子に動きが無いあいだ `wait` の上限 6 時間を眠り、そのあいだに会話のキャッシュ（1 時間）が切れて、起きるたびに会話全体を書き直していた。起きたターンでも子 issue を読み直して主に報告しており、そのぶん発言とトークンを使っていた（親エピックは #1325）。

- `scripts/epic-dispatch.sh`: 関数 `cache_ttl_of <ワークツリーの絶対パス>` を足した。置き場の直下の `*.jsonl`（サブエージェントのものは読まない）で、最後にキャッシュを書いた assistant の行（`entrypoint` が `cli` ちょうど、`isSidechain` でない、`message.usage.cache_creation` の 5m と 1h の書き込みの和が正）の有効期限を `<1h|5m> <epoch 秒>` で出す。判定できなければ何も出さず exit 1。引数が空なら置き場を読まない。`entrypoint` で絞るのは、同じ置き場に hook が SDK で起こしたセッション（`sdk-py`。公式プラグイン security-guidance の hook）や `claude -p`（`sdk-cli`）の行が混ざり、親の有効期限と関係なく 5 分で書くため。絞る前の実装は実機確認で、主のセッションが 1 時間で書いていたのに `sdk-py` の行を読んで `wait limit 21600 (parent cache 5m)`（6 時間眠る側）を出した。`entrypoint` の無い行や知らない値は読まず、判定できない側（短い上限）に倒す。後続の子への声かけの change が子のワークツリーにも使う
- `wait`: `--timeout` も空でない `EPIC_DISPATCH_TIMEOUT` も無いときだけ、上限を親のキャッシュが `5m` なら 21600 秒、`1h` か判定できなければ 3000 秒にし、待つ前に stderr へ `wait limit <秒> (parent cache <5m|1h|unknown>)` を 1 行出す。上限を明示したときは有効期限を読まず、この行も出さない。stdout の 1 行と exit code は変えていない
- 短い上限に 3000 秒を選び、2700 秒を退けた。`wait` は「経過 + 間隔 > 上限」で眠らずに終わるので、3000 秒では最後のリクエストから約 45 分で起き、自動コンパクト（約 54 分）までの余裕が約 9 分ある。2700 秒だと約 40 分で起き、issue の「50 分前後」から遠い
- `skills/develop/references/epic.md`: 手順 5（`timeout` で起こされたとき）を、子 issue もエピックも読まず主にも報告せず、同じ引数の `wait` を背景で掛け直すだけにした（`--timeout` は足さない。主への問いが未回答のあいだは `主がすること: なし` も書かない）。記録を残さずに子のタブで止まった子に気づけないことは、手順 2 でこのセッションの最初の待ちに入る通知で一度だけ主に伝える。子エピックの行で子を外す確認は `closed` のときだけにした。手順 2・4 の片付け待ちの子だけを待つ `wait`（位置引数の子なし）には `--timeout 21600` を付ける。手順 6 などの「最長 6 時間待つ」は、親が気づかないまま待ち続ける旨に直した
- `skills/develop/references/reply-after-idle.md`: 節「親の待ちの費用（#1324）」を足した（3000 と 21600 の理由、使用量の超過中は 5 分に縮むこと、有効期限を固定した人の扱い、PC が寝ている間は効かないこと）。閾値の表とそのまま送るか起動し直すかの表、「親への適用」の文は変えていない
- 版は上げない。プラグインの更新後に起動した `wait` から新しい既定が効く
- 戻し方: 親の環境で `EPIC_DISPATCH_TIMEOUT=21600` を付ければ上限は今までどおりになる。手順の変更ごと戻すときはこの PR の差分を戻す
