# git-destructive-guard: コマンド文字列をシェルと同じ単位で読む（#820）

破壊的 git 操作を止める hook（`scripts/git-destructive-guard.sh`）は、コマンド文字列を単純コマンドと語に分ける段で、シェルの実際の読み方とずれていた。PR #794 のレビューで見つかった 8 件を直した。判定の 9 種・ask / deny・逃げ道・fail-open と、git のサブコマンドとオプションの解釈は変えていない。

| 入力の形 | 直す前 | 直した後 |
|---|---|---|
| 改行を含む引数（`bash -c '<改行>git reset --hard'`、`git -c core.x='a<改行>b' reset --hard`） | 通る | 止まる |
| 置換の中の引用された `)`（`echo "$(printf ')'; git reset --hard)"`） | 通る | 止まる |
| コメントの中の引用符（`# It's cleanup<改行>git reset --hard`） | 通る | 止まる |
| 途中のリダイレクト（`git reset >/dev/null --hard`、`git reset 2>&1 --hard`） | 通る | 止まる |
| 行継続（`git \<改行>reset --hard`） | 通る | 止まる |
| ハイフン入りの区切り語（`<<END-TAG`）と here-string（`<<<`）の後ろの行 | 通る | 止まる |
| 引用された演算子（`echo ';' git reset --hard`） | 止まる | 通る |
| 引用されたヒアドキュメントの本文の置換（`<<'EOF'` の中の `$(git reset --hard)`） | 止まる | 通る |

- 字句の読みを、4 段の走査（置換の取り出し・改行とヒアドキュメントの正規化・`shlex` での分割・演算子での区切り）から、引用状態と「演算子か語か」を保つ 1 回の走査に置き換えた。8 件のうち 6 件は、引用状態を段ごとに数え直していたことが原因だった。引用された `;` と演算子の `;` は `shlex` が同じ文字列で返すので、`shlex` を使う限り区別できない
- 複数行の `git commit -m` や `echo` の引数は、これまでどおりコマンドとして読まない。`bash` / `sh` / `zsh` の `-c` と `eval` の引数だけ、改行を含んでいても中を判定する
- 引用されていないヒアドキュメントの本文の `$(...)` とバッククォートは、シェルが実行するので中を判定する。本文の行そのものは、これまでどおりコマンドとして読まない
- 引用符が閉じていない入力は、これまでどおり空白と引用符の外の改行で割って判定し、置換の中も見る。閉じていない `$(` の中身は、その中の引用符が閉じていれば末尾まで字句読みで読み、`bash -c` / `eval` に渡した引用つきの引数を空白で割って失わない（`echo "$(bash -c 'git reset --hard'` を、書き換え前は止めていた）
- `$(...)` を何重に重ねても、中の git を同じ読み方で判定する。`$(...)` の中の単純コマンドは字句読みがその場で読み、入れ子の深さを `bash -c` / `eval` の再帰の上限（8 段）に数えない（書き換えの途中の版は 9 重以上で見失っていた。書き換え前は止めていた）。字句読みは入れ子を Python の再帰ではなく明示的なスタックで読むので、深さで読み方が変わらない（PR #852 のゲート一周目の指摘。途中の版は再帰が尽きる 3000 重あまりを超えると粗い読みに倒れ、`bash -c` / `eval` に渡した引用つきの引数を空白で割って失っていた）。Python の再帰の上限は既定のまま変えていない（上げると Python 3.9・3.10 が異常終了して無出力＝素通しになる。30000 で実際に落ちた）
- 読み終えた単純コマンドはためずにその場で判定する（ためると深さの 2 乗のメモリを使い、20000 重の二重引用符つきの入れ子で 2GB を超えた。直した後は 80MB）。`bash -c "$(bash -c "$(...)")"` のように `-c` / `eval` の引数を重ねた形は、同じ引数の判定の結果を控えて使い回す（控えが無いと重ねた数の 8 乗に比例する回数だけ判定し直し、24 重で 20 秒かかった）
- 字句読みは、読んだ `$(...)` の範囲を語に持たせる。`bash -c` / `eval` の引数になった語を読み直すときは、その範囲を読まずに飛ばす。範囲の中の単純コマンドは、外側の読みがより浅い深さでもう判定に回していて、判定は深さが浅いほど多くを拾うので、飛ばしても拾うものは減らない。控えだけでは `bash -c "$(bash -c "$(...)")"` を重ねた数だけ内側の引数を読み直していて、500 重で 7 秒、1000 重で 30 秒を超えていた（hook の時間切れは何も止めないのと同じ結果になる。書き換え前は 3000 重で 0.6 秒）。直した後は 6000 重で 0.1 秒。ヒアドキュメントを含む置換は、本文の終わりを行の単位で探して置換の外の文字まで見るので、飛ばす対象にしない
- 判定の仕事量（字句読みとヒアドキュメントの本文探しにかけた文字数の合計）に上限を置き、超えたら判定を打ち切って、破壊的操作を含むものとして ask / deny を返す（理由の文面は「判定しきれなかった」）。素通しの側には倒さない。上限はコマンドの長さの 32 倍で、短いコマンドには 200 万文字の下限を置く。読み直しは `bash -c` / `eval` の引数とバッククォートの中身にしか起きず、深さは 9 段までなので、読み直しが重ならないコマンドの仕事量は長さの 9 倍（バッククォートを引数の中に書いた分を二重に数えても 18 倍）に収まり、上限に届かない。届くのは、ヒアドキュメントを含む置換を `bash -c` / `eval` の引数に何重にも重ねた形と、ヒアドキュメントの本文の `$(...)` の中にヒアドキュメントを何重にも入れた形で、どちらも 10 重や 40 重では届かず、500 重では届いた。この 2 つの形は、破壊的操作を含まなくても 500 重以上で止まる（書き換え前は通していた。確認画面か主の実行で通せる）。字句読みは 1 秒に約 300 万文字を読むので、上限までの所要時間は 3 万文字のコマンドで 1 秒弱、20 万文字のコマンドで約 2 秒
- 深さ 1・9・500・3000・6000・20000 重 × 入れ子の形 10 種 × 中心のコマンド 18 種（1080 件）を書き換え前の版と比べ、書き換え前に止まっていて今は通るのは、引用された `;` の後ろの git（上の表の「引用された演算子」）だけだった。異常終了（終了コードが 0 以外・標準エラー出力・時間切れ）は無い。読み済みの範囲を飛ばす変更の後に、20000 重を除く 900 件を比べ直して同じ結果だった（5 秒を超えた入力は無い）。hook の Python 部分を取り出して Python 3.9・3.10・3.12 で直接実行しても、3.14 と同じ結果になる（深さ 1・9・3000・6000 の 720 件。`python3` が 3.9 の環境では hook のスクリプト自体が Python 部分を起動できず何も止めない。この件は issue #869 に切り出した）
- `bash -c` / `eval` を重ねた形 14 種（引用つき・引用なし・閉じていない形・前後に破壊的操作を置いた形・ヒアドキュメントを挟んだ形）を、深さ 1・9・500・1000・3000・6000 で書き換え前の版と比べた。書き換え前に止まっていた入力はすべて止まり、所要時間は最長 2.2 秒（6000 重のヒアドキュメントを挟んだ形。上限で打ち切って止めた）。読み済みの範囲を飛ばす前の版と、乱数で組んだ 15000 件のコマンド（入れ子・引用・ヒアドキュメント・バッククォートの組み合わせと、その一部を壊したもの）で判定を比べ、違いは無かった
- 仕様は要件「コマンド文字列をシェルと同じ単位で読む」を新しく足した（既存の要件は書き換えていない）。#821 が同じ既存要件を丸ごと書き写して直しているので、こちらも書き写すと、後からマージした側が先の変更を消すため
- 扱わない構文: 算術式 `$((...))` の中身、`${...}` の中の置換、プロセス置換 `<(...)` の中身、`case` の `)`、予約語や記号が先頭に来る形（`do` / `then` / `{` / `!`）。これらは通ることがある。挙げていない形を読み違えて止める側に倒れたときは、確認画面か主の実行で通せる
- 書き換え前後のスクリプトに bats の全入力（重複を除いて 202 件）を流して比べ、結果が変わったのは 21 件で、どれも上の表の 8 種の入力だった
- `tests/git-destructive-guard.bats` に、8 件それぞれの「止まる入力」と同じ構文の「通す入力」を対にして足した
