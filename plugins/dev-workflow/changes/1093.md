# 止まった印のまま completed で閉じた子に、親が完了を促す返事を送る（#1093）

Orca 経路のエピックで、子が主の返事待ちで止まった（`epic-stopped` を付けた）あとに主が子のタブの外で PR をマージして子 issue が閉じても、子には何も届かず `mark done` が付かないので、親の `reap` が `kept <N> not-done` を返し続けてワークツリーが残っていた（2026-10-19、子 #1059 で発生）。

- `plugins/dev-workflow/scripts/epic-dispatch.sh` に `notify-closed [--relaunch] <epic> <child>` を足した。子 issue が `completed` で閉じていて、子のワークツリーの印が `epic-stopped` か `epic-stopped-seen` のときだけ、`reply --as parent` と同じ処理で「記録先は completed で閉じた。完了報告を書き、mark done で終える」を子に送り、送れたあとにエピックへ `親の判断: 子 #<child> 通した — … <停止の記録の URL>` の 1 行を残す。出力は `notified` / `skipped <理由>`（`not-closed`・`not-completed`・`no-worktree`・`already-done`・`not-stopped`）/ `unrecorded`（届いたが 1 行を残せなかった。stderr に投稿し直しのコマンド）/ `failed <段>`
- develop の `SKILL.md`「回し方」の Orca 経路の手順 4 で、`closed <N>` を受けた `completed` の子ごとに `references/reply-after-idle.md` の表で `--relaunch` の要否を決めて `notify-closed` を 1 回呼び、出力ごとの扱いを書いた。呼ぶのは依存が解けた子の `launch` より先（`launch` が `failed` を返すと親は手順 6 で止まり、再開の手順 7 は `notify-closed` を呼ばないため）。`references/reply-after-idle.md` にこの呼び出し元を足した
- 仕様 `dev-workflow-develop` に要件を 1 件足した（change `notify-closed-stopped-child`）
- `plugins/dev-workflow/tests/epic-dispatch.bats` に、偽の `orca`・`gh` で送る場合・送らない場合・手順 4 の文面を確かめる 13 件を足した。停止の記録が複数あるとき最新を取る処理は偽の `gh` の制約で確かめていない
- 既存の `wait`・`reply`・`mark`・`reap` の振る舞いは変えていない
