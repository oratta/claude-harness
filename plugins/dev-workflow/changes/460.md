# エピックの並列起動を 1 段で止める（#460）

`epic-dispatch.sh launch` で並列起動した子の issue がエピックだと、子のセッションが「エピックの扱い」をそのまま実行して孫のワークツリーとセッションを作り、深さに制限が無かった。親の `wait` は子が閉じるまで待つだけなので、子エピックの孫が全部終わるまで親も止まっていた。

- `launch` は子セッションを起動する端末のコマンドを `EPIC_DISPATCH_PARENT_EPIC=<エピック番号> <cmd> --model '<model>'` にする。端末を作れなかった子の作り直しのコマンドにも同じ前置きが入る
- 環境変数 `EPIC_DISPATCH_PARENT_EPIC` が空でないとき、`route` は子の番号の検査のあと `orca` を呼ばずに `nested` を返し、`launch` は引数の検査のあと `orca` も `git` も呼ばずに stderr に理由を出して exit 1 で終わる（子ワークツリーを作らない）。`wait` は変えていない
- develop の SKILL.md「エピックの扱い」に、sub-issue を持つ子（`sub_issues_summary.total` が 1 以上）を外して `後で別に起動するエピック: #N` とコメントすること、`nested` や `launch` の拒否を受けた子のセッションは展開せずにコメントして止まること（「親ワークツリーで開き直す」とは報告しない）、`timeout` と `closed` の確認でその子を待つ対象から外すこと、完了報告にその番号を載せて親エピックを閉じないことを足した
- 受け入れたリスク: sub-issue を持たず本文で子を列挙しているエピックが事前確認をすり抜けて最後の 1 件になると、親の `wait` が最長 6 時間待つ。`回し方:` のコメントからサブエージェント方式を引き継いだ子エピックのセッションはスクリプトでは止まらない
