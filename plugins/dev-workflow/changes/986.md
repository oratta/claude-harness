# 仕様の文言合わせの軽い通し方を足す（#986。エピック #973 の子）

既存の仕様の文言を実装に合わせて直すだけの変更は、数行の直しでも提案・設計・作業一覧・仕様の差分の一式と仕様レビューが付いていた（flatmate#1513 はコード 6 行に対し openspec 305 行）。この変更で、そういう変更を仕様の差分 1 ファイルだけで通し、別担当（R1）の仕様レビューを省けるようにした。

## 足したもの

- `skills/develop/references/decision-criteria.md` Step B に小節「仕様化するが軽く通す（仕様の文言合わせ）」を足した。対象（既存の要件の文を直すだけ・`## MODIFIED Requirements` だけ・設計の選択が無い・1 つの capability に収まる）、当てる条件（記録先の受け入れ条件に「どの仕様のどの文をどう直すか」が書けている）、省くもの（proposal・design・tasks と R1 の仕様レビュー）の正本はここ。迷ったら当てず、主にも聞かない。無人実行も同じ条件
- 仕様化判断のコメントの 2 行目以降に `通し方: 文言合わせ` の行と、直す要件ごとの `直す文: <spec のパス>「<要件名>」— <どう直すか>` の行を書く。書式の正本は `skills/develop/references/roles/spec-reviewer.md`「判断記録の契約」
- 作業者の指示書（`worker/spec.md`・`common.md`・`implement.md`・`finish.md`）に手順を足した。仕様の差分 1 ファイルだけを書き、作業項目は return に置く。検証は `openspec validate <change-name> --type change --strict`（`--type change` が無いと change を見つけられない）。archive は失敗しても終了コード 0 なので、archive 先のディレクトリの実在で確かめる
- develop の `SKILL.md`: 本体は記録先のコメントで通し方の行を確かめてから R1 を飛ばす。PR レビューの担当を起こす前に、`直す文:` の行が archive 済みの差分の要件名と一致することを確かめる
- `skills/pr-review-gate/declarations.md`: 仕様宣言に 3 つ目の形（`仕様レビュー: 省いた（文言合わせ。<仕様化判断のコメントの URL>）`）を足した
- `skills/pr-review-gate/stages/pass.md` の手順 5: 整合表に行を 1 つ足した（計 4 行）。通し方の行がある PR では仕様レビューのコメントを照合せず、代わりに 4 点を実測する（仕様宣言の形・archive 済みの差分がちょうど 1 ファイル・ADDED / REMOVED / RENAMED の見出しが無い・差分の要件名がすべて `直す文:` の行にある）
- `tests/spec-wording-sync-light-path.bats`: 指示書の記述の検査、`pass.md` から抜き出した照合コマンドを fixture で実行する検査、openspec CLI の実測（CLI が無い環境では skip）

## 変えていないもの

- 1 行目の 2 つの正規表現（`^仕様化判断: (する|しない)$`・`^仕様レビュー: (APPROVE|REQUEST_CHANGES)$`）と、それを読む既存の jq
- 通し方の行の無い「する」と「しない」の扱い（通し方の行が無い PR は、宣言を省いた形にしても `仕様レビュー: APPROVE` を求められる）
- 実装後レビューの重さ（light / full の判定・三表の照合・宣言・動作確認）
- `plugins/dev-workflow/scripts/`（スクリプトは足していない）

## 受け入れたリスク（主の決定。#973 の 2026-10-12 のコメント）

挙げた要件の中で文を落とす・直す範囲より広く書き換える差分と、受け入れ条件に直す文が書けていないのに通し方の行を書いた PR は、機械では止まらない。見るのは実装後レビューと主になる。起きる場面は受け入れ条件の指定があいまいなときで、当てる条件でそういう変更を対象から外している。挙げていない要件への書き換えだけは、要件名の突き合わせで止まる。

## 戻し方

この PR を revert する。データの移行は無い。この変更より前に記録された仕様化判断のコメントには通し方の行が無いので、これまでどおりの扱いになる。
