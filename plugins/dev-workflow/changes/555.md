# W の return に読んだコードの要点、tasks.md に触る範囲を書く（#555）

develop の作業者 W が交代すると（コンテキスト上限での手渡し、トリップワイヤーでの乗り換え）、後任は前任が読んだコードを探して読み直していた。直近 10 日の W 420 体では、読んだ量の最大 50% が同じ issue の前任 W が既に読んだファイルの読み直しだった（ファイル名一致で数えた上限値）。引き継ぎの成果一覧にコードの場所が入っていなかったのが原因なので、場所を渡す欄を足した。

- `skills/develop/references/roles/worker.md`「コンテキスト上限と手渡し」: 成果一覧に「読んだコードの要点」を足し、W の場合のみ必須とした。書式は 1 行 1 件の `<リポジトリ相対パス>:<開始行>-<終了行> — <分かったこと>`、上限 20 行、超えたら次の工程で読む必要が高いものを残す。手渡しで起こされた W には、要点は読む場所の案内で判断の根拠ではなく、編集する前に該当範囲を自分で読んで確かめるよう書いた
- 同じ worker.md の「(3a) の return に書くこと」と「昇格トリップワイヤー」の成果の列挙にも同じ欄を足した
- 同じ worker.md の「仕様化する場合（(1) の終わり）」: `tasks.md` の各タスクに `触る範囲: <パス>:<開始行>-<終了行>`（新規は `<パス>（新規）`）を書く。行番号は仕様づくりの時点の値で前のタスクの編集でずれうるので、実装の担い手は編集前に該当範囲を読む。仕様化しない経路では、同じ内容を作業項目ごとに (1) の return に書く
- `skills/develop/references/decision-criteria.md`「コンテキスト上限（サブエージェントの手渡し）」: W / G 共通の成果一覧 2 箇所（`工程完了:` の説明と、通知を受けたときの振る舞い）に、欄の名前を「W の場合のみ必須」の条件付きで足し、書式は worker.md を指すだけにした（上限行数は再掲しない。変えたときに片方が取り残されるため）。G の return の契約は変えていない
- `tests/develop-roles.bats` に worker.md の検査 3 件、`tests/handoff-declaration.bats` に decision-criteria.md の検査 1 件を足した
- openspec change `worker-handoff-code-pointers` で `dev-workflow-develop` に要件 2 つ（W の return は読んだコードの要点を持つ／(1) で作業項目ごとに触る範囲を書く）を足した

## 決めたこと（design の決定 1〜6）

1. 欄は 1 行 1 件・上限 20 行。ファイル名だけではファイル全体の読み直しが残り、上限なしでは return 自体がコンテキストを食う。20 は当たり値で、事後計測の値と一緒に見直す
2. 書式の正本は worker.md。decision-criteria.md は欄の名前と参照だけにする
3. `tasks.md` の `触る範囲:` は着手時点の行番号。ずれは許容し、担い手が編集前に読む
4. 仕様化しない経路では (1) の return に同じ内容を書く
5. 途中計測 hook（`scripts/context-tripwire.sh`）の通知文と `templates/escalation-tripwires.md` は変えない
6. 受け入れ条件 2（交代を伴う develop 1 本の `reread_pct`）はこの issue 自身の (3a) を新しい W への手渡しで起こして測り、PR 本文に記録する。受け入れ条件 3（マージ後 5 本の `reread_pct` を 25% と比べる）はマージ後にしか測れないので、エピック #511 の下の子 issue に移す。25% は合否に使わず記録する

## 受け入れたリスク

- 途中計測の通知を受けた W が通知文だけを見て return を書くと、欄を落とすことがある。落としても後任が今と同じように読み直すだけで済む
- 前任の要点の行番号が外れていると、後任はその範囲を読み直すことになる。範囲の読み直しは安く、外れても今と同じ探し方に戻るだけ
- #556（worker.md を段ごとのファイルに分ける）と同じファイルを触る。後からマージする側が合わせる
