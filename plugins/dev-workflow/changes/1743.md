# #1743 子の本体の長い背景作業待ち

## 選んだ扱い

再開可能な外部依存は、既存の依存登録と途中経過・再開条件の保存が成功し、子所有の実行中作業が残らないと確認してから停止へ移す。実行中の agent・自分の CI・Monitor・Codex コマンドはセッションと実行 ID を保持する。

本体の現行会話が TTL 1h、最後の成功リクエストから 3600 秒未満で、既存の通知や有限待ちが 45 分以内に本体へ返る保証がない場合だけ、一回限りの 45 分タイマーを一つ置く。5m / unknown は維持対象外。元作業の通知を優先し、不要になったタイマーを取り消す。入口と詳細は develop の SKILL.md と child-background-wait.md、雛形と契約の検査は child-background-wait.bats に追加した。

## 費用比較と採用理由

出典: https://github.com/oratta/claude-harness/issues/1743#issuecomment-7087935739

API 定価換算で会話 20 万トークンを比較した。維持ごとに通知受信と再設置の結果応答で少なくとも二回の cache-read があり、新規入力・出力、初回設置・取消・TTL 確認のツール往復も加算される。旧会話部分だけでも、24 時間後に一度だけ再開する比較では維持の方が高い。単にキャッシュが失効しただけでは課金されず、再開リクエストで書き直したときに費用が生じる。サブスク枠の消費率や常に最安になることを保証する比較ではない。

数時間の実作業待ちでは作業を保持して書き直しを避ける余地があるため条件付き維持を採用し、日単位の再開可能な外部依存は保存して止める。一律の再起動や 5m 向けの頻回の起床は採らない。

未実施。実子の 60 分超の待ちについて、会話量・モデル・TTL・実行 ID・通知時刻と通知後の `cache_read_input_tokens`、または停止と再起動の証拠を issue に残す。スリープや観測後の TTL 切替による miss の回避は保証しない。Bats 合格は手順と雛形の検証であり、実機の維持・削減成功とは扱わない。
