# ci-watch: ジョブの上限時間での打ち切りを job-timeout と見分け、直しに回さずオーナーに上げる（#991）

CI のジョブが上限時間（`timeout-minutes`）で打ち切られたとき、`pr-state.sh` はそれを見分けられず、PR が原因の失敗（`real`）として実装者の直しに回していた。セルフホストのランナーでは打ち切りの原因がランナー側にあることが多く、実装者が PR の差分を調べ直しても原因は見つからない（genetta-inc/flatmate#1563。親のエピックは genetta-inc/flatmate#1566）。

- `scripts/pr-state.sh observe`: 落ちたチェックの `cause` に `job-timeout` が増えた。そのジョブの annotation に `maximum execution time` が含まれるときに付く（`annotations` の出力をジョブ ID で引く。新しい `gh` の呼び出しは無い）。判定の順は `runner-lost` → `job-timeout` → `unrelated` → `real`。`--unrelated` で同じチェック名を渡しても `job-timeout` のまま。1 つのジョブに通信切れと上限時間の両方の annotation があれば `runner-lost`
- `job-timeout` は `real` でないので、`retry` の定義（落ちたチェックがすべて `real` でなく run ID を持つ）は変えずに、同じ HEAD で 1 回だけ `rerun` になる
- `scripts/pr-state.sh decide`: その HEAD のやり直しを使い切ったあとに、`real` が混ざらず `job-timeout` を 1 件以上含む `ci-fail`（`retry: true`）を見ると、`fix` ではなく `escalate` を返し、状態に `raised: true` を書く。`fixes` は増やさない。前回の原因は見ない（状態に `cause` を持たない）ので、`unrelated` や `runner-lost` でやり直したあとの初めての `job-timeout` も `escalate` になる
- `decide` の出力の形（`{act, next, obs}`）、`act` の値の種類、状態のキーは変えていない。`cause` の値を列挙して扱っている呼び出し側は、新しい値 `job-timeout` を受け取る
- `runner-lost` と `unrelated` の動き（同じ HEAD の 2 回目は `fix`）、annotation に `maximum execution time` を含まない取り消し（新しい push による打ち切りなど）の扱いは変えていない
- `references/ci-watch.md`: `escalate` の観測に `job-timeout` があるときは「ジョブが上限時間で打ち切られた。ランナーの状態を確かめてほしい」とオーナーに伝え、実装者に直しを頼まないこと、`job-timeout` は `--unrelated` の判断の対象でないこと、`wait` の `timeout`（見張りの上限時間）とは別の出来事であることを書いた
- `scripts/ci-watch.sh` は変えていない。`wait` の上限時間の既定値（`DEV_WORKFLOW_CI_WATCH_TIMEOUT`、3600 秒）も変えていない
- 受け入れること: ランナーが壊れたままのときも 1 回はやり直すので、CI 1 周分を待ってからオーナーに届く。PR 自身がテストを遅くして上限時間に達したときも、実装者ではなくオーナーに届く（ランナーに問題が無ければ、オーナーの指示で実装者が直す）
- 戻し方: この PR の差分を戻す。状態ファイルの形は変えていないので移行は要らない。打ち切りで付いた `raised: true` は `references/ci-watch.md`「2. 1 つの PR を見張るのは 1 セッションだけ」の手順で消す
