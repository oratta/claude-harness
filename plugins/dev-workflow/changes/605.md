## 判定: 変えない

判定条件 (c) は #607 と #568 で不成立。元にはなかったトリップワイヤーが再実行側で発火した。条件 (b) も #568 で不成立で、blocking かつ confirmed が元 0 件から再実行 1 件に増えた。1 件でも不成立なら変更しない規則なので、事前分類表の「1 周目」列、W の上限、昇格ラダーは変えない。

独立レビュアーの内訳は、#462 が Codex gpt-6-sol（phase review、`codex-standard`、thread `01a0eb29-6207-7ab2-a957-1eb27a233ff5`）、#607 と #568 が Claude opus（`dev-workflow:decider`、`claude-default`。両 provider とも余裕がなく fable に上げず）。decider は Bash を持たないためテストは本体が実行した。再実行の R1 は 3 件とも Codex gpt-6-astra（decider entry）。元のゲートのレビュアーは主に Codex で、再実行とはレビュアーの種別とレビュー回数が揃わない。指摘件数の比較は近似である。

検証上の制約と後続課題:

- #568 は元の spec 段の W が Codex sol で、Opus だったのは implement 段だけ。設計段階は Opus 対 Sonnet の比較ではない。捨て PR による実機確認は検証の制約で未実施。
- 再実行 W は GitHub に書かない条件で作業し、archive・PR 作成・ゲートは通していない。
- #607 と #568 の再実行 R1 は 2 周キャップ後も BLOCKER が残った。本来は本体に上げる場面だが、検証を続けるため本体判断で指摘どおりに直させ、実装へ進めた。
- 自動選択の構成（`claude-write-codex-review` など）は W に sonnet を指定するため、事前分類の opus 昇格はその経路では適用されない。この develop 自身の W も sonnet で起動された。表を変えない判定後も、自動選択経路では W が sonnet で動いている点を後続の課題として扱う。
- 3 件では分類ごとに結果が分かれた。課金/法務は同等、層間契約は仕様の発明が増え、マージ権限は安全機構の穴が見つかった。各分類 1 件だけなので、分類別に下げる根拠にはしない。
