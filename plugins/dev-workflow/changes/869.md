# hook スクリプトの python3 まわりの不具合と取りこぼしを塞ぐ（#869・#847）

どちらも、hook が何を止めるか・止めないかの定義は変えていない。特定の環境で hook が働かない不具合（#869）と、hook の外に置いたファイルが hook の中で実行される経路（#847）を直した。

## python3 が 3.9 の環境で hook が何もしなかった（#869）

`python3` が 3.9 系に解決される PC（macOS 標準の `/usr/bin/python3` は 3.9.6）では、次の 5 本が Python の本体を 1 行も実行せず、rc=0・無出力で終わっていた。破壊的 git 操作も model 未指定の Agent 呼び出しも、確認なしで通っていた。

- `scripts/git-destructive-guard.sh`
- `scripts/agent-model-guard.sh`
- `scripts/context-tripwire.sh`
- `scripts/subagent-stop-guard.sh`
- `scripts/model-switch-recache-notice.sh`（`python3 -I /dev/fd/3` の形で、issue の grep には出ないが同じ渡し方）

原因は本体の渡し方。本体を fd 3 のヒアドキュメントに付けて `/dev/fd/3` として読ませていたが、3.9 はこの形で複数行の本体を実行しない（1 行だけの本体は動く。3.10 以降は動く）。

- 本体をヒアドキュメントからシェル変数に読み（`IFS= read -r -d '' PY_SRC <<'PY'`）、`python3 -I -c "$PY_SRC"` で渡す形に変えた。payload はこれまでどおり stdin から読ませる（引数にも環境変数にも載せない）。本体は固定長で最大 35 KB（Linux の引数 1 つの上限 128 KiB に収まる。bats が 100000 バイト未満を検査する）
- 本体を読めなかったとき（変数が空）は、空の本体を python3 に渡して黙って終わる代わりに、stderr に 1 行出して exit 1 で終わる（`model-switch-recache-notice.sh` は通知だけの hook なので exit 0 のまま）
- `python3` が無いときに何も出さず exit 0 で終わる扱い（各 spec の fail-open）は変えていない
- 5 本とも `-I`（隔離モード）で起動する。`/dev/fd/3` で渡す形はカレントディレクトリを検索パスに入れなかったが、`-c` は入れるので、渡し方を変えるのと同時に付けた（#847 の対象でもある）

確かめたこと（macOS、`/usr/bin/python3` は 3.9.6、既定の `python3` は 3.11.1）:

| | 直す前 | 直した後 |
|---|---|---|
| issue の再現スクリプト（`/usr/bin/python3` に 2 行の本体を `/dev/fd/3` で渡す） | 無出力・rc=0 | —（この形を使わなくなった） |
| `python3` を 3.9.6 にして `git reset --hard` の payload を `git-destructive-guard.sh` に渡す | 無出力・rc=0 | `permissionDecision` が `ask` |
| `python3` を 3.9.6 にして 5 本の bats（176 件）を回す | 105 件が失敗 | 176 件すべて通る |
| 既定の `python3`（3.11.1）で同じ 176 件を回す | すべて通る | すべて通る |

`tests/hook-python-invocation.bats` を足した。3.9 が無い環境でも検査が空にならないよう、版に依らない検査を常に走らせる。

- `/dev/fd` で本体を渡す hook スクリプトが 1 本も無い（全プラグインの `scripts/*.sh`）
- 5 本とも、python3 に渡る引数が `-I`・`-c`・本体の 3 つで、本体がスクリプトのヒアドキュメントの本文と 1 バイトも違わない（引数を控える python3 を PATH の先頭に置いて確かめる）
- 3.9 がある環境では、5 本の本体が 3.9 でコンパイルでき、`git-destructive-guard.sh` が ask・`agent-model-guard.sh` が deny を返し、出力が既定の `python3` のときと 1 バイトも違わない（3.9 が無い環境ではこの 4 件だけ skip）

## CLAUDE_PLUGIN_ROOT が空のときにルート直下の /scripts を見ていた・hook の python3 が作業ディレクトリのファイルを読んでいた（#847）

hook が何を止めるか・止めないかの定義は変えていない。hook の外に置いたファイルが hook の中で実行される経路を 2 つ塞いだ。

### CLAUDE_PLUGIN_ROOT が空のとき

`CLAUDE_PLUGIN_ROOT` が未設定か空だと `"${ROOT}/scripts/…"` がファイルシステムのルート直下の `/scripts/…` になり、そこに実行可能なファイルがあれば実行していた。

- `scripts/subagent-start-context.sh`: 空のときは `session-tripwires.sh` を探さず、残量ブロックを空にする（閾値の行はこれまでどおり出す）
- `scripts/session-tripwires.sh`: session の範囲では、空のときはテンプレートが無いときと同じく何も出さず exit 0 で終わる（`/templates/escalation-tripwires.md`・`/scripts/usage-probe.sh`・`/scripts/memory-tripwire.sh` を見ない）。subagent-budget の範囲では `usage_view.py` を読まずに、残量データが無いときの既定の残量ブロックを出す（空の検索先を Python に渡すとカレントディレクトリを指すので、Python の側でも読まないようにした）
- `scripts/prompt-tripwires-refresh.sh` は元から空のとき何もしない（変更なし）
- ルート直下にそのファイルが無い PC では、空のときの出力は直す前と変わらない

### python3 の隔離

`python3 -c` と `python3 <<'PY'`（stdin）は、カレントディレクトリを import の検索先の先頭に入れる。hook は作業リポジトリをカレントにして走るので、そこに `json.py` や `re.py` があると hook の中で実行されていた（直す前の `subagent-start-context.sh` は、カレントに `json.py` を置くだけで何も出さなくなった）。

hooks.json に登録されたスクリプトと、そこから呼ばれる `usage-probe.sh` の python3 に `-I`（隔離モード）を付けた。

| スクリプト | 付けたもの |
|---|---|
| `scripts/subagent-start-context.sh`（2 か所）・`scripts/session-tripwires.sh`・`scripts/prompt-tripwires-refresh.sh`・`scripts/usage-probe.sh`（6 か所） | `-I` |
| #869 で直した 5 本（上の節） | `-I`（#869 の変更で付けた） |
| `scripts/owner-reply-check.sh` | 元から `-I` |

付けなかったもの:

- `scripts/team-mode-warning.sh`: マージ待ちの PR #897 がこのスクリプトから python3 を外すので触っていない
- hook から呼ばれないスクリプト（`accounts-init.sh`・`select-account.sh`・`pr-token-budget.sh`・`subagent-context.sh`・`subagent-context-audit.sh`・`codex-worker.py`）: issue の対象は hook が呼ぶ python3 なので、この PR では触っていない

他のプラグインの分は、それぞれの `changes/869.md` に書いた（capability-registry・worktree・cost-ledger）。

検査は `tests/hook-python-isolation.bats`（11 件）。

- hooks.json に登録された全スクリプトと `usage-probe.sh` の python3 の呼び出しが `-I`（cost-ledger の 3 本は `-E -s`）で始まる
- 偽の `json.py`・`re.py`・`usage_view.py` を置いたディレクトリをカレントにし、`PYTHONPATH` にも入れて hook を走らせても、偽のモジュールは読まれず、出力は置かないときと 1 バイトも違わない（`subagent-start-context.sh`・`session-tripwires.sh`・`prompt-tripwires-refresh.sh`・capability-registry の `browser-guard.sh`）
- `CLAUDE_PLUGIN_ROOT` を空・未設定にして `subagent-start-context.sh` と `session-tripwires.sh` を `bash -x` で走らせ、実行記録に `/scripts/`・`/templates/` で始まるパスが 1 つも現れない。issue の受け入れ条件は「`/scripts/session-tripwires.sh` にスタブを置いて実行されないこと」だが、テストからルート直下には書けない（macOS は読み取り専用）ので、パスを組み立てないことで確かめる

戻し方: この PR の #847 の commit を revert する。
