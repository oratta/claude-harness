# develop:「経路の決め方」に、着手できる子が 0 件なら subagent になることを足す（#865）

develop の SKILL.md「回し方」の「経路の決め方」は、`orca` が PATH にあり Orca 管理のワークツリーにいれば `orca` が返ると読める書き方だった。実際の `scripts/epic-dispatch.sh route` は、`nested` でなければ、着手できる子が 0 件のときは Orca 管理下でも `subagent` を返す（bats の `route: no children under Orca still goes to subagent` が固定している）。

- 「経路の決め方」の段落に、子が 0 件のときは Orca 管理下でも `subagent` が返る旨を 1 文足した。`route` の挙動は変えていない（説明を実物に合わせただけ）
- 足した文には「（エピックの子のセッションでは件数によらず `nested`）」を添えた。`route` は `nested` の判定を件数より先に行うので、並列起動された子のセッションでは子 0 件でも `nested` が返る
- spec（`dev-workflow-develop` の要件「着手できる子が 1 件でも Orca 経路で回す」）の「『経路の決め方』は、件数の条件を書いてはならない」は、文面だけ読むとこの追記も禁じているように読めた。禁じる対象を「`orca` になる条件としての子の件数の下限（2 件以上など）」と書き直し、子 0 件は `subagent`・エピックの子のセッションは `nested` と書いてよいと明記した（同じ要件の Scenario の題と THEN も合わせた）。規範の意味は変えていない。根拠は #844 の記録（`plugins/dev-workflow/changes/844.md` の「『件数の条件が残っていない』とは、2 件以上という条件が無いことを指す」、archive 済みの `2026-10-08-epic-route-single-child-orca` の design.md 決定 1 と tasks.md 4.1）と、同じ要件が子 0 件を `subagent` と定めていること。経緯は `openspec/changes/archive/2026-10-09-epic-route-doc-zero-children/`
- 触った SKILL.md の範囲は「経路の決め方」の段落だけ。Orca 経路の手順 2〜4 と `reap` / `wait` は触っていない
