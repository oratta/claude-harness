# epic-dispatch: reap が PR を作らず issue を閉じた子のワークツリーも片付ける（#1045）

PR を伴わない記録先 issue の子（調査だけの issue など）は、issue を閉じて `mark done` しても、`reap` の確認 7（マージ済み PR の先端と HEAD の一致）で必ず外れ、`kept <N> no-merged-pr` か `kept <N> head-mismatch` でワークツリーが残り続けていた。親エピック #1038 の子。

- `scripts/epic-dispatch.sh reap`: 確認 7 で一致する行が無く HEAD が取れた子について、従来の理由を出す前に次を順に確かめる。(1) `gh pr list --head <ブランチ> --state all` が空（1 件でも PR があれば従来の理由。読めなければ `pr-lookup-failed`）、(2) `gh api repos/{owner}/{repo}/issues/<N> --jq .state` が `closed`（開いていれば従来の理由。読めなければ `issue-lookup-failed`）、(3) `git ls-remote origin refs/heads/<base>` で取ったリモートの今の先端に HEAD が含まれる（`git merge-base --is-ancestor`）。全部通れば既存の close → `--force` なしの rm → ブランチ削除の手順で片付ける
- `<base>` は環境変数 `EPIC_DISPATCH_BASE`（launch と同じ。既定 `main`）
- 新しい `kept` の理由: `unmerged-commits`（main に入っていない commit がある）、`issue-lookup-failed`、`base-lookup-failed`（ls-remote が読めない、または先端の commit が fetch のあとも手元に無い）。祖先を判定できない失敗は既存の `git-failed`
- 判定の相手は手元の追跡参照ではなく ls-remote の今の先端。base が force push で巻き戻されても、巻き戻しで消えた commit を持つ子は残る。ls-remote と fetch は reap 1 回につき最大 1 回ずつ（先端の commit が手元に無いときだけ fetch）
- issue の `state_reason` は見ない。マージ済み PR で一致した子の動きは変えない
- `skills/develop/SKILL.md`「ループの終わり」: PR を伴わない記録先 issue の項に、親の `reap` が片付ける条件と `unmerged-commits` で残ることを 1 文足した
- 受け入れること: commit を積んで PR を作らずに閉じた子は `unmerged-commits` で残る（オーナーが手で扱う）。`--base` で main 以外から起動した親が `EPIC_DISPATCH_BASE` を設定していなければ、PR の無い子は残る。ls-remote から rm までの数秒の間の base の巻き戻しは止めない
- 戻し方: この PR の差分を戻す。状態ファイルや設定の移行は要らない
