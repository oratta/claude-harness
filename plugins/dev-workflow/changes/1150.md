# dev-workflow: 大きい会話の子は待ち時間によらず起動し直す（#1150）

- `wait --resolve` が通す返事は、子の会話量 `context_tokens` が `EPIC_DISPATCH_RELAUNCH_FORCE_TOKENS`（未設定時 150000）以上なら、最後の assistant からの経過時間と `compact_boundary` の有無によらず起動し直す。#1323 の時間条件（`EPIC_DISPATCH_RELAUNCH_IDLE_SEC`、未設定時 3600 秒以上）も独立した OR 条件として維持する。短時間で 149999 なら通常送信、150000 / 150001 なら起動し直す
- 新変数で会話量閾値を上書きできる。数字だけの非負整数を受け付け、0 も可。空・負数・単位付きの値は、有効な `--resolve` が待つ前に変数名と使い方を出して exit 1。廃止した `EPIC_DISPATCH_RELAUNCH_MIN_TOKENS` は引き続き検査せず無視する
- 会話量は既存の `subagent-context.sh --file` の JSON を使い、exit 0 と 2 の `context_tokens` を比較する。最後の有効な assistant usage の input・cache_creation・cache_read の合計で、出力・累計・compact 前のピーク値は使わない。末尾の API エラーや全部 0 の usage を飛ばす既存の計測に従う。サブエージェント用の上限や `over_cap` は判定に使わない
- トランスクリプトが無い・複数・読めない場合は通常送信する。会話量の計測失敗は時間条件を妨げず、時刻不明でも会話量条件が真なら起動し直す。両方とも真と確認できなければ通常送信（端末が無い場合は既存の送信処理で起動し直す）
- 150000 は [#1046 の完了した再集計](https://github.com/oratta/claude-harness/issues/1046#issuecomment-6358891346) の結論に揃えた。起動し直しの平均費用は入力換算 270k、従来の費用比較の境目は 135k で、150k との差を標本の揺れの範囲として維持した。この集計はキャッシュ有効中の新条件の最適値を実証していない。大きい会話の繰り返し読み込みと判断品質への初期設定として採用し、後の計測で変更できる。120000 は自動コンパクト用なので転用しない
- `reply-after-idle.md` の子の表に、端末が無い行の次、時間の行の前に会話量の行を追加。起動し直す際は既存の `/develop #<child>` と停止の記録からの再開を使う。送れたあとにエピックへ記録し、待ち受けの stdout の契約を維持する
- 親の表と値、#1324 のキャッシュ維持の声かけ・親の短い待ち直し、#1085 の CI の見張り再開は対象外。版は上げない
- 戻し方: この変更の会話量判定・子の表・対応テストの差分を戻す。#1323 の独立した時間条件は残す
