# issue が目的として書いた効果をリスク宣言で聞き直さない（#723）

pr-review-gate 手順 3 は、資格情報・安全ゲートの弱体化・エージェント権限の拡張に当たる PR を一律に「主のリスク許容が必要」とし、手順 6 で `needs-approval` を付けて主の返事を待っていた。主が自分で書いたか承認した issue が、まさにその効果を目的にしている場合でも、PR のたびに同じ許容を聞き直されていた。主の手数を減らすため、issue が目的として書いた効果は「issue で承認済み」として聞き直さず、合格後に 1 回だけ事後報告するようにした。

- `skills/pr-review-gate/declarations.md` 手順 3: 「issue で承認済み」の節を足した。第 3 の宣言文ではなく、「主のリスク許容が必要」の宣言に 3 行（目的の引用・承認の証拠・真正性確認）を追記した状態で、宣言本文は書き換えない。追記の行頭は `主の回答: 許容` にしない（3-c の引き継ぎの元に拾われないため）。表の「主のリスク許容が必要」の後続に「issue で承認済みなら手順 4 へ」を足し、出口に試す順（前の HEAD の主の直接の許容があれば 3-c の引き継ぎ → issue で承認済み → 手順 6。先に当たったほうだけを追記する）を書いた
- `skills/pr-review-gate/stages/pass.md` 手順 5: 合格条件の表に「issue で承認済み」の行を足した。G は追記を読むだけで通さず、`owner-reply-check.sh` を回し直して条件を確かめ直し、`確かめ直し: 済 — 確認者 <エージェント名> / <日時>（手順 5）` を 1 行追記する（`真正性確認: 済` の行は足さない。3-c の「前の宣言の選び方」が見る行を増やさないため）。合格したら宣言の URL・引用・分類を主に 1 回で伝える。develop の G は passed の return に `issue で承認済み:` の行を足す
- `skills/pr-review-gate/stages/hold.md`: 「issue で承認済み」の宣言は保留に入らず、3-c の引き継ぎの元にもしない（HEAD が動いたら新しい HEAD で判定し直す）。条件を満たさずに主へ聞くときは、満たさなかった条件を依頼に添える
- `skills/develop/SKILL.md` (4): G の return に `issue で承認済み:` の行があれば、本体が CI の見張りを始める前に主へ 1 回伝える（auto-merge 配備リポではマージまで主との会話が起きないので、本体の手順に無いと報告が起きない）
- テストは `plugins/dev-workflow/tests/pr-review-gate-skill.bats` の `issue approved (#723):`

**当てられるのは 3 分類だけ。** 資格情報への接触・安全ゲートの弱体化・エージェント権限の拡張に限る。外部公開面の変化・データ喪失・課金/法務・プロダクトのユーザーに及ぶ影響は、issue に書いてあっても従来どおり主に聞く。宣言の該当する観点にこの 4 分類が 1 つでも混ざる、または引用の付かない分類があれば、宣言全体を手順 6 で聞く。

**承認の証拠は会話ログで取る。** 証拠は 2 形で、どちらも `owner-reply-check.sh` の終了コード 0 と `MATCH:` の全文で確かめる。

- 主が自分で打った `/develop <番号>`: `<command-args>` の直後が `<番号>` か `#<番号>` で、その後ろが空白か `</command-args>`（`7234` の中の `723` を通さない）。`EPIC_DISPATCH_PARENT_EPIC` が空でないセッション（Orca の親が子に打ち込んだもの）と、`--unmanned` を含む `/develop` は数えない
- 起票の承認: 起票したセッション S で、issue の URL が最初に現れる行より前の主の最後の発言。S は、URL を含む会話ログのうち、URL の初出行が `gh issue create` か `gh api -X POST repos/<R>/issues` の tool_result であるものだけにする（issue を参照しただけのセッションを取り違えないため）。`<command-name>` を含む行は使わない。主がエピックの起票を承認した発言は、同じセッションで続けて起票された子の証拠になるが、別のセッションで親が自動で起こした子の証拠にはならない

**起票の承認は、返事が答えた提案と結び付けて確かめる（#802 をこの PR で取り込んだ）。** PR #801 のゲートのレビューで、URL の初出行より前の主の最後の発言をそのまま証拠にすると、「README の誤字修正を起票しますか」への「OK、起票して」のあとにエージェントが安全ゲートを撤去する issue を起票した場合も証拠になりうる、という指摘が出た（`owner-reply-check.sh` は発言の実在だけを見て、何への返事かは見ない）。follow-up の #802 として切ったが、主の判断でこの PR の中で直した。主の最後の発言は候補にとどめ、返事が答えた起票の提案を会話から特定し、その提案が issue の目的と引用した各効果をすべて含むときだけ証拠にする。特定できない・含まないなら手順 6 で主に聞く。同じセッションで続けて起票したエピックの子は、子の目的と効果が承認された提案の範囲内であることを条件にした。反映先は `declarations.md` の「起票の承認」（負例と正例を書いた）、`stages/pass.md` 手順 5 の確かめ直し、`openspec/specs/dev-workflow-pr-review-gate/spec.md`（シナリオ 2 件を追加）。照合は意味の読み取りなのでスクリプトにせず G が会話を読んで行い、`owner-reply-check.sh` の挙動は変えていない。openspec の change は新しく切らず、archive 済みの main spec を直接直した（判断の記録は issue #723 のコメント）。テストは `pr-review-gate-skill.bats` の `issue approved (#802):`。

どちらの形でも、issue 本文の `lastEditedAt` が null か証拠の発言より前であることを求める。`agent-proposed` が付いた issue、主の承認の記録が無いままエージェントが起こした issue、保留や却下と読める発言には当てない。

**当たらない経路。**

- 別の PC で起票した issue: 起票したセッションの会話ログがゲートの PC に無いと S の候補が 0 件になり、起票の承認の証拠は使えない。`/develop` の証拠が無ければ従来どおり主に聞く
- 無人運用（loop-dev-agent の憲法がレビューモードで回すゲート）と、主に事後報告を届ける先が無い経路（メインセッションで主と会話していない・develop の G でもない）: 条件を満たしても当てず、手順 6 で保留にする。主が気づく保証が無いまま無人でゲートを緩める経路を増やさないため
- `/develop` のあとに issue 本文が編集された場合: `lastEditedAt` の条件で `/develop` の証拠が使えなくなる。W が着手時に受け入れ条件を直す運用があるので、主に聞く側に倒れることが多いかもしれない。安全側なのでこのままにしている

**この PR 自体が安全ゲートの弱体化に当たる。** 資格情報・安全ゲート・エージェント権限に当たる変更が、主が PR を一度も見ないまま合格し main に入る機会が増える。事後報告で後から気づけるが、事前には止まらない。主は 2026-10-07 の会話でこのリスクを受け入れた（issue #723 の備考）。外に及ぶ 4 分類は対象外のまま残している。証拠 `/develop` は、Orca 以外の仕組みが `EPIC_DISPATCH_PARENT_EPIC` を付けずに本体のターミナルへ打ち込んだ `/develop` を主の打ち込みと区別できない（#721 と同じ守備範囲の限界）。
