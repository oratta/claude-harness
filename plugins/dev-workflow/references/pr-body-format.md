# PR / issue 本文フォーマット（pr-body-format）

エージェントが書く PR 本文の型。読者は 2 種類いる: **人間**（承認判断のために冒頭だけ読む）と
**別セッションの LLM**（引き継ぎ・現状把握のために全文読む）。この二重読者を「書き分け」ではなく
**順序と粒度**で両立させる — 上から「判断に必要な順」に置けば、人間は途中で読むのをやめられ、
LLM は全文読むので順序で損しない。

出典: issue oratta/claude-harness#47（設計判断 D-1〜D-5 と外部調査の記録）。
2026-08-13 改訂（主のフィードバック）: 「起こりうる事象の羅列は起きやすさと影響が加味されておらず
読まれない」「実装方針が見えない」「PR の目的だけではプロジェクトの中での位置づけが分からない」
→ 位置づけ節・実装方針節を新設し、リスクを重み付きの表に変更した。

## 設計原則（MUST）

1. **順序が全て**: 下記 5 セクションの順序を入れ替えない。
2. **同じ情報を 2 回書かない**: 人間版/機械版の二重管理をしない（乖離の温床）。Git trailer 等の機械可読メタデータも持たせない。
3. **上から降りる**: 承認者はそのプロジェクトの全体像を頭に入れていない前提で書く。「位置づけ」は
   プロダクトの目的 → この PR が担う部分 → 起きる変化、の 3 段で降りる。
4. **翻訳の規律**: 位置づけに技術用語を出さない。機構名ではなく**発生する事象**を書く（例は後述）。
5. **リスクは重み付き**: 「起こりうる」の羅列を書かない。起きやすさ（高/中/低＋根拠一言）と
   起きたときの影響範囲を必ず添え、重い順に並べる。「なし」と書く場合も根拠を 1 行添える
   （例: 追加のみで既存経路を通らないため）。根拠のない空欄・重みのない羅列は承認判断ができない。
6. **上限を守る**: 各セクションのコメントに記した行数・項目数の上限を超える内容は issue へ切り出す。
7. **誇張の禁止（検証紐付け）**: 「位置づけ」に書く変化は、**動作確認ポイントで検証できないことを書いてはならない**。主張と検証手順を 1:1 で紐付ける。

## PR 本文の型（5 セクション + 任意の折りたたみ）

```markdown
## 位置づけ
<!-- 3行で上から降りる（承認者はプロジェクト全体を頭に入れていない前提）:
     1行目: このプロダクト/リポが目指していること（この PR に関係する範囲で）
     2行目: その中でこの PR が担う部分（どの課題・どのフェーズの話か）
     3行目: この PR で利用者に何が起きるか。技術用語禁止・機構名でなく発生する事象で書く。
            利用者影響がなければ「利用者影響なし」＋何のコストが下がるかを1行 -->

## 実装方針
<!-- どういうやり方で変えるか 1〜2 行＋捨てた代案とその理由 1 行。
     diff を読むときの道しるべになる粒度。ファイル・関数の列挙はしない（diff から読める） -->

## リスク（重い順）
<!-- 承認者にとってのコスト欄。「テストが通った」は答えになっていない。
     起きやすさは 高/中/低＋根拠一言。最大5行、超える分は issue へ切り出す。
     「なし」と書く場合は根拠を1行添える -->
| 起きうること | 起きやすさ | 起きたときの影響 | 戻し方 |
|---|---|---|---|
| | | | |

## 動作確認ポイント
<!-- チェックリスト形式。上のセクションと1:1で対応させる:
     ①「位置づけ」3行目の変化が本当に起きるか確かめる操作
     ②「リスク」の各行が現実化していないか確かめる操作
     各項目は「操作 → 期待される結果」の形。URL・コマンド・画面名を具体的に。 -->
- [ ] <操作> → <期待される結果>

## 実装メモ
<!-- ここから下は主に引き継ぐエージェント向け。ただし折りたたまない。
     制約 / 残課題 / 主要な変更ファイル。最大10行。
     設計判断の理由は「実装方針」に書き、ここに重複させない（diff から読めることも書かない）。 -->

Closes #<番号>

<details><summary>検証ログ</summary>
<!-- テスト出力・ビルドログなど再生成可能なものだけをここに入れる。
     設計判断・制約・却下した代案は絶対に折りたたみに入れない
     （<details> を開かず素通りする LLM 実装があり、引き継ぎの理解欠落を生むため）。 -->
</details>
```

## 翻訳の良い例 / 悪い例

機構名ではなく発生する事象を書く。3 組とも「悪い方は嘘ではないが、承認判断の役に立たない」例である。

1. ❌「楽観ロックを実装した」
   ✅「2 人が同時に同じ予定を編集したとき、後から保存した側が前の変更を無言で上書きしていたのが、警告が出て止まるようになる」
2. ❌「N+1 クエリを解消した」
   ✅「一覧ページの表示が項目数に比例して遅くなっていたのが、項目数に関係なくほぼ一定時間で開くようになる」
3. ❌「CI のキャッシュキーを修正した」
   ✅「利用者影響なし。PR ごとに毎回フルビルドしていた分の CI 待ち時間（約 n 分）が下がる」

リスクの重み付けも同じ規律で書く。

- ❌「stat の方言差で落ちる可能性がある」（起きやすさも影響も不明 → 読まれない）
- ✅「stat の方言差で Linux CI が落ちる | 低（CI で検証済み） | CI 赤のみ・本番影響なし | revert 一発」

## 軽量モード

小さな PR にフル 5 節を強制すると「特になし」の埋め草が並び形骸化する。以下の**すべて**を満たす場合に限り、
「位置づけ」＋「動作確認ポイント」の 2 節のみの軽量モードを使ってよい:

- 振る舞いの変更がない（typo・コメント・docs のみ・フォーマットのみ・振る舞い不変のリファクタ・依存バージョン上げのみ）
- 失敗しても戻し方が自明（revert 一発で完全に元に戻る）

発動はエージェントの自己判断とし、適用した PR は**冒頭に「軽量モード適用（理由: …）」を 1 行明記する（MUST）**。
この理由行が導入後評価（過剰軽量化の監査）の対象になる。**迷ったらフル 5 節を書く**（安全側に倒す）。

## issue 本文の型

issue は既存 4 節（概要 / 触るファイル・関数 / 受け入れ条件 / 備考）の**先頭**に承認判断用の 2 節を足した 6 節構成:

```markdown
## これで何が変わるか          <!-- 最大3行・技術用語禁止（翻訳の規律は PR と同じ) -->
## やらないとどうなるか / 今のコスト  <!-- 着手優先度の判断材料。最大3行 -->
## 概要
## 触るファイル・関数
## 受け入れ条件（測定可能な形で）
## 備考
```

生成ロジックの正本は `plugins/dev-workflow/skills/issueify/SKILL.md`。各リポにインストールされる
issue テンプレート（`.github/ISSUE_TEMPLATE/agent-task.md` 等）は flatmate の `new-resident` が配り、この 6 節に従う。

## 承認を求めるコメント

PR / issue 上の議論コメントはフォーマット対象外。ただし**人間に承認を求めるコメント**だけは
「何を承認してほしいか / 承認した場合の影響 / しない場合の代替」の 3 行を必須とする。
