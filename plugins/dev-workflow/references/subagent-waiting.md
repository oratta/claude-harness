# サブエージェントの待ち方（dev-workflow の共有契約）

長時間処理（Codex レビュー・フルテスト・ビルド）の完了を、サブエージェントがどう待つかの正本。読み手は develop の W / R1 / G と `skills/pr-review-gate/SKILL.md` を読むサブエージェント。各指示書は禁止そのものを 1 行で持ち、詳しい待ち方が要るときだけこのファイルを開く。

## 禁止と許可

**完了を待つ目的でターンを終えてはならない。** 名前付き background サブエージェントは idle になっても、自分が起動した背景タスクの完了では再起動されない。完了通知はキューに積まれるだけで新しいターンを起こさないので、「完了したら続きをやる」と書いてターンを終えると、親が SendMessage を送るまで止まる（2026-09-08 に G が 5 回止まり、合計約 4 時間の停止をオーナーの一言で毎回起こした）。

| | |
|---|---|
| 禁止 | 待ちを背景タスクの完了通知に委ねること・Monitor ツールに委ねること・`run_in_background` の「完了したら続きが動く」挙動に頼ること |
| 許可 | 10 分を超えうる処理を `run_in_background` で**起動**すること・待ちループの中の `sleep` |

禁止されるのは待ち方であって起動方法ではない。Codex レビューは前景 1 回では起動から完了まで到達できないので、起動は background のままにし、**完了の確認だけを同一ターン内の前景ポーリングで行う**。

**この禁止はサブエージェントに限られる。** メインセッション（本体）は背景タスクの完了で再起動されるので、`--background` 起動 ＋ 完了通知で続行してよい。

## 待ちループ（前景・有限）

待ち値は **Bash ツール呼び出しの `timeout` パラメータ（ミリ秒）** に指定する。シェルの `timeout(1)` コマンドは使わない（単位が秒で違ううえ、macOS の既定には GNU 版が無く `gtimeout` になるため環境依存になる）。Bash ツールの前景上限は 600000 ms なので、上限ちょうどを指定するとループの後処理ごと切られる。dev-workflow の既定は **540000 ms（9 分）** で 1 分の余裕を残す。

Bash ツールの入力はこの形になる:

```
command: until grep -q '__CODEX_DONE__' "$out"; do sleep 10; done
timeout: 540000
```

行頭の裸の長時間 `sleep` はハーネスに拒否されるが、ループ内の `sleep` は許可される（`until [ ... ]; do sleep 1; done` が前景で完走することを実測済み）。将来ループ内の `sleep` まで拒否されるようになったら、ポーリング間隔を短く刻んで Bash 呼び出しの回数を増やす形に替える。

**長い待ちに入る前に、これから最大何分待つか（1 回あたり 9 分・上限 27 分）を出力してからループに入る。** その間はサブエージェントがブロックされ、親からの SendMessage も処理されないため。

## 完了シグナル（起動経路ごと）

`codex exec` も `codex-companion.mjs` も出力に完了マーカーを書かないので、マーカーは起動側で付ける。検知方法を自分で発明しない。

**(a) `codex exec` 直叩き** — 起動コマンドにマーカーを書き足し、そのマーカーの出現を終了条件にする。`rc=` の値で成否を判定する。

```bash
# 起動（Bash ツールの run_in_background: true）
{ codex exec -c approval_policy=never -c model_reasoning_effort=medium "<レビュー指示>" ; echo "__CODEX_DONE__ rc=$?" ; } >> "$out" 2>&1
```

```
# 待ち（Bash ツールの前景実行）
command: until grep -q '__CODEX_DONE__' "$out"; do sleep 10; done; tail -n 200 "$out"
timeout: 540000
```

**(b) `codex-companion.mjs` 経由** — `status <job-id> --wait --timeout-ms 540000` の exit code と status 出力を終了条件にする。出力ファイルの中身を推測しない。タイムアウトで返ったのか完了で返ったのかは exit code で区別する。

```
command: node "<companion のパス>" status <job-id> --wait --timeout-ms 540000; echo "rc=$?"
timeout: 540000
```

`--timeout-ms` の既定は 4 分しかないので必ず明示する。

## 総待ちの上限と超過時の分岐

**1 回の Bash 呼び出しはターンの終わりではない。** 1 回で完了しなければ、同じ呼び出しをもう一度発行して待ちを継続する。

**上限は前景ループ 3 回（540000 ms × 3 = 27 分）。** 上限なしに待ち続けない（ジョブが死んで出力が来ない場合と、単に時間がかかっている場合を区別できなくなるため）。27 分の根拠は Codex レビューの実測が 10 分超であることと `model_reasoning_effort=medium` の規約で、足りなければ回数だけを変える。

上限に達したら待ちをやめ、役割ごとの分岐に入る:

- **G**: `needs-reviewer` を return し、根拠に「Codex タイムアウト（27 分）」と書く。**これが `skills/pr-review-gate/SKILL.md` のフォールバック条件「未導入・サブスク切れ・タイムアウト」の「タイムアウト」の定義**で、この上限がフォールバックの発火点になる
- **W / R1**: 待ちをやめて本体に return する（どこまでやってどこで止まったかを書く）
