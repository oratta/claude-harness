# レシピ: loop-dev-agent

> GitHub Issues をタスクキューにした常設の自律開発ループ。レビュー → 修正 → 実装 → 提案の状態機械を
> 1サイクル1仕事で回す。プロジェクト固有の値はすべて対象リポジトリの `docs/agent-loop.md`（憲法ファイル）に
> 外出しし、起動コマンドは全プロジェクト共通の1行になる。
> 導入は `/loops:dev-agent-install`、憲法の雛形は `plugins/loops/templates/agent-loop-template.md`、
> 規約は `plugins/loops/references/recipe-format.md` を参照。

## ループ型

**タイムベース**（4 分類: ターンベース / ゴールベース / タイムベース / プロアクティブ のうち）。
一定間隔で発火し、その時点のリポジトリ状態（レビュー待ち PR・不合格 PR・実行可能 issue・空）から
1サイクルの仕事を自分で選ぶ。起動タイミングを手放したいので `/loop` を使う。
選定基準は `references/loop-types.md` の「トリガー（起動タイミング）を手放す」に従う。

## 目的

人間が寝ている間・離席中も開発を前進させる。人間の関与を「issue へのラベル付け（承認）」と
「レビュー合格済み PR のマージ」の2点に絞り、それ以外（実装・動作確認・レビュー・タスク提案）を
ループに委ねる。実装エージェントと独立したレビュー段階を挟むことで、人間のマージ判断を
「レポートを読んで diff を流し見する」まで軽くし、レビュー・マージのボトルネック化を防ぐ。

前者の「承認」も、**本当に人間にしか下せない判断だけ**に絞る。憲法の3軸ゲート
（①成果物が PR になり止められるか ②人間の判断が要る論点が無いか ③取り消せるか）を満たす `needs-approval` issue は
ループが自分で `agent-ready` へ昇格させる。人間の手元に残るのは、不可逆な操作と、方針を選ぶ判断だけになる。

## 起動コマンド

このレシピは**実行方法非依存**（`references/loop-types.md`「実行機構との責務分離」）。同じ1サイクル手順書
（`docs/agent-loop.md`）を、以下 2 つの配線のどちらから回してもよい。**どちらも最終的に投げるプロンプトは同じ**
（「`docs/agent-loop.md` を読み1サイクルを厳密に実行して結果を報告する」）で、違いは「誰がいつ発火するか」と
「レートガードをどこで判定するか」だけ。

### 配線1: flatmate 常駐（常設・推奨）

flatmate（セッション常駐ハーネス）の住人としてループを回す。実行系の配線一式は flatmate 側の責務であり、
このプラグインはスケジューラ登録・hook・clone 運用に踏み込まない（`references/loop-types.md` の責務分離に従う）:

- flatmate リポで `setup-dev.sh <agent> --repo <path>` を実行して住人を生成する（住人ごとに専用 clone を持ち、
  セッションの cwd はその住人の `repo/`）。
- flatmate の `cron-jobs.md` に登録された `[tick]` ジョブが毎時 1 サイクル分のプロンプト
  （`[tick] docs/agent-loop.md を読み1サイクル実行し結果を報告して`）を投げる。
- **レートガードは flatmate 側の `UserPromptSubmit` rate-guard hook が肩代わり**する（`[tick]` の発火前に判定し、
  SKIP はゼロトークン。閾値は flatmate の環境変数 `RATE_5H_MAX` / `RATE_5H_HEADROOM` / `RATE_7D_MAX` /
  `RATE_7D_HEADROOM`、デフォルト 70/20/85/10）。したがって憲法（`docs/agent-loop.md`）の Step 0 はスキップされる前提。
- **7 日失効の克服**: `/loop` の 7 日自然失効は、常駐ジョブの自己リアームで乗り越える（人間の手動再起動が不要）。

### 配線2: /loop（手元アドホック）

今日この場で数時間だけ回したいときは、現行どおりネイティブプリミティブ `/loop`（ローカル）で起動する。
推奨はランチャーコマンド（対象リポジトリのルートで起動する。事前チェック付きで正規の `/loop` 文字列を組み立てて起動する）:

```
/loops:dev-agent-start        # デフォルト間隔 1h
/loops:dev-agent-start 2h     # 間隔を変える場合
```

ランチャーが組み立てる正規の `/loop` 文字列（手動でコピペしてもよい。一次ソースはこの節）:

```
/loop 1h docs/agent-loop.md を読み、そこに定義された1サイクルを厳密に実行して。結果（実行モード、対象の issue/PR 番号、スキップ・提案の場合はその理由）を必ず報告して
```

この配線では発火前 hook が無いため、**レートガードは憲法の Step 0**（サイクル冒頭の jq 判定・環境変数閾値）が担う。

### 両配線共通

- 実行系はネイティブプリミティブ（`/loop` ローカル or flatmate のセッション内 cron）に委ね、**独自 CLI やラッパースクリプトは作らない**
  （`/loops:dev-agent-start` は /loop に渡す文字列の組み立てと事前チェックだけを行うランチャーで、実行系ではない）。
- **実行間隔のデフォルトは 1h**（1サイクル = 実装またはレビュー1件分の作業量のため、分単位の高頻度は不要）。
  - **間隔の変更方法**: 配線1 は flatmate の `[tick]` ジョブ間隔、配線2 はランチャー引数（例: `/loops:dev-agent-start 2h`）
    またはコマンド文字列先頭の `1h` を書き換える。30 分より短くしない（頻度最小化）。
- プロジェクト固有の設定（テストコマンド・ブラウザ検証の有無・レート閾値など）は起動コマンドではなく
  `docs/agent-loop.md` 側を書き換えて変更する。

## 停止基準

- **明示キャンセル**: 常設ループのため、基本の終了は人間による `/loop` のキャンセル操作。
  `/loop` は 7 日で自然失効するので、継続する場合は人間が再起動する（無期限に走り続けない）。
- **サイクル単位のスキップ（レートガード）**: `~/.claude/.rate-limit-snapshot` の
  `five_hour_pct` / `seven_day_pct` を**枠の経過率に連動した動的閾値**
  （`min(ハードキャップ, 枠の経過率% + ヘッドルーム)`。デフォルトはハードキャップ 70% / 85%、
  ヘッドルーム +20pt / +10pt）と比較し、超えていたらそのサイクルは何もせず状況報告のみで終了する。
  同じ使用率でも枠の序盤（残り時間が長い）ほど厳しく、終盤ほどハードキャップまで緩む。
  `resets_at` が取れない枠はハードキャップのみで判定する。
  **ガードの実装位置は実行系（配線）によって変わる**: 配線1（flatmate 常駐）では `[tick]` 発火前の
  rate-guard hook が判定し（SKIP はゼロトークン）、配線2（単独 /loop）では憲法の Step 0 が
  サイクル冒頭の jq で判定する。いずれも閾値は環境変数（`RATE_5H_MAX` / `RATE_5H_HEADROOM` /
  `RATE_7D_MAX` / `RATE_7D_HEADROOM`）で解決し、同じ閾値観を共有する。
- **タスク単位の隔離**: 同一 issue / PR で 2 回失敗したら `agent-blocked` に切り替えて以後拾わない
  （同じ失敗の無限反復を検知して止める）。
- **無進捗時の縮退**: レビュー待ちも実行可能 issue もなく、かつ未トリアージ提案がストック上限
  （デフォルト 3 件）に達している場合、新しい仕事を作らず報告のみで終了する。
- 対象 PR のマージ・クローズは人間が行い、ループはそれを検知して次の仕事に移る（PR 単位の完了）。

## 前提

- **`dev-workflow` プラグインの導入が必要**: Step 3（実装モード）は開発の中身（opsx 仕様化要否と判断の記録・単一/複数 change 判定・仕様レビュー・TDD 実装）を `dev-workflow` プラグインの `develop` スキルに委譲する。委譲の形は「憲法のメインが develop の本体（オーケストレータ）として W / R1 を spawn する」であり、Step 3 をサブエージェントに丸投げしない（サブエージェントは孫を起こせないため）。ラベル操作・Draft PR 作成・Review Queue 連携などの無人運用の外形は引き続き本レシピが担う。人間がオンデマンドで issue に取り組む場合も同じスキルを `/develop`（旧 `/work-issue`）から使う（`dev-workflow/README.md` 参照）。
- **配備済みの憲法（`docs/agent-loop.md`）はテンプレート更新後に `/loops:dev-agent-install` で再生成が必要**: 再生成するまで旧スキル名を Skill ツールで呼ぼうとして失敗し、失敗コメント → `agent-blocked` のセーフティネットに落ちる（無言では壊れない）。
- **ローカル実行が必要**: レートガードがローカルの `~/.claude/.rate-limit-snapshot`
  （statusline が毎ターン更新する JSON）を読むため。
- `/loops:dev-agent-install` による導入が完了していること。具体的には対象リポジトリに:
  - `docs/agent-loop.md`（憲法ファイル。状態機械・ラベル定義・プロジェクト設定を含む）
  - GitHub ラベル一式（`agent-ready` / `agent-proposed` / `agent-wip` / `agent-blocked` /
    `needs-approval` / `human-only` / `size:large` / `agent-review:pending` / `agent-review:passed` / `agent-review:failed`）
  - permission deny ルール（main へのマージ・push・force 系の封鎖）と pre-push フック
    （main 直 push の拒否に加え、**マージ済み PR のブランチへの push も拒否**する。
    マージ後に残った worktree で作業を再開してもコミットが宙に浮かない）
  - issue テンプレート（測定可能な受け入れ条件を必須化）
- タスクの投入は `/loops:issueify` が支援する（書き殴り・既存バックログ・TODO コメントを、
  原子化 + 測定可能な受け入れ条件付きの issue に変換して起票するまでフォローする）。
- `gh` CLI が使え、対象リポジトリの issue / PR にアクセスできること。
- （任意）**Review Queue 連携**: 複数リポジトリで本ループを並行稼働させる場合、ユーザーレベルの
  GitHub Project「Review Queue」に**人間待ちの PR と issue の両方**（マージ判断待ち PR・
  トリアージ待ち提案・要介入の隔離 issue）を自動登録し、人間の判断をボード1枚に集約できる
  （`gh` トークンに `project` scope が必要。導入は `/loops:dev-agent-install` が行い、
  横断ビューの閲覧は `/loops:review-queue` を使う）。ブロッカーの優先度は GitHub ネイティブの
  issue dependencies（blocked by / blocking）と Blocked count フィールドで可視化する。
- 権限モードが acceptEdits 以上（無人サイクル中に権限プロンプトで止まらないこと）。
- worktree 運用（1 issue = 1 worktree = 1 ブランチ = 1 Draft PR）。

## コスト注意

公式トークン管理の該当項目:
- **実行頻度を必要最小限にする**: デフォルト 1h。夜間だけ回したい場合は就寝前に起動し起床後にキャンセルする。
  レートガードにより枠の残量が少ないときは自動でサイクルをスキップする。
- **決定論的作業のスクリプト化**: issue / PR の取得・ラベル操作は `gh` コマンドで決定論的に行い、
  LLM には実装・レビュー・判断のみを任せる。
- **大規模実行前のパイロット実行**: 初回は 1〜2 サイクルを人間が見ている状態で回し、
  ラベル運用と worktree 作成が意図どおり動くことを確認してから無人化する。
- ループはチャットの約 4 倍のトークンを消費する。レビューモードは実装と独立に検証を再実行するため
  1 タスクあたりのコストは約 2 倍になる。その対価はレビュー検出率で測定し、
  検出率がほぼ 0% ならレビュー段階を外す（憲法ファイルの実行ログで集計できる）。

## エスカレーション

**外向きアクションは非破壊デフォルト（feature ブランチへの push・Draft PR 作成/更新・issue / PR コメント・ラベル操作まで）**。以下は行わず、人間へ引き渡す:

- **マージしない**（deny ルールで封鎖。合格 PR は `agent-review:passed` を付けて人間のマージ判断を待つ）。
- **main への直接 push をしない**（deny ルール + pre-push フックで封鎖）。
- **マージ済み PR のブランチへ push しない**（pre-push フックで封鎖。open な PR が無いブランチへの
  push は行き場が無いため、新しいブランチを切って Draft PR を作り直す）。
- force push・PR クローズ・ブランチ削除・rebase などの不可逆操作もしない（main 追従は
  ブランチへのマージ方式で行い、force push を必要としない）。
- 同一 issue / PR で 2 回失敗 → `agent-blocked` にして経緯をコメントし、人間の判断を待つ。
- 自己生成タスクは `agent-proposed` の起票まで。実行の可否は人間のラベル付けに委ねる。
- 朝ダイジェスト（マージ待ち件数・提案ストック・隔離件数・レビュー検出率）で、人間が対応すべき
  滞留を毎日可視化する。
