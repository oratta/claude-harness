# レシピ: loop-dev-agent

> GitHub Issues をタスクキューにした常設の自律開発ループ。レビュー → 修正 → 実装 → 提案の状態機械を
> 1サイクル1仕事で回す。プロジェクト固有の値はすべて対象リポジトリの `docs/agent-loop.md`（憲法ファイル）に
> 外出しし、起動コマンドは全プロジェクト共通の1行になる。
> 導入は `/loops:dev-agent-install`、憲法の雛形は `plugins/loops/templates/agent-loop-template.md`、
> 規約は `plugins/loops/references/recipe-format.md` を参照。

## ループ型

**タイムベース**（4 分類: ターンベース / ゴールベース / タイムベース / プロアクティブ のうち）。
一定間隔で発火し、その時点のリポジトリ状態（レビュー待ち PR・不合格 PR・実行可能 issue・空）から
1サイクルの仕事を自分で選ぶ。起動タイミングを手放したいので `/loop` を使う。
選定基準は `references/loop-types.md` の「トリガー（起動タイミング）を手放す」に従う。

## 目的

人間が寝ている間・離席中も開発を前進させる。人間の関与を「issue へのラベル付け（承認）」と
「レビュー合格済み PR のマージ」の2点に絞り、それ以外（実装・動作確認・レビュー・タスク提案）を
ループに委ねる。実装エージェントと独立したレビュー段階を挟むことで、人間のマージ判断を
「レポートを読んで diff を流し見する」まで軽くし、レビュー・マージのボトルネック化を防ぐ。

## 起動コマンド

コピペ可能な `/loop` 文字列（対象リポジトリのルートで起動する）:

```
/loop 1h docs/agent-loop.md を読み、そこに定義された1サイクルを厳密に実行して。結果（実行モード、対象の issue/PR 番号、スキップ・提案の場合はその理由）を必ず報告して
```

- 起動コマンドはネイティブプリミティブ `/loop`（ローカル）のみ。**独自 CLI やラッパースクリプトは作らない**。
- **実行間隔のデフォルトは 1h**（1サイクル = 実装またはレビュー1件分の作業量のため、分単位の高頻度は不要）。
  - **間隔の変更方法**: コマンド文字列先頭の `1h` を書き換える（例: `2h`）。30 分より短くしない（頻度最小化）。
- プロジェクト固有の設定（テストコマンド・ブラウザ検証の有無・レート閾値など）は起動コマンドではなく
  `docs/agent-loop.md` 側を書き換えて変更する。

## 停止基準

- **明示キャンセル**: 常設ループのため、基本の終了は人間による `/loop` のキャンセル操作。
  `/loop` は 7 日で自然失効するので、継続する場合は人間が再起動する（無期限に走り続けない）。
- **サイクル単位のスキップ（レートガード）**: `~/.claude/.rate-limit-snapshot` の
  `five_hour_pct` / `seven_day_pct` が憲法ファイルの閾値（デフォルト 70% / 85%）を超えていたら、
  そのサイクルは何もせず状況報告のみで終了する。
- **タスク単位の隔離**: 同一 issue / PR で 2 回失敗したら `agent-blocked` に切り替えて以後拾わない
  （同じ失敗の無限反復を検知して止める）。
- **無進捗時の縮退**: レビュー待ちも実行可能 issue もなく、かつ未トリアージ提案がストック上限
  （デフォルト 3 件）に達している場合、新しい仕事を作らず報告のみで終了する。
- 対象 PR のマージ・クローズは人間が行い、ループはそれを検知して次の仕事に移る（PR 単位の完了）。

## 前提

- **ローカル実行が必要**: レートガードがローカルの `~/.claude/.rate-limit-snapshot`
  （statusline が毎ターン更新する JSON）を読むため。
- `/loops:dev-agent-install` による導入が完了していること。具体的には対象リポジトリに:
  - `docs/agent-loop.md`（憲法ファイル。状態機械・ラベル定義・プロジェクト設定を含む）
  - GitHub ラベル一式（`agent-ready` / `agent-proposed` / `agent-wip` / `agent-blocked` /
    `needs-approval` / `human-only` / `size:large` / `agent-review:pending` / `agent-review:passed` / `agent-review:failed`）
  - permission deny ルール（main へのマージ・push・force 系の封鎖）と pre-push フック
  - issue テンプレート（測定可能な受け入れ条件を必須化）
- `gh` CLI が使え、対象リポジトリの issue / PR にアクセスできること。
- 権限モードが acceptEdits 以上（無人サイクル中に権限プロンプトで止まらないこと）。
- worktree 運用（1 issue = 1 worktree = 1 ブランチ = 1 Draft PR）。

## コスト注意

公式トークン管理の該当項目:
- **実行頻度を必要最小限にする**: デフォルト 1h。夜間だけ回したい場合は就寝前に起動し起床後にキャンセルする。
  レートガードにより枠の残量が少ないときは自動でサイクルをスキップする。
- **決定論的作業のスクリプト化**: issue / PR の取得・ラベル操作は `gh` コマンドで決定論的に行い、
  LLM には実装・レビュー・判断のみを任せる。
- **大規模実行前のパイロット実行**: 初回は 1〜2 サイクルを人間が見ている状態で回し、
  ラベル運用と worktree 作成が意図どおり動くことを確認してから無人化する。
- ループはチャットの約 4 倍のトークンを消費する。レビューモードは実装と独立に検証を再実行するため
  1 タスクあたりのコストは約 2 倍になる。その対価はレビュー検出率で測定し、
  検出率がほぼ 0% ならレビュー段階を外す（憲法ファイルの実行ログで集計できる）。

## エスカレーション

**外向きアクションは非破壊デフォルト（feature ブランチへの push・Draft PR 作成/更新・issue / PR コメント・ラベル操作まで）**。以下は行わず、人間へ引き渡す:

- **マージしない**（deny ルールで封鎖。合格 PR は `agent-review:passed` を付けて人間のマージ判断を待つ）。
- **main への直接 push をしない**（deny ルール + pre-push フックで封鎖）。
- force push・PR クローズ・ブランチ削除・rebase などの不可逆操作もしない（main 追従は
  ブランチへのマージ方式で行い、force push を必要としない）。
- 同一 issue / PR で 2 回失敗 → `agent-blocked` にして経緯をコメントし、人間の判断を待つ。
- 自己生成タスクは `agent-proposed` の起票まで。実行の可否は人間のラベル付けに委ねる。
- 朝ダイジェスト（マージ待ち件数・提案ストック・隔離件数・レビュー検出率）で、人間が対応すべき
  滞留を毎日可視化する。
