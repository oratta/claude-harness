# /loops:design — 設計されたループのレシピを対話で書き出す

このスキルは、Anthropic 公式記事「Getting started with loops」（claude.com, 2026-06-30）の路線に沿って、
ユーザーの業務を **4 ループタイプのどれか**にマッピングし、レシピ形式規約に準拠した設計図（`recipes/<name>.md`）を
書き出す。**独自のループ実行系は作らない**。反復・スケジュール・停止判定はネイティブプリミティブ
（/goal の最大試行・/loop / /schedule のキャンセル・Workflow の budget）に委ねる。

必ず `references/loop-types.md`（4 タイプ表と選択フレームワーク）と `references/recipe-format.md`（7 見出し規約）を
読んでから設計に入ること。

## 設計思想

- ループを設計せよ。エンジニアであり続けよ。設計を「考えることの回避」に使わない。
- 「完了は主張であり証明ではない」。全ループは evidence（テスト出力・exit code・生成物の実在）で成功を判定する設計にする。
- 安全性（暴走・課金・不可逆アクション防止）＞公式路線への忠実さ＞シンプルさ の優先順位で判断する。

## フロー

### Step 1: 選択フレームワーク「何を手放すか」でループ型を選ぶ

ユーザーにインタビューし、**手放す対象**を特定してループ型を 1 つ選定する。対応は以下:

| 手放す対象 | 選ぶループ型 | 対応プリミティブ |
|---|---|---|
| **検証ステップ**（完了判定を任せたい。人間が都度起動） | **ターンベース** | skill の自己検証 |
| **停止条件**（達成まで自律反復） | **ゴールベース** | /goal |
| **トリガー**（起動タイミングも手放す） | **タイムベース** | /loop・/schedule |
| **プロンプト自体**（人間不在で仕事を見つけて回す） | **プロアクティブ** | /schedule + /goal + 動的ワークフロー + オートモード の合成 |

選定フロー:
1. 完了判定だけ手放したい → **ターンベース**
2. 停止条件まで手放したい → **ゴールベース**
3. 起動タイミングも手放したい → **タイムベース**
4. プロンプトすること自体を手放したい → **プロアクティブ**

判断に迷ったら `references/loop-types.md` の表と具体例（PR 面倒見=タイムベース、テスト全 PASS まで=ゴールベース）に立ち返る。

### Step 2: 停止基準を確定する（必須ゲート）

**停止基準が確定するまでレシピを出力してはならない（MUST NOT）。** 停止基準は次のいずれか 1 つ以上:

- **最大試行数**（例: `stop after 5 tries`）
- **時間**（例: 5 分間隔で N サイクル、または明示的キャンセルまで）
- **定量ゴール**（機械検証可能な終了条件。例: 「全 bats PASS」「Lighthouse 90 以上」）

ユーザーが停止基準を提示しないまま書き出しを求めた場合は、**レシピを出力せず**、停止基準
（最大試行数 / 時間 / 定量ゴール）の指定を求めるヒアリングを続ける。これは出力前の**必須チェック**である。

### Step 3: Bad Loop 検査（出力前に必ず実施）

レシピを書き出す前に、以下 4 項目を検査する:

1. **停止基準の欠如** — 停止条件が無い / 曖昧
2. **検証なき成功宣告** — evidence（テスト・exit code・生成物）なしで「完了」を宣言する設計になっていないか
3. **報酬ハッキング余地** — 成功基準が主観的・改竄可能（「良くなったら」等）になっていないか
4. **過剰な実行頻度** — トークン爆発を招く高頻度になっていないか（ループはチャットの約 4 倍、マルチエージェントは約 15 倍）

いずれかに該当したら、**該当項目と修正案をユーザーに提示**し、修正してから再設計する。そのままの出力は行わない。

### Step 4: レシピ形式規約に準拠して書き出す

`references/recipe-format.md` の固定見出し **7 項目**をこの順ですべて持つ `recipes/<name>.md` を書き出す:

1. **ループ型** 2. **目的** 3. **起動コマンド** 4. **停止基準** 5. **前提** 6. **コスト注意** 7. **エスカレーション**

制約:
- 「**起動コマンド**」は **/goal・/loop・/schedule・skill 起動** のいずれかのコピペ可能な文字列で書く。
  **独自 CLI・ラッパースクリプトの新設を提案してはならない（MUST NOT）**。
- 実行機構への配線（スケジューラ登録・セッション運用・課金選択）はレシピに書かない。これは呼び出し側の責務。
  レシピが宣言するのは「発火時プロンプト / 推奨頻度 / 停止基準 / 実行環境の制約」まで。
- テンプレートは `templates/recipe-template.md` を使う。

## 完了時の自己検証（evidence を提示してから完了を宣言する）

- 書き出した `recipes/<name>.md` を Grep し、7 見出しがすべて存在することを確認してから完了を報告する。
- 「起動コマンド」節が /goal・/loop・/schedule・skill 起動のいずれかであり、独自 CLI への言及が無いことを確認する。
