# /loops:issueify — タスクを「ループが実行できる issue」に変換する

自律開発ループ（`recipes/loop-dev-agent.md`）の実装モードは、**測定可能な受け入れ条件が無い issue を拾わない**。
このスキルは「タスクはあるが issue 化と受け入れ条件の定義がハードルになる」問題を埋める:
人間は書き殴るだけでよく、原子化・受け入れ条件の機械検証可能化・触るファイルの特定・起票までをスキルが担う。

受け入れ条件の作り方は `skills/loops-goalify/SKILL.md` の方法論（成功基準の機械検証可能化・
不足だけを最小限ヒアリング）を転用する。issue の品質はループの成功率を最も左右する
（スコープ・コンテキスト・解決方向・粒度が揃った issue は PR マージ率を大きく上げる実証がある）。

## 入力（4モード）

`/loops:issueify <引数>` の引数で分岐する:

1. **インラインテキスト** — 書き殴りのタスクメモを直接解析する
2. **ファイルパス** — バックログ md・TODO リスト・handoff ドキュメント等を読み、未完了タスクを抽出する
3. **引数なし（自動発見 = プロジェクトのタスク総ざらい）** — リポジトリから候補を集めて一括処理する。
   タスク管理を issue でやっていないプロジェクトを丸ごと issue 運用に載せ替えるときの入口はこれ:
   - `docs/` とルート直下の md にある未チェックのチェックボックス（`- [ ]`）→ **新規起票**
   - コード中の `TODO` / `FIXME` コメント（`git grep -n "TODO\|FIXME"`）→ **新規起票**
   - 受け入れ条件セクションが無い、またはラベルの無い open issue（`gh issue list`）→ **本文を補筆**
   発見した候補は種別を問わず Step 1〜4 の同じフローに流し、最終的にすべてが
   「測定可能な受け入れ条件付き・ラベル付きの issue」という単一フォーマットに揃う。
4. **`--existing`（既存 issue の補強のみ）** — 3 のうち既存 open issue の補筆だけを行う狭いモード
   （`gh issue edit`。新規起票はしない）

## フロー

### Step 1: 原子化

入力を **1 issue = 1 論理タスク**に分解する。複数の変更がバンドルされた項目は分割し、
1サイクル（実装〜Draft PR まで）に収まらない規模のものは `size:large` 候補として分割案も添える。

### Step 2: 各タスクのドラフト生成

タスクごとに issue テンプレート（`.github/ISSUE_TEMPLATE/agent-task.md`）の構造でドラフトを作る
（先頭 2 節は人間の承認・優先度判断用。翻訳の規律は `references/pr-body-format.md` を参照）:

- **これで何が変わるか** — 最大 3 行・技術用語禁止。機構名ではなく発生する事象を書く
- **やらないとどうなるか / 今のコスト** — 着手優先度の判断材料。最大 3 行
- **概要** — 1〜3 行。何を・なぜ
- **触るファイル・関数** — codebase を Grep / Glob して当たりを付け、実在するパスを書く（推定なら推定と明記）
- **受け入れ条件（測定可能な形で）** — goalify の方法論で**実行コマンド + 期待値**に変換する:
  - テスト: `<テストコマンド>` が exit 0（新規テストを書くべき場合はテスト名まで指定）
  - API: `curl` 等での呼び出しとステータス・レスポンスの期待値
  - UI: 「ページ X に Y が表示され、操作 Z で W になる」のようにブラウザで再現可能な手順
  - 成果物: ファイルの実在・サイズ・grep での確認コマンド
- **備考** — 依存する issue、前提、参考リンク

**機械検証に変換できない項目は受け入れ条件に書かない**。「良くなる」「きれいになる」等の
主観基準はヒアリングで具体化するか、備考に落とす。

### Step 3: 不足だけヒアリング

ドラフトに埋められなかった箇所（スコープの曖昧さ・期待値の選択肢・優先度）**だけ**を
AskUserQuestion でまとめて質問する（MUST）。導出できた項目は質問しない（MUST NOT）。
全ドラフトが完成している場合は質問 0 問で Step 4 へ。

### Step 4: 確認と起票

1. 全ドラフトを一覧表示する（タイトル・受け入れ条件・提案ラベル）。
2. ラベルの提案基準:
   - ループ単独で完結できる → `agent-ready` を提案
   - 実行に人間の承認・不可逆操作が絡む → `needs-approval`
   - 秘密情報・外部アカウント・ダッシュボード操作 → `human-only`
   - 1サイクルに収まらない → `size:large`
3. ユーザーの承認を得てから `gh issue create`（`--existing` モードは `gh issue edit`）で反映する。
   **ユーザーがこの場で承認した分は直接 `agent-ready` を付けてよい**（このスキルの対話自体が
   人間ゲートを兼ねるため）。ユーザーが「あとで見る」と言った分は `agent-proposed` で起票する。
   起票後、issue 間に実行順の依存（「#A が終わらないと #B に着手できない」）があるものは、
   備考への記述だけでなく **GitHub ネイティブの issue dependencies を張る**:
   `gh api -X POST repos/<owner>/<repo>/issues/<後続の番号>/dependencies/blocked_by -F issue_id=<前提issueのid>`
   （id は `gh api repos/<owner>/<repo>/issues/<番号> --jq .id`）。これにより loop-dev-agent は
   ブロックされた issue を拾わなくなり、Review Queue ボードには Blocked アイコンと
   Blocked count（ブロッカーの優先度シグナル）が自動で乗る。
4. 元ファイルから移行した場合は、元ファイルに「issue へ移行済み（#番号）」の注記を追記する
   （削除はしない）。

### Step 5: 完了レポート

起票・補筆した issue の一覧（番号・タイトル・ラベル）と、`agent-ready` の件数
（= 次のループサイクルで実行可能になったタスク数）を報告する。

## してはならないこと

- 受け入れ条件の無い issue を起票しない（このスキルの存在意義に反する）
- ユーザーの確認なしに issue を起票・編集しない（Step 4 の承認が必須）
- タスクの実行はしない（起票まで。実行は loop-dev-agent の仕事）
- 既存 issue のクローズ・ラベル剥がしはしない（補筆と追加のみ）
