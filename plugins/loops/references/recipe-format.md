# レシピ形式規約（recipe-format）

このリポジトリの「設計されたループ」は、`recipes/<name>.md` という 1 枚の Markdown で宣言する。
レシピは**人間とエージェントが読む設計図**であり、それ自体はランタイムを持たない。反復・スケジュール・停止判定は
ネイティブプリミティブ（/goal の最大試行・/loop / /schedule のキャンセル・Workflow の budget）に委ねる。

出典: 公式記事「Getting started with loops」（claude.com, 2026-06-30）。4 タイプの説明は `references/loop-types.md` を参照。

## 固定見出し 7 項目（MUST）

すべてのレシピは以下 7 つの見出しをこの順で持たなければならない。

### 1. ループ型

公式 4 分類（**ターンベース / ゴールベース / タイムベース / プロアクティブ**）のいずれか 1 つを明記する。
どれを選ぶかの基準は `references/loop-types.md` の選択フレームワーク（「何を手放すか」）に従う。

### 2. 目的

このループが何を達成するのか、なぜ人手ではなくループにするのかを 1〜3 行で書く。

### 3. 起動コマンド

**ネイティブプリミティブのコピペ可能な文字列を第一級の成果物とする**。すなわち `/goal ...`・`/loop ...`・
`/schedule ...`・skill 起動（`/loops:design` など）のいずれかを、そのまま貼り付けて動く形で書く。
**独自 CLI やラッパースクリプトを新設してはならない（MUST NOT）**。決定論的な前処理が必要なら既存スクリプト
（例: daily-report の jq パイプライン）を参照するに留め、ループを回すための driver は作らない。

### 4. 停止基準（必須）

**停止基準は必須項目である（MUST）**。以下のいずれか 1 つ以上を必ず含む:

- **最大試行数**（例: `stop after 5 tries`）
- **時間**（例: 5 分間隔で N サイクル、または明示的キャンセルまで）
- **定量ゴール**（例: 「全 bats PASS」「Lighthouse スコア 90 以上」など機械検証可能な終了条件）

停止基準を持たないレシピは規約違反であり、`/loops:design` はそれを出力しない。
複数の独立した出口（ゴール達成 / 予算切れ / 反復上限 / 無進捗検出）を書けるとより堅牢。

### 5. 前提

このループが依存する skill・設定・データ・環境（例: `gh` CLI、Draft PR 運用、参照パス）を列挙する。

### 6. コスト注意

公式トークン管理 6 項目のうち該当するものを書く（頻度最小化・決定論部分のスクリプト化・大規模実行前のパイロット等）。
「ループはチャットの約 4 倍、マルチエージェント構成は約 15 倍」というコスト倍率を意識する。

### 7. エスカレーション

回復不能なエラー・不可逆な操作（merge / close / force 系）・2 連続失敗などで、人間へ引き渡す条件を書く。
外向きアクションは非破壊デフォルト（Draft PR / issue コメントまで）とし、不可逆操作はここでエスカレーションに倒す。

## 実行機構への配線に踏み込まない（インターフェース宣言の範囲）

レシピが宣言する実行インターフェースは、以下の **4 項目まで**とする（MUST）:

1. **発火時に投入するプロンプト**（起動コマンドの本体）
2. **推奨頻度**（例: 日次 / 5〜10 分 / 週 1）
3. **停止基準**
4. **実行環境の制約**（例: ローカルの `~/.claude/projects/` jsonl を読むループはローカル実行が必要）

**スケジューラへの登録方法・セッション運用・課金選択の記載をレシピに要求してはならない（MUST NOT）**。
これらは**スコープ外**であり、**呼び出し側の責務**である（定期実行の配線は別セッションの Pikke プロセス整理側が担う）。
レシピは実行方法非依存に書く。

## 機械検証はしない（MVP スコープ）

レシピ形式は **Markdown 見出し規約のみ**とし、JSON Schema 等による機械検証を要求してはならない（MUST NOT）。
schema 化・機械検証（loop-audit 相当）は必要になってから backlog で対応する。
