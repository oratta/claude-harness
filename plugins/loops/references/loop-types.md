# 公式 4 ループタイプ 選択リファレンス（loop-types）

出典: 公式記事「**Getting started with loops**」（claude.com, Claude Code チーム, 2026-06-30）。
本文書は `research/loop-engineering.md` 冒頭の公式記事セクションを配布物化したもの。迷ったら公式記事に立ち返る。

> ループ = 「停止条件に達するまでエージェントが仕事を繰り返すサイクル」。
> 公式の立場: **ループのランタイムはネイティブプリミティブ（skill / /goal / /loop / /schedule / workflows / auto mode）であり、ループはその合成で作る**。独自のループ実行系は再発明しない。

## 選択フレームワーク: 「何を手放すか」

ループ型ごとに、人間が手放す対象が異なる。設計の第一歩は「このループで何を手放すか」を決めること。

| ループ型 | 手放す対象 | トリガー | 停止 | 対応するネイティブプリミティブ | 使い分け（どういう業務に選ぶか） | 具体例 |
|---|---|---|---|---|---|---|
| **ターンベース** | **検証ステップ** | ユーザープロンプト | タスク完了 | **skill の自己検証**（SKILL.md に検証ステップを組み込む） | 探索・判断が要る単発タスク。人間が都度起動するが、完了判定をエージェントに任せたい | フロントエンド変更後に dev サーバー起動→ブラウザで操作確認→コンソールエラーなしを確認 |
| **ゴールベース** | **停止条件** | 手動プロンプト | ゴール達成 or 最大試行数 | **/goal**（別のエバリュエータモデルが成功基準を判定） | 検証可能な終了基準があるタスク。基準達成まで自律反復させたい | テスト全 PASS まで（`/goal ... stop after 5 tries`）、Lighthouse スコア 90 以上まで |
| **タイムベース** | **トリガー** | 時間間隔 | キャンセル or 完了 | **/loop**（ローカル）・**/schedule**（クラウド） | 定期的・外部システム連携。いつ起動するかを手放したい | PR 面倒見（`/loop 5m check my PR, address review comments, and fix failing CI`）、日次レポート |
| **プロアクティブ** | **プロンプト自体** | イベント/スケジュール（人間不在） | タスク毎はゴール達成、ルーチンは手動キャンセルまで | **/schedule + /goal + 動的ワークフロー + オートモード の合成** | バグ分類・マイグレーション・依存更新などの定常業務。人間不在で回したい | `/schedule every hour: check feedback for bug reports. /goal: don't stop until every report found this run is triaged` |

### 選定フロー（`/loops:design` が使う）

1. **完了判定だけ手放したい**（人間が都度起動する）→ **ターンベース**（skill に検証ステップを組み込む）
2. **停止条件まで手放したい**（達成まで自律反復）→ **ゴールベース**（/goal + 機械検証可能な成功基準）
3. **起動タイミングも手放したい**（定期実行）→ **タイムベース**（/loop・/schedule）
4. **プロンプトすること自体を手放したい**（人間不在で仕事を見つけて回す）→ **プロアクティブ**（合成）

具体例の対応: **PR 面倒見 = タイムベース**、**テスト全 PASS まで = ゴールベース**、**変更の自己検証 = ターンベース**、**backlog 消化 = プロアクティブ**。

## コード品質維持（公式ベストプラクティス）

1. コードベース自体をクリーンに保つ（Claude は既存パターンに従う）
2. skill に自己検証メカニズムを明示する（ターンベースの最適化）
3. フレームワークの最新ベストプラクティスへのアクセスを確保
4. **第二エージェントによるレビュー**（/code-review skill 等。自分の成果物を自分で採点させない）
5. 個別修正をシステム全体の改善にフィードバックする

## Bad Loop（設計時に避ける 4 兆候）

- **停止基準の欠如**（最も一般的な失敗）
- **検証なき成功宣告**（「完了」は主張であり証明ではない）
- **報酬ハッキング余地**（成功基準が主観的・改竄可能）
- **過剰な実行頻度**（トークン爆発。ループはチャットの約 4 倍、マルチエージェントは約 15 倍）

## 実行機構との責務分離

**このプラグイン（loops）と各レシピは、どう定期実行するかには踏み込まない。**

レシピが宣言する実行インターフェースは、以下の **4 項目まで**とする:

1. **発火時に投入するプロンプト**
2. **推奨頻度**
3. **停止基準**
4. **実行環境の制約**（例: ローカルの `~/.claude/projects/` jsonl を読むループはローカル実行が必要）

一方で、**スケジューラへの登録・セッション運用・課金選択は loops プラグインおよびレシピのスコープ外であり、
呼び出し側の責務**である（定期実行の機構・配線一式は別セッションの Pikke プロセス整理側が担う）。
したがってレシピは**実行方法非依存**に書く。`claude -p` で仕込むか、セッション内 cron で回すか、手動起動するかは
レシピの関心事ではない。この分離により、実行基盤が変わってもレシピ本体は書き換え不要になる。
