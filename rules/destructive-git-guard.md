# 破壊的 git 操作の禁止

実事故から生まれたルール。「元に戻すだけ」という自己正当化が再犯パターン。

## ルール

1. 破壊的操作は**例外なく事前承認**。「元に戻すだけ」も破壊的操作。
2. interrupt 直後は原状回復に走らず**現状報告が先**（`git status` / `git diff` を見せてから聞く）。
3. 承認は可否だけでなく**タイミングと方法まで**確認して完了。「消していい」と言われても、いつ・どうやって消すかまで確認する。

## 頭に浮かんだ瞬間、実行ではなく質問に変換するコマンド

- `git checkout -- <path>` / `git restore <path>`（作業破棄）
- `git reset --hard` / `git clean -f`
- `git commit --amend`（push 済み）/ `git rebase -i`
- `git push <remote> main|master`（remote 名を問わない） / `git push --force[-with-lease]`
- `git branch -D`
- `--no-verify` / `--no-gpg-sign`

「戻すだけ」「消すだけ」「一瞬で終わる」と思ったら、承認を飛ばそうとしているサイン。手を止めて聞く。

## 承認の記録と確認

投稿者名はエージェントも同じなので承認の根拠にしない。主の判断を GitHub に記録するとき、`記録者: エージェント（<名前>）` と出どころを書く。この表記のある記録と伝聞は承認とみなさない。手順: dev-workflow の `references/approval-provenance.md`。

## hook との分担

dev-workflow の hook が入っていれば、一覧のうち push 済みの `--amend` と `rebase -i` 以外を 実行前に止める（対話セッションでは確認画面）。止まったら言い換えず主に聞く。サブエージェントと無人のセッション（起動時に無人の印を付けたもの）では確認画面なしで拒否されるので、子は打ち直さず親に返り、無人のセッションはチャンネルで主に承認を求める。拒否・確認画面なしのときは、承認後も主が自分で実行する（入力欄の `!` か主の端末）。hook はコマンド文字列しか見ないので、push 済みの `git commit --amend`・`git rebase -i`・ブランチ名を書かない `git push`・スクリプト経由の git は止まらない。これらと、hook が入っていない環境での一覧の操作は、このルールだけが止める。
